# Подключение проекта к devkit

Порядок команд для двух сценариев: обычный проект (код и доска в одном
репозитории) и проект корп-контура (чужой репозиторий, куда ничего нашего не
уезжает). Здесь только последовательность, разбор каждой команды в README
утилит: [devkitctl](tools/devkitctl/README.md), [taskctl](tools/taskctl/README.md),
[shipctl](tools/shipctl/README.md), [trackctl](tools/trackctl/README.md).

Каждое подключение заканчивается списком «осталось сделать»: команда сама
называет файлы и ключи, которые за человека не заполнить. Если список пуст, она
это тоже говорит.

## Один раз на машину

```bash
git clone https://github.com/dronrider/devkit.git ~/projects/devkit && python3 ~/projects/devkit/tools/devkitctl/devkitctl.py update --pin
```

Строка одна и делает всё: клон и установку. Шага у неё два, и разделены они не
случайно. Клон лежит рядом с проектами и остаётся на виду, потому что в него
ведёт ссылка `.devkit/devkit` каждого подключённого проекта, через которую тот
зовёт правила, а раз путь виден человеку, выбирает его человек, а не
установщик. `update` доводит остальное сам, и
тулчейна ему не нужно: переводит клон на новейший релизный тег, качает тарболл
своей платформы, сверяет сумму, кладёт бинари утилит и обёртку `devkitctl` в
каталог назначения (`~/go/bin`, если он уже в PATH, иначе `~/.local/bin`) и
раскладывает машинный контур, то есть хуки харнеса и права сессии в
`~/.claude/settings.json`, определения субагентов, скиллы и глобальную точку
правил.

Бутстрапа вида `curl | sh` тут нет и не будет, разбор в
[docs/lld/DK-149-binary-delivery.md](docs/lld/DK-149-binary-delivery.md):
он был бы второй точкой входа с той же работой, выбирал бы путь клона молча и
ставил бы devkit ровно тем способом, от которого devkit уходит. Клон в другое
место значит другой путь во второй половине строки, больше ничего.

Ключ `--pin` нужен ровно один раз: свежий клон стоит на `main`, и перевод его
на тег человек разрешает явно. Дальше чекаут отвязан, и обновление идёт голым
`devkitctl update`, а спросить, вышло ли новое, можно `devkitctl update --check`.

Что она сделала, команда рассказывает построчно, и однотипное считает, а не
перечисляет строка за строкой: сколько утилит установлено и куда, сколько
скиллов и определений субагентов, сколько хуков включено. Недостающее
из того, что ставится пакетным менеджером (`tmux`, `terminal-notifier`), она
ставит сама: раз человек позвал установку, ходить за этими двумя пакетами ему
незачем.

Команда заканчивает списком «осталось сделать»: каталог назначения мимо PATH и
прочее, чего за человека не сделать, например пакет, которого нечем поставить,
когда пакетного менеджера на машине нет. Пустой список она тоже называет.
Снимка квоты в этом списке обычно нет: его снимает хук `SessionStart` при
первой же сессии, и звать за ним человека незачем. Появляется он там ровно
тогда, когда снять снимок нечем, то есть на той же машине без пакетного
менеджера: без tmux хуку не с чего прочитать панель `/usage`, и находка эту
причину называет. Проверка
после установки это `devkitctl doctor`; гоняется он из чекаута devkit, поэтому
в отчёте идут и находки по самому devkit, машинные помечены словом «машина».

Доктор сверяет раскладку, а не работу: жив ли конвейер целиком, проверяет
`devkitctl selfcheck`. Команда заводит временный проект и прогоняет в нём
настоящий круг: строка на доске, вердикт pick, ветка задачи, слияние с тестами
и подставным выкатом, закрытие. Каждый шаг отчитывается отдельной строкой,
конец внятный: «связка жива» либо «шаг такой-то не прошёл» с выводом шага.
Настоящие проекты и дом не трогаются: утилиты devkit пишут в `~/.devkit` и без
ведома вызвавшего, поэтому круг даёт сабпроцессам свой временный дом, а за
собой убирает всё.

## Обычный проект

```bash
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py new -C ~/projects/myproj --prefix MP
```

Кладёт `AGENTS.md`, заводит доску `docs/TASKS.md` с префиксом ID `MP`,
подключает git-хуки и болванку выката. Директории ещё нет, она не под git или в
репозитории ни одного коммита, значит команда доводит всё это сама: отдельных
шагов подготовки у подключения нет. Готовый проект она берёт как есть. Префикс
выбирается коротким и своим, чужих ID на доске нет.

```bash
$EDITOR ~/projects/myproj/.devkit/deploy.local
```

Вписать `test =` (команда общего тест-набора) и `deploy =` (команда выката).
Файл гитигнорнут и живёт только на машине.

```bash
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py doctor -C ~/projects/myproj
```

Проверка обвязки: по проекту находок нет значит он подключён.

```bash
taskctl -C ~/projects/myproj add --title "первая задача" --type task --rank "25+5+1+0+0" --cost S
shipctl -C ~/projects/myproj start MP-001
```

Задача заводится на доске и берётся в работу: `start` делает ветку и отдельное
рабочее дерево рядом с проектом.

## Проект корп-контура

```bash
git clone <корп-репозиторий> ~/projects/corp-proj
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py corp -C ~/projects/corp-proj \
    --contour corp --key ABC --remote <личный приватный remote доски>
```

Заводит боковую директорию `~/projects/corp-local/corp-proj` с доской, файлами
задач и привязкой к трекеру, а в клоне оставляет обвязку: ссылку `.devkit` на
эту директорию, редирект, тонкий файл контекста под `.git/info/exclude` и
обёртки хуков. В корп-репозиторий не уезжает ничего нашего.

Директория сбоку одна на весь контур, `~/projects/<контур>-local`, и проекты
лежат в ней подкаталогами. Репозиторий там тоже один, сколько бы клонов ни
было. Своё место называется флагом `--local <путь>`, а клоны, подключённые
раньше, остаются при прежней `~/projects/corp-proj-local`, и переезжать им
незачем.

Корп-проект работает в одном окне редактора. Доска открывается из клона путём
`.devkit/docs/TASKS.md`, её видят и поиск, и сессия агента. Ссылка нарочно не
спрятана строкой exclude. Поиск редактора читает те же источники игнора, что
git, и спрятанное от одного пропадает у другого. Ценой этого в `git status`
клона висит строка `?? .devkit`. В индекс она не уедет. Обёртка `pre-commit`
отбивает коммит, в чей индекс попала ссылка или тонкий файл, и говорит, чем
снять. Ссылку, потерянную после `git clean -xdf`, возвращает `devkitctl doctor
--fix`.

Первый прогон говорит, что доска и файлы задач лягут в боковую директорию, и
спрашивает недостающее прямо в терминале: префикс доски (предложен по имени
клона, пустой ответ значит согласие) и адрес трекера с именем пользователя для
нового контура компании. Секретов среди вопросов нет, токен приезжает
переменной окружения. Префикс, совпавший с ключом проекта в трекере `--key`,
команда не берёт и спрашивает заново: на совпавшей паре рубеж следов не
отличает локальный ID доски от ключа тикета и правило про ID снимает. Свой
префикс можно назвать сразу флагом `--prefix CB`, а под сессией агента и в CI,
где tty нет, вопросов не будет вовсе, и там флаги обязательны.

Контур компании один на все репозитории компании, второй раз про него не
спрашивают. Таблицу `[status]` в `~/.devkit/tracker/corp.local` стоит сверить
со статусами своего трекера: она положена заполненной обычными именами Jira.

```bash
export TRACKER_TOKEN=<токен трекера>
$EDITOR ~/projects/corp-local/corp-proj/.devkit/deploy.local
```

Имя переменной с токеном названо ключом `token_env` контура, сам токен в файлы
не пишется. В `deploy.local` вписать `test =`; выкат в корп-контуре ведёт
процесс компании, и `deploy =` там обычно пустой.

```bash
trackctl -C ~/projects/corp-proj sync
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py doctor -C ~/projects/corp-proj
trackctl -C ~/projects/corp-proj status
```

`sync` подтягивает статусы тикетов на доску, и он же ставит отметку свежести,
без которой доктор говорит про разошедшуюся доску. Дальше доктор проверяет
обвязку клона и боковой директории, а `status` говорит про трекер: контур,
адрес, токен на месте, статусы расписаны.

```bash
taskctl -C ~/projects/corp-proj add --title "первая задача" --type task --rank "25+5+1+0+0" --cost S --link "ABC-123"
shipctl -C ~/projects/corp-proj start CB-001
```

Строка доски зеркалит тикет: ключ стоит в ссылке, и по нему `start` заводит
ветку в корп-клоне. Локальный ID доски в ветки и коммиты чужого репозитория не
едет никогда.
