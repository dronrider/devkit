# Правила проектов с доской

Дополнение к `RULES.md` для проектов, где задачи ведутся на доске `docs/TASKS.md` (внешнего трекера нет). Проект подключает файл вторым импортом в своём `CLAUDE.md`:

```markdown
@../devkit/RULES.md
@../devkit/RULES.board.md
```

В корпоративном контуре файл не применяется: ревью и слияние там идут через MR, задачи живут в трекере (см. локальные дополнения в `RULES.md`).

## Ветки, ревью и деплой

1. Нужна ли фичеветка, определяется задачей. Мелочь (опечатка, правка доков, однокоммитный багфикс с тестом, подкрутка конфига) коммитится прямо в main. Полноценная фича и всё, что растягивается на несколько коммитов или подходов, делается в ветке с ID задачи строчными (`xr-043-deploy`). При сомнениях заводить ветку.
2. Ветка сливается в main только с зелёными тестами и после ревью. Ревью гоняет агент со свежим контекстом, не тот, что писал код (например, `/code-review` по диффу ветки против main). Мелочь, идущая в main напрямую, обязательного ревью не требует, её страхуют тесты.
3. Замечания ревью живут в файле задачи `docs/tasks/<ID>.md`, раздел «Ревью»: строка на замечание, суть и исход (исправлено или отклонено с причиной), по этим разделам копится статистика, что ревью реально ловит. Исправления коммитятся в ту же ветку, после них ревью прогоняется снова, до прохода без новых замечаний.
4. Слияние без merge-коммитов: ветка ребейзится на main и уходит fast-forward, история остаётся линейной.
5. Выкат. Слитая задача сразу деплоится на живую среду, механика выката у каждого проекта своя и живёт в проектном `CLAUDE.md` или плейбуке. После выката задача переводится в Check: сценарий проверки выполняется пользователем прямо на проде, отдельный статус для деплоя не заводится.
6. Выкаты строго последовательные. Следующее слияние с выкатом возможно, только когда предыдущая задеплоенная задача прошла Check и закрыта. Тестовых сред нет, прод один, поэтому непроверенная правка на нём в каждый момент максимум одна: если после выката что-то сломалось, источник очевиден. Мелочь, закоммиченная в main между выкатами, уезжает попутно со следующим.
7. Провал проверки. Если задеплоенная задача не прошла Check, прод чинится сразу: revert коммитов задачи (находятся по ID в subject) и повторный выкат, либо форвард-фикс, когда корень понятен. Задача возвращается в In progress, очередь стоит, пока прод не починен.
8. Слияние, пуш и выкат агент делает по явной команде пользователя, в остальном действует п. 3 раздела «Git» в `RULES.md`. Проект может в своём `CLAUDE.md` разрешить агенту деплоить самостоятельно после чистого ревью при пустой очереди.

## Трекинг задач (доска в репозитории)

Механику доски (завести строку, перевести статус, поменять тип или ранг, закрыть в архив, пересортировать, проверить инварианты, создать скелет в новом проекте) не делать руками, а гонять через `taskctl` из devkit: `init`/`add`/`move`/`set`/`close`/`sort`/`lint`/`id`, детали в `taskctl/README.md`. Думающая часть (заголовок, разбивка ранга, сценарий проверки) остаётся за исполнителем и передаётся аргументами. После ручных правок доски (если без них не обошлось) прогонять `taskctl lint`.

1. Доска. Три места: `docs/TASKS.md` (открытая работа), `docs/TASKS-archive.md` (сделанное) и `docs/tasks/` (файлы задач). TASKS.md это версионируемая канбан-доска и единственный источник правды по тому, что в работе; крупные проектные разборы остаются на своих местах (`docs/lld/`, гитигнорнутый `local-docs/`). Доска всё это только индексирует: описания не дублировать, в строке задачи короткий заголовок и ссылка.
2. Строка задачи. ID `PREFIX-NNN` (префикс проекта в шапке доски, номера сквозные по репозиторию и не переиспользуются), короткий заголовок (разросшийся заголовок это признак, что содержимому пора в файл задачи), тип `bug`/`task`/`LLD`, приоритет `P0`..`P3`, ранг `R`, ссылка. Приоритет не ставится на глаз, а выводится из ранга по `RANKING.md` (лежит рядом с этим файлом): в строке держится сумма R с разбивкой по пяти слагаемым, сумму и бакет P считает taskctl.
3. Файл задачи. `docs/tasks/<ID>.md`, имя по чистому ID. Заводится, когда появляется содержимое (разбор корня, DoD, сценарий проверки, ход работы): однострочному бэклогу файл не нужен, LLD-задачи ссылаются прямо на LLD без файла-прокладки. Метаданные (тип, приоритет, ранг, статус) живут только в доске и в файле не дублируются. При закрытии `taskctl close` переносит файл в `docs/tasks/archive/<год закрытия>/` тем же коммитом, поэтому `ls docs/tasks/` показывает открытую работу.
4. Статусы: `Backlog`, `In progress`, `Check`, `Blocked`. `Check` это контроль человеком: работа сделана, но задачу закрывает не агент, а пользователь после проверки по приложенному сценарию. В архив уезжает только прошедшее проверку, не прошедшее возвращается в In progress. Живой файл тогда не пухнет, его размер привязан к объёму открытой работы; архив append-only, растёт свободно.
5. Когда обновлять:
   - новую задачу заводить строкой в Backlog сразу, как она проявилась, в том числе баги, найденные по ходу другой работы (`taskctl add` сам ставит строку по рангу);
   - взятую в работу переводить в In progress;
   - на блокере ставить Blocked плюс одна строка почему;
   - доделанную задачу переводить в Check, приложив инструкцию проверки (п. 6);
   - после того как пользователь подтвердил проверку, закрывать через `taskctl close` с датой и коммитами.
6. Инструкция проверки. Перевод в Check возможен только когда готов сценарий, по которому пользователь подтвердит результат: шаги плюс ожидаемый итог. Для бага обязательны точные шаги воспроизведения и ожидаемое поведение, чтобы проверка показывала, что баг ушёл, а не просто что код поменялся. Сценарий держать не в доске, а в файле задачи (или в LLD, если проверка описана там), на него ссылается строка задачи.
7. Связь с гитом. ID задачи ставить в subject коммита там, где он уместен (`feat(core): XR-12 ...`). Тогда git-история и доска ссылаются друг на друга, а полная история закрытого остаётся в git, даже если строку из архива потом почистят.
8. Чувствительное ни в доску, ни в файлы задач не писать. IP, доступы, инфраструктура остаются в гитигнорнутом `local-docs`; в коммитируемых текстах вместо адреса писать роль машины («роутер DE», «VPS RU», «exit-IP timeweb»).
9. Синхронизация доски. Коммит, трогающий `docs/TASKS.md`, `docs/TASKS-archive.md` или `docs/tasks/`, ассистент пушит в origin сразу и самостоятельно, не дожидаясь просьбы (исключение из п. 3 раздела «Git» в `RULES.md`). Доска это общий источник правды, с ней параллельно работают люди и агенты, и отставший remote оборачивается конфликтами и потерянными строками. Пуш ветки уносит и предшествующие локальные коммиты кода: это осознанное следствие, откладывать их ради «чистого» пуша доски не надо, но в отчёте пользователю про них сказать.
