# agentctl: выбор исполнителя под задачу

Механизирует пункт «Выбор модели» из `RULES.board.md`. Сменить модель своей
сессии агент не может, этот рычаг харнес отдаёт пользователю; штатная дверь
это спавн субагента с явной моделью. agentctl и есть решатель для такого
делегирования: читает метаданные задачи с доски `docs/TASKS.md` и печатает
вердикт, сессия-диспетчер отдаёт работу субагенту с этой моделью.

У исполнения две оси: модель и reasoning effort. Вердикт называет обе, но
применяются они по-разному. Модель передаётся параметром при спавне субагента,
а effort от сессии не наследуется и параметра вызова у него нет: его задаёт
поле `effort` во frontmatter определения агента. Поэтому вторая строка вердикта
это выбор определения из набора `devkit/agents` (см. «Определения
исполнителей»).

Никакого ИИ внутри нет, маппинг детерминированный: всё нужное уже проставлено
на доске при грумминге (тип, цена, разбивка ранга, третье слагаемое которой
это неопределённость).

## Команда

```bash
agentctl pick DK-002
```

```text
model: haiku
effort: low
DK-002 (task, цена S, неопределённость 0): совсем атомарная правка с очевидным подходом, дешёвой модели хватает
```

Первые две строки машинно-читаемые (`model: haiku|sonnet|opus|fable` и
`effort: low|medium|high|xhigh|max`), третья для человека. Задача ищется по
всем секциям доски; если её нет, ненулевой код возврата и ошибка «нет на
доске». Общий флаг `-C <dir>` как у остальных инструментов: откуда искать
корень с `docs/TASKS.md`.

## Правила маппинга

Оси считаются порознь, но не совсем независимо: у модели есть свой пол
effort. Модель это калибр исполнителя, её задают тип и цена. Effort это
глубина размышления, её задаёт неопределённость, а у sonnet результат ещё
подтягивается вверх (см. «Effort» ниже). У opus эта свобода не отнята: на
рутинной правке он идёт с `low`, а на задаче с открытыми деталями с `medium`.

### Модель

Порядок значим, первое сработавшее правило решает:

| Условие | Модель | Смысл |
|---|---|---|
| тип LLD, цена L или XL | fable | сложное проектирование, fable делает его лучше opus |
| тип LLD (остальная цена) | opus | дизайн отдаётся сильной модели |
| неопределённость >= 4 | opus | сначала грумминг, исполнять рано |
| цена XL | opus | сначала разбить на серию, целиком не отдавать |
| цена S и неопределённость ровно 0 | haiku | совсем атомарная правка с очевидным подходом |
| цена S и неопределённость ровно 1 | sonnet | небольшая задача, подход уже выбран, дешёвая модель справится |
| остальное | opus | для дешёвых моделей не подходит, по умолчанию идёт сильной |

Под «остальное» попадают M на любой неопределённости, S с неопределённостью
2-3, L на любой неопределённости и неоценённая цена (вердикт тогда напоминает
про оценку). Раньше M с неопределённостью 0-1 доставалась sonnet, теперь и она
уходит в дефолт: экономить effort на дешёвой модели смысла нет, а средняя по
размеру задача заслуживает сильной. Причина в вердикте на эти случаи (кроме
неоценённой цены, у той своя) цену не называет: она не «M и выше», а просто
«не haiku и не sonnet», иначе на S с неопределённостью 2-3 звучала бы
неправдой. Нечитаемая разбивка
ранга (старая доска, прочерк) трактуется как неизвестность в пользу сильной
модели: ни haiku, ни sonnet по ней не выдаются, остаётся opus.

Вердикты opus про грумминг и разбивку это «исполнять рано», а не «исполнять
opus-ом»: сильная модель зовётся снимать неопределённость или резать задачу,
после чего pick даёт уже исполнительский вердикт по обновлённой строке.

### Effort

Уровень идёт за третьим слагаемым ранга по шкале неопределённости из
`RANKING.md`, порядок так же значим:

| Условие | Effort | Смысл |
|---|---|---|
| тип LLD, либо неопределённость >= 4, либо цена XL | xhigh | решение ещё не найдено, размышление это и есть работа |
| нечитаемая разбивка ранга или неоценённая цена | high | метаданным верить рано, осторожность в пользу глубины |
| неопределённость 0 | low | рутина, делалось много раз, размышлять не над чем |
| неопределённость 1-2 | medium | подход выбран, открыты детали |
| неопределённость 3 | high | в деталях есть развилки, размышление их окупает |

Верхний уровень исполнимой задаче не достаётся: неопределённость 4-5 это порог
готовности из `RANKING.md`, там вердикт и так грумминговый, а всё исполнимое
укладывается в 0-3. Так `xhigh` остаётся за проектированием и вердиктами
«исполнять рано». Цена в эту ось входит ровно двумя случаями. XL это разбивка,
то есть тот же «исполнять рано». Прочерк в цене значит, что грумминг не
доведён до конца, и нулю в третьем слагаемом доверия тогда не больше, чем
прочерку в ранге, поэтому оба случая идут на `high`. Уровень `max` маппингом не
выдаётся, он остаётся ручным решением через override-строку файла задачи.

У sonnet таблица выше не последнее слово: `low` и `medium` из неё поднимаются
до `high` полом, который висит на самой модели, а не на неопределённости.
Запросы sonnet стоят копейки, риск потерять качество на них есть, а экономия
на глубине размышления того не стоит. Пол срабатывает и когда sonnet пришла
override-строкой модели, а effort остался от обычного маппинга ниже high;
явная override-строка эффорта пол перебивает целиком, её значение берётся
как есть, хоть и `low`. В человеческой строке вердикта подтяжка видна коротким
хвостом причины («effort поднят до high: sonnet дёшев, экономить глубину
смысла нет»). На haiku пол не распространяется: у Haiku 4.5 параметр effort в
API не работает вовсе, его `low` остаётся формальной меткой, поднимать
нечего.

## Корректор по остатку лимитов

Таблица выше считает вердикт из метаданных задачи и ничего не знает про то,
сколько осталось от недельных лимитов подписки. Расход выходит нерациональным
в обе стороны: за день до сброса с нетронутым бакетом экономить незачем, а на
почти исчерпанном отдавать задачи дорогой модели неправильно. Корректор это
слой поверх маппинга: таблица не меняется, двигается её результат, максимум на
один ярус лестницы `haiku -> sonnet -> opus -> fable`. Дизайн разобран в
[DK-010](../docs/lld/DK-010-quota-corrector.md).

### Файл снимка

Остаток программно недоступен: `/usage` только интерактивный, расчёт серверный,
эндпоинта нет. Поэтому контрактом сделан файл снимка `~/.devkit/quota.local`,
который pick только читает (в сеть и в tmux он не ходит, детерминизм и скорость
прежние). Файл на уровне машины, а не проекта: лимиты общие на подписку.

```text
taken = 2026-07-30T14:20
week_all = 34% сброс 2026-08-04T10:00
week_opus = 78% сброс 2026-08-04T10:00
```

`taken` это момент снятия, дальше бакеты: процент потраченного и дата сброса.
Пятичасовой сессионный бакет не пишется, он протухает быстрее, чем живёт
задача. Известных ключей два, незнакомый игнорируется с предупреждением в
человеческой строке вердикта. Заполняется файл руками с панели `/usage` либо
командой `agentctl quota refresh`, формат один и тот же.

Из каких бакетов тратит ярус:

| Ярус | Бакеты |
|---|---|
| haiku, sonnet | week_all |
| opus, fable | week_all и week_opus сразу |

Своего бакета у fable панель пока не показывает; заведёт, и он добавится в
таблицу, формула не поменяется.

### Формула

По каждому бакету считается темп расхода против равномерного:

```text
remaining = 1 - used
time_left = (сброс - сейчас) / 7 суток
pace      = remaining / time_left
```

Профицит при `pace >= 2`, дефицит при `pace <= 0.5`, между ними норма и сдвига
нет. Зазор широкий сознательно: корректор должен срабатывать на выраженный
перекос, а не дёргать вердикт на каждом колебании.

Свежесть снимка асимметрична, потому что остаток внутри окна только тратится.
Дефицит от старения не рассасывается и валиден до самой даты сброса: снятый
остаток это верхняя граница текущего. Профицит же протухает, для сдвига вверх
снимок должен быть не старше суток. Прошла дата сброса, и бакет отбрасывается
целиком: началось новое окно, про которое снимок ничего не знает.

Правила сдвига, порядок значим:

1. Грумминговые вердикты (неопределённость >= 4, цена XL) не корректируются:
   «исполнять рано» это про порядок работы, расход тут ни при чём.
2. Дефицит любого бакета, из которого тратит модель вердикта, сдвигает на ярус
   вниз. Ниже haiku некуда, остаётся предупреждение.
3. Иначе на ярус вверх сдвигает профицит бакета, который ярус выше добавляет к
   тратам (sonnet -> opus при профиците week_opus). У haiku и sonnet добавочного
   бакета нет, их пару двигает профицит общего week_all.
4. Шаг максимум один, сдвиги не каскадятся. Дефицит проверяется первым: бакет
   тратится взвешенной ценой модели, и сдвиг вверх при дефиците прожёг бы его
   быстрее.

Модель из override-строки файла задачи корректор не двигает: ручное решение
сильнее автоматики, иначе указанную руками модель приходилось бы отстаивать
заново на каждый снимок. Пол effort у sonnet применяется к итоговой модели,
то есть уже после сдвига.

Нет файла, битая строка, протухший бакет: соответствующее отбрасывается, вердикт
остаётся как есть. Отсутствие данных никогда не ошибка pick.

Сдвиг виден в человеческой строке вердикта хвостом:

```text
model: sonnet
effort: high
DK-012 (task, цена M, неопределённость 1): задача для дешёвых моделей не подходит, по умолчанию идёт сильной, effort поднят до high: sonnet дёшев, экономить глубину смысла нет; корректор: дефицит week_opus, opus -> sonnet
```

Сдвинутому вниз LLD-вердикту строка вдобавок советует отложить дизайн до
сброса, если он не горит: дизайн слабой моделью это долгий ущерб. Решение
остаётся за диспетчером, pick только проговаривает.

### Команда quota

```bash
agentctl quota
```

```text
снимок /Users/me/.devkit/quota.local
снят 2026-07-30T14:20, возраст 3ч 2м
week_all: потрачено 34%, сброс 2026-08-04T10:00, pace 1.0, норма
week_opus: потрачено 78%, сброс 2026-08-04T10:00, pace 0.3, дефицит
```

Это окно в решения корректора: сдвиг в вердикте всегда можно объяснить, не
читая файл руками. Снимка нет, значит команда так и говорит, кодом возврата
это не ошибка.

`agentctl quota refresh` заполняет снимок сам: поднимает `claude` в одноразовой
tmux-сессии, посылает `/usage`, дожидается отрисовки, забирает текст панели
через `capture-pane`, разбирает его и пишет файл. Нет tmux, нет claude в PATH,
клиент не залогинен, панель не узналась, значит честный отказ и файл не тронут:
pick живёт по прежнему снимку либо без сдвига. Разметка панели не контракт, она
меняется вместе с клиентом, поэтому парсер гоняется по образцам в
`agentctl/testdata`: редизайн ловится их обновлением, это принятая плата.

## Определения исполнителей

Модель субагента диспетчер передаёт параметром при спавне, а effort приходит
только из определения агента. Поэтому в devkit лежит набор `agents/` по
определению на уровень маппинга:

- `exec-low.md`
- `exec-medium.md`
- `exec-high.md`
- `exec-xhigh.md`

Во frontmatter прибит `effort`, модель не прибита намеренно: одно определение
обслуживает любую модель, которую назвала первая строка вердикта, иначе набор
пришлось бы держать матрицей моделей на уровни. Тело определения короткое, вся
рабочая инструкция это ссылка на правила репозитория и постановку в файле
задачи.

Ставятся определения в пользовательскую директорию, чтобы быть доступными во
всех проектах:

```bash
cp ~/projects/devkit/agents/*.md ~/.claude/agents/
```

Уровня `max` в наборе нет: маппинг его не выдаёт, а под override-строку
определение заводится по месту в проекте.

## Override в файле задачи

Часть случаев (3D-графика, дизайн интерфейсов) в метаданных доски не видна:
тип и цена ничего не говорят про домен. Для них в файле задачи
`docs/tasks/<ID>.md` заводятся строки override:

```text
Модель: fable (3D-графика)
Эффорт: max (незнакомый домен)
```

Допустим и вариант пунктом списка (`- Модель: fable`), поясняющий хвост в
скобках необязателен. Строки живут в файле задачи, не в строке доски: формат
строки доски фиксированный, его парсят три утилиты, а файл задачи доска
только индексирует. pick перед маппингом читает файл, если он есть, и ищет
такие строки.

Оси независимы, каждая перебивается своей строкой, а незаданная берётся из
обычного маппинга. Домен диктует то модель, то глубину размышления, то и
другое сразу, и связывать их одной строкой значило бы заставлять писать лишнее.
Из этого следует неочевидное: override модели на грумминговом вердикте
оставляет effort `xhigh` (маппинг про задачу не передумал), и если исполнять
её надо буднично, рядом ставится и «Эффорт:».

Найденный override модели перебивает модельную часть маппинга целиком, включая
LLD- и грумминг-правила, `Groom` при этом всегда `false`, а в причине вердикта
сказано, что модель задана override-строкой; про effort в причине появляется
своя пометка. Допустимые значения модели `haiku`, `sonnet`, `opus`, `fable`,
эффорта `low`, `medium`, `high`, `xhigh`, `max`; любое другое значение это
жёсткая ошибка pick (опечатка не должна молча провалиться в обычный маппинг).
Нет файла или нет строк, работает обычный маппинг из таблицы выше. Валидацию
держит сам pick, `taskctl lint` эти строки не проверяет: lint проверяет
инварианты доски, а не содержимое файлов задач.

Парсер читает файл целиком и берёт по каждой оси первую попавшуюся строку, не
разбирая контекст: если override уже есть выше по файлу, вторая строка
молча игнорируется, а строка внутри code-fence (пример формата) сработает
как настоящий override. Поэтому в реальном файле задачи держать не больше
одной такой строки на ось и не класть примеры формата с двоеточием после
«Модель» и «Эффорт»; если пример всё же нужен, писать его без двоеточия.

## Запись исполнения (--record)

`agentctl pick DK-002 --record` помимо вердикта дописывает строку в раздел
«Ход работы» файла `docs/tasks/DK-002.md`:

```text
- Исполнение: субагент haiku/low по вердикту pick, 2026-07-28.
```

Через дробь идёт effort из вердикта, то есть какое определение из `agents/`
взято. Сдвинутый корректором вердикт несёт в скобках и маппинг, и причину
сдвига, иначе по файлу задачи не понять, почему модель разошлась с таблицей:

```text
- Исполнение: субагент sonnet/high по вердикту pick (маппинг opus, корректор: дефицит week_opus), 2026-07-30.
```

Так исполнитель остаётся там, куда смотрит пользователь, а не только в
транскриптах сессий. Запись это самоотчёт диспетчера (он фиксирует, кого
собрался спавнить), доказательством она не является. Грумминговый вердикт
(неопределённость >= 4, цена XL) пишется словом «Грумминг» вместо
«Исполнение»: работа по нему не начинается, и строка не обещает того,
чего не было. Без раздела «Ход работы»
тот добавляется в конец файла; повторный вызов дописывает новую строку, история
перезапусков сохраняется. Для задачи без файла выходит ошибка с подсказкой
`taskctl file <ID>`: pick с записью зовётся при взятии в работу, а у взятой в
работу задачи файл обязан быть. Вывод в stdout не меняется, git утилита не
трогает: коммит и пуш строки остаются за диспетчером, как у любой правки
файла задачи.
