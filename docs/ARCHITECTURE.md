# Архитектура devkit

## Границы

- Пять каталогов верхнего уровня и граница языков go/python/sh расписаны
  в [README.md](../README.md), раздел «Раскладка». Текст живёт в одном
  месте, здесь не дублируется.
- Устройство дашборда это пакеты по доменам (chats, board, sessions, runs,
  quota и другие), решено человеком 2026-10-06 в развилке DK-1265. Домен
  ходит в домен через явные точки входа, внутренности с маленькой буквы
  наружу не видны. До конца переезда старые семьи файлов живут в корне
  каталога, переезд идёт задачами DK-1265 и DK-1266. Карта кластеров держит
  [docs/map.md](map.md).
- Маршруты HTTP дашборда собраны в одном месте, handler() в
  `tools/dashboard/server.go`. Хендлеры лежат в доменных файлах с именами
  handle*, логика живёт рядом с хендлером в том же пакете. Сервер считает,
  клиент только рисует, разбор в LLD DK-112.
- Строки доски дашборд сам не правит. Доску он читает, двигает строку
  поднятый им конвейер. Своей базы у дашборда нет, источник правды это
  доска и утилиты (LLD DK-112).
- Общий каркас `internal` дашборд импортирует: sessions, chat, taskhead,
  works и другие. Локальная копия при живом пакете в `internal` это
  находка ревью. Сейчас это прямой вызов git при готовом `internal/gitrun`,
  собрано в DK-1268.

## Инварианты

- Ответы API дашборда идут через единственный writeJSON
  (`tools/dashboard/server.go`), транскрипты разбираются единственным
  parseReplies (`tools/dashboard/sessions.go`), обращения к taskctl
  сходятся в воронку taskctlDo -> runProc (`tools/dashboard/tasks.go`).
- Вставка текстовой разметки вызова в реплике агента сворачивается карточкой
  хода там же, в parseReplies (DK-1378): внешний шлюз модели отдаёт вызов
  текстом, а лента показывает его как настоящий tool_use. Слова вокруг
  остаются репликой, текст человека и выводы инструментов не трогаются.
- Поверхность чата дашборда несёт только разговор: реплики, их оформление и
  одно поле ввода. Взаимодействие с человеком живёт внутри реплик (галочки
  вопросов, DK-864) либо на экране записи, служебные ручки вроде решения цели
  задачам и строки диспетчеру цели кнопок и плашек в чате не получают. Шапка
  чата называет одну запись, состав задач цели виден на экране цели (DK-1484).
- Ожидание согласия на груминг проверяется по показанному PreparedQuestion
  командой `taskctl draft prepared check-ask`. Вместе с ним проверяются состояние
  сессии и отсутствие других выполняющихся вызовов инструментов и дочерних
  работ. Одного `waiting` или наличия старого Ask недостаточно. В этом состоянии доступно
  подтверждение с формы, а анимация вычисления и «Стоп» не показываются.
  Одновременные проверки используют общий лимит taskctl и один запрос по ключу;
  готовый ответ для следующего опроса не сохраняется. После фактического
  согласия связь со старым вопросом клиента проверяется по ID вызова и квитанции.
- Для обычной и подготовленной задачи используется общая полная форма taskForm
  (`tools/dashboard/static/app.js`). Подготовленная задача отличается
  возможностями запуска и чата, адаптером сохранения и ссылкой на исходник.
  Удаление, приписка и отсрочка входят во внутренний план разбора и видны
  в тексте заключения на форме исходника. Отдельных форм задач для них нет.
  Агент создаёт подготовленные задачи при сохранении плана. Пользователь
  может править существующие описания. «Состав разбора» вычисляется из всех
  структурированных действий и показан отдельно от сохранённого текста агента.
- Разделы содержимого формы черновика используют общий `formContentBlock`
  на основе `dfield` с подписью `legend` на границе рамки. Порядок разделов,
  состояния с результатами и без них, отступы и правила расширения описаны
  в [README дашборда](../tools/dashboard/README.md#единые-блоки-формы-черновика).
  Новые разделы этой формы добавляются через тот же компонент.
  В поле мысли разные пользователи оставляют замечания до появления результата.
  После сохранения результата новые замечания идут через тот же «Чат разбора».
  Прежние мысли остаются в исходнике. Общий признак `draftproposal.HasGroomResult`
  используется формой и командой записи мысли; готовность комплекта и согласие
  проверяются отдельно. При пустом prepared-файле и после первой ошибки без
  результата поле остаётся доступным. Запись мысли из устаревшей формы после
  появления результата завершается отказом.
- Новая память процесса дашборда получает свой замок или ложится под
  s.mu сервера. Порядок замков прокомментирован у объявления в
  `tools/dashboard/server.go`. Приём memo-кэша не пишется руками заново,
  сведение мест в общий тип собрано в DK-1268.
- Чаты всех подписок, включая подписку по умолчанию, поднимаются обёрткой
  `agentctl exec` (DK-1271): путь клиента не зависит от окружения serve и
  сохраняется после рестарта launchd-агента. Генератор plist кладёт ту же обёртку,
  при пустом машинном слое команда завершается отказом с подсказкой `devkitctl doctor --fix`.
- Сеть в дашборде знают два места. Это пуш правки доски (commitDocs в
  `tools/dashboard/board.go`) и фоновый догон чекаутов проектов из origin
  (`tools/dashboard/catchup.go`, DK-1414). Догон делает только fetch и
  fast-forward, гарды чистого дерева и главного ствола держат местную работу.
  Чтение доски через taskctl сети не ходит, позиция записана у самой утилиты.
- Всякий подъём процесса в дереве дашборда называет рабочий каталог (DK-1373):
  без него процесс под launchd наследует корень файловой системы, обходит
  защищённые папки macOS и поднимает диалоги доступа на имя дашборда. Каталогом
  служит служебный пустой каталог `internal/clientdir`, каталог команды у
  `agentctl exec`, «-c» у tmux-сессий и WorkingDirectory у launchd-агентов.
  Новую дорогу запуска без каталога ловит сторож TestLaunchSitesNameDir
  (`tools/dashboard/launchdir_test.go`) прогоном, а не диалогами на машине.

## Куда кладётся новое

- Место для нового файла, каталога или команды держит [README.md](../README.md),
  раздел «Раскладка», с белым списком каталогов и границей языков.
- Новый домен дашборда заводится пакетом в `tools/dashboard/<домен>/`, файлы
  домена лежат в нём. Правки старых семей до переезда остаются в их файлах.

## Восстановление исчезнувшего конвейера

`taskhead.Raise` создаёт ID нового запуска до подъёма клиента. Оболочка
подтверждает ID своим PID после принятия замка. Состояние остановки и запуска
хранится вне временного замка задачи. Ключ состоит из канонического корня
и ID задачи, запись атомарна и синхронизирована на диск вместе с каталогом.
Остановка из дашборда и новый запуск используют общий замок этого состояния.

`recovery.py` восстанавливает только подтверждённо погибшего владельца.
Общий замок машины ограничивает одновременные попытки, отдельный журнал
сохраняет расход до внешнего действия. Повреждённый журнал, неизвестная
идентичность и недоступная квота запрещают запуск. Модель и подписка
передаются явно из исходного запуска.

Подтверждение содержит корень, задачу, попытку, новый ID запуска и PID.
Его пишет рабочая оболочка по новому действию собственной сессии. Закрытие
инцидента повторно сверяет подтверждение под замком состояния задачи.
Операционный вход и изолированный прогон описаны в
[документации дежурного](../tools/devkitctl/README.md#первый-запуск-восстановления).
