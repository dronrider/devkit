## Откуда взялись 416 процессов

У всех 416 осиротевших `/bin/sh` родитель PID 1. В аргументах находится
неизменённый shell-код из [cloudstart.go](https://github.com/dronrider/devkit/blob/8c015e7057951eaf9fbf5bb32298810b208b8296/tools/dashboard/cloudstart.go).
Распределение по синтетическим сессиям:

| Сессия стенда | Число процессов |
|---|---:|
| goal-XR-100 | 110 |
| chat-XR-002-1 | 102 |
| chat-XR-002-2 | 102 |
| chat-XR-002-3 | 102 |

Все 416 указывают на `bin/tmux` внутри удалённых каталогов
`devkit-dashboard-smoke/run-*`. Их служебные каталоги `devkit-cloud-start-*`
остались. Подставной tmux отсутствует, ack отсутствует. У всех 416 status содержит 0 и seen существует. В проверенных
образцах probe-error содержит
`cloud-start: line 9: <каталог стенда>/bin/tmux: No such file or directory`.
У двух образцов lsof показал открытый FD 3 на cloud-locks/XR-002 в
синтетическом проекте. Удержание боевых cloud-lock этими образцами не обнаружено.
Часть процессов существует больше 21 часа.

Цепочка подтверждается исходниками:

1. `startManaged` при непустом ID вызывает `startReserved`. Запуск введён
   коммитом `a3d72c76b`, DK-1469. Guardian наследует резервирующие файловые
   дескрипторы и должен дождаться ack от agentctl либо подтверждённой смерти
   сессии.
2. В [smoke.go](https://github.com/dronrider/devkit/blob/8c015e7057951eaf9fbf5bb32298810b208b8296/tools/dashboard/smoke.go) используется настоящий путь
   `startReserved`. Подставной agentctl исполняет клиента, но не реализует
   подтверждение `DEVKIT_CLOUD_ACK`. Подставной tmux не обрабатывает
   has-session/list-sessions и возвращает для них общий exit 0.
3. Guardian остаётся ждать ack. `status=0` означает только успешный ответ
   запуска tmux. Код Go уже возвращает успех и записывает seen.
4. `cmdSmoke` по окончании выполняет `s.close()` и `RemoveAll(run-dir)`.
   В `close()` восстанавливаются подмены; учёта и ожидания этих процессов нет.
5. После удаления стенда оба опроса идут по отсутствующему bin/tmux.
   Выход из цикла предусмотрен для текста `no server running`, но не для
   `No such file or directory`. Предела ожидания ack в этом цикле нет.
6. Оболочка продолжает опрос раз в секунду, сохраняя каталог и FD. При
   окончании родительского процесса она остаётся под PID 1.

У unit-тестов `newTestEnv` есть подмена `startReservedFn`. Она не защищает
этот smoke-путь. Добавить ещё одну подмену без проверки настоящего жизненного
цикла означало бы скрыть дефект.

## Адресное воспроизведение

Локально выполнены два изолированных запуска точного
shell-кода из cloudstart.go. Подставной tmux только возвращает 0; настоящие
чаты, модельные API и боевые замки в опыте не используются.

| Опыт | Действие после появления status | Результат |
|---|---|---|
| Передача резерва | Записать seen и ack | Оболочка завершилась с 0, служебный каталог удалён |
| Удаление стенда | Записать seen, удалить только подставной tmux, ack не создавать | Через 2.3 с оболочка жива, status=0, probe-error содержит No such file or directory |

После опыта завершена только собственная группа изолированного процесса.
Рабочие процессы машины, на которой возник инцидент, не затрагивались.
Отсутствие предела ожидания подтверждено кодом, а не ожиданием бесконечности
в опыте. Полные тестовые наборы на перегруженной машине не запускались.

## Почему штатная защита не остановила накопление

- Guardian намеренно отделён от жизни дашборда и сохраняет резерв после его
  выхода. Одного ожидания cmd.Wait в горутине недостаточно для уборки стенда.
- Общий `full_run_slot` в parallel.py ограничивает живые прогоны. После их
  окончания остающиеся процессы не занимают слот следующего прогона.
- Убийство группы компонента при красном соседнем компоненте не обеспечивает
  уборку всех процессов после успешного выхода и не является учётом владельцев
  для detached-процессов. Фактические остатки пережили окончание прогонов.
- В smoke нет проверки нулевого остатка guardian-процессов и закрытия их FD.
- Отметка `load=true` в журнале описывает результат уже состоявшегося отказа.
  В наблюдавшемся окне она не предотвратила новые дорогие попытки.

Механизм DK-1571 про clitx-обёртки этим снимком не подтверждён и не заменяет
исправление cloud-start. DK-1562 про headless-подъём остаётся отдельной
проблемой тестового окружения.

## Как доработать механизм

Сначала согласуется контракт передачи резерва. Исправление должно сохранить
защиту от изменения облачной записи в промежутке между запуском и принятием
замка клиентом.

1. Завести явные исходы запуска: создан терминал, клиент принял резерв,
   запуск не удался, состояние неизвестно. `status=0` нельзя считать
   подтверждением принятого резерва. Хранить владельца запуска, PID и его
   поколение, ID сессии, ack и основание завершения.
2. Для ошибки опроса задать ограниченное ожидание и наблюдаемую эскалацию.
   После срока нельзя просто отпускать резерв или убивать живой чат.
   При неизвестной живости запуск остаётся защищённым от повторного подъёма,
   а ответственность за резерв передаётся наблюдаемому владельцу. Окончание
   защиты допустимо после ack либо подтверждённого завершения клиента.
3. В стенде реализовать согласованный fake-контракт ack и живости. Каждый
   созданный guardian должен иметь владельца прогона; завершение, ошибка,
   тайм-аут и отмена прогона завершают только его синтетические процессы,
   ожидают их выхода и затем удаляют исполняемые файлы.
4. Проверять отсутствие остаточных процессов, каталогов и резервов по
   завершении каждого сценария. Сохранение отчёта через --keep не должно
   сохранять активные циклы.
5. Перед повтором тяжёлого merge учитывать перегрузку и причину прошлой
   попытки. Одинаковый нагрузочный отказ без нового события переводить в
   видимое ограниченное ожидание с условием возобновления. Порог нагрузки
   и гистерезис выбрать измерением с учётом числа CPU и памяти.
6. Записывать для каждого принудительного завершения инициатора, причину,
   SID адресата, PID/поколение и фактического жильца окна. При неизвестной
   живости не снимать окно на основании устаревшей записи другого разговора.

Число секунд ожидания ack, предел нагрузки и политика завершения при
неизвестной живости ещё требуют выбора. Общий запрет на тайм-ауты не нужен;
нужен явный исход и сохранение защитного инварианта.

## Чем проверить исправление

| Сценарий | Ожидаемый исход |
|---|---|
| Нормальный ack | Резерв передан без разрыва, guardian завершён, чат работает |
| Клиент умер до ack | Доказана смерть, резерв освобождён, причина сохранена |
| Родитель дашборда умер до ack | Резерв сохраняется у известного владельца, повторный запуск исключён |
| Временный сбой опроса tmux | Живой чат сохранён; повтор ограничен и виден |
| Постоянно недоступный tmux при неизвестной живости | Видимая эскалация без бесконечного активного опроса и без снятия защиты наугад |
| Fake tmux удалён до ack | Сценарий красный на старом коде; после исправления нет процессов и FD стенда |
| Успех/ошибка/тайм-аут/отмена smoke | Каждый исход оставляет нулевой набор принадлежащих стенду процессов |
| Серия smoke в штатном общем слоте | Число guardian не растёт между прогонами |
| Повтор нагрузочной красноты merge | Новая тяжёлая попытка ждёт заданного события; очередь показывает причину |
| Чужой жилец под старым именем окна | Чужой разговор сохранён, ошибка адресации записана |
| Запрос перезапуска чата | В журнале различимы инициатор запроса и причина остановки |

## Очередь и границы решения

Новые работы добавлены в [№171-174](concurrency-queue.md#q171). Ближайший
порядок для этого инцидента: №171, №172, затем №173. Диагностика остановок
чатов №174 идёт отдельно. DK-1562 проверяется адресно после разгрузки,
конфликты ребейза разрешаются после восстановления проверок.

№046/047 остаются смежными задачами уборки процессов, но не покрывают
резерв запуска cloud-start. №055 дополнен фактическими нагрузочными
отказами. DK-1571 нельзя считать единственной причиной коллапса.

На момент завершения диагностики реализация, очистка рабочей машины и
изменение автоматики не выполнялись.
Перед восстановлением нужно согласовать исправление и безопасную область
очистки по сохранённому списку синтетических процессов. Общий killall и
удаление замков по возрасту для этого не подходят.

компонентов. На рабочей машине /healthz показал установленный dashboard
