# DK-033: LLD универсального кита: devkit в любом харнесе

## Задача и рамка

Портируемое ядро devkit (taskctl, shipctl, regcheck, RANKING.md, git-хуки,
текст правил) от харнеса не зависит, а прибит к Claude Code список из шести
мест плюс одно допущение про спавн субагентов; перечень в постановке
[DK-033](../tasks/archive/2026/DK-033.md). Скелет решения согласован там же двадцатью
пунктами, этот документ их не переоткрывает, а доводит до контрактов.

Глубина проработки договорена так: контракты, от которых зависит нарезка
задач (формат профиля, слои конфигурации, съёмщик остатка, режим cli,
инвариант одной копии правил, миграция), доведены до конкретики здесь.
То, что упирается в конкретный инструмент (переменные детекта, headless-флаги,
форматы определений, протоколы хуков), фиксируется только проверенным, а
непроверенное остаётся открытым с именем задачи, которая его закрывает:
ложная конкретика в LLD хуже прочерка. Свод по инструментам в разделе
«Профили инструментов: проверенное и открытое».

Словарь документа: **харнес** это инструмент, в котором живёт сессия агента
(Claude Code, Codex, OpenCode, Gemini CLI, Cursor); **профиль** это декларация
его возможностей в devkit; **ярус** это ступень лестницы моделей
(mini/base/pro/max); **маппинг** разворачивает ярус в конкретную
модель харнеса; **съёмщик** снимает остаток лимитов; **адаптер** это код по
имени харнеса там, где деклараций профиля мало (рендер правил и определений,
разбор входа хука).

## Профиль харнеса

Файл `harness/<имя>.toml`, коммитится в devkit. Имя канонично, строчными с
дефисом, оно же значение `--harness` и `DEVKIT_HARNESS`: `claude-code`,
`codex`, `opencode`, `gemini`, `cursor`. Рядом живут скрипты съёмщиков
(`harness/snap/<имя>.sh`) и общие фикстуры парсера (`harness/testdata/`).

### Подмножество TOML

Профиль читают две реализации: Go в agentctl и Python в devkitctl. Тащить
внешний TOML-модуль в Go-утилиту, до сих пор живущую на stdlib, ради конфига
из строк и массивов не хочется, а у Python `tomllib` появился только в 3.11,
тогда как devkitctl обещает голый python3 (на живой машине стоит 3.10).
Поэтому формат объявляется подмножеством TOML, и парсер этого подмножества
пишется дважды, по одному на язык, с общими фикстурами в `harness/testdata/`:
один и тот же набор входов обе реализации обязаны читать одинаково, это
проверяют тесты обеих сторон.

Подмножество: секции одного уровня `[имя]`, ключи `key = value`, значения
это строки в кавычках, целые числа, `true`/`false` и массивы строк в одну
строку, комментарии `#`. Вложенных таблиц, дат, многострочных и literal-строк
нет. Файл при этом остаётся валидным полным TOML, так что подсветка и чужие
читатели работают; инвариант «не вылезать за подмножество» держит валидатор
(см. ниже), а не дисциплина.

Отклонённые альтернативы: полный TOML через зависимость (первый внешний
модуль в Go-утилитах и требование python3 >= 3.11 ради трёх типов значений);
плоский `key = value` как в `deploy.local` (пять осей с массивами и
переопределениями по харнесам не влезают без соглашений об именах ключей,
которые выйдут хуже самих секций).

### Секции и ключи

Пять секций, все пять обязаны присутствовать в файле, даже пустыми: пустая
секция это явное «оси нет», а пропущенная это ошибка валидации. Так профиль
нового инструмента нельзя написать, забыв про ось.

`[detect]`, как узнать себя и найти инструмент:

| Ключ | Тип | Обязателен | Смысл |
|---|---|---|---|
| `env` | строка | если секция непуста | переменная окружения, по которой харнес узнаётся изнутри сессии |
| `value` | строка | нет | точное значение; не задан, значит годится любое непустое |
| `bin` | строка | да, если секция непуста | имя бинаря в PATH, по нему setup находит инструмент |

Пустая секция: харнес изнутри не детектится, активным его делают только
`--harness`, `DEVKIT_HARNESS` или `default` машинного конфига.

`[rules]`, как до инструмента доезжают правила:

| Ключ | Тип | Обязателен | Смысл |
|---|---|---|---|
| `mode` | строка | да | `import`, `embed` или `render` |
| `file` | строка | при `import` | генерируемый тонкий файл в корне проекта (`CLAUDE.md`) |
| `import_line` | строка | при `import` | шаблон строки импорта, `{path}` подставляется (`"@{path}"`) |
| `config` | строка | нет | конфиг инструмента, куда пути прописывает адаптер (вариант import для OpenCode) |
| `dir` | строка | при `render` | директория рендера (`.cursor/rules`) |
| `global_file` | строка | нет | глобальная точка подключения правил (`~/.claude/CLAUDE.md`) |

Секция пустой быть не может: правила обязаны доезжать до каждого
поддержанного инструмента, харнес без `[rules]` не проходит валидацию.
Режим `embed` ключей не требует: вклейка всегда идёт в `AGENTS.md`
(см. «Правила: инвариант одной копии»).

`[delegate]`, как задача уходит исполнителю:

| Ключ | Тип | Обязателен | Смысл |
|---|---|---|---|
| `mode` | строка | да | `native`, `cli` или `none` |
| `command` | массив строк | при `cli` | шаблон команды с плейсхолдерами `{model}`, `{effort}`, `{prompt}`, `{workdir}` |
| `agents_dir` | строка | нет | куда рендерятся определения агентов |
| `agents_format` | строка | нет | имя рендерера определений в коде |
| `map_mini`..`map_max` | строки | нет | предложение маппинга ярусов по умолчанию, его показывает setup |

Пустой секция не бывает: `mode` обязателен всегда, у инструмента без
делегирования это честный `none`.

`[hooks]`, события и проверки текстов:

| Ключ | Тип | Обязателен | Смысл |
|---|---|---|---|
| `protocol` | строка | если секция непуста | имя разборщика входа в таблице `hooks/hookio.py`, обычно совпадает с именем харнеса |
| `config` | строка | нет | файл настроек, куда setup прописывает хуки |
| `events` | массив строк | нет | что инструмент даёт: `write` (событие записи файла), `session-start`, `notify` (сессия ждёт действия), `subagent-done`, `turn-done` (сессия закончила ход), `prompt-submit` (пользователь ввёл запрос) |
| `memory_index` | строка | нет | суффикс пути индекса памяти для `check-memory.py`; нет ключа, проверка не подключается |

Пустая секция: рубежа «сразу при записи» нет, тексты держит только git-рубеж,
который работает у всех одинаково.

События `notify`, `subagent-done`, `turn-done` и `prompt-submit` это то, на
чём висит уведомитель из [DK-034](../tasks/archive/2026/DK-034.md). Объявлены
они по отдельности, потому что инструменты дают их порознь: у claude-code это
`Notification` с матчером по поводу, `SubagentStop`, `Stop` и
`UserPromptSubmit`, а инструмент без своих субагентов объявит одно первое.
`turn-done` и `prompt-submit` ходят парой: ввод пользователя ничего не шлёт, но
снимает отметку ожидания, без которой второй конец хода подряд глохнет в общем
окне троттлинга (DK-062, DK-064). Точные имена событий и матчер в профиль не выносятся,
это дело рендерера, выбранного `protocol`, как и у `write` сегодня: профиль
отвечает на вопрос «есть ли у инструмента такая ось», а не пересказывает
формат его настроек. Чем слать, от харнеса не зависит вовсе (уведомитель
выбирает бэкенд по платформе и PATH), так что в профиле остаётся только
объявление событий.

`[quota]`, остаток лимитов:

| Ключ | Тип | Обязателен | Смысл |
|---|---|---|---|
| `snap` | строка | если секция непуста | `usage-pane` (встроенный tmux-цикл) или `script` |
| `script` | строка | при `snap = "script"` | путь съёмщика относительно `harness/` |
| `buckets` | массив строк | если секция непуста | известные бакеты снимка |
| `required` | строка | если секция непуста | бакет, без которого снимок не принимается (`week_all`) |
| `spend_mini`..`spend_max` | массивы строк | если секция непуста, то все четыре | из каких бакетов тратит ярус |
| `budget_based` | булев | нет | расход в деньгах, setup спрашивает бюджет |

Пустая секция это пункт 15 скелета: снять нечем, корректор для харнеса
выключен, `doctor` говорит находкой, вердикт хвостом причины. У профиля
нового инструмента секция пуста, пока его задача не выяснит, чем снимать.

Скелет (пункт 3) обещал «рядом с профилем скрипт адаптера» везде, где
деклараций мало. В дизайне скриптом остался только съёмщик: рендер правил и
определений и разбор входа хука это код в devkit, который профиль выбирает
именем (`agents_format`, `protocol`). Причина в том, что этим адаптерам
нужны общие тела (генератор вклейки, проверки текстов), и скрипт рядом с
профилем дублировал бы их; съёмщику же общего тела не нужно, его контракт
это stdin/stdout.

### Валидация

Профиль валидируется на каждой загрузке, а не отдельной командой: agentctl и
devkitctl читают его одним и тем же сводом правил (пять секций на месте,
обязательные ключи при выбранных режимах, значения режимов из перечня,
`spend_*` ссылаются только на бакеты из `buckets`). Нарушение это жёсткая
ошибка с именем файла и ключа: битый профиль хуже отсутствующего, потому что
молча выключил бы ось. Незнакомый ключ или незнакомое значение `events`
это предупреждение, а не ошибка: старый бинарь должен переживать профиль
из более свежего devkit. `devkitctl doctor` прогоняет валидацию по всем
профилям `harness/`, не только по активному, и находит битое до того, как
кто-то переключится.

## Слои конфигурации

Три слоя, у каждого своя роль, формат у всех одно и то же подмножество TOML.

1. Профиль в devkit: что инструмент умеет. Обновляется с devkit, руками не
   правится.
2. Машинный `~/.devkit/harness.local`: что на этой машине включено и как
   ярусы разворачиваются в модели. Пишет его `devkitctl setup`, править
   руками можно.
3. Проектный `.devkit/harness.local` (гитигнорнут, как `deploy.local`):
   сужение машинного списка для проекта. Необязателен.

Машинный конфиг:

```toml
default = "claude-code"
enabled = ["claude-code", "codex"]

[claude-code]
mini = "haiku"
base = "sonnet"
pro = "opus"
max = "fable"

[codex]
mini = "gpt-5-mini"
base = "gpt-5-mini"
pro = "gpt-5.2"
max = "gpt-5.2-pro"
budget = 200
```

Секция на включённый харнес: четыре ключа-яруса обязательны все (складывание
соседних ярусов в одну модель записывается повторением значения, а не
пропуском ключа: пропуск неотличим от забытого), `budget` появляется у
инструментов с `budget_based`. Имена моделей в примере условные и это
свободные строки, devkit их не валидирует: перечень моделей чужого
инструмента протухает быстрее, чем обновляется профиль. Из «путей» скелета
(пункт 4) машинной секции нужен один необязательный ключ `bin` с полным
путём к бинарю, когда инструмент стоит вне PATH; остальные пути живут в
профиле, машине их переопределять не для чего. Харнес из `enabled` без
своей секции маппинга считается ненастроенным: ярусная часть вердикта
работает, `model: -` с командой настройки хвостом.

Проектный конфиг понимает только `enabled`: скелет (пункт 4) отводит этому
слою сужение списка, `default` остаётся машинным. Слияние сверху вниз:
профиль объявляет возможности, машинный включает и маппит, проектный сужает.
Конфликты разрешаются в сторону «не гадать»: `enabled` проекта пересекается с
машинным, что вне пересечения, отбрасывается с предупреждением; имя без
профиля в `harness/` отбрасывается так же; пустое пересечение равносильно
«не определилось» в резолве; любой другой ключ в проектном слое это находка
doctor. Машинного конфига нет вовсе, значит слияние отдаёт одну строку:
включён `claude-code` с маппингом-предложением из его профиля. Это пункт 20
скелета, до прогона setup поведение сегодняшнее один в один, что
закрепляется тестом.

## Детект активного харнеса

Резолв идёт по слитому списку включённых (без машинного конфига это
`claude-code`, см. «Слои конфигурации»), порядок, первое сработавшее решает:

1. флаг `--harness <имя>`;
2. переменная `DEVKIT_HARNESS` (её ставит подпроцессу `agentctl run`);
3. `[detect]` включённых харнесов по переменным окружения;
4. `default` машинного конфига, если он в слитом списке (сужен проектным
   слоем, значит пропускается с предупреждением);
5. не определилось: ярусная часть вердикта работает, `model: -`, хвост
   причины называет `devkitctl setup`.

Детект на шаге 3 смотрит и профили вне включённого списка: сессия внутри
установленного, но не включённого харнеса не должна молча уезжать в
`default`. Такое совпадение харнес не активирует, но даёт хвост причины
(«сессия внутри X, он не включён»), и дальше резолв идёт по шагам 4-5.

`DEVKIT_HARNESS` стоит выше детекта по окружению не для красоты: подпроцесс
наследует окружение родителя, и внутри инструмента, поднятого из сессии
Claude Code, `CLAUDECODE=1` родителя останется видимым рядом с переменными
самого инструмента, какими бы они ни были. Детект по env в таком гнезде
неоднозначен по построению, поэтому `run` передаёт целевое имя явно, а
env-детект остаётся для сессий, запущенных руками. Если шаг 3 находит
больше одного совпадения, devkit не гадает: берётся `default`, человеческая
строка вердикта говорит про неоднозначность.

Окно в резолв, по образцу `agentctl quota`:

```text
agentctl harness
```

печатает активный харнес и чем он определён (флаг, переменная, детект,
default), включённый список после слияния слоёв, маппинг ярусов, режим
делегирования, путь и возраст снимка квоты. Любой сдвиг поведения между
машинами объясняется этой командой, а не чтением трёх конфигов руками.

## Ярусы и вердикт pick

Лестница фиксированно четырёхступенчатая: `mini -> base -> pro -> max`. Имена
отвечают на единственный вопрос, который задают ярусу («насколько модель
сильная относительно соседей»), и читаются по порядку без таблицы под рукой.
Внутренние таблицы pick (модель, effort, роль ревьювера, корректор)
переписываются в ярусы без смены семантики, соответствие старым именам
прибито таблицей псевдонимов:

| Псевдоним | Ярус |
|---|---|
| haiku | mini |
| sonnet | base |
| opus | pro |
| fable | max |

Псевдонимы живут дольше миграции: строки «Модель:» в файлах задач написаны
старыми именами, и ломать их об жёсткую ошибку валидации нельзя. Override
принимает и имя яруса, и псевдоним; любое другое значение остаётся жёсткой
ошибкой, как сейчас. Писать в override конкретную модель инструмента
нельзя сознательно: строка в файле задачи переживает смену харнеса, ярус
переносим, имя модели нет.

Пол effort, висевший на sonnet, переезжает на ярус base, пол ревьювера
туда же: «дешёвая рабочая модель, экономить глубину смысла нет» это свойство
ступени лестницы, а не конкретной модели. На харнесе, где base
развёрнут в дорогую модель, пол честно теряет исходное обоснование, но
вреда не наносит: он только поднимает глубину размышления.

Вердикт получает третью машинную строку, первые две не двигаются с мест,
чтобы не переучивать существующих потребителей первой строки:

```text
model: opus
effort: high
tier: pro
DK-042 (task, цена M, неопределённость 1): задача для дешёвых моделей не подходит, по умолчанию идёт сильной
```

Порядок расчёта: маппинг таблиц -> override -> корректор -> роль ревьювера,
всё в ярусах; разворачивание `tier` в `model` идёт последним шагом по
маппингу активного харнеса. Харнес не определён или не настроен, значит
`model: -` и хвост причины с командой настройки, `tier` и `effort` при этом
полноценны: ярусная половина вердикта от инструмента не зависит по
построению. Корректор двигает ярус; если маппинг сложил соседние ярусы в
одну модель и сдвиг модели не сменил, корректор говорит об этом хвостом
(«сдвиг pro -> base, модель та же»), молчаливый холостой ход
неотличим от отсутствия сдвига.

Строка `--record` продолжает нести модель и effort; в режиме cli перед ней
добавляется имя харнеса («подпроцесс codex: gpt-5.2/high по вердикту run»,
имя модели условное, берётся из маппинга), иначе по файлу задачи не
восстановить, каким инструментом задача делалась.

## Делегирование: agentctl run

Точка входа одна: `agentctl run <ID> [--role review]`. Сначала печатается
полный вердикт (те же строки, что у pick, включая запись `--record`, если
флаг передан), затем режим из `[delegate]` активного харнеса решает, что
дальше.

- `native`: печатается инструкция диспетчеру (спавнить субагента с моделью
  из вердикта и определением `exec-<effort>`/`review-<effort>`), выход 0.
  Это сегодняшнее поведение, run ничего не спавнит: спавн субагента есть
  только у самого харнеса.
- `cli`: собирается команда по шаблону `command`, подпроцесс запускается в
  рабочей директории задачи, его код выхода становится кодом выхода run.
- `none`: честная строка «делегировать нечем» с именем харнеса, выход 3.
  Код ненулевой сознательно: скрипт поверх run не должен принять «нечем» за
  сделанную работу; 3, а не 1, чтобы отличаться от ошибок самого run (нет
  задачи, битый профиль).

`pick` остаётся чистым читателем, как был: подпроцессы спавнит только run.

### Сборка команды и промпта

Плейсхолдеры шаблона: `{model}` из вердикта, `{effort}` из вердикта,
`{workdir}` это рабочая директория, `{prompt}` это собранный промпт. Промпт
склеивается из двух частей: тело нейтрального определения агента
(`agents/exec-<effort>.md` или `review-<effort>.md` без frontmatter) плюс
блок задачи: ID, рабочая директория, «постановка в `docs/tasks/<ID>.md`»,
роль. Ровно то, что диспетчер Claude Code передаёт субагенту сегодня, только
собранное в один текст.

Effort там, где у CLI есть рычаг, уходит плейсхолдером `{effort}` в команду
(флаг или ключ конфига, конкретика в профиле инструмента). Где рычага нет,
плейсхолдер в шаблоне просто отсутствует, и effort доезжает только текстом
определения: тела `exec-low`..`exec-xhigh` уже различаются тем, сколько
размышления от исполнителя ждут. Это честная деградация, вердикт effort всё
равно печатает, и по `--record` видно, что назначалось.

### Ограничитель вложенности

Подпроцесс режима cli это полноценная сессия агента, которая читает те же
правила, а правила велят диспетчеру делегировать через run: без ограничителя
выходит воронка из вложенных сессий. Поэтому run ставит подпроцессу
`DEVKIT_RUN_DEPTH=1` (и `DEVKIT_HARNESS=<имя>` для детекта), а сам при
`DEVKIT_RUN_DEPTH >= 1` отказывает с человеческой строкой «вложенный запуск,
исполняй задачу сам» и выходом 1. Флага обхода нет сознательно: сценария,
где воронка легальна, не придумано, а появится, лимит поднимется осознанной
правкой, не флагом на каждый день. Промпт подпроцесса вдобавок говорит
исполнителю, что он исполнитель, а не диспетчер, но текстовая просьба это не
рубеж, рубеж это переменная.

Снимок квоты у харнесов без события старта сессии освежается здесь же: перед
делегированием run отцепленно дёргает refresh `--if-stale` под тем же
замком, что и SessionStart-хук. run уже не чистый читатель, ему можно то,
что pick запрещено.

## Определения агентов

Нейтральный формат это сегодняшние файлы `agents/`: frontmatter с `name`,
`description`, `effort` и короткое тело. Он объявляется исходным контрактом,
рендереры переводят его в формат инструмента:

- `claude-code`: копия как есть в `~/.claude/agents/`, сегодняшнее
  поведение (ключ `effort` для Claude Code лишний, но раскладка с ним
  живёт и спавнится уже сегодня, это наблюдение с работающей машины);
- режим `cli`: рендера нет, тело вклеивается в промпт (см. run);
- `opencode`, `cursor`: формат целевого файла проверяется в задачах их
  профилей, см. «Профили инструментов».

Каркас рендера (интерфейс, выбор по `agents_format`, раскладка) заводится в
задаче setup (DK-042), которому он и нужен первому; claude-code-рендерер
это перенос сегодняшней раскладки doctor под общий интерфейс, а рендереры
чужих форматов едут каждый в задаче своего профиля.

Правило для полей без аналога в целевом формате: судьба каждого поля
фиксируется в рендерере таблицей (переносится, переезжает строкой в тело,
отбрасывается), молчаливое отбрасывание запрещено. `effort`, которому не
нашлось родного поля, вклеивается первой строкой тела («глубина размышления:
xhigh»), чтобы не потеряться совсем.

## Правила: инвариант одной копии

Рукописный файл проекта один, `AGENTS.md`: открытая спека, плоский markdown,
без импортов, ближайший по дереву побеждает. Всё остальное генерируется, и
не отдельной командой, а `devkitctl doctor --fix` (пункт 19 скелета): дрейф
это находка doctor, починка это его же `--fix`, третьего входа в генерацию
нет.

Куда попадает текст правил, решается по составу включённых харнесов:

- embed-инструментов нет: копий текста в дереве проекта ноль. Тонкие
  генерённые файлы ссылаются на `AGENTS.md` и на `../devkit/RULES.md` с
  `RULES.board.md` напрямую, как сегодняшний CLAUDE.md.
- есть хоть один embed-инструмент: единственная копия вклеивается в
  `AGENTS.md` между маркерами, а импорт-инструменты ссылаются только на
  `AGENTS.md` и на `../devkit` больше не ходят: иначе их контекст получил бы
  правила дважды, из вклейки и из импорта.

Режим `render` под инвариант одной копии подчинён жёстко: рендерится тонкий
файл в чужом формате (frontmatter инструмента, тело-отсылка к `AGENTS.md`),
а не копия текста правил. Инструмент, который не умеет ни ссылку, ни чтение
`AGENTS.md`, это кандидат в `embed`, не в `render`: две полные копии в
дереве (вклейка плюс рендер) инвариант запрещает, и doctor такое ловит.

Тонкий `CLAUDE.md` для первого случая:

```markdown
<!-- devkit:generated body=1a2b3c4d5e6f -->
@AGENTS.md
@../devkit/RULES.md
@../devkit/RULES.board.md
```

Импорт `RULES.board.md` ставится только проекту с доской (признак тот же,
что везде: есть `docs/TASKS.md`). Первая строка помечает файл генерённым и
несёт хеш содержимого, как его положил генератор; ключ зовётся `body`, как
у вклейки, потому что роль та же, ловить ручную правку. Второго хеша
тонкому файлу не нужно: его эталон в любой момент пересчитывается из
профиля и признака доски, протухание видно прямым сравнением. Файл без
маркера doctor считает рукописным и не трогает (шаг 4 миграции), файл с
маркером, но с содержимым, разошедшимся с хешем, это находка «правлен
руками», и `--fix` его не перетирает, а просит перенести правку в
`AGENTS.md`.

### Маркеры вклейки

```markdown
<!-- devkit:rules begin src=1a2b3c4d5e6f body=aabbccddeeff -->
...текст RULES.md и RULES.board.md...
<!-- devkit:rules end -->
```

Хеши это первые 12 hex sha256. `src` считается от конкатенации файлов-источников
в порядке вклейки: он отвечает на вопрос «протухла ли вклейка против devkit».
`body` считается от текста между маркерами, как он был сгенерирован: он
отвечает на вопрос «трогали ли вклейку руками». Вопросы независимы, поэтому
хеша два, одним не обойтись: по свежему `src` не видно ручной правки, по
целому `body` не видно протухания.

Поведение `--fix`: `src` разошёлся, `body` цел, значит вклейка перегенерируется
молча, это штатное обновление после `git pull` devkit. `body` разошёлся,
значит внутри маркеров правили руками: находка с инструкцией перенести
правку наружу (в рукописную часть `AGENTS.md`, если это про проект, или в
сам devkit, если про правила), вклейка не перетирается. Ручная правка
правил в одном проекте это ошибка по построению, вклейка не место для
локальных исключений, но и молча стирать чужой текст `--fix` не имеет права:
его контракт «правки строго additive, заполненное не трогает».

Инвариант одной копии охраняется проверкой doctor: скан дерева проекта на
маркер-блоки `devkit:rules`, больше одного файла с блоком это находка. Сам
блок в `AGENTS.md` при выключении последнего embed-инструмента убирается
`--fix` (вместе с переводом ссылок обратно на `../devkit`): это единственный
случай, когда `--fix` удаляет, и удаляет он только текст между целыми
маркерами с совпавшим `body`.

## Квота: снимок по харнесам

Снимок становится директорией: `~/.devkit/quota/<имя>.local`, по файлу на
харнес, формат строк прежний. Бакеты называются ярусами: у claude-code
общий и обязательный это `week_all`, добавочный дорогой зовётся
`week_max`; какой бакет обязателен у другого харнеса, называет
`required` его профиля. Старые ключи читаются псевдонимами:
`week_fable -> week_max`, `week_opus` остаётся известным и вне лестницы трат,
как сейчас. Таблица «какой ярус из какого бакета тратит» уходит в `[quota]`
профиля (`spend_mini = ["week_all"]`, `spend_max = ["week_all", "week_max"]`),
формула корректора не меняется и продолжает работать по именам бакетов, ничего
не зная про инструмент.

Переезд: старый одиночный `~/.devkit/quota.local` двигает в
`quota/claude-code.local` `doctor --fix`; до переезда читатель, не найдя
нового пути, смотрит старый и говорит об этом хвостом. Refresh пишет всегда
в новый путь.

Одно уточнение к пункту 14 скелета. Формула pace делит остаток окна на его
длину, и длина сегодня прибита константой 7 суток, потому что все бакеты
недельные. Бюджет потокенного инструмента чаще месячный, и с окном 7 суток
pace по нему врал бы всемеро. Поэтому окно берётся из префикса имени
бакета: `week_*` это 7 суток, `month_*` это 30. Сама формула, пороги и
правила сдвига не тронуты, съёмщик бюджетного инструмента просто пишет
`month_all` вместо `week_all`, и это имя стоит в `buckets`, `required` и
`spend_*` его профиля.

### Контракт съёмщика

`agentctl quota refresh` смотрит `[quota] snap` активного харнеса:
`usage-pane` это встроенный tmux-цикл над панелью `/usage`, он остаётся в Go
как есть; `script` запускает съёмщик из `harness/snap/`. Контракт скрипта:

- вход: без stdin; окружение `DEVKIT_HARNESS` (имя), `DEVKIT_QUOTA_BUDGET`
  (число из машинного конфига, только у `budget_based`);
- выход: stdout в точном формате файла снимка, `taken = ...` и строки
  бакетов `имя = NN% сброс <момент>`; для budget_based скрипт сам делит
  потраченное на бюджет и печатает долю;
- отказ: ненулевой код выхода, причина человеческой строкой в stderr,
  stdout игнорируется.

Файл пишет не скрипт, а agentctl: вывод сначала парсится тем же парсером,
которым снимок читается, и только валидный атомарно ложится в
`quota/<имя>.local`. Так у сменного съёмщика то же свойство, что у
pty-цикла: сломавшийся съёмщик отказывает громко и файл не трогает, pick
живёт по прежнему снимку или без сдвига. Тестируется контракт без живого
инструмента подложными скриптами: fixture, печатающий образец вывода,
fixture с мусором (файл не должен измениться), fixture с ненулевым выходом.

## Хуки и проверки текстов

Git-рубеж (`pre-commit`, `commit-msg`) общий для всех харнесов и не меняется:
он висит на git, а не на инструменте, и это база, ниже которой проверки не
опускаются. Рубеж «сразу при записи» есть только там, где профиль объявил
`write` в `[hooks] events`.

Тело каждой проверки одно, меняется разбор входа. Флаг `--hook` получает
аргумент с именем протокола: `check-symbols.py --hook claude-code`. Голый
`--hook` остаётся псевдонимом `claude-code`, чтобы команды, уже прописанные
в settings.json на машинах, не сломались об обновление devkit. Таблица
разборщиков живёт в одном месте, `hooks/hookio.py`: функция на протокол,
вход это stdin события, выход это список фрагментов «путь, записанный
текст» плюс канал ответа (у claude-code это выход 2 с находками в stderr,
который агент получает как фидбек). Каждая проверка импортирует таблицу, а
не носит свой разбор. Тестируется по образцам: `hooks/testdata/<протокол>/`
с живьём снятыми JSON событий, `test.sh` прогоняет каждый образец через
каждую проверку; протокол без образцов в таблицу не принимается.

`check-commit.py` перестаёт ловить следы одного ассистента: к
`noreply@anthropic` добавляются адреса и подписи ходовых остальных
(конкретный перечень снимается с их реальных коммитов при реализации,
родовые `co-authored-by` и `generated with` уже сегодня ловят всех).
`check-memory.py` получает путь индекса из `[hooks] memory_index` и не
подключается setup-ом там, где ключа нет: у инструмента без памяти находки
про индекс это шум.

Уведомитель `notify.py` едет тем же порядком, хотя проверкой текстов не
является: разбор входа он берёт из той же таблицы `hookio.py` по имени
протокола, а setup вешает его на события `notify`, `subagent-done`,
`turn-done` и `prompt-submit` там, где профиль их объявил. Инструмент, который про ожидание действия наружу молчать
не умеет, остаётся без уведомлений, и это не находка, а честное отсутствие
оси. Своей копии платформенной логики у профилей нет: бэкенд выбирается по
платформе и PATH, а нет ни одного, значит уведомитель просит выдать OSC 9
через сам терминал.

## devkitctl setup

Мастер машинного контура, поглощает [DK-032](../tasks/DK-032.md) целиком:
хуки в settings.json (п. 1 той задачи) и глобальная точка правил (п. 2) это
два его шага, отдельной задачи не остаётся. DK-032 закрывается вместе с
задачей мастера (DK-042) со ссылкой сюда.

Шаги, все идемпотентны:

1. найти инструменты: по `[detect] bin` каждого профиля пройтись по PATH;
2. предложить включение найденных и маппинг ярусов из `map_*` профилей,
   спросить бюджет у `budget_based`;
3. записать `~/.devkit/harness.local`;
4. разложить обвязку: определения агентов рендерерами включённых харнесов,
   хуки в конфиги из `[hooks] config` (проверки текстов и уведомитель, по
   всем объявленным в `events` осям; additive-слияние по событию с
   дедупликацией по строке команды, чужие записи не трогаются, разошедшаяся
   с devkit команда остаётся находкой), глобальная точка `[rules]
   global_file`, бинари утилит, `doctor --fix` последним шагом (он же
   генерирует файлы правил).

Неинтерактивный режим обязателен и устроен без второго формата: файл ответов
это готовый `harness.local`, `setup --answers <файл>` валидирует его и
выполняет шаг 4. Интерактивный мастер это способ такой файл написать, машина
без клавиатуры (CI, скрипт раскатки) пишет его сама. Повторный прогон
ничего не меняет: заполненное не трогается, это тот же контракт, что у
`doctor --fix`.

## Наблюдаемость

Сводно, потому что «фича, чей результат виден только чтением исходников, не
закрыта»: резолв харнеса печатает `agentctl harness`, решения корректора
`agentctl quota`, вердикт и его разворачивание `agentctl pick`/`run`
(включая `model: -` с командой настройки), состояние раскладки и дрейф
вклейки `devkitctl doctor`, факт делегирования это строка `--record` в файле
задачи с именем харнеса. Молчащих осей не остаётся: выключенный корректор,
неопределённый харнес и пустой `[delegate]` говорят о себе хвостами причин.

## Миграция по шагам

Порядок подобран так, что Claude Code остаётся рабочим после каждого шага, и
у каждого шага есть проверка этого, а не рассуждение.

1. **DK-036, профиль и слои.** Появляются `harness/claude-code.toml`, парсеры
   подмножества, слияние слоёв, детект, `agentctl harness`. Поведение pick
   не меняется ничем: тест снимает вердикты по фикстурной доске до и после и
   сравнивает побайтно (пункт 20 скелета).
2. **DK-037, ярусы.** Таблицы pick в ярусах, третья строка `tier`,
   псевдонимы в override, корректор и роль ревьювера по ярусам. Проверка:
   те же вердикты, что до правки, плюс строка `tier`, ничего больше не
   двинулось.
3. **DK-038, квота по харнесам.** Директория, псевдонимы бакетов, spend из
   профиля, окно по префиксу, контракт съёмщика, переезд файла. Проверка:
   на старом одиночном файле сдвиги корректора те же, что до правки; после
   переезда те же.
4. **DK-039, генерация файлов правил.** Маркеры, хеши, тонкий CLAUDE.md,
   `AGENTS.project.md` вместо `CLAUDE.project.md`, проверки doctor, миграция
   самого devkit и его шаблонов. Существующих проектов шаг не трогает:
   рукописный CLAUDE.md без маркера это находка-подсказка (`git mv CLAUDE.md
   AGENTS.md`, затем `doctor --fix` генерирует тонкий), а не автоматическая
   перезапись: в живых CLAUDE.md бывают локальные вещи вроде импорта
   корпоративного `RULES.local.md`, автоматике их не разобрать. Проверка:
   прогон doctor на проекте до миграции зелёный по-старому, после `git mv`
   плюс `--fix` контекст сессии Claude Code содержит те же правила.
5. **DK-040, agentctl run.** Режимы, сборка промпта, ограничитель. У
   claude-code `mode = "native"`: run печатает инструкцию, сегодняшний
   конвейер диспетчера не меняется.
6. **DK-041, хуки.** `hookio.py`, `--hook <имя>`, следы ассистентов в
   check-commit, `memory_index` из профиля. Проверка: голый `--hook` в
   прописанных командах работает как раньше, образцы claude-code зелёные.
7. **DK-042, setup.** Мастер, `--answers`, каркас рендера определений с
   claude-code-рендерером. Проверка на чистом окружении (временный HOME):
   setup с файлом ответов только для claude-code даёт машину, неотличимую
   от разложенной сегодняшним `doctor --fix` плюс ручными шагами DK-032.
8. **DK-043..DK-046, профили инструментов.** По задаче на Codex, OpenCode,

Ветки и ревью по правилам доски, каждая задача своя фичеветка.

## Профили инструментов: проверенное и открытое

Правило раздела: в профиль попадает только проверенное живьём или по
официальной спеке; всё остальное открытый вопрос своей задачи, и профиль
инструмента не пишется, пока вопрос не закрыт проверкой.

Проверено и кладётся в дизайн. Источники два: живой съём в этой сессии и
проверка постановки по официальным докам и спекам (июль 2026), у каждой
строки помечено, который:

- Claude Code ставит `CLAUDECODE=1` (живьём в этой сессии, клиент 2.1.220;
  там же видны `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`),
  `[detect]` его профиля: `env = "CLAUDECODE"`, `value = "1"`,
  `bin = "claude"`. Импорты `@путь` в CLAUDE.md работают с относительными и
  домашними путями, это сегодняшняя механика подключения правил (живьём,
  каждый день).
- AGENTS.md: плоский markdown без импортов и include, вложенные файлы по
  дереву с победой ближайшего (по открытой спеке agents.md, проверка
  постановки).
- Codex: вложенные AGENTS.md со слиянием по дереву; механизм подтянуть
  внешний путь в спеке не найден, а блоги про `@file.md` ей не
  подтверждаются, поэтому дизайн принимает осторожную сторону «импортов
  нет», отсюда `mode = "embed"` (проверка постановки по спеке; если задача
  профиля найдёт рабочий импорт, embed меняется на import правкой профиля,
  генератор обе ветки уже умеет).
- Gemini CLI: `@path` импорты и настраиваемое имя контекстного файла в
  `.gemini/settings.json`, отсюда `mode = "import"` (проверка постановки по
  докам).
- OpenCode: массив `instructions` в `opencode.json` с путями, читает
  AGENTS.md, отсюда `mode = "import"` через `config` (проверка постановки
  по докам).
- Cursor: читает AGENTS.md, плюс `.cursor/rules/*.mdc` с frontmatter и
  glob-активацией; `.cursorrules` устарел (проверка постановки по докам).

Открыто, закрывается задачей профиля (DK-043..DK-046 соответственно):

- переменные окружения детекта Codex, OpenCode, Gemini CLI, Cursor: на
  машине этих CLI нет, снять живьём нечем, а детект по памяти это ровно та
  ложная конкретика, которой договорились не писать;
- точные headless-команды и их флаги модели и effort (`codex exec`,
  `opencode run`, headless-режим Cursor и Gemini) и коды выхода: от них
  зависит `command` в `[delegate]`, до проверки режим в профиле не
  фиксируется;
- форматы определений агентов OpenCode и Cursor и наличие их вообще: от
  этого зависит, рендерятся определения или живут только вклейкой в промпт
  cli-режима;
- события и протоколы хуков всех четырёх: есть ли событие записи, чем
  снимаются образцы для `hooks/testdata/`;
- чем снимается остаток у каждого: панель, файл статистики, API с бюджетом;
  до ответа `[quota]` профиля пуст, и это штатно выключенный корректор;
- для Cursor: если его чтения AGENTS.md достаточно, `mode = "render"` в
  `.cursor/rules` может не понадобиться вовсе, решается в DK-046.

## Отличия реализации от дизайна

Копится по ходу серии, задача на строку.

DK-036 (профиль, слои, детект, `agentctl harness`):

- свод валидации проверяет и `required`: бакет, без которого снимок не
  принимается, обязан быть в `buckets`. В своде выше названы только `spend_*`,
  но проверка та же по смыслу, а `required` вне списка это заведомо битый
  профиль;
- хвост причины у неопределённого харнеса зовёт не `devkitctl setup`, а файл
  `~/.devkit/harness.local`: мастера до DK-042 нет, и посылать пользователя
  командой, которой не существует, хуже, чем именем файла. Вернётся на место
  вместе с мастером;
- директорию профилей бинарь ищет цепочкой кандидатов (`DEVKIT_HOME`, корень
  проекта, соседний с проектом клон devkit, `~/projects/devkit`). В дизайне
  вопроса не было, а он есть: agentctl живёт в `~/go/bin` и про свой devkit
  ничего не знает, тогда как devkitctl находит его от `__file__`;
- явное имя (флаг или `DEVKIT_HARNESS`) принимается и когда его нет в списке
  включённых, с заметкой в выводе: имя передаёт `run`, и упираться в машинный
  список тут не за чем. Имя без профиля в `harness/` остаётся отказом, чтобы
  опечатка не уезжала тихо в `default`;
- `[quota]` профиля claude-code объявляет бакеты `week_all` и `week_max`, то
  есть имена из раздела «Квота», а читатель снимка сегодня знает `week_fable`.
  Псевдоним кладёт DK-038; до тех пор секцию не читает никто, кроме валидатора,
  и расхождения в поведении из этого не выходит.

DK-037 (ярусы в таблицах pick, третья строка вердикта):

- pick от поломки контура харнесов не падает. Дизайн описывал два случая с
  `model: -` (харнес не определён, харнес не настроен), а их на деле четыре:
  добавляются ненайденная директория профилей и битый профиль. Читающая команда
  не имеет права отказать из-за инструмента, от которого ярусная половина
  вердикта не зависит, поэтому все четыре дают прочерк с причиной хвостом.
  `agentctl harness` при этом на битом профиле отказывает по-прежнему: у него
  работа как раз в том, чтобы называть поломку;
- хвост «модель та же» ставится только там, где модель известна. Развернуть
  ярус нечем, значит обе стороны сдвига это прочерк, и говорить про
  неизменившуюся модель было бы обещанием несуществующего: хвост тогда обычный,
  `pro -> base`;
- строка `--record` при неразвёрнутом ярусе несёт сам ярус («субагент
  pro/medium»). Дизайн обещал модель, но прочерк вместо исполнителя не
  восстанавливает по файлу задачи ничего;
- снимок вердиктов из DK-036 остался тем же файлом и не переснимался. Снимок с
  новой строкой доказывал бы только то, что код совпадает сам с собой, поэтому
  `TestPickVerdictsUnchanged` сверяет сегодняшний вывод со старым снимком через
  обратный перевод: строка `tier` снимается, слова ярусов разворачиваются в
  старые имена по таблице псевдонимов. Мимо этого перевода не проходит ничего,
  кроме самого переименования ступеней, а сегодняшний вид вердикта держит второй
  снимок `pick-verdicts-tiers.txt`;
- псевдонимы override сделаны одной таблицей «значение -> ярус» вместо двух
  списков, и ошибка теперь говорит про неизвестный ярус, перечисляя и имена
  ступеней, и старые имена моделей, и запрет на модель инструмента.

DK-038 (директория снимков, бакеты ярусами, spend из профиля, съёмщик):

- `week_opus` объявлен третьим бакетом в `buckets` профиля claude-code, а не
  списком в коде. Дизайн просил «известный и вне лестницы трат», и из профиля
  это выходит само: бакет в `buckets` есть, ни в один `spend_*` не входит,
  поэтому читается, печатается с пометкой и сдвига не даёт. Псевдонимом он не
  стал сознательно, это другой бакет, а не `week_max` под старым именем;
- свод валидации пополнился префиксом имени бакета: `week_` или `month_`, иначе
  отказ. Окно берётся из префикса, и `quarter_all` молча посчитался бы недельным,
  то есть pace врал бы вчетверо, а профиль выглядел бы принятым;
- годность вывода съёмщика определена строже, чем «валидный»: разобран без
  единого предупреждения, есть момент снятия и обязательный бакет. Файл на диске
  пишут и руками, ему битую строку простить можно, а машине нет: её «почти
  снимок» лучше отбросить целиком, чем записать наполовину. Отдельным отказом
  идёт `budget_based` без бюджета в машинном конфиге, иначе съёмщик получил бы
  `DEVKIT_QUOTA_BUDGET=0` и честно поделил на него;
- контур харнеса резолвится один раз на вызов pick (`harnessContext`): из него
  берётся и объявление квоты, и маппинг ярусов. Поломка контура объясняется
  одной причиной, а не двумя: следствий у неё два (разворачивать ярус нечем и
  корректор без профиля выключен), и хвост вердикта говорит про оба сразу;
- `agentctl quota` при неопределённом харнесе или пустой секции `[quota]`
  отказывает ненулевым кодом, тогда как pick в том же положении печатает вердикт
  с хвостом причины. Разница по роли: команде quota нечего читать и некуда
  писать, а вердикт от инструмента не зависит;
- панель `/usage` пишет в снимок уже каноничные имена (`week_max`), псевдоним
  работает только на чтение. Иначе refresh возвращал бы в файл имя, которое сам
  же переводит;
- сверка вердиктов со снимком DK-036 получила вторым механическим переводом
  подмену пути снимка (`quota/claude-code.local` обратно в `quota.local`): путь
  стоит в хвосте причины, и без перевода снимок пришлось бы переснимать, потеряв
  его доказательную силу.

DK-039 (генерация файлов правил, AGENTS.md источником):

- devkit сам себе проект, и своё ядро он себе не импортирует: в его тонком
  файле стоят `@AGENTS.md` и `@RULES.board.md`, а `RULES.md` нет. Дизайн этого
  случая не разбирал, а он единственный, где файлы правил и проект это один
  репозиторий: ядро приезжает в сессию глобальным подключением, и второй импорт
  был бы ровно той копией, которую задача убирает. Правило прибито к совпадению
  корня проекта с корнем devkit, машину генератор не спрашивает: иначе один и
  тот же коммитимый файл выходил бы разным на разных машинах. `global_file`
  профиля для этого не понадобился и ждёт мастера настройки;
- строка импорта в рукописной части `AGENTS.md` это находка. Дизайн говорил
  «плоский markdown, без импортов» как про свойство формата, но после
  `git mv CLAUDE.md AGENTS.md` строки импорта остаются на месте, и без находки
  правила молча перестали бы доезжать до инструментов, которые импортов не
  понимают;
- маркеры и строки импорта внутри блоков кода не считаются ни вклейкой, ни
  импортом. Проверка инварианта одной копии иначе спотыкалась бы о собственную
  документацию: примеры маркеров стоят и в этом LLD, и в доке devkitctl;
- пустой список включённых харнесов это находка, а не тишина. Проектный слой
  сузить машинный список до нуля может (имя, которого в машинном слое нет, им
  не включить), и молчание тут неотличимо от штатной работы, тогда как правила
  не доезжают никуда;
- у включённого харнеса с битым или пропавшим профилем находка своя, рядом с
  находкой валидатора: сам битый профиль называет проверка из DK-036, а тут
  говорится следствие, что файлы правил по нему не сгенерятся;
- режим `render` файлов пока не генерит и говорит об этом находкой. Рендерер
  чужого формата едет задачей профиля своего инструмента (DK-046), а молчаливое
  «правила не доехали» тут ровно то, чего задача не допускает;
- вклейка кладётся в конец `AGENTS.md`. Дизайн места не называл, а конец удобен
  тем, что правка рукописной части выше ничего не сдвигает.

выше; DK-032 поглощена задачей DK-042 и закрывается при её закрытии со
ссылкой сюда; DK-029 остаётся своей задачей и после DK-039 меряет вес по
сгенерённым файлам активного харнеса. Отличия от этого дизайна, всплывшие в
реализации, фиксируются здесь же, как это сделано в DK-010.
