# DK-112: LLD дашборда управления агентской разработкой

## Задача и рамка

Цель DK-112 это веб-дашборд на машине агентской разработки с заходом с любого
устройства: доска и текущие работы, запуск и стоп задач и целей, живой статус
агента, переписка через состояние цели, правка задач, лента уведомлений,
несколько проектов сразу. Крупное решено постановкой цели: код это компонент
devkit, Go-сервер с вшитой статикой, источник правды это доска и утилиты
taskctl/agentctl/shipctl, своей базы нет, канал вынесен в решение выката,
признак проекта `docs/TASKS.md`.

Этот LLD снимает развилки уровнем ниже: граница сервер-клиент, состав API,
вход, способ брать данные, раскладка кода, конфиг корней, запуск и выкат. По
каждой развилке стоит одно решение с причиной, отвергнутые варианты названы;
исполнителям DK-217..DK-222 остаются детали реализации. Экраны рисует DK-216
параллельно, состав экранов задан целью, а не этим документом.

## Граница сервер-клиент

Решение: считает всё сервер, клиент только рисует. На сервере живут разбор
досок, склейка транскрипта в ленту реплик, хвосты журналов, поиск проектов,
запуск и стоп, коммиты правок. Клиент это пять экранов DK-216, которые
получают готовый JSON и шлют команды; своего состояния у него нет, кроме куки
входа и открытого экрана.

Причины три. Правда одна: логика доски уже лежит в утилитах, и второй разбор
на клиенте разъехался бы с первым на любой правке формата. Клиент на телефоне
обязан быть тонким: транскрипт сессии весит мегабайты, и тянуть его целиком в
браузер ради последних реплик нельзя, режет его сервер. И граница доверия
проходит по серверу: он аутентифицирует, он исполняет код, ему и решать, что
показывать и что принимать.

Толстый клиент отвергнут и технически: у браузера нет доступа ни к файлам
машины, ни к подпроцессам, так что «клиент сам читает доску» означало бы
сырой файловый прокси на сервере, то есть тот же сервер, но с размазанной
логикой и разбором markdown на JS.

### Статика без внешних зависимостей

Клиент пишется руками: HTML, CSS и ES-модули без транспиляции, браузеры
понимают их без сборки. Статика лежит в `tools/dashboard/static/` и вшивается
в бинарь через `go:embed`, наружу сервер не ходит ни за одним байтом.

Отвергнуты все варианты с третьей экосистемой. Фреймворк с CDN ломает правило
внешних зависимостей и оффлайн-работу дома. Вендоренный фреймворк в репозитории
это та же зависимость, только с ручными обновлениями и чужим кодом на ревью.
Бандлер и TypeScript требуют node в сборке devkit, который ставится на голую
машину и в корп-контуре, где тянуть тулчейн неоткуда; у go и python внешних
зависимостей нет, и заводить их для статики нет причины. Объём клиента
(пять экранов, формы и ленты) в vanilla-код помещается без страданий.

Для разработки у `serve` есть ключ `--static <dir>`: статика читается с диска,
правка видна по F5 без пересборки; по умолчанию работает вшитая.

### Живые данные

Живые потоки (журнал цикла, транскрипт, лента уведомлений) едут через
Server-Sent Events: те же GET-ручки с параметром `?stream=1` держат соединение
и дописывают события. SSE выбран за цену: браузерный `EventSource` сам
переподключается, серверная сторона это цикл записи в ответ, зависимостей ноль.
WebSocket отвергнут: двусторонний канал не нужен (команды клиента идут
обычными POST), в stdlib его нет, а свой разбор RFC 6455 с фреймами и масками
это цена без покупателя. Сплошной опрос отвергнут для потоков (лаг и батарея
телефона), но остаётся там, где событийного источника нет: снимок tmux-пейна
экран перечитывает по таймеру, пока открыт, а доску по фокусу и после своих
действий.

За хвостами файлов сервер следит опросом размера и mtime раз в секунду:
fsnotify в stdlib нет, а секундный опрос пары файлов стоит копейки и не
зависит от платформы.

## Состав API

Все ручки под `/api`, JSON, вход кукой (раздел «Вход и секрет»); вне входа
живут `/healthz` и страница `/login` со своей обвязкой (стиль и скрипт формы:
данных в них нет, а рисовать форму входа без них нечем; уточнение DK-217).
Версионирования нет: клиент вшит в тот же бинарь и другой версии клиента не
бывает, а smoke-сценарий DoD ходит тем же API с той же машины, читая токен из
конфига.

Проект в путях называется именем своего каталога; коллизия имён из разных
корней это ошибка конфига, сервер называет её на старте и в `/healthz`, а не
молча берёт первый попавшийся.

Экран доски:

- `GET /api/projects`: проекты по конфигу корней: имя, путь, счётчики секций,
  живые работы (tmux-сессии `goal-*`/`task-*` и цели из реестра
  `~/.devkit/goals`);
- `GET /api/projects/{p}/board`: секции доски со строками и метаданными, из
  `taskctl list --json`.

Экран задачи:

- `GET /api/projects/{p}/tasks/{id}`: строка и секция, текст файла задачи,
  зависимости в обе стороны (`dep list --json`), замечания ревью (уточнение
  DK-221: соседи по зависимости идут с заголовком и секцией, чтобы карточка
  читалась без похода на доску; отсутствие файла задачи называется словами);
- `PATCH /api/projects/{p}/tasks/{id}`: заголовок, тип, разбивка ранга, цена,
  ссылка; сервер зовёт `taskctl set`, порядок строк выводится из ранга, и
  перетаскивания мимо ранга в API нет по решению постановки (уточнение
  DK-221: слагаемые ранга едут списком `r_parts` из пяти значений,
  пропущенное остаётся прежним, так правится и одно слагаемое, и разбивка
  разом; отказ утилиты это 400 её же словами, ненайденный бинарь и сорванный
  срок это 502; уточнение DK-244: поправку на баг ручка сверяет с типом сама и
  отбивает 400 для `task` со стоящим слагаемым, не спрашивая taskctl, потому
  что шкала RANKING.md отдаёт это слагаемое дефекту, а не новой работе; тип и
  слагаемые едут одним запросом, поэтому сверяется то, что получится после
  правки, а не то, что стояло в строке);
- `POST /api/projects/{p}/tasks/{id}/move`: перевод статуса через
  `taskctl move`, рубежи (сценарий проверки, слитый код, причина blocked)
  остаются в утилите и доезжают до клиента её текстом ошибки;
- `PUT /api/projects/{p}/tasks/{id}/file`: текст файла задачи целиком; сервер
  пишет файл и коммитит с пушем, как положено правке `docs/tasks/`
  (уточнение DK-221: заводит файл `POST` той же ручки через `taskctl file`,
  та же команда чинит ссылку в строке, и правка текста поверх ненайденного
  файла отбивается словами);
- `POST /api/projects/{p}/tasks/{id}/deps` и
  `DELETE /api/projects/{p}/tasks/{id}/deps/{dep}`: `taskctl dep add`/`dep rm`
  (уточнение DK-221: коммит доски идёт тем же порядком, что у сообщения витку,
  и провал пуша правку не отменяет, а называется полем `note`).

Запуск и стоп:

- `POST /api/projects/{p}/runs {"id": "DK-NNN"}`: старт. Цель поднимается
  готовой оболочкой `goal-run.py <ID> -C <корень>` в её tmux-сессии
  `goal-<ID>`; одиночная задача поднимается tmux-сессией `task-<ID>` с
  headless-сессией конвейера задачи, промпт и обвязку выбирает DK-218
  (уточнение DK-218: `claude -p` из корня проекта с промптом «возьми задачу
  <ID> в работу и доведи её конвейером по скиллам board-task и board-ship»;
  оболочку goal-run сервер ищет по корням конфига, как проекты, потому что в
  PATH она не ставится, а чекаут devkit лежит среди проектов);
- `DELETE /api/projects/{p}/runs/{id}`: стоп. Перед убийством tmux-сессии
  сервер дописывает в журнал цикла строку про стоп из дашборда
  (`goal-run.py --say`), чтобы стоп был виден там же, где виден ход; замок
  оболочки снимается сам по мёртвому pid. Стоп называется стопом и в API:
  ручки «пауза» нет, возобновление это новый `POST /runs`. Живую сессию чата
  дашборд не убивает: она не его, а запись в реестр целей кладёт гейт бюджета
  у обоих носителей цикла и носителя не хранит, так что цель из реестра без
  tmux-сессии `goal-<ID>` дашборд показывает как ведущуюся снаружи, без
  кнопки стопа.

Живой статус:

- `GET /api/projects/{p}/goals/{id}/log`: хвост журнала цикла
  `.devkit/goal-<ID>.log`, с `?stream=1` продолжается по мере записи;
- `GET /api/projects/{p}/sessions`: сессии проекта из `~/.claude/projects/`:
  каталог берётся по пути проекта с дефисами вместо слэшей (уточнение DK-219:
  дефисом заменяется любой символ кроме букв, цифр и самого дефиса, так имя
  совпадает с раскладкой Claude Code и для путей с точками), плюс каталоги,
  чьё имя продолжает его дефисом, так в список попадают деревья задач и копия
  окна; по сессии отдаются id, время последней записи, ветка и первая реплика;
- `GET /api/projects/{p}/sessions/{sid}`: лента реплик из транскрипта, сервер
  разбирает jsonl и отдаёт последние N с пагинацией назад (`?before=`), с
  `?stream=1` дописывает новые; вызовы инструментов сворачиваются в одну
  строку, тянуть их содержимое на телефон незачем (уточнение DK-219: блоки
  размышлений сворачиваются в пометку без текста, ветки субагентов в ленту
  не попадают);
- `GET /api/tmux` и `GET /api/tmux/{name}`: список сессий и снимок пейна
  через `capture-pane` (уточнение DK-219: цель снимка это `=имя:`, точное
  совпадение имени сессии, иначе tmux взял бы соседку по префиксу).

Переписка:

- `POST /api/projects/{p}/goals/{id}/message`: сообщение человека уходит в
  состояние цели, а не в идущий процесс, это решение постановки. Формой
  выбран раздел «Входящие» в файле цели: строка «- дата, из дашборда: текст»,
  коммит с пушем как у любой правки `docs/tasks/`. Виток читает файл цели
  целиком первым шагом, так что отдельного канала доставки не нужно;
  отработав, он убирает строку из «Входящих» (сторона goal-loop едет в
  DK-220), и пока строка лежит, дашборд честно показывает «ждёт витка».
  Отправка виток не поднимает: кнопка запуска рядом, а поднимать цикл молча
  значило бы изобразить паузу, которой нет. Уточнение DK-220: раздела
  «Входящие» goal-start не заводит, и первый POST ставит его перед
  «Журналом» (без «Журнала» в конец файла); сообщение схлопывается в одну
  строку списка, иначе хвост многострочного текста выпал бы из разбора. GET
  той же ручки отдаёт лежащие строки, по ним клиент и показывает «ждёт
  витка»; провал коммита или пуша запись не отменяет и называется полем
  note.

Лента уведомлений:

- `GET /api/notifications`: хвост журнала уведомителя `~/.devkit/notify.log`
  (время, сессия, повод, уровень, бэкенд, цель перехода, код возврата), с
  `?stream=1` живая лента. Свой канал наружу дашборд не заводит: отправку
  держит `hooks/notify.py`, а лента это окно в его журнал. Стоп агента,
  wait-human и завершение задачи попадают сюда потому, что их уже зовут виток
  и `taskctl move`. Уточнение DK-222: журнал уведомителя тремя типами DoD не
  владел, и задача добавила ему два поля вместо своего канала. Аргументный
  вызов уведомителя берёт повод словом (`--reason`), и его ставят виток
  (`goal_stop`, `wait_human`) и `taskctl` (`task_check`, `task_blocked`,
  `task_fail`); текст баннера едет хвостом строки журнала в ёлочках, иначе
  лента показывала бы событие без слов. Стоп из дашборда зовёт тот же
  уведомитель поводом `run_stop`: снятая tmux-сессия оболочку не будит, и
  сказать о стопе больше некому, а канал остаётся один. Тип события лента
  выводит из повода (`stop`, `wait`, `task`, `other`), по нему же идёт фильтр
  `?kind=`; ID работы достаётся из текста уведомления, своего поля с ним у
  журнала нет. Отметок прочитанного нет: хранить их серверу негде, а
  состояния клиента у дашборда по этому же LLD не бывает.

Вход и служебное:

- `POST /api/login` и `POST /api/logout`;
- `GET /healthz`: без входа, отвечает `ok`, версию, аптайм и число проектов.

Конвейерные шаги (ревью, слияние, выкат) в API не входят: их гоняет агент
внутри запущенной сессии, и дублировать `shipctl` кнопками значило бы завести
второго диспетчера с теми же замками. Дашборд запускает работу и смотрит на
неё, а не исполняет конвейер сам.

## Вход и секрет

Дашборд исполняет код на машине, и сетевому периметру он не доверяет ни при
каком канале: вход обязателен и дома, и через xr-proxy. Ролей нет, любой
вошедший может всё; половинчатый read-only отвергнут как ложная безопасность,
чтение транскриптов и досок это уже полный доступ к содержимому работы.

Решение: единый секрет-токен и подписанная кука.

- Секрет это 256 бит случайности, рождается на машине при первом старте
  `serve` и живёт строкой `token` в `~/.devkit/dashboard.local` с правами 600.
  По сети он не ездит и в репозиторий не попадает: файл лежит рядом с
  `harness.local` и снимками квоты, вне git.
- Вход: страница логина, пользователь вставляет токен (печатает его команда
  `dashboard secret` на машине; на устройство он переносится руками один раз
  и живёт в менеджере паролей). Сервер сверяет токен константным временем и
  ставит куку HttpOnly SameSite=Lax со сроком 30 дней: значение это срок
  действия с подписью HMAC-SHA256 от секрета, состояния сессий на сервере
  нет, и рестарт демона никого не разлогинивает.
- Утечка: `dashboard secret --rotate` заменяет секрет, и все куки разом
  мертвы, потому что подпись перестаёт сходиться; новый токен вводится
  заново. Утечка одной куки ограничена её сроком и тем же rotate. Перебор
  токена гасится паузой после провала входа и строкой в журнале сервера.
- CSRF закрыт SameSite=Lax и сверкой Origin на изменяющих методах; XSS тем,
  что тексты досок и транскриптов рисуются текстом, а не HTML, и CSP
  запрещает инлайн и внешние источники.

TLS сервер не заводит и слушает голый HTTP: канал это решение выката, а не
архитектуры (постановка цели). Извне HTTPS даёт браузерный вход xr-proxy,
дома канал защищает своя сеть; самоподписанный сертификат отвергнут, потому
что доверие к нему на телефоне ставится руками, а привычка прощёлкивать
предупреждения стоит дороже, чем он защищает. Аутентификация при этом своя
при любом канале: она отвечает за вход, канал за прослушивание.

Заход извне (DK-223) канал подключил публикацией xr-proxy на `127.0.0.1:7112`,
и одно его следствие видно в коде: посредник ставит апстриму свой адрес в
`Host`, а внешнее имя кладёт в `X-Forwarded-Host`, как обычный reverse-proxy.
Сверка `Origin` берёт имя оттуда (`externalHost`), иначе за каналом падал бы
сам вход, а не только правки. Сверка от этого не слабеет: подставить заголовок
из браузера чужая страница не может, форма своих заголовков не ставит, а
`fetch` со своим упирается в предполётный запрос, на который дашборд не
отвечает. Шаги подключения и команды проверки живости канала в README
дашборда, раздел «Заход извне».

Отвергнутые варианты входа. Пара логин-пароль: второго пользователя нет, а
токен и есть пароль полной энтропии без словарных привычек. mTLS: выпуск и
установка клиентских сертификатов на телефон дороже пользы при одном
пользователе. Внешний OAuth или passkey-провайдер: внешняя зависимость и
чужой периметр в контуре, который обязан работать из домашней сети без
интернета. HTTP basic: секрет летит в каждом запросе и живёт в браузере без
срока и выхода, утечка любого одного запроса равна утечке секрета, кука со
сроком ограничивает ущерб.

## Откуда сервер берёт данные

Граница проведена по владению форматом: состоянием, у которого есть утилита с
инвариантами, дашборд командует только через её подпроцесс; журналы и потоки,
у которых утилиты нет, читаются с диска напрямую.

Через подпроцессы:

- `taskctl`: чтение доски и задач (`list --json`, `show --json`,
  `dep list --json`; флаг `--json` добавляет DK-217, печатный вывод не
  меняется) и все правки строк (`set`, `move`, `dep add`/`rm`) с `-m` и
  `--push`. Разбирать человеческий вывод хрупко, он для людей и меняется
  свободно, а дублировать разбор markdown доски в дашборде значит получить
  два разбора, которые разойдутся на первой правке формата;
- `tmux`: `ls` и `capture-pane`;
- `goal-run.py`: запуск цикла цели и строка `--say` при стопе;
- `git`: коммит и пуш правок файлов задач и целей, отсев линкованных worktree
  при поиске проектов.

Напрямую с диска: `.devkit/goal-<ID>.log`, реестр `~/.devkit/goals`,
`~/.devkit/notify.log`, транскрипты `~/.claude/projects/*/*.jsonl`, тексты
файлов задач и целей. У всего этого нет ни утилиты чтения, ни инвариантов
записи, которые можно было бы нарушить; транскрипты и журналы вообще пишутся
чужими процессами, и подпроцесс тут нечего было бы звать.

Линковать код taskctl как go-библиотеку вместо подпроцесса отвергнуто: его
разбор живёт в `package main`, выделение библиотеки это перестройка утилиты
ради одного потребителя, и версии разъехались бы, ведь бинарь в PATH один на
машину, а дашборд собирался бы из другого среза. Подпроцесс держит одну
правду и одну версию поведения.

Прецедент обратного решения известен и не подходит: сторожок `devkitctl
watch` читает доску сам, потому что обязан работать и на машине со сломанными
бинарями. У дашборда довод противоположный: он живёт на машине разработки с
утилитами в PATH, и честная ошибка «taskctl не нашёлся» полезнее выживания с
собственным разбором, который молча устареет. Ищется taskctl сначала рядом с
собственным бинарём дашборда, потом по PATH: под launchd PATH системный, а
утилиты devkit лежат одним каталогом (уточнение DK-217 по шагу 5 сценария).

`shipctl` и `agentctl` дашборд не зовёт вовсе: слияние и выкат остаются
агенту внутри запущенной сессии, выбор моделей конвейеру, а квота в экраны
цели не входит.

Пуш правок доски из дашборда рубеж `pre-push` не отбивает: рубеж смотрит
переменные сессии агента, а у демона их нет. Это честно, кнопку жмёт
пользователь. Отбитый пуш при ушедшей вперёд доске сервер лечит одним
`pull --ff-only` с повтором, дальше возвращает ошибку клиенту, а не решает
конфликт сам.

## Раскладка кода

Инструмент живёт в `tools/dashboard/`: имя директории это имя команды, внутри
исходники, тесты, `testdata/` и `README.md`, язык один. Подкоманды:
`serve` (демон), `secret` (напечатать токен, `--rotate` сменить). Статика в
`tools/dashboard/static/`, вшивается `go:embed`.

Язык go по правилу раскладки: инструмент ставится в PATH релизом devkit и
зовётся по имени на любой машине с доской, `net/http` и `embed` лежат в
stdlib, внешних зависимостей не появляется. Python отвергнут правилом (он для
того, что обязано работать до сборки: хуки, подключение, диагностика) и
отсутствием вшивания статики; постановка цели и так решила go.

Отвергнутые имена. `dashctl`: суффикс `-ctl` у нас носят утилиты, которые
командами правят чужое состояние, а тут долгоживущий сервер. `dash`: имя
занято шеллом `/bin/dash` на linux, коллизия в PATH. `boardview`: доска лишь
один экран из пяти. Слово `dashboard` длинно, но руками команда зовётся
редко, процесс держит launchd.

`devkitctl build` и `update` пополняются новым бинарём той же задачей DK-217,
что заводит инструмент; список утилит в ключе `test` обвязки выката devkit
дополняет там же его владелец.

## Конфиг корней

До машинного конфига DK-042 конфиг дашборда живёт в
`~/.devkit/dashboard.local`, формат «`key = value`, `#` комментарий», тот же,
что у `.devkit/deploy.local` и `~/.devkit/watch.local`: разбор такого файла в
devkit уже написан и знаком глазу, вложенность здесь не нужна. Ключи:

```text
# корней несколько, по строке на каждый
root = ~/projects
root = ~/work
addr = 0.0.0.0
port = 7112
token = <секрет входа>
```

Права файла 600, потому что в нём секрет; отдельный файл под секрет отвергнут
как второй файл с теми же правами и тем же временем жизни. Незнакомый ключ
это ошибка старта, а не молчаливый пропуск, как у строк бюджета в `spend`.
Умолчаний для `root` нет: пустой список корней сервер называет в `/healthz` и
журнале, а не подставляет `~/projects` молча. Порт по умолчанию 7112, по
номеру цели; `addr` по умолчанию слушает все интерфейсы, доступ решает канал,
вход решает секрет.

Проект узнаётся как у devkitctl, по `docs/TASKS.md`: проектом считается сам
корень или его прямой подкаталог с доской, глубже обход не идёт, чтобы не
ползать по деревьям сборки. Боковые деревья задач (`../<проект>-<id>`) и
копия окна отсеиваются признаком линкованного worktree, расхождением
`git rev-parse --git-dir` и `--git-common-dir`, как у рубежа taskctl: у них
та же доска, и без отсева каждый проект множился бы на свои деревья. Список
корней в конфиге дашборда это решение постановки, реестра проектов devkit не
заводит; при появлении DK-042 список переезжает в машинный конфиг, форму
переезда решит он.

## Запуск, выкат и наблюдаемость

Процесс держит launchd-агент `ru.devkit.dashboard` с KeepAlive: plist кладёт
и поднимает `devkitctl doctor --fix` по образцу сторожка
`ru.devkit.goal-watch`, там же доктор проверяет, что агент поднят и `/healthz`
отвечает. Живость по `/healthz` доктор меряет после первого старта сервера
(конфиг с секретом кладёт сам `serve`, и пока файла нет, порт не назначен и
стучаться некуда); уточнение DK-217. Агент показывает не на чекаут, а на
бинарь из PATH, но кладётся всё равно только из основного чекаута, как у
сторожка: на машину едет проверенное. На других платформах носителя пока нет,
и доктор говорит об этом находкой, как у сторожка: команду ставят в systemd
руками. Свой демонизатор
отвергнут: менеджер процессов у машины уже есть, а переписывать KeepAlive
руками значит хуже.

Выкат devkit это `deploy = devkitctl build`, пересборка бинарей в PATH, и
дашборд в неё встаёт без правки обвязки: демон раз в несколько секунд
смотрит на иноду собственного бинаря и, заметив замену, доживает начатые
ответы и выходит, а KeepAlive поднимает уже новый. Так правка доезжает
командой deploy до работающего процесса. Шаг `launchctl kickstart` в команде
выката отвергнут: deploy у devkit один на все утилиты, и знание про демона
размазалось бы по обвязке каждой машины; самонаблюдение работает и при
ручном `go build` мимо выката.

Наблюдаемость:

- журнал `~/.devkit/dashboard.log`: старты и остановки, входы и провалы
  входа, изменяющие запросы с кодом ответа, ошибки. Чтения в журнал не
  пишутся, иначе опрос открытых экранов зарастил бы его за день;
- `GET /healthz` без входа: `ok`, версия, аптайм, число проектов, ошибки
  конфига. Версия вшивается как у остальных утилит, и по её смене выкат
  проверяется машинно, это тот самый идентификатор выкаченного билда из
  правил выката;
- следы действий лежат там же, где у ручной работы: правки досок оставляют
  строки в `.devkit/log` проектов через taskctl, запуск и стоп циклов видны
  в `.devkit/goal-<ID>.log`, уведомления в `~/.devkit/notify.log`. Дашборд
  не заводит второй истории поверх существующих.

Молчание различимо: пустая доска, пустой список проектов и недоступная
утилита это разные ответы API с причиной, а не одинаковый пустой экран.
Сервер, который не нашёл `taskctl` в PATH, говорит об этом в `/healthz` и в
каждом ответе доски, потому что тихая деградация здесь неотличима от «задач
нет». Ненайденный `tmux` называется так же, а не отдаёт молча пустые работы:
«tmux не нашёлся» и «сессий нет» это разные ответы, и штатным пустым списком
остаётся только второй (tmux ls без своего сервера отвечает ненулевым кодом);
PATH launchd-агенту с брю-каталогами дописывает `doctor --fix` (уточнение
DK-217 по шагу 5 сценария).

## Тесты

Сами тесты едут задачами серии вместе с кодом, направление такое (уточнение
DK-222: сверх них у инструмента есть сквозной прогон `dashboard smoke`, он
проходит агентскую часть DoD цели на синтетическом окружении, гоняется руками
и тестом и остаётся сторожем дашборда; язык go по правилу раскладки, у
инструмента он один, и отдельного скрипта в `tools/dashboard/` быть не может):

- API поверх `httptest` и синтетического проекта в `testdata/` (доска, файлы
  задач, журналы); подпроцессы (`taskctl`, `tmux`, `goal-run.py`) подменяются
  исполняемыми фикстурами в `testdata/`, как принято изображать чужую
  программу;
- вход: подпись и срок куки, ротация гасит старые куки, сравнение секрета
  константное, Origin на изменяющих, пауза после провала. Мутации, на
  которых обязан краснеть тест: кука без подписи принята, срок не проверен,
  rotate не отзывает выданное;
- конфиг: разбор, тильда в корнях, незнакомый ключ ошибка, права файла;
- потоки: хвост растущего файла, обрыв SSE, битая строка jsonl пропускается
  без обрушения ленты;
- поиск проектов: линкованный worktree отсеян, коллизия имён это ошибка
  конфига.
