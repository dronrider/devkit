# DK-1469: типы черновиков и подтверждение предложений

Постановка и ответы человека лежат в [DK-1469](../tasks/archive/2026/DK-1469.md).
Требования перенесены из пункта 6 [DK-1198](../tasks/DK-1198.md), кейсов
3, 4, 9 и 10 принятого состава и приписки DK-1222. Повторного выбора состава
не требуется. Решения согласованы на разборе 2026-10-29. Ход реализации, результаты
проверок и состояние поставки записываются в файле задачи.

## Пользовательский путь

Пользователь сохраняет текст в накопитель. Тип можно оставить «задача»,
источник «мысль», замок снятым. У старого файла без новых полей те же
умолчания. В полной форме тип, источник и замок видны рядом с текстом,
быстрая запись обходится одним абзацем.

Разбор использует правило выбранного типа. Для разработки сначала проходит
интервью. Его согласованный состав описывает будущую работу. После разбора
пользователь видит карточки предполагаемых результатов. До принятия карточек
доска и задачи сохраняют прежнее содержимое.

В карточке видны исход, будущий текст, срок, назначение, место приписки и
зависимости, когда они есть. Пользователь может поправить предложение,
принять одно, принять все по записи или все показанные в накопителе,
отклонить ненужное. После применения рядом доступны ID и ссылки на результаты.
Непринятые карточки остаются у исходной записи.

Пустой разбор показывает «ничего не выделено» и возможность ручного
оформления. Ошибка разбора показана отдельно с повторным запуском. У записи
с замком до подключения локальной модели виден статус «ждёт локальную
модель». Облачный процесс для неё не поднимается.

Человек договорённости это ответственный за исполнение. Полностью
разобранная запись уходит из накопителя в историю. Исходный текст,
предложения, решения и ссылки на результаты сохраняются. Оба решения
приняты пользователем 2026-10-29. Словом «входящие» в вопросе был назван
действующий накопитель черновиков.

## Словарь и шапка записи

Определения лежат в `kit/draft-types/<имя>.toml` и
`.devkit/draft-types/<имя>.toml`. Схема поиска kit повторяет шаблоны планов.
Общий разбор TOML используется из `internal/subtoml`. Код словаря и чтения
метаданных нужен taskctl и дашборду, его место в общем пакете `internal`.
Встроенные определения поставляются автоматикой devkit, проектные
переопределения остаются файлами проекта.

У определения есть стабильный ключ, русское название, версия схемы, одно
правило разбора, умолчания и перечень обязательных полей результата. Правило
это ссылка на скилл либо текст промпта. Определение не содержит исполняемой
строки shell. Отсутствующий скилл и неизвестное поле показываются с путём
файла до запуска разбора. Непустое неверное определение не заменяется молча
встроенным. Пустой проектный файл обрабатывается по принятому в DK-972
правилу с предупреждением.

Первый набор состоит из задачи, договорённости, вехи и контроля. Тип строки
доски выбирается из `bug`, `task`, `LLD`. Веха оформляется обычной строкой со
сроком, контроль использует поля и проверку DK-1470. Определение типа
черновика не расширяет словарь строк доски.

В шапке черновика рядом с датой и приоритетом появляются тип, источник и
замок. Источник выбирается из мысли, встречи, почты, мессенджера и ссылки.
Ссылка или канал в тексте не меняют замок. Дата, приоритет и новые поля
читаются одним разбором шапки до первого раздела. Совпавшая строка внутри
тела остаётся текстом.

Метаданные выводятся в `draft list --json` и при чтении записи. При обычном
оформлении и приписке тип и источник сохраняются в сведениях о
происхождении. Приоритет разбора по прежнему правилу снимается. Замок
должен учитываться у сохраняемого материала до любого следующего запуска
модели, включая продолжение работы с результатом. Простого переноса слова
«конфиденциально» в текст для этого недостаточно.

## Договор карточек

У карточки свой устойчивый ID в пределах исходной записи, редакция, исход,
текст результата и довод разбора. Данные исхода типизированы. Для новой
строки нужны заголовок, тип строки, полное тело по TASKFORM, ранг, цена и вид
приёмки. Для приписки нужны ID назначения и текст. У отсрочки есть причина
и при необходимости дата возврата. У удаления есть причина. Срок,
назначение и контроль проверяются действующими командами.

Ссылка «после» может вести на существующую строку или на другую карточку.
Ссылки на карточки заменяются полученными ID при применении. Неизвестная
ссылка и цикл считаются ошибкой до записи. Приём зависимой карточки требует
уже принятого предшественника либо его включения в тот же показанный набор.
Предшественник не включается скрыто за пользователя.

В запись сохраняются исходный материал, предложения и результаты решений.
У принятых карточек остаются применённая редакция, полученные ID и точный
результат. Их нельзя незаметно превратить в другое предложение. Повторный
разбор дополняет материал, сохраняя ранее применённое и непринятое.
Когда по всем предложениям принято решение, исходная запись переносится в
историю разбора. Удаление из активного списка не удаляет исходный текст.
Разбор без предложений остаётся в накопителе для ручного оформления.

Четыре исхода применяются к указанному в карточке материалу. Несколько
карточек не должны по очереди расходовать общий исходный файл. На этапе
реализации нужно выделить из команд подготовку результата и запись с общим
набором проверок. В дашборде не создаётся вторая реализация `add`, `attach`,
`defer`, `drop`, `set` или `dep add`. Прямые вызовы этих команд сохраняют
прежнее поведение.

До применения строится полный план выбранных исходов во временном дереве.
Проверяются форма, обязательные поля типа, назначения, зависимости и все
планируемые записи. Выделение ID учитывает оставшиеся черновики и
сохранённые результаты. Первый принятый исход не забирает ID и файл
исходника у остальных предложений.

Снимок подтверждения включает показанные карточки, их редакции, исходный
материал, определение типа и основания изменения назначений. По одному
ключу нельзя принять невидимые карточки из другой записи или обновившегося
разбора. При пакетном приёме используются снимки всех записей, которые
пользователь видел.

Перед записью проверяются актуальность снимка и содержимое затронутых
файлов. Применение сериализуется с другими записями в те же файлы.
При восстановлении после сбоя используются сохранённые план и результаты шагов.
Запрос с тем же ключом и выбором возвращает прежний результат. При
конфликте файлы нельзя откатывать поверх новой правки.

Это наиболее рискованный стык. До подключения панели нужен отдельный
прогон с остановкой после каждого изменения файла. На нём проверяются
несколько исходов одной записи, повтор запроса и вмешательство другого
писателя. Схема, проходящая только успешный путь, к UI не подключается.

### Хранение и восстановление

Предложения и результаты решений записываются в раздел исходного Markdown
одним блоком JSON с версией схемы. После завершения разбора запись получает
состояние истории и исключается из обычного накопителя. Файл остаётся по
прежнему пути, ссылки на источник сохраняются. Исторические записи
учитываются при выдаче ID и чтении результата повторного запроса. Дашборд
получает эти сведения через taskctl.

План применения готовится в отдельном временном дереве существующими
командами с выключенным коммитом. Для нескольких исходов используются
отдельные подготовленные фрагменты; общий исходник остаётся в записи.
Отложенный фрагмент становится отдельным черновиком с датой возврата.
Причина выполненного удаления сохраняется в истории исходной записи.

Перед установкой результата берётся общий файловый замок доски. Под ним
сверяются исходные файлы и сохраняются их ожидаемые и будущие состояния.
План незавершённой установки лежит в служебном каталоге git, у проекта без
git в служебном каталоге проекта. Штатные команды и прямые записи панели
используют тот же замок до первого чтения изменяемых файлов.

После обрыва выполняется установка сохранённых будущих состояний. Команды
создания и приписки повторно не вызываются. Для каждого файла допустимы
только исходное или уже установленное состояние; другое содержимое
считается конфликтом. Результат подтверждения записан вместе с исходником.
После завершения установки служебный план удаляется. Коммит и сетевой пуш
идут после освобождения замка, вложенные проверки git не ждут его повторно.

Внешние проверки старых команд выполняются между чтением снимка и его
повторной сверкой под замком. Изменившиеся документы и путь назначения
не перезаписываются прежними данными. Обновление рабочей копии через
`catchup` использует отдельный служебный барьер и учитывает ещё не
завершённые Git-публикации. Признак начавшейся Git-публикации сохраняется
до освобождения общего замка. При неясном исходе журнал остаётся для диагностики.

Согласованная запись обеспечивается через taskctl и прямые редакторы
панели. Прочим писателям нужен тот же протокол. Служебные журналы внешних
операций не заменяют историю предложений в исходной записи.

## Стык с разговором и запуском

От DK-1446 используются доставка вопроса, черновик ответа, показ в панели
и продолжение. У предложения отдельный предмет подтверждения и отдельный
снимок. Режим `сценарии/1`, ответы «ничего», свои сценарии и состав
рекомендации сохраняют прежний смысл.

Карточки предложений расположены на экране записи. В чате остаётся
обсуждение и подтверждение внутри реплики по общему договору вопросов.
HTTP дашборда вызывает taskctl через существующую воронку, UI показывает
полученные состояния. Разбор и проверка предложения на клиенте не
дублируются.

Показанный вопрос публикуется командой `draft proposals ask`, машинный
ответ принимает `draft proposals answer`. Его контекст отделён от
`сценарии/1`. Свободный вопрос о карточках сохраняет ожидание и не вызывает
применение. При отправке решений используются показанные записи, их
снимки и редакции; новое чтение не подставляется вместо них.

После неоднозначного сбоя доставка уведомления может повториться по
действующему транспорту чата. Ключ и сохранённые результаты позволяют
отличить повтор от нового решения. Применение файлов повторно не
выполняется. Режим выполнения проверяет подтверждённые результаты и
передаёт действующему запуску только ID принятых новых задач.
Он действует для исходной записи, заказанной к выполнению; включение другой
записи в показ карточек не расширяет это разрешение. Статус задачи и
действующий запуск проверяются прежним механизмом. После неоднозначного
обрыва запуска требуется сверка, автоматический повтор исполнения не обещан.

Создание строки доски подчиняется прежней проверке основного checkout.
Подтверждение из дополнительного дерева завершается с указанием причины;
показанный корень не заменяется другим деревом.

До создания сессии процесс запуска удерживает общий резерв. Облачная
обёртка повторно проверяет запись и принимает резерв на время клиента. Команда
приписки закрытого материала завершается с ошибкой при запущенной или
стартующей работе. Общий служебный каталог связывает основной и
дополнительный checkout, в том числе при различающихся HOME.

У груминга в панели есть отдельный запуск и быстрый ввод с немедленным
разбором. Разбор нескольких ID или всего накопителя возможен также из
скилла. Проверка замка выполняется на каждом входе до чтения содержимого
облачной моделью. Заблокированная запись в пачке получает собственный
результат «ждёт локальную модель» и не передаётся внутри общего промпта.

Тип, источник и замок могут измениться после открытия экрана. Проверяется
состояние файла на момент запуска. Неизвестное значение замка или ошибка
чтения не трактуются как разрешение облачного разбора. До подключения
локального маршрута нет автоматического запасного облачного варианта.
Исследование маршрутизации выполняется в DK-1471.

## Работы и проверки

| Работа | Требования | Проверка |
|---|---|---|
| W-1. Словарь, чтение и запись шапки, JSON, старые черновики | FR-1..3, NFR-6 | V-1. Встроенный, заменённый и добавленный тип; неверное определение; старый файл; одноабзацный ввод |
| W-2. Сохранение предложений, правка, отказ, нулевой результат | FR-4, FR-6..8 | V-2. Несколько карточек, повторный разбор, пустой ответ, ошибка, сохранённое частичное решение |
| W-3. План применения через команды taskctl, происхождение и связи | FR-5..7, NFR-1..4, NFR-7 | V-3. Все четыре исхода, смешанная пачка, форма, цикл, неизвестный адресат, прерывания и повтор |
| W-4. Типизированное подтверждение поверх DK-1446 и экран записи | FR-1, FR-4..8, NFR-1..2, NFR-6 | V-4. Живой браузер, правка до приёма, одна/все по записи/все показанные, отказ, устаревший экран |
| W-5. Проверка замка и перенос ограничений при продолжении | FR-1, FR-7..8, NFR-5 | V-5. Счётчик облачных запусков равен нулю для замка на каждом входе, в том числе после смены файла |
| W-6. Раскладка, README первого запуска, установленная приёмка | Все | V-6. Чистый временный проект после doctor --fix, установленный taskctl и дашборд, отдельная сессия |

Для V-3 важны две одновременные доставки одного подтверждения и запись
чужой правки между просмотром и применением. В прогонах проверяется
содержимое файлов и число результатов, одного успешного ответа API мало.
При сбое посередине пачки пользователь видит выполненные и оставшиеся
действия, повтор не создаёт второй результат.

V-4 использует настоящую сборку taskctl и процесс дашборда на временном
проекте. Ответы модели подставляются только на входе разбора. Для V-5
подмена модели записывает факт запуска и полученный stdin. Полезный
отрицательный результат это отсутствие запуска, а не отсутствие строки
секрета на экране.

План проверки установленной версии повторяет шесть пользовательских
сценариев из файла задачи. Независимая сессия сохраняет вывод CLI,
HTTP-ответы, изменения файлов и браузерные подтверждения. Сначала
исполняются проверки сохранности и замка, затем полный пользовательский
путь.
