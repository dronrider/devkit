# DK-149: LLD доставки готовых бинарей devkit и версии на машине

## Задача и рамка

Установка devkit сегодня требует тулчейна: `CONNECT.md` клонирует репозиторий,
собирает шесть бинарей циклом `go build` и зовёт `devkitctl doctor --fix`. Без
go в PATH из этого не выходит ничего, и человеку, которому нужны утилиты доски,
приходится ставить Go. Вторая половина того же перекоса на другом конце жизни:
после `git pull` собранные бинари остаются старыми и работают по-старому, пока
кто-нибудь не позовёт доктора.

Дизайн выбирает канал доставки готовых бинарей, схему версии и её связь с
версией репозитория правил, команду обновления, ответственного за клон при
установке с нуля и вход в python-часть. Кода он не пишет: версию и релизную
автоматику везёт DK-150, установку и обновление DK-151, сверку версий у доктора
DK-152.

Рамка задана постановкой цели DK-138.

- Клон репозитория правил остаётся и остаётся на виду. Правила подключаются
  локальным путём (`@~/projects/devkit/RULES.core.md`), devkit лежит соседом
  проектов, и целиком в Cellar его не спрятать. Цель не про `brew install
  devkit`, а про то, чтобы из установки ушла сборка из исходников.
- Платформы обе, macos и linux: devkit ставится и на VPS, а не только на
  рабочие маки.
- Внешних зависимостей у devkit нет ни в go, ни в python, и решение их не
  заводит. Установщик обходится тем, что есть на голой машине.
- `gh` на машине нет, и релиз с неё проверяется публичным API через curl.

## Живой материал

Шесть Go-утилит лежат по правилу раскладки в `tools/<имя>/`, каждая своим
модулем `github.com/dronrider/devkit/tools/<имя>` на `go 1.26`, все шесть это
`package main` без единого `require`. Общего кода между модулями нет: то, что
повторяется (журнал запусков, разбор корп-обвязки), лежит копией в каждом.

Версии нет ни у одной: флага `--version` не держит никто, и «какой коммит
собран» выводится только из mtime файла. Тегов в репозитории нет тоже, релизов
не выкладывалось ни одного, в `.github/workflows/` лежит единственный `ci.yml`
на одном раннере `ubuntu-latest` с `go-version: stable`.

Расхождение бинаря с исходниками доктор ловит, но грубо
(`check_binaries`, `tools/devkitctl/devkitctl.py:413`): сравнивает mtime бинаря
с mtime `*.go`, в `--fix` пересобирает через `go build`, без go в PATH печатает
находку «собирать нечем». Список у проверки короче списка установки: константа
`BINARIES` на строке 102 держит четыре имени из шести, `trackctl` и `obeycheck`
не проверяет никто. Из worktree ветки задачи проверка не работает вовсе, и это
осознанно: mtime исходников там означает момент выкладки, а не правки.

Каталог назначения выбирает `go_bin_dir()` (строка 350): `$GOBIN`, иначе
`$GOPATH/bin`, иначе `~/go/bin`. Имя каталога говорит про тулчейн, которого на
целевой машине может не быть вовсе.

Команды сборки размазаны по доке девятью местами, и после переезда каталогов
(DK-135, DK-140) шесть из них врут: `CONNECT.md:17` собирает из `~/projects/devkit/$u`
вместо `tools/$u`, так же ошибаются README пяти утилит
(`tools/shipctl/README.md:11`, `tools/taskctl/README.md:13`,
`tools/trackctl/README.md:13`, `tools/obeycheck/README.md:16`,
`tools/regcheck/README.md:19`, `tools/agentctl/README.md:903`). Правильны только
`README.md:116` и `kit/skills/live-core/SKILL.md:57`. Одна точка сборки нужна
не меньше, чем сама доставка: пока строка сборки копируется в доку руками, она
и дальше будет расходиться с деревом.

Вес готового набора: шесть бинарей это около 25 МБ на платформу, самый крупный
`trackctl` (8.8 МБ), в gzip набор садится примерно вдвое.

Python-часть тулчейна не требует и зовётся длинным путём из чекаута
(`python3 ~/projects/devkit/tools/devkitctl/devkitctl.py`). Подкоманд у неё
пять: `doctor`, `new`, `corp`, `stats`, `weigh`.

## Решение 1. Канал один: релизы гитхаба, тапа нет

Готовые бинари едут релизами GitHub того же репозитория. Тег `vX.Y.Z` запускает
сборку, автоматика прикладывает к релизу четыре тарболла (по одному на пару
GOOS/GOARCH из `darwin`/`linux` и `amd64`/`arm64`) и файл `SHA256SUMS`. Внутри
тарболла плоско лежат все Go-утилиты релиза, имя ассета собирается по шаблону
`devkit-<версия>-<os>-<arch>.tar.gz`. Скачивает и распаковывает их python-часть
из чекаута, поэтому отдельного установщика на sh нет.

Свой tap отвергнут, и не по одной причине.

- На linux-VPS brew это тяжёлая зависимость, которую ставят ради самого brew:
  сотни мегабайт и просьба про компилятор. Менять «поставь go ради утилит
  доски» на «поставь brew ради утилит доски» смысла нет, а цель называет обе
  платформы равными.
- Tap это второй репозиторий и формула, которую надо двигать на каждом релизе.
  Релизы всё равно нужны как источник ассетов для формулы, то есть tap не
  заменяет канал, а надстраивается над ним, и цена его это лишний шаг
  сопровождения.
- Главное: brew кладёт в Cellar, а клон правил обязан остаться на виду в
  `~/projects/devkit`. Tap закрыл бы половину установки, и обновление стало бы
  двумя командами (`brew upgrade` плюс `git pull` в клоне) с двумя разными
  представлениями о том, какая версия стоит. DoD цели требует одну команду,
  после которой сходятся обе половины.
- Повод для сравнения (чужой mcp-ai-helper, который ставится через brew одной
  строкой) на devkit не переносится по форме: там самодостаточный бинарь без
  сопутствующего чекаута, тут чекаут это половина продукта.

Отвергнуто заодно и остальное, что напрашивается.

- `go install github.com/dronrider/devkit/tools/taskctl@latest` требует ровно
  того тулчейна, ради ухода от которого цель и заведена.
- Собранные бинари, положенные в сам репозиторий, стоили бы 25 МБ на платформу
  в каждом коммите релиза и раздули бы клон, который тут ставится всем.
- Бутстрап `curl | sh` отвергнут в решении 5 вместе с вопросом про клон.
- Оба канала сразу (tap и релизы) отвергнуты как ответ, который не выбирает:
  два способа установить одно и то же расходятся в версиях и в списке того, что
  положено на машину, а сопровождать их пришлось бы обоими.

## Решение 2. Версия зашивается сборкой и печатается одинаково

Версия приходит в бинарь линковкой, `-ldflags "-X main.version=... -X main.commit=..."`,
и берётся из git того чекаута, из которого идёт сборка:

```sh
version = git describe --tags --always --dirty
commit  = git rev-parse --short=12 HEAD
```

На релизной сборке HEAD стоит ровно на теге, и `describe` даёт `v0.2.0`. На
машине разработчика, где после тега уже накопились коммиты, он даёт
`v0.2.0-7-gabc1234` или `v0.2.0-7-gabc1234-dirty`, то есть строка версии сама
говорит, что бинарь не релизный. Все шесть утилит объявляют пару переменных у
себя в `main` (`var version = "dev"`, `var commit = "unknown"`), значения по
умолчанию видны в бинаре, собранном голым `go build` мимо devkit.

Общего пакета версии нет: шесть модулей это решение DK-139, и общий пакет
потребовал бы либо седьмого модуля с `replace` в каждом из шести, либо
`go.work`, то есть новой машинерии ради четырёх строк. Копия двух переменных в
шести `main` дешевле и лежит в той же форме, в какой в этих утилитах уже лежит
журнал запусков.

Печатается версия одинаково, первой строкой и без всего остального:

```
taskctl v0.2.0 (a1b2c3d4e5f6)
```

Флаг `--version` разбирается до всех прочих аргументов, не требует ни проекта,
ни доски, ни `-C`, выходит с кодом 0 и в сеть не ходит. Формат один на шесть
утилит, потому что его читает не только человек: доктор берёт из этой строки
коммит.

`runtime/debug.ReadBuildInfo` как источник отвергнут. Он даёт `vcs.revision`
даром, но только при сборке из git-дерева, теряется на `-trimpath` и на сборке
из распакованного архива, и тега не знает вовсе: сравнивать по нему можно
только «совпало или нет», а сказать «бинарь отстал от релиза» уже нечем. Место
ему остаётся запасное, на будущее: пока разговор идёт про то, что стоит в
PATH, хватает двух зашитых переменных.

Отдельного файла состояния («какая версия установлена») нет и не заводится.
Записью служит сам бинарь, `--version` спрашивают у него. Файл в `~/.devkit/`
протух бы ровно в тех случаях, ради которых он и заводился бы: бинарь заменили
руками, каталог переехал, копий в PATH оказалось две.

## Решение 3. Сходимость: коммит бинаря против коммита чекаута

Версия репозитория правил это HEAD его основного чекаута. Правило сходимости
одно: **коммит, зашитый в бинарь, равен коммиту HEAD основного чекаута
devkit**. Порог тут не выбирается, любое расхождение это находка доктора:
бинарь и правила составляют одну версию, и «немного разошлись» тут не бывает.

Из правила следуют два режима чекаута, и доктор их называет вслух.

- Чекаут стоит на теге (detached HEAD на `v0.2.0`). Это машина потребителя:
  бинари приехали релизом этого тега, коммиты совпадают, доктор молчит.
  Обновление двигает чекаут на следующий тег вместе с бинарями.
- Чекаут стоит на ветке впереди последнего тега. Это машина разработчика
  devkit: релиза под такой HEAD нет и быть не может, и сходимость держит
  локальная сборка. Она есть чем сделать, раз человек правит go-код.

Потребительский чекаут стоит именно на теге, а не на `main`, и это часть
решения, а не деталь. На `main` он всегда впереди последнего тега (работа после
тега продолжается), совпадения коммитов не случилось бы никогда, и правило
пришлось бы ослаблять до «бинарь равен ближайшему тегу, достижимому от HEAD».
Ослабленное правило молчит ровно в том случае, ради которого цель и заведена:
после `git pull` без нового тега исходники уехали, ближайший тег прежний,
находки нет. Detached HEAD на теге ещё и честно отвечает на вопрос, какие
правила лежат на машине: не «примерно свежие», а те, что вышли релизом.

Тег ставит человек, автоматика его не двигает. Схема `vMAJOR.MINOR.PATCH`,
первый релиз `v0.1.0`, минор на каждый выпуск, патч на починку выпуска.
Автоматической простановки тега в `shipctl ship` эта цель не заводит: релиз это
решение про то, что набранное готово уехать на чужие машины, и принимается оно
человеком.

Сравнение с mtime уходит отовсюду, кроме одного хвоста. Если в основном чекауте
лежат несохранённые правки `*.go`, сравнивать не с чем: коммит бинаря равен
HEAD, а исходники уже другие. В этом и только в этом случае доктор досравнивает
mtime бинаря с mtime `*.go`, как делает сегодня, и говорит про несобранные
правки. Второй механизм тут не дублирует первый, а закрывает область, где
первого не существует.

Отдельно про worktree ветки задачи. Сегодня проверка там выключена целиком,
потому что mtime в свежей выкладке ничего не значит. С коммитами выключать
нечего: доктор берёт HEAD **основного** чекаута (`devkit_checkout()` его уже
возвращает), а не HEAD worktree, и находки в параллельных сессиях не сыплются.
Правило «машинный бинарь с непроверенной ветки не собирается» остаётся:
чинится расхождение только из основного чекаута.

## Решение 4. Обновление одной командой: `devkitctl update`

Команда одна, `devkitctl update`, и она же ставит devkit с нуля: разницы между
установкой и обновлением нет, потому что на голой машине она просто проходит
все шаги впервые. Отдельной команды `install` не заводится, две команды с
пересекающимися обязанностями расходятся в поведении быстрее, чем в названиях.

Порядок шагов такой.

1. Отказ, если позвали не из основного чекаута (`devkit_checkout()` это уже
   умеет): машинные бинари с ветки задачи уехали бы во все проекты сразу.
2. Отказ, если в чекауте есть незакоммиченное или неотправленное в origin: свою
   работу человек не теряет из-за команды обновления. Тут же говорится, что на
   машине разработчика devkit обновление это `git pull` и `doctor --fix`.
3. `git fetch --tags --prune`.
4. Новейший тег берётся из git (`git tag --list 'v*' --sort=-v:refname`), а не
   из API гитхаба. Так обходятся и лимит неавторизованных запросов к
   `api.github.com` (60 в час на адрес), и разбор JSON, и лишний хост в
   диагностике сетевых отказов: качать всё равно с `github.com`. Цена решения
   в том, что тег виден сразу, а ассеты появляются через пару минут после него,
   и скачивание в эту щель упрётся в 404. Сообщение про щель так и говорит:
   релиз ещё собирается, позвать позже.
5. Чекаут переходит на тег (`git checkout --detach <тег>`), если ещё не там.
6. Процесс перезапускает себя (`os.execv`) уже новым кодом. Иначе вторую
   половину работы делает python, прочитанный до перехода на тег, то есть
   старая логика раскладки кладёт новые бинари. Перезапуск идёт с флагом «git
   уже сделан», чтобы шаги 3-5 не повторялись.
7. Скачивается тарболл своей платформы и `SHA256SUMS`, сверяется сумма, архив
   распаковывается во временный каталог. Качает `urllib.request` из stdlib: он
   есть везде, где есть python3, и сам читает `https_proxy` из окружения, а
   curl на голом linux бывает не поставлен.
8. Бинари переезжают в каталог назначения через `os.replace`. Именно
   переименованием, а не записью поверх: на linux запись в работающий файл даёт
   `ETXTBSY`, а переименование атомарно и не трогает уже запущенный процесс.
9. Кладётся обёртка `devkitctl` (решение 6) и раскладывается машинный контур
   тем же кодом, что зовёт `doctor --fix`: хуки харнеса, права сессии,
   определения субагентов, скиллы, глобальная точка правил.
10. Печатается «было -> стало» по версии и список «осталось сделать», как это
    уже делает всякое подключение в devkit.

Когда обновлять нечего (чекаут на новейшем теге, все бинари отвечают его
коммитом), команда так и говорит и в сеть за ассетами не идёт. Молчаливого
холостого хода тут быть не должно: команда, которая ничего не сказала,
неотличима от команды, которая не сработала.

Платформа определяется по `platform.system()` и `platform.machine()`:
`Darwin` -> `darwin`, `Linux` -> `linux`, `x86_64`/`AMD64` -> `amd64`,
`arm64`/`aarch64` -> `arm64`. Всё остальное это внятный отказ с названием пары,
под которую релиза нет, а не молчаливая попытка скачать несуществующий ассет.

## Решение 5. Клон правил делает человек, установщик его не заводит

Первая команда установки остаётся клоном, вторая это обновление:

```bash
git clone https://github.com/dronrider/devkit.git ~/projects/devkit
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py update
```

Три команды становятся двумя, `go build` уходит, тулчейн не нужен. Клон никуда
не прячется: он и так обязан лежать на виду соседом проектов, потому что на его
путь смотрит импорт правил в каждом проектном файле.

Бутстрап-установщик, который клонировал бы сам (`curl -fsSL .../install.sh |
sh`), отвергнут. Он был бы второй точкой входа с той же работой, что и
`devkitctl update`, и на sh: по правилу языка (`README.md`, раздел
«Раскладка») определение платформы, скачивание, сверка суммы и раскладка это
программа, а не тонкая обёртка, и место ей в python. Но python из чекаута до
клона не позовёшь, значит бутстрап пришлось бы писать и держать на языке,
которому эта работа правилом запрещена. Второе: он выбирал бы путь клона молча
за человека, а путь этот и есть то, на что смотрит импорт правил. И третье:
`curl | sh` с чужого хоста это ровно тот способ установки, от которого devkit
уходит принципом «внешних зависимостей нет».

Так что порядок обратный привычному: не установщик приносит правила, а клон
правил приносит установщик. Это же снимает вопрос доверия к скачанному: код,
который качает бинари, приехал гитом вместе с историей, а не потоком в shell.

## Решение 6. Вход в python-часть: обёртка рядом с бинарями

Переписывать `devkitctl` на go нельзя по правилу языка: он обязан работать на
машине, где ещё ничего не собрано, и с приходом готовых бинарей это требование
не ослабло, а усилилось (он же их и ставит). Вопрос только во входе, и он
решается обёрткой, которую devkit кладёт в тот же каталог, что и бинари:

```sh
#!/bin/sh
# devkit:generated
exec python3 "/Users/имя/projects/devkit/tools/devkitctl/devkitctl.py" "$@"
```

Дальше `devkitctl doctor` зовётся по имени наравне с `taskctl` и `shipctl`, а
длинный путь остаётся только в первой команде установки, до которой обёртки
физически ещё нет. Правило языка обёртка не нарушает: три строки без единой
своей функции это ровно то, что на sh разрешено.

Путь в обёртке зашит абсолютным, поэтому пишет её генератор (`update` и
`doctor --fix`), а не релиз: у каждой машины он свой, а после переезда чекаута
обёртка обязана перевыпуститься. Маркер `# devkit:generated` в ней стоит по той
же причине, что в тонких файлах проектов: по нему видно, что файл наш, и
доктор не затрёт чужой скрипт с таким именем.

Симлинк на `devkitctl.py` вместо обёртки отвергнут: он требует бита исполнения
и шебанга на самом модуле python, то есть делает файл, который импортируется
тестами, ещё и исполняемым (за битом исполнения в репозитории следит отдельный
шаг CI), и не оставляет места ни маркеру, ни выбору интерпретатора.

Хуки остаются как есть: их зовут по абсолютному пути git (`core.hooksPath`) и
харнес (команды в `~/.claude/settings.json`), пути эти генерённые, и чинит их
тот же `doctor --fix`. Имени в PATH они не требуют, потому что человек их не
зовёт.

## Решение 7. Каталог назначения выбирается из PATH, а профиль не правится

Каталог ищется по порядку: `$DEVKIT_BIN`, если задан; иначе первый из
`~/go/bin` и `~/.local/bin`, который уже стоит в PATH; иначе `~/.local/bin`, он
создаётся. Первый пункт даёт способ поставить куда угодно, второй не двигает
ничего на уже живых машинах (там бинари лежат в `~/go/bin` и PATH настроен), а
третий выбирает общепринятое место для машины без go, где имя `~/go/bin`
выглядело бы враньём.

Строку `export PATH` в профиль оболочки devkit не дописывает. Профиль это файл,
который человек ведёт сам, и он единственный такой в списке того, что трогает
раскладка; вдобавок правка в уже запущенной сессии всё равно не действует, то
есть команда всё равно обязана сказать про это словами. Вместо правки каталог,
которого нет в PATH, попадает в список «осталось сделать» готовой строкой для
вставки, а доктор держит находку, пока каталог в PATH не появится. Такой
находкой уже занимается `path_winner`, ей просто добавляется случай.

## Сборка релиза: одна точка на CI и на машину

Сборка живёт в `devkitctl`, а не в yml, и зовётся одинаково из CI и с машины.

- `devkitctl build` собирает утилиты для текущей машины в каталог назначения с
  зашитой версией. Это же зовёт `doctor --fix` вместо своего `go build`.
- `devkitctl build --release --out dist` собирает четыре пары GOOS/GOARCH с
  `CGO_ENABLED=0`, пакует тарболлы и считает `SHA256SUMS`. Кросс-сборка
  делается на одном раннере: зависимостей нет, cgo не нужен, матрица из
  раннеров под каждую ОС не окупается.

Список утилит не константа, а выводится из дерева: каталоги `tools/*/` с
`go.mod`. По правилу языка go в devkit это ровно то, что ставится в PATH,
поэтому список сборки, список установки и список проверки доктора совпадают по
построению, а не по внимательности. Сегодняшнее расхождение (`BINARIES` из
четырёх имён против шести устанавливаемых) на такой схеме не воспроизводится, и
седьмая утилита попадает во все три списка тем, что появилась.

Собранное проверяется тут же: `build` запускает каждый свежий бинарь с
`--version` и сверяет строку с тем, что зашивал. Утилита, забывшая флаг,
роняет сборку, и обещание «версию печатают все шесть» держится машиной, а не
ревью. Отдельного шага в CI под это не нужно, проверка едет внутри каждой
сборки, локальной и релизной.

`.github/workflows/release.yml` остаётся тонким: запуск по тегу `v*` и по
`workflow_dispatch`, `actions/checkout` с `fetch-depth: 0` (без полной истории
и тегов `git describe` версии не даст), `actions/setup-go` с
`go-version-file: tools/taskctl/go.mod`, вызов `devkitctl build --release` и
выкладка ассетов через `gh release`, который на раннере есть. Сторонних
экшенов для выкладки не берём: лишний источник кода в цепочке сборки того, что
потом расходится по машинам.

## Что делает DK-150

Версия и релизная автоматика.

- В каждой из шести `tools/*/` появляется `version.go`: `var version`,
  `var commit`, разбор `--version` до всех прочих аргументов и печать строки
  `<имя> <версия> (<коммит>)`.
- `devkitctl build`: список утилит из `tools/*/go.mod`, версия из
  `git describe --tags --always --dirty` и `git rev-parse --short=12 HEAD`,
  сборка с `-ldflags` в каталог назначения, самопроверка `--version` у каждого
  собранного бинаря.
- `devkitctl build --release --out dist`: четыре пары GOOS/GOARCH,
  `CGO_ENABLED=0`, тарболл на пару по шаблону `devkit-<версия>-<os>-<arch>.tar.gz`,
  `SHA256SUMS` рядом.
- `.github/workflows/release.yml` по тегу `v*` и по `workflow_dispatch`, с
  `fetch-depth: 0` и выкладкой через `gh release`.
- `doctor --fix` пересобирает через `devkitctl build`, а не своим `go build`:
  точка сборки одна.

Проверяется живым прогоном: `build --release --out dist` на машине, распаковка
тарболла своей платформы, `taskctl --version` печатает тег. Вторая половина
проверки требует пуша тега, а тег пушит человек, поэтому она идёт после
слияния: `curl -s https://api.github.com/repos/dronrider/devkit/releases/latest`
показывает пять ассетов, и суммы из `SHA256SUMS` сходятся со скачанными.

## Что делает DK-151

Установка и обновление.

- `devkitctl update` по решению 4, со всеми отказами (worktree, неотправленная
  работа), самоперезапуском после перехода на тег, скачиванием через `urllib`,
  сверкой SHA256, атомарной подменой бинарей и раскладкой машинного контура.
- Выбор каталога назначения по решению 7 и находка про PATH.
- Обёртка `devkitctl` по решению 6, её кладут и `update`, и `doctor --fix`.
- `CONNECT.md`: две команды вместо трёх, цикл `go build` уходит.
- `README.md`, раздел про установку Go-утилит (строка 116): переписывается на
  релизы; заодно чинятся шесть устаревших путей сборки в README утилит и в
  `kit/skills/live-core/SKILL.md:57` команда сборки становится
  `devkitctl build`.

Проверяется прогоном в чистом окружении: временный HOME, go убран из PATH, клон
и `update`, дальше `taskctl --version` и `devkitctl doctor` без находок. Живой
релиз для этого обязан существовать, то есть DK-151 упирается в пуш тега после
DK-150, и это её единственная внешняя зависимость. Тесты в неё не упираются: в
них releases подменяются локальным сервером на `http://127.0.0.1`, а прогон в
чистом окружении это шаг сценария проверки, а не тест.

## Что делает DK-152

Сверка версий доктором.

- Список проверяемых выводится из `tools/*/go.mod`, константа `BINARIES`
  уходит; `trackctl` и `obeycheck` попадают под проверку тем, что они есть.
- `check_binaries` спрашивает у бинаря `--version` и сравнивает коммит с
  `git rev-parse HEAD` основного чекаута. Бинарь, не понимающий `--version`,
  это находка «собран до релизной схемы» с той же починкой.
- Хвост про грязное дерево: при несохранённых правках `*.go` доктор
  досравнивает mtime и говорит про несобранные правки.
- `--fix`: чекаут на теге и релиз есть -> скачать; go в PATH -> собрать
  `devkitctl build`; ни того, ни другого -> находка остаётся с причиной, как
  сегодняшнее «собирать нечем».
- Проверка `path_winner` остаётся: чужая копия в PATH и каталог мимо PATH это
  по-прежнему находки.
- Доктор называет режим чекаута («на релизе v0.2.0» или «на ветке main,
  впереди релиза»), иначе расхождение версий читается как поломка.

Проверяется на подставных бинарях, печатающих заданную строку версии: совпало,
разошлось, флага нет вовсе.

## Наблюдаемость

Каналов наружу четыре, и ни один не молчит в штатной работе.

- `--version` у каждой утилиты: человек спрашивает то же, что и доктор.
- Находка доктора при расхождении, с названным режимом чекаута.
- Вывод `update`: «было -> стало», а когда обновлять нечего, он это говорит.
  Отдельно проговариваются случаи бездействия: сеть недоступна, тег есть, а
  ассетов ещё нет, платформа не из четырёх.
- Ассеты релиза видны публичным API без всякого `gh`, то есть «собралось ли»
  проверяется с любой машины одной строкой curl.

## Тесты

Своих тестов у DK-149 нет: задача не трогает код. Правило про красноту
регрессионного теста тут не применяется, багов не чинится, пирамида ложится на
три задачи реализации.

- DK-150: go-тест на формат `--version` в каждом из шести модулей (он же ловит
  забытый флаг у новой утилиты), python-тесты `build` на синтетическом дереве
  (список утилит выводится из `tools/*/go.mod`, ldflags собираются из git,
  тарболлы и `SHA256SUMS` на месте, самопроверка роняет сборку на бинаре без
  флага). Живой прогон релизной сборки идёт сценарием проверки, тестом он не
  заменяется: тест не докажет, что ассет скачивается с гитхаба.
- DK-151: python-пирамида на разбор имени ассета по платформе, сверку суммы
  (подменённый байт роняет установку), атомарную подмену, выбор каталога,
  оба отказа (worktree и неотправленная работа) и самоперезапуск. Сеть в тестах
  это локальный сервер, гитхаб в тестах не участвует. Прогон в чистом окружении
  с убранным go это шаг сценария проверки.
- DK-152: подставные бинари с заданной строкой версии на три случая (совпало,
  разошлось, флага нет), грязное дерево с несобранными правками, worktree
  ветки задачи (сравнение идёт с HEAD основного чекаута и находок не даёт),
  полнота списка (утилита, добавленная в фикстуру, попадает под проверку сама).

## Затрагиваемая документация

Осадок этой задачи в долгоживущей доке один: новый раздел `README.md`
«Версии и доставка» после «Раскладки». Место выбрано так по трём причинам.
Во-первых, README это единственный текст devkit, который описывает сам
репозиторий как устройство, а версия бинаря и канал доставки это про
репозиторий, а не про подключение проекта. Во-вторых, раздел ложится встык к
«Раскладке»: список Go-утилит там выводится тем же правилом языка, из которого
тут выводится список сборки и установки, и читать их порознь нет смысла.
В-третьих, `CONNECT.md` описывает порядок команд, которые работают сейчас, и
писать туда команду, которой ещё нет, значит соврать читателю; его переписывает
DK-151 по факту.

Раздел едет этой задачей, с оговоркой, что механику везут DK-150..DK-152, и
оговорку эту снимает та задача, которая свою половину закрыла. Так же сделано в
DK-139: правило встало в README раньше переезда, который его исполнил.

Дальше по задачам реализации.

- `CONNECT.md`, раздел «Один раз на машину»: две команды вместо трёх, DK-151.
- `README.md`, установка Go-утилит (строка 116): релизы вместо `go build`,
  DK-151.
- `tools/devkitctl/README.md`: `build` и его самопроверка (DK-150), `update` со
  всеми отказами (DK-151), новая находка про версии и режим чекаута в списке
  того, что проверяет `doctor` (DK-152). Там же строка 387, где сегодня
  описан `go build` внутри доктора.
- README шести утилит: строка сборки заменяется на установку из релиза, там же
  чинятся устаревшие после переезда пути. DK-151.
- `kit/skills/live-core/SKILL.md:57`: `go build` становится `devkitctl build`.
  Это инструкция сессии, её копия уезжает на машину, поэтому правится вместе с

- `AGENTS.md` devkit не трогается. Правило «новая go-утилита попадает в релиз

  платится контекстом каждой сессии devkit, и на эту редкость она не окупается.
- `RULES.core.md` и `RULES.md` не трогаются: правило про один репозиторий
  контекстом всех проектов не платится.
