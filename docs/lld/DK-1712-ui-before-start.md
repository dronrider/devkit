# DK-1712: UI согласуется до начала реализации

Статус: проект под рекомендациями, 2026-11-17. Человек ещё не согласовал
решение. Документ разрешает подготовить предмет согласования; общие правила,
код и скиллы начнут меняться отдельными задачами после приёмки.

Рекомендуемый порядок такой. На груминге агент определяет UI-составляющую и
основание допуска. Новый дизайн проходит отдельную задачу с приёмкой user.
Реализация получает ссылку на конкретный материал и согласие человека до
старта. Проверка допуска одинакова для ручного и автономного запуска.

Пользователь в [DK-1536](../tasks/drafts/DK-1536.md) описал разработку UI по
словам без макета. Вид и пользовательский поток расходятся с ожиданиями;
переделка расходует время и подписку. Сценарии СЦ-1, СЦ-2, СЦ-3 выбраны
человеком 2026-11-14. Их состав сохраняется.

[DK-1554](../tasks/drafts/DK-1554.md) добавляет требования к расширению devkit.
Материалы хранятся в Git, доступны из консоли и работают в подключённых
проектах независимо от агентского клиента. HTML, `designctl`, `docs/design`
и навигация дашборда в этой записи остаются предложениями агента.

Этот LLD определяет подготовку UI и допуск реализации. Формат файлов макета,
доставка, просмотр, изоляция активного содержимого и интерфейс выбора редакций

## Что работает сейчас

| Место | Проверяемый факт | Чего для UI не хватает |
|---|---|---|
| [readiness.go](../../tools/taskctl/readiness.go), `taskReady` | Обязательные разделы постановки заполнены | Классификация UI и согласие на материал не проверяются |
| [ops.go](../../tools/taskctl/ops.go), `cmdMove` | При переходе в in-progress проверяется постановка; при выходе из Backlog ещё и рёбра | Прямой move не вызывает проверку дизайна и человеческих развилок |
| [gate.go](../../tools/taskctl/gate.go), `cmdMoveDry` | Сухой старт проверяет постановку | Проверки рёбер из настоящего move в нём нет; добавлять туда отдельную копию UI-проверки нельзя |
| [worktree.go](../../tools/shipctl/worktree.go), `cmdStart`, `forkGate` | Открытые человеческие развилки проверяются до ветки; из Backlog вызывается move | При повторном start из in-progress move не вызывается; нужен самостоятельный вызов общей проверки UI |
| [slot.go](../../tools/taskctl/slot.go), `cmdSlot`; [arm.go](../../tools/taskctl/arm.go) | Slot учитывает рёбра, парковки, цену и занятость; arm ещё проверяет человеческие развилки | Отбор UI-кандидатов не опирается на согласованный материал |
| [edge.go](../../internal/merged/edge.go), `Book.Edge` | Предпосылка с приёмкой user снимает ребро после закрытия, даже если работа слита | Закрытие дизайна не проверяет, что зависимая использует прежний материал |
| [ACCEPTANCE.md](../../ACCEPTANCE.md), раздел об утверждённом макете | Утверждённый до старта эталон позволяет объективно проверить реализацию | Это правило приёмки, отдельной обязательной проверки старта сейчас нет |

Общую развилку можно завести перед стартом, зависимость можно поставить на
задачу дизайна. Они позволяют начать переход без нового механизма. Одна
развилка не обнаруживает её собственное отсутствие, а ребро не различает
редакции макета. Для полного допуска нужны явная классификация и связанное с
материалом согласие.

## Пользовательские сценарии

### СЦ-1: новая фича и существенная переделка

Ситуация: человек поручает агенту новую UI-фичу или изменение пользовательского потока.
Действие: агент готовит макет и поток, предъявляет конкретную редакцию и получает согласие до реализации.
Результат: согласованная редакция допускается к коду; отсутствие или устаревание согласия видны при попытке старта.
Польза: ошибки потока и ожиданий обсуждаются до затрат на реализацию.
Рекомендация: сохранить выбранный сценарий; он покрывает основную жалобу DK-1536.
Ограничение: варианты политики ниже ещё требуют человеческой приёмки.
Источник: слово пользователя, DK-1536, СЦ-1 и сохранённый выбор 2026-11-14.

### СЦ-2: мелочь и явное разрешение без макета

Ситуация: нужен точный локальный штрих либо человек явно разрешает работу без макета.
Действие: агент фиксирует проверяемое основание исключения и его пределы.
Результат: старт разрешён в указанных пределах; новая цель или расширение правки требуют повторной классификации.
Польза: обязательное проектирование не добавляет лишний круг для простой правки.
Рекомендация: сохранить сценарий и согласовать узкий критерий мелочи.
Ограничение: отсутствие макета само по себе не снимает барьер «глаза» на приёмке реализации.
Источник: слово пользователя, DK-1536, СЦ-2 и пример цвета кнопки.

### СЦ-3: переносимый материал до старта

Ситуация: разные агенты готовят UI из консоли в подключённых проектах.
Действие: агент сохраняет материал в Git и связывает выбранную редакцию с задачей и ответом человека.
Результат: другой исполнитель восстанавливает тот же эталон без первого клиента и машины агента.
Польза: согласие относится к одному материалу на всех входах devkit.
Рекомендация: сохранить сценарий; общий контракт ограничить адресацией и доказательством согласия.
Ограничение: доступность просмотра и формат файлов проектируются в DK-1554.
Источник: слово пользователя, DK-1536, СЦ-3; DK-1554, «Контекст обсуждения».

## Дерево решений

- Общие показатели СЦ-1, СЦ-2, СЦ-3.
  - Каждый поддержанный вход старта даёт одинаковый допуск по одному снимку задачи.
  - Каждый допущенный UI-контракт восстанавливается из Git вместе с основанием.
  - Материал, изменённый после согласия, не проходит с прежним согласием.
  - Числовая экономия подписки не задана и не заявляется. Проверяемый результат этой задачи состоит в согласованном контракте и конечных путях ниже.
- Предварительный человеческий вопрос П-1 «область UI».
  - Рекомендация: охватить графический интерфейс и его пользовательский поток, включая общие UI-библиотеки и изменения поведения со стороны сервера.
  - Отдельный вариант: распространить тот же порядок на интерактивный терминал. Эта ветка расширяет исходный запрос; потребуются примеры терминальных макетов в DK-1554.
- СЦ-1 -> предварительный человеческий вопрос П-2 «место дизайна».
  - Рекомендация: классификация на груминге, новый дизайн отдельной задачей user, код после её закрытия и проверки редакции.
  - Альтернативы: закончить дизайн внутри груминга; подготовить его непосредственно перед попыткой старта, сохраняя реализацию в Backlog. Сравнение ниже.
  - Согласованный материал -> решение 4 о связанном согласии -> допуск.
  - Материала или согласия нет -> отказ старта -> подготовка дизайна.
- СЦ-2 -> предварительный человеческий вопрос П-3 «предел мелочи».
  - Рекомендация: агентское исключение при выполнении всех проверяемых условий решения 2; явное разрешение человека остаётся самостоятельным основанием.
  - Альтернатива: всякую видимую правку направлять человеку за дизайном либо разрешением без него.
  - Расширение мелочи или отзываемое разрешение -> решение 5 -> допуск пересматривается.
- СЦ-3 -> решение 3 о контракте с DK-1554.
  - Устойчивый адрес, содержимое и предмет согласия известны -> общий допуск.
  - Недоступны или неоднозначны -> отказ с перечислением пробела; формат и канал не придумываются при старте.
- Общая зависимость -> предварительный человеческий вопрос П-4 «изменение согласованного материала».
  - Рекомендация: новая редакция выбранного материала или UI-контракта требует нового основания. Альтернатива допускает редакционные правки без нового согласия по условиям решения 5.
- Независимый предварительный человеческий вопрос П-5 «переход старых задач».
  - Рекомендация: старые неначатые задачи классифицируются перед стартом; начатые сохраняют историческое основание до изменения предмета.
  - Альтернативы приведены в решении 7; выбор не зависит от П-4.

Карта содержит рекомендации. Имена П-1..П-5 пока не заведены как развилки
`taskctl`. Диспетчер заведёт их после ревью и предъявит человеку. Интервью
завершится после ответов и сверки зависимых решений.

## Решение 1. Груминг определяет путь к реализации

Это рекомендуемый выбор для П-1 и П-2, ожидающий согласия человека.

UI есть, когда результат меняет доступный человеку экран или компонент,
визуальное уведомление, управление, переход, состояние, обратную связь либо
текст, влияющий на действие человека. Существенность определяется изменением
доступных действий, порядка шагов, навигации, результата действия или того,
как человек распознаёт состояние. Новый экран, подтверждение удаления,
исчезнувшая кнопка, иной шаг авторизации и новая ошибка относятся сюда.

Путь файла не является критерием. Изменение общей UI-библиотеки или токена темы
классифицируется по всем затронутым потребителям. Серверная правка тоже
относится к UI, если меняет видимые состояния или путь пользователя. Чистый
рефакторинг компонента без изменения этих свойств получает «UI нет» с
основанием и проверкой сохранённого поведения.

Документация, тесты и внутренний API без видимого изменения сами по себе UI
не добавляют. В рекомендованной области обычный текстовый вывод CLI остаётся
за пределами проверки макетов. Изменение интерактивного терминального
сценария всё равно разбирается интервью по действующим правилам; расширение
нового допуска на него является вариантом П-1.

| Где делать новый дизайн | Польза | Цена и влияние на автономность |
|---|---|---|
| Полностью на груминге | Карточка реализации появляется готовой к старту | Долгий дизайн и ожидание согласия удерживают разбор записи; его цена скрывается в груминге |
| Отдельная задача проектирования | Есть видимая работа и явная предпосылка; ожидание человека относится к дизайну | Нужен отдельный круг доски и ссылка на редакцию; зависимая реализация ещё не готова |
| Непосредственно перед стартом, пока реализация в Backlog | Не требуется отдельная строка | Ручной запуск начинает подготовку в разговоре задачи; автономный выбор пропускает реализацию до согласия. Подготовка видна планом, но отдельного учёта цены на доске нет |

Все три варианта сохраняют реализацию неначатой до согласия. Рекомендуется
второй вариант с классификацией на груминге. Для нового дизайна
заводится LLD с приёмкой user и барьером «согласие». Его продуктом служат макет
и пользовательский поток. Подготовка макета имеет роль «подготовка UI» и
допускается без готового макета; эта роль разрешает только материалы дизайна.
Изменение продукта или прототип, который собираются доставлять пользователю,
оформляются реализацией с обычной проверкой допуска.

Карточка реализации может появиться сразу с зависимостью от дизайна. Если
материал согласован ранее и покрывает задачу, повторная задача дизайна не
нужна. Если дизайн сложился при груминге, его всё равно предъявляют отдельным
предметом согласия до старта. Согласие на применение всего разбора черновика
согласием с макетом автоматически не считается.

Автономный выбор пропускает неготовую реализацию и продолжает независимые
задачи. Подготовка UI доступна по обычным ограничениям неопределённости, цены,
квоты и доступности человека. Новый допуск их не ослабляет.

## Решение 2. Исключение описывает точную правку

Это рекомендация для П-3, ожидающая согласия человека. Размер диффа и оценка
S сами по себе исключением не являются.

Агент может записать «мелкая правка», когда одновременно выполнены условия:

1. Известны все затронутые места и точный конечный результат. Агенту не нужно выбирать вид, текст с новым смыслом или новый поток.
2. Состав действий, порядок, навигация, состояния и смысл обратной связи сохраняются.
3. Сохраняются назначение элементов, доступность и принятые ограничения отображения. Для общей библиотеки названы затронутые потребители и способ проверки каждого класса использования.
4. Названы объективная проверка и граница исключения. Непроверенное влияние или неизвестный потребитель переводят задачу в «нужно проектирование».

«Поменять цвет кнопки» недостаточно. «У кнопки X заменить ошибочное значение
на существующий токен Y, сохранить роль и контраст, проверить перечисленные
экраны» может пройти как мелочь. Выбор нового фирменного цвета, превращение
обычной кнопки в предупреждающую либо изменение общего токена с неизвестными
потребителями требует дизайна. Точная правка опечатки может быть мелкой;
замена «Удалить» на «Скрыть» меняет ожидание результата и мелкой не считается.

Явное разрешение человека работать без макета допустимо независимо от размера
изменения. Агент предъявляет границы работы и последствия для приёмки,
фиксирует дословный ответ на конкретный предмет и связывает его с UI-контрактом.
Молчание, общий заказ «сделай фичу», отсутствие файла, автономный режим и
положительный ответ о другом материале разрешением не являются. Расширение
предмета требует нового ответа или дизайна.

Разрешение без макета снимает только требование предварительного макета.
Функциональные требования, доступность, ревью и остальные барьеры приёмки
действуют обычным порядком. Отказ от макета не является приёмкой готового UI.

## Решение 3. Общий контракт адресует материал в Git

Рекомендуемый контракт отделяет файл задачи от формата макета. В задаче есть
командно поддерживаемый раздел «Проектирование UI». Его отсутствие, пустое
значение и неизвестная версия означают «классификация не закончена».

| Поле контракта | Содержимое и проверка |
|---|---|
| Версия | Версия схемы допуска; неизвестная версия завершается понятной ошибкой |
| Роль | `нет UI`, `реализация UI`, `подготовка UI`; значение выбирается явно с основанием |
| Предмет | Сценарии, действия, затронутые экраны или классы потребителей, изменяемые свойства и ограничения; для реализации это отдельный устойчивый блок |
| Основание | `дизайн`, `мелкая правка`, `разрешение человека`; у `нет UI` и `подготовка UI` свои объяснения |
| Материал | Для дизайна выбранный комплект, точные элементы или состояния, Git-коммит, пути и идентификатор содержимого |
| Согласие | Для дизайна или разрешения без макета ссылка на явный человеческий ответ, предмет ответа и отпечаток согласованного снимка |
| Проверка исключения | Для мелочи подтверждение каждого условия решения 2; одна общая фраза «правка мелкая» не принимается |
| Начальный допуск | Снимок использованного основания, отпечатки предмета и материала, ссылка на коммит с предшествующим согласием; записывается командой старта |

Конкретная сериализация остаётся внутренней деталью реализации. Агент и человек
видят перечисленные значения и причины ошибок в читаемом виде. Произвольный
Markdown вне раздела не заменяет отсутствующее поле.

Минимальный комплект для существенного UI содержит цель и исходную ситуацию,
основной путь пользователя, применимые ошибки, пустые и промежуточные состояния,
переходы, результат действия и способ возврата. Макет показывает изменяемые
экраны и состояния, размеры целевых устройств, длинные тексты и ограничения
доступности, когда они относятся к изменению. Для неизменённой части можно
сослаться на существующий согласованный эталон. Неприменимые состояния
перечисляются с причиной. Несколько альтернатив допустимы, но предмет согласия
выделяет одну выбранную комбинацию.

DK-1554 должен предоставить адресуемый из Git комплект со стабильным
идентификатором содержимого, перечислением файлов и элементов, выбранных
редакций и размеров, а также способом предъявить именно этот комплект
человеку. Идентификатор охватывает описание потока, исходники, ресурсы и
снимки, использованные для согласия. Внешняя ссылка может дополнять комплект;
изменяемый адрес или файл на машине агента самостоятельным эталоном не служат.

Этот контракт допускает разные форматы визуальных файлов. Начальная реализация допуска читает Git-коммит, явный перечень
файлов и выбранных элементов из раздела задачи. Общий модуль рассчитывает
отпечаток по упорядоченному составу и содержимому файлов; версия алгоритма
входит в идентификатор. Сам Git-коммит в отпечаток содержимого не входит.
Адреса элементов должны однозначно указывать на части перечисленных файлов.
Изменённый выбранный файл требует новой редакции, даже если ссылка на
прежний коммит осталась в задаче.

Этих данных достаточно для материала, который уже хранится в Git и доступен
человеку. Описание потока и визуальные файлы могут иметь существующий
проектный формат. Принятие этого LLD согласует минимальный интерфейс допуска.
Полная проработка и реализация DK-1554 не являются его предпосылкой. В DK-1554
согласуются упаковка, расположение, просмотр и способы получения тех же
данных из будущего комплекта. Доставка через дашборд не нужна для консольного
допуска, но доступный человеку просмотр нужен для согласия.

## Решение 4. Согласие относится к снимку предмета и материала

Человек получает описание потока, выбранные элементы и способ просмотра
зафиксированной редакции. Проверка доступности предъявления относится к
DK-1554. До успешного предъявления агент не просит согласовать материал.
Слова «согласовано» от агента и зелёный статус файла согласия не создают.

Рекомендуется расширить существующую запись `taskctl decide` типизированным
снимком UI. В нём находятся ID задачи или задачи-дизайна, версия схемы, устойчивый
предмет, выбранный материал и отпечаток их содержимого. Показ вопроса сохраняет снимок;
при обработке ответа команда сопоставляет его с предъявленным снимком.
Сохраняются источник и текст человеческого решения. Для разрешения без макета
снимок содержит предмет, ограничения и предупреждённый остаток приёмки.

Реализация может использовать согласованный дизайн другой задачи только в
пределах указанного в согласии применения. Предмет реализации ссылается на
устойчивые ID согласованных сценариев, элементов и ограничений. Проверка
сопоставляет эти ссылки и параметры; новый сценарий или изменённое условие
требуют нового согласия. Полноту списка потребителей и смысловое покрытие
проверяют агент и ревьювер. Механизм не выводит их из кода автоматически.

Общие человеческие развилки используются для вопросов о потоке. Их закрытие
не подменяет согласие на конкретный комплект. Задача дизайна с приёмкой user
остаётся предпосылкой реализации до закрытия. После закрытия отдельная
UI-проверка сверяет выбранный комплект с результатом этой задачи и покрытие
предмета реализации. Чужой макет и закрытая строка без указанной редакции
допуска не дают.

В Git до старта реализации должны находиться предмет, материал и запись
согласия. При успешном старте команда сохраняет начальный допуск в том же
коммите захвата, что и перевод в работу. Он ссылается на известный коммит с
согласием и не содержит хеш собственного коммита. Хеш коммита захвата берётся
из истории. Для нового старта UI прямой move без коммита завершается указанием
повторить его с обычным `-m`; проверяемая часть постановки должна быть
закоммичена и совпадать с проверенным снимком.

Так появляется явный момент старта. Сейчас ACCEPTANCE.md ищет первый коммит
с ID задачи. При рекомендуемом порядке карточка реализации может появиться
раньше дизайна, поэтому этот коммит будет созданием карточки. Кандидат 3
уточняет правило для новых задач: возраст эталона проверяется по начальному
допуску в коммите захвата. Старое правило остаётся для задач без такого следа.
Приёмка дизайна по-прежнему имеет барьер «согласие» и вид user.

Снимок проверяет связь и возраст записи в рамках принятого доверия к
`taskctl decide`. Он не доказывает, что человек внимательно посмотрел макет.
Требовать подпись отдельным внешним сервисом этот LLD не предлагает.

## Решение 5. Изменение предмета требует нового допуска

Это рекомендация для П-4, ожидающая согласия человека.

Отпечаток предмета охватывает устойчивый блок UI-контракта. «Ход работы»,
ревью и вывод проверок в него не входят. Отпечаток материала охватывает
зафиксированный состав комплекта. Запись согласия лежит вне этого состава,
поэтому расчёт не зависит от собственного результата.

Изменение выбранного материала, состава состояний или предмета реализации
делает прежнее согласие непригодным для нового содержимого. Команда показывает
старый и новый идентификаторы. Человек согласовывает новую редакцию либо агент
возвращает выбранный материал и предмет к прежнему согласованному снимку.
Новая альтернатива рядом со старой не отменяет согласия, пока выбран старый
неизменённый материал и он покрывает предмет.

Если изменение найдено после старта, исполнитель приостанавливает затронутую
UI-работу, сохраняет написанное и готовит пересмотр. Начальный допуск остаётся
в истории. Для продолжения записывается новое основание тем же порядком;
расширение мелкой правки также проходит повторную классификацию. Независимую
работу конвейер продолжает обычным порядком.

Повторный start, возврат из Check, слияние и перевод в Check сверяют текущий
предмет с действующим основанием. Существующие рёбра при возврате задачи не
проверяются заново автоматически; проверка UI нужна отдельно. Согласовать
новый UI задним числом как исходный эталон нельзя. Новый допуск показывает,
какая часть работы потребовала пересмотра; вид приёмки этой части проверяется
по ACCEPTANCE.md с учётом фактического времени согласия.

Более мягкая альтернатива разрешает агенту считать некоторые изменения
материала редакционными и сохранять согласие по смыслу. Она уменьшает число
повторных вопросов, но вводит новую спорную границу. Рекомендация для первой
версии требует нового согласия при любом изменении выбранного комплекта.
Опечатки в служебной записи вне комплекта этого не требуют.

## Решение 6. Все входы используют одну проверку

Рекомендуется общий модуль Go в `internal/` с чистой проверкой снимка и
отдельным получением данных Git. `taskctl` и `shipctl` вызывают его напрямую.
Дашборд обращается к тем же операциям taskctl. Хук конкретного клиента может
раньше показать причину, но не служит единственным местом проверки.

На входе модуль получает роль, предмет, основание, выбранный материал,
согласие, исходный допуск и контекст операции. На выходе возвращает
`ready`, `preparation`, `not-ready` или `error`, код причины и способ продолжения.
`preparation` разрешает задачу дизайна, но не реализацию. Недоступность Git,
битый комплект, неизвестная схема и неоднозначный предмет дают закрытый допуск
с точной причиной. Ошибка проверки не считается отсутствием UI.

| Вход | Когда нужна проверка | Что происходит при неготовности |
|---|---|---|
| `taskctl move ... in-progress` и его dry-run | До записи доски и коммита; для возврата в работу сверяется действующее основание | Доска не меняется; печатаются пробел и следующий шаг |
| `shipctl start` | До создания или переключения дерева, включая строку уже in-progress | Ветка, дерево и статус остаются прежними |
| Автономные `slot`, `arm`, повторная проверка перед пробуждением | При отборе и непосредственно перед запуском | Кандидат пропускается с причиной; независимые кандидаты остаются доступны |
| Ручной и автоматический запуск головы уже начатой задачи | Перед продолжением UI-реализации | При изменённом основании агент занимается пересмотром, а код UI ждёт |
| Слияние и переход в Check | До операции с кодом или статусом | Устаревший допуск не проходит, текущая работа сохраняется |

Выбор кандидата и старт разделены во времени. Проверка перед стартом заново
читает предмет, выбранные файлы и согласие. Она использует существующий
порядок транзакций, сверяет снимок перед записью и при его изменении предлагает
повтор. Долгие внешние чтения не выполняются под общей блокировкой доски.
Успешный отбор не является разрешением работать с изменившимся содержимым.

Предлагаемые операции интерфейса taskctl: записать классификацию, показать
предмет согласия, сохранить ответ по его снимку, проверить допуск. У проверки
есть читаемый вывод и JSON с версией, результатом, кодом причины, ID задачи,
идентификаторами материала и предмета, следующим действием. Точные имена новых
подкоманд выбирает исполнитель кандидата 1; операции и значения результата
остаются этим контрактом.

Пример сообщения при отказе: «XR-42: UI требует дизайна; нет согласия на
комплект A, редакция B. Подготовить дизайн и предъявить эту редакцию человеку;
после согласия повторить старт». При устаревании выводятся оба идентификатора.
При неизвестной классификации выводится «заполнить Проектирование UI», при
ошибке чтения указывается недоступный источник. Автономный вывод содержит
тот же код причины и ID пропущенного кандидата.

## Решение 7. Переход не выдаёт согласия старым задачам

Это рекомендация для П-5, ожидающая согласия человека.

Новые карточки получают явную классификацию на груминге или при нарезке цели.
Старые строки Backlog дополняются перед ближайшим стартом; массовой правки
всех файлов не требуется. Отсутствие поля не трактуется как «UI нет». В списке
показывается, какие строки ждут классификации, и конвейер выбирает другие.

У начатых до включения проверки задач сохраняется старое основание старта.
Они помечаются как начатые по прежнему порядку и проходят приёмку по
ACCEPTANCE.md с фактическими материалами; автоматического согласия не получают.
При новом UI-предмете требуется новый допуск. При включении механизма в Git сохраняются версия политики и исходный коммит
доски. Такая метка вычисляется по статусу строки в этом коммите; агент не
выставляет её произвольно.

Альтернатива с полным пересмотром всех начатых UI-задач даёт более одинаковое
состояние, но останавливает действующую очередь ради ретроспективного дизайна.
Вариант «только новые ID» проще при включении, но оставляет старый Backlog
неограниченным обходом. Рекомендация применяет новый порядок к каждому новому
старту, сохраняя происхождение уже начатой работы.

Раскладка правил и команд идёт обычным подключением devkit и `doctor --fix`.
Версия схемы проверяется после обновления. Появление старого клиента с новым
контрактом завершается сообщением об обновлении; отключение UI-проверки из-за
неизвестной схемы недопустимо. Дашборд не является обязательной зависимостью.

## Проверка конечных путей

Все исходы таблицы условны до согласия с П-1..П-5. Случай проверяется по одному
снимку; прочие требования старта остаются в силе.

| Случай и вход | Допуск | Следующее действие |
|---|---|---|
| Новый экран, роль реализация UI, материала нет | `not-ready`, нужен дизайн | Агент готовит задачу дизайна; человек согласует материал |
| Материал есть, показан, ответа ещё нет | `not-ready`, нет согласия | Предъявить вопрос по этому снимку и продолжать независимые задачи |
| Дизайн согласован, предшествующая user-задача ещё не закрыта | `not-ready`, неснятая предпосылка | Довести её приёмку и закрытие обычным порядком |
| Предпосылка закрыта; предмет покрыт, комплект и согласие совпадают | `ready` | Команда фиксирует начальный допуск и разрешает реализацию |
| Прямая ссылка на ранее согласованный Git-комплект без новой задачи дизайна | `ready`, если доказаны согласие до старта и покрытие предмета | Зафиксировать основание в коммите захвата |
| Выбранный макет исправлен после согласия | `not-ready`, устаревшее согласие | Новая редакция и новое согласие либо возврат к прежнему снимку |
| Рядом добавлен невыбранный вариант | Прежний `ready` сохраняется при неизменном предмете | Исполнять выбранный комплект; выбор новой альтернативы требует согласия |
| Точная замена цвета на известный токен, все условия мелочи доказаны | `ready`, мелкая правка | Сохранить границы и выполнить объективные проверки |
| Изменён общий токен; влияние на потребителей неизвестно | `not-ready`, недостаточно оснований мелочи | Исследовать потребителей; при изменении смысла подготовить дизайн |
| Человек явно разрешил без макета текущий предмет | `ready`, разрешение человека | Сохранить ответ и пределы, приёмку реализации назначить по барьерам |
| Есть разрешение без макета, но добавлен новый шаг потока | `not-ready`, изменён предмет | Новое разрешение либо дизайн до продолжения изменённой части |
| Нет UI, есть основание и проверка неизменённого поведения | `ready` | Обычный порядок разработки |
| Секция отсутствует, пуста или значение неизвестно | `not-ready`, не закончена классификация | Классифицировать; неизвестное влияние не объявлять отсутствием UI |
| Подготовка UI без изменения продукта | `preparation` | Подготовить материалы, получить человеческое согласие |
| Комплект, Git или согласие невозможно прочитать | `error`, источник недоступен | Восстановить доступ и повторить проверку; статус не меняется |
| После автономного выбора предмет изменился до start | Повторная проверка даёт `not-ready` | Не начинать код по старому отбору, показать изменённое основание |

Статическая сверка показывает достижимость этих исходов без зависимости от
агентского клиента. Неизвестных технических условий для подготовки LLD не
найдено при чтении исходников, формы и текущих проверок. Для реализации нужно
человеческое согласие с политиками и минимальным интерфейсом этого LLD.
Разработка просмотра из DK-1554 может идти отдельно.
Доступы, секреты, публикация и невозвратные операции для данного проекта
решения не требуются.

## Риски и проверка рекомендаций

| Риск и условие | Показатель и последствие | Основание рекомендации и проверка |
|---|---|---|
| UI скрыто в общей библиотеке или сервере | Полнота классификации; неожиданный вид или поток | Классификация по эффекту; разобраны общий токен и серверное состояние, после реализации нужны фикстуры обоих случаев |
| Закрыта задача дизайна, выбран другой материал | Точность эталона; согласие относится к чужой редакции | Ребро и отпечаток проверяются независимо; конечные пути включают замену материала |
| Ручной move или повторный start обошёл проверку | Одинаковый допуск на входах | По коду найдены все перечисленные входы; общий модуль и повторная проверка обязательны для кандидата 2 |
| Служебная запись изменила отпечаток | Стоимость процесса; лишний вопрос человеку | Отпечаток отдельного устойчивого предмета; журнал не входит в комплект, проверяется отдельным сценарием |
| Материал изменился между отбором и записью | Свежесть согласия; код начат по старому решению | Сверка снимка перед фиксацией; отдельный случай изменения во время старта |
| Макет сохранён, но недоступен человеку | Возможность дать согласие; ожидание без результата | Предъявление конкретной редакции проверяет DK-1554; без него вопрос не задаётся |
| Старые задачи обходят новое требование | Полнота применения к новым стартам | Ленивая классификация Backlog и проверяемая историческая метка начатых; варианты перехода вынесены человеку |

Это анализ контракта по текущему коду, а не результат прогона ещё не
существующих команд. Число повторных согласований и влияние на расход
подписки можно измерить после внедрения; числовые обещания здесь не приняты.

## Нарезка

Пробная нарезка 2026-11-17, строк реализации на доске нет. Сначала человек
принимает LLD, включая минимальный интерфейс материала. Кандидаты связаны
последовательностью 1 -> 2 -> 3. Фактические ранги перед заведением пересчитываются
по принятому решению и зависимостям.

- кандидат 1 (task, M, R=65). Задача хранит проверяемый UI-контракт и согласие на снимок. Включает читаемый раздел, операции классификации и согласования, общий разбор, идентификатор предмета и чтение минимального Git-материала по явному составу из раздела задачи. Проверка agent после установки в отдельный подключённый проект: без дашборда классифицировать нет UI, мелочь и реализацию, записать ответ тестового человека в синтетическом разговоре, изменить материал и получить устаревшее согласие. Продукт доступен как явная диагностика допуска; обязательный старт ещё работает по прежним правилам. Полная реализация DK-1554 не требуется; будущий комплект подключается через согласованный минимальный интерфейс.
- кандидат 2 (task, M, R=65). Каждый вход старта и продолжения проверяет UI-допуск. Включает move/dry-run, shipctl start, автономный выбор и пробуждение, начальный допуск, защиту слияния и Check, переход старых задач. Проверка agent после установки: синтетические проекты прогоняют всю таблицу, сопоставляют ручной и автоматический отказ, повторяют start из in-progress и меняют материал между отбором и фиксацией. Без материала состояние, дерево и ветка сохраняются; другая задача доступна выбору. После кандидата 1.
- кандидат 3 (task, M, R=65). Подготовка UI входит в обычный порядок devkit и доезжает в подключённые проекты. Включает board-groom, board-task, нарезку, определения исполнителей и ревью, TASKFORM.md, ACCEPTANCE.md с новым якорем возраста, подключение и входную документацию. Проверка agent после установки: в отдельном проекте без дашборда агент оформляет существенный UI с предпосылкой user, точную мелочь и отсутствие UI; в утверждённом сценарии тестового разговора получает согласие на редакцию, затем проходит запуск и сверку реализации. Нужны obeycheck для изменённых промптов и проверка раскладки doctor; тесты каждой правки едут в её задаче. После кандидатов 1 и 2.

У всех кандидатов предварительная разбивка одинакова. Серьёзность 50
наследует ущерб обхода UI-процесса из DK-1712. Ценность 8 относится к основной
пользе согласования до затрат на реализацию. Неопределённость 3 учитывает
стык инструментов, Git и подключённых проектов после принятия политик.
Поправка на баг 0, потому что вводится новый обязательный порядок. Рычаг 4
даёт общая проверка и доставка будущих UI-задач. Итого
`50+8+3+0+4 = 65`, P1; зависимые кандидаты не выше предпосылки.

Кандидаты agent проверяют уже согласованные правила по синтетическому
разговору; фиктивный ответ не становится согласием на живой дизайн. Приёмка
реальных будущих задач дизайна остаётся user. Кандидат 1 полезен как
диагностика, кандидат 2 механически применяет её, кандидат 3 подключает фазу
подготовки к обычной работе. До кандидата 3 существенные UI-задачи готовятся
по согласованному документу вручную штатными командами.

## Что требуется на приёмке LLD

Человек выбирает П-1..П-5 и проверяет конечные пути, включая цвет кнопки,
общую UI-библиотеку, явное разрешение без макета, изменённое согласие и
неизвестную классификацию. По ответам документ и кандидаты уточняются.
Кандидаты превращаются в задачи только после приёмки. До нарезки и
человеческого согласия DK-1712 не закрывается.
