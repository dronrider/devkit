# DK-194: LLD карты проекта уровня модулей из кода в контекст сессий

## Задача и рамка

Сессия начинает задачу с поиска: знания о том, где что лежит, разбросаны по
коду и докам, и каждая сессия собирает их заново грепами и чтением, а вопрос
«почему так» ищется археологией по docs/lld/. Дизайн фиксирует место, формат и
инструмент карты, состав адаптеров первой очереди и протокол POC-замера на
xr-proxy из постановки задачи. Рамку задают постановка и цель DK-297:

- карта генерится из кода, а не пишется руками, и её целевой размер 40-60
  строк уровня компонентов (уровень функций добывается по запросу через LSP,
  черновик DK-195, и в карту сознательно не едет);
- файл генерённый, но коммитится: на чужой машине без чекаута devkit карта
  обязана оказаться в контексте;
- свежесть держит doctor, доставка идёт тонким файлом харнеса, который
  генератор уже пишет (DK-193);
- до генерализации на все проекты POC на xr-proxy с замером на цифрах;
- индекс решений по docs/lld (приписка DK-293) собирается тем же генератором.

Судьба DK-071 решается здесь, этого требует цель: сторож полноты доки уже
доехал до doctor (задача закрыта 2026-08-14, `describe.check` в
`tools/devkitctl/describe.py`), и карта обязана строиться на его источниках,
а не заводить вторые. Разбор в решении 7.

## Живой материал

Что уже написано и переиспользуется, а не пишется заново.

- `describe.py` умеет находить компоненты: записи workspace-манифестов
  (`members` в Cargo.toml, `use` в go.work, `include` в settings.gradle),
  запасной путь по каталогам верхнего уровня с кодом, исключения
  `.devkit/describe.ignore`. Он же умеет узнавать описания: модульная дока
  корневого файла (`//!` у Rust, `Package` у Go, докстринг `__init__.py` у
  Python), README рядом, заголовок в карте архитектуры.
- devkit: девять утилит в `tools/` (agentctl, cmdout, dashboard, devkitctl,
  obeycheck, regcheck, shipctl, taskctl, trackctl), `internal/` с общим
  go-модулем, `hooks/`, четыре группы `kit/`. У каждой утилиты README, и
  первая его строка несёт готовый однострочник: «# taskctl: механика
  канбан-доски».
- xr-proxy: десять членов Cargo workspace и Android-модуль вне манифеста.
  Модульной доки у крейтов нет, описания живут таблицей состава
  `docs/ARCHITECTURE.md` (колонка «Роль»), и строки там по два-четыре
  предложения.
- docs/lld devkit: девятнадцать документов, сорок один заголовок «Решение N»
  в восьми из них. Одиннадцать остальных пишут тематические заголовки
  («Откуда брать остаток», «Развилка подключения»), нумерованных решений у
  них нет.
- Тонкий файл харнеса: маркер `devkit:generated` с хешем тела, перегенерация
  `devkitctl doctor --fix`, пути наружу через ссылку `.devkit/devkit`
  (DK-193). У xr-proxy тонкий файл сегодня это две строки импорта, ядро и
  ядро доски.
- `devkitctl weigh` меряет вес резидента живым прогоном и держит порог:
  распухание контекста видно цифрой, а не на глаз.

## Решение 1. Источник карты: статический разбор дерева, тулчейн не зовётся

Постановка называла кандидатов `cargo metadata` и `go list -json ./...`.
Оба отвергнуты: команды требуют тулчейна на машине, а генерация карты
обязана работать там же, где работает подключение проекта, на свежем клоне
до всякой сборки и в CI. Статический разбор манифестов уже написан в
`describe.py` и проверен живыми проектами обеих экосистем, заново его писать
незачем. Скорость тут не главное, главное условие «работает до сборки» из
правила языков DK-139.

Единица карты определяется каскадом из трёх шагов, первым сработавший
закрывает каталог:

1. запись workspace-манифеста в корне: член Cargo workspace, модуль go.work,
   include из settings.gradle;
2. каталог с собственным пакетным манифестом (`go.mod`, `Cargo.toml`,
   `pyproject.toml`, `setup.py`, `package.json`, `build.gradle`): обход идёт
   сверху вниз, найденный член внутрь не раскрывается;
3. каталог с кодом по суффиксам из `describe.py`: тот же запасной путь, что у
   сторожа полноты, для скриптовых и бесманифестных деревьев.

На живых проектах каскад даёт ожидаемый результат. xr-proxy: десять членов манифеста
плюс `xr-android`, закрытый вторым шагом по своему build.gradle. devkit:
девять `tools/<утилита>` (у Go-утилит go.mod, у devkitctl сработает третий
шаг по python-файлам), `internal`, `hooks`, `kit/skills` и `kit/harness` с
кодом оболочек; `kit/agents` и `kit/templates` без кода в карту не попадают,
они раскладываются автоматикой и описаны в README devkit.

Исключения `.devkit/describe.ignore` вычёркивают из карты так же, как из
проверки описаний: один список вычетов на оба механизма, вендоренное и
генерённое читателю карты не нужно.

## Решение 2. Описания: те же источники, что у сторожа полноты

Строка карты это «путь: описание», и описание берётся из источников, которые
`describe.py` уже проверяет, в порядке приоритета: модульная дока корневого
файла компонента, первая строка README (заголовок «# имя: » срезается,
остаётся фраза), строка состава из `docs/ARCHITECTURE.md` (колонка роли).
Постановка называла единственным источником модульную доку, но у живых
проектов описания лежат иначе: devkit описан README, xr-proxy таблицей
состава, и требовать доки там, где описание уже есть, значило бы чинить
проекты под генератор. Сторож полноты принимает все три источника с момента
DK-071, карта берёт описания из тех же.

Из найденного источника берётся первое предложение целиком, без жёсткой
обрезки: строка про xr-web в составе xr-proxy несёт три сути (адресация,
сессии, проксирование), и обрезка наугад роняла бы одну из них. Контроль
размера отдельный: вес файла карты виден `weigh`, и выход за порог резидента
это сигнал к сокращению описаний в самих источниках, а не к молчаливой
обрезке в генераторе.

Компонент без описания в карту не едет: строка с прочерком поиску не помогает,
а дыра уже видна находкой `describe.check` (DK-071). Карта на неисправном
проекте неполна по той же причине, и чинится это описанием компонента, не
правкой генератора.

## Решение 3. Место и имя: docs/map.md, генерённый и коммитимый

Постановка оставляла кандидатов docs/ и `.devkit/`. Выбран `docs/map.md`.

Коммитится файл, а не генерится на машине при запуске, потому что чужой
клон без devkit рядом обязан получить карту чекаутом: это и есть способ
«работает на чужой машине», автоматика подключения только освежает. Раз
файл коммитится, ему место в docs/ рядом с долгоживущей докой: `.devkit`
держит машинное и гитигнорнут лишь частично, карта там жила бы вечно
устаревшей копией у каждого, кто не звал доктора. Раскладке DK-139 файл не
противоречит: docs держит материал сессий, карта и есть материал сессии,
кода инструмента в ней нет.

Имя короткое, потому что путь попадает в строку импорта тонкого файла и в
каждый разговор о карте. Рукописные правки исключены той же механикой, что у
тонкого файла: первая строка это маркер `devkit:generated map body=<хеш>`,
расхождение хеша и тела ловится перегенерацией.

Отвергнуто: `docs/ARCHITECTURE.md` как цель записи (в чужих проектах файл
занят рукописной картой, и смешивать генерённое с рукописным в одном файле
нельзя: правка руками и правка генератором затирали бы друг друга); `.devkit/`
(см. выше); отдельный каталог `docs/map/` (один файл, каталог плодит пустоту).

## Решение 4. Формат: плоские строки, таблица отвергнута

Читатель у карты один, контекст модели, и плотность смысла на токен важнее
привычки глаза. Формат фиксирован такой:

```markdown
<!-- devkit:generated map body=<хеш> -->
# Карта проекта

Сгенерировано devkitctl из кода и доки, правится перегенерацией
`devkitctl doctor --fix`, руками не править.

tools/agentctl: вердикты моделей и делегирование субагентам
tools/dashboard: панель наблюдения за доской
...

# Решения по docs/lld

Заголовки «Решение N» из LLD-документов, полный разбор с отвергнутыми
вариантами в самом документе.

DK-139.1 Язык выбирается по тому, что работает до сборки
DK-139.2 Граница sh: сотая строка и своя функция
...
```

Строки карты сортируются по пути, строки индекса по документу и номеру.
Таблица отвергнута: палки и разделители съедают четверть строки, не добавляя
смысла, и постановка это уже предполагала. Список с маркерами `-` отвергнут
по той же причине: два символа на строку при сорока строках индекса.
json и yaml отвергнуты постановкой: плотность ниже, а парсить файл никому
не нужно, свежесть проверяется перегенерацией.

Постановка оставляла раскладку на замер POC. Развилка закрывается здесь, а
POC меряет окупаемость карты целиком, включая формат: раскладку менять по
ходу замера значило бы мерить сразу две переменные.

## Решение 5. Индекс решений из docs/lld, приписка DK-293

Из девятнадцати документов docs/lld восемь держат нумерованные разделы с
разбором отвергнутых вариантов, а навигация по ним ручная: DK-211 поднимала
уже решённую развилку и восстанавливала историю по DK-118 и DK-100 вручную.
Индекс собирается тем же генератором, тем же файлом, вторым разделом:
заголовки второго уровня «Решение N. ...» из `docs/lld/*.md` сводятся в
строки «DK-139.2 граница sh: сотая строка и своя функция». На сегодня это
сорок одна строка по восьми документам.

Тематические заголовки одиннадцати остальных документов в индекс не едут:
строки «Задача и рамка» и «Тесты» про содержание решения не говорят, а
blacklist «шаблонных» заголовков ломался бы на каждом новом разделе. Конвенция
«Решение N» уже живая, её держат восемь документов, и новые LLD пишут так же;
этого достаточно, чтобы индекс рос сам. Архив задач не индексируется: решением
считается раздел LLD, а не строка доски.

Вес индекса это добавка к целевому размеру карты, сорок-пятьдесят строк
сверх сорока-шестидесяти. Добавка принята сознательно: вопрос «почему так»
стоит в начале почти каждой нетривиальной задачи, и DK-211 уже показала цену
его ручного решения. Вес едет в замер `weigh` наравне с картой и режется
первым, если резидент выйдет за порог.

## Решение 6. Доставка: импорт из тонкого файла харнеса

Строка `@docs/map.md` встаёт последним импортом тонкого файла, после правил.
Путь лежит внутри проекта, ссылка `.devkit/devkit` не нужна: карта файл
проектный, а не devkit-овый. Строка появляется только когда файл карты
существует: свежий проект до первого `doctor --fix` не должен получить
битый импорт, а проект без кода (репозиторий одной доки) не должен получать
карту вовсе.

Механика доставки не новая: `thin_text` собирает тело тонкого файла,
перегенерация меняет хеш маркера, `check_thin` видит устаревание и `--fix`
чинит. Свежесть карты и свежесть тонкого файла сцеплены одной командой:
удалил компонент, позвал доктора, получил и новую карту, и новый тонкий
файл.

Харнесы со вклейкой (`mode = "embed"`) получают карту блоком в AGENTS.md той
же механикой, что правила. Сегодня оба профиля devkit работают импортом,
ветка остаётся на реализацию, отдельного решения не требует.

## Решение 7. Свежесть и судьба DK-071

Doctor перегенерирует карту в памяти и сверяет с файлом на диске. Находки
три: файла нет, а компоненты есть («сессии собирают карту грепами;
сгенерировать: devkitctl doctor --fix»); хеш не сходится с телом (файл
правлен руками); тело разошлось с деревом (новый компонент, изменившаяся
первая строка README, новый заголовок «Решение N»). Все три чинятся
перегенерацией по `--fix`, занятого имени, как у ссылки DK-193, тут нет:
файл целиком генерённый.

Цель DK-297 спрашивала судьбу DK-071: строка серии или поглощение механизмом
свежести карты. Поглощение уже состоялось, только в обратную сторону:
сторож полноты доки доехал до doctor раньше этого LLD и остаётся
единственным сторожем описаний. Карта не сторож, а потребитель тех же
источников, и отдельного сторожа полноты карты не заводится: неполнота
карты это либо находка описания (чинится описанием), либо находка свежести
(чинится перегенерацией). Третьего молчаливого состояния нет: карта без
файла, с разошедшимся хешем или без строки компонента всегда видна в
докторе, а доезд в контекст виден замером `weigh` и пробой с кодовым словом
(раздел «Наблюдаемость»).

## Решение 8. Инструмент: подкоманда devkitctl map

Генерация нужна до сборки и в чужом проекте по вызову из чекаута devkit,
значит python по правилу языков DK-139. Отдельный инструмент отвергнут:
карту не зовут по имени из PATH, её зовёт доктор и человек изредка, ради
двух вызовов в день сборку и бинарь не заводят.

Подкоманда: `devkitctl map -C <dir>` печатает карту в stdout (сухой прогон,
удобен для POC и ревью генерации), `--write` пишет `docs/map.md`. Doctor
зовёт ту же функцию генерации для сверки, дублирования логики нет. Код
живёт новым модулем `tools/devkitctl/codemap.py` рядом с `describe.py`,
чьи функции разбора он переиспользует; имя модуля не `map`, чтобы не
тенить встроенное имя в импортах.

## Протокол POC на xr-proxy

Замер из DoD постановки: пара типовых задач с картой и без, сравнение расхода
квоты. Протокол такой, чтобы шум вычитался, а не объяснялся словами.

1. Ветка в xr-proxy: сгенерированная карта (сухой прогон `devkitctl map`,
   запись файла), строка импорта в тонкий файл xr-proxy. До замера проба с
   кодовым словом из карты в `claude -p`: карта доезжает в контекст, иначе
   замер меряет не карту, а дыру доставки.
2. Две пары задач одного типа и размера с бэклога xr-proxy (LLD или
   кодовые, не одна и та же дважды: повторная попытка дешевле выученного).
   Прогон A без карты, B с картой, контрольная пара зеркально: C с картой,
   D без. Порядок чередуется, модель и effort одинаковые во всех четырёх.
3. Расход меряется по журналам сессий (`devkitctl drain -C`) токенами, не
   ощущениями: суммарный расход сессии как основная цифра и доля поисковых
   вызовов (grep, find, чтение файлов подряд) как объяснение механики.
4. Цифры ложатся в файл задачи замера. Критерий генерализации: в обеих
   парах экономия поиска перекрывает собственный вес карты. Не перекрыла:
   карта остаётся внутренним механизмом самого devkit, генерализация отклонена,
   отказ фиксируется в файле задачи с цифрами. Решение читает пользователь, цель
   DK-297 генерализацию в DoD не содержит.

## Наблюдаемость

- Бездействие карты видно находкой доктора (нет файла, разошлась) и
  расхождением `weigh` с живым замером, если импорт не доехал.
- Доезд виден живым замером `weigh -C` и разовой пробой с кодовым словом
  (механика DK-190/DK-193), обе входят в сценарий проверки реализационной
  задачи и в шаг 1 протокола POC.
- Польза видна цифрами POC в файле задачи замера, это и есть способ показать
  снаружи, что фича отработала.

## Тесты

По стандарту devkit, пирамидой в `tools/devkitctl`.

- Генератор на синтетике: манифест Cargo даёт членов, go.work даёт модули,
  дерево без манифестов даёт каталоги с кодом, пакетный манифест на глубине
  закрывается членом и внутрь не раскрывается. Мутация «вернуть подсчёт
  только по каталогам верхнего уровня» роняет тест devkit-подобной синтетики
  (утилиты схлопываются в одну строку `tools`).
- Описания: модульная дока, первая строка README со срезом заголовка, строка
  состава из ARCHITECTURE.md; первое предложение берётся целиком; компонент
  без описаний в карту не едет. Мутация «взять весь README» роняет тест
  длины строки.
- Маркер и свежесть: рукописная правка меняет хеш, новый член манифеста и
  новый заголовок «Решение N» меняют тело, `--fix` перегенерирует,
  describe.ignore вычёркивает и из карты.
- Индекс: заголовки «Решение N» собираются с документом и номером, прочие
  заголовки второго уровня не едут, архив не индексируется.
- Тонкий файл: строка `@docs/map.md` появляется при существующем файле и не
  появляется без него; встаёт последней, после правил.

## Затрагиваемая документация

## Границы и риски

- Описания без жёсткой обрезки могут распухать: контролируется порогом
  `weigh`, первое лекарство это сокращение предложения в источнике, второе
  урезание индекса решений (решение 5).
- Конвенция «Решение N» не универсальна: в чужих проектах индекс пуст,
  карта при этом полноценна. POC на xr-proxy меряет карту без индекса, его
  вес обоснован отдельно (DK-211) и в критерий генерализации не входит.
- Карта дублирует смысл раздела «Состав» README devkit и таблицы состава
  xr-proxy. Дубль осознанный: README пишется руками для человека и живёт
  своей свежестью, карта генерится для сессии и свежесть держит доктор;
  сверять их между собой автоматике незачем, расхождение ловится на ревью.
- POC может опровергнуть пользу: тогда генерализация отклонена по цифрам, а
  не по вкусу, и карта остаётся внутренним механизмом devkit.

## Что делает реализация

Разбивка ложится в цель DK-297.

1. devkitctl, цена M: `describe.py` достаёт текст описания (сегодня он
   возвращает факт наличия), новый модуль `codemap.py` с генератором,
   подкоманда `map` с `--write`, находка свежести в doctor, строка импорта
   в `thin_text`, тесты, дока devkitctl. Той же задачей генерируется и
   коммитится карта самого devkit, тонкий файл devkit получает импорт, вес
   проверяется `weigh`.
2. POC-замер на xr-proxy, цена M: протокол выше, цифры в файл задачи,
   решение о генерализации за пользователем.
