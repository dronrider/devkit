# DK-014: agentctl: effort в вердикте pick отвязать от модели, считать по неопределённости

Замечание пользователя к DK-011: маппинг effort получился жёстко привязанным
к модели. Effort назначается тем же правилом, что выбирает модель, и оси
склеились: haiku всегда low, sonnet всегда medium, fable всегда xhigh, вилка
high/xhigh есть только у opus. В рамках одной модели уровень effort должен
зависеть от задачи.

Направление решения: две независимые функции от метаданных доски. Модель
выводится, как сейчас, из типа и цены (калибр исполнителя), effort считается
отдельно от неопределённости (сколько придётся думать по ходу). Примеры
ожидаемых сдвигов против текущей таблицы: S/M с неопределённостью 0 дают
low вместо medium, L с неопределённостью 1 едет на opus с medium вместо
безусловного high.

Развилки, решить при реализации:

- границы уровней по неопределённости (где кончается medium, с какого
  значения high);
- effort при неоценённой цене и нечитаемой разбивке ранга (сейчас там high
  в пользу осторожности);
- остаётся ли xhigh только за LLD и грумминговыми вердиктами или высокая
  неопределённость исполнимой задачи тоже до него дотягивается;
- хватает ли набора определений agents/ (он уже по уровням, а не по моделям,
  меняться не должен, но проверить).

Обе override-строки («Модель», «Эффорт») и формат вывода pick не меняются,
правится только вычисление. Таблица маппинга в agentctl/README.md
переписывается под две оси той же веткой; п. 10 RULES.board.md формулировок
про склейку не содержит, но перечитать на предмет устаревшего.

## Ход работы

- Исполнение: субагент opus/high по вердикту pick, 2026-07-30.

Вердикт складывается из двух функций: `pickModel` по типу и цене (правила не
тронуты) и новая `pickEffort` по неопределённости.

Принятые развилки.

- Границы уровней по неопределённости взяты с её же шкалы в `RANKING.md`:
  0 это «рутина, делалось много раз» и там `low`, 1 «всё ясно, осталось
  сделать» и 2 (шкала его не описывает, он ближе к единице) дают `medium`,
  3 это «в деталях есть развилки» и там размышление окупается, значит `high`.
- Неоценённая цена и нечитаемая разбивка ранга остались на `high`, как и было.
  Прочерк в цене значит, что грумминг не доведён до конца, и нулю в третьем
  слагаемом доверия тогда не больше, чем прочерку в ранге. Осторожность
  сохранена на обеих осях: модель по такой строке тоже остаётся opus.
- Уровень `xhigh` исполнимой задаче не достаётся. Неопределённость 4-5 это
  порог готовности из `RANKING.md`: вердикт по такой строке и так грумминговый,
  а всё, что исполнимо, укладывается в 0-3. Так верхний уровень остаётся за
  проектированием (LLD), груммингом и разбивкой XL, и «дотягиваться» до него
  исполнимой задаче незачем.
- Набор `agents/` не поменялся, все четыре уровня маппинг по-прежнему выдаёт.
  Поправлены только описания во frontmatter: они пересказывали старую склейку
  («effort low это правка ценой S»), а условие теперь про неопределённость.

## Сценарий проверки

Агентский: все шаги выполняются с машины агента, ничего не меняют, кроме
временной директории в `/tmp`. Проверяется на слитой main.

1. Тесты утилиты:

   ```sh
   cd ~/projects/devkit/agentctl && go test ./...
   ```

   Ожидается `ok  github.com/dronrider/devkit/agentctl`, код возврата 0.

2. Сборка и синтетическая доска. Пары проверяются на ней, а не на живых
   задачах: живую строку перегруммят, и сценарий протухнет.

   ```sh
   cd ~/projects/devkit/agentctl && go build -o /tmp/agentctl-dk014 .
   mkdir -p /tmp/dk014/docs/tasks
   printf '%s\n' '# demo: задачи (префикс T)' '' '## Backlog' '' \
     '| ID | Задача | Тип | P | R | Цена | Ссылка |' '|---|---|---|---|---|---|---|' \
     '| T-001 | мелкая правка | task | P3 | 5 (0+3+0+0+2) | S | - |' \
     '| T-002 | рутинная фича | task | P2 | 33 (25+4+0+0+4) | M | - |' \
     '| T-003 | фича с деталями | task | P2 | 34 (25+4+1+0+4) | M | - |' \
     '| T-004 | объёмная фича | task | P2 | 35 (25+4+1+0+5) | L | - |' \
     '| T-005 | фича с развилками | task | P2 | 37 (25+4+3+0+5) | L | - |' \
     '| T-006 | цена не оценена | task | P2 | 20 (10+5+0+0+5) | - | - |' \
     '| T-007 | дизайн подсистемы | LLD | P1 | 30 (25+5+0+0+0) | L | - |' \
     '| T-008 | неразобранная задача | task | P1 | 64 (50+6+5+0+3) | M | - |' \
     > /tmp/dk014/docs/TASKS.md
   for id in T-001 T-002 T-003 T-004 T-005 T-006 T-007 T-008; do
     printf '%s: ' $id; /tmp/agentctl-dk014 -C /tmp/dk014 pick $id | head -2 | tr '\n' ' '; echo
   done
   ```

   Ожидаются пары `haiku/low`, `sonnet/low`, `sonnet/medium`, `opus/medium`,
   `opus/high`, `opus/high`, `fable/xhigh`, `opus/xhigh`, код возврата 0.
   Главное здесь T-002 и T-003: одна и та же модель едет с разным effort,
   потому что различаются они только неопределённостью.

3. Живая доска отвечает тем же контрактом (значения зависят от текущих
   метаданных задачи и не фиксируются):

   ```sh
   /tmp/agentctl-dk014 -C ~/projects/devkit pick DK-014; echo "код $?"
   ```

   Три строки вывода, первые две начинаются с `model: ` и `effort: `, код 0.

4. Override по каждой оси отдельно (двоеточие подставляется аргументом printf,
   чтобы строка не сработала как override уже в этом файле):

   ```sh
   printf '# T-002\n\nМодель%s opus\n' ':' > /tmp/dk014/docs/tasks/T-002.md
   /tmp/agentctl-dk014 -C /tmp/dk014 pick T-002
   printf '# T-004\n\nЭффорт%s low\n' ':' > /tmp/dk014/docs/tasks/T-004.md
   /tmp/agentctl-dk014 -C /tmp/dk014 pick T-004
   ```

   У T-002 `model: opus` из override и `effort: low` из маппинга, у T-004
   `model: opus` из маппинга и `effort: low` из override, в его третьей строке
   есть «effort задан override-строкой».

5. Опечатка в уровне валит вердикт:

   ```sh
   printf '# T-004\n\nЭффорт%s highest\n' ':' > /tmp/dk014/docs/tasks/T-004.md
   /tmp/agentctl-dk014 -C /tmp/dk014 pick T-004; echo "код $?"
   ```

   Ожидается сообщение про неизвестный effort и код 1.

6. Уровни маппинга покрыты определениями исполнителей:

   ```sh
   grep -h '^effort:' ~/projects/devkit/agents/*.md | sort
   ```

   Четыре строки: `high`, `low`, `medium`, `xhigh`.

Уборка: `rm -rf /tmp/dk014 /tmp/agentctl-dk014`.
