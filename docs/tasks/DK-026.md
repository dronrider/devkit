# DK-026: doctor всегда красный на самом devkit: ссылки в архиве задач ведут мимо

## Разбор корня

taskctl close переносит файл `docs/tasks/<ID>.md` в `docs/tasks/archive/<год>/<ID>.md`. Относительные markdown-ссылки внутри файла разрешались от `docs/tasks/`, и после переноса ведут мимо. Глубина выросла на два уровня. Из других файлов репозитория, ссылающихся на переносимый файл, ссылки тоже ломаются.

Решение: при переносе переписывать относительные ссылки в самом файле (разрешать их от старой директории и пересчитывать относительно новой) и в других markdown-файлах репозитория, которые на него ссылаются. Внешние ссылки и якорные ссылки без пути пропускаются.

## Ход работы

- Правка в taskctl/ops.go: функции rewriteLinksInFile и findAndRewriteReferencesToFile для переписывания ссылок; вызовы в cmdClose перед коммитом.
- Разовая починка трёх битых ссылок в архиве (DK-012, DK-010, DK-030).
- Тесты: TestRewriteLinksInFile, TestFindAndRewriteReferences, TestCloseWithLinks (каждый под конкретную поломку).

## Сценарий проверки

Агентский. Мутации проверяются перед закрытием.

1. `python3 devkitctl/devkitctl.py doctor` выдаёт находок: 1 (только про deploy.local), о битых ссылках не говорит.

Ожидаемый вывод (реальный):
```
находок: 1
нет .devkit/deploy.local: команда выката не задана, shipctl merge оставит выкат пользователю (болванку заводит devkitctl new или doctor --fix)
```

2. `cd taskctl && go test ./...` завершается кодом 0.

3. regcheck --base main --tests taskctl/ops_test.go -- sh -c 'cd taskctl && go test ./...' выдаёт регрессию закрыта.

Ожидаемый вывод содержит:
```
тест краснеет на main и проходит на текущем коде, регрессия закрыта
```

Шаги проверяют регрессионность изменений: тесты падают на старом коде и проходят на новом.

## Ревью

- cmdClose: изменения в файлах, ссылающихся на перенесённую задачу (changedFiles из findAndRewriteReferencesToFile), стейджатся отдельным git add, но в финальный коммит не попадают - p.Commit.apply коммитит только явный список paths (TASKS.md, TASKS-archive.md, старый и новый путь файла задачи), changedFiles туда не включены. git commit -m ... -- <pathspec> берёт только перечисленные пути. Проверено вручную: после успешного close git status показывает M docs/REFERENCE.md, а в HEAD старая ссылка: исправлено
- rewriteLinksInFile и findAndRewriteReferencesToFile переписывают ссылки внутри блоков кода (тройные кавычки и инлайн-код), хотя постановка задачи явно требует их не трогать. Проверено вручную: ссылка внутри тройных кавычек с примером [text] и ../lld/X.md в блоке regcheck -- ... переписывается наравне с обычной, регэксп fullLinkRe не учитывает fenced code blocks: исправлено
- rewriteLinksInFile и findAndRewriteReferencesToFile используют устаревший io/ioutil (ReadFile/WriteFile) вместо os.ReadFile/os.WriteFile, которым пользуется весь остальной taskctl (archive.go, board.go, review.go, view.go, init.go) - лишний импорт и стилевая нестыковка с соседним кодом: исправлено
- rewriteLinksSkippingCodeBlocks удваивает завершающий перевод строки: строки собираются через strings.Split(text, "\n") + WriteString(line+"\n") на каждой итерации, включая пустой хвостовой элемент от файла, уже заканчивающегося на \n, а обрезка в конце функции снимает лишний \n только когда исходный текст им не заканчивался. Проверено end-to-end через taskctl close: и перенесённый файл задачи, и переписанный файл со входящей ссылкой на диске получают \n\n вместо \n на конце (проверено xxd). Ни один тест не ловит - все проверки на strings.Contains, не на точное совпадение
- rewriteLinksSkippingCodeBlocks закрывает забор кода по совпадению первых трёх символов делимитера, не сверяя длину закрывающего забора с длиной открывающего. Вложенный трёхсимвольный ```-забор внутри более длинного четырёхсимвольного ````-забора закрывает внешний блок раньше времени, и содержимое между ними (в т.ч. ссылки) снова попадает под переписывание, хотя по CommonMark должно оставаться защищённым до настоящего закрывающего забора. Подтверждено экспериментом. Заодно проверка отступа indent <= 4 разрешает открывать забор с отступом в 4 пробела, а по CommonMark допустимо не больше трёх; граница ничем не протестирована, мутация indent <= 3 не ловится ни одним тестом
- TestCloseRewritesIncomingLinks проверяет только содержимое INCOMING.md на диске (os.ReadFile), а не то, что правка попала в коммит: CloseParams в тесте не задаёт Commit.Msg, поэтому p.Commit.apply вообще не делает git add/commit. Мутация 'убрать paths = append(paths, changedFiles...)' тестом не ловится. Сама правка в проде работает верно (проверено вручную сквозным прогоном close - git status чист, HEAD содержит переписанную ссылку), но регрессионный тест на исходное замечание 1 по факту его не проверяет
