# DK-030: обоснования из правил в README утилит, в правилах императив

Резидентная часть правил (вес и динамика роста разобраны в
[DK-029](DK-029.md)) состоит не только из самих правил. Изрядная её доля это
объяснение, зачем правило такое: «Поезд выката» занимает 1766 символов и в
основном рассказывает, чем пачка выгоднее одиночных выкатов, «Нужна ли
фичеветка» 598 при правиле в две строки. Человеку это стоит прочитать один
раз, а платится оно каждой сессией и каждым субагентом.

Раскладка по разделам, символы:

```
RULES.md          3486  31%  Код и тексты
                  1918  17%  Git
                  1475  13%  Документация изменений
                  1310  12%  Фича доезжает до пользователя
                  1216  11%  Тесты обязательны
RULES.board.md    7221  45%  Ветки, ревью и деплой
                  8299  52%  Трекинг задач
```

Самые тяжёлые пункты доски: «Выбор модели» 2045, «Поезд выката» 1766, «Выкат»
1102, «Файл задачи» 945, «Инициатива слияния» 887, «Инструкция проверки» 876.

Куда переносить, понятно: README утилит уже читаются по надобности и в
контексте не лежат, а `agentctl/README.md` на 361 строку показывает, что место
для подробного «почему» там есть. Отдельная часть обоснований и вовсе
дублирует то, что утилита не даст сделать неправильно: `shipctl merge` сам не
пустит слияние с открытыми замечаниями, и пересказ этого в правилах резидентен
зря.

Чего делать нельзя. Раздел «Код и тексты» трогать в эту сторону нельзя, и это
не вопрос объёма. У него нет триггера: когда станет ясно, что правило про
символы и мимикрию пора подгрузить, текст уже написан. Такие правила работают,
только пока лежат в контексте, и глобальный `CLAUDE.md` не зря помечает их
«часто нарушается» даже в резидентном виде. То же касается запрета на следы
ассистента в git-истории.

Честная оговорка про сам приём: для модели «почему» не чистый жир. Обоснование
помогает вести себя разумно в случаях, которые правило буквально не покрывает,
поэтому резать надо пересказ механики и повторы, а не всякое объяснение подряд.
Прикидка выигрыша это 30-40% `RULES.board.md`, но проверять её надо не на глаз:
после правки прогнать типовой сценарий (взять задачу, слить, выкатить) и
убедиться, что решения не поехали.
