# DK-034: уведомления, когда сессия ждёт действия или субагент закончил работу

Сессий на машине несколько сразу: у каждой взятой задачи свой worktree после
`shipctl start`, рядом фоновые субагенты. Та из них, что упёрлась в запрос
разрешения или закончила ход, просто стоит, пока на её окно не посмотрят.
Наружу об этом не говорит никто, и время между «агент спросил» и «вопрос
увидели» упирается только в то, как часто переключаешь окна.

Своими средствами харнеса это не закрывается. Канал уведомлений у Claude Code
(`preferredNotifChannel`) прибит к конкретным терминалам: iterm2, kitty,
звонок терминала. Работа идёт в VS Code и в Terminal.app, где из этого набора
не годится ничего, и в `~/.claude/settings.json` канал поэтому не выставлен
вовсе. Вдобавок devkit метит стать китом для любых харнесов (DK-033), а канал
внутри клиента остаётся его частным делом и на Codex или OpenCode не
переносится.

## Что даёт харнес

Событие `Notification` отдаёт хуку на stdin JSON с полями `session_id`,
`cwd`, `transcript_path`, `permission_mode`, `hook_event_name`, текстом
`message` и, главное, поводом `notification_type`. Поводов документировано
восемь: `permission_prompt`, `idle_prompt`, `agent_needs_input`,
`agent_completed`, `elicitation_dialog`, `elicitation_complete`,
`elicitation_response`, `auth_success`. Тип работает и матчером в
`settings.json`, то есть отбор поводов делается конфигом, а не кодом хука.
Решениями хук не управляет, от него ждут кода 0.

Рядом стоит `SubagentStop` с полями `agent_id`, `agent_type` и
`last_assistant_message`.

## Что согласовано с пользователем

1. Поводов три: сессия требует действия (запрос разрешения, вопрос агента,
   диалог MCP), сессия закончила ход и ждёт ввода, фоновый субагент отработал.
2. Конца каждого хода среди поводов нет. Событие `Stop` срабатывает на
   каждом ответе, и уведомление на нём превращается в фон, который перестают
   замечать. Момент «пользователь уже отвлёкся» харнес считает сам и присылает
   его поводом `idle_prompt` примерно через минуту простоя, своей логики с
   замером длительности хода не заводим.
3. На macOS шлём штатным `osascript`, внешних зависимостей нет.
   `terminal-notifier` с кликом-переходом в нужное окно не берём: он ставится
   через brew, а лишний шаг установки на новой машине рано или поздно не
   сделают.
4. Решение не одномашинное: бэкенд выбирается по платформе, но первой очередью
   делается macOS, остальные подставляются тем же интерфейсом.

## Решение

1. Уведомитель это отдельная команда, хук поверх неё тонкий. `hooks/notify.py`
   (python3, как остальные хуки) без флагов принимает заголовок и текст
   аргументами, а в режиме `--hook` читает событие харнеса со stdin и сам
   собирает из него строки. Тогда позвать уведомитель может кто угодно:
   другой харнес по DK-033, скрипт выката, будущая проверка расписания. Разбор
   входа выбирается по имени харнеса (`--hook claude-code`), как это уже
   заложено для проверок текстов в п. 16 постановки DK-033.
2. Бэкенд ищется по платформе и по PATH: macOS шлёт `osascript` с
   `display notification`, Linux `notify-send`, для Windows и WSL остаётся
   заготовка. Переменная `DEVKIT_NOTIFY_BACKEND` перебивает выбор (в тестах
   туда подставляется стаб). Не нашлось ничего, значит уведомитель уходит
   нулём, но пишет отказ в журнал, а не молчит.
3. Текст отвечает на вопрос «какая сессия», иначе при пяти параллельных
   агентах уведомление бесполезно. Заголовок собирается из имени рабочего
   дерева (`cwd`, у worktree задачи в имени лежит её ID) и повода:
   «devkit-dk-026: нужно разрешение». В теле `message` харнеса, для субагента
   первая строка `last_assistant_message`, всё это в одну строку и с обрезкой
   до пары сотен символов.
4. Против шума три ограничителя. Поводы отобраны матчерами в `settings.json`,
   `Stop` не подключается вовсе (п. 2 согласованного). Одинаковый повод одной
   сессии не повторяется чаще, чем раз в окно порядка полуминуты, состояние по
   ключу `session_id` плюс повод лежит в `~/.devkit/notify/`, брошенное старше
   суток убирается само. Полный выключатель отдельной переменной окружения:
   он нужен headless-прогонам, где уведомлять некого.
5. Раскладка идёт автоматикой, а не списком шагов в README. Хук
   `Notification` встаёт в тот же список, который `devkitctl doctor` уже
   проверяет для четырёх нынешних хуков; после DK-032 доктор дописывает такие
   хуки в `~/.claude/settings.json` сам, до неё остаётся находкой с готовым
   JSON. Доктор проверяет и то, что на этой платформе есть чем слать, а чего
   ему не по силам, называет находкой с командой.
6. Наблюдаемость двойная, как у фоновой работы `quota-refresh.sh`. Журнал
   `~/.devkit/notify.log` пишет время, сессию, повод, выбранный бэкенд и код
   возврата, поэтому жалоба «уведомления не приходят» разбирается по факту:
   слали или нет. Плюс самопроверка `notify.py --self-test`, которая шлёт
   пробное уведомление и печатает, чем именно отправила. Без неё macOS
   остаётся дырой в наблюдаемости: баннер от `osascript` приходит от имени
   Script Editor, и если разрешение на уведомления этому имени однажды не
   дали, отправка отвечает нулём, а на экране не появляется ничего.
7. Тесты по пирамиде. Юнитами разбор события в пару «заголовок, тело»
   (включая пустой `message` и многострочный ответ субагента), выбор бэкенда
   по платформе и PATH, окно троттлинга с обеих сторон границы. В `hooks/test.sh`
   прогон целиком: свой PATH со стабом вместо `osascript`, временный HOME,
   событие каждого повода, повтор в окне не шлёт ничего, посторонний тип
   события не шлёт ничего, отсутствие бэкенда даёт код 0 и строку в журнале.
   Мутации, на которых должен краснеть хоть один тест: пропущенный фильтр
   повода, сдвинутая граница окна, `session_id` выпал из ключа троттлинга (все
   сессии сливаются в одну), снятая обрезка тела, потерянная запись в журнал.

## Дока

`hooks/README.md` получает раздел про уведомления (поводы, бэкенды, JSON для
`settings.json`, журнал и самопроверка), `devkitctl/README.md` пополняется
новыми находками доктора, в составе devkit в корневом `README.md` строка про
`hooks/` перестаёт быть только про проверки текстов.

## Открытые вопросы к исполнению

- Что реально прилетает на обычного субагента, поднятого из сессии: повод
  `agent_completed` события `Notification`, событие `SubagentStop` или оба
  сразу. Проверить живьём и подключить то, что срабатывает, иначе на каждом
  субагенте будет по два баннера.
- Учитывает ли харнес поле `terminalSequence` в ответе хука `Notification`
  (решениями это событие не управляет). Если учитывает, оно годится запасным
  путём через сам терминал (OSC 9 или 777) там, где системного бэкенда нет,
  например по ssh.
- Нужно ли молчать, когда окно сессии и так на переднем плане. Спросить
  фронтмост на macOS можно, но это лишний вызов на каждое событие и зависит от
  терминала; по умолчанию не гадаем и шлём всегда.
