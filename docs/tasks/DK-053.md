# DK-053: shipctl: замок конвейера, тесты из конфига, бескодовая задача поезда

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick, 2026-08-02.

Дизайн из `docs/lld/DK-048-batch-dispatcher.md` (разделы «Где кончается
параллельность» с подразделом про задачу без кода, «Команда тестов» и пункты
про shipctl в «Тестах») реализован четырьмя кусками: замок `.devkit/ship.lock`
(новый `shipctl/lock.go`) на `merge`, `ship`, `revert` и `start`; ключ `test` в
`.devkit/deploy.local` с `resolveTest` рядом с `resolveDeploy`; три исхода
`merge --train` по слитому диапазону через `rangeDocsOnly` поверх общего
предиката `docsOnly`; подсказка `scenarioWarning` про отсутствующий раздел
«Сценарий проверки», которая читает файл задачи в дереве ветки.

Отступления от дизайна записаны в самом LLD абзацем «Отличия реализации
(DK-053)»: третий исход поездного слияния оказался не только про пропавший ID
в subject (коммиты задачи находятся ещё и по записи раздела «Выкат»), поэтому
предупреждение называет обе связи; бескодовое поездное слияние тег `deployed`
не заводит; пустой слитый диапазон бескодовым не считается.

По замечанию ревью подсказка про сценарий развилена по ветке: обещать будущий
`ship` на бескодовой задаче было нельзя, её переводит в Check сам merge и тем же
прогоном. Признак берётся тем же `rangeDocsOnly`, только до ребейза, по
диапазону `main..branch`.

Мутации, на которых обязан краснеть хоть один тест, прогнаны скриптом (16
штук): снятый flock, замок без проверки `.devkit`, замок, который не
отпускается, конфиг сильнее явного `--test`, пустой ключ `test` как команда,
пропавшая строка отчёта про источник тестов, `revert`, подхвативший ключ
`test`, `rangeDocsOnly` с константным true и false, пустой диапазон как
бескодовый, тег на бескодовом слиянии, бескодовая задача без перевода в Check,
молчание про пропажу из поезда, снятая подсказка про сценарий, сценарий по
упоминанию в прозе вместо заголовка, чтение сценария не в дереве ветки. Каждая
поймана хотя бы одним тестом.
- Ревью: субагент sonnet/high по вердикту pick, 2026-08-02.

## Сценарий проверки

Агентский: все шаги выполнимы с машины агента, каждый итог проверяется
объективно (код возврата, конкретная строка вывода), на проде ничего не
меняется (весь сценарий во временной директории с временным `HOME` и
синтетическим репозиторием). Обкатан вживую при исполнении задачи.

```sh
BASE=/tmp/dk053-check
BIN=$BASE/bin
WORK=$BASE/repo
export HOME=$BASE/home
export DEVKIT_NOTIFY_OFF=1
export PATH=$BIN:$PATH
rm -rf "$BASE"; mkdir -p "$BIN" "$HOME" "$WORK"
(cd ~/projects/devkit/shipctl && go build -o "$BIN/shipctl" .)
(cd ~/projects/devkit/taskctl && go build -o "$BIN/taskctl" .)

cd "$WORK"
git init -q -b main && git config user.email t@t && git config user.name t
taskctl init --prefix XR --name "Проверка DK-053"
taskctl add --title "Правка кода" --type task --rank "0+1+1+0+1"
taskctl add --title "Правка доки" --type task --rank "0+1+1+0+1"
taskctl add --title "Задача без сценария" --type task --rank "0+1+1+0+1"
mkdir -p .devkit
printf '.devkit/\n' > .gitignore
printf 'test = touch %s/tested.marker\n' "$BASE" > .devkit/deploy.local
printf 'old\n' > code.txt
git add -A && git commit -qm seed
shipctl start XR-001
cd "$BASE/repo-xr-001" && printf 'new\n' > code.txt && git add -A &&
  git commit -qm "fix: XR-001 правка"
cd "$WORK"

# 1) занятый замок: merge отказывает, main не двигается
python3 -c "import fcntl,sys,time;f=open('$WORK/.devkit/ship.lock','w');fcntl.flock(f,fcntl.LOCK_EX);sys.stderr.write('held\n');sys.stderr.flush();time.sleep(30)" 2>"$BASE/held" &
LOCKPID=$!
until grep -q held "$BASE/held"; do sleep 0.2; done
HEAD1=$(git rev-parse main)
shipctl merge XR-001; echo "exit=$?"
[ "$(git rev-parse main)" = "$HEAD1" ] && echo "main не сдвинулся"
kill $LOCKPID

# 2) команда тестов из конфига: merge без --test проходит и гоняет её
shipctl merge XR-001 | grep -E "тесты гнались|в Check"; echo "exit=$?"
ls "$BASE/tested.marker"
taskctl close XR-001 -m "docs(tasks): XR-001 закрыта"

# 3) бескодовая задача поезда уезжает в Check без выката
shipctl start XR-002
cd "$BASE/repo-xr-002" && mkdir -p docs/lld && printf '# LLD\n' > docs/lld/x.md &&
  git add -A && git commit -qm "docs: XR-002 правка LLD"
cd "$WORK"
shipctl merge XR-002 --train | grep -E "поезд задачу не везёт|в Check, коммит"; echo "exit=$?"
taskctl show XR-002 | head -1
taskctl close XR-002 -m "docs(tasks): XR-002 закрыта"

# 4) подсказка про отсутствующий сценарий проверки
shipctl start XR-003
cd "$BASE/repo-xr-003" && printf 'ещё\n' > code.txt && git add -A &&
  git commit -qm "fix: XR-003 правка"
cd "$WORK"
shipctl merge XR-003 --train | grep -E "Сценарий проверки|в поезде:"; echo "exit=$?"
```

Ожидаемый итог по шагам:

1. `merge` при занятом замке падает с `exit=1` и строкой «конвейер занят: замок
   .devkit/ship.lock держит другой запуск shipctl ..., ничего не сделано»;
   `main` остаётся на прежнем коммите (печатается «main не сдвинулся»).
2. `merge` без `--test` проходит (`exit=0`), в отчёте есть строка «тесты
   гнались командой из .devkit/deploy.local: touch /tmp/dk053-check/tested.marker»
   и перевод в Check, а `ls` находит маркер: команда из конфига реально
   запускалась.
3. `merge XR-002 --train` печатает «поезд задачу не везёт: ветка не трогает
   ничего вне docs/, выката ей не нужно» и строку про коммит доски, `exit=0`,
   а `taskctl show` показывает задачу в `check`.
4. `merge XR-003 --train` печатает предупреждение «в docs/tasks/XR-003.md нет
   раздела «Сценарий проверки», а ship переведёт задачу в Check разом со всем
   поездом» и состав поезда, `exit=0`: подсказка слияние не валит.

Реальный прогон (2026-08-02, повторён после правки по замечанию ревью):

```text
=== шаг 1: занятый замок ===
ошибка: конвейер занят: замок .devkit/ship.lock держит другой запуск shipctl
(merge, ship, revert или start), ничего не сделано; дождаться его и повторить
exit=1
main не сдвинулся

=== шаг 2: команда тестов из конфига ===
тесты гнались командой из .devkit/deploy.local: touch /tmp/dk053-check/tested.marker
доска: XR-001 в Check, коммит 0fb2b4a
exit=0
/tmp/dk053-check/tested.marker

=== шаг 3: бескодовая задача поезда ===
поезд задачу не везёт: ветка не трогает ничего вне docs/, выката ей не нужно
доска: XR-002 в Check, коммит dd03ca1
exit=0
XR-002 в check

=== шаг 4: подсказка про сценарий проверки ===
предупреждение: в docs/tasks/XR-003.md нет раздела «Сценарий проверки», а ship
переведёт задачу в Check разом со всем поездом: проверять выкат будет нечем
(RULES.board.md, «Трекинг задач» п. 6)
в поезде: XR-003; выкат поезда: shipctl ship
exit=0
```

## Ревью

- scenarioWarning (shipctl/advice.go:113) при merge --train на бескодовой (docsOnly) ветке без раздела «Сценарий проверки» пишет «а ship переведёт задачу в Check разом со всем поездом», хотя именно этот merge (ops.go:666-681) уже сам переводит задачу в Check без выката: в одном и том же выводе рядом стоят взаимоисключающие строки «нет раздела... ship переведёт» и «доска: XR-003 в Check, коммит ...». Воспроизведено: merge --train на ветке с одним docs-коммитом и без docs/tasks/<ID>.md печатает оба предупреждения разом (проверено вживую). Комбинация docsOnly+нет сценария тестами не покрыта: TestTrainDocsOnlyGoesToCheck использует XR-001, у которого сценарий уже есть в setup().: исправлено, подсказка развилена по ветке: у бескодовой (docsOnly) говорит, что задачу переводит в Check сам merge и прямо сейчас, у остальных осталась про ship и поезд; признак считается до ребейза тем же rangeDocsOnly, дыру в тестах закрыл TestTrainDocsOnlyScenarioWarning, README поправлен
- Повторный проход: правка advice.go (74407f0) закрывает замечание 1 корректно. Живой прогон подтвердил: (1) обычный документированный сценарий (шаги 2-3, свежий временный репозиторий) даёт тот же текст, что раньше; (2) отдельный прогон с продвинутым main, требующим настоящего ребейза перед --train на docsOnly-ветке, показал, что пред-ребейзный признак (main..branch) сходится с фактом. Вывод сразу назвал «merge переведёт бескодовую задачу в Check прямо сейчас», и в том же прогоне задача действительно ушла в Check без ship. Расхождение невозможно, потому что при конфликте ребейз падает раньше, чем warn попадает в вывод (переменная warn собирается до rebase, но печатается только после успешного ff-only). Прогнал go vet и go test ./... по shipctl, taskctl, agentctl и regcheck, везде зелёно (в том числе TestTrainDocsOnlyScenarioWarning). check-symbols.py по изменённым файлам чисто. Своя мутация (убрать ветвление who и вернуть старый безусловный текст про ship) даёт красный TestTrainDocsOnlyScenarioWarning, как и заявлено. Прошёлся по остальным предупреждениям в advice.go (regcheckWarning, цена/размер поезда/пересечение файлов, deploy.warn) и по ops.go (нет ID в subject, не попала в поезд), других мест, где текст расходится с тем, что merge делает на самом деле, не нашёл. README и вложенный прогон в файле задачи актуальны содержанию.: отклонено, проход чистый, подтверждено живыми прогонами и своей мутацией
