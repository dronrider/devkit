# DK-056: Неопределённость в RANKING.md растёт от пересекаемых границ: правка через процессы и языки (сервер плюс клиент, JNI, UI) это минимум 3

Из того же разбора, что и [DK-055](archive/2026/DK-055.md): XR-216 в xr-proxy
стояла на доске с неопределённостью 1, а на деле путь от симптома до правки шёл
через сервер, JNI и экран приложения, и звено на границе не увидели ни тесты,
ни ревью, ни сценарий проверки. Оценку ставили по знакомости корня («ясно, где
чинить»), хотя незнание сидело не в корне, а в числе границ, через которые
правку надо протащить.

Шкала неопределённости в `RANKING.md` сейчас говорит только про разобранность
подхода (5 не разобрано, 3 есть развилки, 1 всё ясно, 0 рутина), и по ней
однопроцессная правка и правка через три границы получают одинаковую единицу.
Правка: добавить в раздел про неопределённость критерий пересекаемых границ.
Правка, живущая в одном процессе и одном языке, оценивается как раньше, а
пересечение границ (сервер плюс клиент, JNI, UI, отдельные релизные циклы)
поднимает оценку минимум до 3, потому что развилки там появляются не в подходе,
а в стыке, и видны только на живом прогоне.

Порог 3 держится и на другой конец правил: неопределённость 2 и выше не пускает
задачу в пачку выката (`taskctl batch`), а по `RULES.board.md` высокий ранг с
высокой неопределённостью зовёт сначала на грумминг. Ровно то поведение, которого
XR-216 не хватило.

Дока: `RANKING.md`, раздел «Неопределённость». Соседние тексты, если они
пересказывают шкалу, привести в соответствие; кода задача не трогает.

## Сценарий проверки (агентский)

Выкат задаче не нужен, проверка идёт в чекауте devkit. Синтетическая доска
заводится во временной директории, живую доску шаги не трогают.

1. Критерий на месте:

   ```sh
   grep -c "пересечение границ" ~/projects/devkit/RANKING.md
   ```

   Ожидание: `1`.

2. Символы по правилам:

   ```sh
   python3 ~/projects/devkit/hooks/check-symbols.py ~/projects/devkit/RANKING.md
   ```

   Ожидание: пустой вывод и код возврата 0.

3. Порог виден утилитам. Собрать `taskctl` и `agentctl`, завести пустую доску
   во временной директории и положить туда два бага одной цены, различающихся
   только неопределённостью (1 против 3, как в новом критерии):

   ```sh
   taskctl init --prefix T
   taskctl add --id T-001 --title "Кнопка не гасится после отправки" \
     --type bug --rank "25+0+1+5+0" --cost S
   taskctl add --id T-002 --title "Статус не доходит до экрана (сервер, JNI, UI)" \
     --type bug --rank "25+0+3+5+0" --cost S
   taskctl batch
   agentctl pick T-002
   ```

   Ожидание: `batch: T-001`, а T-002 в отказах строкой «неопределённость выше
   1: T-002 (3)»; у `pick T-002` строка `effort: high` (у T-001 на том же месте
   `medium`). Строки про ярус и корректор зависят от остатка лимитов и в
   ожидание не входят.

## Ревью

- Шаг 3 сценария проверки: ожидание "pick T-001 -> effort medium" не сходится с кодом. T-001 (cost S, unc 1) маппится в tier base, а floorBaseEffort в agentctl/pick.go безусловно поднимает low/medium до high на этом ярусе (проверено прогоном: agentctl pick T-001 -> tier: base, effort: high, хвост причины "effort поднят до high"). Значит на этой паре задач эффект нового порога неопределённости 3 через effort не виден вовсе: T-001 тоже даст high, но по другой причине (пол base-яруса), а не из-за низкой неопределённости. Сценарий не обкатан по факту, нужна другая пара (например, cost M для T-001, чтобы попасть в tier pro и получить настоящий medium) либо сравнение делать только по taskctl batch, а строку про pick effort убрать или поправить ожидание.
