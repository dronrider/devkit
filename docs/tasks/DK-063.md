# DK-063: громкие уведомления из taskctl и shipctl: Check, блокер, провал выката

После DK-062 уведомитель различает громкий повод и фоновый, но зовут его пока
только хуки харнеса. Поводы, ради которых человек и подходит к машине, из
харнеса не видны: задача доехала до Check и ждёт проверки, работа встала на
блокере, выкат упал. В автономном режиме (`autonomous = true` в
`.devkit/deploy.local`) агент сливает и катит сам, поэтому узнать про это можно
только заглянув в окно сессии или в доску, а сломанный выкат тем временем
стоит на проде.

## Что согласовано

Набор громких поводов зафиксирован в DK-062 (п. 2 раздела «Что согласовано с
пользователем») и в строке задачи:

1. Задача доехала до Check. Статус двигает `taskctl move`, а `shipctl merge` и
   `ship` зовут taskctl сами, значит повод один и живёт он там, где меняется
   статус.
2. Работа встала на блокере: `taskctl move <ID> blocked`.
3. Выкат провалился: команда выката вернула не ноль в `shipctl merge`, `ship`
   или в повторном выкате после `revert`. Прод в этот момент может быть сломан,
   и это самый громкий повод из трёх.

Все три повода громкие: `notify.py "заголовок" "текст"` без `--quiet`.

## Что остаётся решить исполнителю

- Как Go-утилита находит уведомитель. Бинарь лежит в `~/go/bin` и про свой клон
  devkit ничего не знает; похожий поиск уже написан в `agentctl/harness.go`
  (функция `harnessDir`: `DEVKIT_HOME`, корень проекта, соседний клон,
  `~/projects/devkit`). taskctl, shipctl и agentctl это отдельные go-модули,
  общего пакета у них нет, и заводить его ради одной функции вряд ли стоит.
- Что делать, когда уведомителя нет или он упал. Утилита из-за уведомления
  падать не должна, но и молчать про непосланное уведомление нельзя.
- Как сделать, чтобы прогон тестов не слал баннеров. У уведомителя для этого
  есть `DEVKIT_NOTIFY_OFF=1`, но тест должен проверять именно факт вызова.
- Наблюдаемость: по чему видно, что повод ушёл.

## Решение

Реализация без отступлений от постановки, три пункта «что остаётся решить»
закрыты так:

1. Поиск уведомителя. `notifyScript(root)` заведена дважды, в
   `taskctl/notify.go` и `shipctl/notify.go` (общего пакета у go-модулей нет,
   как и предполагалось), порядок кандидатов как у `harnessDir`:
   `DEVKIT_HOME`, `hooks/` рядом с самой доской (случай, когда доска и есть
   devkit), соседний клон `../devkit`, `~/projects/devkit`. Первый
   существующий файл побеждает.
2. Отказоустойчивость. `notify(root, title, body)` зовёт `python3
   <notify.py> title body` и никогда не возвращает error: не нашёлся сценарий
   или сама команда упала, возвращается непустая строка-приписка
   «уведомление не отправлено: ...», которая приклеивается к обычному
   сообщению команды (`taskctl move`) или к тексту уже случившейся ошибки
   выката (`shipctl merge`/`ship`/`revert`). Move и merge не падают
   дополнительно, но и не молчат.
3. Тишина в тестах. У обоих пакетов `TestMain` держит `DEVKIT_NOTIFY_OFF=1`
   по умолчанию: без стаба поиск уходит в `~/projects/devkit/hooks/notify.py`
   (он и правда лежит на машине разработчика), и без этой заглушки прогон
   `go test` слал бы настоящие баннеры. Тесты самого уведомления включают
   отправку точечно (`t.Setenv("DEVKIT_NOTIFY_OFF", "")`) и подсовывают
   поддельный `hooks/notify.py`, который вместо реальной отправки пишет свои
   аргументы в файл: так проверяется факт вызова и его содержимое, а не
   баннер.
4. Наблюдаемость. Баннер и строка в `~/.devkit/notify.log` уже даёт
   `notify.py` сам (DK-062); поверх этого `taskctl move` и провалившиеся
   `shipctl merge`/`ship`/`revert` показывают исход отправки прямо в своём
   выводе, включая случай, когда отправить не удалось вовсе.

Три повода реализованы ровно там, где согласовано: Check и Blocked в
`cmdMove` (`taskctl/ops.go`, между `b2.Save()` и коммитом строки), провал
выката в трёх точках `shipctl/ops.go` (`cmdMerge`, `cmdShip`, `cmdRevert`),
где команда выката уже вернула ошибку. `shipctl merge`/`ship` двигают статус
через реальный бинарь `taskctl` в PATH, поэтому отдельно дублировать
Check-уведомление в shipctl не потребовалось.

## Что затрагивается

- `taskctl` (перевод статуса), `shipctl` (выкат), тесты обоих.
- Доки: `hooks/README.md` (раздел про громкие поводы сейчас говорит про вызов
  снаружи в общем виде), `taskctl/README.md`, `shipctl/README.md`.

## Сценарий проверки

Агентский целиком: каждый шаг выполним с машины агента, итог проверяется по
выводу и по журналу `~/.devkit/notify.log`, а прод не трогается (сборка идёт
во временный `bin`, доски и репозитории тоже временные).

1. Юниты: `cd taskctl && go test ./...` и `cd shipctl && go test ./...`
   кодом 0, `sh hooks/test.sh` печатает «хуки в порядке», `python3
   hooks/notify_test.py` кодом 0.

2. Живой прогон собранных бинарей со стаб-бэкендом `terminal-notifier`
   (как в сценарии DK-062) и настоящим `hooks/notify.py` из рабочего дерева
   задачи (через `DEVKIT_HOME`):

```sh
DEVKIT=<путь к рабочему дереву задачи>
SCRATCH=$(mktemp -d); BIN="$SCRATCH/bin"; mkdir -p "$BIN"
(cd "$DEVKIT/taskctl" && go build -o "$BIN/taskctl" .)
(cd "$DEVKIT/shipctl" && go build -o "$BIN/shipctl" .)
export PATH="$BIN:$PATH"
H="$SCRATCH/home"; D="$SCRATCH/backend"; mkdir -p "$H" "$D"
printf '#!/bin/sh\nprintf "%%s\\n" "$*" >> %s/args\n' "$D" > "$D/terminal-notifier"
chmod +x "$D/terminal-notifier"
export HOME="$H" DEVKIT_HOME="$DEVKIT" DEVKIT_NOTIFY_BACKEND="$D/terminal-notifier"

# 2a. move -> check
PROJ="$SCRATCH/proj"; mkdir -p "$PROJ"
(cd "$PROJ" && git init -q -b main && git config user.email t@t && git config user.name t)
(cd "$PROJ" && taskctl init --prefix XR --name проба >/dev/null)
(cd "$PROJ" && taskctl add --title "Проверка" --type task --rank "0+3+0+0+0" --status in-progress >/dev/null)
ID=$(cd "$PROJ" && taskctl list in-progress | grep -o 'XR-[0-9]*' | head -1)
(cd "$PROJ" && taskctl move "$ID" check)
cat "$D/args"

# 2b. move -> blocked
: > "$D/args"
(cd "$PROJ" && taskctl add --title "Вторая" --type task --rank "0+3+0+0+0" --status in-progress >/dev/null)
ID2=$(cd "$PROJ" && taskctl list in-progress | grep -o 'XR-[0-9]*' | grep -v "$ID" | head -1)
(cd "$PROJ" && taskctl move "$ID2" blocked --reason "ждём стенд")
cat "$D/args"

# 2c. shipctl merge с упавшим выкатом
: > "$D/args"
SHIP="$SCRATCH/ship"; mkdir -p "$SHIP"
(cd "$SHIP" && git init -q -b main && git config user.email t@t && git config user.name t)
(cd "$SHIP" && taskctl init --prefix XR --name выкат >/dev/null)
(cd "$SHIP" && taskctl add --title "Под выкат" --type task --rank "0+3+0+0+0" --status in-progress >/dev/null)
SID=$(cd "$SHIP" && taskctl list in-progress | grep -o 'XR-[0-9]*' | head -1)
echo код > "$SHIP/code.txt"; (cd "$SHIP" && git add -A && git commit -qm seed)
(cd "$SHIP" && git checkout -qb xr-001-fix)
echo правка > "$SHIP/code.txt"; (cd "$SHIP" && git add -A && git commit -qm "fix: $SID правка")
(cd "$SHIP" && shipctl merge "$SID" --test true --deploy 'echo прод сломан >&2; false')
cat "$D/args"

rm -rf "$SCRATCH"
```

   Ожидается: 2a даёт баннер с заголовком `<репо>: <ID> в Check` и телом
   заголовка задачи; 2b даёт `<репо>: <ID> на блокере` с причиной блокировки
   в теле; 2c даёт код возврата 1 у `shipctl merge`, ошибку «выкат упал» и
   баннер `<репо>: выкат <ID> упал` с первой строкой вывода упавшей команды в
   теле; журнал `~/.devkit/notify.log` получает по строке на каждый баннер.

3. Непосланное уведомление не молчит и не роняет move: подставить пустой
   `HOME` и снять `DEVKIT_HOME`, повторить `taskctl move ... check`. Ожидается
   код возврата 0 и строка «уведомление не отправлено: hooks/notify.py не
   нашёлся, искал: ...» в выводе.

## Ревью

- Сценарий проверки, шаг 2c: git checkout -qb fix заводит ветку без ID-префикса, shipctl merge XR-001 падает на проверке имени ветки ("стоишь на fix, а сливается XR-001") раньше, чем доходит до провала выката, и уведомление не проверяется; воспроизвёл дословно по скрипту из задачи.: исправлено, ветка теперь xr-001-fix (с ID-префиксом), шаг доходит до провала выката
- Записанный «Прогон агентской части» для шага 2c не соответствует документированному скрипту: там показан успешный вывод с провалом выката и строка «код возврата merge: 1», которой в скрипте нет и которая не появилась бы при реальном прогоне (branch fix даёт другую ошибку раньше), то есть транскрипт снят не с того скрипта, что в «Сценарий проверки».: исправлено, прогон переснят целиком с текущего скрипта, дословно
