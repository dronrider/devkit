# DK-064: конец хода зовёт по фокусу окна, а не по длительности

Уведомление о конце хода не приходит там, где оно и нужно. Пользователь завёл
новый чат, задал вопрос не по задаче, отошёл, и баннера не дождался. В журнале
видно, что хук отработал и сам себя погасил:

```
12:53:07 сессия c8b6f4e4 повод turn_done уровень громкий бэкенд - цель - пропуск: ход короче 60с
```

Порог длительности хода из DK-062 стоит на догадке: раз ответ занял меньше
минуты, человек эти секунды смотрит в то же окно. Догадка неверная.
Длительность хода про то, сколько работала машина, а звать или молчать зависит
от того, где в это время человек, и одно из другого не выводится. Короткий
вопрос перед тем, как отойти, это ровно тот случай, где догадка промахивается,
и он не редкий.

## Что даёт машина

`System Events` отвечает и на «какое приложение сейчас впереди», и на «как
зовётся его переднее окно»:

```
$ osascript -e 'tell application "System Events" to get name of first application process whose frontmost is true'
Code
$ osascript -e 'tell application "System Events" to tell (first application process whose frontmost is true) to get name of front window'
Investigate task priorit... - devkit
```

В заголовке окна VS Code стоит имя рабочего дерева, а дерево сессии уведомитель
уже знает: он собирает по нему цель перехода по клику. Значит «смотришь ли ты
сейчас на эту сессию» это не догадка, а факт. Вызов стоит около 180 мс, для
конца хода терпимо.

## Решение

1. Порог длительности хода уходит вместе с меткой на `UserPromptSubmit` и
   переменной `DEVKIT_NOTIFY_TURN_MIN`, вместо него решает фокус: окно сессии
   впереди значит молчим, всё остальное значит зовём, хоть через три секунды.
   Хук на `UserPromptSubmit` остаётся, он снимает отметку ожидания (DK-062), но
   метку начала хода больше не кладёт.
2. Правило применяется только к концу хода. Запрос разрешения и вопрос агента
   зовут всегда: они редкие, сессия на них стоит намертво, а повторного события
   от харнеса может и не быть. Фоновых поводов проверка фокуса не касается
   вовсе, лишние 180 мс на каждого субагента ни к чему.
3. Сессия узнаётся по рабочему дереву в заголовке окна. Совпадением считается
   заголовок, который кончается именем дерева сессии (у VS Code это хвост после
   разделителя), иначе окно чужое. Несколько чатов в одном окне редактора друг
   от друга не отличить, и это осознанная грубость: сессии в одном дереве
   считаются одной, зато промах уходит в сторону лишнего баннера, а не тишины.
4. Фокус не определился (не macOS, нет разрешения на управление компьютером,
   `osascript` ответил ошибкой или пусто) значит зовём. Тишина здесь хуже
   лишнего баннера: она неотличима от штатной работы, а разрешение выдают не на
   всякой машине. Отказ пишется в журнал, чтобы «звонит всегда» разбиралось по
   строке.
5. Определение фокуса живёт отдельной функцией с подменяемым способом опроса:
   тесты гоняются без живого `System Events`, а на не-macOS оно просто не
   заводится. Переменной (`DEVKIT_NOTIFY_FOCUS=off`) проверка выключается
   целиком, тогда конец хода зовёт всегда.
6. В журнал пишется, почему промолчали: «пропуск: окно сессии в фокусе». Строки
   про короткий ход исчезают вместе с порогом.

## Что затрагивается

- `hooks/notify.py`, тесты `hooks/notify_test.py`, сквозные шаги `hooks/test.sh`
  (там есть блоки про порог длительности, они переписываются под фокус).
- `hooks/README.md`: раздел «Уведомления о сессии» описывает порог и метку
  начала хода, обе уходят.
- Файл задачи DK-062 в архиве не переписывается, история решения остаётся как
  была; на смену правила ссылается эта задача.

## Сценарий проверки

Пишется исполнителем. Агентская часть держится на подменяемом опросе фокуса
(окно сессии впереди, чужое окно впереди, опрос не отвечает) плюс журнал;
живьём глазами остаётся то, что подменой не проверить: заданный из другого окна
вопрос звонит сразу, а тот же вопрос при взгляде в это же окно молчит.
