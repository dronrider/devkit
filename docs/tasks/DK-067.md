# DK-067: taskctl list: чего ждёт задача в Check и сколько строка лежит без движения

Секция Check держит вещи с разной операционкой, и по строке их не различить.
Задача с выкаченным кодом держит очередь: пока её не проверили, следующий выкат
не пойдёт. Задача без выката (LLD, дока, разбор) очередь не держит и ждёт
подтверждения сколько угодно. Проверку одной закрывает агент своим сценарием,
другой ждёт живого человека. Обе оси существуют, но живут в git и в файле
задачи, а `taskctl list` печатает ровный список строк, из которого не видно,
чего именно ждут от владельца прямо сейчас.

Вторая часть про возраст. Ни доска, ни `list` не говорят, сколько строка лежит
без движения. Дата есть только в git, и заметить залежавшееся можно, лишь
специально сходив в историю: в соседнем проекте медиана жизни в Backlog сутки,
а IRC-6 и IRC-10 лежат там с 7 июля, почти месяц. Ровно так же не видно
задачи, которая застряла в In progress или ждёт в Check дольше обычного.

Что сделать. `taskctl list` помечает строки Check двумя признаками (держит
очередь или нет, агентский сценарий или пользовательский) и показывает возраст
строки. Новых колонок в самой доске не заводить: это выводимые данные, им место
в выводе команды, а не в таблице, которую правят руками.

Открытые развилки:

- откуда брать признак «держит очередь». Логика уже есть в `shipctl`
  (`checkQueue`), и дублировать её в taskctl не хочется; либо признак приходит от
  shipctl, либо после DK-065 обе утилиты читают одну запись в файле задачи;
- откуда брать агентский признак. Пометка живёт прозой в файле задачи, и её
  надо либо формализовать, либо искать по заголовку раздела «Сценарий проверки
  (агентский)», как он пишется сегодня;
- чем мерить возраст. `git blame` по строке доски даёт дату последней правки
  строки, а не дату перевода в текущий статус: правка ранга обнулит счётчик.
  Дата перевода честнее, но её надо где-то держать.

Развилки закрываю так, менять по слову пользователя.

- «Держит очередь» taskctl считает сам, без git и без разговора с shipctl: после
  DK-065 у задачи со слитым кодом есть раздел «Выкат» в файле задачи, и для
  строки в Check этого довольно. Пометка честно называется тем, что она есть
  («код слит»), а не выдаёт себя за полноценный ответ shipctl про тег выката:
  точный ответ по-прежнему за `shipctl status`, и пометка на него ссылается.
- Агентский признак берётся по заголовку `## Сценарий проверки (агентский)` в
  файле задачи, так он уже пишется у девяти закрытых задач. Отдельного поля не
  заводить: формализация ради формализации, а заголовок и так под ревью.
- Возраст мерить по `git log -1` строки доски (последняя правка строки), и
  подписать его именно так: «строка не двигалась N дней». Дата перевода в
  статус честнее, но ради неё пришлось бы держать в доске ещё одно поле, а
  правка ранга у взятой в работу задачи случается редко.

## Что сделано

- `list` и `show` печатают пометки отдельной строкой под строкой доски. Новых
  колонок в самой доске нет: это выводимые данные, и в `TASKS.md` они не
  попадают.
- У строки в Check две оси, ради которых секцию и держат. Держит ли задача
  очередь выката, видно по разделу «Выкат» в файле задачи (его пишет
  `shipctl merge`, DK-065): есть раздел значит «код слит», нет значит «без
  выката», как у LLD или разбора. Кто проверяет, видно по заголовку
  `## Сценарий проверки (агентский)`: «сценарий агентский» против «сценарий
  пользовательский». Оба значения печатаются всегда, даже когда оба «нет»:
  это и есть ответ на вопрос, чего ждут от владельца прямо сейчас.
- Пометка честно говорит «код слит», а не «держит очередь»: точный ответ про
  тег выката остаётся за `shipctl status`, а taskctl в git не ходит и одну
  логику в двух утилитах не держит.
- Возраст строки идёт под любой строкой доски: «строка не двигалась N дней» по
  дате последнего коммита, тронувшего именно эту строку (один
  `git blame --incremental` на весь файл доски). Это не
  дата перевода в статус, и оговорено вслух: правка ранга или переезд между
  секциями счётчик обнуляют.
- Возраст молчит там, где соврал бы: на незакоммиченной доске (номера строк
  рабочей копии и HEAD разъедутся, и возраст достанется чужой строке), вне
  git-репозитория и на строке, ещё не попавшей в коммит. Пометки Check при этом
  остаются: они читаются из файла задачи, а не из git.
- Файла задачи может не быть вовсе (в Check пускают и со ссылкой на сценарий),
  тогда пометок Check нет, а строка печатается как раньше.
- Тесты: `age_test.go` (склонение дней, разбор обеих осей по файлу задачи,
  возраст по подменяемым часам, молчание на грязном дереве и вне git) и
  `view_test.go` (пометки в `list` и `show`, их отсутствие на грязной доске).
  Мутации прогнаны по одной: непрочитанный раздел «Выкат», непрочитанный
  заголовок агентского сценария, возраст, посчитанный на грязном дереве, и
  снятые пометки в `list` красят каждая свой тест.
- По замечаниям ревью закрыты две дыры. Разбор файла задачи пропускает
  ограждённые блоки: заголовок в чужом выводе, вложенном по правилу в файл
  задачи, печатал «код слит» задаче без выката (тот же класс, что DK-070 в
  shipctl и DK-076 в остальных читателях), тест `TestCheckMarksIgnoresFenced`.
  Возраст берётся одним `git blame --incremental` на файл вместо вызова git на
  каждую строку: на живой доске devkit `list backlog` подешевел с 2.9с до
  0.15с, а `git log -L` построчно был тут главной ценой.

## Сценарий проверки (агентский)

Живой проект и живая доска не трогаются, стенд синтетический, со своим `HOME`
и `PATH`.

```sh
sh docs/tasks/DK-067-check.sh
```

Скрипт лежит рядом с файлом задачи и печатает «шаг N: ok» по каждому шагу, а в
конце «СЦЕНАРИЙ ПРОШЁЛ»; провал любого шага это ненулевой код возврата. Шаги:

1. `list check` показывает обе оси разом: у задачи, прошедшей полный цикл
   shipctl, «код слит, сценарий пользовательский», у доковой задачи без выката
   «без выката, сценарий агентский»;
2. у нетронутой строки виден возраст в четыре знака (стенд датирован 2016
   годом), у только что переехавших строк честные «0 дней»;
3. `show` печатает то же самое для одной задачи;
4. незакоммиченная доска гасит возраст, но не пометки очереди и сценария;
5. `taskctl lint` на стенде после всех переходов зелёный.

До выката обкатан на бинаре ветки: пять шагов ok, код возврата 0.

- checkMarks (taskctl/age.go) читает файл задачи построчным HasPrefix без учёта ограждённых блоков: заголовок «## Выкат» или «## Сценарий проверки (агентский)», процитированный внутри тройных кавычек (обычное дело для агентского вывода по RULES.board.md п.6), читается как настоящий раздел. Проверил живым тестом: файл задачи без раздела «Выкат» и с «## Сценарий проверки» (без агентский), но с процитированным в блоке  ## Выкат  дает list check -> «код слит, сценарий пользовательский» вместо «без выката, сценарий пользовательский». Это ровно класс бага DK-070, для которого shipctl уже чинили через fenceMask/sectionLines (shipctl/taskdoc.go, shipctl/record.go), а taskctl/review.go и agentctl/pick.go с тем же классом бага вынесены отдельной строкой DK-076 на доску; новый читатель checkMarks эту доработку не получил и в DK-076 не упомянут. Нужно либо разбирать файл с учётом ограждений (как shipctl), либо явно расширить/дополнить DK-076 и покрыть тестом на процитированный заголовок.: исправлено, разбор пропускает ограждённые блоки, тест на цитату
- list/show зовут git log -L отдельным процессом на каждую печатаемую строку доски (ageLabel в rowNotes), а на Check дополнительно ещё и файловое чтение checkMarks: команда без кэша и без единого batch-вызова git. Замерил на реальной доске devkit: taskctl list (лимит 10 в Backlog) с новым бинарём около 0.7-0.8с против 0.004с у старого, taskctl list backlog целиком (38 строк) около 2.9с.
