# DK-070: mergedShas читает файл задачи построчно и не знает про ограждённые блоки: процитированный раздел «Выкат» становится настоящей записью

Вылезло сразу на DK-065, при первом же прогоне её сценария после выката. В файл
задачи вкладывается реальный вывод (RULES.board.md, «Трекинг задач» п. 6), а в
выводе стоял заголовок `## Выкат` и строка записи из синтетического
репозитория. `mergedShas` (`shipctl/record.go`) идёт по строкам файла и про
ограждённые блоки не знает, поэтому процитированное принял бы за свою запись:
пришлось сдвигать вывод на два пробела и оговаривать это прозой.

Сам по себе чужой sha безвреден, он просто не найдётся в логе. Опасен обратный
случай: файл задачи цитирует чужую запись (разбор соседней задачи, кусок
истории), sha из неё в логе есть, и очередь выката посчитает выкаченной не ту
задачу. Того же поля `openReviewNotes` в `shipctl/board.go`: он тоже ищет
`## Ревью` построчно, и процитированное замечание без исхода отобьёт слияние.

Что сделать: разбирая файл задачи, пропускать содержимое ограждённых блоков
(``` и ~~~), общим хелпером для обоих читателей. Тест на файл, где раздел
процитирован внутри блока.

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick (маппинг sonnet, корректор: профицит week_all), 2026-08-02.
- Общий хелпер лёг в `shipctl/taskdoc.go`: `fenceMask` помечает строки внутри
  ограждённого блока вместе с самими ограждениями, `sectionLines` отдаёт
  строки раздела мимо блоков. Через него пошли `mergedShas` и
  `openReviewNotes`, а `appendToSection` ищет по маске начало и конец своего
  раздела: иначе строка записи уехала бы внутрь процитированного вывода.
- Тот же построчный разбор живёт в `taskctl/review.go` (`loadReview`) и в
  `agentctl/pick.go` (`recordExecution`). Там он опаснее, чем читатели
  shipctl: `review resolve N` перепишет строку внутри блока, а запись
  исполнителя встанет в процитированный «Ход работы». Хелпер лежит в модуле
  shipctl, на два соседних модуля его так просто не растянуть, поэтому эта
  часть уехала отдельной задачей DK-076.
- Регрессия закрыта regcheck на тестах `shipctl/record_test.go`:

  ```
  regcheck --base main -- go test -C shipctl ./ -run 'TestMergedShasSkipsFenced|TestAppendToSectionSkipsFenced|TestMergeIgnoresFencedReviewNote'
  тест краснеет на main и проходит на текущем коде, регрессия закрыта (тесты: shipctl/record_test.go)
  ```
- Ревью: субагент sonnet/high по вердикту pick, 2026-08-02.
- Второй круг по замечанию ревью: тем же хелпером пошёл третий читатель
  модуля, `scenarioWarning` в `shipctl/advice.go` (`hasHeading` в
  `shipctl/taskdoc.go`, заголовок любого уровня вне блоков). Тест
  `TestScenarioWarningSkipsFenced` до правки краснел прямо на ветке.
  Повторный проход по модулю четвёртого читателя файла задачи не нашёл:
  остальные построчные разборы shipctl читают доску (`loadBoard`) и журнал
  `.devkit/log` (`regcheckLogged`), ограждённых блоков там не бывает.
- Третий круг, обратная сторона разбора. `fenceMask` вторым значением отдаёт
  строку незакрытого ограждения, и обрыв файла задачи виден вслух: `status`
  называет такой файл строкой по каждой задаче доски, а `merge` по ней
  отказывает до ребейза. Отказ, а не одна подсказка, потому что предупреждение
  печатается уже после того, как merge слил ветку, дописал запись «Выкат» в
  оборванный хвост и перевёл задачу в Check: сказать про потерю после потери
  это не «видно снаружи», а извещение о случившемся. На отказе не сделано
  ничего, и чинится он закрытием ограждения. Угадывать намерение автора
  (считать незакрытый блок закрытым) не стал: тогда цитата с одним ограждением
  снова начнёт читаться как запись, то есть вернётся исходный баг.
- Четвёртый круг. Обрыв заводится там, где файл задачи и пишется, в дереве
  задачи, а основной чекаут стоит на main и этих правок не видит. `merge` читал
  файл правильно (`reviewRoot`), но покрытия на это не было, а `status` смотрел
  только в основной чекаут и в типовом случае In progress молчал. Теперь
  `status` берёт дерево задачи по её ветке (`branchOfTask` по списку worktree) и
  называет это дерево в строке, а `TestUnterminatedFenceInWorktree` держит обе
  стороны: подмена `reviewRoot` на `root` в merge и потеря дерева в status
  роняют его порознь.

- hasHeading (shipctl/taskdoc.go): мутация 'уровень заголовка любой -> только «## »' не ловится ни одним тестом пакета (прогнал весь go test ./... с этой мутацией: зелёный). TestScenarioWarningSkipsFenced проверяет только уровень 2, заявленное 'заголовок любого уровня' не покрыто: исправлено, добран TestScenarioWarningHeadingLevel на уровни 1 и 3; мутацию '#' -> '## ' в hasHeading прогнал, тест краснеет
- обратная сторона: необрубленный ограждённый блок где угодно раньше по файлу (частый обрыв вставленного вывода) проглатывает весь остаток файла по спецификации markdown, а с ним и настоящие непроцитированные разделы «Выкат»/«Ревью»/«Сценарий проверки» для всех четырёх читателей разом (mergedShas и hasHeading проверил живыми тестами).
