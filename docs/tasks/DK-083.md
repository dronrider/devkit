# DK-083: Адаптер jira: REST-операции и образцы ответов API

Последняя задача серии корп-контура по принятому LLD
[DK-074](../lld/DK-074-corp-contour.md), раздел «Адаптер по имени» (строки
181-209). Идёт после закрытой DK-082: контракт адаптера, таблица по имени,
конфиг контура и маппинг статусов уже на проде, в сборке нет ни одного живого
адаптера, и `trackctl status` честно об этом говорит. Здесь появляется первый.

## Что делать

Адаптер jira в `trackctl/`, регистрируется в таблице `adapters` по имени
`jira`, реализует обязательную часть контракта (`fetch`, `transition`,
`assign`, `estimate`, `worklog`) и обе необязательные операции (`rank`,
`comment`): у Jira они есть, а честное отсутствие оси проверено на подложном
адаптере ещё в DK-082.

1. REST поверх stdlib, как соседи. Адрес берётся из `base_url` контура, токен
   из переменной окружения или файла по ключам `token_env` и `token_file`, сам
   токен в конфиге не лежит и в код не попадает.
2. `transition` работает через список доступных переходов: прямого перехода в
   целевой статус нет, значит отказ перечисляет доступные, а не ищет путь через
   промежуточные. Поля секции `[fields_*]` уезжают в тело перехода как есть.
3. `rank` пишет числовое поле приоритета, имя поля называет контур
   (`rank_field`), в код никакие `customfield_*` не прошиваются: у каждой
   компании они свои, и это чувствительное.
4. Отказы трекера остаются честными: код ответа и текст ошибки Jira видны
   пользователю, а не заменяются своим «что-то пошло не так».

## Образцы ответов API

Образцы кладутся в `trackctl/testdata/jira/`, тесты в сеть не ходят вовсе.
Собираются они из публичной документации Jira Cloud REST API v3, а не снимаются
с корпоративного инстанса: это решение пользователя по ходу цели. Живьём
проверить формат тем самым не выйдет, и это записывается прямо в
`trackctl/README.md`, чтобы первое расхождение с настоящим инстансом не
выглядело неожиданностью. Ничего своего в образцах быть не должно: ни адресов,
ни ключей проектов, ни имён, ни `customfield` реальной компании.

## Дока

- `trackctl/README.md`: адаптер jira в таблице, какие ключи контура он читает,
  откуда взяты образцы и чем это ограничивает доверие к ним.
- `RULES.local.md`, раздел про Jira: контур devkit умеет ходить в Jira сам.
  Файл гитигнорнут и живёт только в основном чекауте.

## Сценарий проверки

Агентский.

Юниты на разборе образцов из `trackctl/testdata/jira/`: `fetch` вынимает
статус, тип, заголовок и оценку; список переходов разбирается, а отсутствие
целевого даёт отказ с перечнем доступных; поля `[fields_*]` уезжают в тело
перехода; `worklog` и `estimate` собирают запрос из контракта; `rank` пишет в
поле из `rank_field`; отказ трекера доносит код и текст. Мутации, которые тесты
обязаны ловить: переход ушёл без полей секции, отказ проглочен и подменён своим
текстом, имя поля ранга захардкожено, токен уехал в тело запроса или в журнал,
адаптер полез в сеть из теста.

Проверка снаружи: `trackctl status` в подключённом корп-проекте называет
адаптер `jira` и больше не говорит, что адаптеров в сборке нет. В файл задачи
вкладывается реальный вывод.

## Что сделано

Адаптер лежит в `trackctl/jira.go` и регистрируется в таблице `adapters` по
имени `jira`. Обязательная часть контракта и обе необязательные операции на
месте, контракт при этом не менялся ни строчкой. Запросы собраны на stdlib,
токен читается контуром на каждом запросе и уезжает заголовком
`Authorization: Bearer`; при сборке адаптера токен не спрашивается намеренно,
иначе `trackctl status` на машине без токена не сказал бы про адаптер вовсе.

Отказ трекера доносится своим типом `jiraError`: код ответа, `errorMessages` и
`errors` по полям, а на пустое тело остаётся хотя бы код и путь. Переход ищется
по имени статуса, в который ведёт (`to.name`), и ненайденный даёт
`transitionRefused` с перечнем доступных. Поля секции `[fields_*]` уезжают в
тело перехода как есть, с одной оговоркой: значение, которое само по себе
валидный JSON, отправляется разобранным, иначе секцией нельзя было бы задать ни
`resolution`, ни `assignee`, у Jira это объекты.

Ограничение записано в `trackctl/README.md` открытым текстом: образцы собраны из
публичной документации Jira Cloud REST API v3, а не сняты с инстанса, поэтому
формат живьём не проверен. Там же названы два ожидаемых расхождения с Jira Data
Center (путь `/rest/api/2`, ключ `name` вместо `accountId` в assign).

## Проверка

Юниты в `trackctl/jira_test.go` разбирают образцы из `trackctl/testdata/jira/`,
разложенные на подставном сервере `httptest`. Мимо него адаптеру ходить нечем:
транспорт клиента в тестах рвёт запрос на любой чужой хост.

Мутации гонялись руками, каждая ловится:

| Мутация | Кто падает |
|---|---|
| переход ушёл без полей секции | `TestJiraTransitionCarriesSectionFields` |
| отказ проглочен и подменён своим текстом | `TestJiraErrorCarriesCodeAndText` |
| имя поля ранга захардкожено | `TestJiraRankFieldFromContour` |
| токен уехал в тело запроса | `TestJiraTokenStaysInHeader` |
| адаптер полез в сеть | все, транспорт рвёт чужой хост |
| переход берётся первый попавшийся | `TestJiraTransitionRefusedListsAvailable` |

Проверка снаружи. В корпоративный инстанс за ней не ходили (решение по ходу
цели), поэтому `status` гонялся на подставном контуре с адресом-плейсхолдером:
проверяется тут, что адаптер собрался, попал в таблицу и виден снаружи.

```text
привязка:	<корень>/.devkit/tracker.local
проект:	ABC, ветки {key}-{slug}
контур:	corp (<домашняя>/.devkit/tracker/corp.local)
адрес:	https://tracker.example, пользователь 5b10ac8d82e05b22cc7d4ef5
токен:	на месте
статусы:	расписаны все секции
адаптер:	jira
операции:	все на месте
sync:	не гонялся ни разу
```

Про адаптеров в сборке `status` больше не говорит: он называет `jira` и обе
необязательные операции считает на месте. Тот же случай на контуре без токена
проверен юнитом `TestJiraStatusWithoutToken`.

Общий тест-набор из `.devkit/deploy.local` прогнан целиком, код 0.
