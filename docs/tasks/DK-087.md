# DK-087: shipctl: ветка по ключу тикета, отказ слияния в корп-контуре

Задача серии корп-контура по принятому LLD
[DK-074](../lld/DK-074-corp-contour.md), раздел «Конвейер: что остаётся от
shipctl» (строки 411-435). Идёт после закрытых DK-081 и DK-082: признак контура
и привязка с шаблоном ветки уже на проде.

## Что делать

В корп-контуре слияние делает MR-флоу компании, и конвейер обязан честно
остановиться на этой границе, а не изображать её.

1. `start` остаётся точкой взятия в работу и делает то же самое с двумя
   поправками: имя ветки строится по шаблону `branch` из привязки
   `.devkit/tracker.local` (ключ тикета вместо локального ID), а после перевода
   строки в In progress зовётся `trackctl take <KEY>`, тем же порядком, каким
   `merge` зовёт `taskctl`. Привязку читает плоский разбор `key = value`,
   который у shipctl уже есть, парсер TOML сюда не тащить.
2. `trackctl` не в PATH или привязки нет, значит `start` проходит, но говорит
   об этом вслух: доска не должна вставать из-за трекера.
3. `merge`, `ship` и `revert` в корп-контуре отказывают честной строкой.
   Подсказка называет ручные шаги: `trackctl submit`, пуш ветки, MR, дальше по
   процессу контура. Команду «подготовь MR» дизайн строить отказывается: пуш в
   корп-origin и создание MR это ровно та граница, где по `RULES.md`
   останавливается агент и начинается пользователь.
4. Локальная часть предусловий merge при этом не пропадает: проверку
   «замечания ревью закрыты, тесты зелёные» берёт на себя локальное ревью по
   обычным правилам доски, оно от контура не зависит.
5. Очередь выката в корп-контуре не считается, и `status` говорит почему, а не
   молчит. Check здесь означает «мяч на чужой стороне»: MR открыт, тикет в
   ревью или тестировании, и двигает строку туда pull синхронизации (DK-084), а
   не выкат, которого нет.
6. Починить найденное DK-081: `status` спрашивает git по корню, а корень в
   корп-контуре это боковая директория со своим репозиторием, поэтому он
   называет веткой ветку доски и падает на `git rev-parse HEAD`, пока в боковой
   директории нет ни одного коммита. Рабочую ветку надо спрашивать у клона.

## Дока

- `shipctl/README.md`: `start` в корп-контуре строит ветку по шаблону тикета и
  зовёт `trackctl take`; `merge`, `ship`, `revert` отказывают с подсказкой про
  MR-флоу; очередь выката в корп-контуре не считается.
- `RULES.board.md`: шапка сегодня отсекает корп-контур целиком («в
  корпоративном контуре файл не применяется»), и это противоречит дизайну, где
  доска, локальное ревью и worktree живут. Формулировка меняется на то, что в
  корп-контуре файл применяется, кроме раздела про слияние и выкат: их делает
  MR-флоу компании, а `merge`, `ship`, `revert` и поезд не работают. Тем же
  абзацем называется, где лежит доска (боковая директория) и что ID задачи в
  subject корп-коммита заменяет ключ тикета. Больше нескольких фраз не нужно,
  раздел резидентный.

## Сценарий проверки

Агентский.

Юниты: ветка строится по шаблону привязки с ключом тикета; `start` зовёт
`trackctl take`; отсутствие `trackctl` или привязки не валит `start`, но видно
в выводе; `merge`, `ship` и `revert` в корп-контуре отказывают и называют
ручные шаги; `status` не считает очередь выката и говорит почему; `status`
берёт рабочую ветку у клона, а не у боковой директории, и не падает, когда в
боковой директории нет коммитов. Мутации, которые тесты обязаны ловить: ветка
собрана по локальному ID вместо ключа, отсутствие trackctl уронило `start`,
`merge` в корп-контуре прошёл, `status` спросил ветку у корня, корп-поведение
включилось в домашнем проекте.

Живая проверка на временном репозитории вне рабочих деревьев: корп-клон с
редиректом и привязкой, `shipctl start` по зеркальной строке, отказ `merge` с
подсказкой на подложном адаптере, `status` в клоне без коммитов в боковой
директории. В файл задачи вкладывается реальный вывод.

Прогон общего тест-набора из `.devkit/deploy.local` (ключ `test`) с кодом 0.

## Найденное по ходу серии

- DK-081: `shipctl status` в корп-контуре спрашивает git по корню, а корень
  теперь боковая директория со своим репозиторием. Из-за этого он называет
  веткой ветку доски, а не рабочую ветку клона, и падает на `git rev-parse
  HEAD`, пока в боковой директории нет ни одного коммита. Рабочую ветку надо
  спрашивать у клона, а не у корня.

### Реализация

- `shipctl/corp.go`: `loadTrackerBinding` читает `.devkit/tracker.local`
  плоским разбором `key = value` (тот же `unquote`, что у `deploy.local`),
  `corpTrackerRepo` переложен на него без смены поведения. `corpActive`
  это местный признак корп-контура для команд конвейера: наличие файла
  привязки в уже отрезолвленном root, домашний проект такого файла не несёт.
  `corpBranchName` разворачивает шаблон `branch` ({key}, {slug}), пустой
  шаблон берёт вид `{key}-{slug}`. `corpWorkBranch` чинит DK-081: без
  привязки или без ключа `repo` спрашивает ветку у `root`, как раньше, а с
  ключом `repo` спрашивает у клона, на который он указывает. `corpRefused`
  формулирует общий отказ merge/ship/revert.
- `shipctl/worktree.go` (`cmdStart`): в зеркальной строке ID и есть ключ
  тикета (DK-074, «Граница доски и тикета»), поэтому подстановка `{key}`
  берёт `p.ID`, а не поле `key` привязки (то общепроектный префикс, не
  тикета). Привязка без ключа `key` не валит `start`, ветка остаётся
  домашней, но находка идёт строкой в отчёт. После успешного создания
  worktree зовётся `trackctl -C root take <ID>` тем же порядком, что
  `taskMove` выше зовёт `taskctl`; ни отсутствие `trackctl` в PATH, ни его
  отказ `start` не валят, оба случая видно в отчёте.
- `shipctl/ops.go`: `cmdMerge`, `cmdShip`, `cmdRevert` отказывают
  `corpRefused` сразу после `primaryRoot`, до захвата замка и до любых
  git-операций. `cmdStatus` берёт ветку через `corpWorkBranch` и, если
  `corpActive`, не считает очередь и поезд вовсе (весь блок `trainTasks`,
  `checkQueue`, `returned`, `resolveDeploy` пропускается), а печатает одну
  объясняющую строку про MR-флоу и `trackctl sync`.
- Место создания worktree (`cmdStart`) не менялось: LLD DK-074 прямым
  текстом говорит, что в корп-контуре worktree остаётся тем же самым
  механизмом (раздел «Рамка»), поэтому он и остаётся сиблингом `root`, как и
  раньше.

### Живая проверка

Временное окружение вне рабочих деревьев (`/tmp`, дальше уже стёрто):
клон-стенд `proj` с редиректом `devkit.local`, боковая директория
`proj-local` с приявязкой и доской (задача `ABC-42` в Backlog), подложный
`trackctl` (шелл-стаб: живого адаптера в сборке нет, DK-083) и настоящие
собранные `shipctl`/`taskctl`.

```
$ cd proj && shipctl start ABC-42 --slug add-x
ветка feature/ABC-42-add-x в worktree .../proj-local-abc-42
доска: ABC-42: backlog -> in-progress, коммит 11c3fa0
работать в .../proj-local-abc-42, по готовности: shipctl merge ABC-42 (оттуда же или из основного чекаута)
трекер: тикет ABC-42: «Open» -> «In Progress»
исполнитель: тестовый пользователь контура

$ cat trackctl-calls.log
trackctl -C .../proj-local take ABC-42

$ cd proj-local-abc-42 && shipctl merge ABC-42 --test true
ошибка: корп-контур: merge здесь не работает, слияние и выкат ведёт MR-флоу компании; дальше руками: trackctl submit, пуш ветки, MR, дальше по процессу контура

$ shipctl ship
ошибка: корп-контур: ship здесь не работает, слияние и выкат ведёт MR-флоу компании; дальше руками: trackctl submit, пуш ветки, MR, дальше по процессу контура

$ shipctl revert ABC-42
ошибка: корп-контур: revert здесь не работает, слияние и выкат ведёт MR-флоу компании; дальше руками: trackctl submit, пуш ветки, MR, дальше по процессу контура

$ cd proj && shipctl status
ветка: main
worktree: feature/ABC-42-add-x в .../proj-local-abc-42

```

Отдельным стендом (второй клон `proj2` на ветке `dk-099-feature`, боковая
директория `proj2-local` заведена git-репозиторием без единого коммита)
проверено репро DK-081 и подтверждение починки:

```

$ cd proj2 && shipctl status
ветка: dk-099-feature
In progress: пусто
Check: пусто
Blocked: пусто
Backlog: 0 задач(и)
корп-контур: слияние и выкат ведёт MR-флоу компании, shipctl очередь и поезд не считает; Check означает «мяч на чужой стороне» (MR открыт, тикет в ревью или тестировании), строку двигает trackctl sync
```

### Мутации

Каждая заводилась в код руками (юнит из `shipctl/corp_pipeline_test.go`
краснел), код возвращался.

| Мутация | Кто ловит |
|---|---|
| ветка собрана по локальному ID вместо ключа тикета (шаблон не применён) | TestCorpStartBranchTemplate |
| отсутствие `trackctl` в PATH уронило `start` или отказ проглочен молча | TestCorpStartTrackctlMissing |
| отказ `trackctl take` проглочен молча | TestCorpStartTrackctlFails |

| `status` падает без коммитов в боковой директории (DK-081) | TestCorpStatusNoCommitsInLocal |
| корп-поведение включилось в домашнем проекте | TestCorpHomeUnaffected |
