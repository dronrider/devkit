# DK-092: shipctl: ворота готовности правки как предусловие merge

записан 2026-08-03

`shipctl merge` держит кодом зелёный прогон тестов, закрытые замечания ревью,
свободную очередь и живой прод, но не держит того, что правка вообще покрыта.
Тест мог не появиться в диффе, `regcheck` по задаче типа `bug` это подсказка, а
не отказ, сценарий проверки и обновление доки смотрит только глаз ревьювера.

## Что происходит

Проверено чтением кода 2026-08-05, ничего из перечисленного за время лежания
черновика не появилось:

- `regcheck` для `bug` уходит в предупреждения (`shipctl/advice.go`, вызов в
  `cmdMerge`), и в самом коде записано, что это подсказка, а не отказ;
- тестовых файлов в диффе не смотрит ни один вызов `git diff --name-only`:
  дифф читается только для пересечения файлов поезда и для сбора коммитов
  задачи;
- раздел «Сценарий проверки» проверяется предупреждением и только на поездном
  слиянии (`trainWarnings`), при одиночном `merge` его отсутствие не звучит
  вовсе.

Пропуск шага ловится, стало быть, вниманием ревьювера, а оно кончается там же,
где кончается сессия.

## Чего хотим

Ворота готовности отдельным предусловием `merge`, в обоих режимах, а не только
в автономном: они про готовность правки, а не про то, кто жмёт слияние.
Кандидаты в отказ названы черновиком, выбор между ними и есть работа задачи:
зелёный `regcheck` для типа `bug` с явной пометкой-исключением в файле задачи
там, где `regcheck` неприменим; наличие тестовых файлов в диффе; раздел
«Сценарий проверки» с пометкой, агентский он или пользовательский.

Оговорка, которую нельзя терять при реализации: код проверяет наличие, а не
качество. Пустая заглушка ворота пройдёт, поэтому обещать «100% проверено»
такими воротами нельзя, они ловят пропуск шага.

## DoD

`merge` отказывает по каждому из принятых ворот с внятной причиной и
подсказкой, чем починить; отказ гасится либо правкой, либо названной вслух
пометкой-исключением в файле задачи. Прогон на синтетической доске: задача без
теста в диффе не сливается, она же с тестом сливается.

## Ход работы

Три ворота готовы и стоят в `cmdMerge` до ребейза, пока дерево не тронуто. Каждый отказывает с причиной и подсказкой, как починить, и действует в обоих режимах слияния, одиночном и `--train`.

- `regcheckGate` (`advice.go`): bug-задача требует зелёного regcheck в `.devkit/log` за время жизни ветки. Живёт только при наличии файла `.devkit/log`: каталога `.devkit` мало, его кладёт обвязка выката и `start` задолго до прогонов. task и LLD ворот не проверяют.
- `testsGate` (`advice.go`): в слитом диапазоне есть тестовый файл. Предикат `isTestFile` опознаёт тест по соглашению об именах (`_test.{go,py,sh}`, `test_*.{py,sh}`), без привязки к языку. Пустой дифф и бескодовая ветка (только `docs/`) ворот не требуют.
- `scenarioGate` (`advice.go`): в файле задачи есть раздел «Сценарий проверки» (заголовок вне ограждённых блоков, уровень любой).

Пометка-исключение разбирается в `taskdoc.go` (`hasException`), формат тот же, что у override в `agentctl pick`: маркерная строка `- Исключение: <ворот> (причина)` вне ограждённых блоков, регистр нестрогий, первое совпадание гасит ворот. Имена ворот: `regcheck`, `тесты`, `сценарий`.

Прежний `regcheckWarning` и `scenarioWarning` убраны: предупреждение, которое звучит после прошедшего слияния, пропускает шаг не громче молчания.
- Ревью: подпроцесс glm-5.2/high по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-13.

## Сценарий проверки

Агентский, на синтетическом репозитории `t.TempDir()` через тесты. Внешнему прогону команды соответствует зелёный прогон набора:

1. Сборка без ошибок: `cd tools/shipctl && GOWORK=off go build .`
2. Прогон тестов зелёный: `cd tools/shipctl && GOWORK=off go test .`
3. Признак приёмки DoD держит `TestMergeTestsGateAcceptance`: ветка без тестового файла отбивается воротом (сообщение «нет тестовых файлов»), та же задача с тестом сливается. Юнит-проверки разбора пометки и предиката теста держат `TestHasException` и `TestIsTestFile`.
