# DK-1059: Потолок go test в parallel.py не поспевает за выросшим dashboard

## Что происходит

`tools/devkitctl/parallel.py`, функция `components`, гоняет каждый go-модуль
командой `go test -count=1 ./...` без флага `-timeout`. В силе дефолтный
потолок Go, 10 минут на пакет. Пакет `tools/dashboard` вырос до 986 тестов, 42
из них поднимают headless Chrome последовательно, без `t.Parallel()`.
Изолированно пакет укладывается в 516 секунд, а в составе полного прогона
`parallel.py`, конкурируя за машину с остальными 17 компонентами, стабильно
перевалил за 600 секунд и падал таймаутом. При слиянии DK-881 `shipctl merge`
не проходил тестовые ворота несколько часов подряд.

## Чего хотим

Потолок `go test` поднят так, чтобы пакет `dashboard` укладывался в него и
под конкурентной нагрузкой прогона. Зависший тест сторож всё равно ловит,
только позже.

## DoD

- `-timeout=20m` стоит в команде `go test` для всех go-компонентов
  `parallel.py`, тест `test_go_raises_timeout_past_the_default` держит ключ.
- `shipctl merge` на задаче, ждавшей в очереди из-за таймаута `go:dashboard`,
  проходит тестовые ворота.

## Ранг

`25+5+0+5+4 = 39`, P2.

- Серьёзность 25. Трение заметное. Тестовые ворота `shipctl merge` время от
  времени наглухо блокируют слияние под обычной параллельной нагрузкой
  машины, обход есть, ждать и повторять, но он дорогой (часы).
- Ценность 5. Снимает блокировку конвейера для всех будущих слияний
  go-модулей, не только для одной задачи.
- Неопределённость 0. Правка однострочная, причина найдена и проверена
  прогоном изолированного пакета.
- Поправка на баг 5. Регресс. Раньше пакет укладывался в потолок, по мере
  роста числа тестов перестал.
- Рычаг 4. Общий тестовый гейт конвейера.
