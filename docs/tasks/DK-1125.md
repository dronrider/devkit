# DK-1125: Итоги прогона по компонентам ложатся в журнал, слияния от чужой красноты считаются командой

Цель: [tasks/DK-1084.md](tasks/DK-1084.md)

## Что происходит

Запись `shipctl` хранит принадлежность коммитов. Итогов прогона `test` в ней нет.
Журнала слияний, отбитых чужой краснотой, нет вовсе, и число это сегодня
считается ручным разбором файлов задач.

Исполнитель видит красный компонент и не знает, своя это краснота или чужая.
В DK-764 записаны четыре отбитых слияния за сутки, в DK-1038 три за одну пачку,
в DK-1000 два лишних прогона по пять минут на одно слияние. Разбор чужого
компонента по DK-845 занял субагента на десять минут ради вывода «не наше».

Третья строка DoD цели DK-1084 требует счёта таких слияний с нулём после выката.
Такого счёта нет.

## Чего хотим

Итог прогона `test` по компонентам ложится в журнал при каждом слиянии. Команда
печатает число слияний, отбитых компонентом вне диффа задачи, за названный срок.
По этому числу видно, падает ли чужая краснота после выката бюджета машины.

## DoD

- `shipctl merge` пишет итог прогона по компонентам: имя компонента, исход,
  длительность, состав диффа задачи.
- Команда печатает число слияний, отбитых компонентом вне диффа задачи, за
  названный срок.
- Прогон на стенде показывает оба исхода: отбой своей краснотой и отбой чужой.
  Первый в счёт не идёт, второй идёт.
- Журнал переживает откат и повторное слияние той же задачи.

## Ранг

`25+6+1+0+4 = 36`, P2 по своим слагаемым. С наследованием от цели DK-1084 ранг
строки 65.

- Серьёзность 25. Ручная работа с дешёвым обходом. Исполнитель разбирает чужой
  компонент глазами и по диффу.
- Ценность 6. Регулярная операция слияния идёт каждый день, и разбор красноты
  входит в неё.
- Неопределённость 1. Форма записи выбирается по месту, опора это раздел «Выкат»
  файла задачи.
- Поправка на баг 0. Строка заводит механику.
- Рычаг 4. Журнал измеряет эффект бюджета машины и удешевляет каждое следующее
  слияние.

Цена M, правка `shipctl` вместе с тестами и командой счёта. Вид приёмки
агентский, барьеров из шести не названо. Журнал и вывод команды читаются с машины
агента.

## Ревью

Уровень 3 до df1540e: неопределённость 1 по рангу задачи, триаж да: тронут критичный путь tools/shipctl (critical_paths конфига), держит DoD цели DK-1084

- [возврат: реализация, 2026-09-23] блокирует: эвристика touchesDiff (tools/shipctl/testlog.go) сравнивает голое имя компонента с сегментом пути диффа, а не с областью, которую компонент реально проверяет, и у части компонентов parallel.py эти две вещи расходятся. Компонент «skills» это связка «python -m unittest discover» по всему kit/skills, а компонент «hooks» так же по всему hooks/: диф любой задачи, тронувшей хоть один файл внутри этих каталогов, получит сегмент «skills» или «hooks» и любой красный исход бакета будет признан своим, даже если упал тест совсем другого скилла или хука, которого дифф не касался. В обратную сторону компонент «check-skills» (скрипт kit/skills/check-skills.py) вообще не совпадёт с собственным диффом: последний сегмент пути это «check-skills.py» с расширением, а имя компонента «check-skills» без него, точное сравнение строк их не отождествит. Итог: foreign-fails может держать ноль после падения чужого скилла (ложный ноль по третьей строке DoD цели DK-1084), а по check-skills считать своё падение чужим. testlog_test.go проверяет эвристику только на чистых именах compA/compB, этот случай не покрыт. Нужно либо матчить по полному пути каталога компонента (cwd из components()), а не по голому сегменту, либо явно исключить бакет-компоненты (hooks, skills) из подсчёта своей красноты с пометкой в журнале, что для них граница не установлена.: исправлено, resolveOwnership (tools/shipctl/testlog.go) больше не сравнивает голое имя компонента с сегментом пути диффа. Он ищет для имени компонента раскладку deploy.<имя>.paths в .devkit/deploy.local и сверяет дифф с её путями тем же приёмом pathUnder, каким deployconf.Match сверяет пути компонентов выката. Компонент без заведённой раскладки Resolved не получает и в Own никогда не попадает: его краснота идёт в foreign-fails как чужая, а не молчаливо прощается, ложный ноль больше не возможен. Оба случая замечания закрыты раздельными тестами: TestResolveOwnershipExactPathMatch проверяет check-skills точным путём kit/skills/check-skills.py, расширение скрипта больше не мешает сравнению; TestResolveOwnershipBucketLayoutTrustsDeclaredBoundary проверяет бакет skills на всём kit/skills, граница доверяется ровно настолько, насколько точна раскладка проекта, а не признаёт своим любой чужой файл по одному имени каталога. TestResolveOwnershipUnresolvedWithoutLayout и TestResolveOwnershipDeclaredButNotTouched закрывают оставшиеся две ветки резолва. Регрессия TestMergeForeignFailsUnresolvedComponentCounted воспроизводит сценарий замечания на полном merge без раскладки: компонент compA красный на диффе, который его и касается, но без deploy.compA.paths не резолвится и не признаётся своим, foreignFails держит 1 вместо молчаливого 0 старой эвристики. regcheck на эту регрессию не применим впрямую, сам инструмент отказал с этой же причиной: база HEAD не собирается, тест зовёт новый символ resolveOwnership, которого в старом коде нет, потому что эвристика переписана целиком, а не залатана точечно. Полный go test ./... пакета tools/shipctl зелёный, 309s, GOWORK=off

## Сценарий проверки

Агентский.

1. `cd tools/shipctl`, затем `GOWORK=off go build ./...`. Сборка проходит без
   ошибок, свежий бинарь понимает подкоманду `foreign-fails --since <срок>`.
2. `GOWORK=off go test ./... -run 'TestMergeForeignFailsOwnRedNotCounted|TestMergeForeignFailsForeignRedCounted|TestJournalSurvivesRevertAndRemerge' -v`.
   Три теста зелёные. Первый держит красный компонент внутри диффа задачи, и
   `foreignFails` после него возвращает 0. Второй держит красный компонент вне
   диффа, и `foreignFails` возвращает 1 (оба исхода DoD, третий пункт). Третий
   проверяет, что после `cmdRevert` и второго `cmdMerge` той же задачи в
   журнале остаются обе записи (четвёртый пункт DoD).
3. `GOWORK=off go test ./...` пакета tools/shipctl целиком, зелёный: новый
   журнал не ломает существующие сценарии merge, revert, ship и train.
4. `PYTHONPATH=. python3 -m unittest devkitctl_test.DeployTest.test_16_machine_ignore_paths -v`
   из `tools/devkitctl`, зелёный: `devkitctl new`/`doctor --fix` раскладывают
   `.devkit/test-runs.log` в `.gitignore` проекта.
