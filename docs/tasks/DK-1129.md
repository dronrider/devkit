# DK-1129: Живой чат продолжает ход после обрыва связи посреди ответа

## Что происходит

Харнес Claude Code 2.1.263 при обрыве соединения посреди стрима печатает в чат
«API Error: Connection lost mid-response. The response above may be incomplete.»
и ждёт ввода человека. Замечено 2026-09-22, повторяется в живых сессиях по
несколько раз в день. По официальной доке (errors.md, network-config.md,
hooks.md, справка 2026-09-22) ретраи харнеса покрывают только ошибки до начала
стрима. Обрыв посреди ответа кончает ход с пометкой «неполный». Дописать
обрезанный ответ харнес сам просит только в печатном режиме `-p` и у
субагентов, в живом чате этого нет. Хук `StopFailure` срабатывает на упавший
ход, но решения не возвращает и продолжить ход не может. Это умеет только хук
`Stop` через `"ok": false`, а на API-ошибке срабатывает не он. Ключи среды
`CLAUDE_ENABLE_STREAM_WATCHDOG` и `CLAUDE_STREAM_IDLE_TIMEOUT_MS` двигают только
пороги таймаутов. Чейнджлог 2026 года возобновления не добавлял. В 2.1.227
текст ошибки переименован из «closed» в «lost», в 2.1.222 починены ложные
таймауты на шлюзах.

Закрытая DK-172 (архив) разбирала тот же класс обрывов и остановилась на
громком баннере «ход упал» через `notify.py` на `StopFailure`. Продолжения хода
она не дала. Ключ `CLAUDE_CODE_RETRY_WATCHDOG` в замере разницы не показал.
DK-156 закрывала обрывы витка цели перезапуском сторожком, живой чат вне цикла
она не трогает.

Каждый обрыв ставит работу сессии до ручного «продолжай». Человек замечает
стоп с задержкой в минуты или десятки минут. За это время исполнители и
конвейер стоят, а сессия, поднятая на ночь, доживает до утра ни с чем.
Баннер DK-172 делает стоп заметным, но не снимает ручной шаг.

Внутри харнеса нет рычага, продолжение строится снаружи. Обход 2026-09-22
разложил каналы доставки реплики в сессию. Файловый вход `chat-in.py`
подхватывается только хуком `PostToolUse`, и после упавшего хода нет ходов
инструмента. Этот канал не годится. Годятся два канала дашборда. Сокет
харнеса `/tmp/cc-socks/<pid>.sock` (функция `peerSay`, `tools/dashboard/peers.go`)
будит простаивающую сессию за секунды, включая окно vscode (проба DK-397).
Второй канал это `tmux send-keys` для сессий, поднятых дашбордом в tmux
(`chats.go`, функция `chatSend`, с проверкой живости pty из DK-863). В архиве
нет прямой пробы «сокет будит сессию, стоящую после `StopFailure`». Все
пробы были на штатно простаивающей сессии, стендом это проверяется первым
шагом. Стенд DK-480 (`tools/dashboard/asksay_test.go`, `askroad_test.go`)
уже гоняет доставку в спящую сессию и берётся за образец.

DK-172 не строила ограничителя попыток, её вклад это баннер на `StopFailure`.
Счётчик подряд идущих попыток есть только у оболочки витка цели (DK-169, три
попытки с паузой), и для живого чата он пишется заново. Событие несёт
категорию в поле `error` (`server_error`, `unknown`) и текст в
`last_assistant_message` (образец `hooks/testdata/claude-code/turn-failed.json`).
Харнес не даёт словаря категорий, обрыв связи отличается от кончившегося
кредита разбором текста. Стенд-стаб DK-172 в репозиторий не коммитился и на
диске отсутствует, повторяется по рецепту из архива.

## Чего хотим

После обрыва соединения посреди ответа живая сессия сама продолжает ход с
места обрыва, без ввода человека, а исчерпание попыток кончается громким
уведомлением.

## Границы

Продолжение положено ходу живой сессии, упавшему по обрыву соединения. Ошибки
другой природы (кончившийся кредит, битый запрос, отказ авторизации) получают
прежний баннер DK-172 и ручной шаг. Печатный режим `-p` и субагентов харнес
дописывает сам, они вне задачи. Виток цели переживает обрывы оболочкой DK-169,
и его эта задача не трогает. Число попыток ограничено, исчерпание кончается
громким уведомлением, а не тихим циклом.

   Ввод «продолжай» человеком и отдельная отправка сокетом в тесте отсутствуют.

   Connection lost mid-response проверяется юнит-тестом. Отдельные сценарии
   держат обрыв до исчерпания трёх попыток и возвращают ошибку кредита.
   Исчерпание сохраняет запрет лишнего повтора сторожком, ошибка кредита
   не создаёт отправителя. После успешного Stop счётчик обнуляется.

4. Проверить раскладку уведомителя и приём межсессионных реплик:

   ```sh
   devkitctl test tools/devkitctl devkitctl_test.CrossSessionInboundTest devkitctl_test.HarnessHooksTest.test_hooks_are_laid_out_once
   ```

   Ожидаются зелёные тесты. Доктор подключает каждый хук ровно один раз,
   выставляет crossSessionInbound и сохраняет явное значение пользователя.

При обкатке в свежем дереве живой клиент передаётся через DEVKIT_LIVE_CLAUDE,
а корень временной рабочей папки через DEVKIT_LIVE_WORK_ROOT. Папка клиента
создаётся вне системного временного каталога, где уведомления намеренно
отключены. Сам notify.py берётся из проверяемого дерева, HOME и настройки
клиента остаются изолированными. Явно запрошенный живой прогон при отсутствии
клиента завершается ошибкой.
