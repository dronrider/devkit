# DK-1138: повторный подъём окна задачи открывает второй чат вместо продолжения

## Что происходит

Задача DK-972, 2026-09-21. В 11:28 дашборд поднял голову задачи в окне tmux task-DK-972, сессия e5142f41, чат «Выполнение задачи DK-972 на доске». В 12:22 голова напечатала человеку развилку «poc-строки» через taskctl decide --chat, строка ушла в Blocked, ход кончился. Оболочка конвейера task-run.py на статусе blocked останавливает цикл и снимает окно tmux со словами «задача запаркована и ждёт человека». В 12:24 ответ человека вернул строку в In progress, и wake.go поднял новую сессию f252c94b в новом окне под тем же именем, чат «Продолжение выполнения задачи DK-972». Склейка заходов в tools/dashboard/chatpast.go клеит по жизни окна (DK-723, DK-859): записи реестра до момента подъёма окна считаются прежним жильцом, и подъём по ответу человека даёт вторую строку списка. В журнале дашборда обе сессии видны строками «подъём головы DK-972» с разными панелями.

По смыслу разговор один. Вопрос задачи стоит в первом чате, ответ человека и продолжение работы во втором, и человек ищет ход задачи по двум лентам. Окно снимается при любой парковке, а также при потолке проходов, воронке молчания, вышедшем клиенте и ребуте машины, так что чат задачи с двумя и более вопросами человеку раздваивается на каждом вопросе. Вместе с окном гибнет фоновая работа хода. У DK-972 в момент сноса шёл ревьювер review-xhigh с прочитанными 72k токенов, хвост терминала в журнале это показывает, и вторая сессия гоняла ревью заново.

## Чего хотим

## DoD

У задачи один чат в списке от взятия в работу до закрытия. Повторный подъём окна task-<ID> по открытой строке доски продолжает прежнюю ленту, записи реестра ложатся в ту же строку списка. Новая строка списка появляется только у чата, убранного в архив руками, и у подъёма после закрытия строки. Сценарий проверки агентский: синтетический реестр с двумя подъёмами окна по открытой строке даёт одну строку списка, а подъём после закрытия строки даёт вторую.

## Что дал разбор

Обход 2026-10-28 подтвердил актуальность. После 2026-09-23 деление chatLife не трогал никто, единственный коммит по chatpast.go это подписи ролей на стыках заходов (DK-871), и раздвоение лент не закрыто ничем.

Механика сегодня такая. chatLife делит ключ окна по моменту подъёма (tools/dashboard/chatpast.go:53-61), порогом служит winSince, который читает метку Raised из присмотра за окном (tools/dashboard/chats.go:1971-1979), а ключ строки списка собирает chats.go:1234. Заходы внутри одной жизни окна клеит chatPasses с потолком в шесть проходов (chatpast.go:163, 167-200). Подъём после ответа человека идёт дорогой wake (tools/dashboard/wake.go:16-31, 370; tools/taskctl/wake.go:227-295) и поднимает новую сессию, которая по нынешнему делению становится новым жильцом.

Окно конвейер снимает при любой парковке (kit/skills/board-task/task-run.py:189, 1980-1982, 2144-2147, 2200-2202), снос делает drop_head (task-run.py:1811-1824). Фоновая работа хода гибнет вместе с окном и гаснет вслух по DK-1317, account_tails добивает хвост записью и криком (task-run.py:1006-1030), а щадящие пути для живого фона (DK-864, DK-941, DK-1454, DK-1463) парковку не покрывают. Гибель фона при парковке это закрытое решение DK-1317, кейсом разбора её не поднимаем.

Дублей нет. DK-1463 закрывал смерть второго окна конвейера, не раздвоение чата. DK-1253 держит тот же предмет у чата диспетчера цели. DK-1117 закрывает один повод сноса окна, парковку из захода исполнителя. DK-723 и DK-859 это фундамент склейки и деления по жильцу. Условий, посильных только человеку, не нашёл, доступов и внешних шагов у строки нет.
