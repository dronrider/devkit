# DK-1142: Набор шаблонов плана kit/plans: task, bug, lld, poc и парсер

## Что происходит

Порядок работы над задачей сегодня разложен по прозе. Перечень этапов повторяют
ядро правил, скиллы и определения субагентов, а ворота доски держат его
хардкодом. Одно и то же знание лежит в нескольких местах и расходится.
LLD DK-972 (`docs/lld/DK-972-plan-templates.md`) выносит порядок в файл
шаблона: решение 1 задаёт формат подмножества TOML, решение 2 раскладку набора
по двум слоям, решение 9 снятие встроенного этапа с причиной. Эта строка первая
в нарезке, без неё остальным нечего читать.

## Чего хотим

Каталог `kit/plans/` с четырьмя файлами. `task.toml` повторяет сегодняшний
порядок из живого материала LLD один в один: те же этапы, те же ворота. У
вычитки поле `gate` пустое, ворота её сегодня не спрашивают.
`bug.toml` это `task` плюс `regcheck` с `gate = merge`. `lld.toml` это `task`
без тестов, обкатки и regcheck, зато с этапом «карта решений» (`trace =
"слово"`) и приёмкой человека. `poc.toml` собирается по решению 12.

Парсер подмножества TOML переезжает из agentctl в `internal/`, а пакет чтения
набора склеивает два слоя по решению 2: одноимённый файл проекта замещает
встроенный целиком. Появляются команды `agentctl plan templates`,
`plan templates --dump <имя>` и `plan show --template <имя>`. Валидатор
подмножества и находки доктора по решению 9 ложатся туда же.

Тесты: фикстуры парсера общие с python-частью, склейка набора с проектной
копией, находка доктора на этапе, снятом без причины, и на отставшей копии.

## Развилки

- «состав тринадцати этапов task»: Какие тринадцать этапов стоят в task.toml
  - решает: исполнитель
  - рекомендация: пункты живого материала один в один, правка с тестами разбита на разработку и тесты
  - решено исполнителем 2026-09-28: Взяты все тринадцать пунктов живого материала, где правка с тестами разбита на секции work и tests, а regcheck остался у bug. Иначе тринадцати этапов из десяти секций примера решения 1 не набирается, а DoD просит ровно тринадцать в том же порядке.
- «строгость валидатора шаблона»: Что валидатор отбивает отказом, а что пропускает предупреждением
  - решает: исполнитель
  - рекомендация: незнакомое значение by, gate и accept это отказ, незнакомый ключ это предупреждение
  - решено исполнителем 2026-09-28: Значение, по которому движок выбирает поведение (by, gate, accept), с опечаткой отбивается отказом: такой этап не спросит никто, а выглядеть он будет поставленным. Незнакомый ключ идёт предупреждением, как у профилей харнесов: набор ключей растёт задачами нарезки, и старая утилита не должна валиться на файле, написанном для новой.
- «где живут находки доктора»: Считать находки решения 9 на стороне python или звать go-пакет
  - решает: исполнитель
  - рекомендация: сверка слоёв на обеих сторонах: python для доктора, go для утилит
  - решено исполнителем 2026-09-28: Доктор написан на python и зовёт tools/devkitctl/plans.py, а те же слои читает go-пакет internal/plans для agentctl. Это вторая пара реализаций одного формата, как у профилей харнесов, и сверяются они общими встроенными шаблонами в тестах обеих сторон.

причиной проходит доктора, а снятие без причины даёт находку.

## Сценарий проверки

Сценарий агентский. Он прогоняется в чекауте devkit после слияния, а вход
это собранный из ветки `agentctl`.

1. Набор виден списком. `agentctl plan templates` печатает четыре шаблона,
   это `bug`, `lld`, `poc` и `task`. У каждого стоит слой «встроенный» и число
   этапов, а последняя строка подсказывает дамп в `.devkit/plans`.
2. Порядок этапов тот же, что у живого материала LLD.
   `agentctl plan show --template task` печатает тринадцать этапов, первый
   «план работ», последний «приёмка», у тестов ворота merge, у сценария check и
   merge, у проверки close, а у вычитки ворот нет.
3. Отличия остальных шаблонов. У `bug` четырнадцать этапов, и среди них
   `regcheck` с воротами merge. У `lld` нет тестов и обкатки, зато есть карта
   решений на слове агента. У `poc` пять снятых этапов с причинами.
4. Проектный слой и доктор. Завести копию и снять этап без причины:

   ```
   mkdir -p .devkit/plans
   agentctl plan templates --dump task > .devkit/plans/task.toml
   python3 - <<'EOF'
   import pathlib
   p = pathlib.Path(".devkit/plans/task.toml")
   t = p.read_text(encoding="utf-8").replace('types = ["task"]', 'types = ["task"]\ndropped = ["tests"]')
   p.write_text(t, encoding="utf-8")
   EOF
   python3 tools/devkitctl/devkitctl.py doctor
   ```

   Доктор называет находку про `dropped` без причины. Дописать причину
   (`dropped = ["tests: <причина>"]`) и убрать из копии секцию `[tests]`: доктор
   молчит. Убрать из копии ещё и секцию `[stand]` без записи `dropped`: доктор
   называет отставшую копию и просит вписать этап либо снять с причиной. Снести
   `.devkit/plans` и убедиться, что находок про шаблоны больше нет.
5. Тесты обеих сторон зелёные:

   ```
   GOWORK=off go test ./internal/subtoml/ ./internal/plans/
   python3 -m unittest plans_test
   ```

Ожидаемый итог. Набор читается двумя слоями, тринадцать этапов task совпадают
с живым материалом LLD, а отставшую копию и снятие без причины называет
доктор.
