# DK-115: находка диагностики про чужой go.work рядом с go-проектом

записан 2026-08-04

Го-проект, лежащий рядом с `~/go.work`, в котором он не перечислен, отвечает на
`go test ./...` отказом «directory prefix . does not contain modules listed in
go.work or their selected dependencies». Для `shipctl merge` это выглядит как
«тесты после ребейза красные», хотя код зелёный, и слияние встаёт на ровном
месте. Поймано на слиянии DK-113 (2026-08-04), тогда пришлось звать `merge` с
`--test` и `--deploy` руками.

## Что происходит

Частный случай в самом devkit уже закрыт: ключи `deploy` и `test` в
`.devkit/deploy.local` обёрнуты `GOWORK=off`, и шапка файла ссылается на этот
черновик. Слияния 2026-08-05 (DK-129, DK-130, DK-132) прошли без флагов.

Общая половина жива. Среда та же: `~/go.work` перечисляет чужие проекты, devkit
в него не вписан, и `go list ./...` из каталога утилиты по-прежнему отвечает тем
же отказом. Находки про `go.work` в `devkitctl` нет: греп по `go.work` и
`GOWORK` не даёт ни одного попадания ни в диагностике, ни в утилитах, ни в
правилах. Любой следующий го-проект, подключённый к devkit, наступит на то же
самое и увидит красные тесты вместо подсказки.

## Чего хотим

Находку `devkitctl doctor`: рядом лежит `go.work`, в нём нет этого проекта, а в
ключах `deploy` и `test` нет `GOWORK=off`. Починка называется прямо в тексте
находки, потому что сама по себе она неочевидна: сообщение го про «directory
prefix» не подсказывает ни причину, ни выход.

## DoD

`devkitctl doctor` в го-проекте рядом с чужим `go.work` печатает находку с
причиной и командой починки, а в проекте, где `GOWORK=off` уже стоит либо
проект вписан в `go.work`, молчит. Проверяется на временном каталоге с
подложенным `go.work`.

## Ход работы

- Исполнение: подпроцесс glm-5.2/high по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-12.
- Ревью: подпроцесс glm-5.2/high по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-12.

## Сценарий проверки

Реальный вывод на временном каталоге. Чужой `go.work` лежит на уровень выше
го-проекта, в `use` один сиблинг, проект не перечислен:

```
$ tree ws -I '.git'
ws
|-- go.work
|-- proj
|   |-- AGENTS.md
|   |-- .devkit/deploy.local
|   |-- docs/TASKS.md
|   `-- go.mod
`-- sibling
    `-- go.mod

$ cat ws/go.work
go 1.21

use (
        ./sibling
)

$ cat ws/proj/.devkit/deploy.local
deploy = make deploy
test = go test ./...
autonomous = false

$ python3 ~/projects/devkit/tools/devkitctl/devkitctl.py doctor -C ws/proj
рядом лежит ../go.work, где проект не перечислен в use: го-команды из каталога проекта ломаются ответом «directory prefix . does not contain modules listed in go.work», для shipctl merge это красные тесты после ребейза на ровном месте; дописать «export GOWORK=off; » в начало ключа test= файла .devkit/deploy.local
```

Молчит в трёх случаях:

- проект дописали в `use` чужого `go.work` -> `go test` проходит, находка не нужна;
- `test = export GOWORK=off; go test ./...` -> го-команда уже обёрнута;
- `test = make test` -> го-команды в обвязке выката нет, GOWORK=off не требуется.

Регрессию гоняет `regcheck`, тест краснеет на HEAD и зелёный на правке:

```
$ regcheck -C . --tests tools/devkitctl/devkitctl_test.py -- \
    sh -c 'cd tools/devkitctl && python3 -m unittest -v devkitctl_test.GoWorkFindingTest'
тест краснеет на HEAD и проходит на текущем коде, регрессия закрыта
```

## Ревью

- Правка: парсер go.work не пропускает комментарии // внутри блока use ( ... ). Строка-комментарий даёт токен //, который начинается с /, резолвится в корень /, и project_in_gowork отвечает True для любого проекта (всякий путь внутри /). Находка молчит на валидном go.work с комментарием в use-блоке, хотя проект не перечислен. Починка: пропускать строки, начинающиеся с //, до разбора; регрессию держит тест с комментарием в use-блоке.: исправлено, Парсер go.work пропускает строки, начинающиеся с //, до разбора путей; регрессию держит GoWorkFindingTest.test_8_comment_in_use_block_does_not_mask_missing_project (regcheck: красный на HEAD, зелёный на правке).
- Правка: README, фраза «Молчит, когда проекта в go.work нет» описывает условие срабатывания находки (проект не перечислен), а не условие молчания. Список условий молчания также не полон: нет «проект вписан в go.work» и «нет go.mod». Переформулировать, чтобы триггер и молчание не смешивались.: исправлено, README переформулирован: триггер срабатывания (проект не перечислен, го-команды без GOWORK=off) отделён от условий молчания; список дополн случаем «проект вписан в go.work» и «нет go.mod».
- Заметка: в докстринге gowork_use_directories «bare-слов го в синтаксисе не допускает», слово «bare» здесь англицизм. Живой русский: «use без префикса ./, ../ или / го в синтаксисе не допускает».: исправлено, Докстринг gowork_use_directories переписан: вместо «bare-слов го в синтаксисе не допускает» написано «use без префикса ./, ../ или / го в синтаксисе не допускает», добавлено, что комментарии // выкидываются до разбора.
- Заметка: текст находки «го-команды ломаются ответом» звучит неестественно. Предмет задачи и кодовая база устояли «отказывает/отказом» (строка subject, соседние находки doctor). Естественнее: «го-команды из каталога проекта отказывают тем же ответом».: исправлено, Текст находки и докстринг check_gowork переписаны: «ломаются ответом» -> «отказывают тем же ответом», в лексике предмета задачи и соседних находок doctor.
