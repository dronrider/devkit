# DK-1162: Потолок проверяющих сессий с полным прогоном одновременно

## Что происходит

Поезд из семи задач выкатился 25 сентября, и на шесть строк в Check разом
поднялись проверяющие сессии. Каждая гоняет полный прогон, и средняя загрузка
дошла до ста пятидесяти при десяти ядрах. Браузерные тесты дашборда у DK-1123
не собрали chrome восемь раз подряд, замер отзывчивости у DK-1124 не взял
порог пять секунд ни разу из десяти. Обе строки получили провал проверки,
прод считался сломанным, очередь выката стояла, а в одиночку упавший тест
проходит за восемь секунд.

Понижение приоритета из DK-1124 работает, дерево прогона идёт с ni=19 целиком.
Просадка идёт не по приоритету, а по числу готовых к счёту потоков: три полных
прогона плюс сорок два процесса chrome. Ответ человека по развилке DK-1124
«порог отзывчивости»: DoD-пункт про порог пять секунд ведётся новой строкой
цели DK-1084 про оверсабскрипцию.

Просится потолок на число проверяющих сессий с полным прогоном одновременно,
либо резерв доли ядер в cpu_budget и очередь на фазу сборки go. Признак ложного
провала снят руками дважды, и без потолка так будет на каждом поезде.

## Чего хотим

## DoD

Число проверяющих сессий с полным прогоном одновременно держит потолок, и
лишние ждут очереди, а не давят машину.

Замер отзывчивости DK-1124 (шаг 4 её сценария) берёт порог пять секунд, когда
рядом идёт один прогон под потолком.

Ложный провал проверки от чужой нагрузки на поезде из нескольких задач не
повторяется.
