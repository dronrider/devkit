# DK-1162: Потолок проверяющих сессий с полным прогоном одновременно

## Что происходит

Поезд из семи задач выкатился 25 сентября, и на шесть строк в Check разом
поднялись проверяющие сессии. Каждая гоняет полный прогон, и средняя загрузка
дошла до ста пятидесяти при десяти ядрах. Браузерные тесты дашборда у DK-1123
не собрали chrome восемь раз подряд, замер отзывчивости у DK-1124 не взял
порог пять секунд ни разу из десяти. Обе строки получили провал проверки,
прод считался сломанным, очередь выката стояла, а в одиночку упавший тест
проходит за восемь секунд.

Понижение приоритета из DK-1124 работает, дерево прогона идёт с ni=19 целиком.
Просадка идёт не по приоритету, а по числу готовых к счёту потоков: три полных
прогона плюс сорок два процесса chrome. Ответ человека по развилке DK-1124
«порог отзывчивости»: DoD-пункт про порог пять секунд ведётся новой строкой
цели DK-1084 про оверсабскрипцию.

Просится потолок на число проверяющих сессий с полным прогоном одновременно,
либо резерв доли ядер в cpu_budget и очередь на фазу сборки go. Признак ложного
провала снят руками дважды, и без потолка так будет на каждом поезде.

## Чего хотим

У полного прогона `parallel.py` есть потолок числа одновременных запусков на
машине. По умолчанию он равен одному. Потолок реализован замком на файловой
системе. Замок общий для всех процессов независимо от того, кто позвал
прогон: `shipctl merge`, `regcheck` или сценарий проверки задачи в Check.

Лишний запуск не падает и не давит машину. Он ждёт своей очереди на свободный
слот. Пока ждёт, он печатает строку ожидания. По этой строке видно, что
прогон стоит в очереди.

Потолок стоит уровнем выше готовой раздачи бюджета внутри одного прогона
(`cpu_budget`, DK-1123) и приоритета его дерева (`nice`, DK-1124). Он эту
раздачу не дублирует. Раздача задаёт, сколько ядер достанется каждому
компоненту внутри одного прогона. Приоритет задаёт, кто выигрывает у
планировщика при столкновении. Потолок задаёт, сколько таких прогонов вообще
имеют право идти разом.

## Развилки

- «рычаг»: чем ограничивать оверсабскрипцию нескольких проверяющих сессий: потолком сессий с полным прогоном или резервом доли в cpu_budget с очередью на фазу сборки go?
  - решает: исполнитель
  - рекомендация: потолок сессий: cross-process семафор в parallel.py (один вход у shipctl merge, regcheck и сценария ревью), лишние ждут слот; резерв доли в cpu_budget работал бы только внутри одного прогона, на уровне DK-1123, и соседних процессов не видит
  - вариант: потолок числа одновременных полных прогонов parallel.py: cross-process замок на N слотов, лишние ждут очереди
  - вариант: резерв доли ядер в cpu_budget и очередь на фазу сборки go
  - решено агентом 2026-09-25: потолок числа одновременных полных прогонов parallel.py, один слот по умолчанию (FULL_RUN_SLOTS=1): cross-process flock в ~/.devkit/parallel-slots держит место на слот держателем дескриптора, лишние ждут очередь с видимой печатью; резерв доли в cpu_budget отвергнут, потому что живёт внутри одного прогона (DK-1123) и не остановил бы второй параллельный прогон machine-wide, а очередь только на фазу сборки go не трогает сюиту devkitctl и браузерные стенды, то есть не самого тяжёлого виновника инцидента

## DoD

Потолок ограничивает число проверяющих сессий с полным прогоном одновременно,
и лишние ждут очереди, а не давят машину.

Замер отзывчивости DK-1124 (шаг 4 её сценария) берёт порог пять секунд, когда
рядом идёт один прогон под потолком.

Ложный провал проверки от чужой нагрузки на поезде из нескольких задач не
повторяется.

## Сценарий проверки

1. Юниты потолка зелёные, включая новые тесты `full_run_slot` (одиночный
   держатель без ожидания, второй ждёт первого, два слота держат двоих
   разом, слот освобождается при исключении, строка ожидания повторяется) и
   `main()` под занятым слотом. Ждём `OK`.

```sh
cd tools/devkitctl && python3 -m unittest discover -p "parallel_test.py" -q 2>&1 | tail -3
```

2. Живая проверка очереди. Два полных прогона `--only-go` запущены разом.
   Слот один. Второй обязан напечатать строку ожидания и не начать
   компоненты, пока первый не закончит. Оба обязаны дойти до `OK`. Условие
   то же, что уронило поезд 25 сентября: несколько прогонов одновременно.
   Теперь ни один прогон не падает от чужой нагрузки. Прогон занимает
   15-20 минут суммарно, два прогона `--only-go` друг за другом, не разом.
   Ждём в обоих логах `OK`, а в одном из двух подстроку `потолок 1 полных
   прогонов занят, жду`.

- Исключение: обкатка (два реальных полных прогона подряд и пятнадцать-двадцать
  минут стенного времени; свежее дерево обкатки `taskctl rehearse` их не
  гоняет)

```
mkdir -p /tmp/dk1162-check
( python3 tools/devkitctl/parallel.py --only-go >/tmp/dk1162-check/run1.log 2>&1; echo $? >/tmp/dk1162-check/run1.rc ) &
( python3 tools/devkitctl/parallel.py --only-go >/tmp/dk1162-check/run2.log 2>&1; echo $? >/tmp/dk1162-check/run2.rc ) &
wait
echo "run1 rc=$(cat /tmp/dk1162-check/run1.rc)"; tail -1 /tmp/dk1162-check/run1.log
echo "run2 rc=$(cat /tmp/dk1162-check/run2.rc)"; tail -1 /tmp/dk1162-check/run2.log
grep -h "потолок 1 полных прогонов занят" /tmp/dk1162-check/run1.log /tmp/dk1162-check/run2.log
```

3. Замер отзывчивости DK-1124 (её шаг 4) под нагрузкой одного прогона рядом,
   на коде с потолком. Сценарий тот же, что закрыл DK-1124, и он же второй
   раз доказывает DoD-пункт 2 этой строки: нагрузка рядом с замером теперь не
   случайно одна, а держится потолком. Ждём `OK`, десять строк с числами не
   больше 5 и «потолок не задет».

- Исключение: обкатка (шаг просит живой сервис дашборда с портом и токеном из
  ~/.devkit/dashboard.local и двадцать минут прогона рядом, как у DK-1124)

```
docs/tasks/DK-1124-check.sh 5
```
