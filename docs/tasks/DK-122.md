# DK-122: отказ «конвейер занят» не говорит, кто держит замок

записан 2026-08-05

При заходе на `shipctl start` (2026-08-05, DK-121) команда отказала «конвейер
занят», а файл `.devkit/ship.lock` был нулевого размера и с временем правки
трёхдневной давности. Живой `merge` в соседней сессии шёл, но узнать это
удалось только через `pgrep` по `shipctl`.

## Что происходит

Замок целиком в `shipctl/lock.go`: файл открывается и запирается `flock`, в
него не пишется ничего, ни pid, ни ID задачи, ни время старта. Отказ поэтому
безымянный, и владельца ищут мимо утилиты.

При разборе 2026-08-05 вторая половина черновика сузилась. «Брошенный от живого
не отличить» буквально неверно: замок держится дескриптором, и ядро снимает его
при завершении процесса, включая аварийное, так что отказ всегда означает
живого владельца, а старый `mtime` пустого файла это обманка, а не причина.
Ручного `rm` случай не требует, снимать протухшее нечего.

Открытым остаётся ровно то, что отказ молчит про владельца. Образец лежит в том
же репозитории: замок оболочки цели (`skills/goal-loop/goal-run.sh`) пишет pid,
снимает мёртвый сам, и отказ там называет, кто держит.

## Чего хотим

Замок пишет владельца: pid, ID задачи, время старта. Отказ печатает их, и
по нему видно, ждать ли (идёт чужое слияние минуту назад) или разбираться
(процесс висит с прошлой ночи). Про `mtime` пустого файла в отказе сказать
прямо, чтобы следующий читатель на него не купился.

## DoD

`shipctl start` при занятом конвейере печатает, кто держит замок и с какого
времени. Проверяется на временном репозитории: запустить долгую команду под
замком, второй вызов обязан назвать pid и время первой.

## Ход работы

- Разработка: opus/medium по вердикту pick, 2026-09-17 00:27-03:33.
- regcheck: «тест краснеет на HEAD и проходит на текущем коде» по tools/shipctl/lock_holder_test.go. Тесты, зовущие acquireLock напрямую, под regcheck не идут. У функции сменилась арность, база с ними не собирается, и краснота ничего не доказывала бы. Ради этого держатель в lock_holder_test.go ставится руками, старыми символами.
- Тесты: пакет tools/shipctl прогнан четырьмя кусками по -run, все зелёные, кроме TestStartWorktreeCarriesCommittedLink. Он падает и на чистом main (git add .devkit/devkit упирается в гитигнор), к правке отношения не имеет.
- Вычитка: 2 файла, 15 правок, 1 пометка, 2026-09-17.

## Сценарий проверки

Прогон идёт на временном репозитории. Живой замок devkit трогать нельзя, через
него идут чужие слияния. Держателем выступает настоящий `shipctl merge` с
долгой командой тестов, второй запуск ловит отказ.

```sh
set -u
BASE=$(mktemp -d /tmp/dk122-XXXX); WORK="$BASE/repo"; mkdir -p "$WORK"
cd "$WORK"
git init -q -b main && git config user.email t@t && git config user.name t
taskctl init --prefix XR --name "Проверка DK-122"
taskctl add --title "Первая правка" --type task --rank "0+1+1+0+1"
taskctl add --title "Вторая правка" --type task --rank "0+1+1+0+1"
mkdir -p .devkit
printf '.devkit/\n' > .gitignore
printf 'old\n' > code.txt
git add -A && git commit -qm seed
shipctl start XR-001
cd "$BASE/repo-xr-001" && printf 'new\n' > code.txt && git add -A &&
  git commit -qm "fix: XR-001 правка"
cd "$WORK"
shipctl start XR-002
cd "$BASE/repo-xr-002" && printf 'ещё\n' > other.txt && git add -A &&
  git commit -qm "fix: XR-002 правка"
cd "$WORK"

# 1) держатель называется: первый merge сидит на тестах, второй получает отказ
shipctl merge XR-001 --test "sleep 40" > "$BASE/first.log" 2>&1 &
until [ -s .devkit/ship.lock ]; do sleep 0.3; done
cat .devkit/ship.lock
shipctl merge XR-002 --test true; echo "exit=$?"

# 2) отпущенный замок держателя за собой не оставляет
wait
wc -c < .devkit/ship.lock

# 3) держатель, который не назвался: замок взят чужим процессом без записи
python3 -c "import fcntl,sys,time;f=open('$WORK/.devkit/ship.lock','w');fcntl.flock(f,fcntl.LOCK_EX);sys.stderr.write('held\n');sys.stderr.flush();time.sleep(20)" 2>"$BASE/held" &
LOCKPID=$!
until grep -q held "$BASE/held"; do sleep 0.2; done
shipctl merge XR-002 --test true; echo "exit=$?"
kill $LOCKPID
```

Ожидаемый итог по шагам:

1. `cat` печатает строку держателя вида
   `pid=<число>	команда=merge XR-001	взят=<время>`, а второй `merge` падает с
   `exit=1` и строкой «конвейер занят: замок .devkit/ship.lock держит merge
   XR-001, pid <то же число>, взят <дата и время> (меньше минуты назад); ...».
   Pid из отказа совпадает с pid из файла, время захвата свежее.
2. `wc -c` печатает `0`. Первый `merge` закончил и стёр свою строку, под
   свободным замком в файле пусто.
3. Отказ говорит «держит неназвавшийся запуск shipctl (замок взят сборкой до
   DK-122 либо запись держателя ещё не легла)», `exit=1`. Чужой замок без
   записи это не поломка и не выдуманный pid.
