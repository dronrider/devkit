# DK-1230: Python-стенды скиллов не признаются замером стенного времени

Цель: [tasks/DK-1084.md](tasks/DK-1084.md)

## Что происходит

Признак нагрузочного падения (DK-1218) читает вывод прогона: маркеры срока и строку loadfail.Mark, которой тест сам называет себя замером стенного времени. Печатают её пока только браузерные хелперы дашборда. У python-стендов скиллов такого признания нет, а под нагрузкой они краснеют так же: 29 сентября компонент board-task отбил слияние DK-1204 за 332 секунды в полном прогоне, а прогнанный один, без соседей, прошёл за 150 секунд зелёным. Очередь слияний отнесла его к прочей красноте вне диффа и остановила проход вместо повтора.

Ставить признание надо не поголовно, а в тех стендах, чей исход держится на стенном времени: ожидание события, срок подпроцесса, счёт запросов в окне.

Найдено при разливе очереди по DK-1218.

У go-стендов признание ставит хелпер `wallClock` из `tools/dashboard/tasks_test.go`. Он печатает `loadfail.Mark` через `t.Log`, и go test показывает строку у провалившегося теста. У python такого хелпера нет. Прямой перенос приёма не работает. `loadfail.Fails` делит вывод на блоки по головам `FAIL: ` и `ERROR: `. Печать стенда в stdout идёт до итогового блока unittest и в блок не попадает. Признание обязано ехать текстом падения.

## Чего хотим

Стенды со стенным замером признаются так же, как браузерные стенды дашборда. Очередь слияний ставит их красноту в хвост и повторяет ветку следующим заходом. Признание кладёт общий python-хелпер. Он дописывает строку `loadfail.Mark` в текст падения теста. Сама строка держится вровень с go-константой, и сверяет её тест по `internal/loadfail/loadfail.go`.

## DoD

- Общий python-хелпер признания лежит в одном месте на все стенды, откуда его видно и `hooks`, и `kit/skills`. Тест хелпера падает на старом коде. Искусственный тест со сроком валится, а строки `loadfail.Mark` в блоке его провала нет.
- Строка признания у python совпадает с константой `loadfail.Mark`. Совпадение держит тест, который читает `internal/loadfail/loadfail.go` и сверяет литерал. Разъехавшиеся строки его валят.
- `shipctl` считает красноту python-компонента с признанием чужой. Кейс в `tools/shipctl/testlog_test.go` несёт блок провала unittest с головой `FAIL: test_...` и признанием в тексте `AssertionError`, и вердикт по нему `load: true`. Тот же блок без признания даёт `false`.
- Признание стоит в тех стендах, чей исход держится на стенном времени. Перечень собран грепом по часам, срокам подпроцесса и ожиданию события. В него входят `kit/skills/board-task/task_run_test.py` и `kit/skills/goal-loop/goal_run_test.py`, где ожидание события и срок подпроцесса стоят прямо в тестах. Стенд, который судит по факту, остаётся без признания.
- Снаружи видно журналом прогона. После выката `shipctl test --json` печатает по такой красноте поля `"load": true` и `"loaded"` с именем python-теста. Очередь слияний ставит ветку в хвост с повтором и идёт дальше по составу.
