# DK-124: Рубеж следов бьёт по ключу тикета: коммит по конвенции компании не проходит

Найдено живым прогоном DoD цели [DK-111](DK-111.md) на подключённом
корп-стенде, когда вся серия DK-081..DK-087 уже была на проде.

## Симптом

В корп-клоне не проходит ни один коммит по конвенции компании. Рубеж следов
devkit (DK-086) видит в сообщении локальный ID доски и валит коммит:

```text
следы devkit в коммите корп-репозитория:
.../COMMIT_EDITMSG:1:[локальный ID доски] AC-001 правка логина
осознанный обход: git commit --no-verify
```

Обход есть, но он снимает и все остальные проверки разом, включая тот самый
рубеж следов, ради которого контур и строился.

## Разбор корня

Узел в самом дизайне [DK-074](../lld/DK-074-corp-contour.md), и видно его
только на живом прогоне.

Раздел «Граница доски и тикета» требует двух вещей сразу. Subject корп-коммита
несёт ключ тикета по конвенции компании, и «домашнее правило про ID задачи в
subject в корп-контуре исполняет ключ тикета». При этом локальный ID доски в
корп-артефакты не попадает никогда, это и держит рубеж следов из раздела
«Хуки».

Оба требования сходятся, только пока префикс боковой доски отличается от ключа
проекта в трекере. А `shipctl start` строит ветку подстановкой `{key}` из ID
зеркальной строки (это выяснилось ревью DK-087), и ветка тогда получается по
локальному ID, а не по ключу тикета, то есть «ветка по ключу тикета» из
дизайна не работает. Сделать префикс доски равным ключу проекта (`AC`) ветку
чинит, но тогда ключ тикета и локальный ID это одна и та же строка, и рубеж
следов начинает бить по каждому нормальному коммиту.

Развилки для решения:

1. Рубеж учит отличать ключ тикета от локального ID: ключ проекта известен из
   привязки (`key`), и совпадение с ним не след, а конвенция. Тогда префикс
   доски равен ключу проекта, ветка и коммиты честные, а рубеж стережёт
   остальное (путь боковой директории, слова контура).
2. Префикс доски и ключ тикета разводятся навсегда, а `shipctl start` берёт
   ключ тикета из ссылки зеркальной строки, а не из её ID.
3. Рубеж перестаёт смотреть в сообщение коммита и стережёт только дифф, а
   сообщение остаётся на человеке. Дешевле всех и слабее всех.

Выбор решения меняет и `RULES.board.md`, и `trackctl`, и `shipctl`, поэтому
задача идёт с неопределённостью 3.

## Сценарий проверки

Агентский. Живой прогон на подключённом корп-стенде: коммит с ключом тикета в
subject обязан пройти, коммит с путём боковой директории или со словом контура
обязан упасть, ветка `shipctl start` обязана нести ключ тикета. Плюс прогон,
где префикс доски и ключ проекта различаются, чтобы решение не держалось на
их совпадении.
