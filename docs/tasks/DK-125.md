# DK-125: Инструкция подключения проекта: два сценария, обычный и корп, без раскладки на пользователя

Найдено вопросом пользователя сразу после закрытия цели
[DK-111](archive/2026/DK-111.md): как выглядят шаги развёртывания devkit для корп-репозитория
и описаны ли они. Оказалось, что описаны, но по кускам трёх README, а цельной
короткой инструкции нет ни для корп-проекта, ни для обычного.

## Что не так

`devkitctl corp` делает свою часть и молчит про остальное. После неё проект не
работает, пока человек не сделает пять шагов, ни разу не собранных в одном
месте:

1. контур компании `~/.devkit/tracker/<имя>.local` (адаптер, адрес, `token_env`,
   пользователь, `cost_*`, таблица `[status]`, поля `[fields_*]`), формат живёт в
   `trackctl/README.md`;
2. токен в переменную окружения, названную в `token_env`;
3. ключи привязки `contour`, `key`, `branch` в `.devkit/tracker.local`:
   подключение кладёт туда только `repo` и остальное оставляет человеку;
4. личный приватный remote боковой директории, без него обрыв машины теряет
   доску;
5. проверка `devkitctl doctor` и `trackctl status`.

Список ручных шагов в README это ровно то, что `RULES.md` называет
перекладыванием раскладки на пользователя.

Отдельная ловушка в первом же шаге: префикс доски надо брать отличным от ключа
проекта в трекере, иначе рубеж следов не отличает локальный ID от ключа тикета
и правило про ID снимает (DK-124). Сказано это в `trackctl/README.md`, а
`--prefix` пользователь выбирает раньше, чем доходит до того файла, и пример в
корневом `README.md` про это молчит.

У обычного проекта своя версия той же дыры: `new` описан абзацем, а что делать
дальше (доска, выкат, тесты, харнесы), собрано по соседним разделам.

## Что делать

Короткая инструкция подключения на два сценария, обычный и корп, одним местом.
Место выбрать самому: годится раздел корневого `README.md` либо отдельный файл
рядом, но ссылки из `devkitctl/README.md` и `trackctl/README.md` обязаны вести
в него, а не пересказывать шаги заново. Инструкция короткая: последовательность
команд с одной строкой пояснения на шаг, разбор остаётся в README утилит.

Ручных шагов при этом должно стать меньше, иначе короткой инструкции не
выйдет. Минимум:

- `corp` заканчивает печатью того, что осталось сделать человеку, с путями
  файлов и именами ключей, а не молчит;
- `corp` предупреждает, когда `--prefix` совпадает с ключом проекта в привязке
  (если та уже есть), и называет последствие;
- то, что подключение может спросить или вывести само, оно спрашивает или
  выводит: решать, какие ключи привязки писать за человека, а какие оставить,
  исполнителю, но молчаливых пустых мест остаться не должно.

Найденное про `new` починить тем же заходом, если это не разносит задачу: у
обычного сценария шагов меньше и они проще.

## Сценарий проверки

Агентский. На чистом временном окружении пройти инструкцию буквально, слово в
слово, двумя прогонами: обычный проект и корп-проект. Считается пройденным,
когда по одной инструкции, без чтения других файлов, получается работающий
проект: у обычного доска и `shipctl start`, у корп-проекта доска в боковой
директории, `trackctl status` без находок и `shipctl start` с веткой по ключу
тикета. Вывод обоих прогонов вкладывается в файл задачи.

Прогон общего тест-набора из `.devkit/deploy.local` (ключ `test`) с кодом 0.

## Прогон инструкции

Оба сценария CONNECT.md пройдены слово в слово на чистом временном окружении
(свой HOME, свой ~/go/bin) и с нуля: ничего, кроме самого devkit и имитации
чужой инфраструктуры, заранее не разложено, каждая команда лога это шаг
инструкции. Подстановка одна: вместо клона devkit с github раскладывается
рабочее дерево ветки, иначе прогон шёл бы по старому коду. В корп-прогоне
корп-репозиторий компании и личный приватный remote доски это голые
репозитории рядом.

## Ревью

- CONNECT.md, раздел «Обычный проект»: инструкция не воспроизводится буквально на чистой машине. Первая команда «python3 ~/projects/devkit/devkitctl/devkitctl.py new -C ~/projects/myproj --prefix MP» падает необработанным traceback (FileNotFoundError на AGENTS.md), потому что ~/projects/myproj ещё не существует, а шага mkdir нигде нет. После ручного mkdir команда new проходит, но без git init каталог остаётся не git-репозиторием: git-хуки не подключаются («не git-репозиторий, git-хуки не подключались» вместо обещанного «подключает git-хуки»), а следующий по инструкции shipctl start MP-001 падает с «fatal: not a git repository». Сценарий corp этой дыры не имеет, там git clone сам создаёт репозиторий; у обычного сценария аналогичного шага (mkdir + git init, либо это же за исполнителя должна сделать new, как corp сама заводит боковую директорию) не хватает. Проверено прогоном на чистом HOME/GOPATH: без git init воспроизводится оба отказа.: исправлено, new заводит директорию, git-репозиторий и первый коммит сама; порог истории в check-commit снял ловушку с первого docs(tasks) коммита доски; оба прогона инструкции повторены с нуля
- devkitctl/devkitctl.py, new(): первый коммит («chore: подключение devkit») делается только когда started непусто, то есть только если new сама завела директорию или git init (условие «started and rev-parse --verify HEAD != 0» на строке ~1021). Если каталог уже существовал как git-репозиторий с нулём коммитов (например, кто-то заранее сделал git init myproj по старой привычке, до всех шагов CONNECT.md), started остаётся пустым, и коммит не делается, хотя HEAD всё так же неродившийся. new в этом случае как ни в чём не бывало пишет «git-хуки: core.hooksPath = ...» и не предупреждает, а следующий по инструкции taskctl add / shipctl start падает с тем же «не нашёл ветку main или master», что и до правки. Проверено прогоном: mkdir + git init (без коммитов) + new -C ... --prefix PE проходит с кодом 0, дальше shipctl start PE-001 падает. Комментарий у кода описывает мотив шире того, что реализовано (свежий репозиторий стоит на неродившейся ветке, это про HEAD, а не про то, кто именно завёл директорию), поджидать HEAD надо независимо от started. Заодно ни один тест в devkitctl/test.sh не доводит проверку до реального shipctl start после new: добавленный тест смотрит только AGENTS.md/.git/hooksPath, а сама заявленная цель правки (shipctl start больше не падает) прогоном не подтверждена.: исправлено, первый коммит теперь спрашивает HEAD, а не то, кто завёл репозиторий; тест доводит проверку до настоящего shipctl start после new на обоих входах, мутацией старое условие краснеет
