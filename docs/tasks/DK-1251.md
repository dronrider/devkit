# DK-1251: Отставший тег deployed роняет слияние на второй машине

## Что происходит

Слияние DK-1243 шло в другом клоне. Там тег deployed передвинут на 644b5a2f2 и отправлен в origin. В этом чекауте main обновлён через git pull. Перемещённый тег при pull не обновляется, и локальный deployed остался на ca18b3c61 от 29 сентября. В результате shipctl status выводит аномалию «код в окне выката, а задача не в In progress». shipctl smoke завершается с ошибкой «нет непроверенного выката», а taskctl closable требует отметку smoke. Починено вручную командой git fetch origin +refs/tags/deployed:refs/tags/deployed. Тег стоит подтягивать в devkitctl catchup или перед сверкой окна выката в shipctl.

Дополнение от 2026-10-23. Пользователь сообщил, что работа на его машине остановила задачу коллеги на другом компьютере. Сообщение агента коллеги:

> Слияние остановлено воротами DK-1001: ее код находится в окне выката при статусе Check. DK-1413 остается в In progress, в очереди слияний.

При разборе проверены tools/shipctl/ops.go, функции trainTasks, freshMain и pushTag. Окно выката вычисляется по локальному deployed..main. Тег после выката отправляется через git push -f origin deployed. В freshMain выполняется git fetch origin main без принудительного обновления существующего тега.

Поведение воспроизведено на временном bare origin и двух клонах. В первом клоне создан коммит с ID DK-1001, main и передвинутый deployed отправлены в origin. Во втором выполнены git fetch origin main и fast-forward main. В результате main совпадает с первым клоном, deployed остаётся старым, а уже выкаченный коммит попадает в deployed..main. Это воспроизведение механизма расхождения средствами Git; полный сценарий shipctl с двумя клонами ещё нужен.

Тег и журнал машины коллеги не проверены. Устаревший deployed объясняет сообщение, но причина конкретного инцидента пока не подтверждена сравнением с origin. На момент разбора в текущем клоне DK-1001 уже в архиве, её коммитов в deployed..main нет.

Из-за старого тега уже выкаченная задача в Check считается кодом предстоящего выката. В trainTasks она попадает в список strays, после чего слияние другой задачи завершается ошибкой. По сообщению пользователя, так остановилась DK-1413 на машине коллеги. Независимая работа команды зависит от состояния выката на другом компьютере.

## Чего хотим

Пользователь ожидает, что задачи на разных компьютерах смогут проходить командный конвейер независимо. Завершённый выкат и статус Check одной задачи не должны останавливать слияние другой из-за устаревшей локальной точки выката. Ограничения для действительно общей среды должны оставаться согласованными между машинами.

## Границы

- Одновременные выкаты с двух машин и общий замок выката за рамками. DK-306 оставил их сознательно, тема уходит отдельным черновиком накопителя.
- Отсутствие тега deployed целиком это открытая строка DK-077. Соседний край той же функции, правкой не закрывается и молча не поглощается.
- Правила выката в RULES.board.md не меняются. При честном теге чужой Check без smoke держит только ship, а merge идёт дальше.
- Семантика тега остаётся по решению 7 LLD DK-1325. Один общий тег как точка правды о содержимом прода, второй тег про установку на машину не заводится.
- Условий, посильных только человеку, не нашёл. Доступы не нужны, стенд с временным origin и двумя клонами гонится на машине агента.

## DoD

- Слияние на второй машине проходит, когда чужой выкат уже в origin. Окно deployed..main не захватывает выкаченные задачи, и strays не останавливают merge.
- shipctl status на отставшем клоне не показывает аномалию «код в окне выката, а задача не в In progress». Тег сверяется с origin при настроенном удалённике.
- При недоступной сети окно печатается по локальному тегу с видимой пометкой.
- shipctl smoke и taskctl closable не отказывают у задачи с прогнанным smoke на отставшем клоне.
- Синхронизация не двигает локальный deployed назад при непушенном выкате. Точка выката идёт только вперёд, следующий push -f не теряет свой выкат.
