# DK-1377: Мёртвая запись реестра агентов держит чужой заход сутки

## Что происходит

Сторож агентов (hooks/agent-watch.py) помечает завершение фоновой команды по
перечню работ на конце хода сессии. Команда может кончиться раньше следующего
хода. Тогда запись в ~/.devkit/agents/<sid>.json остаётся с `state=running`.
Протухшей её считают только через сутки. Таков срок FOREIGN_LIFETIME.

Правило «один заход» в оболочке конвейера читает живую запись с ID задачи
чужим заходом. Такая запись не даёт поднять голову. Проверка живёт в
task-run.py, функция foreign_entry. Из-за мёртвых записей подъём проверяющего
после выката падает. `shipctl check-run` печатает успех и ступень «новое окно».
Оболочка тут же завершается с репликой про чужой заход. Очередь выката стоит, пока
записи не сойдут вручную или по суточному сроку.

## Чего хотим

Записи реестра сходятся со списком живых процессов. Запись команды без
процесса сходит в done либо lost при следующем обходе сторожа. Либо её не
считает живой сама проверка foreign_entry. Признак тот же, что у брошенного
замка. Мёртвый pid снимает запись. Живой субагент или команда по-прежнему
держит строку за одним заходом.

## DoD

- Запись `running` без живого процесса не считается чужим заходом. Проверка
  сверяет запись с процессом и мёртвую снимает сама.
- Смерть сессии-носителя закрывается той же сверкой: у записи нет ни
  процесса, ни живого носителя, обход снимает её без суточного ожидания.
- Живая команда, где ID задачи попал в текст лишь аргументом grep по
  журналу, чужим заходом не считается и подъём этой задачи не глушит.
- Сценарий «команда кончилась, сессия замолчала» закрыт тестом сторожа либо
  оболочки. После обхода запись done и голова поднимается.
- Живая работа по-прежнему держит «один заход». Запись с живым процессом не
  сходит и второй головы не пускает.

## Ранг

- Серьёзность 25: проверяющий после выката молча не поднимается, очередь
  выката стоит сутки, обход есть, но он ручной.
- Ценность 6: страховка тика и автономный выкат стоят на подъёме проверяющего
  каждой агентской задачи.
- Неопределённость 2: место правки ясно (сторож либо foreign_entry), открыт
  выбор канона сверки записи с процессом.
- Поправка на баг 5: правило DK-1317 вышло с дырой в сходе записей.
- Рычаг 2: ускорение своего конвейера, соседние проекты не задеты.

## Из черновика DK-1462 «мёртвая сессия держит чужой заход, конвейер строку не поднимает» (записан 2026-10-25)

### Черновик

#### Ситуация

XR-309: агент exec-high «разработка utun-клиента macOS» записан в реестре
сессии 2b6ef7bb в состоянии running с 24.10.2026. Сессия-носитель умерла,
панель мертва, три подъёма подряд не удержались: окно поднимается, оболочка
замок за 30 секунд не принимает, окно снимается. Запись отжали руками
25.10.2026.

#### Осложнение

Конвейер не поднимает строку с чужим заходом, это защита от подъёма поверх
живой работы. Реестр не узнаёт о смерти сессии-носителя, запись running
переживает и панель, и окно. Класс тот же, что у затора DK-1454: запись
говорит «жива», реальность говорит «мертва», только теперь это реестр
агентов, а не замок задачи.

В тот же вечер второй экземпляр: фоновый монитор чужой сессии закончил
поток, а его запись осталась running. Хуже того, защита матчит чужой заход
по тексту команды, и живой монитор, который просто grep-ает ID задачи в
журнале, глушит подъём этой задачи.

#### Вопрос

Кто и когда отжимает записи закончившихся и осиротевших агентов: хук
агент-сторожа, тик сторожа или сам подъём при отказе?

#### Гипотеза

Смерть носителя видна снаружи, реестр чатов и tmux отвечают живостью. Тик
сторожа может сверять записи running с носителем и отжимать мёртвые с
потолком попыток, как это делает дежурный.

### Контекст обсуждения

Пользователь спросил 25.10.2026, откуда 402 у XR-309, баланс GLM в порядке.
402 оказался чужим: его вернул роутер routerai у проверки XR-310. У XR-309
вскрылся этот класс, запись реестра закрыли руками по решению пользователя.
