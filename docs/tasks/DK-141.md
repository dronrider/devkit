# DK-141: раннер тестов devkitctl на python вместо devkitctl/test.sh

Задача цели [DK-135](DK-135.md). Правило языка принято в
[DK-139](archive/2026/DK-139.md): `tools/devkitctl/test.sh` (2616 строк) правило
относит к сложному, и на sh ему места нет.

## Задача

Переписать раннер `tools/devkitctl/test.sh` на python по правилу «Раскладка»
`README.md`: тест лежит рядом со своим кодом файлом `<модуль>_test.py`, прогон
`python3 -m unittest discover -p '*_test.py'` из директории инструмента,
внешних зависимостей нет (стандартная библиотека, `unittest`). Образец рядом:
`hooks/hookio_test.py` и `hooks/notify_test.py`.

Требование DK-139 к обеим задачам про раннеры: python-тесты обязаны покрывать
то же, что покрывал sh. Показывается это перечнем, а не на глаз. Сначала снять
список проверок раннера (он читается по именам функций и веткам `case`), после
переписывания сверить один к одному, расхождение объяснить в файле задачи.

Раскладка по файлам идёт за кодом: `devkitctl.py`, `rules.py`, `harness.py`,
`weigh.py`, `perms.py`, `context.py`, `corp.py` берут каждый свой
`<модуль>_test.py`. Проверка, которая гоняет CLI целиком и к одному модулю не
привязана, кладётся туда, чей код она проверяет по существу.

Точки, которые звали старый раннер, правятся тем же коммитом: `.github/
workflows/ci.yml`, перечень локальных прогонов в конце `README.md`, команды
внутри `kit/skills/live-core/SKILL.md` и `kit/skills/test-standard/SKILL.md`.
Гитигнорнутый `.devkit/deploy.local` правит диспетчер, туда не лезть.

## Сценарий проверки

Агентский.

1. Перечень проверок sh-раннера и перечень python-тестов сходятся один к
   одному, расхождение объяснено в «Ходе работы».
2. `python3 -m unittest discover -p '*_test.py'` из директории инструмента
   зелёный, sh-раннера в дереве больше нет.
3. Остальные прогоны CI зелёные: шесть `go test ./...`, оставшиеся sh-прогоны,
   `check-exec-bit.py`, `check-symbols.py`.
4. Перечень локальных прогонов в конце `README.md` называет новую команду, а не
   мёртвый `sh .../test.sh`.
