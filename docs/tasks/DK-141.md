# DK-141: раннер тестов devkitctl на python вместо devkitctl/test.sh

Задача цели [DK-135](DK-135.md). Правило языка принято в
[DK-139](archive/2026/DK-139.md): `tools/devkitctl/test.sh` (2616 строк) правило
относит к сложному, и на sh ему места нет.

## Задача

Переписать раннер `tools/devkitctl/test.sh` на python по правилу «Раскладка»
`README.md`: тест лежит рядом со своим кодом файлом `<модуль>_test.py`, прогон
`python3 -m unittest discover -p '*_test.py'` из директории инструмента,
внешних зависимостей нет (стандартная библиотека, `unittest`). Образец рядом:
`hooks/hookio_test.py` и `hooks/notify_test.py`.

Требование DK-139 к обеим задачам про раннеры: python-тесты обязаны покрывать
то же, что покрывал sh. Показывается это перечнем, а не на глаз. Сначала снять
список проверок раннера (он читается по именам функций и веткам `case`), после
переписывания сверить один к одному, расхождение объяснить в файле задачи.

Раскладка по файлам идёт за кодом: `devkitctl.py`, `rules.py`, `harness.py`,
`weigh.py`, `perms.py`, `context.py`, `corp.py` берут каждый свой
`<модуль>_test.py`. Проверка, которая гоняет CLI целиком и к одному модулю не
привязана, кладётся туда, чей код она проверяет по существу.

Точки, которые звали старый раннер, правятся тем же коммитом: `.github/
workflows/ci.yml`, перечень локальных прогонов в конце `README.md`, команды
внутри `kit/skills/live-core/SKILL.md` и `kit/skills/test-standard/SKILL.md`.
Гитигнорнутый `.devkit/deploy.local` правит диспетчер, туда не лезть.

## Сценарий проверки

Агентский.

1. Перечень проверок sh-раннера и перечень python-тестов сходятся один к
   одному, расхождение объяснено в «Ходе работы».
2. `python3 -m unittest discover -p '*_test.py'` из директории инструмента
   зелёный, sh-раннера в дереве больше нет.
3. Остальные прогоны CI зелёные: шесть `go test ./...`, оставшиеся sh-прогоны,
   `check-exec-bit.py`, `check-symbols.py`.
4. Перечень локальных прогонов в конце `README.md` называет новую команду, а не
   мёртвый `sh .../test.sh`.

Расхождение счёта (176 проверок против 162 тестов) не про покрытие: границы
блока в sh и метода в python не совпадают. Крупные блоки перечня разошлись на
несколько тестов (проверка 3 про `new` это три метода, проверка 28 про глубину
шесть), а несколько соседних шагов одной цепочки, наоборот, легли в один метод
там, где разделять их значило бы гонять раскладку дважды (проверки 55-56 про
`autonomous`, 85-88 про форматы момента снятия, 89-90 про переезд снимка).
Каждая проверка перечня названа в докстринге или в комментарии своего теста
теми же словами, что и в sh.

Что изменилось по существу:

- Фикстурные блоки sh (21 штука, в перечень они не шли) стали кодом
  `testenv.py` и `setUpClass`: копия devkit, подставные HOME и PATH, заглушки
  бинарей, генерация глобальной точки правил.
- Заглушки, которые sh писал на `sh` (подложный `claude`, `go`, `taskctl`),
  переписаны на python: раннеру больше не нужен внешний интерпретатор, а
  разбор аргументов у них тот же.
- Проверки 50-52 и 58 (`new --prefix`, болванка выката) в sh молча стояли на
  настоящем `taskctl` из PATH разработчика: без него доска не заводилась и
  находки про `deploy=` не появлялись. В python доску заводит заглушка
  `BOARD_TASKCTL`, и проверка перестала зависеть от машины.
- Проверка 2 (инструменты в PATH) в sh падала по одному вызову `fail` на
  каждый недостающий инструмент, в python это один тест на пустой список
  недостающих.
- Проверка 17 (клик по баннеру) была под `if [ "$(uname)" = Darwin ]`, стала
  `skipUnless`.
- `fail` в sh считал провал и шёл дальше, а метод unittest на первом же
  разошедшемся ожидании обрывается. Там, где шаги стоят друг на друге
  (вклейка, обвязка выката, машинный контур, корп-контур), порядок закреплён
  номером в имени метода, и обрыв цепочки виден по первому упавшему тесту, а
  не тонет в двадцати последующих.

Спорным осталось одно: перечень `hooks/check-exec-bit.py` и `hooks/README.md`
показывают прогон `tools/devkitctl/test.sh` как пример команды из доклада, и
после этой задачи пример указывает на файл, которого нет. Правка лежит в
`hooks/**`, а он за DK-142 и DK-143, поэтому тут не тронут.
