# DK-1425: gitrun перекрывает core.sshCommand репозитория и роняет пуш доски

## Что происходит

Переменная GIT_SSH_COMMAND=ssh -o BatchMode=yes, которую собирает internal/gitrun.Env, затирает конфиг репозитория с выделенным ключом и known_hosts, и внутренние вызовы shipctl и taskctl падают в publickey, хотя ручной git push тем же конфигом проходит.

Проявилось на слиянии DK-1333 2026-10-23: три отказа fetch origin подряд, обход это передача значения core.sshCommand через переменную GIT_SSH_COMMAND при запуске утилиты. gitrun должен читать core.sshCommand репозитория и сохранять его, добавляя BatchMode. Сейчас пакет подменяет команду голым ssh и теряет выделенный ключ.

Проверено на грумминге 2026-10-24 по коду. Функция Env в internal/gitrun/gitrun.go строит GIT_SSH_COMMAND из переменной окружения либо из голого ssh (строки 64-91). Конфиг репозитория не читается вовсе. Тест gitrun_test.go на строке 56 фиксирует нынешнее поведение. Дублей на доске нет, тот же предмет записан черновиками DK-1410 и DK-1435.

## Чего хотим

## DoD

Сетевые вызовы утилит доски (пуш у taskctl, fetch и push у shipctl) проходят в репозитории с локальным core.sshCommand и отдельным known_hosts. Ручной экспорт GIT_SSH_COMMAND перед вызовом больше не нужен. Юнит-тест держит правило: gitrun берёт core.sshCommand репозитория базой, BatchMode дописывается к унаследованной команде. Переменная окружения остаётся приоритетнее конфига.

## Из черновика DK-1435 «gitrun перебивает core.sshCommand репозитория, пуш утилит доски ломается» (записан 2026-10-23)

### Черновик

#### Ситуация

Ситуация: доступ к origin настроен деплой-ключом в core.sshCommand
репозитория, обычный git ходит. Внутренний пакет gitrun при каждой сетевой
команде кладёт GIT_SSH_COMMAND=ssh -o BatchMode=yes, переменная сильнее
конфига, и подмена роняет аутентификацию: taskctl --push и fetch у shipctl
ловят publickey или host key verification, слияния встают.

Обход: экспортировать GIT_SSH_COMMAND из конфига репозитория перед вызовом
утилиты, существующую переменную gitrun не трогает.

Вопрос: должен ли gitrun уважать core.sshCommand вместо безусловной
подмены, например подставлять свой BatchMode только когда конфиг молчит.

## Из черновика DK-1410 «утилиты devkit теряют repo-local core.sshCommand и падают на fetch» (записан 2026-10-18)

### Черновик

#### Ситуация

Ситуация: доступ репозитория devkit в origin едет на отдельном ключе и отдельном known_hosts, названных локальным core.sshCommand. Обёртка gitrun утилит ставит свою переменную GIT_SSH_COMMAND и перекрывает настройку репозитория.
Осложнение: с вечера 17 октября taskctl push и shipctl fetch отказывают с «Host key verification failed», хотя тот же git из шелла проходит. Виноват не доступ, а потерянные опции ssh.
Вопрос: должна ли обёртка gitrun начинать с core.sshCommand репозитория, а не с голого ssh.
Гипотеза: gitrun читает core.sshCommand корня и подставляет её базой, наследование переменной из окружения остаётся приоритетнее.
