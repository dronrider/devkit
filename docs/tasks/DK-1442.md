# DK-1442: Конвейер поднимается поверх живого исполнителя цикла цели

## Что происходит

Ситуация. 2026-10-24 у DK-1429 исполнитель цикла цели DK-1253 (поднят
18:04, сессия glm-2) работал в дереве задачи без записи этапа разработки
в runs-файле. Тик поднял окно конвейера task-DK-1429 (18:15), то окно
подняло второго исполнителя (18:26), и оба правили одно дерево. Конвейер
не увидел чужой живой заход: проверка занятости его не признала.

Осложнение. Дубль снят остановкой младшего исполнителя без потери правок,
но тот же тик поднял окна task-DK-1428, task-DK-871 и task-DK-1438, и на
каждом коллизия повторится, пока причина жива.

Вопрос. Почему спавн исполнителя витком цели не кладёт запись этапа
в runs-файл задачи и почему конвейер не считает такую работу живой.

Гипотеза. Виток цели поднимает исполнителя мимо хука спавна, а проверка
занятости смотрит только на runs-файл и замок головы.

Грубером 26.10 гипотеза проверена наполовину грепом. goal-run.py поднимает
исполнителя через tmux без записи этапа, проверка занятости осталась на
сверку исполнителю. Правок спавна витка цели после события не приезжало.
DK-1454 трогал замок головы и оболочку, спавн не трогал.

## Чего хотим

Спавн исполнителя витком цели идёт через хук спавна, и запись этапа
разработки появляется в runs-файле задачи тем же порядком, что у конвейера.
Проверка занятости в lift.py считает такой заход живым: на задаче с
работающим исполнителем витка цели конвейер второго не поднимает.

## Границы

Правка проходит по спавну витка цели в goal-run.py и по проверке
занятости в tools/devkitctl/lift.py. Слитый DK-1454 предмет не снимает,
он ужесточил замок головы, а спавн мимо хука спавна остался. Условий,
посильных только человеку, не нашёл, обе точки в этом репозитории.

## DoD

Виток цели поднимает исполнителя с записью этапа в runs-файл задачи, тем
же порядком, что и конвейер. Проверка занятости в lift.py считает такой
заход живым. На синтетической доске с работающим исполнителем витка
конвейер отказывается поднимать второго.

## Ранг

`50+6+2+5+4 = 67`, P1.

- Серьёзность 50: два исполнителя правят одно дерево. Дубль снимается
  ручной остановкой младшего, коллизия повторяется на каждом окне тика.
- Ценность 6: конвейер перестаёт плодить дубли над работой витка цели.
- Неопределённость 2: гипотеза наполовину подтверждена грепом. Осталась
  сверка проверки занятости.
- Поправка на баг 5: сломано то, что работало.
- Рычаг 4: каждое окно тика поднимается поверх любой работы витка цели.

## Сценарий проверки

Сценарий для будущей проверки исправления. Команды идут из корня devkit,
каждая в своём временном HOME. На исходной версии оба класса красные,
доказательство снято regcheck и сохранено в «Ходе работы».

1. Живой этап исполнителя витка. Класс открывает и закрывает этап ключами
   `--work` и `--done`, отказывает чужой задаче и второму исполнителю.

```sh
case_home=$(mktemp -d) && trap 'rm -rf "$case_home"' EXIT && env HOME="$case_home" devkitctl test "$PWD/kit/skills/goal-loop" goal_run_test.WorkKeyTests
```

2. Ограда конвейера. Класс держит строку живого цикла цели, отпускает
   мёртвый pid и строку без связи с целью.

```sh
case_home=$(mktemp -d) && trap 'rm -rf "$case_home"' EXIT && env HOME="$case_home" devkitctl test "$PWD/tools/devkitctl" lift_test.GoalCycleCase
```

остаётся живым, конвейер о живом цикле сообщает строкой отчёта.
