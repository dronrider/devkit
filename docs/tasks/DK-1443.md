# DK-1443: Постановка связывает требования с архитектурой и проверками

## Что происходит

Пустой список открытых вопросов не подтверждает готовность постановки.
В пробе DK-1413 явные связи требований, работ и проверок помогали ручной
сверке; сохранность работы после реального обрыва не проверялась.
2026-10-24 пользователь потребовал выводить архитектуру из собранных FR/NFR.
Основание находится в [дизайне DK-1318](../lld/DK-1318-grooming-scenarios.md),
Решения 3, 6.1/6.2 и 7. Пользователь разрешил нарезку по этому дизайну.

Сейчас interview, board-groom, TASKFORM.md и review не дают единого договора
о составе результата и проверке связей в обе стороны. Агент может добавить
часть без требования либо покрыть функции, потеряв согласованное ограничение.

## Чего хотим

Готовая постановка содержит согласованные функциональные и нефункциональные
требования с русскими названиями, источниками и наблюдаемыми критериями.
Архитектура описывает состав, ответственность частей, связи, контракты,
данные и границы изменения. Видна связь требования с архитектурным решением,
работой и проверкой с ожидаемым исходом. У каждой части и свойства есть
обратное основание в требовании либо применимом принятом инварианте с источником.
Несколько допустимых архитектур сравниваются по покрытию и последствиям.

Неизвестное остаётся открытым. При необходимости исследование готово
к выполнению, пока зависимая реализация ждёт его результата. Малому багу
хватает локального описания текущей архитектуры. Истинность исходного требования не выводится
из заполнения формы.

работа не зависит. После W1 выполняются проверка совместимости W2,
prompt-test и обновление документации в той же задаче.

## Границы и условия

Меняются interview, board-groom, авторская часть TASKFORM.md и вопрос review
о соответствии заказанному результату. Новая машинная сущность не вводится.
DK-381 остаётся соседним черновиком про весь состав LLD, отдельный скилл,
наблюдаемость и неоднозначности; эта задача его не оформляет и не сужает.
DK-657 проверяет исходные предпосылки шире текущей сверки. DK-886 задаёт
порядок визуального эталона. Хранение дерева остаётся DK-917.

Доступны репозиторий, источники DK-1318/DK-1413 и временные постановки.
Проба не доказала сокращения переделок или реальной смены исполнителя.
Новые секреты и внешние действия для проверки не нужны; доступ к харнесу
нужен для prompt-test. При новом важном выборе вопрос возвращается человеку
по DK-1108. Нынешнее разрешение нарезки не выдаётся за будущую реализацию.

## Сценарий проверки

Приёмка агентская после доставки правил. Прогоны при подготовке карточки
не выполнялись. Перед Check исполнитель записывает команды сборки пары
раскладок по tools/obeycheck/README.md и места сохранения ответов.

1. В подключённом временном проекте взять полный пример из Решения 7
   и провести постановку установленным interview/board-groom. В результате
   обе цепочки Ф-1/НФ-1 полны, у каждой части есть источник; lint проходит.
2. В двух независимых копиях добавить gateway с аутентификацией без источника
   и убрать архитектурное покрытие либо проверку НФ-1. Ожидание: названы
   конкретные лишняя ответственность и отсутствующая связь; готовность
   зависимой реализации не объявлена, новое требование ради gateway не выдумано.
3. Подать малый баг и исследование неизвестного контракта. Ожидание: баг
   получает краткую локальную архитектуру; исследование получает выход
   и остановку, зависимая реализация остаётся ожидающей результата.
4. Запустить obeycheck по предметам изменённых нормативных файлов
   на раскладках поставленной и прежней версии. Сохранить входы, ответы,
   вердикты V1/V2 и соответствующую ревизию; review проверяет тот же договор.
