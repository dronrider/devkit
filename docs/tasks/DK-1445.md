# DK-1445: Выбор отдельных сценариев работает в текстовом чате

## Что происходит

[Дизайн DK-1318](../lld/DK-1318-grooming-scenarios.md), Решения 1, 3, 4 и 5,
задаёт один список сценариев с устойчивыми ID и переход старых составов.
2026-10-24 пользователь разрешил нарезку по дополненному дизайну.
Текущий internal/taskform.Lineup хранит Width и []string и перенумеровывает
состав. Fork.Choices включает Hint первым вариантом. decideAnswer разбирает
только нерешённые развилки, --open скрывает решённые; снимка раскладки нет.

Одной замены парсера недостаточно. Нужны создание и чтение нового списка,
выбор нескольких сценариев, пересмотр ответа, продолжение и защита от ответа
на изменённый блок. Старые решения должны сохранить смысл.

## Чего хотим

В текстовом чате пользователь видит карточки с источниками и один список,
меняет отдельные пункты и сохраняет выбранное устойчивыми ID. Рекомендация
набора находится в голове вопроса и не становится ещё одним вариантом. Разбираются
несколько позиций/ID, «плюс» и «минус» по опубликованному договору.
При повторном ответе сохраняются история и новый выбор. После перерыва
видны выбранное, открытые вопросы и зависимые решения для сверки.
Устаревший блок не применяется молча. Прямо заданный состав повторно
не спрашивается; агентская рекомендация согласием не считается.

### Как записывается новый список

Выбран отдельный режим существующей развилки. Он задаётся подстрокой
`выбор: сценарии/1`. Каждый сценарий остаётся строкой `вариант`, а
рекомендация содержит набор ID и довод. Подстроки `кейс`, отдельной базы
и дерева здесь нет. В одной записи допускается один такой список.

```markdown
- «сценарии»: какие сценарии включаем?
  - решает: человек
  - выбор: сценарии/1
  - следующий ID: СЦ-4
  - рекомендация: СЦ-1, СЦ-3: нужны отдельный выбор и продолжение
  - вариант: СЦ-1 (слово пользователя): выбрать отдельные сценарии
  - вариант: СЦ-2 (вывод из примера): собрать пример из сырой идеи
  - вариант: СЦ-3 (предложение агента): продолжить после перерыва
```

`СЦ-N` содержит положительное десятичное число без ведущих нулей. ID уникален
внутри записи. Происхождение принимает три значения из Решения 1 LLD.
Название после `):` непустое, остальной текст названия свободный.
`следующий ID` хранит следующий свободный номер и только увеличивается.
Удаление строки и перестановка не меняют этот номер. Если допустимый
следующий номер выдать уже нельзя, команда отказывает до записи. При создании он равен
максимальному ID плюс один. Добавленный пользователем сценарий получает этот
ID, происхождение «слово пользователя» и собственный текст без пересказа.

У нового режима `Choices` возвращает только строки сценариев. `Hint`
остаётся рекомендацией и разбирается как `<ID через запятую>: <довод>`.
Каждый рекомендованный ID должен присутствовать в списке. Обычные развилки
и старые составы продолжают получать рекомендацию первым вариантом.

Карточки хранятся обычным авторским текстом записи и предшествуют блоку
выбора. У нового режима один раздел
`## Пользовательские сценарии`, внутри него по заголовку `### СЦ-N` и
тексту карточки. Утилита выделяет тело карточки по заголовку, наличие полей
перед снимком проверяется по уточнению W1-3. Их содержание проверяет агент.
Снимок включает этот текст целиком. При ответе «плюс свой сценарий» сначала
сохраняются слова и выбор человека; агент дополняет карточку следующим ходом.
Новое условие, меняющее смысл выбора, возвращается на сверку по LLD.

### Уточнение полноты карточек W1-3

Ревизия W1-3 от 2026-10-28 уточняет подготовку снимка после первого ревью.
Выбранный человеком пустой исход A сохраняется. У каждой карточки `### СЦ-N`
внутри раздела «Пользовательские сценарии» обязательны непустые поля
`Ситуация:`, `Действие:`, `Результат:`, `Польза:`, `Рекомендация:`,
`Ограничение:` и `Источник:`. Название поля начинается с отдельной строки,
значение идёт после двоеточия. Регистр букв подписи не влияет на разбор.
Содержание и довод по-прежнему проверяет агент.

Карточка заканчивается следующим заголовком Markdown. Заголовки и подписи
внутри ограждённого примера кодом карточку не дополняют. Поле другого
сценария, чужого раздела или текст вне карточки пропущенное поле не заменяет.
До `--chat` нового режима и до переноса `--given` готовы карточки всех ID
списка. Утилита отказывает с недостающим ID или полем раньше сохранения
снимка, записи решения и изменения ожидания. Открытый список допускает
подготовку без карточек; обычное чтение и старые развилки нового рубежа
не получают. Сохранённый снимок включает подготовленные карточки целиком.

Ответ «плюс свой сценарий» сначала сохраняет исходные слова человека,
выбор и выданный ID. Будущая карточка этого ID до ответа не требуется.
Перед следующим показом агент дополняет её теми же подписанными полями.
Повторная доставка принятой пары сохраняет прежний результат и этот порядок.

### Как создаётся и читается список

Будущий ключ `--scenarios` включает новую форму при создании. `--option`
принимает полную строку с ID и происхождением; утилита проверяет уникальность
и записывает следующий ID. Карточки оформлены до `--chat` или `--given`;
создание открытого подготовительного списка этого ещё не требует.

```sh
taskctl decide DK-1445 --ask «сценарии» --scenarios --hint 'СЦ-1, СЦ-3: нужны отдельный выбор и продолжение' --option 'СЦ-1 (слово пользователя): выбрать отдельные сценарии' --option 'СЦ-2 (вывод из примера): собрать пример из сырой идеи' --option 'СЦ-3 (предложение агента): продолжить после перерыва' 'какие сценарии включаем?'
taskctl decide DK-1445 «сценарии»
taskctl decide DK-1445 «сценарии» --chat
```

Именованное чтение выводит одну развилку. Именованный `--chat` позволяет
показать и решённый список для пересмотра. Без имени сохраняются нынешняя
пачка открытых вопросов и предел в четыре вопроса. Блок нового режима имеет
такую форму; `sc1-<hash>` обозначает реальный ключ снимка из вывода.

```text
снимок сценариев: sc1-<hash>
«сценарии»: какие сценарии включаем? рекомендую 1, 3: нужны отдельный выбор и продолжение
1. СЦ-1. выбрать отдельные сценарии
2. СЦ-2. собрать пример из сырой идеи
3. СЦ-3. продолжить после перерыва

ответ строкой: «сценарии 1, 3», «минус 2», «плюс <свой сценарий>», своими словами или «по рекомендации»
```

Перед ним выводятся карточки с происхождением. При повторном выборе в голове
также виден текущий состав ID. Рекомендация и текущий выбор показаны отдельно.
Печать блока сама по себе согласием не становится.

### Что связывает блок с ответом

Новый `--chat` сохраняет снимок под той же головой в Markdown. Подстрока
имеет вид `снимок: sc1-<sha256> <JSON одной строкой>`. JSON содержит версию 1,
ID записи, имя и вопрос развилки, упорядоченные ID, названия и происхождение,
рекомендованный набор с доводом, текст карточек и текущий выбор до ответа.
Поле `choiceEvent` содержит номер последнего события выбора в истории этой
развилки. До первого события оно равно 0. Событием служит каждая строка `решено`
новой формы либо `пересмотр человеком`, включая ответ с тем же набором и
перенос через `--given`. Номер считается по порядку таких строк с единицы;
история сохраняется целиком. Поэтому после выбора A -> B -> A прежний ключ
не восстанавливается. Ключ считается по всем этим данным; полное значение
SHA-256 хранится и передаётся.
Даты вывода, журнал работы, решения посторонних вопросов и сами строки
снимков в него не входят. Повторная печать неизменного состояния использует
тот же снимок. Старые снимки сохраняются и доступны именованному чтению
с будущим ключом `--snapshot <ключ>`.

Ответ нового режима требует `--snapshot`, в том числе при выборе по ID.
Агент берёт ключ того блока, на который отвечает человек. Подставлять
последний ключ вместо неизвестного запрещено. При неоднозначной ссылке
сначала сверяется блок. Будущий UI передаст тот же ключ вместе с ответом.

```sh
taskctl decide DK-1445 «сценарии» --snapshot 'sc1-<hash>' --answer 'сценарии 1, 3'
taskctl decide DK-1445 «сценарии» --snapshot 'sc1-<hash>'
```

Сначала проверяются наличие снимка, его принадлежность записи и развилке
и целостность. Затем в истории ищется пара из ключа снимка и точного текста
ответа, включая пробелы и пунктуацию. Если найденное событие остаётся
последним событием выбора, команда возвращает сохранённый результат применения.
Файл, следующий ID и признак ожидания не меняются. Это повторная доставка ответа;
она распознаётся раньше обычной проверки устаревания, даже если после ответа
агент дополнил карточку. Если после найденного события появился другой выбор
или пересмотр, повторная доставка даёт устаревание. Возврат к тому же набору
после другого решения прежнюю пару не оживляет.

У новой пары снимок сравнивается с текущим состоянием. Изменение порядка,
состава, названия, происхождения, карточки, рекомендации, текущего выбора
либо `choiceEvent` делает его устаревшим. Срока по часам нет, перерыв сам
по себе ключ не меняет. Подмена JSON при сохранённом ключе даёт ошибку.

При устаревании команда печатает ключ, прежние и нынешние позиции с ID,
какая часть изменилась, и команду повторной печати. Выбор, история ответа
и признак ожидания остаются прежними. Если изменились только карточки или
довод, команда печатает это отдельно. Одинаковые списки не выдаются за разные.
Сверку ведёт агент по обоим состояниям до нового применения.
Номер вне снимка и неизвестный ID дают конкретную ошибку без записи.

Снимок хранится в существующем файле, читается новым процессом и не зависит
от признака ожидания `.ask`. У обычных вопросов печать остаётся чтением.
История снимков растёт вместе с историей решений; очистка в эту задачу не
входит. Конкурентное редактирование одного файла несколькими писателями
не поддерживается нынешним `os.WriteFile` в `runDecide`. W2 должна хотя бы
перечитать исходный файл перед записью и отказаться при изменении; полноценная
сериализация произвольных ручных правок остаётся ограничением.

### Как применяется ответ и сохраняется история

Полный перечень после имени «сценарии» заменяет выбор. В нём допустимы
позиции снимка или ID, например `сценарии 1, 3` и `сценарии СЦ-1, СЦ-3`.
Дубликаты убираются, в решении ID записываются по возрастанию числовой части.
Изменение порядка строк не меняет сохранённый смысл.

«Минус» снимает известный пункт, «плюс» с номером или ID включает известный.
«Плюс» с текстом создаёт сценарий и включает его. Правки применяются к явно
названному в той же строке полному набору, иначе к текущему выбору. До первого
ответа основой служит показанный рекомендованный набор, как у старой правки
состава; это правило печатается в подсказке блока. Человеческая команда
правки считается ответом. Сам показ рекомендации ответом не считается.

```sh
taskctl decide DK-1445 «сценарии» --snapshot 'sc1-<свежий hash>' --answer 'минус СЦ-3, плюс СЦ-2'
taskctl decide DK-1445 «сценарии» --snapshot 'sc1-<свежий hash>' --answer 'плюс "увидеть причину отказа, затем исправить ввод"'
```

После второго примера добавится СЦ-4, соседние ID сохранятся, следующий ID
станет СЦ-5. Разделители частей ответа остаются запятой и точкой с запятой.
В новом режиме текст своего сценария разрешено взять в двойные кавычки;
внутри них разделители сохраняются. Экранирование допускает только `\"` и `\\`.
Другие последовательности с обратным слешем дают отказ до записи.
Слова человека сохраняются в отдельной подстроке `ответ: <JSON>`. Поля
`text` и `snapshot` содержат точный текст и ключ, `event` ссылается на номер
записанного события выбора, `result` хранит текст результата применения
с выбранными и добавленными ID либо исходом пересмотра. Эта подстрока стоит
сразу после соответствующей строки `решено` или `пересмотр человеком` и
сохраняется одной записью с ней. Пробелы и пунктуация в `text` сохраняются
дословно. При повторной доставке возвращается `result`. Повтор того же
«плюс своего сценария» возвращает выданный СЦ-4, новый ID не выдаётся.
Обычные вопросы продолжают разбираться нынешним путём.

Результат непустого выбора записывается стандартной строкой
`решено человеком <дата>: СЦ-1, СЦ-3`. Новый ответ по свежему снимку
дописывает такую же строку под той же головой, старое решение остаётся
в файле. Повторная доставка прежней пары новой строки не добавляет.
Если набор не меняется, выбранные ID остаются теми же. Все изменения одного
ответа, включая выдачу нового ID, сохраняются вместе после полной проверки.
Ошибка номера или снимка не оставляет половины ответа. Неразобранные слова
возвращаются агенту; при них новый список автоматически не закрывается,
«по рекомендации» к нему не применяется. Именованное `--by человек` для
нового режима проходит ту же проверку набора и снимка.

Прямо заданный состав переносится с исходными словами пользователя и
соответствием ID без повторного вопроса. Для этого нужен отдельный будущий
путь `--given` при создании списка. Он принимает перечень ID и основание
`--said '<дословный ответ или ссылка на решение>'`, записывает человеческий
выбор без печати вопроса и парковки. Агентское предложение для этого ключа
основанием не считается. Старый решённый состав автоматически не мигрирует.
При новом разговоре агент переносит его смысл с явным соответствием ID.

### Что видно при продолжении

`taskctl decide DK-1445 --open` показывает текущий выбор сценариев отдельным
блоком, затем открытые вопросы. У решённого обычного вопроса поведение
`--open` остаётся прежним. Для новой формы видны выбранные ID, актуальный
список, открытый остаток и напоминание о сверке зависимых решений после
изменения выбора. Именованное чтение показывает историю ответов и снимков.

W2 не выводит дерево и не угадывает детей по названиям. До DK-917 агент
определяет затронутые решения по содержанию. Под каждой затронутой головой
он дописывает после последнего решения подстроку
`требует сверки <ГГГГ-ММ-ДД>: <что изменилось и что проверить>`. Например:

```markdown
- «срок хранения»: сколько дней хранить отчёт?
  - решает: человек
  - решено человеком 2026-10-26: 30 дней
  - требует сверки 2026-10-27: из состава исключён СЦ-3; проверить срок хранения
```

Пометка действует, пока после неё нет строки `решено`. `--open` выводит
такую развилку с прежним решением, причиной и состоянием «требует сверки»,
даже если до пометки она была решена. При `решает: человек` она держит старт
и попадает в пачку вопросов; при `решает: исполнитель` остаётся работой
агента. Дата не определяет порядок, учитывается положение строк в файле.

Подтверждение прежнего ответа и изменённый ответ записываются обычной более
поздней строкой `решено <кем> <дата>: <ответ и довод>`. Она снимает пометку
из текущего состояния, история остаётся в файле. Отдельного ключа
подтверждения нет. Для человеческого решения агент сохраняет ответ человека,
для внутреннего применяет действующий порядок ответа исполнителя.
Повторная пометка после решения снова требует сверки. Это след пересмотра
затронутого вопроса в существующем перечне; связи родитель-ребёнок здесь
не хранятся. Изменение набора печатает обязательное напоминание выполнить
такую сверку. Готовность постановки по одному отсутствию открытых строк
не объявляется, как требует Решение 3 LLD.

### Как сохраняется отказ от всех

Пользователь выбрал A. Пустая строка ответа даёт ошибку и ничего не меняет.
Явное «ничего» или снятие всех сценариев сохраняет слова человека и событие
пересмотра. Под головой списка дописываются две строки:

```markdown
  - пересмотр человеком 2026-10-27: отказ от всех; требуется пересмотр границ
  - ответ: {"text":"ничего","snapshot":"sc1-<hash>","event":2,"result":"отказ от всех сохранён; прежний состав отменён; выбор открыт для пересмотра границ"}
```

Пока последним событием служит `пересмотр человеком`, действующего состава
нет, выбор открыт и держит старт. Прежние наборы видны только как история.
Агент выясняет новый состав либо прекращение работы. Рекомендованный набор
не подставляется ни при этом ответе, ни при продолжении после перерыва.
Следующие «плюс/минус» без полного набора или явного «по рекомендации»
требуют уточнить основу; правило первого ответа к пересмотру не применяется.
Более поздний непустой ответ по свежему снимку записывает `решено` и закрывает
пересмотр. Пустой исход считается принятым событием для нумерации истории и
проверки повторной доставки. Повтор пары с «ничего» возвращает сохранённый
`result`, пока после него не было нового события выбора.

Источник обхода: код `internal/taskform/lineup.go`, `Add` запрещает пустой
состав; дока `docs/lld/DK-1318-grooming-scenarios.md`, СЦ-1 называет пустой
выбор исключением, но не задаёт исхода. Решения 1/4 запрещают подстановку
рекомендации без ответа, Решение 3 связывает готовность с выбранной работой.
Выбор A сделан пользователем 2026-10-27; технический прецедент кода сам
по себе основанием решения за человека не служит.

Технические детали приняты по свежей проверке договора. Носитель уже задан
архитектурой, устойчивые ID и история заданы Решением 1, отдельная
рекомендация и общий ключ для UI заданы Решением 4. Новое дерево исключено
Решением 5. Дополнительной человеческой развилки по этим пунктам не найдено.

### Что меняется в W2 и чем проверить договор

`internal/taskform` получит разбор нового режима, ID, карточек и снимка,
проверку набора и сохранение прежнего пути `Lineup`. `Fork` и lint будут

вывод продолжения и защиту от устаревания. Обычный `--answer` должен различать
отсутствующий ключ и переданную пустую строку, сейчас ветка выбрана по

interview и сценарии obeycheck. UI остаётся DK-1446.

Дешёвые проверки W2 проводятся на временных файлах рядом с модулями.
Они покрывают создание и чтение новым процессом, позицию и ID одного
сценария, перестановку, удаление без повторной выдачи ID, разные основы
«плюс/минус», текст с запятой, повторное решение и продолжение. Отдельно
проверяются снимок без изменения после перерыва, изменённый список и
карточка, неизвестный/чужой/повреждённый ключ, устаревшая основа правки,
номер вне списка и отсутствие частичной записи. Проверяются повторная
доставка той же пары без новой строки и ID, новый ответ по свежему снимку,
возврат A -> B -> A, повтор «плюс своего сценария» и пустого исхода A.
Отдельно новым процессом проверяются чтение пометки сверки, подтверждение
прежнего решения и повторная пометка. Прежние `lineup_test`,
`decidelineup_test` и проверки обычного блока сохраняются. В W1 сделаны только чтение кода и документа;
будущие команды и V1-V4 ещё не прогнаны.
