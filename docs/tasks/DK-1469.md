# DK-1469: Типизированный черновик со словарём в два слоя и карточками разбора

Цель: [DK-1198](DK-1198.md).

Разбор стыков и порядок проверок лежат в [LLD](../lld/DK-1469-typed-drafts.md).

## Что происходит

У черновика нет типа, записи вроде договорённости или контроля лежат в общем
накопителе. Разбор идёт одним скиллом груминга, исход виден в чате, карточек
предложений нет. Это проверено 2026-10-29 по `tools/taskctl/draft.go`,
`tools/taskctl/json.go` и `tools/dashboard/drafts.go`. Шапка хранит дату и
приоритет разбора. Источника и замка в ней нет.

В DK-1445 и DK-1446 появился выбор сценариев с продолжением разговора.
Его ответ меняет состав работы. Подтверждение предложений разбора меняет
файлы и доску, поэтому одного выбора СЦ для применения недостаточно.
Команды `add --id`, `draft attach` и `draft drop` расходуют исходный
черновик. После первой из нескольких карточек остальные потеряют свою
запись, если вызывать эти команды без общего порядка применения.

## Чего хотим

Пользователь записывает мысль, встречу, письмо, сообщение или ссылку в
накопитель. Тип задаёт будущий результат, источник показывает происхождение.
У встроенных типов «задача», «договорённость», «веха» и «контроль» свои
правила разбора и умолчания. Проект добавляет тип файлом либо заменяет
одноимённый встроенный файл целиком. Для быстрой записи выбирать поля
необязательно, старые черновики остаются читаемыми.

Одна запись даёт несколько предложений. Для разработки перед предложениями
идёт интервью. Пользователь видит будущие строки, приписки, отсрочки и
удаления до применения, правит предложения, принимает одно, все по записи
или все показанные, отклоняет ненужные. Связь «после» между будущими строками
показывается вместе с ними. Применение проходит через команды taskctl с
проверкой формы задачи. В каждом результате видно происхождение записи.
После завершения разбора исходник уходит из накопителя в историю вместе с
предложениями, решениями и ссылками на результаты.

Общий транспорт вопросов и продолжение DK-1446 используются для карточек.
У подтверждения свой предмет и снимок показанной редакции. Повторная
доставка подтверждения возвращает прежний результат. Изменение записи,
предложения или места назначения требует нового просмотра.

У записи с замком облачный разбор не запускается. Пока локального маршрута
нет, пользователь видит «ждёт локальную модель». Источник не назначает
замок автоматически. Пустой ответ разбора и ошибка показаны отдельно.

## Границы

Типы строк доски остаются `bug`, `task`, `LLD`. У вехи обязателен срок,
контроль использует механизм DK-1470. Новый тип черновика не добавляет
сущность на доску. Роутер, маскирование и подключение локальной модели
остаются в DK-1471. Замок проверяется до передачи содержимого модели.

Скачивание страниц, импорт почты и мессенджеров в эту задачу не входят.
Источник можно указать у вставленного текста. Цикл цели DK-1198 этим
поручением не запускается.

## DoD

1. В накопителе можно создать и изменить тип, источник и замок. Старая запись
   и быстрая запись одним абзацем работают с совместимыми умолчаниями.
2. Встроенный словарь и проектное замещение видны пользователю. Добавленный
   тип выбирается без правки кода, неверное определение сопровождается
   сообщением с файлом и полем.
3. Разбор сохраняет несколько редактируемых предложений. До подтверждения
   исходы не применяются. Пустой разбор предлагает ручное оформление.
4. Четыре исхода, приём по одному и пачкой, отказ и связи «после» проходят
   через существующие команды. Происхождение видно в файлах результатов,
   непринятые предложения сохраняются.
5. Повтор подтверждения не создаёт дубли. Устаревший просмотр и параллельное
   применение завершаются понятным результатом без потери чужой правки.
   Прерванное применение можно закончить без повторения выполненного.
6. Запись с замком не передаётся облачной модели ни при отдельном запуске,
   ни при разборе пачки, ни при быстрой записи с разбором.
7. Путь от записи до результатов пройден на установленной версии отдельной
   сессией. Первый запуск описан в README taskctl и дашборда.

## Пользовательские сценарии

### СЦ-1

Ситуация: пользователь записывает одним абзацем мысль, встречу, письмо, сообщение или ссылку.
Действие: сохраняет запись в проект, при необходимости выбирает тип, источник и замок.
Результат: запись видна в накопителе с исходным текстом и выбранными полями; прежние записи читаются.
Польза: фактура не теряется при быстрой записи с телефона.
Рекомендация: включён в DK-1198, кейсы 3, 4 и 10; сохраняем простой вход.
Ограничение: источник это пометка вставленного текста; загрузка внешнего содержимого сюда не входит.
Источник: слово пользователя, DK-1198, решение «сценарии» от 2026-10-26 и пункт 6.

### СЦ-2

Ситуация: встроенный тип не подходит проекту либо нужен ещё один тип.
Действие: пользователь выгружает определение, меняет проектную копию или добавляет новый файл.
Результат: список типов и разбор используют проектное определение целиком, новый тип доступен без сборки.
Польза: правила результата можно настроить под проект.
Рекомендация: включён пунктом 6 DK-1198; применяем принятую схему двух слоёв.
Ограничение: тип строки доски остаётся в закрытом наборе bug/task/LLD; поля определений не сливаются.
Источник: слово пользователя, DK-1198, пункт 6 и решение о типах от 2026-09-27.

### СЦ-3

Ситуация: одна запись содержит несколько будущих дел или дополнений к ним.
Действие: пользователь запускает разбор, для разработки отвечает на вопросы интервью.
Результат: предложения показаны отдельными карточками с текстом, исходом, назначением, сроком и связями; доска ещё не изменена.
