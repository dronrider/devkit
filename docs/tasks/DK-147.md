# DK-147: Read длинного файла целиком отвечает подсказкой читать куском

записан 2026-08-06

## Что происходит

Чтение файла целиком вдвое дороже чтения куском, и зовётся оно чаще. Замер
по транскриптам 972 сессий: из 7577 вызовов Read 4428 (58.4%) идут без
limit и offset, дают 41.4M символов и в среднем 9.4K за вызов, а 3150
(41.6%) с limit или offset дают 12.2M и в среднем 3.9K. Чтение целиком
набирает 38% всего вывода инструментов за выборку, больше любой другой
практики: весь grep за тот же период 8.1M, впятеро меньше. Правило ядра
«не тянуть файл целиком, когда нужен фрагмент» стоит, а рубежа под ним
нет, и статистика показывает, что дисциплиной оно не держится.

## Чего хотим

Рубеж PreToolUse на Read: вызов без limit на файле длиннее порога получает
подсказку читать фрагментом, а место искать грепом. Порог подбирается по
распределению длин из замера, короткий файл проходит без подсказки:
чтение целиком законно там, где файл и есть фрагмент.

Развилки едут неопределённостью и остаются исполнителю: величина порога,
мягкая подсказка или отказ, и случаи, где чтение целиком по делу
(файл короче порога, правка файла целиком следом). PreToolUse в devkit
сегодня не подключён ни к чему (проверено по ~/.claude/settings.json
2026-08-09, разбор в DK-146).

Смежное: DK-146 (повторные чтения, механизм рубежа общий, кто первым
поедет в работу, тот и завозит каркас; предмет другой, не дубль), DK-148
(черновик утилиты замера, её прогон покажет сдвиг доли чтений целиком
после этой правки), DK-137 (цель про выжимку вывода команд, соседняя
дыра расхода контекста).

## DoD

Read без limit на файле длиннее порога получает подсказку вместо
содержимого либо вместе с ним (развилку решает исполнитель); Read
короткого файла и чтение с limit или offset проходят нетронутыми. Порог
выведен из распределения длин, а не взят из головы. Событие PreToolUse
разложено автоматикой подключения devkit, а не руками. Работу рубежа
видно снаружи: подсказка остаётся в транскрипте сессии. Тесты по
стандарту devkit; сценарий проверки пишет исполнитель.

## Решение

Рубеж в `hooks/check-longfile.py`, третий записью в HOOK_LAYOUT на том же
матчере Read, что и check-reread.py. Каркас не переписывался: новая категория
заведена тройкой по правилу из README, имя скрипта в PRE_READ_SCRIPTS, строка
в HOOK_LAYOUT и запись в PRE_READ_GAPS.

Порог 300 строк, выведен из распределения длин. Прогон `devkitctl drain --all`
по корпусу 1603 сессий (94166 вызовов) даёт перцентили размера вывода Read: у
чтений целиком p50 ~120, p75 ~303, p90 ~618 строк; у чтений куском (с
limit/offset) p50 ~66, p75 ~126, p90 ~212 строк. Порог 300 режет верхний
квартиль чтений целиком (примерно 25% их числа, ~70% их объёма), и он выше
p90 куска: если агенту был нужен фрагмент, куска до 212 строк хватило бы, и
чтение файла длиннее 300 строк целиком почти наверняка лишнее. Короткий файл
(медиана чтений целиком ~120 строк) проходит без подсказки.

Отказ (exit 2), а не мягкая подсказка вместе с содержимым. У PreToolUse в
claude-code нет канала «пропустить, но предупредить»: выход 0 это молчаливый
пропуск, выход 2 единственный способ оставить подсказку в транскрипте. Так
же работает check-reread.py, и два рубежа на одном матчера Read живут рядом,
каждый своим выходом 2 со своей подсказкой.

Случаи, где чтение целиком законно: файл короче порога проходит; чтение с
limit/offset/pages проходит нетронутым (это уже фрагмент); бинарный файл
(нуль-байт в теле) проходит, потому что Read отдаёт его как визуальный или
двоичный результат; несуществующий и нечитаемый файлы проходят, Read скажет
сам. Чтение перед правкой файла целиком (Edit/Write следом) рубежу не видно:
на PreToolUse у хука нет будущего, и подсказка летит на любое чтение целиком
длинного файла; агент читает нужный кусок через limit/offset или ищет место
грепом, а для правки всего файла собирает его двумя-тремя кусками. Чтение
600-строчного файла целиком перед правкой двадцати строк это и есть та дыра,
которую рубеж режет.

## Сценарий проверки

1. Юниты и поведение хука: `cd hooks && python3 -m unittest check_longfile_test
   -v`. Покрыты все ветки: короткий файл проходит, длинный без limit режется,
   граница порога (LONG_LINES-1 проходит, LONG_LINES режется), чтение уже
   куском проходит, бинарный и отсутствующий файлы проходят, плохой вход
   уходит нулём, ранний выход на длинном файле, подсказка несёт limit, греп,
   порог и DK-147. Регрессионная краснота проверяется regcheck:
   `regcheck --base main --tests hooks/check_longfile_test.py -- bash -c 'cd
   hooks && python3 -m unittest check_longfile_test'` краснеет на коде без
   check-longfile.py и проходит на новом.

2. Каркас раскладывает рубеж автоматикой: `cd tools/devkitctl && python3 -m
   unittest devkitctl_test.HarnessHooksTest` проверяет, что доктор на чистом
   проекте называет неподключённый check-longfile.py, --fix кладёт его в ту же
   группу с матчером Read, что и check-reread.py, и повторный --fix ходы не
   дублирует. Регрессионная краснота: `regcheck --base main --tests
   tools/devkitctl/devkitctl_test.py -- bash -c 'cd tools/devkitctl &&
   python3 -m unittest devkitctl_test.HarnessHooksTest'`.

3. Два рубежа сосуществуют: `cd hooks && python3 -m unittest check_reread_test
   check_longfile_test` зелёны вместе, и в SETTINGS-фикстуре машинного контура
   (tools/devkitctl/testenv.py) обе команды стоят в одной группе PreToolUse на
   Read.

4. Подсказка видна в транскрипте: ручной прогон `hooks/check-longfile.py
   --hook` с событием PreToolUse на Read длинного файла на stdin выходит кодом
   2 и печатает в stderr подсказку с порогом, limit и грепом; короткий файл и
   чтение с limit выходят нулём молча.
