# DK-155: update не обновляется, пока в origin двигается служебный тег deployed

Задача цели [DK-138](DK-138.md), дорезка: нашлась на прогоне DoD цели, без неё
DoD пункт 2 не сходится.

## Задача

`devkitctl update` и `devkitctl update --check` зовут `git fetch --tags
--prune` (`tools/devkitctl/update.py:527`). В devkit живёт служебный тег
`deployed`, который `shipctl` двигает на каждом выкате, и fetch на такой тег
отвечает отказом:

```
From https://github.com/dronrider/devkit
 ! [rejected]        deployed   -> deployed  (would clobber existing tag)
```

Код возврата ненулевой, и команда печатает «git fetch --tags не прошёл: за
новыми тегами нужна сеть, и ничего не тронуто», хотя сеть на месте, а нужные ей
релизные теги приехали. Обновление на машине потребителя не работает вовсе, и
сообщение уводит в сторону: человек пойдёт чинить сеть.

Проявляется не сразу: в свежем клоне локальный `deployed` совпадает с
origin, а расходится он после первого же выката devkit, то есть у потребителя
через день-два после установки.

Чинить так, чтобы команду интересовали только релизные теги: тянуть их своим
рефспеком (`refs/tags/v*:refs/tags/v*`) либо равным способом, не трогая чужие и
служебные теги вовсе. Отказ сети остаётся отказом и должен по-прежнему давать
внятное сообщение.

Смежное посмотреть заодно: `--prune` в нынешнем виде тоже про все теги, а
удалять чужие теги команде незачем.

## Сценарий проверки

Агентский.

1. Клон, где локальный `deployed` разошёлся с origin: `devkitctl update
   --check` доходит до рассказа про версии, а не печатает отказ про сеть.
2. Там же `devkitctl update`: обновление проходит, бинари и чекаут сходятся на
   новейшем релизном теге.
3. Сеть правда недоступна (адрес origin подменён на несуществующий): отказ
   остаётся внятным и ничего не трогает.
4. Тесты: случай «служебный тег в origin разошёлся с локальным» покрыт и
   краснеет на нынешнем коде, полный набор тестов проекта зелёный,
   `python3 hooks/check-symbols.py` на изменённых файлах молчит.

## Ревью

- Рефспек не огораживает от чужих тегов так, как заявлено в комментарии и доке: git fetch с явным refspec 'refs/tags/v*:refs/tags/v*' всё равно автослежением тянет НЕ-v тег, если его коммит уже есть локально (проверено: свежий тег 'other-tag' на уже известном коммите приезжает при таком fetch, хотя рефспек его не называет). deployed сегодня защищён только тем, что уже существует локально с самого клона (автослежение не перезаписывает существующий тег), но случай 'новый служебный тег появился в origin' рефспек не закрывает, а комментарий (tools/devkitctl/update.py:45-50) и дока (LLD, оба README) утверждают обратное. Лечится добавлением --no-tags к вызову на update.py:534: git fetch --no-tags --prune origin $TAG_REFSPEC. Проверено вручную (git fetch --no-tags + явный refspec не подтягивает посторонний тег, v*-тег из рефспека тянется как прежде), тест на этот случай в update_test.py не заводился.
