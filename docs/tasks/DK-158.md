# DK-158: devkitctl selfcheck: живость связки после установки проверяется одной командой

## Что происходит

Установка devkit на машину заканчивается строкой «проверить devkit можно
командой devkitctl doctor», и доктор честно проверяет раскладку: файлы на
местах, бинари одной версии с чекаутом, каталог назначения в PATH, пакеты,
обвязка проекта. Чего он не проверяет, так это того, что связка живая: доска
правится, ранг считается, вердикт `pick` выдаётся, ветка задачи заводится в
своём дереве, слияние проходит.

Проверка эта сегодня ручная и на пять команд, с уборкой ещё на три:

```
devkitctl new -C ~/projects/myproj --prefix MP
devkitctl doctor -C ~/projects/myproj
taskctl -C ~/projects/myproj add --title "проверка связки" --type task --rank "25+5+1+0+0" --cost S
shipctl -C ~/projects/myproj status && agentctl pick MP-001
shipctl -C ~/projects/myproj start MP-001
git worktree remove ~/projects/myproj-mp-001 && git branch -D mp-001 && taskctl close MP-001
```

Отменить `start` нечем, отдельной команды у `shipctl` нет, так что за пробой
человек убирает руками и на своём же проекте. Помнить этот порядок неоткуда: в
доке его нет, он собирается по README трёх утилит.

Повод пришёл от пользователя после установки devkit на вторую машину: вопрос
был ровно «как убедиться, что devkit работает на моём проекте».

## Чего хотим

Команду `devkitctl selfcheck`, которая гоняет тот же круг сама и за собой
убирает. Круг: временный проект во временном каталоге, подключение, строка на
доске, вердикт `pick`, ветка задачи в отдельном дереве, слияние с зелёными
тестами. Отчёт по шагам, каждый со своим исходом, и внятный конец: связка жива
либо шаг такой-то не прошёл, вот вывод.

Настоящие проекты и HOME при этом не трогаются. Стенд самопроверки devkitctl
это уже умеет (`tools/devkitctl/testenv.py`): временный HOME, подставной PATH,
синтетический проект, уборка в любом исходе.

Открытые развилки, которые снимает исполнитель, а не постановка:

- граница с тестами devkit. Тесты гоняются на стенде из исходников и до
  установки, selfcheck на живой машине и после неё, поверх установленных
  бинарей: он проверяет не код, а собранное и разложенное. Из этого следует,
  какие куски стенда переиспользуются, а какие нет;
- берётся ли проект пользователя или всегда временный. Временный безопаснее и
  повторяем, но не отвечает на вопрос «работает ли на моём проекте»;
- что selfcheck делает с находками `doctor` по машине: считает ли их своим
  провалом, называет ли отдельно, гонит ли доктора вообще;
- гонять ли слияние с настоящим выкатом. У временного проекта команда выката
  своя, подставная, и тогда круг замыкается без риска для чего-либо снаружи.

## DoD

1. `devkitctl selfcheck` на машине, где devkit только что поставлен, проходит
   круг целиком и печатает отчёт по шагам, из которого видно, что живо, а что
   нет.
2. Сломанная связка ловится: подпорченное окружение (бинарь не той версии,
   утилита не в PATH, доска не заводится) даёт провал с названным шагом и
   выводом, а не молчание.
3. После прогона на машине не остаётся ничего: ни временного проекта, ни веток,
   ни worktree, ни правок в HOME. Проверяется слепком до и после.
4. Настоящие проекты и настоящий HOME в прогоне не участвуют вовсе.
5. Команда названа в доке установки как способ проверки: `CONNECT.md` и
   `tools/devkitctl/README.md`.
6. Своя пирамида тестов, полный набор тестов проекта зелёный.
