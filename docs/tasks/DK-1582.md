# DK-1582: Запуск облачного чата не оставляет процессы после проверки

## Что происходит

На рабочей машине 3 ноября обнаружены 416 осиротевших cloud-start guardian
от smoke-проверок dashboard. После окончания стенда его fake tmux удалён,
ack отсутствует, а оболочка раз в секунду повторяет опрос без конечного
исхода. Установленный код 4fb2f5702ccf совпадает с main 8c015e705795 в этих
местах. Утечка изолированно воспроизведена точным shell-кодом cloudstart.go.
Нормальный ack завершает процесс, удаление fake tmux оставляет его живым.

Результаты исследования и критерии №171 и №172 опубликованы в
https://github.com/dronrider/devkit/blob/codex/concurrency-refresh-20261030/docs/concurrency-incident-20261103.md.

## Чего хотим

Запуск различает создание терминала и принятие резерва клиентом. Неизвестная
живость получает ограниченный опрос, сохранённое состояние с владельцем и
диагностику. Резерв остаётся защищённым до ack или доказанной смерти клиента.
Стенд по любому исходу завершает только собственные процессы, ждёт их выхода
и закрытия резервов до удаления фикстур. Повторные прогоны не накапливают
guardian.

## Границы

Работа покрывает №171 и №172. Общая политика нагрузочных повторов №173 и
расследование остановок чатов №174 сюда не входят. Нет изменений квот,
подписок, порога простоя или массового завершения чатов. Простое освобождение
резерва по тайм-ауту запрещено: клиент может ещё работать. По подтверждению
исправления отдельно допускается адресная очистка только синтетических
остатков из снимка с повторной сверкой PID, команды и удалённой фикстуры.

## DoD

- Ack передаёт резерв без разрыва; guardian завершается, рабочий клиент жив.
- Смерть клиента до ack освобождает резерв с причиной. Выход родителя сам
  по себе не снимает резерв, принадлежащий ещё живому запуску.
- Временный сбой опроса не снимает живой чат. Постоянная неизвестная живость
  не создаёт бесконечный частый опрос; состояние и владелец резерва наблюдаемы.
- Smoke поддерживает реальный контракт ack/живости. Успех, ошибка, отмена
  и тайм-аут не оставляют процессов и открытых резервов своего стенда;
  удаление фикстуры происходит после завершения процессов. --keep сохраняет
  материалы без живых циклов.
- Регрессия удаления fake tmux до ack падает на исходном коде и проходит
  после исправления, проверка через regcheck. Серия изолированных запусков
  не накапливает процессы. Боевые сессии и модельные API не используются.
- README описывает состояния запуска, диагностику и порядок завершения стенда.

## Сценарий проверки

Из корня установленного дерева выполнить без обращений к моделям:

```sh
dashboard --version
DEVKIT_HOME="$PWD" dashboard smoke
DEVKIT_HOME="$PWD" dashboard smoke --keep
GOWORK=off python3 tools/devkitctl/devkitctl.py test tools/dashboard -run 'TestCloudStart(ReservationHandoff|FailedLaunchReleasesReservation)|TestSmoke(Close|ClientAcknowledges|RemovedTmuxCleanupIsBounded)' -count=1
```

DEVKIT_HOME указывает на проверяемый чекаут с hooks/notify.py.
Версия dashboard должна соответствовать выкату. Оба smoke завершаются
успешно. --keep сохраняет материалы прогона без работающих guardian.
Адресные тесты проверяют передачу резерва, отказ запуска, отмену активного
старта, повреждённую фикстуру и завершение нескольких групп одного задания.
Боевые чаты не используются.

Неизвестная живость и регрессии на прежнем коде проверены до слияния,
команды и результаты сохранены ниже. Их повторный полный прогон не входит
в каждую приёмку установленного бинаря.

## Проверка

### Команды авторской проверки

Следующие проверки выполнены при разработке; это история воспроизведения,
а не дополнительные шаги приёмки после каждого выката.

1. В дереве задачи выполнить без модельных вызовов:

   ```sh
   GOWORK=off devkitctl test tools/dashboard -run 'TestCloudStart|TestSmoke' -count=1
   ```

   Проверяются передача ack, отказ new-session, временная ошибка tmux,
   выход родителя до ack, сохранение резерва при неизвестной живости,
   уборка до удаления фикстур, отмена, тайм-аут и --keep. Повтор уборки
   выполняется три раза в одном тесте.

2. Подтвердить регрессии на исходном коде:

   ```sh
   GOWORK=off regcheck -C tools/dashboard --base 8c015e705795 --tests tools/dashboard/cloudstart_test.go,tools/dashboard/smoke_test.go -- python3 ../devkitctl/devkitctl.py test . -run 'TestCloudStartFailedLaunch|TestCloudStartMissingTmux|TestSmokeCloudCleanup|TestSmokeClientAcknowledges' -count=1
   ```

   Ожидается exit 0 regcheck. Оба дерева должны собраться. Исполнение
   тестов проходит на текущем коде и падает на базе.

3. Проверить регрессию гонки завершения на первом коммите исправления:

   ```sh
   GOWORK=off regcheck -C tools/dashboard --base e48d02546 --tests tools/dashboard/smoke_context_test.go -- python3 ../devkitctl/devkitctl.py test . -run TestSmokeCloseWaitsForHandlerBeforeRestoringEnvironment -count=1
   ```

4. Проверить пакетную уборку двух запусков одного задания:

   ```sh
   GOWORK=off regcheck -C tools/dashboard --base 711403142 --tests tools/dashboard/smoke_cleanup_test.go -- python3 ../devkitctl/devkitctl.py test . -run TestSmokeCloseKillsAllGroupsBeforeCheckingSharedReservation -count=1
   ```

5. На установленном бинаре выполнить `dashboard smoke` и `dashboard smoke --keep`.
   Оба прогона должны завершиться без модельных вызовов и остаточных guardian.
   Повторить адресные тесты из первого пункта после выката.

6. Выполнить `GOWORK=off devkitctl test tools/dashboard`. Для повторных проверок
   использовать разрешённый Go-кеш, сохраняя изоляцию фикстур и HOME. Боевые чаты,
   сетевые вызовы моделей и очистка чужих процессов не нужны.

7. При разборе неизвестного запуска найти строку `cloud-start` в журнале
   сервера, прочитать `state`, `owner` и `probe-error` по указанному пути.

   только по истечении времени. SIGKILL стенда не выполняет очистку;
   обработка SIGINT/SIGTERM и HTTP timeout проверяется отдельно.
