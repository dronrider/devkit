# DK-160: doctor из каталога проектов ползёт по чужим репозиториям и печатает сотни ложных находок

Повод: коллега поставил devkit по строке из `CONNECT.md` и позвал `devkitctl
doctor` из `~/projects`, то есть из каталога, где лежат проекты. Вместо отказа
доктор пошёл по дереву и напечатал семь находок, пять из которых это битые
ссылки в файлах задач самого devkit.

## Задача

Лог коллеги:

```
чекаут devkit: на релизе v0.9.0
не git-репозиторий: /Users/vea/projects
нет AGENTS.md в корне проекта; подключение: devkitctl new --prefix XX
devkit/docs/tasks/DK-123.md:10: битая ссылка (../../shipctl/corp.go)
devkit/docs/tasks/DK-126.md:6: битая ссылка (../../devkitctl/devkitctl.py)
devkit/docs/tasks/archive/2026/DK-081.md:11: битая ссылка (../../../../taskctl/ops.go#L29)
devkit/docs/tasks/archive/2026/DK-081.md:12: битая ссылка (../../../../agentctl/board.go#L18)
devkit/docs/tasks/archive/2026/DK-081.md:13: битая ссылка (../../../../shipctl/board.go#L27)
находок: 7
```

Воспроизведено на машине с двумя десятками проектов рядом: тот же вызов из
`~/projects` дал **172 находки**, из них 170 битых ссылок, собранных по чужим
репозиториям (`byblos/docs/...`, `README.md` соседнего проекта и так далее).
Код возврата 1.

Дефектов тут два, и второй виден из первого.

1. **Доктор не останавливается вне репозитория.** Строку «не git-репозиторий»
   он печатает находкой и продолжает работу, обходя дерево вниз. В каталоге
   проектов это значит обход всех соседних репозиториев, включая чужие, к
   devkit отношения не имеющие. Проверять там нечего: без репозитория нет ни
   проекта, ни обвязки, и остальные проверки бессмысленны.
2. **Исключение `docs/` не срабатывает у вложенного репозитория.** Правило
   записано в `tools/devkitctl/README.md`: `docs/` из проверки ссылок
   исключается, потому что файл задачи описывает состояние на момент решения и
   после закрытия не правится, значит ссылка на уехавший путь там законна (и
   чинить её правило запрещает). В логе коллеги проверены ровно эти файлы:
   путь `devkit/docs/tasks/...` от корня запуска на `docs/` не начинается, и
   исключение мимо. Ссылки эти к тому же следствие переезда каталогов
   (DK-135): `../../shipctl/corp.go` стал `../../tools/shipctl/corp.go`.

Чинить оба: отказ вместо обхода, когда корень не репозиторий (с внятной
строкой, куда идти: в проект либо в чекаут devkit), и исключение `docs/`,
считаемое от корня того репозитория, которому файл принадлежит, а не от каталога
запуска.

Границы:

- находки про сам devkit (вес резидента, раскладка) остаются как были: доктор,
  позванный из чекаута devkit, работает по-прежнему;
- проверка ссылок в живой доке проекта не ослабляется: исключается только
  `docs/`, и ровно по правилу из README;
- чинить ссылки в файлах задач нельзя, это запрещено правилом доски.

## Сценарий проверки

Агентский.

1. Прогон из каталога, где лежат проекты и нет git: доктор говорит, что тут не
   проект, называет, откуда его звать, и по чужим репозиториям не идёт. Находок
   про ссылки нет ни одной. Машинный контур и строка про режим чекаута при этом
   печатаются как обычно: они от root не зависят и по дереву не ходят.
2. Прогон из чекаута devkit: работает как раньше, находки про сам devkit на
   месте, ссылки в `docs/` не проверяются.
3. Прогон из подключённого проекта: обвязка проверяется как раньше, живая дока
   на битые ссылки проверяется, `docs/` проекта пропускается.
4. Синтетический стенд: каталог без git, внутри репозиторий с битой ссылкой в
   `docs/` и с битой ссылкой в живой доке. Первый прогон из каталога молчит про
   обе (кроме машинного контура и строки про чекаут, они на месте), второй из
   самого репозитория ловит вторую и пропускает первую.
5. Вложенный репозиторий как worktree и как submodule (`.git` внутри него файл
   со строкой `gitdir: ...`, не каталог): его живая дока проверяется, `docs/`
   пропускается тем же правилом, что и у обычного клона.
6. Тесты: случаи (включая worktree и submodule) покрыты и краснеют на прежнем
   коде, полный набор тестов проекта зелёный, `python3 hooks/check-symbols.py`
   на изменённых файлах молчит.

## Ревью

- check_links: исключение docs/ по (dp/'.git').is_dir() не срабатывает для вложенного git-worktree или submodule, там .git это файл, не каталог; такой вложенный репозиторий доктор всё равно обходит, и его docs/ (в т.ч. tasks/*.md со ссылками, уехавшими по правилу задачи) даёт находки, ту же ложную находку, которую DK-160 закрывает для обычного клона. Проверено синтетически: nested/.git как 'gitdir: ...' файл, check_links('proj') находит битую ссылку в nested/docs/tasks/XX-1.md, хотя обычный вложенный клон (is_dir true) её не даёт. Чинить: считать репозиторием (dp/'.git').exists(), не .is_dir(); тест на этот случай (worktree/submodule) в DoctorRootTest не заведён.
- doctor(): ранний return при not in_git обрывает вообще всё, включая машинный контур (чекаут devkit, бинари в PATH, git-хуки Claude, определения агентов/скиллов, tmux, снимок квоты), а он от root не зависит и раньше печатался независимо от git (это и видно в самом логе коллеги из постановки: 'чекаут devkit: на релизе v0.9.0', первая строка, до 'не git-репозиторий'). Проверено: 'python3 devkitctl.py doctor' из каталога без git печатает только находку и всё, без строки 'чекаут devkit' и без машинных находок; убрав return (мутацией) эта строка появляется. Задача формулирует дефект как обход дерева вниз (check_links и rules.check, которые правда дают шум по чужим репозиториям), а не как повод гасить машинную диагностику, которая по дереву не ходит и раньше работала (комментарий над print('чекаут devkit...') прямо говорит, что он называется всегда, а не только рядом с находкой, и справка doctor всё ещё перечисляет машинный контур как часть его работы без оговорки про not-git). Сценарий проверки и тесты этот случай не покрывают ни в одну, ни в другую сторону, стоит явно решить, входит ли машинный контур в границы фикса, и если да, поправить return, если нет, снять комментарий и справку под новое поведение.
