# DK-1601: Основной чат теряется после передачи и продолжения

Цель: DK-1253

## Что происходит

Сквозная проверка DK-1433 воспроизвела скачок ленты после передачи задачи
новому диспетчеру. В синтетической XR-903 две полноценные записи SessionStart
для A, затем B зарегистрированы в одну секунду. После успешного handover
двенадцать чтений адреса основного чата вернули B, B, B, A, A, A, A, A, A,
A, A, B. Контрольную реплику получил только новый диспетчер B.
Адрес ленты выбирался случайно.

После штатного resume XR004 адрес `GET task/chat` продолжает указывать
на правильный SID. Но в `GET /chats?all=1&days=0` пропадает основная строка
с id XR004. Остаётся физический SID в виде обсуждения, и основной чат
теряется при фильтрации. Тот же SID переместился из окна `task-XR004`
в `chat-XR004-1`. Симптом подтверждён синтетической фикстурой и в браузере.

TmuxResident в internal/sessions/sessions.go обходит map и сравнивает только
время с точностью до секунды. При равном времени результат зависит от порядка
обхода. В пути resume chatMainRows ищет исходный tmux-сегмент в byWin
по прежнему имени окна. После перемещения SID основная строка не собирается.
Исходные материалы handover сохранены в
/private/tmp/dk1433-run/proof/tie-proof.json и
/private/tmp/dk1433-run/payload/tie-check.py.

## Чего хотим

После handover и resume адрес и список основных чатов указывают на текущего
диспетчера с полноценной записью запуска. При одинаковом времени выбирается
фактический новый носитель. Порядок регистрации сохраняется при разборе
записей. Перемещение того же SID в другое окно tmux сохраняет основную
строку задачи и её видимость при фильтрации.

## Границы

Исправляются разрешение и представление основного чата при двух переходах
носителя. Доставка реплики, старые ссылки и история разговоров сохраняются.
Новый заказ без транскрипта по-прежнему не скрывает последнюю живую ленту,
как требует DK-1521. Сортировка UUID и искусственная пауза между запусками
не заменяют выбор фактического нового носителя. Дизайн списка чатов
и правила доставки реплик не меняются.

## DoD

- Две полноценные записи A, затем B с одинаковым временем дают B при всех
  повторных разрешениях, независимо от порядка обхода map.
- Новый заказ без транскрипта оставляет A; после полноценного запуска B
  адрес переключается на B. Разные метки времени работают как прежде.
- После resume XR004 тот же SID переходит из `task-XR004`
  в `chat-XR004-1`; `GET task/chat` возвращает этот SID.
  В `GET /chats?all=1&days=0` есть ровно одна основная строка с id XR004,
  и она видна при фильтрации основных чатов.
- После обоих переходов контрольную реплику с nonce получает только текущий
  носитель. История разговоров сохраняется. В handover старая ссылка
  продолжает открывать A.
- Регрессионные тесты обоих переходов краснеют на старом коде и проходят
  на исправленном; результат подтверждён regcheck.
- Быстрая передача и штатное продолжение в установленном синтетическом
  стенде проходят без искусственной паузы. После передачи лента всегда B;
  после продолжения основная строка задачи видна в браузере и в фильтре.

## Приёмка

Вид agent. Выбор адреса, основная строка в списке и её видимость в фильтре
проверяются по API и в браузере на синтетических транскриптах.
Получатель контрольной реплики и сохранность старой истории проверяются
после обоих переходов. Условий, посильных только человеку, нет.
В стенде не используются секреты и внешняя модель.
