# DK-1623: Накопитель дашборда забивает канал сотнями запросов

## Что происходит

HAR пользователя от 2026-11-06 содержит 994 запроса. Из них 933 приходятся на чтение prepared. Экран накопителя renderDrafts в tools/dashboard/static/app.js делает Promise.all по всем 466 черновикам. Две волны по 466 запросов стартовали в 17:54:34 и 17:55:27. Вторую волну вызвало восстановление связи lostAgain -> refresh -> renderDrafts. Запрос projects стоял до отправки 34,29 с, waiting 32,66 с, resources 39,19 с. Получены 35 ответов 502 с Too many open files (os error 24) от посредника. Открытие согласования занимает десятки секунд. Ожидается постоянное число запросов при любом количестве черновиков.

Обход появился в DK-1469, DK-1564 сохранила его при замене proposals на prepared. В DK-1564 есть отдельные изменения формы и подтверждения. Здесь требуется отдельная срочная правка производительности без их переписывания.

## Чего хотим

Восстановить работу накопителя и открытия подготовленной задачи сейчас. Сервер отдаёт общий состав подготовленных задач одним ответом. При открытии и обновлении списка нет сетевых запросов по каждому черновику. Решение может быть небольшим временным шагом до последующей оптимизации серверного чтения.

## Развилки

Открытых человеческих развилок нет. Пользователь 2026-11-06 поручил оформить находки и временно восстановить работоспособность дашборда. Конкретный способ общего чтения выбирает исполнитель по действующему источнику prepared. Ограничение параллельности 466 запросов пользователь отверг как сохранение ошибочной логики. Скрывать подготовленные задачи и отключать подтверждение не требуется.

## DoD

- Накопитель с 466 черновиками получает состав согласования постоянным числом запросов. Нет запроса prepared на каждый ID, в том числе после обновления и восстановления связи.
- Подготовленные задачи доступны для чтения и подтверждения. Сохранены снимки, отказы, совместимость старых записей и прежняя обработка ошибок. Чтение не подтверждает задачи автоматически.
- Проверка числа запросов падает на исходном коде и проходит после правки. Результат записан прогоном regcheck. Проверены пустой состав, ошибки чтения и несколько записей с подготовленными задачами.
- Правка и нужная документация опубликованы штатным выкатом. Установленный dashboard отдаёт новый путь; агентская проверка подтверждает отсутствие массового опроса. Очередь чужого выката не обходить, источник задач не менять руками.

## Сценарий проверки

1. На синтетическом проекте создать 466 черновиков, несколько подготовленных задач с корректными снимками и пустые записи. Открыть накопитель и перечитать его. Счёт запросов к prepared не растёт с числом записей.
2. Открыть подготовленную задачу, сохранить правку, проверить отказ устаревшего снимка и подтверждение синтетической задачи. Повтор после сетевого отказа не создаёт волну запросов по ID.
3. Выполнить адресные проверки по принятому в проекте порядку, прогнать regcheck и сохранить реальные команды и вывод. Исполнитель заменяет этот пункт исполнимыми командами своего стенда до сдачи.
4. После выката отдельная сессия сверяет установленную версию и чтение нового общего API без изменений реальных записей. Сохраняет вывод и штатную отметку smoke.
