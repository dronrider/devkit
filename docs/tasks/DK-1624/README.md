# Сценарий DK-1624: перенос чата Claude -> Codex -> Claude

Одноразовый сценарий проверки задачи [DK-1624](../DK-1624.md). Он прогоняет
живой разговор по цепочке двух клиентов и складывает исходы в отчёт. Тесты
гоняют ту же цепочку на фикстурах вместо клиентов, живой прогон идёт на
рабочей машине диспетчера с действующими подписками.

## Живой прогон

```bash
python3 docs/tasks/DK-1624/chat-port-check.py \
  --workdir /tmp/dk1624-work \
  --out /tmp/dk1624-run1 \
  --claude-cmd "<обёртка подписки Claude>" \
  --codex-cmd "codex app-server --stdio" \
  --codex-model gpt-6.1-sol
```

`--workdir` это родитель временных проектов, сценарий создаёт в нём три
новых каталога. Если каталоги или отчёт `--out` уже существуют, прогон
завершается с ошибкой до любых изменений, повтор идёт в свежих каталогах.
В `--claude-cmd` пишется команда клиента с обвязкой подписки, значения
переменных окружения в отчёте маскируются. Маркеры длинного вывода и
скрытый инструментальный факт генерирует сама команда через `uuidgen`, он
нужен в PATH сеанса Claude. Клиент запускается в отдельной группе
процессов, таймаут останавливает её целиком: под обёрткой подписки живёт
настоящий клиент, и он не остаётся держать канал. Необязательные ключи:
`--timeout` в секундах на прогон клиента и turn, `--claude-model`.

## Шаги прогона

1. Сеанс Claude во временном проекте: команда с длинным выводом из 604 строк,
   маркеры в начале, середине и конце, скрытая строка HIDDEN TOOL, правка
   файла notes.txt, строка assistant_fact. Все значения случайные, в
   принимающей стороне их нет нигде, кроме перенесённой истории. Скрытый
   факт сценарий ни разу не спрашивает у Codex. В обратной истории он
   доступен только из результата инструмента.
2. Журнал сеанса переводится в элементы Responses API и вводится в Codex
   через `thread/inject_items`. Исходную реплику пользователя сценарий
   возвращает в историю из сохранённого точного prompt, stdout клиента её
   не повторяет. Дальше идут опрос фактов и сверка ленты `thread/read`
   с `thread/items/list`.
3. После перезапуска app-server и `thread/resume` те же факты опрашиваются
   снова.
4. Повторно импортируется та же история, затем задаётся вопрос о числе
   вызовов Bash. Дубли модель видит как удвоенное число.
5. Задаётся вопрос о точной строке команды и вывода, потом вызывается
   `thread/compact/start`, и тот же вопрос повторяется после сжатия.
6. Codex создаёт новый факт codex_fact в своём ответе. Дальше вся цепочка
   подаётся клиенту Claude через stream-json с `--max-turns 1`, сначала
   с инструментальной историей, при отказе повтор идёт без неё.

## Отчёт и журналы

В `report.json` лежит таблица исходов по видам данных и обоим направлениям:
«перенесено», «потеряно», «не поддерживается», «не проверено». Доступность
ленты и доступность контекста модели оценены отдельными колонками, пределы
прогона названы числами. Чистая проба инструментальной истории в обратном
направлении это скрытый факт HIDDEN TOOL. Значение печатается исторической
командой и не спрашивается у Codex ни в одном turn. Вне результата
инструмента его взять неоткуда. Таймаут прогона и ответ без JSON
классифицируются как «не проверено». Отказом клиента считается только
явная ошибка входа с tool_use. Текстовый fallback отмечается в отчёте
пометкой: инструментальная история теряется в нём по самой схеме fallback. Маркеры, edit_line, user_fact и assistant_fact
повторяются в репликах и ответах Codex, перенос инструментов по ним не
доказывается. Native-инструменты Codex (custom_tool_call) сценарий не
создаёт, их обратный перенос проверен ручными прогонами диспетчера и в
полном потоке воспроизводимо теряется. Сохранность после перезапуска
меряется по фактам, подтверждённым до перезапуска. Сырые журналы
`*.jsonl` и `*.txt` содержат обе стороны обоих протоколов и пути машины,
в git они не едут.

Коды выхода: 0 прогон дошёл до конца, 1 какая-то проверка не состоялась
из-за сбоя сценария, 2 ошибка запуска.

## Тесты

```bash
devkitctl test docs/tasks/DK-1624
```

Фикстуры `fake_claude_client.py` и `fake_codex_server.py` изображают
поведение клиентов из ручных проб диспетчера. stdout не повторяет user
input, импортированные элементы не видны в ленте, повторный inject
добавляет дубли, сжатие шлёт отдельное событие contextCompaction и теряет
точные строки. Сквозной тест закрывает пять путей: полная цепочка, отказ
клиента принимать исторические tool_use, отказ сервера на inject, отказ
повтора в занятых каталогах и остановка группы клиента при таймауте.
