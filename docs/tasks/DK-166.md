# DK-166: Цель: полный прогон тестов укладывается в две минуты

записан 2026-08-07

## Цель

Полный прогон тестов devkit вырос до 4-5 минут, а прогонов на одну задачу
выходит несколько: regcheck гоняет тест бага на двух ревизиях, свои прогоны
зовут ревью и слияние поезда. Ожидание складывается в заметный тормоз всей
работы над задачей. Хотим, чтобы прогон перестал быть узким местом.

DoD: холодный прогон команды `test` из `.devkit/deploy.local` (go test с
`-count=1`, питоновые unittest, проверочные скрипты) укладывается в 120 секунд.
Проверка агентская: `time` вокруг команды `test`, порог утверждён
пользователем 2026-08-07.

## Бюджет

бюджет: week_all <= 20
бюджет: week_max <= 8

## Разбор 2026-08-07

Актуальность проверена замером: холодный последовательный прогон команды
`test` занял 433 секунды. Раскладка по компонентам:

- py tools/devkitctl: 289 с (две трети всего прогона)
- go tools/shipctl: 59 с
- py hooks: 30 с
- go tools/agentctl: 19 с
- go tools/taskctl и tools/obeycheck: по 10 с
- py kit/skills/goal-loop: 10 с
- go tools/regcheck и tools/trackctl: по 3 с
- остальное (kit/skills, check-skills, check-exec-bit, doctor --layout): ~0 с

Внутри devkitctl время по модулям: devkitctl_test 122 с, update_test 55 с,
rules_test 31 с, corp_test 29 с, weigh_test 19 с, harness_test 11 с, perms_test
и build_test по 8 с, layout_test 4 с, остальные по 0-1 с.

Компоненты в команде `test` независимы и идут строго последовательно, так что
параллель срезает сумму до самого тяжёлого компонента, но пока devkitctl
держит 289 секунд, порог 120 не берётся: тяжёлые наборы придётся ускорять и
сами. Возможные направления, все открыты: профилировка тяжёлых модулей (стенды
с временным HOME, вызовы через subprocess), параллель компонентов, кэш go test
(какие прогоны честно гонять с `-count=1`). Смежные закрытые DK-141 и DK-142
переводили раннеры тестов на python, самих тестов не ускоряли.

Предмет: медленный прогон платится по несколько раз на каждую задачу доски,
теряют все конвейеры (исполнитель, ревью, слияние, выкат). Обхода нет, команда
`test` зовётся автоматикой целиком. Ускорять прогон ценой прорех в покрытии
нельзя: набор тестов остаётся полным, режется время, а не проверки.

## Задачи цели

Пробная нарезка 2026-08-14, строк на доске нет.

Общее для всех кандидатов: серьёзность 25 (Major, прогон тормозит каждую задачу,
но работу не ломает), рычаг 4 (режет время каждой следующей задачи всех
конвейеров), поправки на баг нет, вид приёмки агентский. Порядок режет текущий
максимум прогона: сперва 289 секунд devkitctl, затем параллель остальных
компонентов, под конец разгрузка самого тяжёлого юнита.

- кандидат 1 (task, M, R=39: 25+7+3+0+4). Раннер питоновой сюиты devkitctl:
  юниты идут отдельными процессами с потолком воркеров, провалы печатаются
  целиком. Гранулярность до класса: модульной не хватает, один devkitctl_test
  в 122 с длиннее любого разумного порога. Ценность 7: здесь две трети времени
  прогона. Неопределённость 3: развилки в безопасности параллели, стенды на
  временных каталогах, но есть pty-тесты. Проверка агентская: холодный прогон
  сюиты укладывается в 100 с, счёт тестов совпадает с последовательным прогоном,
  два прогона подряд зелёные.
- кандидат 2 (task, M, R=37: 25+6+2+0+4). Параллель компонентов команды
  `test`: go-инструменты, hooks, сюиты скиллов и doctor идут одновременно
  с потолком воркеров, go остаётся с `-count=1` по DoD, кэш сборки не чистится,
  команда `test` в deploy.local основного чекаута зовёт раннер. Ценность 6:
  складывает остаток прогона параллельно после кандидата 1. Неопределённость 2:
  компоненты независимы по замеру, открыты вывод ошибок и порядок стопа. После
  кандидата 1. Проверка агентская: время команды `test` не дольше самого
  тяжёлого компонента с запасом в треть, замер в файле задачи.
- кандидат 3 (task, M, R=38: 25+6+3+0+4). Разгрузка тяжёлых юнитов devkitctl
  по профилю: devkitctl_test, update_test, rules_test. Вероятные приёмы: сборка
  стабов и распаковка шаблонов один раз на процесс, переиспользование
  чекаута-образца вместо нового git init в каждом тесте. Ценность 6: добивает
  самый тяжёлый юнит, без него порог 120 с держится впритык. Неопределённость 3:
  где сидит время, покажет профиль, заранее не известно. После кандидатов 1 и 2.
  Проверка агентская: самый тяжёлый класс укладывается в 40 с, счёт тестов
  не срезан, финальный замер `time` команды `test` укладывается в 120 с.

оценка: 3 кандидата (3 M), week_all 3-9 из 20, week_max 4.5-9 из 8; рамка
сходится, верх week_max на пункт выше потолка при нижней границе 4.5
