# DK-1675: разбор сохранённых ревью

## Результат

В четырёх парах обе версии нашли все 12 заложенных дефектов. Ложных замечаний
по проверяемому свойству 12 контрольных решений нет. Новая версия получила
228 записей по правилам, по 57 на каждый проект. В одной записи обнаружено
противоречие между статусом и основанием. Превосходство новой версии в поиске
дефектов этим сравнением не установлено.

Исходные отчёты сохранены в [наборе результатов](DK-1675.behavior-evidence.json).
[Подробная оценка](DK-1675.behavior-assessment.json) содержит ссылки на
замечания, состояния строк аудита и хеши входных файлов. Ожидаемые ответы
взяты из [oracle.json](../../tools/obeycheck/testdata/review_cases/oracle.json).
Исторические отчёты не исправлялись.

## Проверка двенадцати случаев

|---|---|---|---|---|
| 1 | Имя обещает скидку, функция начисляет налог | r01 F1 | r02 п. 2 | total_with_tax использует ставку |

| 3 | Лишние id и avatar_blob в SELECT | r01 F4 | r02 п. 1 | WHERE/ORDER BY не расширяют проекцию |
| 4 | Гонка между SELECT и UPDATE резерва | r03 R1 | r04 резервирование | Зависимые вставки охвачены транзакцией |
| 5 | Репозиторий определяет бизнес-скидку | r03 R3 | r04 правило скидки | Готовая сумма сохраняется без пересчёта |

| 7 | Новая ручка расширяет deprecated-путь | r05 F1 | r06 п. 1 | XML escape нужен старому клиенту |
| 8 | Настоящая SQLite в группе unit | r05 F3 | r06 п. 3 | SQLite допустима в integration |

Для каждого контрольного решения оба ревью содержат объяснение допустимости.
Дополнительное замечание о другом свойстве того же кода оценивается отдельно.
Например, r05 предлагает явно закрыть SQLite-соединение, но признаёт верным
размещение теста схемы в integration.

## Архитектура и применимость правил

Во всех восьми отчётах есть архитектурный вывод с конкретными фактами.
В orders рассмотрены атомарность, зависимые вставки и граница ценовой политики.
В policy различены поддержка старого XML и развитие deprecated-механизма.
В claims различены изменяемые продукты, динамический лимит и статическая схема.
Зелёные check.py не послужили основанием принять эти решения.

Четыре аудита новой версии содержат по 57 различных ID без pending.
Прочитаны основания применимости и результаты строк. Причины неприменимости
связаны с отсутствующими механизмами либо ненормативными заголовками.
Исключение для обязательного context проверено как применимое правило.
Для r07 сохранены два снимка с одинаковыми строками; они учтены один раз.

В r05 строка common-architecture:ARCH-006 имеет результат violated.
Основание называет workers=0 и workers=-3, но признаёт их допустимую семантику
неопределённой. В самом замечании F5 запрещённый диапазон также не утверждается.
Это недоказанное нарушение конкретного инварианта. Пробел описания настройки
подтверждён отдельно по ARCH-005/025. В audit.md добавлена проверка согласованности
статуса, основания и замечания с этим примером. Неизвестный необходимый критерий
остаётся pending до выяснения.

## Проверка механики

На слитой реализации повторены существующие интеграционные проверки.
Группа TestReviewAuditIntegration прошла за 17,6 с вместе с обвязкой.
Отдельные проверки taskctl прошли за 6,4 с.
Они проверяют отказ без отчёта и при пропущенном правиле, принятие полного
отчёта на доске и без доски, обновление снимка и изменение кода, требований
или стандартов. Тестовые выводы синтетические; эти прогоны проверяют механику
команд и не доказывают истинность наблюдений ревьювера.

## Пределы вывода

На каждый сценарий есть одна завершённая пара. Повторяемость результата
и статистическое превосходство не измерены. r10 исключён из парного сравнения;
для него нет завершённого ответа новой версии в том же повторе.

Обоим вариантам явно поручили архитектурный вывод. Поэтому эти результаты
не показывают, насколько часто агент вспомнит об архитектуре без подсказки.
Код, запрос и проектные документы в каждой паре совпадают побайтово;
редакции общих стандартов и скилла различаются намеренно.

Старые правила запускались с новым taskctl. В r04 команда audit не смогла
разобрать общие правила без устойчивых ID. Находки по одинаковому коду можно
сопоставить, но отсутствие машинного аудита в старой версии нельзя целиком
приписать поведению ревьювера.

Разбор выполнен по сохранённым ответам с известными ожидаемыми результатами.
Сам разбор сохранённых ответов не потребовал новых ревьюверов и судей. Поправка audit.md проверена одним дополнительным прогоном policy на
gpt-6.1-sol по отдельному разрешению пользователя. Результаты исходной версии
сохранены с обнаруженным противоречием. Устойчивость поведения последующих
ревью этим одиночным прогоном не установлена.

## Проверка поправки на Sol

По отдельному разрешению пользователя выполнен один новый policy на
`gpt-6.1-sol` с усилием medium. Дополнительные агенты отключены.
Модель не получила ожидаемые ответы и сведения о найденном противоречии.
Исходники учебного проекта остались прежними. Модельный судья не запускался.
[Полный результат](DK-1675.policy-sol-evidence.json) содержит параметры,
отчёт, 57 строк аудита, проверочный сценарий и вывод команд.

Ревьювер сохранил все три ожидаемых замечания и объяснил допустимость
XML-исправления, интеграционного теста схемы и env/file адреса.
ARCH-006 имеет результат checked с проверками XML/CSV. В основании указано,
что диапазон workers не выдумывается. В замечании F6 прямо сказано,
что REQUEST не устанавливает допустимый диапазон и значения 0 или -3
сами по себе не объявлены дефектом. Статус и основание согласованы.

В учебном аудите ARCH-007, ARCH-022 и TEST-002 оставлены pending.
Исторический XML-код и прикладные потребители настроек в примере отсутствуют;
создание git notes и worktree запрещено песочницей. Ревьювер вынес эти пределы
в ACCEPTANCE.md и не записал чистый вердикт. Эти ограничения учебного проекта
сохранены в результате и не перенесены в утверждения о проверенной реализации.

Узкий критерий поправки выполнен. Поведенческие проверки DK-1675 выполнены в объёме четырёх сохранённых пар
и одного дополнительного policy. Преимущество
в поиске дефектов и повторяемость не заявляются. Практическая приёмка скилла
на рабочих изменениях остаётся за пользователем.
