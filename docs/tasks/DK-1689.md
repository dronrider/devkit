# DK-1689: Ревью проверяет обоснование решения независимо от его описания

## Что происходит

При разборе реального примера ревью сначала замечает избыточность конфигурации, затем снимает архитектурный вопрос из-за упоминания механизма в постановке. Соответствие выбранному способу подменяет проверку необходимости этого способа. Существующие сценарии не сравнивают одинаковый код с разной формулировкой постановки.

## Чего хотим

Подключённый к разным проектам review отличает цель пользователя, обязательный внешний контракт и предложенный способ реализации. Для настройки прослеживаются независимый выбор, доступные данные, потребитель и необходимые загрузки. Реальный проект используется для выявления класса ошибок; его код и данные в devkit не копируются.

## Границы

Скилл review и его справочники, переносимые учебные проекты и сценарии obeycheck. Без изменения кода рабочего проекта, схемы аудита и новых модельных запусков в этом проходе. Машинная полнота отчёта не объявляется доказательством правильности архитектуры.

## Развилки

Пользователь уточнил предмет работы: улучшать devkit для разных проектов. Новые модельные прогоны требуют отдельного согласования после подготовки проверяемого результата.

## DoD

- Процедура проверяет обоснованность способа реализации даже при его упоминании в постановке; обязательный контракт учитывается явно.
- Есть один обезличенный проект и два варианта постановки с одинаковым кодом. Ожидаемые ответы проверяют переносимость проверки, избыточные настройки и ненужные загрузки, а также допустимые ограничения.
- Локальные проверки подтверждают фактические дефекты примера и корректность контрпримеров; ответы не попадают во вход ревьювера.
- Документация различает проверку учебного проекта и проверку поведения агента. Улучшение поведения без отдельного прогона не заявляется.

## Ранг

`50+7+2+5+4 = 68`, P1.

- Серьёзность 50: архитектурное ревью подменяется соответствием описанию реализации.
- Ценность 7: общий путь ревью разных проектов.
- Неопределённость 2: известен сбой решения, эффект поправки требует поведенческой проверки.
- Поправка на баг 5: пропуск воспроизведён в текущем разборе.
- Рычаг 4: процедура используется исполнителями разных проектов.

## Ход работы
- Уточнена общая процедура review. Нужный результат отделяется от обязательного внешнего контракта и предложенного механизма. Архитектурный вопрос не снимается одной ссылкой на вариант постановки. Для конфигурации прослеживаются доступные поля, потребители и лишние загрузки.
- Подготовлен обезличенный проект projection и сценарии 85/86. Отличается только REQUEST.md; код и проектные стандарты побайтово одинаковы. Ожидаемые ответы и тесты свойств в копируемый проект не попадают. Кода и данных рабочего проекта в примере нет.
- Семь локальных проверок свойств проекта прошли; авторский check.py также зелёный. Проверены обе подготовки сценариев, парсер obeycheck --list и проверки review. Основной текст занимает 17020 из 18000 символов. Подробности в [локальном отчёте](DK-1689.local-evidence.json).
- Модельных запусков не было. Эти результаты подтверждают корректность учебного материала, но не улучшение поведения агента. Поведенческий зачёт не записан; независимое ревью и публикация в main остаются следующим этапом.

## Сценарий проверки

Запустить локальные проверки учебного проекта и статические проверки скилла. Проверить, что оба сценария копируют один проект, но разные постановки, а ожидаемые ответы остаются вне проекта. Живые ответы агентов в этом проходе не получать и поведенческий зачёт не записывать.
