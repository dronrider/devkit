# DK-1703: Полный прогон перед merge выполняется один раз на проверенном дереве

## Что происходит

Подтверждены два вида лишних запусков. В DK-1694 13 ноября сначала прошёл отдельный полный прогон 18/18 за 16м56с, затем shipctl merge заново запустил полный набор на таком же коде вне docs; второй запуск завершился красным через 6м03с. В DK-1271 три слияния на одном SHA f041a014ac8e потратили суммарно 34м52с и повторяли TestDashboardSmokeSayEndedNoTask. Менялась параллельность, исправления кода между попытками не было.

Причина первого случая: произвольный parallel.py в рабочем дереве и штатный merge не имеют общего подтверждения; merge обоснованно проверяет заново в fresh tree и временном HOME. Причина второго: факт неуспеха не привязан к точному входу прогона и сам по себе не запрещает новый дорогой запуск.

Сейчас tools/shipctl/ops.go cmdMerge в блоке подготовки и тестов всегда создаёт freshTestRun и вызывает test; tools/shipctl/testlog.go testRunRecord не хранит проверенный tree, команду и окружение. internal/freshtree уже предоставляет единый механизм изоляции. Доказательства аудита сохранены в /private/tmp/devkit-double-test-audit-20261113/findings.json; постоянные факты изложены выше, временный файл не является единственным основанием задачи.

## Чего хотим

У исполнителя один официальный путь полного предпрогона, одинаковый с тестовым этапом merge. После успешного полного прогона merge использует его подтверждённый результат при неизменном входе. Повторный красный запуск на том же входе автоматически не начинается; видны причина и предыдущий отчёт. Точечные тесты в ходе разработки сохраняются.

## Границы

Один локальный репозиторий и существующее окружение freshtree, без общего распределённого кеша и переноса подтверждений между машинами. Предлагаемый CLI: shipctl test <ID> (название согласовать с существующими командами при реализации), использующий общую с merge подготовку финальной ветки. На первом проходе вход включает полный Git tree, а не только SHA коммита: равное содержимое допускает смену SHA, изменённые docs также инвалидируют подтверждение. Полный набор содержит doctor и проверки скиллов; без доказательства нельзя исключать всё docs из входов.

Практическое предотвращение DK-1694: инструкции убирают отдельный raw parallel.py перед merge; после целевых тестов и оформления результатов исполнитель вызывает merge напрямую либо официальный предпрогон на окончательном дереве. Старый raw stdout не превращается в подтверждение. Общее игнорирование docs и повторное использование отдельных зелёных компонентов после общего падения вне границ.

## Развилки

Дополнительных действий, доступов или решений человека не требуется: пользователь поручил устранить дублирование. Локальный формат подтверждения и имя команды выбираются исполнителем в рамках указанного контракта. Если общий код подготовки test/merge нельзя выделить без изменения очереди, первый небольшой коммит ограничивается запретом standalone full в инструкциях и фиксацией точных входов/результата; дальнейшая часть остаётся открытой, задача по одному изменению инструкций не закрывается.

## DoD

- Официальный предпрогон и merge используют одну подготовку: актуальный main, готовый коммит после rebase, freshtree и те же нормализованные ENV/команда. Предпрогон не сливает, не выкатывает и не переводит задачу в Check.
- Подтверждение записывается атомарно лишь после завершения запуска и содержит схему, ID запуска/задачи, tested SHA и полный tree hash, точную команду, версию политики freshtree, локальный профиль runtime (платформа, версии реально используемых toolchain и существенные переменные), время, исход и ссылку на доступный вывод. Секреты и временные HOME/Tree пути в профиль не входят.
- При точном совпадении входов и свежем успешном результате merge не запускает test повторно, сообщает ID/возраст использованного запуска и проходит все прочие ворота заново. Свежесть ограничена одним локальным окном (предлагаемый срок 60 минут, один параметр политики). До ff повторно проверяется соответствие итогового дерева; catch-up кода исключает использование старого результата.
- Любая правка дерева (включая тесты, конфиги, docs), команды, версии окружения/политики, истёкший срок, отсутствующий/повреждённый/незавершённый результат означает отсутствие зелёного подтверждения; по правилам выполняется новый прогон либо понятный отказ. Произвольный старый test-runs.log не даёт разрешения слияния.
- Красный завершённый запуск на том же входе возвращает прежний отказ/лог без повторного full. Явный повтор с непустой причиной разрешён, записывает новое событие и никогда не превращает красный исход в зелёный; автоматический load-retry очереди должен либо явно пользоваться ограниченной существующей политикой с записанной причиной, либо прекратиться, не обходя новый gate.
- Конкурентные test/merge одного входа не запускают два full: существующий замок конвейера либо общий замок запуска сериализует проверку и повторно читает завершённый результат после захвата.
- Полный прогон остаётся обязательным на новом входе; нет --test true, пропуска проверок или зачёта частичного результата. В инструкции исполнителя записан один официальный full-путь; при реализации самой задачи целевые тесты, затем один штатный полный прогон при merge.

## Сценарий проверки

1. В изолированном fixture-репозитории штатный test выполняет безопасную короткую команду со счётчиком один раз; merge на том же входе не увеличивает счётчик, сливает и указывает использованный запуск. Проверка не требует запуска дорогого набора дважды.
2. Новый SHA при том же полном tree допускает reuse; изменение code, test, config и docs по отдельности, команды, runtime-профиля или срока исключает reuse. Незавершённая/повреждённая запись и старый формат журнала не дают зелёного решения.
3. Красная команда увеличивает счётчик до 1; повторные обычные test/merge оставляют 1 и возвращают предыдущий отказ. Явный retry с причиной даёт 2; причина остаётся в данных. Частичный зелёный вывод при общем nonzero не разрешает merge.
4. Два конкурентных вызова на одинаковом входе дают один фактический запуск и согласованный исход. Изменение main с кодом до ff не проходит со старым подтверждением; обычный catch-up документов проверяется согласно полному tree-контракту.
5. Точный исполняемый сценарий с именами добавленных регрессионных тестов фиксируется исполнителем перед обкаткой; отдельная сессия запускает его штатным devkitctl test. Дорогой полный набор выполняется один раз штатным merge, не отдельной предварительной командой.
