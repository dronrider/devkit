# DK-1720: Первая реплика нового чата задачи уходит в старый разговор

## Что происходит

17 ноября 2026 пользователь создал новый чат DK-1570 и отправил «Нужно довести задачу до завершения. Я согласовал макеты где подписка отображалась свёрнутой, но дальше работа не двинулась. Продолжай».

Ожидался запуск нового чата с полной первой репликой и подтверждением доставки. Реплика осталась на экране недоставленной, хотя индикатор этапов задачи заработал.

В dashboard.log в 19:07:06 записана отправка команды «Продолжай выполнение DK-1570» старой живой голове. Новый чат blank-757fd674-9507-4330-baee-4d4af9776691 остался заготовкой. Полный текст есть в журнале said задачи. В транскрипте старого разговора есть только команда «Продолжай выполнение DK-1570». Полный текст пользователя модели не доставлен; клиент старой подписки остался на повторе HTTP 429 из-за исчерпанного баланса. Индикатор задачи не доказывает доставку в выбранный чат.

## Чего хотим

Первая реплика нового чата задачи запускает выбранный чат и поступает его исполнителю целиком. Доставка и индикатор работы согласованы с фактическим адресатом. Ошибка запуска сохраняет реплику для безопасного повтора.

## Границы

Проверяем создание нового чата задачи при существующем живом или ожидающем чате той же задачи. Саму реализацию выбора подписок DK-1570 эта задача не меняет.

## DoD

- Новый чат задачи получает первую реплику целиком при наличии другого живого чата той же задачи. Старый чат от этой отправки не возобновляется.
- Тест проверяет выбранный адресат, текст и подтверждение доставки для обоих протоколов. Терминальный запуск сохраняет квитанцию до внешнего эффекта, повтор не дублирует успешно принятую реплику. Дорога app-server сохраняет прежнюю семантику повторов. Неизвестный исход не выдаётся за доставку.
- Сохранены штатные ответы из существующего чата и со страницы задачи. Регрессия воспроизводится на старой версии и проходит на исправленной.
- Для инцидента DK-1570 выяснены фактический адресат и состояние реплики. Повторная отправка допускается после проверки отсутствия успешной доставки.

## Ранг

`50+4+2+5+2 = 63`, P1.

- Серьёзность 50. Работа запускается в другом чате; выбранный пользователем новый разговор не начинается.
- Ценность 4. Создание чата задачи входит в регулярную работу через дашборд.
- Неопределённость 2. Ошибочный маршрут подтверждён журналом, требуется проверить границы запуска и подтверждения.
- Поправка на баг 5. Пользовательский инцидент подтверждён состоянием заготовки и журналом сервера.
- Рычаг 2. Исправление восстанавливает последующие первые отправки чатов задач.

## Приёмка

- вид: agent
- Синтетический проект и тестовый отправитель проверяют запуск, точный текст и адресат. Живой чат читается через API без повторной отправки пользовательского текста.

## Условия

Условий, посильных только человеку, не найдено. Журналы, реплика и состояние чатов доступны локально. Исправление и выкат разрешены текущим запросом и autonomous проекта.

## Ход работы

- Маршрут ожидания задачи перехватывал первую реплику нового чата. Новый
  адрес теперь сохраняется при старом живом, ожидающем и кончившемся чате.
- Терминальный запуск хранит отдельную файловую квитанцию до внешнего
  эффекта. Файловый замок общий для двух входов отправки. Поздний черновик,
  ошибка записи заготовки, уборка списка и перезапуск сервера квитанцию не стирают.
- Повтор возвращает прежнюю сессию или проверенное живое окно. Другая
  реплика получает HTTP 409. Неизвестный исход сохраняет текст и причину на
  пузыре без автоповтора, гасит занятость и переживает перезагрузку.
  Доказанный отказ до создания клиента допускает автоматическую новую попытку.
  Смерть без подтверждения доставки и текст терминала доказательством отказа
  не считаются. Эти границы относятся к терминальной дороге; app-server
  сохраняет прежнюю семантику повторов.
- Нативный хук спавна collaboration в этой среде не записывает этап
  разработки. Этап вручную не подменялся.
- `regcheck --base HEAD -- devkitctl test tools/dashboard -run TestTaskBlank -count=1`
  подтвердил падение тестов на старом коде и успех на исправленном.
- Пять мутаций маршрута, адреса, отпечатка, повтора и замка запуска дали
  красные тесты. После каждого прогона исходники восстановлены.

## Ревью

Уровень 2 до fbdf87c: Проверены маршрут панели, терминальный и app-server запуск, повтор, хранение receipt и соседний /say; риски частичного отказа и жизненного цикла блокируют принятие.

- [возврат: реализация, 2026-11-17] блокирует: tools/dashboard/chats.go:2504,2008. На проверенной версии fbdf87ce1 запуск startManaged происходит до сохранения StartKey/Tmux, а chatBlankLift при ошибке chatStoreWrite только пишет журнал и ручка возвращает HTTP 200. Если fake tmux после new-session заменит файл <blank>.lock каталогом, JSON останется прежним Blank без Tmux; повтор POST /chats запустит второго клиента. Такой же промежуток есть при рестарте процесса после запуска до lift. Нарушены ARCH-006, ARCH-010, ARCH-012 и ARCH-013: для внешнего эффекта нужна надёжно сохранённая квитанция до запуска с безопасным поведением при неопределённом исходе. startManaged error сам по себе не доказывает отсутствие клиента (guardian timeout/status-read error). Проверить отказ записи, рестарт и неопределённый исход запуска: ответ не утверждает доставку, повтор не создаёт второй процесс.
- [возврат: реализация, 2026-11-17] блокирует: tools/dashboard/chats.go:2462 и tools/dashboard/appchat.go:537. Общая проверка Tmux/Grown выполнена до ветки app-server, но appStartRecord сохраняет Grown без StartKey. Поэтому точный повтор первой отправки через blank после принятого app-server запуска получает HTTP 409; после ошибки appSpawn повтор той же недоставленной реплики также блокируется, поскольку Grown записан до запуска клиента. Это регрессия существующей дороги и нарушение ARCH-007, ARCH-012 и ARCH-013. Ограничить терминальный receipt своей дорогой либо реализовать полноценный receipt app-server. Проверить appEnv+blank: успешный запуск с потерянным ответом и отказ запуска с последующим повтором должны иметь определённый безопасный исход без потери текста.
- [возврат: реализация, 2026-11-17] блокирует: tools/dashboard/chats.go:2454,3437,4270. Новый замок и проверка StartKey защищают только POST /chats, но поддерживаемая дорога POST /chats/<blank>/say при отсутствии транскрипта вызывает chatRaiseSay и запускает клиента без того же замка и проверки уже принятого Tmux/StartKey. Два разных msg_id либо смешанные /say и /chats до регистрации транскрипта могут создать два процесса одной заготовки; msg_id-дедупликация этого инварианта не защищает. Нарушены ARCH-006, ARCH-010 и ARCH-013. Общую защиту начала записи нужно применить на всех её входах. Проверить последовательный повтор /say с другим msg_id и детерминированный конкурентный /say плюс POST /chats: второй старт не выполняется и другая реплика получает явный отказ.
- [возврат: реализация, 2026-11-17] блокирует: tools/dashboard/chats.go:1746 и chatblankroute_test.go:94. Принятый терминальный запуск очищает Draft, но chatBlankList вызывает chatBlankSweep и сразу удаляет его запись при умершем tmux без Grown. После обычного GET списка точный повтор POST /chats теряет квитанцию и получает 409 про другой проект вместо прежнего адреса; новый тест смерти клиента обходит список и этот жизненный цикл не проверяет. Нарушены ARCH-008 и ARCH-013 и заявленный README контракт повтора после смерти клиента. Сохранить квитанцию на определённый срок, согласовать уборку и документацию. Проверить смерть клиента, GET списка, рестарт сервера, затем точный повтор без второго запуска с прежним адресом.

## Сценарий проверки

1. В свежем дереве с временным HOME прогнать стенды панели и API:

```sh
devkitctl test tools/dashboard -run 'TestTaskBlank|TestChatBlank|TestStaticTaskReplyWithoutLead' -count=1
```

Панель запускает выбранный новый чат при старом живом, ожидающем или
кончившемся разговоре. Проверяются точный многострочный текст, задача,
адрес заготовки, модель и подписка. Ошибка сохраняет реплику без отметки
доставки, успех переносит её в новый разговор. API сохраняет черновик
при отказе и принимает повтор одного запуска без второго клиента.
Две разные параллельные реплики дают один запуск и один явный HTTP 409.
После смерти клиента без данных о доставке повтор получает unknown и
не запускает дубль. Проверяются смерть, GET списка, уборка заготовки,
новый экземпляр сервера и повтор без поля id. После появления grown
повтор открывает прежнюю сессию. Чужой новый жилец того же имени tmux
не становится адресатом. Проверяются отказ записи до запуска, ошибка
сохранения после внешнего эффекта, сигнал прямого запуска и неизвестный
исход guardian.
Панель сохраняет исходную глубину high при отказе, смерти и повторе,
показывает причину unknown и не повторяет его после перезагрузки.
Штатные ответы из существующего чата и со страницы задачи остаются на своих дорогах.

2. После выката только чтением API и журнала проверить восстановление DK-1570.
Новый разговор должен быть связан с исходной заготовкой, моделью
`glm-5.3-flash` и подпиской `glm-code-2`. В его транскрипте должна быть полная
исходная реплика из раздела «Что происходит». В старом разговоре остаётся
только ошибочная команда продолжения. Во входе задачи не должно остаться
безадресной копии исходной реплики. Проверяющий не отправляет новых реплик
и не меняет состояния живых чатов.
