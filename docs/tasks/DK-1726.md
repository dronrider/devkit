## Что происходит

18 ноября пользователь открыл чат «Свёрнутая подписка в макетах», созданный
для DK-1570. В заголовке появилась задача DK-1725. Новые сообщения не
появляются в ленте. Ответа нет.

Ожидается продолжение того же разговора по DK-1570 с сохранением отправленных
реплик. Локальный API возвращает для сессии c99eba5f-e410-424f-ab39-8d85e2975d20
tasks и leads в порядке DK-1725, DK-1570. Запись запуска по-прежнему содержит
task=DK-1570, окно chat-DK-1570-2, модель glm-5.3-flash и подписку glm-code-2.
Клиент числится live и idle. Последняя запись нативного журнала датирована
18 ноября 02:45 по Москве. В ней исполнитель ждёт ревью исправления DK-1725,
которое понадобилось при доводке DK-1570. Судьба новых реплик пока не установлена.

DK-1720 уже устранил неверный маршрут первой реплики заготовки. Здесь речь
об установленном разговоре после работы над побочной задачей. DK-1615 содержит
общий переход к отметкам доставки, а этот инцидент требует установить и
устранить конкретную причину смены привязки и недоступности разговора.

## Чего хотим

Чат, созданный для DK-1570, сохраняет эту основную привязку, пока пользователь
её не сменит. Работа исполнителя над препятствием не подменяет адрес разговора.
Новые реплики сохраняются и попадают выбранному собеседнику. Лента показывает
отправленный текст, подтверждённое состояние доставки и ответ. Если клиент
ждёт сброса лимита подписки, панель показывает причину ожидания.

## Сценарий проверки

Агентская часть проходит в свежем дереве с временным HOME. Первый тест
проверяет API после побочной работы, ручной выбор и отвязку после compact.
Проверяется хронология заказов из двух домов реестра. Семья TaskMessage
проверяет запуск головы и доставку соседним задачам. Сценарии с заказом, старым
журналом, деревом, ручным выбором, отвязкой и compact сравнивают API Leads
и taskHead с реальным нативным подхватом. Историческое касание остаётся в Tasks
и не считается владением входом задачи.
Браузерный тест открывает production-композер с подставленным API.
Живой простаивающий чат с вопросом побочной задачи получает один запрос
/say по прежнему SID, текст и msg_id. Сообщение появляется в ленте, поле очищается. Тесты квоты проверяют реальную
строку GLM1310, отрицательные примеры, причину ожидания в списке и /status.
У совмещённого Weekly/Monthly срок неизвестен; у прежнего недельного лимита
сохраняется срок подписки исходного транскрипта. В браузере причина заменяет
счётчик, а после продолжения хода счётчик возвращается.

```sh
devkitctl test tools/dashboard -run 'TestTaskMessage|TestHeadTasksAnswersLikeTheHook|TestChatKeepsOrderedTaskAfterSideWork|TestChatPrimary|TestChatLeadsMatchNativeAfterManualAndCompact|TestChatSideWorkComposer|TestQuotaVendor1310|TestQuotaWeeklyStatusUsesTranscriptHarness' -count=1 -v
```

После выката проверить основную задачу DK-1570 у исходного SID в API и панели.
Фактическое восстановление набранной реплики требует отдельной сверки живого
поля и журнала. Подтверждение ответа записывается после этой сверки. Зелёный стенд и одна
принятая пользовательская реплика не закрывают DoD ответа в той же ленте.
При исчерпанной квоте этот пункт остаётся открытым до ответа провайдера
и проверки страницы после обновления.


## Приёмка

- вид: mixed
- барьер «событие»: реальный ответ в восстановленной GLM-сессии после снятия
  лимита провайдера в неизвестный момент. Weekly/Monthly не определяет срок.
  - игрушечные часы: не годятся, проверяют местные сроки, но не снимают лимит провайдера
  - синтетические входящие: не годятся, проверяют доставку тестового текста, но не реальный ответ этой учётной записи
  - стенд с подменой события: не годится, не подтверждает доступ реальной учётной записи к модели после снятия лимита

После выката агент проверяет API поднятого дашборда у исходного SID. Основная
задача должна быть DK-1570, принятая реплика должна сохраниться в нативном
журнале и API по одному разу. При том же отказе провайдера /status должен
показывать причину квоты вместо busy, а открытая панель должна получать её
из опроса. Проверка UI выполняется против выкаченного артефакта.

Ответ после принятой реплики и его сохранность в той же ленте после обновления
страницы остаются открытыми до реального события. Для этой проверки нельзя
подставить тестовый ответ или повторно отправить принятую реплику.
