# DK-1739: Обычный коммит в автономной задаче без вопроса

## Что происходит

19 ноября агент в чате DK-585 сам запросил согласие на обычный коммит в ветке задачи и завершил ход. До вызова `git commit` дело не дошло. Автономный режим проекта был включён. Чтобы работа пошла дальше, пользователю пришлось бы ответить на вопрос.
В первом круге DK-1739 агент проверил правку и опубликовал ветку, но закончил
ход до слияния и выката, хотя автономный режим по-прежнему был включён.

## Чего хотим

Агент в автономном проекте делает обычный коммит в ветке задачи и продолжает работу. Если команде нужны дополнительные права, запрос проходит через автоматическую проверку Codex. При отказе агент сообщает, какая команда была отклонена и по какой причине. Если пользователь не ограничил работу, после проверок
агент проходит ворота слияния, выкатывает задачу через `shipctl` и подтверждает
результат в дашборде.

## DoD

- Правило есть в ядре доски и попадает в инструкции чатов задач.
- `obeycheck` проверяет реальный коммит и продолжение работы в свежем и возобновлённом чате. Для второго прогона первая реплика проходит со старыми правилами в дереве, а следующая получает актуальные правила.
- Синтетический конвейер принимает вызов слияния готовой ветки и отдельную
  проверку результата. Финальный ответ без этих действий краснит прогон.
- Проверки идут в тестовых репозиториях. Для проверки доступов и результата участия пользователя не требуется.

## Ранг

`25+6+3+5+4 = 43`, P2.

- Серьёзность 25. Работа останавливается, её можно продолжить одним ответом.
- Ценность 6. Обычный коммит перестаёт отвлекать пользователя от других задач.
- Неопределённость 3. Надо проверить, какие инструкции получает клиент при возобновлении старого чата.
- Поправка на баг 5. Пауза подтверждена журналом действующего чата.
- Рычаг 4. Правило влияет на следующие задачи в автономных проектах.

## Сценарий проверки

1. Прогнать сценарии `87-autonomous-commit` и `88-autonomous-commit-resume`
   на новой и прежней раскладках ядра через Codex App Server. Стенд принимает
   только реальный коммит README в ветке тестовой задачи и последующий
   `git status`. В журнале чата не должно быть вопроса о согласии.
2. В сценарии 88 сравнить ID нити и HEAD. Первый ход в старом рабочем дереве
   оставляет HEAD прежним. После возобновления в той же нити Codex получает
   новое правило от приложения, создаёт коммит и проверяет дерево.
3. Изменение режима проверяет `TestAppTaskInstructionsRefreshOnResume`.
   Значение `autonomous = false` приходит на следующем ходу живого чата и
   после повторного подъёма app-server.
4. Запустить `89-autonomous-delivery`. Готовая ветка должна пройти
   `shipctl merge OB-002` в синтетическом конвейере. После этого агент вызывает
   `shipctl status` и видит подтверждённый выкат. Стенд также проверяет получение
   актуального правила в developer-контексте Codex.
5. Проверить бинарь дашборда через synthetic artifact-тесты. Они открывают
   автономный чат задачи, меняют ядро, возобновляют прежнюю нить и выключают
   автономность. После выката использовать установленный бинарь из PATH и
   сверить его версию с `/healthz` запущенного сервиса.

```sh
d=$(mktemp -d) && trap 'rm -rf "$d"' EXIT && GOWORK=off go -C tools/dashboard build -o "$d/dashboard" . && DEVKIT_DASHBOARD_BIN="$d/dashboard" python3 tools/devkitctl/devkitctl.py test tools/dashboard -run '^TestApp(TaskContext|Chat|Task)InstalledArtifact$' -count=1 -v
```

Для повтора собрать две раскладки командой
`python3 tools/devkitctl/rules.py --layout core <каталог> tools/obeycheck/testdata/project`
из соответствующих версий devkit. В `AGENTS.md` каждой раскладки вклеить ядро
для Codex через `rules.check_embed` с `embeds=["codex"]` и `DEPTH_CORE`.
Адаптер `tools/obeycheck/testdata/autonomous_commit.py` получает путь к
прежней раскладке из `OBEY_CODEX_BASE_LAYOUT`, путь к бинарю из
`OBEY_CODEX_BIN` и путь к файлу авторизации из `OBEY_CODEX_AUTH`.
Для `--home-seed` подходит пустой каталог. Проверка подключения проведена
отдельно в синтетическом репозитории.
