# DK-1750: shipctl check-run запускает отдельную приёмку в Codex

## Что происходит

20 ноября 2026 года `shipctl check-run DK-1748` завершился ошибкой.
Для приёмки требовалась свежая сессия Codex. При попытке запустить
проверяющего через `taskctl run` потребовалась секция `[head]`.
В профиле Codex такой секции нет. Сценарий удалось выполнить из отдельной
сессии Codex, запущенной вручную.

## Чего хотим

`shipctl check-run` запускает проверяющего в свежей сессии Codex, если
этот харнес указан в вердикте `agentctl check`. Проверяющий получает заказ
приёмки. Модель и усилие берутся из вердикта.

## DoD

- Профиля Codex без секции `[head]` достаточно для запуска через
  `shipctl check-run`.
- При закрытии задачи сессия проверяющего определяется по её собственному ID.
- Путь запуска для харнесов с секцией `[head]` продолжает работать.

## Ранг

`50+6+2+5+0 = 63`, P1.

- Серьёзность 50. Автоматическая приёмка останавливается. Для обхода нужно
  вручную запустить и учесть сессию.
- Ценность 6. Задета регулярная приёмка задач, для которых выбран Codex.
- Неопределённость 2. Причина найдена. Нужно проверить контракт запуска.
- Поправка на баг 5. Отказ воспроизведён командой на выкаченной сборке.
- Рычаг 0. Работа восстанавливает существующий сценарий приёмки.

## Ход работы

- Вычитка: 1 файл, 5 правок, 0 пометок, 2026-11-21.
- Запуск Codex вынесен в отдельный процесс с замком задачи и журналом. Отметка
  проверки получает ID потока Codex. Дальше нужны ревью и живой прогон после
  выката.

## Ревью

Уровень 2 до 002cbf2: Проверка отдельной сессии, стыка JSON, замка, остановки и независимости проверяющего

- [возврат: реализация, 2026-11-21] блокирует: при запущенном Codex штатный «Стоп» сохраняет Stopped, но handleRunStop ищет только appTask и tmux, а worker checkcodex.go:175 в них не зарегистрирован; stopWithoutPipeline возвращает 404 или 409, проверяющий продолжает работать и держит замок. Это нарушает сохранение остановки существующего запуска. Проверить живым процессом: после «Стоп» группа завершена, замок снят и повторный автоматический запуск не происходит.
- [возврат: реализация, 2026-11-21] блокирует: при ошибке state.Start, state.Save или чтения JSON checkcodex.go:168-184,203 завершает только процесс agentctl exec через cmd.Process.Kill; agentctl exec запускает Codex дочерним процессом (tools/agentctl/exec.go), который может пережить родителя и отпускание замка. Следующий тик тогда поднимет второй прогон. Проверить на живом потомке, что при каждом таком отказе вся группа завершена до снятия замка.
- [возврат: реализация, 2026-11-21] блокирует: проверяющий запускается без DEVKIT_CHAT_SESSION_ID, CLAUDE_CODE_SESSION_ID и DEVKIT_TMUX (checkcodex.go:154), а agentctl plan выбирает только эти переменные или явный --sid (tools/agentctl/plan.go:95-110) и не читает CODEX_THREAD_ID. Поэтому обязательный для проверки план без ручного указания ID не создаётся. Проверить в настоящей свежей сессии Codex, что plan set/step/done работают с собственным ID сессии и не используют ID родителя.

## Сценарий проверки

1. Запустить стенд и убедиться, что строки PASS есть у `TestCheckRunCodexEntry`,
   `TestCodexCheckWorkerStartsFreshTurn`, `TestCodexCheckWorkerFailsBeforeTurn`,
   `TestCheckRunJSONForTheTick`, `TestOwnCodexSession` и
   `TestOpenKeepsCodexVerificationSession`.

   ```sh
   devkitctl test tools/shipctl -v -run 'TestCodexCheckWorker|TestCheckRun'
   devkitctl test internal -v -run 'TestOwnCodexSession|TestOpenKeepsCodexVerificationSession'
   ```

2. После выката запустить `shipctl check-run <ID>` для задачи в Check с
   вердиктом Codex. В отчёте должен быть ID нового потока и путь к журналу.
   Повторный запуск во время хода должен сообщить о занятом замке. В записи
   этапа проверки должен стоять ID этого потока, отличный от сессий разработки.
