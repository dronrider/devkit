# DK-191: taskctl/shipctl: команда перехода печатает следующий шаг конвейера

записан 2026-08-08

## Что происходит

Исполнитель-диспетчер окна второй подписки (живой прогон DK-180, 2026-08-08)
довёл код и отчитался «закрыта по коду», хотя доска показывала In progress и
ревью не звалось; ревью поехало только после пинка пользователя. Конвейер
описан прозой скиллов board-task/board-ship в расчёте на модель, которая
держит её в голове весь путь: правила словаря отчёта в текстах нет (греп по
kit/skills 2026-08-09, слова «готово» и «отчёт» там только про сценарии и
пачку), и на glm это всплыло в первый же день. Лечить дисциплину строкой
«не останавливаться между фазами» это заплатка под конкретную модель, она
держится ровно до модели, которая прочитает её иначе.

Второй случай за два дня (чат «Выполни DK-205», окно второй подписки,
2026-08-09), и там встал уже финал конвейера. Диспетчер на glm-5.2 довёл
задачу до готовности: ревью пройдено, замечание закрыто тестом, полный набор
зелёный, ребейз на свежий main. Затем прогнал `shipctl status`, увидел
свободную очередь и остановился со словами «пуш кода по правилам за тобой»,
хотя в `.devkit/deploy.local` стоит `autonomous = true`, а сам он часом
раньше констатировал «выкат автономный». Скилл board-ship с развилкой «кто
нажимает кнопку» за сессию не звался ни разу, решение принималось по
резидентному ядру, где исключение про автономный режим сказано одной строкой
в хвосте. Вывод `shipctl status` в точке решения не помог: там ветка,
worktree и очередь, а ветки autonomous и следующего шага нет. Готовая задача
провисела до пинка пользователя, и даже на прямой вопрос «работа идёт или
ждёшь меня» диспетчер повторил неверное обоснование.

## Чего хотим

Знание «что дальше» переезжает из прозы в вывод утилит, через которые проходит
любая модель: команда перехода печатает следующий шаг конвейера. Взял в работу
-> «сдача это Check: после кода ревью, слияние, выкат»; `shipctl merge` ->
«переведи в Check и прогони сценарий»; перевод в Check -> «прогони сценарий:
агентский закрывается сам, пользовательский ждёт человека». Подсказка приходит
свежей строкой ровно в момент, когда нужна, а не абзацем скилла, прочитанным
час назад. Паттерн в shipctl уже есть (advice.go, подсказка про regcheck при
слиянии bug-задачи), задача обобщает его на переходы статусов; точный список
переходов и тексты подсказок выбирает исполнитель по процедуре board-ship.
Подсказка на развилке слияния обязана учитывать флаг autonomous и называть
его ветку явно: при `true` следующий шаг это `shipctl merge <ID>` без
ожидания слова, при `false` ожидание команды пользователя. Печатать её
должен и `shipctl status`: по случаю DK-205 именно его диспетчер гоняет
перед решением о слиянии.

В скиллах вместо пересказа конвейера остаётся одна строка: что дальше,
печатает утилита, а отчёт цитирует доску, слова «готово» и «закрыта» допустимы
только при Check или закрытии. Эталонный промт окна не нужен: окну хватает
«возьми DK-X», дальше ведёт утилита, и при смене модели подгонять нечего.

Границы: агент, вставший молча без единой команды, подсказкой не ловится,
обнаружение повисшего окна (задача в In progress при замолчавшей сессии) это
отдельная тема и сюда не входит. Смежные DK-092 (ворота готовности как
предусловие merge) и DK-133 (единые ворота заведения строки) про отказы на
входе команды, эта задача про подсказку на выходе: место в коде общее, предмет
другой, не дубль.

## DoD

Команды переходов статуса (взятие в работу, слияние, перевод в Check,
закрытие) и `shipctl status` печатают следующий шаг конвейера; подсказки
перед слиянием называют ветку autonomous явно. В board-task, board-ship и
board-batch правило словаря отчёта одной строкой: отчёт цитирует статус доски.
Тесты на подсказки по стандарту devkit; сценарий проверки пишет исполнитель.

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick (квота: week_all 81%, снимок 0м назад, сдвига нет), 2026-08-09.
- Подсказки собраны в одном месте на утилиту: `nextStep` и `mergeFork` в
  `tools/shipctl/advice.go` рядом с подсказкой про regcheck, `nextAfterMove`,
  `mergeFork` и `nextAfterClose` в новом `tools/taskctl/advice.go`. Тексты
  вынесены из тел команд, чтобы ветка выбиралась по состоянию, а не по месту
  в коде, и проверялась юнитом без репозитория.
- Ветка выбирается по срочности: сломанный прод, задачи в Check, стоящий
  поезд, работа в In progress, пустая доска. Порядок держит табличный тест:
  на сбитом порядке он краснеет.
- Флаг `autonomous` taskctl читает сам, одним ключом из `.devkit/deploy.local`
  (полный разбор конфига остаётся у shipctl). Иначе подсказка взятия в работу
  либо молчала бы о развилке, либо звала бы shipctl ради одной строки.
- `merge --train` в подсказке не называет Check словом: тест
  `TestTrainMergeAndShip` ловит перевод доски по слову «Check» в отчёте, и
  подсказка сломала бы его на ровном месте.

## Сценарий проверки (агентский)

Проверяется на синтетическом проекте во временной директории, живая доска и
прод не трогаются. Утилиты собираются из ветки задачи, иначе проверялись бы
бинари из PATH.

```sh
W=/Users/rider/projects/devkit-dk-191; BIN=$(mktemp -d); export GOWORK=off
(cd "$W/tools/taskctl" && go build -o "$BIN/taskctl" .)
(cd "$W/tools/shipctl" && go build -o "$BIN/shipctl" .)
export PATH="$BIN:$PATH"
P=$(mktemp -d)/proj; mkdir -p "$P"; cd "$P"
git init -q -b main .; git config user.email t@t; git config user.name t
taskctl init --prefix XR --name "Песочница" >/dev/null
taskctl add --title "Подсказка конвейера" --type task --rank "50+5+0+0+0" --cost S >/dev/null
git add -A && git commit -qm seed
mkdir -p .devkit && printf 'deploy = echo катим\nautonomous = true\n' > .devkit/deploy.local
taskctl move XR-001 in-progress          # шаг 1
shipctl status | tail -1                 # шаг 2
printf 'deploy = echo катим\nautonomous = false\n' > .devkit/deploy.local
shipctl status | tail -1                 # шаг 3
taskctl move XR-001 check                # шаг 4
taskctl close XR-001 --date 2026-08-09   # шаг 5
```

Ждём на каждом шаге строку «следующий шаг», а на шагах 2 и 3 ещё и названный
флаг с его значением. Реальный вывод прогона 2026-08-09:

```text
== 1. взятие в работу при autonomous = true
XR-001: backlog -> in-progress
следующий шаг: код в дереве задачи (shipctl start XR-001), правка вместе с тестами, дальше ревью и слияние (shipctl merge XR-001); сдача это Check, а не «код написан». Слияние зовёт агент сам: в .devkit/deploy.local стоит autonomous = true, merge пушит и катит выкат, отдельного слова пользователя тут не ждут

== 2. shipctl status на развилке слияния
следующий шаг по XR-001: довести код с тестами, позвать ревью и слить самому (shipctl merge <ID>): в .devkit/deploy.local стоит autonomous = true, merge пушит и катит выкат сам, отдельного слова пользователя тут не ждут

== 3. тот же status при autonomous = false
следующий шаг по XR-001: довести код с тестами, позвать ревью, а слияние за пользователем: в .devkit/deploy.local стоит autonomous = false, агент останавливается на локальном коммите и ждёт команды

== 4. перевод в Check
XR-001: in-progress -> check
следующий шаг: прогнать сценарий проверки из docs/tasks/XR-001.md; агентский сценарий агент прогоняет сам и закрывает задачу (taskctl close XR-001), пользовательский ждёт слова пользователя

== 5. закрытие
XR-001 закрыта 2026-08-09, строка в архиве
следующий шаг: очередь выката свободна, следующая задача берётся с доски (taskctl list, дальше taskctl move <ID> in-progress)
```

## Ревью

- autonomousFlag в tools/taskctl/advice.go снимает кавычки через strings.Trim(val, `"'`), это не парная обвязка, как unquote() в shipctl/config.go, а независимый срез с обоих концов: на значении с несимметричными кавычками (например autonomous = 'true") taskctl считает флаг true и советует агенту слить самому, а shipctl/resolveDeploy на том же файле парсит autonomous=false и ждёт пользователя. Разошлись ровно в опасную сторону: подсказка про слияние без спроса пользователя расходится с тем, что реально сделает shipctl merge. Проверено сборкой обеих утилит на синтетическом проекте с .devkit/deploy.local, содержащим autonomous = 'true": taskctl move печатает 'Слияние зовёт агент сам ... autonomous = true', shipctl status тут же печатает 'слияние за пользователем ... autonomous = false'. Просьба выровнять разбор кавычек с shipctl (парная обвязка, а не срез с двух концов независимо).
