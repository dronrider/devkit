# DK-198: goal-run через Agent SDK вместо разбора вывода claude -p

записан 2026-08-09

## Что происходит

Оболочка витков цели поднимает `claude -p` и судит об итоге витка по его
текстовому выводу: из буферизованного stdout берётся последняя строка, и
маркер засчитывается, только когда она дословно равна `marker: <имя>`
(`kit/skills/goal-loop/goal-run.py`, разбор около строки 350). Контракт
держится на дисциплине текста сессии: маркер прозой, ограда примера или
лишний хвост дают «виток без маркера» и стоп цикла. Сам формат вывода
`claude -p` тоже не контракт и меняется релизами харнеса.

Смежное с записи черновика успело сдвинуться, разбор актуализирован
2026-08-10:

- DK-117 закрыта без SDK: ход витка пишет сама сессия строками
  `goal-run.py <ID> --say`, вариант со `stream-json` там отвергнут. Живой
  ход из этой задачи ушёл, осталась только механика итога.
- `devkitctl weigh` из мотивации снят: он зовёт
  `claude -p --output-format json` и читает поле usage, это документированный
  формат, а не разбор сырого текста. Переводить его не на что.
- DK-136 (двусторонний чат с идущей сессией) остаётся черновиком, и
  потоковый ввод headless-сессии, который даёт SDK, там назван одной из
  механик. Цель DK-112 писать в идущий процесс сознательно не берётся
  (переписка DK-220 идёт через состояние цели) и сессии через Agent SDK в
  свой состав не включила.

## Чего хотим

Подъём витка через Claude Agent SDK: итог витка приходит структурированным
результатом сессии, а не последней строкой текста, события сессии доступны
программно по ходу работы, потоковый ввод остаётся заделом для DK-136.
Деградация обязательна: пока пакет SDK не встал, цикл работает по-старому
через `claude -p`, и предполётная проверка оболочки говорит, каким путём
пойдут витки.

Трейд-офф с правилом «ноль внешних зависимостей»: goal-run не уезжает с
машины и зовётся путём из чекаута, так что зависимость локальна и голую
машину потребителя не трогает.

Развилки исполнителю (едут неопределённостью, не вопросами):

- python или typescript вариант SDK и чем он ставится (кандидат
  `doctor --fix` рядом с tmux и terminal-notifier);
- чем становится маркер витка: структурированный итог сессии, свой
  инструмент или прежняя голая строка поверх SDK;
- как деградация выбирается и чем видна снаружи.

DoD: виток цели на стенде поднимается через SDK и завершается по
структурированному итогу; при снесённом пакете тот же стенд проходит по
старому пути; тесты goal-loop держат оба пути; выбор пути виден в журнале
цикла.
