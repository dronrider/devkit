# DK-212: Ворота перехода в Check: сценарий в файле задачи и слитая ветка

записан 2026-08-09

## Что происходит

Случай IRC-103 (it-road-course, 2026-08-09): исполнитель на GLM перевёл задачу
в Check через две минуты после первого рабочего коммита. Ветка irc-103 осталась
неслитой в своём worktree, в файле задачи ни хода работы, ни сценария проверки,
а на «продолжай» агент счёл строку сданной и взялся за бэклог. Сверху в main
лёг конфликтующий коммит без ID (разбор в DK-213).

Правило прозой есть (RULES.board.md, «Трекинг задач» п. 6: перевод в Check
возможен только с готовым сценарием), но `cmdMove` (tools/taskctl/ops.go)
двигает строку, не глядя ни в файл задачи, ни в гит. Признак «без выката»
`checkMarks` (age.go) уже считает, но пускает его только на подпись строки.
Слабая модель прозу не держит, рубеж должен стоять в утилите, через которую
она обязана ходить.

## Чего хотим

`taskctl move <ID> check` отказывает в двух случаях, называя причину и
следующий шаг:

- в файле задачи нет раздела «Сценарий проверки». Строка, чья ссылка ведёт в
  LLD, а не в файл задачи, пропускается: там сценарию жить можно (п. 6);
- живёт ветка с ID задачи (именование то же, что у `branchOfTask` в
  tools/shipctl/worktree.go), у которой есть коммиты впереди main. Отказ
  называет ветку и отправляет в `shipctl merge`.

Тот же предикат неслитой ветки встаёт находкой в `taskctl lint`: строка уже в
Check при живой ветке с её ID это дрейф, который сегодня ничем не виден.

## DoD

На синтетической доске `move ... check` отказывает задаче без раздела сценария
и задаче с неслитой веткой её ID, называя причину; со сценарием и слитой либо
отсутствующей веткой проходит как раньше; строка со ссылкой на LLD проходит без
файла задачи. `lint` печатает находку про Check при неслитой ветке. Оба рубежа
покрыты тестами, README taskctl описывает ворота.

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick (квота: week_all 82%, снимок 6м назад, сдвига нет), 2026-08-09.
- Оба рубежа живут в новом `tools/taskctl/gate.go`: `checkGate` зовётся из
  `cmdMove` до записи доски, `lintUnmerged` встаёт находкой в `cmdLint`.
  Отдельный файл, а не хвост ops.go: рубеж читается целиком, вместе с
  предикатом ветки и разбором ссылки.
- Разбор файла задачи в age.go разложен на `taskDocSections`: `checkMarks`
  уже умел искать заголовок мимо ограждённых блоков, и сценарию нужен ровно
  тот же обход. Заголовок ищется по префиксу, поэтому «## Сценарий проверки
  (агентский)» тоже считается сценарием.
- Ветку задачи опознаёт копия `branchOfTask` из shipctl (общего пакета у
  утилит нет), неслитость считается как `git rev-list --count main..<ветка>`.
  Вне git, без main и в корп-контуре (доска отдельно от кода) ветки не
  найдётся, и рубеж молчит: врать про несделанное слияние хуже, чем его не
  заметить.
- Ссылка строки решает, требовать ли файл задачи: markdown-ссылка не на
  `<ID>.md` значит LLD, и сценарий живёт там (п. 6). Заглушка «(LLD позже)»
  ссылкой не считается, такую строку рубеж держит.
- `--force` не заводил: обход рубежа руками это ровно тот случай, ради
  которого он и ставился в утилиту.
- Побочное: `shipctl merge` зовёт `move ... check` уже после слияния, и
  задача без сценария теперь упирается в ворота с «слито, но доска не
  переведена». Слияние при этом сделано, лечится дописыванием раздела и
  повтором `move`. Проверять сценарий заранее, в preflight shipctl, это
  отдельная задача.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 82%, снимок 19м назад, сдвига нет), 2026-08-09.

## Решения

Рубеж стоит в `move`, а не в `close`: перевод в Check это и есть заявка «код
доехал», а `close` в чужих руках. Тестовая фикстура доски получила раздел
сценария в файлах задач (`fixtureScenario` в ops_test.go), потому что через
Check ходит половина тестов утилиты, а требовать сценарий выборочно значило бы
держать два разных смысла у одной фикстуры.

## Сценарий проверки (агентский)

Синтетическая доска во временной директории, живой git, собранный из ветки
`taskctl`. Прогон целиком:

```sh
set -e
BIN=$(mktemp -d)/taskctl
cd ~/projects/devkit-dk-212/tools/taskctl && go build -o $BIN .
T=$(mktemp -d); cd $T
git init -q -b main . && git config user.email t@t && git config user.name t
$BIN init --prefix XR --name "Синтетика" >/dev/null
git add -A && git commit -qm init
$BIN add --title "Пример" --type task --rank "25+2+1+0+2" --status in-progress --id XR-001 >/dev/null
echo "== 1 == нет сценария"
$BIN move XR-001 check || true
$BIN file XR-001 >/dev/null
printf '\n## Сценарий проверки\n\n1. Открыть.\n' >> docs/tasks/XR-001.md
git add -A && git commit -qm "docs(tasks): XR-001 сценарий"
echo "== 2 == неслитая ветка"
git checkout -q -b xr-001-fix && echo x > a.txt && git add a.txt && git commit -qm "feat: XR-001 правка" && git checkout -q main
$BIN move XR-001 check || true
echo "== 3 == слили, проходит"
git merge -q --ff-only xr-001-fix
$BIN move XR-001 check 2>&1 | head -1
echo "== 4 == lint видит дрейф"
git checkout -q -b xr-001-hotfix && echo y > b.txt && git add b.txt && git commit -qm "fix: XR-001 хвост" && git checkout -q main
$BIN lint || true
echo "== 5 == ссылка на LLD пускает без файла задачи"
$BIN add --title "Дизайн" --type LLD --rank "25+3+2+0+0" --status in-progress --id XR-002 --link "[lld/search.md](lld/search.md)" >/dev/null
$BIN move XR-002 check 2>&1 | head -1
```

Ожидаемый вывод (реальный прогон 2026-08-09, пути временной директории у
каждого свои):

```
== 1 == нет сценария
ошибка: XR-001: в Check пускают только с готовым сценарием проверки, а файла docs/tasks/XR-001.md нет: завести «taskctl file XR-001», описать шаги и ожидаемый итог разделом «Сценарий проверки» и повторить move
== 2 == неслитая ветка
ошибка: XR-001: ветка xr-001-fix не слита, впереди main её коммитов 1, а Check значит, что код уже доехал до пользователя: сначала «shipctl merge XR-001», он и переведёт строку
== 3 == слили, проходит
XR-001: in-progress -> check
== 4 == lint видит дрейф
/tmp/.../docs/TASKS.md:28: XR-001 в Check, а ветка xr-001-hotfix не слита (коммитов впереди main: 1), слить: shipctl merge XR-001
находок: 1
== 5 == ссылка на LLD пускает без файла задачи
XR-002: in-progress -> check
```

Тесты: `cd tools/taskctl && go test .` (весь пакет зелёный), краснота новых
тестов на старом коде проверена

```sh
regcheck -C . --tests tools/taskctl/gate_test.go,tools/taskctl/ops_test.go,tools/taskctl/review_test.go,tools/taskctl/commit_test.go,tools/taskctl/dep_test.go -- \
  sh -c 'cd tools/taskctl && go test -run "MoveToCheck|LintFindsUnmerged" .'
```

вывод: «тест краснеет на HEAD и проходит на текущем коде, регрессия закрыта».
