# DK-212: Ворота перехода в Check: сценарий в файле задачи и слитая ветка

записан 2026-08-09

## Что происходит

Случай IRC-103 (it-road-course, 2026-08-09): исполнитель на GLM перевёл задачу
в Check через две минуты после первого рабочего коммита. Ветка irc-103 осталась
неслитой в своём worktree, в файле задачи ни хода работы, ни сценария проверки,
а на «продолжай» агент счёл строку сданной и взялся за бэклог. Сверху в main
лёг конфликтующий коммит без ID (разбор в DK-213).

Правило прозой есть (RULES.board.md, «Трекинг задач» п. 6: перевод в Check
возможен только с готовым сценарием), но `cmdMove` (tools/taskctl/ops.go)
двигает строку, не глядя ни в файл задачи, ни в гит. Признак «без выката»
`checkMarks` (age.go) уже считает, но пускает его только на подпись строки.
Слабая модель прозу не держит, рубеж должен стоять в утилите, через которую
она обязана ходить.

## Чего хотим

`taskctl move <ID> check` отказывает в двух случаях, называя причину и
следующий шаг:

- в файле задачи нет раздела «Сценарий проверки». Строка, чья ссылка ведёт в
  LLD, а не в файл задачи, пропускается: там сценарию жить можно (п. 6);
- живёт ветка с ID задачи (именование то же, что у `branchOfTask` в
  tools/shipctl/worktree.go), у которой есть коммиты впереди main. Отказ
  называет ветку и отправляет в `shipctl merge`.

Тот же предикат неслитой ветки встаёт находкой в `taskctl lint`: строка уже в
Check при живой ветке с её ID это дрейф, который сегодня ничем не виден.

## DoD

На синтетической доске `move ... check` отказывает задаче без раздела сценария
и задаче с неслитой веткой её ID, называя причину; со сценарием и слитой либо
отсутствующей веткой проходит как раньше; строка со ссылкой на LLD проходит без
файла задачи. `lint` печатает находку про Check при неслитой ветке. Оба рубежа
покрыты тестами, README taskctl описывает ворота.
