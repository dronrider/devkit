# DK-214: Копия окна второй подписки едет за main сама

записан 2026-08-09

## Что происходит

Копия окна второй подписки (`../<проект>-<поставщик>`, shipctl code) отстаёт
от main: окно открывает docs/TASKS.md и показывает срез на момент последнего
переключения копии, а не реальную доску. Живой случай 2026-08-09: devkit-glm
застрял на четыре коммита позади main, DK-212 и DK-213 в его окне выглядели
открытыми. Опасно это и для сессии в самой копии: стухшая доска предлагает
взять уже закрытую задачу.

Дизайн копии обещает «после merge под ногами слитое состояние main» (README
shipctl, раздел «Копия на окно, а не на задачу»), но держит обещание только
когда слитая ветка стояла в самой копии: cmdMerge (ops.go) зовёт
detachWorktree лишь по совпадению дерева ветки с windowTree. Мимо проходят
два случая:

- задача ехала не из копии (одноразовое дерево субагента либо основной
  чекаут): копия не трогается вовсе;
- даже в обслуженном случае checkout --detach оставляет копию на коммите
  слияния, а main тут же уезжает вперёд коммитами файла задачи, закрытия и
  доски.

У первой подписки вечной копии на окно нет, поэтому там проблема не
наблюдается.

## Чего хотим

Выполнение задачи само оставляет копию окна на свежем main, ручной команды во
флоу нет. Merge, одиночный и поездной, в конце подтягивает копию, когда она
есть, стоит detached и чиста. Копия на ветке или с незакоммиченными правками
не трогается, про это строка в отчёте: молчание тут неотличимо от штатной
работы.

## DoD

После merge любой задачи проекта с заведённой копией окна копия стоит на
свежем main (включая коммиты файла задачи и доски, сделанные тем же merge);
занятая веткой или грязная копия остаётся на месте, и отчёт merge называет
причину. Поведение покрыто тестами, раздел README shipctl про копию дополнен.

## Ход работы

- Исполнение: субагент sonnet/high по вердикту pick (квота: week_all 83%,
  снимок 42м назад, сдвига нет), 2026-08-09.
- `tools/shipctl/worktree.go`: новая `syncWindowTree(root, main)` рядом с
  `detachWorktree`. Копия ищется по `windowTree(root)` в списке worktree; нет
  её вовсе -- пустая строка (merge молчит); стоит на ветке -- строка с именем
  ветки и без движения; есть незакоммиченное (`git status --porcelain
  --untracked-files=no`, тот же критерий, что у чистоты worktree задачи в
  cmdMerge) -- строка с причиной и без движения; чистая detached -- `git
  checkout --detach <main>` и строка про успех.
- `tools/shipctl/ops.go`: вызов `syncWindowTree` в трёх точках, где main
  дописан всеми коммитами merge (задача, доска) и дальше не тронется: конец
  одиночного `cmdMerge` (после пуша доски), конец бескодовой ветки поездного
  `cmdMerge` (сама переводит себя в Check и не ждёт `ship`), конец `cmdShip`
  (после пуша доски всего состава). Обычный поездной `cmdMerge` (код есть,
  перевод в Check ждёт `ship`) вызов не получил: там main ещё не дописан,
  подтяжка тут увела бы копию на промежуточный коммит.
- `tools/shipctl/window_test.go`: шесть тестов. `TestMergeSyncsWindowTree`
  (чистая detached копия подтягивается, включая коммит доски, а не только
  слитый код), `TestMergeLeavesBranchedWindowTree` (копия на чужой ветке не
  трогается, причина в отчёте), `TestMergeLeavesDirtyWindowTree` (грязная
  копия не трогается, правка не теряется), `TestMergeSilentWithoutWindowTree`
  (без копии merge её не упоминает), `TestTrainDocsOnlySyncsWindowTree`
  (бескодовая ветка поездного merge подтягивает копию сама),
  `TestShipSyncsWindowTree` (обычный поезд подтягивает копию в `ship`, после
  коммита доски поездом). Красноту всех шести проверил `git stash` источника
  (`ops.go`, `worktree.go`) с прогоном тестов на неизменённых: пять из шести
  красные (`TestMergeSilentWithoutWindowTree` зелёный и на старом коде,
  молчание там было и раньше -- тест страхует его от будущей регрессии, а не
  ловит текущий баг), после `stash pop` все шесть зелёные.
- `tools/shipctl/README.md`: раздел «Копия на окно, а не на задачу» дополнен
  абзацем про подтяжку в конце merge и ship, с перечнем причин, по которым
  копия остаётся на месте.
- Полный прогон `GOWORK=off go test ./...` в `tools/shipctl`: зелёный.

## Сценарий проверки

Агентский, гоняется из `tools/shipctl`:

```sh
GOWORK=off go test ./...
```

Ожидание: `ok`, без падений. Точечно про эту задачу:

```sh
GOWORK=off go test ./... -run 'TestMergeSyncsWindowTree|TestMergeLeavesBranchedWindowTree|TestMergeLeavesDirtyWindowTree|TestMergeSilentWithoutWindowTree|TestTrainDocsOnlySyncsWindowTree|TestShipSyncsWindowTree' -v
```

Ожидание: все шесть тестов `PASS`.
