# DK-217: Каркас дашборда: сервер с аутентификацией и доска проектов на чтение [после DK-215, DK-216]

записан 2026-08-09

Задача цели DK-112 ([DK-112.md](DK-112.md)).

## Чего хотим

Первый живой срез дашборда: Go-сервер с вшитой статикой по раскладке из
DK-215, вход по своей аутентификации, доска на чтение. Сервер читает список
корней из конфига, проектом считает каталог с `docs/TASKS.md`, доску и
статусы берёт через taskctl тем способом, который назвал LLD, своей базы нет.
Экран доски по макету DK-216: задачи и цели со статусами нескольких проектов,
видно, что сейчас в работе. Правок доски в этом срезе нет.

Состав:

- инструмент в `tools/` под именем из LLD, go, статика вшита в бинарь;
- вход по механизму из LLD, без входа не отдаётся ни одной строки данных;
- API на чтение: список проектов, доска проекта со статусами и текущими
  работами;
- экран доски под телефон и ноутбук;
- конфиг корней, запуск процесса и выкат по решению LLD; нехватку раскладки
  называет диагностика, а не молчание.

После слияния и выката дашборд стоит на машине и отвечает из домашней сети с
телефона: наблюдение за агентами работает само по себе, и цикл может встать
на любой следующей строке без полуфабриката на проде.

## Ранг

`25+8+3+0+4 = 40`, P2.

- Серьёзность 25 (Major). Первая половина основного сценария цели: доска
  видна без машины. Обход есть, сидеть за машиной, поэтому Major, а не
  Critical.
- Ценность 8. «Видно, над чем агенты работают прямо сейчас» это первый пункт
  цели, ради наблюдения она и затевается.
- Неопределённость 3. Подход решён LLD, но правка пересекает границу
  сервер-клиент, порог RANKING.md: развилки стыка видны живым прогоном, а не
  чтением исходников.
- Поправка на баг 0. Новая работа.
- Рычаг 4. Сервер, вход, статика и конфиг это каркас, на котором едут все
  следующие срезы, каждая задача серии дешевле.

## Сценарий проверки

Агентский.

1. Собранный дашборд поднимается на свободном порту с конфигом, где корень
   поиска указывает на временный каталог с синтетическим проектом (фикстурная
   `docs/TASKS.md`); окружение задаётся явно, живая доска не участвует.
2. Запрос без входа получает отказ (код по решению LLD: 401 или редирект на
   вход), в теле нет ни одной строки доски.
3. После входа API проектов отдаёт синтетический проект, API доски отдаёт его
   задачи со статусами, коды 200, строки сверяются с фикстурой командой.
4. Экран доски отдаётся тем же сервером из вшитой статики, в HTML нет ссылок
   на внешние хосты (греп по ответу).
5. На проде без правок: GET к стоящему на машине дашборду после входа отдаёт
   живую доску devkit; при поднятой tmux-сессии (`tmux new-session -d -s
   task-DK-999`) список работ проекта показывает её в works via tmux, после
   проверки сессия убирается (`tmux kill-session -t task-DK-999`); `/healthz`
   без ошибок про taskctl и tmux. Кроме служебной tmux-сессии шаги ничего не
   меняют.

## Ревью

- Нет теста на паузу после провала входа. LLD DK-112, раздел «Тесты», называет её прямо, а tools/dashboard/server_test.go только обнуляет loginPause в newTestEnv и больше к ней не возвращается: выкинь строку time.Sleep(loginPause) из handleLogin (server.go:177), и весь пакет останется зелёным. Нужен тест, который эту мутацию красит: поднять сервер с ненулевой паузой и померить, что провал входа занял её, а верный вход нет.: исправлено
- Секрет входа может уехать в журнал с правами 644. config.go:75 на строке без знака равенства печатает её целиком («жду строку «key = value», получил %q»), а cmdServe отдаёт эту ошибку в fatal, то есть в stderr, который launchd-агент льёт в ~/.devkit/dashboard.log. Достаточно руками написать «token abc123» без «=», и секрет из файла с правами 600 ляжет в журнал, который читает кто угодно. Печатать в этой ошибке номер строки без её содержимого, тест на то, что секрета в тексте ошибки нет.: исправлено
- У демона нет ни одного таймаута, а слушает он все интерфейсы. http.Server в main.go:159 собран голым: без ReadHeaderTimeout молчащее соединение висит вечно, и набрать их можно сколько угодно. Рядом exec.Command(taskctl ...) в board.go:31 и tmux в board.go:105 идут без контекста со сроком: подвисший подпроцесс держит горутину запроса и после того, как клиент ушёл. WriteTimeout ставить нельзя, дальше по серии едет SSE, а ReadHeaderTimeout и срок подпроцессам поставить надо, с тестом на то, что зависший taskctl оборачивается ошибкой ответа, а не вечным ожиданием.: исправлено
- show --json теряет заголовок черновика. В json.go:154 findDraft возвращает Draft с полем Title, но в ответ уходит только id, sect и file, тогда как печатный show отдаёт и заголовок, и текст. Машинному читателю про черновик известно меньше, чем человеку, а поле уже под рукой: положить Title в jsonRow и накрыть тестом рядом с TestShowJSONArchiveAndMissing.: исправлено
- Один подпроцесс остался мимо runProc, и как раз на открытой ручке. gitLine в projects.go:47 зовёт git голым exec.Command, а через него ходит isLinkedWorktree, то есть по два git rev-parse на каждый каталог-кандидат при каждом scanProjects: это /api/projects, /api/projects/{p}/board и /healthz, который отвечает без входа. Срыв тут маловероятен (rev-parse локальный и быстрый), поэтому замечание мелкое, но правило подпроцессов теперь живёт в runProc, и одна точка вне его сначала читается как разрешение, а потом копируется: дальше по серии едут capture-pane, goal-run.py и git commit с push. Перевести gitLine на runProc.: исправлено
- Дефект шага 5 закрыт наполовину: у tmux ровно та же болезнь, и она молчит. Корень не в taskctl, а в том, что launchd даёт демону системный PATH; на живом агенте это видно прямо: launchctl print gui/501/ru.devkit.dashboard печатает default environment PATH => /usr/bin:/bin:/usr/sbin:/sbin. taskctl теперь находится соседом по каталогу, а tmux лежит в /opt/homebrew/bin и соседом бинарю devkit не приходится, так что env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin tmux ls отвечает «No such file or directory». Дальше tmuxSessions (board.go:129) на ошибке возвращает nil, liveWorks молча отдаёт список без единой работы via tmux, и ни /healthz, ни ответ /api/projects, ни журнал об этом не говорят. То есть на проде первый пункт цели DK-112, «видно, над чем агенты работают прямо сейчас», не работает вовсе: сессии task-* не показываются никогда, а цели видны только тем, что реестр читается с диска без подпроцесса. Хуже, что tmux ls и при живом tmux без сервера отвечает ненулевым кодом, так что «tmux не нашёлся» и «сессий нет» в коде сейчас один и тот же случай, а по LLD («Молчание различимо») и по правилу про доводку фичи до пользователя они обязаны быть разными ответами. Сосед по каталогу тут не лекарство, tmux не утилита devkit: либо агенту дописывается PATH (EnvironmentVariables в plist, dashboard.py), либо путь берётся из конфига, но в любом случае ненайденный tmux обязан стать названной ошибкой в /healthz и в ответе проектов, а не пустым списком работ. Тест по образцу соседнего: с PATH без tmux работы via tmux пропадают, а причина называется.: исправлено
