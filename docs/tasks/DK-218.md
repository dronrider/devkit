# DK-218: Запуск и стоп задачи и цели с дашборда [после DK-217]

записан 2026-08-09

Задача цели DK-112 ([DK-112.md](DK-112.md)).

## Чего хотим

Управление с дашборда: запустить задачу или цель в работу и остановить.
Запуск зовёт тот же механизм, что и руками (какой именно, решил LLD DK-215:
goal-run для цели, конвейер задачи для строки), стоп это стоп сессии, и
интерфейс честно называет его стопом: паузы нет, возобновление это новый
виток, читающий состояние с диска. Кнопки на экранах доски и задачи по макету
DK-216, те же действия доступны по API, на них дальше встаёт smoke DK-222.

## Ранг

`25+8+3+0+3 = 39`, P2.

- Серьёзность 25 (Major). Вторая половина основного сценария: без запуска и
  стопа дашборд остаётся смотрелкой, за управлением по-прежнему садиться за
  машину. Обход дешёвый и очевидный, полоса Major.
- Ценность 8. Полное управление процессом с любого устройства это заявленная
  ценность цели, запуск и стоп её ядро.
- Неопределённость 3. Граница сервер-клиент плюс стык с процессами: tmux,
  goal-run, живые сессии; что вылезет на стыке, покажет прогон.
- Поправка на баг 0. Новая работа.
- Рычаг 3. Цели запускаются и снимаются без привязки к рабочему месту, каждый
  следующий виток любой цели стартует раньше.

## Сценарий проверки

Агентский.

1. На синтетическом проекте с задачей-фикстурой (временный HOME, свой корень,
   окружение задаётся явно) запуск через API отвечает 200, строка переходит в
   In progress (`taskctl show`), процесс исполнителя виден тем признаком,
   который назвал LLD (pid или tmux-сессия).
2. Стоп через API отвечает 200, процесса больше нет, ответ и экран называют
   состояние стопом; слова «пауза» в статике нет (греп).
3. Повторный запуск после стопа поднимает новый виток, читающий состояние с
   диска.
4. Живая доска в сценарии не участвует, прод шаги не меняют.
