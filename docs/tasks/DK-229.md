# DK-229: settings.json: allow без литеральных токенов, копии прочь, находка doctor

Задача цели DK-207. В `~/.claude/settings.json` литеральные секреты осели в
`permissions.allow`: 36 правил несут значения в своём тексте. Из них 19 правил с
заголовком `Authorization: Bearer ...` (Jira и Confluence PAT), 11 с
`PRIVATE-TOKEN: ...` (GitLab PAT), 4 присваивания `RELEASE_GITLAB_TOKEN=...` в
env, 2 с release-signing-key для Android-сборки. Маска `__TRACKED_VAR__` уже
прижита в трёх местах, её и предстоит разнести на остальные. Две резервные
копии, `settings.json.bak-dk062` и `settings.json.pre-dk113`, содержат те же
литералы.

## Что делается

Литеральные значения в allow-правилах заменяются на шаблон без значения в
тексте правила, по образцу уже прижитого `__TRACKED_VAR__`. Резервные копии
`.bak-dk062` и `.pre-dk113` удаляются. Шаблон фиксируется здесь и описывается в
кратком виде: как именно правило получает значение в момент запуска команды
(env-переменная, подставляемая secretctl, либо маска, резолвимая харнесом).

Чтобы чистота не разрушилась снова, `devkitctl doctor` получает новую
check-функцию по образцу `perms.check` (`tools/devkitctl/perms.py:185-189`):
грепает `settings.json` по шаблонам литеральных токенов в allow и проверяет
отсутствие `.bak`/`.pre` копий. Находа перечисляет с командой исправления, как
остальные.

## DoD

- греп по `~/.claude/settings.json` не находит ни заголовков авторизации с
  литеральным значением, ни присваиваний токенов значением: только шаблоны;
- файлов `settings.json.bak-dk062` и `settings.json.pre-dk113` на диске нет;
- `devkitctl doctor` не выдаёт находок по литералам и копиям; если вносить
  литерал обратно, doctor его ловит.

## Сценарий проверки

Агентский.

    grep -nE 'Authorization: Bearer [^ ]|PRIVATE-TOKEN: [^ ]' ~/.claude/settings.json
    => пусто

    ls ~/.claude/settings.json.bak-dk062 ~/.claude/settings.json.pre-dk113 2>&1
    => No such file

    python3 ~/projects/devkit/tools/devkitctl/devkitctl.py doctor
    => нет находок про литеральные токены и копии

Регресс-тест на check-функцию doctor пишется по образцу существующих: на
settings.json с подсунутым литералом doctor выдаёт находку, на чистом молчит.

## Развилки

Если выбранный шаблон требует источника значения из хранилища (например,
переменная, подставляемая через `secretctl exec`), задача жёстко зависит от
DK-226, и исполнитель ставит зависимость явно. Если шаблон сводится к маске,
которую резолвит сам харнес, зависимости нет. Как именно резолвится маска
`__TRACKED_VAR__` сегодня, исполнитель выясняет по существующим трём правилам и
держится того же механизма.
