# DK-229: settings.json: allow без литеральных токенов, копии прочь, находка doctor

Задача цели DK-207. В `~/.claude/settings.json` литеральные секреты осели в
`permissions.allow`: 36 правил несут значения в своём тексте. Из них 19 правил с
заголовком `Authorization: Bearer ...` (Jira и Confluence PAT), 11 с
`PRIVATE-TOKEN: ...` (GitLab PAT), 4 присваивания `RELEASE_GITLAB_TOKEN=...` в
env, 2 с release-signing-key для Android-сборки. Маска `__TRACKED_VAR__` уже
прижита в трёх местах, её и предстоит разнести на остальные. Две резервные
копии, `settings.json.bak-dk062` и `settings.json.pre-dk113`, содержат те же
литералы.

## Что делается

Литеральные значения в allow-правилах заменяются на шаблон без значения в
тексте правила, по образцу уже прижитого `__TRACKED_VAR__`. Резервные копии
`.bak-dk062` и `.pre-dk113` удаляются. Шаблон фиксируется здесь и описывается в
кратком виде: как именно правило получает значение в момент запуска команды
(env-переменная, подставляемая secretctl, либо маска, резолвимая харнесом).

Чтобы чистота не разрушилась снова, `devkitctl doctor` получает новую
check-функцию по образцу `perms.check` (`tools/devkitctl/perms.py:185-189`):
грепает `settings.json` по шаблонам литеральных токенов в allow и проверяет
отсутствие `.bak`/`.pre` копий. Находа перечисляет с командой исправления, как
остальные.

## DoD

- греп по `~/.claude/settings.json` не находит ни заголовков авторизации с
  литеральным значением, ни присваиваний токенов значением: только шаблоны;
- файлов `settings.json.bak-dk062` и `settings.json.pre-dk113` на диске нет;
- `devkitctl doctor` не выдаёт находок по литералам и копиям; если вносить
  литерал обратно, doctor его ловит.

## Сценарий проверки

Агентский.

    # Литеральное значение начинается буквой или цифрой, маска -- подчёркиванием,
    # поэтому класс [A-Za-z0-9] ловит только литерал и пропускает __TRACKED_VAR__.
    grep -cE 'Authorization: Bearer [A-Za-z0-9]|PRIVATE-TOKEN: [A-Za-z0-9]' ~/.claude/settings.json
    => 0

    ls ~/.claude/settings.json.bak-dk062 ~/.claude/settings.json.pre-dk113 2>&1
    => No such file

    # Авторитетная сверка по всем пяти заголовкам и копиям -- сам модуль doctor.
    python3 ~/projects/devkit/tools/devkitctl/leak.py
    => литеральных токенов и резервных копий нет
    python3 ~/projects/devkit/tools/devkitctl/devkitctl.py doctor
    => нет находок про литеральные токены и копии

Регресс-тест на check-функцию doctor пишется по образцу существующих: на
settings.json с подсунутым литералом doctor выдаёт находку, на чистом молчит.

## Развилки

Если выбранный шаблон требует источника значения из хранилища (например,
переменная, подставляемая через `secretctl exec`), задача жёстко зависит от
DK-226, и исполнитель ставит зависимость явно. Если шаблон сводится к маске,
которую резолвит сам харнес, зависимости нет. Как именно резолвится маска
`__TRACKED_VAR__` сегодня, исполнитель выясняет по существующим трём правилам и
держится того же механизма.

## Ход работы

- Исполнение: подпроцесс glm-5.2/medium по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-10.
- Развилка: маска `__TRACKED_VAR__` нигде не резолвится. В `tools/devkitctl/harness.py`
  подстановки текста правила нет, а `secretctl exec` кладёт значение секрета в env
  подпроцесса по имени секрета, маску в теле allow-правила не трогая. Правило с
  маской перестаёт быть рабочим разрешением, но форму команды хранит без
  литерала. Зависимости от DK-226 нет, механизм тот же, что в трёх прижитых.
- Код: модуль `tools/devkitctl/leak.py` (check-функция по образцу `perms.check`),
  вызов в `check_harness_contour` рядом с `perms.check`, регрессионный тест
  `tools/devkitctl/leak_test.py`. Шаблоны ловят заголовки `Authorization: Bearer`,
  `PRIVATE-TOKEN:`, `RELEASE_GITLAB_TOKEN=`, `RELEASE_JIRA_TOKEN=`,
  `ORG_GRADLE_PROJECT_xrReleasePublicKey='` негативным lookahead поверх маски;
  копии ищутся по суффиксам `.bak-*` и `.pre-*` рядом с файлом. regcheck: тест
  краснеет на HEAD и проходит на правке.
- Замена в живом `~/.claude/settings.json` выполнена `sed -i` по паттернам
  заголовков, значения в контекст не попадали. Заменено правил: 19
  `Authorization: Bearer`, 11 `PRIVATE-TOKEN:`, 5 `RELEASE_GITLAB_TOKEN=`,
  1 `RELEASE_JIRA_TOKEN=`, 2 `ORG_GRADLE_PROJECT_xrReleasePublicKey='`. После
  замены в файле 40 правил с маской `__TRACKED_VAR__` и ни одного литерала. В
  строках с
  JSON-экранированными кавычками (`\"...\"`) первый проход sed съел обратную
  косу перед закрывающей кавыкой, JSON сломался; коса восстановлена вторым
  проходом, `json.load` проходит.
- Копии `settings.json.bak-dk062` и `settings.json.pre-dk113` удалены.
- DoD: `grep -cE` по всем пяти заголовкам с алфавитно-цифровым значением даёт 0,
  `python3 .../leak.py` по живому файлу молчит («литеральных токенов и резервных
  копий нет»), полный `doctor` в выводе не упоминает литералы, токены и копии.
  Обнаружение регрессии закрыто тестом `LeakDoctorTest.test_doctor_flags_and_fixes_literal`.
- Ревью: подпроцесс glm-5.2/high по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-10.

## Ревью

- Шаг сценария с grep не воспроизводим: шаблон `Authorization: Bearer [^ ]` ловит и саму маску `__TRACKED_VAR__` (подчёркивание подходит под [^ ]), на чистом файле grep выдаёт 33 строки, а не пусто. В DoD исполнитель сверял алфавитно-цифровым классом и получил 0, а в сценарий попал [^ ]. Шаг поправить: негативный lookahead в PCRE (grep -PE 'Authorization: Bearer (?!__TRACKED_VAR__)'), алфавитно-цифровый класс как в DoD либо ссылка на leak.py/doctor, которые уже сверяют правильно.: исправлено
