# DK-236: shipctl, agentctl и trackctl молча теряют флаг за позиционным: pick отдаёт вердикт не той роли

записан 2026-08-10

Подкоманды `shipctl`, `agentctl` и `trackctl` берут позиционный аргумент из
`args[1]` до `fs.Parse`, а хвост `fs.Args()` не смотрят вовсе. Приём тот же,
который в `taskctl` чинила DK-099, и последствия те же: `flag.Parse`
останавливается на первом не-флаге, поэтому всё, что стоит за лишним
позиционным, выбрасывается без единого слова.

## Что происходит

Прогон 2026-08-10, симптом жив:

```text
$ agentctl pick DK-146 --role review
model: sonnet
effort: high
tier: base
$ agentctl pick DK-146 junk --role review
model: opus
effort: high
tier: pro
```

Лишний `junk` съел `--role review`, и диспетчер получил исполнительский вердикт
вместо ревьюверского, без отказа и без предупреждения. Промах мимо флага
оборачивается работой не на той модели и не в той роли.

Вторая форма отбивается громко: у всех трёх стоит проверка
`strings.HasPrefix(args[1], "-")`, и `shipctl merge --push DK-236` отвечает
`жду: merge <ID> --test "cmd" ...`. Данные тут не теряются, но и форма «флаг
перед ID» не работает, так что правило «флаг стоит где угодно» держится сегодня
только в `taskctl`.

Обход у пользователя есть и дешёвый: писать флаги строго после ID и не
промахиваться мимо них. `helpRequested` из DK-099 в эти три утилиты уже
разъехался, `parseArgs` и `needArgs` нет.

## Чего хотим

Три утилиты разбирают аргументы подкоманд так же, как `taskctl`: позиционный
снимается из хвоста после `Parse`, разбор продолжается с остатка, лишний
позиционный отбивается с внятной строкой вместо тихого выброса.

Развилка «копия или общий модуль» из этой задачи ушла: замер каркаса показал 35
функций в копиях и около 1122 лишних строк на восемь модулей, поэтому решение
принимается разом по всему каркасу в DK-237, а не по тридцати строкам разбора
аргументов. Здесь `parseArgs` и `needArgs` едут туда, куда их положит DK-237.

## DoD

Формы `<команда> --флаг <ID>` и `<команда> <ID> --флаг` работают одинаково во
всех трёх утилитах. Лишний позиционный отказывает с сообщением, а не молчит.
Тест на каждую форму падает на старом коде и проходит на исправленном
(regcheck), рабочие формы держатся от регресса своими тестами. Раскладку задаёт
DK-237, отдельного решения здесь не принимается.

## Ход работы

- Исполнение: подпроцесс glm-5.2/medium по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-13.
- Перенёс `parseArgs`/`needArgs` в `internal/frame` как `frame.ParseArgs`/`frame.NeedArgs`
  (LLD DK-237, волна из DK-236). `ParseArgs` переехал как есть, `NeedArgs` вместо
  чужого `fail` возвращает `error`: fail у каждой утилиты свой и в общий модуль не
  въехал. В каждой утилите заведена тонкая обёртка `needArgs`, которая зовёт
  `frame.NeedArgs` и при ошибке делает локальный `fail(err)`, поэтому точки вызова
  остались лаконичными.
- taskctl переключён на `frame.ParseArgs`/`frame.NeedArgs`, локальная `parseArgs`
  убрана. agentctl, shipctl, trackctl подключили `internal` (require+replace),
  разбор «args[1] до fs.Parse» заменён на `frame.ParseArgs` + `frame.NeedArgs`, а
  проверка `HasPrefix(args[1], "-")` убрана: разбор сам переваривает форму «флаг
  перед ID», и отдельная отбивка для неё больше не нужна. Завернул через
  `needArgs(pos, 0, 0, ...)` и подкоманды без позиционных (status, ship, budget,
  harness, quota refresh, sync), чтобы лишний позиционный у них тоже отбивался, а
  не молчал, как у taskctl.
- usageText agentctl/shipctl/trackctl дополнен короткой заметкой: флаги подкоманд
  стоят где угодно относительно позиционных, лишний позиционный отбивается
  ошибкой. До правки такое утверждение было только в usageText taskctl.

## Сценарий проверки

Агентский. Симптом и починка проверяются `go test` и `regcheck` по каждому модулю,
ручного прогона не требуется.

Тесты лежат:
- `internal/frame/args_test.go`: `TestParseArgsMixesFlagsAndPositionals` (переехал
  из taskctl) и `TestNeedArgs` (нехватка, лишний, max=0, max<0).
- `tools/agentctl/args_test.go`: `TestPickFlagAnywhere` (обе формы дают одинаковый
  вердикт), `TestPickExtraPositionalRejects` (junk не съедает --role review),
  `TestPickMissingID`.
- `tools/shipctl/args_test.go`: `TestStartFlagAnywhere`, `TestStartExtraPositionalRejects`,
  `TestStatusExtraPositionalRejects`.
- `tools/trackctl/args_test.go`: `TestSubmitFlagAnywhere`, `TestStatusExtraPositionalRejects`,
  `TestIssueExtraPositionalRejects`.

Прогон:

```
cd internal && GOWORK=off go test ./...
cd tools/taskctl && GOWORK=off go test ./...
cd tools/agentctl && GOWORK=off go test ./...
cd tools/shipctl && GOWORK=off go test ./...
cd tools/trackctl && GOWORK=off go test ./...
```

Regcheck (база HEAD, правка не закоммичена в начало прогона; тестовые файлы
переносятся на базу сами):

```
regcheck --base HEAD -- sh -c 'cd tools/agentctl && GOWORK=off go test -run "TestPickFlagAnywhere|TestPickExtraPositionalRejects|TestPickMissingID" .'
regcheck --base HEAD -- sh -c 'cd tools/shipctl && GOWORK=off go test -run "TestStartFlagAnywhere|TestStartExtraPositionalRejects|TestStatusExtraPositionalRejects" .'
regcheck --base HEAD -- sh -c 'cd tools/trackctl && GOWORK=off go test -run "TestSubmitFlagAnywhere|TestStatusExtraPositionalRejects|TestIssueExtraPositionalRejects" .'
```

Реальный вывод regcheck (все три прогона):

```text
тест краснеет на HEAD и проходит на текущем коде, регрессия закрыта (тесты: tools/taskctl/main_test.go, internal/frame/args_test.go, tools/agentctl/args_test.go, tools/shipctl/args_test.go, tools/trackctl/args_test.go)
```

На старом коде (HEAD до ветки) тесты падают ровно по симптому DK-236:
- `agentctl pick T-002 junk --role review` выходит успехом с `model: opus`
  (exec-вердикт вместо review), `pick --role review T-002` отбивается
  «жду: pick <ID>»;
- `shipctl start --slug хвост XR-999` отбивается «жду: start <ID>»,
  `start XR-001 junk --slug хвост` выходит успехом (junk съел --slug),
  `shipctl status junk` печатает статус (junk проигнорирован);
- `trackctl submit --log-only ABC-12` отбивается «жду: submit <KEY>»,
  `status junk` и `issue ABC-12 junk` игнорируют лишний аргумент.
