# DK-252: Транскрипт активной задачи мешает чужие сессии: выбор по mtime вместо привязки к задаче

записана 2026-08-11, замечание 5 третьей пачки пользовательской проверки цели DK-112

## Чего хотим

Экран агента и чат берут «свежую сессию проекта по mtime» (открытый вопрос
DK-219, тогда записанный честно), и при двух живых окнах по одному проекту в
транскрипт задачи DK-112 попадал вывод соседнего окна, делавшего DK-207.
Показ чужой работы под заголовком своей это дефект точности данных.

Придумать и сделать привязку сессии к задаче или цели: связи в транскриптах
нет, кандидаты это упоминание ID в первых репликах сессии (виток поднимается
фразой «продолжай цель DK-NNN», конвейер «возьми задачу DK-NNN»), сопоставление
времени сессии с tmux-сессией работы, фильтр по рабочему каталогу из
транскрипта (боковые деревья задач в нём различимы). Решение назвать в LLD;
сессии без узнанной задачи честно подписываются, а не приписываются первой
попавшейся строке.

## Ранг

`25+5+3+5+1 = 39`, P2.

- Серьёзность 25 (Major). Под заголовком задачи чужой транскрипт, доверие к
  экрану падает; обход есть, смотреть tmux руками.
- Ценность 5. Возвращает экрану правду.
- Неопределённость 3. Способ привязки предстоит выбрать и проверить на живых
  транскриптах.
- Поправка на баг 5. Для пользователя это дефект, компромисс DK-219 его не
  оправдывает.
- Рычаг 1. Точная привязка нужна и чату, и будущим экранам.

## Сценарий проверки

Агентский: на фикстурных транскриптах двух сессий (одна с упоминанием
DK-101, другая DK-102) экран задачи DK-101 отдаёт только свою сессию; сессия
без узнанной задачи не приписывается никому и подписана словами; живой
прогон на машине с двумя окнами повторяет то же руками диспетчера.

## Ход работы

- Исполнение: субагент opus/high по вердикту pick (квота: week_all 11%, week_max 12%, снимок 0м назад, сдвига нет), 2026-08-11.
- Способ привязки выбран по живым транскриптам: задачу называет сама сессия,
  и источников три по убыванию доверия. Хвост имени каталога транскриптов
  (боковое дерево `devkit-dk-252` заводится ровно под одну задачу), первая
  реплика человека («Выполни цель DK-112», «возьми задачу DK-207 в работу»,
  промпт исполнителя) и ветка из шапки записи. Ветка последняя потому, что
  окно главного дерева часто стоит на ветке от прошлой работы. Сопоставление
  с tmux-сессией отброшено: связать её с файлом транскрипта можно разве что
  временем, то есть той же догадкой, из-за которой задача и завелась.
- Сделано: `GET /sessions` отдаёт по сессии узнанную задачу с подписью и
  фильтрует по `?task=`, экраны агента и переписки спрашивают сессии своей
  задачи, нераспознанная сессия подписана и видна списком под словами о
  пустоте, пустоты различимы, шапка транскрипта запоминается в памяти
  процесса по образцу DK-242. Решение с причинами в LLD DK-112 уточнением
  DK-252, поведение в README дашборда.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 11%, week_max 12%, снимок 0м назад, сдвига нет), 2026-08-11.
- Замечание 1 закрыто тестом на дочитанную голову: транскрипт длиннее предела,
  подмена головы с дописыванием, повторный запрос отдаёт прежнюю задачу.
  Заодно голова читается через io.ReadFull, иначе короткий ответ ядра выдал бы
  недочитанную голову за дочитанную и память процесса поверила бы ей. Краснота
  снята мутацией: без ветки e.full тест падает, соседний тест на отпечаток
  остаётся зелёным.

## Ревью

- В sessions.go нет теста на дочитанную голову (headEntry.full = n >= metaScanLimit): когда шапка вычитана до предела 256КБ, sessionHeadCached обязана отдавать её из памяти и после дописывания файла со сменившимся отпечатком (см. условие e.full || e.stamp == stamp). TestSessionHeadCached проверяет только путь с совпавшим/сменившимся отпечатком на маленьком файле, где full всегда false, поэтому ветка full=true никогда не выполняется. Руками проверил: поведение работает как задумано (см. LLD и README, «дочитанная голова переживает дописывание»), но без теста эта ветка не защищена регрессией.: исправлено
