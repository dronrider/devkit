# DK-262: Приёмочный тест из сценария проверки задачи

записан 2026-08-11

## Что происходит

У задачи доски есть сценарий проверки, и board-task требует обкатать его до
перевода в Check (раздел «Сценарий проверки»: что выполнимо без выката, автор
прогоняет сам). Но обкатка не делает сценарий приёмочным тестом: сегодня
сценарий остаётся текстом шагов в файле задачи, исполнитель не переводит его в
исполняемый тест до реализации и красноту не проверяет, а ревьювер получает
дифф без готового критерия соответствия сценарию и оценивает его с нуля.

Связка с TDD-порядком видна из DK-261: тест до реализации отсекает характерный
отказ LLM-исполнителя, когда тест оказывается зелёным и без фичи, проверяя
существующее поведение или ничего. DK-262 даёт этому порядку источник: тест
берётся не из головы, а переводом готового сценария задачи.

## Чего хотим

Исполнитель с агентским сценарием начинает с перевода сценария в исполняемый
приёмочный тест и проверяет его красноту до реализации. Ревьювер получает
готовый критерий «тест соответствует сценарию» вместо чтения диффа с нуля.

Граница переводимости уже стоит в board-task (раздел «Сценарий проверки»):
сценарий агентский, когда каждый шаг выполним с машины агента и итог
проверяется объективно (код возврата, HTTP-статус, конкретная строка вывода);
приёмочный тест едет только для него. Пользовательский сценарий (посмотреть
глазами, живой прод, чужой сервис) по определению в автотест не переводится.

Открытые развилки, которые снимает исполнитель, а не постановка:

- как именно вписать шаг в порядок исполнителя и в раздел «Сценарий проверки»
  board-task, в том числе связка с DK-261;
- что пишется в файл задачи, когда приёмочного теста нет: пометка, что сценарий
  пользовательский и проверяется на приёмке, а не автотестом;
- хватает ли правки board-task или приходится трогать RULES.board.md (раздел про
  инструкцию проверки).

test-standard отдельно: порядок «тест до реализации для новой функциональности»
правит DK-261, здесь только источник теста.

## DoD

1. В board-task (раздел «Сценарий проверки» и порядок исполнителя) закреплён
   шаг: агентский сценарий переводится в исполняемый приёмочный тест до
   реализации, краснота проверяется прогоном, с оговоркой слабой красноты по
   DK-261, когда тест падает сборкой из-за отсутствующего кода.
2. Для пользовательского сценария приёмочного теста нет: в файле задачи
   помечается, что сценарий пользовательский и проверяется на приёмке.
3. Тесты скиллов (kit/skills/check-skills.py) держат новую формулировку
   дословной подстрокой, полный набор тестов проекта зелёный.
