# DK-271: Замок ship.lock попал под git: rm пустого файла грязнит дерево и рвёт flock

записан 2026-08-11

Замок конвейера shipctl держится не наличием файла, а flock на дескрипторе
(`tools/shipctl/lock.go`): после первого запуска `.devkit/ship.lock` лежит
пустым всегда, и по существованию файла занятость не читается. Коммитом
5973956 файл по недосмотру уехал в git и с тех пор отслеживается, хотя это
машинное состояние того же рода, что `.devkit/log`.

## Что происходит

Сессия, получив «конвейер занят», ждёт исчезновения файла, которого не
дождётся, тратит на это 15-20 минут, объявляет замок протухшим и снимает его
через `rm`. Дальше два последствия:

- `rm` отслеживаемого файла даёт незакоммиченное удаление: дерево грязное,
  следующий `shipctl merge` отказывает уже по чистоте дерева, и сессия, найдя
  файл в HEAD, строит ложную теорию «замок свободен, когда файл пустой» и
  возвращает его через `git restore`.
- `rm` под живым flock рвёт взаимное исключение: держатель остаётся с замком
  на старом inode, следующий запуск создаёт файл заново и берёт flock на
  новом, и два конвейера едут одновременно, ровно в тот зазор, ради которого
  замок заводился.

По транскриптам сессий обеих раскладок «конвейер занят» встречался в 39
сессиях, до `rm` с последующим восстановлением дошли три; разобранный пример
целиком лежит в чате «Проверка задачи DK-137 перед взятием в работу»
(2026-08-11).

## Починка

- `git rm --cached .devkit/ship.lock` и строка в `.gitignore`: машинному
  состоянию в истории делать нечего, `rm` перестаёт грязнить дерево.
- Дописать текст отказа в `lock.go`: файл лежит пустым и когда замок
  свободен, наличие его ничего не значит, занятость проверяется повторным
  запуском, а не ожиданием исчезновения.
- После взятия flock сверять inode дескриптора с файлом на диске и
  перебирать замок при расхождении: снятый чужим `rm` файл перестаёт
  открывать второй конвейер параллельно первому.

## Сценарий проверки

Агентский, через `regcheck` (объективный итог по строке вывода и коду
возврата, первый прогон воспроизводит исходный баг красным тестом на
дофиксовом коде):

```
cd tools/shipctl && GOWORK=off regcheck --base HEAD~1 -- go -C . test ./... \
  -run 'TestLockRefusalExplainsEmptyFile|TestLockRetriesWhenFileReplacedMidAcquire' -v
```

Ожидаемый итог: `тест краснеет на HEAD~1 и проходит на текущем коде,
регрессия закрыта (тесты: tools/shipctl/lock_test.go)`, код возврата 0.
Реальный прогон (ветка `dk-271`, база `HEAD~1` = коммит до правки):

```
тест краснеет на HEAD~1 и проходит на текущем коде, регрессия закрыта (тесты: tools/shipctl/lock_test.go)
```

Плюс отслеживание файла в гите (объективно по коду выхода `grep`, 1 значит
совпадений нет, файл не отслеживается):

```
git ls-files | grep -c '^\.devkit/ship\.lock$'
```

Ожидаемый итог: `0`, код возврата grep 1. Реально получено то же самое.

Полный прогон пакета (нет регрессии по остальным тестам замка и команд,
которые его берут):

```
GOWORK=off go -C tools/shipctl test ./...
```

Ожидаемый итог: `ok`. Реально: `ok  	github.com/dronrider/devkit/tools/shipctl	83.869s`.

## Ход работы

- Исполнение: субагент sonnet/high по вердикту pick (квота: week_all 19%,
  снимок 2м назад, сдвига нет), 2026-08-11.
- `git rm --cached .devkit/ship.lock`, строка `.devkit/ship.lock` добавлена в
  `.gitignore` рядом с `.devkit/log`. Файл на диске остался (пустой), только
  перестал отслеживаться.
- `lock.go`: отказ теперь прямо говорит, что файл лежит пустым и при занятом,
  и при свободном замке, поэтому по нему занятость не читается и ждать
  исчезновения бессмысленно, а проверяется она повторным запуском.
- `lock.go`: `acquireLock` взят в цикл (`maxLockAttempts = 20` сверху, чтобы
  не крутиться вечно на сломанном окружении). После каждого успешного flock
  сравниваются inode дескриптора и файла на диске (`os.SameFile`); при
  расхождении (файл сняли и пересоздали между `open` и `flock`, либо путь
  вовсе исчез) дескриптор закрывается и попытка повторяется на актуальном
  файле. Для детерминированного теста гонки без `sleep` добавлен пакетный
  хук `lockRaceHook func()` (в проде `nil`), дёргается сразу после `open`,
  до `flock`: тест синхронно подменяет файл под своим держателем в этот
  момент, реальная гонка потоков не нужна.
  - Важная оговорка по границам починки: сравнение ловит гонку между `open`
    и `flock` того же захвата и случай, когда конкурент уже успел создать и
    занять актуальный файл к этому моменту: второй заход тогда корректно
    получает честный отказ вместо тихого параллельного хода. Оно не умеет
    восстановить исключение задним числом, если держатель уже давно работает,
    его файл сняли, и никто больше в этот момент за путь не борется: тогда
    более поздний одиночный запуск получит свежий файл и свободный flock, как
    и раньше. От этого остаточного риска защищают пункты 1-2 починки: без
    отслеживания в git и с честным текстом отказа у сессии больше нет повода
    трогать файл руками.
- Тесты (`tools/shipctl/lock_test.go`):
  - `TestLockRefusalExplainsEmptyFile` проверяет: текст отказа при занятом
    замке содержит объяснение про пустой файл и проверку повторным запуском,
    а не только факт «конвейер занят» (уже был покрыт в
    `TestLockRefusesSecondRun`).
  - `TestLockRetriesWhenFileReplacedMidAcquire` через `lockRaceHook`
    имитирует чужой `rm` и мгновенный захват актуального пути другим
    держателем между `open` и `flock` нашей попытки; на дофиксовом коде
    захват тихо проходил бы (второй конвейер едет параллельно первому), на
    исправленном корректно отказывает `конвейер занят`.
  - Оба падают на коде до правки и проходят после, красным прогонены
    `regcheck` (вывод в «Сценарий проверки» выше).
- Дока: `tools/shipctl/README.md`, раздел «Замок конвейера» дополнен тем, что
  пустой файл ничего не значит, что он исключён из git, и как замок
  восстанавливается после чужого `rm`.
- Символы: `python3 ~/projects/devkit/hooks/check-symbols.py` по всем
  правленым текстовым файлам, чисто.
