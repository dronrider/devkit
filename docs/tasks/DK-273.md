# DK-273: shipctl merge: коммит доски за время тестов роняет fast-forward

записан 2026-08-11

## Что происходит

`shipctl merge` ребейзит ветку на main, гонит тестовый набор и только потом
делает `merge --ff-only` (tools/shipctl/ops.go). Между ребейзом и ff лежит
многоминутный прогон, и любой коммит в main за это время оставляет ветку
позади: git отвечает `fatal: Not possible to fast-forward`, слияние падает,
а повтор гонит весь набор заново. Замок конвейера зазор не закрывает: его
берут команды shipctl, а коммиты доски кладёт taskctl соседних сессий, и
замка он не берёт. При активном цикле цели merge DK-271 прошёл с шестого
захода, DK-264 рядом ловил то же самое.

Из двух вариантов черновика добор ff «под тем же замком» отпадает проверкой:
коммиты доски идут мимо замка, держать его бесполезно. Остаётся повтор
ребейза и ff внутри merge.

## Чего хотим

merge переживает main, уехавший за время тестов на коммиты доски: после
красного ff повторить ребейз и ff без повторного прогона тестов, когда
дельта уехавшего main лежит целиком под docs/ (признак уже считается
функцией rangeDocsOnly для поезда). Дельта с кодом остаётся честным отказом:
чужой код обязан пройти тесты вместе с веткой. Число доборов ограничено
сверху, отказ после потолка говорит, что main меняется быстрее, чем идёт
слияние.

## DoD

Коммит доски, легший в main между ребейзом и ff, не валит слияние: merge
проходит одним вызовом без повторного прогона тестов, добор виден в
сообщении слияния. Коммит с кодом за то же окно даёт прежний отказ.
Регрессионный тест кроет обе ветки: гонка имитируется тестовой командой,
кладущей коммит в main во время прогона.

Сценарий проверки остаётся исполнителю.
