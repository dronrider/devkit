# DK-273: shipctl merge: коммит доски за время тестов роняет fast-forward

записан 2026-08-11

## Что происходит

`shipctl merge` ребейзит ветку на main, гонит тестовый набор и только потом
делает `merge --ff-only` (tools/shipctl/ops.go). Между ребейзом и ff лежит
многоминутный прогон, и любой коммит в main за это время оставляет ветку
позади: git отвечает `fatal: Not possible to fast-forward`, слияние падает,
а повтор гонит весь набор заново. Замок конвейера зазор не закрывает: его
берут команды shipctl, а коммиты доски кладёт taskctl соседних сессий, и
замка он не берёт. При активном цикле цели merge DK-271 прошёл с шестого
захода, DK-264 рядом ловил то же самое.

Из двух вариантов черновика добор ff «под тем же замком» отпадает проверкой:
коммиты доски идут мимо замка, держать его бесполезно. Симметричный вариант
«научить taskctl брать тот же замок» закрывает гонку у источника, но
отпадает ценой: коммит доски соседней сессии ждал бы весь многоминутный
прогон, а правило доски требует пушить её сразу. Остаётся повтор ребейза и
ff внутри merge.

## Чего хотим

merge переживает main, уехавший за время тестов на коммиты доски: после
красного ff повторить ребейз и ff без повторного прогона тестов, когда
дельта уехавшего main состоит целиком из коммитов доски. Признак тут
boardOnly (ops.go), а не docsOnly: тестовый набор самого devkit читает
docs/ (doctor --layout ловит код-файлы под ним), и дельта «весь docs/»
провезла бы красноту мимо тестов. Дельта шире доски остаётся честным
отказом: такой код и такие файлы обязаны пройти тесты вместе с веткой.
Число доборов ограничено сверху, отказ после потолка говорит, что main
меняется быстрее, чем идёт слияние.

Ловушки, снятые на грумминге чтением ops.go:

- Дельту уехавшего main наивным preSha..main не увидеть: preSha снимается
  уже после уезда, и диапазон в момент красного ff пуст, а пустой диапазон
  rangeDocsOnly считает отказом. Считать дельту от merge-base ветки и main.
- preSha переснимается на каждом заходе добора: иначе recordMerge запишет
  чужие коммиты доски в файл задачи, а deployTag поезда втащит их в окно
  выката.
- В пути без worktree к моменту красного ff сделан checkout main и ветка не
  в чекауте; повторный ребейз чекаутит её сам, и ошибочный выход добора
  обязан вернуть дерево на main, как оставляет его красный ff сегодня.

## DoD

Коммит доски, легший в main между ребейзом и ff, не валит слияние: merge
проходит одним вызовом без повторного прогона тестов, добор виден в
сообщении слияния. Коммит с кодом за то же окно даёт прежний отказ, как и
серия коммитов сверх потолка доборов. Регрессионный тест кроет все три
ветки гонкой из тестовой команды, кладущей коммит в main во время прогона,
и проверяет, что после добора в файл задачи записаны только коммиты ветки,
без чужих.

## Сценарий проверки

Агентский.

1. В основном чекауте воспроизвести гонку прогоном регрессионных тестов:
   `(cd tools/shipctl && GOWORK=off go test ./... -run TestMergeCatchUp -v)`.
   Первый тест кладёт коммит доски в main из тестовой команды, то есть ровно
   тем окном, где ff падал.
2. Убедиться, что выкат довёз добор до бинаря в PATH:
   `strings $(which shipctl) | grep -c "ff добран"`.

Ждём: три PASS (`TestMergeCatchUpBoardCommit`, `TestMergeCatchUpCodeRefused`,
`TestMergeCatchUpLimit`) и `ok` пакета, на втором шаге счётчик не нулевой.
