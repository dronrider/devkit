# DK-288: shipctl записывает коммит в задачу по упоминанию её ID в чужом subject, merge встаёт

записан 2026-08-13

## Что происходит

Слияние очередной задачи отбивается из-за соседки, у которой в окне выката нет
ни одного своего коммита. Поймано 2026-08-13 на merge DK-287: shipctl вывел
сообщение «код в окне выката, а задача не в In progress: DK-137 в check», и
слияние встало до тех пор, пока чужую цель не закроют.

Код задачи shipctl отбирает функцией `codeCommits`
([tools/shipctl/ops.go:426](tools/shipctl/ops.go#L426)): коммит считается
принадлежащим задаче, когда её ID стоит словом где угодно в subject. Правило
доски требует ID в начале строки, но упоминание чужого ID дальше по тексту
законно и встречается постоянно, особенно у задач цели. Коммит DK-278 «docs:
DK-278 раскладка машинных файлов .devkit в README, пробел DoD №6 цели DK-137
снят» (1dbcac91) трогает `tools/devkitctl/README.md`, то есть под фильтр
`docsOnly` не попадает, и записался в код DK-137. Дальше `trainTasks` находит
код задачи, которая стоит не в In progress, и помечает её осиротевшей, а этим
признаком merge и ship отбиваются по построению.

То же правило стоит ещё в двух местах. `taskCommits`
([tools/shipctl/ops.go:1162](tools/shipctl/ops.go#L1162)) собирает по нему
коммиты к откату, и там цена ошибки выше: `revert` возьмёт чужой коммит.
Подсказка о пересечении файлов между задачами поезда
([tools/shipctl/advice.go:331](tools/shipctl/advice.go#L331)) считает по нему
же и покажет пересечение, которого нет.

Актуальность проверена на груминге 2026-08-17 прогоном на стенде
`tools/shipctl` с синтетической доской: XR-001 в In progress, XR-002 в
Backlog, коммит ветки XR-001 с subject «fix: XR-001 правка, пробел DoD цели
XR-002 снят», после `merge --train` функция `trainTasks` вернула
`train=[XR-001] strays=XR-002 в backlog`. Предмет на месте.

## Чего хотим

Владельцем коммита считается первый ID в subject, прочие упоминания в тексте
не берутся. Запись раздела «Выкат» файла задачи остаётся вторым источником и
работает как раньше: слитое через shipctl находится по ней, а поиск по subject
остаётся запасным путём для слитого руками.

Правило одно на все три места, где сейчас стоит поиск ID словом, иначе состав
поезда, состав отката и подсказка о пересечении разойдутся между собой.

## DoD

- Коммит принадлежит задаче, чей ID стоит в subject первым; коммит с чужим ID
  дальше по тексту в состав задачи не попадает. Правило общее у `codeCommits`,
  `taskCommits` и подсчёта пересечения в `advice.go`.
- Коммит без единого ID в subject и коммит, найденный по записи раздела
  «Выкат», ведут себя как раньше.
- Регрессионный тест на стенде `tools/shipctl`: соседка, чей ID лишь упомянут
  в чужом subject, не приходит осиротевшей и не отбивает merge. Тест красный на
  старом коде, и это подтверждено `regcheck`.
- Свой тест на откат: `taskCommits` не отдаёт чужой коммит к `revert`.
- Раздел README shipctl про то, какие коммиты у задачи (строки 300-308),
  называет правило первого ID.

## Ранг

`50+5+2+5+3 = 65`, P1.

- Серьёзность 50 (Critical). Основной сценарий конвейера, слияние задачи,
  встаёт наглухо, и обход болезненный: чтобы сдвинуться, приходится разбираться
  в чужой строке и трогать чужую задачу (закрыть цель либо вернуть её в In
  progress, отдав свой выкат чужим грузом). Своими силами задачу, которую
  сливают, не сдвинуть.
- Ценность 5. Слияние перестаёт вставать на ровном месте, а разбор такого
  отказа каждый раз стоит сессии.
- Неопределённость 2. Подход назван в самой находке, другого разумного нет.
  Открыта деталь: чем считать первый ID у коммитов, где ID вообще не в начале
  (`docs: DK-278 ...` идёт после префикса), и распространяется ли смена на
  `taskCommits`, где по ней собирается откат.
- Поправка на баг 5. Сломано то, что работало: shipctl приписывает задаче
  чужой код.
- Рычаг 3. Чинит инструмент, через который проходит каждая задача доски.
