# DK-298: taskctl: вид приёмки суффиксом строки доски, флаги add и set, ворота move check

## Ход работы

- Исполнение: подпроцесс glm-5.2/medium по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-13.
- Ревью: подпроцесс glm-5.2/high по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-13.

## Сценарий проверки

Ворота и разбор вида проверяются Go-тестами и ручным прогоном команд на
синтетической доске. Тесты обязаны падать на старом коде (без поля `Accept` в
`AddParams`, без суффикса в `splitTitle`/`joinTitle`) и проходить на новом.

### 1. Тесты (DoD 1, 3, 4)

Сборка и прогон модуля taskctl (go.work требует `GOWORK=off`, см. MEMORY.md
«go test ./... из toplevel сломан»):

```sh
cd tools/taskctl && GOWORK=off go test .
```

Что покрывают новые и обновлённые тесты:

- `TestSplitJoinTitle` разбирает и собирает суффикс `[приёмка: ...]` в
  фиксированном порядке (после, приёмка, провал, блок), round-trip сохраняет
  заголовок;
- `TestAcceptOfSuffix`, `TestAcceptSuffix` читают и собирают вид, агентский
  остаётся без суффикса;
- `TestAddAcceptRequired` отбивает `add` без `--accept`, отбивает `agent` с
  `--barrier`, агентский заводится без суффикса;
- `TestAddNonAgentRequiresBarrier` отбивает `user`/`mixed` без `--barrier`,
  отбивает чужой ключ, для `user` с барьером «глаза» заводит суффикс в заголовке
  и скелет «Приёмка» в файле задачи;
- `TestMoveCheckGateRejectsNonAgentWithoutBypasses` отбивает `move check` без
  перебора обходов и пропускает при ровно трёх строках для барьера «глаза»;
- `TestMoveCheckGateAgentSkipsAcceptance` агентский вид в Check «Приёмка» не
  требует;
- `TestClosePreservesAcceptSuffix` суффикс вида переживает `close` и попадает в
  архивную строку;
- `TestSetAcceptRevision` `set --accept` меняет вид, барьер «согласие»
  повышения не допускает;
- `TestJSONAcceptField` `list --json` кладёт вид в отдельное поле `accept`;
- `TestParseAcceptanceCountsByBarrier` счёт обходов по подсписку второго
  уровня;
- `TestAcceptanceSectionHonoursFences` заголовок «Приёмка» внутри блока кода
  чужой и в раздел не попадает;
- `TestCheckMarks` переработан под новую подпись `checkMarkLabel(root, id,
  title)` и формат «код слит, вид agent» вместо «сценарий агентский»;
- `TestListAnnotatesCheckRows`, `TestListNoAnnotationsWhenDirty`,
  `TestShowAnnotatesCheckRow` печатают «вид agent»/«вид user», Check-строка с
  user-суффиксом в фикстуре доски выражает вид.

### 2. Ручной прогон команд (DoD 1 и 4)

На синтетической доске во временном репозитории проверяются флаги `add`/`set`
и чтение вида в `list`, `age`, `view`/`show`, `json` и `lint`.

Завести минимальный репозиторий и доску:

```sh
tmp=$(mktemp -d)
mkdir -p "$tmp/docs/tasks"
git -C "$tmp" init -q -b main
git -C "$tmp" config user.email t@t && git -C "$tmp" config user.name t
taskctl -C "$tmp" init --prefix XR --name "песочница"
git -C "$tmp" add docs && git -C "$tmp" commit -qm init
```

DoD 1, флаги add. Без `--accept` отказ, агентский без суффикса, user и mixed
без `--barrier` отказ, с барьером заводят суффикс и файл задачи:

```sh
# Отказ: add без --accept.
taskctl -C "$tmp" add --title "Без вида" --type task --rank "0+1+1+0+1"
# Агентский: суффикса нет.
taskctl -C "$tmp" add --title "Агентская" --type task --rank "0+1+1+0+1" --accept agent
# Отказ: user без --barrier.
taskctl -C "$tmp" add --title "Юзер" --type task --rank "0+1+1+0+1" --accept user
# Отказ: agent с --barrier.
taskctl -C "$tmp" add --title "С барьером" --type task --rank "0+1+1+0+1" --accept agent --barrier глаза
# User с барьером «глаза»: суффикс в заголовке, файл задачи со скелетом «Приёмка».
taskctl -C "$tmp" add --id XR-010 --title "С видом" --type task --rank "0+1+1+0+1" --accept user --barrier глаза
taskctl -C "$tmp" show XR-010
cat "$tmp/docs/tasks/XR-010.md"
```

В файле `XR-010.md` стоит скелет: `## Приёмка`, `- вид: user`,
`- барьер «глаза»:`. Заголовок строки: `С видом [приёмка: user]`.

DoD 4, чтение вида. Суффикс разбирается в `list`, `show`, `json` и `lint`:

```sh
taskctl -C "$tmp" list backlog
taskctl -C "$tmp" show XR-010
taskctl -C "$tmp" list backlog --json | python3 -m json.tool
taskctl -C "$tmp" lint
```

В печатном `list` под строкой XR-010 идёт `вид user`; в `show` то же самое. В
JSON поле `accept` у агентской пустое, у XR-010 равно `"user"`, поле `title`
несёт основу без суффикса. `lint` на только что заведённой строке молчит:
файл есть, раздел «Приёмка» есть, барьер из шести, число обходов у скелета
нулевое, а ворота move check срабатывают только при переводе в Check, lint же
проверяет разбор и наличие раздела, не счёт (счёт это отказ move).

DoD 1, пересмотр вида. `set --accept` меняет суффикс, «согласие» повышения не
допускает:

```sh
# User -> agent на барьере «глаза» проходит.
taskctl -C "$tmp" set XR-010 --accept agent
taskctl -C "$tmp" show XR-010
# Барьер «согласие» повышения не подлежит.
printf '\n## Приёмка\n\n- вид: user\n- барьер «согласие»:\n  - подтверждение заказчика\n' \
  >> "$tmp/docs/tasks/XR-010.md"
taskctl -C "$tmp" set XR-010 --accept user
taskctl -C "$tmp" set XR-010 --accept agent   # отказ: согласие
```

Ожидаем: первая команда снимает суффикс (`вид agent -> user` уже не написать,
ибо было user; в примере обратный ход), вторая ставит user, третья
отбивается сообщением про непреходящий барьер «согласие».

DoD 2, ворота move check. Не агентский вид без перебора обходов в Check не
пускает, с ровно тремя строками для «глаза» проходит:

```sh
taskctl -C "$tmp" set XR-010 --accept user   # вернуть user, если сняли
taskctl -C "$tmp" move XR-010 in-progress
printf '\n## Сценарий проверки\n\n1. Шаг.\n2. Ожидаем.\n' >> "$tmp/docs/tasks/XR-010.md
# Отказ: в «Приёмка» нет строк обхода.
taskctl -C "$tmp" move XR-010 check
# Дописать три строки обхода барьера «глаза».
cat >> "$tmp/docs/tasks/XR-010.md" <<'EOF'
  - headless-замер: годится, ширина уходит агенту
  - регcheck по хуку: годится, гоняется на comмите
  - глазом по дашборду: не годится, нужна доставка ревьюверу
EOF
# Теперь проходит.
taskctl -C "$tmp" move XR-010 check
```

DoD 3, сохранение вида в архиве. `close` переносит суффикс в архивную строку:

```sh
taskctl -C "$tmp" close XR-010 --date 2026-08-13
grep 'приёмка: user' "$tmp/docs/TASKS-archive.md"
```

## Ревью

- tools/taskctl/accept.go:42,65. acceptOf читает вид end-anchored регуляркой ``\s*\[приёмка: ...\]\s*$``, а фиксированный порядок суффиксов (dep.go:13-16) ставит [приёмка:] ДО [провал:] и [блок:]. Любая user/mixed-задача с суффиксом провала или блокировки читается как agent. Это ломает acceptOf на чьем-то суффиксе, а splitTitle разбирает суффиксы в правильном порядке и работает, поэтому json верен, а view/lint/gate читают вид неверно. Воспроизведено end-to-end: задача user, прошедшая Check, после taskctl fail несёт заголовок «Foo [приёмка: user] [провал: 500]»; если после этого испортить раздел «Приёмка» (убрать обходы) и снова сделать move check, acceptOf в gate.go:96 возвращает agent, ворота приёмки молчат, move проходит с exit 0. Дополнительно: в Check view.go:168 печатает «вид agent» вместо user, а вне Check kind-метка гаснет; lint.go:107 на failed/blocked user-задачах целиком их пропускает. Тест TestAcceptOfSuffix (accept_test.go:13) не покрывает случай [приёмка:] с последующим [провал:]/[блок:], поэтому баг прошёл. Лечится тем, чтобы acceptOf разбирал вид тем же путём, что splitTitle (снимать хвосты fail/block/dep перед сопоставлением), а не сырой end-anchored регуляркой.
- tools/taskctl/lint.go:134. lintAcceptance проверяет не только наличие раздела «Приёмка» и ключ барьера из шести, но и число строк обхода (bypasses != want). Сценарий этой же задачи (DK-298.md:102-105) ждёт, что lint на свежем скелете молчит, и явно пишет «lint же проверяет разбор и наличие раздела, не счёт». На деле add --accept user --barrier глаза заводит файл с нулём строк обхода, и lint тут же печатает «у барьера «глаза» обходов 3, а перебор в «Приёмка» имеет строк 0» (воспроизведено, exit 1). Шаг «taskctl lint» сценария на свежезаведённой user-задаче падает. LLD DK-292, решение 6 относит lint к строке user/mixed без раздела с ключом барьера, а счёт обходов оставляет воротам move check (решение 4). Пересчёт у lint создаёт шум на каждой новой user/mixed-задаче до того, как исполнитель допишет обходы. Лечится тем, чтобы убрать проверку bypasses != want из lintAcceptance, оставив наличие раздела и валидность ключа барьера.
- tools/taskctl/README.md:124-127. Абзац про пометки Check остался от старой схемы и противоречит новой: «заголовок `## Сценарий проверки (агентский)` в файле значит «сценарий агентский», иначе «сценарий пользовательский»» и «файла задачи нет вовсе ... меток тоже нет: строка печатается как раньше». Оба утверждения больше не верны: вид читается из суффикса строки доски (LLD DK-292, решение 3), а Check-строка без файла теперь печатает «вид agent» всегда (view.go:165-168, checkMarkLabel уже не возвращает пусто). Новый пункт про вид лежит ниже (README.md:268), и документ противоречит сам себе. LLD решение 3 прямо требовал переписать это место оговоркой, что заголовок с пометкой (агентский) стал наследием, а вид уехал в суффикс строки. Надо переписать строки 124-127 под новую схему.
