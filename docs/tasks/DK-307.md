# DK-307: Цикл цели в одном окне, исполнители на любом операторе

записан 2026-08-13, разобран 2026-08-15

## Что происходит

Задача на второй подписке начинается с запускатора: shipctl code готовит
отдельное окно vscode с glm-окружением и своим деревом, и пользователь дежурит
в двух окнах. Механика делегирования при этом уже есть: agentctl run поднимает
уехавшую ступень подпроцессом claude -p с окружением второй подписки прямо из
текущего окна. До жизни в одном окне ей не хватает трёх вещей:

- модель субагенту в glm-сессии передаётся только опусканием model, иначе
  расход утекает в квоту claude-code;
- headless-запуск убивает фоновых субагентов через 10 минут после конца хода,
  длинный конвейер в делегате гибнет;
- диспетчер расходует квоту того харнеса, в котором сидит, поэтому цикл цели
  уводили целиком в glm-окно.

## Чего хотим

Диспетчер сидит в одном окне, исполнители и ревьюверы уходят ступенью вердикта
на любой оператор, второе окно с ручным дежурством не нужно. Разбор начать с
вопроса, можно ли поднять субагента с другим окружением харнеса (свой
ANTHROPIC_BASE_URL и ключ на процесс), не смешав учёт расхода; если окружение
процесса развести нельзя, честно записать это ограничением харнеса и закрыть
строку с причиной.

## DoD

Цикл цели запускается из окна первой подписки, исполнитель ступени base уходит
на вторую подписку и доводит задачу до конца без второго окна, а расход ступени
виден в панели той подписки, на которой она работала. Смежные строки (DK-203
окно без задачи, DK-269 отставание glm-дерева) после этого пересматриваются.
