# DK-312: taskctl close зовёт ship --drain после закрытия задачи

## Что происходит

Очередь выката освобождается вместе с `taskctl close`. Задача уехала в архив,
копящийся поезд (его копит `merge --train`, DK-274 и DK-311) можно катить.
Сегодня close об этом молчит. Разлив остаётся звать руками (`shipctl ship`)
либо диспетчеру пачки, готовые задачи ждут, пока есть кому подойти к машине.

Разбор лежит в `docs/lld/DK-306-merge-queue.md`, решение 4. Общий хук с
маркером там отвергнут, разлив зовут напрямую две точки, и первая из них
close.

## Чего хотим

`close` после записи и пуша доски зовёт `shipctl ship --drain` в том же
основном чекауте. Замок `ship.lock` держат только команды shipctl, close его
не берёт. close успевает закоммитить доску до вызова, а ship заходит в замок
с чистого листа.

Вызов best-effort. Провал выката дописывается в отчёт close предупреждением и
не роняет его, отсутствие shipctl в PATH предупреждает тем же порядком и
называет способ поставить набор утилит.

## DoD

- `close` зовёт `shipctl -C <корень> ship --drain` после архива, когда строки
  задачи на доске уже нет.
- Провал разлива и отсутствие shipctl в PATH не роняют close, дописываются
  предупреждением с выводом ship.
- Тесты закрывают вызов, порядок «после архива» и оба предупреждения,
  краснеют на коде до правки (regcheck).
- `tools/taskctl/README.md` называет вызов и его best-effort.

## Ранг

38 (25+7+2+0+4), слагаемые из нарезки LLD DK-306. Серьёзность 25: без вызова
освобождение очереди событием не подхватывается, обход ручной `ship`.
Ценность 7: задача уехала в архив, и следующая готовая катится без чужого
захода. Неопределённость 2: close в taskctl, разлив в shipctl, стык через
subprocess. Рычаг 4: каждое закрытие становится точкой доставки разлива.

## Сценарий проверки

Агентский.

1. После слияния прогнать regcheck на новых тестах разлива против коммита с
   самой правкой:

```
cd ~/projects/devkit
regcheck --base "$(git log -1 --format=%H --grep 'DK-312 close зовёт ship --drain')^" \
  --tests tools/taskctl/drain_test.go \
  -- sh -c 'cd tools/taskctl && GOWORK=off go test . -run "TestCloseCallsShipDrainAfterArchive|TestCloseDrainFailureWarns|TestCloseDrainSilentSuccess|TestCloseDrainNoShipctl" -count=1'
```

   Ждём строку про красноту на коде до правки и зелень на текущем: «тест
   краснеет на ...^ и проходит на текущем коде, регрессия закрыта».

2. Прогнать весь пакет taskctl, соседние ворота close (архив, маркеры
   «после», ворота агентской проверки) должны остаться на месте:

```
cd ~/projects/devkit/tools/taskctl
GOWORK=off go test . -count=1
```

   Ждём `ok` без FAIL.

3. Стык выкаченных бинарей. Закрытие самой DK-312 (`taskctl close DK-312` в
   основном чекауте после выката) это первый живой прогон вызова, и в выводе
   close ждём строку разлива от настоящего shipctl: «разлив не нужен: ...» на
   пустом поезде либо отчёт выката на непустом. Молчание значило бы, что
   выкаченный close зовёт старую логику.
