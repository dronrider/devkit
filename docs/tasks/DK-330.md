# DK-330: Подсказка taskctl add и set не называет --accept и --barrier

## Что происходит

После DK-298 у `taskctl add` появились флаги вида приёмки: `--accept` без
него команда отказывает, а `--barrier` обязателен для `mixed` и `user`. Шапка
`usageText` (`tools/taskctl/main.go`) перечисляет прежний набор `add`:
`--title`, `--type`, `--rank`, `--cost`, `--link`, `--status`, `--id`,
`--reason`; про `--accept` и `--barrier` там ни слова. То же у `set`: флаг
`--accept` есть в разборе (`main.go:356`), в шапке нет. Узнаются флаги только
из отказа команды («для --accept mixed нужен --barrier <ключ> из шести
барьеров») либо из `-h` подкоманды. Поймано на нарезке цели DK-327
2026-08-14; на 2026-08-18 воспроизводится, `taskctl` без аргументов печатает
шапку без обоих флагов.

Обход дешёвый (второй заход после отказа), но подсказку читает агент на каждом
груминге и нарезке, и лишний заход стоит хода.

## Чего хотим

Шапка `add` и `set` в `usageText` называет `--accept agent|mixed|user` и
`--barrier <ключ>` с закрытым списком барьеров (глаза, доступ, необратимость,
секрет, согласие, событие). Тест сверяет шапку с набором флагов, объявленных
у подкоманды, чтобы следующее расхождение ловилось само.

## DoD

`taskctl` без аргументов и `taskctl help` печатают у `add` и `set` флаги
`--accept` и `--barrier` со списком ключей барьера. Тест на подсказку падает
на старом `usageText` (regcheck красный до фикса) и проходит после; тот же
тест сверяет флаги шапки с флагами `flag.FlagSet` подкоманды `add`.

## Ранг

`25+4+0+5+2 = 36`, P2.

- Серьёзность 25. Трение с дешёвым обходом: флаг узнаётся из отказа команды
  вторым заходом.
- Ценность 4. Регулярная операция: `add` зовётся на каждом груминге и каждой
  нарезке цели.
- Неопределённость 0. Рутина: строка справки и тест на неё.
- Поправка на баг +5. Подсказка отстала от кода после DK-298.
- Рычаг 2. Небольшая своя польза: агент не тратит ход на отказ.

Цена S: правка одной константы и один тест.

## Ход работы

Шапка `add` в `usageText` (`tools/taskctl/main.go`) называет `--accept
agent|mixed|user` в первой строке и `--barrier` с шестью ключами отдельной
строкой; шапка `set` называет `--accept`. Объявления флагов обеих подкоманд
вынесены в `addFlags` и `setFlags`, чтобы тест собирал тот же `flag.FlagSet`,
что и команда, и сверял с ним блок шапки. Дальше DoD правка не идёт: у `set`
флага `--barrier` в разборе нет, в шапке его и не обещаем.

## Тесты

Два теста в `tools/taskctl/main_test.go`:

- `TestUsageTextAcceptBarrier`: регрессионный, шапка содержит `--accept
  agent|mixed|user` у `add` и `set` и `--barrier` с перечнем ключей у `add`.
- `TestUsageMatchesFlagSet`: каждый флаг, объявленный `addFlags` и `setFlags`,
  назван в блоке своей подкоманды в шапке (блок вырезает `usageEntry`); общие
  `-C`, `-m`, `--push` описаны абзацем ниже и из сверки исключены. Следующее
  расхождение шапки с разбором ловится этим тестом.

Прогон: `cd tools/taskctl && GOWORK=off go test ./...` даёт `ok`.
Краснота: `regcheck --base main -- sh -c 'cd tools/taskctl && GOWORK=off go
test -run "TestUsageTextAcceptBarrier|TestUsageMatchesFlagSet" .'` печатает
«тест краснеет на main и проходит на текущем коде, регрессия закрыта».

## Сценарий проверки

Вид агентский, гоняется после слияния на собранном бинаре.

1. Воспроизведение на старом коде: `git show <sha до слияния>:tools/taskctl/main.go | sed -n '/^const usageText/,/^`/p' | grep -c -- '--accept'`
   печатает `0`: в шапке до правки флага нет.
2. `taskctl help | grep -E '^  add .*--accept agent\|mixed\|user'` находит
   строку `add`.
3. `taskctl help | grep -- '--barrier глаза|доступ|необратимость|секрет|согласие|событие'`
   находит строку с шестью ключами.
4. `taskctl help | sed -n '/^  set /,/поправить/p' | grep -c -- '--accept'`
   печатает `1`.
5. Как раньше и не сломалось: `taskctl add --title t --type bug --rank "1+1+1+1+1" -C /tmp/нет-такого` отказывает
   по каталогу, а не по разбору флагов, то есть `flag.FlagSet` собирается.
