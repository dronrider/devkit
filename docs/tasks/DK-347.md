# DK-347: deploy.local: компоненты команды test идут параллельно с потолком воркеров [после DK-346]

## Ход работы

- Исполнение: подпроцесс glm-5.2/medium по вердикту pick, 2026-08-15. Первый исполнитель упёрся в лимит API с готовым раннером и тестами, доделка вторым исполнителем той же модели: разбор кода, regcheck, замер стены, ключ deploy.local, этот файл.
- Раннер `tools/devkitctl/parallel.py`: 14 компонентов (восемь go-утилит, hooks,
  сюита devkitctl, skills, check-skills, goal-loop, doctor), общая очередь с
  потолком воркеров (по умолчанию 8). Первый провал валит прогон: занятые
  компоненты получают TERM по группе процессов, а упрямый подпроцесс,
  игнорирующий TERM, через пару секунд получает KILL, иначе стоп виснул бы
  на нём. Вывод провалившегося компонента печатается целиком, `--list` печатает
  перечень.
- Дефект, найденный при доделке: задокументированный зов раннера из корня
  падал на машине с чужим `~/go.work` по первому же go-компоненту (та же
  находка DK-115, ради которой ключ `test` нёс `GOWORK=off` в обёртке).
  Глушить workspace обязан сам раннер: go-компоненты идут с `GOWORK=off` в
  собственном env, тест закрывает связку.
- Скрытый флак, вскрытый параллельным прогоном: тесты памяти дашборда
  `TestScanReadOnceForRepeatedRequests` и `TestBoardReadOnceForRepeatedScreens`
  проверяли кэш без заморозки часов сервера, хотя инъекция `s.now` для этого
  есть и соседние тесты ею пользуются. Под нагрузкой цепочка запросов
  перешагивала срок памяти (5 и 10 с) и обход честно шёл в git заново: два
  полных прогона упали именно на этом тесте. Часы заморожены, семантика тестов
  та же. Regcheck по этой паре зелёный и на старом коде: продукт не менялся,
  краснота видна только под параллельной нагрузкой, доказательством служат
  упавшие прогоны выше.
- Тесты раннера в `tools/devkitctl/parallel_test.py` (12 тестов) на
  синтетическом каталоге с короткими скриптами: живые компоненты для проверки
  раннера тяжёлые. Связка закрыта regcheck: тесты краснеют на HEAD, зелёные
  на правке.
- Ключ `test` в гитигнорнутом `.devkit/deploy.local` этого дерева зовёт раннер
  строкой `export GOWORK=off; python3 tools/devkitctl/parallel.py`.
- Замеры стены на машине исполнителя (10 ядер, Docker VM на 5 vCPU, чужая
  нагрузка): последовательная цепочка 433 с (нарезка DK-166), полный прогон
  раннера 305-327 с при потолках 8, 4 и 2. Ожидание нарезки (не дольше

  копирование дерева и
  сюита devkitctl (98 классов, каждая копирует стенд) удваивают её стену при

Агентский. Прогон идёт по выкаченной ревизии из корня чекаута:

1. Полный прогон раннера:

   ```
   python3 tools/devkitctl/parallel.py; echo "exit=$?"
   ```

   Ожидание: `exit=0`, строка итога `Ran 15 of 15 components` и последняя
   строка `OK`. Стена не дольше самого тяжёлого компонента с запасом в треть:
   на тихой машине это порядок 150-220 с (тяжёлый компонент go:dashboard в

## Ревью

- Ключ `test` основного чекаута не переведён на раннер: в /Users/rider/projects/devkit/.devkit/deploy.local до сих пор `export GOWORK=off; (cd tools/devkitctl && python3 suite.py)`, а кандидат 2 цели DK-166 требует прямо «команда test в deploy.local основного чекаута зовёт раннер». Файл гитигнорнут, слиянием не приедет, в файле задачи назван только ключ «этого дерева», про основной чекаут молчание. Ворота shipctl merge читают ключ дерева слияния, так что даже слияние самой DK-347 погонит старую цепочку, и на выкате раннер не позовёт никто. Перевести ключ основного чекаута на раннер (строка уже записана в корневом README) или вслух записать в файле задачи, кому оставлено это звено и почему: исправлено, ключ основного чекаута переведён на раннер
- Компонент `check-exec-bit` потерян из цепочки: старый ключ `test` (замер 433 с в DK-166) и корневой README гоняли `python3 hooks/check-exec-bit.py` отдельным шагом, а раннер его не гонит, и в списке компонентов его нет (--list: 14 позиций без него). Замена не полная: юнит-тест check_exec_bit_test.py гоняется в компоненте hooks, но сам чекер по живому репозиторию в локальном прогоне больше не ходит (в CI остаётся). README при этом продолжает звать его «по одному руками», то есть перечисление честное, но замысел задачи был перенести цепочку test в раннер целиком. Вернуть компонент в перечень (работает и из cwd hooks, проверено: exit 0) и убрать упоминание из ручного списка README, либо вслух обосновать в файле задачи, почему чекер остаётся за раннером: исправлено
- Компонент, который не может стартовать, молча исчезает из прогона: Popen кидает FileNotFoundError (несуществующий cwd или бинарник) прямо в потоке-воркере, трейсбек уходит в stderr, а прогон завершается `Ran N of 14` с числом меньше 14 и кодом 0, если остальные зелёные. Воспроизвёл на ветке: компонент с несуществующим cwd выпал из outcomes, first_fail остался None. Правило ядра: случай, когда фича бездействует из-за окружения, неотличим от штатной работы, и это ровно он. Для фиксированного перечня из 14 известных компонентов путь почти всегда валиден, но раннер зовётся человеком по докам и потолок -j произволен, а переименованный каталог утилиты или убранный скрипт дадут зелёный прогон без одного go-инструмента. Обернуть старт компонента и гонять исключение как провал этого компонента (код возврата не 0, вывод с трейсбеком), тогда стоп по первому провалу сам разрулит её: исправлено
- Правка чужой сюиты едет тем же коммитом, что и раннер: `feat(devkitctl): DK-347 ...` вёз parallel.py с тестами и tools/dashboard/cache_test.go. История проекта держит коммиты по зонам (feat(dashboard) отдельно от feat(devkitctl), в DK-346 тесты раннера ехали своим feat(devkitctl), доки отдельно). Заморозка часов сама по себе уместна и достаточна (срок памяти остаётся покрытым тестами TestScanCacheExpires и TestBoardCacheCeiling через advance, семантика не менялась, сюита зелёная), претензия только к составу коммита. Расщепить переносом правки cache_test.go в отдельный коммит с ID задачи, например `test(dashboard): DK-347 заморозка часов в тестах памяти под параллельным прогоном`: исправлено
