# DK-362: dashboard: headless-запуск с доски не наблюдаем, чата нет в сессиях

## Что происходит

Реплика пользователя во «Входящие» цели DK-327, 2026-08-15 (доставлена
витку почтальоном DK-341): случайный запуск с дашборда перевёл DK-194 в In
progress, исполнитель ушёл в headless (tmux task-DK-194 через agentctl
exec), но работа не видна: чата нет в списке сессий, экрана агента с доски
тоже нет, найти можно только раскопками по транскриптам. Сценарий 2 цели
(«видеть, чем агент занят») на headless-запусках не закрыт: строка In
progress не подкреплена ничем наблюдаемым.

## Чего хотим

Headless-сессия, поднятая с доски через agentctl exec, видна как обычная:
разговор стоит в списке сессий задачи, экран агента открывается с доски
(чип «работает» ведёт на живой статус), и это держит тест. Разобрать, чем
headless-запуск через exec отличается для sessions.go от прежнего прямого
подъёма (каталог, cwd, session_id), и закрыть щель.

## DoD

- Запуск с доски через agentctl exec даёт разговор в списке сессий задачи и
  рабочий экран агента; тест воспроизводит headless-сессию (транскрипт в
  каталоге дерева задачи с cwd от exec) и падает на старом коде.
- Смок или стенд держит стык, regcheck зелёный.

## Итог

Каталог журналов у второй подписки свой, и список сессий его теперь учитывает.
Каталог хозяйства подписки в машинном виде `agentctl harness --json` это поле
`home`. Дашборд складывает из него и своего `~/.claude` корни журналов и
обходит их все: список сессий задачи, экран агента по id разговора, работы из
транскриптов и вопрос груминга ходят одним и тем же перечнем корней. Разговор
headless-запуска с доски стоит в списке сессий своей задачи, и чип «работает»
ведёт на живую ленту. Стык держит смок: клиент второй подписки на стенде пишет
транскрипт в своё хозяйство, а шаг выбора подписки после запуска запрашивает
список сессий задачи и ленту разговора.

## Сценарий проверки

Сценарий агентский, главный шаг живой и идёт после выката: тесты ветки зелёные
и до него, а стык до конца проверяет только настоящий подъём на второй
подписке. Обход исполним, вторая подписка на машине настроена
(`~/.devkit/harness.local`, хозяйство `~/.devkit/claude-glm`), квота её не
лимитируется, и заказ берётся одноходовый.

1. Живой подъём и обе ручки, на собранных с ветки бинарях. Пробное окружение:
   свой дом с копией `harness.local` (путь к хозяйству второй подписки
   абсолютный, чтобы клиент поднялся со своей авторизацией), свой корень
   проектов с каталогом-пробой и `docs/TASKS.md` в нём, `dashboard.local` с
   этим корнем и своим портом, `DEVKIT_HOME` на чекаут devkit.

   ```bash
   cd <проба> && agentctl exec --harness glm-code -- \
     claude -p 'Выполни XR-362: ответь одним словом «готово», ничего больше не делай'
   dashboard serve   # с домом пробы, agentctl рядом с бинарём
   curl -b cookies '.../api/projects/<проба>/sessions?task=XR-362'
   curl -b cookies '.../api/projects/<проба>/sessions/<id>'
   ```

   Ждём: транскрипт лежит в `~/.devkit/claude-glm/projects/<путь пробы>`, а не
   в `~/.claude`; список сессий задачи отдаёт этот разговор с подписью «по
   первой реплике»; лента отдаёт реплики, первой стоит заказ, последней ответ
   агента. Вывод прогона занесён в «Ход работы».
2. Ничего не сломано (шаг дублирует тесты ветки, гоняется коротко): `GOWORK=off
   go test ./...` из `tools/dashboard` и `tools/agentctl` зелёные, смок внутри
   проходит шаг «выбор подписки доезжает до команды» с припиской про виденный
   разговор.

Вторая подписка (glm-code, дом ~/.devkit/claude-glm) реально настроена на машине, это подтверждает сам исполнитель в «Ходе работы» живым журналом DK-194.
