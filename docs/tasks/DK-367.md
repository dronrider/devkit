# DK-367: go test ./... из toplevel не раскрывается в модули tools, merge --test и regcheck падают

записан 2026-08-13, оформлен 2026-08-13

## Что происходит

Go-модули devkit лежат в подкаталогах `tools/`, в корне репо нет ни go.mod,
ни go.work. README при этом зовёт каноническим прогоном `go test ./...`, и тот
же ключ `test` лежит в гитигнорнутом `.devkit/deploy.local`, откуда его берёт
`shipctl merge`.

На этой конфигурации команда падает ещё до запуска тестов:

    $ go test ./...
    pattern ./...: directory prefix . does not contain modules listed in go.work or their selected dependencies

`go test ./tools/...` падает по той же причине: tools это каталог с модулями,
а не модуль. Прогон возможен только явным перечислением модулей из go.work
(`go test ./tools/taskctl/... ./tools/shipctl/...`), и паттерн для «всех
модулей» в командах собрать нельзя.

Ветки у проблемы две, обе проверены на живом конвейере при слиянии DK-277
(2026-08-13):

- `shipctl merge` берёт `test` из `.devkit/deploy.local`, зовёт его в worktree
  задачи и падает «тесты после ребейза красные», хотя тесты зелёные: красна
  сама команда. Каждый merge обязан перекрывать её явным `--test` со списком
  модулей этой задачи;
- regcheck изолирует прогон во временный worktree, куда локальный корневой
  go.work не переезжает, и не может проверить красноту регрессионного теста.
  Красноту доказывают откатом исходников к base при оставленных тестах, чем
  теряется и сам смысл regcheck.

Отягчающее: корневой go.work нужен локально и не едет в git, иначе его
придётся коммитить и поддерживать. Чужой `~/go.work` при этом перехватывает
сборку: без своего go.work в корне репо go смотрит в домашний, и модули devkit
собираются в непредсказуемом окружении.

## Чего хотим

Одна команда из toplevel репо прогоняет тесты всех go-модулей проекта, и её
можно положить ключом `test` в `.devkit/deploy.local`, чтобы merge брал её из
конфига, а не из флага. Регрессионная проверка regcheck после этого тоже
должна находить модули и доказывать красноту без ручного отката исходников.

Направления два, выбор за исполнителем:

- git: корневой go.work коммитится в репо, README и deploy.local зазывают
  `go test ./...`, CI уже согласован с этим. Цена: файл едет в репо со списком
  модулей, и новый инструмент надо вписывать в go.work руками;
- обёртка: ключом `test` лежит короткая команда (`make test`, `devkitctl
  test`, скрипт `tools/test.sh`), которая сама находит модули и гоняет каждый.
  Цена: новая точка правды про состав модулей, ей нужна дока.

В обоих случаях regcheck обязан заработать: либо go.work переезжает в его
изолированный worktree, либо обёртка находит модули и там.

## Соседние строки, которые задача не дублирует и не ждёт

- DK-277 чинил критерий закрытости ревью в taskctl и shipctl; невозможность
  прогнать `go test ./...` она обошла явным `--test`, но не починила;
- ключ `test` в `.devkit/deploy.local` не едет в git, поэтому чинить надо сам
  способ прогона, а не значение ключа на одной машине.

## DoD

`go test ./...` (или обёртка из README) из toplevel репо прогоняет все
go-модули tools и зелёный; merge без явного `--test` проходит с командой из
`.devkit/deploy.local`; regcheck на ветке с регрессионным тестом доказывает
красноту сам, без ручного отката исходников. Способ прогона описан в README.

## Ход работы

Направление git (корневой go.work) проверено и отвергнуто. Даже с закоммиченным
`go.work` паттерн `go test ./...` из корня репозитория не собирается: пустой
корень сам не модуль, и go workspace не разворачивает `./...` в объединение
пакетов всех модулей workspace, только в пакеты каталога, откуда команда
позвана (проверено вживую после `go work init` на каждом из devkit-модулей).
`go test all` собирается, но тянет всю стандартную библиотеку как часть графа
зависимостей: несколько минут стандартных пакетов на каждый прогон, негодно.
Единственный рабочий паттерн с go.work это явный список модулей
(`go test ./tools/taskctl/... ./tools/shipctl/... ...`), то есть обещанной
короткой команды `go test ./...` go.work не даёт ни при каком раскладе.
Плюс раньше это же направление разбирал и отверг LLD DK-237 (раздел «Решение»,
`docs/lld/DK-237-shared-go-module.md`, строки 123-128): `GOWORK=off`, нужный
против чужого `~/go.work` (DK-115), глушит workspace целиком, и свой `go.work`
под этим ключом невидим ровно так же, как чужой.

Выбрано направление обёртка. Ключ `test` в `.devkit/deploy.local` уже гонит
`python3 tools/devkitctl/parallel.py` (задача DK-347, слита 2026-08-15, уже
позже записи этой задачи): раннер обходит каждый го-модуль в своём каталоге с
`GOWORK=off`, общий `go.work` ему не нужен вовсе. Но список модулей
(`GO_TOOLS`) хранился в коде руками и успел разойтись с деревом: модуль
`cmdout` (девятый го-модуль `tools/`) выпал из него молча, и обещание «обёртка
находит модули сама» не выполнялось. Починено: `parallel.go_tools()` ищет
модули по факту `go.mod` под `tools/*` глобом, список руками больше не
держится (тот же разбор попутно нашёл, что CI, `.github/workflows/ci.yml`,
не тестирует ни `cmdout`, ни `secretctl`; это отдельный, не относящийся к
DK-367 предмет, DoD задачи про CI ничего не говорит, и правка CI сюда не
входит).

Вторая половина бага была не в отсутствии go.work, а в самом regcheck: команда
теста в нём всегда гонялась в корне репозитория (`root`), даже когда `-C`
указывал на другой каталог, и переносила во временный worktree только
тестовые файлы, не смещение самого прогона. Поэтому что `go test ./... -run X`,
что явный список модулей из корня не работали для правки внутри
`tools/<модуль>`, что с go.work, что без него: `regcheck` не давал прогону
попасть в каталог модуля вообще. Починено: команда теста гоняется в `-C dir`
(и в изолированном worktree на том же относительном месте от корня), поэтому
`regcheck -C tools/<модуль> -- go test ./... -run X` работает без общего
go.work и без чужого `~/go.work` под ногами: каждый го-модуль tools
самодостаточен своим `go.mod`.

Итог: `go.work` в репозиторий не добавлен (согласуется с прежним решением
DK-237). Одна команда для «всех го-модулей tools» из toplevel это
`python3 tools/devkitctl/parallel.py` (уже документирована в README и
`tools/devkitctl/README.md`, уже стоит ключом `test`), regcheck на модуле
внутри tools вызывается флагом `-C` (документировано в
`tools/regcheck/README.md`).

## Сценарий проверки

Агентский: задача про сам прогон тестов, проверкой служит живой вызов команд
конвейера. Все три шага прогнаны вживую в дереве задачи, вывод настоящий.

1. Воспроизвести исходный баг. Из toplevel devkit (без локального go.work в
   корне, его в дереве и не было):

       $ go test ./...
       # ./...
       pattern ./...: directory prefix . does not contain modules listed in go.work or their selected dependencies
       FAIL    ./... [setup failed]
       FAIL

   Совпадает с описанием задачи буква в букву. Обёртка из README на
   исправленном коде:

       $ python3 tools/devkitctl/parallel.py
       go:dashboard      259.7s ok
       go:shipctl        230.0s ok
       hooks             142.1s ok
       devkitctl         138.5s ok
       go:agentctl       108.7s ok
       goal-loop         101.7s ok
       go:taskctl         73.9s ok
       go:obeycheck       25.6s ok
       go:secretctl       17.7s ok
       go:cmdout          14.7s ok
       go:trackctl        10.1s ok
       go:regcheck         5.5s ok
       skills              0.9s ok
       doctor              0.2s ok
       check-exec-bit      0.2s ok
       check-skills        0.1s ok
       Ran 16 of 16 components in 4m20s
       OK

   `go:cmdout` в списке впервые: до правки `parallel.py` его пропускал
   (модуль выпал из хранёного руками списка). Все 9 го-модулей `tools/`
   зелёные, ненулевой код возврата был бы виден строкой FAIL по конкретному
   компоненту.

2. merge без явного `--test`. Ключ `test` `.devkit/deploy.local` этой машины
   уже стоит строкой `export GOWORK=off; python3 tools/devkitctl/parallel.py`
   (заведён задачей DK-347): прогон шага 1 это она же и есть, `shipctl merge`
   берёт эту команду из конфига и на зелёном коде проходит этап тестов, не
   требуя `--test` со списком модулей руками.

3. regcheck на регрессионном тесте самой правки (`TestRunsInDirNotRoot`,
   `tools/regcheck/check_test.go`) доказывает красноту без ручного отката
   исходников, вызовом ровно того паттерна, который правка и вводит:

       $ regcheck -C tools/regcheck -- go test ./... -run TestRunsInDirNotRoot
       тест краснеет на HEAD и проходит на текущем коде, регрессия закрыта (тесты: tools/regcheck/check_test.go)

   HEAD здесь это код до этой задачи (команда теста в regcheck ещё гоняется в
   root, а не в `-C dir`): тест красный, потому что старый regcheck теряет
   каталог модуля. На текущем коде (правка check.go применена) тест зелёный.
   Бинарь собран из правки этой же задачи (`go build` в `tools/regcheck`),
   `git status` там же чистый до коммита, лишний бинарь в дерево не попал.
