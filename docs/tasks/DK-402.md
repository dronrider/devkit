# DK-402: Парковка задачи по вопросу и пробуждение тиком watch

Цель: [docs/tasks/DK-395.md](docs/tasks/DK-395.md)

## Что происходит

`Blocked` сегодня терминальный: никто не следит за приходом ответа и не
поднимает строку обратно. Вопрос с таймаутом написан (`goal-run --ask` держит
ящик признаком с внутренним сроком), но адреса у вопроса нет: он живёт в ленте
и ящике цели, поля задачи у него нет. Адрес вопроса и общий носитель писем
кладут транспортные строки DK-397 (DK-345 и инструмент ожидания), эта задача их
наследует.

## Чего хотим

Вопрос исполнителя паркует свою задачу и только её: машинная причина в blocked,
связь с вопросом по адресу. Ответ, положенный в ящик, будит строку тиком
`devkitctl watch` и возвращает её в кандидаты, а не сразу в работу. Устройство
парковки и пробуждения решает DK-400.

## DoD

На синтетической доске с тремя задачами вопрос по одной паркует только её:
строка уходит в blocked с машинной причиной и адресом вопроса, две другие
остаются в кандидатах. Письмо-ответ будит припаркованную тиком watch и
возвращает в кандидаты. Тесты модулей taskctl и devkitctl зелёные, regcheck
зелёный.

## Ход работы

- Разработка: подпроцесс glm-5.3/medium по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-17 18:32-18:32.

Протокол взят из решения 2 LLD DK-400 без отступлений: парковка это
`taskctl move <ID> blocked --reason "вопрос: <суть>"`, будит тик сторожка
`devkitctl watch`, возврат тем же `move <ID> in-progress`. Три места, где LLD
назвал не всё и решение дописано здесь:

- Где лежит ящик задачи. LLD говорит «в ящике этой задачи», не называя
  дерево, а транспорт DK-345 кладёт ящик в дерево сессии: исполнитель
  спрашивает из дерева задачи, диспетчер из основного. Сторожок ищет ящик
  в обоих: `<корень>/.devkit/mail/task-<ID>.inbox` и тот же путь в дереве
  задачи `../<проект>-<id>`, выведенном правилом shipctl treePath.
- Снимок ожидания. Свежий признак `.ask` у ящика отдаёт его инструменту
  ожидания (DK-397): пока срок не вышел, сторожок не будит, ответ заберёт
  сам ждущий заход. Протухший признак будить не мешает.
- Бинарь taskctl у агента launchd. Сторожок зовёт `taskctl -C <корень>
  move`, но launchd даёт агенту системный PATH без каталога бинарей, поэтому
  за PATH стоят каталоги установки релиза (те же, что перебирает
  `devkitctl update`).

Сторожний тик по припаркованным молчит только там, где парковок нет вовсе:
корень с припаркованными получает строку итога «припаркованных вопросом N,
разбуждено M» в свой журнал, чтобы «тик работает» проверялось по журналу,
а не по вере. Будит только «вопрос:»: «окружение:» и проза писем не ждут.
Сессию поверх доски сторожок не поднимает: возврат в In progress делает
строку кандидатом планировщика (DK-404), и это решение LLD, а не недоделка.

В taskctl добавлена страховка машинного префикса: причина со сломанной
формой («вопрос : суть») отбивается сразу с подсказкой, потому что сторожок
ищет в причине ровно «вопрос:» и битый префикс спал бы в Blocked без надзора.
Проза с похожим первым словом («вопросительный поиск») не отвергается.

Коммиты: сторожок с тестами, страховка префикса в taskctl с тестом, дока
(README обоих инструментов и карта переходов).

## Ревью

- Будит bare move без -m: taskctl -C <корень> move <ID> in-progress правит docs/TASKS.md и не коммитит, а за будящим никого нет. Правка висит грязной в основном чекауте: preflight следующего shipctl merge в этом корне откажет («в рабочем дереве незакоммиченное»), чужой taskctl -m подметёт её в свой коммит по pathspec, а правило доски про немедленный пуш не выполняется. Shipctl свой bare move накрывает commitBoard ровно поэтому. Будить с -m "docs(tasks): <ID> разбуждена ответом" и пушем по правилу доски либо записать осознанное решение в файл задачи с учётом отказа preflight; тест на состав вызова.: исправлено, будящий move идёт с -m "docs(tasks): <ID> разбуждена ответом" и --push, тем же вызовом taskctl (у него своя DEVKIT_PUSH_OK для pre-push), тест на состав вызова добавлен
- В файле задачи нет раздела «Сценарий проверки», а ворот merge спросит заголовок и откажет. Вид по умолчанию агентский, барьеров из ACCEPTANCE.md не названо, значит в сценарии обязан быть шаг, прогоняемый после выката и не повторяющий тесты ветки: припарковать строку вопросом, положить ответ в ящик, прогнать тик watch и увидеть возврат строки и строку итога в журнале.: исправлено, сценарий дописан диспетчером: болванка на живой доске паркуется вопросом, ответ в ящике будит её выкаченным тиком, будящий move сам коммитит и пушит правку доски
- taskctl_bin: ветка без taskctl в PATH (import update и перебор BIN_DIRS) не покрыта тестом, а именно она вынесена в решение про launchd-агента. Тест возможен подменой update.BIN_DIRS на временный каталог с исполняемым файлом.: исправлено, тест подменяет BIN_DIRS на временный каталог и проверяет оба исхода перебора (найден бинарь и пустой каталог)
- Страховка префикса пропускает заглавную форму: checkParkPrefix сравнивает первое слово причины с «вопрос»/«окружение» без учёта регистра, а сторожок ищет в заголовке ровно «[блок: вопрос:». Причина «Вопрос: нужна схема» (заглавная, естественное начало предложения при ручной парковке) проходит страховку молча и паркует строку, которую PARKED не матчит: её не будит ни один тик, и в строку итога «припаркованных вопросом N» она не попадает, ровно тот сон в Blocked без надзора, от которого страховка ставилась. Сравнение первого слова нормализовать регистром (strings.ToLower у проверяемого слова до сравнения с parkPrefixes), чтобы «Вопрос:» отбивалось той же подсказкой про машинный префикс; в TestMoveToBlockedQuestionPrefix добавить случай с заглавной формой.: исправлено, проверяемое слово нормализуется регистром и срезом двоеточия (strings.ToLower, TrimSuffix «:»), «Вопрос: нужна схема» отбивается той же подсказкой, случай с заглавной формой добавлен в тест
- Сценарий, шаг 1 и 4: болванка заводится «taskctl add, тип task, цена S» без названного вида приёмки, а add требует --accept обязательным. Возьми прогоняющий agent (привычный на доске вид), и close на шаге 4 отбивается воротами closeAgentGate: у файла болванки нет непустого раздела «Проверка», и шаг 4 без ещё одного ненаписанного шага (вписать в болванку раздел «Проверка» с выводом прогона) не исполняется. Назвать в шаге 1 вид и барьер явно, например --accept user --barrier <ключ из ACCEPTANCE.md>: у неагентского вида close без ворот проверки, сценарий становится исполнимым как написан.: исправлено, шаг 1 называет вид (--accept agent) и заводит файл болванки, шаг 4 вкладывает вывод тика в раздел «Проверка» и закрывает: барьер выдумывать не пришлось, ворота close заполнены самим прогоном

## Сценарий проверки

Вид агентский, прогон после выката в основном чекауте devkit выкаченными
бинарями на живой доске, материалом служит одноразовая строка-болванка.

1. Завести болванку (`taskctl add --accept agent`, тип task, цена S) и её
   файл (`taskctl file <ID>`), перевести in-progress и припарковать
   вопросом: `taskctl move <ID> blocked --reason "вопрос: сценарий DK-402,
   ответ лежит в ящике"`. Правка доски одним коммитом с пушем.
   `taskctl list blocked` показывает ровно её.
2. Положить ответ безадресной строкой в `.devkit/mail/task-<ID>.inbox`
   основного дерева.
3. Тик сторожка из PATH: `devkitctl watch`. Вывод содержит «припаркованных
   вопросом 1, разбуждено 1», `taskctl list in-progress` возвращает болванку,
   `git log -1 --pretty=%s` основного дерева печатает «docs(tasks): <ID>
   разбуждена ответом», и этот коммит уже в origin: будящий move коммитит
   и пушит сам.
4. Вывод тика вкладывается в раздел «Проверка» файла болванки, и она
   закрывается (`taskctl close`): ворота close агентского вида требуют
   непустой раздел, прогон его и заполняет.
5. `GOWORK=off python3 tools/devkitctl/parallel.py` зелёный: сторожок,
   страховка префикса и почтальон в общем прогоне.
