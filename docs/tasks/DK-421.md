# DK-421: Правила доки фичи: вход для читателя, впервые её видящего, и проверка чужим контекстом

записан 2026-08-17

## Что происходит

Пользователь, читая 2026-08-17 доку запускатора окна второй подписки в
`tools/shipctl/README.md`, не нашёл порядка первого запуска: разделы
разбирают устройство и доводы решения (DK-420 чинит именно эту доку). Дока
писалась агентом на закрытии задачи, и это не случай одной доки, а следствие
правил: они требуют от доки наличия, формы и актуальности, а содержания для
читателя, впервые видящего фичу, не требуют вовсе. Новичок по такой доке
фичу не запускает, агент тратит токены на вопросы в чат.

Что правила требуют сегодня и чего нет, проверено чтением `RULES.md`,
`RULES.core.md`, скиллов `board-ship`, `test-standard`, `proofread` и
раздела сторожа полноты в `tools/devkitctl/README.md`:

- `RULES.md`, «Документация изменений», п. 1: дока обязана быть («оседает
  в долгоживущей доке той же задачей»). Сторож полноты `devkitctl doctor`
  (DK-071) считает компонент описанным по заголовку или README, содержимого
  не смотрит;
- мимикрия и `proofread` правят форму по восьми пунктам DK-173, ни один не
  про то, дойдёт ли по тексту читатель до результата;
- ревью в `board-ship` п. 4 проверяет доку «по содержанию», конкретика там
  только про сценарий бага;
- нигде не сказано, что в доке фичи должно быть и в каком порядке. Агент на
  закрытии пишет то, что у него в контексте, а там решение и обоснование:
  заголовки раздела shipctl («Копия на окно, а не на задачу», «Окружение
  живёт в директории, а не в запуске») это заголовки решений LLD, внутри
  история (DK-192, IRC-097) и доводы. Текст LLD переехал в README, входа
  для пользователя нет; индекс решений при этом уже есть в `docs/map.md`.

Что усугубляет:

- `RULES.md` п. 36 и ядро: «Список ручных шагов в README это не решение, а
  перекладывание раскладки на пользователя». Правило про автоматику
  раскладки окружения, но читается как запрет писать шаги вообще, и агент
  порядок запуска не пишет вовсе. Список «что вызвать по порядку» и список
  «что руками отредактировать» это разные вещи;
- ядро: «по умолчанию комментариев не писать, только где неочевидно почему».
  Про код верно, а проза по инерции едет туда же: сплошное «почему» без
  «как»;
- `RULES.md` п. 87: «устоявшиеся факты переезжают из LLD в README», не
  сказано какие. Переезжают доводы, а нужны факты использования;
- между README утилит нет общего порядка разделов: где-то первым «Запуск»
  (cmdout, regcheck), где-то сразу механика (shipctl, dashboard). Новичок не
  знает, где искать вход.

## На что опереться

Стандарты, которые классифицируют содержимое доки (а не язык и тон, это
закрывает мимикрия), сравнены по нашей нужде: правило для README утилиты,
которое агент пишет на закрытии задачи, формулируется коротко, известно
моделям и проверяется прогоном чужого контекста.

- Diataxis (Procida, выросла из Divio): четыре вида по нужде читателя,
  tutorial, how-to, reference, explanation, смешивать нельзя. Прямо называет
  наш дефект: README shipctl состоит из explanation, tutorial и how-to в нём
  нет. Одна страница, моделям известна по имени, ссылка на неё тянет в
  контекст дисциплину без пересказа. Про порядок разделов внутри одного
  файла молчит: у неё виды это отдельные страницы сайта.
- DITA (OASIS): типы топика concept, task, reference под XML-тулчейн. Из
  неё берётся одно: у task есть предусловие, шаги и наблюдаемый результат,
  это и есть проверка «дошёл до `--dry-run`».
- Google developer docs (overview, quickstart, tutorial, how-to, concept,
  reference) и типы страниц Kubernetes (concepts, tasks, tutorials,
  reference с шаблонами «Before you begin», «What's next»): те же виды с
  большей дробностью; quickstart отдельно от tutorial для README утилиты
  избыточно, ссылаться в правилах devkit на чужой проект странно.
- Good Docs Project: готовые шаблоны README, quickstart, how-to, reference,
  explanation, ADR. Шаблон README закрывает порядок секций, но многословен и
  под открытые проекты с community-разделами.
- Standard Readme и порядок man-страницы (NAME, SYNOPSIS, DESCRIPTION,
  OPTIONS, EXAMPLES): только очерёдность, содержания вида не задают, зато
  правило «синопсис и запуск раньше устройства» в одну строку.
- Information Mapping (Horn): исторический корень перечисленных, procedure
  против process это «как запустить» против «как устроено»; методика
  проприетарная, в правилах не сослаться.

Все они одна мысль в разной упаковке: «делай» и «объясняй» это разные
тексты, и «делай» идёт первым. Ни одна не покрывает и виды, и порядок
разом, поэтому опора это пара: Diataxis как классификация и имя, на которое
ссылается правило; порядок man-страницы как очерёдность внутри README; из
DITA требование к шагам (предусловие, шаги, наблюдаемый результат). Наши LLD
с «Решение N» это ADR по сути, и Diataxis как раз говорит, что этому тексту
в README не место.

## Чего хотим

1. `RULES.md`, «Документация изменений», новый пункт: у доки фичи есть вход
   для читателя, впервые её видящего, и README организован по Diataxis:
   сначала первый запуск с нуля шагами с предусловием и наблюдаемым
   результатом (`--dry-run`, находка доктора, что-то видимое снаружи), потом
   повседневные команды, потом справка; разбор устройства и доводы решений
   остаются в LLD и файле задачи, README на них ссылается. Там же снять
   двусмысленность п. 36: автоматика раскладывает окружение, а порядок
   вызовов доке писать можно и нужно; под запретом ручные правки файлов,
   которые должна делать автоматика. Уточнить п. 87: из LLD в README
   переезжают факты использования, доводы остаются в LLD. Там же
   требование примеров, оно и есть половина входа: каждая команда и каждый
   конфиг показаны рабочим примером, а не перечнем параметров. Пример это
   готовая строка запуска с реальными значениями (не `<флаг> <значение>`,
   а `shipctl code DK-175 --dry-run`) и фрагмент конфига с настоящими
   ключами и правдоподобными значениями, который читатель копирует и
   правит под себя; секция EXAMPLES man-страницы, а не одна OPTIONS.
   Наблюдение того же дня по DK-420: сухая выжимка параметров у читателя не
   работает, порядок он собирает по примерам. Секреты в примерах заменяются
   заглушкой с видом настоящего значения (`ANTHROPIC_AUTH_TOKEN=sk-...`),
   а не словом «токен».
2. `RULES.core.md`, «Дока едет вместе с правкой»: одно предложение про вход
   для новичка, резидентно. Бюджет ядра держится (DK-173.2), ради этого
   ужимается соседнее.
3. Проверка чужими глазами, как у `proofread`: чужой контекст на чистом
   окружении идёт по доке и доходит до результата без подсказок (форму этой
   проверки нашла приёмка DK-420). Прописать её в `board-ship` п. 4
   (ревьювер гоняет для задач с новой пользовательской поверхностью) и в
   чеклист `test-standard` («заметное поведение осело в доке» дополняется
   «и у него есть вход»).
4. Детерминированная часть. Правило очерёдности машиноразличимо, вид текста
   нет, поэтому сторожу полноты `devkitctl doctor` добавляется одна
   структурная находка: у README утилиты первый раздел `##` это вход из
   фиксированного набора имён («Запуск», «Первый запуск», «Команды»,
   «Установка»), а не устройство. Тот же класс проверки, что первая строка
   README: грамматика файла без чтения смысла; `--fix` её не чинит, находка
   названа, и агент на закрытии её видит. Эвристики глубже (в разделе шагов
   есть блок кода или команда проверки) не брать: ложных срабатываний больше
   пользы. Понятность новичку сторож не ловит принципиально, это барьер
   «глаза» из `ACCEPTANCE.md`, и место его обходу в ревью и приёмке, а не в
   докторе. Отдельный стенд по образцу `obeycheck` в задачу не входит:
   прогонов столько, сколько задач заводят новую поверхность, и ревьювер их
   гоняет и так.
5. Уже написанное. DK-173.4 («стиль действует вперёд») про форму, а
   отсутствие входа это дефект содержания, и он не ждёт своей очереди
   молча: правило говорит, что делать агенту с плохой докой, которую он
   встретил. Встречается она двумя путями: находкой доктора (п. 4) и по
   ходу работы, когда агент читает README и по нему не доходит до
   результата. Дальше развилка по тому же порогу мелочи `RULES.board.md`,
   которым `live-core` решает судьбу правки devkit по ходу цели: вход в
   пару абзацев (что зовётся, чем проверить) дописывается сразу той же
   задачей, docs-коммитом отдельно; всё крупнее (переписать раздел, собрать
   порядок из нескольких мест, как в DK-420) уходит черновиком
   `taskctl draft` с названным местом пробела и тем, на чём читатель
   застрял. Правило ссылается на порог и на `live-core`, а не дублирует их:
   в проекте с целью расход пишется в «Журнал» по `live-core`, без цели
   правка идёт обычным порядком доски. Молча пройти мимо плохой доки
   правило не даёт: либо правка, либо черновик. Находки доктора по README
   самого devkit исполнитель этой задачи разбирает тем же правилом: входы в
   пару абзацев дописывает сразу, остальное (shipctl уже DK-420) заводит
   черновиками с указанием README и первого раздела.

## Образец

Правило откалибровано на живом тексте до оформления строки: раздел «Окно на
второй подписке» в `tools/shipctl/README.md` переписан по нему поверх
результата DK-420 (коммит `a66c05a0`): предусловие до шагов, фрагменты
`harness.local` и `settings.json` целиком, снятый прогоном вывод `--dry-run` и
пробника, команды с реальным ID. Пользователь образец подтвердил; текст
правила и проверка чужим контекстом сверяются с ним.

## DoD

В `RULES.md` есть пункт про вход для новичка, порядок README по Diataxis
и рабочие примеры команд и конфигов вместо перечня параметров, с
уточнениями п. 36 и п. 87, в `RULES.core.md` резидентное предложение про
вход при том же весе ядра, в `board-ship` и `test-standard` проверка чужим
контекстом; `devkitctl doctor` печатает находку на README утилиты, чей
первый раздел не вход, и молчит на README с входом (тесты на синтетическом
дереве, регрессионных нет, функциональность новая). Тексты правил и скиллов
проходят `proofread` и `check-symbols`. Правило про встреченную плохую доку
(правка сразу либо черновик по порогу мелочи, со ссылкой на `live-core`)
стоит в том же пункте `RULES.md`, а находки доктора по README devkit
разобраны: у каждого либо дописан вход, либо заведён черновик. Родня: DK-420
(частный случай), DK-173 (мимикрия и вычитка), DK-071 (сторож полноты),
скилл `live-core` (порог мелочи и канал правки).

## Приёмка

Вид agent. Находка доктора проверяется прогоном на синтетическом дереве с
двумя README (вход первым и устройство первым). Правило проверяется чужим
контекстом: свежий агент с новым текстом правил пишет доку на синтетическую
утилиту, а второй свежий контекст на временном `HOME` идёт по ней до
результата без подсказок; дошёл значит правило удерживает, застрял значит
место пробела названо шагом. Дока без рабочего примера хотя бы у одной
команды или конфига в этом прогоне считается провалом правила. Барьер «глаза» этим обходом закрыт.

## Ранг

`25+7+2+0+4 = 38`, P2.

- Серьёзность 25 (Major). Заметное трение: новичок по доке фичу не
  запускает, агент тратит токены на вопросы; обход дешёвый, спросить в чате
  или собрать порядок из кода, пока знающий рядом.
- Ценность 7. Пользователь назвал пробел системным и очень важным сам,
  просит правило, а не одну правку.
- Неопределённость 2. Подход выбран (Diataxis плюс порядок man, находка
  доктора, проверка чужим контекстом), открыты детали: формулировка в ядре
  при удержании веса, набор имён разделов входа.
- Поправка на баг 0. Кода со сломанным поведением нет, недостаёт правила.
- Рычаг 4. Сильно ускоряет будущую работу агента: каждая следующая дока в
  любом проекте devkit пишется со входом, вопросы в чат не уходят.
