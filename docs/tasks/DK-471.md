# DK-471: Чистый вердикт ревью записывается командой taskctl review

## Что происходит

Ревью, прошедшее без замечаний, записывать сегодня нечем: раздел «Ревью» файла
задачи заводит только `taskctl review add`, и чистый вердикт приходится
изображать замечанием с текстом «замечаний нет». Из-за этого «ревью прошло
чисто» неотличимо от «ревью не гонялось», и на этом стоит вся дыра, ради
которой заведена DK-460.

Строка первая в плане [LLD DK-460](../lld/DK-460-review-gate.md), раздел «Что
меняется в строках», пункт 1. Пункт вытащен из цели DK-183: держать его внутри
нерезанной цели XL значит ждать её цикл ради одной команды.

## Чего хотим

У ревьювера есть штатная команда записать чистый вердикт, и запись эта
машинно отличима от отсутствия ревью.

## DoD

Подкоманда вердикта в `taskctl review` с чистым исходом, её тесты, справка
команды и README `taskctl`. Перечень подкоманд в `RULES.board.md` п. 3 («Формат
держит `taskctl review` (`add`, `resolve`, `show`, `stats`)») дополнен: без
новой подкоманды он становится неполным в тот же день. Текстов процедуры строка
не трогает, это рамка нарезки цели DK-183 (вердикт отдельно от правок текстов),
процедуру правит DK-472. Форма записи совместима с критерием исхода после
DK-469.

## Ранг

`25+5+1+0+4 = 35`, P2.

- Серьёзность 25: заметное трение, обход есть и им пользуются (замечание с
  текстом «замечаний нет»).
- Ценность 5: ждут её ворота следа ревью, без записи они видят только отметку
  назначения.
- Неопределённость 1: дизайн принят LLD DK-460, осталось сделать.
- Поправка на баг 0: команды не было никогда.
- Рычаг 4: разблокирует DK-472 и DK-473, без неё ворот отказывал бы на честной
  работе.

## Ход работы

- Нарезана из LLD DK-460 после утверждения пользователем, 2026-08-22.
- Разработка: субагент opus/medium по вердикту pick (маппинг sonnet, корректор: профицит week_all, week_max; квота: week_all 93% профицит, week_max 37% профицит, снимок 16м назад), 2026-08-31 10:47-10:47.
- Подкомандой стала `review clean <ID> ["пояснение"]`. Соседи в `review`
  названы английскими словами, а форму записи («Вердикт: без замечаний.» плюс
  пояснение) диктует критерий исхода, который DK-469 привязала к голове
  элемента.
- Общий ход `add` и `clean` (файл задачи, ссылка в строке, вставка элемента в
  раздел) вынесен в `reviewItem`.
- Вердикт поверх открытого замечания отбивается. Ворот замечаний видел бы
  открытый пункт, а ворот следа ревью чистый итог. Закрытые замечания вердикту
  не мешают, это второй круг ревью. Второй вердикт подряд отбивается как дубль.
- Перечень подкоманд в скилле `board-ship` (`SKILL.md:92`) не тронут. По LLD
  DK-460 он едет строкой 2 вместе со своим разделом процедуры, то есть в
  DK-472.
- Вычитка: 3 файла, 3 правки, 0 пометок, 2026-08-31.

## Сценарий проверки

1. Тесты подкоманды:

```sh
cd tools/taskctl && GOWORK=off go test . -run TestReviewClean -count=1
```

Ожидание: `ok`, шесть тестов подкоманды проходят.

2. Весь пакет, вынос общего хода в `reviewItem` не задел `add`, `resolve`,
   `show` и `stats`:

```sh
cd tools/taskctl && GOWORK=off go test . -count=1
```

Ожидание: `ok`.

3. Запись вердикта на песочной копии доски. Шаг идёт одной строкой: обкатка
   гоняет каждую строку блока своим прогоном в свежем дереве, и переменные
   между строками не живут.

```sh
mkdir -p "$HOME/bin" && GOWORK=off go build -o "$HOME/bin/taskctl" ./tools/taskctl && S=$(mktemp -d) && mkdir -p "$S/docs/tasks" && cp docs/TASKS.md docs/TASKS-archive.md "$S/docs/" && "$HOME/bin/taskctl" -C "$S" review clean DK-471 "Дифф прочитан целиком." && "$HOME/bin/taskctl" -C "$S" review show DK-471 && grep -n "Вердикт: без замечаний" "$S/docs/tasks/DK-471.md"
```

Ожидание: в файле задачи песочницы стоит строка `- Вердикт: без замечаний. ...`,
`show` печатает её с исходом `[чисто]`, а `grep` эту строку находит.

4. Обе отбивки там же, вердикт поверх открытого замечания и дубль вердикта:

```sh
mkdir -p "$HOME/bin" && GOWORK=off go build -o "$HOME/bin/taskctl" ./tools/taskctl && S=$(mktemp -d) && mkdir -p "$S/docs/tasks" && cp docs/TASKS.md docs/TASKS-archive.md "$S/docs/" && "$HOME/bin/taskctl" -C "$S" review add DK-472 "критерий исхода не сверен" && ! "$HOME/bin/taskctl" -C "$S" review clean DK-472 && "$HOME/bin/taskctl" -C "$S" review clean DK-471 "Дифф прочитан целиком." && ! "$HOME/bin/taskctl" -C "$S" review clean DK-471 "повтор" && echo "обе отбивки отработали"
```

Ожидание: обе отбивки дают код возврата 1 (потому шаг и построен на
отрицании), первый отказ называет `review resolve`, второй говорит про уже
записанный вердикт, шаг кончается строкой «обе отбивки отработали».

5. После слияния, из основного чекаута на main: `devkitctl update`, дальше
   `taskctl help | grep "review clean"` и первый живой вердикт ревьювера
   командой вместо замечания-затычки. Ожидание: справка установленного бинаря
   знает подкоманду, вердикт ложится в файл задачи, `taskctl review stats` не
   считает эту запись замечанием, а `shipctl merge` пропускает задачу.
