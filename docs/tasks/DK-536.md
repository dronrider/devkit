# DK-536: review add из чужого дерева молча пишет замечание в свой чекаут

## Что происходит

Ревьювер DK-533 позвал review add из основного чекаута, а не из дерева задачи. Команда нашла файл задачи по своему пути, дописала замечание в копию из старого коммита main и вышла без единого слова. Заметил ревьювер только по git status в обоих деревьях, а замечание в дереве задачи так и не появилось бы.

Изменяющие доску команды taskctl из линкованного worktree отказывают сами, тут же вышло наоборот: команда, чьё место в дереве задачи, отработала в основном чекауте. Похоже, review add стоит сверять текущее дерево с веткой задачи и отказывать при расхождении так же, как отказывают команды доски.

Замечание уходит в копию файла и не доезжает до исполнителя, а команда об этом
молчит. Ревьювер узнаёт о промахе только чужим ходом, через `git status` в
обоих деревьях. Молчание тут дороже отказа: ревью считается записанным, дальше
по нему идёт слияние.

## Чего хотим

`review add` и `review resolve` сверяют текущую ветку с веткой задачи и при
расхождении отказывают, называя, где лежит нужное дерево. У задачи без своей
ветки поведение остаётся прежним.

## Развилки

Чем считать законное дерево, когда у задачи ветки нет вовсе либо она уже слита.

Решение. Отказ ловит только задача с живой веткой, у которой есть коммиты, не
доехавшие до main (та же проверка, что у ворот перевода в Check). Тогда законное
дерево то, где стоит ветка задачи, и отказ называет его путь из списка
`git worktree`. У задачи без ветки и у слитой законное дерево то, где стоит
вызов. Вне git и в корп-контуре, где доска отдельно от кода, ветки не найдётся
и рубеж молчит.

## DoD

- `review add` и `review resolve` из чужого дерева отказывают и называют дерево
  задачи. Молчаливой записи мимо ветки нет.
- Задача без своей ветки и задача, слитая в main, отказа не ловят.
- Тесты на временном репозитории: запись из дерева задачи, запись из основного
  чекаута при живой ветке, запись у задачи без ветки.

## Ранг

`50+6+2+5+2 = 65`, P1.

- Серьёзность 50: конвейер ведёт не туда, замечание ревью теряется молча.
  Обход есть, но держится на внимательности ревьювера.
- Ценность 6: ревью идёт у каждой задачи с веткой.
- Неопределённость 2: подход назван, открыто поведение у задачи без ветки и у
  слитой.
- Баг 5: команда пишет мимо адресата, это дефект.
- Рычаг 2: чинит свой поток ревью.

## Сценарий проверки

Агентский. Весь ход идёт на временном репозитории под подставным `HOME`, живые
доски машины не трогаются. Задача XR-001 заводится в основном чекауте, её ветка
`xr-001-fix` с одним коммитом впереди main стоит в соседнем дереве.

```bash
box=$(mktemp -d); trap 'rm -rf "$box"' EXIT; export HOME="$box/home"; mkdir -p "$HOME" "$box/proj" && git -C "$box/proj" init -q -b main && git -C "$box/proj" config user.email t@t && git -C "$box/proj" config user.name t && taskctl -C "$box/proj" init --prefix XR >/dev/null && taskctl -C "$box/proj" add --title "Задача" --type task --rank 0+1+1+0+1 --accept agent >/dev/null && git -C "$box/proj" add -A && git -C "$box/proj" commit -qm init && git -C "$box/proj" worktree add -q -b xr-001-fix "$box/wt" && echo x > "$box/wt/code.txt" && git -C "$box/wt" add code.txt && git -C "$box/wt" commit -qm "XR-001: код" && { taskctl -C "$box/proj" review add XR-001 "замечание из основного чекаута" 2>&1 | sed "s#$box#BOX#g; s#/private##g"; echo "основной чекаут, строк замечаний: $(grep -c '^- замечание' "$box/proj/docs/tasks/XR-001.md")"; taskctl -C "$box/wt" review add XR-001 "замечание из дерева задачи" 2>&1; taskctl -C "$box/proj" review resolve XR-001 1 fixed 2>&1 | sed "s#$box#BOX#g; s#/private##g"; taskctl -C "$box/wt" review resolve XR-001 1 fixed 2>&1; grep '^- замечание' "$box/wt/docs/tasks/XR-001.md"; }
```

Ожидание по строкам вывода. Первый `review add` из основного чекаута падает с
отказом «ветка xr-001-fix не слита» и называет дерево `BOX/wt`, строк замечаний
в основном чекауте после него 0. `review add` из `BOX/wt` печатает «замечание 1
записано». `review resolve` из основного чекаута падает с тем же отказом.
`review resolve` из `BOX/wt` печатает «замечание 1 исправлено», и в файле задачи
дерева остаётся строка про замечание из дерева задачи с исходом «исправлено».
