# DK-587: devkitctl из PATH в дереве ветки молча исполняет код main

## Что происходит

Ревью DK-583, 2026-08-29. Обёртка `~/go/bin/devkitctl` это шелл-скрипт с
зашитым абсолютным путём на `~/projects/devkit/tools/devkitctl/devkitctl.py`.
`devkitctl build`, запущенный из дерева ветки `devkit-dk-583`, пересобирает
только go-бинари, обёртку не переписывает.

`devkitctl corp ...` из PATH в дереве задачи исполняет код main вместо кода
ветки.
Ревьювер поймал это только по расхождению поведения с DoD и обошёл прямым
`python3 <ветка>/tools/devkitctl/devkitctl.py`. Любое ревью или сценарий
проверки, что зовёт `devkitctl` из PATH, проверяет не тот код и молчит об этом.

## Чего хотим

Вызов `devkitctl` из дерева ветки devkit исполняет код этого дерева вместо
main, либо громко говорит, что исполняет чужой.

## Развилки

Обёртке идти по `git rev-parse` от cwd (в дереве devkit брать devkitctl.py
дерева), или `build` в дереве ветки должен печатать предупреждение и путь
прямого вызова?

## DoD

Вызов `devkitctl` из дерева devkit исполняет код этого дерева. Где так не
выходит, команда называет чекаут, чей код она исполняет, и путь прямого
вызова. Регрессионный тест краснеет на старом коде, краснота сверена прогоном
regcheck. Снаружи это видно из дерева ветки. Подкоманда, поведение которой в
ветке изменено, отзывается по-новому либо печатает, что взяла код main.

## Ранг

`25+5+2+5+3 = 40`, P2.

- Серьёзность 25: ревью и сценарии проверяют не тот код и молчат об этом, обход
  дешёвый и очевидный, прямой вызов файла из дерева.
- Ценность 5: ревью ветки перестаёт врать, а сценарии проверки в дереве задачи
  начинают проверять то, что написано.
- Неопределённость 2: подход понятен, развилка в том, идти ли обёртке по
  `git rev-parse` от каталога вызова или ограничиться громкой строкой от
  `build`.
- Поправка на баг +5: обёртка обещает утилиту в PATH, а даёт чужой чекаут.
- Рычаг 3: ревью и обкатка в дереве ветки перестают требовать оговорок.

Цена S, генератор обёртки и тест рядом. Вид приёмки агентский. Дерево ветки с
изменённой подкомандой заводится на временном репозитории, ни один из шести
барьеров не назван.
