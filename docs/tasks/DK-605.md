# DK-605: Снимок квоты читает кеш клиента, а не разбирает панель

Цель: [tasks/DK-605.md](tasks/DK-605.md)

## Что происходит

Снимок расхода снимается разбором панели `/usage` в одноразовой tmux-сессии.
Разметку панели правят в клиенте без предупреждения, и каждый такой сдвиг
ломает снимок. За последние сутки это чинилось дважды (DK-574, DK-584), и оба
раза починка была подгонкой под нынешний вид.

Разбор DK-584 нашёл, откуда панель берёт цифры. Клиент кладёт ответ в
`~/.claude.json`, ключ `cachedUsageUtilization`. Там проценты по общему бакету
и по моделям, даты сброса и момент удачного запроса. Долгоживущая панель
рисует этот кеш, а свежий клиент съёмщика его не наследует: общий бакет он
берёт из заголовков своих ответов, а разбивку теряет.

Отсюда расхождение, которое пользователь видел 2026-08-29. На экране
`Fable 10%`, в снимке той же минуты разбивки нет.

## Чего хотим

Цифры расхода берутся из того же источника, что рисует экран клиента. Разбор
нарисованного текста остаётся запасной дорогой.

## Развилки

Возраст. У кеша свой момент снятия, и метка времени снимка обязана идти от
него. Свежая метка над старыми цифрами это та же молчащая ложь, от которой
уходила DK-584.

Запасная дорога. Панель остаётся для харнесов, у которых такого кеша нет. Надо
решить, кто выбирает дорогу и что писать в снимок, когда кеш есть, но старый.

Чужой формат. Файл принадлежит клиенту, его ключи могут смениться. Разбор
обязан говорить об этом словами, а не молчать, и тут есть готовый образец из
DK-584.

Решение по возрасту. Момент снятия идёт из `fetchedAtMs`, кеш без этого поля
съёмщик не берёт вовсе. Старый кеш пишется как есть, со своим моментом:
протухание в снимке уже работает, вверх корректор по нему не двинет, а вниз
двинет, и это честнее, чем свежая метка над старыми цифрами. Цена решения
видна сразу: на живой машине панель успевала отдавать общий бакет из
заголовков своих ответов свежее, чем клиент обновлял кеш, и снимок после
правки помолодеть не может. Зато он больше не смешивает два возраста в одной
метке и несёт разбивку по моделям, которой у панели не было.

Решение по дороге. Выбирает не профиль, а сам съёмщик: `snap = "usage-pane"`
теперь значит «спросить клиента Claude Code», кеш это первая дорога, панель
вторая. Ключа в профиль не добавлено сознательно, иначе каждая машина без кеша
чинилась бы правкой файла, а машина с кешем получала бы разбивку только после
такой правки. Смену дороги `refresh` печатает строкой перед снимком.

Решение по чужому формату. Разбираются только нужные поля, лишнее json
пропускает сам. Незнакомый вид лимита и модель без бакета уходят строкой в
вывод, а пропажа обязательного бакета, ключа кеша или момента запроса это
отказ с путём файла в тексте, после которого пробуется панель.

## DoD

- Снимок несёт разбивку по моделям, когда клиент её знает, без поднятия
  клиента в терминале.
- Момент снятия идёт от момента удачного запроса клиента. Время записи файла
  тут ни при чём.
- Незнакомый формат кеша называется словами, снимок при этом не врёт.
- Стенд на кеше с известными полями падает на прежнем коде.

## Ранг

`25+8+2+0+4 = 39`, P2.

- Серьёзность 25: цифры устаревают молча, обход есть, снимок пишется руками.
- Ценность 8: снимает целый разряд поломок наперёд, дважды чинили за сутки.
- Неопределённость 2: источник найден и разобран, открыты развилки выше.
- Поправка на баг 0: новое поведение.
- Рычаг 4: снимок кормит выбор исполнителя и корректор ставки.

## Ход работы

- regcheck: `regcheck -C tools/agentctl --base main --tests tools/agentctl/usagecache_test.go,tools/agentctl/testdata/usage-cache.json -- env GOWORK=off go test -run 'TestSnapUsageCache|TestSnapClaudeUsage' .` краснеет на main, проходит на ветке.

## Ревью

- TestCmdQuotaRefreshIfStale (usage_test.go) собирает q через specAt без q.Home, и теперь snapClaudeUsage -> snapUsageCache при пустом Home читает os.UserHomeDir(): тест читает настоящий ~/.claude.json машины, где гоняется go test. Проверено вживую: на этой машине лежит валидный cachedUsageUtilization, tmux и claude есть в PATH, и тест проходит за 0.5с без единого обращения к панели (запасная дорога заняла бы минимум usageReadyTimeout 20с) - значит читался реальный кеш разработчика. На машине без такого кеша тест уйдёт на настоящую tmux-сессию с настоящим claude вместо детерминированного стенда. usagecache_test.go верно ставит q.Home = t.TempDir() через cacheSpec, а старый тест панели этой защиты не получил.
- snapUsageCache помечает partial (markPartial(q, "кеш клиента этой модели не знает")) любой сконфигурированный бакет яруса, которого нет в utilization.limits, безусловно - в отличие от панели, где markPartial получает пустую причину (партиал не ставится), когда панель дочитала кадр, а бакета у подписки просто нет (usage.go, комментарий у panelNoBreakdown и README строка 266: 'Пометки нет, значит панель досчитала и бакета у подписки правда не оказалось'). README при этом заявляет, что кеш 'значит то же самое' (строки 268-269), но код не различает 'клиент реально не знает модель' от 'на этой неделе трат по Fable ещё не было' - week_max уйдёт в partial даже на здоровом кеше без формата-поломки, хотя аккаунт им пользуется штатно.
- cacheBucketName для kind=weekly_scoped сворачивает три независимые проверки (l.Scope == nil, l.Scope.Model == nil, l.Scope.Model.DisplayName == "") в одно условие, но тестами покрыт только случай с непустым scope.model и незнакомым именем (Chartreuse, usagecache_test.go). Ветку со scope: null или scope.model: null никакой стенд не гоняет, мутация первых двух проверок пройдёт незамеченной.

## Сценарий проверки

1. `agentctl quota refresh` на машине с живым клиентом: снимок встаёт с
   разбивкой по моделям (`week_max`), tmux при этом не поднимается, а момент
   снятия совпадает с `fetchedAtMs` из `~/.claude.json`.
2. `python3 -c "import json;print(json.load(open('/Users/me/.claude.json'))['cachedUsageUtilization']['fetchedAtMs'])"`
   рядом с выводом `agentctl quota`: возраст снимка считается от этого числа, а
   не от времени правки файла.
3. `go test ./tools/agentctl/` в дереве задачи: стенды кеша зелёные, стенды
   разбора панели тоже.
