# DK-606: LLD: приёмы прозы по типу страницы, разметка и счёт переживают правку скиллом prose

## Что происходит

29 августа пользователь показал снимок раздела README до и после правки
скиллом prose. Три буллета с жирными лид-инами стали сплошными абзацами. Счёт
в прозе сбит, стоит «вторая беда», следом «третья», а первая нигде не названа.
Времена смешаны. Абзац открывается словом «раньше», глаголы стоят в настоящем,
хвост абзаца снова в прошедшем. Второй случай пришёл от коллеги, там правка
срезала таблицы. Замер корпуса эталонов объясняет оба. В kit/skills/prose/corpus
жанр readme это 15 фрагментов и 3 строки перечисления на 204 строки. Таблиц и
подзаголовков нет ни в одном из четырёх жанров, 0 на 1024 строки.

Скилл сам говорит, что примеры держат форму сильнее запретов. В эталонах одна
сплошная проза, и агент приводит к ней чужой текст. Сносится при этом
навигация. README и справочник читают по диагонали, таблицу читают по столбцу,
а после правки читателю приходится читать абзац целиком. Заодно правка рвёт
связность, счёт перечисления и время глаголов. Сторож hooks/check-prose.py и
тринадцать пунктов вычитки этого не видят. Они меряют частоты внутри фразы, а
сломана страница. Оба случая нашёл человек глазами, и другого способа найти
такое сейчас нет.

### Что нашёл грумминг

Замер корпуса подтверждён: таблиц и подзаголовков 0 на 1024 строки, в жанре
readme три строки нумерованного перечисления. Разбор скилла дал шесть находок.

1. Единица стиля в скилле это фраза. Пять примет горячего списка и двенадцать
   пунктов вычитки говорят про предложение и абзац, про страницу ни одного.
2. Формат корпуса исключает структуру сам: «тело фрагмента, один или два
   абзаца», источники это реплики чата и issue трекеров. Расширение корпуса
   без правки формата даст те же абзацы.
3. Жанр выбирается точкой вызова, а не текстом. Под `readme` попадают входная
   страница, справочник флагов и таблица команд, набор закрыт четырьмя
   файлами, а полный перечень типов документов заранее не известен.
4. Режима правки готового текста нет: выборка берётся до первой фразы. У
   proofread раздел «Что не трогает» разметку и структуру не называет.
5. `hooks/check-prose.py` выкидывает таблицы и заголовки до счёта (строки 49 и
   83), сбитый счёт и спор времён он не увидит.
6. Раз вся выборка это сплошная проза, а примеры держат форму сильнее
   запретов, оговорка словами проигрывает примерам.

Пользователь на грумминге: типы текстов разные, весь их набор неизвестен,
элементы стиля надо скорректировать на каждый тип; корпус расширять добычей
из интернета с выбором по типу документа. Решено вести дизайном.

### Свежие правки скиллом с 27 августа

Разобраны коммиты devkit с 2026-08-27 по 2026-08-30, где звались prose или
proofread либо правилась проза: README утилит, RULES, скиллы, LLD, файлы
задач (DK-525, DK-522, DK-523, DK-524, DK-548, DK-530, DK-366, DK-583,
DK-584, DK-605, DK-581, DK-585, DK-577, DK-428), больше тридцати коммитов.

- Ни в одном коммите строки списков, таблиц и заголовков в минусе не
  превышают плюса, лид-ины `- **` не снимались нигде. Правки шли внутри
  абзацев, структура прибавлялась (agentctl/README.md, proofread/SKILL.md).
- Оба случая потери структуры лежат вне гита devkit. Снимок 29 августа это
  README чужого проекта автотестов (раздел «Проблема, которую это решает»,
  сессия 2cc76dac, скриншот в загрузках дашборда): три буллета с лид-инами
  стали двумя абзацами, счёт «вторая беда, третья» без первой, «это» трижды в
  соседних фразах, «раньше» при глаголах в настоящем. Тире сняты правильно,
  перестройкой. Срезанные таблицы у коллеги известны со слов, диффа нет.
- Один дефект по существу внутри devkit: `8421ff09` (DK-428), правка двух
  строк ради порога сторожа «а не». «Парсер читает грамматику, а не имена»
  стало «Парсер знает грамматику, список имён живёт в таблице» (одушевление
  вопреки ядру), «конечный источник максимума, а не ближайший сосед» стало
  «задача, чей ранг стал максимумом, даже если она держится через цепочку».
  Утверждение переписано ради метрики, а не ради читателя.

Следствие для дизайна. Тексты devkit, куда скилл заходил, почти сплошь
абзацные, и там ему нечего сносить; ломается чужой текст с живой структурой,
то есть ровно тот случай, под который корпус эталонов не собран. Второй класс
дефекта, подгонка смысла под порог сторожа, к структуре не относится, но
показывает тот же механизм: правило фразы исполняется в ущерб странице. Обе
находки идут в развилку про инвариант правки готового текста.

## Чего хотим

После правки скиллом prose разметка исходного текста остаётся на месте,
меняются формулировки внутри пунктов. Сбитый счёт и спор времён ловит сквозная
проверка после переписывания, и находка приходит в тот же заход.

## Развилки

Правится корпусом (фрагменты readme с живым перечислением и таблицей) или
оговоркой в SKILL.md о том, что разметка не предмет мимикрии? Второй вопрос про
режим захода. Скилл написан под письмо с нуля, выборка берётся до первой фразы,
а оба случая это переписывание готового текста со своей неприкосновенной
структурой. Нужен ли этому режиму свой раздел. Третий вопрос про раскладку
приёмов по типу документа. Хватает ли одного слоя про страницу поверх общего
слоя про фразу или приёмы делятся по жанрам.

- Ключ раскладки приёмов: имя типа документа или режим чтения (по диагонали,
  по столбцу, подряд, по шагам), в который новый тип попадает без правки
  скилла.
- Где живёт инвариант правки готового текста «структура исходника это данные,
  а не стиль»: в prose, в proofread или общим правилом.
- Как корпус везёт список и таблицу: поле формы у фрагмента, отдельный жанр
  или правка формата, и как отбирается добыча из интернета под тип.

## Ранг

`25+6+3+0+4 = 38`, P2.

- Серьёзность 25: снесённую структуру ловит человек глазами, обход дешёвый
  (откатить правку).
- Ценность 6: правка долгоживущего текста идёт каждый день, страдает
  навигация README и справочников.
- Неопределённость 3: подход понятен, три развилки открыты, потому LLD.
- Поправка на баг 0.
- Рычаг 4: снимает просмотр глазами с каждой правки текста агентом.
