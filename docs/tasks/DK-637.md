# DK-637: shipctl: ветка, вобравшая main слиянием, сливается без ребейза

## Что происходит

Как воспроизвести. Завести длинную ветку, дать main уйти вперёд по тем же
файлам, догнать ветку не ребейзом, а `git merge main`, развести конфликты один
раз и позвать `shipctl merge <ID>`.

Что ожидалось. Ветка уже потомок main, fast-forward у неё есть, слияние идёт
дальше к тестам и выкату.

Что вышло. `shipctl merge` зовёт `git rebase main` безусловно. На ветке, где
main уже предок, ребейз не бездействует: он проигрывает коммиты ветки заново
поверх main, выбрасывая merge-коммиты вместе с разведёнными в них конфликтами.
Конфликты возвращаются по одному на коммит, ребейз падает, `shipctl` его
абортит и отказывает.

Нашлось 2026-08-30 на ветке цели DK-397: 346 коммитов, сшивка с main сделана
слиянием, ребейз в клоне-песочнице падает на пятом коммите из 346 конфликтом в
`.gitignore`. Развести те же конфликты 346 раз нечем, то есть слияние такой
ветки упирается намертво, и единственный обход это сплющить историю недели
работы в один коммит.

## Чего хотим

`shipctl merge` спрашивает `git merge-base --is-ancestor main HEAD` и зовёт
ребейз только тогда, когда main ветке не предок. Ветка, догнанная слиянием,
сливается штатно и приезжает в main со своей историей.

## DoD

Сверх общего: ветка цели DK-397 проходит `shipctl merge` без сплющивания.

## Ранг

`50+2+0+5+4 = 61`, P1.

- Серьёзность 50: длинная ветка не сливается вовсе, обход есть, но платит

- Ценность 2: починка ради статус-кво, нового пользователь не увидит.
- Неопределённость 0: причина найдена прогоном, место в коде названо.
- Поправка на баг 5.
- Рычаг 4: сшивка слиянием становится законной дорогой, и следующая длинная
  ветка проходит слияние сама.
