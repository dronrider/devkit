# DK-664: Сторожок цели идёт с голым PATH launchd, и разлив очереди падает

## Что происходит

~/.devkit/goal-watch.log на 2026-08-31 циклически пишет «taskctl не найден в
PATH» по трём корням: devkit, it-road-course, xr-proxy.

Надзор крутится вхолостую: парковки и переходы цели никто не будит, и цель
стоит, пока в лог не заглянут руками. Молчание не отличить от штатной работы.

## Чего хотим

Сторож находит taskctl из любого окружения запуска, а падение такого рода
видно снаружи, не только в логе.

## Развилки

Откуда сторожу брать PATH: зашить каталог бинарей при установке или тянуть
профиль пользователя при запуске.

Решение: зашить. `doctor --fix` считает PATH агента по машине (наличием
каталогов) тем же сборщиком, что у дашборда, `dashboard.agent_path`, и кладёт
готовую строку в `EnvironmentVariables` plist. Профиль пользователя (`.zshrc`
и подобные) launchd не читает вовсе, у него своя, отдельная от логина среда
запуска: тянуть его смысла нет. Зашитый срез вместо живого PATH сессии не
плывёт от прогона к прогону, и `doctor --fix` не переписывает агента заново
на каждом вызове (тот же довод уже стоит в docstring `dashboard.agent_path`
про дашборд).

## DoD

Launchd-агент сторожка получает PATH тем же сборщиком, что агент дашборда, и
разлив очереди из-под него доходит до конца. Доктор считает агента без PATH
находкой и переписывает plist по `--fix`, как переписывает показывающего не
туда. Тест держит каталог бинарей в PATH агента, краснота сверена прогоном
regcheck. Снаружи это видно журналом сторожка. Строки про ненайденный taskctl
уходят, на их месте печатается отчёт разлива.

## Ранг

`50+8+1+5+4 = 68`, P1.

- Серьёзность 50: надзор цели крутится вхолостую, парковки и переходы никто не
  будит, а очередь слияния стоит часами; обход есть, но ручной, звать разлив и
  читать журнал глазами.
- Ценность 8: на этом сторожке держатся автономный цикл цели и разлив очереди,
  и сейчас он молчит про собственную бесполезность.
- Неопределённость 1: подход взят у соседнего агента, осталось позвать тот же
  сборщик PATH.
- Поправка на баг +5: сторожок работал, пока его дети не пошли за утилитами.
- Рычаг 4: чинится носитель автономного цикла, от него дешевеет каждая
  следующая цель и каждая пачка.

Цена S, это раздел в plist, вызов готового сборщика и тест рядом. Вид приёмки
агентский. Агент подделывает дом, зовёт проверку носителя и читает plist, ни
один из шести барьеров не назван.

- Из черновика DK-664 «надзор цели падает на «taskctl не найден в PATH» по всем корням»: записан 2026-08-31, оформлен 2026-09-01.
- Разработка: субагент sonnet/high по вердикту pick (квота: week_all 0% профицит, снимок 3ч 48м назад, протух, сдвига нет), 2026-09-03 04:55-04:56.
- 2026-09-03: `plist_text` в tools/devkitctl/watch.py несёт раздел
  `EnvironmentVariables`/`PATH`. Собран он тем же сборщиком, что у
  launchd-агента дашборда, `dashboard.agent_path`, по бинарю dashboard из
  PATH. `check()` получил ключ `which` (по умолчанию `shutil.which`) и новую
  находку. Бинаря devkit нет в PATH, значит собирать PATH агента неоткуда.
  Класть plist `--fix` тогда не берётся. Старый plist без такого PATH это
  находка тем же путём, каким находкой считается plist, показывающий на
  чужой чекаут: обе сверяются по тексту целиком. `--fix` переписывает его
  тем же правилом. В tools/devkitctl/devkitctl.py `watch.check` сдвинут
  после `check_binaries`, тем же порядком, что уже стоит у `dashboard.check`.
  На прогоне с `--fix` бинарь dashboard успевает встать в PATH до подъёма
  агента сторожка.
- 2026-09-03: первый выбор якоря был taskctl, а не dashboard, и полный прогон
  юнитов (720 тестов) нашёл по нему красноту в `board_test.DoctorDepsTest` и
  `corp_test.CorpTest`. Причина: эти тесты кладут в PATH проекта свой
  подставной taskctl (`board_taskctl`) поверх обычного стенда, и фикстура
  `Sandbox.watch_agent` (пишется один раз при заводе стенда, по обычному
  taskctl) разъезжалась с `watch.check()` (считает PATH заново на каждом
  вызове доктора, находит уже подставной taskctl). У бинаря dashboard такого
  дублёра ни один тест не заводит, якорь на нём общий с дашбордом и с этим
  классом тестов не расходится. Якорь и фикстура переведены на dashboard
  всюду; полный прогон юнитов после правки зелёный целиком.
- Фикстура `Sandbox.watch_agent` в testenv.py и тесты watch_test.py
  (`test_missing_binary_is_a_finding`, `test_old_agent_without_path_is_rewritten`,
  PATH-проверка в `test_fix_installs_and_loads`) держат каталог бинарей в PATH
  агента по образцу dashboard_test.py. Дока: tools/devkitctl/README.md,
  находка про сторожка в перечне доктора и раздел «Сторожок цикла цели»
  дополнены разбором PATH.

## Сценарий проверки

Агентский. `taskctl rehearse` режет заход на шаги построчно. Каждая строка
блока идёт своим прогоном со своим временным HOME. Между строками не
переживает ничего, это проверено самой обкаткой (см. «Ход работы»). Поэтому
шаг тут это одна строка целиком. Окружение собирает не сама строка, а стенд
`AgentTest` в watch_test.py. `Stand.setUp` кладёт временный каталог,
`AgentTest.setUp` подставной бинарь `dashboard`. `check` зовёт
`watch.check()` с `home`, `which`, `call` из стенда, живой PATH и живой
launchd мимо. Настоящего launchd-агента поднимать в сценарии незачем. Он
делит имя `ru.devkit.goal-watch` с агентом живой машины, и трогать его
опасно.

```sh
cd tools/devkitctl && python3 -m unittest watch_test.AgentTest.test_missing_binary_is_a_finding watch_test.AgentTest.test_old_agent_without_path_is_rewritten -v
```

Ожидание: обе строки `... ok`, исходный баг DK-664. Первый тест: без бинаря
dashboard в PATH класть PATH агента неоткуда, доктор отвечает находкой
`devkitctl update`. Второй тест: старый plist, положенный до
EnvironmentVariables (таким был агент до этой правки), доктор считает
находкой `doctor --fix`.

```sh
cd tools/devkitctl && python3 -m unittest watch_test.AgentTest.test_fix_installs_and_loads watch_test.AgentTest.test_agent_path_makes_children_findable -v
```

Ожидание: обе строки `... ok`. Первый тест: после `--fix` plist несёт
`EnvironmentVariables`/`PATH`, первым элементом идёт каталог подставного
бинаря dashboard. Второй тест: тем PATH, что plist кладёт агенту launchd,
ребёнок тика `devkit_bin("shipctl")` находит соседний бинарь. Разбора
«shipctl не найден в PATH», которым падал разлив очереди, нет (DK-664).
