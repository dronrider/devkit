# DK-677: Тесты notify в hooks падают в чистом окружении прогона merge

Цель: [tasks/DK-161.md](tasks/DK-161.md)

## Что происходит

После DK-641 прогон тестов слияния идёт в свежем дереве с временным HOME и
урезанным PATH. Первый же merge (DK-643) упал компонентом hooks. Три теста
notify_test.TestArgumentMode получают пустой sent(), уведомление до
подставного бэкенда не доходит. В прогретом окружении те же тесты зелёные
(hooks 586 ok в прогонах исполнителей). Тесты полагаются на живое окружение
сессии, ровно класс 98b43e7, который должен ловить прогон в чистом дереве.
Пока компонент красный, слияние отбивает любую ветку.

### Причина

Метод `HookCase.cli()` в `hooks/notify_test.py` не задавал подпроцессу свой
`cwd`. Подпроцесс наследовал рабочую директорию самого раннера тестов.

Аргументный режим `notify.py` сам зовёт `sandbox_reason(os.getcwd())`. Он
читает корень под TMPDIR песочницей, вроде синтетической доски из обкатки
сценария (DK-069). Баннер из такого корня ложный, и `deliver()` тогда не
зовётся.

В прогретом чекауте раннер стоит в обычном дереве. Песочница не срабатывает.
В свежем дереве прогона merge (`freshTestTree`, DK-641/643) весь чекаут лежит
под TMPDIR. Унаследованный `os.getcwd()` подпроцесса тоже оказывается под
TMPDIR. `sandbox_reason` читает это песочницей, `deliver()` не вызывается, `sent()`
у теста пустеет.

Так падают ровно три теста `TestArgumentMode`, что проверяют `sent()` без
явного `cwd`. Тесты с явным `cwd` (`self.tree(...)`, `self.tmp`) не задеты.
Не задеты и тесты, что проверяют только журнал. Пропуск в него пишется
строкой, и поля там остаются точными. Пропуск не теряется. Он виден и на
выходе, и в `~/.devkit/notify.log`. Это штатное поведение DK-069,
продукционный код тут без дефекта.

Правка живёт в `hooks/notify_test.py`. `HookCase.cli()` теперь задаёт
подпроцессу собственный `cwd`: `CLI_CWD`, каталог интерпретатора `python3`,
заведомо вне `TMP_ROOTS`. Раннер больше не отдаёт подпроцессу свою рабочую
директорию. Регрессионный тест
`test_reaches_the_backend_even_when_the_suite_itself_runs_from_tmp` явно
переходит в `self.tmp` перед вызовом `cli()`. Так он воспроизводит случай,
когда сам раннер стоит под TMPDIR. Тест отмечен маркерами
`regcheck:test-begin/end`. Правка и тест живут в одном файле.

Прогон `regcheck -C hooks --inline hooks/notify_test.py -- python3 -m
unittest
notify_test.TestArgumentMode.test_reaches_the_backend_even_when_the_suite_itself_runs_from_tmp`
подтверждает разбор. Тест краснеет на HEAD без правки и проходит на текущем
коде.

### Второй компонент: watch_test.QuotaTick (DK-633)

Тот же класс дефекта нашёлся в `tools/devkitctl` следующим чистым прогоном.
`watch.run()` внутри тика зовёт `quota_snap(call)` без параметра `agentctl`.
`quota_snap` резолвит бинарь сама. Она ищет его живым PATH и каталогами
релиза (`devkit_bin`). Тесты `QuotaTick` подставляли только `call` (`Fake`).
Бинарь `agentctl` они брали из живого PATH сессии, обычно `~/go/bin`.

В окружении прогона merge каталоги под домом из PATH срезаны. `devkit_bin`
ничего не находит. `quota_snap` сразу возвращает строку «бинаря agentctl
нет...», `Fake` не зовётся. Красных тестов пять. Четыре из них ждут строки
вида «снято 1», «кодом 1», «оставлено 1».
`test_fresh_snapshots_stay_out_of_the_journal` падает наоборот, он находит в
журнале лишнюю строку про отсутствие бинаря.

Правка меняет `watch.run()`. Функция принимает параметр `agentctl` и
пробрасывает его в `quota_snap()`, приёмом, каким уже пробрасываются
`taskctl` и `shipctl`. Тесты подставляют фейковый путь `AGENTCTL =
"/bin/подставной-agentctl"`. `Fake` его не исполняет, только записывает
`argv`, реальный бинарь по этому пути не нужен.

Добавлен тест `test_missing_agentctl_reaches_the_journal_through_the_tick`.
Это штатный случай отсутствия бинаря через тик целиком. `call` не зовётся,
причина доезжает и до отчёта, и до журнала. Прогон `regcheck -C
tools/devkitctl --base main -- python3 -m unittest watch_test.QuotaTick`
подтверждает разбор. Тест краснеет на main и проходит на текущем коде.

## Чего хотим

Тесты hooks строят своё окружение сами и зелёные в чистом прогоне merge.
Причина молчания sent() названа в файле задачи и закрыта правкой тестов или
notify.py (если тот молча глотает отсутствие бэкенда там, где должен звать
подставной). Краснота регрессии подтверждена прогоном regcheck.

Той же веткой дорезан второй случай того же класса. Пять тестов
`watch_test.QuotaTick` в `tools/devkitctl` полагались на живой `agentctl` из
PATH сессии. Они падали в том же чистом прогоне (раздел «Второй компонент»
выше).

## DoD

1. Компонент hooks зелёный в окружении прогона merge (временный HOME,
   урезанный PATH), три прогона подряд.
2. Причина записана в файле задачи, у фикса регрессионный тест, краснота
   подтверждена regcheck.
3. shipctl merge очередной ветки не отбивается компонентом hooks.
4. Компонент tools/devkitctl (в частности `watch_test.QuotaTick`) зелёный в
   том же окружении, у фикса регрессионный тест, краснота подтверждена
   regcheck.

## Сценарий проверки

Агентский. У `parallel.py` нет флага `--only`, компонент hooks гоняется
напрямую его же командой из `components()`.

```sh
cd hooks && python3 -m unittest discover -p '*_test.py'
cd tools/devkitctl && python3 suite.py
```

Ожидание: оба компонента зелёные. Дальше слияние очередной ветки проходит их
без отбоя, диспетчер закрывает это фактом merge DK-643.
