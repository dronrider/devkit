# DK-697: git push доски виснет на osxkeychain, коммиты копятся локально

## Что происходит

29.08 около 18:28 в main лежали восемь неотправленных коммитов доски, сессия 8257b5e0. Пуш из неинтерактивной сессии повисает намертво на credential helper osxkeychain, ловушка уже знакома по памяти сессий, но записана только там.

Доска это общий источник правды, и отставший remote оборачивается конфликтами у соседних сессий. Правило немедленного пуша доски при этом молча не исполняется, а shipctl merge при повисшем пуше звать нельзя, конвейер встаёт.

## Чего хотим

Пуш доски из любой сессии либо проходит, либо отказывает за секунды с причиной. Молчаливого зависания нет.

## Развилки

Чинить доставку токена в неинтерактивную сессию или ставить пушу таймаут со внятным отказом?

Решение: предел времени. Доставка токена лечит только связку ключей macOS.
Упереться в вопрос без человека пуш может ещё десятком способов, от пароля ssh
до чужого хоста с непринятым ключом. Предел закрывает весь класс, и внятный
отказ у него получается один на все поводы.

Закрытие запроса переменными нужно, но само по себе не спасает.
`GIT_TERMINAL_PROMPT=0` глушит только собственный вопрос git. Помощник учётки
запускается всё равно, и диалог связки ключей поднимает уже он. Предел времени
обязателен, а переменные идут к нему добавкой.

Предел живёт одним пакетом `internal/gitrun`, общим для всех утилит доски.
Список переменных у копий разошёлся бы на первой же правке. Это уже случалось с
каркасом перед DK-237. В пакете лежит и разрешение `DEVKIT_PUSH_OK=1`, которое
до этого было отдельной функцией в обеих утилитах.

Величина предела тридцать секунд. Пуш доски укладывается в пару секунд, слияние
с тегом ненамного дольше. Запас есть даже на медленном канале, а сессия за
полминуты встать не успевает. Долгому каналу предел поднимают переменной
`DEVKIT_GIT_TIMEOUT`, и кривое её значение это громкая ошибка. Опечатка вернула
бы то самое зависание.

Предел ставится только сетевым командам (`push`, `fetch`, `pull`, `clone`,
`ls-remote`). Локальный коммит в большом дереве бывает долгим сам по себе, и
обрывать его не за что.

## DoD

- `git push` внутри `taskctl` и `shipctl` идёт с закрытым интерактивным
  запросом и с пределом времени.
- Упёршийся в учётку пуш кончается отказом за секунды, и отказ называет
  причину и ход руками.
- Тест на временном репозитории. Подменённый credential helper, который спит,
  доводит команду до отказа по пределу времени.

## Ревью

- флаки: internal/gitrun/gitrun_test.go TestPushHangingCredentialHelper падает "помощник учётки не был позван" примерно в 1 из 5-6 прогонов на незагруженной машине (воспроизведено GOWORK=off go test ./gitrun/ -run TestPushHangingCredentialHelper -count=1, серии по 10 и 6 прогонов). За 2s (тестовый DEVKIT_GIT_TIMEOUT) не всегда успевает провернуться связка git -> запрос учётки -> exec спящего помощника -> запись pid-файла, и SIGKILL группы иногда бьёт раньше, чем помощник вообще стартовал. Тест сам себе противоречит с требованием детерминизма из ACCEPTANCE и с DoD ("тест ... доводит команду до отказа по пределу"): нужен запас времени между стартом помощника и пределом (например больший предел теста, или ожидание появления pid-файла отдельным этапом) вместо жёсткого совпадения одного окна на оба события.
- герметичность: tools/taskctl/push_timeout_test.go (TestPushDoesNotHangOnCredentials) и tools/shipctl/push_timeout_test.go не изолируют HOME/GIT_CONFIG_GLOBAL/GIT_CONFIG_SYSTEM, в отличие от initRepo в internal/gitrun/gitrun_test.go. На машине с настоящим глобальным credential.helper (например osxkeychain) он тоже встаёт в цепочку помощников учётки перед тестовым спящим и может дать сторонний эффект (обращение к реальной связке ключей, в худшем случае диалог) прямо во время прогона теста, который чинит ровно этот класс поломки. Изолировать окружение теста так же, как это уже сделано в internal/gitrun.
- сценарий проверки (агентский вид, раздела «Приёмка» в файле нет): все три шага это go test ветки, напрямую (TestPushHangingCredentialHelper, TestPush* в taskctl и shipctl) или через regcheck, который тоже гоняет тот же go test. Ни один шаг не прогоняется после выката поверх собранного бинаря и не является чем-то, кроме повтора тестов ветки: сценарий из одних тестов зелен всегда, и молчание taskctl fail в нём неотличимо от работы. Нужен хотя бы один шаг вроде запуска собранных taskctl/shipctl (не go test) против временного репозитория со спящим помощником учётки, который показывает отказ за секунды на реальном бинаре.

## Сценарий проверки

Первый шаг воспроизводит поломку. Помощник учётки, который ждёт человека,
раньше вешал пуш навсегда.

```sh
cd ~/projects/devkit/internal && GOWORK=off go test ./gitrun/ -run TestPushHangingCredentialHelper -count=1 -v
```

Ожидание: `PASS`, прогон укладывается секунд в пять. Отказ пуша назван словами
«не кончился за 2s», в нём есть слово про учётку и имя переменной
`DEVKIT_GIT_TIMEOUT`, а спящий помощник умирает вместе с git.

```sh
cd ~/projects/devkit/tools/taskctl && GOWORK=off go test -run 'TestPush' -count=1 ./...
cd ~/projects/devkit/tools/shipctl && GOWORK=off go test -run 'TestPush' -count=1 ./...
```

Ожидание: `ok` у обоих. Пуш доски через `CommitOpts` и пуш `shipctl` кончаются
отказом по пределу. Разрешение `DEVKIT_PUSH_OK=1` при этом доезжает до хука
`pre-push`, и коммит доски доходит до remote.

```sh
cd ~/projects/devkit && regcheck -C tools/taskctl --tests tools/taskctl/push_timeout_test.go -- env GOWORK=off go test -run TestPushDoesNotHangOnCredentials -count=1 ./...
```

Ожидание: «тест краснеет на HEAD и проходит на текущем коде». На старом коде
пуш висит до потолка теста, на новом кончается отказом.
