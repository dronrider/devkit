# DK-716: Работа по задаче из любого чата даёт строке «Стоп» и вход в живой чат

## Что происходит

2026-09-02, DK-704 в in-progress. Работу по ней ведёт доводящий чат dff98764, поднятый с дашборда под именем chat-<ID>-<n>. Чат привязан к задаче по факту работы, в реестре сессий лежит запись «работа, повод taskctl move DK-704». Файла этапа в ~/.devkit/runs у задачи нет, agentctl stage чат не звал.

Признак «строка присвоена» считает leadsTask в tools/dashboard/registry.go. При непустом имени tmux решает только имя. Ведут task-* и goal-*, всё остальное считается разговором (решение DK-460, чтобы чат про задачу не выглядел вторым исполнителем). Такая работа помечается Talk, фильтры run и run_busy в tools/dashboard/tasks.go её пропускают, и у строки пустой run. Чип этапа по тому же пустому run гаснет в rowStage. У сессии без имени tmux (терминал, окно vscode) ведущей считается почти любая привязка, кроме «рука».

Для доски запись реестра сворачивается правилом «последняя выигрывает», а список чатов задачи берёт множество Touched. Чат dff98764 сначала двигал DK-684, потом DK-704, и для доски он работа только по DK-704.

На форме DK-704 стоят рядом чип «активна» и жёлтая кнопка «Продолжить», в списке у строки нет ни кружка работы, ни «Стоп». По нажатию «Продолжить» тот же чат находится по реестру, и в его живой ход попадает вводная «Продолжай работу по DK-704». Кнопка «Выполнить» у такой строки доступна, и с неё поднимается второй исполнитель поверх идущей работы. Иконка чата открывает список чатов, до разговора с идущим ходом ещё один клик. Человек не может по экрану сказать, работают ли по задаче и где.

### Проверено на груминге

2026-09-02, чтением кода. `leadsTask` (tools/dashboard/registry.go:173) при
непустом имени tmux решает только по префиксам `task-` и `goal-`, а без имени
считает работой всё, кроме привязки рукой. Строка собирается тем же признаком.
За неё отвечают `run` и `run_busy` в tools/dashboard/tasks.go, чип этапа
гаснет в `rowStage` по тому же пустому `run`. Ни `Stage`, ни `Record` в
internal/stage/stage.go поля сессии не несут, дописывать его придётся вместе
с форматом записи.

## Чего хотим

Задача, над которой идёт работа в любом чате (дашборд, терминал, окно vscode), в списке и на форме показывает «Стоп» и чип этапа, кнопок «Выполнить» и «Продолжить» у неё нет. Иконка чата открывает ту сессию, где ход идёт сейчас, при нескольких самую свежую по реплике. Когда все рабочие сессии остановились или строка ушла из in-progress, кнопки возвращаются.

## Границы

Защита DK-460 остаётся. Чат, который задачу только читал, записей «работа» не
набирает и вторым исполнителем не становится. Индикатор внутри панели чата
правит DK-701, здесь трогаются строка задачи и её кнопки.

DK-723 эта правка не снимает. Там свой предмет, склейка перезапусков конвейера
в одну запись списка чатов. Строки списка ключует `chatEntries` по ID сессии, и
эту дорогу тут никто не трогал. Вклад косвенный. Список рабочих задач сессии
теперь считает `sessions.Works`, и группировать перезапуски есть по чему, не
разбирая имя окна.

## Развилки

Развилки сняты в разговоре 2026-09-02, исполнителю остаётся механика.

1. Одиночного «ведущего» в модели нет. У задачи множество рабочих сессий. Рабочей сессию делает запись реестра «заказ», «дерево» или «работа», запись «рука» оставляет разговором, «снята» снимает. Имя tmux в критерии не участвует. Дашбордный чат, который только читал задачу, записей «работа» не набирает и рабочим не становится, защита DK-460 остаётся.

   Решение исполнителя 2026-09-04: слов в критерии два, «дерево» и «работа».
   «Заказ» из него убран. Разбор такой. Слово это пишет хук старта всякому
   подъёму дашборда. `launchEnv` ставит `DEVKIT_TASK` одинаково конвейеру,
   циклу цели, разбору черновика и чату по строке. Возьми критерий
   «заказ», и рабочей становилась бы любая строка, по которой человек открыл
   чат почитать. Кнопка запуска у неё уезжала бы в тот же чат вместо подъёма
   исполнителя по вердикту pick. Это противоречит «Границам» этой же задачи и
   сносит защиту DK-460 вместе с её регрессионным тестом. Конвейер и цикл цели
   строку от этого не теряют. Их работа видна списком tmux по собственному
   имени сессии, и до критерия дело не доходит. Остаётся узкая дыра. Сессия
   конвейера, чьё окно уже умерло, а транскрипт ещё свеж, строку до первой
   команды доски не присваивает. Цена дыры меньше цены отобранной кнопки
   запуска, и правило board-task эту дыру закрывает само, обязывая взявшего
   открыть этап.
2. Состояние строки это свёртка по множеству. Ход идёт, если идёт хоть у одной. Ждёт человека, если ждёт хоть одна и никто не работает. Иначе простаивает.
3. Привязку снимает конец работы по задаче. Следующая задача той же сессии прежнюю привязку оставляет. Закрытие строки, перевод её из in-progress и «отпустить» рукой кладут «снята». Пока этого не было, сессия работает по всем своим задачам, и каждая строка её показывает.
4. Взятие задачи в любом чате это действие. Правило board-task обязывает открыть этап agentctl stage <ID> разработка, тот кладёт запись «работа» в реестр. В запись этапа добавляется ID сессии, сейчас в Record его нет. Страховкой остаётся кнопка привязки на форме.
5. «Стоп» у конвейера убивает tmux, как сейчас. «Стоп» у чата прерывает текущий ход, кладёт «снята», а в чат приходит сообщение, что работа по задаче остановлена. Разговор остаётся живым. При нескольких рабочих сессиях «Стоп» показывает список.
6. Доска не опрашивается по таймеру, обновляется по фокусу и событию уведомителя. Начало и конец хода уведомитель видит (UserPromptSubmit, Stop). Перерисовку кнопки после смены состояния проверить живым прогоном.

## DoD

- Рабочей сессию задачи делает запись реестра «дерево» или «работа», имя tmux в
  критерии не участвует, а «рука» оставляет сессию разговором. «Заказ» в
  критерий не входит, разбор в развилке 1. Рабочих сессий у задачи может быть
  несколько.
- Состояние строки собирается свёрткой по этому множеству: ход идёт, ждёт
  человека, простаивает.
- Пока по строке идёт работа, в списке и на форме стоят чип этапа и «Стоп», а
  кнопок «Выполнить» и «Продолжить» нет. Остановились все рабочие сессии или
  строка ушла из in-progress, кнопки вернулись.

  реплике.
- В записи этапа появляется ID сессии, и `agentctl stage <ID> разработка`
  кладёт запись «работа» в реестр.
- Тесты на критерий рабочей сессии и на свёртку состояния; перерисовка кнопки
  после смены состояния проверена живым прогоном дашборда.
- Правило рабочей сессии и свёртка записаны в docs/lld/DK-430-task-chat.md,
  поведение кнопок строки в tools/dashboard/README.md.

## Сценарий проверки

1. Критерий рабочей сессии и свёртка состояния строки. Работой сессию делает
   слово источника, а не имя окна; подъём разговора и привязка рукой работой не
   считаются; именная отвязка снимает одну задачу, а не всю сессию; состояние
