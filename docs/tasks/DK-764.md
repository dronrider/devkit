# DK-764: Тесты со стенным потолком времени валят чужие слияния под нагрузкой

## Что происходит

Прогон слияния убивает chrome по стенным секундам, когда машина занята: TestBoardNarrowNoSideScroll, TestBoardRowActionsAligned, TestBoardTableHeadFitsRow, TestStaticRunSplitLayout, TestStaticTactsRowHeights. В изоляции каждый идёт полсекунды, под нагрузкой сидит по девяносто и снимается сигналом.

За сутки это отбило слияния четыре раза, причём задачам, которые дашборда не касались вовсе: DK-660, DK-739 дважды, DK-724 дважды. Разбор каждый раз съедает время на выяснение, что падение чужое, и подталкивает сливать с урезанной параллельностью, то есть в обход честного прогона.

Смежное уже закрыто: DK-635 про потолок стенных секунд в раннере, DK-733 про фикстуры, зависящие от часа суток. Здесь третья беда того же семейства: сам браузерный стенд не переживает соседей по прогону.

Двенадцатого сентября семейство вышло за пределы браузера. Прогон слияния
DK-934 под нагрузкой уронил сначала go:dashboard, а на повторе go:agentctl:
TestQuotaStaleConfigured отработал девять с лишним секунд вместо доли
секунды и снялся по сроку. Поодиночке оба компонента зелёные, правка
задачи их не касалась.

Разобрать надо, чем мерить такие тесты. Похоже, потолок им нужен не стенной, а свой, либо браузерные стенды должны идти отдельным звеном раннера, не соревнуясь за процессор с остальными семнадцатью.

## Сценарий проверки

Агентский. Предмет правки это сам стенд, и прежний его текст фикс уносит
целиком. Исходную поломку на нём уже не воспроизвести. Механизм её
воспроизводится на новом стенде задержкой `STUB_HEAD_DELAY`. Задержка держит
оболочку стенда без процессора столько секунд, сколько сказано, и играет то
самое голодание, которое даёт соседний полный прогон. Старый стенд краснел на
задержке три секунды, новый держит двадцать пять и краснеет за боевым потолком
`DefaultAdopt` на тридцати пяти. Третий шаг гоняет все четыре теста стенда три
захода подряд под фоновыми busy-loop.

Каждый шаг это одна физическая строка. `taskctl rehearse` режет блок по
переводам строки и гоняет строку своим прогоном без общего состояния. Поэтому
busy-loop, переменная `spin` и завершающий `kill` живут в одной строке третьего
шага. Сторожевой `kill` через 240 секунд подчищает busy-loop, если шаг
оборвётся раньше своего конца.

```sh
cd tools/taskctl; export GOWORK=off; STUB_HEAD_DELAY=25 go test -run 'TestRunTakesModelFromPick$' -count=1
cd tools/taskctl; export GOWORK=off; out=$(STUB_HEAD_DELAY=35 go test -run 'TestRunTakesModelFromPick$' -count=1 2>&1); echo "$out" | tail -4; echo "$out" | grep -q 'не приняла замок за 30s' && echo repro=ok
cd tools/taskctl; export GOWORK=off; for i in $(seq 1 12); do ( while true; do :; done ) & done; spin="$(jobs -p)"; ( sleep 240; kill $spin >/dev/null 2>&1 ) & sleep 4; ok=0; for i in 1 2 3; do go test -run 'TestRunTakesModelFromPick|TestRunModelFlagBeatsPick|TestRunPickRefusalStartsWithoutModel|TestWakeRaisesWithPickedModel' -count=1 && ok=$((ok+1)); done; kill $spin >/dev/null 2>&1; echo "green_runs=$ok"; test "$ok" -eq 3
```

Ожидание по шагам.

1. `--- PASS: TestRunTakesModelFromPick` и код возврата 0 при задержке
   двадцать пять секунд. Стенного срока у стенда больше нет.
2. Строка `repro=ok` и код возврата 0. За боевым потолком тест краснеет той же
   строкой `оболочка headless не приняла замок за 30s`, что стояла в отбитом
   слиянии DK-908.
3. Строка `green_runs=3` и код возврата 0. Три подряд зелёных захода четырёх
   тестов стенда под двенадцатью фоновыми busy-loop.

## Из черновика DK-956 «Полный прогон тестов валится под нагрузкой на жёстких потолках времени» (записан 2026-09-12)

### Черновик

#### Ситуация

Раннер гонит компоненты в восемь воркеров. Внутри компонентов сидят проверки с
зашитым потолком времени. Браузерные тесты доски ждут хром до полутора минут,
подъём головы в taskctl ждёт замок оболочки две секунды.

#### Осложнение

На DK-947 три захода слияния подряд сгорели на трёх разных тестах:
TestBoardNarrowNoSideScroll (90 секунд), TestBoardTableLabelsNotCut (95 секунд)
и TestWakeRaisesWithPickedModel (замок за 2 секунды). Каждый из них поодиночке
проходит за две секунды. Каждый заход слияния стоит около шести минут и
кончается отказом, а задача стоит в In progress.

#### Вопрос

Чем лечить. Поднять потолки в самих тестах, снять их с общего прогона в
отдельную дорожку, урезать число воркеров по умолчанию или брать потолок из
замера машины.

#### Гипотеза

Потолки писались от свободной машины. Под восемью воркерами хром и tmux
получают процессорное время позже, и две секунды на замок это не запас, а
случай. Дешевле поднять потолки там, где ожидание внешнего процесса, и оставить
число воркеров как есть.
