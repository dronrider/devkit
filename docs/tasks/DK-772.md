# DK-772: Строка с ! из чата отдаёт sudo и ssh пароль через askpass дашборда

## Что происходит

2026-09-03, чат дашборда. Написал в разговор живой сессии строку с `!` и
командой под sudo, а в ответ получил от агента, что оболочка сессии сидит без
терминала и sudo некуда показать запрос пароля, идите в Terminal.app. Сама
дорога DK-480 при этом цела: строка клавишами доезжает до клиента, клиент
включает bash-режим и гоняет команду без витка модели. Но команду bash-режим
запускает без tty, а sudo пароль читает только с терминала. Когда клавишная
дорога занята (сессия стоит на вопросе разрешения, своей tmux у неё нет),
строка уезжает агенту текстом, тот запускает её Bash-инструментом, и там tty
нет тем более. Итог один на все дороги: любая команда с sudo из чата не
проходит, и починить это доставкой нельзя.

Проверил на своём Маке, как sudo ведёт себя без терминала. Без переменной
`SUDO_ASKPASS` он отказывает словами «a terminal is required». С помощником в
`SUDO_ASKPASS` и любым значением `DISPLAY` (либо ключом `-A`) sudo зовёт
помощника, передаёт ему текст запроса первым аргументом и берёт пароль из его
вывода. ssh с passphrase ключа делает то же самое через `SSH_ASKPASS`.

## Чего хотим

Дашборд становится помощником ввода пароля для сессий, которые сам поднимает.
В окружение каждой поднятой сессии кладутся `SUDO_ASKPASS`, `SSH_ASKPASS` и
`DISPLAY`, помощник это скрипт devkit. Когда sudo или ssh его зовут, в ленте
разговора встаёт вопрос «sudo просит пароль» с закрытым полем ввода и текстом
запроса, как встают сейчас вопросы разрешения клиента. Человек вводит пароль в
панели, помощник отдаёт его вызвавшей программе, команда идёт дальше, а её
вывод ложится в ленту как у любой строки с `!`. Отказ (кнопка «отменить» или
срок ожидания) кончает помощника ненулевым кодом, и sudo отказывает, как при
пустом пароле.

Пароль живёт только в памяти демона на время ожидания и в ответе помощнику.
В журнал дашборда, транскрипт сессии, ленту и `~/.devkit/chats` он не
попадает.

## Границы

- Сессии, поднятые не дашбордом (окно vscode, свой терминал), помощника не
  получают: там у sudo есть свой терминал.
- Команды, у которых пароль просит не sudo и не ssh (скажем, `su`), задача
  не трогает: у них нет askpass.
- Хранить пароль между вызовами дашборд не будет. Кэш sudo на пять минут
  делает сам sudo, этого хватает.

## Развилки

- Канал помощника к демону. Помощник зовётся из-под sudo с окружением
  клиента, поэтому ему доступны те же переменные, что и клиенту: адрес демона
  и ID разговора берутся оттуда. Кука входа помощнику не нужна: он живёт на
  той же машине, и демон узнаёт своего по локальному секрету, а не по куке
  панели.
- Куда класть переменные. В общие пары окружения подъёма (`launchEnv`), а не
  в одну дорогу: конвейер задачи и чат поднимаются разными вызовами, и sudo
  из окна задачи нужен не меньше, чем из свободного чата.
- `DISPLAY` со значением-заглушкой. Без него sudo без tty помощника не зовёт,
  а ключ `-A` требовать от человека в каждой строке негоже. Побочный эффект
  один, программы с графикой под X11 на Маке, и их в сессиях агента нет.
- Пароль через панель. Панель и так ходит к демону по HTTPS с кукой, и
  ответ на запрос разрешения идёт тем же каналом; поле ввода закрытое, в
  локальное хранилище браузера не пишется.

- Где что лежит, по разведке 2026-09-03. Пары окружения подъёма собирает
  `launchEnv` (`tools/dashboard/chats.go`, около строки 1631), через неё идут
  и чат, и конвейер задачи, и разбор черновика. Вопрос клиента живёт типом
  `tmuxAsk` в `tmux.go`, панель опрашивает `GET .../chats/{sid}/ask` раз в
  три секунды (`watchClientAsk` в `static/app.js`) и отвечает `POST` на тот же
  адрес, серверная сторона это `handleChatAsk` и `handleChatAskAnswer`.
  Локального канала без куки у демона нет: HTTP только TCP под `s.auth`,
  открыт лишь `/healthz`; сокеты `/tmp/cc-socks` принадлежат клиенту, а свой
  сокет демон слушает только как адрес отправителя. Помощнику нужен свой
  вход: локальный секрет файлом под `~/.devkit` с правами 0600, который
  демон пишет на старте, а помощник читает и предъявляет. Сторож раскладки
  `tools/devkitctl/layout.py` признаёт sh-скрипты только в `hooks/`,
  `kit/harness/snap/` и `docs/tasks/`, py-скрипты в `tools/` и `hooks/`.
  Стенды для правки: `termsay_test.go` (фикстура tmux пишет `send-keys` в
  `sent.log`), `fakeTmuxAsking` в `waiting_test.go`, `newTestEnv` в
  `server_test.go`.

## DoD

- `! sudo <команда>` из чата живой сессии доходит до конца: в ленте вопрос
  с закрытым полем, после ввода пароля вывод команды на месте.
- То же для ssh с passphrase ключа.
- Отмена вопроса или срок ожидания отказывают sudo, команда не висит.
- Пароль не находится грепом ни в одном файле под `~/.devkit` и в
  транскрипте сессии.
- Помощник раскладывает `devkitctl doctor --fix`, без него sudo из чата
  отказывает словами про отсутствие помощника, а не молчит.
- README дашборда: раздел про доверенный ввод из чата получает вход с
  примером `! sudo`.

## Приёмка

- вид: mixed
- барьер «секрет»: пароль пользователя, единственный, кому его знать, это
  человек.
  - `secretctl` в подпроцесс: не годится, пароль учётки Мака в хранилище
    секретов класть нельзя, задача как раз о том, чтобы он нигде не лежал.
  - фикстура ответа: годится для стенда демона и помощника (ответ панели
    подставляется в тест), но не доказывает, что настоящий sudo примет
    введённое, и остаётся агентской частью.
  - стенд вместо живой службы: подменный `sudo`, зовущий помощника как
    настоящий, годится для агентской части и покрывает цепочку целиком, но
    сам факт «настоящий sudo с настоящим паролем» остаётся человеку.

## Проверка

Машинная часть судит машину после выката. Разложен ли помощник, несёт ли живой
демон его вход, внятно ли отказывает помощник, когда звать некого. Настоящий
`sudo` с настоящим паролем остаётся человеку, так решено в «Приёмке».

- Исключение: обкатка. Шаги судят разложенный помощник и живой демон
  дашборда, во временном `HOME` свежего дерева нет ни того, ни другого.

Машинная часть, после выката:

```sh
test -x ~/.devkit/askpass.py && echo "помощник на месте"
stat -f '%Sp' ~/.devkit/askpass.local
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py doctor | grep -c askpass
DEVKIT_ADDR= python3 ~/.devkit/askpass.py "Password:"; echo "код $?"
DEVKIT_ADDR=127.0.0.1:1 DEVKIT_CHAT=нет python3 ~/.devkit/askpass.py "Password:"; echo "код $?"
```

Ждём такого. Первая строка печатает «помощник на месте». Права секрета
`-rw-------`. Доктор насчитывает ноль жалоб про askpass. Два последних запуска
уходят ненулевым кодом, и каждый называет причину словами, про пустой
`DEVKIT_ADDR` и про неответивший демон.

Человеческая часть, из панели дашборда:

1. Открыть разговор живой сессии и написать `! sudo id`. В ленте встаёт вопрос
   с текстом запроса и закрытым полем. Ввести пароль. Ждём вывод команды в
   ленте со строкой `uid=0(root)`.
2. Написать ту же строку снова и нажать в вопросе «отменить». Ждём отказ sudo
   и возврат разговора к работе. Команда не висит.
3. Написать `! ssh -T <хост с ключом под passphrase>`. Ждём тот же вопрос
   закрытым полем, после ввода passphrase соединение идёт.
4. Поискать введённый пароль на машине:
   `grep -r "<пароль>" ~/.devkit ~/.claude/projects 2>/dev/null | head`.
   Ждём пустую выдачу.
