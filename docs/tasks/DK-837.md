# DK-837: Ворот следа ревью не находит след слитой задачи и молчит у shipctl push

## Что происходит

После слияния ветка задачи удаляется, и рубеж пуша перестаёт видеть след ревью. Строку уровня он ищет в файле задачи только пока стоит на ветке задачи, а на main переходит к заметке git. Заметку же в проекте с доской поставить нечем: ярлык обязан быть ID с доски, а для ID с доски команда пишет в файл задачи, не в заметку.

Выходит замкнутый круг. Код DK-716 слит в main, ревью прошло восемью кругами, вердикт «принято» записан в разделе «Ревью», а git push отбит словами «нет следа ревью у кода в диапазоне». Обхода изнутри нет, остаётся прямая команда человека с переменной.

Всплыло на DK-716, когда слияние прошло, а пуш не успел: сеть пропала между ними, и push поехал отдельным ходом уже с main.

Разобрать надо, где рубежу искать след слитой задачи. Похоже, по ID в subject коммитов диапазона: они там есть у каждого, и по ним же рубеж уже проверяет, что код не безымянный.

Правило «код перед пушем проходит ревью» держится на этом вороте, а он мимо цели
с обеих сторон. С одной стороны отбивает пуш кода, у которого ревью записано
восемью кругами, и обход остаётся только у человека переменной, а в автономном
режиме обхода нет вовсе. С другой стороны обычный `shipctl push` его не зовёт
совсем (черновик DK-855), и `internal/gitrun` ставит разрешающую переменную на
каждый свой `git push`, то есть гитовый `pre-push` пропускает такой пуш без
разбора.

## Чего хотим

След ищется по ID в subject код-коммитов диапазона, а не по стороне, с которой
на них смотрят: ID там есть у каждого, и `rangeVerdict` его уже достаёт. Строка
уровня берётся из файла задачи этого ID, в том числе из архивного. Обычный пуш
зовёт тот же ворот, и обход становится отказом, а не молчанием.

## Границы

Заметку ревью на коммит слияния из `shipctl merge` не заводим: на уже слитом
коде её нет, и старые случаи так не чинятся (развилка «путь»). Что считать
кодом в диапазоне, разбирает черновик DK-766, эта строка критерий `boardOnly`
не трогает.

## DoD

`reviewTraceGate` судит диапазон по коммитам, а не по текущему чекауту: для
каждого код-коммита берётся ID из subject тем же `firstID`, каким его берёт
`rangeVerdict`, и строка уровня ищется в файле этой задачи, включая архивный
`docs/tasks/archive/<год>/<ID>.md`. Заметка на HEAD остаётся следом там, где
доски нет. След требуется от каждой задачи диапазона, а отказ называет ID и
файлы, в которых строки уровня не нашлось.

Обычный `shipctl push` зовёт тот же ворот, что и `--check-only`, и разрешающая
переменная, которую `internal/gitrun` ставит своему `git push`, ворот больше не
открывает молча.

Ворот стоит общей функцией на всех путях пуша devkit (ответ человека на
развилке «охват»). Одним `shipctl push` дело не кончается. Тот же ворот зовёт
`taskctl ... --push`, который сегодня пушит обычным `git push` через
`internal/gitrun` без всякой проверки, и путь дашборда. Смешанный пуш, где коммит доски уносит и
предшествующие код-коммиты ветки, отбивается наравне с голым кодом (развилка
«смешанный пуш»). Чистая доска без код-коммитов проходит по-прежнему.

Тесты: слитый диапазон с удалённой веткой проходит, архивный файл задачи
проходит, задача без строки уровня отбивается, обычный `push` без следа
отбивается, смешанный пуш доски с код-коммитом без следа отбивается тоже, а
`taskctl --push` на таком же диапазоне отбивается тем же отказом. Краснота
регрессионных тестов сверена `regcheck`.

Снаружи это видно прогоном сценария проверки: слить задачу, удалить ветку и
запушить main без переменной обхода. Раздел про ворот следа ревью в
`tools/shipctl/README.md` описывает поиск по ID и оба файла задачи.

## Разбор

Воспроизвёл на синтетическом репозитории с доской 2026-09-07. Задача DK-900 в
работе, ветка `dk-900-fix`, код-коммит с ID в subject, строка уровня записана в
`docs/tasks/DK-900.md` командой `taskctl review level`. После слияния
fast-forward и удаления ветки `shipctl push --check-only` на том же диапазоне
отбивает пуш, а стоя на ветке задачи до слияния пропускает его словами
«диапазон пропущен: доска либо код со следом ревью». Диапазон один и тот же,
след ревью один и тот же, расходится только текущая ветка чекаута: ворот судит
не коммиты, а сторону, с которой на них смотрят. В тексте отказа второй
половины про файл задачи нет вовсе, потому что `branchTaskID` вернул пустую
строку.

Тем же прогоном подтвердилось, что обхода изнутри доски нет:
`refs/notes/review` после `taskctl review level` не заводится, `noteRoot` при
найденной доске отдаёт пустую строку, и след уходит в файл задачи.

Рядом вылез второй случай того же корня, независимый от первого. Файл задачи
после закрытия уезжает в `docs/tasks/archive/<год>/<ID>.md`, а `taskFilePath`
знает только `docs/tasks/<ID>.md`. Прогон на DK-901: ветка задачи цела,
`branchTaskID` сработал, а пуш всё равно отбит словами «строки уровня в
docs/tasks/DK-901.md тоже нет». Ловится он и без слияния, так что в работу
берутся оба, а не первый с оговоркой.

Дублей не нашёл. DK-472, DK-473 и DK-474 правят ворот слияния и команду
`ready`, черновик DK-766 спорит о том, что считать кодом, а черновик DK-855 про
обратный случай: обычный `shipctl push` ворот следа не зовёт вовсе.

Условий, посильных только человеку, не нашёл: предмет проверяется на
синтетическом репозитории, доступов и секретов правка не просит, наружу ничего
не выносит.

## Из черновика DK-855 «Обычный shipctl push проходит мимо ворот следа ревью» (записан 2026-09-07)

### Черновик

#### Ситуация
`shipctl push` (`tools/shipctl/push.go:76`) гоняет только `rangeVerdict`, а
`reviewTraceGate` не зовёт, и при этом `internal/gitrun` ставит
`DEVKIT_PUSH_OK=1` на каждый свой `git push`, то есть гитовый `pre-push`
пропускает такой пуш без разбора. Поймано 2026-09-07 ревью круга доработки
DK-808.
#### Осложнение
Ворота следа ревью обходятся штатной командой самого devkit, и обходятся
молча: ни отказа, ни находки. Правило «код перед пушем проходит ревью» держится
на том, что агент позвал merge, а не push, то есть на памяти, ради ухода от
которой ворота и заводились.
#### Вопрос
Звать `reviewTraceGate` из обычного пуша или снимать `DEVKIT_PUSH_OK` там, где
разбор не прошёл?
#### Проверка
Воспроизведено 2026-09-07 на синтетическом репозитории с доской и bare-origin:
`shipctl push` увёл в origin код-коммит без следа ревью и вышел нулём, а
`shipctl push --check-only` на том же диапазоне отбил его отказом
`reviewTraceGate`. Гитовый `pre-push` до проверки не доходит: первой строкой он
видит `DEVKIT_PUSH_OK` и выходит нулём, а ставит переменную сам же `gitrun`,
через который `shipctl` гоняет весь свой git. Оба слоя, команда и хук, сходятся
на одной лазейке. Тем же путём мимо ворота идёт `taskctl ... --push`
(`tools/taskctl/ops.go:277`): там обычный `git push` без всякой проверки. У
слияния ворот на месте, `reviewLevelGate` зовётся из `cmdMerge`
(`tools/shipctl/ops.go:1013`).
#### Гипотеза
Код без следа ревью не уезжает в origin никакой командой devkit, и обход
называется отказом, а не молчанием.
