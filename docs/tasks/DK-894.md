# DK-894: shipctl выбирает команду выката по путям диффа задачи

## Что происходит

В xr-proxy файл `.devkit/deploy.local` держит ключи `deploy` (xr-server на оба VPS) и `deploy_xr_hub`, а комментарий говорит, что роутеры, хаб, relay и APK «катаются по своим шагам из хэндоффа», и на такие merge надо передавать `--deploy` руками. Ключа под APK нет, релиз идёт скриптом `scripts/release-apk.sh`. В сессии XR-294 (2026-09-09, чат «Проблема с маршрутизацией трафика в xr-proxy») правка легла в `xr-core`, то есть в приложение, а пользователь попросил «задеплоить всё, обновить роутеры и перевыпустить приложения». Агент сам решал, какой компонент задет, и какой скрипт под него звать, читая комментарии конфига.

Автономия по пункту 8 правил доски кончается там, где кончается дефолтный ключ. Компонент не из дефолта агент катит либо по памяти, либо не катит совсем и отдаёт пользователю список команд. В XR-294 релиз APK ушёл пользователю с формулировкой «за владельцем», и пользователь вернул его вопросом «почему ты сам не сделал». Подсказка «что дальше» у `shipctl status` не называет компонентов диффа, это то же требование, что стояло в DK-191 про ветку автономии.

### Что снял разбор

Обвязка `internal/deployconf` знает четыре ключа: `deploy`, `test`,
`autonomous` и `deploy_timeout`. Остальные строки файла разбор пропускает
молча. `deploy_xr_hub` для утилиты не существует, его подставляют в `deploy`
руками перед хабовым слиянием. Формат плоский, «ключ = значение» через
`internal/kvconf`, секций в нём нет. Точка внутри имени ключа проходит без
правки разбора.

Команды компонентов в xr-proxy уже написаны и лежат скриптами:
`deploy-server.sh`, `deploy-router.sh`, `deploy-hub.sh`, `release-apk.sh`,
`release-xr-setup.sh`, `release-xr-share.sh`. Раскладке остаётся сопоставить
пути диффа со скриптом. Сочинять команды выката не придётся.
Условия, посильного только человеку, разбор тут не нашёл.

У `shipctl ship` есть тег `deployed`, и диапазон для правки, легшей мимо ветки,
берётся оттуда же, откуда состав поезда.

Соседний черновик DK-895 держит вторую половину той же сессии XR-294: текст
правил автономии и сторожа стенда. Здесь остаётся утилита, и связь между
строками ставится `taskctl dep add`.

## Чего хотим

`shipctl status` и `shipctl merge` печатают, какие компоненты задел дифф задачи и каким ключом каждый катится. При autonomous=true merge катит их все сам, а компонент без ключа это отказ с названным путём и подсказкой, какой ключ завести. Явное «задеплой» пользователя в проекте с раскладкой компонентов сводится к одной команде без чтения комментариев.

## DoD

- Обвязка `.devkit/deploy.local` знает компоненты: у каждого своя команда
  выката и свои пути, которые его задевают. Разбор компонентных ключей лежит в
  `internal/deployconf` вместе с остальными.
- `shipctl status` по задаче печатает, какие компоненты задел дифф ветки и
  какой командой каждый катится.
- `shipctl merge` при `autonomous = true` катит задетые компоненты по очереди
  в порядке из конфига. Первый провал останавливает остальные, и это видно в
  отказе.
- Путь диффа, не попавший ни в один компонент, это отказ с названным путём и
  подсказкой, какой ключ завести.
- `shipctl ship` считает компоненты по диффу от тега `deployed` до `main`.
  Правка, легшая мимо ветки, выкатывается тем же способом.
- Тесты идут на синтетическом репозитории с командами-заглушками. Прогон
  проверяет печать компонентов, порядок выката, остановку на провале и отказ
  без ключа.
- Раздел про компоненты стоит в `tools/shipctl/README.md`, а образец ключей в
  `CONNECT.md` рядом с остальной раскладкой обвязки.
- Раскладка компонентов заведена в проекте, где их несколько, и выкат оттуда
  проходит одной командой. Проектных имён при этом нет ни в коде, ни в доке
  devkit. Они живут в гитигнорнутом конфиге самого проекта.
