# DK-935: Кнопка и подъёмы дашборда запускают голову через taskctl run

Цель: [tasks/DK-902.md](tasks/DK-902.md)

## Что происходит

2026-09-11, нарезка цели DK-902 чтением кода. Дашборд поднимает голову своей
функцией `startTaskSession` (tools/dashboard/runs.go:406). К ней ведут кнопка
экрана, `dashboard wake`, `dashboard check` и `dashboard round`. DK-931
заводит команду `taskctl run` с замком и лестницей. Путей запуска станет два,
и кнопка сможет поднять вторую голову рядом с той, что поднял тик.

## Чего хотим

Кнопка экрана и три подъёма дашборда запускают голову через общий код
запуска из DK-931. Замок один на все пути. Дашборд показывает отказ на
занятом замке теми же словами, что сейчас отказ 409.

## Границы

Вид экрана не меняется. Здесь только путь запуска.

## Ревью

Уровень 3 до 671a8f8: неопределённость ревью 3 (вердикт pick effort high), путь через четыре точки входа и лестницу носителей taskhead

- [возврат: реализация, 2026-09-11] блокирует: headless-ступень taskhead.Raise (internal/taskhead/raise.go, функция headless) не получает Request.Prefix. Дашборд собирает Prefix (headlessEnv/launchEnv) ровно затем, чтобы поднятая голова взяла PATH с приоритетом штатного kit-каталога вместо своего экземплярного (где лежат возможные устаревшие копии agentctl/taskctl, комментарий launchEnv про DK-457), настоящий HOME, DEVKIT_ADDR для askpass и метки печатного режима. Для newWindow (tmux-окно) Prefix встаёт приставкой команды (raise.go:344-352), а headless (raise.go:386-428) строит cmd.Env только из os.Environ()+q.env(...), Prefix туда не попадает вовсе. Лестница проваливается в headless именно тогда, когда newWindow не смог поднять окно (в т.ч. штатный случай 'холодный старт tmux-сервера под нагрузкой', ради которого и заведён AdoptEnv/DefaultAdopt, см. комментарий в raise.go:57-59), то есть ровно тогда, когда кнопка/wake/check/round дашборда особенно нуждаются в исправленном PATH. Итог: возможен молчаливый возврат к 'чужому бинарю' (баг класса DK-457/DK-691) или падению agentctl внутри уже поднятой (и объявленной поднятой) headless-головы, потому что found(head.Bin) в Raise проверяет только клиентский бинарь (например 'клиент-2'), а не 'agentctl', которым обёрнут клиент второй подписки. Теста на этот путь для дашборда нет: в tools/dashboard/*_test.go нет ни одного сценария, где кнопка/wake/check/round реально поднимают RungHeadless и проверяют его окружение (grep RungHeadless по пакету dashboard пуст). Чем проверить: добавить стенд, где tmux есть, но 'tmux new-session' отказывает (как в TestTaskWakeReparksAfterFailedStart), а task-run.py фикстуры принимает замок и печатает окружение в файл, и свериться, что PATH/HOME/DEVKIT_ADDR те же, что у окна. Починка либо прокидывает Prefix в headless() (парсингом пар, а не шелл-строкой), либо осознанно документирует ограничение и делает Preflight/headRequest отказом на этой ступени для дашборда.
- [возврат: реализация, 2026-09-11] не блокирует: handleRunStart (tools/dashboard/runs.go, цикл по tmuxSessions() перед вызовом startTaskSession) продолжает своей проверкой ловить занятую tmux-сессию task-/goal-<ID> и убивать простаивающий remainder разговора, хотя тем же самым (по другому источнику истины) теперь ведает taskhead: newWindow сам убирает остаток окна при свободном замке (raise.go, комментарий 'Замок свободен, живого окна в реестре нет...'), а занятый замок сам даёт headBusy с тем же текстом через runBusy. Из диффа видно только косметическую правку (текст ошибки собран через runBusy), сама проверка не тронута, так что это не находка этого MR, а скорее ответ на собственный вопрос исполнителя (двойная проверка): по факту сейчас оба пути формируют одинаковый текст 409 через общий runBusy() и тесты (TestRunStartAlreadyRunning, TestRunStartBusyHeadLock) это подтверждают, расхождения не нашёл. Кандидат на упрощение в отдельной задаче: убрать сканирование tmuxSessions() по имени и положиться на лестницу/замок taskhead целиком, раз она уже покрывает и живую сессию, и остаток разговора.

## Сценарий проверки

Агентский. Шаги гоняются из корня дерева. `taskctl rehearse DK-935` прогоняет
их в свежем дереве. Живой tmux и живой клиент шагам не нужны. Стенды
дашборда кладут поддельный tmux, который исполняет окно конвейера, и оболочку,
принимающую замок.

1. Общий код подъёма ставит приставку зовущего за своими парами, и её пары
   перекрывают пары подъёма. Имя профиля и срок передачи замка читаются одной
   функцией, занятый замок отбивает вторую голову. Ждём `ok` пакета taskhead.

```sh
GOWORK=off go -C internal test -count=1 -run 'TestNewWindowPrefixFollowsPairs|TestHarnessName|TestAdoptWait|TestBusyLockRefusesSecondHead' ./taskhead/
```

2. Кнопка «Выполнить» поднимает голову через taskhead. Окно заводится под
   именем `task-<ID>`, клиента собирает секция `[head]` профиля подписки,
   приставка дашборда стоит за парами подъёма, а замок держит оболочка. Голова,
   поднятая мимо кнопки, даёт 409 теми же словами, что живая tmux-сессия. Ждём
   `ok` пакета dashboard.

```sh
GOWORK=off go -C tools/dashboard test -count=1 -run 'TestRunStartTaskPromptBySection|TestRunStartOnChosenHarness|TestRunStartWithoutHarnessKeepsOldWay|TestRunStartTierFromVerdict|TestRunStartBusyHeadLock|TestRunStartHeadTakesSharedLock|TestRunStartAlreadyRunning' ./...
```

3. `dashboard wake`, `check` и `round` идут тем же подъёмом. Занятый замок
   они считают живой работой, и wake не возвращает строку в Blocked. Ждём `ok`
   пакета dashboard.

```sh
GOWORK=off go -C tools/dashboard test -count=1 -run 'TestTaskWake|TestCheckRunRaisesSession|TestCheckRunBusyLockIsNotFailure|TestRoundRaisesSession|TestRoundSendsToLiveSession' ./...
```

4. Сквозной прогон `dashboard smoke` доводит выбор подписки до клиента через
   профиль, и в коде дашборда по-прежнему нет имён харнесов. Ждём `ok`.

```sh
GOWORK=off go -C tools/dashboard test -count=1 -run 'TestSmokePassesTheChain|TestSmokeLeavesNothingBehind|TestQuotaNoHarnessNamesInCode' ./...
```

5. Своей логики tmux у запуска дашборда не осталось. В `runs.go` нет ни
   `new-session`, ни прежних сборщиков команды, а `taskhead.Raise` зовётся
   один раз. Ждём `1`.

```sh
! grep -n '"new-session"\|sessionCommand(\|clientCommand(' tools/dashboard/runs.go && grep -c 'taskhead.Raise(' tools/dashboard/runs.go
```

6. `taskctl run` после переезда имени профиля и срока передачи замка в taskhead
   работает как прежде. Ждём `ok` пакета taskctl.

```sh
GOWORK=off go -C tools/taskctl test -count=1 -run 'TestRun' ./...
```
