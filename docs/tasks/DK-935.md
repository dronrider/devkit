# DK-935: Кнопка и подъёмы дашборда запускают голову через taskctl run

Цель: [tasks/DK-902.md](tasks/DK-902.md)

## Что происходит

2026-09-11, нарезка цели DK-902 чтением кода. Дашборд поднимает голову своей
функцией `startTaskSession` (tools/dashboard/runs.go:406). К ней ведут кнопка
экрана, `dashboard wake`, `dashboard check` и `dashboard round`. DK-931
заводит команду `taskctl run` с замком и лестницей. Путей запуска станет два,
и кнопка сможет поднять вторую голову рядом с той, что поднял тик.

## Чего хотим

Кнопка экрана и три подъёма дашборда запускают голову через общий код
запуска из DK-931. Замок один на все пути. Дашборд показывает отказ на
занятом замке теми же словами, что сейчас отказ 409.

## Границы

Приставку Prefix собирает дашборд (headlessEnv/launchEnv). Она чинит PATH: ставит штатный kit-каталог впереди экземплярного, где могут лежать старые копии agentctl/taskctl (комментарий launchEnv про DK-457). Она же несёт настоящий HOME, DEVKIT_ADDR для askpass и метку печатного режима. У newWindow (окно tmux) Prefix встаёт приставкой команды (raise.go:344-352). У headless (raise.go:386-428) cmd.Env собран только из os.Environ() и q.env(...), Prefix туда не попадает. В headless лестница падает ровно тогда, когда newWindow не поднял окно. Один из таких случаев штатный: холодный старт tmux-сервера под нагрузкой, ради него и заведён AdoptEnv (raise.go:57-59). Это тот самый момент, когда кнопке, wake, check и round особенно нужен исправленный PATH. Итог: headless-голова может тихо взять чужой бинарь, класс DK-457/DK-691. Либо уронить agentctl уже после отчёта об успехе. found(head.Bin) в Raise проверяет только клиентский бинарь ('клиент-2' у второй подписки). Agentctl, которым он обёрнут, эта проверка не видит. Проверить можно стендом: tmux есть, а 'tmux new-session' отказывает, как в TestTaskWakeReparksAfterFailedStart. Фикстура task-run.py берёт замок и пишет своё окружение в файл. Дальше сверка, что PATH, HOME и DEVKIT_ADDR те же, что у окна. Чинить можно двумя путями. Первый: прокинуть Prefix в headless, парсингом пар, не шелл-строкой. Второй: осознанно отказывать на этой ступени для дашборда и написать почему.: исправлено, исправлено в 3d224143, headless-ступень получает Prefix той же шелл-дорогой, что окно, поверх пар подъёма, и снимает DEVKIT_TMUX; тесты TestHeadlessPrefixFollowsPairs и TestTaskWakeHeadlessGetsLaunchEnv (bcb6cd78) красны на старом коде по regcheck. Проверку бинаря обёртки agentctl в предполёт не добавлял. Путь головы собирает приставка, а found() смотрит путь зовущего и у дашборда отказал бы там, где agentctl лежит только в ките

## Сценарий проверки

Агентский. Шаги гоняются из корня дерева. `taskctl rehearse DK-935` прогоняет
их в свежем дереве. Живой tmux и живой клиент шагам не нужны. Стенды
дашборда кладут поддельный tmux, который исполняет окно конвейера, и оболочку,
принимающую замок.

1. Общий код подъёма ставит приставку зовущего за своими парами, и её пары
   перекрывают пары подъёма. Имя профиля и срок передачи замка читаются одной
   функцией, занятый замок отбивает вторую голову. Ждём `ok` пакета taskhead.

```sh
GOWORK=off go -C internal test -count=1 -run 'TestNewWindowPrefixFollowsPairs|TestHarnessName|TestAdoptWait|TestBusyLockRefusesSecondHead' ./taskhead/
```

2. Кнопка «Выполнить» поднимает голову через taskhead. Окно заводится под
   именем `task-<ID>`, клиента собирает секция `[head]` профиля подписки,
   приставка дашборда стоит за парами подъёма, а замок держит оболочка. Голова,
   поднятая мимо кнопки, даёт 409 теми же словами, что живая tmux-сессия. Ждём
   `ok` пакета dashboard.

```sh
GOWORK=off go -C tools/dashboard test -count=1 -run 'TestRunStartTaskPromptBySection|TestRunStartOnChosenHarness|TestRunStartWithoutHarnessKeepsOldWay|TestRunStartTierFromVerdict|TestRunStartBusyHeadLock|TestRunStartHeadTakesSharedLock|TestRunStartAlreadyRunning' ./...
```

3. `dashboard wake`, `check` и `round` идут тем же подъёмом. Занятый замок
   они считают живой работой, и wake не возвращает строку в Blocked. Ждём `ok`
   пакета dashboard.

```sh
GOWORK=off go -C tools/dashboard test -count=1 -run 'TestTaskWake|TestCheckRunRaisesSession|TestCheckRunBusyLockIsNotFailure|TestRoundRaisesSession|TestRoundSendsToLiveSession' ./...
```

4. Сквозной прогон `dashboard smoke` доводит выбор подписки до клиента через
   профиль, и в коде дашборда по-прежнему нет имён харнесов. Ждём `ok`.

```sh
GOWORK=off go -C tools/dashboard test -count=1 -run 'TestSmokePassesTheChain|TestSmokeLeavesNothingBehind|TestQuotaNoHarnessNamesInCode' ./...
```

5. Своей логики tmux у запуска дашборда не осталось. В `runs.go` нет ни
   `new-session`, ни прежних сборщиков команды, а `taskhead.Raise` зовётся
   один раз. Ждём `1`.

```sh
! grep -n '"new-session"\|sessionCommand(\|clientCommand(' tools/dashboard/runs.go && grep -c 'taskhead.Raise(' tools/dashboard/runs.go
```

6. `taskctl run` после переезда имени профиля и срока передачи замка в taskhead
   работает как прежде. Ждём `ok` пакета taskctl.

```sh
GOWORK=off go -C tools/taskctl test -count=1 -run 'TestRun' ./...
```
