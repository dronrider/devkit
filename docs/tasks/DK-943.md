# DK-943: Ребро «после» снимается слиянием предпосылки

Цель: [tasks/DK-902.md](tasks/DK-902.md)

## Что происходит

2026-09-11, дорезка цели DK-902 по нарезке LLD DK-933. Ребро «после»
снимается закрытием предпосылки. Код предпосылки к этому часу давно слит и
выкачен, а строка ждёт прогона сценария или взгляда человека. Так цель DK-713
встала на DK-696 и DK-723. Их предпосылки DK-695 и DK-716 стояли в Check со
смешанной приёмкой.

Решение 2 LLD DK-933 переносит снятие ребра на слияние кода предпосылки.
Признак «слита» читает запись «Выкат» в файле задачи и subject коммитов, а
ветку после слияния удаляет shipctl. DK-930 кладёт этот признак в пакет
`internal/merged`.

## Чего хотим

Функция снятости ребра из решения 2 встаёт рядом с признаком «слита» в
internal. На неё переходят ворота `move` на старте из Backlog, ворота
`dep add`, `lintDeps`, `openDeps` у `batch` и `slot` и `dep list --json`.
Последний отдаёт состояние каждого ребра словами «слита», «закрыта» и «ждёт».
Остальные переходы в In progress рёбер не проверяют. `lintDeps` у начатой
строки находит только ребро, которое ворота старта не пропустили бы ни разу.
JSON строки отдаёт неснятые рёбра отдельным полем, и экран дашборда держит
строку по нему.

`shipctl merge` отказывает строке с неснятым ребром и печатает команду
парковки «слияние: X» (решение 3). `shipctl revert X` печатает строки с ребром
на X, чья работа уже в main.

Дока правится в трёх местах. Это п. 4 раздела «Трекинг задач» в
RULES.board.md про смысл маркера, README taskctl и README shipctl. Правка
RULES.board.md проходит стенд obeycheck по скиллу `prompt-test`.

## Развилки

- «парковка вида user»: какой разряд парковки печатает отказ `shipctl merge`, когда ребро держит вид user предпосылки?
  - решает: исполнитель
  - рекомендация: «закрытие: X» у вида user, «слияние: X» у отката и прочих
  - решено исполнителем 2026-09-11: по рекомендации. Код предпосылки вида user уже лежит в main, и парковку «слияние: X» отбила бы проверка причины из DK-932. Событие уже случилось. Отвергнут один разряд «слияние:» на все случаи, как в постановке. У вида user он не проходит `move blocked`. Провал предпосылки до этих ворот не доходит. Раньше его отбивает сломанный прод.
- «вне git»: что отвечает функция, когда признак «слита» не спросить?
  - решает: исполнитель
  - рекомендация: ребро держится, снимает его одно закрытие
  - решено исполнителем 2026-09-11: по рекомендации. Нет git или ветки main, и ребро снимает только архив, как до решения 2. Причина словами «признак «слита» не спрошен». Отвергнута ошибка команды. taskctl работает и на досках без git (стенды, корп-контур). Ворота встали бы на каждом переходе.
- «slot и начатые строки»: проверяет ли slot рёбра у начатых строк?
  - решает: исполнитель
  - рекомендация: да, у всех строк, как прежде
  - решено исполнителем 2026-09-11: по рекомендации. Начатая строка при откаченной предпосылке упрётся в ворота слияния. Слот на неё тратить незачем. Отвергнут пропуск начатых строк в slot. У читателей ребра стало бы два правила вместо одного.
- «одно чтение лога»: как считать снятость десятков рёбер за одну команду?
  - решает: исполнитель
  - рекомендация: книга `merged.Book`, лог main читается один раз на команду
  - решено исполнителем 2026-09-11: по рекомендации. Книга кеширует лог, файлы коммитов, деревья и ответы рёбер. `merged.Task` для `agentctl wait` и хвоста обхода идёт через ту же книгу. Отвергнут вызов `merged.Task` на каждое ребро. `list --json` дашборд зовёт на каждом обновлении. Вызовы git на десятки рёбер копились бы секундами. Отвергнут и лог с `--name-only` одним вызовом, на истории devkit он стоит 0,4 с.
- «поля JSON»: где лежат неснятые рёбра и состояние ребра?
  - решает: исполнитель
  - рекомендация: `held_by` у строки, `edges` у `dep list --json`, `after` остаётся маркером
  - решено исполнителем 2026-09-11: по рекомендации. У `edges` три поля: `id`, `state` словами «слита», «закрыта», «ждёт» и `why`. Строка держится на экране по `held_by`, чипы «после X» рисуются по `after`. Отвергнута подмена смысла `after`. Маркер снимает close. Чип у снятого ребра остаётся дорогой на предпосылку.

## DoD

- Тест на временном репозитории. Слияние X пускает Y в работу, откат X и
  провал X снова держат Y, вид user держит Y до закрытия X. Правка X только в
  доске и файле задачи ребро не снимает, правка в docs/lld снимает.
- `dep list --json` и JSON строки отдают неснятые рёбра, и экран по снятому
  ребру строку не держит.
- `shipctl merge Y` при откаченной X отказывает и называет X.
- Возврат Y из Check при откаченной X проходит, и lint не требует вернуть
  начатую Y в Backlog.
- `shipctl revert X` при слитой Y называет Y.
- RULES.board.md, README taskctl и README shipctl называют новый смысл ребра,
  след стенда obeycheck лежит в файле задачи.
