# DK-998: Тест потолка кеша доски считает запуски, не дождавшись фонового подъёма

## Что происходит

`TestBoardCacheCeiling` в `tools/dashboard/cache_test.go` падает через раз, и
падение ловится общим прогоном `shipctl merge`. Сообщение всегда одно: «заход
после потолка срока стоил 1 запусков taskctl, жду два».

Причина в `projectBoard` (`tools/dashboard/cache.go`). Ответ старше потолка
уезжает на экран как есть, а свежую доску процесс поднимает в фоне, отдельной
горутиной `go s.fly`. Тест ходит на ручку и сразу считает строки журнала
запусков. Успела горутина позвать `taskctl` или нет, решает планировщик, и на
загруженной машине она не успевает.

Так же устроен соседний `TestFeedTailSkipsWholeJournals`: он меряет разницу
холодной ленты в миллисекундах и краснеет на той же нагрузке.

Ловится это на любой ветке, правка предмета не касается. Прогон в одиночку
зелёный, полный прогон при слиянии красный, и слияние встаёт у всех задач
подряд.

## Чего хотим

Тест ждёт события, а не удачи планировщика. Счёт запусков снимается после
того, как фоновый подъём кончился, с внятным потолком ожидания.

## DoD

- `TestBoardCacheCeiling` не зависит от скорости машины, и это показано
  прогоном пакета под нагрузкой;
- порог `TestFeedTailSkipsWholeJournals` пересмотрен той же правкой либо на
  него заведена своя строка с причиной;
- `shipctl merge` проходит общий прогон тестов без повторных заходов.

## Ранг

`50+0+1+5+4 = 60`, P1.

- серьёзность 50. Слияние встаёт у любой задачи, обход это повторный прогон
  вслепую либо подмена команды тестов;
- ценность 0. Пользователь ничего не замечает, чинится статус-кво;
- неопределённость 1. Причина найдена, подход выбран, открыта форма ожидания;
- поправка на баг +5;
- рычаг 4. Зелёный прогон стоит перед каждым слиянием.

## Сценарий проверки

1. Признак, по которому чинили: команда воспроизведения из разбора, до правки
   красила через раз, теперь нет.
```sh
GOWORK=off go test -C tools/dashboard -count 1 -run TestBoardCache ./...
```
Ожидание: `PASS` и `ok`, без `FAIL`.

2. Пакет целиком, трижды подряд, каждый раз своим запуском (не `-count 3`:
   у пары `TestDraftGroomDeathSaid` и `TestBindsWithoutTheLog` в этом пакете
   не убрано глобальное состояние между повторами внутри одного процесса,
   это чужая находка, DK-1001).
```sh
for i in 1 2 3; do GOWORK=off go test -C tools/dashboard -count=1 ./... || exit 1; done
```
Ожидание: `PASS` и `ok` во всех трёх повторах, без `(cached)` в выводе.
`-count=1` держит каждый запуск настоящим прогоном.

3. Тот же пакет под нагрузкой параллельного прогона соседнего пакета.
```sh
GOWORK=off go test -C tools/internal -count=1 ./... >/dev/null 2>&1 & for i in 1 2 3; do GOWORK=off go test -C tools/dashboard -count=1 ./... || exit 1; done; wait
```
Ожидание: `PASS` и `ok` у пакета `dashboard`, без `FAIL` ни в одном из трёх повторов.

## Ход работы

- Найдено при слиянии DK-852: два захода `shipctl merge` подряд упали на этом
  тесте, а одиночный прогон того же теста прошёл трижды.
- Разработка: субагент sonnet/high по вердикту pick (квота: week_all 14%, снимок 27м назад, сдвига нет), 2026-09-15 01:44-01:44.
- Исключение: regcheck (правка только теста, `cache.go` не тронут; краснота
  не про регресс кода, а про то, что тест не ждал события).
- `TestFeedTailSkipsWholeJournals` красит по другой причине, порог секундомера,
  а не потерянное событие. Вынесен своей строкой DK-999.
- Обкатка нашла соседнюю красноту: полный пакет с `-count 3` в одном процессе
  красит `TestDraftGroomDeathSaid` и `TestBindsWithoutTheLog`, к предмету
  DK-998 не относится. Вынесена своей строкой DK-1001, сценарий проверки
  переписан на отдельные запуски вместо `-count 3`.
