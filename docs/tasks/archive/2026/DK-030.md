# DK-030: обоснования из правил в README утилит, в правилах императив

Резидентная часть правил (вес и динамика роста разобраны в
[DK-029](DK-029.md)) состоит не только из самих правил. Изрядная её доля это
объяснение, зачем правило такое: «Поезд выката» занимает 1766 символов и в
основном рассказывает, чем пачка выгоднее одиночных выкатов, «Нужна ли
фичеветка» 598 при правиле в две строки. Человеку это стоит прочитать один
раз, а платится оно каждой сессией и каждым субагентом.

Раскладка по разделам, символы:

```
RULES.md          3486  31%  Код и тексты
                  1918  17%  Git
                  1475  13%  Документация изменений
                  1310  12%  Фича доезжает до пользователя
                  1216  11%  Тесты обязательны
RULES.board.md    7221  45%  Ветки, ревью и деплой
                  8299  52%  Трекинг задач
```

Самые тяжёлые пункты доски: «Выбор модели» 2045, «Поезд выката» 1766, «Выкат»
1102, «Файл задачи» 945, «Инициатива слияния» 887, «Инструкция проверки» 876.

Куда переносить, понятно: README утилит уже читаются по надобности и в
контексте не лежат, а `agentctl/README.md` на 361 строку показывает, что место
для подробного «почему» там есть. Отдельная часть обоснований и вовсе
дублирует то, что утилита не даст сделать неправильно: `shipctl merge` сам не
пустит слияние с открытыми замечаниями, и пересказ этого в правилах резидентен
зря.

Чего делать нельзя. Раздел «Код и тексты» трогать в эту сторону нельзя, и это
не вопрос объёма. У него нет триггера: когда станет ясно, что правило про
символы и мимикрию пора подгрузить, текст уже написан. Такие правила работают,
только пока лежат в контексте, и глобальный `CLAUDE.md` не зря помечает их
«часто нарушается» даже в резидентном виде. То же касается запрета на следы
ассистента в git-истории.

Честная оговорка про сам приём: для модели «почему» не чистый жир. Обоснование
помогает вести себя разумно в случаях, которые правило буквально не покрывает,
поэтому резать надо пересказ механики и повторы, а не всякое объяснение подряд.
Прикидка выигрыша это 30-40% `RULES.board.md`, но проверять её надо не на глаз:
после правки прогнать типовой сценарий (взять задачу, слить, выкатить) и
убедиться, что решения не поехали.

## Ход работы

- Исполнение: субагент opus/high по вердикту pick, 2026-07-31.
- Обоснования уехали в README тех утилит, которые этот кусок правил и
  исполняют. В `shipctl/README.md`: на чём держится очередь выката (прод один,
  источник поломки после одиночного выката очевиден, выкаченная задача от
  бескодовой отличается по git, а не по типу на доске, и заранее проверять
  очередь не надо), зачем поезд (фиксированная обвязка платится один раз) и
  откуда взялся потолок в 3-5 задач, разбор несерверного выката (сборка и
  подпись приложения, разрез на автоматизируемое и физически ручное,
  машинно-читаемый идентификатор билда для агентской проверки). В
  `taskctl/README.md`: экономия контекста на `list` и `show`, зачем архив
  (живой файл не пухнет, размер привязан к открытой работе), почему
  LLD-задаче в бэклоге файл не заводится.
- В `agentctl/README.md` не добавлено ни строки. Всё, что снято с п. 10
  (корректор по остатку лимитов, пол effort у sonnet, ярус ревьювера, статус
  записи `--record` как самоотчёта), там уже лежало подробнее, чем в правилах,
  и правка просто убрала резидентную копию.
- Пересказ предусловий, которые утилита и так держит, выкинут после проверки
  по коду: «shipctl merge не пустит слияние с открытыми замечаниями» стоит в

  тестами `ops_test.go` и `worktree_test.go`. Само правило (у каждого
  замечания фиксируется исход, ревью гоняется до чистого прохода) осталось,
  ушёл только пересказ отказа.
- `RULES.md` тронут одним буллетом раздела «Тесты обязательны»: добавлена
  ссылка на `regcheck/README.md` и режим `--inline`, снята финальная фраза,
  повторяющая выделенное правило про краснеющий тест. Заодно ушла неточность:
  «где regcheck не применим (тест и правка в одном файле)» перестало быть
  правдой, когда появился `--inline`. Разделы «Код и тексты» и «Git» не
  тронуты вовсе, они сверены с базой побайтно (шаг 3 проверки).
- Цифры (символы, замер `wc -m`, база ee9133f). `RULES.md` 11209 -> 11153.
  `RULES.board.md` 16623 -> 11987, это -28%. По разделам: «Ветки, ревью и
  деплой» 7445 -> 4901 (-34%), «Трекинг задач» 8774 -> 6682 (-24%). Самые
  тяжёлые пункты: «Выбор модели» 2524 -> 1536, «Поезд выката» 1769 -> 994,
  «Выкат» 1105 -> 599, «Файл задачи» 948 -> 656, «Инициатива слияния» 890 ->
  601.
- До ориентира в 30-40% доска не дотянула, и дожимать её было нечем.
  В «Трекинг задач» почти всё оставшееся это императив: список «когда
  обновлять» (509), инструкция проверки (861), формат строки и файла задачи.
  Резать там пришлось бы уже сами правила, а не объяснения к ним.
- Прогон сценариев по новому тексту (п. 6 постановки). «Взять в работу ->
  слить -> выкатить -> закрыть»: pick с `--record` и делегирование (п. 10),
  перевод в In progress (п. 5), ветка и worktree через `shipctl start`
  (п. 1), ревью вердиктом с закрытыми исходами (п. 2 и 3), слияние

  «Трекинг задач»), провал по п. 7. Ни один шаг не потерял ни утилиты, ни
  условия. «Выбрать исполнителя и ревьювера»: п. 10 называет команду, обе оси,
  способ применения (модель параметром спавна, effort через определение) и
  роль ревьювера.
- Одно место в этом прогоне пришлось вернуть императивом. После первой правки
  из п. 10 выпало, какое определение агента брать под вердикт: набор
  `devkit/agents` назван, а соответствие уровню осталось только в README.
  Вписано `exec-<effort>` и `review-<effort>` прямо в правило.
- Где сознательно оставлено объяснение. «Свою модель сессия сменить не может,
  поэтому вердикт применяется делегированием» держит весь способ применения
  вердикта, без него команда выглядит справочной. В п. 9 «Синхронизации доски»

  В п. 6 «Инструкции проверки» осталась оговорка про баг («иначе проверка
  покажет только, что код поменялся»): она задаёт планку сценария, а не
  хвалит правило.

## Проверка

Сценарий агентский: все шаги выполнимы с машины агента, итог объективный (коды
возврата, конкретные числа и строки вывода), ничего не меняется ни на проде,
ни на машине. Кода на проде задача не трогает вовсе, правка документационная.

1. Объём правил до и после. База это коммит ee9133f, последний перед веткой:

   ```sh
   cd ~/projects/devkit
   LC_ALL=en_US.UTF-8 wc -m RULES.md RULES.board.md
   git show ee9133f:RULES.board.md | LC_ALL=en_US.UTF-8 wc -m
   ```

   Ожидается 11153 у `RULES.md` и 11987 у `RULES.board.md` против 16623 в
   базе, то есть доска похудела на 28%.

2. Правила ссылаются на живые README, а не на пропавшие файлы:

   ```sh
   cd ~/projects/devkit
   for f in shipctl/README.md taskctl/README.md agentctl/README.md \
            regcheck/README.md hooks/README.md RANKING.md; do
     test -f "$f" || echo "нет $f"
   done; echo "код $?"
   ```

   Ожидается пустой вывод и код 0: каждый упомянутый в правилах файл на месте.

3. Разделы без триггера подгрузки не тронуты. Сравнение с базой побайтно:

   ```sh
   cd ~/projects/devkit && python3 - <<'PY'
   import subprocess
   def sec(text, name):
       out, on = [], False
       for ln in text.splitlines(True):
           if ln.startswith('## '):
               on = ln[3:].strip() == name
           if on:
               out.append(ln)
       return ''.join(out)
   base = subprocess.run(['git', 'show', 'ee9133f:RULES.md'],
                         capture_output=True, text=True).stdout
   cur = open('RULES.md', encoding='utf-8').read()
   for name in ('Код и тексты', 'Git'):
       print(name, sec(base, name) == sec(cur, name))
   PY
   ```

   Ожидается `Код и тексты True` и `Git True`.

4. Обязательные шаги конвейера из правил не пропали:

   ```sh
   cd ~/projects/devkit
   for s in "shipctl start" "shipctl merge" "shipctl ship" "shipctl revert" \
            "taskctl close" "taskctl review" "taskctl lint" "agentctl pick" \
            "--role review" "--record" "--train" autonomous; do
     printf '%s: %s\n' "$s" "$(grep -c -- "$s" RULES.board.md)"
   done
   ```

   Ожидается ненулевой счётчик у каждой строки.

5. Тесты утилит и самопроверки:

   ```sh
   cd ~/projects/devkit
   for m in taskctl shipctl agentctl regcheck; do (cd $m && go test ./...); done
   sh devkitctl/test.sh; sh hooks/test.sh
   ```

   Ожидается четыре `ok`, «devkitctl в порядке» и «хуки в порядке».

6. Символы в изменённых файлах:

   ```sh
   cd ~/projects/devkit
   python3 hooks/check-symbols.py RULES.md RULES.board.md shipctl/README.md \
     taskctl/README.md docs/tasks/DK-030.md; echo "код $?"
   ```

   Ожидается код 0 без находок.
