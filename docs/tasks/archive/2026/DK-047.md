# DK-047: клик по уведомлению переключает в окно сессии: отправитель terminal-notifier на macOS

Уведомления из [DK-034](DK-034.md) приходят, но клик по баннеру
открывает Finder с директорией скриптов, а не окно позвавшей сессии. Причина в
отправителе: `display notification` постит уведомление от имени Script Editor,
своего обработчика клика у команды нет вовсе, и клик активирует Script Editor.
Смена атрибуции через `tell application id "com.microsoft.VSCode" to display
notification` на этой macOS не работает, проверено живьём: код возврата 0,
баннер приходит, иконка по-прежнему от Script Editor.

Заголовок с именем рабочего дерева проблему смягчает (видно, какая сессия
зовёт), но переключаться всё равно приходится руками, а параллельных сессий на
машине несколько.

## Что согласовано с пользователем

1. Чиним через `terminal-notifier`: она шлёт от своего имени и берёт цель
   перехода прямо в аргументах уведомления, состояние держать не надо.
   Зависимость мягкая: не нашлась, значит уведомления идут как сейчас, через
   `osascript`, только без клика.
2. Клик это необязательная способность бэкенда, а не общее свойство
   уведомителя. Кроссплатформенного пути тут нет: на Linux кнопки `notify-send`
   требуют процесса, дожившего до клика, и поддержки со стороны демона, на
   Windows это protocol activation у тостов. Обе платформы остаются с нынешним
   поведением, задача про macOS.

## Решение

1. Цель перехода это необязательное поле уведомления рядом с заголовком и
   телом. Собирается она из `cwd` события: `vscode://file/<путь>` открывает
   и поднимает окно VS Code с этим рабочим деревом, а у worktree задачи в
   имени лежит её ID, так что попадаем именно в ту сессию, что позвала.
   Шаблон перебивается переменной `DEVKIT_NOTIFY_OPEN` с подстановкой `{cwd}`
   (кто работает не в VS Code, ставит своё), пустое значение выключает клик.
2. Бэкенд объявляет, умеет ли он клик. `terminal-notifier` умеет и получает
   `-open <цель>`, `osascript` не умеет и цель просто игнорирует. Выбор
   бэкенда на macOS становится таким: есть `terminal-notifier` в PATH, берём
   её, иначе `osascript`. `DEVKIT_NOTIFY_BACKEND` перебивает выбор, как и
   сейчас.
3. Журнал пишет не только бэкенд и код возврата, но и была ли у уведомления
   цель перехода. Жалоба «клик не работает» тогда разбирается по факту: слали
   с целью или без, и каким отправителем.
4. Доктор проверяет, чем на этой платформе слать, и с этой задачи различает
   два случая: слать нечем вовсе (находка, как сейчас) и слать есть чем, но
   клик не поддержан (находка с командой `brew install terminal-notifier` и
   пояснением, что без неё уведомления работают, а переход по клику нет).
   Вторая находка не должна выглядеть поломкой: это предложение, а не отказ.
5. Тесты. Юнитами сборка цели из `cwd` (в том числе путь с пробелами и
   кириллицей), подстановка своего шаблона, пустой `DEVKIT_NOTIFY_OPEN`,
   выбор бэкенда при наличии и отсутствии `terminal-notifier` в PATH. В
   `hooks/test.sh` прогон целиком со стабом вместо `terminal-notifier`: стаб
   пишет свои аргументы в файл, тест проверяет, что цель уехала в `-open`
   ровно та, что ждали, и что при откате на `osascript` цели в команде нет.
   Мутации, на которых должен краснеть хоть один тест: цель собрана не из
   `cwd` (все сессии ведут в одно место), потерянный флаг `-open`,
   `terminal-notifier` не предпочитается `osascript`, снятое действие
   `DEVKIT_NOTIFY_OPEN`, пропавшая пометка цели в журнале.

## Дока

Раздел про уведомления в `hooks/README.md` пополняется частью про клик (что
ставится, как выбирается цель, чем перебивается, почему без установки всё
работает без перехода), `devkitctl/README.md` получает новую находку доктора.

## Открытые вопросы к исполнению

- Доступна ли хуку переменная `TERM_PROGRAM` (в окружении инструментов сессии
  её не видно, но у хука окружение своё). Если доступна, цель по умолчанию
  стоит выбирать по ней: `vscode` это `vscode://file/<путь>`, Terminal.app и
  iTerm это активация самого терминала, и тогда переменная `DEVKIT_NOTIFY_OPEN`
  нужна только на нестандартный случай.
- Что делает `-open vscode://file/<путь>`, когда окно с этим деревом уже
  открыто: поднимает существующее или заводит второе. Проверить живьём на
  worktree задачи, второе окно на каждое уведомление это хуже, чем нынешний
  Finder.
- Годится ли `-activate <bundle id>` как запасной путь, когда цель собрать не
  из чего (`cwd` в событии пуст).

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick, 2026-08-01. Делегирование
  пользователь отклонил, задачу закрыла сама сессия.
- `hooks/notify.py`: цель перехода собирается `click_target`, бэкенд объявляет
  поддержку клика (`supports_click`), на macOS `terminal-notifier` идёт впереди
  `osascript`. Журнал пишет цель, которая реально уехала: бэкенд без клика её
  не получает, и в строке стоит прочерк.
- `devkitctl doctor`: находка про клик мимо окна сессии с командой установки.
  Она мягкая и появляется только там, где слать есть чем, но выбран
  `osascript`; своя команда в `DEVKIT_NOTIFY_BACKEND` под неё не попадает.
- Тесты: юниты на сборку цели (пути с пробелами и кириллицей, свой шаблон,
  пустой шаблон, терминалы, предпочтение отправителя, аргументы каждого
  бэкенда), прогон в `hooks/test.sh` со стабом `terminal-notifier`, случаи
  доктора в `devkitctl/test.sh` под `uname = Darwin`.
- Мутации прогнаны на копии файла, на каждой краснеет хоть один тест: цель не
  из `cwd`, потерянный `-open`, снятое предпочтение `terminal-notifier`,
  нечитаемая `DEVKIT_NOTIFY_OPEN`, цель мимо журнала, цель мимо отправителя,
  цель уходит бэкенду без клика, выпавшая находка доктора.

### Открытые вопросы, чем кончились

- `TERM_PROGRAM` у сессии из расширения VS Code нет вовсе: она живёт не в
  терминале, а в extension host. Снято с живого процесса сессии (`ps eww`), там
  есть `VSCODE_PID` и `CLAUDE_CODE_ENTRYPOINT=claude-vscode`, по ним VS Code и
  узнаётся. `TERM_PROGRAM` остаётся для случая, когда агент запущен из
  Terminal.app или iTerm.
- `open vscode://file/<путь>` на уже открытом дереве поднимает существующее
  окно, второго не заводит. Проверено на worktree задачи: девять окон до, девять
  после, нужное вышло вперёд (`System Events`, счёт и список окон процесса
  Code).
- `-activate <bundle id>` годится запасным путём и подключён: он поднимает
  приложение, когда цели из чего собирать нет (`cwd` пуст) и когда работа идёт
  в терминале, где окно по дереву не найти.

## Сценарий проверки

Агентский, кроме шага 5. Сам клик по баннеру агент с машины не выполнит, это
проверяет пользователь, а всё остальное видно объективно: аргументы, уехавшие
отправителю, строки журнала и находки доктора.

1. Тесты: `sh hooks/test.sh` печатает «хуки в порядке», `python3
   hooks/notify_test.py` завершается кодом 0, `sh devkitctl/test.sh` печатает
   «devkitctl в порядке».

2. Самопроверка на этой машине говорит и про отправителя, и про цель:

```sh
python3 hooks/notify.py --self-test; echo "код возврата: $?"
tail -1 ~/.devkit/notify.log
```

   Ожидается код возврата 0, строки `послано через terminal-notifier, код
   возврата 0` и `клик по баннеру ведёт в vscode://file/<путь до devkit>`, в
   журнале та же цель рядом с `код возврата: 0`.

3. Цель ведёт в дерево позвавшей сессии, а не в общее место. На временном HOME
   и подставном отправителе, живой журнал не трогается:

```sh
h=$(mktemp -d); d=$(mktemp -d)
printf '#!/bin/sh\nprintf "%%s\\n" "$*" > %s/args\n' "$d" > "$d/terminal-notifier"
chmod +x "$d/terminal-notifier"
printf '{"hook_event_name":"Notification","notification_type":"permission_prompt","session_id":"s1","cwd":"/p/devkit-dk-047","message":"проба"}' |
  HOME="$h" CLAUDE_CODE_ENTRYPOINT=claude-vscode DEVKIT_NOTIFY_BACKEND="$d/terminal-notifier" \
  python3 hooks/notify.py --hook claude-code
cat "$d/args"; grep -c 'цель vscode://file/p/devkit-dk-047' "$h/.devkit/notify.log"
```

   В аргументах ожидается `-open vscode://file/p/devkit-dk-047`, в журнале одна
   такая строка.

4. Доктор на машине без terminal-notifier предлагает её поставить:

```sh
d=$(mktemp -d); printf '#!/bin/sh\nexit 0\n' > "$d/osascript"; chmod +x "$d/osascript"
DEVKIT_NOTIFY_BACKEND="$d/osascript" python3 devkitctl/devkitctl.py doctor 2>&1 | grep 'клик по баннеру'
```

   Ожидается находка про клик мимо окна сессии с командой `brew install
   terminal-notifier`. Без переменной (на этой машине terminal-notifier стоит)
   находки нет.

5. Пользовательский шаг: дождаться настоящего уведомления от сессии и кликнуть
   по баннеру. Ожидается переход в окно VS Code с рабочим деревом той сессии,
   которая позвала, а не Finder с папкой скриптов.

## Ревью

- click_target: проверка isinstance(cwd, str) не покрыта тестом. Нужен юнит на click_target с cwd не строкой (например, cwd=7 или cwd=['/a']), который ловит именно эту мутацию.: исправлено, юнит test_cwd_of_wrong_type на cwd числом, списком и со своим шаблоном плюс случай в hooks/test.sh; на мутации 'cwd or пустая строка' краснеют и он, и прогон
