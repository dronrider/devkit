# DK-106: Хуки вместо прозы: разбор в текстах находок, тесты в pre-commit, pre-push на запрет пуша

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick (потолок цели: pro, вердикт и так не выше; квота: week_all 15%, снимок 1ч 49м назад, протух, сдвига нет), 2026-08-04.
- Постановка это раздел «E, хуки» дизайна
  [DK-100](../../../lld/DK-100-context-tree.md) плюс две находки первого прохода
  стенда, записанные там же (разбор в [DK-104](DK-104.md)).
- Ревью: субагент sonnet/high по вердикту pick (потолок цели: pro, вердикт и так не выше; квота: week_all 16%, снимок 11м назад, сдвига нет), 2026-08-04.

## Что сделано

Четыре правила, которые до сих пор держались прозой правил, получили рубеж.

- Разбор «как переписать» переехал в тексты находок. `check-symbols.py`
  подбирает его по видам символов, которые встретились (перечень `ADVICE`), и
  печатает и в CLI, и в режиме `--hook`; `check-commit.py` носит разбор при
  каждой своей находке (след ассистента, body, чужой префикс). Резидент теперь
  может ограничиться запретом: чем переписывать, агент узнаёт ровно тогда,
  когда ошибся.
- Правка кода без единого теста в коммите отбивается `pre-commit` через новый
  `check-tests.py`. Обход осознанный и узкий: `DEVKIT_NO_TESTS=1` пропускает
  только эту проверку, остальные рубежи остаются.
- Пуш из сессии агента отбивает новый `pre-push`. Разрешение выдают утилиты
  devkit: `taskctl` и `shipctl` ставят `DEVKIT_PUSH_OK=1` в окружение своего
  `git push` и только его. Ручной пуш пользователя рубеж не видит, переменной
  сессии агента у него нет.
- `check-sensitive.py` перестал верить, что `local-docs` заигнорен: на записи
  файла туда он спрашивает git, а в `pre-commit` находкой считается сам факт,
  что файл из `local-docs` попал в коммит.

## Решения

- Проверка тестов вынесена отдельным файлом, а не написана в `pre-commit`: у
  неё своя таблица кода и тестов, и таблица эта будет пополняться. Смотрятся
  имена файлов коммита, а не содержимое, и проверка нарочно грубая. Она ловит
  отсутствие теста, а качество и красноту оставляет `regcheck`, о чём говорит и
  текст находки.
- Файл без расширения читается по шебангу: сами хуки и утилиты devkit живут
  так, и без этого правка `pre-commit` за код бы не считалась.
- Фикстура в `testdata` идёт за тест: правка, приехавшая с новой фикстурой,
  покрытием закрыта, а требовать рядом ещё и `*_test.*` значит красить рубеж на
  ровном месте.
- Разрешение на пуш выдаёт не только shipctl, как сказано в дизайне, но и
  taskctl: у коммита доски свой путь, `taskctl ... --push`, и без переменной
  рубеж отбивал бы ровно то исключение, ради которого он написан.
- Признак сессии агента в `pre-push` не один `CLAUDECODE`, а короткий перечень:
  переменных у харнеса бывает несколько, и рубеж, знающий одну, молча
  пропускает пуш из соседнего.
- Сценарий стенда «завести новую подсистему» (дока в той же ветке) эта задача
  не закрывает. DK-104 разобрала его отдельно: механизации на него не
  планировалось, ловит такое ревью, и придумывать рубеж на дифф ветки тут не
  стал.

## Стенд послушания

Прогнать не на чем: бинаря `claude` в PATH этой машины нет вовсе, а `obeycheck`
без него не стартует. Красный на обеих раскладках сценарий `02-bug-fix` (0/5 и
0/5, причины «в коммите нет файла теста» и «зелёного прогона regcheck в журнале
нет») закрывается механикой, а не текстом, и проверяется прямыми прогонами
`pre-commit` из сценария ниже. Перегон стенда остаётся за диспетчером цели,
когда CLI вернётся на машину.

## Тесты

- `hooks/test.sh`: разбор в находках `check-symbols` (тире, стрелка, кавычки,
  прочий символ) и `check-commit`, `check-tests.py` на коде без теста, коде с
  тестом, доке, фикстуре в `testdata` и файле с шебангом, `pre-commit` красный
  на коммите с кодом без теста и зелёный с тестом, обход `DEVKIT_NO_TESTS` без
  выключения символов, `pre-push` на трёх окружениях, `check-sensitive` на
  `local-docs` заигноренном и нет.
- `taskctl`, `shipctl`: `TestPushEnv`, разрешение едет только с самим пушем, а
  родительское окружение не теряется.
- Краснота проверена прогоном: `regcheck --tests hooks/test.sh -- sh
  hooks/test.sh` и по `TestPushEnv` в обеих утилитах, все три сказали
  «регрессия закрыта».

## Сценарий проверки

Агентский: каждый шаг выполним с машины агента, итог проверяется кодом возврата
или строкой вывода, прод шаги не трогают. Гоняется в чекауте devkit после
выката.

1. Тесты проекта зелёные:

   ```sh
   cd ~/projects/devkit && export GOWORK=off
   for d in taskctl shipctl agentctl regcheck obeycheck; do (cd "$d" && go test ./...) || exit 1; done \
     && sh hooks/test.sh && sh devkitctl/test.sh && sh skills/goal-loop/test.sh
   ```

   Ждём код 0 и строку `хуки в порядке`. `GOWORK=off` тут потому, что в
   `~/go.work` машины перечислены чужие проекты, а devkit туда не вписан, и без
   этого `go test ./...` отвечает `directory prefix . does not contain modules
   listed in go.work` на зелёном коде (разбор в черновике DK-115).

2. Рубеж тестов краснеет на правке кода без теста и зеленеет с тестом:

   ```sh
   cd ~/projects/devkit && python3 hooks/check-tests.py taskctl/ops.go; echo "без теста: $?"
   python3 hooks/check-tests.py taskctl/ops.go taskctl/ops_test.go; echo "с тестом: $?"
   ```

   Ждём `без теста: 1` с находкой, где названы `regcheck` и `DEVKIT_NO_TESTS`,
   и `с тестом: 0`.

3. Пуш из сессии агента отбивается, а разрешение утилит проходит:

   ```sh
   cd ~/projects/devkit
   CLAUDECODE=1 hooks/pre-push origin git@example.com:x.git </dev/null; echo "сессия: $?"
   CLAUDECODE=1 DEVKIT_PUSH_OK=1 hooks/pre-push origin git@example.com:x.git </dev/null; echo "разрешение: $?"
   env -u CLAUDECODE -u CLAUDE_CODE_ENTRYPOINT -u CURSOR_AGENT hooks/pre-push origin git@example.com:x.git </dev/null; echo "руками: $?"
   ```

   Ждём `сессия: 1` с разбором, где названы `taskctl` и `DEVKIT_PUSH_OK`, а
   дальше `разрешение: 0` и `руками: 0`.

4. Утилиты это разрешение выдают, и только на пуше:

   ```sh
   cd ~/projects/devkit && (cd taskctl && go test ./... -run TestPushEnv) && (cd shipctl && go test ./... -run TestPushEnv)
   ```

   Ждём код 0 и два `ok`.

5. Находка про символы несёт разбор, а не только запрет:

   ```sh
   cd ~/projects/devkit && printf 'текст с тире \342\200\224 вот\n' | python3 hooks/check-symbols.py --stdin
   ```

   Ждём код 1, а под находкой строку `как переписать:` и разбор про длинное
   тире.

6. `local-docs` не проезжает в коммит:

   ```sh
   cd ~/projects/devkit && printf 'local-docs/hosts.md:1:строка\n' | python3 hooks/check-sensitive.py --diff
   ```

   Ждём код 1 и находку со словом `gitignore`.

7. Рубеж стоит в самом devkit без ручных шагов (git-хуки подключены через
   `core.hooksPath`, новый файл подхватывается тем же путём):

   ```sh
   cd ~/projects/devkit && git config core.hooksPath && [ -x hooks/pre-push ]; echo "хук на месте: $?"
   ```

   Ждём путь до `hooks` и `хук на месте: 0`.

Шаги 1-7 обкатаны в дереве задачи до перевода в Check. Прогон стенда послушания
в сценарий не входит: `claude` вернулся в PATH машины уже после исполнения
задачи, и перегон стенда остаётся за витком цели, а не за этим сценарием.

Рубеж пуша поймал первым делом сам выкат задачи. `shipctl merge` слил ветку и
упёрся в собственный новый `pre-push`: хуки в чекауте уже были новые, а бинарь
`shipctl` в PATH старый, без `DEVKIT_PUSH_OK`. Круг разрывается пересборкой
бинарей до выката, дальше `shipctl ship` запушил и выкатил сам. Ловушка эта
одноразовая, она живёт ровно в том слиянии, которое сам рубеж и приносит, но
сказать про неё стоит: та же пара «новые хуки, старый бинарь» повторится на
любой машине, куда правка приедет пуллом без пересборки.

Шаг 1 на живой машине потребовал `GOWORK=off`: в `~/go.work` перечислены чужие
проекты, devkit туда не вписан, и `go test ./...` падает на зелёном коде. Тем
же упёрлось слияние (`shipctl merge` сказал «тесты после ребейза красные»),
починено в машинном `.devkit/deploy.local`, широкий разбор ждёт в черновике
DK-115.
