# DK-122: отказ «конвейер занят» не говорит, кто держит замок

записан 2026-08-05

При заходе на `shipctl start` (2026-08-05, DK-121) команда отказала «конвейер
занят», а файл `.devkit/ship.lock` был нулевого размера и с временем правки
трёхдневной давности. Живой `merge` в соседней сессии шёл, но узнать это
удалось только через `pgrep` по `shipctl`.

## Что происходит

Замок целиком в `shipctl/lock.go`: файл открывается и запирается `flock`, в
него не пишется ничего, ни pid, ни ID задачи, ни время старта. Отказ поэтому
безымянный, и владельца ищут мимо утилиты.

При разборе 2026-08-05 вторая половина черновика сузилась. «Брошенный от живого
не отличить» буквально неверно: замок держится дескриптором, и ядро снимает его
при завершении процесса, включая аварийное, так что отказ всегда означает
живого владельца, а старый `mtime` пустого файла это обманка, а не причина.
Ручного `rm` случай не требует, снимать протухшее нечего.

Открытым остаётся ровно то, что отказ молчит про владельца. Образец лежит в том
же репозитории: замок оболочки цели (`skills/goal-loop/goal-run.sh`) пишет pid,
снимает мёртвый сам, и отказ там называет, кто держит.

## Чего хотим

Замок пишет владельца: pid, ID задачи, время старта. Отказ печатает их, и
по нему видно, ждать ли (идёт чужое слияние минуту назад) или разбираться
(процесс висит с прошлой ночи). Про `mtime` пустого файла в отказе сказать
прямо, чтобы следующий читатель на него не купился.

## DoD

`shipctl start` при занятом конвейере печатает, кто держит замок и с какого
времени. Проверяется на временном репозитории: запустить долгую команду под
замком, второй вызов обязан назвать pid и время первой.

Сам замок больше не пишется и остаётся пустым даже под git. Это снимает причину возврата: TestShipDrainRaisesCheckRunForTrain ловил грязь дерева и отказ checkout поверх изменённого замка.

На торможенной записи lockBusy деградирует к «неназвавшийся» тем же путём, что и раньше. lockBusy зовётся только при занятом flock. Протухший owner-файл при свободном замке поэтому не выдаётся за живого держателя. Это проверено вручную на временном репозитории: подложен ship.lock.owner с мёртвым pid без flock, merge взял замок молча, перезаписал файл своим держателем и убрал его при завершении.

  Тесты: go build чистый. TestLock*, TestAcquireLockKeepsTreeClean, TestTrackedLockNotDirtyTree, TestMergeSurvivesTrackedLock и TestShipDrainRaisesCheckRunForTrain зелёные (33s). regcheck по tools/shipctl/lock_holder_test.go краснеет на main и зелёный на ветке. devkitctl test_16_machine_ignore_paths зелёный: проверен глоб .devkit/ship.lock*, живое имя .owner, старые проекты без записи и doctor --fix. ## Сценарий проверки

Прогон идёт на временном репозитории. Живой замок devkit трогать нельзя, через
него идут чужие слияния. Держателем выступает настоящий `shipctl merge` с
долгой командой тестов, второй запуск ловит отказ. Весь прогон идёт одним
шагом и одной строкой: переменные и фоновые процессы между шагами обкатки не
живут, а три проверки читаются по порядку вывода.

```sh
set -u; BASE=$(mktemp -d /tmp/dk122-XXXX); WORK="$BASE/repo"; mkdir -p "$WORK"; cd "$WORK"; git init -q -b main && git config user.email t@t && git config user.name t; taskctl init --prefix XR --name "Проверка DK-122"; taskctl add --title "Первая правка" --type task --rank "0+1+1+0+1" --accept agent; taskctl add --title "Вторая правка" --type task --rank "0+1+1+0+1" --accept agent; mkdir -p .devkit; printf '.devkit/\n' > .gitignore; printf 'old\n' > code.txt; for t in XR-001 XR-002; do printf '\n## Сценарий проверки\n\n1. Шаг проверки.\n\n## Проверка\n\n- Исключение: обкатка (синтетическая строка сценария)\n' >> docs/tasks/$t.md; done; git add -A && git commit -qm seed; shipctl start XR-001; cd "$BASE/repo-xr-001" && printf 'new\n' > code.txt && printf 'def test_x(): pass\n' > code_test.py && git add -A && git commit -qm "fix: XR-001 правка"; taskctl -C "$BASE/repo-xr-001" review level XR-001 1 "синтетика" >/dev/null; taskctl -C "$BASE/repo-xr-001" review clean XR-001 "без замечаний" >/dev/null; git -C "$BASE/repo-xr-001" add -A && git -C "$BASE/repo-xr-001" commit -qm "docs(tasks): XR-001 ревью" || true; cd "$WORK"; shipctl start XR-002; cd "$BASE/repo-xr-002" && printf 'ещё\n' > other.txt && printf 'def test_y(): pass\n' > other_test.py && git add -A && git commit -qm "fix: XR-002 правка"; taskctl -C "$BASE/repo-xr-002" review level XR-002 1 "синтетика" >/dev/null; taskctl -C "$BASE/repo-xr-002" review clean XR-002 "без замечаний" >/dev/null; git -C "$BASE/repo-xr-002" add -A && git -C "$BASE/repo-xr-002" commit -qm "docs(tasks): XR-002 ревью" || true; cd "$WORK"; shipctl merge XR-001 --test "sleep 40" > "$BASE/first.log" 2>&1 & n=0; until [ -s .devkit/ship.lock.owner ] || [ $n -ge 200 ]; do sleep 0.3; n=$((n+1)); done; cat .devkit/ship.lock.owner; git status --porcelain --untracked-files=no; shipctl merge XR-002 --test true; echo "exit=$?"; wait; ls .devkit/ship.lock.owner; echo "ls=$?"; wc -c < .devkit/ship.lock; python3 -c "import fcntl,sys,time;f=open('$WORK/.devkit/ship.lock','w');fcntl.flock(f,fcntl.LOCK_EX);sys.stderr.write('held\n');sys.stderr.flush();time.sleep(20)" 2>"$BASE/held" & LOCKPID=$!; n=0; until grep -q held "$BASE/held" || [ $n -ge 100 ]; do sleep 0.2; n=$((n+1)); done; shipctl merge XR-002 --test true; echo "exit=$?"; kill $LOCKPID; rm -rf "$BASE"
```

Ожидаемый итог по шагам:

1. `cat` печатает строку держателя вида
   `pid=<число>	команда=merge XR-001	взят=<время>`, а второй `merge` падает с
   `exit=1` и строкой «конвейер занят: замок .devkit/ship.lock держит merge
   XR-001, pid <то же число>, взят <дата и время> (меньше минуты назад); ...».
   Pid из отказа совпадает с pid из файла, время захвата свежее. `git status`
   при этом молчит: держатель дерево не грязнит.
2. `ls` не находит файла держателя (`ls=1`), `wc -c` печатает `0`. Первый
   `merge` закончил, свой файл убрал, а замок остался пустым.
3. Отказ говорит «держит неназвавшийся запуск shipctl (замок взят сборкой до
   DK-122 либо запись держателя ещё не легла)», `exit=1`. Чужой замок без
   записи это не поломка и не выдуманный pid.
