# DK-132: taskctl: исходы разбора черновика, команды defer, attach и drop

Задача цели DK-128 (`docs/tasks/DK-128.md`), заведена дорезкой по составу
правок дизайна DK-129. Разобранный черновик сегодня не оставляет следа: у
`taskctl draft` есть только запись новой мысли и `draft list`, а оформление
везёт `add --id`. Черновик, который после разбора оформлять рано, приходится
оставлять как есть, и следующий заход разбирает его с нуля.

Дизайн назвал четыре исхода разбора: строка на доске (`add --id`, уже есть),
приписка к стоящей строке, пометка с причиной, удаление протухшего. Три
последних кода не имеют, эта задача их заводит. Решения и доводы в
`docs/lld/DK-129-groom-process.md`, разделы «Решение 2» и «Решение 4», состав
работы в разделе «Разбивка на задачи».

## Что сделать

- `draft defer <ID> "причина"` и `draft defer <ID> --clear`: пометка разделом
  «Грумминг» в самом файле черновика;
- `draft attach <ID> <TASK-ID>`: текст черновика уезжает в файл задачи разделом
  вида `## Из черновика <ID>`, черновик удаляется. Счёт трогаемых путей по
  прецеденту
  `ensureTaskFile` разобран в решении 4;
- `draft drop <ID> --reason "..."`: удаление протухшего, причина живёт
  сообщением коммита;
- узнавание подкоманд в разборе аргументов `case "draft"` точным совпадением
  первого позиционного аргумента, как сегодня узнаётся `list`. Стык с
  черновиком DK-099 (тот переносит чтение текста за `fs.Parse`) описан там же;
- дата записи строкой в файле черновика, `loadDrafts` читает её, фолбэк на
  `ModTime` для старых черновиков;
- показ пометки в `draft list` и в хвосте `list`;
- рубеж доски на новых командах: из линкованного worktree они отказывают, как
  отказывает `draft`.

## Границы

Текст скилла `board-groom` не трогается, это DK-130. Разбор самого накопителя
идёт на DK-131.

## DoD

Команды работают, `go test ./...` в `taskctl` зелёный, раздел про `draft` в
`taskctl/README.md` описывает подкоманды, узнавание аргументов, дату записи и
пометку в выводе.

## Сценарий проверки

Агентский, на синтетической доске во временном каталоге: завести черновик,
пометить его `draft defer` с причиной и увидеть пометку в `draft list`, снять
`--clear`, приписать другой черновик к стоящей строке через `draft attach` и
увидеть его текст в файле задачи, удалить третий через `draft drop --reason`.
Отдельно: `taskctl draft "текст"` новыми подкомандами не сломан, и из
линкованного worktree новые команды отказывают.

## Ход работы

- Исполнение: субагент opus/medium по вердикту pick (квота: week_all 26%, снимок 35м назад, сдвига нет), 2026-08-05.
- Команды исходов живут в `taskctl/groom.go` отдельным файлом: `draft.go` держит
  накопитель (чтение, возраст, список), а разбор это своя механика с правкой
  файла черновика и файла задачи.
- Дата записи пишется строкой «записан ГГГГ-ММ-ДД» под заголовком черновика,
  `loadDrafts` читает её вместе с заголовком и пометкой одним чтением файла.
  Фолбэк на время правки остался для старых черновиков, `defer` по такому
  черновику сначала проставляет ему строку из времени правки.
- `attach` дописывает раздел «Из черновика <ID>» и опускает разделы черновика на
  уровень ниже: иначе его «## Черновик» разорвал бы раздел приписки в файле
  задачи.
- Незакоммиченный черновик гиту неизвестен, `git rm` по нему падает, поэтому
  `removeDraft` отвечает, попало ли удаление в индекс, и такой путь в pathspec
  коммита не едет (иначе `git commit` валился бы на нём целиком).
- По первому замечанию ревью дата записи уехала в заголовок раздела приписки
  («## Из черновика <ID> (записан ГГГГ-ММ-ДД)»): в теле она висела голой строкой
  без контекста, а выбросить её значит потерять возраст мысли там, где он потом
  и нужен.
- Заодно, из того, что ревьювер оставил на моё усмотрение: опускается теперь
  заголовок черновика любого уровня, а не только второго (свой «### » встал бы
  вровень с опущенным «## »), и решётка внутри блока кода за заголовок не
  считается. Позиционную причину `defer`, начинающуюся с дефиса, не трогал:
  разбор отбивает её громко, своим сообщением про неизвестный флаг, а форма
  «флаг перед позиционным аргументом» это семейство DK-099 и DK-101 из
  накопителя, и чинить её тут значит развести две правки одного места.
- Проверено на копии живого накопителя (десять черновиков без строки даты):
  фолбэк даёт «8 дней» по времени правки, `defer` проставляет «записан
  2026-07-28» и возраст после пометки не сбрасывается. Сами черновики в дереве
  не тронуты.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 26%, снимок 0м назад, сдвига нет), 2026-08-05.
- 2026-08-05, сценарий проверки прогнан диспетчером после выката, синтетическая

## Ревью

- attach копирует строку «записан ГГГГ-ММ-ДД» в тело файла задачи: draftSection не срезает эту строку, только заголовок H1, и после attach в docs/tasks/<TASK-ID>.md под «## Из черновика <ID>» повисает голая дата без контекста. Воспроизводится на любом черновике, заведённом draft после этой задачи (записан пишет её всегда): newDraft -> defer (необязательно) -> attach -> в файле задачи виден блок «записан 2026-08-05» перед «### Черновик». Тест TestDraftAttachToTaskWithFile строку не проверяет и проходит с этим дефектом.: исправлено
- removeDraft: ветка отказа git rm (незакоммиченный черновик -> os.Remove, staged=false) без единого теста. Все сценарии attach/drop в groom_test.go коммитят черновик перед вызовом (git add + git commit), сценарий свежезаведённого и ещё не закоммиченного черновика не проверяется нигде. Мутация, которая ломает именно эту ветку (os.Remove успешен, но removeDraft всё равно возвращает ошибку), красноты не даёт, go test -count=1 ./... остаётся зелёным.: исправлено
