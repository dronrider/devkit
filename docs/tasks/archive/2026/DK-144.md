# DK-144: devkitctl doctor ловит файл не по правилу раскладки

Задача цели [DK-135](../../DK-135.md), последняя в её нарезке. Правило принято в
[DK-139](DK-139.md), раздел «Машинная проверка для DK-144»
документа `docs/lld/DK-139-repo-layout.md` описывает её целиком: таблица из
семи проверок с текстами находок, три места, где проверка спотыкается, и
сторож, сверяющий белый список из кода с перечнем в README.

## Задача

Научить `devkitctl doctor` ловить файл, лежащий не по правилу раскладки, и
инструмент, написанный не на том языке. Работать по разделу «Машинная проверка
для DK-144», а не по памяти: там и белый список из тринадцати записей, и семь
проверок с текстами находок, и исключения (съёмщик квоты
`kit/harness/snap/<харнес>.sh`, `*/testdata/`, `docs/tasks/`, общая фикстура
`kit/harness/testdata`).

Из того же раздела, потому что мимо этого проехать легче всего:

- ходить по `git ls-files`, а не по диску: на живом дереве лежат `__pycache__`,
  собранные бинари и рабочие файлы worktree, и проверка по диску краснела бы
  каждый день;
- sh определяется по расширению и по shebang: три точки входа git расширения не
  имеют, и проверка, смотрящая только на `*.sh`, не увидит именно тех файлов,
  ради которых правило пишет исключение;
- проверка включается только на самом devkit (признак тот же, по которому стенд
  послушания находит чекаут: `RULES.core.md` и `hooks/` в корне);
- гоняться она обязана без машинной обвязки, иначе шаг в CI не заведётся.
  Форма (флаг `doctor --layout` против своей подкоманды) остаётся за
  реализацией, требование одно: печатать только находки раскладки и возвращать
  код выхода по их наличию;
- находка называет правило, а не только факт.

Сверх раздела LLD эта задача закрывает вторую половину пункта 3 DoD цели, про
молчание на чистом дереве. Сегодня `doctor` на чистом main печатает пять
находок про битые ссылки в `docs/tasks/`: две в `DK-123.md` и `DK-126.md`, три
в архивном `DK-081.md`. Ссылки эти законны, файл задачи описывает состояние на
момент решения и по правилу DK-139 не правится, значит границу должна знать
сама проверка: живая дока проверяется (корневые `*.md`, `tools/*/README.md`,
`kit/**`, `hooks/**`), а `docs/` стареет и не проверяется. Разбор этого
разделения лежит в файле закрытой [DK-140](DK-140.md).

Оговорку в конце раздела «Раскладка» `README.md` про то, что проверку заводит
DK-144, снять: это её половина.

## Сценарий проверки

Агентский.

1. Прогон на временном репозитории: раскладка по правилу молчит; подложенный
   `.go` в корне, `.sh` на 120 строк в `kit/` и лишний каталог верхнего уровня
   дают по находке каждый, и каждая находка называет правило.
2. Исключения не краснеют: съёмщик `kit/harness/snap/<харнес>.sh` на полторы
   сотни строк, python внутри `tools/<имя>/testdata/`, сценарий проверки задачи
   на sh с функциями, общая фикстура `kit/harness/testdata`.
3. Сторож жив: тест сверяет белый список из кода с перечнем записей раздела
   «Раскладка» `README.md` и краснеет, когда списки расходятся.
4. `doctor` на чистом живом дереве devkit молчит целиком, включая проверку
   ссылок: пяти находок про `docs/tasks/` больше нет.
5. Прогоны CI зелёные: четыре `unittest discover`, шесть `go test ./...`,
   `check-skills.py`, `check-exec-bit.py`, `check-symbols.py`.

## Ревью

- layout.py:30,33: SH_PLACES и PY_PLACES проверяют префикс kit/skills/, а не kit/skills/<имя>/ из таблицы LLD. Послабление ради check-skills.py и check_skills_test.py (реально лежат прямо в kit/skills/) для python оправдано, но реализовано шире необходимого и без теста: файл, подложенный прямо в kit/skills/foo.py, kit/skills/foo.sh или вложенный глубже kit/skills/<имя>/sub/x.py|.sh, проходит молча (проверено вручную на синтетическом дереве). Для sh послабление вовсе не имеет прикрытия: ни один .sh не лежит прямо в kit/skills/, поэтому широкий префикс там просто открытая дыра. Ни README, ни devkitctl/README.md, ни ход работы задачи это отступление от LLD не называют.: исправлено
