# DK-149: LLD: чем доставляются готовые бинари devkit и откуда бинарь знает свою версию

Задача цели [DK-138](DK-138.md), первая в её нарезке: остальные три задачи едут
по решению этого документа.

## Задача

Сегодня devkit заезжает на машину тремя командами `CONNECT.md`: клон, цикл
сборки шести бинарей через `go build` и `devkitctl doctor --fix`. Без go в PATH
из репозитория не получается ничего, и человеку без тулчейна остаётся ставить
go ради утилит доски. Вторая половина того же: после `git pull` собранные
бинари остаются старыми, и утилита работает по-старому, пока кто-нибудь не
позовёт доктора. Разбор обоих перекосов и разведка по репозиторию в файле цели.

Решить и записать:

- канал доставки готовых бинарей: свой tap, релизы гитхаба с установщиком или
  оба сразу. Обе платформы, macos и linux, обе архитектуры проца там, где это
  дёшево. Учесть, что gh на машине нет и релиз проверяется через публичный API
  курлом;
- откуда бинарь берёт свою версию и как она зашивается сборкой (`-ldflags`
  либо равный ему способ), как она печатается наружу и одинаково ли у всех
  шести утилит;
- как версия бинаря связывается с версией репозитория правил: клон правил
  остаётся на машине и уезжает вперёд бинарей, значит нужен способ сказать
  «бинари отстали от чекаута» и порог, за которым это находка доктора;
- что такое обновление одной командой: чем оно зовётся, что делает с клоном
  правил и с бинарями, и как ведёт себя на машине, где devkit уже стоит;
- кто отвечает за клон репозитория правил при установке с нуля: тянет ли его
  установщик сам или человек клонирует руками до него;
- чем зовётся python-часть (`devkitctl` и хуки) на фоне готовых бинарей:
  сегодня это длинный путь из чекаута, и правило языка (`README.md`, раздел
  «Раскладка») держит её на python сознательно, значит вопрос не в переписывании
  на go, а во входе.

Границы, названные на постановке цели:

- клон репозитория правил остаётся и остаётся на виду: правила подключаются
  локальным путём (`@~/projects/devkit/RULES.core.md`), devkit лежит соседом
  проектов, и целиком в Cellar его не спрятать. Цель не про `brew install
  devkit`, а про то, чтобы из установки ушла сборка из исходников;
- платформы обе, devkit ставится и на VPS, а не только на рабочие маки;
- внешних зависимостей у devkit нет ни в go, ни в python, и решение их не
  заводит: установщик обходится тем, что есть на голой машине.

Что из этого проверяемо машиной: DK-150 зашивает версию и заводит релизную
автоматику, DK-151 делает установку и обновление вместе с переписанным
`CONNECT.md`, DK-152 учит `devkitctl doctor` сверять версии всех
устанавливаемых бинарей. Решение должно быть сформулировано так, чтобы каждая
из трёх была выполнима без второго круга дизайна, и перечень «что делает
какая» лёг в документ.

Решение принимается прямо в документе: выбранный вариант один, отвергнутые
названы с причиной. Веера вариантов на выбор пользователю не оставлять, задача
идёт внутри цели, спрашивать некого.

## Ревью

- Самопроверка сборки не сходится с кросс-сборкой на одном раннере: раздел «Сборка релиза» обещает запуск каждого свежего бинаря с --version «внутри каждой сборки, локальной и релизной», а на ubuntu-раннере три пары из четырёх (обе darwin и linux/arm64) не исполняются вовсе. Решить в документе, чем проверяется релизная сборка, иначе DK-150 упрётся в exec format error на первом же теге.: исправлено, раздел «Сборка релиза» разведён на два режима: своя пара исполняется, три кросс-пары проверяются байтовым поиском зашитой строки; обе ОС исполняются живьём в разных прогонах (mac локально, linux на раннере), оба прогона стоят в сценарии DK-150
- Шаг 8 решения 4 переносит бинари через os.replace из временного каталога, а на linux /tmp обычно отдельная файловая система, и rename через её границу даёт EXDEV: обещанная атомарность держится только внутри одной ФС, и установка ляжет ровно на VPS, ради которого названы обе платформы. Сказать, что архив распаковывается во временный каталог рядом с каталогом назначения.: исправлено, шаг 7 распаковывает в <каталог назначения>/.devkit-update-<pid>/, EXDEV назван причиной
- Решение 4 не отвечает на вопрос постановки «как обновление ведёт себя на машине, где devkit уже стоит»: шаг 5 читается как «всегда перевести чекаут на тег», отказы перечислены только про грязное дерево и неотправленное, и на чистом чекауте, стоящем на main, update молча уведёт основной чекаут в detached HEAD вместе с работой доски в нём (shipctl merge, ветки задач). Назвать поведение update для чекаута на ветке явно, как решение 3 называет два режима.: исправлено, перед шагами добавлен разбор трёх случаев: тег (обычный ход), ветка (отказ с названным путём git pull и doctor --fix), ветка с --pin (первая установка); CONNECT.md и README тоже
- Отказ «в чекауте есть неотправленное в origin» не определён для detached HEAD, а это штатное состояние машины потребителя после первого же обновления: upstream у HEAD там нет, и проверка через @{u} откажет или свалится на каждом следующем update. Сказать, чем меряется «своя работа не потеряется» в каждом из двух режимов чекаута.: исправлено, @{u} не используется: две меры на оба режима, git status --porcelain --untracked-files=no и git rev-list --count HEAD --not --remotes
- Про вышедший релиз машине потребителя не говорит никто: правило сходимости сравнивает бинарь с HEAD, оба стоят на старом теге, доктор молчит, а git pull в клоне после перевода в detached HEAD перестаёт работать вовсе, и привычный способ обновиться человек теряет. Раздел «Наблюдаемость» обещает, что в штатной работе не молчит ни один канал: решить, кто зовёт обновляться (находка доктора по fetch тегов или иное), либо отказаться от этого с причиной.: исправлено, заведён update --check и находка доктора по возрасту FETCH_HEAD основного чекаута (порог 14 дней), без похода в сеть; «Наблюдаемость» и README переписаны
- Не разобран случай «тегов нет вовсе», когда git tag --list по маске пуст: это состояние репозитория сегодня и всё время работы над DK-151 до пуша первого тега, а перечень случаев бездействия update (сети нет, тег есть и ассетов ещё нет, платформа не из четырёх) его не называет.: исправлено, случай «тегов нет вовсе» назван в перечне бездействия update и в DK-152, добавлен отдельным тестом DK-151
- Мелочь в доводе против симлинка: сказано, что за битом исполнения в репозитории следит отдельный шаг CI, а hooks/check-exec-bit.py без аргументов смотрит только семейство test.sh и требует бит, а не запрещает его, то есть исполняемый devkitctl.py этот шаг не поймает. Довод держится на остальных причинах, а эту либо убрать, либо назвать точно.: исправлено, довод переписан: мнимые причины (импорт соседей через симлинк работает, check-exec-bit.py смотрит только test.sh) названы мнимыми, остаётся бит исполнения на модуле и некуда положить маркер
- Находка доктора и update --check не смыкаются в цикл: доктор советует позвать --check, а сам --check заявлен как «ничего не двигает». Если он ходит через ls-remote, mtime FETCH_HEAD не меняется и находка после выполнения совета не гаснет; если он делает fetch --tags, то он двигает, и находка гаснет на 14 дней ровно в тот момент, когда человек узнал про новый тег и обновляться не стал. Сказать, чем ходит --check; и там же: после любого fetch новейший тег лежит локально, то есть точный ответ «стоит v0.2.0, вышел v0.3.0» считается без сети и без порога, а решение берёт вместо него возрастную прикидку.: исправлено, находка стала точной (тег HEAD против новейшего тега в клоне, без сети и порога), возрастная осталась второй и косвенной; --check делает git fetch --tags --prune, ls-remote отвергнут с причиной, цикл сомкнут: --check гасит косвенную и зажигает точную, точная гаснет только от обновления
- Сценарий проверки DK-150 опирается на прогон release.yml по workflow_dispatch без тега, а сам workflow описан одним путём, с выкладкой ассетов через gh release: без тега выкладывать некуда, и шаг проверки закончится красным прогоном либо релизом с именем ветки. Сказать, что на прогоне без тега сборка и обе проверки идут, а выкладка пропускается.: исправлено, у workflow два пути: по тегу всё, по workflow_dispatch выкладка пропускается условием по github.ref, остаётся репетиция сборки и обеих проверок; сценарий DK-150 сверяется по логу
