# DK-150: Бинари называют свой коммит, а собирает их релизная автоматика на macos и linux

Задача цели [DK-138](../../DK-138.md), вторая в её нарезке. Решение принято в
[DK-149](DK-149.md), документ `docs/lld/DK-149-binary-delivery.md`:
дизайн там уже сделан, и второго круга задача не требует.

## Задача

Версии у бинарей сегодня нет вовсе, флага `--version` не держит ни один, и
«какой коммит собран» выводится только из mtime файла. Готовых бинарей не
выкладывается нигде: в `.github/workflows/` один `ci.yml` с тестами. Задача
закрывает обе половины, состав правки назван в разделе «Что делает DK-150»
документа DK-149:

- в каждой из шести `tools/*/` появляется `version.go`: `var version`,
  `var commit`, разбор `--version` до всех прочих аргументов и печать строки
  `<имя> <версия> (<коммит>)`;
- `devkitctl build`: список утилит выводится из `tools/*/go.mod`, версия из
  `git describe --tags --always --dirty` и `git rev-parse --short=12 HEAD`,
  сборка с `-ldflags` в каталог назначения, самопроверка запуском `--version` у
  каждого собранного бинаря;
- `devkitctl build --release --out dist`: четыре пары GOOS/GOARCH,
  `CGO_ENABLED=0`, тарболл на пару по шаблону
  `devkit-<версия>-<os>-<arch>.tar.gz`, `SHA256SUMS` рядом. Запуском
  проверяется пара своей машины, остальные три байтовым поиском зашитой строки
  (несуществующий символ `-X` линковщик молча пропускает, и ловится это только
  так);
- `.github/workflows/release.yml` по тегу `v*` и по `workflow_dispatch`, с
  `fetch-depth: 0` и выкладкой через `gh release`; на прогоне без тега сборка и
  обе проверки идут, а шаг выкладки пропускается по `github.ref`;
- `doctor --fix` пересобирает через `devkitctl build`, а не своим `go build`:
  точка сборки одна.

Тесты по разделу «Тесты» документа DK-149: go-тест на формат `--version` в
каждом из шести модулей (он же ловит забытый флаг у новой утилиты) и
python-тесты `build` на синтетическом дереве (список утилит из `tools/*/go.mod`,
ldflags из git, тарболлы и `SHA256SUMS` на месте, самопроверка запуском роняет
сборку на бинаре без флага, байтовая проверка роняет её на кросс-паре без
подстановки). Живой прогон релизной сборки идёт сценарием проверки, тестом он
не заменяется.

Дока едет той же задачей: `tools/devkitctl/README.md` про `build` и его
самопроверку, `kit/skills/live-core/SKILL.md:57` (`go build` становится
`devkitctl build`).

Границы:

- пуш тега в этой задаче не делается: тег ставит человек, и третья часть
  проверки (ассеты в релизе) идёт после слияния;
- диспатч workflow возможен только когда `release.yml` уже лежит на дефолтной
  ветке, это ограничение гитхаба. С ветки задачи диспатч пробовать бесполезно,
  и «workflow сломан» из этого не следует;
- `gh` на машине нет: статус прогона и состав ассетов смотрятся публичным API
  через `curl`, строка версии из лога прогона так не достаётся, и шаг сценария
  под неё пишется по факту;
- установка и обновление (`devkitctl update`) это DK-151, доктор со сверкой
  версий это DK-152; сюда не тащить.

## Сценарий проверки

Агентский, кроме третьей части.

1. `--version` у всех шести: собранный `devkitctl build` бинарь печатает
   `<имя> <версия> (<коммит>)`, коммит совпадает с `git rev-parse --short=12
   HEAD`.
2. `devkitctl build --release --out dist` на машине разработки (mac,
   darwin/arm64): четыре тарболла и `SHA256SUMS` на месте, распаковка тарболла
   своей платформы даёт рабочий `taskctl`, он печатает тег.
3. Первый прогон `release.yml` по `workflow_dispatch` с ветки, без тега: по
   логу видно, что четыре пары собрались, версия напечаталась и шаг выкладки
   пропущен. Этим же прогоном пара linux/amd64 исполняется живьём.
4. Тесты: go-тесты шести модулей и python-тесты `build` зелёные, полный набор
   тестов проекта зелёный, `python3 hooks/check-symbols.py` на изменённых
   файлах молчит.
5. Пользовательская часть, после слияния: человек пушит тег `v*`, и
   `curl -s https://api.github.com/repos/dronrider/devkit/releases/latest`
   показывает пять ассетов, а суммы из `SHA256SUMS` сходятся со скачанными.

## Ревью

- Флаг --version проверяется только в позиции args[0]: 'taskctl -C /tmp --version' и 'regcheck -C /tmp --version' не печатают версию, а падают с посторонней ошибкой (неизвестная команда / flag provided but not defined), хотя LLD говорит про разбор --version до всех прочих аргументов и без -C, а -C по документации ставится и до, и после команды; --help для сравнения ищет флаг по всему списку аргументов (helpRequested): исправлено, printVersion ищет флаг по всей строке аргументов, как helpRequested; тесты: юнит на композицию и прогон собранного бинаря с -C dir --version в каждом из шести модулей, оба краснеют на старом разборе
- В docs/lld/DK-149-binary-delivery.md раздел «Что делает DK-150» (строка ~491) до сих пор показывает версию как git describe --tags --always --dirty без --match 'v*', хотя отступление задокументировано выше в «Решение 2»: в одном документе две разные версии одной и той же команды: исправлено, раздел «Что делает DK-150» цитирует describe с --match 'v*', как в «Решении 2»
- В tools/devkitctl/devkitctl.py остались два места (строки 1083 и 1198), где отсутствие taskctl в PATH предлагает старый цикл cd .../taskctl && go build -o ~/go/bin/taskctl ., хотя соседняя функция check_binaries в этой же ветке уже переведена на единую точку сборки devkitctl build: исправлено, обе подсказки зовут devkitctl build, сторож SinglePointOfBuildTest краснеет на старом тексте
- Правка по замечанию 1 (printVersion сканирует весь args) сломала регресс-сепаратор regcheck: 'regcheck -- <тестовая команда>' теперь матчит --version по значению внутри самой тестовой команды после --, а не только как флаг regcheck. До правки (d0da641) 'regcheck --tests foo.go -- echo --version' доходил до настоящей логики (ошибка про отсутствующий тестовый файл), после правки печатает 'regcheck dev (unknown)' и молча выходит кодом 0, тестовая команда не запускается вовсе; versionRequested() зовётся в main до собственного разбора -- у regcheck (main.go: --version проверяется раньше цикла 'if a == "--"'), и шаблон version.go одинаков на все шесть утилит без учёта того, что только у regcheck -- разделяет свои флаги от чужой команды: исправлено, printVersion останавливается на первом голом --, правило одно на шесть утилит; regcheck --tests foo.go -- echo --version снова говорит про ненайденный тестовый файл и выходит кодом 1, а свой --version до разделителя работает; тесты: юнит на композицию с -- и прогон собранного бинаря на хвосте после --, оба краснеют на правке без остановки
