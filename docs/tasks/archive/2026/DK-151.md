# DK-151: Установка и обновление devkit на чистой машине без сборки из исходников

Задача цели [DK-138](../../DK-138.md), третья в её нарезке. Решение принято в
[DK-149](DK-149.md), документ `docs/lld/DK-149-binary-delivery.md`:
дизайн там сделан целиком, второго круга задача не требует.

## Задача

Релиз уже выкладывается: [DK-150](DK-150.md) научил бинари
называть свою версию и завёл `release.yml`, тег `v0.1.0` собран, пять ассетов
лежат в релизе и суммы сходятся. Ставится devkit по-прежнему сборкой из
исходников, и эта задача её убирает. Состав правки назван в разделе
«Что делает DK-151» документа DK-149, шаги команды в «Решении 4»:

- `devkitctl update`: разбор режима чекаута (тег, ветка, ветка с `--pin`),
  отказы (позвали не из основного чекаута, грязное отслеживаемое, коммиты мимо
  origin), `git fetch --tags --prune`, новейший тег из git, переход на тег,
  самоперезапуск через `os.execv` уже новым кодом, скачивание тарболла своей
  платформы и `SHA256SUMS` через `urllib` во временный каталог рядом с
  каталогом назначения, сверка суммы, атомарная подмена бинарей через
  `os.replace`, обёртка `devkitctl`, раскладка машинного контура тем же кодом,
  что зовёт `doctor --fix`, и вывод «было -> стало»;
- поимённые сообщения на всех пяти случаях бездействия, включая «тегов нет
  вовсе», «тег есть, а ассетов ещё нет», «сети нет» и «платформа не из
  четырёх»: молчаливого холостого хода у команды нет;
- `devkitctl update --check`: `git fetch --tags --prune` и рассказ, без правки
  чекаута, бинарей и раскладки;
- выбор каталога назначения по решению 7 и находка про PATH;
- обёртка `devkitctl` по решению 6, её кладут и `update`, и `doctor --fix`.

Дока едет той же задачей: `CONNECT.md` (две команды вместо трёх, вторая с
`--pin`, цикл `go build` уходит), `README.md` (раздел про установку Go-утилит),
README шести утилит и `tools/devkitctl/README.md` про `update` со всеми
отказами. Устаревшие после переезда каталогов пути сборки в этих README
чинятся заодно, они перечислены в разделе «Затрагиваемая документация»
документа DK-149.

Тесты по разделу «Тесты» того же документа: python-пирамида на разбор имени
ассета по платформе, сверку суммы (подменённый байт роняет установку),
атомарную подмену, выбор каталога, самоперезапуск, все три режима чекаута и оба
отказа, причём отказ по неотправленной работе проверяется и на отвязанном
чекауте, где `@{u}` не существует. Отдельным тестом состояние «тегов нет
вовсе». Сеть в тестах это локальный сервер, гитхаб в тестах не участвует.

Границы:

- доктор со сверкой версий это DK-152, сюда не тащить: `check_binaries`,
  константа `BINARIES` и находки про релизы остаются ей;
- репозиторий публичный, токен для скачивания ассетов не нужен, и заводить
  работу с ним не надо;
- `.devkit/deploy.local` уже переведён на `devkitctl build`, трогать его
  незачем: файл гитигнорнут и живёт только на машине.

## Сценарий проверки

Агентский.

1. Прогон в чистом окружении: временный HOME, go убран из PATH, клон
   репозитория и `devkitctl update --pin`. Дальше `taskctl --version` печатает
   тег релиза, а `devkitctl doctor` находок по машине не даёт.
2. Второй заход той же командой без ключа на уже поставленном devkit: чекаут
   отвязан, обновлять нечего, и команда это говорит, в сеть за ассетами не
   идёт.
3. `devkitctl update --check` на том же чекауте: рассказывает про версии и
   ничего не двигает (HEAD, бинари и раскладка на месте).
4. Отказ на чекауте, стоящем на ветке: команда без `--pin` не двигает чекаут и
   называет `git pull` с `doctor --fix`.
5. `CONNECT.md` и `README.md` не оставляют цикла `go build` как основного
   способа установки, а `grep` по репозиторию не находит строк сборки, которые
   ведут в несуществующие после переезда каталоги.
6. Тесты: python-пирамида задачи зелёная, полный набор тестов проекта зелёный,
   `python3 hooks/check-symbols.py` на изменённых файлах молчит.
