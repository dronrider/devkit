# DK-1691: Тесты дашборда расходуют минуты на ожидания и подготовку стендов

## Что происходит

11 ноября 2026 года общий прогон остановился на лимите пакета dashboard в 20 минут. Отдельный прогон того же пакета с установленным Playwright прошёл за 998,29 секунды. Из 1416 тестов прошли 1410, ещё шесть штатно пропущены. Команда воспроизведения из дерева задачи:

```sh
NODE_PATH=/opt/homebrew/lib/node_modules GOWORK=off devkitctl test tools/dashboard -json
```

TestCloudStartMissingTmuxParksWithOwner занял 90,99 секунды, TestGroomConsentWaiting 54,24 секунды. Девять браузерных тестов вместе заняли 208,98 секунды. В guardian подтверждены ожидания рабочих интервалов длительностью одну секунду и 60 секунд. Причины остальных задержек ещё нужно установить. Отдельный успешный тест за 91 секунду расходует заметную часть общего лимита. При общей нагрузке прогон пакета не укладывается в лимит, и слияние останавливается.

Ожидался завершённый прогон в пределах штатного лимита. В общем прогоне получен timeout всего пакета; тест TestStopWaitEndsBySpell успел выполняться около четырёх секунд. В отдельном прогоне он прошёл за 3,95 секунды. Данных о зависании этого теста нет.

Исходный JSON лежит в /private/tmp/dk-dashboard-timing-20261111.jsonl, сводка в /private/tmp/dk-dashboard-timing-summary-20261111.json. Замер сделан на ветке DK-1690. Эти временные файлы нужны исполнителю для сравнения, итоговые числа и причины должны остаться в файле задачи.

## Чего хотим

Ускорить несколько дорогих тестов dashboard в одной задаче. Начать с guardian, затем проверить остальные самые длительные тесты по замеру. Убрать подтверждённые ожидания реального времени и повторную подготовку стендов там, где это сохраняет смысл проверок. Для проверки времени использовать управляемый ход времени или событий с сохранением рабочего поведения.
