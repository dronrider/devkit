# DK-1692: Тик поднимает второго исполнителя рядом с agentctl run

## Что происходит

11 ноября 2026 года при выполнении DK-1691 два исполнителя одновременно правили одно рабочее дерево. Первый был запущен в 19:12 через agentctl run из сессии Codex. В 19:16 тик поднял голову той же задачи через taskctl run. В результате появился дубль guardianScript, сборка стала красной, выполнение остановилось на вопросе о выборе исполнителя.

Ожидалось, что при занятой задаче тик не запустит независимого исполнителя. Оба запуска состоялись. Наблюдение записано в разделе «Развилки» DK-1691 и в журналах сессий 7b9a5c0f-d64d-495c-8d81-89426cc990d1 и 30c29e99-6c41-46df-b998-e0653b78feab. Первый подпроцесс затем завершился и уступил дерево. Правки сохранены.

Для воспроизведения нужен временный проект с задачей In progress. Запустить длительного исполнителя через agentctl run вне головы задачи, затем вызвать подъём той же задачи штатным путём тика. Проверить число независимых исполнителей и право записи в одно дерево. На рабочей доске повторять столкновение нельзя.

По результатам чтения кода dashboard и taskctl run используют общий taskhead, а agentctl run запускает подпроцесс без замка головы задачи. В первом запуске отсутствовал адрес родительской сессии CLAUDE_CODE_SESSION_ID. Команда напечатала предупреждение об отсутствии родительского транскрипта, но продолжила запуск. Точный вклад отсутствующей привязки и распознавания живости ещё нужно проверить тестом. Запись startup исполнителя в реестре существовала. Одного требования «дописать сессию в реестр» недостаточно.

Обычный запуск через дашборд уже защищён от повторного подъёма через taskctl run. Проверка на DK-1691 после разбора завершилась отказом повторного запуска с кодом 3 и указанием занятого замка. Баг касается согласования разных путей запуска.

## Чего хотим

Согласовать делегирование через agentctl run и владение задачей через taskhead. Пока внешний исполнитель ведёт задачу, тик и дашборд не поднимают рядом независимого исполнителя. Уже работающая голова может штатно делегировать этапы. Пользователь видит, кем занята задача и почему повторный запуск отклонён.

## Границы

Исправление относится к владению задачей и защите запуска. Ускорение тестов dashboard остаётся в DK-1691. Простая замена agentctl run на taskctl run в инструкциях не сохраняет различие между делегированием этапа и запуском головы. Очередь слияний и удержание от выката не заменяют защиту выполнения.

Код и наблюдения доступны локально. Для разработки не найдены условия, которые может выполнить только человек. Способ согласования выбирает исполнитель в пределах сохранения штатного делегирования и защиты одного дерева от независимых исполнителей.

## DoD

- Независимые запуски через agentctl run и taskhead защищены от одновременной работы над одной задачей в обоих порядках запуска. Одновременный старт тоже не допускает двух владельцев.
- Проверен исходный случай без родительской сессии и случай штатного делегирования из живой головы. Исполнитель не конфликтует с собственной головой и не зависает на её замке.
- При завершении, ошибке запуска и аварийном выходе занятость безопасно снимается. Другая задача продолжает запускаться независимо; причина отказа повторного запуска видна снаружи.
- Регрессионный тест на временном проекте воспроизводит двойной запуск на старом коде и проходит после исправления через regcheck. Проверки не запускают исполнителей на настоящей доске.
- Инструкции и описание команд соответствуют исправленному порядку запуска и делегирования.
