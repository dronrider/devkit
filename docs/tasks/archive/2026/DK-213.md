# DK-213: Хук check-commit: ID задачи в коммите на main проекта с доской

записан 2026-08-09

## Что происходит

Тот же случай IRC-103, что в DK-212: коммит f519c70 лёг в main it-road-course
мимо ветки задачи, с subject без ID, и теперь конфликтует с настоящей веткой
irc-103 по AGENTS.md. Ядро правил доски требует ID в subject (по нему находятся
коммиты задачи, revert и состав поезда, и связь эта чинится дорого), но
check-commit.py проверяет только следы ассистента, одну строку и префикс из
истории. Коммит в main без ID проходит молча.

## Чего хотим

check-commit.py в репозитории с доской (docs/TASKS.md у корня) на ветке main
даёт находку коммиту, который трогает файлы вне доски (docs/TASKS.md,
docs/tasks/, docs/TASKS-archive.md) и не несёт ID вида ABC-123 в subject.
Внезадачной мелочи остаётся штатный обход `--no-verify`. Фичеветки не
проверяются: рубеж про main, куда код задачи доезжает слиянием.

## DoD

Тесты хука: коммит кода на main без ID даёт находку, с ID проходит, коммит
одних файлов доски проходит, фичеветка и репозиторий без доски не трогаются.
hooks/README.md описывает рубеж.

## Ход работы

- Исполнение: субагент sonnet/high по вердикту pick (квота: week_all 82%, снимок 6м назад, сдвига нет), 2026-08-09.
- `hooks/check-commit.py`: пятый рубеж. `repo_context()` спрашивает у git
  корень репозитория, текущую ветку и staged-дифф (то же, что видит
  `commit-msg` на будущий коммит); находка встаёт в `check()`, когда в корне
  есть `docs/TASKS.md`, ветка `main`, коммит трогает файл вне трёх мест доски
  и в subject нет `TASK_ID` (`[A-ZА-Я]+-[0-9]+`, тот же класс символов, что у
  `idRe` в `tools/taskctl/board.go`). Вне git-репозитория, без `docs/TASKS.md`
  и на ошибке git-команды рубеж молчит, как и остальные проверки на
  git-контексте в этом файле.
- `hooks/check_commit_test.py`: `TestCheckCommit.run_tool` получил явный
  `cwd=self.tmp`, иначе новый рубеж спрашивал бы git у самого devkit, в
  котором тесты и выполняются, и результат плавал бы от ветки и индекса
  той сессии. Новый класс `TestBoardIdOnMain` (6 тестов) заводит настоящий
  репозиторий с веткой `main` и проверяет все случаи DoD: код без ID на main
  ловится, с ID проходит, коммит одной доски проходит, доска и код без ID в
  одном коммите ловится по коду, фичеветка и репозиторий без доски рубеж не
  видят.
- `hooks/README.md`: новый раздел «ID задачи в subject на main» с условиями
  находки и обходом, ссылка на него из абзаца про `commit-msg`.
- Красноту проверил `regcheck --base main --tests hooks/check_commit_test.py
  -- python3 hooks/check_commit_test.py -v`: тест красный на main, зелёный на
  текущем коде.
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 82%, снимок 16м назад, сдвига нет), 2026-08-09.
- Замечание N1: ссылка на правило была не на тот пункт (`«Ветки, ревью и
  деплой» п. 7` вместо `«Трекинг задач» п. 7`, «Связь с гитом»). Поправлено в
  четырёх местах: `hooks/check-commit.py` (докстринг и текст находки в
  `check()`), `hooks/check_commit_test.py` (докстринг `TestBoardIdOnMain`),
  `hooks/README.md` (абзац про `commit-msg`). Раздел «ID задачи в subject на
  main» в README сам по себе номер пункта не называл, правки не потребовал.
  Прогон `cd hooks && python3 -m unittest discover -p '*_test.py'`: 255
  тестов, `OK`.

## Сценарий проверки

Агентский, гоняется из `hooks/`:

```sh
cd hooks && python3 -m unittest discover -p '*_test.py'
```

Ожидание: `OK` и число прогнанных тестов, находок нет. Точечно про этот
рубеж:

```sh
python3 -m unittest check_commit_test -v
```

Ожидание: 24 теста, все `ok`, среди них шесть `TestBoardIdOnMain.*`.
Регрессия (падает на main, проходит на текущем коде) из корня репозитория:

```sh
regcheck --base main --tests hooks/check_commit_test.py -- python3 hooks/check_commit_test.py -v
```

Ожидание: строка «тест краснеет на main и проходит на текущем коде, регрессия
закрыта».
