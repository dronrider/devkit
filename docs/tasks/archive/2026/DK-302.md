# DK-302: shipctl и taskctl batch читают вид: один совет после выката и отбор пачки полем

## Сценарий проверки

Агентский. Обе правки покрываются go-тестами двух модулей и общего пакета;
живого слияния и выката сценарий не запускает.

1. Общий разбор вида в суффиксе строки доски:
   ```
   cd internal && GOWORK=off go test ./accept/
   ```
   Ожидание: `ok`. Тест покрывает чтение вида из суффикса, умолчание agent и
   снятие хвостов провала/блокировки перед поиском приёмки.

2. Отбор пачки по виду:
   ```
   cd tools/taskctl && GOWORK=off go test -run 'TestBatch' ./...
   ```
   Ожидание: `ok`. TestBatchAcceptKind проверяет, что смешанный и
   пользовательский вид отсеиваются в группу «вид приёмки не агентский», а
   агентский проходит. TestBatchSelect проверяет, что неагентские задачи не
   занимают слотов в поезде: XR-115 и XR-116 (user и mixed) отсеиваются по
   виду, а XR-112 за ними уходит в лимит, как и без них.

3. Один совет после выката:
   ```
   cd tools/shipctl && GOWORK=off go test -run 'TestNextAfterMerge' ./...
   ```
   Ожидание: `ok`. Тест проверяет три вида по отдельности: агентский
   прогоняет сценарий и закрывает, смешанный прогоняет агентскую часть,
   пользовательский ждёт человека.

4. Интеграционная проверка совета через cmdMerge:
   ```
   cd tools/shipctl && GOWORK=off go test -run 'TestMergeNextStep' ./...
   ```
   Ожидание: `ok`. После merge агентской задачи (XR-001 без суффикса) совет
   называет прогон сценария и закрытие и не содержит слова «пользовательский».
   На старом коде (обе ветки сразу) совет содержал «пользовательский», и
   проверка его отсутствия падала.

5. Полные прогоны модулей:
   ```
   cd tools/taskctl && GOWORK=off go test ./...
   cd tools/shipctl && GOWORK=off go test ./...
   ```
   Ожидание: оба `ok`, ни одного провала.

## Ход работы

- Исполнение: подпроцесс glm-5.2/high по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-13.
- Вынес разбор вида приёмки в общий пакет `internal/accept`: регулярка
  `acceptSufRe` и функция `KindOf` живут там однажды, доступны обоим модулям.
  taskctl делегирует `acceptOf` в `accept.KindOf`, shipctl читает вид тем же
  путём для совета после выката. Регулярка не дублирована.
- taskctl/batch.go: в переключатель отбора добавлен фильтр «вид приёмки не
  агентский» после типа LLD. В поезд идут только агентские задачи; смешанный и
  пользовательский вид отсеиваются в отдельную группу с указанием вида.
- shipctl/advice.go: `nextAfterMerge` принимает доску и список ID, читает вид
  каждой задачи из строки и печатает один шаг на вид (LLD DK-292, решение 2).
  Три call site в ops.go передают доску и ID. У поезда задачи группируются по
  виду, каждый вид звучит своей строкой.
- Тесты: TestBatchAcceptKind (новый, отбор по виду), TestNextAfterMerge (новый,
  три вида совета), TestBatchSelect обновлён под новую фикстуру с неагентскими
  задачами, TestMergeNextStep обновлён под один совет вместо двух веток.
- Дока: shipctl README секция «Следующий шаг конвейера» описывает совет по
  виду; taskctl README секция `batch` включает критерий вида приёмки в список
  проверок.
- Ревью: подпроцесс glm-5.2/high по вердикту pick (квота: объявления нет, корректор выключен), 2026-08-13.

## Ревью

- advice.go nextAfterMerge: группировка совета для поезда из задач разных видов не покрыта тестом. TestNextAfterMerge гоняет каждый вид по одной задаче (один ID), TestMergeNextStep покрывает одиночный merge, а TestTrainMergeAndShip гоняет cmdShip на поезде из двух задач, но не утверждает текст совета. Группировка по виду, склеивание одноранговых ID через запятую и порядок строк agent/mixed/user (tools/shipctl/advice.go:72-89) это описанный контракт (докстринг и README «задачи поезда группируются по виду, каждый вид звучит своей строкой»), и регрессия здесь ловится только глазами. Добавить в TestNextAfterMerge случай с доской из 2-3 задач разных видов и утверждать число строк и их порядок.: исправлено, добавлен TestNextAfterMergeTrain: поезд из 4 задач 3 видов, утверждает число строк, порядок agent/mixed/user и склейку одноранговых ID
