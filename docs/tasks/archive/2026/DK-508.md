# DK-508: CI не гоняет тесты модулей cmdout и secretctl

записан 2026-08-24, оформлен 2026-08-24

## Что происходит

Го-модулей в `tools/` девять, а шаг тестов в `.github/workflows/ci.yml`
перечисляет каталоги руками, и в перечне их семь: `cmdout` и `secretctl`
не гоняются вовсе. Нашлось это ревью DK-367, где раннер `parallel.py`
перестал держать список модулей руками и стал искать их глобом
`tools/*/go.mod`: локально после этого прогон покрывает все девять, а CI
остался со своим списком.

Локальный прогон дыру прикрывает, поэтому вживую она не стреляла, но регресс
в `cmdout` или `secretctl` проходит CI зелёным.

## Чего хотим

CI гоняет тесты всех го-модулей `tools/` и не расходится с деревом, когда
появляется новый инструмент. Способ на выбор исполнителя: либо тот же поиск
модулей глобом одним шагом, либо матрица по найденным каталогам вместо
семи выписанных шагов.

## DoD

Прогон CI на ветке с заведомо красным тестом в `cmdout` (и отдельно в
`secretctl`) краснеет. Новый го-модуль в `tools/` попадает в CI без правки
workflow руками.

## Ревью

Уровень 2 до 506e286: неопределённость 0, триаж: да на «ломает ли путь DoD», так как правка меняет способ, которым CI видит красноту go-модулей, а ошибка в exit code или в выводе раннера маскирует регресс тем же способом, что и баг задачи; critical_paths не тронуты

- Вердикт: без замечаний. `ci.yml` валиден (ruby -ryaml), шаги хуков и
  python-тестов на месте. `--only-go --list` видит все 9 го-модулей, включая
  `cmdout` и `secretctl`. Прямой `go test` в `tools/cmdout` с внесённым
  красным тестом даёт rc=1. Тем же путём его ловит `parallel.py`: `run_all`
  печатает `FAIL <имя>` и возвращает 1, вывод не глушится. Оба новых теста
  `parallel_test.py` зелёные на HEAD. Полный прогон раннера по всем 9
  модулям не гонялся из-за нагрузки машины, точечно проверены `cmdout` и
  списочный вывод.

## Сценарий проверки

Агентский. Каждый шаг идёт одной строкой: переменные и ловушки между шагами
обкатки не живут, временные файлы каждый шаг убирает сам. Раннер идёт с
девятью воркерами, чтобы красный модуль остановил прогон первым.

1. Раннер, которым CI гоняет `cmdout`, краснеет из-за заведомо красного
   теста.

```sh
f=tools/cmdout/zz_dk508_red_test.go; printf 'package main\n\nimport "testing"\n\nfunc TestDK508Red(t *testing.T) { t.Fatal("red") }\n' > $f; out=$(PATH=/usr/local/go/bin:$PATH python3 tools/devkitctl/parallel.py --only-go -j 9 2>&1); rc=$?; rm -f $f; test $rc -ne 0 && echo "$out" | grep 'FAIL go:cmdout'
```

Ожидание: код возврата ненулевой, в выводе строка `FAIL go:cmdout`; временный
тестовый файл удаляется тем же шагом.

2. То же для `secretctl`, второго модуля, выпавшего из ручного списка CI.

```sh
f=tools/secretctl/zz_dk508_red_test.go; printf 'package main\n\nimport "testing"\n\nfunc TestDK508Red(t *testing.T) { t.Fatal("red") }\n' > $f; out=$(PATH=/usr/local/go/bin:$PATH python3 tools/devkitctl/parallel.py --only-go -j 9 2>&1); rc=$?; rm -f $f; test $rc -ne 0 && echo "$out" | grep 'FAIL go:secretctl'
```

Ожидание: код возврата ненулевой, в выводе строка `FAIL go:secretctl`.

3. Новый го-модуль в `tools/` подхватывается без правки workflow. Перечень
   строится глобом по `go.mod`, а не хранится руками.

```sh
mkdir -p tools/zzdk508mod && printf 'module example.com/zzdk508mod\n\ngo 1.22\n' > tools/zzdk508mod/go.mod && PATH=/usr/local/go/bin:$PATH python3 tools/devkitctl/parallel.py --only-go --list | grep 'go:zzdk508mod'; rc=$?; rm -rf tools/zzdk508mod; exit $rc
```

Ожидание: `go:zzdk508mod` в перечне `--only-go --list`, хотя имя не
упомянуто ни в `ci.yml`, ни в `parallel.py`.

4. `.github/workflows/ci.yml` запускает этот раннер, а не хранит список
   руками.

```sh
cd tools/devkitctl && python3 -m unittest -v parallel_test.CiWorkflowTest parallel_test.MainTest.test_only_go_narrows_the_list_to_go_modules
```

Ожидание: оба теста `ok`, без `FAIL`.
