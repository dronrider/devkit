# DK-512: dashboard: память обхода корней не держит цепочку экрана, main красный

## Что происходит

На main красный тест `TestScanReadOnceForRepeatedRequests`
(`tools/dashboard/cache_test.go:158`): цепочка экрана стоит 19 запусков git
против 7 за первый запрос, то есть обход корней в память не лёг. Найдено на
слиянии DK-503, где правка была чисто документной и к дашборду отношения не
имела.

Красный main держит слияние всем задачам разом: `shipctl merge` гоняет весь
набор компонентов и отказывает по первому провалу, так что каждая следующая
ветка упирается в тот же тест.

## Чего хотим

Тест снова зелёный на main: обход корней ложится в память и цепочка из трёх
запросов подряд не гоняет git заново.

## Развилки

- Где чинить: в стенде или в дашборде. Память обхода корней цела, лишние
  запуски git приходят не от неё, а от живого `agentctl`, которого стенд звал
  из PATH разработчика. Чинится стенд: раскладку подписок он теперь берёт из
  своей фикстуры, как доску и tmux.
- Кэш раскладки подписок оставлен как был. Дашборд намеренно не запоминает
  ответ с причиной вместо списка (`harnesses.go`), и поставленный бинарь
  обязан доезжать до экрана сразу, а не по выходе срока.

## DoD

- Стенд `newTestEnv` не зовёт ни одного бинаря машины: подпроцессы теста
  считаются честно при любом состоянии `agentctl` и его конфигов.
- Сторож изоляции краснеет на старом коде, и это показано прогоном `regcheck`.

## Ревью

- Сценарий проверки состоит из трёх go test-запусков (TestScanReadOnceForRepeatedRequests, TestStandKeepsLiveAgentctlOut, go test ./...) над теми же тестовыми файлами, что лежат в самом диффе: это повтор тестов ветки, они зелёные ещё до слияния (см. Ход работы: regcheck уже прогнал их и это записал), и после выката знания не добавляют (ACCEPTANCE.md, «Самодостаточность агентской части»). Ни один шаг не проверяет реальный эффект правки на выкаченном - например что main после слияния снова принимает merge других веток (то, ради чего заведена задача: «красный main держит слияние всем задачам разом»). Вид agent можно оставить, но сценарий нужно дополнить шагом, который прогоняется после слияния в main и доказывает что-то про выкаченное, а не повторяет тесты ветки.: исправлено, сценарий переписан: шаги 2 и 3 гоняются после слияния на main, шаг 2 это ворота слияния из .devkit/deploy.local в том окружении, где они отказывали

## Сценарий проверки

1. Воспроизведение исходной поломки. В окружении, где `agentctl` отказывает
   (пустой `DEVKIT_HOME`), на коде до правки цепочка экрана считала запуски git
   живой утилиты своими:

   ```
   mkdir -p /tmp/dk512-empty
   cd tools/dashboard
   DEVKIT_HOME=/tmp/dk512-empty GOWORK=off go test -run TestScanReadOnceForRepeatedRequests -count=1 .
   ```

   Ожидание до правки: `цепочка экрана стоила 19 запусков git против 7 за первый
   запрос`.

2. После слияния, из основного чекаута на main: ворота слияния проходят в том
   самом окружении, где они отказывали. Команда та же, что зовёт `shipctl
   merge` (`.devkit/deploy.local`, ключ `test`):

   ```
   cd ~/projects/devkit
   DEVKIT_HOME=/tmp/dk512-empty sh -c 'export GOWORK=off; python3 tools/devkitctl/parallel.py'
   ```

   Ожидание: прогон зелёный, `tools/dashboard` в перечне пройденных
   компонентов. Это и есть предмет задачи: main снова принимает слияние чужих
   веток.

3. Сторож изоляции на слитом коде, в том же окружении:

   ```
   cd ~/projects/devkit/tools/dashboard
   DEVKIT_HOME=/tmp/dk512-empty GOWORK=off go test -run 'TestStandKeepsLiveAgentctlOut|TestScanReadOnceForRepeatedRequests' -count=1 .
   ```

   Ожидание: `ok github.com/dronrider/devkit/tools/dashboard`, стенд находит
   `agentctl` в своём каталоге фикстур.
