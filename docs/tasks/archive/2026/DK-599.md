# DK-599: Слияние не доставляет правку до бинарей в PATH

## Что происходит

Задача закрывается, код лежит в main, а на машине продолжает работать прежняя
сборка. Слияние гоняет тесты и пушит код, пересборку бинарей в `~/go/bin` оно
не делает.

Живой случай 2026-08-29. Правка съёмщика квоты (DK-584) легла коммитом в 14:54,
установленный `agentctl` был собран в 14:41. Снимок в 18:12 сделан старой
сборкой и опять встал без пометки, хотя починка уже была слита и задача закрыта.
Нашёл это пользователь, а не сторож.

Это третий случай того же разряда за день. DK-549: каталог POC стоял в PATH
демона первым, и вердикты неделю считала сборка ветки. DK-582: хуки на машине
зовутся из дерева ветки, правки в main до пользователя не доезжают.

Правило devkit требует, чтобы фича работала на чужой машине, и слияние тут
рубеж не держит. Что решить разбором: звать ли сборку из выката, сторожить ли
расхождение бинаря с вершиной main отдельной проверкой доктора, и как быть с
`devkitctl update`, который у пользователя тоже ставит бинари.

## Чего хотим

Выкат и установка кончаются сверкой по победителю PATH. `devkitctl build` без
ключей кладёт бинари в каталог назначения, а потом спрашивает `--version` у
каждой утилиты по имени из PATH, как её позовёт человек. Ответ чужой копии
роняет сборку с именем утилиты и путём заслонившего файла. Этой сборкой едет
deploy-команда devkit. Поэтому вместе с ней падают `shipctl merge` и
`shipctl ship`, и подмена в PATH перестаёт переживать выкат молча.
`devkitctl update` кладёт бинари релиза в тот же каталог и кончается той же
сверкой.

## Границы

Сверка закрывает живой случай DK-584 только наполовину. Правка тогда легла на
main прямым коммитом, мимо merge, и выкат после неё никто не звал. Сверке в
таком заходе негде сработать. Расхождение бинаря с чекаутом дальше ловит
`devkitctl doctor` (проверка `check_binaries`), а дорога правок ревью через
merge остаётся правилом процесса, не этой задачей.

## Развилки

- Где живёт сверка. Выбраны сборка и установка devkitctl, отдельный ключ
  `.devkit/deploy.local` у shipctl отвергнут. shipctl общий для всех проектов,
  и учить его устройству бинарей devkit значило бы завести вторую копию знания
  о раскладке. Слияние падает через код возврата deploy-команды, этого хватает
  на оба DoD-пункта про shipctl.
- Имя, которого в PATH нет вовсе, сверка не судит. Про каталог мимо PATH
  говорят находки раскладки у доктора и «осталось сделать» установки. Отказ
  сборки на машине без установленного devkit запер бы первый же выкат.

## DoD

- `shipctl merge` и `shipctl ship` при выкате пересобирают бинари утилит в
  PATH, и после выката `<утилита> --version` печатает хеш вершины main.
- Если после выката версия установленного с вершиной не сошлась, shipctl
  печатает расхождение с именем утилиты, а не молчит.
- `devkitctl update` ставит бинари той же дорогой, двух сборок не остаётся.

## Сценарий проверки

1. Стенд исходной беды. Свежая сборка лежит в каталоге назначения, а раньше
   него в PATH стоит чужая копия:

   ```sh
   cd ~/projects/devkit
   mkdir -p /tmp/dk599-shadow
   printf '#!/bin/sh\n[ "$1" = "--version" ] && echo "agentctl v0.0.1 (staroe)"\nexit 0\n' > /tmp/dk599-shadow/agentctl
   chmod +x /tmp/dk599-shadow/agentctl
   PATH=/tmp/dk599-shadow:$PATH python3 tools/devkitctl/devkitctl.py build
   ```

   До правки команда выходила нулём и печатала «сборка в порядке». Это
   исходная беда. После правки она выходит единицей и называет agentctl, путь
   `/tmp/dk599-shadow/agentctl` и сборку `v0.0.1 (staroe)`.
2. Убрать стенд и собрать без подмены: `rm -rf /tmp/dk599-shadow`, затем
   `python3 tools/devkitctl/devkitctl.py build`. Выход нулём, «сборка в
   порядке».
3. Шаг после выката. Установленная утилита отвечает хешем вершины main:

   ```sh
   agentctl --version
   git -C ~/projects/devkit rev-parse --short=12 main
   ```

   Коммит в скобках из первой команды совпадает с выводом второй.
