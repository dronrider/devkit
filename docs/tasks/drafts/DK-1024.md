
### Приписка 2026-09-16: разбор инцидента у соседней сессии и субагентский конец

Соседняя сессия разобрала свой пропуск выборки и вычитки на правке README и
назвала четыре причины. Работа шла в своём окне, исполнителя не поднимали.
Абзац README писался python-скриптом внутри правки кода, и момента «сейчас
пишу прозу» не было. Выборка из начала сессии принималась за действующую.
Сторожа молчали, потому что абзац порогов плотности на большом файле не
сдвинул, а следа выборки и вычитки никто не требует. Три из четырёх сверены с
devkit, и они меняют состав сторожа.

Хук на Edit|Write закрывает половину записей. Сторожа PostToolUse стоят на
Edit|Write|NotebookEdit, а текст, вписанный heredoc, sed или python-скриптом
из Bash, идёт мимо них. Вторая половина это pre-commit, где `check-prose.py
--diff` уже меряет добавленные строки: след выборки проверяется там же, по
добавленным строкам в файлах доки. Один сторож, два места.

Шаг «эталоны прозы берутся до первой фразы раздела» стоит только у
exec-xhigh, и там жанр lld. У exec-low, exec-medium и exec-high его нет, и
прогон сценария 38 субагентским концом с exec-low на mini дал 0 вызовов prose
из 6, по журналам субагентов в доме прогона. Отдать текстоёмкую правку
исполнителю со встроенным шагом в devkit нельзя, кроме проектирования.

След вычитки не требует ни `taskctl lint`, ни ворота слияния. Единственное
упоминание вычитки в shipctl это исключение для стенда. Предложение соседней
сессии, строка «Вычитка» в ходе работы у задачи с правкой доки и проверка
её lint-ом, ложится сюда вторым сторожем либо отдельной строкой доски.

К вопросу о сроке следа. Скилл prose пишет, что инструкция из начала сессии
к моменту письма уже не действует, и соседняя сессия на этом и споткнулась.
След выборки живёт ограниченное число ходов или до сжатия контекста, число
подбирается по журналам сессий.
