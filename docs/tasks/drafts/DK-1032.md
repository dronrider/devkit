# DK-1032: указатель на скилл chat кладёт хук по транскрипту, а не каждая реплика

записан 2026-09-17
приоритет: средний

## Черновик

### Ситуация

Строка старта сессии из hooks/session-task.py (CHAT_RULE и NO_TASK_CHAT_RULE) говорит «на каждой реплике человека первым действием вызови скилл chat инструментом Skill». Хук кладёт её раз при старте и раз после сжатия контекста, а модель, следуя букве, зовёт скилл на каждом сообщении заново. Замечено 2026-09-17 в консольной сессии devkit: второй и последующие вызовы приходят с ответом «Skill /chat is already loaded above». Оговорка «на каждой реплике» появилась из сценария 41 стенда obeycheck: без неё модель яруса mini отвечала на простой вопрос без скилла и к работе на втором ходу тоже шла без него (4 из 5 против 5 из 5).

### Осложнение

Каждый ход чата несёт лишний вызов инструмента и тело скилла (около сорока строк) в контексте, в долгом разговоре контекст растёт на эти строки с каждой репликой. Решение «подключён скилл или нет» отдано модели, а в списке доступных скиллов подключённость не видна, выводится только из собственного транскрипта; слабая модель как раз этого и не выводит, сильная делает лишнюю работу.

### Вопрос

Хук UserPromptSubmit получает путь к транскрипту: искать в нём вызов Skill с chat после последнего сжатия и класть указатель только при его отсутствии? Тогда строка старта теряет «на каждой реплике», а повод compact хука старта остаётся или уходит в тот же хук. Сценарии стенда 29, 30, 32, 41 кладут указатель текстом промпта, под хук их надо перестроить, стенд должен уметь гонять хук на реплике. Что считать вызовом после сжатия: запись compact в транскрипте или иной маркер.

### Гипотеза

Указатель на скилл chat приходит в сессию только тогда, когда тела скилла в контексте нет: на первой реплике и после сжатия. Сильная модель зовёт скилл один раз за окно контекста, слабая по-прежнему не пропускает его перед работой, сценарий 41 держится 5 из 5.
