# DK-1061: шаг сценария обкатки двигает теги живого репозитория

записан 2026-09-19
приоритет: высокий

## Черновик

### Ситуация

2026-09-19, DK-1060. `taskctl rehearse` гоняет шаги сценария в свежем дереве, а оно делит git-ссылки с живым репозиторием, как любой worktree. Шаг исполнителя `git -C "$D" tag -f deployed HEAD` выполнился с пустой переменной: каждая строка блока sh это отдельный процесс, и значение из строки выше до неё не дожило. Пустой `-C` означает текущий каталог, то есть свежее дерево, и команда сдвинула настоящий тег `deployed` на коммит ветки задачи. Исполнитель заметил и вернул тег на значение из origin.

### Осложнение

Тег `deployed` держит окно выката: сдвинутый молча, он меняет состав следующего поезда и диапазон, по которому shipctl выбирает команды выката. Обкатка обещает чистое окружение (свежее дерево, временный HOME), а теги, ветки и конфиг репозитория у неё общие с живым. Та же ловушка у любого сценария, который трогает ссылки git.

### Вопрос

Гонять шаги в отдельном клоне вместо worktree либо оставить worktree и отбивать шаги, меняющие ссылки вне своего дерева?

### Гипотеза

Шаг сценария обкатки не может сдвинуть тег или ветку живого репозитория, какой бы командой он ни был.

## Что дал разбор 2026-10-27

Обход кода и истории. Правки после 2026-09-19 нет. Обкатка заводит дерево
`git worktree add --detach` (internal/freshtree/freshtree.go:363), теги, ветки
и конфиг у неё общие с живым репозиторием, изолированы только окружение и HOME
(freshtree.go:99-118). Шаги идут отдельными `sh -c`
(tools/taskctl/rehearse.go:210-213) без гварда на команды над ссылками;
подсказка DK-689 о построчном sh это подсказка, не рубеж. Сторож записи
check-tree-write.py сам заявляет, что правка через Bash ему не видна.

Цена тихого сдвига тега `deployed` шире одного поезда. Окно `deployTag..main`
держит состав поезда (tools/shipctl/ops.go:720-724, 843), очередь Check мечет
строки как выкаченные (ops.go:919-930), strays-ворота роняют слияние по
ложному окну (ops.go:1026-1028), раскладка компонентов выката идёт по неверному
диффу (ops.go:1691-1698), а следующий ship разносит сдвинутый тег `push -f`
в origin.

Дублей нет. DK-1060 (архив, закрыт 2026-09-19) закрывал сам инцидент, сценарий
той задачи строил песочницу своим `git init`. Ближайшие открытые строки других
поверхностей: DK-1113, DK-1411, DK-1338, DK-1480, черновики DK-1330 и DK-1452
(изоляция прогонов, не ссылки). Прецедент отдельного репозитория в проекте
есть. Стенд самопроверки testenv.py заводит копию своим git-репозиторием;
прецедента `clone --shared` нет.

Условий, посильных только человеку, не нашёл. Доступов, секретов и
невозвратных шагов наружу у задачи нет.

## Развилки

- «кейсы»: какие пользовательские кейсы у DK-1061? рекомендую сбалансированный: узкий закрывает только симптом тега, а широкий тянет замер накладных расходов отдельной темой
  - решает: человек
  - рекомендация: сбалансированный состав, 3 кейса: (1) шаг сценария с git-командой над ссылками не двигает теги и ветки живого репозитория; (2) прогон обкатки не меняет окно выката deployTag..main, тег deployed на месте; (3) шаг с пустой переменной в аргументе падает внутри дерева обкатки с диагностикой, живой каталог не задет
  - вариант: узкий состав, 1 кейс: (1) тег deployed не сдвигается прогоном обкатки
  - вариант: широкий состав, 5 кейсов: (1) ссылки живого репозитория не двигаются шагами; (2) окно выката не меняется прогоном; (3) пустая переменная валит шаг внутри обкатки; (4) конфиг и настройки git живого репозитория не меняются обкаткой; (5) накладные расходы изоляции в допуске, сценарий класса DK-1060 проходит новой дорогой
- «изоляция ссылок»: чем обкатка изолирует git-ссылки живого репозитория?
  - решает: исполнитель
  - рекомендация: отдельный клон для обкатки по прецеденту testenv (своя копия репозитория, свои refs), worktree остаётся у слияния и regcheck: гвард по тексту команды дыряв, сторож Bash не видит
  - вариант: оставить worktree и ставить гвард на шаги, трогающие ссылки вне дерева
  - источник: код internal/freshtree/freshtree.go:363
- «пустой шаг»: что делает шаг обкатки с пустой переменной в аргументе?
  - решает: исполнитель
  - рекомендация: шаг с пустой переменной в аргументе git падает отказом с диагностикой внутри обкатки, рядом с подсказкой DK-689 о построчном sh
  - вариант: оставить поведение sh как есть, пустые аргументы молча склеиваются
  - источник: код tools/taskctl/rehearse.go:186

## DoD

Прогон обкатки с шагом `git tag -f deployed HEAD` (и веткой вместо тега) не
меняет ни одной ссылки живого репозитория. Тег, ветки и конфиг на месте,
окно выката `deployTag..main` тем же прогоном не тронуто. Шаг с пустой
переменной в аргументе падает внутри дерева обкатки с внятной диагностикой.
Тест держит пару. Сценарий над ссылками проходит, ссылки живого репозитория
неизменны.
