# DK-1121: Команды груминга не делают чат работой задачи, кнопка запуска остаётся

записан 2026-09-22
приоритет: средний

## Черновик

### Ситуация

2026-09-22, груминг DK-879 из свободного чата дашборда (chat-5). После `taskctl set DK-879` реестр `~/.devkit/sessions.log` получил строку с источником «работа», и строка доски пришла с полями run: chat, run_busy: true. Вместо кнопки «Выполнить» у строки стоял «Стоп». Перечень touchCmds в tools/taskctl/touch.go считает работой add, move, close, ask, fail, set, file, review, dep и progress. Комментарий к taskChats в tools/dashboard/chats.go говорит обратное: груминг, привязка рукой и разговор о задаче строку не присваивают. Привязку снял ручкой POST /api/projects/{p}/sessions/{sid}/task с пустой задачей, после этого поля run у строки пропали.

### Осложнение

Каждый груминг из чата зовёт add и set, и разговор становится работой над строкой. Пока чат жив, у строки «Стоп» вместо запуска, и кнопкой конвейер не поднять. После смерти чата кнопка становится «Продолжить» и ведёт в разговор разбора, исполнителя она не поднимает. Такое случается на каждой задаче, оформленной из чата; оформление с экрана черновика этого не задевает.

### Вопрос

Какие команды остаются работой: move в In progress, ask, fail, review и этапы agentctl stage, а add, set, file, dep и progress уходят из перечня? Нужна ли запись «снята» на add --id, и старые чаты разбора отпустят строки без руки?

### Гипотеза

Задача, оформленная или поправленная из чата, стоит в Backlog с кнопкой «Выполнить», а чат разбора в списке чатов остаётся разговором о задаче без признака работы.

## Развилки

- «кейсы»: какие пользовательские кейсы у DK-1121? рекомендую сбалансированный: узкий роняет кейс (4), с которым человек столкнётся руками сразу после выката, а кейс (5) широкого это сам предмет развилки про состав перечня, а не отдельный путь
  - решает: человек
  - рекомендация: сбалансированный состав, 4 кейса: (1) груминг из свободного чата зовёт add --id и set, строка остаётся в Backlog с кнопкой «Выполнить»; (2) исполнитель берёт строку командой move в In progress, привязка ставится, «Стоп» на строке законен; (3) разговор о задаче правит метаданные командами set, file и dep, строка своей не становится; (4) строки, за которыми привязку записали старые чаты разбора, отпускаются без ручки
  - вариант: узкий состав, 2 кейса: (1) груминг из свободного чата зовёт add --id и set, строка остаётся в Backlog с кнопкой «Выполнить»; (2) исполнитель берёт строку командой move в In progress, привязка ставится, «Стоп» на строке законен
  - вариант: широкий состав, 5 кейсов: (1) груминг из свободного чата зовёт add --id и set, строка остаётся в Backlog с кнопкой «Выполнить»; (2) исполнитель берёт строку командой move в In progress, привязка ставится, «Стоп» на строке законен; (3) разговор о задаче правит метаданные командами set, file и dep, строка своей не становится; (4) строки, за которыми привязку записали старые чаты разбора, отпускаются без ручки; (5) сессия, отчитывающаяся одним progress без move, остаётся видна работой
- «перечень»: какой состав остаётся работой над строкой?
  - решает: человек
  - рекомендация: сузить до move в In progress, ask, fail и review, убрав add, set, file, dep и progress: ни один живой тест не держится за эти пять имён, а взятие строки всё равно идёт через move
  - вариант: сузить, но оставить progress: отчёт о ходе работы по смыслу ближе к ask и fail, чем к правке метаданных
  - вариант: перечень не трогать, а научить утилиту различать сессию разбора и исполнителя
  - источник: код, tools/taskctl/touch.go:20 и tools/dashboard/registry.go:262, работой строку делает слово источника в реестре
- «снята»: нужна ли запись «снята» на командах разбора?
  - решает: исполнитель
  - рекомендация: записи снятия не заводить: у сужённого перечня привязка на add --id и set не появляется вовсе, и отвязывать нечего
  - источник: код, internal/sessions/sessions.go:218, запись «снята» гасит уже поставленную привязку
- «отвязка»: заводить ли команду отвязки сессии от строки?
  - решает: исполнитель
  - рекомендация: своей команды не заводить: привязку снимают кнопка «Стоп» и ручка сессии, а строки, за которыми привязку записали старые чаты, разбираются ими же
  - источник: код, tools/dashboard/runchat.go:92, отдельной команды отвязки в taskctl нет
- «подхват»: чем привязывается сессия, подхватившая строку, которая уже стоит в In progress?
  - решает: исполнитель
  - рекомендация: отдельной правки не просит: привязку подхватившей сессии ставит agentctl своим перечнем (pick, run, stage), и сужение taskctl его не задевает
  - источник: код, tools/taskctl/ops.go:555, повторный move в тот же статус отбивается ошибкой
