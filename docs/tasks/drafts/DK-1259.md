Тик зовёт shipctl merge на строку in-progress каждые пять минут

Ситуация. У DK-1072 в «Ходе работы» с 23:41 до 00:17 легло пятнадцать строк «Слияние: shipctl merge». Шаг между ними пять минут. Строка доски показала «этап: слияние, круг 62». Ветка задачи в это время была пуста или в разработке, сливать было нечего.

Осложнение. Запись этапа ложится в файл задачи в основном чекауте. На живой строке настоящие этапы тонут под этим шумом. В чекауте остался файл .devkit/merge-queue.json.lock.

Вопрос. Кто зовёт merge по тику на строку, которая не в Check и не в очереди выката? Почему зов оставляет этап в ходе работы, ничего не слив?

Гипотеза. Разлив очереди на тике devkitctl watch берёт строку по устаревшему состоянию очереди слияния. Хук записи этапов пишет «слияние» на любой запуск shipctl merge и с исходом не сверяется.

Разбор 8 ноября. Фактура ниже сверена с main d0e7ae42d. Инцидент DK-1072 на
этом коде не воспроизводился, механизм остаётся гипотезой, уточнённой по
текущему коду. Разбор родился из вопросов про последовательность событий,
смысл «устаревшего состояния» и признак готовности слияния.

Последовательность. Строка DK-1072 стоит в In progress, не в Check и не в
очереди выката, ветка пуста или в разработке. Тик devkitctl watch каждые
пять минут делает разлив очереди слияния. Разлив считает строку кандидатом
и зовёт shipctl merge. Сливать нечего, merge ничего не делает. В main
правки задачи не уезжали, коммита слияния не было, ложным был только этап
на строке. Хук записи этапов срабатывает от факта запуска shipctl merge,
с исходом не сверяется и пишет в файл задачи строку «Слияние: shipctl
merge». С 23:41 до 00:17 таких записей легло пятнадцать, доска показала
«этап: слияние, круг 62», в чекауте остался файл .devkit/merge-queue.json.lock.

Механизм разлива. Разлив это shipctl queue --drain, сторож зовёт его раз в
пять минут (queue.go:40), за один проход уходит одна ветка (queue.go:553).
Состав пересчитывается на каждом прогоне из живой доски (queue.go:536),
залежавшегося списка отбора нет. Кандидатом становится любая строка In
progress, на ветке которой есть хоть один кодовый коммит сверх main
(queue.go:244; queueCode в queue.go:290 пропускает только коммиты доски и
снятия). Готовность разработки и ревью при подборе не спрашивается, то же
подтверждает статус №072 очереди. Отдельно живут отметки файла
.devkit/merge-queue.json (queue.go:47), в них проверенный SHA, блокировка
и ожидание regcheck. Стирание queueClear (queue.go:410) зовётся после
слияния, возврат строки в разработку отдельного стирания не имеет.
Уточнение гипотезы. Список кандидатов всегда свежий, устаревает решение,
что строка годится для слияния. Слабый признак отбора не гаснет при
возврате строки в работу, отметки переживают смену состояния в общем файле
основного чекаута.

Метки готовности. Всё, что отличает готовую строку от живой разработки,
уже лежит в дереве задачи, отбор это не спрашивает. В файле задачи
docs/tasks/<ID>.md на фичеветке лежат раздел «Ревью» с уровнем и
замечаниями (открытые замечания читает trace.OpenReviewNotes, gates.go:262),
пометки-исключения ворот (gates.go:154) и ограждение файла (оборванное
ловит cutTaskFile, ops.go:1190). Merge читает файл из worktree задачи,
основной чекаут на main этих правок не видит (ops.go:1144, комментарий у
ops.go:1184). В доске docs/TASKS.md лежат секция строки, провал и рёбра
(ops.go:1121). В git лежат незакоммиченное в worktree как признак живой
доработки (ops.go:1103), кодовые коммиты сверх main и свежесть main
(ops.go:1218). В журнале .devkit/log в дереве задачи лежит след regcheck
(gates.go:21, gates.go:137, действует для bug-строк). Ворота, читающие эти
метки, встроены в shipctl merge у ops.go:1108-1122. Вынос их в общую
функцию и команду shipctl ready положил LLD DK-460 решение 1, строка
DK-474 стоит в Backlog за DK-473 (разбор в DK-972, строки 107-111).

Направление исправления. Признак готовности слияния проверять при подборе
кандидатов в поезд по актуальному дереву задачи, до заказа merge. Признак
держать производным от машинных меток, правило DK-400.1 запрещает держать
рубеж полем. Поставленный флаг забывается снять, и устаревшая очередь
переезжает в новое место. Производный признак гаснет сам. Новый коммит
после regcheck или открытое замечание снимает готовность на следующем
обходе. Окно между проверкой и слиянием остаётся, цикл пять минут. Живую
доработку и незаписанные замечания перепроверяют ворота merge перед самой
операцией, того же требует строка №022 очереди.

## Пользовательские сценарии

### СЦ-1

Ситуация: Строка стоит в In progress, на её ветке есть кодовые коммиты
сверх main. Ревью не закрыто или следа ревью нет.
Действие: Разлив очереди идёт очередным тиком сторожа.
Результат: Merge не заказывается. В «Ходе работы» строки не появляется
запись «Слияние: shipctl merge».
Польза: Настоящие этапы живой строки читаются без ручной фильтрации шума.
Рекомендация: Включить. Это записанное направление исправления и сам
предмет черновика.
Ограничение: Признак готовности выводится из машинных меток. Отдельное
поле не заводится (DK-400.1).
Источник: Слово пользователя (ситуация из черновика).

### СЦ-2

Ситуация: Строка вернулась из проверки в In progress. В файле
.devkit/merge-queue.json у неё остался проверенный SHA прошлой готовности.
Действие: Следующий обход разлива собирает кандидатов.
Результат: Merge по старому решению не заказывается. Готовность выводится
из текущего дерева задачи заново.
Польза: Устаревшее решение не переживает возврат строки в работу.
Рекомендация: Включить. Возврат строки в разработку сейчас отдельного
стирания отметок не имеет.
Ограничение: Отметки файла остаются носителем блокировки и ожидания.
Меняется только отбор кандидатов.
Источник: Вывод из примера (разбор: queueClear работает после слияния,
возврат стирания не имеет).

### СЦ-3

Ситуация: Строка в In progress, ревью закрыто, след regcheck свежий, дерево
задачи чистое.
Действие: Разлив очереди идёт тиком сторожа.
Результат: Merge заказывается в тот же проход, слияние едет штатно.
Польза: Исправление не тормозит штатный путь готовой ветки.
Рекомендация: Включить. Без этого сценария правка рискует удержать готовые
ветки в очереди.
Ограничение: Окно между проверкой и слиянием остаётся. Живую доработку и
незаписанные замечания перед операцией перепроверяет merge.
Источник: Предложение агента (находка обхода о цене переноса проверок).

### СЦ-4

Ситуация: В индексе репозитория лежит файл .devkit/merge-queue.json.lock.
Он въехал коммитом с закрытием чужой задачи.
Действие: Правка убирает файл из индекса и закрывает его гитигнором.
Результат: git ls-files больше не показывает замок. Новые клоны его не
получают.
Польза: Машинное состояние конвейера одной машины не разъезжается по чужим
клонам.
Рекомендация: Включить отдельной мелкой карточкой. Это тот же мусор, на
который указывает осложнение черновика.
Ограничение: Замок на диске остаётся. Меняются индекс и гитигнор.
Источник: Предложение агента (находка обхода, git ls-files).
