# DK-1269: TestCmdRunBusyLock красный на main: синтетика без glm-code.toml

записан 2026-10-01
приоритет: высокий

## Черновик

### Ситуация

Замечено 2026-10-01 на слиянии DK-1262: полный прогон shipctl merge упал на
go:taskctl, TestCmdRunBusyLock (tools/taskctl/run_test.go:101) печатает
«нет профиля харнеса .../devkit/kit/harness/glm-code.toml». Тот же тест
падает и на чистом main обёрткой devkitctl test tools/taskctl -run
TestCmdRunBusyLock, ветка DK-1262 taskctl не трогает. Тест ставит профиль
сам (t.Setenv(taskhead.HarnessEnv, "glm-code"), run_test.go:44), от сессии
и окружения не зависит. run_test.go последний раз менялся 2026-09-27
(DK-1194), profile.go 2026-09-22 (DK-935), kit/harness/glm-code.toml в
чекауте есть.

Вторая краснота того же дня, CoreBudgetTest (tools/devkitctl/rules_test.py:516):
ядро правил RULES.core.md на main 5670 символов при бюджете 5500, файл не менялся
с 2026-09-14, тест с 2026-09-17; полный прогон сюиты даёт ровно один провал,
этот. Доске это тоже стоит на пути слияний с полным прогоном.

### Осложнение

Каждое слияние гоняет полный прогон и умирает на первом провале, конвейер
доски стоит: DK-1262 пришлось сливать с суженным --test по тронутым
компонентам. Любая следующая ветка упрётся в то же.

### Вопрос

Что сломалось между 2026-09-27 и 2026-10-01: раскладка стенда перестала
копировать профили харнесов в синтетическое дерево, или glm-code.toml
получил поле, которого синтетика не даёт?

### Гипотеза

Полный прогон на main снова зелёный, слияния идут без сужения --test.
