# DK-1284: Закладка «Затраты» на форме задачи с живым расходом токенов и ценой

записан 2026-10-02
приоритет: средний

## Черновик

### Ситуация

После выполнения задачи я не вижу, во сколько она реально обошлась в токенах и деньгах. Сегодня затраты известны одной буквой размера (S/M/L/XL, шкала RANKING.md), и это догадка до исполнения. Фактический расход известен только по транскриптам сессий, и смотреть их каждый раз неудобно. Хочу, чтобы на форме задачи была закладка «Затраты» с таблицей, где:

- строки это типы работ (код, ревью, проверка, грумминг, оркестрация и т.д.);
- колонки это входящие токены, исходящие токены и итоговая цена (для поставщиков по подписке остаются только токены, routerai платит ещё и деньгами);
- итоговая строка с суммой по каждому столбцу.

Таблица обновляется в реальном времени по ходу работы. Заход агента, ревью и прогон проверки добавляют строку или досчитывают итог, диспетчерская сессия суммирует затраты субагентов.

### Осложнение

Данные сегодня есть в транскриптах (журнал `~/.devkit/sessions.log`, usage каждого вызова), но не агрегированы по задаче и не привязаны к типам работ. Вызовы утилит идут от разных субагентов, и оркестрация (главный контур) тоже даёт заметный расход, его надо отделять от продуктивной работы. Нужен инструмент сбора затрат, который понимает, какой этап задачи сейчас идёт и сколько токенов на него ушло.

### Вопрос

Собирать затраты из журналов сессий асинхронно (опрашивать раз в N ходов) или считать в реальном времени на каждом инструментальном вызове? Как отделить расход диспетчера от расхода субагентов? Показывать цену только для открытых биллингов (routerai) или для всех, где есть цена токена в конфиге?

### Гипотеза

На форме задачи появляется третья закладка «Затраты» рядом с «Задача» и «Чат». На ней таблица с колонками: Этап работы, Входящие токены, Исходящие токены, Цена (для провайдеров с известной ценой). Ниже строка итога. Данные собирает фоновая утилита (или расширение вывода какого-то из существующих инструментов), которая читает связку задача-сессия по файлу задачи и подтягивает usage из реестра сессий. Обновление по живому ходу задачи идёт через опрос на каждом инструментальном вызове или по тику с периодом. Типы работ берутся из этапов шаблона (DK-972) или из реестра этапов сессии. Порог точности: для открытых биллингов плюс-минус доллар достаточно, для подписочных провайдеров достаточно токенов с примерной аппроксимацией дневной цены. Отдельный вопрос: повторный прогон (перезапуск сессии задачи) не удваивает затраты, а обновляет.
