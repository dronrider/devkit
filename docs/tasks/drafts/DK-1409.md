# DK-1409: askpass отвечает на вопрос о подлинности хоста ssh

записан 2026-10-18
приоритет: высокий

## Черновик

### Ситуация

18 октября 2026, слияние DK-1325: shipctl merge четыре раза падал на git fetch с «Host key verification failed», живой git fetch тем же временем проходил. gitrun (DK-697) зовёт ssh с -o BatchMode=yes, чтобы сессии агента не висели на вопросах. У машины записи github.com в known_hosts нет. Живой вызов выручает SSH_ASKPASS (.devkit/askpass.py, DK-772): на вопрос «are you sure you want to continue connecting» помощник отвечает, соединение проходит, но ключ в known_hosts не ложится, и каждый вызов спрашивает заново. Утренние пуши сессии поэтому работали, а BatchMode-вызовы shipctl нет.

### Осложнение

Автосогласие с вопросом о подлинности хоста это TOFU на каждом соединении: в моменты, когда на github.com:22 отвечал кто-то чужой (мигающий перехват, четыре отказа за десять минут), ключ перехватчика прошёл бы молча и пуш ушёл ему. Пакетный режим gitrun честен, но из-за отсутствующей записи ломает весь конвейер слияния.

### Вопрос

Помощнику askpass запретить отвечать на вопросы о подлинности хоста (отдавать неуспех и валить соединение), а машине один раз разложить настоящий ключ github в known_hosts? Кто и как кладёт ключ: установщик devkit, devkitctl doctor или человек.

### Гипотеза

askpass перестаёт подписывать неизвестные хосты, doctor при нахождении пустой записи зовёт человека с командой проверки отпечатка против опубликованного, соединения в BatchMode становятся единственным путём и перехват начинает падать громко.
