# DK-1511: дежурный поднимается по фразе в прозе хода работы

записан 2026-10-30
приоритет: средний

## Черновик

### Ситуация

2026-10-30 в 05:56 тик поднял дежурного по DK-1442 с причиной «по строке без этапа». Причина собрана из прозаической строки 62 файла docs/tasks/DK-1442.md: «...стреляла эскалация дежурному по строке без этапа». Строка описывает исходный инцидент 2026-10-24, который чинит сама DK-1442. Разобрав журналы, дежурный реального сбоя за поводом не нашёл. Записей по DK-1442 в журнале инцидентов нет, строка стоит в Check по проекту. Агентская половина сценария прогнана зелёной и отмечена в 05:54 (glm-5.3), отметки smoke ещё нет, close и merge не проходят из-за неё. Фантомная метка воспроизводится командой из корня репозитория.

```console
$ python3 -c "import sys; sys.path.insert(0, 'tools/devkitctl'); import duty; print([m[:2] for m in duty.task_marks('.') if m[0] == 'DK-1442'])"
[('DK-1442', 'по строке без этапа')]
```

### Осложнение

Функция parse_mark в tools/devkitctl/duty.py принимает любой текст после фразы «эскалация дежурному» в разделе «Ход работы». Дата перед меткой и двоеточие после неё не обязательны, а настоящую запись исхода пишет task_record из tools/devkitctl/watch.py строкой «- <дата> эскалация дежурному: <причина>.», и от прозаической строки её отличает только форма. Каждое появление фразы в прозе поднимает сессию дежурного, и причина заказа оказывается куском описания. Одна сессия уже поднялась, подпись «по строке без этапа» закрылась этим черновиком. Фраза остаётся в файле задачи на весь срок жизни строки, а состояние дежурного (~/.devkit/watch.duty) машинное, на другой машине или после сброса подъём повторится.

### Вопрос

Чинить ли разбор parse_mark под форму записи task_record (дата перед меткой, двоеточие после) или уйти от совпадения сменой самой метки? Править ли прозу DK-1442, если парсер починят?

### Гипотеза

Дежурный поднимается только по записям исхода, написанным task_record, а проза раздела «Ход работы» его не поднимает. Исход пока ждёт только агент: разбор вёл дежурный, пользователь не участвовал.

## Контекст обсуждения

Разбор сделал дежурный агент 2026-10-30. Слой эскалации работает без прав на правки, исправление уедет конвейером задачи. Проверено по журналам: ~/.devkit/watch.duty хранит подпись «по строке без этапа» попыткой 1, в журнале инцидентов записей по DK-1442 нет. Прозу файла DK-1442 на предмет фразы не правил, чтобы не задеть идущий Check.
