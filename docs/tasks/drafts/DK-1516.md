# DK-1516: Разбужденная строка работает невидимкой и закрывается без коммита

записан 2026-10-30
приоритет: средний

## Черновик

### Ситуация

DK-538 припаркована вопросом 2026-10-30 в 11:03 (коммит 00900dd11), человек
ответил около 13:46: «хвост уезжает в DK-502, DK-538 закрыть». Коммит
разбуждения 85911b2b3 (13:45:59) унёс строку доски и закрытую запись
ожидания, а строку ответа taskctl decide вписал в файл задачи после коммита,
незакоммиченной. Тик 13:49:21 получил отворот запуска по ребру [после
DK-502], но следующий taskctl run в ту же секунду прошёл. Исполнитель
поднялся и работал около часа, не оставив ни записи этапа, ни хвоста
.devkit/task-538.tail, ни плана. Тики 13:54 и 13:59 продолжали отворотить
запуск той же строки при живом исполнителе. В 13:59:59 он закрыл DK-538 в
архив (taskctl close, успех) сразу после отворота ship (код 1). DoD 5 и
абзац про выкачанную механику легли в DK-502, приписка DK-1514 переехала
вместе с ними, развилка «сброс» оформлена строкой DK-1515 (коммит 4ad409d8f).
Итог закрытия остался в рабочем дереве без коммита. Правки docs/TASKS.md,
docs/TASKS-archive.md, docs/tasks/DK-502.md и переезд файла DK-538 в архив
лежали грязными до коммита исполнителя.

### Осложнение

Сторож не видит исполнителя побужденной строки и эскалирует дежурному
«состояние неизвестно» по живой работе. Разбор 2026-10-30 поднялся по строке,
которая в тот момент исправно закрывалась. Ворота запуска отворотят строку с
уже поднятым исполнителем, и каждый тик повторяет отказ. Решение человека и
итог его исполнения лежат незакоммиченными, а грязные досочные файлы
отбивают круги слияния. Дежурному это стоило окна разбора и столкновения
ID. Писатель черновиков дважды выдал номер DK-1514, занятый припиской,
а taskctl id называл свободным DK-1515.

### Вопрос

Почему исполнитель побужденной строки не оставляет записи этапа, по которой
сторож отличает живую работу от пропавшей? Почему ворота запуска
не видят уже поднятого исполнителя и повторяют отворот? Кто коммитирует ответ
decide и итог close, и почему ship перед close ушёл с отворотом? Почему у
черновиков два счётчика и писатель выдает занятый ID?

### Гипотеза

Пользователь хочет, чтобы побудка с ответом поднимала видимого исполнителя.
Запись этапа кладётся тем же тиком, ворота запуска видят живую работу.
Ответ и закрытие едут коммитом сразу по правилу доски, а свободный номер
выдаёт один счётчик. Пока этого нет, дежурный разбирает ложные пропажи и
грязное дерево держит очередь.

## Контекст обсуждения

- Ответ человека дословно (развилка «остаток», 2026-10-30): «хвост уезжает в
  DK-502, DK-538 закрыть: DoD 1-4 сделаны выкачанной 28 октября DK-1466,
  единственный живой пункт это предложение льготного часа в предупреждении
  DK-502».
- Ребро «после DK-502» по решению DK-933.2 снимается слиянием предпосылки.
  Закрытие строки ребро не снимает, и отвороты ворота продолжат видеть.
- Родственная находка DK-1260: побудка без текста ответа. Здесь ответ есть,
  но невидимо исполняется.
- Наблюдал дежурный агент 2026-10-30 по журналу .devkit/log, git истории и
  рабочему дереву; время 13:45-14:05. Единственный след исполнителя в файле
  задачи это запись «Токены: ходов 60, вывод 97k...».
- Незакоммиченный итог закрытия на момент записи принадлежит сессии
  исполнителя, дежурный его не трогал.
