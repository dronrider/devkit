# DK-1554: Макеты доступны для согласования в любом проекте с devkit
источник: thought

записан 2026-11-02
приоритет: средний

## Черновик

### Ситуация

Пользователь сообщил 2026-11-02, что агент подготовил HTML-макет и открыл его на машине с запущенным дашбордом. Пользователь работает с дашбордом с другой машины и не может посмотреть результат таким способом. В обсуждении предложен просмотр макетов в центральной панели дашборда. Для этого предложены список задач с макетами и выбор конкретного макета при открытии.

Связанный черновик DK-1536 посвящён обязательной подготовке и согласованию дизайна при разработке UI. В настоящей записи сохранено обсуждение хранения, доставки и просмотра этих материалов.

### Осложнение

Локальный файл или браузер машины агента недоступен пользователю на другом устройстве. Агент считает макет предъявленным, хотя пользователь не может его открыть и согласовать.

Пользователь отдельно уточнил, что это расширение devkit. Промпты и скиллы должны работать из консоли в любом подключённом проекте. Решение, зависящее от запущенного дашборда или средств конкретного агентского клиента, этому требованию не соответствует. Пользователь хочет хранить материалы дизайна в Git.

В мобильной навигации дашборда уже стоят задачи, сессии, черновики и LLD. Ещё один пункт не помещается. По одной задаче может быть несколько макетов. Требуется доступ к каждому из них.

### Вопрос

- Какой общий формат комплекта выбрать для макетов, ресурсов, снимков и описания? Подходит ли HTML как основной формат и какие альтернативы поддержать без обязательной интеграции с Figma?
- Где хранить материалы проекта в Git, как связать их с задачей и различать отдельные макеты, альтернативы, редакции и размеры экрана?
- Как доставить результат пользователю при работе из удалённой консоли без дашборда? Как выбрать доступный способ просмотра и проверить его до предложения согласовать макет?
- Нужен ли отдельный скилл designer, где подключать его к порядку работы с UI и какие условия проверять командой devkit?
- Как показывать макет из рабочей ветки до слияния, в том числе когда агент и сервер дашборда работают на разных машинах?
- Как записывать согласование конкретной редакции из консоли и дашборда? Что происходит после изменения согласованного макета?
- Как разместить вход к макетам в мобильной навигации? Объединять ли их с LLD в разделе «Материалы»?
- Что пользователь увидит по ссылке на GitHub и достаточно ли снимков в README для просмотра без отдельного хостинга?

### Гипотеза

Пользователь хочет, чтобы агент готовил и предъявлял доступные макеты в любом проекте с подключённым devkit. Исходники и материалы дизайна сохраняются в Git. Работа из консоли поддерживается независимо от дашборда и конкретного агентского клиента. Через дашборд пользователь может просмотреть те же материалы в центральной панели и выбрать нужный макет задачи.

## Контекст обсуждения

Требования пользователя. Расширение относится к devkit целиком. Задействованные промпты и скиллы должны работать и просто в консоли для любого подключённого проекта. Пользователь не хочет привязки к собственным решениям Claude или Codex. Обязательная интеграция с Figma или несколькими системами усложняет devkit. HTML пока рассматривается как вариант, окончательный выбор формата пользователь не делал.

Предложения агента, которые пока не утверждены пользователем:

- Общий формат материалов и операции devkit, поверх которых дашборд предоставляет просмотр и согласование. Условное имя команды designctl пока рабочее.
- Скилл designer описывает подготовку, проверку, сохранение и предъявление макета общими командами. Проверяемые условия контролируются инструментом. При подключении проекта инструкции устанавливаются обычной автоматикой devkit.
- Каталог docs/design/<ID задачи>/ с README, описанием набора и отдельными каталогами макетов и редакций. Метаданные и согласования хранятся в файлах репозитория.
- Для веб-интерфейсов комплект HTML/CSS с локальными ресурсами и снимками экрана. Просмотр без сборки, установки пакетов и локального сервера агента. Первая версия без JavaScript; показ HTML в дашборде через изолированный iframe.
- Другие редакторы могут давать изображения и ссылку на исходник. Снимок результата сохраняется в Git.
- Для согласования создаётся неизменяемый снимок комплекта с идентификатором содержимого. Изменение макета требует нового согласования. Снимок рабочей ветки доступен до слияния. Передача на сервер дашборда относится к интеграции дашборда.
- В форме отдельно выбираются макет, редакция и ширина просмотра. Вход есть из задачи. Общий список группируется по задачам. Вкладка «Материалы» объединяет LLD и макеты, сохраняя четыре пункта навигации.
- Замечания на первом этапе остаются в разговоре задачи со ссылкой на редакцию. Комментарии поверх элементов можно рассмотреть позже.
- Сначала общий сценарий devkit из консоли в отдельном подключённом проекте, затем дашборд поверх тех же файлов и команд.

### Устройство расширения devkit

Ниже сохранено развёрнутое предложение агента. Пользователь подтвердил область применения к devkit; остальные решения пока предложены для обсуждения.

Devkit задаёт формат комплекта и общие операции. В репозитории проекта лежат исходники макетов, ресурсы, снимки экранов, описание набора, связь с задачей, редакции и сведения о согласовании. Дашборд читает те же материалы и вызывает те же операции, которыми агент пользуется в консоли. Отдельная база дашборда для них не требуется.

Условная команда designctl создаёт набор, выводит список макетов, проверяет комплект, подготавливает конкретную версию к согласованию и записывает решение пользователя. Имя команды и точный состав подкоманд пока не выбраны.

Скилл designer задаёт порядок работы. Агент изучает существующий интерфейс и ограничения, готовит нужные экраны и состояния, проверяет отображение на телефоне и компьютере, сохраняет исходники и снимки, предоставляет комплект для просмотра. После этого он передаёт доступную ссылку или другой способ открытия и формулирует предмет согласования.

В скилле описываются общие команды devkit. Конкретный агентский клиент может использовать собственные средства подготовки дизайна при соблюдении итогового формата. Инструкции устанавливаются обычным подключением проекта. Скилл нужно включить в существующий порядок работы с задачами интерфейса, иначе агент может его не вызвать. Фазу подключения ещё нужно обсудить вместе с DK-1536.

Скилла недостаточно для обязательных условий. Общая команда проверяет наличие файлов, полноту ресурсов, наличие снимков и возможность предъявить результат пользователю. Какие проверки можно выполнить автоматически для каждого способа доставки, ещё нужно определить.

### Пример хранения и выбора макета

Предложенный пример каталога одной задачи:

```text
docs/design/DK-919/
  README.md
  design.json
  activity-row/
    r1/
      index.html
      desktop.png
      mobile.png
    r2/
      index.html
      desktop.png
      mobile.png
  activity-card/
    r1/
      index.html
      desktop.png
      mobile.png
```

Макет обозначает экран, компонент или альтернативный вариант решения. Редакция обозначает изменение конкретного макета после замечаний. Размер просмотра задаётся отдельно. Телефонное представление адаптивного экрана обычно остаётся тем же макетом.

В design.json предлагается хранить названия, пути, порядок и сведения о согласовании. README описывает набор для человека, который открыл каталог через GitHub или работает без дашборда. Точный формат описания пока не выбран.

В дашборде предложены выпадающий список макетов, отдельный выбор редакции и переключатель ширины. В задаче прямой вход «Макеты (3)» находится в блоке связей. Список материалов группируется по задачам, одна строка показывает задачу, количество макетов и отметку «Ждёт согласования». При открытии пользователь сразу видит выбранный макет.

Предложенная навигация проекта сохраняет четыре пункта: «Задачи», «Сессии», «Черновики», «Материалы». Внутри «Материалов» переключатель «Все / Макеты / LLD». Основание предложения: пятый пункт не помещается на телефоне, а у LLD уже есть список, отдельная форма и связь с задачей.

### Просмотр в разных окружениях

Сохранение файла ещё не означает предъявление результата. Агент должен предоставить способ, доступный пользователю. Если удалённый канал не настроен, агент сообщает об этом и предлагает конкретный вариант доставки.

| Где работает пользователь | Предложенный способ просмотра |
|---|---|
| На машине с checkout проекта | Открыть HTML или запустить локальный просмотр |
| Через удалённую консоль | Получить комплект для скачивания либо открыть просмотр через туннель |
| Через дашборд | Открыть комплект в центральной панели |
| На GitHub | Посмотреть снимки и описание; интерактивный просмотр требует публикации |

Для дашборда браузер пользователя получает HTML и все ресурсы через сервер по обычному HTTPS-адресу. Пути file:// и адрес localhost машины агента не обеспечивают просмотр на другом устройстве.

Предложенный порядок предъявления версии:

1. Агент сохраняет и проверяет комплект файлов.
2. Команда devkit создаёт неизменяемый снимок комплекта с идентификатором содержимого.
3. При использовании дашборда сервер получает снимок и возвращает ссылку на него.
4. Агент передаёт пользователю доступный способ просмотра этой версии.

На одной машине снимок можно копировать из worktree. На разных машинах предложены передача комплекта через авторизованный API или получение из доступного Git-коммита. Просмотр не должен требовать слияния ветки. Ссылка на согласование открывает предъявленную версию, даже если агент уже продолжил работу.

После уточнения пользователя агент пересмотрел границу решения. Общая возможность devkit включает подготовленный и проверенный комплект, его идентификатор и запись согласования. Передача на сервер дашборда относится к интеграции дашборда. Сценарий из консоли должен работать без запущенного сервера.

### Согласование редакции

Предложены состояния «Черновик», «На согласовании», «Нужны изменения», «Согласован». При согласовании записывается идентификатор просмотренного содержимого. После изменения макета новая редакция требует нового согласования, предыдущая остаётся доступной.

В консоли агент предъявляет конкретную редакцию и после явного решения пользователя записывает согласование общей командой devkit. Дашборд предоставляет кнопки для той же операции. Замечания можно оставлять в существующем разговоре задачи со ссылкой на макет и редакцию. Комментарии поверх отдельных элементов предложено отложить.

### Выбор формата и просмотр на GitHub

Агент предложил HTML/CSS в качестве основного формата для веб-интерфейсов. В нём можно проверять реальные размеры, длинные тексты и адаптивность. Комплект открывается после клонирования репозитория. Для первой версии без JavaScript проверяются статические состояния; простые взаимодействия потребуют отдельного решения.

Предложенные ограничения: просмотр без сборки и установки пакетов, ресурсы внутри комплекта, отсутствие зависимостей от локального сервера агента. HTML в дашборде показывается в изолированном iframe без доступа к странице дашборда и его API.

Для иллюстраций, сложной графики и материалов из внешнего редактора предложены изображения и ссылка на исходник. Локальный снимок сохраняет согласованный вид в Git. Интеграция с графическим редактором остаётся необязательной.

Вместе с HTML предложено сохранять PNG и вставлять их в README. Тогда на GitHub видны макет, пояснения и история изменений без отдельного хостинга. Для интерактивного просмотра HTML нужна отдельная публикация, например GitHub Pages.

### Порядок реализации и сценарий проверки

Сначала предложено реализовать формат, общие команды, скилл и подключение к правилам проектов. Затем добавить просмотр и согласование в дашборде поверх тех же файлов и команд.

Основной сценарий проверки проходит в отдельном проекте с подключённым devkit, без дашборда. Агент подготавливает несколько макетов. Пользователь открывает их доступным способом, выбирает вариант, запрашивает правку и согласовывает новую редакцию. Исходники, снимки и согласование сохраняются в Git.

Первую реализацию предложено ограничить хранением комплектов, предъявлением снимка из рабочей ветки, выбором макета и редакции, согласованием конкретной версии и просмотром в центральной панели дашборда. Отдельный графический редактор, обязательные интеграции и комментарии на элементах экрана в этот объём не входят.

### Основания из проверок

По tools/dashboard/README.md, раздел «Экран LLD», в дашборде уже есть список LLD, отдельный экран документа и связи с задачей. В разделе об обнаружении проектов описано исключение боковых worktree. Это не доказывает невозможность чтения их файлов, но требует отдельно спроектировать выбор источника макета.

Обычная ссылка на HTML-файл GitHub показывает исходник. GitHub Pages публикует HTML/CSS/JS как сайт. Это отдельный способ размещения. Изображения можно просматривать в репозитории и вставлять в README. Источники проверки 2026-11-02:

- https://github.com/htmlpreview/htmlpreview.github.com/blob/master/readme.md
- https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages
- https://docs.github.com/en/repositories/working-with-files/using-files/working-with-non-code-files
