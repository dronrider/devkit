# DK-1577: дежурный поднимается по уже снятому отказу конвейера

записан 2026-11-03
приоритет: средний

## Черновик

### Ситуация

2026-11-03, DK-1570. Слияние отказывало пять раз с 16:46 до 17:10: в файле задачи ветки не было раздела «Сценарий проверки». Тик записал эскалацию дежурному в 17:03:55 (коммит 03eb1e728). Конвейер закрыл отказ сам: сценарий приехал коммитом 6f9350264 в 17:11:23, обкатка зелёная e91aad96b в 17:14:50, в 17:15:35 поднят ревьювер (журнал этапов ~/.devkit/runs/DK-1570-Users-rider-projects-devkit.run). Голова дежурного по этой подписи встала лишь в 17:21: подъёму мешал замок задачи, который держал конвейер (журнал .devkit/log, «чужой заход по DK-1570: exec-high (18adf49b), голова не поднимается», последний отворот в 17:15:54), и заказ через десять минут после снятия отказа всё ещё называл отсутствующий сценарий.

### Осложнение

Сессия дежурного тратится на отказ, которого уже нет. Подпись в ~/.devkit/watch.duty держит попытку без исхода, а контракт дежурного знает два исхода: вопрос человеку либо черновик. Без исхода тик поднимет дежурного ещё дважды и на потолке попыток добьёт громким зовом, и человек получит шум про снятую проблему. Лаг закономерен: голова дежурного стоит за замком задачи, замок занят, пока конвейер работает над строкой, и отказ, закрытый за время ожидания, приходит к дежурному уже снятым.

### Вопрос

Где сверять свежесть отказа: перезапускать условие записи перед подъёмом (наличие раздела в ветке ворота проверяют дёшево) либо дать дежурному третий исход «конвейер закрыл сам» по образцу возобновления у инцидентов (RESUME_MARK в tools/devkitctl/duty.py), с закрытием подписи тиком по этому исходу?

### Гипотеза

Отказ, снятый конвейером до подъёма дежурного, перестаёт тратить его сессии и не добивается громким зовом человеку. Исход пока ждёт только агент, дежурный слой; пользователь его не обсуждал.

## Контекст обсуждения

Наблюдение и разбор: дежурный агент по эскалации слияния DK-1570, сессия 2026-11-03. Артефакты снятия: коммиты ветки 6f9350264 (сценарий) и e91aad96b (обкатка зелёная), ревью идёт с 17:15:35, после него очередь слияния повторит подход сама.

Механика: заказ дежурному собирается из текста записи (duty_order в tools/devkitctl/duty.py), сверки условия с живой веткой на подъёме нет. У инцидентов конвейера (DK-1415) исход «возобновление» уже есть: строка «- Возобновление:» в «Ходе работы», которую исполняет тик. У записей из файлов задач такого исхода нет.

Рядом нашлось: подпись отказа несёт счётчик минут, и перезапись отказа с новым счётчиком проходит новой подписью. Сегодня «сессия молчит 172 минуты» и «179 минут» из одной тишины заняли две записи с отдельными попытками в ~/.devkit/watch.duty: SESSION_TAIL снимает с подписи только хвост сессии, и граница одинаковых отказов DK-1115 перезапись не узнаёт.
