# DK-1609: дежурный разбирает устаревший отказ слияния повторно

записан 2026-11-06
приоритет: средний

## Черновик

### Ситуация

2026-11-05 02:52-03:19 сторож писал в /Users/rider/.devkit/goal-watch.log отказ «слияние: в docs/tasks/DK-1570.md нет раздела «Сценарий проверки», а ship переведёт задачу в Check разом со всем поездом». Тогда раздела в файле правда не было: он въехал в main коммитом e1ccb5953 2026-11-05 03:50:14, и ветка dk-1570 его несёт, `grep -n '^## ' docs/tasks/DK-1570.md` в дереве ветки даёт строку 379, ограждения сбалансированы.

2026-11-06 13:55:01 тик записал «место кончилось, строка ждёт следующего захода» и свежего слияния DK-1570 не делал. Через секунду тот же отказ пришёл в разбор дежурного: строка 490 goal-watch.log называет его уже известным, строка 492 считает попытку 1 из 3 и шлёт в живое окно реплику с текстом «слияние: в docs/tasks/DK-1570.md нет раздела». Текст обрезан на первой кавычке, по нему не видно, какого раздела нет.

Разбор дежурного по DK-1570 кончился черновиком, правок не делал.

### Осложнение

Отказ, чья причина устранена, остаётся в памяти подписи и каждый заход тратит на него попытку разбора. Три попытки кончаются громким зовом человеку по уже закрытому поводу, а слот конвейера занят разбором пустого отказа. Человек получает обрезанный текст и не может понять, что от него хотят. Замерено на DK-1570: отказ от 02:52 держится в разборе больше суток после починки.

### Вопрос

Как снимать подпись отказа, когда причина ушла: срок жизни записи, сброс при смене вершины ветки либо повторная проверка ворот перед подъёмом дежурного? Не обсуждали.

### Гипотеза

Сторож перестаёт звать дежурного по отказу, который больше не воспроизводится, а текст отказа в реплике виден целиком, с именем раздела.
