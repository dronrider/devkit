# DK-162: Скилл безопасности разрабатываемых решений

записан 2026-08-07

## Черновик

Скилл безопасности разрабатываемых решений

Идея: закрыть дыру в devkit, темы безопасности нет ни в правилах, ни в скиллах
(греп по «безопасн/security/secret/уязвим» пуст). Сделать без раздувания
контекста: спящий скилл стоит одну строку описания.

Разбивка по слоям из обсуждения:

- Слой 0, детерминированное в хуки, не в прозу: скан секретов и ключей в диффе,
  аудит зависимостей (cargo audit / pip-audit / govulncheck) рядом с
  hooks/check-symbols.py. Ноль контекста, работает без памяти сессии.
- Слой 1, резидентная цена только description: скилл в kit/skills/, имя не
  путать со встроенным /security-review харнеса. В RULES.core.md максимум
  строка-отсылка. Триггеры перечислить в description предметно: правка трогает
  авторизацию, парсинг внешнего ввода, сеть, файловые пути, секреты, права,
  зависимости.
- Слой 2, SKILL.md на 90-150 строк как у test-standard: опросник модели угроз
  (что за данные, кто снаружи, что при компрометации) и чеклист по классам:
  внешний ввод, секреты, авторизация и границы доверия, файлы и пути, сеть,
  зависимости, конкурентность. Исход находки: серьёзное задачей на доску,
  мелкое чинится сразу с тестом на дыру (краснота через regcheck).
- Слой 3, широкий аудит по дереву отдаётся субагенту, в контекст оседают
  находки, а не выдача.

Открытые вопросы к груммингу:

- Граница со встроенным /security-review: свой скилл держит процедуру вокруг
  (когда звать, куда едут находки), ревью диффа можно отдать встроенному.
- Вшить вызов в существующие точки, чтобы скилл звался, а не забывался:
  строка в board-ship (ревью) и/или test-standard (закрытие правки).
- Автономный режим отдельно: перед слиянием без человека взгляд
  безопасности на дифф это единственный рубеж, секреты check-sensitive
  ловит только в доске и доках, кода он не видит. Как минимум слой 0
  (скан секретов в диффе) обязан стоять до автономного merge.
- Решить, резать ли на две задачи: хуки (слой 0) и скилл (слои 1-3).
