# DK-1633: Пересчёт доски задерживает ответ дашборда на секунду

записан 2026-11-06
приоритет: высокий

## Черновик

### Ситуация

2026-11-06 установленный taskctl list --json для devkit в четырёх адресных замерах выполнялся 1,21-1,32 с. В trace зафиксированы 19 процессов git, включая полный log main за 116 мс, cat-file --batch за 61 мс, два show по 500 и 195 ревизий за 70 и 22 мс, blame за 162 мс. Дополнительно читаются этапы, файлы задач и реестры. cache.go projectBoard после изменения TASKS.md ждёт этот полный пересчёт.

### Осложнение

При частых изменениях доски открытие экранов снова требует синхронного ожидания. Результаты истории main перечитываются процессом утилиты при каждом пересчёте. Оставшиеся примерно 0,8 с внутри taskctl пока не разложены по функциям.

### Вопрос

Какая часть оставшегося времени приходится на вычисления и файлы? Какие результаты зависят от TASKS.md, SHA main и реестров отдельно? Нужен внутренний профиль утилиты до выбора оптимизации.

### Гипотеза

Пользователь хочет быстрый ответ доски при изменении одной строки. Неизменившаяся история и состав коммитов повторно не вычисляются.

## Контекст обсуждения

Источник фактов: исследование тяжёлых ручек 2026-11-06. Пакетирование git уже есть, 695 ревизий не означают 695 процессов. Предложение агента о раздельном сохранении расчётов пока не является выбранной реализацией. Увеличение общего TTL не устраняет зависимость от изменившейся доски. Лавину prepared устраняет DK-1623. Сырые HAR и trace со всеми задачами не переносить в публичный текст.
