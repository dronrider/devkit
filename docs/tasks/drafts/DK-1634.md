# DK-1634: Показ ресурсов ждёт поиск проектов и свежий снимок

записан 2026-11-06
приоритет: средний

## Черновик

### Ситуация

Собственный сбор resources в адресном стенде занимает 25-31 мс. resCollect вызывает projects ради подписей сессий. При просроченном списке он запускает 37 процессов git и занимает 94 мс. resSnapshot хранит снимок одну секунду, затем синхронно собирает новый. Другие читатели ждут этот сбор, старый снимок во время обновления не возвращается.

### Осложнение

Машинные числа зависят от обхода проектов и его задержек. В HAR при лавине запрос ресурсов занял 46,77 с, из них 39,19 с до отправки. До лавины 13 измерений дали 155-477 мс, медиана 178 мс. Задержка в 1,5 с из-за собственной системной работы resources здесь не подтверждена.

### Вопрос

Разделить ли машинные числа и подписи проектов? Как показывать возраст старого снимка при фоновом обновлении и ошибке сбора? Нужна ли отдельная задача после устранения повторного поиска проектов?

### Гипотеза

Пользователь получает доступный снимок ресурсов сразу и видит его возраст. Обновление чисел не ждёт поиска проектных подписей.

## Контекст обсуждения

Это предложение агента по результатам исследования, пользователь поручил сохранить находки. Объединение одновременного системного сбора уже реализовано, лишних параллельных ps по одному ключу не найдено. В начале диагностики fseventsd занимал около 105% CPU и почти 8 ГБ памяти; причина его нагрузки не исследована, связь с реализацией dashboard не доказана. Не ставить задачу на ускорение ps без воспроизведения.
