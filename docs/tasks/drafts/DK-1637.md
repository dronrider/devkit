# DK-1637: Проверка регрессии в headless-сессии упирается в разрешения cmdout

записан 2026-11-06
приоритет: низкий

## Черновик

### Ситуация

При работе над DK-1623 исполнитель на glm-code-2 сообщил о препятствии. Рубеж DK-722 требует переживаемого шага для regcheck. При вызове cmdout --detach в headless-сессии запрашивается одобрение человека. Проверка регрессии прошла у диспетчера штатным regcheck. Выпуск срочной правки не заблокирован.

### Осложнение

Требуемый процедурой способ запуска недоступен в этой сессии без отдельного вмешательства. Исполнитель сообщил, что запускал переживаемый процесс через python3. Это отчёт исполнителя, а не проверенная причина отказа. Разрешения, настройки харнеса и рубежи по ходу исправления не менялись.

### Вопрос

При каких точных параметрах cmdout --detach и политике запуска воспроизводится запрос одобрения? Согласованы ли требование переживаемого шага и разрешённый способ его запуска? Разобрать на синтетическом проекте без ослабления рубежей и доступа к реальным чатам.

### Гипотеза

Автономный исполнитель проходит обязательную проверку регрессии через предусмотренный инструмент и получает понятный исход без ручной подмены способа запуска.
