# DK-1727: Квота подписки часами остаётся старой после отказов обновления

записан 2026-11-18
приоритет: высокий

## Черновик

### Ситуация

18 ноября 2026 года при разборе DK-1726 пользователь спросил, почему статус подписки остаётся неактуальным много часов. В чате задачи DK-1570 после восстановления доставки обнаружился отказ GLM Coding Plan. Клиент получал HTTP 429 с кодом 1310 и сообщением Weekly/Monthly Limit Exhausted. Одиночный запрос модели glm-5.3 без повторов подтвердил тот же отказ за 2,06 секунды.

Снимок glm-code-2 снят 17 ноября в 19:22 по Москве. В нём оставались 3% за пятичасовое окно и 79% за неделю. В ответе GET /api/quota 18 ноября возраст снимка составил 16 часов 32 минуты, stale=true. При этом снимки Codex и routerai обновлялись. Цикл обновления продолжал работать.

В журнале демона 17 ноября в 22:49:58 и 18 ноября в 04:00:01 есть отдельные отказы съёмщиков glm-code и glm-code-2. Для обоих мониторинг вернул JSON с code=500, success=false и сообщением об отсутствии Coding Plan у текущего пользователя (перевод ответа). В журнале SessionStart тот же отказ повторился 18 ноября в 11:15:42 и 11:41:01. Съёмщик сохранил предыдущий снимок. Причина ответа мониторинга ещё не установлена.

### Осложнение

Пользователь видит старые проценты при фактически исчерпанном лимите. Пометка о возрасте есть, но сообщение об ошибке в блоке квоты содержит только первый отказ glm-code. Ошибка второй подписки glm-code-2 в короткую сводку не попадает.

Отказ реального запроса 1310 отражается в состоянии отдельного чата. Доступность подписки для остальных моделей и автоматических запусков по нему не меняется. При разборе DK-1726 команда agentctl check выбрала glm-5.3 через glm-code-2. Проверка на назначенной подписке оказалась недоступна. Новый процесс мог бы долго повторять запросы к исчерпанному лимиту.

### Вопрос

Почему мониторинг с текущими endpoint и учётными данными сообщает об отсутствии Coding Plan, а запросы модели завершаются с HTTP 429 и кодом 1310 Weekly/Monthly Limit Exhausted? Это изменение контракта API, прав мониторинга или области учётной записи? Из имеющихся ответов выбрать причину нельзя.

Как показывать отдельно состояние обновления каждой подписки и фактическую доступность моделей на ней? На каких подтверждениях снимать отметку недоступности после 1310? Время сброса провайдер передал без часового пояса. Конкретная реализация с пользователем не согласована.

### Гипотеза

По вопросу пользователя требуется, чтобы состояние подписки объясняло её текущую доступность и причину задержки обновления. Агент предлагает сохранять последние измеренные проценты с возрастом и отдельно показывать отказ мониторинга и подтверждённое ограничение запросов. Такой исход и способ его реализации ещё требуют разбора.

## Контекст обсуждения

### Проверенные причины

Периодическое обновление вызывает agentctl quota refresh --all --if-stale. Отказ одной подписки не прекращает обход. В cmdQuotaRefreshAll ошибки складываются в список, затем обрабатывается следующая подписка. В журнале 18 ноября в 04:00:01 записано: подписок 4, снято 0, свежих 2, отказов 2. Снимки Codex и routerai оставались свежими.

Съёмщик GLM читает origin и токен из settings.json соответствующего профиля и обращается к /api/monitor/usage/quota/limit. Ответ code=500 не содержит ожидаемых data.limits. При таком ответе прежний снимок остаётся на месте. Факт ошибки не доказывает, что токен неверен или у пользователя действительно нет подписки.

Демон сохраняет одну общую строку ошибки обновления. Функция quotaFailWords оставляет первую строку общего вывода. Поэтому GET /api/quota сообщает только о glm-code, хотя полный журнал содержит и отказ glm-code-2.

Обработка 1310 в чате не записывает наблюдение о доступности подписки в источник, который читают другие чаты и отбор моделей. Старая цифра 79% может сосуществовать с отказом Weekly/Monthly Limit Exhausted. Из этого отказа нельзя вывести точное значение недельного процента или заменить его на 100%.

### Предложенный концепт

Весь концепт предложен агентом при диагностике. Пользователь его не согласовывал. Эта запись сохраняет фактуру для груминга. Реализация не входит в исправление привязки и доставки DK-1726.

1. Для каждой подписки хранить и показывать исход последнего обновления с временем и причиной. Последние измеренные проценты сохраняются вместе с возрастом. Отказы нескольких подписок показываются отдельно, даже когда обновление остальных прошло успешно.
2. Подтверждённый ответ реального запроса 1310 сохранять отдельно от процентов использования. Наблюдение содержит ключ подписки, модель и источник, время получения, код и исходную строку сброса. Оно распространяется на модели той же подписки. По нему интерфейс показывает недоступность, а автоматические запуски не повторяют заведомо отклоняемые запросы. Состояние снимается после ограниченной успешной проверки, надёжно определённого сброса либо свежего авторитетного ответа об аккаунте. Выбор этих условий остаётся открытым.
3. После установления причины code=500 исправить контракт или авторизацию мониторинга GLM. Затем проверить изолированное обновление glm-code-2 и общий обход при одновременной ошибке другой подписки. Отдельно проверить несколько ошибок в интерфейсе и обработку 1310 без подмены измеренных процентов.

Повтор одного и того же refresh не устраняет известный ответ code=500. Изменение только busy/idle в чате тоже не обновит сведения о подписке. Увеличение срока свежести оставит старые цифры доступными дольше.

### Ограничения и источники

Настройки безопасности, токены и глобальный допуск подписок автоматике в ходе диагностики не менялись. Пользователь выбрал новый ручной чат Codex для DK-1570; этот выбор не разрешает автоматически менять политику независимой проверки других задач. Проверка на недоступной GLM не отмечалась выполненной.

Все времена журналов и снимков выше указаны по Москве. В ответе модели строка сброса была 2026-11-19 01:58:02 без часового пояса. Пересчёт в местное время не подтверждён.

Исходники на момент диагностики: tools/agentctl/usage.go:383-418, обход и сбор ошибок; kit/harness/snap/glm-code.sh, запрос мониторинга и проверка data.limits; tools/dashboard/quota.go:659-663, сокращение ошибки до первой строки; tools/dashboard/quota.go:744-793, сохранение исхода обновления и цикл раз в десять минут; tools/dashboard/chats.go:1366 и 3539, состояние ожидания квоты отдельного чата. Номера строк могут измениться после слияния DK-1726.

На машине диагностики сохранены GET /api/quota в /private/tmp/DK1726-current-quota-view.json, одиночный ответ модели в /private/tmp/dk1726-qa-glm53-health.json и подробный разбор в /private/tmp/DK1726-quota-snapshot-diagnosis.md. Эти временные файлы помогают найти первичные свидетельства, существенные результаты приведены в этом черновике. Журналы обновления: ~/.devkit/dashboard.log и ~/.devkit/quota-refresh.log; снимок: ~/.devkit/quota/glm-code-2.local. В записи нет токенов или адресов инфраструктуры.
