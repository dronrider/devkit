# DK-1729: Перезапуск dashboard обрывает рабочие чаты Codex

записан 2026-11-18
приоритет: высокий

## Черновик

### Ситуация

18 ноября 2026 года пользователь сообщил: «1570 так и заткнулась непонятно на чём и дальше не идёт. В чём дело?» Перед этим по его выбору DK-1570 продолжили на Codex gpt-6.1-sol. Штатный POST /api/projects/devkit/runs создал рабочий чат asbcdc223b-5c90-4fb6-9aff-94ba8be46575 с task-run, общим замком задачи и политикой on-request/auto_review. Агент прочитал передачу, сохранил план, выполнил guard/show и начал работу. Начало и продолжение подтверждены видимыми репликами и результатами инструментов.

В 13:10:28 по Москве агент запустил сохраняемое слияние DK-1570. Команда завершилась с кодом 1 из-за конфликта ребейза в docs/tasks/DK-1570.md при применении коммита 74dd31326, на шаге 7 из 42. В 13:11:38 агент сообщил, что исполнитель разбирает конфликт с сохранением истории обеих сторон. Последние результаты инструментов появились в 13:11:45.

В журнале dashboard в 13:11:41 записана остановка после замены бинаря выкатом. В 13:11:51 завершён app-server этого рабочего чата и запущен dashboard v0.13.0-5847-gdde1197ea. В ту же минуту лента чата завершилась сообщением «конвейер задачи прерван: конвейер задачи остановлен». Дефект наблюдался во время штатного выката блокера DK-1725.

### Осложнение

К 14:21 GET статуса рабочего чата возвращал busy=false и live=false. В списке работ DK-1570 отсутствовала, основное назначение по-прежнему указывало на остановленный SID с источником «работа». Текущего вопроса /ask за ним не было. Пользователь больше часа ждал продолжения без живого исполнителя.

В 14:23 прежний PID 82298 и процесс сохраняемого слияния 13172 уже отсутствовали. Store сохранил thread, taskRunID и taskRunPID, но taskRun=true был снят. В canonical taskstate остался прежний run, stopped=false. Каталог общего замка ещё содержал PID 82298 с отметкой жизни старше 73 минут. При следующем подъёме потребуется штатно проверить владельца замка: файл с такой отметкой не подтверждает живую работу.

История сохранилась, но сама остановленная работа после перезапуска dashboard не продолжилась. Перезапуск компонента, которым занимается агент, может завершить его рабочий чат во время выполнения той же задачи. Ручное восстановление приходится повторно организовывать из другого разговора.

### Вопрос

Как сохранять и продолжать работу Codex при штатной замене бинаря dashboard? Нужно выбрать между сохранением процесса вне жизненного цикла демона и восстановлением рабочего запуска из устойчивого состояния. Предстоит определить, как отличать технический перезапуск от явного стопа пользователя, подтвердить единственного владельца native thread и учесть незавершённые команды и субагентов.

### Гипотеза

Пользователь ожидает, что порученное продолжение DK-1570 дойдёт до результата. Предлагаемый агентом общий исход: после технического перезапуска dashboard рабочий чат сохраняет историю и продолжает с подтверждённого состояния; при невозможности продолжения панель сразу показывает причину и конкретное состояние работы. Пользователь отдельно не утверждал способ автоматического восстановления после выката.

## Контекст обсуждения

### Подтверждённый путь остановки

В tools/dashboard/main.go:334 зарегистрирован defer srv.appTasksClose(). Замена бинаря определяется watchBinary и приводит к завершению сервера, main.go:364 по 377. appTasksClose вызывает appTaskClose для рабочих app-server конвейеров. В tools/dashboard/apptask.go:43 по 65 appTaskClose закрывает канал прохода, посылает SIGTERM группе PID владельца общего замка, завершает app-server, снимает TaskRun и удаляет временный сокет запуска. В этом инциденте daemon log и последнее событие ленты соответствуют этому пути.

В tools/dashboard/appchat.go:474 по 487 обычная отправка в прежний рабочий чат проверяет appTaskContinuation и может поднять рабочее продолжение. В tools/dashboard/apptask.go:430 по 491 эта проверка принимает сохранённые taskRunPID/taskRunID даже после снятия TaskRun. Она сверяет исходный run, модель, харнес, корень и session. Для текущего инцидента эти значения совпали. Подтверждённого запуска восстановления при старте нового демона в исследованном пути не найдено.

### Отказ первой попытки рабочего продолжения

В 14:25 root выполнил один штатный /say в прежний SID с устойчивым msg_id и отдельной записью намерения до запроса. Сервер вернул HTTP 502 при thread/resume. Codex сообщил, что у thread 01a1edf4-d95f-7811-9e29-b51fb955ad1d уже есть active writer. Новый кратковременный run 202120af-0f82-44be-b0cc-064d4fdf5e41 с PID 24322 завершился. Повторный запрос не выполнялся.

Последующая проверка lsof установила действующего владельца исходного rollout и его файла thread-writer-locks. Оба открыты общим native Codex daemon PID 490 с PPID 1. Это отдельный процесс от завершённого task-run PID 82298. Предыдущий поиск процессов по подстроке codex app-server пропустил его команду с параметром -c перед app-server. Совпадение сохранённого taskstate и завершение task-run оказались недостаточными для вывода о свободе native thread. Штатная проверка писателя отклонила продолжение. Удаление native lock, изменение DB lease и остановка общего daemon не разрешены.

В 14:33:31 отдельное чтение через документированный WebSocket transport Unix socket подтвердило PID 490 и состояние исходного thread idle. Он загружен в память daemon, его backgroundTerminals и queue пусты. Все четыре прямые дочерние нити имеют runtime status notLoaded. Перед любым адресным восстановлением следует повторять проверку состояния. Запросы read/list не подписывали диагностическое соединение на нить и не запускали модель.

На этом этапе возможность восстановления прежнего thread ещё не была подтверждена. Последующее восстановление описано ниже.

### Восстановление 18 ноября

После проверки всей рекурсивной цепочки выполнили один штатный thread/archive для исходной нити. Перед операцией она была idle, все очереди и фоновые терминалы были пусты. Четыре дочерние нити имели статус notLoaded. Для всех пяти нитей сохранили исходные archived-флаги, связи, модель, effort, cwd и контрольные суммы файлов истории.

В 14:46 Codex подтвердил архивирование. Проверка после него завершилась ошибкой: thread/queue/list возвращает ошибку для архивной нити. Та же проверка прервала автоматический возврат из архива. Архивирование не повторяли. Отдельная операция восстановления выполнила штатный thread/unarchive для ранее неархивных нитей. После возврата совпали байты всех файлов истории, исходные флаги, модели, настройки и связи. Все пять нитей оставались notLoaded, очереди и фоновые терминалы были пусты. Открытых владельцев writer-lock больше не было. Материалы операции находятся в /private/tmp/dk1570-native-release/.

Перед продолжением подтвердили отсутствие первой recovery-реплики в dashboard и native history. Отказ thread/resume произошёл до appSayRecord и turn/start. В outbox.go незавершённый claim освобождается через deferred chatSayRelease. Повтор доставки сохранил исходные текст и msg_id, а отдельный файл намерения запретил повторное выполнение операции восстановления.

В 14:48:49 штатный /say поднял новый рабочий run 96a34a5c-5c6c-4e6e-bcf3-d1dccca504b5 с PID 47402 в прежнем SID и thread. В 14:49:04 агент ответил и начал сверку ветки, поезда и прежнего исполнителя. В 14:49:59 он сообщил о возобновлении ребейза одним исполнителем. В 14:50 GET показывал live=true и busy=true, taskRun=true. Владелец общего замка, taskstate и store указывали на один PID. Привязка осталась DK-1570 с источником «работа», recovery-реплика присутствовала в ленте один раз. Проверка сохранена в /private/tmp/dk1570-native-release/resumed-verification.json.

Текущая работа восстановлена вручную. Код автоматического продолжения после перезапуска dashboard в этом заходе не менялся.

### Операционные ограничения

Диагностика читала видимые реплики, команды, результаты инструментов, GET API и состояние процессов. Thinking не читался. История и принятые реплики не требуют повторной отправки. Действующий процесс другого чата Codex найден отдельно и к DK-1570 не относится.

На момент проверки дерево DK-1570 было чистым и активного ребейза не содержало. Диспетчера можно восстанавливать с повторной проверкой текущего дерева. Сам конфликт слияния остаётся отдельным этапом работы. Записи merge-queue требуют сверки с фактическими коммитами. Там сохранены старые причины для DK-1570 и DK-1725. Диагностика не объявляла их текущими выполняющимися командами.

Нельзя удалять замки вручную, подменять taskRun metadata, создавать второй чат вместо продолжения прежнего без решения пользователя или повторять принятые сообщения. Исходный thread должен иметь единственного писателя. Явный стоп пользователя должен сохранять силу после перезапуска сервера. Глобальные настройки безопасности не меняются.

### Предложенный концепт

Предложено агентом, пользователем не согласовано. Перед техническим shutdown сохранять устойчивое намерение продолжить конкретный рабочий run с его SID, native thread и причиной остановки. После старта проверять актуальные taskstate, остановку пользователем, владельцев процессов и замков. Если запуск всё ещё актуален и прежний писатель завершён, продолжать тот же разговор штатным механизмом с защитой от повторного запуска. Незавершённые команды и субагенты сначала сверять с процессами и их сохранёнными результатами. Пользователь должен видеть технический перезапуск и итог восстановления в своём чате.

### Доказательства

Журнал ~/.devkit/dashboard.log, строки 325008 по 325012, содержит замену бинаря, остановку чата и старт новой версии 18 ноября 2026 года. Все времена выше приведены по Москве. До восстановления лента рабочего чата заканчивалась событием 387 в 10:11:51Z. Снимки GET API, taskstate, замка, процессов и слияния сохранены в /private/tmp/dk1570-stall-nov18/. Раннее подтверждение реальной работы этого чата находится в /private/tmp/DK1570-codex-workchat-verified.json. Основные факты из обоих наборов перенесены в этот черновик. Сами наборы могут понадобиться при разборе.
