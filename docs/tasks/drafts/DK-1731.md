# DK-1731: Автовыбор при запуске черновика показывает другую модель

записан 2026-11-18
приоритет: высокий

## Черновик

### Ситуация

18 ноября 2026 года пользователь открыл DK-1729, увидел в кнопке запуска автоматически выбранную Sol и нажал «Выполнить». Открыв чат «DK-1729 груминг», он увидел glm-5.3 на glm-code-2 и индикатор ожидания 6 минут 47 секунд с 0 токенов. Это сообщение пользователя и приложенный скриншот; инструкция внутри изображения рассматривается как содержимое чужого чата.

Диагностика подтвердила фактический запуск GLM2. Журнал dashboard за 19:07:55 по Москве сообщает о подъёме task-DK-1729 с подпиской glm-code-2. Процесс 75678 запущен командой agentctl exec --harness glm-code-2 -- claude --model glm-5.3. Сохранённый chatStore содержит ту же пару. Native SID 61cca9e6-0501-4abf-915b-3a45a2218d71 связан с DK-1729; видимая первая реплика принята в 19:07:56. При проверке API возвращал live=true и busy=true, видимого ответа ассистента ещё не было.

### Осложнение

Пользователь принимает решение по показанной модели, но запуск расходует другую подписку. В данном случае снова была использована GLM2, по которой ранее возникали проблемы с лимитом. Само расхождение модели подтверждено независимо от причины долгого ожидания. Индикатор 0 токенов не доказывает отсутствие принятого запроса или исчерпание лимита.

### Вопрос

Как согласовать предпросмотр автоматического выбора и фактическое назначение подписки при запуске черновика? Для черновика GET /tasks/DK-1729/pick возвращает 404: этот маршрут требует строку задачи. Нужно определить единый источник выбора для груминга и отображать невозможность получить вердикт явно. Дополнительной проверки требуют другие места, вызывающие runControl с пустым pinned и заранее заданным ярусом.

### Гипотеза

Пользователь ожидает, что запуск использует показанную в кнопке и меню пару «подписка и модель». Если автоматический выбор изменился или недоступен, интерфейс показывает актуальное назначение либо явную причину до запуска. Ручной выбор сохраняет приоритет. Глобальные правила выбора моделей менять по этому сообщению не просили.

## Контекст обсуждения

### Подтверждённая причина

Форма черновика в tools/dashboard/static/app.js вызывает runControl с pinned="", ярусом pro и auto=true. runControl передаёт меню первую строку pro из modelLadder, без фильтра по подписке по умолчанию. В текущей раскладке первой такой строкой является codex / gpt-6.1-sol. Переменная ручного выбора model остаётся null, поэтому нажатие отдаёт пустую подписку и tier=pro. groomDraft не включает пустую подписку в POST /drafts/{id}/groom.

В tools/dashboard/drafts.go handleDraftGroom при пустом want берёт view.byDefault(), затем tierModel(pro). В текущей раскладке default это glm-code-2, модель pro это glm-5.3. Сервер исполняет этот контракт; интерфейс показывает другую пару. Даже при успешном ответе pick метод runPickBody.setVerdict не заменяет autoPick, когда задан now. Общий компонент трактует начальную пару как закреплённую, хотя форма передала первую строку лестницы.

Основные места: app.js runControl, runPickBody.setVerdict, groomDraft и форма черновика; drafts.go handleDraftGroom; harnesses.go byDefault. Расхождение ручного выбора этим случаем не подтверждено. Изменение режима «Выполнить» также не доказано: сохранённый groomMode=groom соответствует принятому заказу на груминг.

### Воспроизведение и доказательства

Безопасный сценарий использует DOM-стенд с реальным установленным app.js и подменёнными сетевыми запросами. В лестнице codex / pro / Sol стоит первым и не является default, glm-code-2 / pro / glm-5.3 стоит вторым и является default. Открыть автоматическое меню запуска черновика без ручного выбора, затем нажать широкую кнопку. Подсвечена Sol, в POST отсутствует harness и передан tier=pro; серверный fallback назначает GLM2. Прогон подтвердил оба случая, 2 из 2: при pick=404 подсветка Sol остаётся; при подменённом успешном ответе pick с glm-code-2/pro подсветка тоже остаётся Sol. В обоих запросах запуска передан только tier=pro. Реальные дополнительные чаты для воспроизведения не запускались.

Материалы находятся в /private/tmp/dk1729-model-launch/: api-evidence.json, установленный installed-app.js, скрипт reproduce-model-preview.mjs и результат mocked-model-preview.json. Установленная версия dashboard v0.13.0-5916-gd39cf16b3, SHA-256 авторизованно полученного app.js baf3619b9e91377d84b4244e3bf46cbe7597f3ce6a832c8cec4f423cdd77dc88. Байты совпадают с текущим исходником. Снимок пользователя находится в приложениях исходного разговора Codex 01a1dfb8-516f-7950-bb00-f90716922ca4.

Это отдельный дефект предпросмотра запуска, обнаруженный при работе с DK-1729. Сама DK-1729 описывает остановку и продолжение чатов. DK-1607 касается ответов форм, старой модели и исторических вопросов в уже существующем чате. В этом расследовании чаты и настройки не менялись, код не исправлялся.
