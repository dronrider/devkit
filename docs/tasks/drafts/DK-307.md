# DK-307: Вторая подписка из текущего окна, без запускатора и отдельного окна

записан 2026-08-13

## Черновик

Вторая подписка из текущего окна, без запускатора и отдельного окна

Сегодня задача на второй подписке начинается с запускатора: shipctl code
готовит отдельное окно vscode с glm-окружением и своим деревом, и только
там можно сказать «выполни DK-XXX». Это двойная механика (окно на подписку,
дерево на окно), своя цепочка болей (отставание glm-дерева от main, DK-269;
окно без задачи, DK-203) и лишний переключатель головы: работа та же,
проект тот же, а окон два.

Хочется полноценной работы из одного окна: сессия первой подписки отдаёт
задачу исполнителю на второй подписке так же, как отдаёт субагенту сейчас,
без подготовки отдельного окна руками.

Главная неопределённость, из-за которой так сложилось, это разделение
квоты: замер квоты claude-code и модели opus работают только из окружения
claude-code, а модель glm-харнеса субагенту передаётся опусканием model,
иначе расход утекает в квоту claude-code. Разбор на груминге начать с
того, можно ли внутри одного окна поднять субагента с другим окружением
харнеса (свой ANTHROPIC_BASE_URL и ключ на процесс), не смешав учёт
расхода, и что при этом происходит с замером остатка второй подписки
(DK-181). Если окружение процесса развести нельзя, честно записать это
как ограничение харнеса и закрыть черновик с причиной.

Смежное: DK-203 (окно без задачи), DK-269 (отставание glm-дерева),
DK-181/DK-182 (учёт остатка и ступени по подписке). Если один-оконный
путь взлетит, запускатор и glm-дерево становятся не нужны вовсе, и эти
строки пересматриваются.
