# DK-421: Правила доки фичи: вход для читателя, впервые её видящего, и проверка чужим контекстом

записан 2026-08-17

## Черновик

Правила доки фичи: вход для читателя, впервые её видящего, и проверка чужим контекстом

Наблюдение пользователя 2026-08-17 (разбор доки запускатора окна второй
подписки, DK-420): дока, написанная агентом на закрытии задачи, разбирает
устройство и доводы решения, а порядка первого запуска не даёт. Новичок по
ней не запускает фичу, агент тратит токены на вопросы в чат. Пробел не в
одной доке, а в правилах: DK-420 чинит shipctl, этот черновик про причину.

Что правила требуют от доки сегодня и чего не требуют:

- RULES.md «Документация изменений» п. 1 требует, чтобы дока была
  («оседает в долгоживущей доке той же задачей»); сторож полноты
  devkitctl doctor (DK-071) считает компонент описанным по заголовку или
  README, содержимое не смотрит;
- мимикрия и proofread правят форму по восьми пунктам DK-173, ни один не про
  то, дойдёт ли по тексту читатель, впервые видящий фичу;
- ревью в board-ship п. 4 проверяет доку «по содержанию», конкретика там
  только про сценарий бага;
- нигде не сказано, что в доке фичи должно быть и в каком порядке. Агент
  на закрытии пишет то, что в контексте, а в контексте решение и его
  обоснование: заголовки раздела shipctl («Копия на окно, а не на задачу»,
  «Окружение живёт в директории, а не в запуске») это заголовки решений
  LLD, внутри история (DK-192, IRC-097) и доводы. Текст LLD переехал в
  README, входа для пользователя нет; индекс решений при этом уже есть в
  docs/map.md, README его дублирует.

Что усугубляет:

- RULES.md п. 36 и ядро: «Список ручных шагов в README это не решение, а
  перекладывание раскладки на пользователя». Правило про автоматику
  раскладки окружения, но читается как запрет писать шаги вообще: агент
  порядок запуска не пишет вовсе. Список «что вызвать по порядку» и список
  «что руками отредактировать» это разные вещи;
- ядро: «по умолчанию комментариев не писать, только где неочевидно
  почему». Про код верно, а проза по инерции едет туда же: сплошное
  «почему» без «как»;
- RULES.md п. 87: «устоявшиеся факты переезжают из LLD в README», не
  сказано какие. Переезжают доводы, а нужны факты использования;
- между README утилит нет общего порядка разделов: где-то первым «Запуск»
  (cmdout, regcheck), где-то сразу механика (shipctl, dashboard). Новичок не
  знает, где искать вход.

Чего хотим:

1. RULES.md «Документация изменений», новый пункт: у доки фичи есть вход
   для читателя, впервые её видящего, и порядок фиксирован: кому и когда
   зовётся; первый запуск с нуля шагами с проверкой результата (--dry-run,
   находка доктора, что-то наблюдаемое); повседневные команды; и только
   потом устройство. Доводы «почему так, а не иначе» и история (ID задач,
   инциденты) остаются в LLD и файле задачи. Там же снять двусмысленность
   п. 36: автоматика раскладывает окружение, а порядок вызовов доке писать
   можно и нужно; под запретом ручные правки файлов, которые должна делать
   автоматика. Уточнить п. 87: из LLD в README переезжают факты
   использования, доводы остаются в LLD.
2. RULES.core.md «Дока едет вместе с правкой»: одно предложение про вход
   для новичка, резидентно. Бюджет ядра держим (DK-173.2), ради этого ужать
   соседнее.
3. Проверка чужими глазами, как у proofread: DK-420 в приёмке нашла
   правильную форму: чужой контекст на чистом окружении идёт по доке и
   доходит до результата без подсказок. Это и есть проверка «понятно ли
   новичку», формой не ловится. Прописать её в board-ship п. 4 (ревьювер
   гоняет для новой пользовательской поверхности) и в чеклист test-standard
   («заметное поведение осело в доке» дополняется «и у него есть вход»).
4. Уже написанное: по DK-173.4 стиль действует вперёд, переписывать всё не
   надо, но входы дешёвые. DK-420 закрывает shipctl; обход остальных README
   на «есть ли вход» (кандидаты по структуре заголовков: dashboard,
   agentctl-харнес, devkitctl-доктор) это отдельный черновик после этой
   задачи, когда правило будет, по чему сверять.

Приёмка: вид agent. Правило проверяется на паре README чужим контекстом на
временном HOME: по доке дошёл до результата без подсказок значит вход есть.
Тексты правил и скиллов проходят proofread и check-symbols. Родня: DK-420
(частный случай), DK-173 (мимикрия и вычитка), DK-071 (сторож полноты).
