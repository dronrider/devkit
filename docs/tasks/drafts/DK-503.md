# DK-503: исполнитель растит контекст до сжатия и перечитывает всё заново

записан 2026-08-24
приоритет: средний

## Черновик

### Ситуация

Субагент-исполнитель DK-181 прожил с 23.08 21:13 до 24.08 07:52 по UTC одним
заходом: 347 обращений к модели, 211 вызовов Bash, 58 правок, средний контекст
100 тысяч токенов при максимуме 167 тысяч. В 06:39 сработало автоматическое
сжатие (167376 токенов до 14703, отброшено 152673), после чего агент пошёл
перечитывать те же файлы и через час умер по отказу 429. Задача не сделана.
Группа этой сессии съела 43.4 миллиона токенов, из них 41.5 миллиона пришлось
на субагентов, а на главную сессию только 1.9 миллиона.

### Осложнение

Стоимость одного захода растёт быстрее числа шагов: материал, влитый на десятом
обращении из 347, оплачивается ещё 337 раз, и 88 процентов кредитов уходит на
прогонку накопленного, а не на ответы модели. Потолка у исполнителя нет ни по
обращениям, ни по контексту, поэтому длинная задача неизбежно доезжает до
сжатия, а сжатие обнуляет не расход, а только пользу от прочитанного. Отдать ту
же работу двумя заходами по своему куску дешевле, чем одним длинным.

### Вопрос

Чем ограничивать заход: числом обращений, накопленным контекстом или временем?
И кто режет работу дальше, когда потолок достигнут: сам исполнитель сдаёт хвост
диспетчеру или диспетчер поднимает следующего с короткой вводной.

### Гипотеза

Задача, которая не влезает в один заход, доезжает несколькими короткими вместо
одного длинного, и ни один заход не доходит до автоматического сжатия контекста.
