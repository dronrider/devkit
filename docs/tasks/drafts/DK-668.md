# DK-668: regcheck --base main зеленеет после слияния и топит регрессию сценария

записан 2026-08-31
приоритет: высокий

## Черновик

### Ситуация

Сценарий проверки DK-652 (docs/tasks/DK-652.md, шаг 2) прогоняется командой
`regcheck -C tools/dashboard --tests tools/dashboard/agentask_test.go -- env GOWORK=off go test -run '...' .`
с базой по умолчанию `--base main`. Проверено 2026-08-31, уже после слияния и
выката: правка на этот момент сама лежит в main, и тест зелёный на обеих
сторонах diff. regcheck честно отказал: «тест зелёный и на старом коде (HEAD),
регрессию он не ловит; если правка уже закоммичена, укажи базу без неё
(--base main)». Заход разобрался сам, взял базой `a113c76c^` и получил нужную
строку про красноту до фикса.

### Осложнение

Шаг сценария проверки написан так, что дословно его прогнать нельзя, а сам
сценарий по смыслу пишется для дословного прогона чужими руками. Каждый
прогонявший заново соображает, чем заменить базу, и на этом можно свернуть не
туда: взять базу, где тест и так зелёный, и записать в файл задачи ложную
зелень. Случай не разовый: сценарий проверки по определению живёт после
слияния, значит эта мина лежит под каждой задачей, где шаг сценария написан
командой regcheck.

### Вопрос

Три гипотезы, ни одна не выбрана.
1. regcheck сам ищет базу, когда `--base main` вырождается: коммит, добавивший
   названный тест.
2. Скилл test-standard пишет в сценарии базу видом `<коммит фикса>^`, а не
   веткой.
3. Шаг сценария после слияния пишется не командой regcheck, а отсылкой к уже
   прогнанному разу.

### Гипотеза

Прогон сценария проверки после слияния либо ловит регрессию сам, либо честно
отказывает вместо ложной зелени, независимо от того, кто и когда его повторяет.
