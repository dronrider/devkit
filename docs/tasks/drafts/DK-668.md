# DK-668: regcheck --base main зеленеет после слияния и топит регрессию сценария

записан 2026-08-31
приоритет: высокий

## Черновик

### Ситуация

Сценарий проверки DK-652 (docs/tasks/DK-652.md, шаг 2) прогоняется командой
`regcheck -C tools/dashboard --tests tools/dashboard/agentask_test.go -- env GOWORK=off go test -run '...' .`
с базой по умолчанию `--base main`. Проверка прошла 2026-08-31, уже после
слияния и выката. Правка на этот момент лежит в main, и тест зелёный на обеих
сторонах diff. Инструмент `regcheck` отказал: «тест зелёный и на старом коде
(HEAD), регрессию он не ловит; если правка уже закоммичена, укажи базу без
неё (--base main)». В заходе взяли базой `a113c76c^` и получили нужную строку
про красноту до фикса.

### Осложнение

Шаг сценария проверки написан так, что дословно его прогнать нельзя, а сам
сценарий по смыслу пишется для дословного прогона чужими руками. Каждый
прогонявший заново соображает, чем заменить базу. Здесь легко свернуть не
туда. База выходит такая, где тест и так зелёный, и в файл задачи попадает
ложная зелень. Случай не разовый. Сценарий проверки по определению живёт
после слияния, и такая ошибка возможна под каждой задачей, где шаг сценария
написан командой regcheck.

### Вопрос

Три гипотезы, ни одна не выбрана.
1. regcheck сам ищет базу, когда `--base main` вырождается, и берёт коммит,
   добавивший названный тест.
2. Скилл test-standard пишет в сценарии базу коммитом `<коммит фикса>^`
   вместо имени ветки.
3. Шаг сценария после слияния пишется не командой regcheck, а отсылкой к уже
   прогнанному разу.

### Гипотеза

Прогон сценария проверки после слияния либо ловит регрессию сам, либо
отказывает вместо ложной зелени, независимо от того, кто и когда его
повторяет.
