# DK-764: Браузерные тесты дашборда гибнут по времени и валят чужие слияния

записан 2026-09-03
приоритет: высокий

## Черновик

### Ситуация

Прогон слияния убивает chrome по стенным секундам, когда машина занята: TestBoardNarrowNoSideScroll, TestBoardRowActionsAligned, TestBoardTableHeadFitsRow, TestStaticRunSplitLayout, TestStaticTactsRowHeights. В изоляции каждый идёт полсекунды, под нагрузкой сидит по девяносто и снимается сигналом.

За сутки это отбило слияния четыре раза, причём задачам, которые дашборда не касались вовсе: DK-660, DK-739 дважды, DK-724 дважды. Разбор каждый раз съедает время на выяснение, что падение чужое, и подталкивает сливать с урезанной параллельностью, то есть в обход честного прогона.

Смежное уже закрыто: DK-635 про потолок стенных секунд в раннере, DK-733 про фикстуры, зависящие от часа суток. Здесь третья беда того же семейства: сам браузерный стенд не переживает соседей по прогону.

Разобрать надо, чем мерить такие тесты. Похоже, потолок им нужен не стенной, а свой, либо браузерные стенды должны идти отдельным звеном раннера, не соревнуясь за процессор с остальными семнадцатью.

## DoD

Полный прогон слияния зелёный при загруженной машине: браузерные стенды не снимаются по времени, когда рядом идут другие компоненты. Проверяется прогоном под нагрузкой, поднятой нарочно.

## Не только браузерные, 2026-09-04

Тем же болеет TestPulseRemembersJournalSteps: он меряет время тёплого опроса
кольца против порога в тридцать миллисекунд. Под общим прогоном падает, по
одному проходит трижды подряд. Это уже не chrome, а обычный замер в go-тесте,
значит семейство шире, чем браузерные стенды.

Общее у всех: тест меряет стенные секунды, а прогон идёт восемнадцатью
компонентами разом на занятой машине. Разбирать стоит не каждый тест по
отдельности, а сам приём: чем заменить замер времени там, где проверяется
поведение, а не скорость.
