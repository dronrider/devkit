# DK-788: След regcheck сгорает от ребейза, который делает сам shipctl merge

записан 2026-09-04
приоритет: средний

## Черновик

### Ситуация

Ворот слияния у задачи типа bug спрашивает зелёный regcheck за время жизни
ветки. В DK-784 прогон был зелёным, дальше shipctl merge пошёл ребейзом на
main, ребейз наткнулся на конфликт и откатился. После ручной пересборки
ветки тот же merge отбился словами «нет зелёного regcheck за время жизни
ветки»: коммит стал другим, а след остался при старом.

Выходит, merge может отбить по regcheck после того, как сам переписал
ветку, и прогон приходится повторять без единой правки кода. Прогон не
дешёвый, он собирает старое дерево и гоняет тесты дважды.

Вопрос: чем помечать прогон, чтобы ребейз его не гасил.

Гипотеза: считать след не по коммитам ветки, а по содержимому тестовых
файлов и правки (тот же отпечаток, каким обкатка сверяет сценарий).
Ребейз содержимого не меняет, и повторный прогон тогда нужен только после
настоящей правки.
