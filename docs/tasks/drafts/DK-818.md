# DK-818: тесты taskctl льют записи этапов в настоящий ~/.devkit/runs

записан 2026-09-05
приоритет: высокий

## Черновик

### Ситуация

5 сентября 2026 разбирал тормоза дашборда. В ~/.devkit/runs лежало 18601
файл *.run, из них 18548 с именами вида
XR-004-var-folders-...-T-TestMoveQuestionCeiling...-001.run: поле root у них
указывает во временный каталог go-теста, которого на диске уже нет. Писатель
берёт дом через stage.Home(), то есть os.UserHomeDir(), а setup(t) в тестах
taskctl подменяет только корень проекта, HOME не трогает. Каждый cmdMove в
тесте кладёт запись в боевой каталог машины. Больше всех дают
TestMoveQuestionCeiling (1937 файлов), TestMoveQuestionCeilingLinkForms (771),
TestPush (517). Мусор удалён руками той же сессией.

### Осложнение

За день прогонов набегает по тысяче с лишним файлов. stage.List читает каталог
целиком на каждый запрос пульса и доски дашборда, и через две недели после
чистки ручки снова отвечают по секунде, а демон держит 60-85% CPU. Без правки
чистка одноразовая.

### Вопрос

Подменять HOME в общей setup(t) тестов taskctl или дать stage.Home() шов для
тестов? Нужен ли сторож, который падает, если прогон тестов оставил след в
настоящем доме?

### Гипотеза

Прогон go test в tools/taskctl не оставляет ни одного файла в ~/.devkit/runs,
и есть тест, который это проверяет.
