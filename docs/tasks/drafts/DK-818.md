# DK-818: тесты taskctl льют записи этапов в настоящий ~/.devkit/runs

записан 2026-09-05
приоритет: высокий

## Черновик

### Ситуация

5 сентября 2026 разбирал тормоза дашборда. В ~/.devkit/runs лежал 18601 файл
*.run. Из них 18548 носят имена вида
XR-004-var-folders-...-T-TestMoveQuestionCeiling...-001.run. Поле root у них
смотрит во временный каталог go-теста, и на диске его уже нет. Писатель берёт
дом через stage.Home(), а это os.UserHomeDir(). Общий setup(t) в тестах taskctl
подменяет корень проекта, а HOME не трогает. Каждый cmdMove внутри теста кладёт
запись в боевой каталог машины. Больше всех дают TestMoveQuestionCeiling (1937
файлов), TestMoveQuestionCeilingLinkForms (771) и TestPush (517). Мусор я
удалил руками в той же сессии.

### Осложнение

За день прогонов набегает больше тысячи файлов. stage.List читает каталог
целиком на каждый запрос пульса и доски дашборда. Через две недели после чистки
ручки снова отвечают по секунде, а демон держит 60-85% CPU.

### Вопрос

Подменять HOME в общей setup(t) тестов taskctl или дать stage.Home() шов для
тестов? Нужен ли сторож, который падает, когда прогон оставил след в настоящем
доме?

### Гипотеза

Прогон go test в tools/taskctl не оставляет ни одного файла в ~/.devkit/runs.
Есть тест, который это проверяет.
