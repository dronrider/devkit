# DK-900: Субагент затирает план родителя общей меткой agentctl plan

записан 2026-09-10
приоритет: средний

## Черновик

### Ситуация

Ситуация. План работ сессии живёт файлом под меткой, метку берут из
DEVKIT_PLAN_LABEL либо из аргумента --label (tools/agentctl/plan.go:35, 71).
Признак дочерней сессии DEVKIT_PLAN_CHILD у механики есть.

Осложнение. При работе над DK-888 исполнитель вёл план под меткой задачи, а
поднятый им субагент-ревьювер позвал plan set --label DK-888 со своей стороны и
переписал файл целиком. Исполнитель восстанавливал этапы руками, повторными
plan done. Метка совпала, потому что она называет задачу, а задача у них одна.

Двенадцатого сентября повторилось на DK-936, и путь метки там другой. Субагент
вычитки унаследовал ID сессии исполнителя, метку взял из окружения и позвал
plan set без всякого --label, а план захода переписался целиком. Значит
дочерней сессии мало запретить явную метку, у неё и наследованная зовёт тот
же файл.

Вопрос. Должна ли метка различать заходы внутри одной задачи, или дочерней
сессии писать в общий план вообще незачем.

Гипотеза. Дочерняя сессия узнаётся признаком DEVKIT_PLAN_CHILD, и явный --label
у неё либо уходит в свою ветку файла, либо отклоняется с подсказкой.

### Приписка 2026-09-17

Третий случай на пачке мелких задач. Исполнитель DK-467 позвал `plan done` без `--label`, и пункт «спавн исполнителей» закрылся в плане диспетчера. Обход тот же: субагент дальше звал план только с `--label DK-467`.

### Приписка 2026-09-17, разнобой записи и чтения

Четвёртый случай той же механики, и субагент тут ни при чём. В сессии груминга
DK-1029 `plan set` записал план в `~/.devkit/plans/<sid>.json`, а `plan show`
следом напечатал ветку субагента из `<sid>-sub-DK-1029.json`. Запись и чтение
в одном окружении разошлись по файлам, и `--sid <sid>` картины не поменял.
Файл плана самой сессии при этом цел, диспетчер просто не видит своих пунктов.

В окружении сессии стоит `CLAUDE_CODE_CHILD_SESSION=1`, который клиент ставит
всем сессиям подряд (DK-852). Похоже, `show` читает признак дочерней сессии, а
`set` его не смотрит, и обход «звать план только с --label» от этого случая не
спасает: метки у команды не было вовсе.
