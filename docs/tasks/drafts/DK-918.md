# DK-918: Сохранение с дашборда отказывает в пуше, когда main отстал от origin

записан 2026-09-10
приоритет: средний

## Черновик

### Ситуация

10 сентября 2026, правка строки DK-916 с дашборда. Запись и коммит прошли, а в уведомлении хвост отказа: `! [rejected] main -> main (fetch first)`. Причина в `commitDocs` (`tools/dashboard/board.go`): после `git commit` зовётся голый `git push`, без fetch и rebase. На origin к тому моменту лежали три коммита доски с другой машины (DK-917), и все три сохранения подряд отказали одинаково. Вручную помогли `git rebase origin/main` и `shipctl push`.

### Осложнение

Каждое сохранение с дашборда после чужого пуша даёт уведомление на экран текста git на десять строк, а локальные коммиты копятся неотправленными, пока кто-то не перебазирует руками. Работа с двух машин делает это регулярным: доска расходится ровно в том месте, ради которого её пушат сразу.

### Вопрос

Подтягивать через `git pull --rebase` перед пушем прямо в `commitDocs` или звать `shipctl push`, у которого рубеж пуша уже есть? Что делать при конфликте в `docs/TASKS.md`: откатывать rebase и показывать короткий текст вместо вывода git?

### Гипотеза

Сохранение с дашборда при отставшем main перебазирует локальные коммиты доски поверх origin и пушит молча; уведомление появляется только при конфликте, короткой фразой с подсказкой, что делать.
