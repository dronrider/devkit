# DK-921: Агент стенда obeycheck правит и коммитит живой main devkit

записан 2026-09-10
приоритет: высокий

## Черновик

### Ситуация

2026-09-10, прогон стенда исполнителем DK-916 сценарием
32-interview-exec-fork (подготовка кладёт черновик OB-032 про поиск по тегу
со словарём вместо перебора). Во время прогона 19:34-19:48 в основном
дереве /Users/rider/projects/devkit на main появились два коммита
«fix(taskctl): OB-032 cache depSides ...» (29df905c в 19:39, 427238d7 в 19:45)
с правкой tools/taskctl/*.go, а между ними в дереве лежал незакоммиченный
view.go. Ни одна сессия из ~/.claude их не писала, транскрипт агента стенда
уехал вместе с рабочим каталогом --keep. CLAUDE.md подменного дома пишет
«ядро правил живёт в ~/projects/devkit», и в PATH стенда стоят утилиты с
машины (DK-907).

### Осложнение

Исполнитель DK-914 в это же время упёрся в shipctl merge: сначала
«незакоммиченное в основном чекауте» (чужой view.go), потом рубеж пуша
отбил диапазон с ID не с доски. Задача встала вопросом к человеку, сессия
погасла, чат DK-914 завис. Коммиты без ревью и без строки доски уехали в
origin пушем доски в 19:49. Каждый прогон стенда с фиксацией задачи про
«кэш» или «утилиту» может повторить это в любом живом репозитории машины.

### Вопрос

Чем держать агента стенда в его каталоге: подменный дом без пути на живой
devkit, сеанс без прав на запись вне проекта или рубеж на git commit вне
корня стенда? И что делать с двумя коммитами в main: откатывать или
оставлять как найденную доработку с отдельной строкой доски.

### Гипотеза

Сессия стенда не видит живых репозиториев машины и не может в них писать,
а попытка видна в отчёте прогона как провал сценария по изоляции.
