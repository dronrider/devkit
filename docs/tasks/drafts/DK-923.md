# DK-923: Прогон стенда оставил коммиты в живом main вместо песочницы

записан 2026-09-10
приоритет: средний

## Черновик

### Ситуация

10 сентября в живом чекауте devkit появились два коммита с ID синтетической
доски стенда. `fix(taskctl): OB-032 cache depSides to avoid double computation
in show` (29df905c) и `fix(taskctl): OB-032 cache depSides результат в Board для
избежания повторных вычислений` (427238d7). Оба правят настоящий код taskctl,
кэш depSides в Board и тесты к нему. Подписаны они пользователем `t <t@t>`,
хотя песочница стенда коммитит своей подписью `obeycheck <stand@obeycheck>`.

### Осложнение

Префикс OB стенд раздаёт синтетической доске подопытного, `seedRepo` в
tools/obeycheck/env.go кладёт туда OB-000, OB-001 и OB-002. На доске devkit
таких строк нет, и ревью эти правки не проходили. Пока коммиты лежали
незапушенными, они держали пуш main. Рубеж `shipctl push --check-only`
отбивает диапазон, где у код-коммита нет ID вида DK-NNN. Слияние соседней
задачи DK-914 из-за этого встало на четверть часа, а потом коммиты уехали в
origin чужим пушем.

### Вопрос

Как подопытный оказался в живом дереве. Рабочий каталог прогона, унаследованное
окружение или ручной заход с синтетическим ID. И чем такое ловить. Подписью
коммита, проверкой каталога на старте подопытного или рубежом, который не
пускает в живой репозиторий коммит с чужим префиксом.

### Гипотеза

Прогон поднимает подопытного с рабочим каталогом живого devkit, когда сценарию
нужна настоящая доска. Дешёвый сторож это отказ хука на коммит с ID не с доски
проекта. Дорогой разбор это выяснить, кто задаёт подопытному каталог.
