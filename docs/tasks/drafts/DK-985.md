# DK-985: shipctl merge подтягивает main сам, а не шлёт агента ребейзить дерево

записан 2026-09-14
приоритет: средний

## Черновик

### Ситуация

2026-09-14 01:59, сессия цели DK-902 звала shipctl merge DK-971. Ответ утилиты: «локальный main отстал от origin/main, сначала подтянуть его (git pull --rebase)». В основном дереве лежали незакоммиченные черновики соседней сессии, и ребейз отказал: «You have unstaged changes». Сессия пошла чистить чужие правки (checkout, потом stash), рубеж безопасности оболочки отбил команды, четвёртый повтор ушёл вопросом человеку, и цель простояла ночь. Пришедшие в origin коммиты ветку dk-971 не задевали, слияние было возможно без ребейза дерева.

### Осложнение

Отказ утилиты посылает агента в общее дерево с чужой работой и подсказывает команду, которая это дерево перепишет. Дальше два исхода: рубеж отбивает команду и цель встаёт, либо рубежа нет и чужие незакоммиченные правки теряются. Оба хуже, чем если бы утилита подтянула main сама. Случай повторяется всякий раз, когда в основном дереве работает вторая сессия, а это штатный режим доски.

### Вопрос

Подтягивать main перемоткой ссылки (fetch origin main:main) при чистом пересечении, то есть когда пришедшие коммиты не трогают незакоммиченные файлы дерева, а при пересечении отказывать с именем файла и ждать коммита соседа? Или сливать ветку в origin/main напрямую, не касаясь рабочего дерева main вовсе? Нужен ли тот же порядок в shipctl push и в taskctl move в Check, где main тоже сверяется с origin?

### Гипотеза

shipctl merge при отставшем main подтягивает его сам, когда чужие незакоммиченные файлы с пришедшими коммитами не пересекаются, и слияние идёт одной командой. При пересечении отказ называет файл и сессию, которая его держит, и не советует ребейз грязного дерева. Агент в общее дерево руками не лезет ни в одном исходе.
