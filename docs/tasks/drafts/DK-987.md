# DK-987: Ворота regcheck теряют прогон после ребейза внутри shipctl merge

записан 2026-09-14
приоритет: средний

## Черновик

## Черновик

### Ситуация

2026-09-14, слияние DK-826. Исполнитель прогнал regcheck в дереве ветки в 11:15, записи легли в журнал дерева. Первый shipctl merge ребейзнул ветку на main (8c876f1f, коммит 11:23) и упал на тестах. Повторный merge отказал: «в .devkit/log нет зелёного regcheck за время жизни ветки». Ворот regcheckGate (tools/shipctl/advice.go) считает начало жизни ветки по времени merge-base, а ребейз сдвинул merge-base вперёд, за прогон.

### Осложнение

Прогон, сделанный честно до слияния, ворота перестают видеть после первой же неудачной попытки merge, и агент гоняет regcheck второй раз на том же коде. Каждый повтор слияния после подъехавшего main стоит ещё одного прогона, а при частых коммитах доски main уезжает постоянно. Ворот ловит время, а не код, который проверяли.

### Вопрос

Считать начало жизни ветки по первому коммиту ветки с ID задачи (время автора не меняется при ребейзе), а не по merge-base? Или писать в журнал вместе с записью regcheck sha ветки и сверять с ним?

### Гипотеза

Ворот берёт за начало жизни ветки авторское время первого коммита задачи, и прогон regcheck, сделанный до ребейза, остаётся видимым, пока код тестов не менялся.
