## DK-1650 - Очередь слияний запускает merge на неготовые строки

```toml
revision = 1
outcome = "add"
board_id = "DK-1650"
reason = "четыре проверки готовности пройдены, состав работ подтверждён человеком 2026-11-08 выбором СЦ-1, СЦ-2, СЦ-3, материал DK-1498 влит по развилке «поглощение»"
rationale = "строка доски из дозревшего черновика DK-1259"
board_type = "bug"
rank = "25+7+1+5+3"
size = "M"
accept = "agent"
status = "accepted"
```

## Что происходит

У DK-1072 с 23:41 до 00:17 в «Ходе работы» легло пятнадцать записей «Слияние:
shipctl merge» с шагом пять минут, доска показала «этап: слияние, круг 62»,
а строка стояла в In progress с веткой в разработке. 28 октября у DK-1497
тик дважды запустил shipctl merge на незакоммиченное дерево, отвороты ушли
дежурному эскалацией «неизвестный отказ конвейера», после коммитов попытки
продолжались до 21:50 и отворачивались проверкой ревью.

Отбор берёт кандидатом любую строку In progress с хоть одним кодовым
коммитом сверх main (queue.go:244, queueCode в queue.go:290) и готовности
не спрашивает. Разлив идёт тиком сторожа каждые пять минут, поэтому каждая
живая строка с коммитами получает попытки слияния до конца разработки.
Отметки .devkit/merge-queue.json переживают возврат строки в работу:
queueClear работает после слияния, отдельного стирания при возврате нет.

Запись этапа «Слияние» ставит сам shipctl после большинства проверок
(ops.go:1018 без очереди, ops.go:1285 в очередном пути), поэтому версия
«сливать было нечего» с пятнадцатью записями этапа расходится: попытки
доходили дальше пустой ветки.

## Чего хотим

Отбор спрашивает готовность слияния до заказа merge. Признак выводится из
машинных меток дерева задачи, отдельного поля нет (DK-400.1). В отбор едут
дешёвые метки: файл задачи, открытые замечания, след regcheck, статус.
Тяжёлые проверки остаются в merge. Метки читаются из двух источников:
распакованный файл из worktree и git show с ветки.

Готовность гаснет сама: новый коммит после regcheck, открытое замечание или
возврат строки в работу снимают её на следующем обходе. Перед операцией
merge перепроверяет живую доработку и замечания, окно между проверкой и
слиянием остаётся.

## Границы

- Отметки .devkit/merge-queue.json остаются носителем блокировки и
  ожидания, меняется отбор.
- Отбор читает существующие проверки из internal/trace. Перевод отбора на
  библиотеку этапов шаблонов остаётся за DK-1145, ребро не ставится
  (решение человека 2026-11-08).
- Работа идёт после DK-1334: та правка меняет тот же проход queueDrain и
  его отчёт (решение человека 2026-11-08).
- Разметка исходов отворотов для дежурного слоя не трогается: зова на
  неготовой строке больше нет, размечать нечего.
- Отвороты shipctl push без вывода (наблюдение из DK-1498) не входят:
  причина неизвестна, материал сохранён этим разбором.

## Развилки

- «отворот»: что считать отворотом инцидента DK-1072 при постановке задачи?
  - источник: код tools/shipctl/ops.go:1018, tools/shipctl/ops.go:1285
  - решает: исполнитель
  - рекомендация: сверить по журналу DK-1072, что отворачивало merge после
    открытия этапа: запись этапа ставится после большинства проверок
    (ops.go:1285), значит попытки доходили дальше пустой ветки, и фраза
    «сливать было нечего» с фактом записи этапа расходится
- «источники»: откуда отбор читает метки готовности строки без
  распакованного дерева?
  - источник: код tools/shipctl/queue.go:224-227, tools/shipctl/advice.go:175
  - решает: исполнитель
  - рекомендация: из двух источников: распакованный файл из worktree и
    git show branch:docs/tasks/<ID>.md, иначе кандидат без дерева молча
    выглядит неготовым, queueRows ищет ветку по имени, а не по дереву
- «метки»: какие проверки едут в отбор кандидатов?
  - источник: код tools/shipctl/queue.go:32-34
  - решает: исполнитель
  - рекомендация: в отбор едут файл задачи, открытые замечания, след
    regcheck и статус, а тесты и ребейз остаются в merge: перенос тяжёлых
    проверок в отбор сделает часть отказов дороже нынешней
- «ребейз»: как признак готовности переживает ребейз, сделанный самой
  очередью?
  - источник: доска DK-1398, DK-987
  - решает: исполнитель
  - рекомендация: судить содержимым диффа задачи, гипотеза DK-1398;
    запасной ход предлагает очереди обновлять отметки после своего ребейза;
    линия коммитов гасит готовность зря и вслед за DK-1398 и DK-987
    добавляет мёртвый цикл

## DoD

На временном репозитории с синтетической доской разлив не заказывает merge
на строку без признаков готовности и заказывает на готовую в тот же проход.
На живой разработке запись «Слияние: shipctl merge» не появляется. После
возврата строки в работу готовность снимается на следующем обходе. После
ребейза, сделанного самой очередью, готовность зря не гаснет.
Регрессионный тест падает на старом коде и проходит на исправленном
(regcheck).

## Ранг

`25+7+1+5+3 = 41`, P2.

- Серьёзность 25: у читающего живую строку настоящие этапы тонут в записях
  «Слияние», у дежурного каждый отворот живой разработки съедает реплику.
  Обход дешёвый: шум отличим по времени записи, отвороты исчерпываются
  сами по ходу разработки.
- Ценность 7: улучшения ждут, черновики DK-1259 и DK-1498 записали один
  предмет, инциденты прошли на DK-1072 и DK-1497.
- Неопределённость 1: подход записан в разборе и сверен с кодом, открытые
  развилки внутренние с рекомендациями.
- Поправка на баг 5: конвейер запускает слияние там, где его быть не
  должно, и пишет ложный этап.
- Рычаг 3: дежурный слой перестаёт получать эскалации живой разработки,
  очередь перестаёт гонять пустые попытки.

замок работает и под свободным состоянием.

## Чего хотим

Убрать файл из индекса (git rm --cached) и закрыть путь гитигнором. Замок
на диске остаётся работать как раньше.

git ls-files не показывает .devkit/merge-queue.json.lock, путь закрыт
гитигнором, замок создаётся и снимается как раньше. Новые клоны файл не
получают.
