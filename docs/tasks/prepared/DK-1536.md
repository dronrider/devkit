## DK-1712 - UI-задачи стартуют по согласованному порядку дизайна

```toml
revision = 2
outcome = "add"
board_id = "DK-1712"
board_type = "LLD"
rank = "50+8+5+0+2"
size = "M"
accept = "user"
barrier = "согласие"
```

## Что происходит

В DK-1536 пользователь описал разработку UI без предварительного макета. Результат расходится с ожиданиями. Ошибки пользовательского потока требуют переделок и расходуют подписку. Проверка 2026-11-14 подтвердила, что ACCEPTANCE.md учитывает согласованный до старта макет. В tools/taskctl нет специальной проверки готовности дизайна. Есть общие ворота развилок и зависимостей.

## Чего хотим

Согласованное LLD определяет порядок подготовки и согласования UI до разработки, проверяемые исключения и механический допуск задачи к старту. Решение охватывает СЦ-1, СЦ-2 и СЦ-3 исходника DK-1536. Агент получает однозначное основание разрешить старт или объяснить отказ человеку.

## Границы

Результатом этой задачи будет проект решения, согласованный человеком. Изменения скиллов, правил и кода ворот оформляются отдельными задачами после принятия LLD. Доставка и просмотр макетов остаются предметом DK-1554. Из него учитываются требования переносимости между клиентами и проектами, работы из консоли и хранения материалов в Git. HTML, designctl и docs/design пока не согласованы.

## Предмет LLD

1. Определить признаки UI-составляющей, существенного изменения потока и мелкой правки. Разобрать пример изменения цвета кнопки и явный отказ человека от дизайна.
2. Сравнить фазу дизайна на груминге, отдельную задачу проектирования и подготовку перед стартом. Описать влияние на автономный выбор задач и зависимости.
3. Определить минимальный состав макета и пользовательского потока, связь с задачей, хранение и переносимый формат. Согласовать контракт с DK-1554; просмотр и доставку здесь не реализовывать.
4. Описать явное согласование конкретного материала, фиксацию исключений и последствия изменения дизайна или состава UI после согласования.
5. Определить место механических ворот, поведение ручного и автономного старта, сообщения об отказе и способ продолжения. Проверить использование существующих развилок и зависимостей.
6. Показать схему для UI без дизайна, согласованного дизайна и дизайна, исправленного после согласия. Также показать её для мелкой правки, явного разрешения без макета и задачи без UI. Неизвестные условия вынести на согласование, без молчаливого выбора политики.

## DoD

- Подготовлено LLD в docs/lld с альтернативами, принятым решением, контрактом допуска UI-задач и границей с DK-1554.
- Для каждого случая из предмета описаны входные условия, основание допуска или отказа и дальнейшее действие агента и человека. Решение согласовано с ACCEPTANCE.md.
- Определены критерии исключений, способ фиксации согласия и поведение при изменении согласованного дизайна. Процесс переносим между подключёнными проектами и агентскими клиентами.
- Человек согласовал решение. После принятия выделены задачи реализации с зависимостями и сценариями проверки.

## Ранг

50+8+5+0+2 = 65, P1

- Серьёзность 50: конвейер UI-задач ведёт к результату, расходящемуся с ожиданиями, и требует существенных переделок; наблюдение пользователя в DK-1536.
- Ценность 8: согласование до реализации должно уменьшить повторные затраты на UI и пользовательские потоки; это основная польза запроса. Числовая экономия пока не измерена.
- Неопределённость 5: не выбраны место фазы, границы исключений, формат и контракт ворот; нужен проект решения.
- Поправка на баг 0: добавляется требование к процессу, регресс существующего контракта не установлен.
- Рычаг 2: улучшает будущие UI-задачи; эффект не распространяется на каждую задачу devkit.

## Цена

M: один связный документ решения и его согласование; реализация исключена из оценки.

## Приёмка

- вид: user
- барьер «согласие»: решение меняет общие правила подготовки и старта UI-задач.
  - обхода нет: субагент-критик проверяет противоречия, но не даёт согласие человека.
- Остальные барьеры проверены: внешний вид экрана не является результатом LLD; физический доступ, секреты, невозвратные операции и наступление внешнего события для проектирования не требуются.

## Условия

Условий, посильных только человеку, для начала подготовки LLD не нашёл при проверке исходника, DK-1554, формы и кода ворот. Согласование общего процесса потребуется при приёмке LLD. Согласие на применение этой карточки отдельно запрашивается в разговоре груминга.
