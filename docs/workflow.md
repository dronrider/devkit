# Карта переходов работы

Карта показывает путь задачи от идеи до архива. Узлы это состояния работы,
рёбра плоские строки «из -> в: кто делает» скиллом или командой. Пишется руками,
и это осознанно: смысловые переходы вида «после груминга строка идёт под вердикт
pick» из текстов автоматически не выводятся (LLD DK-400, решение 8). Полноту
держит сторож `devkitctl doctor`: каждый скилл `kit/skills/*`, каждый статус доски
и все пять рубежей обязаны быть упомянуты, неупомянутое это находка. Проекцию той
же карты на ось одной задачи печатает `taskctl progress`, карта компонентов живёт
отдельно в [map.md](map.md), а правила, из которых переходы выведены,
в `RULES.board.md`.

Статусы у доски четыре: Backlog, In progress, Check и Blocked; сделанное
уезжает в архив отдельным файлом `docs/TASKS-archive.md`. Ниже карта разбита
по участкам пути, рёбра плоские: «из -> в: кто делает».

## Зарождение

- идея -> черновик: сырая мысль, ради которой не хочется останавливаться на
  разбор, ложится мимо доски командой `taskctl draft` в `docs/tasks/drafts/`;
  как её писать (заголовок, ситуация, осложнение), в скилле `board-draft`.
- черновик -> строка Backlog: скилл `board-groom` разбирает накопитель
  (ворота готовности, дубль, ранг по слагаемым) и оформляет перенос
  `taskctl add --id <ID>`.
- черновик -> приписка к стоящей строке: `taskctl draft attach`.
- черновик -> отложен или удалён: `taskctl draft defer` с причиной, протухшее
  убирает `taskctl draft drop`.

Разобранная работа идёт строкой сразу, мимо черновика: ворота готовности тогда
проходит сама сессия по скиллу `board-task`, а очевидные находки едут строкой
без ворот. Строку-цель длинной работе ставит скилл `goal-start`, см. раздел
«Цель» ниже.

## Работа

- Backlog -> In progress: диспетчер берёт задачу по вердикту
  `agentctl pick <ID> --record` и переводит `taskctl move <ID> in-progress`;
  процедура одного раза в скилле `board-task`, пачку задач ведёт `board-batch`.
- In progress -> ветка: `shipctl start <ID>` заводит ветку и worktree на задачу
  (скилл `board-ship`); мелочь идёт коммитом прямо в main, без ветки.
- правка -> проверенная правка: тест пишется вместе с правкой и обязан падать
  на старом коде, стандарт и прогон regcheck держит скилл `test-standard`;
  долгоживущая проза вычитывается свежим контекстом по скиллу `proofread`.
- замысел -> долгоживущий текст: черновик, файл задачи, решение LLD и раздел
  README пишутся с эталонами из корпуса скилла `prose`, который кладёт в
  контекст письма случайный набор фрагментов своего жанра; вычитка остаётся
  вторым рубежом и идёт после.
- правка промптов -> проверенная правка: скилл, определение субагента или
  страница-контракт проверяются прогоном стенда по скиллу `prompt-test`;
  повод называет подсказкой `taskctl move <ID> check`, когда в коммитах
  задачи есть такие пути.

## Ревью и слияние

- ветка -> ревью: ревьювера называет `agentctl pick <ID> --role review`,
  замечания ложатся в раздел «Ревью» файла задачи командой
  `taskctl review add`.
- ревью -> ветка: замечания исправляются коммитами в ту же ветку и закрываются
  `taskctl review resolve`, после исправлений ревью прогоняется снова.
- ревью -> слияние: `shipctl merge` проверяет ворота (зелёный regcheck,
  тестовый файл в диффе, сценарий проверки) и уходит fast-forward в main.
- слияние -> выкат: merge катит команду выката из гитигнорнутого
  `.devkit/deploy.local` и переводит задачу в Check; выкат бывает за
  пользователем, тогда merge останавливается на слитом main.
- слияние -> Check без выката: бескодовая задача (дока, LLD, разбор) едет
  в Check сама и очередь выката не держит.
- слияние -> поезд: `shipctl merge --train` копит в main без выката, задача
  остаётся в In progress; `shipctl ship` везёт накопленное одним выкатом
  и переводит состав в Check (скилл `board-batch`).

## Выкат и приёмка

Приёмка двухступенчатая: агентская часть сценария прогоняется на проде сразу
после выката, глазами задача принимается потом, в Check. Непроверенным
считается выкат без прогнанного smoke, а не незакрытая задача.

- выкат -> очередь занята: выкат без отметки smoke держит следующее слияние,
  непроверенный выкат в каждый момент один.
- очередь -> свободна: исполнитель прогоняет агентскую часть сценария и
  отмечает прогон `shipctl smoke <ID>` строкой «smoke прогнан, <дата>»
  в разделе «Выкат» файла задачи; приёмка глазами очередь не держит, строки
  с отметкой копятся в Check и закрываются пачкой.
- Check -> архив: приёмка прошла, `taskctl close <ID>` уносит строку в архив;
  задачу с агентским сценарием закрывает сам агент по прогону.
- Check -> In progress: приёмка с замечаниями, `taskctl move <ID> in-progress`,
  выкат за такой задачей проверен и очередь не держит.
- Check -> провал: сломанный прод отмечает `taskctl fail <ID> --reason`,
  задача возвращается в In progress с пометкой «[провал: ...]» и держит
  очередь целиком.
- провал -> выкат: `shipctl revert` и повторный выкат либо форвард-фикс
  одиночным `merge`; пометка гаснет повторным переводом в Check.

## Парковка и возврат

- In progress -> Blocked: задача, упёршаяся в обстоятельства снаружи доски,
  паркуется `taskctl move <ID> blocked --reason "вопрос: <суть>"`; причина
  с машинным префиксом отличима от прозы («вопрос:» ждёт человека,
  «окружение:» ждёт среды задачи, «автор:» ждёт ответа коллеги в тредах чужого
  MR, «спор:» стоит на отказе автора чинить блокирующее), и паркует задачу
  инструмент ожидания в том же заходе, что спрашивает человека.
- Blocked -> In progress: ответ ложится строкой во вход разговора задачи
  `.devkit/chat/task-<ID>.in` (основное дерево или дерево задачи), и
  сторожок `devkitctl watch` будит строку своим тиком; будит он только
  ожидание человека, «окружение:» и проза реплик не ждут, а «автор:» тот же
  сторожок снимает сам, увидев ответ в тредах MR. Возврат это повод
  решить заново, а не приказ работать.
- ожидание своей задачи: зависимость ставится `taskctl dep add`, без смены
  статуса и секции.

## Цель

Длинная работа ставится целиком и ведётся циклом витков поверх обычного
конвейера задач.

- идея -> цель: скилл `goal-start` пишет постановку: строка-цель на доске,
  файл цели с DoD и бюджетом, пробная нарезка списком кандидатов.
- цель -> задачи доски: нарезка идёт по скиллу `goal-cut`; первый виток
  материализует список строками и сверяет сумму цен с остатком бюджета.
- виток: скилл `goal-loop` режет, исполняет, ревьюит и выкатывает задачи
  обычным конвейером; следующий виток поднимает оболочка `goal-run` либо
  человек фразой «продолжай цель <ID>».
- сбой ядра по ходу цели: скилл `live-core` чинит утилиты devkit на месте,
  расход пишется строкой в «Журнал» цели.

## Рубеж

`taskctl progress <ID>` печатает рубеж задачи числом F, производным от машинных
меток и не двигающимся назад: 0.00 строка заведена, 0.35 первый коммит в ветке,
0.56 сдано на ревью, 0.89 слито и выкачено, 1.00 приёмка пройдена. Это проекция
настоящей карты на ось одной задачи, читает её и планировщик, и дашборд.
