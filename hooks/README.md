# Хуки: проверки текстов, уведомления и фоновая работа по расписанию сессии

Механизация правил, которые иначе держатся на внимательности: запрещённые
символы (RULES.md, «Код и тексты» п. 1), разбухание индекса памяти,
чувствительное в доске (RULES.board.md, «Трекинг задач» п. 8), правка кода без
тестов и пуш из сессии агента без разрешения (RULES.md, «Тесты обязательны» и
«Git»). Каждая
проверка стоит в двух рубежах: git-хуки ловят перед коммитом, PostToolUse-хук
Claude Code сразу при записи файла (агент получает находки как фидбек и
переписывает сам, правило не занимает контекст). Отдельно от них стоят два
PreToolUse-хука. Один, на Bash, закрывает чтение секретов через shell: `deny`
режет инструмент Read, а хук прикрывает обход через `cat`, `grep` и подобное
(задача DK-228, цель DK-207). Два других, на Read, режут повторное чтение файла,
что не менялся в этой сессии (задача DK-146, цель DK-206), и чтение длинного
файла целиком, когда хватило бы фрагмента (задача DK-147, та же цель). Отдельно от проверок тут же
живут `quota-refresh.sh`, `session-task.py`, `notify.py`, `chat-in.py` и
`board-catchup.sh`: первый ничего не проверяет, а пользуется стартом сессии как
единственным регулярным событием на машине (см. «Снимок квоты на старте
сессии»), второй записывает на том же старте, какую задачу сессия ведёт (см.
«Реестр чатов задачи»), третий подаёт наружу сигнал, что сессия ждёт действия
(см. «Уведомления о сессии»), четвёртый работает в обратную сторону и доносит
реплику человека до идущего витка цели (см. «Разговор с идущим витком»), а
пятый догоняет боковое дерево доски до свежего указателя, пока сессия не
прочла из него устаревшую доску (см. «Догон бокового дерева на старте
сессии»).

Ядро проверки символов: в своём тексте только символы клавиатурных раскладок
en/ru, «ёлочки» и `№`.

Находка говорит не только про запрет, но и про то, чем текст переписывать.
Правило в резиденте держит сам запрет, а разбор («длинное тире перестраивается
в живую прозу, а не подменяется двоеточием») приезжает ровно в тот момент,
когда его нарушили, и потому в резиденте не лежит. `check-symbols.py` подбирает
разбор по видам символов, которые встретились (перечень `ADVICE` в нём же),
`check-commit.py` носит его при каждой своей находке, `check-tests.py` и
`pre-push` целиком состоят из него. Новый вид находки заводится вместе со
строкой разбора, иначе агент получает запрет без выхода и тратит виток на
догадки.

Ядро одно, `check-symbols.py` (нужен только python3): аргументами файлы, либо
`--stdin` для потока, либо `--hook` для хука харнеса. Выход 0 чисто, 1 находки
(в режиме `--hook` находки дают 2, так их видит агент). Файлы из директории
`testdata` проверка пропускает: там лежат снятые живьём снимки чужого вывода,
и переписать их клавиатурными символами нельзя, значит без пропуска такой
снимок красит проверку насовсем.

## Первый запуск

Нужен python3 и клон devkit рядом с проектом. Хуки подключаются к проекту
одной командой из его корня, и то же самое чинит диагностика
(`devkitctl doctor --fix` ставит настройки харнеса, git-хуки называет
находкой с этой самой командой):

```sh
cd ~/projects/xr-proxy
git config core.hooksPath ../devkit/hooks
```

Результат видно сразу, отдельного стенда для этого не нужно: положить
запрещённый символ в файл и спросить проверку напрямую.

```sh
$ printf 'Правило \u2014 оно такое.\n' > /tmp/probe.md
$ python3 ../devkit/hooks/check-symbols.py /tmp/probe.md | tail -2
как переписать:
- длинное тире: перестроить предложение живой прозой, а не подменять двоеточием, запятой или дефисом
```

Строкой выше проверка называет файл, номер строки и саму строку с находкой;
тут она срезана `tail`, потому что сам символ в этот README не положить, его
отобьёт та же проверка.

Выход 1 и есть находка. Тот же текст, попавший в коммит, отобьёт `pre-commit`,
а в сессии Claude Code его поймает PostToolUse-хук сразу при записи файла:
раскладывает оба рубежа `devkitctl doctor --fix`, руками тут ничего не
правится. Что именно стоит на каждом рубеже, разобрано ниже по разделам.

## Git-хуки (подключаются на проект)

Из корня проекта, devkit лежит рядом:

```sh
git config core.hooksPath ../devkit/hooks
```

`pre-commit` проверяет состав коммита (правка кода без тестов, см. ниже) и
добавленные строки staged-диффа: символы во всех файлах, чувствительное в
файлах доски, прозу, сбившуюся на агентский шаблон (все три разобраны ниже).
`commit-msg` смотрит текст коммита без комментариев git: сначала символы,
затем `check-commit.py` по разделу «Git» RULES.md. Тот ловит следы ассистента
(строгий запрет п. 4), body у коммита (пишется одной строкой, п. 2),
тип conventional-префикса, которого нет в последней сотне коммитов проекта
(п. 1), и ID задачи в
subject на main репозитория с доской (RULES.board.md, «Трекинг задач»
п. 7, разбор ниже). Короткая история
(меньше `HISTORY_MIN` коммитов) и subject без префикса проверку типа выключают,
`revert` разрешён всегда: его пишет `shipctl revert` на аварийном пути.

Порог на историю нужен свежим проектам. Сразу после `devkitctl new` в проекте
стоит один коммит подключения, и на нём перечень префиксов нормой ещё не стал:
первая же строка доски приезжала бы коммитом `docs(tasks)` и вставала находкой
про чужой тип на ровном месте (DK-125).

След ищется не одного ассистента. Родовые `Co-authored-by` и `Generated with`
ловят почти всех, но подпись доезжает и мимо них (автором коммита, строкой
«paired with»), поэтому рядом стоит перечень `ASSISTANTS` из самого
`check-commit.py`: адреса и боты Claude Code, Codex, Cursor, aider, OpenHands,
Devin, Copilot и Jules, снятые с их реальных коммитов на github. Новый
ассистент добавляется туда строкой вместе с прогоном по нему в
`check_commit_test.py`. Совпадения в чужом коде не всплывают, пока
его не трогаешь; для осознанного исключения (тестовые данные с юникодом,
законный новый тип коммита) `git commit --no-verify`.

`core.hooksPath` выключает `.git/hooks` целиком. Если у проекта уже есть свои
хуки, вместо этого симлинки на конкретные:

```sh
ln -s ../../../devkit/hooks/pre-commit .git/hooks/pre-commit
ln -s ../../../devkit/hooks/commit-msg .git/hooks/commit-msg
ln -s ../../../devkit/hooks/pre-push .git/hooks/pre-push
```

## ID задачи в subject на main

Ядро правил доски держит связь коммита с задачей на ID в subject: по нему
находятся коммиты задачи, revert и состав поезда, и связь эта чинится дорого
(DK-213, случай IRC-103: коммит без ID лёг в main мимо ветки задачи и
столкнулся с настоящей веткой, у которой ID тот же по смыслу, но в истории
не найти). Прозой правило было и раньше, рубеж на коммите нет.

`check-commit.py` спрашивает у git саму ветку, корень репозитория и
staged-дифф коммита (то, что видит `commit-msg`, это уже состав будущего
коммита). Находка встаёт, когда сошлись все условия сразу: в корне
репозитория есть `docs/TASKS.md` (репозиторий с доской), текущая ветка
`main`, коммит трогает хоть один файл вне трёх мест доски (`docs/TASKS.md`,
`docs/TASKS-archive.md`, `docs/tasks/`), а в subject нет строки вида
`ABC-123`. Коммит одной только доски (её пишет `taskctl` с ID в
подписи) рубеж пропускает без вопросов, а мелочь вне задачи, для которой ID
не нужен, обходится осознанно тем же `git commit --no-verify`, что и
остальные находки `check-commit.py`.

Фичеветки рубеж не смотрит вовсе: ID там уже есть в имени ветки
(`xr-043-deploy`), а до main код доезжает слиянием, где ID остаётся в
subject коммита истории. Репозиторий без доски (`docs/TASKS.md` в корне
нет) рубеж тоже не трогает: спрашивать про задачу там не с чего. Вне
git-репозитория и на любой ошибке команды (`git` не в PATH, битый индекс)
проверка молчит по тому же принципу, что и остальные рубежи на git-контексте
в этом файле: спросить было негде, значит рубеж не сторож.

## Правка кода без тестов

`check-tests.py` держит правило «Тесты обязательны» на рубеже коммита: если в
коммите есть код, а тестового файла нет ни одного, коммит не проходит. Смотрятся
имена файлов, а не содержимое: тест, дописанный к правке, это либо новый
тестовый файл, либо изменённый старый, и то и другое видно по имени. Код узнаётся
по расширению (перечень `CODE_EXT`) и по шебангу у файлов без расширения, тестом
считается путь с каталогом `tests`, `testdata`, `spec` и подобными либо имя вида
`*_test.*`, `test_*`, `*.spec.*`; фикстура в `testdata` идёт за тест, потому что
правка, приехавшая с новой фикстурой, покрытием закрыта.

Проверка грубая нарочно: она ловит не качество теста, а его отсутствие, а
краснота регрессионного теста проверяется `regcheck`, и об этом же говорит текст
находки. Обход осознанный и узкий:

```sh
DEVKIT_NO_TESTS=1 git commit -m '...'   # пропускает только эту проверку
git commit --no-verify                  # пропускает весь pre-commit
```

Первый вариант для случаев, где тесту взяться неоткуда (перенос файла, правка
сборки), и остальные рубежи он не выключает.

## Пуш из сессии агента

`pre-push` держит правило «push в origin и создание MR делает пользователь».
Рубеж смотрит окружение: переменная сессии агента (`CLAUDECODE`,
`CLAUDE_CODE_ENTRYPOINT`, `CURSOR_AGENT`) и есть признак того, что пуш идёт не
руками. Ручной пуш пользователя рубеж не видит вовсе, таких переменных у него в
окружении нет, и новый харнес добавляется в хук строкой.

Исключений из правила два, и оба идут через утилиты devkit: коммит доски
пушится сразу и без просьбы (`taskctl ... --push`), автономный режим сам сливает
и катит (`shipctl`). Обе утилиты ставят `DEVKIT_PUSH_OK=1` в окружение своего
`git push` и только его, поэтому разрешение не растекается на попутные команды
git.

Сверх того рубеж сам пропускает пуш, где в диффе только доска: `docs/TASKS.md`,
`docs/TASKS-archive.md` и `docs/tasks/`. Правка файла задачи, сделанная руками
(журнал цели, постановка, вывод сценария), у изменяющих команд taskctl своего
флага не имеет, а правило требует пушить её сразу, поэтому обычный
`git commit` + `git push` тут проходит без разрешения (DK-119). Калитка узкая:
она разбирает строки stdin, которые git подаёт хуку, и требует движения вперёд
от известного ремоута; новая ветка, удаление ветки, дивергенция и неизвестный
sha доской не считаются и отбиваются как раньше, как и любой пуш, где кроме
доски в диффе есть хоть один файл.

По прямой команде пользователя пуш делается руками:

```sh
DEVKIT_PUSH_OK=1 git push
git push --no-verify
```

## Хук Claude Code (подключается глобально)

В `~/.claude/settings.json`:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|NotebookEdit",
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/check-symbols.py --hook" }
        ]
      }
    ]
  }
}
```

Хук смотрит не файл целиком, а записанный фрагмент (new_string/content из
tool_input), поэтому чужой существующий текст не трогает.

## Разбор входа по имени протокола

Тело проверки одно на все инструменты, меняется только форма события на stdin.
Своего разбора в проверках нет: таблица разборщиков живёт в `hookio.py`.
Строка таблицы это протокол, три разборщика и два канала ответа. Разборщики
снимают с события запись (путь и записанные куски текста), событие сессии для
уведомителя и завершённый ход инструмента: сессию целиком, дерево хода, имя
инструмента и роль субагента, если ход шёл под ним. У хода самой сессии роли в
событии нет вовсе, и пустое место читается именно так. Сессия на этой оси не
режется до восьми символов, как режется на оси уведомителя: там ID идёт
подписью в баннере, а тут сверкой с именем витка, которой половина UUID не
годится.

Каналов ответа два, и путать их нельзя. Находка (`Reply`) это stderr с выходом
2: харнес отдаёт написанное агенту фидбеком в рамке «с тем, что ты сделал,
что-то не так, поправь», и ею живут все проверки ниже. Добавка контекста
(`Context`) это запись JSON на stdout с полем
`hookSpecificOutput.additionalContext` и выход нулём: текст приезжает к модели
без всякой рамки, а ход остаётся удачным. Рамка находки безобидна ровно потому,
что проверки стоят на записи файла и на чтении, где повторить ход дёшево. На
ходе с побочным эффектом вроде `git push` та же рамка читается как провал, а
понятная реакция на провал это повтор, поэтому всё, что не является
претензией к ходу, идёт добавкой.

Имя протокола приходит аргументом:

```sh
python3 hooks/check-symbols.py --hook claude-code
python3 hooks/check-symbols.py --hook              # то же самое
```

Голый `--hook` остаётся псевдонимом claude-code: команды в settings.json
прописаны на машинах без имени, и обновление devkit не должно их ломать. Имя,
которого в таблице нет, это отказ кодом 2 со строкой про незаведённый разбор, а
не тихий пропуск: опечатка в настройках иначе выключила бы проверку насовсем.

Проверяется разбор по образцам. В `hooks/testdata/<протокол>/` лежат события,
снятые живьём с работающего инструмента (у claude-code это запись файла четырьмя
инструментами, ввод пользователя, конец хода, отработавший субагент, запрос
разрешения и завершённый ход инструмента, свой у сессии и свой у субагента).
`hookio_test.py` гоняет каждый образец через каждую проверку, а
`notify_test.py` через уведомитель. Протокол без образцов в таблицу не принимается: форма события живёт
на стороне инструмента, и разбор, проверенный по памяти, закрепляет наше
представление о ней вместо неё самой.

## Линт индекса памяти

`check-memory.py` следит, чтобы индексы памяти Claude Code (`memory/MEMORY.md`
проектов) не разбухали: каждая запись это одна строка-указатель до 160
символов, содержимое и статусы живут в файлах памяти. Разжиревший индекс
грузится в контекст каждой сессии проекта. Подключается вторым PostToolUse-хуком
рядом с проверкой символов:

```json
{ "type": "command", "command": "python3 ~/projects/devkit/hooks/check-memory.py --hook" }
```

Где лежит индекс, знает не хук, а профиль харнеса: `[hooks] memory_index` в
`kit/harness/<протокол>.toml` держит хвост пути (`/memory/MEMORY.md` у Claude Code),
и на файлы мимо него хук не реагирует. Ключа в профиле нет, значит памяти у
инструмента нет, проверка молчит и setup её не подключает: находки про индекс
были бы там шумом. Ручной прогон профиля не спрашивает:
`hooks/check-memory.py <путь к MEMORY.md>`.

## Чувствительное в коммите

`check-sensitive.py` следит, чтобы в коммитируемые тексты не попадали
IP-адреса, токены, приватные ключи, пары вида «пароль: значение» и
корп-домен. Скоуп шире доски: смотрится любой коммитимый файл, не только
`docs/TASKS.md`, `docs/TASKS-archive.md`, `docs/tasks/`, `docs/lld/`. Так
секрет, попавший в исходник или в доку вне `docs/`, ловится тем же рубежом,
что и доска. Сторонний код и сборочный мусор пропускаются: `vendor`,
`node_modules`, `__pycache__`, `.git`, `.devkit`, `dist`, `build`,
окружения `.venv`/`venv` перечислены в `SKIP_DIRS`. Тестовые файлы с
фикстурами тоже пропускаются: адреса и токены там это данные, а не утечка,
шаблоны `*_test.*`, `test_*.*`, `*.spec.*` лежат в `SKIP_FILES`. Вместо
адреса пишется роль машины («роутер DE», «VPS RU»), а конкретика остаётся в
гитигнорнутом `local-docs`. Loopback и документационные диапазоны RFC 5737
не считаются находкой.

Корп-домен как паттерн держит значение вне кода: в `check-sensitive.py` его
нет, хук берёт домен в рантайме из переменной окружения `DEVKIT_CORP_DOMAIN`
или из ключа `corp_domain` в `RULES.local.md` рядом с CWD (несколько доменов
через запятую). Источника нет, домен неизвестен, паттерн не активен, хук
молчит. Так значение домена не въезжает ни в код хука, ни в коммит
репозитория, где лежит сам рубеж.

В git-рубеж проверка встроена в общий `pre-commit`, отдельного подключения не
надо. PostToolUse-хук ставится третьим рядом с остальными:

```json
{ "type": "command", "command": "python3 ~/projects/devkit/hooks/check-sensitive.py --hook" }
```

Файлы из `SKIP_DIRS` хук на содержимое не смотрит. Ручной прогон:
`hooks/check-sensitive.py <файлы>` (фильтра путей в этом режиме нет).

Отдельно проверяется сам `local-docs`: правило отправляет туда всю конкретику,
но держится оно на том, что каталог заигнорен, а это забывается молча. На записи
файла в `local-docs` хук спрашивает git (`git check-ignore`), заигнорен ли путь,
и находкой говорит добавить строку в `.gitignore`; в `pre-commit` находка это уже
сам факт, что файл из `local-docs` попал в коммит. Вне репозитория и без ответа
git находки нет: рубеж тут не сторож.

## Проза, сбившаяся на агентский шаблон

`check-prose.py` меряет записанный кусок текста шестью счётчиками и сверяет их
с порогами. Метрики взяты из замера 38,5 тыс. слов агентской прозы против
человеческого корпуса (`docs/tasks/DK-446.md`, раздел «Что показал замер»):
средняя длина предложения, доля предложений длиннее 25 слов, довод в той же
фразе, двоеточие-довод в середине фразы, хвост «..., а не Y» и вывод-обобщение
в конце абзаца. Проверка не зовёт модель и не разбирает смысл текста, она
считает частоты регулярками.

Первый прогон по своему файлу:

```
hooks/check-prose.py docs/tasks/DK-446.md
```

Печатается объём куска и шесть строк с числами, а рядом с числом стоит
перейдённый порог, если он перейден. Тот же разбор идёт на записи файла и на
коммите, только по добавленному тексту, а не по файлу целиком.

Пороги и режим лежат в `kit/prose.toml`, в коде их нет вовсе. Ключ `mode`
выбирает, чем кончается превышение: `warn` это подсказка добавкой к ходу, ход
остаётся удачным; `block` это отказ, и агент переписывает написанное. Порог
предупреждения стоит выше человеческой колонки замера, порог блокировки на
уровне агентской. `min_words` отсекает куски, где частота скачет от одного
предложения. `suffixes` называет расширения, которые вообще считаются прозой.
Конфига нет или в нём не хватает метрики, и сторож молчит; про это молчание
говорит находкой `devkitctl doctor`, который спрашивает сам хук режимом
`check-prose.py --config`. Свой конфиг на прогон подставляется переменной
`DEVKIT_PROSE_CONFIG`.

В git-рубеж проверка встроена в общий `pre-commit` четвёртой: выход 1 отбивает
коммит, вывод при нулевом выходе печатается предупреждением и коммит проходит.
PostToolUse-хук ставится четвёртым рядом с остальными:

```json
{ "type": "command", "command": "python3 ~/projects/devkit/hooks/check-prose.py --hook" }
```

Не меряются образцы: пути с `testdata`, каталоги `corpus` и файл `corpus.md`.
В сторожевом корпусе вычитки плохие фразы лежат нарочно, и находка на них
означала бы поломку там, где её нет.

Калибровка порогов записана в `docs/tasks/DK-521.md`, раздел «Проверка».
Перекалибровка это правка `kit/prose.toml` с новым прогоном по тому же корпусу,
а не правка кода. Счёт метрики меняется по замеру: задача DK-524 сняла с
метрики `argued` полную форму «не X, а Y», у которой замер дал 1,5 на тысячу
слов у агентов против 2,3 у людей.

Человеческая опора порогов это колонка трекеров того же замера и реплики
пользователя из корпуса эталонов. Реплики лежат в `kit/skills/prose/corpus`,
у таких фрагментов в источнике стоит журнал сессии. Первый коммит `RULES.md`
опорой больше не служит, приёмка DK-522 отбраковала его как текст, писанный
вместе с моделью. По оставшимся источникам DK-533 пересчитала три порога
предупреждения, `argued`, `colon_mid` и `but_not_tail`.

Там же хвост научили разбирать форму. Хвост это запятая, оборот «а не» и
договорённое отрицание. Без запятой оборот работает союзом. В кавычках или в
обратных апострофах лежит чужая фраза. Ни в том, ни в другом случае находки
нет.

Те же шесть примет стоят первыми пунктами чек-листа вычитки
(`kit/skills/proofread/SKILL.md`), ключ метрики выписан рядом с пунктом, и
совпадение списков держит тест `check_prose_test.py`.

## Чтение секретов через Bash

`check-read-secret.py` закрывает направление, которое `check-sensitive`
оставляет открытым: то, что не уехало в коммит, агент всё равно читает из
контекста, и файл доступов, приватные ключи, хранилище `secretctl` и `local-docs`
уезжают в модель через `Read` или `cat`. Инструмент `Read` режет `permissions.deny`
(правила `SECRET_DENY` в `perms.py`, та же четвёрка путей), а этот хук прикрывает
обход через shell: `cat`, `grep`, `head`, `tail` и подобное на тех же путях.
Значение секрета остаётся доступно через `secretctl`, поэтому рубится только
прямой доступ к значениям, не работа с секретом вообще.

Подключается PreToolUse-хуком на Bash:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/check-read-secret.py --hook" }
        ]
      }
    ]
  }
}
```

Матчинг путей берёт надёжный минимум: разворот `~/` и сравнение с эталонными
абсолютными путями и их префиксами, без попыток интерпретировать shell целиком.
Переменные (`$HOME` и подобные), кавычки и пайпы не разворачиваются, поэтому
обход через них хуком не ловится: надёжно режется прямой вид путей, и этого
хватает для основного сценария, а хитрый обход остаётся за рубежом. Оба слоя
раскладывает `devkitctl doctor --fix`, перечень путей один на оба. Ручной прогон:
`hooks/check-read-secret.py <команда>`.

## Повторные чтения файла

`check-reread.py` закрывает правило «прочитанное лежит в контексте до конца
сессии»: четверть вызовов Read это перечитывание уже прочитанного, и дисциплиной
оно не держится (замер DK-148 по 972 сессиям, рекорд 85 чтений одного файла за
сессию). Хук стоит на PreToolUse на Read и отвечает подсказкой вместо
содержимого, когда файл уже прочитан в этой сессии и с тех пор не менялся.
Первый Read и чтение после правки файла проходят как раньше; чтение другого
окна того же файла (другие `offset`/`limit`/`pages`) повтором не считается.

Подключается PreToolUse-хуком на Read:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Read",
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/check-reread.py --hook" }
        ]
      }
    ]
  }
}
```

История чтений своя, не транскрипт: журналы `jsonl` растут на десятки
мегабайт, и каждое чтение гнать их через парсер накладнее самой пользы.
Состояние лежит в `~/.devkit/reread/<session_id>.json`, по записи на окно.
Неизменность файла проверяется парой `(mtime_ns, size)` из одного `stat`:
любая правка (Edit, Write, `git checkout`, `echo >`) меняет `mtime`, а `size`
подстрахует на файловых системах с грубым разрешением времени. `mtime` без
правки меняет только `touch`, и держать этот случай за рубежом нечем, но и
вред от него узкий: один пропуск подсказки после холостого `touch`. Окно это
четвёрка `(file_path, offset, limit, pages)`: тот же файл другим окном читает
своё состояние, и резать его нельзя. Запись состояния атомарна через
`os.replace`, параллельные сессии друг другу не портят файл; брошенное
состояние старше недели убирается тем же проходом, что и читает.

Подсказка идёт каналом `PreToolUse` (stderr с выходом 2), и харнес скармливает
её агенту фидбеком, поэтому она остаётся в транскрипте сессии. По этому
хвосту в замере DK-148 виден сдвиг доли повторных чтений после выката. Хук не
роняет сессию ни на каком входе: плохой JSON, отсутствие `session_id` или
несуществующий файл уходят нулём, и Read проходит как обычно.

Ручной прогон: `hooks/check-reread.py --hook` с событием на stdin (для тестов
каталог состояния перебивается флагом `--state <путь>`).

## Чтение длинного файла целиком

`check-longfile.py` закрывает правило «не тянуть файл целиком, когда нужен
фрагмент»: больше половины вызовов Read идут без `limit`/`offset` и дают ~73%
объёма вывода Read, а чтение целиком длинного файла почти всегда избыточно,
потому что нужное место нашлось бы грепом или куском (замер DK-148). Хук стоит
на PreToolUse на Read и отвечает подсказкой вместо содержимого, когда файл
длиннее порога читают целиком, без `limit`/`offset`/`pages`. Короткий файл и
чтение уже куском проходят нетронутыми.

Подключается PreToolUse-хуком на Read рядом с `check-reread.py`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Read",
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/check-reread.py --hook" },
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/check-longfile.py --hook" }
        ]
      }
    ]
  }
}
```

Порог 300 строк выведен из распределения длин чтений, а не взят из головы.
Замер `devkitctl drain` по корпусу сессий даёт перцентили размера вывода:
у чтений целиком p75 ~303 строки, у чтений куском (с `limit`/`offset`) p90
~212 строк. Порог режет верхний квартиль чтений целиком, и он выше p90
куска: если агенту был нужен фрагмент, куска до 212 строк ему хватило бы, и
чтение файла длиннее 300 строк целиком почти наверняка лишнее. На корпусе
порог задевает ~25% чтений целиком, но они несут ~70% их объёма; короткие
файлы (медиана чтений целиком ~120 строк) проходят без подсказки.

Строки, а не байты: `Read` режет `limit` в строках, и подсказка должна звать
к `limit`. Число строк считается сканированием байт по переводу строки без
декодирования (работает с любым Encoding), с ранним выходом на пороге:
длинный файл ради точного числа строк не читается, и накладные расходы хука
меньше вывода `Read`, который он предотвращает. Бинарный файл (нуль-байт в
теле) рубеж пропускает: `Read` отдаёт его как визуальный или двоичный
результат, и строки там не считать.

Выход 2 (блокировка с подсказкой), а не мягкое предупреждение: у PreToolUse в
claude-code нет канала «пропустить, но предупредить», выход 0 это молчаливый
пропуск, а выход 2 единственный способ оставить подсказку в транскрипте.
Так же работает `check-reread.py`, и два рубежа на одном матчере `Read` живут
рядом, каждый своим выходом 2 со своей подсказкой; харнес скармливает агенту
обе. Состояния у рубежа нет: решение принимает одно сканирование длины файла.

Чтение файла целиком перед правкой (Edit/Write следом) рубежу не видно: на
PreToolUse у хука нет будущего. Контракт поэтому прямой: подсказка летит на
любое чтение целиком длинного файла, а агент читает нужный кусок через
`limit`/`offset` или ищет место грепом. Для правки всего файла он собирает
его двумя-тремя кусками, и это малая плата против разового вывода в десятки
тысяч символов. Хук не роняет сессию ни на каком входе: плохой JSON,
отсутствие `file_path` и несуществующий файл уходят нулём, и Read проходит
как обычно.

Ручной прогон: `hooks/check-longfile.py --hook` с событием на stdin.

### Каркас для нескольких рубежей на одном событии

`HOOK_LAYOUT` в `tools/devkitctl/devkitctl.py` рисует раскладку хуков, которую
кладёт `devkitctl doctor --fix`. На одном событии с одним матчером записей
может быть сколько угодно: три PostToolUse-проверки текстов на
`Edit|Write|NotebookEdit` живут рядом, и тот же шаблон держит PreToolUse на
`Read`, где стоят два рубежа: `check-reread.py` (повторные чтения) и
`check-longfile.py` (длинные чтения). `install_hooks` разложит их отдельными
командами в одну группу с матчером `Read`. Каждая блокирует Read своим
выходом 2 со своей подсказкой; харнес скармливает агенту обе, и подсказка о
повторе не глушит подсказку о чтении целиком. Новая категория рубежа
заводится тройкой: имя скрипта в кортеже (`POST_SCRIPTS`, `PRE_SCRIPTS`,
`PRE_READ_SCRIPTS`), строка в `HOOK_LAYOUT` и запись в `PRE_READ_GAPS`
(сообщение `hook_gaps`, которое доктор говорит про неподключённый рубеж).
Сообщения у рубежей на Read разные: «повторные чтения» и «длинные чтения»
режут разные дыры, и находка обязана назвать именно ту, что не закрыта.

## Корп-репозиторий: цепочка хуков и следы devkit

В корп-клоне `core.hooksPath` не годится: он выключает `.git/hooks` целиком
вместе с чужими хуками проекта, а молча отключённый линтер компании это
поломка чужого процесса. Симлинки не спасают, их перетирает чужой инсталлер.
Поэтому в `.git/hooks` кладётся обёртка-цепочка: файл devkit, который гоняет
проверки devkit, а следом чужой хук проекта, переехавший при подключении в
соседнее имя `<хук>.chained`. Ненулевой код любой стороны валит коммит, ни
одна сторона молча не проглатывается.

Обёртку раскладывает `install_chain` из `corp.py`, зовёт её подключение
`devkitctl corp`. Прогон повторяемый: свой файл функция узнаёт по маркеру
`devkit-corp-chain` в шапке и чужим хуком его не считает, а совпадающее
содержимое не переписывает. Первую строку занимает shebang, без него git хук
не запустит, так что маркер стоит следующей строкой. Перезаписавший обёртку
чужой инсталлер виден по пропавшему маркеру, и чинится это повторным
`devkitctl corp --fix`, который разворачивает цепочку заново.

Рубеж следов devkit (`check-traces.py`) добавляется к обычным проверкам в
цепочке: локальный ID доски и путь боковой директории не уезжают ни в дифф, ни
в сообщение коммита. Внутренняя кухня разработчика чужому репозиторию не
нужна, а ссылка на локальный ID из истории компании ещё и никуда не ведёт.
Префикс ID берётся из шапки доски боковой директории, путь считается её
именем и полным путём, а имя добавленного файла смотрится наравне с его
строками. Перечень расширяется ключом `traces` в привязке
(`.devkit/tracker.local`, слова через запятую); широкие эвристики туда не
просятся: рубеж, который врёт, отключают.

Одно правило рубеж снимает сам: когда префикс доски совпал с ключом проекта в
трекере (`key` привязки), локальный ID доски и ключ тикета это одна и та же
строка, отличить их нечем, и правило про ID валило бы каждый коммит по
конвенции компании (DK-124). Путь боковой директории и слова контура на такой
паре стерегутся по-прежнему, а про снятое правило говорит `devkitctl doctor`:
снаружи ослабленный рубеж выглядит ровно как работающий. Держать префикс доски
отличным от ключа проекта дешевле, чем терять правило.

Включается всё это признаком корп-контура из `corp.py`: ключом `devkit.local`
в конфиге клона, тем же, по которому корень devkit ищут утилиты. Без редиректа
проверка молчит, и домашние проекты цепочки не замечают, даже если обёртка у
них разложена. Осознанный обход прежний, `git commit --no-verify`.

Рубеж чувствительного для самой доски переезжает вместе с доской: боковая
директория это свой git-репозиторий, и в нём стоят обычные хуки devkit через
`core.hooksPath`, корп-специфичного там нет.

## Бит исполнения test.sh

`check-exec-bit.py` следит, чтобы каждый `test.sh` в репозитории (в корне и
в любой вложенной директории) нёс бит x в git-индексе. Обычный `chmod +x` на
диске регресс не чинит: бит живёт в режиме объекта git, и без `git add` или
`git update-index --chmod=+x` следующий чекаут его снова снимет. Без бита
команда из докладов вида `kit/skills/test.sh` падает `permission denied`
вместо честного вывода теста (DK-072), а соседний скрипт с битом на вид
неотличим, пока его не запустишь.

```sh
python3 hooks/check-exec-bit.py
```

Выход 0 чисто, 1 построчные находки «путь: режим NNN вместо 100755». CI
гоняет её на каждый push тем же прогоном.

## Снимок квоты на старте сессии

`quota-refresh.sh` освежает снимок остатка лимитов активного харнеса
(`~/.devkit/quota/<харнес>.local`), по которому корректор `agentctl pick`
двигает вердикт. Снимок нужен свежий (порог 45 минут, разбор в
`tools/agentctl/README.md`), а руками его не переснимает никто: корректор из-за этого
простоял выключенным с самого появления. Старт сессии Claude Code это
единственное регулярное событие, к которому такую работу можно привязать,
поэтому хук ставится на `SessionStart`:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "sh ~/projects/devkit/hooks/quota-refresh.sh" }
        ]
      }
    ]
  }
}
```

Сессию хук не задерживает: он проверяет, чем снимать (`agentctl`, `tmux`,
`claude` в PATH), берёт замок и уходит, а `agentctl quota refresh --if-stale`
доснимает панель отцепленным процессом. Свежий снимок при этом не трогается,
порог живёт в agentctl, второй его копии в хуке нет.

Замок `~/.devkit/quota-refresh.lock` держит две вещи сразу. Главная: refresh
поднимает `claude` в tmux, старт того клиента дёргает этот же хук, и без замка
получилась бы воронка из сессий. Заодно параллельные сессии не снимают панель
наперегонки. Брошенный замок старше десяти минут снимается сам, весь цикл
refresh укладывается в минуту.

Нечем снимать (нет tmux, нет claude, нет самого agentctl), значит хук молча
уходит и следов не оставляет: он стоит у всех сессий на машине и ругаться в
каждой не должен. Так же он ведёт себя на харнесе без объявленной квоты (пустая
секция `[quota]` профиля): `agentctl quota refresh`
там честно отказывает, снимать нечего по построению, и журнал из одних отказов
перестал бы отвечать на вопрос, ради которого заведён. Молчание тут узкое,
незалогиненный клиент и неузнанная панель в журнал по-прежнему попадают, а про
сам харнес без квоты говорят `agentctl harness` и хвост вердикта `pick`. Про нехватку скажет `devkitctl doctor`, он же ловит
неподключённый хук и протухший снимок. Что фоновая работа реально была, видно
по журналу последнего запуска `~/.devkit/quota-refresh.log` (время, код
возврата и причина отказа, если панель не снялась) и по возрасту снимка в
выводе `agentctl quota`.

## Догон бокового дерева на старте сессии

`board-catchup.sh` закрывает отставание бокового дерева доски (DK-269): такое
дерево живёт в detached HEAD, ветку main в него не чекаутить, она занята
основным чекаутом, и доска в нём молча читается устаревшей как свежая. Чинить
дерево надо до того, как сессия что-то из него прочла, поэтому хук стоит на
`SessionStart` и раскладывается доктором вместе с остальными:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "sh ~/projects/devkit/hooks/board-catchup.sh" }
        ]
      }
    ]
  }
}
```

Сам хук тонкий, как `quota-refresh.sh`: гард и действие живут в
`taskctl catchup --hook` (ветки, чистота дерева и отставание разобраны в
`tools/taskctl/README.md`). Гард берёт только линкованные деревья в detached
HEAD, чистые и позади `origin/main`: основной чекаут на main и деревья задач на
ветках хук молча пропускает, им догон не нужен. Сеть хук не ходит, свежесть
указателя оставлена обычному git-циклу машины.

Дальше два исхода. Дерево позади: хук чекаутит его на свежий sha и печатает в
stdout, сколько коммитов приехало, сессия видит это в контексте старта. Догнать
нельзя (дерево грязное, идёт rebase): хук громко отказывается с причиной в том
же stdout, чтобы отставание не выглядело починенным. Прочее молчит, и про
отсутствующий taskctl тоже: хук стоит у всех сессий машины, а про нехватку
скажет `devkitctl doctor`, он же ловит неподключённый хук.

Посреди сессии отставание видно без хука: `taskctl list` и `taskctl show`
печатают предупреждение с числом коммитов и командой подтяга, закрыть его
можно руками той же `taskctl catchup`.

## Реестр чатов задачи

`session-task.py` записывает, какую задачу ведёт родившаяся сессия. До него эта
связь была только угаданной (хвост каталога бокового дерева, ID в первой
реплике, имя ветки), и угадывание ошибалось в обе стороны: разговор про задачу из
главного чекаута загорался её живой работой, а сессия, не попавшая ни под один
способ, оставалась карточкой без имени и без входа. Записать связь может только
тот, у кого есть ID сессии в момент её рождения, поэтому хук стоит на
`SessionStart`:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/session-task.py --hook claude-code" }
        ]
      }
    ]
  }
}
```

Раскладывает эту строку `devkitctl doctor --fix`, руками её писать не надо;
неподключённый хук у доктора значится находкой.

Строка ложится в машинный журнал `~/.devkit/sessions.log` рядом с журналом
уведомителя, поля именованные, и читаются они по ключевым словам:

```
2026-08-18T12:03:11 сессия 0f2c...e91 задача DK-430 проект devkit дерево /Users/r/projects/devkit-dk-430 транскрипт /Users/r/.claude/projects/-Users-r-projects-devkit/0f2c...e91.jsonl источник заказ повод startup tmux chat-DK-430-1
```

Задачу хук берёт из двух мест. Переменная `DEVKIT_TASK` это заказ того, кто
поднял сессию: её ставит дашборд в начало команды сессии, и только так узнаётся
конвейерная сессия, стартующая в главном чекауте. Хвост имени рабочего дерева
(`devkit-dk-431`) это боковое дерево, заведённое ровно под одну задачу. Ни доски,
ни сети хуку не нужно, форма ID проверяется регуляркой. Источник это слово, по
которому дашборд подписывает привязку на экране: `заказ` и `дерево` пишет хук,
`рука` и `снята` пишет ручка привязки дашборда. Имя tmux-сессии приезжает
переменной `DEVKIT_TMUX` оттуда же, откуда задача: вывести `chat-<ID>-<n>` из
записи нечем, а на живости этого имени стоит мера кончившегося разговора.

Сессия без задачи тоже пишет строку, с пустыми полями задачи и источника: по ней
разговор доски виден сразу, без угадывания по транскрипту заново. Сессия вне
git-дерева пишет строку с пустым деревом и хук не роняет. Перепривязка и отвязка
это обычные записи, файл никто не правит: читатель сворачивает журнал в
отображение «сессия -> задача», где выигрывает последняя строка. Растёт журнал
той же обрезкой, что журнал уведомителя (`hookio.append_capped`).

Что запись реально была, видно тремя способами: сам журнал читается глазами,
чип на карточке сессии в дашборде подписывает источник словами («по заказу
дашборда», «по дереву задачи», «привязана рукой»), а `devkitctl doctor` ловит
неподключённый хук. Разбор устройства целиком в `docs/lld/DK-430-task-chat.md`,
решение 1.

## Сторож фоновых субагентов

`agent-watch.py` говорит сессии, что её фоновый субагент отработал. Отчёт
фонового субагента едет к сессии уведомлением харнеса, и уведомление это
теряется: на ревью DK-181 два субагента из трёх закончили работу молча, сессия
считала их живыми, задача стояла часами, а итог пришлось собирать опросом
агентов руками. Сторож ведёт свой счёт запущенным работам и на конце хода
сдаёт сессии то, чего она не получила.

Три события, три дела. Ход инструмента делегирования с фоновым ответом заводит
запись в реестре, `SubagentStop` её закрывает вместе с первой строкой отчёта, а
`Stop` сдаёт сессии всё, о чём она не узнала:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Agent",
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/agent-watch.py --hook claude-code" }
        ]
      }
    ],
    "SubagentStop": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/agent-watch.py --hook claude-code" }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/agent-watch.py --hook claude-code" }
        ]
      }
    ]
  }
}
```

`devkitctl doctor --fix` раскладывает эти строки, руками их писать не надо;
неподключённый сторож у доктора значится находкой.

Сдача идёт только на конце хода, и это не экономия, а суть. Пока сессия
работает, уведомление харнеса ещё может доехать само, и дублировать его незачем;
ход, законченный при незабранном отчёте, это и есть та потеря, ради которой
сторож стоит. Сдаётся весть решением `block` на `Stop`: харнес отдаёт текст
модели и продолжает ход вместо сна, а сессия видит его репликой «Stop hook
feedback».

```
Сторож фоновых субагентов devkit: работа кончилась, а сессия про это не узнала.
- фоновый субагент «Ревью ветки dk-181» (review-high, ID a555b8615fe4588f3) отработал, а весть о нём до сессии не дошла, отчёт лежит в /private/tmp/claude-501/.../tasks/a555b8615fe4588f3.output, первая строка отчёта: «Замечаний три, все в разделе Ревью файла задачи»
Считать такого субагента работающим нельзя: забери отчёт из его файла и продолжай работу. Второй раз сторож про эти работы не скажет.
```

Сторож отличает забранную работу от потерянной по транскрипту сессии: весть о
конце фоновой работы едет через очередь харнеса, и запись очереди с `<task-id>`
лежит в транскрипте раньше самой реплики. Нет там ни того, ни другого, значит
сессия про работу не знает. Между концом субагента и записью очереди проходит
доля секунды, поэтому сторож пережидает свежий конец: по умолчанию пять
секунд, меняется переменной `DEVKIT_AGENT_WATCH_GRACE`. Весть, доехавшая на
секунду позже сдачи, стоила бы сессии лишнего хода, а не потери.

Перечень фоновых работ, который харнес кладёт в событие конца хода, ловит
молчаливую пропажу. Работа, которую реестр числит запущенной, а харнес в
перечне уже не называет (или называет с отказом), кончилась молча: так выглядит
субагент, убитый перезапуском процесса. Сторож говорит про такую отдельно,
отчёта у неё нет, и в реестре она остаётся пропавшей.

Реестр правится под замком: диспетчер поднимает исполнителей пачкой, ходы
инструмента делегирования идут разом, и два хука одной сессии пишут в один файл.
Ожидание вести при этом остаётся вне замка, иначе конец хода запирал бы реестр
на все пять секунд. Занятый чужим ходом замок значит пропущенную правку, а не
упавший ход: сторож не вправе ронять работу сессии из-за своего файла.

Синхронный субагент сторожу не интересен: он отчитывается ходом инструмента, и
сессии негде его терять. В реестр попадает только запущенное фоном, а сторож
пропускает конец незнакомой работы молча. Сторож тоже пропускает ход,
продолженный стоп-хуком (`stop_hook_active`): сказанное один раз повторять не
надо, а второй заход закрутил бы сессию в цикле.

Реестр лежит по файлу на сессию в `~/.devkit/agents/<сессия>.json` и живёт
сутки, журнал сдач в `~/.devkit/agents.log` рядом с журналом уведомителя:

```
2026-08-25T14:41:02 сессия d17dfb46 агент a555b8615fe4588f3 событие запуск текст «Ревью ветки dk-181»
2026-08-25T14:52:19 сессия d17dfb46 агент a555b8615fe4588f3 событие конец текст «Замечаний три, все в разделе Ревью файла задачи»
2026-08-25T14:52:24 сессия d17dfb46 агент a555b8615fe4588f3 событие сдача текст «Замечаний три, все в разделе Ревью файла задачи»
```

Жалоба «сессия проспала субагента» разбирается по этому журналу: в нём видно и
запуск, и конец, и сдачу с её причиной, а событие `весть` значит, что
уведомление харнеса дошло само и сдавать было нечего. Выключается сторож
переменной `DEVKIT_AGENT_WATCH_OFF=1`, свой каталог реестра на стенде задаётся
через `DEVKIT_AGENT_WATCH_DIR`.

## Уведомления о сессии

`notify.py` говорит наружу, что сессия ждёт действия. Параллельных сессий на
машине несколько (у каждой задачи свой worktree после `shipctl start`, рядом
фоновые субагенты), и та, что упёрлась в запрос разрешения, стоит, пока на её
окно не посмотрят. Канал уведомлений самого Claude Code
(`preferredNotifChannel`) прибит к конкретным терминалам и в VS Code с
Terminal.app не годится, поэтому уведомление шлётся своими руками.

Уведомитель это отдельная команда, хук поверх неё тонкий: позвать его может и
скрипт выката, и другой харнес.

```sh
hooks/notify.py "заголовок" "текст"          # аргументами, повод громкий
hooks/notify.py --quiet "заголовок" "текст"  # то же фоновым поводом
hooks/notify.py --reason goal_stop "заголовок" "текст"  # повод словом в журнал
hooks/notify.py --task DK-323 --project devkit "заголовок" "текст"  # задача и проект
hooks/notify.py --hook claude-code           # событие харнеса на stdin
hooks/notify.py --self-test                  # пробное уведомление
```

Флаг `--reason` называет повод словом. У события харнеса повод свой
(`permission_prompt`, `turn_done`, `subagent_stop`), а аргументный вызов без
флага пишется в журнал прочерком, и разобрать по строке, о чём был баннер,
нельзя. Слово нужно ленте дашборда: по нему она отбирает стоп цикла
(`goal_stop`, `run_stop`), зов человека (`wait_human`) и события задач
(`task_check`, `task_blocked`, `task_fail`) в свои фильтры. Ставят его
`goal-run.py` на стопе цикла, `taskctl move` и `taskctl fail`, а стоп из
дашборда шлёт `run_stop`.

Событие несёт задачу и проект своими полями журнала, а не текстом баннера,
который ленте дашборда пришлось бы разбирать (DK-323). В хук-режиме они собираются
из рабочего дерева: дерево задачи названо «проект-ID» (`shipctl start`), и
оттуда читаются оба поля, а у обычного чекаута ID лежит на ветке. Аргументный
вызов называет их ключами `--task` и `--project`, и без ключей поля собираются
по рабочей директории тем же правилом. У события может честно не быть задачи
(самопроверка канала, авария контура, ветка `main`), и тогда в поле стоит
прочерк: лента показывает такое событие с пометкой, а не ведёт с него на
выдуманную строку доски. Ключ `--task` ставят `taskctl move`, `taskctl fail`,
`goal-run.py`, `shipctl` на упавшем выкате и сторожок простоя `devkitctl
watch`, а стоп из дашборда называет ещё и `--project`: имя проекта там
берётся из запроса, и по нему лента поднимает виток в том проекте, где стоп
случился.

### Громкий повод и фоновый

Поводы двух сортов, и от сорта зависит, как баннер выглядит. Громкий зовёт
подключиться, приходит со звуком и своей строкой. Фоновый рассказывает о ходе
работы, приходит молча и схлопывается по сессии: новый баннер сессии вытесняет
её же предыдущий, а не ложится под него. Без такого деления канал забивается
тем, что срочности не несёт (за первые сутки работы уведомителя в журнале
набралось 84 отчёта об отработавших субагентах на одно `idle_prompt`), и
момент, когда сессия правда ждёт человека, тонет среди них.

Громкие поводы:

- сессия упёрлась в вопрос: `permission_prompt`, `agent_needs_input`,
  `elicitation_dialog` события `Notification`;
- сессия закончила ход: событие `Stop`, плюс `idle_prompt`, который харнес
  присылает примерно через минуту простоя. Конец хода уведомляет не всякий,
  решает фокус окна (см. «Фокус окна на конце хода»);
- позвали снаружи: `notify.py "заголовок" "текст"` считается громким по
  умолчанию, понижает его флаг `--quiet`. Так зовут `taskctl move` (задача
  доехала до Check или встала на блокере) и `shipctl merge`/`ship`/`revert`
  (выкат упал, самый громкий повод из трёх, прод в этот момент может быть
  сломан); разбор в README обеих утилит;
- ход упал API-ошибкой: событие `StopFailure`. Сетевые обрывы харнес ретраит
  сам, и сюда доезжает только исчерпание ретраев или неретраибельная ошибка
  (см. «Возобновление после обрыва связи»). Баннер подписан типом ошибки, а
  фокус окна не спрашивается: упавший ход стоит намертво, как и запрос
  разрешения.

Фоновый пока один: субагент отработал, событие `SubagentStop`. Повод
`agent_completed` события `Notification` сюда не относится, он про фоновые
сессии, а не про субагентов, поднятых из сессии (проверено живьём, разбор в
`docs/tasks/DK-034.md`).

Отбор поводов `Notification` держат матчеры в `settings.json` (тип события
работает матчером, отдельного кода для отбора не нужно). В
`~/.claude/settings.json`:

```json
{
  "hooks": {
    "Notification": [
      {
        "matcher": "permission_prompt|agent_needs_input|elicitation_dialog|idle_prompt",
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/notify.py --hook claude-code" }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/notify.py --hook claude-code" }
        ]
      }
    ],
    "SubagentStop": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/notify.py --hook claude-code" }
        ]
      }
    ],
    "UserPromptSubmit": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/notify.py --hook claude-code" }
        ]
      }
    ]
  }
}
```

Хук на `UserPromptSubmit` ничего не шлёт, он снимает отметку ожидания: человек
вернулся к сессии, и конец следующего хода это новый повод позвать, а не повтор
прошлого (см. про окно троттлинга ниже).

Как уровень выглядит на баннере, решает бэкенд. `terminal-notifier` берёт
`-sound default` у громкого и `-group devkit-<сессия>` у фонового,
`osascript` только звук (группировки у `display notification` нет вовсе),
`notify-send` срочность `critical` либо `low` вместе с подсказкой
`x-canonical-private-synchronous`. Своя команда из `DEVKIT_NOTIFY_BACKEND`
уровня не понимает и получает заголовок с телом, как раньше.

Заголовок отвечает на вопрос «какая сессия»: имя рабочего дерева плюс повод
(`devkit-dk-034: нужно разрешение`), а работал субагент в дереве задачи, значит
в скобках стоит и она (`it-road-course (irc-75): субагент отработал`, см. «Клик
по баннеру»). Имя дерева задачу не назвало (сессия сидит в основном чекауте,
а не в linked worktree с ID в имени), а дерево стоит на ветке задачи, значит
в скобках эта ветка (`devkit (dk-121): ход закончен`); ветку читаем файлом
`.git/HEAD` самого дерева, `git` не зовём, а `main` и `master` за метку задачи
не считаем. В теле одна строка сообщения харнеса, а на конце хода и у субагента
это первая строка последней реплики (`last_assistant_message`), у субагента
ещё и с его ролью. Чем слать, выбирается по платформе
и PATH: macOS `terminal-notifier`, а без неё `osascript`, Linux `notify-send`,
для Windows и WSL пока заготовка. `DEVKIT_NOTIFY_BACKEND` перебивает выбор
именем бэкенда либо своей командой (её зовут как `команда заголовок тело`),
`DEVKIT_NOTIFY_OFF=1` гасит уведомитель целиком, это для headless-прогонов, где
уведомлять некого, а `DEVKIT_NOTIFY_FOCUS=off` снимает проверку фокуса, и конец
хода зовёт всегда. В сессии подпроцесса делегирования (`DEVKIT_RUN_DEPTH` в
окружении, её поднимает `agentctl run`) хуки молчат и пишут в журнал строку
пропуска: такой сессии никто не ждёт у окна, диспетчер стоит на `run` синхронно
и заберёт результат сам, а звонок на каждый её конец хода это шум, от которого
потом глохнет настоящий. Окна редактора на второй подписке правило не касается,
там переменной нет. Системного бэкенда не нашлось, значит хук уходит нулём, но
просит харнес выдать уведомление через сам терминал (OSC 9), и это же остаётся
запасным путём по ssh.

### Фокус окна на конце хода

Конец хода зовёт не всякий раз: смотришь в окно этой самой сессии, значит всё
и так видно, и баннер только мешает. Куда смотрит человек, отвечает
`System Events`: заголовок переднего окна переднего приложения. У VS Code в
заголовке хвостом стоит имя рабочего дерева (`Правка notify.py -
devkit-dk-064`), а дерево сессии уведомитель и так знает, он собирает по нему
цель перехода по клику. Заголовок кончается именем этого дерева, значит молчим,
всё остальное значит зовём, хоть через три секунды после ввода. Хвост берётся
целым словом: `devkit` и `devkit-dk-064` это разные деревья, а значит и разные
окна.

Раньше тут стоял порог длительности хода в минуту (DK-062): считалось, что
короткий ответ пользователь дожидается, глядя в то же окно. Догадка неверная, и
короткий вопрос, заданный перед тем как отойти, терялся ровно из-за неё.
Длительность хода это про то, сколько работала машина, а звать или молчать
зависит от того, где в это время человек, и одно из другого не выводится.

Проверка стоит только на конце хода. Запрос разрешения и вопрос агента зовут
всегда: они редкие, сессия на них стоит намертво, а повторного события от
харнеса может и не быть. Фоновых поводов проверка не касается вовсе, иначе
каждый отработавший субагент стоил бы лишнего опроса (около 180 мс).

Спросить не удалось (не macOS, нет разрешения на управление компьютером,
`osascript` ответил ошибкой или пусто) значит зовём: тишина тут хуже лишнего
баннера, она неотличима от штатной работы, а разрешение выдают не на всякой
машине. Отказ уходит в журнал строкой «фокус не определился, зовём», так что
жалоба «звонит всегда» разбирается по факту. Совсем гасит проверку
`DEVKIT_NOTIFY_FOCUS=off`.

Несколько чатов в одном окне редактора друг от друга не отличить, и это
осознанная грубость: сессии в одном дереве считаются одной, зато промах уходит
в сторону лишнего баннера, а не тишины.

### Клик по баннеру

Клик переключает в окно позвавшей сессии, но только когда шлёт
`terminal-notifier` (`brew install terminal-notifier`). Своего обработчика
клика у `osascript` нет: он постит от имени Script Editor, и клик открывает
Finder с папкой скриптов. Сменить одну атрибуцию мало, проверено: баннер от
`tell application id "com.microsoft.VSCode"` всё равно приходит от Script
Editor. Без `terminal-notifier` уведомления работают по-прежнему, просто не
кликаются, и доктор предлагает её поставить.

Цель перехода ведёт в дерево, на котором стоит окно сессии:
`vscode://file/<путь>?windowId=_blank` поднимает это окно, а при пяти
параллельных сессиях попадаем в нужную. Уже открытое окно поднимается, второго
VS Code не заводит. Параметр `windowId=_blank` тут обязателен: без него редактор
открывает дерево в активном окне, и когда своего окна у дерева нет, кликом
сносится то окно, в котором сейчас работают, вместе со всеми его агентами.

Дерево сессии берётся не из `cwd` события, а из первых записей её транскрипта
(`transcript_path`, до 20 записей: сверху там служебное, а транскрипт вырастает
на десятки мегабайт). Причина в субагентах: субагент уходит в worktree задачи,
и `cwd` события показывает уже его дерево, у которого своего окна нет. Клик по
такой цели открывал бы лишнее окно вместо того, где идёт работа. Транскрипт не
читается (нет пути, битые записи, `cwd` в первых записях не попался), значит
цель собирается из `cwd`, как раньше. Заголовок при этом показывает и окно, и
задачу: `it-road-course (irc-75): субагент отработал`.

Работа идёт не в VS Code, значит переключается сам терминал по `TERM_PROGRAM`
(Terminal.app, iTerm), окно там по рабочему дереву не найти.
`DEVKIT_NOTIFY_OPEN` перебивает цель своим шаблоном с подстановкой `{cwd}`,
пустое значение гасит переход совсем.

Против шума, кроме отбора поводов и уровня, работает окно: один и тот же повод
одной сессии не повторяется чаще, чем раз в полминуты. Конец хода и
`idle_prompt` при этом считаются одним поводом «сессия ждёт тебя», ключ у них
общий, а окно три минуты: `idle_prompt` приходит через минуту после конца хода
и своим окном повторил бы тот же баннер. Отметку ожидания снимает ввод
пользователя: он к сессии вернулся, и конец следующего хода это новый повод
позвать, а не повтор прошлого, так что второй ход подряд звучит даже в
пределах общего окна. Состояние по ключу «сессия плюс повод» лежит в
`~/.devkit/notify/`, брошенное старше суток убирается само. В аргументном режиме окна нет: позвал скрипт, значит шлём.

Помимо `DEVKIT_NOTIFY_OFF`, оба пути вызова глушит фильтр песочницы по корню
во временной директории (`TMPDIR`, `/tmp`, `/var/folders`). Такой корень это
песочница вроде синтетической доски из обкатки сценария или вложенной
headless-сессии из scratchpad: живой баннер про неё ложный, клик ведёт в
репозиторий, которого через минуту нет. Рубеж стоит в самом уведомителе, а не
в зовущих утилитах, чтобы не зависеть от заглушки, про которую надо помнить в
каждом прогоне. Пропуск не молчит: в журнале остаётся строка «пропуск:
песочница, корень ... лежит под ...», а у аргументного вызова и в stdout
строка «уведомление пропущено: ...», которую зовущая утилита доносит до своего
вывода (приписка у `taskctl move`). Хук-путь в stdout ничего не печатает: его
забирает харнес, и пропуск там виден только по журналу.

Что уведомления реально идут, видно по журналу `~/.devkit/notify.log` (время,
сессия, повод, уровень, бэкенд, цель перехода, задача, проект и код возврата,
дальше хвостом текст баннера заголовком и телом в ёлочках; там же пропуски по
окну и по фокусу, отказы и события, которых хук не понял), так что
жалоба «не приходит ничего» разбирается по факту, «клик никуда не ведёт» по
тому, уехала ли цель, а «важное не отличается от фонового» по уровню:

```
2026-08-02T14:03:11 сессия f07df579 повод permission_prompt уровень громкий бэкенд terminal-notifier цель vscode://file/p/devkit?windowId=_blank задача - проект devkit код возврата: 0
2026-08-02T14:07:52 сессия f07df579 повод subagent_stop уровень фоновый бэкенд terminal-notifier цель vscode://file/p/devkit?windowId=_blank задача DK-323 проект devkit код возврата: 0
2026-08-02T14:08:30 сессия f07df579 повод turn_done уровень громкий бэкенд - цель - задача - проект devkit пропуск: окно сессии в фокусе
2026-08-02T14:12:04 сессия f07df579 повод idle_prompt уровень громкий бэкенд - цель - задача - проект devkit пропуск: повтор в окне 180с
2026-08-10T00:41:02 сессия - повод run_stop уровень громкий бэкенд terminal-notifier цель - задача DK-112 проект devkit код возврата: 0 текст «devkit: DK-112 стоп из дашборда» «цикл цели снят из дашборда»
```

Хвост с текстом появился ради ленты дашборда: строка без слов говорит, что
уведомление было, но не о чём оно. Ёлочки внутри текста заменяются угловыми
скобками, иначе разбор хвоста развалился бы на первой цитате.

Кривой вход хук не роняет: форма события целиком на стороне харнеса, поэтому
что не json, что json не объектом, что поле не той формы заканчиваются кодом 0
и строкой в журнале. Отдельно есть `notify.py --self-test`: он шлёт пробное
уведомление и печатает, чем именно послал и куда поведёт клик. Без него macOS
остаётся дырой в наблюдаемости: баннер приходит от имени отправителя (Script
Editor у `osascript`, terminal-notifier у неё самой), и если разрешение этому
имени однажды не дали, отправка отвечает нулём, а на экране не появляется
ничего.

Подключён ли хук на все пять событий, есть ли на машине чем слать и ведёт ли
клик в окно сессии, проверяет `devkitctl doctor`.

## Возобновление после обрыва связи

Обрыв сети (уснувший ноутбук, переезд между Wi-Fi, пропавший VPN) прежде
убивал ход живой сессии: в чате «API Error: Unable to connect to API
(ENOTFOUND)», и работа стоит, пока человек не заметит и не напишет
«продолжай».

Харнес и без раскладки devkit часть сетевых сбоев ретраит сам: стенд DK-172
(разбор, команды и сырой вывод в `docs/tasks/DK-172.md`) показал это на двух
видах сбоя. Обрыв соединения посреди стрима харнес выжидает таймаутом тишины
около трёх минут и повторяет запрос без стриминга; ответ 529 (перегрузка)
повторяет с беккофом несколько раз ещё до начала стрима. Потолок попыток у
каждого вида сбоя свой и нигде не задокументирован, поэтому общее число тут не
называется: сколько раз харнес попробует сам, решает он, а не эта раскладка.

Кандидат на управление этим ретраем, найденный `strings` бинаря харнеса версии
2.1.241 рядом с `CLAUDE_CODE_MAX_RETRIES`, `CLAUDE_ENABLE_STREAM_WATCHDOG` и
`CLAUDE_ENABLE_BYTE_WATCHDOG`, это env-ключ:

```json
{"env": {"CLAUDE_CODE_RETRY_WATCHDOG": "1"}}
```

Ключ нигде в публичной доке Claude Code не описан, и это не формальность:
разделяющий замер стенда DK-172 (один и тот же обрыв посреди стрима трижды
подряд, ключ=1, ключ=0, ключа вовсе нет) разницы в поведении не нашёл: все
три прогона отработали одинаково, вплоть до числа попыток и итоговой ошибки.
Опора на этот ключ как на причину возобновления не подтвердилась. Раскладка
всё равно кладёт его: вреда от лишнего env-ключа нет, а на другой версии или
платформе харнеса он вполне может что-то значить, недокументированный флаг
может и вовсе пропасть или поменять смысл со следующей версией харнеса.
Этот ключ, по замеру, не управляет ни числом попыток, ни тем, доедет ли ход
до возобновления.

Руками этот ключ не кладётся: его вписывает `devkitctl doctor --fix`, а
отсутствие доктор называет находкой. Разложенность видно тут же:

```sh
$ python3 -c 'import json; print(json.load(open("'$HOME'/.claude/settings.json"))["env"])'
{'CLAUDE_CODE_RETRY_WATCHDOG': '1'}
```

Значение, вписанное человеком (хоть `"0"`), доктор не трогает: это его
решение, а не пробел раскладки. Ключ вовсе не касается штатного конца хода:
даже если он на что-то влияет, это влияние на ретрай запроса внутри хода, а не
на пробуждение сессии после её обычного стопа или ожидания ответа.

Исчерпание не молчит, и это настоящий, проверенный вклад DK-172. Когда харнес
отказывается от дальнейших попыток или ошибка неретраибельная (битый запрос,
кончившийся кредит), ход падает событием `StopFailure`, на котором тем же
хуком стоит `notify.py`: баннер громкий, подписан типом ошибки («ход упал
(server_error)»), телом едет текст ошибки, а в журнале `~/.devkit/notify.log`
остаётся строка с поводом `turn_failed`. На штатном конце хода `StopFailure`
не срабатывает (снято стендом там же), поэтому баннер положен только ходу,
убитому API-ошибкой: раньше молчаливый стоп сессии становится громким, и
пропустить его сложнее, чем заметить.

## Разговор с идущим витком

`chat-in.py` доносит реплику человека до идущей сессии, и носителей у него два:
«Входящие» файла цели для витка цели (этот раздел) и входы разговора
`.devkit/chat` для всех остальных (раздел «Вход разговора любой сессии» ниже).
Механика замка и признака ожидания общая, третьей копии нет. Реплику с
экрана чата дашборд кладёт строкой в раздел «Входящие» файла цели, и до этого
хука её читал только следующий виток, то есть человек, написавший «стой, не
туда», ждал десятки минут. Подхват реплики стоит на `PostToolUse` с пустым
матчером и на каждом завершённом ходе инструмента вносит лежащие строки в
контекст витка каналом добавки. Решение целиком в `docs/lld/DK-136-live-chat.md`, раздел
«Устройство почты»; матчер пустой потому, что реплику надо доставлять на любом
ходе, а не на записи файла, и у добавки нет рамки провала (см. выше про два
канала ответа).

Адрес ищется в три шага, и промах на любом это молчание, а не доставка кому
попало.

- Реестр целей `~/.devkit/goals/*.watch` называет цель, её корень и файл.
  Гейт бюджета пишет реестр, через который проходят оба входа цикла, поэтому
  цель, которую ведут в чате без оболочки, там тоже есть. Корень берётся из поля
  `file`, приведённого к абсолютному пути, а не из `root`, записанного как
  пришёл.
- Дерево хода это `cwd` события, а не дерево сессии из транскрипта: ход
  исполнителя в дереве задачи под адрес цели попадать не должен, а транскрипт
  назвал бы как раз корень цели. Сверка текстовая и по границе пути, иначе
  соседнее дерево `проект-dk-101` сошло бы за корень `проект`.
- Сессия сверяется с именем витка из файла `session` в каталоге замка цели,
  пока замок держит живая оболочка (живость меряется тем же `kill -0`, каким
  меряет её сама оболочка). Каждый виток выдаёт себе имя ключом `--session-id`,
  и между витками в файле лежит имя того, кто уже кончился: реплика тогда никуда
  не уезжает и её прочитает шаг 1 следующего витка. Замка нет или `pid` мёртв,
  значит виток идёт в живом чате, имени ему никто не выдавал, и адрес остаётся
  деревом.

У подхвата нет своего правила про песочницу харнеса, и это отказ сознательный:
песочный `cwd` под корень цели не ложится никогда, значит сверка с корнями режет
его сама, а лишняя проверка поверх меняла бы ровно один случай, стенд с корнем
под временным каталогом, который тесты как раз и строят. Ход субагента не
получает реплик вовсе: в событии есть его роль, а реплика адресована витку, а не
тому, кого он позвал.

Живость цели решает, доставлять ли, и признаки идут от точного к грубому.
Первый не требует читать ничего: хук сработал, значит в дереве прямо сейчас идёт
живая сессия. Второй это замок с живым `pid`, и под ним не смотрится никаких
меток времени. Третий читается только в режиме чата, это метка движения самой цели:
свежая из двух, `seen` в записи реестра (её пишет гейт в начале каждого витка и
она закрывает холодный старт) и последняя чужая строка журнала цикла (она
двигается всю дорогу и закрывает виток длиннее порога). Отсутствующий журнал это
отсутствующая метка, а не нулевое время. Порог у метки три часа и взят заведомо
крупным: он ограничивает окно брошенной цели, а не судит, идёт ли виток прямо
сейчас. Отметку `stopped` подхват не читает ни в одном режиме: сторожок меряет
ею движение дерева, а не цели, и у живого витка, висящего на ожидании
исполнителей, она стоит наравне с брошенным.

Отметки доставки лежат в `.devkit/goal-<ID>.mail` рядом с журналом цикла, а не в
файле цели: `docs/tasks/` пушится коммитом на каждую правку, и хук, дописывающий
файл цели на ходе инструмента, наплодил бы коммитов посреди витка. Запись это
две строки, «время сессия» и сама доставленная строка «Входящих» целиком:

```
2026-08-15T14:03:07 5a2d4b71-9c30-42ef-8f6d-cc0011223366
2026-08-15 14:03, из дашборда: посмотри ещё на DK-1
```

Ключ отметки это строка целиком, вместе с датой и подписью дашборда, а не текст
сообщения: тот же текст, посланный через час заново, иначе нашёл бы старую
отметку и не доехал бы вовсе. Горизонт у отметки тот же, что у её строки: оба
читателя входа читают «Входящие» раньше отметок, отметку без лежащей строки не
считают и в новый файл не переносят, поэтому файл не растёт и уборка ему не
нужна. Ставится отметка до доставки, а не после, и размен тут в пользу потери:
реплика, доставленная в тут же упавшую сессию, полежит во «Входящих» до
следующего витка, а реплика, доставляемая на каждом ходе по кругу, превратила бы
виток в мельницу.

Файл отметок и признак ожидания `.devkit/goal-<ID>.ask` общие с ключом `--ask`
оболочки: он задаёт человеку прямой вопрос и читает те же «Входящие». Отсюда два
правила. Отмечает строку тот, кто отдал её витку, иначе съеденная вопросом
реплика приезжает витку вторым экземпляром. Пока признак ожидания не протух,
подхват во вход цели не лезет вовсе. Пишется отметка под `flock` соседнего файла
`.devkit/goal-<ID>.mail.lock`, и под ним идёт всё разом, чтение «Входящих»,
чтение отметок и запись нового файла временным с `os.replace` поверх: прогонов
подхвата в одну минуту бывает несколько, и два разошедшихся на доли секунды
доставили бы одну строку дважды. Своё имя замку нужно ради сверки inode: файл
отметок пересоздаётся на каждой записи, и замок на нём самом разъезжался бы с
путём. Не взявший замок подхват уходит тихим нолём, лежащую строку доставит
сосед.

Доставку видно снаружи, и без единой новой ручки: строка едет в журнал цикла тем
же ключом `goal-run.py <ID> --say`, каким пишет свой ход сам виток, то есть
человек видит её в той же панели, где смотрит работу. Начало у строки своё,
«разговор», и нужно оно не для красоты: журнал это одна из двух меток живости, а
свои строки подхват не должен считать движением цели. Вывод оболочки
подхват забирает себе: `--say` печатает записанную строку в свой stdout, а на
stdout у подхвата лежит его единственный ответ, JSON добавки, и приехавшая
туда строка журнала встала бы перед ним.

Любая беда за развилкой цели это тихий ноль и строка в свой журнал
`~/.devkit/chat-in.log` (время, сессия, адрес и повод, обрезка та же, что у
уведомителя): хук стоит на каждом ходе чужой работы и ронять её не вправе, а
молчать про непонятое значит держать дыру незаметной. Поводы перечислены
поимённо: доставка; отказ при найденной цели (битая запись реестра без единой
метки движения, непротухший признак ожидания, промах имени сессии при лежащей
реплике); провал записи отметки; ненулевой код `--say`. Всё это за развилкой
«дерево сошлось с корнем цели», так что строк тут ровно столько, сколько на
машине живых целей. Слово в журнале одно на оба носителя, «адрес»: у цели это
её ID, у разговора ниже его имя, и читать журнал можно одним глазом.

```
2026-08-15T14:03:07 сессия 5a2d4b71-9c30-42ef-8f6d-cc0011223366 адрес DK-327 доставлено строк 1, первая «посмотри ещё на DK-1»
2026-08-15T14:05:19 сессия 7c1e9a02-1111-2222-3333-444455556666 адрес DK-327 отказ: реплика адресована витку 5a2d4b71-9c30-42ef-8f6d-cc0011223366, а ход идёт сессией 7c1e9a02-1111-2222-3333-444455556666, непомеченных строк 1
```

Путь мимо корней целей уезжает молча, и это не пропуск: под широкое правило
подошла бы любая сессия машины вне целей, то есть строка на каждый ход
инструмента в каждом чужом проекте. Разбирается такой случай нарочно:
`DEVKIT_CHAT_TRACE=1` в окружении сессии кладёт строку и на непопавший путь
вместе с ним самим, и на каждый промах имени сессии, так что жалоба «реплика не
доезжает вот из этой сессии» закрывается одним прогоном с ключом, а не чтением
машинного журнала за сутки.

На событие `Stop` подхват не ставим отдельным решением: хук на нём умеет
держать виток от завершения, и это ровно тот рычаг, которым автономный цикл
подвешивается навсегда, а выигрыша нет, потому что конец витка это и есть
момент, когда «Входящие» и так прочитает следующий виток. Упавший ход
(`PostToolUseFailure`) подхвату тоже не нужен: виток, разбирающийся с
падением, реплику читать не готов, а следующий удачный ход рядом.

Подключён ли хук, проверяет `devkitctl doctor`, а раскладывает `--fix`. Прежнее
имя `inbox.py` в настройках харнеса доктор тоже находит, а `--fix` убирает эту
строку и ставит на её место `chat-in.py`: править `settings.json` руками не
нужно.

## Вход разговора любой сессии

Второй носитель (DK-345) доносит реплику до сессии, которая не виток цели:
исполнителю задачи в боковом дереве, грумеру черновика, окну человека. Пишет
реплику дашборд своей ручкой `POST /api/projects/{p}/sessions/{sid}/message`
(разбор в README tools/dashboard), подхват только читает и доставляет.

Реплики лежат строками в `.devkit/chat/<имя>.in` дерева работы. Имя живёт
дольше сессии: `task-<ID>` это разговор задачи, и ответ припаркованной задаче
ложится туда без адресата, чтобы достаться той сессии, что задачу продолжит
(парковка и пробуждение за DK-402), а `sess-<ID>` это личный разговор сессии без
узнанной задачи. Адресат записан в самой строке, перед подписью дашборда:

```
2026-08-15 14:03, сессии 5a2d4b71-9c30-42ef-8f6d-cc0011223366, из дашборда: не туда, откатись
```

Строка без адресата (рукописная или написанная без сессии) доезжает любой
сессии дерева. Реплика чужой сессии лежит и ждёт своего адресата, промах
называется в журнале под `DEVKIT_CHAT_TRACE=1`, тем же ключом, что и у цели.

Адресность у реплики выбирает та ручка, которой её написали, а не догадка о
живости собеседника (LLD DK-430, решение 2). Ручка сессии ставит адресата
всегда, поэтому молчащее окно человека получает свою реплику в свой вход и
дожидается хода. Ручка задачи `POST /api/projects/{p}/tasks/{id}/message` пишет
безадресно всегда и кладёт строку во вход задачи основного чекаута: чекаут
переживает боковое дерево, снесённое слиянием. Отсюда и разделение читателей.
Подхват читает один корень, дерево своего хода, и адресная реплика лежит там,
где идёт сессия-адресат; безадресную строку из чекаута забирает первый же ход
сессии чекаута, а сторожок `devkitctl watch` читает оба места и считает ответом
задаче ровно её, безадресную.

Главное отличие от цели в том, что доставленная строка уходит из входа тут же,
под тем же замком `take_chat_lock` (файл `<имя>.lock` рядом со входом).
Отдельной механики отметок входу не нужно и она была бы вредна: у отметки цели
есть читатель, виток, забирающий строку своей записью «Входящих», а у входа
такого читателя нет, и отметки росли бы вечно. Отсутствие строки и есть
отметка, поэтому ровно один прогон подхвата доставляет реплику, а будущий
инструмент ожидания DK-402 различит непрочитанное лежащей строкой, не строя
своего состояния. Запись под тем же замком кладёт и дашборд, так что доставка
и отправка не теряют реплик друг друга.

Признак ожидания `.devkit/chat/<имя>.ask` первой строкой несёт штамп срока, тем
же форматом, что у цели, а ниже поля инструмента ожидания `taskctl ask`: ждущая
сессия, задача и пачка вопросов JSON (LLD DK-430, решение 2). Пока срок не
вышел, подхват запирает не весь вход, а только то, что заберёт ждущий:
безадресные строки и адресованные ждущей сессии остаются лежать, а реплики
другим сессиям доезжают ходом как обычно. Так два живых чата по одной задаче
лежат в одном входе и не глушат друг друга. Частичный отказ называется в
журнале подхвата строкой со сроком. Протухший признак не держит ничего, а
тик `devkitctl watch` страховкой сам паркует брошенный ход ожидания.

Прежняя пара имён, каталог `.devkit/mail` с файлами `<имя>.inbox`, читается
наравне с новой один выпуск (DK-440). Реплика, написанная дашбордом за минуту
до выката, лежит в старом каталоге, и пропасть из-за момента обновления она не
должна. Признак ожидания `.ask` и замок `.lock` имён не меняли, так что у такой
строки они лежат рядом с ней, в том же старом каталоге.

Дерево работы меряется ближайшим предком `cwd` с `.git`, а не подъёмом до
первого `.devkit`: у бокового дерева задачи `.git` это файл со ссылкой на
общий каталог, и без границы git сессия дерева задачи поднялась бы к
основному чекауту и забрала чужой разговор. Ход субагента не получает реплик и
здесь, по той же роли в событии. Реплик нет, входа нет, каталога нет и путь
вне git-дерева это тихий ноль без строки в журнале: пустых входов на машине
бывает больше, чем лежащих реплик.

## Самопроверка

```sh
cd hooks && python3 -m unittest discover -p '*_test.py'
```

Тест лежит рядом со своим хуком и зовётся по нему: `check-symbols.py` проверяет
`check_symbols_test.py`, уведомитель `notify_test.py`, таблицу разборщиков
`hookio_test.py`. Дефис в имени хука в имени теста становится подчёркиванием, и
это не вкусовщина: файл, чьё имя не годится в имя модуля python, `discover`
пропускает молча, и потерянная проверка выглядит как зелёный прогон. Что
раскладка цела (у каждого хука есть тест, а каждый тест доехал до прогона),
следит `TestRunnerLayout` в `hookio_test.py`.

Точки входа git своего модуля не имеют и проверяются оттуда, откуда их зовут по
существу: три рубежа `pre-commit` из тестов проверок, которые он гоняет,
`commit-msg` из `check_commit_test.py`, `pre-push` из своего `pre_push_test.py`.
Проверка идёт прогоном хука как процесса с подсунутым stdin: код возврата это и
есть то, что видит git и харнес.
