# Хуки: проверки текстов, уведомления и фоновая работа по расписанию сессии

Механизация правил, которые иначе держатся на внимательности: запрещённые
символы (RULES.md, «Код и тексты» п. 1), разбухание индекса памяти,
чувствительное в доске (RULES.board.md, «Трекинг задач» п. 8), правка кода без
тестов и пуш из сессии агента без разрешения (RULES.md, «Тесты обязательны» и
«Git»). Каждая
проверка стоит в двух рубежах: git-хуки ловят перед коммитом, PostToolUse-хук
Claude Code сразу при записи файла (агент получает находки как фидбек и
переписывает сам, правило не занимает контекст). Отдельно от проверок тут же
живут `quota-refresh.sh` и `notify.py`: первый ничего не проверяет, а
пользуется стартом сессии как единственным регулярным событием на машине
(см. «Снимок квоты на старте сессии»), второй говорит наружу, что сессия ждёт
действия (см. «Уведомления о сессии»).

Ядро проверки символов: в своём тексте только символы клавиатурных раскладок
en/ru, «ёлочки» и `№`.

Находка говорит не только про запрет, но и про то, чем текст переписывать.
Правило в резиденте держит сам запрет, а разбор («длинное тире перестраивается
в живую прозу, а не подменяется двоеточием») приезжает ровно в тот момент,
когда его нарушили, и потому в резиденте не лежит. `check-symbols.py` подбирает
разбор по видам символов, которые встретились (перечень `ADVICE` в нём же),
`check-commit.py` носит его при каждой своей находке, `check-tests.py` и
`pre-push` целиком состоят из него. Новый вид находки заводится вместе со
строкой разбора, иначе агент получает запрет без выхода и тратит виток на
догадки.

Ядро одно, `check-symbols.py` (нужен только python3): аргументами файлы, либо
`--stdin` для потока, либо `--hook` для хука харнеса. Выход 0 чисто, 1 находки
(в режиме `--hook` находки дают 2, так их видит агент). Файлы из директории
`testdata` проверка пропускает: там лежат снятые живьём снимки чужого вывода,
и переписать их клавиатурными символами нельзя, значит без пропуска такой
снимок красит проверку насовсем.

## Git-хуки (подключаются на проект)

Из корня проекта, devkit лежит рядом:

```sh
git config core.hooksPath ../devkit/hooks
```

`pre-commit` проверяет состав коммита (правка кода без тестов, см. ниже) и
добавленные строки staged-диффа: символы во всех файлах, чувствительное в
файлах доски (см. ниже). `commit-msg` смотрит
текст коммита без комментариев git: сначала символы, затем `check-commit.py`
по разделу «Git» RULES.md. Тот ловит следы ассистента (строгий запрет п. 4),
body у коммита (пишется одной строкой, п. 2) и тип conventional-префикса,
которого нет в последней сотне коммитов проекта (п. 1). Короткая история
(меньше `HISTORY_MIN` коммитов) и subject без префикса проверку типа выключают,
`revert` разрешён всегда: его пишет `shipctl revert` на аварийном пути.

Порог на историю нужен свежим проектам. Сразу после `devkitctl new` в проекте
стоит один коммит подключения, и на нём перечень префиксов нормой ещё не стал:
первая же строка доски приезжала бы коммитом `docs(tasks)` и вставала находкой
про чужой тип на ровном месте (DK-125).

След ищется не одного ассистента. Родовые `Co-authored-by` и `Generated with`
ловят почти всех, но подпись доезжает и мимо них (автором коммита, строкой
«paired with»), поэтому рядом стоит перечень `ASSISTANTS` из самого
`check-commit.py`: адреса и боты Claude Code, Codex, Cursor, aider, OpenHands,
Devin, Copilot и Jules, снятые с их реальных коммитов на github. Новый
ассистент добавляется туда строкой вместе с прогоном по нему в
`check_commit_test.py`. Совпадения в чужом коде не всплывают, пока
его не трогаешь; для осознанного исключения (тестовые данные с юникодом,
законный новый тип коммита) `git commit --no-verify`.

`core.hooksPath` выключает `.git/hooks` целиком. Если у проекта уже есть свои
хуки, вместо этого симлинки на конкретные:

```sh
ln -s ../../../devkit/hooks/pre-commit .git/hooks/pre-commit
ln -s ../../../devkit/hooks/commit-msg .git/hooks/commit-msg
ln -s ../../../devkit/hooks/pre-push .git/hooks/pre-push
```

## Правка кода без тестов

`check-tests.py` держит правило «Тесты обязательны» на рубеже коммита: если в
коммите есть код, а тестового файла нет ни одного, коммит не проходит. Смотрятся
имена файлов, а не содержимое: тест, дописанный к правке, это либо новый
тестовый файл, либо изменённый старый, и то и другое видно по имени. Код узнаётся
по расширению (перечень `CODE_EXT`) и по шебангу у файлов без расширения, тестом
считается путь с каталогом `tests`, `testdata`, `spec` и подобными либо имя вида
`*_test.*`, `test_*`, `*.spec.*`; фикстура в `testdata` идёт за тест, потому что
правка, приехавшая с новой фикстурой, покрытием закрыта.

Проверка грубая нарочно: она ловит не качество теста, а его отсутствие, а
краснота регрессионного теста проверяется `regcheck`, и об этом же говорит текст
находки. Обход осознанный и узкий:

```sh
DEVKIT_NO_TESTS=1 git commit -m '...'   # пропускает только эту проверку
git commit --no-verify                  # пропускает весь pre-commit
```

Первый вариант для случаев, где тесту взяться неоткуда (перенос файла, правка
сборки), и остальные рубежи он не выключает.

## Пуш из сессии агента

`pre-push` держит правило «push в origin и создание MR делает пользователь».
Рубеж смотрит окружение: переменная сессии агента (`CLAUDECODE`,
`CLAUDE_CODE_ENTRYPOINT`, `CURSOR_AGENT`) и есть признак того, что пуш идёт не
руками. Ручной пуш пользователя рубеж не видит вовсе, таких переменных у него в
окружении нет, и новый харнес добавляется в хук строкой.

Исключений из правила два, и оба идут через утилиты devkit: коммит доски
пушится сразу и без просьбы (`taskctl ... --push`), автономный режим сам сливает
и катит (`shipctl`). Обе утилиты ставят `DEVKIT_PUSH_OK=1` в окружение своего
`git push` и только его, поэтому разрешение не растекается на попутные команды
git. По прямой команде пользователя то же делается руками:

```sh
DEVKIT_PUSH_OK=1 git push
git push --no-verify
```

## Хук Claude Code (подключается глобально)

В `~/.claude/settings.json`:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|NotebookEdit",
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/check-symbols.py --hook" }
        ]
      }
    ]
  }
}
```

Хук смотрит не файл целиком, а записанный фрагмент (new_string/content из
tool_input), поэтому чужой существующий текст не трогает.

## Разбор входа по имени протокола

Тело проверки одно на все инструменты, меняется форма события на stdin, и
своего разбора проверки не носят: таблица разборщиков живёт в `hookio.py`.
Строка таблицы это протокол, функция разбора записи (путь и записанные куски
текста), функция разбора события сессии для уведомителя и канал ответа. У
claude-code канал это stderr с выходом 2, такой ответ харнес отдаёт агенту
фидбеком.

Имя протокола приходит аргументом:

```sh
python3 hooks/check-symbols.py --hook claude-code
python3 hooks/check-symbols.py --hook              # то же самое
```

Голый `--hook` остаётся псевдонимом claude-code: команды в settings.json
прописаны на машинах без имени, и обновление devkit их ломать не должно. Имя,
которого в таблице нет, это отказ кодом 2 со строкой про незаведённый разбор, а
не тихий пропуск: опечатка в настройках иначе выключила бы проверку насовсем.

Проверяется разбор по образцам. В `hooks/testdata/<протокол>/` лежат события,
снятые живьём с работающего инструмента (у claude-code это запись файла четырьмя
инструментами, ввод пользователя, конец хода, отработавший субагент и запрос
разрешения), `hookio_test.py` гоняет каждый образец через каждую проверку, а
`notify_test.py` через уведомитель. Протокол без образцов в таблицу не принимается: форма события живёт
на стороне инструмента, и разбор, проверенный по памяти, закрепляет наше
представление о ней вместо неё самой.

## Линт индекса памяти

`check-memory.py` следит, чтобы индексы памяти Claude Code (`memory/MEMORY.md`
проектов) не разбухали: каждая запись это одна строка-указатель до 160
символов, содержимое и статусы живут в файлах памяти. Разжиревший индекс
грузится в контекст каждой сессии проекта. Подключается вторым PostToolUse-хуком
рядом с проверкой символов:

```json
{ "type": "command", "command": "python3 ~/projects/devkit/hooks/check-memory.py --hook" }
```

Где лежит индекс, знает не хук, а профиль харнеса: `[hooks] memory_index` в
`kit/harness/<протокол>.toml` держит хвост пути (`/memory/MEMORY.md` у Claude Code),
и на файлы мимо него хук не реагирует. Ключа в профиле нет, значит памяти у
инструмента нет, проверка молчит и setup её не подключает: находки про индекс
были бы там шумом. Ручной прогон профиля не спрашивает:
`hooks/check-memory.py <путь к MEMORY.md>`.

## Чувствительное в доске

`check-sensitive.py` следит, чтобы в коммитируемые тексты доски
(`docs/TASKS.md`, `docs/TASKS-archive.md`, `docs/tasks/`, `docs/lld/`) не
попадали IP-адреса, токены, приватные ключи и пары вида «пароль: значение».
Доска пушится сразу и автоматически, поэтому утечка туда дороже стилевых
проколов; вместо адреса пишется роль машины («роутер DE», «VPS RU»), а
конкретика остаётся в гитигнорнутом `local-docs`. Loopback и документационные
диапазоны RFC 5737 не считаются находкой.

В git-рубеж проверка встроена в общий `pre-commit`, отдельного подключения не
надо. PostToolUse-хук ставится третьим рядом с остальными:

```json
{ "type": "command", "command": "python3 ~/projects/devkit/hooks/check-sensitive.py --hook" }
```

Файлы вне перечисленных путей хук на содержимое не смотрит. Ручной прогон:
`hooks/check-sensitive.py <файлы>` (фильтра путей в этом режиме нет).

Отдельно проверяется сам `local-docs`: правило отправляет туда всю конкретику,
но держится оно на том, что каталог заигнорен, а это забывается молча. На записи
файла в `local-docs` хук спрашивает git (`git check-ignore`), заигнорен ли путь,
и находкой говорит добавить строку в `.gitignore`; в `pre-commit` находка это уже
сам факт, что файл из `local-docs` попал в коммит. Вне репозитория и без ответа
git находки нет: рубеж тут не сторож.

## Корп-репозиторий: цепочка хуков и следы devkit

В корп-клоне `core.hooksPath` не годится: он выключает `.git/hooks` целиком
вместе с чужими хуками проекта, а молча отключённый линтер компании это
поломка чужого процесса. Симлинки не спасают, их перетирает чужой инсталлер.
Поэтому в `.git/hooks` кладётся обёртка-цепочка: файл devkit, который гоняет
проверки devkit, а следом чужой хук проекта, переехавший при подключении в
соседнее имя `<хук>.chained`. Ненулевой код любой стороны валит коммит, ни
одна сторона молча не проглатывается.

Обёртку раскладывает `install_chain` из `corp.py`, зовёт её подключение
`devkitctl corp`. Прогон повторяемый: свой файл функция узнаёт по маркеру
`devkit-corp-chain` в шапке и чужим хуком его не считает, а совпадающее
содержимое не переписывает. Первую строку занимает shebang, без него git хук
не запустит, так что маркер стоит следующей строкой. Перезаписавший обёртку
чужой инсталлер виден по пропавшему маркеру, и чинится это повторным
`devkitctl corp --fix`, который разворачивает цепочку заново.

Рубеж следов devkit (`check-traces.py`) добавляется к обычным проверкам в
цепочке: локальный ID доски и путь боковой директории не уезжают ни в дифф, ни
в сообщение коммита. Внутренняя кухня разработчика чужому репозиторию не
нужна, а ссылка на локальный ID из истории компании ещё и никуда не ведёт.
Префикс ID берётся из шапки доски боковой директории, путь считается её
именем и полным путём, а имя добавленного файла смотрится наравне с его
строками. Перечень расширяется ключом `traces` в привязке
(`.devkit/tracker.local`, слова через запятую); широкие эвристики туда не
просятся: рубеж, который врёт, отключают.

Одно правило рубеж снимает сам: когда префикс доски совпал с ключом проекта в
трекере (`key` привязки), локальный ID доски и ключ тикета это одна и та же
строка, отличить их нечем, и правило про ID валило бы каждый коммит по
конвенции компании (DK-124). Путь боковой директории и слова контура на такой
паре стерегутся по-прежнему, а про снятое правило говорит `devkitctl doctor`:
снаружи ослабленный рубеж выглядит ровно как работающий. Держать префикс доски
отличным от ключа проекта дешевле, чем терять правило.

Включается всё это признаком корп-контура из `corp.py`: ключом `devkit.local`
в конфиге клона, тем же, по которому корень devkit ищут утилиты. Без редиректа
проверка молчит, и домашние проекты цепочки не замечают, даже если обёртка у
них разложена. Осознанный обход прежний, `git commit --no-verify`.

Рубеж чувствительного для самой доски переезжает вместе с доской: боковая
директория это свой git-репозиторий, и в нём стоят обычные хуки devkit через
`core.hooksPath`, корп-специфичного там нет.

## Бит исполнения test.sh

`check-exec-bit.py` следит, чтобы каждый `test.sh` в репозитории (в корне и
в любой вложенной директории) нёс бит x в git-индексе. Обычный `chmod +x` на
диске регресс не чинит: бит живёт в режиме объекта git, и без `git add` или
`git update-index --chmod=+x` следующий чекаут его снова снимет. Без бита
команда из докладов вида `kit/skills/test.sh` падает `permission denied`
вместо честного вывода теста (DK-072), а соседний скрипт с битом на вид
неотличим, пока его не запустишь.

```sh
python3 hooks/check-exec-bit.py
```

Выход 0 чисто, 1 построчные находки «путь: режим NNN вместо 100755». CI
гоняет её на каждый push тем же прогоном.

## Снимок квоты на старте сессии

`quota-refresh.sh` освежает снимок остатка лимитов активного харнеса
(`~/.devkit/quota/<харнес>.local`), по которому корректор `agentctl pick`
двигает вердикт. Снимок нужен свежий (порог 45 минут, разбор в
`tools/agentctl/README.md`), а руками его не переснимает никто: корректор из-за этого
простоял выключенным с самого появления. Старт сессии Claude Code это
единственное регулярное событие, к которому такую работу можно привязать,
поэтому хук ставится на `SessionStart`:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "sh ~/projects/devkit/hooks/quota-refresh.sh" }
        ]
      }
    ]
  }
}
```

Сессию хук не задерживает: он проверяет, чем снимать (`agentctl`, `tmux`,
`claude` в PATH), берёт замок и уходит, а `agentctl quota refresh --if-stale`
доснимает панель отцепленным процессом. Свежий снимок при этом не трогается,
порог живёт в agentctl, второй его копии в хуке нет.

Замок `~/.devkit/quota-refresh.lock` держит две вещи сразу. Главная: refresh
поднимает `claude` в tmux, старт того клиента дёргает этот же хук, и без замка
получилась бы воронка из сессий. Заодно параллельные сессии не снимают панель
наперегонки. Брошенный замок старше десяти минут снимается сам, весь цикл
refresh укладывается в минуту.

Нечем снимать (нет tmux, нет claude, нет самого agentctl), значит хук молча
уходит и следов не оставляет: он стоит у всех сессий на машине и ругаться в
каждой не должен. Так же он ведёт себя на харнесе без объявленной квоты (пустая
секция `[quota]` профиля, сегодня это вторая подписка): `agentctl quota refresh`
там честно отказывает, снимать нечего по построению, и журнал из одних отказов
перестал бы отвечать на вопрос, ради которого заведён. Молчание тут узкое,
незалогиненный клиент и неузнанная панель в журнал по-прежнему попадают, а про
сам харнес без квоты говорят `agentctl harness` и хвост вердикта `pick`. Про нехватку скажет `devkitctl doctor`, он же ловит
неподключённый хук и протухший снимок. Что фоновая работа реально была, видно
по журналу последнего запуска `~/.devkit/quota-refresh.log` (время, код
возврата и причина отказа, если панель не снялась) и по возрасту снимка в
выводе `agentctl quota`.

## Уведомления о сессии

`notify.py` говорит наружу, что сессия ждёт действия. Параллельных сессий на
машине несколько (у каждой задачи свой worktree после `shipctl start`, рядом
фоновые субагенты), и та, что упёрлась в запрос разрешения, стоит, пока на её
окно не посмотрят. Канал уведомлений самого Claude Code
(`preferredNotifChannel`) прибит к конкретным терминалам и в VS Code с
Terminal.app не годится, поэтому уведомление шлётся своими руками.

Уведомитель это отдельная команда, хук поверх неё тонкий: позвать его может и
скрипт выката, и другой харнес.

```sh
hooks/notify.py "заголовок" "текст"          # аргументами, повод громкий
hooks/notify.py --quiet "заголовок" "текст"  # то же фоновым поводом
hooks/notify.py --hook claude-code           # событие харнеса на stdin
hooks/notify.py --self-test                  # пробное уведомление
```

### Громкий повод и фоновый

Поводы двух сортов, и от сорта зависит, как баннер выглядит. Громкий зовёт
подключиться, приходит со звуком и своей строкой. Фоновый рассказывает о ходе
работы, приходит молча и схлопывается по сессии: новый баннер сессии вытесняет
её же предыдущий, а не ложится под него. Без такого деления канал забивается
тем, что срочности не несёт (за первые сутки работы уведомителя в журнале
набралось 84 отчёта об отработавших субагентах на одно `idle_prompt`), и
момент, когда сессия правда ждёт человека, тонет среди них.

Громкие поводы:

- сессия упёрлась в вопрос: `permission_prompt`, `agent_needs_input`,
  `elicitation_dialog` события `Notification`;
- сессия закончила ход: событие `Stop`, плюс `idle_prompt`, который харнес
  присылает примерно через минуту простоя. Конец хода уведомляет не всякий,
  решает фокус окна (см. «Фокус окна на конце хода»);
- позвали снаружи: `notify.py "заголовок" "текст"` считается громким по
  умолчанию, понижает его флаг `--quiet`. Так зовут `taskctl move` (задача
  доехала до Check или встала на блокере) и `shipctl merge`/`ship`/`revert`
  (выкат упал, самый громкий повод из трёх, прод в этот момент может быть
  сломан); разбор в README обеих утилит.

Фоновый пока один: субагент отработал, событие `SubagentStop`. Повод
`agent_completed` события `Notification` сюда не относится, он про фоновые
сессии, а не про субагентов, поднятых из сессии (проверено живьём, разбор в
`docs/tasks/DK-034.md`).

Отбор поводов `Notification` держат матчеры в `settings.json` (тип события
работает матчером, отдельного кода для отбора не нужно). В
`~/.claude/settings.json`:

```json
{
  "hooks": {
    "Notification": [
      {
        "matcher": "permission_prompt|agent_needs_input|elicitation_dialog|idle_prompt",
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/notify.py --hook claude-code" }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/notify.py --hook claude-code" }
        ]
      }
    ],
    "SubagentStop": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/notify.py --hook claude-code" }
        ]
      }
    ],
    "UserPromptSubmit": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/projects/devkit/hooks/notify.py --hook claude-code" }
        ]
      }
    ]
  }
}
```

Хук на `UserPromptSubmit` ничего не шлёт, он снимает отметку ожидания: человек
вернулся к сессии, и конец следующего хода это новый повод позвать, а не повтор
прошлого (см. про окно троттлинга ниже).

Как уровень выглядит на баннере, решает бэкенд. `terminal-notifier` берёт
`-sound default` у громкого и `-group devkit-<сессия>` у фонового,
`osascript` только звук (группировки у `display notification` нет вовсе),
`notify-send` срочность `critical` либо `low` вместе с подсказкой
`x-canonical-private-synchronous`. Своя команда из `DEVKIT_NOTIFY_BACKEND`
уровня не понимает и получает заголовок с телом, как раньше.

Заголовок отвечает на вопрос «какая сессия»: имя рабочего дерева плюс повод
(`devkit-dk-034: нужно разрешение`), а работал субагент в дереве задачи, значит
в скобках стоит и она (`it-road-course (irc-75): субагент отработал`, см. «Клик
по баннеру»). Имя дерева задачу не назвало (сессия сидит в основном чекауте,
а не в linked worktree с ID в имени), а дерево стоит на ветке задачи, значит
в скобках эта ветка (`devkit (dk-121): ход закончен`); ветку читаем файлом
`.git/HEAD` самого дерева, `git` не зовём, а `main` и `master` за метку задачи
не считаем. В теле одна строка сообщения харнеса, а на конце хода и у субагента
это первая строка последней реплики (`last_assistant_message`), у субагента
ещё и с его ролью. Чем слать, выбирается по платформе
и PATH: macOS `terminal-notifier`, а без неё `osascript`, Linux `notify-send`,
для Windows и WSL пока заготовка. `DEVKIT_NOTIFY_BACKEND` перебивает выбор
именем бэкенда либо своей командой (её зовут как `команда заголовок тело`),
`DEVKIT_NOTIFY_OFF=1` гасит уведомитель целиком, это для headless-прогонов, где
уведомлять некого, а `DEVKIT_NOTIFY_FOCUS=off` снимает проверку фокуса, и конец
хода зовёт всегда. В сессии подпроцесса делегирования (`DEVKIT_RUN_DEPTH` в
окружении, её поднимает `agentctl run`) хуки молчат и пишут в журнал строку
пропуска: такой сессии никто не ждёт у окна, диспетчер стоит на `run` синхронно
и заберёт результат сам, а звонок на каждый её конец хода это шум, от которого
потом глохнет настоящий. Окна редактора на второй подписке правило не касается,
там переменной нет. Системного бэкенда не нашлось, значит хук уходит нулём, но
просит харнес выдать уведомление через сам терминал (OSC 9), и это же остаётся
запасным путём по ssh.

### Фокус окна на конце хода

Конец хода зовёт не всякий раз: смотришь в окно этой самой сессии, значит всё
и так видно, и баннер только мешает. Куда смотрит человек, отвечает
`System Events`: заголовок переднего окна переднего приложения. У VS Code в
заголовке хвостом стоит имя рабочего дерева (`Правка notify.py -
devkit-dk-064`), а дерево сессии уведомитель и так знает, он собирает по нему
цель перехода по клику. Заголовок кончается именем этого дерева, значит молчим,
всё остальное значит зовём, хоть через три секунды после ввода. Хвост берётся
целым словом: `devkit` и `devkit-dk-064` это разные деревья, а значит и разные
окна.

Раньше тут стоял порог длительности хода в минуту (DK-062): считалось, что
короткий ответ пользователь дожидается, глядя в то же окно. Догадка неверная, и
короткий вопрос, заданный перед тем как отойти, терялся ровно из-за неё.
Длительность хода это про то, сколько работала машина, а звать или молчать
зависит от того, где в это время человек, и одно из другого не выводится.

Проверка стоит только на конце хода. Запрос разрешения и вопрос агента зовут
всегда: они редкие, сессия на них стоит намертво, а повторного события от
харнеса может и не быть. Фоновых поводов проверка не касается вовсе, иначе
каждый отработавший субагент стоил бы лишнего опроса (около 180 мс).

Спросить не удалось (не macOS, нет разрешения на управление компьютером,
`osascript` ответил ошибкой или пусто) значит зовём: тишина тут хуже лишнего
баннера, она неотличима от штатной работы, а разрешение выдают не на всякой
машине. Отказ уходит в журнал строкой «фокус не определился, зовём», так что
жалоба «звонит всегда» разбирается по факту. Совсем гасит проверку
`DEVKIT_NOTIFY_FOCUS=off`.

Несколько чатов в одном окне редактора друг от друга не отличить, и это
осознанная грубость: сессии в одном дереве считаются одной, зато промах уходит
в сторону лишнего баннера, а не тишины.

### Клик по баннеру

Клик переключает в окно позвавшей сессии, но только когда шлёт
`terminal-notifier` (`brew install terminal-notifier`). Своего обработчика
клика у `osascript` нет: он постит от имени Script Editor, и клик открывает
Finder с папкой скриптов. Сменить одну атрибуцию мало, проверено: баннер от
`tell application id "com.microsoft.VSCode"` всё равно приходит от Script
Editor. Без `terminal-notifier` уведомления работают по-прежнему, просто не
кликаются, и доктор предлагает её поставить.

Цель перехода ведёт в дерево, на котором стоит окно сессии:
`vscode://file/<путь>?windowId=_blank` поднимает это окно, а при пяти
параллельных сессиях попадаем в нужную. Уже открытое окно поднимается, второго
VS Code не заводит. Параметр `windowId=_blank` тут обязателен: без него редактор
открывает дерево в активном окне, и когда своего окна у дерева нет, кликом
сносится то окно, в котором сейчас работают, вместе со всеми его агентами.

Дерево сессии берётся не из `cwd` события, а из первых записей её транскрипта
(`transcript_path`, до 20 записей: сверху там служебное, а транскрипт вырастает
на десятки мегабайт). Причина в субагентах: субагент уходит в worktree задачи,
и `cwd` события показывает уже его дерево, у которого своего окна нет. Клик по
такой цели открывал бы лишнее окно вместо того, где идёт работа. Транскрипт не
читается (нет пути, битые записи, `cwd` в первых записях не попался), значит
цель собирается из `cwd`, как раньше. Заголовок при этом показывает и окно, и
задачу: `it-road-course (irc-75): субагент отработал`.

Работа идёт не в VS Code, значит переключается сам терминал по `TERM_PROGRAM`
(Terminal.app, iTerm), окно там по рабочему дереву не найти.
`DEVKIT_NOTIFY_OPEN` перебивает цель своим шаблоном с подстановкой `{cwd}`,
пустое значение гасит переход совсем.

Против шума, кроме отбора поводов и уровня, работает окно: один и тот же повод
одной сессии не повторяется чаще, чем раз в полминуты. Конец хода и
`idle_prompt` при этом считаются одним поводом «сессия ждёт тебя», ключ у них
общий, а окно три минуты: `idle_prompt` приходит через минуту после конца хода
и своим окном повторил бы тот же баннер. Отметку ожидания снимает ввод
пользователя: он к сессии вернулся, и конец следующего хода это новый повод
позвать, а не повтор прошлого, так что второй ход подряд звучит даже в
пределах общего окна. Состояние по ключу «сессия плюс повод» лежит в
`~/.devkit/notify/`, брошенное старше суток убирается само. В аргументном режиме окна нет: позвал скрипт, значит шлём.

Единственное, что глушит аргументный вызов помимо `DEVKIT_NOTIFY_OFF`, это
проект во временной директории (`TMPDIR`, `/tmp`, `/var/folders`). Такой
корень это песочница вроде синтетической доски из обкатки сценария: живой
баннер про неё ложный, клик ведёт в репозиторий, которого через минуту нет.
Рубеж стоит в самом уведомителе, а не в зовущих утилитах, чтобы не зависеть
от заглушки, про которую надо помнить в каждом прогоне. Пропуск не молчит:
в журнале остаётся строка «пропуск: песочница, корень ... лежит под ...», а
в stdout строка «уведомление пропущено: ...», которую зовущая утилита доносит
до своего вывода (приписка у `taskctl move`).

Что уведомления реально идут, видно по журналу `~/.devkit/notify.log` (время,
сессия, повод, уровень, бэкенд, цель перехода и код возврата, там же пропуски
по окну и по фокусу, отказы и события, которых хук не понял), так что
жалоба «не приходит ничего» разбирается по факту, «клик никуда не ведёт» по
тому, уехала ли цель, а «важное не отличается от фонового» по уровню:

```
2026-08-02T14:03:11 сессия f07df579 повод permission_prompt уровень громкий бэкенд terminal-notifier цель vscode://file/p/devkit?windowId=_blank код возврата: 0
2026-08-02T14:07:52 сессия f07df579 повод subagent_stop уровень фоновый бэкенд terminal-notifier цель vscode://file/p/devkit?windowId=_blank код возврата: 0
2026-08-02T14:08:30 сессия f07df579 повод turn_done уровень громкий бэкенд - цель - пропуск: окно сессии в фокусе
2026-08-02T14:12:04 сессия f07df579 повод idle_prompt уровень громкий бэкенд - цель - пропуск: повтор в окне 180с
```

Кривой вход хук не роняет: форма события целиком на стороне харнеса, поэтому
что не json, что json не объектом, что поле не той формы заканчиваются кодом 0
и строкой в журнале. Отдельно есть `notify.py --self-test`: он шлёт пробное
уведомление и печатает, чем именно послал и куда поведёт клик. Без него macOS
остаётся дырой в наблюдаемости: баннер приходит от имени отправителя (Script
Editor у `osascript`, terminal-notifier у неё самой), и если разрешение этому
имени однажды не дали, отправка отвечает нулём, а на экране не появляется
ничего.

Подключён ли хук на все четыре события, есть ли на машине чем слать и ведёт ли
клик в окно сессии, проверяет `devkitctl doctor`.

## Самопроверка

```sh
cd hooks && python3 -m unittest discover -p '*_test.py'
```

Тест лежит рядом со своим хуком и зовётся по нему: `check-symbols.py` проверяет
`check_symbols_test.py`, уведомитель `notify_test.py`, таблицу разборщиков
`hookio_test.py`. Дефис в имени хука в имени теста становится подчёркиванием, и
это не вкусовщина: файл, чьё имя не годится в имя модуля python, `discover`
пропускает молча, и потерянная проверка выглядит как зелёный прогон. Что
раскладка цела (у каждого хука есть тест, а каждый тест доехал до прогона),
следит `TestRunnerLayout` в `hookio_test.py`.

Точки входа git своего модуля не имеют и проверяются оттуда, откуда их зовут по
существу: три рубежа `pre-commit` из тестов проверок, которые он гоняет,
`commit-msg` из `check_commit_test.py`, `pre-push` из своего `pre_push_test.py`.
Проверка идёт прогоном хука как процесса с подсунутым stdin: код возврата это и
есть то, что видит git и харнес.
