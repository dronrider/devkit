# Разбор черновиков доски

`taskctl draft` записывает сырую мысль мимо доски, чтобы она не терялась на
пятиминутном разборе шкал, и накопитель растёт сам собой. Здесь обратная
половина, и начинается она не с оформления, а с разбора: черновик сначала
проверяется на живость и на дубль, и только дозревший становится строкой
Backlog. Правило, из которого процедура выведена, лежит в `RULES.board.md`
(п. 5 раздела «Трекинг задач»), шкалы в `RANKING.md`, механика исходов в
`tools/taskctl/README.md`, решения в `docs/lld/DK-129-groom-process.md`.

Работа идёт в сессии, а не субагентом: ранг, поставленный без уточнений, это
ранг наугад, а вопрос задаёт только тот, кто говорит с пользователем. Отдать
субагенту можно проверку актуальности, когда она упирается в широкий поиск по
дереву: в контексте тогда осядет ответ, а не вся выдача.

## Входы

Вход по одному ID, по нескольким ID или без аргументов. Без ID список для
модели даёт `taskctl draft list --safe`: обычный список предназначен локальному
экрану и может содержать закрытые заголовки. Для каждого ID до чтения заголовка
или тела и до запуска модели выполняется `taskctl guard <ID>`. Закрытая запись
ждёт локальную модель; ошибка проверки тоже останавливает её разбор. Не
передавать закрытый материал облачной модели, даже если она обещает его не
читать. В пачке остальные записи разбираются отдельно.

Тип, источник и замок независимы. После успешного guard прочитать метаданные
и получить действующее определение через `taskctl draft types --json` или
`taskctl draft types --dump <тип>`. Проектный файл заменяет одноимённый файл
kit целиком. Следовать указанному в определении `skill` или `prompt`, а не
выбирать процедуру по списку известных имён. Новый тип работает тем же путём.
Неизвестный или ошибочный тип показать как ошибку, не подменять другим.

## Процедура

1. Прочитать материал и уже принятые решения после guard. Сохранить источник,
   тип и замок отдельно от предлагаемого исхода. Проверить актуальность,
   предмет, конец работы и условия по воротам ниже. Для поиска дублей дать
   модели `taskctl list --safe` и `taskctl draft list --safe`: первый список
   включает активную доску и архив. До чтения тела каждой найденной задачи,
   архивной записи или черновика выполнить `taskctl guard <ID>`. Не искать по
   файлам задач, `docs/TASKS.md` и `docs/TASKS-archive.md` прямыми `rg` или
   `cat`: там могут быть закрытые заголовки и тела. Код для проверки
   актуальности искать по явно выбранным файлам или каталогам кода. Поиск по
   всему дереву с исключениями может задеть архив, его не использовать.
   Скрытый ID оставить для проверки человеком на локальном экране; закрытый
   материал облачной модели не передавать. Неизвестное совпадение отметить в
   подготовленных задачах. Его локальная проверка нужна до применения, но не
   мешает сохранить редактируемые задачи для обсуждения. Текстовая похожесть
   не доказывает дубль. Мысли человека попадают в раздел «Идеи» записи действием
   «Оставить мысль» на экране записи или командой `taskctl draft idea <ID>
   "текст"`. Разбор читает их наравне с исходником.
   У разобранной записи повторный разбор запускать только при мыслях без
   приписанной судьбы или после ошибки предыдущего разбора. Наличие подготовленных задач не означает, что все
   мысли разобраны. Открытие разговора по записи возвращает в прежний чат
   при любом числе новых мыслей. История и исходный материал доступны без повторного запуска.
   Явное действие «Разобрать мысли» доступно внутри чата при новых мыслях,
   когда разбор не идёт. После ошибки там доступно действие «Повторить разбор»
   без добавления новой мысли.
2. Позвать `interview` по каждой записи до подготовки задач. Обход,
   первый раунд сценариев и дальнейшие развилки идут его порядком. До
   подготовки задач сохранить состав сценариев; если для состава нужен
   ответ человека, дождаться его. Сохранённые решения не спрашивать заново.
   Ответ, меняющий предмет или DoD, сверить с человеком. Выбор сценариев
   определяет состав работы, но не разрешает применять задачи к доске.
3. До подготовки задачи взять выборку `prose.py sample --genre task` по
   скиллу `prose`. Разделить материал на самостоятельные задачи. У
   каждой указать смысл, исход и причину, а для приписки адресата, для
   отложения событие и дату возврата, для удаления причину. Связи и порядок
   между задачами указать явно. Для новой строки подготовить заголовок,
   тип bug/task/LLD, DoD, цену и ранг по пяти слагаемым `RANKING.md`, каждое
   с фактом и причиной.
   Мысли раздела «Идеи» разбираются той же развилкой: годная мысль становится
   подготовленной задачей, поправка самой записи вливается в её материал,
   посторонняя отбрасывается с доводом.
   Вид приёмки выбрать по шести барьерам `ACCEPTANCE.md`; для неагентского
   назвать барьер и обход. Сверить форму с `TASKFORM.md`. Недостающий факт не
   подменять оценкой. Для LLD приёмка user с барьером согласия.
4. Получить `taskctl draft prepared <ID>` и сохранить заключение, действия и
   задачи командой `taskctl draft prepared save <ID> --base <snapshot>` через
   stdin.
   `snapshot` здесь снимок редактирования исходника. В `conclusion` записать
   читаемое заключение о предложенных удалениях, приписках, отсрочках и
   новых задачах. В `proposals` сохранить полный структурированный план.
   Только `add` это отдельная подготовленная задача с постоянным номером.
   У `drop` обязательна причина `reason`, текст отдельной задачи не нужен.
   `target` у `drop` и `defer` указывает черновик назначения. Без назначения
   действие относится к материалу исходника.
   JSON без `complete` сохраняет промежуточный результат. Команда дописывает
   новые задачи и обновляет присланные редакции. Правка задачи повышает её редакцию,
   решённая задача правке не подлежит. При замене всего непринятого состава
   передать `replace_pending: true` и полный новый набор непринятых задач.
   Принятые задачи и квитанции сохраняются. Удалённые ключи остаются занятыми.
   Пустой анализ сохранить как пустой. Ошибка должна быть видна. Исходник
   остаётся активным и доступным для ручного дополнения. Не придумывать
   задачу вместо отсутствующего результата.
   Приписать судьбу каждой мысли рядом с её пунктом в разделе «Идеи» правкой
   файла записи. Допустимы «поднята в задаче <ключ>», «влита в материал
   записи» и «отклонена: <довод>». Для задачи взять сохранённый ключ.
   Отметкой судьбы считается сегмент после стрелки «->» в строке пункта либо
   отдельная строка под пунктом, начатая словом судьбы или пометкой «судьба:».
   Слово судьбы внутри текста самой мысли отметкой не считается. Не вписывать
   отметку в текст мысли без стрелки. Судьба видна человеку в самой записи.
   Приписка это правка доски, её коммит уезжает сразу.
   После записи всех судеб получить свежий `snapshot` и завершить подготовку
   сохранением JSON с `complete: true`. Проверяется весь непринятый состав,
   готовность связывается с текущим материалом записи. Новая мысль, правка
   исходника или состава требуют снова завершить подготовку.
5. Дождаться успешного завершения `save` и только затем опубликовать вопрос
   командой `taskctl draft prepared ask <ID>`, добавляя выбранные источники
   ключами `--also <ID>`. Не запускать сохранение и публикацию параллельно.
   Команда сохраняет ожидание и возвращает показанный вопрос. На каждую задачу
   в нём строка «<заголовок>: <ссылка>». Описание человек читает по ссылке.
   В вопросе показаны заключение, ссылка на исходник и ссылки только на
   задачи `add`. Удаления, приписки и отсрочки остаются читаемым текстом
   заключения. Для каждого источника в машинной части вопроса указаны весь
   подготовленный состав, `basis` и редакция разбора `revision`. Согласие
   отмечается у черновика.
   Поле `delivery` в выводе команды задаёт способ показа. При `panel`
   показать возвращённое заключение в ленте, завершить ход и ждать согласия.
   Панель добавит отмеченные рекомендации по исходным записям и кнопку
   «По рекомендации». Второй вопрос инструментом оболочки здесь не задавать.
   При `dialog` получить согласие на весь разбор штатным инструментом вопросов
   оболочки. При `text` показать вопрос текстом. Если человек спрашивает о задачах,
   ответить на вопрос и оставить ожидание и задачи без применения.
   Явное согласие человека на весь показанный разбор в его чате разрешает
   применить результат через сохранённый Ask. Вопросы, комментарии
   с замечаниями и частичное согласие остаются обсуждением. Несогласие требует
   доработать задачи и показать актуальный состав для нового подтверждения.
   Готовые старые разборы без pack_revision и prepared_source сервер
   проверяет при чтении. Для них не требовать карандаш, фиктивную правку
   или Save. Чтение не применяет результат. Новый разбор и современный
   незавершённый пакет требуют complete:true.
6. Применить только явное решение человека о всём показанном разборе
   выбранного черновика. Ответ на `сценарии/1`, показ вопроса и история
   не разрешают применять задачи. Передать согласие через
   `taskctl draft prepared answer <ID>` на stdin в машинной форме команды.
   Взять из показанного вопроса дерево, `basis` и `revision` каждого выбранного
   источника. Снимок содержит редакцию всего разбора, а массив `decisions`
   содержит все непринятые пункты плана, включая `add`, `attach`, `defer`
   и `drop`, с их редакциями и `action: "accept"`.
   Не подменять `basis` свежим скрытым снимком. Частичные решения и отдельное
   отклонение запрещены. Показать канонические результаты или ошибку.
   Подтверждение применяет весь состав и завершает исходник одной транзакцией.
   При ошибке любого элемента записи остаются прежними. `--repeat-only`
   возвращает сохранённый результат точного повтора. Прямыми `add`, `attach`,
   `defer` и `drop` обходить подтверждение нельзя.

## Ворота готовности

Черновик дозрел, когда по нему собирается строка доски, каждая ячейка которой
опирается на факт из текста или из ответа пользователя. Ворот четверо, и все
четыре проверяются. Это единственное место с полным
описанием четырёх ворот; остальные входы ссылаются сюда.

1. **Актуальность.** Предмет черновика воспроизводится или отсутствует сегодня,
   и проверка названа командой: для находки это прогон на временном
   репозитории с синтетической доской, для нехватки греп по коду или чтение
   того места, где её ждут. Исходов у проверки три:
   - предмет воспроизвёлся либо нехватка на месте, черновик идёт дальше по
     воротам;
   - предмета нет, симптома не было вовсе либо его сняла чужая правка, исход 4;
   - симптом наблюдался вживую, но по требованию не воспроизводится, а
     оставшиеся версии проверяются только в момент, когда он случится снова.
     Исход 3, и в причине пишется, чего ждём.
2. **Предмет.** Названо, что именно ломается или чего не хватает, у кого это
   перестаёт получаться и есть ли обход. Отсюда берутся серьёзность и ценность,
   и без этих двух фраз обе оценки ставятся пальцем в небо.
3. **Конец работы.** Названо, чем работа кончается и чем это видно снаружи.
   Отсюда берутся тип и цена, и это же становится DoD задачи.
4. **Условия.** Названо, что понадобится от человека, пока задача делается, и
   чего агент не добудет сам. Сюда входят доступ или секрет, публичность
   репозитория, невозвратный шаг наружу, чужая команда, согласие на развилку,
   меняющую правила другим строкам. Каждое условие записано развилкой с
   `решает: человек`, и открытая держит старт. Пишет развилку команда
   `taskctl decide <ID> --ask «имя» --hint "рекомендация" "вопрос"`, а ответ
   человека закрывает её командой `taskctl decide <ID> «имя» --by человек
   "ответ"`. Раздел «Развилки» руками не правится, и пересказ ответа прозой
   рядом с вопросом за ответ не считается. Условий не нашлось, а в разборе
   всё равно записано, что их искали и где. Пустой перечень неотличим от
   непроверенного, и строка «условий, посильных только человеку, не нашёл»
   эту неотличимость снимает.

Выбранного подхода в воротах нет сознательно. Открытая развилка это законное
содержимое строки. Она едет третьим слагаемым, поднимает ранг и даёт либо тип
`LLD`, либо грумминговый вердикт `pick`, который зовёт сильную модель снять
неопределённость. Объём и стройность текста воротами не меряются тоже. Самый
длинный черновик накопителя оказался зрелым, а единственный отложенный
подробнее большинства.

## Исходы разбора

У каждой подготовленной задачи один из четырёх исходов: `add` создаёт строку,
`attach` приписывает материал к существующей строке, `defer` откладывает
фрагмент с причиной и датой, `drop` снимает его с причиной. Человек
подтверждает весь подготовленный состав черновика одним решением.
Полностью разобранная запись становится историей в том же файле: исходный
материал, задачи и результаты сохраняются. Её ID остаётся занятым. Историю
можно увидеть через `taskctl draft list --history --safe --json`. Новая мысль
по завершённому разбору записывается отдельным черновиком.

Поля типа относятся к будущему принятому результату. Для agreement нужен
ответственный человек с ролью исполнения, для milestone срок; отсутствие
этих полей не запрещает захват мысли, отказ, отложение или удаление. Проверка
формы и обязательных полей перед применением не заменяет показ и согласие.

## Где процедура упирается

Непонятный материал остаётся активным; предложить отложение с причиной, если
известно событие возврата. Не дошедшие до разбора записи не помечаются
отложенными. Если идея распадается на несколько работ, сохранить несколько
подготовленных задач и их связи. Если задача ссылается на другую, не принимать
её раньше предшественника. При ошибке или устаревшем снимке показать причину и
повторить просмотр, не обходить проверку прямыми командами.
