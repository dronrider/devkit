# Процесс интервью

Развилка это нерешённый вопрос в разделе «Развилки» записи. Поле
`решает: человек` означает, что задачу нельзя начинать без подтверждения
человека. Поле `решает: исполнитель` само по себе не запрещает старт;
исполнитель принимает записанную рекомендацию как ответ по умолчанию.
Готовность постановки при любом значении поля проверяй по шагу 6.

## 1. Прочитай запись и определи текущий этап

Выбери файл для вопросов и ответов:

| Вид работы | Файл |
| --- | --- |
| Разбор записи через `board-groom` | Файл исходной записи |
| Постановка цели через `goal-start` | Файл черновика цели, после `add --id` файл цели |
| Подготовка LLD | Файл LLD-задачи |
| Нарезка через `goal-cut` | Файл той задачи, к которой относится вопрос |
| Выполнение задачи | Файл выполняемой задачи |

В командах замени `<ID>` идентификатором записи. Выполни `taskctl guard <ID>`,
прочитай постановку, дерево решений, сохранённые ответы и пометки сверки.
Открытые вопросы посмотри командой:

```sh
taskctl decide <ID> --open
```

Темы интервью бери из постановки и инструкций вызывающего скилла.
Пустой `--open` не доказывает полноту постановки; её проверь на шаге 6.

При новой постановке выполняй следующие шаги по порядку.
При продолжении проверь применимость сохранённых выводов к текущим
показателям, нагрузке и условиям использования; повтори затронутые действия.
Если вопрос возник во время выполнения задачи, проведи обход на шаге 2
и переходи к шагу 4 для затронутых сценариев и показателей. Если находка меняет состав или
смысл сценариев, вернись к шагу 3. Быстрый `board-draft` интервью не проводит;
оно начинается при разборе записи.

## 2. Собери недостающие факты

До вопроса человеку проверь, нет ли ответа в записи, файле цели, коде,
документации, на доске или в форме `TASKFORM.md`. Найденный ответ используй
с указанием источника. Прецедент в коде обосновывает рекомендацию, но сам
по себе не означает согласия человека на изменение поведения.

Для `board-groom` и `goal-start` до первого вопроса вызови субагента со
свежим контекстом для обхода кода, документации и доски вокруг предмета
записи. При подготовке LLD учти находки этого обхода. Исполнитель вызывает
такой обход для вопроса, найденного во время работы, до ожидания человека.
Подробности задания субагенту и сохранения источников прочитай в
[research.md](research.md) перед обходом.

Первый обход выполняется на запись, у исполнителя на найденную развилку.
Используй сохранённые находки, пока их основания остаются актуальными.
При новом риске, данных или изменении условий повтори исследование
затронутой части, даже если текст постановки ещё не изменён. Отсутствие
находок допустимо, если указано, что проверено; оно не подтверждает полноту
дерева и достижимость продуктовых показателей.

Оставшиеся вопросы проверь по критерию шага 4. Передавай внутренний вопрос
исполнителю только после проверки влияния на продуктовые показатели.
Если влияние или нужный уровень ещё неизвестны, продолжай исследование.

## 3. Определи пользовательские сценарии

Пользовательский сценарий описывает, кто, в какой ситуации и ради какой
цели использует результат работы, что делает и какой наблюдаемый результат
получает. У автоматической операции укажи получателя результата и событие
запуска. Например: «Бухгалтер перед сверкой выгружает операции за месяц,
получает CSV и сверяет его с выпиской».

Сценарий должен объяснять пользу и позволять проверить результат. «Добавить
экспорт» слишком неопределённо, а «использовать библиотеку CSV» описывает
реализацию. Пустая выборка, ошибка записи и повторный запуск обычно являются
ветками сценария экспорта. Выделяй отдельный сценарий, когда меняется цель,
получатель или ситуация использования и появляется самостоятельный результат.

Собери сценарии из требований, примеров и решений. У задачи используй
«Что происходит» и «Чего хотим», у цели и LLD равнозначные разделы.
Для каждого непокрытого требования добавь сценарий либо уточни его смысл.
Если неизвестно, кто пользуется результатом или для чего он нужен, сначала
выясни это предметным вопросом по шагу 5, затем готовь карточки для выбора.

Для каждого сценария отдели происхождение от основания включения:

| Основание | Действие |
| --- | --- |
| Прямое требование или сохранённый выбор человека | Включи с точной ссылкой на источник; повторно не спрашивай |
| Необходимое следствие принятого требования | Запиши связь: без этого сценария какое требование не выполняется. Применяй без вопроса только при единственном допустимом выводе |
| Правдоподобный вывод из примера | Сохрани как предположение. Если трактовки различаются поведением, объёмом или продуктовыми показателями, уточни их |
| Предложение агента о дополнительной пользе | Обоснуй пользу и цену; включай только после выбора человека |

Предлагай дополнения, связанные с целью пользователя. Если идея не нужна
для достижения продуктовых показателей и человек не просил её рассмотреть,
оставь её за пределами состава; она не мешает готовности исходной задачи.

Пример не определяет все границы задачи. Прямое требование одного сценария
не исключает остальные, если человек не ограничил состав явно. У бага
сохрани заданное поведение и проверь соседние условия, влияющие на исправление.

До выбора проверь выполнимость, зависимости, риски для продуктовых показателей
и существенные последствия каждого кандидата. Покажи, какую цель покрывает рекомендованный состав,
что останется за его пределами, какие есть ограничения и почему разумны
добавления. Уверенность агента и меньший объём сами по себе не основание
исключать нужный сценарий. Не предлагай нарушающие требования варианты.
Связанные сценарии нельзя представлять как независимо выбираемые.

Каждому сценарию присвой устойчивый `СЦ-N` и укажи происхождение:
«слово пользователя», «вывод из примера» или «предложение агента».
В разделе `## Пользовательские сценарии` под `### СЦ-N` заполни строки
`Ситуация:`, `Действие:`, `Результат:`, `Польза:`, `Рекомендация:`,
`Ограничение:` и `Источник:`. Значения должны быть непустыми, результат
наблюдаемым снаружи, рекомендация с причиной.
До показа выбора должны быть понятны получатель, цель и результат сценария.
Неизвестные детали явно отмечай в ограничениях. Если такая деталь способна
изменить выбор состава, выясни её до выбора; остальные разбери по дереву.

Перед командами выбора сценариев прочитай [scenarios.md](scenarios.md).
Подготовь все карточки до `--chat` и `--given`. При настоящем выборе покажи
карточки и список из вывода команды, сохрани ответ с ключом показанного
снимка. Рекомендацию сохраняй отдельно от вариантов.

При ответе «ничего» или снятии всех сценариев выясни новый состав либо
прекращение работы. После пересмотра состава сверь зависимые решения по
`scenarios.md`. При новом существенном условии уточни только затронутый выбор.
После любого выбора проверь покрытие требований, зависимости сценариев
и достижимость нужных продуктовых показателей выбранного состава.
Если выбранный набор исключает требование или необходимую зависимость,
объясни последствие и уточни, пересматривает ли человек исходное требование.
До разрешения расхождения постановка не готова.

В `board-groom` выбор сценариев и дальнейшие вопросы предшествуют подготовке
задач. Выбор сценариев не подтверждает применение подготовленных задач;
для этого требуется отдельное решение по показанным задачам и их снимку.

## 4. Раскрой и зафиксируй дерево решений

Для каждого сценария и их совместной работы раскопай полное дерево решений
в пределах задачи. Начни с условий запуска, действий, результата и продуктовых
показателей, по которым оценивается польза и качество фичи. Для каждого
показателя определи нужный уровень, условия оценки и источник требования.
Учитывай функциональные и нефункциональные ограничения: например, успешность
выполнения пользовательской задачи, полноту и точность результата,
время выполнения, надёжность, удобство использования
и стоимость операции, если они значимы для этой фичи. Используй измеримую
величину или проверяемый признак качества. Неизвестный показатель, целевой
уровень или допустимый компромисс выясни по материалам и с человеком;
собственное предположение не считай согласованным требованием.

Для каждого решения определи допустимые варианты и вопросы, которые
открывает каждый из них. Проверь существенные ошибки,
граничные условия, повторные действия, прерывание и восстановление, права
и взаимодействие с другими частями системы там, где они влияют на результат.

До выбора сценариев раскрой последствия, способные изменить их пользу,
выполнимость или состав. После выбора углубляй все применимые ветки.
Проверь общие ограничения фичи и взаимодействие сценариев: совместную
нагрузку, конкуренцию за ресурсы, суммарную стоимость и другие значимые
показатели. Успех каждого сценария отдельно не доказывает успех их сочетания.
Отвергнутую ветку сохрани с причиной исключения; если выбор пересмотрен,
верни её в разбор. Разные ветки могут зависеть от одного решения: укажи
общую зависимость вместо повторного вопроса.

После каждого ответа разбери дочерние вопросы. Например, выбор
«перезаписывать CSV» требует проверить сохранность прежнего файла при
прерывании записи и повтор после ошибки.

Фиксируй дерево в файле записи в разделе «Дерево решений» по форме
[decision-tree.md](decision-tree.md). Сохраняй связь сценария, родительского
решения, условия ветки и зависимых вопросов. `taskctl` хранит вопросы и
ответы в «Развилках»; карту зависимостей обновляй после ответов и находок сам.

Продолжай углубление, пока остаются неразобранные риски недостижения нужных
продуктовых показателей, включая функциональные и нефункциональные
ограничения. Для каждого риска запиши затронутый показатель, условие
возникновения, ожидаемое ухудшение и решения, от которых оно зависит.
Проверяй риск по фактам и условиям использования. Например, правильный
экспорт может выполняться слишком долго: исследуй объём данных, время
ожидания, отзывчивость интерфейса, отмену и повтор запуска.

Число вопросов и уровней дерева не является критерием полноты.
Для конечного пути определи условия, наблюдаемый результат, нужные уровни
показателей и способы проверки. Решение по риску обоснуй фактами, расчётом
или пробой в соответствующих условиях. Необходимую проверку выполни в
доступных пределах либо оставь исследование незавершённым. План теста после
реализации не разрешает неизвестный риск на этапе постановки.
Оставить деталь исполнителю можно, задав границы выбора, в которых
сохраняются нужные продуктовые показатели и ограничения. Запиши эти
границы, обоснование и рекомендацию. Передача вопроса исполнителю сама
по себе не доказывает, что ветка разобрана.

Начни с решения, сильнее всего влияющего на объём и другие ветки, затем иди
вглубь одной применимой ветки до выполнения этих критериев. Покажи краткую
карту в начале; перед вопросом называй текущую ветку и оставшийся пробел.
Стыки, влияющие на продуктовые показатели, исследуй в соответствующей ветке.
После предметных решений разбирай ранг и организационный состав работ.

Зависимый вопрос задавай после ответа на предыдущий. Одновременно можно
задать до четырёх независимых вопросов текущей темы.

Для каждого нерешённого вопроса, включая уже записанные с
`решает: человек`, последовательно примени следующие условия:

1. Если ответ прямо задан человеком или следует из принятого решения,
   используй его с указанием источника. Повторно этот выбор не спрашивай,
   но проверь его последствия для продуктовых показателей и дочерних решений.
2. Если выбор меняет поведение, заметное пользователю, действия человека,
   целевые продуктовые показатели, допустимые компромиссы между ними,
   другие задачи или общие правила процесса, решает человек. Дай
   рекомендацию с доводом и допустимые варианты.
3. Если вопрос касается внутренней реализации, есть одна обоснованная
   рекомендация и выполнены критерии передачи выше, передай его исполнителю.
   При неизвестном влиянии на показатели продолжай исследование. При равно
   обоснованных вариантах спроси человека с доводом равенства через `--tie`.

Для новой внутренней развилки используй `decide --ask ... --who исполнитель`
с рекомендацией. Уже открытую человеческую развилку передай командой:

```sh
taskctl decide <ID> "<имя>" --leave --by агент "<довод передачи исполнителю>"
```

Строкой `решено человеком` фиксируй только полученный ответ человека.
Переходи к следующей ветке
после проверки полноты текущей, включая переданные исполнителю вопросы.

## 5. Сохрани вопрос и обработай ответ

Для обычной развилки используй команды ниже. Для выбора сценариев используй
`scenarios.md`, включая ключ показанного снимка при сохранении ответа.
Тексты в угловых скобках замени данными текущего вопроса.

Сохрани человеческий вопрос до того, как задашь его:

```sh
taskctl decide <ID> --ask "<имя>" --hint "<рекомендация и довод>" --option "<другой допустимый вариант>" "<вопрос>"
```

При равных доводах вместо `--hint` используй `--tie "<довод равенства>"` и
перечисли варианты. Для вопроса из обхода добавь источник по `research.md`.
Если имя занято, выбери другое имя. Пересмотр существующего решения сохраняй
под той же развилкой по процедуре `taskctl decide` из `tools/taskctl/README.md`.
Для архивной записи заведи новую запись.

Покажи вопросы текущей темы командой `taskctl decide <ID> "<имя>" --chat`.
Для пачки используй `taskctl decide <ID> --chat`, только если вывод содержит
выбранные независимые вопросы одной темы и их не больше четырёх.

Если команда напечатала блок, передай его в реплику знак в знак, без
ограждения кода. Сохрани нумерацию вариантов, имя развилки и хвост
«ответ строкой:». Если команда предписывает диалог выбора, используй его
с теми же вариантами.

Полученный ответ передай команде дословно:

```sh
taskctl decide <ID> --answer "<ответ человека>"
```

Свободный ответ, который команда не разобрала, сопоставь с открытым вопросом
по смыслу и сохрани:

```sh
taskctl decide <ID> "<имя>" --by человек "<ответ и довод человека>"
```

Если ответ неоднозначен, уточни его. Просьбу «оставь исполнителю» запиши
через `--leave`; ответственность за решение меняется, требования к глубине
разбора сохраняются. Встречный вопрос или возражение разбери как новый вопрос;
если он меняет сценарии, вернись к затронутой части шага 3. Изменение
показателей или условий оценки требует пересмотра затронутых веток шага 4,
даже если состав сценариев остался прежним.
Сохранённые ответы учти в соответствующих разделах постановки и при
подготовке задач.

## 6. Продолжи или заверши интервью

После ответа обнови дерево по шагу 4. При изменении родительского решения
сверь всех затронутых потомков, включая решённые вопросы, отметь требующие
пересмотра и исследуй новые применимые ветки. Если ответ расходится с фактом,
покажи факт, влияние на продуктовые показатели и рекомендацию. Повторный
ответ сохрани, но проверь совместимость выбора с нужными уровнями показателей.
Если они недостижимы, выясни, меняется ли решение или само требование.
Согласие с вариантом не означает согласия на неизвестное ухудшение.
До разрешения противоречия ветка остаётся незавершённой. При завершении
темы переходи к следующей.

Если ответ ещё не получен, сохрани вопрос открытым. Продолжай только работу,
которая от него не зависит. При разборе записи и постановке цели остановись
на вопросе до ответа. В LLD можно продолжить документ с явно названным
допущением, решение остаётся на согласование. При нарезке можно продолжить
другие задачи, сохранив ограничение старта затронутой задачи.
Третий раз неотвеченный вопрос не повторяй. `board-groom` откладывает запись
через `draft defer`; цель и LLD фиксируют допущение. Допущение не закрывает
человеческий вопрос и не разрешает зависимую работу. Ожидание, откладывание
и прекращение работы по решению человека фиксируй отдельно от завершённого
интервью; они не означают, что риски разобраны и постановка готова.

Завершай интервью, когда выполнены все условия:

- Все человеческие вопросы решены либо обоснованно переданы исполнителю
  по шагу 4.
- Требования покрыты сценариями; состав имеет записанное основание.
  Предположения, влияющие на поведение, объём или продуктовые показатели,
  разрешены.
- Для сценариев и их совместной работы определены значимые продуктовые показатели,
  нужные уровни, функциональные и нефункциональные ограничения, условия
  проверки. Источники требований и принятые компромиссы записаны.
- Дерево сохранено. Все применимые конечные пути отвечают критериям шага 4,
  исключённые ветки имеют причину. Нет неизвестных значимых показателей
  или нужных уровней, непроверенного влияния решений и неразобранных рисков
  недостижения этих уровней.
- Для каждого выявленного риска записаны решение, основания достижимости
  нужного уровня и способ проверки. Пометок «требует исследования» или
  «требует сверки» в применимых ветках не осталось. Передача исполнителю,
  рекомендация и план будущего теста сами по себе этот критерий не выполняют.
- Решения отражены в постановке, зависимые решения сверены. Для деталей,
  оставленных исполнителю, записаны границы выбора и их обоснование.

Сверь открытый остаток командой `taskctl decide <ID> --open`. Если вопросов
нет, но критерии полноты не выполнены, добавь недостающий вопрос и вернись
к шагу 4. При нехватке фактов или доступа зафиксируй пробел и затронутые
ветки; интервью остаётся незавершённым. При продолжении начни с шага 1.
