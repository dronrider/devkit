# вход README

Жанр первой страницы: человек, который про инструмент ничего не знает, должен
за один экран понять, зачем инструмент нужен, и запустить его. Фрагменты взяты
из первого коммита devkit (11 июля 2026, `7ccc03f8`), написанного пользователем
до того, как за тексты проекта взялись агенты. Этот же коммит служил
человеческим ориентиром в замере цели DK-446.

Что тут ловится. Первый абзац отвечает на «зачем», а не на «как устроено».
Команда идёт раньше объяснения. Условие, при котором инструмент не нужен,
сказано прямо и в самом начале. Абзацы короткие, по одной мысли, и ни один не
кончается обобщением.

## 1
источник: devkit, README.md первого коммита
роль: пользователь

Один репозиторий на все проекты: правила работы с ассистентом, система
приоритизации задач и инструменты доски. Клонируется рядом с проектами:

```bash
git clone https://github.com/dronrider/devkit.git ~/projects/devkit
```

Проект подключает правила импортом в своём `CLAUDE.md`:

```markdown
@../devkit/RULES.md
```

Импорт это локальный путь, поэтому devkit должен лежать в соседней с проектом
директории. Если файла нет, агент по строке-подсказке в проектном `CLAUDE.md`
клонирует devkit сам.

## 2
источник: devkit, RULES.md первого коммита
роль: пользователь

Файл живёт в репозитории `devkit`, который клонируется рядом с проектами
(`~/projects/devkit`). Проект подключает правила импортом `@../devkit/RULES.md`
в своём `CLAUDE.md` и дописывает проектные особенности снизу.

Правила универсальны и не зависят от того, где хостится репозиторий (GitHub,
GitLab, что-то ещё). Специфика конкретного окружения в devkit не коммитится, а
живёт в локальных дополнениях.

## 3
источник: devkit, RULES.md первого коммита
роль: пользователь

Доска ведётся в проектах, у которых нет внешнего трекера. Если у проекта
трекер есть (это фиксируется в проектном `CLAUDE.md` или в локальных
дополнениях), доска не нужна: задачи живут в трекере. Проверять это перед тем,
как заводить или обновлять доску.

## 4
источник: devkit, RULES.md первого коммита
роль: пользователь

Статусы в TASKS.md: `Backlog`, `In progress`, `Check`, `Blocked`. Файл держать
сгруппированным по статусу, чтобы бэклог и текущая работа читались с одного
взгляда. `Check` это контроль человеком: работа сделана, но задачу закрывает не
агент, а пользователь после проверки по приложенному сценарию. В архив уезжает
только прошедшее проверку, не прошедшее возвращается в In progress. Живой файл
тогда не пухнет, его размер привязан к объёму открытой работы, а не ко всему
сделанному. Архив append-only, растёт свободно.

## 5
источник: devkit, RULES.md первого коммита
роль: пользователь

`docs/tasks/<ID>.md`, имя по чистому ID, чтобы ссылка строилась не глядя
(заголовок и так в первой строке файла). Заводится, когда появляется
содержимое (разбор корня, DoD, сценарий проверки, ход работы): однострочному
бэклогу файл не нужен, LLD-задачи ссылаются прямо на LLD без файла-прокладки.
Метаданные (тип, приоритет, ранг, статус) живут только в доске и в файле не
дублируются.
