# Отчёт о проверке правил

Этот файл читается при каждом ревью. Отчёт отделяет пропуск проверки от
обоснованного вывода и связывает доказательства с версией кода и правил.

## Создать и проверить отчёт

```sh
taskctl -C /дерево review audit <ID> --base <база>
```

Базу первого прохода укажи явно. Для ветки это коммит, от которого оценивается
изменение относительно целевой ветки; база должна охватывать весь предмет
ревью. Не выбирай последний коммит только ради уменьшения диффа.

Команда создаёт JSON со снимком кода, источниками и полным перечнем правил.
У задачи доски путь `docs/tasks/<ID>.review-audit.json`. Без доски файл лежит
в `.devkit/review-audits/`, имя выводится из хеша ярлыка ревью; точный путь
печатает команда. Существующий отчёт не перезаписывается обычным вызовом.

Заполни архитектурную оценку, затем разбери каждую строку правил и внеси
доказательства. Перед чистым вердиктом выполни:

```sh
taskctl -C /дерево review audit-check <ID>
taskctl -C /дерево review clean <ID> "что проверено"
```

`audit-check` проверяет отчёт без записи вердикта. `clean` выполняет ту же
проверку до записи в файл задачи или git-заметку. Апрув чужого MR через
`approve-mr` также требует завершённого отчёта. Ворота `shipctl push
--check-only` проверяют его для отправляемой версии, `shipctl merge` до и
после ребейза; штатные исключения автономного пуша и прямого разрешения
пользователя сохраняются. Разрешения на публикацию и
апрув остаются по `foreign.md`; наличие отчёта их не заменяет.

## Источники и идентификаторы

В обязательный общий набор входят `RULES.architecture.md`, `RULES.style.md`
и раздел «Тесты обязательны» файла `RULES.md` из чекаута devkit. Общие правила
имеют постоянные идентификаторы `ARCH-NNN`, `STYLE-NNN`, `TEST-NNN`.
В JSON к ним добавлено имя источника, например
`common-architecture:ARCH-001`. При перестановке правил их номера сохраняются.

Проектный набор берётся из `docs/ARCHITECTURE.md` и `docs/STYLEGUIDE.md`
проверяемого репозитория. В перечень входят пункты, абзацы и заголовки,
в том числе без явного ID: заголовок тоже может содержать требование.
Для таких блоков команда строит ID из имени источника и хеша нормализованного
текста, например `project-architecture:block-<хеш>`. При изменении текста
такого блока меняется ID. Повторения одинакового блока различаются суффиксом
`:2`, `:3` и далее. Проектные правила со своими ID сохраняют их при
правке формулировки; содержимое всё равно проверяется по хешу источника.

Если документ содержит описание, а не требование, объясни это в результате
его блока. Нельзя вычеркнуть блок из отчёта только потому, что он кажется
ненужным. Дополнительные стандарты по ссылкам из `AGENTS.md` и проектных
документов подключи до создания отчёта в `.devkit/review.conf`:

```ini
rule_sources = docs/SECURITY.md, docs/RULES.extra.md
```

Это список путей относительно корня проекта через запятую. Абсолютные пути,
`..`, повторения и отсутствующие объявленные файлы отклоняются. Их правила
входят в тот же обязательный перечень под источником
`project-extra:<путь>`. Требования самой задачи и инструкции `AGENTS.md`
тоже проверяются и отражаются в выводах. Машинная полнота ограничена
каноническими источниками и этим явным списком; она не доказывает, что
ревьювер нашёл все ссылки на дополнительные стандарты.

Отсутствие проектного документа отмечается в `sources` как `absent`.
Это отсутствие источника, а не доказательство отсутствия проектных
ограничений. Укажи пробел в итоговом отчёте. Недоступный обязательный общий
источник не даёт завершить проверку. Если без отсутствующего правила нельзя
судить решение, оставь оценку незавершённой и выясни требование.

Поля версии, SHA, хешей, источников и списка правил заполняет команда.
Не переписывай их для обхода устаревания и не удаляй строки. Проверка заново
читает файлы источников и сравнивает их с перечнем в отчёте.

## Архитектурная оценка

В объекте `architecture` заполняются:

- `goal`: какой пользовательский результат требуется;
- `decision`: какое решение предложено и какой путь даёт результат;
- `boundaries`: ответственность частей, владельцы данных и жизненный цикл;
- `alternative`: более простой вариант или объяснение, почему упрощать
  нечего в границах изменения;
- `justification`: почему выбранный вариант подходит с учётом требований,
  ограничений и согласованных решений;
- `evidence`: конкретные места кода, требования, прогоны и наблюдения,
  на которых основана оценка;
- `result`: `pending`, `checked` или `violated`.

Сначала оценка остаётся `pending`. `checked` означает, что решение проверено
и обосновано. `violated` означает найденный архитектурный дефект; он описывается
замечанием. И незавершённая проверка `pending`, и найденное нарушение
`violated` исключают чистый вердикт. Аккуратная реализация и зелёные тесты
не меняют этот результат автоматически.

В `goal` укажи результат для потребителя, в `decision` опиши предложенный
механизм. В `justification` раздели обязательный контракт, записанное
ограничение и вариант из постановки. Совпадение с вариантом не снимает
архитектурного вопроса. Например, обязательный тип, полностью определённый
источником, требует объяснения своей пользы. Явная проверка типа по контракту
внешнего потребителя может быть обоснованной; её основание нужно назвать.

Для применимых правил о конфигурации и данных внеси в `evidence`:

- какой выбор доступен и какой результат он меняет;
- откуда известен перечень допустимых полей, какие из них требуют правки кода;
- кто использует загруженные данные и какие вызовы остаются без выбранной опции;
- что является ограничением протокола, безопасности или доменной модели.

Проверяй конкретный путь, например экспорт только профиля без счётчиков.
Если он всё равно требует хранилище счётчиков, назови вызов, отсутствие
потребителя и последствие отказа этого хранилища. Наличие значения в модели
не означает разрешения выгружать его; проверь публичную проекцию и контракт.

## Результат по правилу

Каждая строка `rules` уже содержит `id`, `source` и `text`. Ревьювер заполняет
`applicability`, `result`, `reason` и `evidence`.

| Состояние проверки | applicability | result | Что записать |
|---|---|---|---|
| Ещё не разобрано | `pending` | `pending` | Что мешает определить применимость |
| Применимо, не проверено | `applicable` | `pending` | Какие проверки ещё нужны |
| Применимо, проверено | `applicable` | `checked` | Обоснование и доказательства по объектам |
| Найдено нарушение | `applicable` | `violated` | Условие, последствие, места и замечание |
| Неприменимо | `not_applicable` | `checked` | Конкретная причина неприменимости |

Перед завершением отчёта сверь `result` с `reason`, доказательствами и
замечаниями. Для `violated` назови установленное требование и факт его
нарушения. Если допустимый диапазон настройки неизвестен, принятие значений
0 или -3 само по себе не доказывает нарушение диапазона. Недостающий критерий
запиши как `pending`, когда без него проверку нельзя завершить. Пробел
документации оцени отдельно по правилу, которое требует описать настройку.

В `reason` нужен вывод по данному правилу. «Проверено», «всё хорошо»,
«не касается правки» без разбора не подтверждают результат. Для неприменимости
назови, какое условие правила отсутствует и по чему это установлено.

Каждый элемент `evidence` содержит `object`, `location`, `observation`:
объект проверки, место и наблюдение. Например, для лишней настройки объектом
будет конкретный ключ, местами будут его разбор и потребитель, наблюдением
будет зависимость допустимого значения от другого ключа. Файл целиком без
названия объекта и результата чтения не заменяет доказательство.

Не ставь один результат по правилу после проверки единственного объекта,
если изменены несколько. Перечисли все затронутые объекты и доказательства
для них. Для общего механизма можно объединить наблюдение, если из записи
видно, какие объекты проходят через него. Для каждого исключения нужны
условия, которые действительно действуют в этом коде.

Допустимое исключение внутри самого правила проверяется как применимое
правило: назови условие исключения и подтверждение. Согласованное отступление
дополнительно ссылается на записанное решение. Наличие исключения нельзя
выдать за неприменимость или за разрешение нового отступления без основания.

## Новый проход и ограничения проверки

Если изменился код, база или источники правил, создай новый снимок:

```sh
taskctl -C /дерево review audit <ID> --refresh
```

`--refresh` сохраняет предыдущий отчёт резервной копией рядом и сбрасывает
выводы. Без `--base` сохраняется прежняя база; смена базы задаётся явно.
Старые доказательства используются только после проверки, что они относятся
к новой версии. Повторные проходы не ограничены числом или бюджетом.
Если код прежний, но изменились постановка или стандарты, после обновления
и проверки отчёта запиши новый вердикт через `review clean <ID> --new-round`.
Этот флаг разрешает новый проход, но не отменяет проверку актуальности аудита.

Успешный `audit-check` означает, что перечень полный, отчёт актуален и
обязательные поля заполнены допустимыми состояниями. Машина не доказывает,
что наблюдение истинно, все объекты найдены и неприменимость обоснована.
Это проверяется чтением доказательств и поведенческими сценариями ревью.
Формально заполненный отчёт с неверными выводами остаётся плохим ревью.
