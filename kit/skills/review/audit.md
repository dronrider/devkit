# Отчёт о проверке правил

## Создать и проверить отчёт

```sh
taskctl -C /дерево review audit <ID> --base <база>
```

Для ревью вне доски передай файл исходной постановки через
`--request /путь/к/REQUEST.md` при создании аудита. В ссылке `task:N`
укажи номер строки исходного файла вместо N. Если файл переместился,
передай его новый путь в `audit-progress --request` и `audit-check --request`.
Если изменилось содержимое, обнови аудит через `--refresh`.

База должна охватывать всю правку относительно целевой ветки. Команда
создаёт снимок кода, источников и правил. Путь печатает команда:
`docs/tasks/<ID>.review-audit.json` для задачи доски, иначе файл в
`.devkit/review-audits/`. Сверь `sources` с выбранным комплектом правил.
Версию, SHA, хеши, источники и тексты правил заполняет команда.
Для `STYLE-001`, `STYLE-015` и `ARCH-018` команда заполняет `files` из
Git-диффа, а для Go дополнительно подбирает `targets`. Список путей в
`files` и элементы `targets` не меняй. Дополнительный объект добавь
одинаковым ключом в `objects` правила и `files.objects` его файла;
проверки запиши в `evidence`.

После записи итога сверь снимок, доказательства и ссылки на замечания.
Для полного аудита исправляй указанные пробелы и повторяй сверку.
В отчёте по сценариям укажи открытые области и результат команды.

```sh
taskctl -C /дерево review audit-check <ID> --coverage /путь/к/итогу.md
```

Для структурированных записей возьми заготовки из `taskctl`, например
`taskctl review audit-template ARCH-016 --object файл:строка`.
Для одной записи задай `--check` и `--result`. Вставь заполненные
записи в `evidence` нужного правила. Для `STYLE-001` передай их через
`audit-record` по [формату записи имени](naming-audit.md).

Для чистого вердикта дополнительно выполни:

```sh
taskctl -C /дерево review audit-check <ID>
taskctl -C /дерево review clean <ID> "что проверено"
```

`audit-check` проверяет снимок и заполненность. `clean` проверяет их
перед записью вердикта. `approve-mr` также требует завершённого отчёта.

## Источники и идентификаторы

Прочитай `RULES.architecture.md`, `RULES.style.md` и раздел «Тесты
обязательны» в `RULES.md`. Прочитай проектные `docs/ARCHITECTURE.md`
и `docs/STYLEGUIDE.md`. Проверь применимость правил из обоих наборов.
Дополнительные стандарты из `AGENTS.md` и проектных документов укажи
перед созданием отчёта в `.devkit/review.conf`, например
`rule_sources = docs/SECURITY.md, docs/RULES.extra.md`. Пути относительные
от корня, через запятую. Дубликаты, `..` и отсутствующие объявленные файлы
отклоняются. Требования задачи и `AGENTS.md` тоже отражай в выводах.

ID общего правила содержит имя источника и постоянный номер, например
`common-architecture:ARCH-001`. Проектные заголовки, абзацы и пункты без ID
получают ID по хешу текста, повторы различаются суффиксом. Дополнительные
источники имеют префикс `project-extra:<путь>`. Если блок содержит только
описание, обоснуй это в его строке. Перечень правил сохраняется целиком.

Отсутствующий проектный документ отмечается в `sources` как `absent`.
Назови пробел в итоге. Оставь связанную проверку открытой, если без этого
источника нельзя сделать вывод. Обязательные общие источники нужны для
завершения аудита.

## Требования задачи

В отчёте выпиши отдельной строкой каждое требование из постановки и
DoD. Если требование повторяется, сведи повторы и укажи оба источника.
Для каждой строки запиши ссылку на требование, ожидаемый и фактический
результат, место в коде или другом артефакте, результат проверки и статус.
Для требования к поведению укажи штатный вход или условие выполнения.
Для требования к документации, тестам или настройке укажи проверенный
файл, команду или наблюдение. Ставь `checked` после сверки, `violated`
при расхождении или `pending` с указанием недостающих данных.

При расхождении укажи, какое требование и на каком входе нарушено,
ожидаемый и фактический результат и последствие. Перенеси этот вывод
в замечание. Для нового поведения, настройки или ограничения внешнего
контракта найди основание в постановке или согласованном решении.
Если основания нет, укажи, кто увидит изменение и на каком входе,
и вынеси вопрос о его включении в задачу.

## Архитектурная оценка

В `architecture` заполни `goal` (результат для пользователя), `decision`
(выбранный механизм), `boundaries` (ответственность и жизненный цикл
данных), `alternative` (более простой вариант или причина его отсутствия),
`justification` (почему механизм нужен с учётом обязательного контракта)
и `evidence` (места и факты). Для совместимости запиши сохраняемое
поведение на базе и его потребителя. Сверь его на вершине.

В `result` поставь `checked` после оценки, `violated` при доказанном
дефекте или `pending`, если не хватает факта или требования. Для последних
двух статусов запиши дефект или открытый вопрос в `reason`. Перед итоговой
сверкой укажи в `heading` точный заголовок замечания или вопроса в Markdown.
Сверь архитектурный вывод вместе с остальным отчётом. Чистый вердикт
требует `checked`.

## Объекты проверки

Сверь перечень изменённых файлов, например
`git diff --name-status -M <база> <вершина>`, и содержательный дифф.
Для удаления и переноса открой объект на базе. В рабочем дереве учти
относящиеся к задаче незакоммиченные и новые файлы.

В `files` по каждому пути заполни `objects` теми же ключами, что и в
списке объектов правила. Если в файле нет подходящего объекта, укажи
конкретное основание в `reason`. Для удалённого кода сверяйся с базой.
Для любого языка найди затронутые имена и операции с БД по коду. Если
вывод по объекту пока невозможен, добавь его в список и запиши `pending`.
Если проверку оставляешь `pending` из-за отсутствующего файла, запиши `missing_file`
с точным путём `path` от корня Git и `revision` (`base` или `head`).
Команда сверит путь в дереве соответствующего SHA ревью. Для `head`
также открой относящиеся к задаче файлы рабочего дерева, если они есть.

При полной проверке покрытия сверь каждый объект из `targets`. По `STYLE-001`
это добавленные, переименованные и изменённые функции Go вне сгенерированного
кода. По `ARCH-018` это кандидаты с параметром-коллекцией и вызовом
драйвера напрямую или через помощник. Команда ищет их и вне диффа по именам
вызовов из изменённых функций. Установи по коду, какая реализация вызывается.
Если кандидат не обращается к БД или не выполняется на затронутом пути,
запиши `not_applicable` во всех трёх подпроверках и укажи место, которое
это подтверждает. В `applicability` правила с `targets` укажи `applicable`.

Веди список по штатным сценариям. Записывай входы, вызовы, реализации,
потребителей, побочные эффекты и тесты по мере чтения цепочки. Для
каждого объекта отмечай применимые правила. Варианты, у которых вывод
различается, записывай отдельно. Например, пакетная операция в одном
адаптере и поштучная в другом требуют двух выводов.

## Разбор объектов по правилам

Открой разделы по затронутым объектам. Для настроек и форматов смотри
«Конфигурация и контракт», для SQL и репозиториев «Данные и запросы»,
для новых модулей и вызовов «Модули и ход операции». Изменённые объявления,
отказы и описания разбирай по «Имена, ошибки и описания», а тесты,
фикстуры и команды запуска по «Тесты и проверка исправлений».
Для остальных правил бери критерий из источника.

### Конфигурация и контракт

- **`ARCH-022`, действие настройки.** Проследи допустимое значение от
  чтения до результата. Если конфиг выбирает поля из уже загруженных
  данных, а код ограничивает выбор списком, возьми одно имеющееся поле
  вне списка, если такое есть. Укажи место загрузки, настройку, фактический
  результат и пункт контракта, по которому поле разрешено или исключено.
  Для разрешённого контрактом поля потребность в правке кода означает
  нарушение. Если контракт молчит, запиши проверенный факт и вопрос по
  `ARCH-005`. Новый вид источника оцени отдельно. Для списка вариантов
  проверь один отклоняемый вариант. Явный список рабочих данных проверь
  по `ARCH-023`.
- **`ARCH-023`, новый или изменённый ключ.** Для каждого ключа проверь
  поведение (`behavior`) и основание выбора (`basis`). Для списка возьми
  новый элемент рабочих данных. Покажи результат со старым конфигом и
  после добавления элемента, затем проверь выключенный и отсутствующий
  элемент. Укажи, когда правка конфига вступит в силу. Для производного
  значения проверь удаление ключа и попытку указать другое значение.
  Найди требование или ограничение доступа, которое обосновывает выбор.
  Для списка процитируй согласованное требование именно для нового
  включённого элемента вне конфига. В записи `basis` укажи `list_decision`
  `automatic` для автоматического включения или `explicit` для явного
  допуска. Если источник лишь допускает выбор или предлагает вариант
  реализации, ищи принятое решение отдельно. Если его нет, укажи
  `undecided`, поставь `basis: pending` и вынеси в итог вопрос, должен ли
  элемент появляться без правки конфига.
- **`ARCH-024` и `ARCH-025`, источник, применение или доставка.** Укажи,
  кто меняет значение, где оно хранится и когда должно вступать в силу.
  Сверь тип, умолчание, приоритет источников и действующее значение.
  Укажи, когда нужны правка файла, перезапуск или пересборка.
- **`ARCH-005`, контракт операции или поля.** На каждом входе, который
  меняет результат, сверь объявленную форму (`schema`), выданное значение
  или отказ (`output`) и ожидание потребителя (`consumer`). Используй
  один объект для трёх записей. Проверь тип, пустое значение, отсутствие
  поля и явный `null`. Для обязательного поля проверь, какое значение
  удовлетворяет контракту. Для конфигурируемого результата проверь
  разрешённые поля или правило отбора. Сравни операции с тем же
  предметным смыслом на одном пограничном входе. Если они расходятся и
  контракт молчит, запиши `consumer: pending` с конкретным вопросом.
- **`ARCH-007`, существующие потребители.** Сверь формы, которые они
  принимают. При пробеле назови конкретного потребителя и форму.
  Ожидание потребителя запиши в `ARCH-005 / consumer`.

### Данные и запросы

- **`ARCH-015`, изменённая выборка.** Покажи, где потребитель использует
  проекцию, строки и соединения (`usage`). Для `ORDER BY` покажи
  потребителя порядка или сравни результат после перестановки строк
  (`order`). Если сортировки нет, отметь `order: not_applicable` со
  ссылкой на запрос. Для сужения выборки назови сохраняемый результат.
- **`ARCH-016`, несколько обращений к БД.** Проследи запросы операции
  целиком. Добавь в `objects` строку вызова каждого чтения. Для того
  же вызова проверь два входа: с использованием результата
  (`with_consumer`) и без него (`without_consumer`). При нескольких
  вариантах конфигурации возьми минимальный допустимый вход, которому
  результат чтения не нужен. Проверь его, даже если код сейчас читает
  данные безусловно. Проследи использование результата и преобразований
  до ответа, а отказ чтения до его последствия для операции.
  Если входа без потребителя нет, укажи `not_applicable` и покажи,
  где контракт или код делает использование результата обязательным.
  Если данных для вывода мало, укажи `pending` и конкретный вопрос.
  При лишнем чтении предложи проверку нуля вызовов и штатного результата.
- **`ARCH-018`, чтение коллекции.** Проследи штатный вход до конкретной
  реализации. Измерь обращения этой операции к хранилищу для одного
  ключа, двух разных ключей и повтора, если такие входы допустимы.
  Сверь число обращений и возвращённые записи. Для аудита заполни
  [достижимость входа и замер](query-audit.md).
- **`ARCH-017`, атомарность.** Назови инвариант и механизм защиты.
  Для нескольких чтений сверь требование согласованного снимка с кодом.
- **`ARCH-019`, граница доступа к данным и параметры запроса.** Найди
  потребителя данных и место принятия предметного решения. Для SQL сверь
  значения отбора с их источниками. Если меняется привязка параметров,
  проверь порядок фактических аргументов на каждом затронутом адаптере.
  Для предложенного исправления проверь его в отдельной копии по
  [протоколу проверки запроса](query-audit.md).

### Модули и ход операции

- **`ARCH-001`, новая ответственность.** Покажи, кто
  координирует вызовы, преобразует формат, получает данные, выполняет
  бизнес-правила и побочные эффекты. На конкретном изменении предметного
  правила назови затронутые модули и причину.
- **`ARCH-003`, переиспользование.** Перечисли новые и изменённые
  вспомогательные операции в затронутых модулях. Для каждой покажи
  реализацию, места вызова, доменные типы и правила либо отсутствие
  таких зависимостей. Для общего кода проверь существующие модули.
  Для предметного кода назови функции с общей задачей и покажи, где
  проходит граница с вызывающим кодом. Запиши решение о размещении
  для каждой операции и одно изменение, которое проверяет эту границу.
- **`STYLE-009` и `STYLE-011`, ход операции.** Определи варианты точек
  входа с учётом конфигурации и прочих условий. Для каждого проследи
  цепочку вызовов до результата и отказов. Для каждого вызова укажи
  первый потребитель прочитанных, вычисленных или изменённых данных
  либо объясни, почему значение остаётся неиспользованным. Назови
  необходимый побочный эффект и какие вызовы прекращаются при отказе.
  Если варианты передают результат или ошибку через общие переменные,
  покажи их путь до возврата. Проверь, можно ли вернуть результат
  раньше, сохранив порядок действий, причину ошибки и публичный код.
  Запиши цепочку по каждому варианту в `STYLE-011`.

### Имена, ошибки и описания

- **`STYLE-001`, имя соответствует назначению.** На проверяемом пути
  открой определение изменённого объекта и место использования. Коротко
  опиши его назначение по коду. Прочитай слова имени как фразу и сопоставь
  её с этим описанием. Для функции проверь, что получает вызывающий код
  и какие данные меняются. При расхождении укажи слово, фактическое
  поведение и строки, где виден результат. Применяй ту же проверку к
  именам модулей, типов, параметров и переменных, включая объекты,
  назначение которых изменилось при прежнем имени.
  Для сплошной проверки и формата доказательств открой
  [пообъектный аудит имён](naming-audit.md).

- **`ARCH-014`, `STYLE-013` и `STYLE-014`, изменённый отказ.** Для каждого
  вызова из цепочки `STYLE-011`, отказ которого меняет ответ или прерывает
  выполнение, запиши отдельный объект `ARCH-014` по строке вызова.
  Покажи, какая операция упала, где присвоена первая классификация,
  что означает её код и что получил вызывающий. Сверь смысл первого
  кода с упавшей операцией, даже если внешний слой меняет код. Отдельно
  проследи цепочку причины и формирование текста. Проверь, не попадает
  ли причина в сообщение дважды через текст и вложенную ошибку.
  При недоступной границе назови открытый вопрос.
- **`STYLE-015`, комментарии к изменённому коду.** Проверь каждый
  добавленный или изменённый блок и сохранившиеся комментарии к
  изменённому поведению. Для Go команда включает в `targets` изменённые
  блоки и комментарии к изменённым функциям, включая блоки внутри них.
  Найди комментарии о том же поведении у вызывающих функций и
  потребителей даже вне диффа. Для других языков найди блоки по `files`.
  Добавь найденные блоки в `objects`. Самостоятельные директивы сборки,
  генерации и линтера пропускай.

  На каждый блок запиши одно `evidence`. В `object` укажи его
  `файл:строка` из `targets` или начало найденного блока. Возьми заготовку
  через `taskctl -C /дерево review audit-template STYLE-015 --object файл:строка`.
  Заполни по одному выводу на каждый фрагмент, сохрани порядок и `quote`.
  При нарушении укажи в `comment_quote` фрагмент, о котором пишешь в итоге.

  Для каждого утверждения во фрагменте укажи конкретный вход и проследи
  цепочку вызовов до места, где формируется результат, выбирается
  источник или возникает побочный эффект. Укажи это место в `location`.
  Для `checked` выпиши в `value` выражение или идентификатор из этой
  строки, который подтверждает утверждение. В `text` опиши вход и
  фактическое поведение. Если комментарий прямо называет источник,
  например `table.field` или `table_name`, запиши вход в `case`,
  строку чтения в `via` и использование значения в `location`.
  Если утверждение выполняется только при определённом условии,
  проверь, указано ли оно в комментарии.
  Если комментарий обещает сохранение поведения, сравни прежний и
  текущий путь вызова. Для утверждения только о типе аргумента или
  результата можно сослаться на сигнатуру и указать точное имя типа в `value`.

  Поставь фрагменту `checked`, если подтвердил все его утверждения,
  `violated`, если нашёл контрпример или подтвердил пересказ либо
  дублирование. Если для вывода не хватает данных, поставь `pending`,
  назови недостающий факт в `text` и перенеси его в итоговый отчёт.
  Поставь блоку `violated`, если нарушен хотя бы один фрагмент, иначе
  `pending` при открытой проверке и `checked` при всех `checked`.
  В `observation` запиши вывод блока, в `location` укажи его основание
  в коде. Для пересказа укажи повторённую
  операцию, для дублирования процитируй второй комментарий и проверь,
  добавляет ли он условие для своего читателя. При `checked` назови
  причину, ограничение или условие и подтверждающую строку кода. Для
  `violated` и `pending` укажи
  в `heading` раздел итога с цитатой или вопросом и ссылкой на комментарий.
- **`STYLE-016`, изменённое поведение или его описание.**
  Начни с комментария к изменившемуся объекту, затем открой описание у
  потребителя и пример в документации, даже если они вне диффа. Ищи по
  имени объекта, параметру или ключу конфигурации. Сверь утверждение о
  входе, результате, особом случае или побочном эффекте с поведением на
  том же входе. Для каждого утверждения или примера запиши точную
  цитату и строку кода, по которой проверено поведение.

### Тесты и проверка исправлений

- **`TEST-003`, изменение поведения.** Покажи тест логики и тест стыка.
  Для перенесённого, изменённого или удалённого утверждения сравни базу и
  вершину. Укажи, где оно теперь проверяется и какой командой.
- **`TEST-003` и `TEST-005`, конечный артефакт.** Назови
  свойство, которое должно сохраниться до потребителя. Возьми вход,
  на котором сериализация, упаковка или другое преобразование может его
  нарушить. Получи артефакт через штатный путь и проверь свойство в том
  виде, в котором его получает потребитель. Если чтение скрывает потерю
  данных, проверь и выданное представление. Если штатный запуск недоступен, проверь доступный
  участок штатным кодом и укажи, какую часть осталось подтвердить в приёмке.
- **`TEST-005`, поведение зависимости.** Если вывод зависит от
  поведения парсера, сериализатора или другой зависимости, проверь спорный
  вход с используемой в проекте версией и рабочим кодом вызова. Сравни
  фактический результат с ожиданием по контракту. Запиши вход и результат
  и при подтверждении дефекта, и когда проверка сняла подозрение.
- **`TEST-003` и `TEST-005`, изменение существующих тестов.** По диффу выдели
  удалённые или отключённые тесты, ослабленные утверждения и пороги,
  обновлённые эталоны и изменения отбора в командах запуска или CI.
  Назови поломку, которую ловила прежняя проверка. Покажи, где и какой
  командой она ловится теперь, либо укажи изменение контракта или
  измерение, обосновывающее новую проверку. Если поломка теперь проходит
  и основание отсутствует, вынеси это в замечание.
- **`TEST-004`, тест, команда или общая фикстура.** Назови тест, команду
  и условие отбора. Проследи реальные зависимости через фикстуры. Для
  каждого затронутого варианта сборки сверь исключение интеграционного
  теста из юнитов и отбор отдельной интеграционной командой.
- **`TEST-005`, тест или проверяемое поведение.** Назови конкретное
  утверждение со строкой, границу наблюдения и дефект, при котором тест упадёт
  (`strength`). Для каждого изменённого свойства найди утверждения на
  других уровнях. Сопоставь входы, команды, фактические зависимости
  и общую поломку (`overlap`). Укажи дополнительную гарантию каждого
  теста и где оставить общую проверку. Если пары на другом уровне нет,
  покажи место поиска. Повторы на одном уровне запиши отдельно. Сравни
  исходники даже при недоступном стенде, выполненные команды укажи отдельно.

Проверяй побочный эффект на границе, где он происходит. При отказе до
записи проверь отсутствие записи. Если контракт задаёт вид ошибки,
сверь ошибку у потребителя с исходной причиной.

## Результат по правилу

Заполни `applicability`, `result`, `reason` и `evidence` каждой строки.

| Состояние | applicability | result | Основание |
|---|---|---|---|
| Применимость открыта | `pending` | `pending` | Что нужно установить |
| Применимо, проверка открыта | `applicable` | `pending` | Недостающий вход, код или контракт |
| Проверка завершена | `applicable` | `checked` | Факты и вывод по каждому объекту |
| Найдено нарушение | `applicable` | `violated` | Требование, расхождение и последствие |
| Неприменимо | `not_applicable` | `checked` | Какого условия правила нет и по чему это видно |

Для открытого общего или проектного правила укажи причину в `reason`.
Запиши в `evidence` недостающий факт с результатом `pending` и заголовком
раздела итога, где описан открытый вопрос.

Если диапазон настройки неизвестен, назови недостающий критерий в
`pending`. Отсутствие описания проверь по правилу о контракте.
Исключение внутри правила разбери как применимое правило и покажи
его условие. Для согласованного отступления укажи записанное решение.

## Доказательства по парам

Один элемент `evidence` относится к одному символу, блоку комментариев,
операции или сценарию.
В `object` укажи его имя из перечня, в `location` места в коде, тесте или
контракте, в `observation` проверенный факт и вывод по правилу. Один факт
можно использовать для нескольких выводов. Например, «`createInvoice`
обещает создать счёт. Вызывающий получает PDF уже рассчитанного счёта и
передаёт файл в архив. Имя `createInvoiceFile` отражает результат».

Заполни `objects` для правил с подпроверками, `ARCH-022` и правил из
таблицы ниже. На объект и каждый ключ из `checks` запиши одно `evidence`
с тем же `object` и ключом в `check`. Для правил без `checks` запиши по
одному `evidence` на объект.

В `facts` ключи обозначают роль доказательства. Значение каждого ключа
представляет список записей с `location` и `text`. Укажи строки как
`файл:строка`, для базы как `base@файл:строка`. В `text` запиши факт
этой роли. Для открытой записи заполни `facts.question` со строкой
проверенного кода и перенеси текст вопроса в раздел из `heading`.
Для `ARCH-014` также заполни `origin`.

| Правило и подпроверка | Ключи `facts` |
|---|---|
| `ARCH-023 / behavior` | `input`, `before`, `after`, `activation`. Укажи `kind: list`, `option` или `derived`. Для `list` добавь `disabled`, `absent`. Для `derived` добавь `derive` с цитатой определения, `omitted` и `incompatible`. В `value` запиши соответственно производное значение, исход удаления и другое проверенное значение. |
| `ARCH-023 / basis`, `ARCH-005 / consumer` | `contract` с точной `quote`. Сошлись на базу, согласованную постановку (`task:номер`) или внешний контракт по HTTPS. Для задачи доски номера берутся из текста без служебных разделов. Для `derived` с `basis: checked` добавь `necessity` с цитатой согласованного требования обязательности именно этого ключа. |
| `ARCH-005 / schema`, `output`, `consumer` | Укажи одинаковый `case` в `schema`, `input`, `output` и `contract` либо `question`. В `schema` процитируй объявление и перечисли `forms`, в `output` запиши одну фактическую форму. При расхождении отметь нарушение либо запиши `exception` с тем же `case`, формой, цитатой исключения, ссылкой на объявление в `related` и явной отсылкой из объявления в `value`. Если есть вторая операция с тем же предметным смыслом, добавь `compare` с тем же `case`, её результатом в `value` и `verdict: same` или `different`. Для `different` нужен вывод о нарушении либо вопрос потребителю по тому же входу. |
| `ARCH-003` | Одна операция на объект. Укажи `symbol`, `implementation` с цитатой объявления, `caller` со строками использования, `dependency` с `verdict: domain` или `shared`, `change` и `placement` с модулем в `value`. Если вызовов не нашёл, укажи `caller.verdict: searched` и место поиска. |
| `ARCH-015 / usage`, `order` | `query` и `consumer` для использования данных. `order` и `effect` для сортировки. |
| `ARCH-016 / with_consumer`, `without_consumer` | В `read_scenario` укажи конкретный `input`, его строку `input_at`, строку чтения `call_at`, ссылки `consumers`, числа вызовов `observed` и `expected`, исход при сбое `failure` и строку `failure_at`. Для входа без потребителя укажи пустой `consumers` и `expected: 0`. Для `not_applicable` достаточно входа и ссылки на обязательного потребителя. |
| `ARCH-019 / parameters` | По одному `filter` на каждое вхождение значения отбора. Для литерала запиши точную строку SQL в `location`, сам литерал в `quote` и `sql_literal.source` как `constant`, `fixed` или `pending`. Для первых двух запиши строку источника в `related` и её цитату со значением в `sql_literal.source_quote`. Для `constant` запиши имя нового параметра в `parameter`, укажи `binding_change: true` и заполни `proposed_binding`. Для `fixed` сошлись на схему SQL, документ контракта или `task:номер`, а в `text` укажи, где искал константу. |
| `ARCH-019 / binding` | Запиши `sql`, `input` и по одному `argument` на аргумент с соответствующим параметром SQL в `related`. |
| `ARCH-019 / proposed_binding` | В `sql_proposal` запиши полный `sql` с пометками `{{позиция:имя}}`, `style` (`positional`, `numbered` или `sqlite` для сочетания `?N` и `?`), `arguments` (`parameter` и `value` либо `ids`), `expected` (`id` и `rows`), `evidence` (`location` и `text`). Для `checked` укажи имя JSON в `probe_file`. Положи его в соседний с аудитом каталог `<имя-аудита>.bindings` и запиши `code_hash` из аудита, `object` и `location` из записи, `command` пробы, фактический `sql` и массив `arguments` в порядке драйвера. ID запиши строками. Если драйвер получает массив ID в одном аргументе, сохрани его в одной позиции. |
| `STYLE-011` | `entry`, `condition`, упорядоченные `step`, `outcome`, `control`, `return_value`, `return_error`. В двух записях о возврате назови значение или исход отказа в `value`. Для `step` запиши `failure: true`, если отказ влияет на дальнейшее выполнение или ответ, иначе `false`. Для каждого шага запиши `use` со строкой шага в `related`, значением в `value` и `verdict: used`, `unused` или `effect`. |
| `ARCH-014` | `origin`, `classification`, `classification_definition`, `boundary`, `cause`, `message`. В `object` запиши строку вызова из `origin` и `step`. Для классификации процитируй присвоение и определение, укажи идентификатор в `value`, вывод `match`, `mismatch` или `forwarded` в `verdict`. При `forwarded` процитируй источник и передачу ошибки. В `boundary.value` запиши код или исход. Для `cause` укажи `preserved`, `lost` или `absent`, для `message` укажи `once` или `repeated`. |
| `STYLE-015` | Заполни `claim` по фрагментам из снимка или шаблона. Для `checked` запиши `purpose`. Для `violated` укажи `kind: contradiction`, `restatement` или `repeat` и одноимённый факт. Для `repeat` процитируй второй комментарий в `quote`. Для блока `pending` запиши открытый вопрос в `facts.question`. |
| `STYLE-016` | `statement` с точной `quote` и `implementation` для фактического поведения. |
| `TEST-004` | `test`, `dependency`, `unit_selection`, `integration_selection`. Для отсутствующей команды укажи проверенную строку сборки и результат поиска. |
| `TEST-005 / strength` | `assertion` с `quote`, `boundary`, `failure_case`. |
| `TEST-005 / overlap` | В `first` и `second` укажи `quote` утверждения и строку объявления теста в `related`. Для утверждения во вспомогательной функции запиши её объявление в `via`. Для пары добавь `first_input`, `second_input`, `first_command`, `second_command`, `common_failure`, `guarantees`. Укажи зависимости и уровень в `first_level` и `second_level`, значение `unit`, `component`, `integration` или `system` запиши в `value`. Для пары разных уровней используй `kind: cross_level`. Для `pair` одного уровня и `single` добавь `search` со строкой поиска и другим уровнем в `value`. |

Поставь записи `checked`, `violated`, `pending` или `not_applicable`.
Для неприменимой подпроверки назови отсутствующее условие и место, по
которому это видно. Для открытой укажи недостающий код, вход или контракт.
Нарушение даёт правилу `violated`. При отсутствии нарушений открытая запись
даёт `pending`. Укажи оставшиеся открытые проверки в `reason`.

Перед итогом сверь перечень объектов и сценариев с доказательствами.
Групповое описание реализации оставляет проверку конкретного объекта
открытой. Каждую отдельную причину нарушения и открытый вопрос, от
которого зависит вывод по требованию или правилу, перенеси в итог.
В `heading` укажи точный заголовок Markdown со знаками `###` для
соответствующего замечания или вопроса. Общую причину
из нескольких правил опиши один раз со ссылками на все правила.
Для каждого `violated` или `pending` по объекту из `targets` включи
в соответствующий раздел итога ссылку `файл:строка` из его `location`.

## Новый проход и ограничения проверки

При изменении кода, базы или правил вызови
`taskctl -C /дерево review audit <ID> --refresh`. Команда сохраняет прежний
отчёт резервной копией и сбрасывает выводы. Без `--base` база сохраняется.
Переноси доказательства после сверки с новой версией. Если SHA прежний,
а постановка или правила изменились, после проверки обновлённого аудита
используй `review clean <ID> --new-round`.

`--coverage` пересобирает `files` и `targets`, сверяет подпроверки объектов,
статусы и ссылки на итог. Для чистого вердикта все применимые подпроверки
должны быть закрыты. Ревьювер дополняет перечень объектами, которые выявил
при разборе, и обосновывает выводы.
