# Образцы к скиллу review

Файл читается по надобности: раздел «Ревью» целиком перед первым ревью
задачи доски, реплики перед первым комментарием человеку, конфиг перед
настройкой проекта.

Каждому вердикту ниже предшествует заполненный отчёт по `audit.md`.
`review audit <ID> --base <база>` создаёт перечень правил и архитектурную
оценку, `review audit-check <ID>` проверяет полноту перед `review clean`.
Примеры краткого вердикта не заменяют доказательства в JSON-отчёте.

## Раздел «Ревью» целиком

Задача DK-1, первый проход и проверка исправлений. Строку уровня пишет
`taskctl review level`, замечания `review add`, исходы `review resolve`,
вердикты `review clean`.

```
## Ревью

Уровень 2 до a1b2c3d: риск пропуска ворот слияния, проверка разбора раздела и живого пути.

- блокирует: shipctl merge не видит раздел «Ревью» за ограждённым блоком,
  проверить на docs/tasks/DK-338.md. Исправлено.
- не блокирует: имя флага --at читается как время, а не как sha. Отклонено:
  флаг назван по образцу taskctl stage --at, менять один в паре хуже.
- ревью: перенос строки в README поправил сам, коммит b2c3d4e.
- Вердикт: без замечаний до e4f5a6b. fixed 1 сверено прогоном
  readiness_test.go, rejected 2 принято. Прогнано: shipctl ready на DK-338 и
  на болванке без раздела.
```

Первая строка отчёта ревьювера к такому разделу: «вернуть: 1» при обнаружении
проблемы, «принято» после проверки исправления. Чистый вердикт пишет
`review clean` с новым sha: «Вердикт: без замечаний до
e4f5a6b. fixed 1-3 сверены».

Влияние на принятие пишется словом в начале строки замечания:

```
taskctl review add DK-1 "блокирует: shipctl merge не видит раздел «Ревью» за ограждённым блоком, проверить на docs/tasks/DK-338.md"
taskctl review add DK-1 "не блокирует: имя флага --at читается как время, а не как sha"
```

## Файл замечаний чужого ревью

Журнал ревью чужого MR лежит рядом с файлом задачи, в
`docs/tasks/<ID>.review.md`. Шапку заполняет первый `review draft` по файлу
задачи, блоки копятся вызовами `draft`, состояние правят `approve`, `drop` и
`publish`. Ручная правка допустима: порядок полей свободный, номера в
заголовках блоков держит утилита.

```
# Замечания ревью DK-1

- MR: https://gitlab.example.com/group/proj/-/merge_requests/42
- ревью до: a1b2c3d
- уровень: 2
- пометка: автор ответил

## Замечание 1

- файл: tools/shipctl/ops.go
- строка: 214
- метка: issue
- состояние: опубликовано, тред 7f21c8a

Ворота слияния не видят раздел «Ревью» за ограждённым блоком: раздел с
примером вывода команды проходит как пустой.

## Замечание 2

- метка: suggestion (non-blocking)
- состояние: черновик

Имя флага --at читается как время, а не как sha.

## Замечание 3

- метка: итог
- состояние: снято, не публикуется

Прогнал живой путь по DoD и тесты тронутых пакетов. Не смог проверить выкат:
доступа к стенду нет. Открытым остался вопрос про повторный запуск миграции,
жду ответа автора в треде замечания 1.
```

Блок с меткой «итог» это отчёт владельцу строки. Автору MR он не адресован.
`publish` его пропускает и ставит состояние «снято» с припиской «не
публикуется», в трекер он не уходит ни при каком значении ключа `publish`.
Уровень и sha в нём не повторяются, они стоят в шапке файла.

Строку «пометка» ведёт опрос тредов, и её же печатает `taskctl list` под
строкой доски: «автор ответил», «автор молчит с 2026-09-02», «апрув
поставлен», «MR слит без апрува ревью», «MR закрыт». Приписка в состоянии
блока стоит там же, где id треда: судьба MR снимает опубликованные блоки
скопом, а тред в чужом MR не трогает.

## Замечание человеку: было и стало

Живой случай про `request_id`. Слева то, что модель написала сама, справа то
же замечание после проверки по разделу «Обоснованность замечаний».

Было:

```
suggestion (non-blocking): Обогащённый логгер можно положить в контекст
рядом с id и брать его в хендлерах.
```

Автор прочитал это и спросил «как?». Места нет, вызова нет, и зачем это ему
тоже нет.

Стало:

```
issue: В хендлерах берётся пакетный логгер, и request_id в запись не
попадает. По логам не собрать цепочку одного запроса, и разбор инцидента
упирается в ручную склейку по времени. Положи логгер с id в контекст там же,
где кладётся сам id (middleware/request.go:41), а в хендлере бери его оттуда:

log := logger.FromContext(ctx)

Правка стоит одной строки на хендлер, а поддержка перестаёт платить часами
дежурного за каждый разбор.
```

Добавились чем это грозит, конкретное место и вызов вместо намёка, пример
кода одной строкой (столько пропускают правила проекта про короткое тело
треда) и цена для бизнеса.

## Конфиг ревью целиком

Образец `.devkit/review.conf` с комментариями, он же лежит в самом devkit.

```
# пути для внимания к последствиям изменения
critical_paths = tools/shipctl tools/taskctl hooks
# метки тредов человеку
labels = issue, suggestion (non-blocking)
# проектные вопросы, применяются по смыслу изменения
checks = новых пакетов npm без согласования не берём
# ревью чужой задачи: публикация замечаний в MR и апрув
# confirm ждёт слова человека, auto одобряет черновики сам
publish = confirm
# пауза между публикациями тредов, секунды вилкой
pause = 20-60
# шаг опроса тредов тиком сторожка и порог молчания автора
poll = 5m
silence = 1d
# писать ли время этапа «ревью» в чужой тикет при закрытии строки
worklog = off
```

## Живые реплики

Как пишет пользователь devkit. Копируется длина и регистр, символы и
эмоции нет.

- Замечание: «Давай сократи описание MR. Суть же простая». «Опять вижу
  определения со словом "нитка", не надо так». «Удаление ветки после
  вливания не сработает, запрещено в гитлабе, так что убери».
- Вопрос: «А зачем указывать путь к папке, если шара уже есть?». «А почему
  smoke сам не запустил?». «Так если запуск в докере это обходит, то зачем
  такая защита?».
- Отказ: «Не надо. Я уже внёс из чата той задачи». «Согласен, что это
  отдельная фича. Нужно завести задачу в бэклог». «Закрываем, если что
  всплывёт, поправим отдельно».
- Несогласие: «Не, так не пойдёт. Мне нужна одна команда для обновления».
  «Нет, остановись и сначала ответь, почему так».
- Подтверждение: «Согласен, заводи». «Принято». «Закрывай, если что
  переоткроем». «Пункт 7 понял, берём твой вариант. По пункту 8 тоже
  согласен».
- Правка ревьювером: «нашёл мелкий косяк, поправил сам». Ответ автора на
  блокирующее: «Согласен, косяк. Исправил». Или короче: «Готово».

## Как выбрать проверки

Локальная правка текста ошибки. Прочитай дифф и место формирования ответа,
проверь, что код ошибки и формат ответа не изменились. Подходящий тест на
текущем SHA можно взять из CI. Проверка миграций к этой правке не относится.

Маленький дифф в миграции данных. Проследи преобразование и потребителей
схемы, проверь повторный запуск и отказ между шагами на копии данных.
Назови способ отката или согласованную необратимость. Размер диффа не
сокращает эти проверки.

Исправление замечания меняет общий помощник. Начни с нового диффа и исходного
замечания, затем проверь остальные вызовы помощника и тесты его контракта.
Предыдущий чистый прогон не подтверждает новую реализацию. Если после этой
проверки пришла ещё одна правка, проверь её без ограничения числа кругов.
