# Образцы к скиллу review

Файл читается по надобности: раздел «Ревью» целиком перед первым ревью
задачи доски, реплики перед первым комментарием человеку, конфиг перед
правкой бюджетов.

## Раздел «Ревью» целиком

Задача DK-1, второй уровень, два круга. Строку уровня пишет
`taskctl review level`, замечания `review add`, исходы `review resolve`,
вердикты `review clean`.

```
## Ревью

Уровень 2 до a1b2c3d: неопределённость 1, тронут tools/shipctl.

- блокирует: shipctl merge не видит раздел «Ревью» за ограждённым блоком,
  проверить на docs/tasks/DK-338.md. Исправлено.
- не блокирует: имя флага --at читается как время, а не как sha. Отклонено:
  флаг назван по образцу taskctl stage --at, менять один в паре хуже.
- ревью: перенос строки в README поправил сам, коммит b2c3d4e.

Круг 2 до e4f5a6b: fixed 1 сверено прогоном readiness_test.go, rejected 2
принято. Прогнано: shipctl ready на DK-338 и на болванке без раздела.
```

Первая строка отчёта ревьювера к такому разделу: «вернуть: 1» на первом
круге, «принято» на втором. Последняя строка: «ходов 41». Чистый вердикт
второго круга пишет `review clean` с новым sha: «круг 2 до e4f5a6b: fixed 1-3
сверены».

Ярус пишется словом в начале строки замечания:

```
taskctl review add DK-1 "блокирует: shipctl merge не видит раздел «Ревью» за ограждённым блоком, проверить на docs/tasks/DK-338.md"
taskctl review add DK-1 "не блокирует: имя флага --at читается как время, а не как sha"
```

## Файл замечаний чужого ревью

Журнал ревью чужого MR лежит рядом с файлом задачи, в
`docs/tasks/<ID>.review.md`. Шапку заполняет первый `review draft` по файлу
задачи, блоки копятся вызовами `draft`, состояние правят `approve`, `drop` и
`publish`. Ручная правка допустима: порядок полей свободный, номера в
заголовках блоков держит утилита.

```
# Замечания ревью DK-1

- MR: https://gitlab.example.com/group/proj/-/merge_requests/42
- ревью до: a1b2c3d
- уровень: 2
- пометка: автор ответил

## Замечание 1

- файл: tools/shipctl/ops.go
- строка: 214
- метка: issue
- состояние: опубликовано, тред 7f21c8a

Ворота слияния не видят раздел «Ревью» за ограждённым блоком: раздел с
примером вывода команды проходит как пустой.

## Замечание 2

- метка: suggestion (non-blocking)
- состояние: черновик

Имя флага --at читается как время, а не как sha.

## Замечание 3

- метка: итог
- состояние: снято, тред 9c02b41, MR закрыт

Уровень 2: прогнан живой путь по DoD и тесты тронутых пакетов, дифф прочитан
по составу.
```

Строку «пометка» ведёт опрос тредов, и её же печатает `taskctl list` под
строкой доски: «автор ответил», «автор молчит с 2026-09-02», «апрув
поставлен», «MR слит без апрува ревью», «MR закрыт». Приписка в состоянии
блока стоит там же, где id треда: судьба MR снимает опубликованные блоки
скопом, а тред в чужом MR не трогает.

## Конфиг ревью целиком

Образец `.devkit/review.conf` с комментариями, он же лежит в самом devkit.

```
# бюджет первого круга по уровням: минуты активной работы и ходы
level1 = 5 минут, 20 ходов
level2 = 20 минут, 70 ходов
level3 = 40 минут, 100 ходов
# доля бюджета на второй круг и потолок кругов
retry = 1/3
rounds = 2
# критичные пути проекта, совпадение файла диффа даёт «да» в триаже
critical_paths = tools/shipctl tools/taskctl hooks
# метки тредов человеку
labels = issue, suggestion (non-blocking)
# проектные вопросы, уровень и текст, продолжают перечень своего уровня
checks = 2: новых пакетов npm без согласования не берём
# ревью чужой задачи: публикация замечаний в MR и апрув
# confirm ждёт слова человека, auto одобряет черновики сам
publish = confirm
# пауза между публикациями тредов, секунды вилкой
pause = 20-60
# шаг опроса тредов тиком сторожка и порог молчания автора
poll = 5m
silence = 1d
# писать ли время этапа «ревью» в чужой тикет при закрытии строки
worklog = off
```

## Живые реплики

Как пишет пользователь devkit. Копируется длина и регистр, символы и
эмоции нет.

- Замечание: «Давай сократи описание MR. Суть же простая». «Опять вижу
  определения со словом "нитка", не надо так». «Удаление ветки после
  вливания не сработает, запрещено в гитлабе, так что убери».
- Вопрос: «А зачем указывать путь к папке, если шара уже есть?». «А почему
  smoke сам не запустил?». «Так если запуск в докере это обходит, то зачем
  такая защита?».
- Отказ: «Не надо. Я уже внёс из чата той задачи». «Согласен, что это
  отдельная фича. Нужно завести задачу в бэклог». «Закрываем, если что
  всплывёт, поправим отдельно».
- Несогласие: «Не, так не пойдёт. Мне нужна одна команда для обновления».
  «Нет, остановись и сначала ответь, почему так».
- Подтверждение: «Согласен, заводи». «Принято». «Закрывай, если что
  переоткроем». «Пункт 7 понял, берём твой вариант. По пункту 8 тоже
  согласен».
- Правка ревьювером: «нашёл мелкий косяк, поправил сам». Ответ автора на
  блокирующее: «Согласен, косяк. Исправил». Или короче: «Готово».

## Что показал корпус devkit

Цифры, на которых стоят правила скилла, по 280 ревью и 508 лентам
ревьюверов до скилла и десяти кругам первой ночи по нему.

- 19 из 30 вторых кругов случились из-за одного-двух замечаний, среди них
  номер шага в сценарии и вёрстка одного комментария. Дорог круг.
- Исполнитель отчитывался чужим прогоном четырёхминутной давности, поймал
  это только второй круг. Отсюда «исправлено» не принимается текстом.
- Правка «ровно процитированной строки» ломала одиннадцать соседних
  вызовов. Отсюда «править по смыслу».
- Тринадцать замечаний за четыре захода это проектирование перепиской, стоп
  должен был случиться на втором круге. Отсюда потолок в два круга.
- За ночь по скиллу дифф и show взяли 37% результатов инструментов, чтение
  кусками внахлёст ещё 34%. Отсюда дифф в файл и срезы.
- Один ревьювер на пять задач дорос до 352k контекста против 20k у
  свежего. Отсюда свежий ревьювер на каждую задачу и круг.

## Порядок чужого ревью целиком

Восемь шагов от строки до архива. Первые четыре ведёт ревьювер, дальше строку
ведёт тик сторожка, а ревьювер возвращается на втором круге.

1. `trackctl review AB-123` заводит строку на боковой доске и тянет в файл
   задачи постановку тикета со ссылкой на MR.
2. `taskctl review level <ID> 2 "причина"`, дальше живой путь и дифф по
   своему уровню.
3. Замечания блоками: `taskctl review draft <ID> --file <путь> --line <N>
   --label issue "текст"`, итог уровня с `--label итог`.
4. `taskctl review publish <ID>` несёт одобренное в MR и вписывает id тредов.
   При `publish = confirm` перед этим вопрос человеку последней репликой хода
   и парковка «ждёт подтверждения».
5. `taskctl move <ID> blocked --reason "автор: ждёт ответа в тредах MR"`. Ход
   на этом кончается.
6. Тик `devkitctl watch` опрашивает треды шагом `poll`. Реплика автора, резолв
   треда и новый коммит в ветке MR снимают парковку, ставят пометку «автор
   ответил» и заказывают второй круг: живой сессии задачи репликой в её окно,
   а без неё подъёмом новой. Молчание дольше `silence` это одно уведомление
   человеку.
7. Второй круг сверяет каждое исправление с диффом. Отказ автора на
   блокирующее это одно возражение фактом, дальше `taskctl move <ID> blocked
   --reason "спор: ..."` и зов человека. Апрув `taskctl review approve-mr
   <ID>`, при `confirm` с `--yes` после слова человека.
8. Слитый или закрытый MR тик видит сам: строка уходит в архив с пометкой,
   открытые блоки снимаются припиской, а с `worklog = on` время этапа «ревью»
   уезжает в чужой тикет через `trackctl submit --log-only`.

Дифф читается не всегда. Функционал, очевидный по своей сути и покрытый
тестами (эндпойнт, куда добавили параметр), первый уровень проверяет
вопросами. Слова «хорошо покрыт» сами по себе утверждение, и первый уровень
проверяет его.
