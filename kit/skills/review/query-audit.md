# Проверка запросов по ARCH-018 и ARCH-019

- **`ARCH-018`, запросы для коллекции.** Для каждой операции укажи
  конкретный метод адаптера. В `objects` и `object` используй ссылку
  `файл:строка` на его объявление. Проверяй реализации отдельно, включая
  код вне диффа.
  - **Число запросов (`calls`).** Начни с объявления этого метода.
    Для каждого перехода укажи строку вызова и объявление функции,
    которая действительно вызывается. Дойди до строки обращения к
    драйверу. Укажи, повторяется ли вызов из-за цикла на любом шаге
    цепочки, и по какой коллекции идёт цикл. Посчитай обращения на
    успешном пути для одного ключа, двух разных ключей и повтора,
    если эти входы допустимы. Если цепочка выполняет запрос в цикле
    и штатный вход допускает два разных ключа, запусти проверяемый
    метод с ключами из `inputs` и запиши обращения на границе драйвера.
    Для сложной цепочки также измерь число обращений. Если обязательный
    замер недоступен, сохрани подсчёт по коду, поставь `pending` и
    вынеси вопрос из `facts.question` в итог.
  - **Достижимость (`inputs`).** Приведи конкретный штатный вход со
    значениями параметров. Покажи, почему он проходит валидацию,
    какие записи выбираются, где удаляются повторы и какие два разных
    ключа получает проверяемый адаптер. Дай ссылку на каждый переход.
    Если два ключа исключены, покажи ограничение для каждого связанного
    входа.
    Открой каждый вход, перечисленный для операции в `query_entries`.
    В `query_inputs.entries` укажи `entry` (строка объявления),
    `call_at` (строка вызова из перечня `calls`) и `observation`
    (как вход связан с операцией). Для связанного входа поставь
    `result: inspected` и укажи в `validation_at` строку проверки
    или формирования входа. Если она в помощнике, укажи также
    `validation_call_at` и `validator` (строку объявления помощника).
    Для несвязанного входа поставь `result: unrelated` и объясни связь
    вызова с другой операцией.

    При `pending` заполни `query_inputs.gap`. В `last_at` укажи
    последний проверенный переход. В `kind` укажи `missing_file`,
    `contract` или `chain`. Для `missing_file` заполни одноимённое
    поле записи с путём и ревизией. В `question` запиши конкретный
    недостающий факт и перенеси вопрос в раздел из `heading`.
  - **Пакетирование (`batch`).** Сопоставь число обращений с допустимым
    входом. Если запрос выполняется на каждый ключ, укажи ограничение,
    которое оправдывает поштучное выполнение. При отсутствии такого
    ограничения отметь нарушение, предложи пакетную операцию и укажи,
    как проверить число обращений и сохранение результата по каждому
    ключу. Если `calls` или `inputs` остаётся открытой, оставь открытой
    и эту проверку.

  Для завершённых записей `ARCH-018` используй следующие поля.

  - `query_calls` в `calls` содержит `paths` и числовые `one`, `two`,
    `repeat`. В каждом пути `steps` перечисляет переходы от `object`:
    `at` для строки вызова, `to` для объявления вызываемого метода,
    `receiver_at` для объявления помощника, если метод вызван на
    возвращаемом им объекте. `driver_at` указывает на последний вызов
    драйвера внутри последнего метода. Для подсчёта по простому циклу
    укажи `keys_param` (параметр метода-объекта) и `loop_at` в пути.
    Для Go команда проверяет цепочку и цикл по синтаксису. Для остальных
    языков она сверяет ссылки и счётчики, а ревьювер доказывает ход вызовов.
    Заготовку для цикла выведи через `taskctl review audit-template
    ARCH-018 --check calls --kind loop --object файл:строка`.
    Запиши замер в JSON-файл в каталоге `<имя-аудита>.queries` рядом
    с аудитом. Укажи имя в `probe.file`. В файл запиши `code_hash` из
    аудита, `object`, `command` и `runs`. В каждом запуске укажи `case`
    (`one`, `two`, `repeat`), `ids` на входе адаптера и массив `calls`
    с одним `driver_at` на каждое зафиксированное обращение.
  - `query_inputs` в `inputs` содержит массивы ключей на входе в метод
    `one`, `two`, `repeat` и ссылки `locations` на валидацию и отбор.
    Для двух ID заполни `two_scenario`: `entry`, `parameters` (имена и
    значения), `validation`, `selection`, `adapter` (факты с `location`,
    `quote` и `text`), `ids` (та же пара, что в `two`). Если два
    ключа исключены, опусти `two` и заполни `two_limits` с `entry` и
    фактом `condition` для каждого связанного входа. В `repeat` запиши ключи,
    которые доходят до метода при повторе. Опусти случай, если он
    неприменим, и объясни причину в `observation`.
  - Если `two` или `repeat` отсутствует в `query_inputs`, опусти и
    соответствующий счётчик в `query_calls`. Если на двух ключах
    обращений больше, чем на одном, для `batch: checked` запиши
    основание в `query_justification`.

- **`ARCH-019`, граница доступа к данным и параметры SQL.** Укажи в
  перечне операции и конкретные запросы по адаптерам.
  - **Границы (`boundaries`).** Если правка меняет получение данных или
    обработку результата, покажи на конкретной операции, где выполняются
    SQL и преобразование строк и где принимается бизнес-решение. Укажи
    код обеих сторон. Отметь нарушение, если детали хранения попали в
    бизнес-сценарий или адаптер принимает предметное решение, не связанное
    с хранением.
  - **Параметры отбора (`parameters`).** В каждом добавленном или
    изменённом запросе перечисли значения отбора. Для каждого укажи SQL
    и источник значения. Для каждого литерала найди в коде константу
    того же назначения. Если нашёл, процитируй её объявление, поставь
    `parameters: violated` и укажи имя нового параметра. Специализация
    запроса не отменяет передачу такой константы параметром. Если
    константы нет, укажи, где искал, и приведи строку схемы или контракта,
    которая задаёт фиксированное значение. При нехватке доказательств
    оставь вопрос в итоге и отметь проверку привязки как `pending`.
    В `parameters` укажи
    `binding_change: true`, если исправление меняет состав или порядок
    аргументов, иначе `false`. Для заменяемого литерала запиши имя
    предлагаемого параметра в `facts.filter.parameter`. При изменении
    привязки укажи `kind: collection`, если запрос принимает список ID,
    даже если добавляются только скалярные параметры. Для запроса без
    списка укажи `scalar`.
  - **Привязка аргументов (`binding`).** Если меняются параметры запроса
    или их передача, сверь итоговый SQL с фактическими аргументами для
    каждого затронутого адаптера. Если передаётся список ID, возьми два
    разных ID вместе со скалярными параметрами, если они есть. Покажи,
    какое значение получает каждый параметр и какие строки должны вернуться.
  - **Привязка предлагаемого запроса (`proposed_binding`).** При
    `binding_change: true` заполни отдельную запись для того же запроса
    и адаптера. Внеси предложение во временную копию. Если привязка
    генерируется, выполни штатную генерацию проекта. Вызови изменённый
    метод и запиши SQL и аргументы, полученные драйвером. Для списка
    передай два разных ID и все скалярные параметры, укажи ожидаемые
    строки для каждого ID. Ставь `checked` после сверки фактического
    порядка с плейсхолдерами. Если проба недоступна, поставь `pending`
    и укажи в итоге, что осталось проверить. Если привязка остаётся
    прежней, укажи `not_applicable` и основание.
