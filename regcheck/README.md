# regcheck: краснота регрессионного теста

Механизация правила из RULES.md («Тесты обязательны»): регрессионный тест
должен падать на старом коде и проходить на исправленном, иначе он не ловит
регрессию и покрытием не считается. Проверять это руками (временно вернуть
баг, прогнать, откатить) долго и никто не проверяет; утилита делает то же
самое без единой правки рабочего дерева.

Как устроена проверка:

1. команда теста гоняется в рабочем дереве, обязана пройти;
2. в временный `git worktree` выкладывается старый код (база), поверх него
   из рабочего дерева переносятся только тестовые файлы;
3. команда гоняется там и обязана упасть; worktree убирается в любом исходе.

Сборка в PATH, как у taskctl:

```
cd ~/projects/devkit/regcheck && go build -o ~/go/bin/regcheck .
```

## Запуск

```
regcheck [-C dir] [--base ref] [--tests f1,f2] [--inline f1,f2] -- <команда теста ...>
```

Типовые случаи:

```
# правка и тест ещё не закоммичены: база выбирается сама (HEAD)
regcheck -- go test ./... -run TestBoardMove

# правка закоммичена на фичеветке: старый код живёт в main
regcheck --base main -- python3 -m pytest tests/test_ops.py
```

Тестовые файлы ищутся сами среди изменённых относительно базы (`*_test.*`,
`test_*`, `*.spec.*`, каталоги `tests/`, `testdata/` и подобные); если
автопоиск промахнулся, файлы перечисляются флагом `--tests` через запятую.

Выход 0 значит регрессия закрыта. Выход 1 с объяснением: тест красный на
текущем коде (сначала чинить), тест зелёный на старом (не ловит регрессию),
тестов относительно базы не нашлось.

## Инлайновые тесты (правка и тест в одном файле)

Когда тест живёт в том же файле, что и правка (инлайновые тесты Rust
`#[cfg(test)] mod tests { ... }` и подобное), файл целиком на старый код не
перенести: он утащит с собой и исправление. Такие файлы перечисляются флагом
`--inline` через запятую, на базу переносится не файл целиком, а только его
тестовый регион, остальное остаётся базовым (возможно, багованным):

```
regcheck --inline src/lib.rs -- cargo test
```

Границы региона ищутся автоматически: сначала явные маркеры
`regcheck:test-begin` / `regcheck:test-end` (комментарий любого синтаксиса,
работают для любого языка), если их нет, то единственный блок Rust
`#[cfg(test)] mod ... { ... }` по совпадению фигурных скобок. Если в базовой
версии тестового региона ещё не было (тест целиком новый), он просто
дописывается в конец базового файла; если регион уже был, новый заменяет
его целиком.

Найти регион однозначно получается не всегда, и тут инструмент не гадает, а
падает с объяснением: несколько блоков `#[cfg(test)]` в файле, маркер без
пары, несбалансированные скобки (эвристика не разбирает строки и
комментарии, поэтому фигурная скобка внутри строкового литерала её собьёт),
и во всех этих случаях нужны явные маркеры `regcheck:test-begin/end` вокруг
тестовой части. Файл без тестового региона вообще (ни маркеров, ни
`#[cfg(test)]`) через `--inline` не проверить: отделить тест от правки
нечем.

Каждый прогон оставляет строку в журнале `.devkit/log` репозитория (время,
код выхода), когда директория `.devkit` заведена: по этому журналу
`shipctl merge` подсказывает при слиянии bug-задачи без зелёного прогона.

## Ограничения

- Worktree это чистая копия базы: тест, которому нужны несобранные артефакты
  или зависимости из рабочего дерева (`node_modules` и подобное), в нём
  упадёт не из-за бага. Такой тест сначала сделать самодостаточным.
