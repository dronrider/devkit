# shipctl: слияние и откат задач

Механика раздела «Ветки, ревью и деплой» RULES.board.md: самый длинный ручной
процесс из тех, что остаются агенту. Утилита держит порядок шагов и
предусловия, думающая часть (само ревью, команда тестов и выката проекта)
остаётся за исполнителем и передаётся флагами.

Сборка в PATH, как у taskctl (который тоже нужен в PATH: доску двигает он):

```
cd ~/projects/devkit/shipctl && go build -o ~/go/bin/shipctl .
```

Корень находится как у taskctl: поиском `docs/TASKS.md` вверх от текущей
директории, при необходимости стартовую задаёт общий флаг `-C <dir>`.

## Команды

```
status                                    очередь выката, поезд и вердикт
merge <ID> --test "cmd" [--deploy "cmd"] [--train] [--push]
ship [--deploy "cmd"] [--push]
revert <ID> [--test "cmd"] [-m "..."] [--push]
```

`merge` с фичеветки проверяет предусловия и проводит слияние:

- рабочее дерево чистое, задача в In progress, секция Check пуста (выкаты
  строго последовательные, непроверенная правка на проде одна);
- раздел «Ревью» файла задачи без замечаний с незафиксированным исходом
  (каждая строка кончается «исправлено» либо «отклонено» с причиной);
- ребейз на main, прогон `--test` (строка уходит в `sh -c`), fast-forward
  без merge-коммита, фичеветка удаляется;
- выкат (см. «Обвязка выката» ниже);
- перевод задачи в Check через taskctl и коммит доски.

Если в коммитах ветки нет ID задачи в subject, merge проходит, но
предупреждает: revert такие коммиты потом не найдёт.

## Поезд выката

Мелкие независимые задачи выкатываются пачкой (критерии отбора в
RULES.board.md, «Ветки, ревью и деплой» п. 9): `merge --train` проводит то же
слияние с полными предусловиями, но без выката, задача остаётся в In progress,
а `ship` одним деплоем везёт всё накопленное и разом переводит в Check. Каждая
задача проверяется на этом билде по своему сценарию, провал одной чинится
точечным `revert`: он откатывает и перекатывает только её, остальной поезд
остаётся на проде. Откат задачи из ещё не выкаченного поезда деплой не
запускает вовсе: до прода она не доехала, а повторный выкат увёз бы туда
остальной поезд раньше времени.

Состав поезда нигде не хранится, а вычисляется из git: точку последнего выката
держит лёгкий тег `deployed`, в поезде стоят задачи из In progress, чьи
коммиты кода (по ID в subject) слиты после него. Коммиты, трогающие только
доску и файлы задач, членства не дают, а задача, откаченная внутри окна, из
поезда выбывает. Тег заводит первое `merge --train` (на main до себя: что
было на main к этому моменту, считается выкаченным), двигает `ship` после
деплоя, пуш тега идёт с `-f` вместе с пушем кода. На второй машине тег
подтягивается `git fetch --tags --force`.

Одиночный `merge` при непустом поезде отбивается: он увёз бы на прод чужие
непроверенные правки, а в Check перевёл только свою задачу. Либо сливать с
`--train`, либо сначала `ship`.

`revert` чинит прод после провала проверки: откатывает коммиты задачи с main
(ищутся по ID в subject, новые первыми, коммиты доски и файлов задач не
трогаются), одним коммитом, и возвращает задачу в In progress. Граница
поиска это прошлый откат той же задачи, поэтому повторные заходы на задачу
откатываются корректно. При конфликте revert отменяется целиком, тогда чинить
форвард-фиксом.

`--push` у обеих команд отправляет результат в origin; без него пуш остаётся
за пользователем (RULES.md, «Git» п. 3), кроме автономного режима, где обе
команды пушат и без флага (см. «Обвязка выката»). Сообщение коммита-отката по
умолчанию «revert: <ID> откат ...», в проекте с белым списком префиксов своё
задаётся флагом `-m`.

Перед необратимыми шагами merge сверяет локальный main с origin (fetch плюс
проверка, что origin/main не ушёл вперёд): отставший клон, чья доска не знает
о задаче в Check с другой машины, отсекается до слияния, а не на пуше.

## Обвязка выката

Команда выката у каждого проекта своя, и в ней обычно адрес или роль машины,
поэтому она не в коммитимом `CLAUDE.md`, а в гитигнорнутом `.devkit/deploy.local`
(болванку заводит `devkitctl new`). Формат простой: строки `key = value`,
`#` это комментарий.

```
deploy = ssh vps 'systemctl restart foo'
autonomous = false
```

`merge` (и `ship` тем же порядком) разбирается с выкатом так:

- явный `--deploy "cmd"` это указание выкатить прямо сейчас, выполняется
  всегда и сильнее конфига (пуш тогда по `--push`, как обычно);
- без флага и при `autonomous = true` shipctl катит команду из `deploy` сам;
- без флага и при `autonomous = false` команда остаётся за пользователем,
  merge печатает, что именно запустить;
- команды нет вовсе (или файла нет) это выкат по плейбуку проекта, как раньше.

При `autonomous = true` merge, ship и revert пушат в origin сами, без `--push`,
это часть автономного конвейера: иначе origin отстал бы от задеплоенного прода
и доски, а `revert` по ID не нашёл бы коммитов на origin. Код уходит в origin
до выката, а доска после: pull-выкат тогда тянет с origin уже свежий main,
а строка в Check появляется после успешного деплоя. Revert в автономном
режиме тем же порядком пушит откат и сам катит повторный выкат командой из
`deploy`, прод чинится без ручных шагов. При `autonomous = false` пуш и
повторный выкат остаются за пользователем (или по флагу `--push`).

Флаг автономии виден в `status`, а `devkitctl doctor` ловит пустую или
негитигнорнутую обвязку.
