# taskctl: механика канбан-доски

Утилита для рутинных операций с `docs/TASKS.md` и `docs/TASKS-archive.md`:
завести строку, перевести между статусами, закрыть в архив, пересортировать
Backlog, проверить инварианты. Думающая часть (заголовок, слагаемые ранга по
`RANKING.md`, сценарий проверки) остаётся за исполнителем и передаётся
аргументами, утилита ничего не сочиняет.

Утилита общая для всех проектов с доской, живёт в devkit. Один раз собрать
бинарь в PATH:

```
cd ~/projects/devkit/taskctl && go build -o ~/go/bin/taskctl .
```

и дальше звать `taskctl <команда>` из любого места внутри проекта: корень
находится сам (поиском `docs/TASKS.md` вверх от текущей директории), при
необходимости стартовую директорию задаёт флаг `-C <dir>`.

## Команды

```
list [backlog|in-progress|check|blocked]    доска по секциям без прозы
show <ID>                                   строка задачи, секция, файл задачи
id                                          следующий свободный ID
add --title "..." --type bug|task|LLD --rank "а+б+в+г+д"
    [--cost S|M|L|XL] [--link "..."] [--status ...] [--id XR-NNN] [--reason "..."]
move <ID> <backlog|in-progress|check|blocked> [--reason "..."]
set <ID> [--title "..."] [--type ...] [--rank "..."] [--cost ...] [--link "..."]
file <ID>                                   создать docs/tasks/<ID>.md и ссылку
close <ID> [--commit sha1,sha2] [--date ГГГГ-ММ-ДД] [--link "..."]
dep add <ID> <DEP-ID>                       ID делается после DEP-ID
dep rm <ID> <DEP-ID>                        снять зависимость
dep list [ID]                               кто после кого; без ID вся доска
sort
lint
init --prefix XR [--name "..."]             скелет доски в корне репозитория
review add <ID> "суть замечания"            замечание в раздел «Ревью»
review resolve <ID> <N> fixed|rejected [--reason "..."]
review show <ID>                            замечания с номерами и исходами
review stats                                свод по живым задачам и архиву
```

Смотреть доску дешевле через `list` и `show`, а не чтением `TASKS.md` целиком:
`list` печатает секции без прозы и обрезает Backlog до верхних десяти строк
(вся секция по `list backlog`), `show` находит задачу и в архиве. Изменяющие
команды принимают `-m "docs(tasks): ..."` и `--push`: закоммитить ровно те
файлы, которые тронула операция (и запушить); что было в индексе до этого, в
коммит не попадает.

Что утилита держит сама:

- `init` создаёт доску нового проекта (`docs/TASKS.md` с шапкой и секциями,
  `docs/TASKS-archive.md`, `docs/tasks/`) в вершине git-репозитория; префикс
  ID пишется в шапку, и первая задача заводится уже без `--id`;
- сумма R и бакет P считаются из разбивки `--rank`, руками их не передать;
  разбивка проверяется по шкалам `RANKING.md` (серьёзность из {0,25,50,75},
  ценность 0-10, неопределённость 0-5, баг 0 или 5, рычаг 0-5);
- колонка «Цена» держит грубую оценку затрат агента на исполнение (S / M / L /
  XL, шкала в `RANKING.md`), в ранг не входит; `--cost` не передан или «-»,
  значит «не оценено»; доску без этой колонки разбор принимает и переводит в
  новый формат при первой изменяющей команде (на месте это делает
  `taskctl sort`, старый формат подсвечивает lint);
- Backlog отсортирован по R убыванию, при равенстве по возрастанию ID; `add`
  сразу ставит строку в правильное место;
- статусы принимаются в любом регистре («In progress» = in-progress); голый
  путь в `--link` оборачивается в markdown-ссылку, чтобы её видел lint;
- `add` без `--link` ссылается на существующий `tasks/<ID>.md`, а без файла
  ставит в ячейку «-»: однострочному бэклогу файл не положен;
- `file` создаёт файл задачи со строкой-заголовком и чинит ссылку в строке,
  когда содержимое задачи переросло заголовок;
- `move` в blocked требует `--reason` и дописывает причину к заголовку, при
  выходе из blocked причина из заголовка снимается;
- `set` правит ячейки существующей строки (заголовок, тип, ранг, цену, ссылку);
  P пересчитывается из новой разбивки, строка в Backlog встаёт на место по
  новому рангу, в остальных секциях остаётся где была; у заблокированной
  строки пометка «[блок: ...]» переживает смену заголовка;
- `close` дописывает строку в архив (без колонок R и «Цена», с датой закрытия),
  переносит файл задачи в `tasks/archive/<год>/` (`git mv` с фолбэком на
  обычный rename) и ставит ссылку уже на новое место; хеши из `--commit`
  добавляются в ячейку ссылки; заодно снимает «[после `<ID>`]» со всех строк
  доски, ссылавшихся на закрытую задачу, и в архивную строку маркер не
  переносит;
- зависимость между задачами («A делается после B») живёт суффиксом
  заголовка `[после B]` (несколько ID через запятую) перед пометкой «[блок:
  ...]»; хранится только это направление, обратное («кого держит B») taskctl
  считает по доске. `dep add <ID> <DEP-ID>` ставит зависимость (проверяет, что
  обе задачи существуют и добавление не замкнёт цикл), `dep rm` снимает,
  `dep list [ID]` печатает обе стороны (без ID по всей доске); `show` тоже
  печатает «после» и «держит». И `move <ID> in-progress`, и `dep add` на
  задачу, уже стоящую в In progress или Check, с незакрытой (не найденной в
  архиве) зависимостью падают с ошибкой, где назван её ID; `--force` нет;
- `lint` проверяет разбор всех строк, бакеты P, сортировку, дубли ID по доске
  и архиву, формат дат, что локальные markdown-ссылки ведут на существующие
  файлы, что у задачи в работе есть файл `docs/tasks/<ID>.md`, а у задачи в
  Check хотя бы ссылка на сценарий проверки (RULES.board.md, «Трекинг задач»
  п. 3 и 6), а также маркер зависимости: ID из «[после ...]» существует (на
  доске или в архиве), не ссылается сам на себя, без дублей внутри маркера,
  без циклов, и что задача в работе или на проверке не держит незакрытую
  зависимость;
- `review` держит формат раздела «Ревью» файла задачи: `add` дописывает
  строку-замечание (файл задачи и ссылка в строке заводятся сами), `resolve`
  фиксирует исход («исправлено» либо «отклонено» с обязательной причиной),
  а `stats` считает по живым задачам и архиву, что ревью реально ловит;
  чужие секции файла не трогаются.

Правило надёжности: нетронутые строки сохраняются байт в байт, файл вне таблиц
не переформатируется. Строка, которую не удалось разобрать, валит операцию с
ошибкой вида `файл:строка` до какой-либо записи на диск.

Справка доступна и по `-h`/`--help` у любой подкоманды. Каждый запуск оставляет
строку в журнале `.devkit/log` проекта (время, команда, код выхода), если
директория `.devkit` заведена: по журналу видно, что реально гоняется и как
часто падает; файл гитигнорнут (об этом заботится devkitctl).
