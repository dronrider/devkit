# agentctl: выбор исполнителя под задачу

Механизирует пункт «Выбор модели» из `RULES.board.md`. Сменить модель своей
сессии агент не может, этот рычаг харнес отдаёт пользователю; штатная дверь
это спавн субагента с явной моделью. agentctl и есть решатель для такого
делегирования: читает метаданные задачи с доски `docs/TASKS.md` и печатает
вердикт, сессия-диспетчер отдаёт работу субагенту с этой моделью.

Ролей у субагента две. Исполнитель пишет код, ревьювер читает готовый дифф, и
вердикт для них считается одной и той же таблицей, но у ревьювера с поправкой
(флаг `--role review`, см. «Роль ревьювера»).

У исполнения две оси: калибр исполнителя и reasoning effort. Вердикт называет
обе, но применяются они по-разному. Модель передаётся параметром при спавне
субагента, а effort от сессии не наследуется и параметра вызова у него нет: его
задаёт поле `effort` во frontmatter определения агента. Поэтому вторая строка
вердикта это выбор определения из набора `devkit/kit/agents` (см. «Определения
субагентов»).

Калибр считается не именами моделей, а ярусами лестницы
`mini -> base -> pro -> max`: имена отвечают на единственный вопрос, который
ярусу задают («насколько исполнитель сильный относительно соседей»), и от
инструмента не зависят. Все внутренние таблицы (маппинг, корректор, роль
ревьювера) работают в ярусах, а в конкретную модель ярус разворачивается
последним шагом, маппингом активного харнеса (см. «Харнес: профиль, слои и
детект»).

Никакого ИИ внутри нет, маппинг детерминированный: всё нужное уже проставлено
на доске при грумминге (тип, цена, разбивка ранга, третье слагаемое которой
это неопределённость).

## Команда

```bash
agentctl pick DK-002
```

```text
model: haiku
effort: low
tier: mini
via: claude-code
DK-002 (task, цена S, неопределённость 0): совсем атомарная правка с очевидным подходом, дешёвой модели хватает
```

Первые четыре строки машинно-читаемые (`model` это модель харнеса назначения,
`effort: low|medium|high|xhigh|max`, `tier: mini|base|pro|max`, `via` это имя
харнеса, чьей подпиской платится работа), пятая для человека. Порядок строк не
менялся с их появлением: `tier` дописан третьим, `via` четвёртым, чтобы
потребителям первых двух не пришлось переучиваться. Строка `via` печатается
всегда, в том числе когда ступень домашняя (`via: claude-code`): строка,
появляющаяся через раз, заставляла бы читать вывод условно, а «дома» это такой
же ответ на вопрос «чьей подпиской», как и любой другой. Имя харнеса при этом в
строке `model` не повторяется, там всегда голая модель.

Харнес не определён или не настроен, значит в строке модели стоит прочерк, а
причина хвостом называет файл, которым это чинится:

```text
model: -
effort: medium
tier: pro
via: -
DK-019 (task, цена M, неопределённость 1): задача для дешёвых моделей не подходит, по умолчанию идёт сильной; харнес claude-code не настроен, маппинга ярусов нет; вписать секцию [claude-code] в /Users/me/.devkit/harness.local
```

Ярус и effort при этом полноценны: ярусная половина вердикта от инструмента не
зависит по построению, и разбираться приходится только с последним шагом.

Задача ищется по всем секциям доски; если её нет, ненулевой код возврата и
ошибка «нет на доске». Общий флаг `-C <dir>` как у остальных инструментов:
откуда искать корень с `docs/TASKS.md`. Ищется он как у taskctl, сначала по
редиректу `devkit.local` из конфига git (корп-контур, доска в боковой
директории рядом с клоном), а без ключа прежним подъёмом вверх; pick и
корректор работают по боковой доске без иных отличий, разбор редиректа в
[tools/taskctl/README.md](../taskctl/README.md). Флаг `--role review` отдаёт вердикт для
агента-ревьювера, разбор в разделе «Роль ревьювера», а `--goal <файл цели>`
режет вердикт потолком яруса цели, разбор в разделе «Гейт бюджета цели».

## Правила маппинга

Оси считаются порознь, но не совсем независимо: у яруса есть свой пол effort.
Ярус это калибр исполнителя, его задают тип и цена. Effort это глубина
размышления, её задаёт неопределённость, а на ярусе base результат ещё
подтягивается вверх (см. «Effort» ниже). У pro эта свобода не отнята: на
рутинной правке он идёт с `low`, а на задаче с открытыми деталями с `medium`.

### Ярус

Порядок значим, первое сработавшее правило решает:

| Условие | Ярус | Смысл |
|---|---|---|
| тип LLD, цена L или XL | max | сложное проектирование, max делает его лучше pro |
| тип LLD (остальная цена) | pro | дизайн отдаётся сильной модели |
| неопределённость >= 4 | pro | сначала грумминг, исполнять рано |
| цена XL | pro | сначала разбить на серию, целиком не отдавать |
| цена S и неопределённость ровно 0 | mini | совсем атомарная правка с очевидным подходом |
| цена S и неопределённость ровно 1 | base | небольшая задача, подход уже выбран, дешёвая модель справится |
| остальное | pro | для дешёвых моделей не подходит, по умолчанию идёт сильной |

Под «остальное» попадают M с неопределённостью 0-3, S с неопределённостью 2-3,
L с неопределённостью 0-3 и неоценённая цена (вердикт тогда напоминает про
оценку); неопределённость 4 и выше в любом случае ловится грумминговым
правилом строкой выше. Нечитаемая разбивка ранга (старая доска, прочерк)
трактуется как неизвестность в пользу сильной модели: ни mini, ни base по
ней не выдаются, остаётся pro.

Вердикты pro про грумминг и разбивку это «исполнять рано», а не «исполнять
сильной моделью»: она зовётся снимать неопределённость или резать задачу,
после чего pick даёт уже исполнительский вердикт по обновлённой строке.

### Effort

Уровень идёт за третьим слагаемым ранга по шкале неопределённости из
`RANKING.md`, порядок так же значим:

| Условие | Effort | Смысл |
|---|---|---|
| тип LLD, либо неопределённость >= 4, либо цена XL | xhigh | решение ещё не найдено, размышление это и есть работа |
| нечитаемая разбивка ранга или неоценённая цена | high | метаданным верить рано, осторожность в пользу глубины |
| неопределённость 0 | low | рутина, делалось много раз, размышлять не над чем |
| неопределённость 1-2 | medium | подход выбран, открыты детали |
| неопределённость 3 | high | в деталях есть развилки, размышление их окупает |

Верхний уровень исполнимой задаче не достаётся: неопределённость 4-5 это порог
готовности из `RANKING.md`, там вердикт и так грумминговый, а всё исполнимое
укладывается в 0-3. Так `xhigh` остаётся за проектированием и вердиктами
«исполнять рано». Цена в эту ось входит ровно двумя случаями. XL это разбивка,
то есть тот же «исполнять рано». Прочерк в цене значит, что грумминг не
доведён до конца, и нулю в третьем слагаемом доверия тогда не больше, чем
прочерку в ранге, поэтому оба случая идут на `high`. Уровень `max` маппингом не
выдаётся, он остаётся ручным решением через override-строку файла задачи.

У яруса base таблица выше не последнее слово: `low` и `medium` из неё
поднимаются до `high` полом, который висит на самой ступени, а не на
неопределённости. Это дешёвая рабочая ступень лестницы, риск потерять качество
на ней есть, а экономия на глубине размышления того не стоит. Пол срабатывает и
когда base пришёл override-строкой, а effort остался от обычного маппинга ниже
high; явная override-строка эффорта пол перебивает целиком, её значение берётся
как есть, хоть и `low`. В человеческой строке вердикта подтяжка видна коротким
хвостом причины («effort поднят до high: base дёшев, экономить глубину смысла
нет»). На харнесе, где base развёрнут в дорогую модель, пол теряет исходное
обоснование, но вреда не наносит: он только поднимает глубину размышления.

На ярус mini пол не распространяется: модель вроде Haiku 4.5 про параметр
effort в API вовсе не знает, поднимать для неё нечего. Обычным маппингом mini
достаётся только с `low`, но override или сдвиг корректора могут привести его и
с `medium`: для такой модели это всё равно формальная метка, что бы в ней ни
стояло.

## Роль ревьювера

Ревью по правилу 2 раздела «Ветки, ревью и деплой» гоняет агент со свежим
контекстом, и модель ему тоже назначается вердиктом, а не на глаз:

```bash
agentctl pick DK-023 --role review
```

Отдельной подкомандой это не сделано намеренно: роль меняет один шаг расчёта,
а всё остальное (метаданные строки, override, корректор, запись в файл задачи)
у ролей общее, и разведя их по подкомандам, пришлось бы держать таблицу в двух
местах. Без флага роль исполнительская, как было.

Считается роль поверх готового исполнительского вердикта, последним шагом по
ярусной оси (после override и корректора, иначе корректор увёл бы ревьювера
ещё на ступень вниз):

| Условие | Ярус ревьювера | Смысл |
|---|---|---|
| грумминговый вердикт | как у исполнителя | работы ещё не было, ревьюить нечего |
| тип LLD | как у исполнителя | дизайн читается тем же калибром, каким пишется |
| ярус исполнителя mini или base | base | пол: mini читает дифф бегло и замечаний не находит |
| остальное | ярус ниже исполнителя | ревьюверу нужен не калибр автора, а внимательность на диффе |

Лестница та же, что у корректора (`mini -> base -> pro -> max`), шаг один.
Основная масса задач приходит с дефолтным pro, и ревьюит их base, а вот
дизайн так не удешевляется: разбор чужого LLD это то же проектирование, только
задом наперёд, и слабой модели он не по силам. Выигрыш поэтому не в разы: доля
ревью в недельном расходе небольшая, зато решение перестаёт приниматься на
глаз.

Совет отложить работу до сброса лимитов (см. «Корректор по остатку лимитов»)
в вердикт ревьювера не идёт: он адресован тому, кто решает, браться ли за
задачу сейчас, а к ревью и исполнение, и дизайн уже сделаны. Хвост самого
корректора при этом остаётся, сдвиг объяснять всё равно надо.

Effort роль не меняет: глубина размышления идёт за неопределённостью задачи, а
от смены роли задача проще не становится. Пол base при этом никуда не девается
и считается по итоговому ярусу, поэтому ревьювер с base почти всегда приходит с
`high`. Причина в человеческой строке несёт хвост про роль («роль ревью:
pro -> base, ...»), так что по выводу видно, от чего вердикт оттолкнулся.

## Корректор по остатку лимитов

Таблица выше считает вердикт из метаданных задачи и ничего не знает про то,
сколько осталось от недельных лимитов подписки. Расход выходит нерациональным
в обе стороны: за день до сброса с нетронутым бакетом экономить незачем, а на
почти исчерпанном отдавать задачи дорогой модели неправильно. Корректор это
слой поверх маппинга: таблица не меняется, двигается её результат, максимум на
одну ступень лестницы `mini -> base -> pro -> max`. Дизайн разобран в
[DK-010](../../docs/lld/DK-010-quota-corrector.md).

### Файл снимка

Остаток программно недоступен у Claude Code: `/usage` только интерактивный,
расчёт серверный, эндпоинта нет. Поэтому контрактом сделан файл снимка, который
pick только читает (в сеть и в tmux он не ходит, детерминизм и скорость
прежние). Лежит он на уровне машины, а не проекта (лимиты общие на подписку), и
по файлу на харнес: `~/.devkit/quota/<харнес>.local`. Лимиты у инструментов
свои, и одним файлом их не описать.

```text
taken = 2026-07-30T14:20
week_all = 41% сброс 2026-08-03T15:00
week_max = 78% сброс 2026-08-03T15:00
```

`taken` это момент снятия, дальше бакеты: процент потраченного и дата сброса.
Пятичасовой сессионный бакет не пишется, он протухает быстрее, чем живёт
задача. Какие бакеты бывают и какой из них обязателен, объявляет `[quota]`
профиля харнеса (`buckets`, `required`): у claude-code обязателен общий
`week_all`, а дорогой панель показывает не всегда. Незнакомый ключ игнорируется
с предупреждением в человеческой строке вердикта. Заполняется файл руками с
панели `/usage` либо командой `agentctl quota refresh`, формат один и тот же;
сам себя он освежает хуком старта сессии (см. «Снимок освежается сам»).

Бакеты зовутся ярусами, как и вся остальная лестница, а панель называет
добавочный бакет моделью, поэтому старое имя читается псевдонимом
(`week_fable -> week_max`): снимки пишутся руками и живут на машинах со старым
клиентом, ломать их об незнакомый ключ нельзя. Ключ `week_opus` псевдонимом не
стал, это другой бакет: он остаётся известным, но лестницу трат не задаёт, и в
выводе `agentctl quota` идёт с пометкой.

Одиночный `~/.devkit/quota.local`, каким снимок был до директории, читатель
понимает: не найдя файла по новому пути, он берёт старый и говорит об этом
хвостом причины. Переезд делает `devkitctl doctor --fix`, а `refresh` пишет
всегда по новому пути.

Снимка нет, момента снятия в нём нет, снимок протух: pick про каждый случай
говорит вслух хвостом человеческой строки.

```text
model: opus
effort: medium
tier: pro
via: claude-code
DK-019 (task, цена M, неопределённость 1): задача для дешёвых моделей не подходит, по умолчанию идёт сильной; снимка квоты нет (/Users/me/.devkit/quota/claude-code.local), вердикт идёт без корректора; снять: agentctl quota refresh
```

Молчать тут нельзя, и это стоило задачи DK-019: корректор простоял выключенным
с самого появления, потому что снимка на машине не завели, а вердикт без него
выглядит совершенно обычным. Тихо отброшенные данные неотличимы от данных,
которые посмотрели и сдвигать не стали.

Из каких бакетов тратит ярус, говорит `spend_mini`..`spend_max` профиля. У
claude-code это:

| Ярус | Бакеты |
|---|---|
| mini, base, pro | week_all |
| max | week_all и week_max сразу |

Отдельным бакетом панель добирает самую дорогую модель. Своего бакета у pro
поэтому больше нет, и от base он отличается только тем, что жжёт общий бакет
дороже. Формула корректора работает по именам бакетов и про инструмент не знает
ничего: другой харнес объявит свои имена и свою лестницу, а расчёт останется
тем же.

Проценты панель считает от действующего лимита, и в этом подвох, когда лимит
временно поднят промо (панель пишет об этом строкой вроде «+50% weekly limits
promo through Aug 19»). Пока промо идёт, проценты меряются от увеличенного
лимита, а в день его окончания тот же расход разом станет большей долей, хотя
потрачено ничего не было. Корректор честно отработает по цифрам и съедет вниз,
поэтому снимок вокруг этой даты стоит переснять и не удивляться сдвигу.

### Формула

По каждому бакету считается темп расхода против равномерного:

```text
remaining = 1 - used
time_left = (сброс - сейчас) / окно бакета
pace      = remaining / time_left
```

Окно берётся из префикса имени: `week_*` это 7 суток, `month_*` это 30. Лимиты
подписки недельные, а потокенный бюджет чаще месячный, и по нему недельное окно
завышало бы pace всемеро, то есть рисовало профицит на ровном месте. Имя без
известного префикса профиль не проходит: молчаливого умолчания тут быть не
должно.

Профицит при `pace >= 2`, дефицит при `pace <= 0.5`, между ними норма и сдвига
нет. Зазор широкий сознательно: корректор должен срабатывать на выраженный
перекос, а не дёргать вердикт на каждом колебании.

Свежесть снимка асимметрична, потому что остаток внутри окна только тратится.
Дефицит от старения не рассасывается и валиден до самой даты сброса: снятый
остаток это верхняя граница текущего. Профицит же протухает, для сдвига вверх
снимок должен быть не старше 45 минут. Прошла дата сброса, и бакет
отбрасывается целиком: началось новое окно, про которое снимок ничего не знает.

Момент снятия позже текущего времени это не «свежее свежего», а разошедшиеся
часы: когда снимок сняли на самом деле, по такому файлу не сказать вовсе.
Профицит по нему поэтому не применяется наравне со снимком без `taken`, и pick
про расхождение говорит.

Порог в десятках минут берётся из темпа расхода. Он доходит до 10% подписки в
час, то есть pace уезжает примерно на 0.2 за час, и к сорока пяти минутам
набегает десятая часть зазора между порогами статуса (`0.5` и `2`). Снимок
трёхчасовой давности при таком темпе описывает уже другую подписку, а цена
ошибки у профицита наибольшая: pick поднимет вердикт до дорогой модели на
запасе, которого нет. Тот же порог решает, когда pick говорит «снимок протух»,
и это не совпадение: разведи два числа, и нашлось бы окно, где одна строка
вердикта зовёт переснять снимок, а другая по нему же поднимает модель.

### Снимок освежается сам

Руками снимок не переснимает никто, а протухший корректор просто выключает,
поэтому обновление повешено на старт сессии Claude Code: SessionStart-хук
`devkit/hooks/quota-refresh.sh` отцепленно запускает `agentctl quota refresh
--if-stale` и сразу возвращается, подключение и подробности в
`hooks/README.md`. Свежий снимок при этом не трогается, порог живёт здесь же в
agentctl, второй его копии в хуке нет.

Сам pick остаётся чистым читателем: в сеть и в tmux он не ходит, процессов не
спавнит, вердикт по одному и тому же снимку всегда один и тот же. Вариант
«refresh дёргает сам pick отцепленным процессом» отвергнут именно поэтому:
читающая команда, которая заводит себе фоновую работу, теряет и детерминизм, и
право быть вызванной из теста, а выключать её пришлось бы флагом или
переменной окружения.

Нет tmux, нет claude, клиент не залогинен: хук молча уходит, ничего не ломая.
Что на машине чего-то не хватает, говорит `devkitctl doctor`, у которого это и
есть работа; он же ловит неподключённый хук и протухший снимок.

Правила сдвига, порядок значим:

1. Грумминговые вердикты (неопределённость >= 4, цена XL) не корректируются:
   «исполнять рано» это про порядок работы, расход тут ни при чём.
2. Дефицит любого бакета, из которого тратит ярус вердикта, сдвигает на ступень
   вниз. Ниже mini некуда, остаётся предупреждение.
3. Иначе на ступень вверх сдвигает профицит всех бакетов, из которых будет
   тратить ярус выше: `pro -> max` при профиците week_all и week_max сразу,
   `mini -> base` и `base -> pro` при профиците одного week_all. Одного
   добавочного бакета мало: подъём на самую дорогую модель нельзя решать, ничего
   не зная про запас общего бакета.
4. Шаг максимум один, сдвиги не каскадятся. Дефицит проверяется первым: бакет
   тратится взвешенной ценой модели, и сдвиг вверх при дефиците прожёг бы его
   быстрее.

Ярус из override-строки файла задачи корректор не двигает: ручное решение
сильнее автоматики, иначе указанный руками калибр приходилось бы отстаивать
заново на каждый снимок. Пол effort у base применяется к итоговому ярусу, то
есть уже после сдвига.

Маппинг харнеса вправе сложить соседние ярусы в одну модель (в машинном конфиге
это записывается повторением значения). Сдвиг по такой паре модель не меняет, и
корректор говорит об этом хвостом: «корректор: дефицит week_all, сдвиг pro ->
base, модель та же». Молчаливый холостой ход был бы неотличим от отсутствия
сдвига.

Нет файла, битая строка, протухший бакет: соответствующее отбрасывается, вердикт
остаётся как есть. Отсутствие данных никогда не ошибка pick, но и не молчание:
про сам снимок (нет его, нет момента снятия, протух) вердикт говорит хвостом
причины, см. «Файл снимка».

Состояние квоты идёт хвостом «квота: ...» и тогда, когда сдвига не было:
проценты бакетов, из которых платят исходный и итоговый ярусы, возраст снимка и
слова «сдвига нет». Иначе вердикт по снимку в норме читался бы так же, как
вердикт, для которого снимка не нашлось вовсе. Там, где про снимок уже сказано
предупреждением, состояние второй раз не повторяется: предупреждение говорит то
же самое и вдобавок несёт команду починки.

```text
model: opus
effort: medium
tier: pro
via: claude-code
DK-018 (task, цена M, неопределённость 1): задача для дешёвых моделей не подходит, по умолчанию идёт сильной; квота: week_all 41%, снимок 10м назад, сдвига нет
```

Сдвиг виден в человеческой строке вердикта хвостом:

```text
model: sonnet
effort: high
tier: base
via: claude-code
DK-012 (task, цена M, неопределённость 1): задача для дешёвых моделей не подходит, по умолчанию идёт сильной, effort поднят до high: base дёшев, экономить глубину смысла нет; корректор: дефицит week_all, pro -> base; квота: week_all 95% дефицит, снимок 10м назад; сдвиг вниз на цене M и выше это заметная потеря качества в исполнении, а сброс близко, так что если не горит, лучше отложить
```

Сдвинутому вниз вердикту строка вдобавок советует отложить до сброса, если не
горит: у LLD условие по типу (дизайн слабой моделью это долгий ущерб), у
остальных по цене (M и выше, потому что пол effort у base калибр модели не
заменяет). Цена S совета не получает: дешёвая модель на ней штатный
исполнитель и без всякого сдвига. Не получает его и вердикт ревьювера: дифф к
моменту ревью уже написан, откладывать нечего. Решение остаётся за
диспетчером, pick только проговаривает.

### Команда quota

```bash
agentctl quota
```

```text
снимок /Users/me/.devkit/quota/claude-code.local (харнес claude-code)
снят 2026-07-30T14:20, возраст 3ч 2м
week_all: потрачено 41%, сброс 2026-08-03T15:00, pace 1.1, норма
week_max: потрачено 78%, сброс 2026-08-03T15:00, pace 0.4, дефицит
```

Это окно в решения корректора: сдвиг в вердикте всегда можно объяснить, не
читая файл руками. Снимка нет, значит команда так и говорит, кодом возврата
это не ошибка. Протухший снимок печатается со своим возрастом и порогом, а
профицит по нему идёт с пометкой, что вверх он больше не двигает:

```text
снят 2026-07-30T09:20, возраст 3ч 0м при пороге 45м: протух, вверх корректор не двинет
week_all: потрачено 5%, сброс 2026-08-04T10:00, pace 4.2, профицит (снимок протух, вверх не двигает)
```

`agentctl quota refresh` заполняет снимок сам, а чем именно снимать, говорит
ключ `snap` профиля: `usage-pane` это встроенный цикл над панелью Claude Code,
`script` это сменный съёмщик рядом с профилем (см. «Сменный съёмщик»).

Встроенный цикл поднимает `claude` в одноразовой tmux-сессии, дожидается строки
ввода, набирает `/usage`, убеждается, что набранное видно в панели, и только
тогда жмёт Enter, дожидается панели, забирает её текст через `capture-pane`,
разбирает и пишет файл.

Три места этого цикла держатся на осторожности, и все три стоили ошибок:

- строка ввода. Готовой считается панель, где непустая строка обведена двумя
  сплошными линейками, такую рамку клиент рисует только вокруг ввода. Признак
  «в панели что-то появилось» и даже «есть линейка» не годятся: диалог доверия
  каталогу тоже начинается сплошной линейкой, и команда ушла бы прямо в него;
- Enter вслепую. Пока набранного не видно в панели, Enter не отправляется:
  на неузнанном экране он подтвердил бы подсвеченный там пункт, а не открыл
  панель. Диалог доверия каталогу и мастер первого запуска refresh узнаёт
  поимённо и отказывает с подсказкой, что сделать руками;
- дорисовка панели. Панель приезжает не одним кадром: сначала общий бакет,
  дорогой появляется примерно полсекунды спустя. Первый успешный разбор поэтому
  не принимается как есть: полная панель идёт в снимок сразу, а панель с одним
  общим бакетом должна продержаться три секунды, иначе в снимок попал бы
  наполовину отрисованный кадр, и корректор молча потерял бы сдвиг вверх.

Флаг `--if-stale` добавляет к этому одну проверку в начале: снимок свежий,
значит остаток не снимается вовсе и команда сразу говорит об этом. На этом
режиме стоит хук старта сессии, иначе клиент в tmux поднимался бы по десятку
раз в день впустую.

Нет tmux, нет claude в PATH, клиент не залогинен, ввод перехвачен чужим экраном,
панель не узналась, значит честный отказ и файл не тронут: pick живёт по
прежнему снимку либо без сдвига. Разметка панели не контракт, она меняется
вместе с клиентом, поэтому парсер и признаки экранов гоняются по образцам в
`tools/agentctl/testdata`: редизайн ловится их обновлением, это принятая плата.

### Команда budget

`agentctl pick` правит вердикт на одну задачу, а пачка из пяти задач это
десять запусков (исполнитель и ревьювер на каждую), и про такой расход
формула ничего не знает. Потолок пачки поэтому считает отдельная команда, там
же, где живёт снимок остатка:

```bash
agentctl budget
```

```text
batch: 3
week_all: потрачено 41%, сброс 2026-08-03T15:00, pace 1.1, норма; корректор вердикт не двигает, потолок 3, на задачу идёт пара запусков (исполнитель и ревьювер)
```

Первая строка машинная, её значение уходит в `taskctl batch --limit`; вторая
называет бакет, темп, статус и причину потолка.

Из каких бакетов пачка потратит, budget не выводит своим рассуждением про
проценты, а спрашивает у той же формулы: зовёт `correctModel`, тонкую
обёртку над той же `correctTier`, что двигает вердикт pick, на модели `opus`
(`tierPro`, самый дорогой ярус, который маппинг выдаёт задачам пачки по
умолчанию, цена M с неопределённостью 0-1), и потолок читает по тому, что
корректор сделал с ним. Своё предсказание разошлось бы с корректором ровно
там, где ошибка дороже всего: подъём `opus -> fable` случается при свежем
профиците `week_all` и `week_max` сразу, то есть в том самом состоянии, где
потолок и хочется поднять до пяти, а пять запусков верхнего яруса сожгут
бакет, которого расчёт по одному бакету не увидел бы.

| Что корректор делает с opus | Потолок |
|---|---|
| сдвигает вниз, дефицит `week_all` | 1 |
| поднимает на fable, свежий профицит `week_all` и `week_max` | 3 |
| не двигает, `week_all` в профиците на свежем снимке | 5 |
| не двигает в остальных случаях (норма, протухший профицит, снимка нет, бакет за датой сброса) | 3 |

`batch: 1` читается как «пачку не собирать, работать по одной», отдельного
слова для этого не нужно. На верхнем ярусе потолок режет до трёх, а не
запрещает вовсе: профицит там настоящий, но запуск fable стоит другого
порядка, и пятью такими парами запас `week_max` съедается быстрее, чем
восстанавливается недельное окно.

Асимметрия свежести приходит из той же формулы корректора и по той же причине
(см. «Формула» выше): остаток внутри окна только тратится, дефицит от
старения не рассасывается, а профицит протухает, и поднимать по нему потолок
нельзя. Снимка нет вовсе, он битый, харнес не объявил секцию `[quota]`: во
всех этих случаях потолок остаётся значением по умолчанию 3, а не падает и не
угадывает, но хвост строки называет способ снять снимок (`agentctl quota
refresh`), как это делает pick.

Считать пачку в процентах лимита budget не пытается: цена задачи в процентах
подписки неизвестна и вывести её неоткуда, локальные транскрипты размеров
лимитов не знают (см. [DK-010](../../docs/lld/DK-010-quota-corrector.md)).
Придуманный коэффициент дал бы ложную точность, поэтому потолок идёт по тем же
статусам темпа, по которым живёт корректор.

### Сменный съёмщик

Панель `/usage` это способ Claude Code, у остальных инструментов остаток
снимается иначе: своей командой, файлом статистики, запросом к API с бюджетом.
Профиль такого харнеса ставит `snap = "script"` и путь `script` относительно
`kit/harness/`, а сам скрипт лежит рядом с профилями, в `kit/harness/snap/`. Контракт
скрипта короткий:

- вход: stdin не даётся вовсе; в окружении `DEVKIT_HARNESS` (имя) и
  `DEVKIT_QUOTA_BUDGET` (число из машинного конфига, только у `budget_based`,
  и без него refresh отказывается звать съёмщика);
- выход: stdout это готовый текст снимка, `taken = ...` и строки бакетов; у
  бюджетного инструмента скрипт сам делит потраченное на бюджет и печатает долю;
- отказ: ненулевой код выхода и человеческая причина в stderr, stdout при этом
  не смотрится вовсе.

Файл пишет не скрипт, а agentctl: вывод сначала разбирается тем же парсером,
которым читается снимок, и только целый ложится на место, атомарно. Целый это
разобранный без единого предупреждения, с моментом снятия и обязательным
бакетом: снимок на диске пишут и руками, ему битую строку простить можно, а
машине нет, её «почти снимок» лучше отбросить, чем записать наполовину. Так у
сменного съёмщика то же свойство, что у встроенного цикла: сломавшийся отказывает
громко и файл не трогает, а pick живёт по прежнему снимку либо без сдвига.

## Гейт бюджета цели (spend)

Автономный цикл цели (скилл `goal-loop`, дизайн в
[DK-079](../../docs/lld/DK-079-autonomous-loop.md)) работает витками без человека,
и цену этой работы назначает пользователь при постановке. Гейт стоит в начале
каждого витка и отвечает одним словом, ехать дальше или останавливаться:

```bash
agentctl spend --goal docs/tasks/DK-100.md
```

```text
gate: ok
week_all: потрачено 12 из 25; week_max: потрачено 4 из 10; потолок яруса pro; точек расхода 2; снимок 0м назад
```

Первая строка машинная (`gate: ok` либо `gate: over`), вторая для человека.
Кодом возврата гейт не отвечает: `over` это штатный ответ команды, а не её
поломка, и ненулевой код спутался бы с ошибкой постановки.

Цена цели меряется процентными пунктами бакетов панели, а не токенами и не
деньгами. Причина та же, по которой в процентах не считается пачка: локальные
транскрипты размеров лимитов подписки не знают, и вывести из токенов процент
неоткуда ([DK-010](../../docs/lld/DK-010-quota-corrector.md)). Лимиты живут в
разделе «Бюджет» файла цели, строка на бакет плюс необязательная строка потолка
моделей:

```text
бюджет: week_all <= 25
бюджет: week_max <= 10
ярус: pro
```

Строки читаются и пунктами списка, и внутри ограды примера; проза раздела
разбором не считается. Бакет, которого харнес не знает, это ошибка постановки,
а не молчаливый пропуск: посчитанный без него расход выглядел бы штатным. По
той же причине отказом отвечают нечитаемая строка `бюджет:` и раздел вовсе без
лимитов, гейту тогда нечего считать. Старые имена читаются псевдонимами, как и
везде (`week_fable -> week_max` у бакета, `opus -> pro` у яруса).

Расход считается по цепочке снимков: строки из раздела «Журнал» файла цели плюс
текущий снимок квоты. Между соседними точками берётся дельта, и сумма дельт это
потраченное за цикл:

```text
- снимок 2026-08-03T09:00: week_all 10%, week_max 2%
- снимок 2026-08-03T23:23: week_all 22%, week_max 6%
```

Отрицательная дельта значит не возврат потраченного, а сброс окна: панель
меряет от действующего лимита, поэтому расходом берётся значение нового окна
целиком. Так сброс не обнуляет счётчик цели, бюджет это сумма потраченного за
цикл, а не остаток в текущем окне. Флаг `--record` дописывает текущий снимок в
конец «Журнала» (симметрия с `pick --record`), и следующий виток читает его как
предыдущую точку цепочки; виток зовёт команду именно так.

Свежесть снимка идёт по тому же порогу, что у корректора. Протухший снимок гейт
не роняет, но говорит об этом вслух, и виток начинается с `agentctl quota
refresh`. Снимка нет вовсе, битая строка в «Журнале», у харнеса пустая секция
`[quota]`: расход тогда считается по тому, что есть, а причина уходит хвостом
строки. Расход по неполной цепочке занижен, и молчать про пропуск нельзя.

Мера честна ровно настолько, насколько честны бакеты панели: они общие на
машину, и параллельная чужая сессия тратит тот же `week_all`, а дельта припишет
её расход цели. Лимит поэтому верхняя граница трат машины за время цикла, а не
точный счётчик цели; точнее по имеющимся данным не посчитать, и изображать
точность команда не берётся. Говорится это в строке остановки:

```text
gate: over
week_all: потрачено 12 из 10, исчерпан; week_max: потрачено 4 из 10; потолок яруса base; точек расхода 3; снимок 0м назад; бюджет цели исчерпан по week_all, цикл останавливается; мера верхняя: бакеты общие на машину, чужая сессия тратит те же проценты
```

Тем же вызовом гейт отмечает цель в реестре сторожка цикла
(`~/.devkit/goals`, разбор в [devkitctl](../devkitctl/README.md#сторожок-цикла-цели)):
файл на цель, а в нём ID, корень проекта, файл цели и время витка. Место это
выбрано не случайно, гейт единственная точка, через которую проходят оба входа
цикла, оболочка `goal-run` и сессия живого чата, а замок оболочки живёт только у
неё. Отметка идёт до счёта: вставший цикл надо заметить и тогда, когда сам гейт
кончился ошибкой. Запись переписывается целиком, вместе с отметкой стопа,
которую ставил сторожок, потому что вызов гейта это и есть движение цикла.
Провал записи гейт не роняет, как и провал журнала запусков: без надзора цикл
работает, просто молча.

Граница читается как написана: `week_all <= 25` значит, что 25 пунктов это ещё
`ok`, а 26 уже `over`. Сам гейт стоит в начале витка, а не внутри него, поэтому
начатый виток доезжает до конца и расход перескакивает границу на его
стоимость. Витки короткие по построению, так что лимит читается как «примерно
столько», а не «ни пунктом больше».

### Потолок яруса цели (--goal у pick)

Вторая половина цены цели это потолок моделей. Задаётся он строкой `ярус` в том
же разделе «Бюджет», а применяет его pick, когда цикл зовёт его с файлом цели:

```bash
agentctl pick DK-101 --goal docs/tasks/DK-100.md --record
```

```text
model: sonnet
effort: high
tier: base
via: claude-code
DK-101 (task, цена M, неопределённость 1): задача для дешёвых моделей не подходит, по умолчанию идёт сильной, effort поднят до high: base дёшев, экономить глубину смысла нет; потолок цели: base, pro -> base; квота: week_all 22%, снимок 0м назад, сдвига нет
```

Потолок режет вердикт последним шагом ярусной оси, после override и корректора,
и только вниз: пользователь задал рамку трат, а не назначил ярус, и подтягивать
потолком дешёвый вердикт вверх значило бы тратить бюджет там, где его никто не
просил. Строку override в файле задачи потолок режет тоже: оба решения ручные,
но бюджетную рамку пользователь задал на всю цель, и задача внутри цели её не
переопределяет. Effort потолок не трогает вовсе, а пол base считается по
итоговому ярусу, как у корректора.

Исключение одно: грумминговый вердикт ниже `pro` не режется. Нарезка цели
дешёвой моделью выйдет плохой, и весь бюджет уедет на переделку, так что
экономия тут мнимая. Строки `ярус` в файле цели нет, значит потолка нет и
вердикт работает как обычно; файла нет вовсе, значит отказ, а не тихая работа
без рамки.

Причина среза идёт и в человеческую строку вердикта, и в запись `--record`
вместе с исходным маппингом, молчаливой подмены нет:

```text
- Исполнение: субагент sonnet/high по вердикту pick (маппинг opus, потолок цели: base, pro -> base; квота: week_all 22%, снимок 1м назад, сдвига нет), 2026-08-03.
```

Стопом превышение потолка не делается сознательно: потолок задан с открытыми
глазами про потерю качества, а цель превыше всего.

## Харнес: профиль, слои и детект

Харнес это инструмент, в котором живёт сессия агента (Claude Code, Codex,
OpenCode, Gemini CLI, Cursor). Портируемое ядро devkit от него не зависит, а
всё, что зависит, вынесено в профиль: файл `kit/harness/<имя>.toml` в devkit,
объявляющий возможности инструмента по осям. Дизайн разобран в
[DK-033](../../docs/lld/DK-033-universal-kit.md), тут краткий пересказ.

Формат профиля это подмножество TOML: секции одного уровня, ключи `key =
value`, значения это строки в двойных кавычках, целые, `true`/`false` и массивы
строк в одну строку, комментарии с решётки. Вложенных таблиц, дат,
многострочного и literal-строк нет, и парсер за эту границу не выпускает.
Читают профиль две реализации, agentctl на Go и devkitctl на Python, поэтому
входы у них общие: `kit/harness/testdata` с ожидаемым отчётом на каждый файл, и
сверяются с ним обе стороны.

Обязательных секций пять, и все пять обязаны быть в файле, хотя бы пустыми:
пустая секция это явное «оси у инструмента нет», а пропущенная это ошибка. Так
профиль нового инструмента нельзя написать, забыв про ось. Шестая секция,
`[skills]`, необязательна: она появилась позже
([DK-100](../../docs/lld/DK-100-context-tree.md)), и профиль, написанный до неё,
обязан читаться и дальше.

| Секция | О чём | Пустой быть может |
|---|---|---|
| `detect` | как узнать себя изнутри сессии (`env`, `value`) и найти инструмент в PATH (`bin`) | да, тогда активным его делают только флаг, переменная или `default` |
| `rules` | как до инструмента доезжают правила: `mode` это `import`, `embed` или `render`, дальше пути | нет |
| `delegate` | как задача уходит исполнителю: `mode` это `native`, `cli` или `none`, шаблон команды, маппинг-предложение `map_mini`..`map_max` | нет, `mode` обязателен всегда |
| `hooks` | что инструмент даёт по событиям: `protocol` разбора входа, `config`, `events`, `memory_index` | да, тогда тексты держит только git-рубеж |
| `quota` | чем снимается остаток: `snap`, `buckets`, `required`, `spend_mini`..`spend_max` | да, тогда корректор для этого харнеса выключен |
| `skills` | есть ли у инструмента скиллы и как они до него доезжают: `discovery` это `auto` или `manual`, плюс `dir` и `format` | да, тогда скиллов у него нет; секции нет вовсе, значит про ось ещё не разбирались |

Валидируется профиль на каждой загрузке, отдельной команды проверки нет: пять
секций на месте, обязательные ключи при выбранных режимах, значения режимов из
перечня, `spend_*` и `required` ссылаются только на бакеты из `buckets`.
Нарушение это жёсткая ошибка с именем файла и ключа, потому что битый профиль
хуже отсутствующего: он молча выключил бы ось. Незнакомый ключ, незнакомая
секция и незнакомое событие это предупреждение, а не отказ: старый бинарь
обязан переживать профиль из более свежего devkit. Профили целиком, а не только
активный, прогоняет `devkitctl doctor`.

### Слои конфигурации

Три слоя одного формата, сверху вниз:

1. профиль в devkit: что инструмент умеет, обновляется вместе с devkit;
2. машинный `~/.devkit/harness.local`: что на этой машине включено (`enabled`),
   какой по умолчанию (`default`) и как ярусы разворачиваются в модели (секция
   на харнес с ключами `mini`, `base`, `pro`, `max`, плюс необязательные
   `budget` и `bin` для инструмента вне PATH). Ярусы задаются либо все четыре,
   либо ни одного: сложенные соседние пишутся повторением модели, пропуск одного
   ключа из четырёх неотличим от забытого и поэтому ошибка, а секция вовсе без
   ярусов это харнес, который в конфиге присутствует только назначением соседей и
   своей машинной обвязкой (встав активным, он останется ненастроенным);
3. проектный `.devkit/harness.local` (гитигнорнут, как `deploy.local`): понимает
   только `enabled` и машинный список сужает, добавить им ничего нельзя.

Конфликты разрешаются в сторону «не гадать»: имя без профиля в `kit/harness/`
выбрасывается с предупреждением, что вне пересечения слоёв, тоже, а пустое
пересечение равносильно «не определилось». Включённый харнес без своей секции
маппинга считается ненастроенным: ярусная часть вердикта работает, модель
разворачивать нечем. Машинного конфига нет вовсе, значит слияние отдаёт одну
строку: включён `claude-code` с маппингом-предложением из его профиля, то есть
до первой настройки поведение остаётся сегодняшним.

### Назначение яруса и уехавшая ступень

Значение ключа-яруса в машинном слое получает необязательный префикс с именем
харнеса: так ярус уезжает в чужой инструмент, у которого своя подписка и свои
лимиты. Дизайн в
[DK-090](../../docs/lld/DK-090-heterogeneous-ladder.md).

```toml
[claude-code]
mini = "haiku"
base = "glm-code:glm-5.2"
pro = "opus"
max = "fable"
```

Разделитель это первое двоеточие: слева каноничное имя харнеса, справа всё
остальное как имя модели. Второй разделитель отнимал бы часть пространства имён,
а двоеточия в именах моделей чужих инструментов бывают, так что модель с
двоеточием внутри (`llama3:8b`) пишется с явным префиксом своего харнеса
(`claude-code:llama3:8b`). Значение без двоеточия читается как раньше и означает
домашнюю ступень; префикс, совпавший с активным харнесом, значит то же самое,
запись избыточна, но законна.

Ступень **домашняя**, когда её харнес совпадает с активным, и **уехавшая**,
когда не совпадает; лестница **гетерогенная**, когда среди четырёх ступеней есть
уехавшие. Что devkit делает с назначением:

| Что в значении | Что делает devkit |
|---|---|
| имя без профиля в `kit/harness/` | назначение битое: предупреждение слияния с именем файла и ключа, ступень не разворачивается (`model: -`, `via: -`) |
| имя с профилем, но вне `enabled` | назначение действительно, вердикт полноценный; заметка `agentctl harness`, потому что раскладки devkit (правила, хуки, скиллы) у такого харнеса нет |
| имя активного харнеса | домашняя ступень |
| пустое имя до двоеточия (`base = ":opus"`) | жёсткая ошибка чтения машинного слоя: это опечатка, а не запись |
| пустая модель после двоеточия | жёсткая ошибка там же |

Битое назначение `pick` не роняет: читающая команда не имеет права отказать
из-за инструмента, от которого ярусная половина вердикта не зависит, поэтому в
машинных строках стоят прочерки, а причина уходит хвостом. Корректор на такую
ступень вердикт не двигает: сдвиг ради прочерка вместо модели это потерянный
вердикт. `agentctl harness`, наоборот, называет поломку именем файла и ключа: у
него работа как раз в этом.

Корректор пока считает бакеты одного харнеса, поэтому вердикт, вставший на
уехавшую ступень, идёт без корректора с причиной хвостом, и сдвиг через границу
подписок тоже не идёт:

```text
DK-018 (task, цена L, неопределённость 1): задача для дешёвых моделей не подходит, по умолчанию идёт сильной; корректор: дефицит week_all, ступень base уезжает в glm-code, чужую подписку мерить нечем, сдвига нет
```

Мерить дефицит уехавшей ступени домашним снимком значило бы врать, а печатать
бакеты итоговой ступени по домашнему профилю врать во второй раз. Снимется
сторож тогда, когда корректор научится считать ступень по её подписке.

Запись `--record` в файле задачи называет исполнителя так, чтобы по закрытой
задаче восстанавливалось, чьей подпиской она сделана: у уехавшей ступени имя
харнеса стоит перед моделью тем же `харнес:модель`, что и в машинном конфиге, а
слово идёт по режиму делегирования харнеса-исполнителя (`субагент` при `native`,
`подпроцесс` при `cli`). Домашняя ступень нативного харнеса пишется как раньше,
и написанные до этого файлы задач читаются одинаково.

```text
- Исполнение: подпроцесс glm-code:glm-5.2/high по вердикту pick (квота: ступень base уезжает в glm-code, остаток чужой подписки мерить нечем, вердикт без корректора), 2026-08-07.
```

Имена бакетов в хвосте состояния квоты квалифицируются харнесом там, где бакет
не активного харнеса (`glm-code/week_all`). Домашние бакеты остаются голыми, и
однородный вывод не меняется ни на байт.

### Детект активного харнеса

Порядок, первое сработавшее решает:

1. флаг `--harness <имя>`;
2. переменная `DEVKIT_HARNESS`;
3. `[detect]` по переменным окружения;
4. `default` машинного конфига, если он в слитом списке;
5. не определилось: ярусная часть вердикта работает, модель развернуть нечем.

`DEVKIT_HARNESS` стоит выше детекта по окружению не для красоты. Подпроцесс
наследует окружение родителя, и внутри инструмента, поднятого из сессии Claude
Code, `CLAUDECODE=1` родителя останется видимым рядом с переменными самого
инструмента: детект в таком гнезде неоднозначен по построению. Нашлось больше
одного совпадения, значит devkit не гадает, а идёт дальше к `default` и говорит
про неоднозначность вслух. Шаг 3 смотрит и профили вне включённого списка:
сессия внутри установленного, но не включённого инструмента не должна молча
уезжать в `default`, поэтому такое совпадение харнес не активирует, но даёт
заметку в выводе.

### Команда harness

```bash
agentctl harness
```

```text
харнес: claude-code (детект по переменной CLAUDECODE)
включены: claude-code, glm-code (/Users/me/.devkit/harness.local)
маппинг ярусов: mini = haiku, base = glm-code:glm-5.2, pro = opus, max = fable (машинный конфиг)
назначение: ярус base уезжает в glm-code
делегирование: native (профиль /Users/me/projects/devkit/kit/harness/claude-code.toml)
снимок квоты: /Users/me/.devkit/quota/claude-code.local, возраст 12м
```

Это окно в резолв: любой сдвиг поведения между машинами объясняется командой, а
не чтением трёх конфигов руками. Уехавшая ступень называется своей строкой, и
она же говорит про неполную раскладку, когда харнес назначения не в списке
включённых: подписку перепутать легко, а замечается это по счёту, то есть
поздно. Ниже идут заметки резолва (неоднозначный детект, сессия внутри
невключённого инструмента, пропущенный `default`) и предупреждения слияния,
среди них битое назначение. Харнес не определился, значит первая строка так и
говорит, а пустой список включённых называет файл, куда вписывается `enabled`.
Битый профиль это отказ с ненулевым кодом, именем файла и ключа. Флаг
`--harness <имя>` перебивает детект, как и `DEVKIT_HARNESS`.

Директорию профилей бинарь ищет сам: переменная `DEVKIT_HOME`, затем корень
проекта (в самом devkit профили лежат там), соседний с проектом клон devkit и
`~/projects/devkit`. Не нашёл, значит говорит, где искал.

Этим же маппингом pick разворачивает ярус в строку `model`, и делает это
последним шагом расчёта. Битый профиль команде `harness` это отказ, а pick от
него не падает: ярусная половина вердикта от инструмента не зависит, поэтому
вместо модели встаёт прочерк, а причина уходит хвостом человеческой строки.
Читающая команда, которая молчит про сломанный контур, была бы хуже: вердикт
без модели выглядел бы обычным.

## Определения субагентов

Модель субагента диспетчер передаёт параметром при спавне, а effort приходит
только из определения агента. Поэтому в devkit лежит набор `kit/agents/` по
определению на уровень маппинга, и так для каждой роли:

- `exec-low.md`, `exec-medium.md`, `exec-high.md`, `exec-xhigh.md`
- `review-low.md`, `review-medium.md`, `review-high.md`, `review-xhigh.md`

Во frontmatter прибит `effort`, модель не прибита намеренно: одно определение
обслуживает любую модель, которую назвала первая строка вердикта, иначе набор
пришлось бы держать матрицей моделей на уровни. Тело определения короткое, вся
рабочая инструкция это ссылка на правила репозитория и постановку в файле
задачи; у ревьюверов вместо неё сказано, что замечания пишутся через
`taskctl review add`, а код правит исполнитель.

Ставятся определения в пользовательскую директорию, чтобы быть доступными во
всех проектах:

```bash
cp ~/projects/devkit/kit/agents/*.md ~/.claude/agents/
```

Руками этого делать не надо: раскладку и перекладку разошедшегося держит
`devkitctl doctor --fix`. Запущенный из worktree ветки задачи, а не из
основного чекаута, он по-прежнему только называет находку.

Уровня `max` в наборе нет: маппинг его не выдаёт, а под override-строку
определение заводится по месту в проекте.

## Override в файле задачи

Часть случаев (3D-графика, дизайн интерфейсов) в метаданных доски не видна:
тип и цена ничего не говорят про домен. Для них в файле задачи
`docs/tasks/<ID>.md` заводятся строки override:

```text
Модель: max (3D-графика)
Эффорт: max (незнакомый домен)
```

Допустим и вариант пунктом списка (`- Модель: max`), поясняющий хвост в
скобках необязателен. Строки живут в файле задачи, не в строке доски: формат
строки доски фиксированный, его парсят три утилиты, а файл задачи доска
только индексирует. pick перед маппингом читает файл, если он есть, и ищет
такие строки.

Оси независимы, каждая перебивается своей строкой, а незаданная берётся из
обычного маппинга. Домен диктует то модель, то глубину размышления, то и
другое сразу, и связывать их одной строкой значило бы заставлять писать лишнее.
Из этого следует неочевидное: override модели на грумминговом вердикте
оставляет effort `xhigh` (маппинг про задачу не передумал), и если исполнять
её надо буднично, рядом ставится и «Эффорт:».

Найденный override перебивает ярусную часть маппинга целиком, включая LLD- и
грумминг-правила, `Groom` при этом всегда `false`, а в причине вердикта сказано,
что модель задана override-строкой; про effort в причине появляется своя
пометка. Допустимые значения строки «Модель:» это ярусы `mini`, `base`, `pro`,
`max` и старые имена моделей `haiku`, `sonnet`, `opus`, `fable`, которые
переводятся в ярус псевдонимами (`haiku -> mini`, `sonnet -> base`,
`opus -> pro`, `fable -> max`). Псевдонимы живут дольше миграции: строки в уже
написанных файлах задач сделаны старыми именами, и ломать их об жёсткую ошибку
нельзя. Конкретную модель инструмента (`claude-opus-4-6`, `gpt-5.2`) писать
нельзя сознательно: строка в файле задачи переживает смену харнеса, ярус
переносим, имя модели нет. Допустимые значения эффорта `low`, `medium`, `high`,
`xhigh`, `max`; любое другое значение по обеим осям это жёсткая ошибка pick
(опечатка не должна молча провалиться в обычный маппинг).
Нет файла или нет строк, работает обычный маппинг из таблицы выше. Валидацию
держит сам pick, `taskctl lint` эти строки не проверяет: lint проверяет
инварианты доски, а не содержимое файлов задач.

Парсер читает файл целиком и берёт по каждой оси первую попавшуюся строку, не
разбирая контекст: если override уже есть выше по файлу, вторая строка
молча игнорируется, а строка внутри code-fence (пример формата) сработает
как настоящий override. Поэтому в реальном файле задачи держать не больше
одной такой строки на ось и не класть примеры формата с двоеточием после
«Модель» и «Эффорт»; если пример всё же нужен, писать его без двоеточия.

## Запись исполнения (--record)

`agentctl pick DK-002 --record` помимо вердикта дописывает строку в раздел
«Ход работы» файла `docs/tasks/DK-002.md`:

```text
- Исполнение: субагент haiku/low по вердикту pick (квота: week_all 41%, снимок 10м назад, сдвига нет), 2026-07-28.
```

Через дробь идёт effort из вердикта, то есть какое определение из `kit/agents/`
взято. Строка несёт модель, а не ярус: по ней восстанавливают, чем задача
делалась. Развернуть ярус нечем (харнес не определён или не настроен), значит в
строку идёт сам ярус, иначе исполнителя в записи не осталось бы вовсе.

В скобках идёт состояние квоты на момент решения, и идёт оно всегда, а не
только на сдвиге: проценты бакетов, из которых платят исходный и итоговый
ярусы, возраст снимка и был ли сдвиг. Без этого одинаково выглядят три разных
случая (корректор выключен вовсе, снимок в норме, снимок протух и профицит не
применялся), а по закрытой задаче потом не восстановить, на каких данных
выбиралась модель. Предупреждения человеческой строки в файл задачи не идут,
так что состояние там единственный источник.

```text
- Исполнение: субагент opus/medium по вердикту pick (квота: снимка нет, корректор выключен), 2026-07-29.
- Исполнение: субагент opus/medium по вердикту pick (квота: week_all 5% профицит, снимок 3ч 0м назад, протух, сдвига нет), 2026-07-29.
```

Сдвинутый корректором вердикт несёт в скобках ещё и маппинг с причиной сдвига,
иначе по файлу задачи не понять, почему модель разошлась с таблицей; куда съехал
ярус, сказано там, и состояние про сдвиг тогда молчит:

```text
- Исполнение: субагент sonnet/high по вердикту pick (маппинг opus, корректор: дефицит week_all; квота: week_all 95% дефицит, снимок 10м назад), 2026-07-30.
```

С флагом `--role review` строка пишется словом «Ревью» вместо «Исполнение»,
так что по «Ходу работы» видно и кто делал задачу, и кто читал её дифф:

```text
- Ревью: субагент sonnet/high по вердикту pick (квота: week_all 41%, снимок 10м назад, сдвига нет), 2026-07-31.
```

Так исполнитель остаётся там, куда смотрит пользователь, а не только в
транскриптах сессий. Запись это самоотчёт диспетчера (он фиксирует, кого
собрался спавнить), доказательством она не является. Грумминговый вердикт
(неопределённость >= 4, цена XL) пишется словом «Грумминг» вместо
«Исполнение»: работа по нему не начинается, и строка не обещает того,
чего не было. Без раздела «Ход работы»
тот добавляется в конец файла; повторный вызов дописывает новую строку, история
перезапусков сохраняется. Для задачи без файла выходит ошибка с подсказкой
`taskctl file <ID>`: pick с записью зовётся при взятии в работу, а у взятой в
работу задачи файл обязан быть. Вывод в stdout не меняется, git утилита не
трогает: коммит и пуш строки остаются за диспетчером, как у любой правки
файла задачи.

## Установка

```bash
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py update
```

Утилита едет готовым бинарём в релизе devkit вместе с остальными, тулчейна для
установки не нужно. Собрать из исходников (машина разработчика devkit):
`python3 ~/projects/devkit/tools/devkitctl/devkitctl.py build`.
