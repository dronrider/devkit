# dashboard: веб-дашборд агентской разработки

Go-сервер с вшитой статикой: доска и текущие работы проектов с любого
устройства пользователя, запуск и стоп задач и целей, разговор с агентом
панелью справа (лента реплик, поле ввода, журнал витка на экране задачи).
Срез цели DK-112,
решения приняты в [LLD](../../docs/lld/DK-112-dashboard.md): считает всё
сервер, клиент только рисует; источник правды это доска и утилиты, своей
базы нет; строк доски сам сервер в этом срезе не правит, доску он читает, а
двигает строку поднятый им конвейер, как если бы его подняли руками.

Инструмент общий, живёт в devkit и едет готовым бинарём в его релизе, как
`taskctl` и соседи: ставит его в PATH `devkitctl update` (или `build` из
исходников). Держит процесс launchd-агент `ru.devkit.dashboard` с KeepAlive,
его кладёт и поднимает `devkitctl doctor --fix`; тот же доктор проверяет, что
агент поднят и `/healthz` отвечает без ошибок конфига. Замену собственного
бинаря выкатом демон замечает сам по иноде, доживает начатые ответы и
выходит, а KeepAlive поднимает уже новый: правка доезжает до работающего
процесса командой deploy, без правки обвязки.

## Команды

```
serve [--static <dir>]      поднять сервер; --static читает статику с диска
                            вместо вшитой, правка видна по F5 без пересборки
secret [--rotate]           напечатать токен входа; --rotate заменяет секрет,
                            и все выданные куки разом мертвы
smoke [--keep]              сквозной прогон по API на синтетическом окружении,
                            разбор ниже; --keep оставляет его каталог на диске
check [<ID>...] [-C <дир>]  поднять прогон сценария проверки по строкам Check
                            проекта; без ID берётся вся секция, разбор ниже
round <ID>... [-C <дир>]    начать второй круг чужого ревью; живой сессии
                            задачи репликой в её окно, иначе новой сессией
```

## Конфиг

`~/.devkit/dashboard.local`, формат «`key = value`, `#` комментарий», тот же,
что у `.devkit/deploy.local`. Права 600, потому что в файле секрет входа;
файл с правами шире сервер не берёт. Незнакомый ключ это ошибка старта, а не
молчаливый пропуск.

```
# корней несколько, по строке на каждый
root = ~/projects
root = ~/work
addr = 0.0.0.0
port = 7112
token = <секрет входа, рождается сам при первом старте>
```

Умолчания: порт 7112 (по номеру цели), `addr` слушает все интерфейсы (доступ
решает канал, вход решает секрет). Умолчания для `root` нет: пустой список
корней сервер называет в `/healthz` и журнале, а не подставляет что-то молча.

Проект узнаётся как у devkitctl, по `docs/TASKS.md`: проектом считается сам
корень или его прямой подкаталог с доской, глубже обход не идёт. Боковые
деревья задач отсеиваются признаком линкованного worktree (расхождение
`git rev-parse --git-dir` и `--git-common-dir`). Совпадение имён проектов из
разных корней это ошибка конфига: оба выпадают из списка и называются в
`/healthz`, а не молча берётся первый попавшийся.

## Вход

Единый секрет-токен и подписанная кука (разбор развилки в LLD). Секрет
рождается на машине при первом старте `serve` и живёт строкой `token` в
конфиге; по сети он не ездит. На устройство токен переносится руками один
раз: печатает его `dashboard secret`, вставляется он на странице `/login` и
живёт в менеджере паролей. Сервер сверяет токен константным временем и
ставит куку HttpOnly SameSite=Lax на 30 дней: значение это срок действия с
подписью HMAC-SHA256 от секрета, состояния сессий на сервере нет, и рестарт
демона никого не разлогинивает.

Утечка лечится ротацией: `dashboard secret --rotate` заменяет секрет. Подпись
всех выданных кук перестаёт сходиться, и токен вводится заново. Ротация
действует на живой демон сразу, без рестарта: секрет перечитывается из
конфига по mtime файла на каждой проверке входа. Дорогой разбор всей строки
идёт только при изменившемся файле. Провал перечитывания (файл временно
недоступен) не роняет сервер и не открывает вход: действует последний удачно
прочитанный секрет, а причина видна в `/healthz` и журнале. Перебор токена
гасится секундной паузой после провала входа и строкой в журнале. CSRF закрыт
SameSite=Lax и сверкой Origin на изменяющих методах, XSS тем, что тексты
досок рисуются текстом, а CSP запрещает инлайн и внешние источники.

Без входа не отдаётся ни одна строка данных: API отвечает 401, страницы
уводят на `/login`. Открыты только сам `/login` с его обвязкой и `/healthz`.
TLS сервер не заводит: канал это решение выката, а не архитектуры.

## Заход извне

Дома дашборд открывается по адресу рабочей машины в своей сети, и больше
ничего не нужно. Извне канал даёт браузерный вход соседнего проекта xr-proxy:
телефон приходит по HTTPS на фронт входа (VPS RU), фронт через relay достаёт
клиента шар на рабочей машине, а тот проксирует запрос на `127.0.0.1:7112`.
Своего порта наружу машина не открывает и в NAT не пробивается: соединение до
VPS держит сам клиент шар, изнутри.

Дверей на пути две, и обе свои: сначала владельца пускает фронт входа
(логин и пароль админки хаба xr-proxy, имя из `[[admin.users]]` его конфига), потом токен спрашивает сам
дашборд. Порядок этот не совпадение: плейнтекст браузерной сессии живёт в
памяти фронта, то есть фронт это доверенный посредник, и вход дашборда его
доверием не заменяется.

Подключение делается на стороне xr-proxy, дашборд для него ничего не
настраивает:

1. на рабочей машине поставить клиент шар с поддержкой relay
   (`cargo build --release -p xr-share --features relay` в чекауте xr-proxy),
   привязать его к хабу (`xr-share install --hub <хаб> --token <рег-токен из
   админки>`) и поднять автозапуском (`xr-share service install`, нужен root);
2. завести публикацию на дашборд:
   `xr-share expose add --name <имя> --upstream 127.0.0.1:7112`. Имя
   публикации становится поддоменом входа, и оно же уникально на весь хаб;
3. на VPS RU выпустить сертификат на это имя и добавить правило фронта; DNS на
   новую публикацию не трогается, звёздочка на домен входа стоит с выката
   xr-proxy.

Заголовки на этом пути ведут себя как у любого сервиса за прокси: клиент шар
переписывает `Host` на адрес апстрима, а внешнее имя кладёт в
`X-Forwarded-Host`. Дашборд берёт внешнее имя оттуда в сверке `Origin`, иначе
изменяющие запросы, начиная с самого входа, отвечали бы «чужой Origin» и с
телефона было бы не войти. Живая лента идёт по SSE, и её соединение фронт
рвёт по потолку сплайса (на выкате час); `EventSource` переподключается сам,
так что видно это как секундный разрыв ленты, а не как мёртвый экран.

Что заход извне жив, видно двумя командами. Адрес входа и пароль владельца
это чувствительное, в devkit они не едут и лежат именами в хранилище
`secretctl`:

```sh
# фронт входа отвечает (сама машина при этом может быть и выключена)
secretctl exec DASHBOARD_ENTRY -- \
    sh -c 'curl -fsS "$DASHBOARD_ENTRY/.xr-web/healthz"'          # -> ok

# весь путь до дашборда: вход владельца, потом /healthz самого дашборда
secretctl exec DASHBOARD_ENTRY -- secretctl exec DASHBOARD_ENTRY_PASSWORD -- \
    sh -c 'jar=$(mktemp) && \
      curl -fsS -o /dev/null -c "$jar" "$DASHBOARD_ENTRY/.xr-web/login" \
           -d "username=admin&password=$DASHBOARD_ENTRY_PASSWORD" && \
      curl -fsS -b "$jar" "$DASHBOARD_ENTRY/healthz"; rm -f "$jar"'
# -> {"errors":[],"ok":true,"projects":N,...}
```

Первая команда отвечает `ok` на любом поддомене и до машины не идёт, поэтому
живость публикации она не доказывает. Доказывает вторая: JSON `/healthz`
рождается уже на рабочей машине. Машина не на связи, и фронт отвечает 502
страницей «Машина не на связи»; имени нет в хабе, и он отвечает 404.

Такой отказ приходит в браузер страницей html, а не JSON, и переводит его в
слова `outerFail` в `static/app.js`. Отказ этот не дашборда, а ворот перед ним,
и сказано так и есть: 502 это ворота не достучались до дашборда на машине
(ноутбук уснул, сеть моргнула, дашборд перезапускался), 504 это достучались и
не дождались ответа. Хвостом идёт судьба набранного, и она разная у разных
запросов: реплику панель дожимает сама, у прочей отправки повтор за человеком,
а чтение экрана повторится следующим заходом.

## API

Все ручки под `/api`, JSON, вход кукой. Доску сервер берёт подпроцессом
`taskctl list --json`, своего разбора markdown у него нет. Ищется taskctl
сначала рядом с бинарём самого дашборда (под launchd PATH системный, а
утилиты devkit лежат одним каталогом), потом по PATH; не нашёлся нигде, это
названная ошибка в `/healthz` и в каждом ответе доски, потому что тихая
деградация неотличима от «задач нет».

- `POST /api/login` (`{"token": "..."}`) и `POST /api/logout`;
- `GET /api/projects`: проекты по конфигу корней: имя, путь, префикс ID доски
  (`prefix`, им проект подписан на главной), счётчики секций
  и живые работы: tmux-сессии `goal-*`/`task-*`, привязанные префиксом ID
  доски. Хвост имени после префикса обязан выглядеть как ID (та же проверка, что
  у ручек журнала и черновика), иначе сессия работой не считается: у
  производной сессии конвейера (`task-DK-208_1_1786532648`, номер и
  unix-момент запуска после ID) войти в неё всё равно некуда (DK-279). Дальше
  цели из реестра `~/.devkit/goals`, привязанные корнем (цикл, который
  ведёт другая сессия, без tmux-сессии), и интерактивные сессии человека в окне
  агента, узнанные свежим транскриптом (`via: session`, порог двенадцать
  минут, разбор в LLD DK-112). Порог держит только окна людей: транскрипт,
  чья первая реплика это заказ груминга (`Проведи груминг ...`, слова
  groomPrompt из ручки черновиков), жив, пока жива его tmux-сессия, и после
  смерти `claude -p` работой не считается (DK-358): законченный разбор
  иначе висел бы живым до протухания транскрипта, а снять интерактивную
  работу с экрана нельзя. Фильтр узнаёт заказ, а не говорившего, поэтому
  интерактивное окно, где человек заказал груминг теми же словами прямо в
  чате агента, карточки живой работы тоже не получит (сама работа видна в
  экране сессий и ленте задачи; жертва принята в разборе DK-358). У
  интерактивной работы есть поле `session` с
  id транскрипта, а `id` стоит только при узнанной задаче; не узнав задачу,
  работа остаётся в списке с подписью `note`. Вид (`kind`) у неё берётся со
  строки доски, чтобы цель осталась целью и в интерактивном окне, а без
  строки это `session`. Заголовок строки доски едет полем `title`: им работа и
  подписана на экране, имя сессии `goal-DK-112` о занятии агента не говорит
  ничего и остаётся мелкой подписью; без строки на доске поля нет. Статус
  строки едет ключом секции в поле `sect` (`in-progress`, `check`, `backlog`,
  `blocked`), русское слово ему подбирает клиент; без строки на доске поля
  тоже нет. Момент
  начала едет полем `started` (unix-секунды): знает его один tmux, у которого
  сессия заведена, а запись реестра и транскрипт помечены последним касанием, и
  у такой работы поля нет вовсе, потому что ноль минут был бы неотличим от
  только что поднятой. Ненайденный tmux называется в
  `/healthz`, в списке проектов и в ответе доски, а не отдаёт молча пустые
  работы; tmux без единой сессии (его сервер не живёт, `ls` отвечает
  ненулевым кодом) это штатно пустой список без ошибки;
- `GET /api/projects/{p}/board`: доска проекта, как её отдал
  `taskctl list --json`, рядом живые работы. Каждой строке сервер дописывает
  поле `run`, признак идущей работы: `tmux` у конвейера (его «Стоп» снимает
  сессию целиком), `chat` у работы, идущей в нашем окне разговора (там «Стоп»
  прерывает ход), `registry` у цикла цели, поднятого другой сессией, `session`
  у чужого окна и `gone` у строки из In progress, за которой живой сессии нет
  вовсе. У стоящей задачи поля нет. Признак едет
  строкой, а не собирается на клиенте сведением с полем `works`: сведение по
  ID отвечало на один вопрос, «есть ли сейчас работа с таким же номером», и
  оборванный конвейер был в нём неотличим от очереди (DK-317).
  Рядом едет `run_stopping` у строки, чей стоп уже нажат и дожимается.
  Рядом едут `run_state` и `run_busy`, состояние строки свёрткой по её рабочим
  сессиям: `busy` (ход идёт хоть у одной), `waiting` (кто-то ждёт человека, а
  хода нет), `idle`, `dead`. Рабочей сессию задачи делает запись реестра со
  словом источника «дерево» или «работа»; имя tmux-сессии в критерии не
  участвует, разбор в `docs/lld/DK-430-task-chat.md`, решение 8. Тем же
  заходом дописывается `run_chat`, разговор с идущим ходом. В него ведёт иконка
  чата у строки, а при нескольких рабочих сессиях сервер называет свежайшую по
  последней реплике. Тем же заходом
  дописывается поле `order`, заказ дословно: его считает `rowOrder`, та же
  функция, что собирает промпт headless-сессии (DK-286). Подсказка кнопки
  запуска на экране читает готовое поле, а не пересказывает заказ вторым
  разбором на клиенте: второй разбор рано или поздно разошёлся бы с настоящим
  заказом. У строки цели нет поля, следующий виток сочиняет `goal-run.py`, а
  не дашборд; у проверенной строки с пользовательской приёмкой тоже нет, она
  закрывается прямо с экрана командой `taskctl close`, без сессии агента.
  Тем же заходом дописываются поля `stage` и `stage_since`, вид деятельности
  словом (`разработка`, `ревью`, `снаружи`, `уточнение`) и начало этапа в
  unix-секундах, теми же единицами, что `started` у живой работы. Конвейер
  отмечает этап записью `~/.devkit/runs/<ID>-<slug>.run` (её формат в
  `tools/agentctl/README.md`, раздел «Отметка этапа»), дашборд её только
  читает: пиши он этап сам, работа, поднятая из терминала, осталась бы
  неотмеченной (DK-338). Оборванный этап за работу не выдаётся: запись
  переживает и умершую сессию, поэтому вид деятельности едет только у строки с
  живым признаком `run`, тем же рубежом, что `gone`. Ожидание снаружи из этого
  правила исключено: там ждут человека, по смыслу за таким этапом нет живой
  сессии, и требовать её значило бы гасить единственный этап, который экран и
  должен показать серым.
  Тем же заходом дописывается поле `waiting`, состояние «ждёт человека»
  (`waiting.go`): состояние словом, машинный разряд источника, подпись
  словами, вопросы пачкой, момент начала и срок в unix-секундах и ждущая
  сессия. Пустое поле значит, что никто никого не ждёт, а у непустого источник
  назван всегда: разбор источников ниже, в разделе «Ожидание человека».
  Строки при разметке идут через общие карты, поэтому ключи в ответе стоят по
  алфавиту, а не в порядке утилиты; состав строки при этом полный, включая
  поля, которых сервер не знает. Те же поля несёт строка в ответе `GET
  /api/projects/{p}/tasks/{id}`;
- `GET /api/projects/{p}/search?q=`: поиск задач четырьмя группами в постоянном
  порядке: `board` («Доска»), `drafts` («Черновики»), `archive` («Архив») и
  `text` («В тексте задач»). Ищется номер, заголовок и текст файлов задач,
  регистр не важен, а запрос, похожий на номер, поднимает точное попадание
  первой строкой группы, причём `324`, `dk-324` и `DK324` считаются одним
  номером. Доска берётся из кэша сервера, накопитель у
  `taskctl draft list --json`, архив разбирается файлом `docs/TASKS-archive.md`,
  а текст ищется обходом `docs/tasks` вместе с подкаталогами `archive/<год>` и
  `drafts`; индекса нет вовсе, потому что инвалидировать его пришлось бы на
  каждой правке файла задачи. Строка выдачи одного вида на все группы, а
  разница между ними это заполненные поля: у доски секция, тип, цена и ранг
  слагаемыми, у черновика возраст, у архивной строки дата закрытия без ранга и
  цены (в архиве этих колонок нет), у найденного в тексте путь файла, номер
  строки, цитата и место (`архив`, `черновик`). Задача, нашедшаяся по номеру
  или заголовку, в текстовую группу второй строкой не попадает. Потолки: запрос
  короче двух символов выдачи не поднимает вовсе, в группе до двадцати строк, в
  текстовой до тридцати, а остаток едет числом в поле `more`, и урезанная
  выдача не выглядит полной. Пустые случаи подписаны словами (`note`): чего
  ждёт короткий запрос и где искали, если не нашлось ничего. Отказ
  `taskctl draft list` остаётся при своей группе и весь поиск не роняет: доска
  с архивом читаются мимо утилиты;
- `POST /api/projects/{p}/drafts` (`{"text": "...", "prio": "mid"}`): черновик в
  накопитель через `taskctl draft`, предел 16 КБ. Текст уезжает утилите на вход
  подпроцесса, а не аргументом: аргумент проходит разбор флагов и стража
  подкоманд, и мысль из одного слова латиницей («fix») или начатая с дефиса
  там теряется целиком. Уровень разбора обязателен и берётся из `prio`
  (`high`, `mid`, `low`): запись без него сервер отбивает сам, не доходя до
  утилиты, а на экране записи уровень выбирается из списка трёх значений со
  средним по умолчанию. В ответе ID и путь `docs/tasks/drafts/<ID>.md`.
  Каталога накопителя на проекте может не быть, это не отказ: заводит его
  первая же команда `draft`;
- `GET /api/projects/{p}/drafts`: накопитель черновиков через
  `taskctl draft list --json`: ID, первая строка записи, путь файла, дата
  записи, возраст днями и словами утилиты, пометка «отложен». Пустой
  накопитель приходит пустым списком со словами `note`: пустая карточка
  неотличима от неотрисованной;
- `GET /api/projects/{p}/drafts/{id}`: текст записи целиком, файлом
  `docs/tasks/drafts/<ID>.md`, и вместе с ним `hash`, база правки. Файла нет,
  это 404 со словами: грумминг мог уже завести по нему задачу;
- `PUT /api/projects/{p}/drafts/{id}` (`{"text": "...", "base": "<хэш>"}`):
  правка записи с экрана. Своей команды на это у `taskctl` нет, и текст ложится
  файлом целиком, а следом идёт коммит доски с пушем (`commitDocs`). Пустой
  текст это 400. Он затёр бы запись, а удаление у черновика своё, с причиной.
  Отказов, кроме пустоты, два, и оба про второго писателя. Живой разбор это
  409. Пока по записи идёт грумминг, файл принадлежит агенту, он его читает и
  уносит исходом. Спрашивается это тем же вопросом, что и подъём второго
  грумера (`draftBusy`). Живое ожидание ответа замок снимает. Агент спит в
  инструменте ожидания, файла не трогает, и ответ правкой текста законен.
  Разошедшаяся `base` это тоже 409. Ответ несёт текущий текст с новым `hash`,
  и экран показывает оба. Правка без базы отбивается так же: сверять её не с
  чем;
- `DELETE /api/projects/{p}/drafts/{id}` (`{"reason": "..."}`): удаление
  записи через `taskctl draft drop`. Причина обязательна и здесь, и у утилиты:
  файла после команды нет, и причина уезжает только сообщением коммита доски,
  который ручка делает следом. Пустая причина это 400 со словами, пропавший
  черновик 404;
- `POST /api/projects/{p}/drafts/{id}/groom` (`{"ask": "..."}`, тело
  необязательно): разбор черновика. Поднимает tmux-сессию `task-<ID>` с
  headless-сессией конвейера и заказом «Проведи груминг DK-NNN», теми же
  словами, какими эту работу просят в чате. Имя сессии с префиксом `task-` не
  случайно: грумминг кончается строкой доски с тем же ID (`taskctl add --id`), и
  работа видна в общем списке работ проекта, а стоп ей достаётся тот же самый.
  Уточнение из `ask` дописывается в тот же заказ («Человек уточняет: ...»), и
  это дорога первого слова. Вопрос грумер задаёт штатным AskUserQuestion,
  перехваченным хуком `ask-panel.py`, а человек отвечает на него репликой в
  разговор записи, который панель ведёт адресом `task-<ID>`.
  В закончившуюся сессию дашборд не пишет. Проверки те же, что
  у запуска задачи: пропавший черновик, ненайденный tmux или claude и
  живая сессия с тем же ID называются словами, а не молчаливо мёртвой сессией.
  Заказ дословно («Проведи груминг DK-NNN», без уточнения) едет и списком
  накопителя (`GET .../drafts`, поле `order` записи), и текстом записи (`GET
  .../drafts/{id}`, то же поле): кнопка «Провести груминг» показывает его
  подсказкой до нажатия, читая готовое поле у `groomPrompt`, а не пересказывая
  его вторым разбором на клиенте (DK-286);
- `POST /api/projects/{p}/tasks`: полная строка через `taskctl add`. Поля те
  же, что у правки: `title`, `type`, `cost` и слагаемые `r_parts` (пять
  значений по RANKING.md) либо `rank` строкой «а+б+в+г+д». Файл задачи
  `docs/tasks/<ID>.md` заводит тот же `add`, строка без файла это дыра, и
  ручка не предлагает её заведение без файла; оба пути едут в один коммит
  создания. ID выдаёт утилита, нумерация сквозная и своей у сервера нет.
  Кривой ранг, пустой заголовок и незнакомый тип отбивает она же своими
  словами, а поправку на баг у типа `task` ручка теми же словами, что
  и `PATCH`;
- `GET /api/projects/{p}/tasks/{id}`: строка задачи с секцией, зависимости в
  обе стороны (кого ждёт строка и кто ждёт её, `taskctl dep list --json`) с
  заголовками соседей и текст файла `docs/tasks/<ID>.md`. Файла нет, это
  сказано словами `note`, а не пустым текстом; зависимость без строки на
  доске подписана как закрытая, а не выглядит опечаткой;
- `PATCH /api/projects/{p}/tasks/{id}`: заголовок, тип, слагаемые ранга, цена
  и ссылка через `taskctl set`. Слагаемые идут списком `r_parts` из пяти
  значений по RANKING.md, пропущенное (`null`) остаётся прежним, так правится
  и одно слагаемое, и вся разбивка разом; строкой «а+б+в+г+д» то же самое
  делает поле `rank`. Сумму R, бакет P и место строки в Backlog считает
  утилита; ручки «поставить строку на место N» в API нет, порядок выводится
  из ранга. Поправку на баг ручка сверяет с типом: у `task` слагаемое не
  ставится (по RANKING.md оно про дефект или регресс), и сверяется то, что
  получится после правки, а не то, что стояло, потому что тип со слагаемыми
  едет одним запросом. Ответ называет фактическое место строки полем `place`:
  свежая разбивка с суммой и бакетом, секция и соседи сверху и снизу с их
  рангами. Клиент считает целевой ранг сам, пока идёт жест перетаскивания, но
  это превью по той доске, которую показывал экран, а порядок строк переставляет
  утилита по свежей. Необязательное поле `expect_r_parts` это разбивка,
  которую отправитель считает сегодняшней: разошлась, значит строку успели
  поправить с другой стороны, и ручка отвечает 409 со словами («строку
  поправили, ранг сейчас 41, откат не применён»), а доску не трогает. С этим
  полем едет откат жеста;
- `POST /api/projects/{p}/tasks/{id}/file`: `taskctl file`, чинит строке без
  файла дыру (строка до рубежа либо снятый руками файл): заводит
  `docs/tasks/<ID>.md` по шаблону и чинит ссылку в строке доски;
- `PUT /api/projects/{p}/tasks/{id}/file` (`{"text": "..."}`): текст файла
  задачи целиком, предел 256 КБ. Пустой текст и файл, которого ещё нет,
  отбиваются словами: постановка не затирается, а заводит файл утилита;
- `GET /api/projects/{p}/lld?q=`: документы `docs/lld`, свежие сверху по времени
  правки: ID, файл, заголовок из первой решётки и дата правки. Запрос сначала ищется в
  имени файла и заголовке, а не нашёлся там, идёт по тексту, и совпадение едет
  цитатой со строкой, как в поиске задач;
- `GET /api/projects/{p}/doc?path=lld/<файл>.md` и `PUT` туда же
  (`{"text": "..."}`): текст документа и его правка. Пишется только `docs/lld`:
  у файла задачи своя ручка со своими правилами, а прочего в `docs` дашборд не
  трогает. Пустой текст и несуществующий файл отбиваются словами, новые LLD
  заводятся в репозитории. Правка коммитится и едет в origin тем же путём, что
  правка файла задачи, сообщением `docs(lld): <ID> правка <файл> с дашборда`;
- `POST /api/projects/{p}/tasks/{id}/deps` (`{"id": "DK-NNN"}`) и
  `DELETE /api/projects/{p}/tasks/{id}/deps/{dep}`: `taskctl dep add` и
  `dep rm`. Рубежи держит утилита, и её слова доезжают до экрана: цикл
  зависимостей, живая строка с незакрытой зависимостью, чужой линкованный
  worktree. Каждая правка строки и файла коммитится с пушем тем же порядком,
  что сообщение витку: провал коммита или пуша правку не отменяет и
  называется полем `note`;
- `POST /api/projects/{p}/runs` (`{"id": "DK-NNN"}`, необязательное поле
  `harness`) и `DELETE /api/projects/{p}/runs/{id}`: запуск и стоп, разбор
  ниже. Поле `harness` это выбранная подписка: пусто значит «как раньше», на
  подписке по умолчанию. У проверенной задачи с пользовательской приёмкой
  запуск это само закрытие (`taskctl close`), за ним нет сессии агента;
- `GET /api/harnesses`: подписки машины, из которых собран выбор в кнопке
  запуска: имя, признак «по умолчанию», чем поднимается клиент и имена пар
  окружения. Ручка машинная, а не проектная, как и `/api/quota`: харнесы
  принадлежат машине. Список берётся подпроцессом `agentctl harness --json`,
  а не чтением `~/.devkit/harness.local`: слоёв конфигурации три, и проектное
  сужение при прямом чтении потерялось бы. Показываются одни включённые
  харнесы с клиентом: невключённому devkit не раскладывает правила, хуки и
  скиллы, а без клиента поднимать нечем. Пустой список это не отказ ручки, а
  причина словами в `note` (нет `agentctl`, отказ команды, пустой `enabled`):
  запуск от этого не ломается, он идёт как до DK-326. Ответ живёт в памяти
  процесса полминуты, ответ с причиной вместо списка не запоминается вовсе;
- `POST /api/projects/{p}/chats` (`{"id": "DK-NNN", "ask": "...", "harness": "..."}`):
  поднимает новый разговор по задаче в tmux-сессии `chat-<ID>-<n>`, где `n` это
  первый свободный номер среди живых сессий. Клиент поднимается интерактивным, а
  не headless: headless-ход кончается вместе с ответом, и разговор был бы
  кончившимся к тому времени, как человек прочитает первую реплику. Заказ
  разговорный (`chatPrompt` в `chats.go`): прочитать строку и файл задачи,
  сказать, где она стоит, и ждать реплик, работу не начиная; `ask` уезжает тем же
  заказом первым вопросом. Имя `chat-<ID>-<n>` не ложится под форму работы в
  `internal/works`, поэтому в занятость задачи разговор не считается и
  конвейеру `task-<ID>` не мешает: отказ «работа уже идёт» остаётся у второго
  конвейера и разговоров не задевает. Цель отбивается словами: разговор с ней
  идёт её ручкой, и поднятая сессия читала бы чужой вход. Разговора без задачи
  ручка не поднимает вовсе, заказать такой сессии нечего;
- `GET /api/projects/{p}/goals/{id}/log`: хвост журнала цикла
  `.devkit/goal-<ID>.log` (`?n=` глубина, по умолчанию 200 строк); с
  `?stream=1` соединение остаётся жить как SSE-поток и новые строки
  доезжают по мере записи, файл опрашивается раз в секунду. Источников
  журнала два: цикл под оболочкой `goal-run` пишет `goal-<ID>.log`, а цель,
  которую ведёт живой чат, такого файла не заводит, и её ход лежит в разделе
  «Журнал» файла цели (`docs/tasks/<ID>.md`, путь берётся со ссылки строки
  доски). Ссылка в колонке стоит markdown-разметкой целиком
  («[tasks/DK-112.md](../../docs/tasks/archive/2026/DK-112.md)», так её
  пишет taskctl), путём работает
  адрес в скобках, и считается он от каталога `docs/`, как и у линтера
  taskctl; голая ссылка без разметки читается так же. Ссылка, которая никуда
  не ведёт (путь наружу проекта, чужая схема, файла по ней нет), откатывается
  на обычное место `docs/tasks/<ID>.md`: колонка доски бывает и устаревшей, а
  файл цели лежит рядом, и прочитать его честнее, чем ответить «журнала нет». Без журнала оболочки читается второй источник: строками едут пункты
  списка раздела, проза и соседние разделы туда не попадают. Откуда взяты
  строки, говорит поле `source` (`goal-log`, `goal-file`, `none`) со словами
  в `source_note`, в потоке это событие `source`; заведись журнал оболочки при
  открытом экране, поток скажет `source` заново и дальше повезёт строки
  оттуда. Файл цели переписывается целиком, поэтому в потоке он дострачивается
  не смещением, а по изменению файла и числу уже отданных строк. Пустота
  различима тремя причинами и в каждой называется словами (полем `note`, в
  потоке событием `note`): файла цели нет вовсе, раздела «Журнал» в нём нет,
  раздел заведён и пуст;
- `GET /api/projects/{p}/sessions`: сессии проекта из каталогов журналов:
  каталог берётся по пути проекта, где всё, кроме букв, цифр и дефиса,
  заменено дефисом, плюс каталоги, чьё имя продолжает его дефисом, так в
  список попадают боковые деревья задач. Корней журналов больше одного: свой
  `~/.claude/projects` и `projects` в хозяйстве каждой подписки со своим
  каталогом конфигурации (`home` из `agentctl harness --json`). Клиент второй
  подписки поднимается с `CLAUDE_CONFIG_DIR` и пишет разговор туда. Поэтому
  headless-сессия, поднятая с доски на выбранной подписке, из одного
  `~/.claude` не видна вовсе: строка стоит в In progress, а чата нет ни в
  списке, ни в панели разговора (DK-362). По сессии отдаются id, время
  последней записи (UTC), ветка, боковое дерево (`tree`, у главного дерева
  пусто) и первая реплика человека из шапки файла, а
  также узнанная задача (`task`) с подписью, чем она узнана (`taskNote`:
  «по заказу дашборда», «по дереву задачи», «привязана рукой», «по первой
  реплике», «по ветке», «привязка снята рукой» либо «задача не распознана») и
  машинный разряд привязки (`bound`: `lead` значит «ведёт», `about` значит
  «говорит о», см. «Реестр чатов задачи»). Тем же ответом едет то, чем список
  разговоров панели различает соседей: подписка (`harness`, имя из раскладки
  машины; у своего `~/.claude` пусто), свежесть транскрипта (`live`) и ручка
  реплики с причиной (`reply`, `replyNote`, те же поля, что у шапки разговора).
  По ним панель выводит состояние словом: «идёт», «молчит», «кончился».
  Свежие сверху; `?task=DK-NNN`
  оставляет только сессии этой задачи, мусор вместо ID отбивается словами.
  `?free=1` оставляет разговоры без узнанной задачи: ими живёт общий чат доски,
  и вместе с `?task=` ключ отбивается, потому что просят они разное. Без `?task=` шапки читаются у
  полусотни свежих: общий список показывают десятком строк. С `?task=` обход
  идёт по всем транскриптам проекта: иначе разговор законченной работы теряется
  за окном свежих. На новом дереве, где транскриптов тысячи, обход упирается
  в бюджет в три секунды и говорит словами `note`, сколько успел просмотреть.
  Пустой список тоже идёт со словами `note`, и пустоты различимы: «сессий
  задачи DK-NNN нет» со счётом просмотренных, чужих и нераспознанных отдельно
  от «транскриптов нет вовсе»;
- `GET /api/projects/{p}/sessions/{sid}`: лента реплик транскрипта, последние
  `?n=` (по умолчанию 40) с пагинацией назад через `?before=<seq>`; с
  `?stream=1` дострение новых реплик, каждое событие это одна реплика в
  JSON. Сервер разбирает jsonl сам: служебные записи и ветки субагентов
  выпадают, вызов инструмента сворачивается в одну строку (имя и суть
  ввода), размышления в пометку без текста, битая строка пропускается без
  обрушения ленты. Пустая лента называется словами `note` и в обычном
  ответе, и первым событием потока: молчащий стрим неотличим от
  оборвавшегося. Вместе с лентой едет шапка разговора (`head`): те же поля,
  что у строки списка сессий, включая узнанную задачу с подписью, чем она
  узнана. Панель, открытая по id сессии, собирает из неё заголовок: строки доски
  у такого захода нет, и брать заголовок больше неоткуда (DK-294). Там же едет
  ручка для реплики: `reply` со значением `session` у живого разговора, `task` у
  кончившегося разговора с живой задачей и пустое значение там, где отвечать
  некому, а `replyNote` называет причину словами. Вместе с лентой едет план
  сессии (`plan`): им подписаны деления кольца и блок работ. Источников у него
  три. Файл плана и последний вызов TodoWrite это слова агента, и побеждает
  свежий. Третий источник машинный: боковые журналы субагентов, по одному на
  вызов, и каждый такой журнал это работа, которую агент раздал, независимо от
  того, переписал ли он файл плана. Подпись работе даёт её заказ: коротким его
  пишет мета-файл вызова, а у вызова без заказа подпись берётся из самого
  журнала, первой содержательной строкой заказа, без служебных приписок
  (правила плана, ротации, темпа, канала) и обрезанной по ширине строки. Имя
  определения («claude», «Explore») остаётся последним запасным вариантом:
  работой оно не называется. Работа сходится с пунктом плана по обоим ключам,
  короткой подписи вызова и заказу, иначе она встала бы рядом с пунктом
  двойником. Ленту дальше переиспользует переписка;
- `GET /api/projects/{p}/goals/{id}/message` и `POST` туда же
  (`{"text": "..."}`): переписка через состояние цели. Файл цели обе ручки
  ищут тем же разбором, что и журнал выше (`goalDocPath`: ссылка строки
  доски, а без неё или с битой ссылкой откат идёт на `docs/tasks/<ID>.md`),
  жёсткой склейки пути мимо ссылки тут нет (DK-270). POST кладёт сообщение
  строкой «`- дата, из дашборда: текст`» в раздел «Входящие» файла цели (нет
  раздела, он встаёт перед «Журналом») и коммитит с пушем, как положено
  правке `docs/tasks/`; провал коммита или пуша запись не отменяет и
  называется полем `note`. Переводы строк схлопываются в пробелы: сообщение
  это одна строка списка, тело ограничено 16 КБ, и отказ сверх предела
  называет предел, а не прикидывается битым JSON. Повтор того же текста второй
  строки не заводит: ключ повтора это сами неподхваченные строки «Входящих»
  (своего состояния сервер не держит), причём своими считаются строки своего
  же вида, с датой, временем и подписью в начале, а рукописную строку раздела
  повтор не блокирует. Ответ остаётся успешным и называет
  лежащую строку, а после подхвата витком тот же текст кладётся заново. На это
  же узнавание опирается очередь исходящих в браузере: она шлёт неушедшее
  сама, пока не дошлёт, и дублей не плодит именно потому, что своя лежащая
  строка узнаётся сервером. GET
  отдаёт лежащие строки, их виток ещё не подхватил, а вместе с ними доставку и
  живость витка. Доставка это поле `delivered`, отметки подхвата реплики
  `hooks/chat-in.py` из `.devkit/goal-<ID>.mail` (время, сессия витка и
  доставленная строка целиком): подхват вносит лежащую строку прямо в идущий
  виток и отмечает её. Отдаются только отметки лежащих строк, и порядок
  состояний тот же, в каком живут отметки: строки нет во «Входящих», значит её
  подхватил виток, и отставшая отметка этого не перебивает. Отметку ставит и
  подхват, и ключ `--ask` оболочки, вход у них один; у съеденной ключом
  строки сессии нет, и пустота эта штатная, а не битый разбор. Живость это
  поле `live`, и судится она правилом подхвата (`goalLive`, `mail.go`): живой
  `pid` в замке цели, а без замка свежая метка движения (`seen` записи реестра
  и последняя чужая строка журнала цикла) с тем же трёхчасовым порогом. Списком
  живых работ (`liveWorks`) этот вопрос не решается: убитая оболочка запись
  реестра не снимает, и цель с мёртвым циклом показывала бы на экране минуты
  до доставки, хотя доставлять некому. Отказы словами: строка не
  на доске, строка не цель (заголовок не от «Цель:»), файла цели нет. Своей
  ручки каналу доставки не нужно, а писать в идущий процесс дашборд
  по-прежнему не берётся: строку вносит подхват на завершённом ходе
  инструмента, сторона витка описана в скилле goal-loop. При стоящем цикле POST отвечает
  прямо: живых работ цели нет (ни tmux-сессии оболочки, ни записи реестра целей, ни
  живого окна человека), и ответ приходит с полем `idle` и словами «цикл цели
  не идёт», вместо обещания следующего витка. Строка при этом всё равно ложится
  во «Входящие»: отказ от записи был бы потерей сообщения, а поднятый виток
  прочитает её первым шагом. Нечитаемая доска считается идущим циклом: сказать
  «цикл стоит» там, где он идёт, дороже (DK-319);
- `POST /api/projects/{p}/sessions/{sid}/message` (`{"text": "..."}`): реплика
  любой живой сессии, не только витку цели (DK-345). Сессия ищется по
  транскриптам тем же обходом, что список сессий, дерево берётся из хвоста её
  каталога (боковое дерево задачи `../<проект>-<хвост>`), и реплика ложится
  строкой «`дата, сессии <sid>, из дашборда: текст`» во вход разговора
  `.devkit/chat` этого дерева. Вход называется задачей сессии (`task-<ID>`), а
  без узнанной задачи самой сессией (`sess-<sid>`); имя приходит в ответе полем
  `chat`, а сессию, ведущую цель, ручка отправляет к ручке цели, у цели свой
  носитель. Читает и доставляет вход тот же подхват реплики
  `hooks/chat-in.py` на завершённом ходе инструмента, доставленная
  строка уходит из входа, и повтором считается такая же лежащая. Пишется
  строка под flock файла замка входа (`takeChatLock` в `chat.go`), тем же
  замком, каким собирается подхват. Адресата ручка ставит всегда: адрес у
  реплики это адресат разговора, а не состояние собеседника, поэтому молчащее
  окно человека получает свою реплику в свой же вход и дожидается хода
  (LLD DK-430, решение 2). Протухший транскрипт это честное поле
  `idle` и слова «сессия, похоже, не идёт», реплика при этом ложится и ждёт
  хода. Панель разговора выбирает эту ручку по полю `reply` шапки (DK-435).
  Отказы словами: сессия не нашлась по журналу, боковое дерево
  сессии удалено;
- `POST /api/projects/{p}/tasks/{id}/message` (`{"text": "..."}`): ответ самой
  задаче, а не сессии. Строка ложится безадресной («`дата, из дашборда: текст`»)
  во вход разговора `task-<ID>.in` каталога `.devkit/chat` основного чекаута:
  чекаут переживает боковое дерево, которое сносится слиянием, и сторожок
  `devkitctl watch` читает оба места. Безадресную строку берёт любая сессия
  дерева, поэтому ответ достаётся той, что задачу продолжит, а припаркованную
  вопросом строку тик сторожка возвращает в работу, о чём ручка и говорит полем
  `parked`. Повтор той же реплики второй строки не заводит, пишется она под тем
  же замком, что у ручки сессии. Отказы словами: строки нет на доске (закрытая
  названа архивом), строка цели отправляется к ручке цели, пустой текст;
- `POST /api/projects/{p}/sessions/{sid}/task` (`{"task": "DK-431"}`): привязка
  разговора к задаче рукой, пустое значение снимает привязку. Ручка дописывает
  строку в реестр чатов `~/.devkit/sessions.log` со словом источника `рука`
  (`снята` у отвязки), тем же форматом, каким пишет хук; прежнее имя
  tmux-сессии переезжает в новую запись. Сессия сверяется с транскриптами
  проекта: привязка без разговора никому не видна, и отказы тут словами (нет
  транскрипта, ID не похож на задачу, битое тело);
- `GET /api/notifications`: лента уведомлений, хвост журнала уведомителя
  `~/.devkit/notify.log` (`?n=` глубина, по умолчанию 200 строк). Своего
  канала наружу дашборд не заводит: отправку держит `hooks/notify.py`, а
  лента это окно в его журнал. Строка разбирается в событие: время, повод,
  тип, заголовок и тело баннера, уровень, бэкенд и признак `sent` (дошёл ли
  баннер: по окну повтора или по фокусу событие не отменяет, но доставкой не
  был). Строку, которую уведомитель сам пометил пропуском по песочнице
  (корень прогона под TMPDIR), лента не отдаёт вовсе: это чужой синтетический
  прогон, а не событие машины, и с живыми его смешивать нельзя (DK-283).
  Повод сводится к типу: `stop` (стоп работы
  из дашборда и стоп цикла маркером), `wait` (виток зовёт человека), `task`
  (задача доехала до Check, встала на блокере, провалила проверку), `other`
  (хуки сессии и всё остальное); `?kind=stop,wait` отбирает типы. Событие несёт
  задачу и проект своими полями (`id` и `project`), их пишет сам
  уведомитель: в хук-режиме по рабочему дереву, в аргументном ключами
  `--task` и `--project` (DK-323). Пустая задача это честная пустота
  (самопроверка канала, авария контура), а не потерянная строка доски. Строки,
  писанные до полей, читаются по-прежнему: у них задача вылавливается из текста
  баннера, а проекта нет вовсе. Битая
  строка пропускается без обрушения ленты, а три пустоты различимы словами:
  журнала нет, журнал пуст, под фильтр ничего не попало. С `?stream=1`
  соединение живёт SSE-потоком и новые события доезжают по мере записи, файл
  опрашивается раз в секунду;
- `GET /api/waiting`: полка ждущих, все задачи и разговоры машины, стоящие на
  вопросе человеку. Ручка машинная. Место ждущих одно на
  дашборд, и открывается оно с любого экрана. Запись несёт проект, задачу,
  заголовок строки, адрес разговора и то же поле `waiting`, что у строки доски.
  Собирается она двумя заходами. Первый берёт строки всех досок с их состоянием
  ожидания, всеми тремя источниками сразу (раздел «Ожидание человека»). Второй
  берёт живые признаки ожидания, чьей строки на доске не нашлось. Это вопрос
  грумера черновика и вопрос сессии, раздавшей работу, и в Blocked их нет
  вовсе. Задача, у которой есть и строка, и признак, едет одной записью. Адрес
  разговора выбирает сервер. Это ID ждущей сессии, если он известен, иначе ID
  задачи, который панель читает как «последний разговор этой задачи». Порядок
  идёт по давности молчания, дольше всех ждущий первым; запись без момента
  начала (парковка, повод из журнала) уходит в конец. Нечитаемая доска не
  выдаётся за тишину. Она называется строкой в `errors`, а ждущие остальных
  досок приезжают своим ходом;
- `GET /api/quota`: остаток подписок из снимков `~/.devkit/quota/*.local`, по
  снимку на подписку. Каталог читается с диска: имя харнеса берётся из имени
  файла, бакеты из строк, и ни одного имени харнеса в дашборде нет, поэтому
  подключённая завтра подписка появляется на экране сама. По подписке едут
  бакеты с процентом потраченного и датой сброса, момент снятия и возраст
  словами; снимок старше 45 минут помечен `stale`, порог тот же, что у
  `agentctl` (по такому снимку он уже не двигает вердикт вверх). Битая строка
  снимка теряет только себя и называется в `warns`, а пустоты различимы:
  каталога нет, каталог без снимков, снимок без бакетов и снимок без момента
  снятия это разные ответы;
- `GET /api/tmux` и `GET /api/tmux/{name}`: список tmux-сессий машины (имя,
  окна, время создания) и снимок пейна через `capture-pane` подпроцессом со
  сроком; точное имя сессии (`=имя:`), чтобы не взять соседку по префиксу.
  «tmux не нашёлся», «сессий нет» и «сессия не найдена» это три разных
  ответа, а не одинаковая пустота;
- `GET /healthz`: без входа; `ok`, версия (по её смене выкат проверяется
  машинно), аптайм, число проектов и ошибки конфига.

## Цена экрана

Экран стоит ровно столько, сколько стоят подпроцессы под ним, и на живой
машине это заметная величина: обход корней зовёт git на каждый каталог с
доской (боковые деревья задач отсеиваются признаком линкованного worktree), а
каждый проект стартовой стоит своего `taskctl list --json`. Держится время
двумя средствами, и оба ничего не хранят дольше жизни процесса: своей базы у
дашборда нет, правда лежит в доске и утилитах.

Память процесса:

- обход корней живёт 5 секунд. Заведённый рядом проект показывается через
  секунды, а не через перезапуск демона, зато цепочка одного экрана (список
  проектов, доска, строка задачи) платит за обход один раз;
- ответ `taskctl list --json` живёт, пока не тронут файл доски: ключ это
  время правки и размер `docs/TASKS.md`, поэтому правка чужой рукой (агент в
  соседнем окне, `git pull`) доезжает до экрана сразу. Сверх этого стоит
  потолок в 10 секунд: часть вывода утилита считает не по файлу, а по git
  (возраст строки, метки слитого кода), и коммит доски файла не трогает;
- ошибки не запоминаются вовсе. «taskctl не нашёлся» это причина, а не
  ответ, и поднятый бинарь виден на экране сразу, а не по выходе срока;
- раскладка подписок (`agentctl harness --json`) живёт полминуты. Спрашивает
  её каждая сборка экрана и каждый запуск, а меняется она правкой конфига
  руками; список с причиной вместо подписок не запоминается по правилу выше;
- шапка транскрипта (ветка, первая реплика, узнанная задача) живёт по тому же
  ключу из времени правки и размера, с потолком в пять минут. Голова, читанная
  до предела в четверть мегабайта, переживает и дописывание: jsonl только
  растёт, и заново её тянуть незачем. Без этой памяти запрос сессий перечитывал
  бы по четверти мегабайта на каждую из полусотни свежих сессий. На ней же
  стоит поиск разговора по ID задачи: обход идёт по всему каталогу
  транскриптов, но платится он один раз, а не на каждое открытие экрана.

Своей памяти нет и у поиска: он берёт доску из того же кэша, что и её экран, а
файлы задач читает обходом на каждый запрос. Индекс тут стоил бы инвалидации на
каждой правке файла задачи, а платится за обход сотня мелких файлов из горячего
кэша файловой системы; удерживают цену не память, а потолки выдачи и задержка
ввода в четверть секунды, из-за которой набранное слово уходит одним запросом,
а не шестью.

Памяти нет там, где нет и цены: снимки квоты это каталог с парой файлов по
сотне байт, и чтение всего каталога стоит 80 микросекунд против сотни
миллисекунд подпроцесса (замер 2026-08-11, M1 Pro). Кэш тут покупал бы три
порядка ниже шума и платил остатком, который отстаёт от снятого. Число
печатает команда

```sh
GOWORK=off go test -run '^$' -bench Quota -benchtime 200x .
```

Полка ждущих обходит все доски машины, и платит она тем же кэшем, что и экран
доски. Свежий ответ `taskctl list --json` она берёт из памяти процесса, а
своего кэша не заводит. Опрос у неё поэтому реже экранного, раз в пятнадцать
секунд против пяти у пульса.

Опрос разом: кандидаты обхода и проекты стартовой спрашиваются
одновременно (до восьми подпроцессов сразу), поэтому экран ждёт худший ответ,
а не их сумму. Срок подпроцесса при этом свой у каждого, как и был. Паника
внутри опроса ловится и стоит одного проекта: он остаётся в списке строкой с
причиной, стек уходит в журнал, а демон живёт дальше.

Толпа за одним ключом принята осознанно: запросы, промахнувшиеся мимо памяти
разом, гонят каждый свой подпроцесс, одиночного полёта на ключ нет. У дашборда
один пользователь и полдюжины запросов в цепочке экрана, так что цена этому
несколько лишних процессов в момент истечения срока, а одиночный полёт это своя
таблица летящих ключей с замками поверх той же памяти. Появятся устройства,
которые ходят разом и часто, решение пересматривается числом.

Замер экранов печатает команда из каталога инструмента:

```sh
GOWORK=off go test -run '^$' -bench Screen -benchtime 5x .
```

Окружение замера повторяет живую машину числами: четыре проекта, девять
боковых деревьев, фикстуры git и taskctl спят снятую на машине цену вызова.
Холодный замер это первый заход на пустой памяти, тёплый повторный.

## Запуск и стоп

Запуск зовёт тот же механизм, что и руками. Цель (строка с заголовком от
слова «Цель:») поднимается оболочкой `goal-run.py <ID> -C <корень>` в её
tmux-сессии `goal-<ID>`; оболочка не ставится в PATH, и сервер ищет её сперва
в своём дереве (чекаут, из которого поднят сам дашборд, его называет
`DEVKIT_HOME` в окружении службы), а запасным путём по корням конфига
(`kit/skills/goal-loop/goal-run.py` в корне или его прямом подкаталоге), где
среди проектов лежит и чекаут devkit. Порядок этот не косметика: агентская
часть devkit едет вместе с кодом дашборда, а в корнях рядом лежит и другой
чекаут, где свежих флагов ещё нет. Оболочка, не понявшая переданного, отвечает
справкой argparse, и человеку она не показывается: вместо портянки идут
короткие слова с путём найденной оболочки. Одиночная задача
поднимается tmux-сессией `task-<ID>`, а в ней стоит своя оболочка,
`task-run.py <ID> -C <корень> --order <заказ> --again <заказ следующих> --
<клиент>`. Без оболочки конвейер живёт один ход головы, поэтому ненайденная
оболочка это отказ до подъёма окна. Ищется она теми же двумя дорогами, что и
оболочка цикла (`kit/skills/board-task/task-run.py`).

Промпт этой сессии собирает сервер по статусу строки, теми же словами, какими
эту работу заказывают в чате: из Backlog «Выполни <ID>», из In progress
«Продолжай выполнение <ID>», из Check «Закрой <ID>». Тексты держит тест
запуска, иначе они разъедутся со скиллами доски, которые по ним и разводят
конвейер. У цели заказ один на все статусы: и «выполнить», и «продолжить» это
следующий виток, а промпт витка сочиняет сама оболочка цикла, дашборд в её
слова не лезет.

До DK-286 подсказка кнопки была общей («Начатую задачу конвейер продолжит с
того места, где она стоит»), и нажимать было страшно: неясно, что уйдёт агенту
и куда смотреть после нажатия. Заказ дословно едет тем же полем `order`, что
сервер уже посчитал для промпта. Клиент его не пересказывает вторым разбором,
а показывает готовую строку («Конвейер получит заказ «Продолжай выполнение
DK-208» в tmux-сессии task-DK-208»): второй разбор рано или поздно разошёлся
бы с настоящим заказом. Панель разговора удачный запуск не открывает вовсе:
человек, разбирающий итоги одной задачи в её чате, вылетал из разговора на
каждое нажатие «Выполнить» у соседней (замечание пользователя). Вместо этого
запуск оставляет след: имя поднятой сессии ложится в память подъёма, и по ней
кнопка чата этой задачи мягко моргает рамкой (`chatlive`), пока работа идёт.
Признак берётся у самой работы (состояние `busy` или `waiting`), а память
подъёма закрывает те секунды, пока сессия ещё не назвалась в реестре. Тем же
приёмом помечены кнопка чата в строке доски, значок чатов в шапке на экране
задачи и кнопка «Чат груминга» у идущего разбора. Откроет человек чат задачи
сам, панель встретит его ожиданием подъёма, как и раньше. На строке списка доски
кнопка запуска остаётся на месте нарочно (DK-316): экран там и так показывает
признак идущей работы прямо в строке, и уводить с доски после каждого нажатия
незачем, подсказка при этом такая же.

Проверенная задача с пользовательской приёмкой из этого правила выпадает:
кнопка «Закрыть» у неё это подтверждение принятого глазами, а не заказ работы,
и сервер зовёт `taskctl close <ID>` сам, без сессии. Вид приёмки приезжает
полем `accept` ответа `taskctl list --json`, куда утилита кладёт разобранный
суффикс заголовка строки `[приёмка: user]` (LLD DK-292): вид назначают на
доске, и своего признака дашборд не заводит. За закрытием идёт коммит доски с
пушем, тем же порядком, что у правки строки, и с ID в subject; провал коммита
закрытия не отменяет и называется полем `note`. Ответ приходит той же
карточкой, что у запуска, только со словами утилиты («XR-003 закрыта
2026-08-14, строка в архиве») и с `kind` равным `close` вместо имени сессии.
Смешанный и агентский виды остаются за сессией, там закрытие это работа, а не
подтверждение уже проверенного; пользовательская строка в Backlog тоже
поднимает конвейер, потому что закрывать ещё нечего. До DK-289 сессию поднимало
любое нажатие в Check, и приёмка с телефона стоила минут ожидания и квоты там,
где хватало одной команды.

Строке, которой на доске уже нет, отказ называет настоящую причину: лежит ID в
архиве проекта, ответ говорит «задача XR-003 уже закрыта 2026-08-13 и уехала в
архив: экран устарел», а не «на доске нет строки». Видно это ровно на
устаревшем экране, когда задачу закрыли с ноутбука, а нажали с телефона, и
выдуманная причина там читается как поломка. Архив читается файлом
`docs/TASKS-archive.md`, тем же порядком, что у состава цели, и то же самое
отвечает экран задачи, открытый по закрытому ID.

### Подъём прогона после выката

Выкат при `autonomous = true` доводит задачу до прода сам, а дальше конвейер
упирался в правило независимости. Агентскую часть сценария гоняет не автор
правки, и позвать этого проверяющего было некому. Строка стояла в Check,
держала очередь непроверенного выката и ждала, пока человек поднимет сессию
руками (DK-684 простояла так час, и всё это время слитая DK-704 ждала выката
поездом).

Поднимает прогон команда `dashboard check`. Зовут её двое. Первый это `shipctl`
сразу за выкатом, у которого нет человека в окне (автономный `merge` и
`ship --drain`). Второй это тик `devkitctl watch`, страховкой по всем строкам
Check. Механика подъёма та же, что у кнопки экрана, вплоть до оболочки
проходов и очистки чужого окружения. Своих решений у команды два, кому прогон
нужен и кому его не отдавать.

Первым команда спрашивает проект. Подъём заводит только конвейер, доверенный
агенту целиком (`autonomous = true` в `.devkit/deploy.local`, читает его общий с
shipctl `internal/deployconf`). На проекте с выкатом за пользователем команда
отказывает сразу. Там человек в окне, до Check строка доходит с его рук, и
сессия поверх его работы вставала бы каждым тиком сторожка.

Дальше нужен прогон строке Check с непользовательским видом приёмки, погашенным
провалом, файлом задачи и без отметки «smoke прогнан» на последний выкат.
Признаки те же, по которым `taskctl closable` отбирает строки в закрытие
автоматикой. Заказ поднятой сессии называет обе отметки
(`agentctl stage <ID> проверка --by <модель>` и `shipctl smoke <ID>`) и то, чем
кончается провал сценария. Смешанному виду заказ велит прогнать агентскую
половину и оставить закрытие человеку.

Ярус проверяющего назначает вердикт роли ревью (`agentctl pick <ID> --role
review`). Прогон это второй взгляд на ту же работу, независимость у него та же,
что у ревью. Развернулся ярус в модель, которая вела разработку, и подъёма не
будет вовсе. Ворота закрытия такой прогон всё равно не примут, а отказ словами
дешевле сожжённой квоты. Кто вёл разработку, команда читает там же, где читают
ворота, в незакрытом пакете этапов и в разделе «Ход работы» файла задачи.

Перед самым подъёмом команда спрашивает права машинного контура тем же
перечнем, каким их спрашивает оболочка цели (`tools/devkitctl/perms.py`, не
подложный дом демона, а пользовательский). Проход поднятой сессии идёт
headless, у него нет окна, и запрос разрешения одобрить некому. Клиент
отвечает отказом, работа встаёт, а задача паркуется вопросом к человеку. Прав
на машине нет. Сессия не поднимается вовсе, а отчёт называет нехватку словами
перечня вместе с командой починки. Права машинного контура при этом выданы двум
подкомандам дашборда, `dashboard check` и `dashboard smoke`. На весь бинарь их
не выдают: `dashboard secret` печатает живой токен входа панели, а с `--rotate`
разом разлогинивает все сессии, и сессии без человека это не отдают. Клиенту
своей подписки ставится `--permission-mode auto`, тот же режим, с каким
поднимается клиент чужой. До
DK-739 своя шла без флага, и строка дашборда перебивала умолчание оболочки
проходов, которая ставит этот режим себе сама.

Молчащего исхода у команды нет ни одного. На каждую строку печатается своя
строка отчёта. Поднятый прогон называет tmux-сессию и модель, ненужный подъём
называет причину. Код возврата 1 отдаёт зовущему один факт, нужный подъём не
вышел, и эти слова зовущий уносит в свой отчёт или журнал.

### Второй круг чужого ревью

Ревью чужого MR ждёт автора парковкой, и ответ коллеги видит тик сторожка
(разбор в `tools/devkitctl/README.md`, раздел «Опрос тредов чужого ревью»).
Второй круг заказывает `dashboard round`, и дорог у него две. Обе уже есть у
экрана.

Первая дорога это живая сессия задачи. В окне `task-<ID>` лежит первый круг с
диффом и замечаниями. Второй круг едет туда репликой через `tmux send-keys`,
той же клавиатурой, какой панель подаёт реплику человека (DK-724). Поднимать
поверх такой сессии вторую значило бы читать тот же дифф заново. Разговор
человека под тем же именем сюда не годится. Реплика встала бы поверх его хода,
и команда говорит об этом строкой, а второй круг не подаёт.

Вторая дорога это подъём новой сессии, той же tmux-сессией `task-<ID>`, что у
кнопки экрана и у подъёма прогона сценария. Права машинного контура, ярус роли
ревью и оболочка конвейера тут те же. Заказ называет второй круг словами.
Сверить исправления с диффом, на отказ автора возразить один раз фактом,
дальше парковка «спор: ...» и зов человека.

Молчащего исхода нет и тут. На каждую строку печатается своя, а код возврата 1
отдаёт зовущему один факт. Второй круг был нужен и не начался. Такую строку
тик уносит в зов человеку, ответ автора уже лежит в MR.

### Живая сессия конвейера и запасная череда проходов

Голова конвейера это одна интерактивная сессия в окне tmux (DK-724). Оболочка
`task-run.py` поднимает её в своей же панели, первый заказ едет клиенту первым
аргументом, а следующие приходят в тот же процесс через `tmux send-keys`, той
же дорогой, какой панель подаёт в живое окно реплику человека. Процесс между
проходами не выходит. Поэтому долгая команда и фоновый субагент доживают до
конца, уведомление доходит до головы, а в реестре чатов на задачу приходится
одна запись, а не по записи на проход.

Конец прохода оболочка узнаёт отметкой хука `Stop` (`hooks/turn-mark.py`,
журнал `~/.devkit/turns.log`). Кода возврата у живой головы нет, транскрипт
растёт и на середине долгого хода, а харнес говорит про конец хода прямо, своим
событием. Свою сессию оболочка узнаёт по реестру чатов. Имя окна там пишет
только клиент со своим терминалом (DK-673), и чужие отметки в счёт не идут.
Позиции в файле оболочка при этом не держит. Журнал общий на машину и режется
хуком по размеру, а после реза смещение прошлого чтения вернуло бы уже
прочитанную отметку второй раз, и оболочка сочла бы идущий ход кончившимся.
Свои строки она отбирает по началу ID сессии и помнит прочитанные.
Отметка «начат» держит оболочку от заказа поверх чужого хода. Реплику человека
панель подаёт в это же окно, и свой заказ встал бы второй строкой ввода.

Кончился проход, оболочка спрашивает `taskctl show <ID>` и смотрит на секцию.
Задача в архиве значит стоп по-хорошему, `blocked` значит парковку и зов
человека, всё остальное значит следующий заказ. Заказ первого прохода приходит
от дашборда по статусу строки, заказ следующих всегда «Продолжай выполнение
<ID>». К тому времени строку уже двигали. Потолок проходов шесть, и
отдельно оболочка ловит воронку, три прохода подряд, где ход кончился быстрее
полутора минут и строку не сдвинул. За такой воронкой обычно стоит сломанное
окружение, нет логина, кончилась квота, уехал чужой флаг, и стоп после третьего
прохода бережёт остаток бюджета.

Живая голова зовёт человека уведомителем на трёх случаях: сессия упёрлась в
незнакомый запрос разрешения, сессия молчит получасом без единой отметки (хук
отметки не подключён либо окно замёрзло) и клиент вышел раньше задачи.
Молчаливого стопа у конвейера нет. С экрана закрывшееся окно неотличимо от
штатного конца.

Вопрос сессии узнаётся двумя журналами. Первый это отметка «ждёт» с поводом
`permission_prompt`, второй строка того же повода в журнале уведомителя
`~/.devkit/notify.log`. Второй нужен. Отметки пишет хук `turn-mark.py`, а в
настройки харнеса он ложится доктором, и сессия, поднятая до этого, вопрос
задаст, а отметку не напишет. Так простоял двенадцать минут конвейер DK-724 в
день, когда хук приехал слиянием.

Один вопрос приходит обоими каналами, и второй зов о нём придержан. Держится
придержание за время самого события из строки журнала и живёт пять секунд, а
конец и начало хода снимают его сразу. Второй вопрос той же причины, пришедший
следом за первым, зовёт человека заново.

Запасной вход остался прежним. Череда печатных проходов (`claude -p`, свой
процесс на каждый проход, конец хода это его выход) берётся там, где живую
голову вести негде: нет tmux, нет имени окна в `DEVKIT_TMUX` либо конвейер
позвали с флагом `--headless`. Расписание и подъём после ребута идут ею же.

Конец прохода виден в журнале утилит проекта, `.devkit/log`, и строка называет
сессию, задачу, её статус, номер прохода и то, чем проход кончился:

```
2026-09-03T11:55:33	task-run	конец прохода живой головы task-DK-658 (кончен), DK-658 в in-progress, проход 1 из 6, 47 с
```

До DK-691 естественный выход головы не писал никто, и с 26 августа в журнале
лежали 39 одинаковых строк `agentctl exec 0`, по которым мёртвую сессию не
отличить от отработавшей.

Метка печатного режима, пара `DEVKIT_HEADLESS=дашборд`, стоит в команде окна, а
перед прочими парами идёт чистка чужого наследства (`env -u` в `launchEnv`).
Причину держит tmux. Сервер его переживает ту сессию, из которой его завели
однажды, и раздаёт её окружение всем новым окнам. Замер DK-691 снял с нового окна
`CLAUDE_CODE_ENTRYPOINT=claude-vscode`, `CLAUDECODE=1` и
`CLAUDE_CODE_SESSION_ID` сессии, кончившейся сутками раньше. Клиент своего
значения поверх такого наследства не ставит, и рубеж синхронности
(`hooks/check-background.py`) считал конвейер живым окном, пропуская фоновые
вызовы, которые голова уносила с собой. Теперь наследство чистится, а метка
держит признак и там, куда чистка не дошла.

Живому клиенту метку снимает сама оболочка. Окно у него есть, фоновый ребёнок
переживает конец хода, и рубеж отбивал бы ему как раз то, ради чего живая
голова заведена. Печатному проходу метка остаётся, и `check-background.py
--why` в таком проходе отвечает «сессия headless».

У печатной сессии свой срок жизни, и череда проходов под него подстроена.
Финальный текст диспетчера кончает ход `claude -p`, а фоновые субагенты сессия
добивает через десять минут после этого. Поэтому скиллы доски зовут исполнителя
и ревьювера синхронным спавном: ход не кончается, пока субагент жив. Правило
лежит в `kit/skills/board-batch/SKILL.md` (шаг «Исполнители») и
`kit/skills/board-ship/SKILL.md` (раздел «Ревью»), а держит его проверка
`check_sync_spawn` в `kit/skills/check-skills.py`. Нарушенное, оно стоит
дорого: субагент длиннее десяти минут обрывается на середине, работа остаётся
незакоммиченным диффом в дереве задачи, а tmux-сессия схлопывается. Видно это
по признаку работы: строка остаётся в In progress, живой сессии за ней нет, и
список задач помечает её чипом «сессии нет» рядом с кнопкой «Продолжить»
(DK-317).

Стоп это стоп сессии, ручки «пауза» нет: `DELETE .../runs/{id}` дописывает в
журнал цикла строку про стоп (`goal-run.py --say`, чтобы стоп был виден там
же, где виден ход), снимает tmux-сессию, зовёт уведомитель поводом `run_stop`
(строка в ленте) и называет состояние стопом; замок оболочки отпадает сам по
мёртвому pid. Уведомитель ищется в корнях конфига там же, где оболочка цикла
(`hooks/notify.py` чекаута devkit); не нашёлся или упал, это приписка `note`,
а не отказ: сессия уже снята, и отменять стоп из-за уведомления нельзя.
Ответ на нажатие приходит карточкой поверх экрана, в том же правом верхнем
углу, где всплывают события ленты: и удача («конвейер задачи DK-136 поднят в
tmux-сессии task-DK-136»), и причина отказа (занятый замок, пропавший tmux или
`goal-run`). Удача гаснет сама через несколько секунд, отказ ждёт крестика:
причину человек читает, а не ловит. Ответ на экране один, слова о начале
сменяются словами об исходе. Строкой над списком ответ стоял до приёмки
DK-316: пустой он был свёрнут стилями, а со словами о нажатии двигал доску
вниз на свою высоту, и нажатие выглядело промахом. Карточка лежит вне потока
документа (`position:fixed` у контейнера), поэтому ни её появление, ни уход
ничего на экране не двигают. Каркас у неё общий с флеш-уведомлением ленты
(`toast` в `static/app.js`): карточка, крестик, полоска остатка времени и
потолок числа карточек. У ответа своё только содержимое и то, что нажимать на
нём нечего, а в ленту он не ведёт.

Работу, идущую в окне разговора, тот же `DELETE .../runs/{id}` останавливает
иначе. Снимать разговор нельзя, у него память человека. Ход прерывается двумя
Escape, в реестр ложится конец работы сессии над задачей (запись «снята» с
названной задачей), в ленту разговора встаёт строка о причине, а уведомитель
зовётся тем же поводом `run_stop`. Разговор остаётся жить и следующую реплику
берёт. Рабочих сессий у строки бывает несколько, и тогда ручка отвечает 409 со
списком `sessions`, а выбранную называет параметр `?session=<id>`. Какая из
сессий та самая, знает человек, и прерванный чужой ход стоит потерянной работы.
Кнопка на экране показывает этот список всплывашкой у себя же.

Прерванный ход останавливает работу не всегда. Субагентов агент раздаёт фоном,
их журналы пишутся рядом с транскриптом. Вернувшись, такая работа поднимает
агента новым ходом. Пока фоновая работа жива, стоп остаётся заказом дожима.
Привязка держится, строка стоит под «Стопом» с полем `run_stopping` и своей
подсказкой. Сторож разговоров прерывает всякий поднявшийся ход теми же двумя
Escape. Заказ кончается тишиной. Нового хода нет, фоновая работа встала, и в
реестр идёт «снята», в ленту слова о причине, уведомителю повод `run_stop`.
Слова человека в тот же разговор снимают заказ раньше, любой дорогой доставки.
Срок заказа четверть часа от первого нажатия.

Живой фоновую работу держат три мерки, и хватает любой. Две первые те же, что у
кольца пульса раздела «Агенты». Боковой журнал субагента без метки возврата
писался последние две минуты, либо ответа на его вызов в транскрипте нет вовсе
и журнал моложе получаса. Третья мерка про долгий инструмент. Субагент в сборке
или в прогоне тестов журнала не трогает минутами, а в хвосте журнала у него
висит вызов без ответа, и спрашивается этот хвост тем же разбором, каким
меряется ход разговора. Той же меркой строка доски считает себя занятой при
молчащем транскрипте.

Возобновление это новый `POST /runs`: виток или конвейер читают состояние с
диска. Цель из реестра без tmux-сессии ведёт другая сессия, которую дашборд не
поднимал, и её он не останавливает, а отвечает конфликтом словами: стоп отсюда
недоступен, снимать там, где цикл поднят. Работу в чужом окне он не
останавливает тем же порядком. Её ведёт человек, клавиатуры к этому окну у
дашборда нет, и кнопки стопа у такой работы нет ни на карточке, ни на экране
задачи.

Стоп симметричен запуску и берёт работу только у того проекта, которым его
позвали: запуск ищет строку на его доске, стоп ищет работу среди его живых
работ, где tmux-сессии привязаны префиксом ID с той же доски. Сессия с чужим
префиксом для проекта не идёт и отвечает 404, а не режется.

Отказы называются словами, а не молчат: строка не на доске, живая сессия под
тем же ID (запуск поверх не идёт, сначала стоп), занятый замок оболочки,
пропавшие `tmux`, `claude`, `goal-run.py` или `task-run.py`. Проверка `claude` идёт до
подъёма сессии: tmux-сессия с ненайденной командой умерла бы молча, и провал
был бы неотличим от запуска.

### Выбор подписки

Подписок на машине бывает несколько, и работу поднимают на любой из них
(DK-326, LLD [DK-328](../../docs/lld/DK-328-dashboard-screens.md), решение 3).
Выбор живёт в самой кнопке запуска: широкая часть с прежним словом
(«Выполнить», «Продолжить», «Закрыть») поднимает работу на подписке по
умолчанию, узкая со стрелкой открывает список, и нажатие на строку списка
запускает работу на ней же, без второго нажатия. Так частый путь не подорожал
ни на одно нажатие. Выбор действует на один запуск, а не на экран: две работы
рядом идут на разных подписках, и переключателя-настройки для этого не нужно.
В строке списка стоит имя, чип «по умолчанию» и остаток квоты полосками из
того же снимка, что рисует блок квоты; снимка нет, значит так и написано, а не
нарисован ноль. Возраст снимка назван у каждой строки: остаток, снятый час
назад, и остаток, снятый минуту назад, это разные ответы на вопрос «хватит ли
квоты». Подписка по умолчанию в списке подсвечена, шапка списка называет, что
выбирают, а подвал говорит, откуда список взялся и что выбор действует на один
запуск.

Вид кнопки держит принятый макет «11 Подписка при запуске» проекта «Дашборд
devkit» (DK-336): половины одного цвета стоят стык в стык, полоска внутри
узкой части делит их, галочка нарисована рамкой, узкая часть шириной 30
пикселей на ноутбуке и 44 на телефоне, где по ней жмут пальцем. На телефоне
список раскрывается вверх от кнопки, если под ней не хватает места, иначе он
уезжает под нижние вкладки; считается это по месту кнопки на экране, а не по
ширине окна, потому что кнопка стоит низко и на ноутбуке при прокрученной
доске.
Приёмка нашла кнопку распавшейся на две, и такое не берётся разбором правил:
зазор рисовало сложение флекса с радиусами. Поэтому вид меряется настоящим
движком, стенд `testdata/split_run.js` в разделе «Экраны доски и задачи».

Меняется при этом только окружение сессии. Команда сессии заворачивается в
новую подкоманду `agentctl exec`:

```text
tmux new-session -d -s task-DK-326 -c <путь> "<пары окружения> python3 <task-run.py> DK-326 -C <путь> --project <проект> --order '<заказ>' --again '<заказ следующих>' -- <agentctl> exec --harness <подписка> -- <клиент>"
```

Клиент тут стоит хвостом и без заказа. Ключ `-p` с заказом прибавляет оболочка
проходов на каждом подъёме головы, и обвязка подписки от этого не меняется.
Ярус уезжает в тот же хвост флагом `--model`. Клиент второй подписки принимает
имя модели из своей лестницы, и сессия поднимается выбранным ярусом вместо
дефолта её профиля (DK-750). На незнакомое имя клиент отвечает предупреждением
unrecognized_model, жалобой на неизвестное ему окно контекста. Подъёму сессии
она не мешает и оставлена осознанно.

Пары окружения подписки (её каталог конфигурации, а через него base URL и
токен) кладёт `agentctl`, и значения при этом никуда не уезжают: веб-сервер их
не читает, не хранит и не печатает, а в панель сессии, которую дашборд
показывает на экране, попасть им неоткуда. Собирать пары самому дашборду
нельзя ровно поэтому. Одного имени в окружении тут мало: без каталога
конфигурации второй подписки сессия пошла бы на подписке по умолчанию, называя
себя чужим именем, и на экране это выглядело бы удачным запуском. `agentctl`
зовётся полным путём: сессия наследует PATH дашборда, а под launchd он
системный, и утилит devkit в нём может не быть. Клиент подписки (`bin` из
раскладки) ищется тем же PATH, что и прежний `claude`, и ненайденный называется
до подъёма сессии.

Строка результата называет подписку («конвейер задачи DK-326 поднят на
подписке <имя>»), и сказано в ней именно про сессию конвейера: куда та отдаст
исполнителя дальше, решает вердикт `agentctl pick` по лестнице этой подписки.
Куда поедет работа, сказано всегда: при двух подписках надпись под полосой
действий задачи называет ту, на которой поднимет широкая часть («поедет на
<имя>, подписок на машине две»), потому что кнопку жмут не заглядывая в
список. Два вырожденных случая названы явно, молчания нет ни в одном. Подписка
на машине одна: стрелки нет, а подсказка кнопки говорит, куда поедет работа.
Список не прочитан (нет `agentctl`, пустой `enabled`, отказ команды): стрелки
тоже нет, запуск работает ровно как до DK-326, а причина стоит подсказкой на
кнопке и надписью под полосой действий задачи. Имя, которого в раскладке нет,
отбивается 400 со словами: устаревший экран не должен молча уезжать на подписку
по умолчанию. У цели выбора нет вовсе: виток поднимает оболочка `goal-run`
своей сессией, передать ей подписку нечем, и запрос с именем отбивается той же
причиной. Закрытие принятой задачи подписки не требует: сессии агента за ним
нет, и выбранное имя остаётся строкой в журнале.

## Экраны доски и задачи

Вшитая статика (`static/`, `go:embed`): рукописные HTML, CSS и ES-модули без
сборки и внешних зависимостей, наружу сервер не ходит ни за одним байтом,
шрифты IBM Plex берутся через системные фолбэки. Вёрстка по макетам проекта
«Дашборд devkit» в Claude Design (DK-216, обновлены DK-248): на ноутбуке
боковая колонка с проектами и разделами, на телефоне нижние вкладки и
переключатель проекта в шапке. Разделы «Главная», «Доска» и «LLD» ведут на
свои экраны. В ленту ведёт колокольчик в шапке, разделом она не стоит, а сессии
это таб самой доски.
Уже 520 точек шапка ложится в две строки: имя с выбором проекта в первой,
подпись экрана, легенда и кнопки-действия во второй, длинное имя режется
многоточием. Одним рядом всё это упиралось примерно в 470 точек, и на обычном
телефоне в 390-430 страница уезжала в горизонтальную прокрутку.

Отступы и скругления форм меряются одной лестницей в `:root`. Своих чисел в
правилах формы больше нет. Шаг это `--sp1`, `--sp2`, `--sp3` и `--sp4`, зазор
между блоками формы `--fgap`, радиусы `--rad1`, `--rad2` и `--rad3`. Прежде
между описанием и рангом стояло двадцать точек, между прочими блоками
четырнадцать, и форма читалась рыхлой. «Выровнять отступы» означало подогнать
пять чисел на глаз, а на следующей правке они разъезжались снова (замечание
пользователя). Держит рубеж сторож `TestStaticFormsUseSharedSteps`: он
вычитывает `static/style.css` и падает, если блок формы написал свои `px` в
отступе, зазоре или радиусе.

Правило вёрстки общее и держится замером: вбок не ездит ни тело страницы, ни
раздел. Раздел тут свой скроллер (`.groups` просит `overflow-y`, а браузер
делает прокручиваемой и вторую ось), и уехать вбок он может от одного широкого
куска. Широкое ужимается на месте, а не подавляется скроллом: длинная фраза в
чипе режется кромкой с полным текстом в подсказке (`.cwhy` у причин блока и
провала), неразрывный путь в подписи сессии и в тексте вопроса клиента
разрывается по месту (`overflow-wrap:anywhere`), сетка строк держит `minmax` и
`min-width:0`. Живой случай: причина блока строки DK-466 приезжала целым
предложением и уносила таб задач на 385 точек при окне 390.

Держит правило замер `TestBoardNarrowNoSideScroll`: настоящий движок, окна 390
и 430, все три таба доски и блок вопроса клиента; мера это ширина содержимого
раздела против его собственной ширины.
Доска перечитывается по фокусу окна и по событию уведомителя, пришедшему на
открытый список задач своего проекта: статус строки двигает агент у себя, и
без этого «в работе» доезжало до списка только после ухода из окна и обратно.
Постоянного опроса при этом нет, ход идёт на событие; хвост журнала, который
поток отдаёт при подключении, доску не дёргает.

Третий повод перечитать доску это возврат на вкладку (`visibilitychange`).
Телефон гасит экран и будит его, вкладка уходит в фон и приходит назад. Фокуса
окна при этом бывает и нет. Страница из фона показывала состояние часовой
давности.

Круг обновления заводит и живая сессия проекта, у которой строки ещё нет. Такая
сессия присвоит строку первой же командой доски, `agentctl stage` или
`taskctl move`. До этой минуты признака работы у строки нет, и круг заводился
по тому самому признаку, который взятие и добавляет. Приёмка DK-716 нашла это
живым случаем. Человек написал в чат по задаче, работа открылась через
полминуты, а кнопка «Выполнить» стояла вместо «Стопа» до перезагрузки страницы.
Тихий проект круга не заводит, живых сессий у него нет.

Пустой хэш это главная, список проектов. Уйти на неё можно с любого экрана:
переход держит логотип в левом верхнем углу, на ноутбуке он стоит вверху
боковой колонки, на телефоне слева в шапке, на самой главной погашен и никуда
не ведёт. Отдельной кнопки «На главную» нет; на телефоне то же место занимает
первая нижняя вкладка.

Состояние проекта говорит кружок: серый работы нет, зелёный идёт работа,
красный требуется внимание. Внимание считается по доске, а не по ленте: запись
уведомителя машинная и проекта в себе не несёт, а задача в Check ждёт ровно
человека. Цветом одним такое не сказать, поэтому рядом с зелёным и красным
стоит причина словами («2 задачи в работе: DK-112, DK-247», «ждёт проверки:
1 задача в Check»), а у серого её нет: сказать о нём нечего. Что значит какой
цвет, рассказывает легенда у заголовка: на ноутбуке она всплывает по знаку, на
телефоне тот же знак разворачивает её нажатием.

Остаток подписок стоит блоком по макету «00 Главная»: на ноутбуке в подвале
боковой колонки, на телефоне колонки нет, и тот же блок едет карточкой на
главную, потому что смотрят на остаток как раз с телефона. Блок на подписку:
имя харнеса, полоска на каждый бакет с процентом потраченного и днём сброса,
подпись с возрастом снимка. Протухший снимок подписан словом «протух» и жёлтой
подписью, а пустота говорит, чего не хватает и чем это чинится
(`agentctl quota refresh`). Читается блок той же ручкой `GET /api/quota` и
живёт отдельно от экрана: остаток нужен над любым из них.

Показ остатка честен в трёх местах, и все три выросли из живого случая, где
цифры двух подписок разъехались, а выглядели одинаково свежими. Первое:
подписка машины, у которой снимка нет вовсе, стоит в блоке строкой со словами
«снимка нет: остаток неизвестен», а не пропускается. Список снимков собирается
по файлам каталога, и подписка без съёмщика в него не попадала ни строкой, а
молчание читалось как «всё в порядке». Сверяет список сам экран: подписки он и
так знает, из них собрана кнопка запуска. Второе: давность снимка подписана у
каждой подписки своей цифрой («снимок 4ч 49м назад»), и в блоке, и в списке
выбора при запуске, а сравнение человек делает сам. Слов о том, что снимки
разъехались по времени, дашборд не говорит: сперва это была красная плашка на
весь блок (она вытесняла из колонки сами цифры, ради которых блок и
открывают), потом приписка «раньше остальных» у старшего снимка, и оба раза
лишнее слово мешало (решение пользователя). Третье: выбор
подписки при запуске опирается на ту же картину, и в списке подписок стоят и
возраст снимка, и слова про его отсутствие, и предупреждение о разъезде.
Имя бакета в показе идёт без приставки `window` (`window5h_all` показывается
как `5h_all`, полное имя остаётся подсказкой): приставка занимала треть строки
в колонке шириной с ладонь, а ключи данных при этом прежние.

Заведение живёт кнопкой, которая раскрывает выпадашку с двумя пунктами:
черновик и задача. Кнопка эта стоит плюсом у карточки проекта на главной,
плавающим плюсом на телефоне и кнопкой со словами в накопителе, а меню у них
одно (`makeMenuAt`) и закрывается теми же тремя путями, что остальные
всплывашки: повторным нажатием, кликом мимо и Escape. Пункт ведёт сразу в свою
форму (`#проект/new/draft` и `#проект/new/task`, макет «07 Заведение»); голый
`#проект/new` остаётся живым входом и открывает задачу.

Форма у каждого вида своя. Прежде она была одна на оба случая, поля черновика
стояли в ней вперемешку с полями строки доски, а гашеные чипы объясняли, чего у
черновика нет («каша полей», замечание пользователя); промежуточный экран
выбора из двух дверей тоже не прижился, он стоил лишнего перехода там, где
хватает выпадашки. Памяти выбора нет нарочно: заведение это осознанное
действие.

Черновик несёт только себя: поле текста с подсказкой про SCQA (ситуация,
осложнение, вопрос, гипотеза) и пометку, что ранг, тип и цену выдаст груминг.
Задача повторяет правку строки: те же поля в том же порядке, та же сумма ранга
и вид приёмки с барьером. Поле написанного тоже одно: у задачи это заголовок строки, у
черновика текст записи, и переключение его не теряет. В режиме черновика поля
не прячутся, а гасятся с подписью, кто их заполнит («тип выдаст груминг»,
«ранг выведет груминг»): перестроенная форма скрывала бы, чего черновик лишён.
Там же стоит пометка про то, что черновику доступен только груминг, задачи на
доске у него нет и в работу его не взять. У задачи под кнопкой сказано и это:
взять в работу можно с карточки, до заведения у строки нет ни ID, ни статуса,
от которого конвейер берёт заказ. Сумма R считается в форме на глазах, но
правды в ней нет: итоговый ранг, бакет P и место строки в Backlog считает
`taskctl`, и заведённая строка сразу открывается своим экраном. Файл задачи
`docs/tasks/<ID>.md` заводит тот же `add`, отдельного чекбокса на форме
нет: строка без файла это дыра. Поправку на баг форма сверяет с типом теми
же словами, что и ручка, а кнопки гаснут на время запроса: повторное
нажатие на медленной связи завело бы вторую строку тем же текстом. Поля
переживают перечитывание по фокусу окна, набранное на телефоне не пропадает.

Кнопок сохранения у черновика две, и расходятся они только дорогой после
записи. «Сохранить» пишет запись и возвращает в накопитель, оттуда же плюсом
пишется следующая. «Сохранить и грумить» той же ручкой пишет запись, без лишних
вопросов поднимает разбор и открывает экран записи, где виден его ход. Обе
кнопки живут и гаснут вместе, рубеж у них один. Подсказка под ними говорит,
куда ведёт каждая: кнопки уводят с экрана, и знать это надо до нажатия. Прежде
запись кончалась одной кнопкой и промежуточным экраном «Черновик записан» с
кнопками «Записать ещё», «В накопитель» и «На доску». Обе его дороги теперь
закрыты возвратами самих кнопок, а лишний переход снят. Задачную половину формы
это не трогает, после «Завести задачу» по-прежнему открывается карточка
заведённой строки: следующий шаг с телефона это дописать постановку, а искать
строку глазами по Backlog неудобно.

Вид приёмки назначается тут же (DK-301): закрытый список из трёх значений
(agent по умолчанию, mixed, user), а у не агентского вида под ним открываются
барьер из шести и строка причины, почему обход не годится. Ручка `POST
/api/projects/{p}/tasks` шлёт `--accept` всегда и `--barrier` при не
агентском виде, причина ложится в раздел «Приёмка» файла задачи рядом со
строкой барьера, и её читает ревьювер. Барьер без вида не отправляется
вовсе: форма держит тот же рубеж, что и ворота `taskctl add`, и говорит
словами, что без названного барьера приёмка повисает без причины.

Рядом с заведением, на доске и на главной, стоит вход в раздел «Черновики»
(`#проект/drafts`): накопитель `docs/tasks/drafts/` списком. Строка идёт одним
рядом слева направо: отметка выбора, важность, номер, наименование, дата
последней правки записи и кнопка чата; пометка «отложен» чипом стоит там же,
среди приписок. Дата тут в том же виде, что у строки доски (`2026-08-20`), а не
возрастом днями: «три дня» отвечало не на тот вопрос. На узком экране строка
ужимается, наименование режется кромкой, а полный текст показывает подсказка.
Своей кнопки заведения у раздела нет: заводят и черновик, и задачу меню кнопки
«плюс» рядом с полем поиска.

Порядок списка выбирает человек. Открывается накопитель свежими записями
сверху. `taskctl draft list` печатает записи по возрастанию ID, и записанное
пять минут назад лежало последней строкой под тремя десятками старых. В шапке
карточки, справа от счётчика, стоит кнопка о двух положениях, «свежие сверху» и
«по заголовку». Нажатие перебирает список на месте, без похода на сервер. Выбор
живёт в `localStorage` и переживает обновление страницы. Порядка по ID среди
положений нет нарочно. Номера растут по времени записи, и такой порядок совпал
бы с датой. День записи берётся из поля `written`. У записи без строки
«записан» он выводится из возраста, который `taskctl` меряет правкой файла.
Внутри одного дня выше стоит запись с большим номером. В самих утилитах
порядок прежний, груминг читает накопитель по возрастанию ID.

Черновик на доске не виден вовсе, и без раздела записанная с телефона мысль
лежит в файле, до которого с телефона не добраться. Нажатие на строку открывает
экран записи, а разбор запускается не из строки: у каждой стоит отметка выбора,
а над списком одна кнопка «Провести груминг». Пока ничего не отмечено, кнопки
нет вовсе, а подпись рядом говорит, что разбор поднимается на отмеченное.
Справа от кнопки стоит поле модели: человек спрашивает, чем будет разбираться, и
ответом ему имя модели, а не пара «подписка и ярус», из которой её надо
выводить. Список моделей собирается из той же раскладки машины
(`agentctl harness`), что и выбор подписки у запуска задачи, а в заказ разбора
уезжают всё те же подписка с ярусом: имени модели ручка груминга не знает.
Прежде разбор поднимала кнопка в самой строке, и накопитель разбирали по одной
записи, а нажатие всплывало до обработчика строки и открывало форму вместо
запуска.

Подтверждения перед подъёмом нет. Выбор записей отметками это и есть
осознанное действие человека, и второй вопрос поверх него он назвал лишним.
Прежняя карточка вдобавок оставляла исходную кнопку доступной, и нажать её
можно было поверх открытого вопроса (замечание пользователя по снимку). Число
выбранных стоит теперь в подписи самой кнопки, «Провести груминг (3)», а
нажатие поднимает разбор сразу. На время подъёма кнопка гаснет: пачка идёт по
одной сессии, и второе нажатие подняло бы их дважды. Записи, у которых разбор
уже идёт, пропускаются, и пачка от этого не падает. Сколько сессий поднялось,
что пропущено и что не поднялось, говорит одна строка итога, как у запуска
задачи. После подъёма выбор снимается, экран остаётся на накопителе, а ход
разбора виден пометкой в строке и рамкой у кнопки чата. Пустой накопитель
говорит словами сервера.

У записи свой экран (`#проект/draft/<ID>`, макет DK-328): слева текст записи с
путём файла, справа то, что с ней сделали. Груминг живёт здесь же и зовётся
грумингом: прежнее «Оформить» скрывало, что у разбора четыре исхода вплоть до
удаления записи.

Исход разбора форма не пересказывает вовсе: карточек «Груминг кончился без
исхода», «Черновик оформлен строкой» и прочих шести состояний на ней нет ни
одной. Разговор с агентом у нас всегда идёт в чате, там же виден и исход, а на
доске он виден по факту: строка появилась или нет (решение пользователя).
Прежде форма пересказывала след разбора своими словами, и человек читал их
вместо самой записи. На экране остались сама запись, её действия и пометка
идущего разбора.

Груминг идёт: пометка «груминг идёт» стоит чипом в шапке, поднять второй разбор
поверх идущего экран не предлагает, а ход смотрят в чате. Идущим разбором
считается только его собственная tmux-сессия (`draftSession`, имя `task-<ID>`):
всякий разговор про запись грумингом не является, и прежде открытый чат о
черновике показывал форме «груминг идёт», хотя сессии разбора не было вовсе
(живой случай пользователя). Тот же признак разводит работу и разговор у строк
доски. Конец разбора экран замечает сам: пока пометка стоит, состояние
перечитывается по кругу, и кнопка «Провести груминг» возвращается без
перезагрузки страницы.

Вход в разговор на экране записи один и стоит значком, как у строк задач:
кнопка «Чат груминга» вела в тот же самый чат, что и значок рядом, и две двери
в одну комнату человек читал как две разные.

Вопросы разбора живут в разговоре, а не на форме. Груминг идёт живой сессией
(решение 1 LLD DK-354), и заказ прямо велит агенту заводить пачку вопросов с
вариантами и рекомендацией штатным инструментом AskUserQuestion. Хук
`ask-panel.py` перехватывает вызов, кладёт признак без срока и встаёт на
экране структурным блоком. Ожидание видно чипом «ждёт ответа» у самой записи,
и на её экране, и в строке накопителя: чип тот же и теми же словами, что у
строки доски, а снимает его ответ человека.

Текст записи правится тут же, карандашом в строке статуса, тем же полем, каким
экран задачи правит постановку. При сохранении на сервер уходит база правки,
хэш текста, с которым экран открылся. Писателей у файла записи двое, человек и
агент разбора, и без базы последнее сохранение затирало бы чужое молча. Запись
ушла из-под рук (вторая вкладка, разбор), и сохранение отбивается. Набранное
остаётся в поле, а текст с диска встаёт карточкой рядом, читать и сличать.
Свести их за человека дашборд не берётся, что оставить, знает только он.

Пока разбор идёт, карандаша на экране нет вовсе, а над текстом стоит плашка
«Разбор идёт, запись у агента» с кнопкой «Стоп». Запись в эти минуты
принадлежит грумеру, он её читает и уносит исходом. Правка человека либо
пропала бы под ним, либо сделала бы исход ответом не на тот текст. Замок этот
не один, тем же правилом отвечает и ручка. Отпирает его живое ожидание. Плашка
меняется на «Агент ждёт ответа, правка открыта», карандаш возвращается.
Ответить грумеру правкой самой записи можно, пока он спит в ожидании.
Несохранённая правка уезжает на диск до подъёма разбора. Без этого агент
прочитал бы старый текст, и потеря была бы молчаливой.

Удаление стоит на том же экране: «Удалить» раскрывает подтверждение на месте,
строкой с полем причины. Без причины запрос не уходит вовсе, отказ виден там же,
где поле, а прошедшее удаление зовёт `taskctl draft drop`, и причина уезжает
сообщением коммита доски. Модальных окон в дашборде нет, и подтверждение
занимает ту же строку, где стояла кнопка.

На телефоне порядок колонок тот же, что у формы задачи: действия сверху, текст
записи под ними.

Поиск задач стоит в шапке доски (LLD DK-328, решение 2): на ноутбуке поле
видно всегда, слева от колокольчика, и косая черта ставит в него курсор, не
отрывая рук от клавиатуры. На телефоне шапка тесная, и там же стоит лупа рядом
с колокольчиком, а поле во всю ширину открывается на самом экране выдачи и
сразу ждёт набора. Ввод уходит на сервер с задержкой в четверть секунды, ответ
на прежний запрос поверх свежей выдачи не рисуется, а набранное уезжает в адрес
экрана, а не в ручку напрямую. Поле всегда отражает адрес: запрос переживает
переход на форму и возврат кнопкой «назад» вместе с адресом, а на экране без
запроса поле пустеет, и выдача не противоречит полю (прежде после возврата с
формы в поле оставалась строка поиска при полном списке). Крестик сброса в
поле идёт той же дорогой, что Escape: стирает запрос и возвращает доску.

Выдача занимает свой экран (`#проект/find/<запрос>`), а не выпадает списком под
полем: запрос в адресе делает её ссылкой и переживает кнопку «назад», а на
телефоне выпадающий список дрался бы с клавиатурой за нижнюю половину экрана.
Доска при этом никуда не девается и не перестраивается. Группы идут в
постоянном порядке, «Доска», «Черновики», «Архив» и «В тексте задач», пустые не
рисуются вовсе. Строка доски ведёт на экран задачи, архивная туда же (там
закрытая задача называет свой архив словами), черновик ведёт в накопитель.
Совпадения подсвечены везде, включая заголовки и цитаты из текста задач.
Урезанная потолком группа подписана хвостом («ещё 7 совпадений, уточните
запрос»), а пустые случаи говорят словами сервера, чего ждёт короткий запрос и
где искали, если не нашлось ничего.

Строка доски работает сама, без захода внутрь: справа у неё кнопка действия
по статусу («Выполнить» в Backlog, «Продолжить» в In progress, «Закрыть» в
Check) либо «Стоп» у живой работы, и зовут они те же ручки `POST` и `DELETE
/runs`, что и экран задачи; у цели, которую ведёт живой чат без tmux-сессии
дашборда, вместо кнопки стоит «ведёт другая сессия». Вид приёмки строки решает,
что стоит за «Закрыть»: у пользовательской это `taskctl close` тут же и без
сессии, у остальных сессия с заказом «Закрой <ID>». Заблокированная маркером
`[после ...]` задача действия не получает: кнопка стоит погашенной, а причину
(«сначала DK-248») говорит подсказка. Нажатие на кнопку внутрь
задачи не уводит. При двух и более подписках у кнопки запуска есть узкая часть
со стрелкой, и она открывает выбор подписки прямо в строке (разбор в разделе
«Выбор подписки»).

Текущее состояние строка теперь берёт из своего поля `run`, а не из
сведения со списком работ: у идущей работы первым чипом стоит зелёное
«работает» с точкой, и чип ведёт на её живой статус, а у строки из In
progress, за которой живой сессии нет, стоит серое «сессии нет». Оборванный
конвейер до этого выглядел штатным ожиданием: строка стояла в работе, кнопка
предлагала продолжить, и сказать, идёт по ней кто-нибудь или нет, было нечем
(хвост DK-314). Тот же чип стоит и в шапке задачи. Нажатая кнопка гаснет до
ответа сервера: пока запуск шёл, строка выглядела прежней, и второе нажатие
уходило вторым запуском, а возвращалось отказом «работа уже идёт».

Ранг в строке это одна сумма: слагаемые ест место, а нужны
изредка, поэтому на ноутбуке они приходят подсказкой при наведении, а нажатие
на сумму разворачивает их прямо в строке, и это же работает на телефоне, где
наведения нет. Вместо возраста строки днями показывается дата её последней
правки (поле `moved` из `taskctl list --json`, считает его `git blame`):
перевод в статус двигает ту же строку, и на грязном дереве или вне git поля
нет вовсе, вместо выдуманной даты пусто. Слова «правка» рядом с датой нет, о
том, что это за дата, говорит подсказка по наведению. Маркер зависимости
назван словами блока зависимостей: «заблокирована задачей DK-248».

Строка очереди двигается перетаскиванием, и исходом становится пересчитанный
ранг, а не позиция (LLD DK-328, решение 1). Жест правит одно слагаемое,
ценность. Серьёзность это суждение об ущербе и полоса, её перетаскиванием не
двигают вовсе. Неопределённость снимается разбором, поправка на баг привязана
к типу строки, а рычаг проверяется, а не назначается. Отсюда коридор строки: при
серьёзности S и сумме прочих мягких слагаемых M ей доступны ранги от S+M до
S+M+10, и полосу серьёзности такой коридор не переезжает никогда. Живёт жест
только в Backlog: в остальных секциях порядок ручной и от ранга не зависит, и
пересчитанный ранг строку там не двинет.

Пока строку держат, коридор нарисован прямо на списке: за его краем строки
приглушены, у самого края стоит причина («выше не поднять: жест правит только
ценность, и её потолок даёт DK-325 ранг 40»), а живые щели подписаны рангом,
который в них нужен. Целевой ранг считается по паре ключей сортировки Backlog
(ранг убыванием, номер возрастанием, тем же порядком, что `insertIdx` в
`tools/taskctl/board.go`), и из подходящих берётся ближайший к сегодняшнему:
жест не раздувает ценность впрок. Щель, в которую строка не встаёт ни одним
рангом (у соседей общий или соседний ранг, а номер строки между их номерами не
попадает), подписана словами, какой ранг нужен, чтобы встать выше обоих или
ниже обоих. Со строкой едет ярлык «ранг 37 -> 39, ценность 7 -> 9», а у
верхнего края коридора рядом с рангом переезжает и полоса: «ранг 49 -> 50,
ценность 9 -> 10, полоса P2 -> P1». Полоса считается из суммы, и это
единственное, что видно на доске без разворота ранга, поэтому молча она не
меняется.

Пальцем строка берётся долгим нажатием: короткое касание по-прежнему открывает
задачу, а пролистывание списка остаётся пролистыванием, потому что поехавший
раньше удержания палец жест снимает вовсе (телефонная доска DK-285). Мышью
строка берётся сразу, с порогом в несколько пикселей, чтобы клик остался
кликом. Пока строку держат, экран не перерисовывается: пересобранный список
увёл бы из-под пальца и строку, и щели.

Прокрутку под взятой строкой отменяет обработчик `touchmove`, объявленный не
passive, а не `touch-action` в стилях. Судьбу касания браузер решает по первому
движению пальца и смотрит на `touch-action` таким, каким тот был в момент
касания: у строки, которая берётся долгим нажатием, класс приезжает через
400 мс, и запрет опаздывает на целое касание. Не отменив это движение, касание
уезжает прокруткой, указатель отменяется (`pointercancel`), и жест умирает, не
начавшись. Браузерная приёмка на телефоне нашла ровно это. До взятия строки
обработчик не отменяет ничего, поэтому список листается пальцем как прежде.

Отпущенная там же, откуда взята, строка правкой не считается и запроса за собой
не тянет. Правка уезжает той же ручкой `PATCH` со слагаемыми, что и форма
задачи, дальше `taskctl set --rank`, своей записи в `docs/TASKS.md` дашборд не
заводит. Строка результата пишется по ответу сервера, а не по превью: «DK-325:
ценность 7 -> 9, ранг 37 -> 39. Строка встала между DK-319 и DK-326». Разошлись
соседи с расчётом экрана, значит так и сказано («Доска успела уехать, строка
встала между DK-317 и DK-319»): пока шёл жест, доску могли переписать соседняя
сессия или цикл цели, но ранг остаётся тем, что человек назначил. У строки
результата стоит «Вернуть»: она кладёт обратно слагаемые, а не место, и едет с
ожидаемой разбивкой, поэтому чужую правку не затирает молча, а получает отказ
словами. Переехавшая строка на пару секунд подсвечена вместе с рангом и чипом
полосы: найти её глазами на новом месте иначе нечем.

На телефоне доска собрана под ширину телефона (DK-285). Заголовок строки идёт
своей строкой во всю ширину, чипы уходят под него отдельным рядом `.rchips`.
Рядом с заголовком чипы не отдают ширины, и от длинного названия оставался
столбик обрубков по букве. Разделы доски разложены по двум табам полосы
`.btabs`: «Сессии» это In progress и Check (то, что уже двинулось), «Бэклог»
это Backlog и Blocked (очередь). Третий таб той же полосы уводит в накопитель
черновиков: с телефона мысль чаще записывают, чем разбирают. Секции при
переключении не пересобираются, а гасятся стилями по классу `.onsec`, поэтому
прокрутка и фокус остаются на месте. На ноутбуке полосы нет вовсе, и все
разделы идут списком подряд. Заведение задачи на телефоне это плавающий плюс
`.fab` в правом нижнем углу над нижними вкладками. Полоса кнопок «Новая
задача» и «Черновики» вставала в два ряда и съедала полэкрана до первой
строки, и на телефоне она спрятана. Подпись плюса задана в `title` и
`aria-label`, иначе кнопка со знаком безымянная. Держит раскладку замер в
headless-chrome (стенд `testdata/board_narrow.js`): предмет проверки это
ширина заголовка и края блоков, а разбором правил стилей такую поломку уже
пропускали. Тем же движком меряется составная кнопка запуска (стенд
`testdata/split_run.js`, DK-336): стык половин без зазора, ширина узкой части
под палец, ширина и край списка подписок на телефоне и раскрытие вверх. Третий
стенд меряет остальные кнопки действий (`testdata/buttons.js`, DK-337): высоту,
поля, радиус, кегль и гашение у кнопки строки доски, кнопки полосы действий и
кнопок экрана черновика, на ноутбуке и на телефоне. Размеры кнопок держит общая
тема макетов проекта «Дашборд devkit»: мелкая кнопка это 30 пикселей высоты,
поля по 12 и радиус 8, полноразмерная 36, поля по 16 и радиус 9, погашенная
видна на 45 процентов и курсора не меняет. Приёмка нашла разошедшимся именно
общий класс, а не отдельную кнопку. Все три стенда повторяют разметку статики
руками, и go-тест рядом с замером сверяет, что она собирается теми же блоками:
замер на своей вёрстке зеленел бы и после правки статики.

На главной кнопки заведения называют доску: «Новая задача в devkit» и
«Черновики devkit». Досок на дашборде несколько, рядом с кнопкой на главной
нет заголовка, и прежняя «Новая задача» молча заводила строку в тот проект,
который дашборд показывал последним. На самой доске подписи остаются
короткими, там проект назван заголовком экрана.

Клик по строке доски открывает экран задачи (`#проект/DK-NNN`): шапка строки,
полоса сохранения и действий, ранг со слагаемыми, зависимости в обе стороны и
файл задачи. Полоса одна на всё: сначала «Сохранить» с «Отменить правку» (обе
появляются только у изменённой формы), за разделителем вход в разговор
и «Стоп» у живой работы либо действие по
статусу у стоящей, теми же словами, что и на строке доски, а рядом надпись
называет заказ дословно (раздел «Запуск и стоп»). Снятие сессии зовётся одним
словом на весь дашборд: «Стоп» и на форме, и в строке, и в табе сессий, потому
что действие одно. Удачный запуск разговора не открывает, а помечает кнопку
чата задачи рамкой (раздел «Запуск и стоп»); закрытие
пользовательской приёмки идёт без сессии, и вести после него некуда, там
подсказка называет команду `taskctl close` вместо заказа. Вход в разговор
стоит у любой задачи и меняет только подпись: у живой работы это
«Живой статус», у законченной
«Разговор агента». Разговор кончившейся работы лежит транскриптом на диске, и
пока кнопку ставили только у живой работы, попасть в него с экрана задачи было
нечем (DK-280). Отдельной карточки действий у задачи нет. У живых работ кнопка
стопа есть и на карточках доски. Слова «пауза» в статике нет, это держит тест:
стоп называется стопом, а последствия остановки висят подсказкой на самой
кнопке («Сессия агента будет завершена, при возобновлении состояние агента
возобновится с диска»).

Правится строка тут же, по месту, и вся форма разом: заголовок, тип и цена,
слагаемые ранга списком допустимых значений с подсказкой из RANKING.md рядом,
текст файла задачи целиком. Кнопка сохранения одна на весь экран: любое
изменение поля её включает, по ней уезжает всё изменённое (строка через
`PATCH`, файл через `PUT`), а не прошла первая ручка, вторая не идёт и правка
остаётся в полях. Отдельных кнопок правки у заголовка и у файла нет, с
телефона это разваливало правку на два похода. У нетронутой формы кнопок
сохранения нет вовсе: и «Сохранить», и «Отменить правку» появляются с первой
правкой поля, надписи про отсутствие правки нет, а отмена перечитывает экран и
черновик выбрасывает. Отказ ручки гасит «Сохранить» и называет причину рядом.
Зависимости названы словами, «Заблокировано задачами» и
«Блокирует выполнение задач», и живут своими кнопками «Добавить» и «Снять»
(обе стороны одинаковы, вторая снимается у той задачи, в чьём заголовке стоит
маркер); файла нет, и кнопка «Завести файл» чинит дыру: обе правки идут своей
командой утилиты и формой не собираются.

Поправку на баг экран сверяет с типом теми же словами, что и ручка: у типа
`task` слагаемое не ставится, кнопка гаснет и причина сказана вслух. Бакет P
рукой не выбирается вовсе, и рассказывает об этом подсказка на самом бакете
(«Бакет считается из суммы ранга, рукой не ставится: правьте слагаемые»).
Порядок в Backlog выводится из ранга, и говорит это счётчик секции («64, по
рангу»), а не надпись под формой.

У цели (заголовок от слова «Цель:») над содержимым стоит состав сабтасками
(макет «06 Цель», ручка `GET /goals/{id}/tasks`): счётчики «закрыто, в работе,
впереди», полоса прогресса и строки задач. Живые идут сверху и открываются
кликом, закрытые свёрнуты в одну строку «Ещё N закрытых задач»: у долгой цели
их набирается больше, чем помещается на экран, а смотрят в состав ради
несделанного. Заголовок задачи берётся со строки доски или из архива, а судьба
из нарезки остаётся подсказкой: строка говорит, что это за задача, нарезка,
зачем она цели. Своего реестра состава у цели нет: нарезка живёт разделом
«Задачи цели» файла цели, его пишет виток скилла goal-loop, и задачей цели
считается ID, который открывает элемент списка либо назван с метаданными в
скобках (`DK-252 (bug, M, R=39, ...)`), включая перечисление через запятую
перед общими скобками. Так из состава выпадают чужие упоминания вроде «ждёт
XR-252 на доске xr» и «остаётся черновиком DK-136 вне цели». Пустота различима
тремя причинами и в каждой названа словами: файла цели нет, раздела «Задачи
цели» в нём нет, раздел заведён и пуст.

Живое обновление ввод не подменяет: пока в форме лежит правка, перечитанные
данные экран не перерисовывают, а уехавшая под руками строка отмечается
пометкой «задача обновилась, перечитать» с кнопкой. Перечитывает рука, потому
что перечитывание теряет черновик, и решать это таймеру фокуса не по чину.
На телефоне тот же экран собран под ширину телефона (DK-284). Доска, номер и
статус стоят одной строкой крошек, заголовок идёт под ними во всю ширину:
тремя уровнями по вертикали они съедали экран до того, как начиналось само
содержимое. Ранг остаётся на своём месте над описанием, но свёрнут в одну
строку с суммой, и слагаемые разворачивает нажатие на неё; зависимости уходят
под описание, а описание идёт во всю ширину. Разворот стоит в строке ранга
настоящей кнопкой («развернуть», «свернуть»), поэтому слагаемые открываются и
с клавиатуры; на ноутбуке кнопка спрятана стилями, там карточка открыта
всегда. Ширину статика нигде не считает, раскладку и доступность решают
стили. Карточки те же и идут одной колонкой во всю ширину, растягивает их
`align-items:stretch` у колоночного флекса. Подсказки к слагаемым прячутся,
списки значений открываются родным барабаном. Полоса действий на телефоне
стоит под содержимым и собрана кнопками значками с пальцем в 44 пикселя, на
ноутбуке она идёт над содержимым, и у тех же кнопок значок стоит со словом;
подпись у значка остаётся в `aria-label`, иначе с телефона кнопка безымянная.
Ответ на нажатие приходит карточкой поверх экрана и места в раскладке не
занимает (раздел «Запуск и стоп»).

Порядок блоков на телефоне задаёт разметка, а не `order` в стилях: обход табом
идёт по разметке, и полоса, уехавшая вниз одними стилями, оставалась под табом
первой, уводя фокус с заголовка в низ экрана и обратно вверх к описанию.
Блоки переставляет `watchTaskLayout`: на ноутбуке описание слева, ранг и
зависимости в правой колонке, полоса над содержимым; на телефоне колонки нет
вовсе, и всё идёт потоком (ранг, описание, зависимости, полоса). Держит место
подписка `matchMedia(...).addEventListener("change", ...)`, а не снимок ширины
при отрисовке: окно растягивают и планшет поворачивают, экран при этом не
перерисовывается. Подписка живёт одна: следующая отрисовка экрана задачи
снимает прежнюю.

Раскладку узкого экрана держит замер настоящим движком
(`TestStaticTaskNarrowWidths`): стенд открывает страницу дашборда в
headless-chrome на 390 и на 1280 пикселях, подкладывает разметку экрана задачи
и снимает ширины описания, ранга и зависимостей, сдвиг списка от карточки
ответа, место полосы действий и то, сходится ли обход табом с картинкой
(следующая под табом кнопка не стоит выше предыдущей). Проверка
текстом стилей тут не годится, поломку даёт сложение правил из разных мест
файла: строки про флекс и `order` стояли на месте, а описание занимало 240
пикселей из 390. Браузер стенду называет `DASHBOARD_CHROME`, без него шаг
пропускается, как и стенд обрыва связи без node.

Разговор с агентом открывается панелью справа поверх любого экрана проекта:
клик по имени живой работы на карточке доски, чип работы в строке, кнопка
«Живой статус» (у законченной работы «Разговор агента») на экране задачи. Своего
экрана у разговора больше нет, и это первая половина DK-435: прежде он жил
двумя экранами, «Живой статус» показывал ленту без поля ввода, «Чат с агентом»
ту же ленту с полем, но заведён был только для целей, а с экрана задачи
разговор не открывался вовсе.

Панель это хвост адреса: `#проект/chat/<адрес>` над доской,
`#проект/DK-NNN/chat/<адрес>` над экраном задачи. Адрес разговора это либо id
сессии, либо ID задачи, и второе значит «последний разговор этой задачи».
Кандидатов при этом даёт сама задача независимо от переключателя фильтра
списка, а нет у неё своих диалогов, открывается новый чат с её привязкой:
с выключенным фильтром вход с формы задачи открывал последний разговор всего
проекта (живой случай, чат DK-397 с формы DK-459).
Разбор отрезает хвост `/chat/...` первым, остальное читается как раньше,
поэтому панель встаёт над доской, задачей, накопителем и поиском одинаково, а
экран под ней от её открытия не пересобирается (разговора нет в ключе экрана
`screenKey`). Открытие идёт через `pushState`, поэтому кнопка «назад» браузера
и крестик панели закрывают её и возвращают доску на прежнее место, ссылка на
разговор переживает обновление страницы, и послать её себе в заметки можно.
Старые адреса ведут в ту же панель: `#проект/agent/DK-NNN` открывает экран
задачи с её разговором, `#проект/session/<id>` доску с ним же, а
`#проект/chat/DK-NNN` ложится в новую форму как есть.

Ширина панели тянется хватом за левый край и помнится одним числом в
`localStorage` на весь дашборд, а не на задачу: человек ставит её под свой
экран, а не под предмет разговора. Ниже 320 точек лента нечитаема, и это её
пол; потолка в точках у панели нет, он меряется самим окном (ширина окна без
полосы доски в 72 точки), потому что разговор бывает главным делом экрана, а
доска при нём справкой. Память держит запрошенное человеком, а обрезает его
окно при чтении: заход с узкого экрана не усаживает панель навсегда. Ширина уезжает в
переменную `--cw` корня документа и достаётся ленте; список разговоров слева
стоит своей колонкой (`--clw`) и прибавляется к ней, а не делит её. Шире 1100 точек панель стоит колонкой экрана
и сжимает доску рядом; ниже 1100 места на две колонки нет, и панель ложится
поверх доски, а не режет её; на узком экране она занимает его целиком тем же
адресом, отдельного маршрута для телефона нет. Ужимать чат в колонку на 375
точках незачем, там он нечитаем.

Модель разговора стоит в строке отправки списком. У живого разговора список
показывает ту модель, которой сессия работает на самом деле: свою tmux-сессию
дашборд поднял сам и знает её модель, чужое окно vscode называет её
транскриптом. Выбор в списке и есть команда, подтверждений нет: модель
уезжает в память диалога (`POST .../model`), живая сессия снимается целиком
(`POST .../stop` с `{"drop": true}`) и поднимается резюмом с новой моделью,
контекст разговора при этом сохраняется. Мёртвому разговору хватает записи:
её возьмёт ближайший резюм. Заказ резюма едет служебной рамкой
`<devkit-remodel>`, и пузырём человека лента его не рисует: этих слов человек
не говорил. Про саму смену говорит разделитель ленты («модель изменена: fable
-> opus») той же разметкой, что и граница дня; живёт он записью журнала
разговора (`said/<разговор>.jsonl`, разряд `kind: "mark"`), поэтому переживает
и перерисовку панели, и перезагрузку страницы. У живого разговора на второй
подписке список заперт и показывает её имя. Рамка devkit-remodel поднимает
резюм в каталоге первой подписки, а история разговора живёт в каталоге второй,
и сменить модель живого разговора панель тут не может. Модель выбирается
подъёмом нового чата, и выбранное имя доезжает до клиента той же обвязкой
`agentctl exec`, что и у запуска задачи (DK-750).

Разговор общий по машине, и по своему адресу он один и тот же, с какой доски
на него ни смотри: смена проекта в шапке меняет доску под панелью, а панель не
трогает вовсе. Ручки чата при этом адресуются его собственным проектом
(`chatState` возвращает его полем `project`): транскрипт ищется по дереву
проекта, и лента, спрошенная у соседней доски, ответила бы пустотой.

Так ведёт себя адрес сессии. Половина адресов панели своего смысла не несёт и
читается в том проекте, который стоит на доске сейчас. Таковы новый чат
(`new`), чат задачи (`DK-NNN`) и общий чат доски (`board`). Смена проекта в
шапке перечитывала такой хвост заново, и открытый разговор devkit сменялся
пустым чатом соседней доски. Отсюда жалоба пользователя про «чат иногда
переключается на новый пустой диалог», и «иногда» тут ровно эти три вида
адреса. Переход на чужую доску теперь закрепляет хвост за своим проектом и
пишет его видом `проект~адрес` (`chatKeepTail`), тем же, каким его собирает
ссылка из ленты. Разбирает вид обратно `paintChat`, и список, лента и доска
спрашиваются у проекта разговора. Закреплённый разговор бывает нечем показать,
когда доски, за которой он стоит, в конфиге уже нет. Тогда панель пишет
причину в ленту словами сервера. Сторожит стенд `testdata/poc_chatkeep.mjs`.

Список диалогов приезжает окном свежести, а не целиком: транскрипты с машины
не исчезают, и общий список копится сам собой (на живой машине сто сорок пять
разговоров при сорока одном живом). По умолчанию видно разговоры последних трёх
суток плюс живые любого возраста, а глубину открывает кнопка «показать раньше»
в конце списка: она догружает следующую ступень окна (неделя, месяц, весь
список машины). Порог трёх суток живёт одним местом, константой
`chatWindowDays` на сервере, панель его не повторяет и первое окно спрашивает
без ключа; ключ `days` двигает окно, а `days=0` снимает его вовсе. Поиск окна
не знает: набранный запрос догружает весь список машины и ищет по нему, потому
что за поиском идут как раз тогда, когда разговор лежит глубже свежего верха.
Открытый панелью разговор и последний разговор задачи едут в запросе ключом
`keep` и остаются в списке любого возраста: иначе окно уносило бы из выпадашки
то, на чём панель стоит прямо сейчас.

Строки идут группами. Первой стоит обособленная группа открытого чата,
если панель его держит. Подпись у неё «открытый чат», и до него не надо
долистывать: он верхний при любом своём возрасте. Ниже подписанная группа
живых («активные»), дальше по дням, «сегодня», «вчера» и датой («21 августа», с
годом только у чужого года). Порядок по свежести внутри групп прежний.
Подпись у активных стоит не для красоты. Без неё трёхдневной давности живой чат
вставал выше сегодняшнего мёртвого. Заголовок «сегодня» съезжал вниз и читался
поломкой сортировки, хотя порядок по времени был верным всегда (жалоба
пользователя). Порядок групп и подписи собирает `chatGroups` в static/app.js.

Пока список открыт, порядок строк на экране не пересчитывается. Сложенную при
первом показе последовательность помнит замер `order` в `chatDropOpen`.
Досыпанное поиском или кнопкой «показать раньше» встаёт в конец своей группы,
уже показанное оно не трогает. Уборка отработавшего разговора не выбрасывает
его строку сразу и не сдвигает соседей. Тронутая запись остаётся на месте
гашёной, клеймом «в архиве» и потускневшей рамкой, до следующего открытия
списка. Признак архива на это время держит клиент: перечитка списка идёт следом за
уборкой, не дожидаясь её подтверждения, и более быстрый ответ сервера мог бы
вернуть строку к жизни раньше времени. Без этого замера уборка
пачкой отработавших чатов раскладывала список заново на каждое нажатие.
Соседняя строка успевала встать под курсор, и человек промахивался мимо нужной
записи (жалоба пользователя). Три положения кнопки архива и тумблер фильтра
задачи всё равно открывают список заново: под ними и должен стоять другой
набор, а не прежний замер.

Уборка в архив того самого разговора, что открыт в панели, переводит панель на
следующий разговор из оставшихся. Второй заход в список для этого не нужен
(жалоба пользователя: «после закрытия чата диалог сам не закрывается»).
Следующий разговор выбирает `chatPanelNext`. Он берёт свой список задачи, если
панель к ней привязана, а иначе видимый список того же проекта, без только что
убранного и без архивных. Нет ни одного подходящего, панель уходит на новый
чат. Окно и группы держат стенды `testdata/poc_chatwin.mjs` и
`testdata/poc_chatday.mjs`, ручку `chatwin_test.go`. Порядок, замер на месте и
переключение панели держат стенды `testdata/poc_chatgroup.mjs` и
`testdata/poc_chatnext.mjs`, ручку `chat_test.go`.

Новый разговор заводится кнопкой «+» до всякой реплики. Прежде разговор и
сессия клиента были одним и тем же: разговор это транскрипт сессии, поэтому до
первой реплики его не существовало нигде, кроме адресной строки вкладки, а
адрес этот (`new`) был один на всю вкладку. Отсюда и жалоба пользователя:
набранный в новом чате текст встречал человека в следующем новом чате, самого
чата в списке было не видно, а завести рядом второй было нечем, «+» уводил на
тот же единственный адрес. Теперь нажатие заводит запись разговора на сервере,
памятью диалога (`~/.devkit/chats/<id>.json`, поле `blank`), и с этой минуты
разговор живёт строкой списка с подписью «не начат». Записей человек заводит
сколько угодно, у каждой свой ID, своя строка и свой набранный текст. Ручка это
`POST /api/projects/{p}/chats/blank` с телом `{"id": "<задача>", "model": "opus"}`,
задача в нём необязательна: с экрана задачи «+» предлагает завести чат про неё
либо произвольный.

Сессию клиента по-прежнему поднимает первая реплика: поднимать её впустую
дорого, а до слов человека и незачем. Дорога подъёма та же, что и была
(`POST .../chats`), только заказ называет свою запись полем `chat`, и запись
запоминает имя поднятой tmux-сессии. Как клиент назовётся в реестре, так список
сверяет это имя и приписывает записи ID выросшей из неё сессии (поле `grown`).
Панель, стоящая на адресе записи, переезжает по нему на живой разговор, в том
числе после перезагрузки и в соседней вкладке, где памяти подъёма нет вовсе.
Строкой списка выросшая запись больше не показывается: разговор уже стоит в нём
своей строкой, с заголовком от первой реплики.

Набранная, но не отправленная реплика живёт при своём разговоре. У начатого её
держит вкладка, у незачатого держать её негде, транскрипта нет, и уезжает она в
память диалога полем `draft` (`POST .../chats/{sid}/draft`). Она же говорит
уборке, что запись человеку нужна. Брошенной считается запись, в которой нет ни
реплики, ни набранного текста, и через трое суток (тот же порог
`chatWindowDays`, что и у окна списка) её стирает очередной заход за списком.
Третьей механики уборки тут не заводится: начатое живёт в списке сколько
угодно, а убрать его рукой можно архивом. Держат всё это ручки
`chatblank_test.go` и стенд `testdata/poc_chatblank.mjs`.

Отработавший разговор убирается в архив рукой, значком в углу его строки. После
разбора десятка черновиков десяток чатов стоит в списке и мозолит глаза. Окно по
свежести их не прячет, они свежие. Убранный разговор пропадает из списка. Живая
сессия у него снимается той же дорогой, что и стоп под перезапуск (`chatKill`).
Дорога назад та же. Значок у архивной строки возвращает разговор в список.
Признак лежит памятью диалога на сервере, полем `archived` в
`~/.devkit/chats/<id>.json`. Он переживает перезапуск дашборда и виден с любой
вкладки. Ручка это `POST /api/projects/{p}/chats/{sid}/archive` с телом
`{"archived": true|false}`.

Разговор груминга уходит в архив сам, когда разбор кончился. Разбор десяти
черновиков оставляет десять мёртвых чатов, и человек убирает их по одному.
Убирает дашборд той же механикой, что и рука (`chatArchive`), второй дороги в
архив у него нет. Условий три, и все обязательны. Первое, разбор оставил
твёрдый след на диске. Файла записи в `docs/tasks/drafts/` больше нет либо
строка с этим ID стоит на доске. Смотрим по факту, слова агента тут не мера.
Отложенный с вопросом сюда не попадает, его файл остаётся лежать. Второе,
человека никто не ждёт, признака ожидания по этому ID нет. До DK-715 признак
жил до срока и протухал сам, а живёт до ответа, и уборка ждёт настоящего
снятия, а не остывшего таймера. Третье, в
разговоре нет непрочитанного. Своей отметки прочтения у нас нет, и сравниваются
два времени. Это последняя запись разговора и последний его показ. Показ
отмечает чтение ленты панелью, полем `seen` в памяти диалога, шагом в полминуты.
Разговор, который человек ни разу не открывал, считается непрочитанным весь.
Возраст хвоста тут не мера. Живой случай до DK-715: чат разбора DK-502 стоял с
вопросом к человеку, разбор при этом кончился строкой на доске, признак
ожидания протух по сроку, и по возрасту такой чат уехал бы в архив вместе с
вопросом. Сверх трёх условий сторож не трогает разговор с
идущим ходом. Снятая посреди работы сессия обрывает разбор. Узнаётся разбор по первой реплике, по заказу `Проведи груминг <ID>`
(`groomOrderPrefix`). Второго признака у него нет, имя tmux-сессии общее с
конвейером задачи. Конвейер сторож не трогает вовсе, обкатывается это на
разборе. Зовётся уборка с экрана накопителя, оттуда груминг и заказывают.
Держит её `groomarch_test.go`.

Показ архивных правит кнопка со значком коробки справа от поля поиска. Положений
у неё три. Не показывать архивные, показывать их вместе со всеми, показывать
только их. По умолчанию стоит первое. Выбор живёт в localStorage ключом
`devkit.chat.arch` и переживает перезагрузку страницы. Пустой запрос считается
с положением кнопки, а набранный текст идёт мимо него. Поиск ищет по всей
машине, и убранный разговор находится без кругового нажатия кнопки (DK-726).
Найденная архивная строка помечена тем же клеймом «в архиве», своей группы у
неё нет. Список, оставшийся пустым при спрятанном архиве, называет число скрытых
им разговоров словами. Убранный живой разговор в положении «показывать все»
стоит группой живых сверху. Поиск сквозь архив и слова о скрытом держат стенд
`testdata/poc_chatfind.mjs` и ручки `TestDashboardSmokeChatFindArchived`,
`TestChatFindBeyondWindow`. Уборку держат стенд `testdata/poc_chatarch.mjs` и
ручка `chatarch_test.go`.

Разговор без единой содержательной реплики в список не едет вовсе: сессия
поднялась и умерла, служебный подъём клиента, заголовок так и не сложился.
Мера тут общая с лентой (`chatBlank` поверх шапки транскрипта): содержательным
считается ровно то, что лента рисует пузырём, слова человека и ответ агента, а
служебные вставки харнеса пузыря не заводят. Своего чтения транскриптов отсев
не стоит, шапка на строку уже прочитана; окно вдобавок снимает чтение шапок с
тех, кто в него не попал, и в этом его выигрыш: на живой машине в окне остаётся
67 строк из 144, ответ весит 41 килобайт против 75, а заход за списком стоит
0,17 секунды против 0,26 у полного (холодный заход, где ещё не прочитана ни
одна шапка, 1,2 против 1,7).

Раскладку панели меряет headless-браузер (`TestStaticChatPanelMeasured` со
стендом `testdata/chat_panel_widths.js`, тот же приём, что у экрана задачи в
DK-284): лента берёт ширину из `--cw`, список разговоров стоит слева от неё
своей колонкой. Доска рядом сжимается ровно на прибавку ленты: на 1120 точках
панель ещё колонка, на 1000 уже лежит поверх доски и доска остаётся той же
ширины, что и без панели. На 390 панель занимает экран целиком, хвата там
нет, и список ложится полосой над лентой. Проверкой текста стилей это не берётся: правила стоят
по разным местам файла, складываются с раскладкой `.screen`, и поломка тут
выглядит целой строкой в css при разрезанной пополам доске. Браузер стенду
называет `DASHBOARD_CHROME`, без него шаг пропускается, и пропуск этот тихий:
голое `go test` печатает `ok` и на машине без chrome. Поэтому по сценарию
проверки DK-435 нужен отдельный прогон, с `-run TestStaticChatPanelMeasured -v`
и строкой `--- PASS` в выводе.

В шапке панели стоит заголовок задачи со строки доски (а у разговора без
задачи первая реплика), под ним день, время и дерево последней записи, рядом
разряд привязки словами («ведёт DK-435, по дереву задачи» против «говорит о»),
переход на экран задачи и привязка разговора к задаче рукой. Кнопка привязки
называет то, чего разговору не хватает. У свободного чата это сама привязка, и
кнопка подсвечена. У привязанного привязка уже сделана и видна чипом задачи,
поэтому предлагать её второй раз нечем: кнопка там говорит про смену и снятие,
а в её окне вместо «Привязать» стоят «Сменить» и «Снять привязку». Прежде окно
было одно на оба случая и первой кнопкой предлагало привязать разговор, у
которого чип задачи уже стоял (замечание пользователя). Лента одна на прежние два экрана: слова человека и агента идут
пузырями, а свёрнутый вызов инструмента и размышления строкой между ними. По
пузырям читают разговор, по строкам инструментов видят, чем агент занят прямо
сейчас; прежде это показывала полоса tmux, у работы из чужого окна всегда
пустая. Панель собирается один раз на разговор, и перерисовка экрана под ней
не трогает ни ленты, ни очереди исходящих, ни набранного в поле ввода; правится
в ней от обновления одна плашка цели, которая ходит за живой работой.

У свёрнутых блоков ленты одна шапка, общая у размышлений, пересказа сжатого
начала и вести о фоновой работе. Подпись до двоеточия стоит жирным, сводка
после неё уходит в хвост. Хвост режется многоточием, полный текст остаётся
подсказкой. Кнопки копирования и разворота прижаты к правому краю. Длинный
заголовок их больше не сдвигает. Так сошлось после замечания по снимку чата
задачи. У блока «Фоновый агент: killed» шеврон стоял вплотную к заголовку,
копирования не было, а сводка подлиннее уводила шеврон за край экрана. Держит
шапку стенд `testdata/poc_feedhead.mjs`. Автоматическое уведомление о фоновой
работе приезжает с английской преамбулой-дисклеймером. Сервер режет её до
первого тега, и от записи в ленте остаётся один блок.

Промежуток между соседними записями ленты один и тот же у всякого вида блока.
Сборка кладёт всякую запись в обёртку строки с кружком нити, и зазор между
соседями набирали поля самих записей, а они у видов разные: капсулы служебки
с полями с обеих сторон вставали парами просторнее, чем к репликам. Теперь
шаг несёт строка, полем сверху одним токеном, а запись внутри строки полей
по вертикали не несёт. Держит шаг стенд `testdata/poc_feedstep.mjs`.

В строке отправки стоит кнопка выбора места на экране. Замечание про место
человек описывает словами («та строка с рангом слева»), и исполнитель ищет это
место в статике наугад. Кнопка включает режим выбора. Наведение подсвечивает
элемент рамкой, нажатие кладёт его в набор и гасится, иначе сработало бы само
место под курсором. Выход по Esc и по повторному нажатию кнопки. Панель
разговора из зоны выбора исключена. В реплику едет не живой узел, а описатель,
снятый в момент нажатия: тег с классами, id, data-поля, обрезанный текст, пара
уровней родителей и экран из адреса. У строк задач в описатель входит ID задачи
из dataset, им и различаются двадцать одинаковых строк. Набранные места стоят
фишками в строке вложений и снимаются крестиком. Уезжают они префиксом реплики,
той же дорогой, что и выделение текста, блоком `<picked screen="...">`. Сервер
режет блок из пузыря (`cutPicked`), и при пузыре он встаёт свёрнутой строкой.
Держат пикер стенд `testdata/poc_pick.mjs` и ручка `humansend_test.go`.

Открытая панель разговора не сносится при переключении, а прячется. Возврат в
уже открытый чат показывает готовый узел тем же ходом, без похода в сеть за
состоянием. Прежде каждый заход пересобирал панель заново, и человек смотрел на
плашку ожидания там, где всё было нарисовано минуту назад. Слоты лежат пулом по
ключу разговора, потолок шесть, вытесняется давний по счёту. Вытесненный
разговор возвращается обычной сборкой. Прячется слот через
`content-visibility: hidden`. Узел при этом остаётся в дереве. Браузер держит
отрисовку скрытого поддерева, повторный показ не платит за раскладку, и при
узле остаются позиция прокрутки с раскрытыми блоками. Спрятанный разговор никто
не опрашивает. Живые потоки уходящего гасит `closeChatLive`, общего фона по
пулу нет вовсе. Возврат из пула и перерисовка панели поднимают опросы заново,
тем же порядком, что и первую сборку. Поднимаются лента, занятость и кольцо
хода работ в шапке. У кольца подъём долго никто не звал, и оно замирало в
состоянии ухода до обновления страницы (DK-711). Прочая свежесть возвращённого
приходит этими же опросами, отдельной пересборки слота за показом нет.
Замер возврата при задержке сети 60 мс на запрос: до правки содержимое
появлялось через 62 мс и четыре запроса, после правки тем же ходом, 0 мс.
Держат пул стенды `testdata/poc_pool.mjs`, `testdata/poc_bench_swap.mjs` и
`testdata/poc_ringwake.mjs`, а возврат кольца в живом браузере проверяет
сквозной прогон `TestDashboardSmokeRingWakesOnReturn`.

В пузыре ответа агента сверху стоит цитата: кусок реплики человека, на которую
он отвечает. Механика тут та же, что в мессенджерах. В плотном потоке замечаний
ответ теряется среди ходов инструментов, и по цитате видно, на что он. Нажатие
на цитату ведёт к исходной реплике и подсвечивает её на секунду. Пару считает
сервер. Это реплика человека и первый текстовый пузырь агента после неё по
порядку ленты. Ходы инструментов, размышления и служебные вставки в счёт не идут, а
ответ, ушедший каналом в панель, идёт наравне с обычным пузырём. Слова другого
агента, приехавшие каналом, репликой человека не считаются. На пачку реплик с
одним ответом цитируется последняя, и подсказка цитаты говорит, что реплик было
несколько. Едет цитата полями `quote`, `quoteKey` и `quoteMany` записи ленты.
Верстается она одной строкой мельче основного текста, приглушённой, с тонкой
чертой слева, отступы из общей лестницы. Пузырь она не раздувает, длинная цитата режется
многоточием. Держат её стенд `testdata/poc_quote.mjs` и ручка
`humansend_test.go`.

Ход, которым агент обратился к человеку, стоит в ленте пузырём агента. Реплики панели в сессию без терминального входа доезжают каналом, и ответ агент
шлёт тем же каналом обратно, вызовом `SendMessage` в сокет дашборда. Строкой
инструмента такой ответ терялся среди ходов, и человек своего ответа в чате не
находил (живой случай груминга DK-509). Узнаёт такие ходы сервер, полем `human`
записи ленты. Адрес дашборда он берёт из самой переписки, из рамки
`from-name="dashboard"`, и знает свой сокет вдобавок. Сокет у дашборда новый на
каждый запуск, а разговор с прежним адресом читается дальше. Служебная обвязка
в пузырь не едет. Адрес доставки и ответ канала висят подсказкой подписи.
Отправка субагенту остаётся ходом инструмента, как была.

Сессия, стоящая на вопросе AskUserQuestion, перехваченном хуком (DK-715),
получает реплику разными дорогами по тому, жив ли у неё терминал. С терминалом
она отвечает на клавиши, едва хук отбил диалог и её ход кончился. Реплика едет
той же дорогой, что и любая другая, `send-keys` в её tmux-окно (раздел
«Доверенный ввод из чата»). `settleAsk` рядом с этим только снимает признак
и своим ходом сводит строку в In progress, не дожидаясь тика сторожка. Живого
процесса, который читал бы вход разговора сам, у сессии больше нет. До этой
правки ответ уходил ему файлом, а тому, кто уже кончил ход и вернулся к
приглашению, файл никто не прочитал бы. Без терминала (делегат-субагент,
издательский клиент без tty, задача без живой сессии вовсе) реплика по-прежнему
ложится с адресатом во вход дерева ждущего, ручка называет дорогу словом `ask`
и тут же снимает признак. Без этого он висел бы до второго вопроса. Признака
нет вовсе, или вопрос задала соседняя сессия того же разговора. Тогда реплика
едет обычной дорогой, клавишами или сокетом. Разбор правила адресности лежит в
`docs/lld/DK-430-task-chat.md`, решение 2, держат его стенды `asksay_test.go`.

Правило про этот канал едет в каждый заказ поднятой работы. Собраны общие приписки функцией `orderRules`, текст правила лежит
одной константой `channelRule`. Прежде правило стояло только у разговора, у
груминга черновика заказ свой, и грумер DK-509 прочёл рамку панели как просьбу
другой сессии.

### Доверенный ввод из чата

Реплика из панели входит в живую сессию так же, как набранная в её терминале.
Попробовать просто. Откройте разговор живой tmux-сессии и напишите
`! git status`. Команда исполнится терминалом сессии без витка модели, а сама
она и её вывод встанут в ленте служебными строками. Когда агент заперт вопросом
разрешения, ответьте в тот же чат «да», «нет» или номером пункта. Ответ уедет
клавишами выбора, диалог отпустится, и работа пойдёт дальше без похода к
терминалу.

Строка с `! sudo <команда>` тоже доходит до конца, хотя терминал сессии
поднят без tty и самому sudo пароль показать некуда (DK-772). Дашборд
подставляет себя помощником ввода пароля: sudo зовёт его вместо своего
диалога, и в ленте разговора встаёт вопрос «Пароль просит sudo» с закрытым
полем. Пароль вводится там же, панель отправляет его помощнику, а тот отдаёт
sudo, и вывод команды ложится в ленту как у любой строки с `!`. То же
получает ssh с passphrase ключа. Отмена вопроса или срок ожидания отказывают
sudo, будто пароль не ввели вовсе, и подвисшей команды не остаётся. Помощника
раскладывает `devkitctl doctor --fix` (`tools/askpass/askpass.py`), без него
sudo и ssh из чата отказывают словами про отсутствие помощника, а причина
оседает в журнале дашборда.

Дорог у реплики четыре, и выбираются они по порядку. Сессию, стоящую на вопросе
инструмента ожидания, обслуживает вход разговора (дорога `ask` выше). Дальше
идёт терминальная дорога (DK-480). Разговору с живой tmux-сессией, чьим
хозяином реестр называет его же, реплика подаётся клавишами (`send-keys`) и
приходит агенту вводом человека, без рамки межсессионного канала. Сокет клиента
остаётся сессиям без своей tmux, вроде окна vscode. Текст туда доезжает
межсессионным сообщением с подписью дашборда, `!`-строка там не исполняется, а
подтверждением разрешения такое сообщение не считается. Про это бессилие в
поле `note` стоят слова, и панель показывает их тостом. Мёртвой сессии
реплика поднимает резюм, как и раньше.

Резюм не спрашивает у разговора задачу. Кончившийся разговор без задачи, тот
самый свободный чат из шапки доски, принимает реплику так же, как разговор
задачи. Дашборд поднимает `claude --resume <sid>` в новой tmux-сессии, реплика
человека едет вводной, а ответ агента приходит в ту же ленту. Транскрипт у
продолжения тот же файл. Иначе такой разговор на экране неотличим от живого, а
человек не знает, работает ли чат вообще (замечание пользователя про разговор
из архива).

Индикатор работы над полем ввода один на оба состояния, идущий ход и его
остановку (`makeBusy`, DK-701). Пока агент работает, точка пульсирует и рядом
стоят слова текущего действия («думает...», имя инструмента), взятые из
транскрипта. Когда за разговором нет процесса, индикатор встаёт сам, без
нажатий. Точка гаснет и краснеет тем же цветом, что и «Стоп» строки задачи, а
подпись говорит, что реплика поднимет разговор заново. Раньше это состояние
несла отдельная строка «сессии нет» с кнопкой «Поднять». Кнопка читалась
обязательным шагом там, где хватало и так поднимающей разговор первой реплики.
Кнопки больше нет, поднимать разговор руками не надо.

Поле ввода панели гаснет в двух случаях, и оба называют причину словами.
Первый это подъём сессии. Пока заказанная сессия называет себя в реестре, поле
заперто на несколько секунд, а над ним стоит «агент запускается». Реплика
оттуда ушла бы первым аргументом клиента и подняла бы второго агента рядом с
первым. Второй это адрес без транскрипта. По нему нет разговора ни в списке,
ни на диске, резюмить нечего, и плашка зовёт выбрать разговор в шапке или
начать новый. Прежде причин было четыре, и одной из них стоял кончившийся
разговор без задачи (решение 6 LLD DK-430, пересмотрено задачей DK-727).

Имя окна из реестра адресом само по себе не считается. Запись кладёт хук старта
из переменной `DEVKIT_TMUX`, а её наследует всякий процесс, поднятый изнутри
окна. Печатный `claude -p --resume` чужой сессии записал этим именем себя, и
хозяином `chat-DK-161-1` стал разговор, кончившийся сутками раньше (DK-673).
Поэтому перед клавишами дашборд спрашивает самих клиентов. Реестр клиента
`~/.claude/sessions/<pid>.json` называет tmux-сессию, в которой процесс поднят,
и запись живёт, пока жив процесс. Занято окно другим разговором, и клавиш там
не будет, реплика уедет резюмом. Хозяин окна назван в журнале дашборда строкой
«в окне chat-9 идёт разговор 9dc49d57».

Тем же словом живых клиентов меряется снятие. Уборка в архив и снятие под
перезапуск гасят tmux-сессию, только когда в ней идёт убираемый разговор. Чужая
работа под тем же именем остаётся жить, а ответ ручки говорит, чей это стал
разговор. В списке чатов такая карточка приходит с полями `gone` и `goneTo`, то
есть выглядит снятой и называет занявшего имя. Реплике в такой чат ехать
некуда, панель не отправляет её на сервер вовсе. Пузырь остаётся недоставленным
с причиной и ссылкой на живой чат, куда переехал разговор.

На запертый вопрос разрешения по терминальной дороге отвечается строго. Свободная
реплика превращается в выбор пункта только при однозначном совпадении. Годятся
номер, слова согласия и отказа («да» это первый пункт Yes, «нет» это первый
пункт No) либо однозначное начало текста варианта (`askOptionOf`). Всё прочее в
модальный виджет не печатается вовсе. Латинская буква в свободных словах
сработала бы горячей клавишей, и кнопка нажалась бы вместо человека. С живым
сокетом такая реплика ложится в очередь клиента, и поле `stuck` называет
причину. Без сокета
она остаётся у панели причиной с кнопкой повтора. Молча она не
теряется. Той же дорогой едет и подобранный вариант, когда клавиши подать
нельзя. Клиент перерисовал виджет криво, и знак курсора не попал в разбор
(`errAskBlind`). Стрелки от неизвестной остановки выбрали бы не тот пункт, и
Enter подтвердил бы чужой выбор. Поэтому реплика вместо ответа ложится в
очередь клиента, а без сокета остаётся у панели с причиной. Замороженный
терминал принимает send-keys без эха. Поэтому перед клавишами зонд сокета
проверяет живость событийного цикла. Молчание зонда оборачивается отказом
с именем клина.

Дорога в терминал есть только у человека с дашборда. Ручка `/say` стоит за
входом по куке и сверкой Origin, запись без входа отбивается до первой клавиши.
Правила доверия харнеса при этом не тронуты, сообщение соседней сессии
одобрением так и не считается, починена доставка. Стенды `termsay_test.go`
держат дорогу.

Своя реплика встаёт пузырём сразу по нажатию и стоит в панели одной копией в
любой момент: сверка снимает местный пузырь той же перерисовкой, которой его
копия встаёт в ленту. Сверяется вся лента после каждой перерисовки, а не одна
свежеприехавшая запись: дорог у записи четыре (начальный хвост, поток, догон
после спящей вкладки и страница истории), и страница истории кладёт записи
мимо разбора приехавшего куска, отчего пузырь висел вторым экземпляром
реплики. Сверка идёт по нормализованному сырому тексту, а не по показанному:
в ленте реплика собрана разметкой, а по дороге к транскрипту обрастает рамкой
канала и приписками заказа. Одна запись ленты снимает не больше одного пузыря,
иначе две одинаковые реплики подряд считались бы дублем. Своего номера у
записи журнала два быть не должно: поток дочитывает журнал с номера строки в
файле, а не с числа выживших после слияния записей, иначе одна реплика
приезжает под двумя ключами и лента показывает её дважды. Пришивание нового чата переносит память первой реплики к родившемуся
диалогу, а не стирает её, поэтому пузырь переживает переезд панели и уходит
только своим эхом. Переключение диалога держит прежнее содержимое до готового
нового: плашка «чат открывается...» видна только у пустой панели.
У недоставленной реплики рядом с «повторить» стоит «отменить»: реплика уходит
из очереди и из персиста, автодожим по ней останавливается, а отменённая
первая реплика нового чата возвращает панель в чистое состояние нового чата.

Панель, открытая по задаче без единого разговора, называется самой задачей.
Лента под заголовком говорит одну короткую строку про то, с чего начать.
Прежде заголовок сообщал «Чатов пока нет», а лента повторяла «чатов тут пока
нет, заведите новый кнопкой +». Человек читал два сообщения о пустоте подряд
там, где панель уже открыл. Плашка поля ввода нейтральная, «Написать
агенту...», одна на все дороги реплики. Казённое «Ответ задаче DK-466...»
убрано. Куда уедет реплика, говорит подсказка самого поля.

Поле ввода стоит всегда и гаснет только с названной причиной, причин ровно
четыре. Дерева сессии больше нет (боковое дерево снято слиянием, реплику читать
некому); разговор ведёт цель, и тогда реплика уходит ручкой цели, во «Входящие»
её файла, а панель называет это, а не отказывает; задача закрыта, и живых
сессий у неё нет, разговор лежит в архиве; разговор кончился по жёсткой мере
LLD DK-430, а задачи за ним нет, и тогда рядом с причиной стоит дорога, кнопка
привязки разговора к задаче. Ручку для реплики называет ответ сервера полем
`reply` шапки разговора, а причину гашения полем `replyNote` (`chatReply` в
`chat.go`), и панель выбирает по ним, куда слать. У живого разговора запись
идёт ручкой сессии, у кончившегося с живой задачей ручкой задачи безадресной
строкой, у задачи без единого разговора ею же: строка ляжет во вход и
дождётся первого хода. Молчащая, но живая сессия ввода не гасит, реплика
ложится и ждёт хода.

Ведущей сессии у задачи может не быть ни одной. Доставки тогда нет. Строка
лежит во входе и ждёт. Забрать её вправе только сессия, ведущая эту задачу, и
держит это правило подхват `hooks/chat-in.py`. Ручка говорит про такую реплику
полями `undelivered` и `why`. Панель ставит пузырь недоставленным с причиной
«работа по задаче не идёт, отвечать некому, и реплика ждёт во входе задачи».
Рядом с пузырём стоят повтор, отмена и выход к задаче, откуда поднимают работу.
Сам пузырь не снимается и переживает перезагрузку. Текст человека не теряется
ни при каких условиях. Прежде панель отчитывалась доставкой и снимала пузырь
через десять секунд. Безадресную строку успевала подхватить посторонняя живая
сессия того же чекаута. Человек читал свой вопрос про DK-466 в чужом разговоре
(живой случай). Гасить молча тут нельзя: молчание неотличимо от поломки,
и человек трижды нажмёт «Отправить», прежде чем поймёт.

Клин это разговор, у которого все признаки живого. Сокет берёт реплики и
отвечает удачей, состояние `live`, а хода нет и не будет. Родов у него два.
Клиент пишет в исчезнувший терминал либо стоит с мёртвым событийным циклом при
живом pty, и второй ловится зондом канала. Оба меряются одним порогом,
`stuckLostTerm`: раньше него молчание транскрипта это пауза между ходами.
Признак считает сервер и зовёт его твёрдым полем `heal`.

Твёрдый клин дашборд лечит сам. Плашки с кнопкой «Продолжить» тут больше нет
вовсе: чат должен просто работать, а решение при твёрдом признаке одно и
очевидно. Лечение это два шага. Сначала снятие зависшего процесса, потом резюм
той же сессии с недоставленными репликами вводной. Пока идёт лечение, панель
говорит одно и честное, «разговор перезапускается...». Прежде рядом с плашкой
мигало «агент работает...», хотя ход стоял намертво. Постфактум в ленте
остаётся одна спокойная строка, «разговор перезапущен, продолжаю», пометкой,
как разделитель смены модели.

Снятие процесса необратимо, и осторожности тут три. Лечится только твёрдый
признак, а третий род стоящего чата (клиент спросил разрешение в своём
терминале) не трогается вовсе. Заявку сверяет сервер ручкой
`POST /chats/{sid}/heal` по тому, что видит сам. И один разговор лечится
один раз подряд: клин, повторившийся в окне `healWindow`, получает отказ и
строку в ленте про то, что перезапусков больше не будет. Без этой памяти
получился бы цикл перезапусков.

Кончившаяся подписка это третий род молчащего разговора (DK-647). С клином
его путать нельзя. Признаки живого те же самые. Сокет отвечает, реплика
клавишами уходит удачей. Харнес при этом сам себя ретраит. В транскрипт и в
свою ошибку он не пишет ничего. Разбор 480 сессий машины за 10 дней нашёл 11
таких немых смертей. Единственный след на всей машине это собственная строка
ретрая клиента в пейне tmux-сессии, вида «Weekly limit reached, Retrying in
1h (3pm), attempt 1/300». Лечить тут нечего. Снятый и поднятый заново процесс
упрётся в тот же лимит. Самолечение клина (`heal`) на этот род не отвечает.

Сервер узнаёт строку по паре слов, `limit reached` и `retrying`. Разбор
терпит перенос строки. Часу и часовому поясу в ней верить нельзя, «(3pm)» не
называет ни того, ни другого. Срок сброса сервер берёт из снимка
`~/.devkit/quota` (DK-633). Тот уже умеет считать квоту, и второго источника
тут не заводится. Точно снимок называет только недельное окно. Для прочих
(пятичасовая сессия, к примеру) панель `/usage` его не сохраняет. Срок
остаётся неизвестным.

Причина и срок едут одной фразой, «лимит подписки исчерпан, сброс 15:00».
Полем `quota` разговора она стоит сразу в двух местах. Живым статусом над
лентой открытой панели (`chatWay`, та же строка, что у Login, Stuck и Gone) и
чипом выпадающего списка, до открытия панели. Поле ввода при этом не
гасится. Реплика уезжает клавишами и садится в очередь харнеса. Ответ ручки
`/say` несёт ту же фразу полем `stuck`. Пузырь встаёт «не доставлено» этой
причиной вместо часовой тишины, а лента получает её же пометкой (`saidMark`).
Открывшему разговор позже не приходится гадать, что случилось.

Живого статуса как отдельного места больше нет: всё, что не разговор, стоит на
экране задачи. Там журнал витка панелью с чипом «хвост дописывается» (у цели и
у задачи с живой работой; источник называет сервер, журнал оболочки или раздел
«Журнал» файла цели), состояние работы чипом («активна», «ждёт ответа»,
«простаивает», «сессии нет»), этап работы с временем
(«ревью, 40 мин», поля `stage` и `stage_since` строки доски) и кнопка
«Стоп» с подсказкой о последствиях. Слова состояния приходят из одного словаря
на весь дашборд (`LIVE_WORD` в `static/app.js`): прежде одно и то же состояние
звалось «работает» в табе сессий, «tmux-сессия активна» на форме задачи и
«активна» в снимке tmux, и человек читал это как три разных состояния
(замечание пользователя). Кто ведёт работу (наша сессия, окно человека,
поднятая мимо дашборда), ушло в подсказку чипа: это про происхождение работы, а
не про то, идёт ли она. Полоса tmux убрана совсем: она
брала снимок только у сессий, поднятых самим дашбордом, и у работы из vscode
всегда пустовала, а чем занят агент, теперь видно лентой. Снимок tmux остался
на одном экране черновика, где сессию груминга поднимает сам дашборд и снимок
не бывает пустым.

У задачи, которая ждёт человека, вопрос стоит блоком над полем ввода: чья
задача ждёт, сам вопрос и кнопка на каждый вариант. Обратный отсчёт есть
только пока у признака стоит срок, а признак без срока (обычный случай с
DK-715) висит без отсчёта до самого ответа.
Устройство блока в разделе «Вопрос агента тем же блоком», разбор состояния
ниже, в разделе «Ожидание человека».

Разговоров у задачи бывает несколько (взяли, вернули на доработку, доделали
другой сессией), и панель открывает последний по времени записи. Остальные
стоят списком слева от ленты (DK-436): день и время последней записи, состояние
словом («идёт», «молчит», «кончился»), разряд привязки («ведёт DK-436» против
«говорит о DK-436»), подписка, если её назвала раскладка машины, и первая
реплика подписью. Нажатие меняет разговор заменой адреса, а не толчком в
историю: экран под панелью остаётся прежним, и «назад» после пяти просмотренных
разговоров это одно нажатие до доски, а не пять. Своего экрана «Чаты» нет
нарочно, он был бы третьим местом с лентой.

Оттуда же поднимается новый разговор по задаче: кнопка «Новый чат» спрашивает
первый вопрос (можно оставить пустым) и зовёт `POST /chats`. Сессия зовётся
`chat-<ID>-<n>`, живому конвейеру не мешает и работой задачи не считается,
поэтому вторая карточка живой работы от разговора не появляется. В списке новый
разговор встаёт первым своим ходом: id сессии рождается позже команды, и ответ
ручки говорит об этом словами.

Общий чат доски открывается той же панелью с пустой привязкой, входом из шапки
проекта (значок разговора рядом с колокольчиком, адрес `#проект/chat/board`).
Лента и поле ввода там те же, реплика уходит в личный вход сессии `sess-<sid>`,
а список слева показывает разговоры проекта без задачи (`?free=1`). Нового
разговора без задачи дашборд не поднимает: заказать такой сессии нечего, а
поднятый рукой в любом дереве виден списком с первого своего хода, потому что
запись кладёт хук старта.

Пустоты различимы словами: разговоров у задачи нет вовсе (и рядом слова
сервера о том, сколько транскриптов просмотрено), в транскрипте нет ни одной
реплики, во «Входящих» пусто. Неполный обход каталога транскриптов панель тоже
не скрывает.

Лента разговора приезжает общим куском (`wireFeed` в `static/app.js`, DK-371).
До выноса лент было две, со своим хвостом, своей подгрузкой истории, своим
`firstSeq` и своим `EventSource` у каждой, и правка ленты делалась дважды.
Разницу везут параметры: адрес источника (проект и сессия), размер хвоста
(`CHAT_TAIL`, сорок реплик, столько же шлёт первым делом поток), разметка
реплики, коробка ленты и коробка прокрутки, поколение живых потоков. Устройство
одно: хвост приезжает обычным ответом, дальше дострение потоком с отсевом по
`seq`, а прокрутка вверх тянет историю через `?before=` и пересобирает ленту
(DK-434). Отсев обязателен: свой хвост поток шлёт заново, и без него последние сорок реплик
встали бы в ленту вторым разом. Поколение у панели своё (`chatGen`), а не общее
с экраном: перерисованная по фокусу окна доска иначе гасила бы ленту открытого
рядом разговора. Поток поднимается после ответа с хвостом, и между запросом и
подъёмом открыта щель: смена разговора попадает как раз в неё. Снятую ленту
дашборд помечает на ней самой, а не только общим списком остановок, и
запоздавший ответ эту пометку проверяет: дальше он не идёт и не поднимает
второго потока за спиной у открытой ленты.

Подгрузка вверх слушает саму прокрутку, а не кнопку (DK-434): коробка ленты
слушает событие `scroll`, и запрос за историей уходит, как только взгляд
подходит к верху (`LOAD_MARGIN`, запас до самой границы, чтобы подгрузка
успела встать в дерево раньше, чем её было бы видно). Флаг `loadingOlder` не
пускает второй запрос, пока висит первый: прокрутка у самого верха шлёт
событие на каждый пиксель. Дошедшая до начала разговора лента вместо кнопки
показывает надпись «это начало разговора»: бесконечная попытка подгрузки у
самого верха неотличима от зависшего запроса, и конец истории назван словами.
Слушатель снимается вместе с лентой (`opts.live`), иначе он копился бы у
общей коробки прокрутки на каждое переключение вкладки разговора.

Позиция ленты держится при уходе с экрана и возврате, у каждого разговора
своя: место (у низа или расстояние от него, и глубина истории на тот момент,
`firstSeq`) пишется в `feedPlace` (карта в памяти вкладки с ключом по ID
сессии) на каждый сдвиг прокрутки. Открытие ленты читает карту прежде, чем
решить, куда встать: разговор, открытый впервые или стоявший внизу, встаёт
вниз, как и раньше, а прежде прочитанный восстанавливает своё место. Свежий
заход приносит только хвост (`CHAT_TAIL`). Если до ухода была подгрузка
вверх, прежняя высота ленты больше высоты одного хвоста, и расстояние от
низа само по себе мерилось бы против чужой, куда меньшей высоты, и
клампилось бы к нулю (замечание ревью DK-434). Поэтому перед тем, как встать
на прежнее место, `restorePlace` дособирает историю до той же глубины тем же
запросом, что и подгрузка от прокрутки, не дожидаясь самого жеста. Открытие
хвостом это не задерживает: подъём истории идёт после того, как хвост уже
показан и поток открыт.
`localStorage` тут не участвует: карта живёт, пока открыта вкладка, тот же
выбор описан для памяти позиции у будущей панели разговора решением 5
`docs/lld/DK-430-task-chat.md`.

Держит вынос стенд `testdata/feed_shared.mjs`: статика поднимается в node с
заглушкой DOM, и стенд проверяет
хвост при открытии, отсев повтора, подгрузку от прокрутки вверх без кнопки,
отбор реплики, уход с ленты посреди запроса и слова о пустоте. Позицию за
пределами хвоста стенд проверяет отдельным разговором (свежим ID, не
задетым более ранними шагами файла): подгрузка идёт до ухода, а при
возврате высота коробки занижена. Без дособора глубины (`restorePlace`)
место клампилось бы к нулю. Рост высоты от досбора подаёт сам стенд
(`growScroll` в заглушке `fetch`): заглушка DOM не пересчитывает
`scrollHeight` от вставленных узлов, как настоящий layout. Стенд сам
задерживает и отпускает
ответ сервера: щель между запросом хвоста и подъёмом потока не открывается
мгновенно разрешённым обещанием. Панель целиком держит
стенд `testdata/chat_panel.mjs`: разбор адреса вместе со старыми ссылками,
разворот задачного адреса в свежий разговор, выбор ручки для реплики, четыре
причины гашения, запоминание ширины и её зажим. Проверкой текста статики такое
не берётся: причина гашения складывается из ответа сервера, строки доски и
наличия сессии, а ошибка тут стоит реплики, ушедшей мимо адресата. Без node оба
стенда пропускаются.

Плашка над полем ввода у цели говорит, что сообщение уйдёт агенту, и
закрывается крестиком: прочитав её однажды, держать её над полем незачем. Текст
в ней разный, и зависит он не от списка работ, а от живости витка с ручки
сообщения (поле `live`, правило подхвата): у живого витка в плашке стоят минуты
до доставки и отдельной фразой добавлено, что развернуть работу виток может и
позже, на границе шага, а у цели с мёртвым циклом остаются прежние слова про
следующую рабочую итерацию. Убитая оболочка запись реестра не снимает, и по
списку работ в плашке стояли бы минуты там, где подхвату вносить реплику
некуда. При стоящем цикле плашка показывает, что цикл цели не идёт и сообщение
будет лежать во «Входящих», пока виток не поднят, и держит кнопку «Поднять
виток» с той же ручкой `POST /runs`, что у кнопки в ленте. Отказ крестиком не
закрывается: спрятанный отказ это то же молчание, из которого выросла беда
DK-319, когда человек писал завершившемуся агенту и ждал ответа. Лента прижата
к полю ввода: свежие реплики стоят внизу, у самого поля, а пустота короткой
переписки остаётся сверху.

Своя реплика встаёт под ленту сразу по нажатию «Отправить», ещё до ответа
сервера, и сама говорит, что с ней: «в очереди», «ждёт витка», «доставлено
агенту» или «прочитано агентом». Третье состояние это отметка подхвата на
лежащей строке: реплика внесена в идущий виток, и рядом с состоянием стоит
время доставки, а у отметки с сессией ещё и её начало. Сессии у отметки бывает
и нет (строку съел вопрос витка), и тогда дашборд пишет то же «доставлено
агенту» со временем, а не пустую скобку. Состояние приходит без участия
человека, поэтому открытый чат перечитывает «Входящие» сам, раз в пятнадцать
секунд: доставку делает подхват, и страницу ради неё не перезагружают. Нажимать на реплике нечего, кнопки «Повторить» нет: неушедшее
дожимает сам дашборд, как это делают телеграм с сигналом, а человек видит
только состояние отправки. На слабой связи это разница между видимой отправкой
и молчанием, из которого росли дубли: пока шёл запрос, кнопка гаснет, а второе
нажатие по потерянному ответу добивает серверная дедупликация повтора.
Оборванная связь сюда же: `fetch` в этом случае не отдаёт ответ со статусом, а
бросает исключение, и реплика остаётся в очереди именно перехватом, а не
проверкой статуса.

Очередь исходящих лежит в том же списке своих отправок, что и остальные
состояния, то есть в `localStorage`: перезагрузка страницы её не теряет, а
запись идёт до первой попытки, чтобы закрытая на полуслове вкладка не унесла
текст с собой. Отправка повторяется сама: первая задержка 2 секунды, дальше
удвоение до потолка в минуту, вне очереди повтор идёт по событию `online`
(телефон вышел из метро) и при следующем открытии чата. Дублей от повторов не
будет, и держится это на сервере: ручка `message` узнаёт свою неподхваченную
строку во «Входящих» и второй раз её не кладёт, так что сломанное там
узнавание обернётся строкой на каждый повтор. Вкладки между собой не
договариваются, и две открытые вкладки одного чата шлют текст почти разом,
поэтому сверка с лежащим и запись держатся замком на стороне сервера. Замок
свой у каждого репозитория, а не один на дашборд: под ним держится и коммит с
пушем, и общий запирал бы отправку во все доски, пока один проект ждёт
недоступный origin. Узнаётся
при этом только ещё не подхваченная строка: виток, забравший сообщение между
попытками, оставляет повтор без пары, и текст ложится второй строкой. Риск
принят решением в файле задачи DK-287: закрывать его значит заводить
сообщению сквозной идентификатор и память о выданных, то есть второй источник
правды рядом с файлом цели. Уход с экрана цикл очереди гасит флагом, а не
одним снятием таймера: цикл, застигнутый на запросе, иначе дожил бы до
следующего повтора и удвоился бы при возвращении в чат. Через минуту безуспешных попыток
подпись реплики перестаёт молчать о причине: вместо «в очереди» встаёт «в
очереди N мин, связи нет», и залежавшееся сообщение отправленным не выглядит.
Держит это стенд `testdata/outbox_offline.mjs`: статика поднимается в node с
заглушкой DOM, игрушечными часами и игрушечными «Входящими», связь рвётся и
возвращается, а стенд смотрит подпись реплики, запись в хранилище браузера и
число строк в файле цели. Настоящий браузер тут не подошёл бы: обрыв связи в
нём так не подделать, а ждать растущую задержку по-честному значит держать
тест минутами. Без node шаг пропускается.

Подхваченная витком строка из «Входящих»
уходит, но из ленты не пропадает, а подписывается прочитанной: своих отметок
прочитанного у сервера нет, и список своих отправок держит сам браузер
(`localStorage`, приём DK-246), поэтому в другом браузере такого следа не
будет, зато второго источника правды рядом с файлом цели не заводится.

Чат открывается концом разговора: читается последняя порция реплик
(`?n=40`), лента стоит внизу, поле ввода видно без листания, а история
подгружается сама от прокрутки вверх через `?before=`, и надпись «это начало
разговора» встаёт вместо неё, когда раньше нечего показать (DK-434). Место
взгляда держит якорь: перед каждой перерисовкой меряется, стоит ли лента у
нижнего края, и низ держится только тогда; при чтении истории дописанная
реплика прокрутку не трогает и вниз не бросает. Им же лента встаёт на прежнее
место при возврате на разговор.

Реплики рендерятся своим минимальным markdown (заголовки, списки, код-блоки и
строчный код, жирный и курсив, ссылки): внешних библиотек в статике нет, а
разметка из реплики становится узлами через `textContent`, поэтому тег в
ответе агента виден словами и не исполняется. Кликаются только адреса http и
https, открываются в новой вкладке с `rel="noopener noreferrer"`, а
`javascript:` в реплике остаётся текстом. Время и день реплики берутся в поясе
того, кто смотрит (`toLocaleTimeString`), а не вырезкой символов из метки
транскрипта.

## Промежутки ленты

Записи ленты разговора идут одним промежутком на все виды: реплика, ход
инструмента и заголовок дня стояли с разными отступами (14, 8 и снова 14
точек), лента читалась рвано, а над свежей репликой зиял лишний воздух
(замечание пользователя). Промежуток назван одним токеном (`--feedgap`), и
правится он одним местом; первая запись воздуха сверху не просит, отделять там
нечего. Держит правило стенд `testdata/poc_feedgap.mjs`.

## Перерисовка экрана

Доска перечитывается по фокусу окна, лента чата достраивается событиями, и
обновление это ровно тот момент, когда человек смотрит на экран. Собранный
заново список тут отнимает всё сразу: место, на котором человек стоял, кнопку
под пальцем, раскрытую запись черновика, набранное в поле ввода. Поэтому
перерисовка идёт по месту, а не пересборкой: у каждого узла списка есть ключ
(кто это) и отпечаток (из чего он нарисован), и обновление трогает только те
узлы, чей отпечаток разошёлся. Слой один на все списки (`sync` в
`static/app.js`), и на нём держатся доска, накопитель черновиков, таб сессий,
список LLD, выдача поиска, экран задачи с целью, колонка проектов с селектором
шапки, лента разговора и панели с хвостом. Вне слоя остаются лента уведомлений,
главная и форма заведения: они собираются целиком и держат снимком хотя бы
позицию пролистывания.

Что это даёт с экрана:

- позиция пролистывания переживает обновление. Список прокручен внутри себя, и
  опустевшая на миг коробка сбрасывала прокрутку к началу: обновление по фокусу
  окна уводило человека в начало доски;
- фокус остаётся на своей кнопке. Узел, у которого ничего не изменилось,
  обновление не трогает вовсе, а перерисованный по месту находится снова по
  ключу вместе с кареткой в поле ввода;
- нажатие кнопки не сдвигает экран. Ответ на него приходит карточкой поверх
  экрана и в поток документа не входит (раздел «Запуск и стоп»), а поднявшаяся
  работа прибавляет карточку в полосу живых работ, и список едет вниз на её
  высоту: якорь возвращает картинку на место;
- раскрытое остаётся раскрытым: подтверждение удаления черновика вместе с
  набранной причиной и реплики ленты
  чата переживают обновление теми же узлами;
- разговор собирается один раз на разговор. Перечитанная доска больше не рвёт
  поток событий панели и не собирает ленту заново: обновление правит в панели
  одну плашку цели, а закрывает поток смена разговора или уход с панели;
- открытый разговор остаётся открытым. Лента прежнего экрана агента собиралась
  заново на каждом обновлении и бралась по нулевому элементу списка сессий, а
  список стоит по времени последней записи: соседняя работа поднималась
  наверх списка, и человек дочитывал уже её ход.

Пока строку очереди держат пальцем, экран не перерисовывается вовсе:
пересобранный список увёл бы из-под пальца и саму строку, и щели с коридором,
нарисованные по той доске, с которой жест считает. Обновление возвращается
сразу после броска, его зовёт и сама правка.

Переход это не повод ждать сеть. Экран задачи открывают чаще всего ссылкой из
ленты разговора, и до правки такое нажатие уходило в лесенку из пяти кругов по
сети: список проектов, уведомления, остаток квоты, список подписок, доска и
только потом сама строка задачи. Всё это время человек смотрел на прежний
экран, и форма при обычной для телефона задержке открывалась две-три секунды,
хотя ручки сервера отвечают за десятки миллисекунд (жалоба пользователя).

Теперь переход отвечает в тот же ход, как отвечает переключение разговоров:
пока сеть молчит, на экране уже стоит хлебная крошка с номером и слова «Читаем
DK-100...», а настоящая форма встаёт поверх, когда приедет строка. Заказ строки
уходит тем же ходом, что и запрос списка проектов, а не после него, и ждут они
вместе. Доска экрану задачи не нужна вовсе: живые работы приезжают тем же
ответом, что и список проектов, и поход за доской с подпроцессом taskctl из
перехода ушёл. Список подписок экран ждёт только в первый раз: дальше он
перечитывается в стороне, а кнопка запуска собирается тем, что было верно
мгновение назад.

Держит это замер `testdata/poc_bench_task.mjs`: он открывает панель разговора,
жмёт автоссылку в реплике и смотрит три вещи, отклик в тот же ход, состав
запросов перехода и время до готовой формы. При круге по сети в 60 мс было
«отклика в тот же ход нет, первый отклик 247 мс, шесть запросов лесенкой»,
стало «отклик в тот же ход да, готовая форма 67 мс, доски в переходе нет».

Пустой список проектов и «список не приехал» это разные случаи, и путать их
нельзя: фраза «в корнях конфига не нашлось ни одной доски» вылезала у человека
при четырёх живых досках (замечание пользователя). Ответ, приехавший с отказом
(обрыв связи, отказ входа перед сервером), про настройку не говорит никогда и
уже нарисованное не стирает: экран остаётся как был. Ответ, приехавший после
ухода с экрана, не рисует ничего вовсе: обход идёт и по фокусу окна, и по
опросу, и сверка адреса после ответа отсекает чужой экран.

Про сам отказ связи экран сперва молчит. Одиночный отказ это штатная жизнь
ноутбука: он засыпает, сеть моргает, а сам дашборд перезапускается на каждом
выкате, и уведомления о таком человек не заказывал («зачем о штатной ситуации
делать уведомление»). Экран просто ходит заново через короткую паузу
(`LOST_RETRY`), а слова приходят, только если связь не вернулась за несколько
заходов подряд (`LOST_TRIES`, три захода, то есть около десяти секунд). Тогда
это одна спокойная строка «связь с дашбордом прервалась, экран обновится сам»,
а перечисление причин живёт подсказкой карточки: поверх интерфейса оно
разрасталось красной простынёй на пол-экрана. Вид у карточки спокойный, а не
красный: это не поломка, а временная тишина, и типовой случай тут наш же
перезапуск при выкате. Приехали данные, значит карточка ушла сама.

Тот же порог считает и отправку реплики: связь одна на всё, и число названо
одним местом. Реплику дожимает своя очередь, пузырь помечен и держит кнопку
повтора, поэтому про первый неудачный заход человеку не говорится ничего.

Экран, собираемый целиком (лента уведомлений, главная, форма заведения), через
тот же слой держит хотя бы позицию пролистывания: снимок места берётся до
обновления и возвращается после него. Переход это другой экран, и он
открывается сверху, прежнее место к нему не относится.

Экран задачи и цели живёт на слое целым узлом, а не построчно: у него один
ключ и один отпечаток, собранный из ответа ручки задачи, признаков живой
работы и списка подписок. Строка не менялась, значит возврат в окно не трогает
ничего вовсе, и на экране остаются раскрытый служебный раздел файла, каретка в
поле правки и место чтения длинного файла цели. Уехавшая под руками строка
отпечаток меняет, и экран встаёт заново одной подменой узла, а не на
опустевшей коробке. Живые потоки экрана (журнал витка, план агента) от
обновления по фокусу больше не рвутся: снимает их либо уход с экрана, либо та
самая пересборка. Несохранённая правка формы всё это переживает как раньше:
пока в полях лежит черновик, экран не перерисовывается вовсе, а уехавшая
строка отмечается плашкой «задача обновилась».

Колонка проектов и селектор проекта в шапке на том же слое: отпечаток строки
это её вид, имя с подсветкой выбранного, кружок состояния и число рядом.
Прежде колонка перебиралась целиком на каждый фокус окна вместе с выпадашкой
шапки.

Стенд `testdata/screen_keep.mjs` держит поведение: статика поднимается в node с
игрушечным DOM, где опустевшая коробка сбрасывает прокрутку, а снятый с дерева
узел теряет фокус, то есть ровно с тем, от чего страдал человек. Стенд
прокручивает доску, ставит фокус на кнопку строки, набирает текст в чате,
открывает разговор задачи и после обновления смотрит, что осталось. Экран
задачи он проверяет тем же способом: раскрывает служебный раздел файла, входит
в правку карандашом, ставит каретку в середину текста и зовёт слушателя фокуса
окна, как его зовёт браузер. После этого узлы экрана обязаны остаться теми же,
прокрутка на месте, каретка на месте, раздел раскрытым, а живые потоки
непотревоженными; уехавшая на доске строка, наоборот, обязана экран
перерисовать. Тем же
стендом проверяются состояния экрана черновика: идущий груминг с живым хвостом
и стопом, четыре исхода разбора со своими словами и переходами, вопрос груминга
с уточнением для новой ходки и удаление с подтверждением на месте, где
набранная причина переживает обновление, а пустая не уходит запросом вовсе.
Там же он проверяет признак работы в строке: нажатая кнопка гаснет
до ответа, поднявшаяся работа помечает строку словом «работает» и «Стопом»,
строка в работе без сессии помечена «сессии нет», а событие уведомителя
перечитывает список задач, не сбивая прокрутки. Разговоров у задачи в стенде два, и порядок их меняется между
обновлениями: так стенд ловит и склейку двух работ в одной ленте, и поток,
оставшийся живым после ухода с экрана. Последним шагом он подаёт слова о
нажатии и проверяет, что ни один узел из потока документа их не получил: поток
берётся из настоящего `index.html`, а «поверх экрана» сверяется с настоящим
`style.css`, иначе проверка пересказывала бы саму себя. Тем же стендом держится
и поиск: набор буквы за буквой уходит одним запросом по задержке, поле выдачи
между буквами не пересобирается и курсора не теряет, запоздавший ответ не
рисуется поверх свежей выдачи, а в поиск ведут и косая черта с клавиатуры, и
лупа шапки на телефоне. Им же держится перетаскивание строки очереди: расчёт
коридора и щелей проверяется прямыми вызовами по краевым случаям (верх списка,
низ, равные ранги, глухая щель, единственная строка), а сам жест игрушечными
событиями указателя, и стенд смотрит нарисованный коридор, тело запроса, слова
после броска и откат с ожидаемой разбивкой. Игрушечный DOM ради этого считает
вертикаль списка: щель под пальцем берётся из неё, как в браузере. Он же держит
правило браузера про судьбу касания: не перехватил движение пальца никто,
значит это прокрутка, и указатель отменяется. Взятая строка обязана пережить
первое движение, а до взятия перехвата быть не должно, иначе список перестанет
листаться. Проверкой
текста исходника такое не берётся, а настоящий браузер тут не нужен: предмет
это узлы и фокус, а не ширины. Без node шаг пропускается.

## Экран агентов

Таб «Сессии» на доске (`#проект/sess`) по макету «08 Агенты»: живые работы
проекта одним списком, «кто чем занят», не уходя с доски. Отдельного раздела
«Агенты» с обзором всех досок сразу больше нет: сессия это работа проекта, и
место ей на его доске, а сквозной обзор машины живёт общим списком разговоров
в панели (решение пользователя). Прежний адрес `#/agents` и `#/agents/<запрос>`
переезжает на таб текущего проекта вместе с набранным запросом, чтобы ссылки и
память вкладки не ломались. Своей ручки у таба нет, работы приходят в ответе
`GET /api/projects` вместе со списком проектов, и второго похода на сервер он не
стоит; счётчик на самом табе считает тот же список, что рисует экран.

Табов у доски три на любой ширине: задачи, сессии, черновики. Половин доски
(«Бэклог» и «Сессии» переключателем на телефоне) больше нет: они отвечали на
тот же вопрос, что и полоса табов над ними, и все разделы теперь стоят подряд.
Список сессий один, вложенных табов «Дашборд» и «Прочие» в нём нет:
происхождение видно чипом «мимо дашборда» в самой строке. Поле поиска в шапке
на этом табе фильтрует сессии, а не задачи доски: слова в пустом поле говорят
это же («Поиск сессий»), а набранное живёт в адресе таба.

У каждого таба доски свой бадж с числом: задачи считает доска, сессии список
работ, черновики сервер чтением накопителя (поле `drafts` в ответе
`/api/projects`, без подпроцесса taskctl). Вид баджа один на все три, и голой
цифры у одного лишь таба сессий больше нет: она читалась признаком самого таба.
Полоски «работает N агентов» над доской нет вовсе, она повторяла число с таба и
уводила туда же вторым способом.

Состояние работа получает от сервера полем `live`, и клиент за него ничего не
додумывает: работа без состояния помечена серым кружком и подписью «состояние
неизвестно», снятие ей не предлагается вовсе. Зелёный кружок был умолчанием, и
работа, о которой сервер промолчал, выходила работающей (замечание
пользователя). Занятость самого разговора считается тем же правилом, что и у
работ: транскрипт старше всего, а слову реестра клиента («busy») верят, пока
запись свежа. Прежде разговор, чьей записи в реестре нет вовсе, считался
занятым нулевым значением поля, и семичасовой разговор стоял в списке активным.

Снятая сессия уходит из списка тем же ходом: сервер узнаёт о снятии не
мгновенно (он смотрит список tmux, а тот успевает ответить по-старому), поэтому
снятая строка держится убранной короткой памятью экрана, пока сервер не
договорит своё. Разговор при этом не теряется, и подтверждение снятия говорит
это прямо: снимается только сессия, разговор остаётся в общем списке чатов и
продолжается резюмом.

Порядок строк отвечает на вопрос «чем машина занята сейчас»: сперва
работающие, за ними ждущие ответа, дальше простаивающие, мёртвые в самом низу,
а внутри группы свежий ход выше. Работа без состояния идёт к простаивающим:
неизвестность это не повод хоронить. Список живой, пока таб открыт: он
переспрашивает состояние раз в `SESS_POLL` (четыре секунды) своей ручкой
`GET /api/projects/{p}/works` и перерисовывает только строки, узел за узлом по
их ключам. Полного обхода экрана тут нет нарочно: он уже стоил нам тормозов
панели. Опрос гаснет при уходе с таба вместе с остальными живыми потоками
экрана, и таймер у него один, сколько бы раз таб ни перерисовали. Ручка стоит
недорого: доска приезжает из памяти по отпечатку файла, а разбор хвостов
транскриптов («идёт ли ход») из памяти по отпечатку транскрипта, и повторный
заход на живой машине с тремя десятками сессий укладывается в 15 мс против 63
мс без памяти.

Строка начинается с заголовка задачи, за ним чипами состояние, проект,
происхождение («мимо дашборда» у сессии, поднятой не им) и вид работы («агент
цели», «конвейер задачи», «сессия кончилась», «интерактивная сессия»); ID, статус задачи с доски русским словом («в очереди», «в работе»,
«на проверке», «заблокирована»), имя сессии для поиска в tmux и причина, по
которой задача не узнана, стоят мелкой подписью второй строкой. Словарь
статусов один на весь клиент и лежит рядом с подписями действий строки доски.
Работа, чьей строки на доске нет, остаётся без статуса. Время идёт с начала работы
по данным tmux; у работы из реестра и интерактивной сессии времени в
строке нет. Переходы те же, что на экране задачи: разговор агента у работы
с узнанной задачей, разговор по id сессии у той, чью задачу узнать не удалось
(кнопка «Разговор», DK-294), кнопка стопа только у tmux-работы. Работа, поднятая
мимо дашборда, объясняет это словами и вместо кнопок ведёт на задачу: её сессией дашборд не
распоряжается. Пустота говорит словами и зовёт запустить задачу с доски. На
телефоне работа встаёт карточкой, кнопки в ряд с пальцем в 44 пикселя.

Состояние работы стоит первым чипом и красит кружок строки: «работает» (ход
идёт сейчас), «ждёт ответа» (агент спросил человека), «простаивает» с
давностью последнего хода, «сессии нет». Зелёным горит только идущий ход:
прежде зелёной была всякая живая сессия, и три десятка окон, молчавших часами,
выглядели работающими. Считает состояние сервер (`workState` в `board.go`) по
трём источникам: признак ожидания во входе разговора, транскрипт (по нему
считается сам ход, и только он честен у окон vscode, где реестр состояния не
пишет) и запись реестра клиента с её состоянием и временем касания. Время в
реестре лежит в миллисекундах, нулевое значит «времени нет», и живой такая
запись не считается. Рубеж простоя один на дашборд и назван в коде
(`workIdleAfter`).

Саму давность («простаивает 75 ч 0 мин») сервер считает по последней
содержательной реплике. Это слова человека или ответ агента, те самые, что лента
рисует пузырём. Время правки файла на этот вопрос не отвечает. Транскрипт трогают
и при мёртвом содержимом. Разговор, брошенный трое суток назад, стоял на экране
простаивающим одну минуту (живой случай, сессия adf6218c). Разбор тут общий с
лентой. Служебные записи давность не двигают, будь то отметка харнеса с пустым
телом, постановка реплики в очередь или ход инструмента. Тем же приёмом лечилась
и сортировка списка чатов. Разговор, где содержательных реплик не нашлось вовсе,
говорит об этом словами. Чип читается «простаивает, реплик нет», а время начала
разговора уходит в подсказку. Молчание тут было бы хуже. Касание файла,
показанное как ход, выдаёт брошенное окно за работающее.

Сессию закрывают оттуда же, где она видна. У разговора, живущего в нашей tmux,
это кнопка «Закрыть»: она снимает tmux-сессию той же ручкой
(`POST /chats/{sid}/stop` с `drop`), какой снимает её смена модели, а транскрипт
остаётся, и разговор продолжается резюмом. Занятая сессия (ход идёт, ждут
ответа) снимается только вторым нажатием, простаивающая первым.

Чипов в строке ровно столько, сколько нужно, и состав их разобран с человеком.
Ушли пятеро: имя проекта повторяло таб доски, «агент цели» повторял название
работы, «интерактивная сессия» не значила ничего (headless-заходов в списке и
так не видно), «разговор о задаче» переехал словом к номеру задачи
(«DK-397, разговор» против номера без приписки у ведущей работы), а «активна»
повторяло третий раз то, что уже несут бегущий кружок строки и время работы
справа. Осталось то, ради чего на таб и заходят: чем работа идёт (подписка и
модель) и признак внешней сессии там, где он объясняет отсутствие кнопок.

Подписка узнаётся по дому транскрипта, тем же способом, каким её узнаёт список
чатов: вторая подписка уводит журналы в своё хозяйство каталогом конфигурации,
и транскрипт вне её дома ей принадлежать не может. Своего поля у подписки нет
ни в реестре, ни в имени tmux-сессии. Пусто там, где подписка честно
неизвестна: чип с ней человек читает как факт, и выдумывать её нельзя.

Что стоит в хвосте строки, решают два вопроса. Идёт ли в ней ход: у работы из
списка tmux без признака разговора это конвейер, и кнопка называется «Стоп»,
потому что снимает она работу. Есть ли что снимать: работа из списка tmux
снимается всегда (сама сессия в этом списке и есть доказательство), у неё
своего id сессии в ответе нет вовсе, и снимает её ручка работы по имени
`kind-ID`; разговор снимается, когда его подняли мы и состояние его известно.
Строке, где кнопки нет (окно vscode, терминал, цикл цели, поднятый в другом
месте), вместо неё стоит приписка о том, где эту работу закрывают: «поднята вне
дашборда» у чужого окна, «идёт вне дашборда» у цикла цели из реестра, «имени
сессии нет в реестре» у своей работы с потерянным именем. Прежде там стояло
«снимать нечем», и человек эти слова не читал («совершенно непонятная
формулировка»): сказано было про бессилие дашборда, а не про то, что делать.
Пустой хвост при этом тоже не годится, он читался как недоделанный экран. Слова
берутся одним местом (`workNoDropSay`) и стоят во всех трёх точках показа: чип,
хвост строки и подсказка самой строки, иначе одно и то же объяснялось бы
по-разному.

Закрытие идемпотентно: нашей tmux-сессии уже нет, значит дело сделано, и ручка
отвечает удачей `way: "gone"` со словами «сессия уже закрыта», а не отказом.
Тем же родом отвечает и прерывание хода в снятой сессии. Отказ остаётся там,
где он по делу: разговор, который дашборд не поднимал, снимать отсюда нечем.
Строка уходит с экрана тем же ходом и держится убранной короткой памятью
(`sessGone`, минута): сервер узнаёт о снятии не сразу, он смотрит список tmux, а
тот успевает ответить по-старому.

Прогон тестов в живой реестр сессий не пишет. Команды доски отмечают работу
сессии строкой в реестре (`touchWork` -> `sessions.Touch`), адрес реестра
берётся из дома, а ID сессии из окружения: прогон, запущенный из живого
разговора, дописывал записи деревьями `/var/folders/...` в живой
`~/.devkit/sessions.log`. Реестр после этого забывал имя tmux живой сессии, она
показывалась внешней, и дашборд переставал видеть, чем её снимать (живой случай
`chat-DK-397-1`). Песочницу ставит `TestMain` на весь бинарь прогона: дом
уводится во временный каталог, а ID сессии снимается вовсе, и без него отметка
работы не пишется никуда. Сторожат это стенды `TestRunLeavesLiveRegistryAlone` в
обоих пакетах.

Читатель реестра при этом тоже стал крепче. Запись по факту работы кладут
утилиты доски, и про tmux им не известно ничего: имя сессии в такой строке
стоит прочерком. Свёртка брала свежую запись целиком и имя теряла; теперь поля
не задачные (дерево, транскрипт, имя tmux) добираются из прежних записей, как
это давно делает `sessions.Last`.

Правило таба общее: он показывает живые работы. Разговор, чьей tmux-сессии не
видно, уходит из таба независимо от того, как она кончилась, снял ли её
дашборд, убил ли человек снаружи, вышел ли клиент сам; из общего списка чатов
он никуда не девается и открывается резюмом. Прежде память снятия покрывала
только первый случай, и умершие сами висели строками «сессии нет 7 мин» с
припиской «снимать нечем»: работы в них нет, действий нет, толку от строк тоже
(снимок пользователя). После этого приписка «снимать нечем» осталась ровно там,
где она по делу: сессия жива, а снять её нечем (окно vscode, терминал).

Два случая из правила выпадают нарочно. Цикл цели из реестра дашборд не видит
вовсе, а идёт он на машине, и прятать его строку значило бы врать о работе.
Только что поднятая работа держится в табе льготным окном в две минуты: между
нажатием и первым ходом клиента проходят секунды, сессия ещё не жива, но и не
мертва, а пропавшая строка читалась бы как несработавшее нажатие. Счётчик таба
считает то же, что показано списком: бадж «5» над списком из двух строк
отправлял бы искать пропавшие три.

Пачки «Закрыть простаивающие» тут больше нет. Она считала по разговорам всей
машины, а таб показывает сессии проекта: при пяти видимых строках она
предлагала снять два с половиной десятка, назвав их именами tmux, по которым не
видно, с чем прощаешься. Массовое снятие вернётся другим способом, если
понадобится.

### Кольцо: этапы, окно и живость

В середине кольца стоит ход работы этапами, «выполнено/всего», а не число
агентов: агент один и тот же, а знать надо, сколько шагов позади (замечание
пользователя). Сегменты кольца это те же этапы: пункты файла плана плюс работы
из боковых журналов субагентов. Работа субагента в списке помечена словом
«субагент»: в файле плана такого пункта нет вовсе, он машинный след розданной
работы, и без пометки человек, сверяющий кольцо с `~/.devkit/plans`, читает
такие пункты чужим планом (живой разбор сессии devkit-2e: кольцо «8 из 9» при
шести закрытых пунктах в файле, а девятым стояло её же ревью, розданное
субагенту и ещё не вернувшееся).

У субагентов свои планы, и каждый виден отдельно. `CLAUDE_CODE_SESSION_ID`
субагент берёт у внешней сессии, и на всю пачку он один. По адресу
`<sid>-sub.json` два исполнителя писали план поверх соседского. У DK-641 и
DK-642 ход работы снаружи пропал вовсе. Теперь в адресе стоит метка самого
субагента, `<sid>-sub-<метка>.json`. Метку он выбирает себе одним разом и держит
до конца захода. Годится ID задачи, годится короткое слово.

Метку называет сам субагент, потому что готового признака у него нет.
`CLAUDE_PID` и сокет сообщений у пачки тоже общие, а свой PID шелла живёт одну
команду. Кольцо собирает такие файлы маской по началу имени. Старый адрес без
метки читается по-прежнему. Пункты чужих планов помечены тем же словом
«субагент», что и работы из журналов. Журнал говорит, что работа роздана. План
исполнителя говорит, чем она занята сейчас.

План принадлежит ровно своей сессии. Файл по sid спорных случаев не даёт, имя
сессии не переиспользуется, а вот запасной адрес правила плана (файл по имени
tmux-сессии, его пишет клиент без `CLAUDE_CODE_SESSION_ID`) опирается на имя,
которое дашборд переиспользует: `chat-1`, `task-DK-100`. Такой файл считается
своим, только когда написан после начала самой сессии: раньше её начала писать
её план было некому. Вызовы одного исполнителя в этап сводить не
пришлось: харнес заводит журнал на агента, а продолжения через `SendMessage`
пишутся в тот же журнал, и на живой сессии семьдесят шесть журналов это
семьдесят шесть разных субагентов.

Ждать ответа может и сама строка. Живых сессий за задачей тогда нет ни одной, и
кольцо про это молчит. Ореол не пульсирует, числа в середине нет, от кольца
остаётся тонкий контур. Причина блока стоит рядом чипом, тем же, что у строки
доски, и полный её текст висит подсказкой. Прежде тут горел красный моргающий
кружок с единицей внутри. Единица считала ждущих агентов, которых не было ни
одного. Моргание читалось тревогой, хотя блокировка это состояние задачи
(разбор снимка DK-466). Признак приезжает с сервера полями `parked` и `block`
ручки пульса.

Сегментами кольцо показывает текущую работу, а не историю сессии. В окне
остаются все незакрытые этапы и последние закрытые (`RING_DONE_KEEP`, пять), а
если и после этого этапов больше, чем кольцо умеет показать дольками
(`RING_MAX_SEGS`), остаются свежие. Прежде длинный план рисовался одной
сплошной дугой с засечкой, и человек видел слипшуюся полосу вместо долек.

А дробь в центре считается за сессию целиком: сверху все закрытые этапы, снизу
все этапы сессии. По окну показа она искажала ход работы: числитель
залипал на пятёрке навсегда, окно держит ровно пять последних закрытых, и
продвижения по кольцу видно не было. Обе вещи называет подсказка: «этапов за
сессию 20 из 22, сегментами видно 7 последних». Сам ход стоит дробью в два
яруса: выполнено сверху, всего снизу, между ними тонкая черта. В строку
(«5/12») каждое число делило ширину с соседом и с косой чертой, и крупный шрифт
задевал дугу, а мелкий не читался; в два яруса каждому достаётся вся ширина
просвета, и кегль берётся крупнее. Двузначные числа с обеих сторон (40/47) под
этот просвет и мерялись, а трёхзначным (сотня этапов за три дня делегирования)
кегль сбавлен классом `rlong`.

Занятость бежит подсветкой по самому кольцу этапов, по той же дуге, на которой
стоят сегменты, и той же толщины: тонкой дугой она читалась вторым кружком
внутри, отдельным прибором рядом с кольцом, а не жизнью этой работы. Толщина
берётся одним числом (`RING_W`) и делениями, и подсветкой, а видно деления под
ней за счёт прозрачности в стилях. Отрезок её короткий, на простое анимации нет
вовсе.

Живость кольца держит метка боковых журналов (`subStamp`). В неё идёт не только
каталог, но и время последней записи в самих журналах: новый субагент каталог
трогает, а ход уже начатой работы нет, и кольцо стояло замороженным до
следующего субагента, хотя работа успевала закрыться. Разбор заказов при этом
лежит в памяти процесса по отпечатку файла: план пересчитывается на каждое
движение журналов, а заказов у сессии, делегирующей третий день, под сотню.

### Вопрос клиента кнопками

Клиент, поднятый в незнакомом каталоге, встаёт на вопросе о доверии («Yes, I
trust this folder»), а следом на вопросе про внешние импорты правил, и до
ответа не делает ни хода. Человек этих вопросов не видел вовсе: лента пустая,
реплика висит недоставленной, а ответить можно было только руками в tmux
(замечание пользователя: «не хочу каждый раз чинить что-то через тебя»).

Тем же блоком приходит и вопрос самого агента с вариантами (`AskUserQuestion`):
живой случай, где панель не показывала его вовсе, а человек писал реплики,
которые доходили, но клиент их не читал, потому что ждал выбора. Со стороны это
выглядело как «чаты не работают».

Панель показывает такой вопрос блоком над полем ввода: сам вопрос словами и
кнопка на каждый вариант. Читает его ручка `GET /chats/{sid}/ask`, разбирая
снимок панели tmux (`parseTmuxAsk`): вопросом считается блок вариантов, текстом
вопроса абзац над ним до рамки клиента, а курсор клиента виден стрелкой.
Пояснения под вариантами блок не рвут, и рамка внутри него тоже: у опроса под
вариантами стоит своя кнопка отправки, отбитая рамкой.

Никакой догадки по форме строк тут нет и быть не может. Списком клиент печатает
и собственный ответ, и эхо реплики человека, а строка ввода начинается с того же
знака курсора, что и выбранный вариант. Живых случая два: человек прислал в чат
реплику из трёх пунктов, и панель показала её же заголовком блока «Клиент ждёт
ответа», а пункты 2 и 3 кнопками; следом тем же блоком приехал список задач из
ответа агента, обрезанный по ширине панели терминала.

Рубеж опирается только на то, что печатает сам виджет и чего в выводе агента не
бывает, и родов у него два (`askOnWidget`). Первый и обычный это подсказка
навигации под блоком («Enter to confirm», «Tab/Arrow keys to navigate», «Esc to
cancel»). Второй это сводка ответов, которой виджет кончает опрос. Своей
подсказки она не печатает вовсе (проверено на живом снимке сессии chat-98), но
узнаётся не хуже: несёт и свой заголовок («Review your answers»), и
пары «вопрос-ответ» значками виджета. Прочие следы (полоса шагов, флажки, свои
кнопки) разбираются дальше и в блок доезжают, но сами по себе его не
поднимают. Размен тут осознанный: виджет без обоих родов следа (так стоит выбор
темы в первом запуске клиента, где подсказку унесло за нижнюю кромку панели)
блоком не покажется, и это дешевле, чем показать человеку кнопки от списка,
который агент просто напечатал.

Блоков вариантов на панели бывает несколько, и берётся нижний с подсказкой:
выше него лежит уже прочитанный текст, а строка ввода клиента блок обрывает.
Второй барьер стоит в самой ручке: разобранный вопрос, чьи варианты уже стоят в
ленте разговора репликой человека или ответом агента, это эхо вывода, и до
панели он не едет (`askEchoesFeed`). Совпасть должны все варианты, а не один:
у виджета бывает пункт со словами из разговора.

Виджеты различаются способом ответа, и способ этот читается с самой панели, а
не угадывается. Под нумерованным вопросом клиент пишет «Enter to confirm», и
пункт там выбирается номером. Под опросом агента он пишет про стрелки и Tab, и номер
не работает вовсе: ответ идёт ходом стрелками от той остановки, где стоит
курсор, и Enter. Остановками там бывают не только варианты: на кнопке самого
виджета («Next», «Submit») и на свободном ответе курсор стоит наравне с ними, и
счёт шагов их учитывает (проверено на живой панели).

Вопрос доверия каталогу свежий клиент рисует без номеров вовсе: варианты стоят
голыми строками, выбранный помечен стрелкой, а курсор клиент держит на «No,
exit». Такой блок разбирается своим проходом (`askBareBlocks`): опорой служит
сама строка с курсором, а соседними пунктами считаются только строки, чей текст
начинается ровно в том же столбце, иначе пунктом стал бы всякий абзац под
строкой ввода. Рубеж тут прежний, подсказка навигации под блоком. Отвечается
такой виджет ходом курсора, и это не мелочь оформления: номер в нём не работает
вовсе, а слепой Enter попал бы по «No, exit» и снял бы сессию вместо
подтверждения доверия. Кнопка ведёт курсор до нужного пункта явно (живой снимок
2026-08-28: два чата xr-proxy простояли на этом виджете полдня, потому что
прежний разбор его не видел).

Шаги опроса это табы, и ходят по ним свободно: переход не требует ответа на
текущий шаг, ответы копятся у клиента, а вернуться к отвеченному вопросу можно
в любой момент. Полоса собрана той же механикой и тем же видом, что полоса
табов доски (задачи, сессии, черновики): подчёркивание открытого, тот же размер
и отступы. Кнопки в рамках читались набором действий, а шаг опроса это место,
где человек сейчас стоит.

Переход едет тем же `POST /chats/{sid}/ask`, только полем `step`: он подаёт
стрелки влево-вправо от открытого таба. Открытый таб клиент метит одной
заливкой, поэтому снимок снимается с раскраской (`capture-pane -e`): без неё
считать переход не от чего. Виден переход в тот же ход: подчёркивание
переезжает на нажатый таб сразу, а под ним встаёт каркас соседнего шага с его
именем и словом «открывается», потому что данных соседнего шага у панели нет
вовсе (виджет отдаёт только открытый). Приехавший снимок собирает блок начисто
и всё расставляет по правде. До этого нажатие ждало нового снимка панели, то
есть полсекунды, и всё это время подчёркнут был прежний таб.

Плашки «клиент ждёт ответа в терминале» с командой `tmux attach` под блоком
больше нет: она была нужна, пока ответить на вопрос из панели было нечем.
Собранный блок её гасит, а остаётся она только там, где вопрос с панели не
прочитался, и говорит тогда ровно об этом, называя окно сессии словами, а не
командой для терминала.

Варианты идут списком, каждый своей строкой: отметка слева, слова рядом, а
пояснение клиента второй строкой мельче. Флажок множественного выбора приезжает
состоянием варианта, а не словами: нажатие переключает отметку, не закрывая
вопроса, а отправляет отмеченное кнопка самого виджета. У вопроса с одиночным
выбором флажков нет вовсе, и выбранный вариант клиент метит галочкой в конце
строки, которая тоже читается состоянием.

Слова служебных пунктов клиент печатает по-английски, а панель говорит
по-русски и своими словами: «Next» это «Дальше», «Submit» это «Готово»,
«Chat about this» это «Обсудить в чате». Вариант «Type something» это свободный
ответ: он стоит пунктом списка, а поле с подсказкой «Свой ответ» раскрывается
под списком и только после выбора, а не занимает место в ряду вариантов. Текст
едет клиенту следом за выбором (поля `option` и `text`).

Сводкой («Review your answers») виджет кончает опрос, и второго подтверждения
человеку не нужно: последний ответ и есть отправка. Дашборд проходит сводку сам
(`askPassReview`) и только когда отвечено всё; со своим предупреждением сводка
доезжает до панели и стоит там итогом с одной кнопкой «Отправить ответы», а не
ещё одним опросом.

Блок правится по месту и только когда снимок и правда сменился (подпись
снимка): ответ на шаг опроса не повод собирать разговор заново, а сборка на
каждый заход стирала бы набранное в поле своего ответа. Спрашивается снимок
только у разговора с живой tmux-сессией дашборда.

Открытой панелью показ не кончается, иначе вопрос виден одному тому, кто в чат
зашёл. Про стоящего клиента говорит и строка доски: `widgetWaits` спрашивает
панели живых сессий реестра и кладёт задаче состояние «клиент ждёт ответа», а
сам вопрос уезжает в подсказку чипа. Источник этот стоит вторым, после живого
признака ожидания и раньше парковки: у припаркованной строки захода нет вовсе,
а тут клиент ждёт нажатия прямо сейчас. Тем же снимком список чатов ставит
разговору слово «ждёт ответа в терминале» там, где прежняя мера молчала: на
вопросе доверия сессия ещё не родилась, своего ID у неё нет, и в журнале
уведомителя её нет ни строкой. Снимок стоит подпроцесса, поэтому он помнится
десять секунд (`tmuxAsking`): спрашивают его теперь и список чатов, и каждая
сборка доски.

Доверие каталогу дашборд за человека не подтверждает и в конфиг подписки не
пишет: решение остаётся его, меняется только место, где он его принимает. А вот
предупредить он обязан заранее: подъём нового чата отвечает полем `trust`, если
клиент подписки этого каталога ещё не знает (`trustNote` читает конфиг профиля
тем же разбором, каким его читает выбор каталога для снимка квоты). Человек
узнаёт про вопрос сразу, а не через минуту тишины.

### Вопрос агента тем же блоком

Агент спрашивает человека штатным AskUserQuestion. В сессии, поднятой панелью,
хук PreToolUse `ask-panel.py` перехватывает вызов, кладёт признак ожидания
`.devkit/chat/<разговор>.ask` без срока (DK-715) и паркует задачу. Признак
стоит до ответа, часы ему не указ. Вопрос по розданной работе панель показывала
плоскими строками, а вопрос по своей же задаче не показывала вовсе. От него
оставалась подсказка на поле ввода, которую видно только с мышью, а с телефона
не видно никак. Живой случай DK-650: восемь минут ожидания и парковка, человек
вопроса не нашёл. До DK-715 признак к тому же протухал по сроку. Цель
DK-713 однажды простояла четыре часа: панель диалог диспетчера не
показала вовсе, а его собственная реплика встала в очередь за ним.

Собирает такой вопрос та же ручка `GET /chats/{sid}/ask`, а рисует тот же блок,
что у вопроса клиента. Признак это файл, снимок панели tmux ему не нужен.
Поэтому вопрос агента отвечается первым и разговору с чужим окном тоже.
Варианты стоят кнопками, рекомендованный подписан словами «советует агент»,
пачка вопросов идёт шагами. Шаги приезжают разом, переход между ними никуда не
ходит, а ответы копятся в панели и уезжают одной репликой. Второго ответа
ждать некому. Живого процесса, который бы его читал, больше нет, ответ снимает
признак сама ручка ответа.

Ответ уходит той же дорогой, что реплика из поля ввода, и признак снимается
всегда, а вот куда идёт сам текст, решает живость терминала. Сессия с
терминалом получает его клавишами. Она снова отвечает на ввод, едва хук
кончил её ход, и вход разговора для неё читателя не имеет вовсе. `settleAsk`
рядом с этим только снимает признак и сама сводит строку в In progress, чтобы
доска не осталась висеть «ждёт ответа». Без терминала (делегат, издательский
клиент, задача без живой сессии) текст по-прежнему ложится во вход. Его
забирает идущий ход подхватом, если сессия жива иначе (раздел «Доверенный
ввод из чата»), либо строка остаётся лежать до тика сторожка, если задача уже
припаркована, и её берёт тот, кто задачу продолжит. Вопросов бывает несколько,
и отвечают тому, кто спросил раньше. Порядок считается по времени файла
признака, а не по сроку, которого у него больше нет. Остальные названы в
блоке строкой «следом ждут ответа».

#### Две дороги вопроса и строка журнала

Дорог у вопроса две, и ручка `GET /chats/{sid}/ask` ходит по ним по очереди.
Первой идёт признак ожидания. Это файл, живой tmux ему не нужен, и разговору с
чужим окном вопрос приезжает тем же блоком. Второй идёт снимок панели tmux, и
на нём стоят вопросы самого клиента, доверие каталогу и разрешение на команду.

К разговору признак относят три правила. Сессия в признаке та же, что у
разговора. Сессия в признаке это делегат разговора, и реестр чатов называет ему
родителя. Сессии в признаке нет вовсе, и тогда вопрос идёт в разговор своей
задачи. Про безадресный признак `taskctl ask` так и пишет, что ждёт безадресные
реплики, и ответ панели ложится во вход такой же безадресной строкой. Разговор
без своей задачи не берёт себе безадресный вопрос.

Ни одна дорога вопроса не дала, а клиент по журналу уведомителя стоит на
разрешении. Тогда в `~/.devkit/dashboard.log` уходит строка «клиент chat-13
похоже ждёт ответа, а показывать нечего». Человеку дашборд об этом не сообщает.
Он и так видит своё окно (решение пользователя). Одна и та же строка выходит не чаще
раза в пять минут на разговор.

Строка называет обе дороги порознь. Дорога признака ожидания называет
одно из трёх.

- «вопросов за разговором нет». Признаков во входе не лежит.
- «признак лежит, но не за этим разговором: XR-9 (ждёт сессию 9999aaaa)».
  Вопрос стоит, а сессия в нём чужая. Смотреть надо, кто положил признак.
- «живого признака нет, лежит просроченный: XR-9 (срок вышел в 14:05:00)».
  Ждущий заход кончился, а файл остался. Такой признак снимает сторожок.

Дорога снимка панели называет одно из трёх.

- «вариантов не собралось, разбор надо чинить». Виджет на панели есть, а
  `parseTmuxAsk` его не поднял. Снимок берётся командой
  `tmux capture-pane -p -e -t =chat-13:`.
- «вопрос собрался, но повторяет ленту разговора». Агент напечатал в своё окно
  чужой список, и разбор поднял его как виджет. `askEchoesFeed` отбивает такое.
- «вариантов нет, а панель ответила виджету 1с назад». Человек только что нажал
  кнопку, клиент пошёл дальше, и чинить нечего. Свежесть ответа меряется не
  сроком, а отметкой записи журнала уведомителя, на которой стояла сессия в
  минуту ответа. Отметка это счёт повторов строки плюс сама строка: время там
  пишется до секунды, и два вопроса в одну секунду дают дословно одинаковые
  строки.

До DK-695 строка была одна на обе дороги, и по ней всегда чинили разбор
снимка. Живой случай 31.08-01.09 по клиентам chat-DK-161-1, chat-12, chat-13 и
chat-14 дал восемь таких строк. Шесть из них стоят в пределах секунды после
строки «ответ на вопрос клиента chat-13 в devkit: пункт 1 (Починить сейчас
(Recommended))», две через 5м41с и 5м50с после такой же строки ответа. Текст
варианта берётся из разобранного виджета.

### Вход в клиента с телефона

Разлогиненный разговор дашборд узнаёт и чинит перезапуском. Сам вход оставался
ручным: плашка отправляла человека на машину делать `/login` в терминале.
Живой случай 2026-08-29. Вход истёк посреди работы, разговор встал. С телефона
хода не было вовсе, хотя смотрят дашборд и с телефона.

Вход идёт теперь прямо на плашке разлогина. Дашборд поднимает отдельную
одноразовую tmux-сессию (`login-N`, ручка `POST /chats/login`). Чужой
транскрипт остаётся чистым от диалога входа. Свежий токен ложится в связку
ключей машины и достаётся каждому новому процессу.

До ссылки авторизации сессия проходит выбор способа входа. Разбор панели тот
же, что у вопросов клиента (`parseTmuxAsk`), берётся пункт со словом
subscription. Ссылка узнаётся по своей строке на `https://` в панели. Ручка
стоит на поллинге панели до двадцати секунд и отдаёт человеку готовую
кликабельную ссылку на плашку.

Код авторизации это одноразовый ключ учётной записи. Едет он своей дорогой
(`POST /chats/login/code`), отдельным полем на плашке, нажатиями в сессию
входа. Поле реплики, лента разговора и журнал дашборда кода не видят. Поле
после отправки очищается. Журнал получает только факт и имя сессии.

Исход считывается панелью. Поле кода пропало и не вернулось за пару секунд,
значит вход сделан. Поле вернулось со словами отклонения, значит код не принят.
Умершая сессия это обрыв середины. Каждый отказ назван словами на самой
плашке. После отказа шаг входа остаётся для новой попытки; после смерти сессии
придётся нажать «Войти» снова. Успех снимает одноразовую сессию и зовёт
перезапустить разговор кнопкой. Живые процессы держат старый токен в памяти, и
сами они его не перечитывают.

## Экран ленты

Колокольчик в шапке (`#проект/feed`) по макету «05 Лента»: события трёх типов
DoD цели, чипы фильтров «Все», «Остановки», «Ожидание пользователя» и
«Задачи», группировка по дням («Сегодня», «Вчера», дальше датой) и свежие
сверху. Заголовок ленты её состав не пересказывает, о нём говорит значок
информации рядом. Отбор держит сервер, экран ходит тем же
параметром `?kind=`, что и сквозной прогон. Лента живёт на SSE: стоп,
случившийся при открытом экране, встаёт в неё без перезагрузки страницы.

Событие с задачей ведёт к её строке и к журналу агента, у стопа рядом стоит
действие «Поднять виток» (тот же `POST /runs`, что и кнопка на доске).
Переходы идут по полям события, а не по открытому на экране проекту: лента
машинная, событий всех досок сразу, и виток поднимается в том проекте, где
событие случилось (DK-323). Событие без задачи (самопроверка канала, авария
контура) помечено словами прямо в карточке и не выглядит оторванным. У события
ожидания задача добирается реестром чатов по обрезанному ID сессии: в журнале
уведомителя поле задачи у сессии главного чекаута пустое, и без реестра лента
вела бы в никуда. Когда связать не удалось, причина стоит рядом словами
(раздел «Ожидание человека»).
Уведомление, чей
баннер не ушёл по окну повтора или по фокусу сессии, в ленте остаётся:
событие было, а причина молчания стоит строкой рядом. Пропуск по песочнице
это другое: лента его не показывает вовсе, строкой такое событие не было
своим (DK-283). Отметок
прочитанного у ленты нет: хранить их серверу негде, а держать состояние
клиента дашборд не берётся.

Вход в ленту это колокольчик в шапке, и стоит он там на обоих форм-факторах:
шапка видна над любым экраном, отдельного пункта разделам и нижним вкладкам не
нужно. Счётчика непрочитанного у колокольчика нет, вместо числа точка новых
(DK-246): время последнего захода на ленту помнит браузер в `localStorage`, а
дашборд сравнивает с ним время свежего события журнала и зажигает точку, если
после захода что-то случилось. Заход на ленту точку гасит, событие, пришедшее
на открытый экран, её не зажигает. Отметка живёт в одном браузере: с другой
машины лента выглядит нечитанной, и врать числом «непрочитанных» дашборд не
берётся.

Новое событие всплывает флеш-уведомлением в правом верхнем углу окна и гаснет
само через несколько секунд, полоска под текстом показывает остаток времени, а
тап по телу ведёт в ленту. Крестик и смахивание пальцем в сторону закрывают
карточку на месте, не трогая открытый экран (DK-282): единственным способом
убрать её раньше был переход в ленту, а на телефоне копящиеся карточки
закрывают собой весь рабочий экран. Копится не больше трёх штук, последнее
сверху; на узком экране (тот же рубеж 900px, что у боковой колонки) видна
только верхняя карточка, лишние ждут своей очереди скрытыми. Поток флеша живёт
отдельно от экранов и переживает переходы: закрывался бы он вместе с экраном,
уведомление приходило бы только на ленте, где оно и так видно строкой. Хвост
журнала, который сервер отдаёт при подключении, не всплывает: флеш это про то,
что случилось при открытом окне; тем же событием загорается и точка на
колокольчике, ждать ради этого фокуса окна незачем.

## Экран LLD

Дизайны это своя сущность со своим списком и своей формой, а не хвост экрана
задачи (круг 2 POC DK-470). В шапке проекта рядом с «Главной» и «Доской» стоит
раздел «LLD» (`#проект/lld`): список документов `docs/lld`, свежие сверху по
времени правки, у строки ID, заголовок и дата правки. Поле поиска шапки
фильтрует тот же список, и запрос, не нашедшийся в имени и заголовке, ищется по
тексту документа с цитатой найденной строки.

Строка списка открывает форму документа (`#проект/doc/lld/<файл>.md`) той же
сборкой, что задача и черновик: по умолчанию чтение во всю ширину страницы,
правку включает карандаш, сохранение уводит текст ручкой `PUT /doc` с коммитом
и пушем. Крошки над формой ведут на доску, в список LLD и на задачу документа,
если её ID стоит в имени файла; последней крошкой стоит путь, по нему документ
открывают в редакторе на машине. Незаписанная правка переживает перерисовку
экрана и теряется только со сменой документа.

Обратная дорога идёт блоком «Связи» экрана задачи: свой LLD задачи стоит там
первым чипом, чужие упомянутые следом (`tools/dashboard/lld.go`, `taskLinks`).

## Сквозной прогон

`dashboard smoke` проходит по API агентскую часть DoD цели DK-112 целиком:
доска со статусами и текущими работами, журнал цели из её файла, состав цели
сабтасками, поиск по доске с архивом и текстом задач, запуск работы, сообщение
цели, доставка реплики витку отметкой подхвата и приём строки витком,
стоп, уведомление о стопе в живой ленте, реплика стоп-хука в ленте
служебкой с подписью, уведомление о фоновой работе без портянки
дисклеймера, сообщение
при стоящем цикле, закрытие принятой задачи без витка, выбор подписки при
запуске, подъём нового разговора по задаче поверх живого конвейера, реплика и
уборка при занятом окне, удаление
черновика с причиной, ожидание человека строкой доски и полкой ждущих,
пересчёт ранга перетаскиванием и смерть поднятой сессии, названная исходом;
пройдя, печатает
`dashboard smoke: ok` и выходит нулём, а споткнувшись, печатает шаг и причину
и выходит единицей. Каждый шаг печатает, что увидел, поэтому прогон читается
и как рассказ, а не только как код возврата.

```sh
dashboard smoke            # прогон целиком
dashboard smoke --keep     # то же, но временное окружение остаётся на диске
```

Живого прогон не задевает: свой дом в рабочем каталоге прогона, свой корень с
синтетическим проектом, свой сервер на случайном порту, а `taskctl`, `tmux`,
`claude` и оболочка цикла изображаются фикстурами того же прогона. Бэкенд
уведомлений подменён пустышкой, и баннера на машине не появляется.
Настоящий в прогоне один `hooks/notify.py`: формат его журнала это контракт
ленты, и сквозной прогон держит его проверенным. Чекаут devkit прогон ищет по
`DEVKIT_HOME`, рядом с рабочей директорией и в `~/projects/devkit`; не найдя,
говорит об этом словами, а не тихо подменяет уведомитель фикстурой. Шаг
«уведомление о стопе в ленте» сверяет задачу и проект события по полям ответа,
а не по словам баннера: проекта в тексте нет вовсе, и пустое поле тут значит,
что цепочка от `--task` уведомителя до JSON ручки где-то порвалась (DK-323).

Рабочий каталог прогона лежит в кеше пользователя (`devkit-dashboard-smoke`
под системным кешем), не под системным temp: `hooks/notify.py` метит корень
под `/tmp`, `/var/folders` и `TMPDIR` песочницей и гасит баннер ещё до выбора
бэкенда, а шаг «уведомление о стопе в ленте» проверяет именно доставку через
подменённый бэкенд. Под системным temp сам пропуск по песочнице погасил бы
строку в ленте там, где она обязана быть. Лента больше не показывает такие
строки вовсе (DK-283). Тестовый стенд остальных пакетных тестов
(`tasksEnv` в `tasks_test.go`) идёт тем же путём для своего HOME: настоящий
`taskctl` на фикстурной доске зовёт настоящий `hooks/notify.py` при move на
Check и на блокер, и без подмены HOME его журнал ложится в живой
`~/.devkit/notify.log` машины, а не в песочницу прогона.

Ссылка на файл цели стоит в фикстурной доске прогона тем же markdown, что
пишет taskctl: журнальный шаг идёт до запуска работы, когда журнала оболочки
ещё нет, и проверяет, что строки пришли из раздела «Журнал» файла цели по этой
ссылке. Разметка, принятая за путь, оставляла экран задачи без журнала,
и нашла это живая проверка, а не прогон (DK-255).

Прогон сверяет признак идущей работы в самих строках доски, а не только в
списке работ: до запуска строка цели помечена `gone` (стоит в работе, живой
сессии за ней нет), задача в Backlog не помечена ничем, после запуска у строки
цели стоит `tmux`, по которому список задач и рисует «Стоп», а после стопа
она возвращается к `gone`. У прогона не было шага, который смотрел бы на
строку, а не на список работ, и строка со списком расходились молча
(DK-317).

Пересчёт ранга прогон проверяет исходом, а не жестом: пальца у него нет, зато
есть ручка, которой жест правит строку. Шаг правит одну ценность, сверяет
команду утилиты (`set XR-002 --rank 25+6+1+0+2`), читает новый ранг с
синтетической доски обратно и смотрит, что ответ назвал фактическое место
строки. Там же откат с разошедшейся ожидаемой разбивкой: ручка отвечает словами
и доску не трогает.

Состав цели прогон проверяет на обоих источниках статуса: одна задача нарезки
стоит строкой на фикстурной доске, вторая лежит в фикстурном архиве
`docs/TASKS-archive.md`, и без второй закрытая половина состава долгой цели
выглядела бы потерянной.

Виток в прогоне фикстурный: сообщение проверяется там, откуда его читает шаг
1 скилла goal-loop (раздел «Входящие» файла цели), а запись витка изображается
той же правкой файла, после которой дашборд перестаёт показывать «ждёт
витка». Там же проверяется повтор: вторая отправка того же текста второй
строки витку не заводит. Шаг про сообщение стоящему циклу идёт после стопа и в
этом весь его смысл: цикл уже снят, и ответ ручки сообщения обязан прийти со
словами, что цикл не идёт, а не положить строку молча (DK-319).

Шаг с принятой задачей закрывает её: фикстура `taskctl` отвечает доской из
файла и умеет её править, поэтому нажатие «Закрыть» у строки с пользовательской
приёмкой сверяется трижды. Вызов `close <ID>` виден в журнале вызовов утилиты,
строка уходит и из ответа `list --json`, и из файла синтетической доски, а
tmux-сессии `task-<ID>` за нажатием не появляется: виток тут лишний. Вторым
нажатием прогон проверяет ответ устаревшему экрану, тот самый, ради которого
фикстура дописывает строку в архив (DK-289).

Шаг выбора подписки идёт до самого клиента, а не до строки запроса. В PATH
стенда лежат фикстуры под оба имени клиентов, `agentctl` изображён своей
фикстурой (машинный вид раскладки и `exec`), а фикстура `tmux` команду сессии
не только записывает, но и исполняет. Запрос называет вторую подписку, и
прогон сверяет, что поднялся её клиент с её именем в окружении, а не соседний:
между запросом и клиентом лежат команда сессии, обёртка `agentctl exec` и само
имя, и сломаться может любое из трёх (DK-326). Тем же шагом проверяется отказ
на имени, которого в раскладке нет.

Последним идёт удаление черновика: в синтетическом накопителе лежит запись из
одного слова, ровно такой мусор с доски и снимают. Первое нажатие идёт без
причины и обязано получить отказ с файлом на месте, второе с причиной, и тогда
прогон сверяет вызов `draft drop <ID> --reason ...` по журналу фикстуры, пропажу
файла и ответ ручки исхода: следов нет ни одного, и это `dropped`, а не
молчание. Гоняется прогон руками и тестом (`smoke_test.go`, он же в CI):
сторожем он остаётся только пока его зовут.

## Реестр чатов задачи

Какую задачу ведёт сессия, дашборд читает из машинного журнала
`~/.devkit/sessions.log` (`registry.go`), а не выводит из транскрипта. Пишут
журнал двое: SessionStart-хук `hooks/session-task.py` на рождении сессии и ручка
привязки рукой. Дашборд при подъёме ставит в начало команды сессии
пары `DEVKIT_TASK` и `DEVKIT_TMUX`, и по ним хук пишет задачу и имя
tmux-сессии. Конвейер стартует в главном чекауте, где по дереву задача не
узнаётся. Устройство целиком в `docs/lld/DK-430-task-chat.md`, решение 1.

Собирает эти пары одно место на все дороги подъёма, `launchEnv` в `chats.go`.
Дорог четыре: разговор, конвейер задачи, цикл цели и разбор черновика. Своего
набора у дороги нет ни одного. Прежде сборка звалась `chatVars`, жила у
разговора, а конвейер с разбором звали её сбоку, и разнобой тут стоил дорого.

Дом поднятой сессии настоящий, машинный. Так требует раскладка подписок.
`agentctl exec` разворачивает тильду ключа `home`, и под подложным домом демона
`CLAUDE_CONFIG_DIR` второй подписки указывает в тонкий каталог без логина.
Экземпляр дашборда, поставленный своим домом, из-за этого читает не тот реестр,
куда пишут его же сессии. Живой случай: разбор пачки поднял пять сессий
DK-482..486, агенты работали, а чаты в панели стояли пустыми. Поэтому реестр
читается по обоим домам сразу, своему и машинному (`bindHomes`), той же
дорогой, какой читаются каталоги транскриптов и файлы планов. Записи склеиваются
и сворачиваются по времени, свежая выигрывает.

Привязка делится на два разряда, и разница между ними видна на экране.

- «Ведёт» (`bound: lead`) стоит на записи реестра и на хвосте каталога бокового
  дерева. Только она делает сессию работой задачи: карточка живой работы и
  разговор `task-<ID>` считаются по ней.
- «Говорит о» (`bound: about`) стоит на угадывании по первой реплике и по ветке.
  Такая сессия стоит в списке чатов задачи и открывается, но живой работой не
  горит и пишет в свой личный вход `sess-<sid>` (DK-360).

Отвязка гасит и угадывание: человек сказал «это не работа задачи», и возвращать
её первой репликой значило бы не слышать сказанного. Реестра нет вовсе это
штатный первый запуск, угадывание тогда работает как до задачи.

Признак работы строки доски считается по тому же реестру, но своим критерием, и
разряд привязки в нём не участвует. Работой сессию делают два слова источника,
«дерево» и «работа». Первое кладёт хук старта в боковом дереве задачи, второе
утилиты доски по факту хода: `taskctl move`, `shipctl merge`,
`agentctl stage <ID> разработка`. Слово «заказ» сюда не входит. Его пишет хук
всякому подъёму дашборда, и чат, открытый по строке ради вопроса, отбирал бы у
неё кнопку запуска. Имя tmux-сессии в критерии не участвует вовсе. Поэтому
строку одинаково ведут конвейер, доводящий чат панели и окно vscode. Рабочих
сессий у строки бывает несколько, одна сессия ведёт несколько строк, а конец
работы это запись «снята» с названной задачей. Кладут её `taskctl close`,
`taskctl move` в любой статус кроме In progress и стоп со строки. Разбор в
`docs/lld/DK-430-task-chat.md`, решение 8.

## Исход подъёма сессии

Подъём чата это `tmux new-session -d`, и удачей до DK-728 считался код возврата
tmux. Он означает только то, что сессия создана. Клиент, умерший через секунду,
уносил её с собой, а ручка успевала ответить `200`. Панель в это время обещала
разговор, который вот-вот назовётся в реестре, и обещание висело до конца
опроса.

Теперь у подъёма есть исход. Имя поднятой сессии ложится в свою запись
`~/.devkit/chats/tmux-<имя>.json` вместе с временем подъёма (`chatRaised`).
Дальше за именем смотрят двое. Первый это опрос самой панели. Ожидание подъёма
спрашивает `GET /api/projects/<проект>/chats?tmux=<имя>`, и тем же заходом
сервер сверяет живость сессии. Второй это сторож демона (`chatwatch.go`). Он
обходит поднятые сессии каждые пять секунд и закрывает случай, когда на
разговор никто не смотрит.

Причина смерти берётся у самого терминала. Пока сессия жива, снимается её
панель через `tmux capture-pane`, и снимок держится в памяти процесса со сроком
годности в двадцать секунд. У мёртвой сессии панели нет вовсе. Снимок,
сделанный при жизни, остаётся единственным местом, где написано «Invalid API
key» или «Credit balance is too low». В ленту едут последние двенадцать строк.
Длинный неразрывный кусок латиницы с цифрами затирается. Журнал ленты живёт
столько же, сколько разговор, и ключ подписки остался бы в нём навсегда.

Исход виден человеку тремя местами.

- Ответ поиска по имени несёт поле `dead` со словами и хвостом терминала. Им
  кончается ожидание в панели: память подъёма снимается, плашка гаснет, а на
  месте обещания встаёт причина.
- Лента разговора получает строку-пометку с той же причиной. Лежит она в
  журнале `said`. Поэтому она переживает перезагрузку страницы и видна со
  второго устройства.
- Журнал `~/.devkit/dashboard.log` получает ту же строку для разбора.

Слова у двух смертей разные. Сессия, не назвавшаяся в реестре, умерла немым
подъёмом, и реплика человека до агента не доехала. Сессия, начавшая ход, просто
кончилась, и следующая реплика поднимет продолжение резюмом.

Снятое рукой смертью не считается. `chatWatchOff` зовут все четыре дороги
снятия: стоп чата под перезапуск, уборка разговора в архив, стоп работы и
снятие остатка прошлого разбора перед новым. Сессия уходит с присмотра до того,
как её снимут.

Присмотр стоит там, где панель ждёт рождения сессии опросом. Таких дорог шесть.
Пять это подъёмы чата в `chats.go`: кнопка «+», реплика в незачатую запись,
резюм кончившегося разговора, продолжение работы по задаче и новый чат работы.
Шестая это разбор черновика в `drafts.go`, дорога ожидания у него та же самая.
`groomDraft` зовёт `chatSewHere`, а та ходит в тот же поиск по имени. Смерть
разбора едет в журнал задачи, своего разговора у него ещё нет.

Седьмая дорога это запуск конвейера задачи (`startTaskSession` в `runs.go`).
Панель опроса на него не вешает, работу живой помечают строка доски и карточка.
Присмотр ему нужен ради другого. По смерти конвейера человеку приходит сигнал
об осиротевшей задаче (DK-660, ниже своим разделом).

Одна дорога подъёма остаётся без присмотра. Это сессия входа
(`clientlogin.go`), у неё свой опрос со своим снимком панели и свои слова об
исходе входа.

Перезапуск демона присмотр не теряет. Сторож на старте перечитывает записи имён
и берёт те, у которых стоит время подъёма и не стоит смерть
(`chatWatchRestore`). Выкат меняет бинарь каждый день, и сессии, поднятые до
него, иначе оставались бы без сторожа.

## Задача без ведущей сессии

Исполнитель погибает на середине хода, и строка остаётся стоять в разработке.
Живой случай стоил полутора часов простоя. Сессия исполнителя DK-652 умерла в
16:52, чат задачи стоял пустым, реплика человека лежала во входе
недоставленной, а заметил это человек сам в 18:10. Снаружи такая строка не
отличалась от штатной очереди: кружка живой работы у неё нет, кнопка предлагает
продолжить, и сказать, идёт ли по ней кто-нибудь, было нечем.

Замечает пропажу сторож подъёма. Смерть сессии он ловил и раньше, а тут у неё
появился второй адресат. `chatDeathSay` зовёт `noLeadSay` (`nolead.go`).

Человека зовут не на всякую смерть, а на три условия сразу.

- Умершая сессия вела задачу. Имя задачи лежит в записи имени с самого подъёма,
  и у разговора без задачи его нет.
- Строка стоит в разработке. Строка из Check доработана, из Backlog не начата,
  и звать человека там не к чему.
- Живой работы за строкой не осталось. Мера та же, что у признака строки на
  экране. Разговор о задаче работы ей не даёт, и открытая карточка чата
  осиротелость не отменяет.

Канал тот же, что и у стопа из дашборда. Своего уведомителя дашборд не
заводит, отправку выполняет `hooks/notify.py`, а лента показывает его журнал.
Повод строки `task_nolead`, задача и проект едут своими полями, и с ними лента
ведёт от события к строке доски. Заголовок называет задачу и проект, тело
содержит слова смерти. Ненайденный уведомитель остаётся строкой в
`~/.devkit/dashboard.log`.

Снятое рукой человека тревоги не поднимает. Стоп работы зовёт `chatWatchOff`
до `kill-session`, и о своём стопе человек уже знает. Рядом с ним в ленте
стоит `run_stop`.

Сессия, поднятая мимо дашборда, под присмотр не попадает. Витки цели поднимает
`goal-run.py`, работу из окна человек поднимает сам, и запись имени тогда никто
не заводит. Такая работа видна лентой чата и строкой доски, а уведомления о ней
не будет.

## Ожидание человека

Задача встаёт на первом же вопросе агента, и увидеть это надо с доски, а не
обходом сессий. Состояние собирает `waiting.go` и отдаёт полем `waiting` у
строки доски и у ответа экрана задачи. Устройство целиком в
`docs/lld/DK-430-task-chat.md`, решение 4.

Источников три, и они ранжированы от точного к запасному; выигрывает первый
найденный.

1. Признак ожидания `.devkit/chat/task-<ID>.ask` основного чекаута, его кладёт
   внутренний писатель `taskctl ask`, а зовёт его хук `ask-panel.py` на вопросе
   агента (DK-715). Состояние «ждёт ответа», подпись «спросил агент», в поле
   едут вопросы пачкой, ждущая сессия и срок, если он есть. С DK-715 признак
   обычно живёт без него, до ответа. Признак с вышедшим сроком за ожидание не
   выдаётся. Ждущего за ним нет, снять признак ему было нечем.
2. Строка в Blocked с машинным разрядом причины «вопрос: ...». Состояние
   «припаркована вопросом», подпись «парковка», вопрос берётся из причины.
   Заход тут уже кончился рубежом, и от первого источника это отличается
   словами.
3. Повод `idle_prompt` из журнала уведомителя по сессии, которую реестр чатов
   связал с задачей. Состояние «сессия ждёт ввода», подпись «повод из журнала
   уведомителя», вопроса нет вовсе. Ожиданием считается только событие,
   стоящее в журнале последним у своей сессии: сходившая ход сессия оставила
   бы после него конец хода. Событие старше полусуток тоже не считается:
   у повода нет отбоя, и без срока чип горел бы на строке неделю.

Третий источник опирается на реестр чатов. В журнале уведомителя ID сессии
обрезан до восьми знаков, поэтому сопоставление идёт по префиксу; попали под
префикс две записи с разными задачами, значит событие остаётся без задачи, а
причина стоит рядом словами («обрезанный до восьми знаков ID сессии ... носят
несколько записей реестра чатов»). Выбирать между ними наугад дороже: чип
загорелся бы на чужой строке.

Куда состояние попадает. На строку доски и на карточку задачи чипом со словами,
а обратный отсчёт есть только у первого источника и только пока у признака
стоит срок. У признака без срока (обычный случай с DK-715) чип горит без
отсчёта, сколько бы времени ни прошло. В ленту уведомлений типом `wait`, туда
же переехал повод
`idle_prompt`. В прочих событиях он прятал ровно тот случай, ради которого
строка и загорается. Отдельным уведомлением ожидание шлёт сам писатель
`taskctl ask` поводом `task_ask`, а `task_blocked` остаётся за парковкой. Два
события про один вопрос человек читает как «спросили» и «встали, ответа не
дождавшись». В панели разговора вопрос рисуется блоком с кнопками, тем же,
каким приходит вопрос клиента: варианты, шаги пачки и своё поле для ответа
словами (раздел «Вопрос агента тем же блоком»). Ответ живой сессии с
терминалом уходит ей клавишами, тем же ходом, что и любая другая реплика
панели (раздел «Доверенный ввод из чата»). `settleAsk` снимает признак и сама
сводит строку в In progress, не дожидаясь тика. Без живого терминала
(делегат-субагент, издательский клиент без tty) ответ ложится во вход
разговора файлом, как и раньше, а у задачи без живой сессии вовсе уходит
ручкой задачи `POST /api/projects/{p}/tasks/{id}/message` безадресной
строкой: отвечают тут задаче, и припаркованную строку будит по такой
строке сторожок.

У состояния нет своего поля на доске: доска живёт в git, а ожидание меняется
минутами. Всё, что нужно доске, уже стоит причиной блока.

### Место ждущих

Состояние у строки было, а собранного места у него не было. Человек шёл в
Blocked и сверял строки глазами. После уборки секции дорога удлинялась ещё на
один щелчок.

Полка ждущих это то самое место. Кнопка с часами стоит в шапке рядом с
колокольчиком, на ней число ждущих. Открывается она с любого экрана доски, в
том числе с главной. Лента и полка отвечают на разные вопросы. В ленте видно,
что случилось, а в полке видно, кому отвечать сейчас.

Строка полки несёт проект, задачу с её заголовком, состояние словами, вопрос
текстом и давность молчания. Вопрос стоит в самой строке. За
ним сюда и приходят, а наведением человек читал бы его, уже открыв разговор.
Щелчок по строке открывает разговор ждущего. Над полем ввода там стоит блок
вопроса с вариантами. Разговор чужой доски открывается со своим проектом в
адресе, менять проект доски для этого не нужно.

Список приходит ручкой `GET /api/waiting`. Собирает она его двумя заходами.
Первый берёт строки всех досок с их состоянием ожидания. Второй берёт живые
признаки ожидания, чьей строки на доске не нашлось. Это вопрос грумера
черновика и вопрос сессии, раздавшей работу, и в Blocked их нет вовсе. Порядок
идёт по давности молчания, дольше всех ждущий первым. В пустой полке стоит
строка «никто не ждёт ответа». Нечитаемая доска называется отдельной строкой
под списком. Без такой строки отказ читался бы тишиной.

Число на кнопке обновляется само, раз в пятнадцать секунд, и ещё раз на каждом
заходе на экран. Открытие полки перечитывает список заново. Между заходами
опроса вопрос успевает и прийти, и уйти.

## Наблюдаемость

Журнал `~/.devkit/dashboard.log`: старты и остановки, входы и провалы входа,
ошибки чтения досок. Чтения в журнал не пишутся, иначе опрос открытых
экранов зарастил бы его за день. Молчание различимо: пустая доска, пустой
список проектов и недоступная утилита это разные ответы API с причиной, а не
одинаковый пустой экран.

Каждый исход ручки запуска, стопа и грумминга уходит в журнал с кодом ответа
и причиной отказа (если он есть). Формат одинаков: действие, ID работы, проект
(если известен), номер HTTP-статуса и описание ошибки. Примеры:
`запуск XR-002 в demo не удался: доска не прочиталась 502: ...`,
`стоп отклонён: чужой Origin 403`,
`груминг XR-005 в demo отклонён: файл черновика не найден 404`.
Строка появляется до ответа клиенту и пишется одной строкой без разбиения.
