# devkitctl: обвязка проекта

Подключение devkit к проекту размазано по ручным шагам (шаблон `AGENTS.md`,
файлы правил под каждый инструмент, `taskctl init`,
`git config core.hooksPath`), а сломанную обвязку раньше никто не
диагностировал. Утилита сводит это к двум командам; агент в
свежей сессии гоняет `doctor` и чинит по находкам, вместо чтения инструкций
по подключению. Нужен только python3, запуск прямо из devkit:

```
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py <команда>
```

Длинный путь нужен только первой установке: `update` и `doctor --fix` кладут
рядом с бинарями обёртку, и дальше утилита зовётся по имени, `devkitctl
<команда>`.

## Команды

```
new --prefix XX [--name "..."] [--no-board] [-C dir]
corp [--prefix XX] [--name "..."] [--contour имя] [--key ABC] [--branch tpl]
     [--remote адрес] [-C dir]
doctor [--fix] [--layout] [-C dir]
update [--pin] [--check]
build [--release] [--out dir]
stats [--context] [-C dir]
weigh [--runs N] [--limit T] [--model M] [--prompt "..."] [-C dir]
```

Порядок подключения целиком, оба сценария подряд, лежит в
[CONNECT.md](../../CONNECT.md); здесь разбор самих команд.

`new` подключает проект и доводит его до рабочего состояния сам: директории нет
значит заводит её, каталог не под git значит делает `git init` (без него
`core.hooksPath` вешать некуда, а `shipctl start` падает на первом же шаге). У
репозитория без единого коммита он оставляет свой, пустой: HEAD там
неродившийся, ветку задачи от него `shipctl start` не заводит, и спрашивается
поэтому HEAD, а не то, кто завёл репозиторий (пустым он бывает и заведённым
заранее руками). Не прошёл коммит (git не знает автора) значит шаг уезжает в
список «осталось сделать», а не теряется.
Дальше он копирует шаблон `kit/templates/AGENTS.project.md` в
корень как `AGENTS.md` (плейсхолдеры заполняются), выставляет `core.hooksPath`
на хуки devkit (если у проекта уже есть свои хуки, не трогает их и
подсказывает симлинки), заводит доску через `taskctl init` и болванку
`.devkit/deploy.local` для shipctl (гитигнорит её, `deploy` и `test` пустые,
`autonomous = false`), а последним шагом генерит файлы правил под включённые
харнесы: доска к этому моменту уже есть, и ссылка на правила доски в них
попадает. Для проекта с внешним трекером `--no-board`: доска и обвязка выката
не создаются, трекер вписывается в `AGENTS.md` руками.

`corp` подключает проект корп-контура, где рабочим файлам devkit в дереве не
место: доска, файлы задач и `.devkit` уезжают в боковую директорию
`../<проект>-local`, а в клоне остаётся обвязка. Команда заводит эту директорию
со скелетом доски (`taskctl init`, `docs/tasks/`, болванка `.devkit/deploy.local`)
и своим git-репозиторием, вписывает в её привязку `.devkit/tracker.local` ключ
`repo` с путём клона, ставит в клоне редирект `git config devkit.local
../<проект>-local` (по нему утилиты devkit находят корень, и он же машинный
признак контура), генерит в корне клона тонкий файл контекста харнеса с импортом
на `AGENTS.md` боковой директории, прячет его строкой в `.git/info/exclude` и
разворачивает обёртки хуков на `pre-commit` и `commit-msg` (цепочка из
`hooks/corp.py`: сперва проверки devkit, следом чужой хук проекта, переехавший в
`<хук>.chained`). Оба хука обязательны: дифф смотрит `pre-commit`, сообщение
коммита `commit-msg`, и клон с одной обёрткой пропускал бы локальный ID молча.

Тонкий файл контекста это единственный негитигнорнутый файл обвязки в дереве:
харнес читает его только из корня проекта. Осознанный компромисс, один файл под
строкой exclude против всей остальной обвязки.

Привязка к трекеру заводится тем же прогоном: `--contour` называет контур
компании, `--key` ключ проекта в трекере, `--branch` шаблон ветки, и все три
ложатся в `.devkit/tracker.local` рядом с `repo`. Названного контура на машине
нет, значит `~/.devkit/tracker/<имя>.local` заводится болванкой с заполненной
таблицей `[status]`: сверить её с трекером дешевле, чем писать с нуля, а адрес и
пользователя вписывает человек. `--remote` добавляет боковой директории
origin, тот самый личный приватный remote, без которого обрыв машины теряет
доску.

Префикс доски, совпавший с ключом проекта в трекере, `corp` не пропускает: на
незаведённой доске это отказ с кодом 2 (префикс ещё выбирается), на заведённой
предупреждение, потому что рубеж следов на такой паре не отличает локальный ID
от ключа тикета и правило про ID снимает (DK-124).

Обе команды подключения заканчивают списком «осталось сделать»: что человеку
дописать, с путями файлов и именами ключей, и чем это проверяется. Пустой список
печатается тоже, отдельной строкой: молчание команды и «шагов не осталось»
снаружи выглядят одинаково, а значат разное. В корп-контуре команду выката
список не спрашивает, там её ведёт процесс компании.

Прогон повторяемый: заведённая боковая директория не трогается, доводится
только обвязка клона. Поэтому та же команда и восстанавливает обвязку после
переклонирования или `git clean -xdf`, которые сносят её молча (живёт она в
`.git` и в негитигнорнутом дереве), и подсказка утилит про потерянный корень
зовёт именно её.

`doctor` проверяет обвязку существующего проекта и выходит с 1 при находках. Корень
не под git (например, позван из каталога, где просто лежат проекты рядом) это
находка, а не отказ: без репозитория нет ни проекта, ни обвязки, и проектная
половина проверки (файлы правил, git-хуки, доска, обвязка выката,
markdown-ссылки, ниже списком) по дереву вниз не идёт, иначе там лежат чужие
репозитории, и обход их доктором был бы шумом их находками, а не диагностикой
(DK-160). Машинный контур (раздел ниже) и строка про режим чекаута от корня не
зависят и печатаются как обычно: человек, позвавший доктора из каталога
проектов, часто спрашивает ровно про машину. Список для случая, когда корень
свой:

- файлы правил в порядке (раздел ниже);
- git-хуки devkit подключены (`core.hooksPath` либо симлинки);
- при наличии доски `taskctl lint` проходит;
- при наличии доски есть `.devkit/deploy.local` с непустыми командами выката и
  тестов и он гитигнорнут (иначе адрес из команды утечёт в git). В корп-контуре
  пустой `deploy =` это норма: слияние и выкат там ведёт процесс компании, и
  shipctl отказывает честной строкой. Пустой `test =`
  это отдельная находка: без ключа `shipctl merge` требует `--test` на каждый
  вызов, а процедуре пачки сочинять его под проект нечем;
- журнал запусков `.devkit/log` (его пишут taskctl, shipctl, regcheck и сам
  devkitctl) гитигнорнут, иначе замусорит status;
- локальные markdown-ссылки живой доки ведут на существующие файлы (обобщение
  проверки, которую lint делает для доски). Внутрь блоков кода проверка не
  заглядывает, как и в инлайн-код: ссылка в примере команды это текст, а не
  ссылка. `docs/` не проверяется вовсе: файл задачи описывает состояние на
  момент решения и после закрытия не правится, так что ссылка на уехавший путь
  там законна, и находка по ней звала бы чинить то, что чинить запрещено.
  Исключение считается от корня репозитория, которому принадлежит файл, а не
  от каталога запуска: `docs/` вложенного репозитория, встреченного при обходе
  дерева, исключается тем же правилом (DK-160);
- в корп-контуре обычные проверки идут по боковой директории (доска, файлы
  правил, обвязка выката лежат там), а сверх них идут корп-: файл обвязки в
  корп-индексе, пропавшая строка `.git/info/exclude`, потерянная или
  перезаписанная чужим инсталлером обёртка на любом из двух хуков (пропал
  маркер `devkit-corp-chain`), отсутствующий ключ `repo` в привязке,
  отсутствующий remote боковой директории, префикс доски, совпавший с ключом
  проекта в трекере (на такой паре рубеж следов не отличает локальный ID от
  ключа тикета и правило про ID снимает, `hooks/README.md`), и свежесть
  последнего sync по отметке `.devkit/tracker.sync` (её спрашивают только у
  привязанного к трекеру проекта). Всё, кроме remote и префикса, доводит `--fix`; потерянный редирект `--fix` не
  чинит, там нужна вся раскладка целиком, и находка зовёт `devkitctl corp`.
  Доктор, прогнанный в боковой директории, идёт по ключу `repo` привязки и
  проверяет обвязку названного клона: так потеря находится и тогда, когда сам
  клон про devkit уже ничего не знает;
- в чекауте devkit (`root` совпадает с `DEVKIT`) вес резидента по карманам не
  выше порога, а тело каждого скилла не выше своего (раздел «Вес резидента»
  ниже, DK-029). Находка не проектная, поэтому подключённым проектам её не
  показывает;
- в чекауте devkit раскладка по правилу (раздел «Раскладка» README devkit,
  разбор в `docs/lld/DK-139-repo-layout.md`): запись верхнего уровня вне белого
  списка, код инструмента мимо `tools/<имя>/`, инструмент на двух языках, sh не
  обёрткой и sh, переросший обёртку. Находка называет файл и правило, а не
  только факт. Признак devkit тот же, по которому чекаут находит стенд
  послушания (`RULES.core.md` и `hooks/` в корне): в чужом проекте раскладка
  своя, и правило туда не едет.

На релизном чекауте самого devkit (`root` совпадает с `DEVKIT`, HEAD отвязан
на теге `v*`, тот же признак, по которому строка режима чекаута ниже говорит
«на релизе») из списка выше молчат вовсе: git-хуки, `taskctl lint` вместе со
всей обвязкой выката (`.devkit/deploy.local`, его гитигнор, журнал запусков) и
порог веса резидента с телом скиллов. Все три адресованы тому, кто в devkit
коммитит, сливает задачи через `shipctl` или пишет скиллы и правила, а машина
потребителя, поставившая devkit по `CONNECT.md`, ничего из этого не делает: её
чекаут детач на теге, коммитов там не бывает вовсе (DK-163). Файлы правил
(проверка вклейки в `AGENTS.md`) и markdown-ссылки в этот список не входят и
считаются всегда: они разбирают содержимое самого чекаута, на исправном
релизе молчат сами, а находка по ним значит дефект самого выпуска, который
стоит увидеть и потребителю. На ветке (машина разработчика) состав проверок не
меняется, и подключённого через `-C` проекта эта поправка не касается вовсе:
его обвязка проверяется в прежнем составе независимо от режима чекаута devkit.

Раскладку зовут и отдельно, без машинной обвязки:

```sh
python3 tools/devkitctl/devkitctl.py doctor --layout
```

Печатает только находки раскладки и выходит с 1 при них. Отдельная форма нужна
CI: полный `doctor` смотрит на `~/.claude`, собранные бинари, tmux и снимок
квоты, и на голой машине сборщика дал бы десяток находок про ненастроенное
окружение, а не про дерево. Ходит проверка по `git ls-files`, а не по диску,
иначе `__pycache__`, собранные бинари и рабочие файлы worktree краснели бы на
чистом репозитории каждый день. Sh она узнаёт по расширению и по shebang: три
точки входа git расширения не имеют. Не смотрит вовсе на `docs/tasks/`,
`testdata/` любой утилиты и `kit/harness/snap/`: там код под чужой контракт или
под один прогон. Смысловое (оправдан ли go новому инструменту, верна ли группа
внутри `kit/`) остаётся на ревью, машина ловит форму.

Место оболочки скилла проверка понимает буквально: `kit/skills/<имя>/` рядом со
своим `SKILL.md`, а не «где-нибудь под `kit/skills/`». Широкий префикс пускал бы
и файл прямо в каталог скиллов, и файл подкаталогом глубже оболочки, и таких
мест правило не заводило. Самопроверка скиллов `check-skills.py` с её тестом
названа в проверке поимённо (`SKILLS_SELFCHECK`): она и правда лежит в самом
`kit/skills/`, потому что проверяет каталог рядом с собой, но список закрытый, и
соседний python исключением не становится.

Белый список верхнего уровня стоит в `layout.py` и тем же составом в разделе
«Раскладка» README devkit, а сверяет их сторож (`layout_test.py`): правило,
которое читают, и проверка, которая его стережёт, обязаны называть одно и то
же.

## Установка и обновление

`update` ставит devkit на машину и он же его обновляет: тулчейна для этого не
нужно, бинари едут готовыми в релизе гитхаба. Отдельной команды `install` нет,
на голой машине та же команда просто проходит все шаги впервые. Решение в
[docs/lld/DK-149-binary-delivery.md](../../docs/lld/DK-149-binary-delivery.md),
порядок установки с нуля в [CONNECT.md](../../CONNECT.md).

```sh
# установка с нуля, одной строкой: клон и первая установка
git clone https://github.com/dronrider/devkit.git ~/projects/devkit && python3 ~/projects/devkit/tools/devkitctl/devkitctl.py update --pin

devkitctl update          # дальше обновление голой командой
devkitctl update --check  # только рассказать, ничего не двигая
```

Шаги такие: отказ, если позвали не из основного чекаута; разбор режима чекаута;
`git fetch --no-tags --prune origin refs/tags/v*:refs/tags/v*` (тегов, а не
всего разом: служебный `deployed`, который двигает `shipctl`, команде не
нужен, голым `--tags` роняет fetch, как только расходится с origin, а один
именной рефспек без `--no-tags` всё равно тащит посторонний тег автослежением,
если его коммит клону уже известен); новейший тег из git (`git tag --list
'v*'`, а не из API гитхаба); переход на тег; самоперезапуск уже кодом тега;
тарболл своей платформы и `SHA256SUMS` во временный каталог рядом с каталогом
назначения; сверка суммы; подмена бинарей через `os.replace`; обёртка
`devkitctl` рядом с ними; раскладка машинного контура тем же кодом, что зовёт
`doctor --fix`; рассказ о сделанном и список «осталось сделать».

Рассказ этот человек читает сверху вниз, поэтому однотипное в нём считается, а
не идёт строкой на файл: утилиты одной строкой с версией, числом и именами
(«установлено 6 утилит devkit v0.6.0 (fb1f8d5f9868) в ~/go/bin: agentctl, ...»),
тем же порядком скиллы, определения субагентов и хуки харнеса, а права
машинного контура одним счётом, без перечня самих правил. Число стоит перед
словом, а слово при нём меняет падеж («установлен скилл», «установлено 8
скиллов»): формы слова и сборка строки живут в `say.py`, чтобы установка,
доктор и права говорили одинаково. Сами слова про то, что случилось с машиной
(установлено, обновлено, включено, дописано), а не про раскладку файлов.

То же правило действует и на находки, и оно одно на весь вывод: шесть утилит
мимо PATH это одна строка с их перечнем, а не шесть строк подряд, и так же
считаются недостающие скиллы, определения субагентов и хуки харнеса. Порознь
остаются только беды с разным текстом (своя версия, свой коммит): их и надо
прочитать по одной.

Режим чекаута команда не угадывает, а различает, и случаев три.

- **Отвязанный HEAD на теге**, машина потребителя. Обычный ход: перейти на
  новейший тег и поставить бинари этого тега. Ключей не надо.
- **Ветка**, чекаут разработчика devkit. Команда отказывается: в основном
  чекауте ведётся доска, оттуда `shipctl` заводит ветки задач, и отвязанный
  HEAD ломает всю эту работу разом. Обновление тут это `git pull` и
  `doctor --fix` с локальной сборкой.
- **Ветка и `--pin`**, первая установка. Свежий клон стоит на `main`, и перевод
  его на тег человек разрешает явно. Ключ нужен ровно один раз, обратный ход
  это `git checkout main`.

Отвязывает чекаут режим, а не расхождение коммитов. Тег ставится на голову
`main`, и на свежем клоне вершина ветки и новейший тег это обычно один коммит:
переходить некуда, а `git checkout --detach` всё равно нужен, иначе машина
остаётся на ветке и следующий вызов отказывает ей как дереву разработчика.

Своя работа под отказ не попадает: перед переходом меряются изменённое
отслеживаемое (`git status --porcelain --untracked-files=no`) и коммиты, до
которых не достаёт ни одна ветка origin (`git rev-list --count HEAD --not
--remotes`). Через `@{u}` это не считается: у отвязанного HEAD upstream нет
вовсе, и проверка отказывала бы на машине потребителя каждый раз.
Untracked-файлы переходу не мешают, `git checkout` их не теряет.

Самоперезапуск (`os.execv`) стоит после перехода на тег: иначе вторую половину
работы делал бы python, прочитанный до перехода, то есть старая логика
раскладки клала бы новые бинари. Тег, собранный до появления самой команды,
такой передачи не понимает, и туда команда не перезапускается, а доделывает
работу на месте и говорит об этом.

Молчаливого холостого хода у команды нет, случаи названы поимённо: обновлять
нечего (чекаут на новейшем теге и все бинари отвечают его коммитом, в сеть за
ассетами команда не идёт); тегов нет вовсе (релизов ещё не выпускалось, чекаут
и бинари не тронуты, назван `devkitctl build`); тег есть, а ассетов ещё нет
(щель между пушем тега и концом сборки, позвать позже); сети нет (отказ на
`fetch` либо на скачивании, ни один шаг не сделан наполовину); платформа не из
четырёх пар релиза.

`--check` делает только `git fetch --no-tags --prune origin
refs/tags/v*:refs/tags/v*` и рассказывает: на каком теге машина, какой
новейший, что поставит обычный `update`. Чекаут, бинари и раскладку он не
трогает, а теги в клон приносит, и иначе быть не может: знание о вышедшем
релизе неоткуда взять, кроме origin.

Каталог назначения выбирается по порядку: `DEVKIT_BIN`, если задан, иначе
первый из `~/go/bin` и `~/.local/bin`, который уже стоит в PATH, иначе
`~/.local/bin` (он создаётся). Профиль оболочки команда не правит: каталог мимо
PATH уезжает в «осталось сделать» готовой строкой и держится находкой доктора.
Туда же кладётся обёртка `devkitctl` из трёх строк с абсолютным путём до
чекаута, по ней python-часть зовётся по имени наравне с бинарями. Пишет обёртку
генератор (`update` и `doctor --fix`), а не релиз: путь у каждой машины свой, и
после переезда чекаута она перевыпускается. Помета `# devkit:generated` в ней
стоит затем же, зачем в тонких файлах проектов: чужой скрипт с тем же именем
доктор не затрёт, а скажет про него.

Адрес релизов подменяется переменной `DEVKIT_RELEASE_BASE`. Это шов для тестов
и для прогона в чистом окружении: гитхаб в тестах не участвует, релиз им отдаёт
локальный сервер.

## Сборка бинарей

`build` собирает Go-утилиты devkit с зашитой версией, и точка сборки эта одна:
её же зовёт `doctor --fix`, когда пересобирает устаревший бинарь, и её же гоняет
релизный workflow на раннере. Решение в
[docs/lld/DK-149-binary-delivery.md](../../docs/lld/DK-149-binary-delivery.md).

```sh
python3 tools/devkitctl/devkitctl.py build                    # под свою машину
python3 tools/devkitctl/devkitctl.py build --release --out dist  # четыре пары
```

Что собирать, команда выводит из дерева (каталоги `tools/*/` с `go.mod`), а не
из списка в коде: по правилу языка go тут это ровно то, что ставится в PATH,
поэтому список сборки, список установки и список проверки доктора совпадают по
построению, и седьмая утилита попадает в релиз тем, что появилась. Версия
берётся из git того чекаута, откуда идёт сборка (`git describe` по релизным
тегам `v*` плюс `git rev-parse --short=12 HEAD`), и уезжает в бинарь линковкой,
`-ldflags -X`. Служебный тег `deployed`, который двигает `shipctl` на каждом
выкате, в счёт не идёт: версия считается по релизным тегам, иначе бинарь
назвался бы именем тега выката. Собирается всё с `CGO_ENABLED=0` и `GOWORK=off`:
чужой `go.work` на машине увёл бы сборку из модуля утилиты, а своего у devkit
нет.

Кладётся собранное рядом с целью и переезжает на место переименованием, а не
пишется поверх: `go build` отказывается писать поверх файла, который не его
(«already exists and is not an object file»), а такой в каталоге назначения как
раз и бывает, доктор чинит расхождение в том числе с чужой копией. На linux к
тому же запись в работающий бинарь даёт `ETXTBSY`.

Собранное проверяется тут же, и проверки две, потому что кросс-собранный бинарь
на раннере не исполняется (darwin на ubuntu даёт `exec format error`).

- Пара своей машины запускается с `--version` и обязана напечатать ту строку,
  которую в неё зашивали: `<имя> <версия> (<коммит>)`. Утилита, забывшая флаг,
  роняет сборку, и это единственное место, где такая пропажа видна.
- Остальные три пары проверяются байтами: зашитая строка обязана найтись в
  артефакте. Проверка слабее, но ловит главную беду `-ldflags -X`,
  несуществующий символ линковщик молча пропускает и собирает бинарь без версии.

Обе пары всё равно исполняются живьём, просто в разных прогонах: `--release` на
раннере проверяет запуском linux/amd64, а та же команда на маке разработчика
darwin/arm64.

`--release` пакует тарболл на пару, `devkit-<версия>-<os>-<arch>.tar.gz`, внутри
плоско лежат все утилиты релиза, и кладёт рядом `SHA256SUMS`. Каталог назначения
по умолчанию `dist` (гитигнорнут), под обычной сборкой тот же, куда ставит
`update`. Промежуточные бинари складываются в каталоге
назначения и убираются после упаковки. Пара, не прошедшая проверку, тарболла не
получает, и в `SHA256SUMS` её нет, а код выхода 1 называет находку.

## Файлы правил

Рукописный файл правил в проекте один, `AGENTS.md`: открытая спека, плоский
markdown, импортов не понимает. Всё остальное генерится, и не отдельной
командой, а тем же `doctor --fix`: дрейф это находка доктора, починка это его
же `--fix`, третьего входа в генерацию нет. Что именно генератор считает
эталоном для проекта, печатает отдельная команда, она же удобная точка для
глаза, когда доктор говорит «устарел»:

```sh
python3 tools/devkitctl/rules.py .
```

Она же собирает раскладку правил для стенда послушания
[obeycheck](../obeycheck/README.md): директория с файлами правил, тонким файлом
харнеса и глобальной точкой в `home/`, ровно та, что доезжает до сессии при
заданной глубине. Стенду раскладка это вход, и боевую пару он получает от
генератора, а не от руки:

```sh
python3 tools/devkitctl/rules.py --layout full ../rules-full tools/obeycheck/testdata/project
python3 tools/devkitctl/rules.py --layout core ../rules-core tools/obeycheck/testdata/project
```

Файлы правил ложатся в корень раскладки голыми именами, и импорты зовут их так
же: раскладка едет в чужой проект целиком, и путь наружу из неё не развернулся
бы. Текст, который глобальная точка и тонкий файл тянут оба, кладётся одной
копией, а лишняя строка импорта из точки снимается: на машине это один файл под
двумя путями, и платить за него дважды стенд не должен. Раскладка саму
глобальную точку только читает: этот раздел про файлы проекта, а генерит и
чинит её отдельная проверка машинного контура (раздел ниже).

Куда попадают правила, решает состав включённых харнесов (`enabled` в
`~/.devkit/harness.local`, проектный `.devkit/harness.local` его только
сужает; конфига нет вовсе, значит включён claude-code):

- все включённые понимают импорты: копий текста правил в дереве ноль. Каждому
  генерится тонкий файл (`file` из его профиля, у Claude Code `CLAUDE.md`) со
  ссылками на `AGENTS.md` и на правила devkit, а проекту с доской ещё и на
  правила доски;
- есть хоть один embed-инструмент: текст правил вклеивается в `AGENTS.md`
  между маркерами `devkit:rules`, а тонкие файлы на devkit больше не ходят,
  иначе их контекст получил бы правила дважды.

Сколько текста правил доезжает, решает не только режим доставки, но и глубина.
Выводится она из оси скиллов профиля харнеса (секция `[skills]`, ключ
`discovery`), разобрана в [DK-100](../../docs/lld/DK-100-context-tree.md):

- `auto`: скиллы инструмент подхватывает сам, значит ему хватает ядра правил
  (`RULES.core.md`, проекту с доской ещё `RULES.board.core.md`), а процедуры
  доезжают скиллами;
- `manual`: скиллы инструменту доступны, но сам он их не объявляет, поэтому к
  ядру прикладывается таблица указателей: строка на скилл с описанием (по нему
  видно, когда он нужен) и путём, по которому его читать;
- секции нет вовсе: едет полный текст правил, как ехало всегда. Пустая секция
  значит то же самое, но по другой причине: ось у инструмента разобрана, и
  скиллов у него нет.

Объявленная глубина это ещё не доехавшая. Пока в devkit не нарезаны все тексты,
которые тянет проект, генератор берёт полный: ядро правил лежит нарезанным
(`RULES.core.md`, `RULES.board.core.md`), а тексту, у которого ядра ещё нет,
урезаться не во что. Ждут ядра обе неполные глубины, и указатели тоже: они
заменяют процедуры, уехавшие в скиллы, а рядом с полным текстом стали бы второй
копией того же самого. Признак глубины в файле показывает факт, а не обещание:
`depth=core` в маркере тонкого файла, `depth=pointers` там же или в маркере
начала вклейки. У полной глубины признака нет, потому что это и есть
сегодняшняя раскладка, а приписка к ней перегенерила бы каждый файл на машине,
не сказав ничего нового. Что объявлено и что доехало, печатает `rules.py`
строкой на харнес:

```text
глубина правил, claude-code: ядро (discovery = "auto", скиллы инструмент подхватывает сам)
```

Вклейка в `AGENTS.md` одна на всех embed-инструментов, поэтому глубина у неё
самая полная из запрошенных: тому, кому нужен весь текст, урезанного не хватит.
Таблица указателей входит в хеш источников наравне с файлами правил, иначе
добавленный в devkit скилл не доехал бы до вклейки молча.

Первая строка генерённого файла это маркер с хешем тела
(`<!-- devkit:generated body=... -->`), у вклейки хеша два: `src` от
источников в devkit и `body` от текста между маркерами. Вопросы разные,
поэтому и хеша два: по свежему `src` не видно ручной правки, по целому `body`
не видно протухания. Отсюда поведение доктора:

- файла нет, а харнес включён: `--fix` его генерит;
- файл устарел (правила devkit обновились, появилась доска, включился
  embed-инструмент): `--fix` перегенерирует и говорит об этом строкой;
- файл правлен руками (содержимое разошлось с хешем): не перетирается, а
  доктор зовёт перенести правку в `AGENTS.md`. То же у вклейки: локальным
  исключениям в общих правилах не место, но и молча стирать чужой текст
  `--fix` не вправе;
- файла нет вовсе, зато лежит рукописный `CLAUDE.md` без маркера: это проект,
  подключённый до переезда, и доктор подсказывает `git mv CLAUDE.md AGENTS.md`
  плюс `--fix`. Сам не переносит: в живых `CLAUDE.md` бывают локальные вещи
  вроде импорта корпоративных правил, автоматике их не разобрать;
- строка импорта в рукописной части `AGENTS.md`: находка, потому что читают
  его и инструменты без импортов, и правила по такой строке до них не
  доедут. Обычно она остаётся после переезда, убирается руками;
- вклейка лежит больше чем в одном файле дерева: находка, копия должна быть
  одна. Маркеры внутри блока кода за копию не считаются, это документация;
- последний embed-инструмент выключен: `--fix` убирает вклейку и возвращает
  тонким файлам ссылки на devkit. Это единственный случай, когда `--fix`
  удаляет, и удаляет он только текст между целыми маркерами с совпавшим
  `body`.

Отдельным разделом идёт машинный контур: он общий для всех проектов, поэтому
находки помечены словом «машина». Проверяется то, без чего конвейер тихо
работает наполовину:

- PostToolUse-хуки Claude Code прописаны в `~/.claude/settings.json` (символы,
  индекс памяти, чувствительное), там же SessionStart-хук `quota-refresh.sh`:
  без него снимок квоты сам не освежается и корректор pick рано или поздно
  остаётся с протухшим. Недостающее дописывает `--fix` тем же порядком, что
  права: команда встаёт в группу со своим матчером либо заводит её, чужие группы
  и порядок остаются на месте, а раскладка событий и матчеров живёт таблицей
  `HOOK_LAYOUT` в `devkitctl.py`. С ветки задачи хуки на машину не едут, как и
  права: там они только сверяются;
- уведомитель `notify.py` подключён сразу на четыре события: `Notification`,
  `Stop`, `SubagentStop` и `UserPromptSubmit`. Пропажа любого проверяется
  отдельно, потому что без первого сессия не зовёт, когда ждёт разрешения, без
  `Stop` молчит про конец хода, без `SubagentStop` про отработавшего субагента,
  а без `UserPromptSubmit` не снимается отметка ожидания, и второй конец хода
  подряд глохнет в общем окне троттлинга. Тут же проверяется, чем эти уведомления слать: бэкенд
  выбирает сам `notify.py` по платформе и PATH, и когда его нет (нет
  `notify-send` на Linux, необычная платформа), доктор называет это находкой
  с командой `notify.py --self-test`. Отдельная находка на macOS, где слать
  есть чем, но клик по баннеру уводит в Finder: `osascript` постит от имени
  Script Editor, переход в окно сессии даёт `terminal-notifier`. Пакет этот
  ставит сам `--fix`, потому что человек за такой мелочью не пойдёт, а без
  перехода баннер наполовину бесполезен; когда ставить нечем, остаётся находка
  с причиной. Поломкой это не считается, уведомления и без неё доходят;
- права машинного контура в `permissions.allow` тех же настроек. Сессии,
  поднятой без человека (`claude -p`), одобрить запрос харнеса некому:
  неразрешённый инструмент отвечает отказом, а сессия идёт дальше и не делает
  ничего. Так встал первый headless-виток цели DK-109, девять отказов подряд
  вместе с правкой файлов, и в «Журнале» цели не появилось ни строки, так что
  со стороны стоп был неотличим от молчания. Перечень прав лежит в
  `tools/devkitctl/perms.py`: утилиты devkit, git, чем гоняются тесты и сборки,
  мелочь вроде `wc` и `sed`, чтение и правка файлов. `--fix` дописывает
  недостающее в конец `allow`, рукописных правил не трогая и порядка их не
  меняя; право, записанное пользователем в `deny` или `ask`, остаётся
  находкой, снимать запрет автоматике не по чину. Разрешённый целиком
  инструмент (`Bash` без скобок) перечень покрывает, чинить исправное доктор
  не зовёт. Эталон тут тот же, что у определений субагентов, основной чекаут:
  из worktree ветки задачи доктор права только сверяет, потому что видны они
  каждой сессии на машине сразу, и выписывать их себе непроверенной веткой
  цикл не должен даже случайно. Тот же перечень спрашивает оболочка цели перед
  первым витком, поэтому у него есть свой вход, дешевле полного доктора:

  ```sh
  python3 tools/devkitctl/perms.py [--fix]
  ```

- бинари devkit в PATH и на одной версии с чекаутом. Список берётся из дерева
  (`tools/*/go.mod`), поэтому новая утилита попадает под проверку тем, что она
  есть, а не правкой перечня в доке и в коде. Сверяется коммит: доктор
  спрашивает у бинаря `--version` и смотрит, есть ли в этом коммите последняя
  правка кода утилиты (`git log -1 -- tools/<имя>/*.go` и её файлы сборки).
  Свежим считается бинарь, собранный из этого коммита либо из любого более
  позднего, то есть сборка с HEAD годится всегда. По HEAD напрямую сверять
  нельзя: доска devkit лежит в том же репозитории, и коммит доски уводил бы HEAD
  вперёд, не меняя в бинаре ни байта, так что после каждого слияния доктор давал
  бы шесть находок на ровном месте, а `--fix` гонял бы сборку впустую. README
  утилиты в счёт не идёт по той же причине: из него ничего не собирается.
  Порога тут нет, отставший бинарь это находка, и бинарь, не понимающий
  `--version`, тоже: он собран до релизной схемы версий. Рядом доктор называет
  режим чекаута («на релизе v0.3.0», «на ветке main, впереди релиза v0.3.0»),
  иначе на машине разработчика отставание читалось бы как поломка. Чинит
  находку `--fix` тем, что на машине есть: чекаут стоит на теге, значит ставит
  бинари этого релиза, иначе собирает через `build`, а без тега и без go находка
  остаётся с причиной. История берётся у **основного** чекаута, поэтому параллельная
  сессия в worktree ветки задачи находок не сыплет, но и чинить их оттуда
  нельзя: машинный бинарь с непроверенной ветки уехал бы во все проекты сразу.
  Единственный остаток mtime это несохранённые правки `*.go`: коммита у них ещё
  нет, сравнивать нечего, и тут доктор смотрит на время файла;
- вышедший релиз, и это единственный канал, которым машина потребителя про него
  узнаёт: `git pull` в отвязанном чекауте не работает. Находок две. Точная
  сравнивает тег чекаута с новейшим тегом, известным клону («стоит v0.2.0,
  вышел v0.3.0»), и гаснет только от обновления. Косвенная отвечает на второй
  вопрос, давно ли вообще спрашивали: mtime `FETCH_HEAD` старше двух недель
  либо файла нет вовсе, и гасит её `devkitctl update --check`. В сеть доктор не
  ходит ни в той, ни в другой, обе считаются по локальному клону;
- определения субагентов `kit/agents/*.md` (исполнители `exec-*`, ревьюверы
  `review-*`) лежат в `~/.claude/agents/` и совпадают с devkit; без них effort
  из вердикта pick применять нечем, и спавн молча уходит на дефолтного агента.
  Определением файл считается по frontmatter с `effort:`, соседняя проза вроде
  README на машину не уезжает. Эталон, как и у бинарей, это основной чекаут: из
  worktree ветки задачи определения только сверяются, а раскладка и перекладка
  ждут слияния;
- скиллы devkit `kit/skills/*/SKILL.md` лежат в `~/.claude/skills/` и совпадают с
  devkit. Скилл это процедура, общая всем проектам (`board-batch` собирает пачку
  задач доски, `board-groom` оформляет черновики), поэтому копии в репозиториях
  не заводятся, а канал доставки взят тот же, что у определений субагентов: не
  разложенный скилл это находка, а расхождение с devkit чинит `--fix`. Скиллом
  считается директория с `SKILL.md`, соседняя проза в `kit/skills/` на машину не
  уезжает, и рубеж основного чекаута действует так же. Путь раскладки доктор
  пока держит своим, как и для определений субагентов: `dir` из `[skills]`
  профиля объявлен для глубины правил, а совпадает он с этим путём или нет,
  выяснится на профиле второго инструмента;
- глобальная точка правил (`[rules] global_file` профиля, у Claude Code
  `~/.claude/CLAUDE.md`) сгенерирована и свежа. В отличие от тонкого файла
  проекта она видна каждой сессии на машине, даже вне проектов devkit, поэтому
  тянет не тонкий текст проекта (AGENTS.md, правила доски), а свой короткий
  импорт ядра правил с парой строк прозы на случай, если он не развернулся.
  Файл без маркера `devkit:generated` (сегодняшний ручной, наполовину
  повторяющий ядро) генератор не трогает: локальные добавления руками
  переносятся в `RULES.local.md`, дальше файл заменяется сгенерированным.
  Устаревший (девкит переехал, ядро выросло) `--fix` перегенерирует так же, как
  тонкий файл проекта. Эталон, как у бинарей и определений субагентов, это
  основной чекаут: из worktree ветки задачи файл только сверяется, класть
  правила с непроверенной ветки на машину, видную каждой сессии, нельзя;
- tmux в PATH, иначе `agentctl quota refresh` не снимет панель `/usage`. Его,
  как и `terminal-notifier`, ставит `--fix` тем менеджером, который на машине
  уже есть (`brew`); чужого менеджера devkit не подставляет, и без своего
  остаётся находка, которая называет причину. Причин этих три, и говорит доктор
  ту, что случилась: менеджера нет вовсе, менеджер ответил ошибкой (его ответ
  идёт в находку последней строкой) и менеджер отработал нулём, а пакет в PATH
  так и не появился, то есть сломан он сам;
- снимки квоты в `~/.devkit/quota/` есть и не протухли: порог 45 минут, тот же,
  по которому судит сам корректор, а на протухшем снимке pick теряет сдвиг
  вверх. Проверяется каждый файл директории, а не один: снимок теперь свой на
  харнес. Одиночный `~/.devkit/quota.local`, каким снимок был раньше, это
  находка про переезд: читатель его ещё понимает, но чинит расхождение `--fix`,
  а не пользователь. Лежат оба сразу, значит читается новый, а про старый
  доктор говорит и удалять его сам не берётся. Снимка нет вовсе, а хук
  `SessionStart` подключён и tmux на месте: находки тут не будет, потому что
  снимок появится сам при первой же сессии, и звать за ним человека значило бы
  выдумать ему работу. Находка возвращается, когда снять снимок нечем: хук не
  подключён либо tmux на машине нет, и причина эта названа в ней прямо;
- профили харнесов `devkit/kit/harness/*.toml` разбираются и проходят валидацию.
  Проверяются все, а не только активный: битый профиль находится до того, как
  кто-то на него переключится. Чинится это правкой в devkit, поэтому находка
  остаётся находкой и под `--fix`.

Валидатор профилей живёт в `tools/devkitctl/harness.py` вместе с парсером
подмножества TOML. Парсер этот второй: тот же формат читает agentctl своим
кодом на Go (`tomllib` появился в python3.11, а devkitctl обещает голый
python3, тащить же в Go-утилиту первую внешнюю зависимость ради конфига из
строк и массивов не хочется). Расхождение двух реализаций ловится общими
фикстурами `kit/harness/testdata`: на каждый вход там лежит ожидаемый отчёт, и
сверяются с ним обе стороны. Отчёт по любому файлу печатается и руками, это
удобная точка для глаза:

```sh
python3 tools/devkitctl/harness.py kit/harness/claude-code.toml
```

`doctor --fix` доводит обвязку уже подключённого проекта и машины до актуальной:
после `git pull` devkit это способ забрать новые её части одной командой, без
ручного заведения файлов. Большинство правок additive: подключает отвязанные
git-хуки, заводит болванку `.devkit/deploy.local` и строку в `.gitignore`. Если
`deploy.local` уже есть, но заводился до появления очередного ключа (так
`test` не доехал до проектов, подключённых раньше DK-053), `--fix` дописывает
недостающие ключи в конец файла вместе с их комментарием: значения имеющихся
ключей, шапка и их порядок не трогаются, а дописанный ключ остаётся пустым,
поэтому находка про него никуда не девается и по-прежнему просит вписать
команду. Дальше он доводит бинари до версии чекаута тем, что на машине есть:
чекаут на релизном теге, значит ставит бинари этого релиза, иначе собирает тем
же `build` (в тот же каталог назначения, куда ставит `update`), кладёт рядом с ними обёртку
`devkitctl`, кладёт определения субагентов в `~/.claude/agents/` и скиллы в
`~/.claude/skills/`, дописывает недостающие права машинного контура в
`permissions.allow`. Определение или скилл,
разошедшийся с эталоном (устарел после правки в devkit либо кто-то поправил его
прямо на машине), `--fix` перекладывает: devkit источник правды, и правка
обязана доехать до спавна субагента сама, а не остаться находкой, которую надо
чинить руками на каждой машине. Перекладка не молчаливая, отчёт называет файл и что он разошёлся, так
что подправленное на машине видно в выводе, даже если его тут же перезаписали.
Той же меркой правится и глобальная точка правил, только генерится она заново
целиком, а не перекладывается копией файла: пропавшая заводится, устаревшая
перезаписывается, а руками правленная (нет маркера либо тело разошлось с его
хешем) остаётся находкой, как и рукописный `AGENTS.md`. Тем же порядком он
генерит и обновляет файлы правил проекта (раздел «Файлы правил»).
Заполненное иначе `--fix` не трогает (готовый `deploy=`, рукописный `AGENTS.md`
и правленый руками генерённый файл), а неоднозначное оставляет находкой: битый
импорт и ссылку правит человек, пустые `deploy=` и `test=` ждут команд проекта,
а Go ставится пакетным менеджером с ведома человека: тулчейн это не мелочь
вроде tmux, и тянуть его молча `--fix` не берётся. Неadditive правок
две, и обе называют себя в отчёте. Первая это переезд
снимка квоты: одиночный `~/.devkit/quota.local` `--fix` перекладывает в
`~/.devkit/quota/claude-code.local` (снять его было нечем, кроме панели Claude
Code), и в отчёте называет оба пути. Файл при этом не пропадает, а меняет место;
если по новому пути снимок уже лежит, старый остаётся нетронутым и попадает в
находки. Вторая это удаление вклейки правил, когда последний embed-инструмент
выключен, и удаляется только целый блок с совпавшим `body`. Собранный бинарь
может проиграть в PATH чужой копии, и это тоже находка, а не молчаливая
пересборка на каждом прогоне. Повторный прогон уже ничего не меняет.

`stats` собирает статистику по журналу запусков `.devkit/log`: выводит таблицу
с частотой каждой команды (утилита + субкоманда), долей ошибочных запусков
(код выхода != 0) и итоговой строкой. Битые строки в журнале молча пропускаются.
Разбивку объёма сессий печатает та же команда с `--context`, раздел ниже.

## Куда ушёл объём сессии

У `stats` второй источник данных, журналы сессий харнеса
(`~/.claude/projects/<слепок пути проекта>/*.jsonl`). Журнал запусков знает
только, какие команды звали; расход контекста лежит в `message.usage` записей
ассистента, и разбирает его `stats --context`.

```sh
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py stats --context -C ~/projects/myproj
```

Печатается разбивка: старт (префикс первого запроса каждого потока) против
истории (всё, что дописалось дальше: переписка, результаты тулов, тела скиллов),
рядом повторное чтение префикса, дальше перезаписи префикса с их ценой и топ
тулов по объёму результатов. Объём тулов считается в символах, а не в токенах:
это код и вывод команд, а коэффициент 2,45 снят с русской прозы правил и на них
соврал бы.

Считается по потокам, а не по сессиям: журнал одной сессии бьётся на несколько
файлов (рядом с `<id>.jsonl` лежит `<id>/subagents/` с потоками субагентов), и у
каждого потока свой префикс. Запись с `usage` повторяется по числу итераций
ответа, поэтому запросы склеиваются по `requestId`; без склейки объём вырос бы в
разы. Сессия может идти на нескольких моделях, они перечисляются шапкой с числом
запросов на каждую.

Правило подписи перезаписи. Штатное дописывание в хвост оставляет прочитанный
префикс на месте: чтение кеша от запроса к запросу растёт, а запись держится на
объёме прироста. Перезаписью считается запрос, у которого сошлись оба признака:
чтение кеша просело относительно предыдущего запроса того же потока и записано
больше, чем прочитано (`cache_creation > cache_read`). Порога в токенах тут нет
намеренно, оба признака относительные, и правило не надо перенастраивать под
длину сессии или модель. Первый запрос потока это старт, он пишет префикс с нуля
и идёт отдельной строкой, а не нарушением.

Число перезаписей это сторож запрета из [дизайна дерева
контекста](../../docs/lld/DK-100-context-tree.md): механизма, который правит голову
контекста по ходу, devkit себе не заводит, и всплеск перезаписей после правки
devkit виден цифрой, а не догадкой. Часть перезаписей приходит не от devkit, а
от истечения TTL кеша на паузе в работе, поэтому смотрят на сдвиг числа между
периодами, а не на нулевой итог.

## Вес резидента

Резидент это текст, который едет в каждый запрос сессии: цепочка файлов правил,
описания определений `kit/agents/` и скиллов. Растёт он монотонно, и заметить это
можно только специально, поэтому вес меряется двумя способами сразу. Расчёт
считает символы по карманам и переводит их в токены коэффициентом 2,45 из
[дизайна дерева контекста](../../docs/lld/DK-100-context-tree.md); он бесплатный, и
его порогом дальше живёт `doctor` (DK-029). Замер спрашивает цену у самого
харнеса и говорит, чему в расчёте верить.

```sh
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py weigh -C ~/projects/myproj
```

`weigh` гоняет два headless-прогона `claude -p` с одинаковым тривиальным
запросом и `--output-format json`. Полный вход прогона это `input_tokens` плюс
запись и чтение кеша (резидент лежит в кешируемом префиксе, и одного
`input_tokens` мало). Базовый прогон идёт без раскладки devkit, целевой с ней, а
разница это цена текста devkit в токенах.

Пол замера (системный промпт харнеса и схемы тулов) зависит от машины:
подключённые MCP-серверы приносят свои схемы. Прогон под пустым `HOME` мерил бы
не ту машину, поэтому оба прогона идут под слепком `~/.claude` во временной
директории, и отличается он ровно раскладкой devkit: глобальной точкой правил,
определениями агентов и скиллами. В слепок не едут транскрипты сессий, история и
прочее тяжёлое, чего в запросе нет; хуки из `settings.json` снимаются, чтобы
замер под подменённым `HOME` ничего на машине не трогал. Целевой прогон идёт не
в самом чекауте, а в директории замера с той же раскладкой правил (`AGENTS.md`
проекта, файлы правил и тонкий файл харнеса): чекаут принёс бы в контекст ещё и
git-статус с листингом файлов, которых у базового прогона нет, и разница вобрала
бы их. Файлы правил кладутся рядом с тонким файлом, и зовёт он их голым именем:
импорт за пределы рабочей директории клиент не разворачивает и молчит об этом,
так что правила до прогона просто не доезжают, а замер выходит занижен ровно на
их вес. Отличие от боевого тонкого файла остаётся только в длине строки импорта
(`@RULES.md` против `@../devkit/RULES.md` у проекта с соседним devkit).

Авторизация клиента в слепок не копируется, но и не теряется. На macOS она
лежит в связке ключей, а ищет её клиент от `HOME` (`~/Library/Keychains`), и
слепок без этого каталога встречает прогон ответом «Not logged in». Каталог
кладётся симлинком на настоящий. На платформах, где такого каталога нет, слепок
остаётся прежним.

Симлинк это единственное место, где слепок смотрит на живой файл машины, и риск
названный: освежая истекающий токен, клиент запишет его в настоящую связку, а не
в одноразовую копию. Копия связки в слепке работает (в той же login-сессии она
открывается и вход из неё читается), но берётся симлинк. Копия положила бы на
диск второй экземпляр всех секретов пользователя, а не только входа в Claude, и
освежённый токен из неё уехал бы в мусор вместе с временной директорией, тогда
как через симлинк освежение доезжает туда же, куда доезжает от обычного запуска
`claude`. Записать на машину замер может ровно это и ровно руками клиента;
раскладку devkit и хуки он не трогает.

Вход гуляет от прогона к прогону, поэтому пар прогонов несколько (`--runs`, по
умолчанию три), а рядом с замером печатается разброс. Точнее разброса замер не
знает, и читать его точнее нельзя. Печатается пара за парой, потом сам замер,
таблица карманов в символах и токенах, коэффициент этого прогона и расхождение
расчёта с замером. Расхождение в проценты это нормально: два способа дизайна
разошлись на 2,5%.

Код возврата 1, когда замер выше потолка резидента (`--limit`, по умолчанию 6 500
токенов из бюджета дизайна), и тогда замер годится шагом сценария проверки, а не
только для чтения глазами. Отдельный код 2 у отказа мерить, и поводов у него
два. Первый это несвежая раскладка на машине: кладёт её `doctor --fix`, а выкат
devkit пересобирает только бинари утилит, так что по вчерашней раскладке замер
соврал бы молча. Перед прогонами `weigh` гоняет те проверки доктора, которые за
раскладку и отвечают (определения агентов, скиллы, файлы правил проекта), и при
находках печатает их и не меряет. Остальной машинный контур (снимок квоты,
tmux) на вес резидента не влияет и мерить не мешает. Второй повод это сорванный
прогон: нет `claude` в PATH, клиент вышел с ошибкой, в ответе нет `usage`.

Команда отдельная, а не флаг `doctor`, потому что прогон стоит денег, требует
`claude` в PATH и сети и занимает минуты, а доктора гоняют в каждой сессии.
Расчёт по карманам живёт функцией `weigh.pockets` отдельно от прогонов: порог
резидента в докторе считается ею же, чтобы обе цифры брались из одного места.
Самопроверка живого клиента не поднимает, вместо него в PATH ложится скрипт,
который отдаёт usage по той раскладке, какую видит.

### Порог в doctor

`doctor` печатает ту же таблицу карманов без единого запроса к сети: расчёт по
символам бесплатный, и в каждой сессии его можно себе позволить. Порогов три,
из бюджета дизайна DK-100, а не из сегодняшнего веса: ядро (`RULES.core.md`)
не длиннее 5 500 символов, ядро доски (`RULES.board.core.md`) не длиннее
1 500, а сумма по всем карманам не выше 6 500 токенов (коэффициент тот же,
2,45 символа на токен). Превышение любого из трёх это отдельная находка,
которая называет карман, его вес в символах и в токенах, порог и разбивку по
всем карманам целиком, чтобы сразу было видно, что именно распухло.

Второй порог на тело каждого скилла в `kit/skills/*/SKILL.md`: тело не резидентно,
но платится записью в контекст в момент вызова, и разбухший скилл это та же
болезнь роста в другом месте. Порог 16 000 символов текста без шапки
frontmatter; превышение это находка с предложением резать скилл надвое.
Меряется тело той же меркой, что и резидент: 16 000 символов это потолок
резидента (6 500 токенов по 2,45 символа, 15 925) с округлением вверх до сотен.
Смысл равенства такой: один вызов скилла стоит сессии не дороже, чем весь
резидент devkit, который она платит безусловно и до всякой работы. Выше этой
черты тело перестаёт быть процедурой и становится второй раскладкой правил, а
вызов уже не дешевле чтения полного текста, ради которого скиллы и заводились
(`RULES.board.md` это 18 тысяч символов). От сегодняшних тел порог не считается
вовсе: DK-029 брала запас в треть над самым толстым скиллом, и такая мерка
объясняет только то, что уже написано.

Оба порога проверяются только в самом чекауте devkit (`root` совпадает с
`DEVKIT`), не в каждом подключённом проекте: карманы резидента и тела скиллов
общие для всех проектов devkit, находка про них не проектная, и в
подключённом проекте её некому чинить. Логика находок (`weigh.evaluate_residency`,
`weigh.evaluate_skill_body`) отделена от чтения дисков (`weigh.pockets`,
`weigh.skill_body_chars`), поэтому пороги проверяются юнитами без файловой
системы, а стык с диском и с `doctor` отдельными интеграционными тестами
(`tools/devkitctl/weigh_test.py`).

## Самопроверка

Тесты лежат рядом с кодом, каждый модуль своим `<модуль>_test.py`; общий
стенд (копия devkit во временной директории, подставные HOME и PATH) в
`testenv.py`.

```sh
cd tools/devkitctl && python3 -m unittest discover -p '*_test.py'
```

Стенд держит два рубежа, и оба про то, чтобы прогон не зависел от машины, на
которой запущен.

Настоящий HOME тестам не виден: `testenv` подменяет его пустой директорией на
весь процесс. Инструмент читает раскладку машины через `expanduser`, и тест,
забывший подставить свой HOME (`home=` у `run`, `fake_home` у вызова модуля
прямо в процессе), мерил бы `~/.claude` того, кто запустил прогон: у одного
зелено, у другого красно, и увидеть это можно только у второго. С пустым HOME
такой тест краснеет сразу и у всех. Единственное, за чем стенд ходит в
настоящий HOME, это пути кеша сборки go (`go_cache_env`), иначе сборка бинарей
для прогона `shipctl start` каждый раз компилировала бы стандартную библиотеку
заново.

Копия devkit заводится одна на класс (заводить её на каждый тест дорого), и
за то, что тест вернул её в исходное состояние, отвечает не обещание в
комментарии: `SandboxCase` сверяет слепок копии по содержимому до и после
каждого теста. Невосстановленная правка называется на том тесте, который её
оставил, а не всплывает через полчаса в соседнем. Класс, где шаги нарочно
стоят друг на друге (цепочка вклейки правил), объявляет это полем
`CHAIN = True` и за состояние отвечает сам; дальше класса оно всё равно не
течёт, копия у каждого класса своя.
