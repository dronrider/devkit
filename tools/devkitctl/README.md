# devkitctl: обвязка проекта

Подключение devkit к проекту размазано по ручным шагам (шаблон `AGENTS.md`,
файлы правил под каждый инструмент, `taskctl init`,
`git config core.hooksPath`), а сломанную обвязку раньше никто не
диагностировал. Утилита сводит это к двум командам; агент в
свежей сессии гоняет `doctor` и чинит по находкам, вместо чтения инструкций
по подключению. Нужен только python3, запуск прямо из devkit:

```
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py <команда>
```

Длинный путь нужен только первой установке: `update` и `doctor --fix` кладут
рядом с бинарями обёртку, и дальше утилита зовётся по имени, `devkitctl
<команда>`.

## Команды

```
new --prefix XX [--name "..."] [--no-board] [-C dir]
corp [--prefix XX] [--name "..."] [--contour имя] [--key ABC] [--branch tpl]
     [--remote адрес] [--local dir] [-C dir]
doctor [--fix] [--layout] [-C dir]
map [-C dir] [--write]
update [--pin] [--check]
catchup [--hook]
build [--release] [--out dir]
stats [--context] [-C dir]
watch [--idle минуты]
weigh [--runs N] [--limit T] [--model M] [--prompt "..."] [-C dir]
drain [-C dir] [--all]
user [--gender мужской|женский]
selfcheck
```

Порядок подключения целиком, оба сценария подряд, лежит в
[CONNECT.md](../../CONNECT.md); здесь разбор самих команд.

`new` подключает проект и доводит его до рабочего состояния сам: директории нет
значит заводит её, каталог не под git значит делает `git init` (без него
`core.hooksPath` вешать некуда, а `shipctl start` падает на первом же шаге). У
репозитория без единого коммита он оставляет свой, пустой: HEAD там
неродившийся, ветку задачи от него `shipctl start` не заводит, и спрашивается
поэтому HEAD, а не то, кто завёл репозиторий (пустым он бывает и заведённым
заранее руками). Не прошёл коммит (git не знает автора) значит шаг уезжает в
список «осталось сделать», а не теряется.
Дальше он копирует шаблон `kit/templates/AGENTS.project.md` в
корень как `AGENTS.md` (плейсхолдеры заполняются), выставляет `core.hooksPath`
на хуки devkit (если у проекта уже есть свои хуки, не трогает их и
подсказывает симлинки), заводит доску через `taskctl init` и болванку
`.devkit/deploy.local` для shipctl (гитигнорит её, `deploy` и `test` пустые,
`autonomous = false`), а последним шагом генерит файлы правил под включённые
харнесы: доска к этому моменту уже есть, и ссылка на правила доски в них
попадает. Для проекта с внешним трекером `--no-board`: доска и обвязка выката
не создаются, трекер вписывается в `AGENTS.md` руками.

`corp` подключает проект корп-контура, где рабочим файлам devkit в дереве не
место. Доска, файлы задач и `.devkit` уезжают в боковую директорию, а в клоне
остаётся обвязка. Директория эта общая на контур, `../<контур>-local`, и проекты
лежат в ней подкаталогами со своим `.devkit` каждый. Репозиторий на неё один,
сколько бы проектов контура в ней ни лежало. Умолчание переопределяется флагом
`--local <путь>`. Клон, подключённый прежней раскладкой, остаётся при своей
`../<проект>-local`, редирект называет её явно, и повторный прогон её не двигает.

Команда заводит эту директорию со скелетом доски (`taskctl init`, `docs/tasks/`,
болванка `.devkit/deploy.local`), вписывает в её привязку `.devkit/tracker.local`
ключ `repo` с путём клона, ставит в клоне редирект `git config devkit.local
../<контур>-local/<проект>` (по нему утилиты devkit находят корень, и он же
машинный признак контура), кладёт в дерево клона ссылку `.devkit` на боковую
директорию, генерит в корне клона тонкий файл контекста харнеса с импортами
через неё (`@.devkit/AGENTS.md` и правила devkit через собственный каталог
обвязки боковой директории, `@.devkit/.devkit/devkit/...`), прячет тонкий файл
строкой в `.git/info/exclude` и разворачивает обёртки хуков на `pre-commit` и
`commit-msg` (цепочка из `hooks/corp.py`: сперва проверки devkit, следом чужой
хук проекта, переехавший в `<хук>.chained`). Оба хука обязательны: дифф смотрит
`pre-commit`, сообщение коммита `commit-msg`, и клон с одной обёрткой пропускал
бы локальный ID молча.

Ссылка `.devkit` и тонкий файл контекста это всё, что лежит в дереве клона
негитигнорнутым. Харнес читает файл только из корня проекта, а импорт наружу не
разворачивает, и оба конца этой пары обязаны быть тут. Ссылка вдобавок открывает
корп-проект одним окном редактора. Доска лежит по пути `.devkit/docs/TASKS.md`,
и её видят поиск, панель git и сессия агента без `--add-dir`. Строкой exclude
ссылка нарочно не прячется. Ripgrep и git читают одни источники игнора, и
спрятанное от git пропадает заодно из поиска редактора (DK-583).
Ценой этого в чужом `git status` висит строка `?? .devkit`. В индекс она не
уедет. Обёртка `pre-commit` отбивает коммит, в чей индекс попала ссылка или
тонкий файл, и называет `git rm --cached`. В чужую историю не едет ни то, ни
другое. Рабочим файлам devkit в корп-репозитории не место, и кладёт их
автоматика (`corp` при подключении, `doctor --fix` при потере).

Привязка к трекеру заводится тем же прогоном: `--contour` называет контур
компании, `--key` ключ проекта в трекере, `--branch` шаблон ветки, и все три
ложатся в `.devkit/tracker.local` рядом с `repo`. Названного контура на машине
нет, значит `~/.devkit/tracker/<имя>.local` заводится с заполненной таблицей
`[status]`: сверить её с трекером дешевле, чем писать с нуля. `--remote`
добавляет боковой директории origin, тот самый личный приватный remote, без
которого обрыв машины теряет доску.

Недостающее первый прогон спрашивает сам, а не оставляет человеку с редактором
(DK-240). Перед вопросами он говорит, куда лягут доска и файлы задач: команду
зовут из клона, а рабочие файлы ложатся сбоку, и знать это стоит до, а не после.
Прогон без вопросов говорит это же, но только когда и правда заводит доску:
отказавший первый прогон про директорию, которой не завёл, молчит.
Спрашивается префикс доски, с предложением по имени клона (инициалы слов, а у
имени в одно слово две первые буквы; пустой ответ значит согласие), и для нового
контура компании адрес трекера с именем пользователя. Секретов среди вопросов
нет: токен в файлы не пишется вовсе и приезжает переменной окружения из
`token_env`. Про боковую директорию вопроса нет, её место выводится однозначно
(`../<контур>-local/<проект>`, а без имени контура прежняя `../<проект>-local`),
и на соседстве держатся восстановление после переклонирования и относительный
редирект.

Префикс доски, совпавший с ключом проекта в трекере, `corp` не пропускает:
названный в вопросе спрашивается заново (префикс ещё выбирается, и отказывать
незачем), названный флагом на незаведённой доске это отказ с кодом 2, а на
заведённой предупреждение, потому что рубеж следов на такой паре не отличает
локальный ID от ключа тикета и правило про ID снимает (DK-124).

Вопросы задаются только живому человеку, признак тому tty на вводе и выводе.
Под сессией агента, в CI и в пайпе команда идёт как раньше: контур ложится
болванкой, недоделанное едет в хвост «осталось сделать», а первый прогон без
`--prefix` отказывает с кодом 2, а не ждёт ответа, которого некому дать.

Обе команды подключения заканчивают списком «осталось сделать»: что человеку
дописать, с путями файлов и именами ключей, и чем это проверяется. Пустой список
печатается тоже, отдельной строкой: молчание команды и «шагов не осталось»
снаружи выглядят одинаково, а значат разное. В корп-контуре команду выката
список не спрашивает, там её ведёт процесс компании.

Прогон повторяемый: заведённая боковая директория не трогается, доводится
только обвязка клона. Поэтому та же команда и восстанавливает обвязку после
переклонирования или `git clean -xdf`, которые сносят её молча (живёт она в
`.git` и в негитигнорнутом дереве), и подсказка утилит про потерянный корень
зовёт именно её.

`doctor` проверяет обвязку существующего проекта и выходит с 1 при находках. Корень
не под git (например, позван из каталога, где просто лежат проекты рядом) это
находка, а не отказ: без репозитория нет ни проекта, ни обвязки, и проектная
половина проверки (файлы правил, git-хуки, доска, обвязка выката,
markdown-ссылки, ниже списком) по дереву вниз не идёт, иначе там лежат чужие
репозитории, и обход их доктором был бы шумом их находками, а не диагностикой
(DK-160). Машинный контур (раздел ниже) и строка про режим чекаута от корня не
зависят и печатаются как обычно: человек, позвавший доктора из каталога
проектов, часто спрашивает ровно про машину. Список для случая, когда корень
свой:

- файлы правил в порядке (раздел ниже);
- ссылка на дерево devkit на месте: `.devkit/devkit` есть, ведёт в дерево
  правил и не занята чужим файлом. Спрашивается только у того, кто через неё и
  правда зовёт импорт: проекту без доски на глубине ядра ссылка не нужна;
- git-хуки devkit подключены (`core.hooksPath` либо симлинки);
- при наличии доски `taskctl lint` проходит;
- при наличии доски вход, названный в файле задачи фразой «как вход» или
  «вход этой задачи», стоит маркером «после» хотя бы у одной из двух строк
  (DK-168): связь, оставшаяся фразой в тексте, диспетчером не читается, и
  задача уходит в работу раньше предпосылки. Цитата в «ёлочках» называнием
  не считается, закрытая задача тоже: вход из архива диспетчеру уже не
  мешает;
- при наличии доски есть `.devkit/deploy.local` с непустыми командами выката и
  тестов и он гитигнорнут (иначе адрес из команды утечёт в git). В корп-контуре
  пустой `deploy =` это норма: слияние и выкат там ведёт процесс компании, и
  shipctl отказывает честной строкой. Пустой `test =`
  это отдельная находка: без ключа `shipctl merge` требует `--test` на каждый
  вызов, а процедуре пачки сочинять его под проект нечем;
- рядом с го-проектом лежит чужой `go.work`, в котором он не перечислен, а
  го-команды в `test =`/`deploy =` не обёрнуты `GOWORK=off` (DK-115): го
  отвечает «directory prefix . does not contain modules listed in go.work», и
  `shipctl merge` видит красные тесты после ребейза на ровном месте. Находка
  молчит, когда проекта в `go.work` нет в принципе (нет ни одного `go.work` по
  дереву вверх), когда проект вписан в чужой `go.work`, когда `go.mod`
  отсутствует (не го-проект), когда го-команды зовёт внутренность обёртки
  (сборка devkit прячется за `python3 ... build`, GOWORK=off ставит сама), либо
  когда команды уже обёрнуты.
- журнал запусков `.devkit/log` (его пишут taskctl, shipctl, regcheck и сам
  devkitctl) гитигнорнут, иначе замусорит status;
- машинные записи `.devkit/cmdout/` (полные выводы команд под обёрткой cmdout,
  DK-264), `.devkit/ship.lock` (замок конвейера shipctl), `.devkit/goal-*`
  (рабочее состояние цикла цели: журнал витков `goal-<ID>.log`, отметки доставки
  `goal-<ID>.mail` и замки рядом с ними) и `.devkit/chat/` (лежащие реплики
  человека живой сессии, DK-345) гитигнорнуты, иначе тоже замусорят
  status. Проверка идёт в блоке `in_git`, а не в блоке доски: cmdout и shipctl
  работают и в проекте без доски, а цель ведут не все. Каталога `.devkit/cmdout`
  на диске в момент проверки может ещё не быть, поэтому путь сверяется со
  слэшом на конце, иначе `git check-ignore` по отсутствующему каталогу не
  подтверждает ответ. Те же записи раскладывают подключение нового проекта
  (`new`) и `doctor --fix`;
- локальные markdown-ссылки живой доки ведут на существующие файлы (обобщение
  проверки, которую lint делает для доски). Внутрь блоков кода проверка не
  заглядывает, как и в инлайн-код: ссылка в примере команды это текст, а не
  ссылка. `docs/` не проверяется вовсе: файл задачи описывает состояние на
  момент решения и после закрытия не правится, так что ссылка на уехавший путь
  там законна, и находка по ней звала бы чинить то, что чинить запрещено.
  Исключение считается от корня репозитория, которому принадлежит файл, а не
  от каталога запуска: `docs/` вложенного репозитория, встреченного при обходе
  дерева, исключается тем же правилом (DK-160);
- у каждого компонента сборки есть описание (DK-071). Компоненты читаются из
  манифеста в корне (`Cargo.toml` workspace, `go.work`, `settings.gradle`),
  а без него это каталоги верхнего уровня с кодом. Описан компонент, если про
  него есть заголовок в карте архитектуры (`docs/ARCHITECTURE.md`),
  `README.md` рядом с кодом либо модульная дока в корневом файле
  (`//!` у main.rs/lib.rs, `// Package` у doc.go, docstring у `__init__.py`);
  достаточно любого из трёх, стиль доки проект выбирает сам. Заголовок без
  ссылки закрывает только члена верхнего уровня, у которого имя и есть
  путь; члену из вложенного каталога (`crates/hub`) нужно имя со ссылкой.
  Таблица состава описанием не считается: в ней названы все подряд, включая
  те, у кого раздела нет. Генерённое и вендоренное вычёркивается строкой в
  `.devkit/describe.ignore` («имя: причина»), файл коммитится рядом с
  deploy.local. Проверка смотрит на всё дерево сразу, а не на дифф ветки:
  компонент, проехавший мимо доки при рождении, не описывается уже никогда,
  потому что последующие правки в нём мелкие и порога «заметное поведение»
  не берут, и накопленный до правила долг находится тем же прогоном, что и
  свежий пропуск;
- у README утилиты первым разделом идёт вход, а не устройство (DK-421). Дока
  утилиты это `README.md` в каталоге, где рядом лежит код; корень репозитория,
  каталоги без кода и стенды (`testdata`) сюда не считаются. Первый заголовок
  `##` сверяется с коротким списком имён входа («Первый запуск», «Запуск»,
  «Команды», «Установка», сверка по началу заголовка, так что «Команда names»
  проходит), заголовок внутри забора кода за раздел не берётся, а README без
  разделов вовсе молчит: короткая дока библиотеки перевёрнутым порядком не
  считается. Находка эта грамматическая, как первая строка README: сторож
  видит порядок разделов и не видит вида текста, поэтому понятность новичку
  ловится не тут, а ревью и приёмкой (барьер «глаза» из `ACCEPTANCE.md`).
  `--fix` её не чинит, вход пишется руками; само правило про вход, примеры и
  порядок разделов лежит в `RULES.md`, раздел «Документация изменений»;
- в корп-контуре обычные проверки идут по боковой директории (доска, файлы
  правил, обвязка выката лежат там), а сверх них идут корп-: файл обвязки в
  корп-индексе, пропавшая строка `.git/info/exclude` на тонкий файл и, наоборот,
  оставшаяся там строка `.devkit` (она прячет доску от поиска редактора),
  пропавшая, уехавшая или занятая чужим каталогом ссылка `.devkit` на боковую
  директорию, потерянная или
  перезаписанная чужим инсталлером обёртка на любом из двух хуков (пропал
  маркер `devkit-corp-chain`), отсутствующий ключ `repo` в привязке,
  отсутствующий remote боковой директории, префикс доски, совпавший с ключом
  проекта в трекере (на такой паре рубеж следов не отличает локальный ID от
  ключа тикета и правило про ID снимает, `hooks/README.md`), и свежесть
  последнего sync по отметке `.devkit/tracker.sync` (её спрашивают только у
  привязанного к трекеру проекта). Всё, кроме remote и префикса, доводит `--fix`; потерянный редирект `--fix` не
  чинит, там нужна вся раскладка целиком, и находка зовёт `devkitctl corp`.
  Доктор, прогнанный в боковой директории, идёт по ключу `repo` привязки и
  проверяет обвязку названного клона: так потеря находится и тогда, когда сам
  клон про devkit уже ничего не знает;
- вес резидента по карманам печатается и считается всегда, а судятся карманы по
  тому, чей это чекаут (раздел «Вес резидента» ниже). В самом devkit (`root`
  совпадает с `DEVKIT`) под порогом ядро, ядро доски, общий итог и тело каждого
  скилла: это карманы devkit, общие для всех проектов, и подключённому проекту
  их чинить нечем, поэтому там они молчат (DK-029). В подключённом проекте под
  порогом его проектная часть, `AGENTS.md` со своим тонким файлом (DK-190);
- импорты файла правил проекта доезжают до контекста и зовут ядро, а не полный
  текст (раздел «Куда доезжают импорты правил» ниже, DK-190);
- карта проекта (`docs/map.md`) существует и свежа: нет файла при живых компонентах,
  хеш разошёлся с телом, тело разошлось с деревом (новый компонент, изменившаяся
  первая строка README, новый заголовок «Решение N» в docs/lld). Все три находки
  чинятся `doctor --fix` перегенерацией. Карта генерируется статическим разбором
  дерева без тулчейна (манифесты Cargo.toml members, go.work use, settings.gradle
  include, fallback по каталогам с кодом), описания берутся из тех же источников,
  что сторож полноты доки (модульная дока корневого файла, первая строка README с
  срезом заголовка, строка состава из ARCHITECTURE.md). Компонент без описания в
  карту не едет. Вторым разделом идёт индекс решений: заголовки «Решение N» из
  `docs/lld/*.md` (строки «DK-XXX.N текст», сортировка по документу и номеру,
  архив задач не индексируется). Карта доставляется в контекст импортом
  `@docs/map.md` из тонкого файла харнеса, когда файл существует. Детали в
  `docs/lld/DK-194-project-map.md`;
- карта переходов работы (`docs/workflow.md`) полна: каждый скилл
  `kit/skills/*`, каждый статус доски и все пять рубежей F из `taskctl
  progress` на ней упомянуты (DK-400, решение 8). Источники те же, что и у
  самой доски: скиллы это каталоги, статусы это таблица секций
  `tools/taskctl/board.go`, рубежи это константы `tools/taskctl/progress.go`,
  поэтому правка taskctl доезжает до карты тем же прогоном. Карта пишется
  руками, `--fix` её не генерит: находка зовёт дописать переход, а источник,
  который перестал разбираться, становится отдельной находкой: молчание
  сторожа неотличимо от его согласия. Проверяется только чекаут самого devkit,
  по тому же признаку, что раскладка: в подключённом проекте ни карты, ни
  скиллов нет;
- в чекауте devkit раскладка по правилу (раздел «Раскладка» README devkit,
  разбор в `docs/lld/DK-139-repo-layout.md`): запись верхнего уровня вне белого
  списка, код инструмента мимо `tools/<имя>/`, инструмент на двух языках, sh не
  обёрткой и sh, переросший обёртку. Находка называет файл и правило, а не
  только факт. Признак devkit тот же, по которому чекаут находит стенд
  послушания (`RULES.core.md` и `hooks/` в корне): в чужом проекте раскладка
  своя, и правило туда не едет.

На релизном чекауте самого devkit (`root` совпадает с `DEVKIT`, HEAD отвязан
на теге `v*`, тот же признак, по которому строка режима чекаута ниже говорит
«на релизе») из списка выше молчат вовсе: git-хуки, `taskctl lint` вместе со
всей обвязкой выката (`.devkit/deploy.local`, его гитигнор, журнал запусков) и
проверкой названных входов, и порог веса резидента с телом скиллов. Все три
адресованы тому, кто в devkit
коммитит, сливает задачи через `shipctl` или пишет скиллы и правила, а машина
потребителя, поставившая devkit по `CONNECT.md`, ничего из этого не делает: её
чекаут детач на теге, коммитов там не бывает вовсе (DK-163). Файлы правил
(проверка вклейки в `AGENTS.md`) и markdown-ссылки в этот список не входят и
считаются всегда: они разбирают содержимое самого чекаута, на исправном
релизе молчат сами, а находка по ним значит дефект самого выпуска, который
стоит увидеть и потребителю. На ветке (машина разработчика) состав проверок не
меняется, и подключённого через `-C` проекта эта поправка не касается вовсе:
его обвязка проверяется в прежнем составе независимо от режима чекаута devkit.

Раскладку зовут и отдельно, без машинной обвязки:

```sh
python3 tools/devkitctl/devkitctl.py doctor --layout
```

Печатает только находки раскладки и выходит с 1 при них. Отдельная форма нужна
CI: полный `doctor` смотрит на `~/.claude`, собранные бинари, tmux и снимок
квоты, и на голой машине сборщика дал бы десяток находок про ненастроенное
окружение, а не про дерево. Ходит проверка по `git ls-files`, а не по диску,
иначе `__pycache__`, собранные бинари и рабочие файлы worktree краснели бы на
чистом репозитории каждый день. Sh она узнаёт по расширению и по shebang: три
точки входа git расширения не имеют. Не смотрит вовсе на `docs/tasks/`,
`testdata/` любой утилиты и `kit/harness/snap/`: там код под чужой контракт или
под один прогон. Смысловое (оправдан ли go новому инструменту, верна ли группа
внутри `kit/`) остаётся на ревью, машина ловит форму.

Место оболочки скилла проверка понимает буквально: `kit/skills/<имя>/` рядом со
своим `SKILL.md`, а не «где-нибудь под `kit/skills/`». Широкий префикс пускал бы
и файл прямо в каталог скиллов, и файл подкаталогом глубже оболочки, и таких
мест правило не заводило. Самопроверка скиллов `check-skills.py` с её тестом
названа в проверке поимённо (`SKILLS_SELFCHECK`): она и правда лежит в самом
`kit/skills/`, потому что проверяет каталог рядом с собой, но список закрытый, и
соседний python исключением не становится.

Белый список верхнего уровня стоит в `layout.py` и тем же составом в разделе
«Раскладка» README devkit, а сверяет их сторож (`layout_test.py`): правило,
которое читают, и проверка, которая его стережёт, обязаны называть одно и то
же.

`map` генерирует карту проекта и индекс решений. Без флагов печатает в stdout
(сухой прогон для POC и ревью генерации), `--write` пишет `docs/map.md`. Карта
строится статическим разбором дерева: члены сборки из манифеста в корне
(Cargo.toml members, go.work use, settings.gradle include), либо при отсутствии
манифеста из каталогов верхнего уровня с кодом (суффиксы `.go`, `.py`, `.rs`,
`.js`, `.ts` и другие). Исключения из `.devkit/describe.ignore` вычёркиваются и
из карты. Описание компонента берётся из первого сработавшего источника:
модульная дока корневого файла (//! у Rust, Package у Go, docstring у Python),
первая строка README с срезом заголовка «# имя: », строка состава из
`docs/ARCHITECTURE.md`. Из найденного описания берётся первое предложение целиком.
Компонент без описания в карту не едет. Формат плоские строки «путь: описание»,
сортировка по пути, вторым разделом идёт индекс решений (заголовки «Решение N»
из `docs/lld/*.md`, сортировка по документу и номеру). Детали в
`docs/lld/DK-194-project-map.md`.

`user` держит настройки самого пользователя, а не проекта и не харнеса. Пока в
ней одна настройка: род, в котором агент пишет о себе (DK-704). Мимикрия велит
держаться голоса пользователя, а род из корпуса не выводится. О себе он пишет
редко, и дефолт модели совпадает с его родом случайно. Промах видно снаружи, в
ревью и в описаниях задач. Без ключа команда печатает заданный род и пути, с
`--gender` записывает новый.

Хранение раздвоено. Значение ложится строкой `gender = женский` в
`~/.devkit/user.local`, рядом с остальными машинными конфигами, а в контекст
сессии едет развёртка `~/.devkit/user.md`. Её зовёт импортом глобальная точка
правил, и текст приезжает и в сессию, и в субагента, и в вычитку `proofread`.
Прямо в тело глобальной точки род не пишется. Его переписывает генератор
правил целиком, и одна рука на этих файлах затирала бы раскладку стенда
послушания. Страница лежит на месте всегда, даже когда род не задан. Импорт в
пустоту у клиента не разворачивается вовсе, и вместе с ним пропадает всё, что
точка везёт, а заглушка ещё и говорит агенту, чего не хватает.

Кладёт страницу `doctor --fix`, а сам род доктор не угадывает. Назвать его
может только человек, и незаданный род это находка с этой командой. Раскладка
для obeycheck кладёт заглушку поверх того, что стоит на машине. Род там
свойство прогона, и задаёт его подготовка сценария вызовом той же команды.

```
$ devkitctl user
род первого лица: не задан
конфиг: /Users/t/.devkit/user.local
страница в контекст: /Users/t/.devkit/user.md
поставить: devkitctl user --gender <мужской|женский>
```

`selfcheck` гоняет живой круг связки после установки (DK-158). Доктор сверяет
файлы и версии, а эта команда проверяет конвейер в движении: заводит временный
проект с собственным голым origin (перевод доски и слияние при
`autonomous=true` пушат сами, и без origin круг умирал бы на первом же шаге),
проходит его целиком (подключение, строка на доске, вердикт pick, ветка задачи,
сценарий проверки, слияние с тестами и подставным выкатом, закрытие) и убирает
за собой всё, включая дерево задачи. Каждый шаг отчитывается строкой «ок» либо
«не прошёл», провал останавливает круг и печатает вывод шага, конец внятный:
«связка жива» либо «шаг такой-то не прошёл, связка не жива». Выкат и тесты
временного проекта подставные (метка в своём каталоге и пустая команда на
python3). Настоящие проекты не трогаются, а дом у круга свой: утилиты devkit
пишут в `~/.devkit` без ведома вызвавшего (записи runs, журнал уведомлений),
и сабпроцессы круга получают вместо настоящего временный. Утилиты зовутся
по имени из PATH, как их позовёт человек. Находки доктора (код 1) круг не провалят:
отдельный шаг в начале, их отчёт печатается в конце; код 2 это отказ запуска,
круг встаёт. Отличие от тестов devkit: тесты гоняются на стенде из исходников
до установки, selfcheck зовётся после неё, поверх установленных бинарей.

## Установка и обновление

`update` ставит devkit на машину и он же его обновляет: тулчейна для этого не
нужно, бинари едут готовыми в релизе гитхаба. Отдельной команды `install` нет,
на голой машине та же команда просто проходит все шаги впервые. Решение в
[docs/lld/DK-149-binary-delivery.md](../../docs/lld/DK-149-binary-delivery.md),
порядок установки с нуля в [CONNECT.md](../../CONNECT.md).

Команду выполняет python-часть из самого чекаута, и отсюда единственный случай,
когда обновление руками всё-таки нужно: машина стоит на теге, где живёт баг
самой команды. Своей починки она не применит, потому что чинит себя же тем
кодом, который сломан. Разрывается это одним переходом на новейший тег, дальше
`update` работает как обычно:

```sh
cd ~/projects/devkit && git fetch --no-tags --prune origin 'refs/tags/v*:refs/tags/v*' && git checkout --detach v0.12.0
```

Так вышло с DK-164 (до `v0.12.0` второе обновление подряд отказывало,
принимая отставший `origin/main` за невыложенную работу) и с DK-155 (до
`v0.9.0` fetch спотыкался о служебный тег `deployed`). Машины, поставленные
раньше этих версий, поднимаются строкой выше; поставленные позже про неё не
узнают.

```sh
# установка с нуля, одной строкой: клон и первая установка
git clone https://github.com/dronrider/devkit.git ~/projects/devkit && python3 ~/projects/devkit/tools/devkitctl/devkitctl.py update --pin

devkitctl update          # дальше обновление голой командой
devkitctl update --check  # только рассказать, ничего не двигая
```

Шаги такие: отказ, если позвали не из основного чекаута; разбор режима чекаута;
`git fetch --no-tags --prune origin refs/tags/v*:refs/tags/v*` (тегов, а не
всего разом: служебный `deployed`, который двигает `shipctl`, команде не
нужен, голым `--tags` роняет fetch, как только расходится с origin, а один
именной рефспек без `--no-tags` всё равно тащит посторонний тег автослежением,
если его коммит клону уже известен); новейший тег из git (`git tag --list
'v*'`, а не из API гитхаба); переход на тег; самоперезапуск уже кодом тега;
тарболл своей платформы и `SHA256SUMS` во временный каталог рядом с каталогом
назначения; сверка суммы; подмена бинарей через `os.replace`; обёртка
`devkitctl` рядом с ними; раскладка машинного контура тем же кодом, что зовёт
`doctor --fix`; рассказ о сделанном и список «осталось сделать».

Рассказ этот человек читает сверху вниз, поэтому однотипное в нём считается, а
не идёт строкой на файл: утилиты одной строкой с версией, числом и именами
(«установлено 6 утилит devkit v0.6.0 (fb1f8d5f9868) в ~/go/bin: agentctl, ...»),
тем же порядком скиллы, определения субагентов и хуки харнеса, а права
машинного контура одним счётом, без перечня самих правил. Число стоит перед
словом, а слово при нём меняет падеж («установлен скилл», «установлено 8
скиллов»): формы слова и сборка строки живут в `say.py`, чтобы установка,
доктор и права говорили одинаково. Сами слова про то, что случилось с машиной
(установлено, обновлено, включено, дописано), а не про раскладку файлов.

То же правило действует и на находки, и оно одно на весь вывод: шесть утилит
мимо PATH это одна строка с их перечнем, а не шесть строк подряд, и так же
считаются недостающие скиллы, определения субагентов и хуки харнеса. Порознь
остаются только беды с разным текстом (своя версия, свой коммит): их и надо
прочитать по одной.

Режим чекаута команда не угадывает, а различает, и случаев три.

- **Отвязанный HEAD на теге**, машина потребителя. Обычный ход: перейти на
  новейший тег и поставить бинари этого тега. Ключей не надо.
- **Ветка**, чекаут разработчика devkit. Команда отказывается: в основном
  чекауте ведётся доска, оттуда `shipctl` заводит ветки задач, и отвязанный
  HEAD ломает всю эту работу разом. Обновление тут это `git pull` и
  `doctor --fix` с локальной сборкой.
- **Ветка и `--pin`**, первая установка. Свежий клон стоит на `main`, и перевод
  его на тег человек разрешает явно. Ключ нужен ровно один раз, обратный ход
  это `git checkout main`.

Отвязывает чекаут режим, а не расхождение коммитов. Тег ставится на голову
`main`, и на свежем клоне вершина ветки и новейший тег это обычно один коммит:
переходить некуда, а `git checkout --detach` всё равно нужен, иначе машина
остаётся на ветке и следующий вызов отказывает ей как дереву разработчика.

Своя работа под отказ не попадает, и мера тут в два шага. Сначала, ещё до
fetch и без сети, изменённое отслеживаемое (`git status --porcelain
--untracked-files=no`). После fetch тегов, не до него, коммиты, до которых не
достаёт ни одна ветка origin и ни один известный релизный тег
(`git rev-list --count HEAD --not --remotes --tags=v*`). Через `@{u}` это не
считается: у отвязанного HEAD upstream нет вовсе, и проверка отказывала бы на
машине потребителя каждый раз. Untracked-файлы переходу не мешают,
`git checkout` их не теряет.

`--tags=v*` тут не для симметрии (форвард-фикс DK-164, в двух кругах). Первый
круг: ветки origin в клоне обновляет только клонирование, `update` дальше
тянет исключительно теги, и `origin/main` застывает на моменте клонирования
навсегда, а HEAD уезжает по тегам вперёд с каждым релизом. Без тегов в мере
второе обновление подряд принимало бы этот разрыв за чужую работу и отказывало
всегда, хотя коммиты давно лежат в origin под именем тега. Второй круг,
найденный ревью: голый `--tags` матчит любой локальный тег, а не только
пришедший из origin, и `git tag foo` поверх невыложенного коммита обнулял бы
меру, хотя работа как раз на кону. Маска `v*` сама по себе не спасает: тег
может называться `v9.9.9-local` и пройти мимо неё тоже. Спасает порядок: мера
считается уже после `git fetch --no-tags --prune origin
refs/tags/v*:refs/tags/v*`, того самого, каким `update` и так тянет релизные
теги, а `--prune` на этом рефспеке убирает из клона самозваный тег с похожим
именем раньше, чем мера успеет на него посмотреть; тег с именем вне маски
`v*` этот fetch не трогает никогда, и его дополнительно отсекает сам паттерн
меры.

Самоперезапуск (`os.execv`) стоит после перехода на тег: иначе вторую половину
работы делал бы python, прочитанный до перехода, то есть старая логика
раскладки клала бы новые бинари. Тег, собранный до появления самой команды,
такой передачи не понимает, и туда команда не перезапускается, а доделывает
работу на месте и говорит об этом.

Молчаливого холостого хода у команды нет, случаи названы поимённо: обновлять
нечего (чекаут на новейшем теге и все бинари отвечают его коммитом, в сеть за
ассетами команда не идёт); тегов нет вовсе (релизов ещё не выпускалось, чекаут
и бинари не тронуты, назван `devkitctl build`); тег есть, а ассетов ещё нет
(щель между пушем тега и концом сборки, позвать позже); сети нет (отказ на
`fetch` либо на скачивании, ни один шаг не сделан наполовину); платформа не из
четырёх пар релиза.

`--check` делает только `git fetch --no-tags --prune origin
refs/tags/v*:refs/tags/v*` и рассказывает: на каком теге машина, какой
новейший, что поставит обычный `update`. Чекаут, бинари и раскладку он не
трогает, а теги в клон приносит, и иначе быть не может: знание о вышедшем
релизе неоткуда взять, кроме origin.

Каталог назначения выбирается по порядку: `DEVKIT_BIN`, если задан, иначе
первый из `~/go/bin` и `~/.local/bin`, который уже стоит в PATH, иначе
`~/.local/bin` (он создаётся). Профиль оболочки команда не правит: каталог мимо
PATH уезжает в «осталось сделать» готовой строкой и держится находкой доктора.
Туда же кладётся обёртка `devkitctl` из трёх строк с абсолютным путём до
чекаута, по ней python-часть зовётся по имени наравне с бинарями. Пишет обёртку
генератор (`update` и `doctor --fix`), а не релиз: путь у каждой машины свой, и
после переезда чекаута она перевыпускается. Помета `# devkit:generated` в ней
стоит затем же, зачем в тонких файлах проектов: чужой скрипт с тем же именем
доктор не затрёт, а скажет про него.

Адрес релизов подменяется переменной `DEVKIT_RELEASE_BASE`. Это шов для тестов
и для прогона в чистом окружении: гитхаб в тестах не участвует, релиз им отдаёт
локальный сервер.

## Догон чекаута до origin/main

`catchup` подтягивает чекаут devkit до `origin/main` и раскладывает приехавший
`kit` по харнесам. Команда написана для машины, где devkit правят веткой, а
работают за двумя машинами. `update` двигает только клон потребителя, стоящий на
теге, а ветку `main` на машине разработчика не подтягивает никто. Скиллы,
определения субагентов и хуки действуют копиями в каталогах харнесов, и кладёт
копии `doctor --fix`. Правка со второй машины лежала в origin до ближайшего
`git pull` руками.

Зовёт команду SessionStart-хук `hooks/devkit-catchup.sh` с ключом `--hook`.
Чекаут догоняется до того, как сессия прочла из него устаревшие правила.

```sh
devkitctl catchup         # руками, с рассказом на каждой развилке
devkitctl catchup --hook  # режим старта сессии, гард молчит
```

Развилки такие.

- Чекаут не основной (дерево ветки задачи), HEAD не на `main` (тег, отвязанный
  HEAD, другая ветка), `origin` не заведён. Команда ничего не делает.
- `FETCH_HEAD` моложе десяти минут. В сеть команда не идёт, отставание считает
  по уже известному указателю.
- Сеть недоступна. Чекаут остаётся как есть, потолок у `fetch` десять секунд.
- Своя работа в `main` впереди origin, а origin вровень. Подтягивать нечего,
  в режиме хука это молчание.
- Разошлись: в origin чужая правка, в `main` своя незапушенная. Печатается
  строка про расхождение с числом своих и чужих коммитов, и в режиме хука
  тоже.
- Позади, и fast-forward проходит. Команда двигает `main` и печатает короткий
  sha с числом приехавших коммитов.
- Fast-forward не прошёл, правка на месте пересеклась с приехавшей. Печатается
  причина от самого git.

Каталоги `kit/`, `hooks/`, `tools/` и `internal/` в приехавшем диапазоне это
второй шаг. Команда зовёт тем же заходом `doctor --fix` и печатает его строки
«починено»: скиллы и определения ложатся копиями по харнесам, утилиты
пересобираются в PATH. Упавший доктор печатается одной строкой, подтяг при
этом уже случился. Находки доктора
про машину наружу не идут, на старте сессии они собрались бы в простыню. Правка
одной доки второго шага не стоит, копий по харнесам у неё нет.

В режиме `--hook` молчит только гард. Подтяг, расхождение с origin и отказ
слияния печатаются и там. Старт сессии обязан видеть, что случилось с чекаутом,
и молчание после подтяга неотличимо от молчания на месте.

## Сборка бинарей

`build` собирает Go-утилиты devkit с зашитой версией, и точка сборки эта одна:
её же зовёт `doctor --fix`, когда пересобирает устаревший бинарь, и её же гоняет
релизный workflow на раннере. Решение в
[docs/lld/DK-149-binary-delivery.md](../../docs/lld/DK-149-binary-delivery.md).

```sh
python3 tools/devkitctl/devkitctl.py build                    # под свою машину
python3 tools/devkitctl/devkitctl.py build --release --out dist  # четыре пары
```

Что собирать, команда выводит из дерева (каталоги `tools/*/` с `go.mod`), а не
из списка в коде: по правилу языка go тут это ровно то, что ставится в PATH,
поэтому список сборки, список установки и список проверки доктора совпадают по
построению, и седьмая утилита попадает в релиз тем, что появилась. Версия
берётся из git того чекаута, откуда идёт сборка (`git describe` по релизным
тегам `v*` плюс `git rev-parse --short=12 HEAD`), и уезжает в бинарь линковкой,
`-ldflags -X`. Служебный тег `deployed`, который двигает `shipctl` на каждом
выкате, в счёт не идёт: версия считается по релизным тегам, иначе бинарь
назвался бы именем тега выката. Собирается всё с `CGO_ENABLED=0` и `GOWORK=off`:
чужой `go.work` на машине увёл бы сборку из модуля утилиты, а своего у devkit
нет.

Кладётся собранное рядом с целью и переезжает на место переименованием, а не
пишется поверх: `go build` отказывается писать поверх файла, который не его
(«already exists and is not an object file»), а такой в каталоге назначения как
раз и бывает, доктор чинит расхождение в том числе с чужой копией. На linux к
тому же запись в работающий бинарь даёт `ETXTBSY`.

Собранное проверяется тут же, и проверки две, потому что кросс-собранный бинарь
на раннере не исполняется (darwin на ubuntu даёт `exec format error`).

- Пара своей машины запускается с `--version` и обязана напечатать ту строку,
  которую в неё зашивали: `<имя> <версия> (<коммит>)`. Утилита, забывшая флаг,
  роняет сборку, и это единственное место, где такая пропажа видна.
- Остальные три пары проверяются байтами: зашитая строка обязана найтись в
  артефакте. Проверка слабее, но ловит главную беду `-ldflags -X`,
  несуществующий символ линковщик молча пропускает и собирает бинарь без версии.

Сборку на машину (без `--release` и без `--out`) кончает ещё одна сверка, по
победителю PATH. Каждая утилита после укладки обязана отвечать на `--version`
строкой свежей сборки. Этой дорогой едет выкат devkit, `deploy` в
`.devkit/deploy.local` зовёт `devkitctl build`. До DK-599 копия из чужого
каталога, стоявшего в PATH раньше каталога назначения, переживала выкат молча.
Слияние отчитывалось зелёным при старой команде на машине, так неделю
вердикты `agentctl` считала сборка ветки (DK-549). Теперь расхождение роняет сборку
с именем утилиты и путём заслоняющей копии, а через неё `shipctl merge` и
`shipctl ship`. Той же сверкой кончается `update`. Бинари релиза он кладёт в
тот же каталог, и вторая сборка, выигравшая в PATH, оборачивается отказом
установки. Имя, которого в PATH нет вовсе, сверка не судит. Про каталог мимо
PATH говорят находки раскладки.

Обе пары всё равно исполняются живьём, просто в разных прогонах: `--release` на
раннере проверяет запуском linux/amd64, а та же команда на маке разработчика
darwin/arm64.

`--release` пакует тарболл на пару, `devkit-<версия>-<os>-<arch>.tar.gz`, внутри
плоско лежат все утилиты релиза, и кладёт рядом `SHA256SUMS`. Каталог назначения
по умолчанию `dist` (гитигнорнут), под обычной сборкой тот же, куда ставит
`update`. Промежуточные бинари складываются в каталоге
назначения и убираются после упаковки. Пара, не прошедшая проверку, тарболла не
получает, и в `SHA256SUMS` её нет, а код выхода 1 называет находку.

## Файлы правил

Рукописный файл правил в проекте один, `AGENTS.md`: открытая спека, плоский
markdown, импортов не понимает. Всё остальное генерится, и не отдельной
командой, а тем же `doctor --fix`: дрейф это находка доктора, починка это его
же `--fix`, третьего входа в генерацию нет. Что именно генератор считает
эталоном для проекта, печатает отдельная команда, она же удобная точка для
глаза, когда доктор говорит «устарел»:

```sh
python3 tools/devkitctl/rules.py .
```

Она же собирает раскладку правил для стенда послушания
[obeycheck](../obeycheck/README.md): директория с файлами правил, тонким файлом
харнеса и глобальной точкой в `home/`, ровно та, что доезжает до сессии при
заданной глубине. Стенду раскладка это вход, и боевую пару он получает от
генератора, а не от руки:

```sh
python3 tools/devkitctl/rules.py --layout full ../rules-full tools/obeycheck/testdata/project
python3 tools/devkitctl/rules.py --layout core ../rules-core tools/obeycheck/testdata/project
```

Файлы правил ложатся в корень раскладки голыми именами, и импорты зовут их так
же: раскладка едет в чужой проект целиком, и путь наружу из неё не развернулся
бы. Текст, который глобальная точка и тонкий файл тянут оба, кладётся одной
копией, а лишняя строка импорта из точки снимается: на машине это один файл под
двумя путями, и платить за него дважды стенд не должен. Раскладка саму
глобальную точку только читает: этот раздел про файлы проекта, а генерит и
чинит её отдельная проверка машинного контура (раздел ниже).

Куда попадают правила, решает состав включённых харнесов (`enabled` в
`~/.devkit/harness.local`, проектный `.devkit/harness.local` его только
сужает; конфига нет вовсе, значит включён claude-code):

- все включённые понимают импорты: копий текста правил в дереве ноль. Каждому
  генерится тонкий файл (`file` из его профиля, у Claude Code `CLAUDE.md`) со
  ссылками на `AGENTS.md` и на правила devkit, а проекту с доской ещё и на
  правила доски;
- есть хоть один embed-инструмент: текст правил вклеивается в `AGENTS.md`
  между маркерами `devkit:rules`, а тонкие файлы на devkit больше не ходят,
  иначе их контекст получил бы правила дважды.

Сколько текста правил доезжает, решает не только режим доставки, но и глубина.
Выводится она из оси скиллов профиля харнеса (секция `[skills]`, ключ
`discovery`), разобрана в [DK-100](../../docs/lld/DK-100-context-tree.md):

- `auto`: скиллы инструмент подхватывает сам, значит ему хватает ядра правил
  (`RULES.core.md`, проекту с доской ещё `RULES.board.core.md`), а процедуры
  доезжают скиллами;
- `manual`: скиллы инструменту доступны, но сам он их не объявляет, поэтому к
  ядру прикладывается таблица указателей: строка на скилл с описанием (по нему
  видно, когда он нужен) и путём, по которому его читать;
- секции нет вовсе: едет полный текст правил, как ехало всегда. Пустая секция
  значит то же самое, но по другой причине: ось у инструмента разобрана, и
  скиллов у него нет.

Объявленная глубина это ещё не доехавшая. Пока в devkit не нарезаны все тексты,
которые тянет проект, генератор берёт полный: ядро правил лежит нарезанным
(`RULES.core.md`, `RULES.board.core.md`), а тексту, у которого ядра ещё нет,
урезаться не во что. Ждут ядра обе неполные глубины, и указатели тоже: они
заменяют процедуры, уехавшие в скиллы, а рядом с полным текстом стали бы второй
копией того же самого. Признак глубины в файле показывает факт, а не обещание:
`depth=core` в маркере тонкого файла, `depth=pointers` там же или в маркере
начала вклейки. У полной глубины признака нет, потому что это и есть
сегодняшняя раскладка, а приписка к ней перегенерила бы каждый файл на машине,
не сказав ничего нового. Что объявлено и что доехало, печатает `rules.py`
строкой на харнес:

```text
глубина правил, claude-code: ядро (discovery = "auto", скиллы инструмент подхватывает сам)
```

Вклейка в `AGENTS.md` одна на всех embed-инструментов, поэтому глубина у неё
самая полная из запрошенных: тому, кому нужен весь текст, урезанного не хватит.
Таблица указателей входит в хеш источников наравне с файлами правил, иначе
добавленный в devkit скилл не доехал бы до вклейки молча.

Первая строка генерённого файла это маркер с хешем тела
(`<!-- devkit:generated body=... -->`), у вклейки хеша два: `src` от
источников в devkit и `body` от текста между маркерами. Вопросы разные,
поэтому и хеша два: по свежему `src` не видно ручной правки, по целому `body`
не видно протухания. Отсюда поведение доктора:

- файла нет, а харнес включён: `--fix` его генерит;
- файл устарел (правила devkit обновились, появилась доска, включился
  embed-инструмент): `--fix` перегенерирует и говорит об этом строкой;
- файл правлен руками (содержимое разошлось с хешем): не перетирается, а
  доктор зовёт перенести правку в `AGENTS.md`. То же у вклейки: локальным
  исключениям в общих правилах не место, но и молча стирать чужой текст
  `--fix` не вправе;
- файла нет вовсе, зато лежит рукописный `CLAUDE.md` без маркера: это проект,
  подключённый до переезда, и доктор подсказывает `git mv CLAUDE.md AGENTS.md`
  плюс `--fix`. Сам не переносит: в живых `CLAUDE.md` бывают локальные вещи
  вроде импорта корпоративных правил, автоматике их не разобрать;
- строка импорта в рукописной части `AGENTS.md`: находка, потому что читают
  его и инструменты без импортов, и правила по такой строке до них не
  доедут. Обычно она остаётся после переезда, убирается руками;
- вклейка лежит больше чем в одном файле дерева: находка, копия должна быть
  одна. Маркеры внутри блока кода за копию не считаются, это документация;
- последний embed-инструмент выключен: `--fix` убирает вклейку и возвращает
  тонким файлам ссылки на devkit. Это единственный случай, когда `--fix`
  удаляет, и удаляет он только текст между целыми маркерами с совпавшим
  `body`.

Источник правил для проекта, который сам является чекаутом devkit
(self-hosting, как сам devkit себе), это всегда он сам, а не переданный
`devkit`-параметр: генератор проверяет это не равенством путей, а признаком
«у корня есть свои `RULES.md` и `tools/devkitctl/devkitctl.py`»
(`rules.is_devkit_checkout`). Иначе `doctor`, запущенный не тем чекаутом
devkit (временная копия для тестов, чужой клон), молча вклеил бы в
коммитируемый `CLAUDE.md` путь до неё, а тот мёртв с первой же уборки
временной директории (DK-127).

Подключённый проект (devkit не self-hosting) зовёт правила не путём до чекаута,
а через свою ссылку `.devkit/devkit`, и физического чекаута тонкий файл не
называет вовсе: `@.devkit/devkit/RULES.board.core.md`. Отсюда и стабильность
коммитируемого файла: прогон доктора из временной копии devkit или из чужого
клона выдаёт те же байты, что и обычный, и подменить путь ему нечем (DK-127).
Ссылку такой прогон тоже не перевешивает: годной ей считается любое дерево
правил, а не тот чекаут, из которого позвали доктора.

### Куда доезжают импорты правил

Строка импорта в файле правил проекта разворачивается не всегда, и клиент про
пропущенную не говорит ни слова. Граница замерена 2026-08-08 живыми прогонами
`claude -p`: в каждом файле лежало кодовое слово, а прогон просил перечислить
те, что доехали до контекста. Вышло так:

- импорт внутрь каталога, где лежит сам файл (`@sub/A.md`), разворачивается;
- импорт наружу (относительный `@../devkit/RULES.md`, абсолютный, от `~`) по
  умолчанию не разворачивается. Заперт он воротами одобрения, а не устройством
  клиента: состояние лежит в `~/.claude.json` флагом
  `hasClaudeMdExternalIncludesApproved` по проекту, с флагом внешний импорт
  разворачивается как внутренний, без него пропускается молча (замер
  2026-08-09 теми же прогонами с кодовым словом). Одобрение клиент спрашивает
  диалогом при первой встрече, но headless-прогону диалог показать некому, и
  на живой машине он не показывался нигде: одобрение стоит только у чекаута
  самого devkit. Флаг `--add-dir` на ворота не влияет, разрешение читать
  каталог тут ни при чём;
- граница лексическая, по записанному пути: симлинк внутри проекта, ведущий
  наружу (`@link/RULES.md`), разворачивается как обычный путь внутрь;
- вглубь клиент идёт на четыре ступени импорта, дальше цепочка обрывается;
- у глобальной точки правил (`~/.claude/CLAUDE.md`) граница другая: её импорт в
  `~/projects/devkit/RULES.core.md` доезжает, на том вся раскладка devkit и
  держится.

Отсюда была дыра в раскладке «devkit по соседству». Тонкий файл проекта звал
правила путём `@../devkit/RULES.core.md`, то есть наружу, и до контекста они по
этой дороге не ехали вовсе. Ядро правил спасала глобальная точка: тот же текст
она везёт своей дорогой, и сессия его получает. А вот правила доски глобальная
точка не везёт, и проект с доской работал без них: ни ядра, ни полного текста, и
молчание тут неотличимо от штатной работы. Ровно на этом сессия проекта
`it-road-course` вывезла процедуру доски скиллами, не имея её правил в резиденте
(разбор в `docs/tasks/DK-190.md`).

Дыра закрыта дорогой из [docs/lld/DK-193-rules-delivery.md](../../docs/lld/DK-193-rules-delivery.md):
импорт снова ведёт «внутрь», через ссылку на соседнее дерево внутри самого
проекта.

- В проекте лежит `.devkit/devkit -> ../../devkit`, и правила зовутся путём
  через неё: `@.devkit/devkit/RULES.board.core.md`. Граница у клиента
  лексическая, записанный путь остаётся внутри проекта, и импорт
  разворачивается как внутренний. Ссылка лежит в каталоге обвязки, а не в
  корне: скрытый каталог не берут ни go-тулчейн, ни сборщик pytest, ни
  `discover`, ни глоб-инструменты, и чужое дерево не утягивается в прогон
  тестов проекта.
- В своих проектах ссылка коммитится (git хранит её записью 120000) и
  приезжает чекаутом на любую машину, включая дерево задачи. Гитигнор обвязки
  точечный (`.devkit/*.local`, `.devkit/log`) и её не задевает. На машине без
  devkit по соседству ссылка висит битой и никому не мешает: клиент молча
  пропускает импорт в несуществующий путь.
- Ядро общих правил тонкий файл не выписывает вовсе: его везёт глобальная
  точка, и вторая копия того же текста стоила бы проекту контекста ни за что.
  Это констатация раскладки devkit, а не замер машины: коммитируемый тонкий
  файл обязан выходить одинаковым везде. Полные тексты глубины `full`
  глобальная точка не везёт, и они по-прежнему выписываются, только через
  ссылку. Проект без доски на глубине ядра не импортирует из devkit ничего, и
  ссылка ему не кладётся.
- Ссылку кладут `new` и `doctor --fix`, и кладут только тому, у кого через неё
  и правда идёт импорт. Её отсутствие и чужая цель это находки, которые
  `--fix` чинит; занятое имя (по пути лежит свой файл или каталог) остаётся
  находкой и с `--fix`, чужое молча не сносится.

Доктор про это молчать перестал. Строка импорта, которая уводит за пределы
проекта, а файл на диске есть, это находка с именем недоехавшего файла. Импорт,
чей текст всё равно приезжает глобальной точкой, находки не даёт: считается не
строка, а то, что в контексте оказалось. Вторая находка про соседнее: импорт
тянет полный текст правил (`RULES.md`, `RULES.board.md`), хотя рядом лежит ядро,
против раскладки «резидентно ядро, полный текст по надобности». Обе смотрят на
файл правил проекта как он записан, а не как его сгенерировал бы генератор:
рукописный `CLAUDE.md` проекта, подключённого до переезда на `AGENTS.md`,
генератору не принадлежит вовсе, а в контекст едет наравне с генерённым.

Обе находки остаются в силе и после перехода на ссылку: перегенерённый проект
их не даёт (путь через ссылку лексически внутренний), а проект с рукописным
`CLAUDE.md` или с ушедшей ссылкой даёт, и молчаливого состояния у дыры не
остаётся. Про саму пропавшую ссылку говорит своя находка, про её несуществующую
цель проверка битого импорта.

Отдельным разделом идёт машинный контур: он общий для всех проектов, поэтому
находки помечены словом «машина». Проверяется то, без чего конвейер тихо
работает наполовину:

- PostToolUse-хуки харнеса прописаны в его `[hooks] config` (символы,
  индекс памяти, чувствительное), там же SessionStart-хук `quota-refresh.sh`:
  без него снимок квоты сам не освежается и корректор pick рано или поздно
  остаётся с протухшим. Недостающее дописывает `--fix` тем же порядком, что
  права: команда встаёт в группу со своим матчером либо заводит её, чужие группы
  и порядок остаются на месте, а раскладка событий и матчеров живёт таблицей
  `HOOK_LAYOUT` в `devkitctl.py`. С ветки задачи хуки на машину не едут, как и
  права: там они только сверяются;
- команда хука зовёт файл из выкаченного дерева devkit. Строка с путём дерева
  ветки выглядит подключённым хуком, и по именам скриптов доктор её раньше
  пропускал. Работает по такой строке своя копия файла. Правка хука в основном
  чекауте до сессий машины не доезжает, пока её не возьмёт та ветка (DK-582).
  Находка называет чужое дерево, выкаченное и сами хуки. `--fix` меняет в
  команде только путь до каталога `hooks`, а событие, матчер и хвост команды
  остаются как были. Рубеж тут тот же, что у прав. С ветки задачи пути на неё не
  переписываются, и находка зовёт чинить из основного чекаута. Судится только
  тот скрипт, который в выкаченном дереве есть, свои скрипты человека доктор не
  трогает. Ищет чужое дерево `stray_hooks()`, перенацеливает `repoint_hooks()`;
- реестр чатов `session-task.py` подключён на `SessionStart` с пустым матчером.
  Без него дашборд возвращается к угадыванию задачи по транскрипту: разговор о
  задаче горит её живой работой, а нераспознанную сессию не открыть по ID,
  которого у неё нет. Находка про него своя, а не общая со снимком квоты:
  событие то же, беда другая;
- подхват реплики `chat-in.py` подключён на `PostToolUse` с пустым матчером.
  Без него реплика человека из чата цели ждёт следующего витка вместо идущего,
  а на экране это неотличимо от штатной тишины, поэтому находка про него своя,
  а не общая с проверками текстов: событие то же, но матчер и беда другие.
  Матчер пустой не по недосмотру, доставлять реплику надо на любом ходе витка,
  а не на записи файла. Прежнее имя `inbox.py`, застрявшее в настройках от
  старой раскладки, доктор находит отдельно: такая строка зовёт файл, которого
  в чекауте уже нет, и харнес спотыкается на ней каждым ходом.
  Поэтому `--fix` сперва убирает её, а потом ставит `chat-in.py`, и править
  `settings.json` руками не нужно; перечень переименованных хуков лежит в
  `RETIRED_HOOKS`, уборку делает `drop_hooks()`, а `hook_script()` достаёт
  имя файла из команды;
- уведомитель `notify.py` подключён сразу на пять событий: `Notification`,
  `Stop`, `StopFailure`, `SubagentStop` и `UserPromptSubmit`. Пропажа любого
  проверяется отдельно, потому что без первого сессия не зовёт, когда ждёт
  разрешения, без `Stop` молчит про конец хода, без `StopFailure` про ход,
  убитый API-ошибкой, без `SubagentStop` про отработавшего субагента,
  а без `UserPromptSubmit` не снимается отметка ожидания, и второй конец хода
  подряд глохнет в общем окне троттлинга. Тут же проверяется, чем эти уведомления слать: бэкенд
  выбирает сам `notify.py` по платформе и PATH, и когда его нет (нет
  `notify-send` на Linux, необычная платформа), доктор называет это находкой
  с командой `notify.py --self-test`. Отдельная находка на macOS, где слать
  есть чем, но клик по баннеру уводит в Finder: `osascript` постит от имени
  Script Editor, переход в окно сессии даёт `terminal-notifier`. Пакет этот
  ставит сам `--fix`, потому что человек за такой мелочью не пойдёт, а без
  перехода баннер наполовину бесполезен; когда ставить нечем, остаётся находка
  с причиной. Поломкой это не считается, уведомления и без неё доходят;
- сторож фоновых субагентов `agent-watch.py` подключён на три события:
  `PostToolUse` с матчером `Agent` (запуск работы), `SubagentStop` (её конец) и
  `Stop` (сдача сессии того, о чём её не уведомили). Пропажа любого это одна
  находка со своим текстом: без сторожа отчёт фонового субагента теряется по
  дороге, а сессия уходит спать, считая его работающим (DK-519). С уведомителем
  они висят на одних событиях, но говорят в разные стороны, уведомитель наружу
  человеку, сторож внутрь сессии, поэтому и находки у них разные;
- ретрай-вотчдог харнеса: env-ключ `CLAUDE_CODE_RETRY_WATCHDOG` в секции `env`
  тех же настроек (DK-172); публичная дока Claude Code его не описывает.
  Разделяющий замер стенда разницы в поведении с ним и без него не нашёл,
  `--fix` всё равно вписывает ключ безвредным заделом; значение, вписанное человеком (хоть
  `"0"`), не трогается. Разбор поведения и стенда в `hooks/README.md`, раздел
  «Возобновление после обрыва связи»;
- права машинного контура в `permissions.allow` тех же настроек. Сессии,
  поднятой без человека (`claude -p`), одобрить запрос харнеса некому:
  неразрешённый инструмент отвечает отказом, а сессия идёт дальше и не делает
  ничего. Так встал первый headless-виток цели DK-109, девять отказов подряд
  вместе с правкой файлов, и в «Журнале» цели не появилось ни строки, так что
  со стороны стоп был неотличим от молчания. Перечень прав лежит в
  `tools/devkitctl/perms.py`: утилиты devkit вместе с `dashboard` и `devkitctl`,
  git, чем гоняются тесты и сборки, включая `node` для стендов дашборда, мелочь
  вроде `wc` и `sed`, чтение и правка файлов. Перечень не собран по каталогу
  `tools`, а держится именным списком. Право без подтверждения выдаётся
  разбором, и `secretctl` туда не попадает нарочно. Команда, которой в перечне
  нет, останавливает сессию без человека вопросом разрешения. Перечень поэтому
  закрыт сторожем в `perms_test.py`. Команды, на которых держатся сценарии
  проверки, обязаны в нём быть. `--fix` дописывает
  недостающее в конец `allow`, рукописных правил не трогая и порядка их не
  меняя; право, записанное пользователем в `deny` или `ask`, остаётся
  находкой, снимать запрет автоматике не по чину. Разрешённый целиком
  инструмент (`Bash` без скобок) перечень покрывает, чинить исправное доктор
  не зовёт. Эталон тут тот же, что у определений субагентов, основной чекаут:
  из worktree ветки задачи доктор права только сверяет, потому что видны они
  каждой сессии на машине сразу, и выписывать их себе непроверенной веткой
  цикл не должен даже случайно. Тот же перечень спрашивает оболочка цели перед
  первым витком, а `dashboard check` перед подъёмом прогона сценария после
  выката, поэтому у него есть свой вход, дешевле полного доктора:

  ```sh
  python3 tools/devkitctl/perms.py [--fix]
  ```

- бинари devkit в PATH и на одной версии с чекаутом. Список берётся из дерева
  (`tools/*/go.mod`), поэтому новая утилита попадает под проверку тем, что она
  есть, а не правкой перечня в доке и в коде. Сверяется коммит: доктор
  спрашивает у бинаря `--version` и смотрит, есть ли в этом коммите последняя
  правка кода утилиты (`git log -1 -- tools/<имя>/*.go` и её файлы сборки).
  Свежим считается бинарь, собранный из этого коммита либо из любого более
  позднего, то есть сборка с HEAD годится всегда. По HEAD напрямую сверять
  нельзя: доска devkit лежит в том же репозитории, и коммит доски уводил бы HEAD
  вперёд, не меняя в бинаре ни байта, так что после каждого слияния доктор давал
  бы шесть находок на ровном месте, а `--fix` гонял бы сборку впустую. README
  утилиты в счёт не идёт по той же причине: из него ничего не собирается.
  Порога тут нет, отставший бинарь это находка, и бинарь, не понимающий
  `--version`, тоже: он собран до релизной схемы версий. Рядом доктор называет
  режим чекаута («на релизе v0.3.0», «на ветке main, впереди релиза v0.3.0»),
  иначе на машине разработчика отставание читалось бы как поломка. Чинит
  находку `--fix` тем, что на машине есть: чекаут стоит на теге, значит ставит
  бинари этого релиза, иначе собирает через `build`, а без тега и без go находка
  остаётся с причиной. История берётся у **основного** чекаута, поэтому параллельная
  сессия в worktree ветки задачи находок не сыплет, но и чинить их оттуда
  нельзя: машинный бинарь с непроверенной ветки уехал бы во все проекты сразу.
  Единственный остаток mtime это несохранённые правки `*.go`: коммита у них ещё
  нет, сравнивать нечего, и тут доктор смотрит на время файла;
- вышедший релиз, и это единственный канал, которым машина потребителя про него
  узнаёт: `git pull` в отвязанном чекауте не работает. Находок две. Точная
  сравнивает тег чекаута с новейшим тегом, известным клону («стоит v0.2.0,
  вышел v0.3.0»), и гаснет только от обновления. Косвенная отвечает на второй
  вопрос, давно ли вообще спрашивали: mtime `FETCH_HEAD` старше двух недель
  либо файла нет вовсе, и гасит её `devkitctl update --check`. В сеть доктор не
  ходит ни в той, ни в другой, обе считаются по локальному клону;
- определения субагентов `kit/agents/*.md` (исполнители `exec-*`, ревьюверы
  `review-*`) лежат в `[delegate] agents_dir` и совпадают с devkit; без них effort
  из вердикта pick применять нечем, и спавн молча уходит на дефолтного агента.
  Определением файл считается по frontmatter с `effort:`, соседняя проза вроде
  README на машину не уезжает. Эталон, как и у бинарей, это основной чекаут: из
  worktree ветки задачи определения только сверяются, а раскладка и перекладка
  ждут слияния;
- скиллы devkit `kit/skills/*/` лежат в `[skills] dir` и совпадают с devkit.
  Скилл это процедура, общая всем проектам (`board-batch` собирает пачку задач

  считается директория с `SKILL.md`, и на машину она едет целиком, со всеми

  или правленный руками спутник это то же расхождение, что правка самого

- глобальная точка правил (`[rules] global_file` профиля, у Claude Code

  `SessionStart` подключён и tmux на месте: находки тут не будет, потому что
  снимок появится сам при первой же сессии, и звать за ним человека значило бы
  выдумать ему работу. Находка возвращается, когда снять снимок нечем: хук не
  подключён либо tmux на машине нет, и причина эта названа в ней прямо;
- носитель сторожка цикла цели: launchd-агент `ru.devkit.goal-watch` положен,
  показывает на основной чекаут и поднят. Он несёт в `EnvironmentVariables`
  собранный PATH, тем же сборщиком `dashboard.agent_path` и по тому же якорю,
  что у соседней проверки ниже, по бинарю dashboard из PATH. Без этого PATH
  launchd даёт агенту голый системный путь, и дети тика (taskctl, shipctl,
  dashboard, agentctl) не находят себя: агент циклически пишет об этом в свой
  журнал (DK-664). Его след в `~/.devkit/goal-watch.log` не старше трёх
  интервалов, иначе это находка сама по себе, как и не положенный вовсе
  агент. Обе находки чинит и перевзводит `--fix`; эталон тут тот же, что у
  правил и бинарей, из worktree ветки задачи агент только сверяется. Бинаря
  dashboard нет в PATH вовсе, значит собирать PATH агента неоткуда, и это своя
  находка, зовущая `devkitctl update` или `build`. Проверка идёт после
  бинарей нарочно, тем же порядком, что у дашборда ниже. Разбор самого
  сторожка в разделе «Сторожок цикла цели»;
- носитель дашборда: launchd-агент `ru.devkit.dashboard` держит `dashboard
  serve` с KeepAlive, показывает на бинарь из PATH (а не на чекаут: замену
  бинаря выкатом демон замечает сам по иноде и перезапускается), несёт в
  `EnvironmentVariables` собранный PATH (каталог бинаря, системные пути
  launchd, брю-каталоги и `~/.local/bin` с машины: умолчание launchd не знает
  ни брю, ни каталога бинарей, и демон не находил tmux, а `~/.local/bin`
  добавлен следом, там символьной ссылкой стоит claude, и без него конвейер
  не поднимал headless-сессию, DK-247), поднят, и
  `/healthz` на порту из `~/.devkit/dashboard.local` отвечает без ошибок
  конфига. Живость меряется после первого старта: конфиг кладёт сам `serve`,
  и пока файла нет, доктор про `/healthz` молчит, агент только что взведён.
  Каждая нехватка своя находка: нет бинаря, зовётся `devkitctl
  update`; агент не положен или показывает на старый бинарь, чинит `--fix`;
  `/healthz` молчит или несёт ошибки конфига, находка называет их и журнал
  `~/.devkit/dashboard.log`. Проверка идёт после бинарей нарочно: на прогоне
  с `--fix` бинарь dashboard успевает встать в PATH до подъёма агента. На
  платформах без launchd носителя пока нет, и доктор говорит об этом
  находкой, когда дашбордом пользуются (есть конфиг или бинарь): команду
  ставят в systemd руками. Сам инструмент разобран в
  `tools/dashboard/README.md`;
- конфиг второй подписки `settings.json` разложен и заполнен. Каталог его берётся
  из машинного ключа `home` секции `[glm-code]`, а не из константы: тот же ключ
  читают раскладка хозяйства и окружение подпроцесса делегирования, и два места
  под один каталог разъезжаются. Ключа в машинном слое нет значит второй
  подписки на этой машине не заведено, и доктор про неё молчит: звать вписывать
  endpoint того, чего у человека нет, значит выдумать ему работу. Порядок
  первого запуска целиком, от заведения ключа до рабочего окна `shipctl code`,
  лежит в [tools/shipctl/README.md](../shipctl/README.md), «Окно на второй
  подписке»; здесь только то, что делает сам доктор. `--fix` кладёт болванку с
  пустыми ключами `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` и
  `ANTHROPIC_MODEL`, сузив права каталога и файла: там лежит токен. Значения
  берутся в кабинете подписки, придумать их автоматике нечем, поэтому пустые
  ключи остаются находкой, пока их не впишут, а сам токен ни в находку, ни в
  отчёт не попадает никогда. Битый json `--fix` не переписывает: там мог
  остаться вписанный руками токен, и перезапись потеряла бы его молча;
- окружение копии окна второй подписки сошлось с машинным слоем. Копия это
  вечное дерево `../<проект>-<поставщик>` рядом с проектом, в котором живёт окно
  редактора (`shipctl code`), а ключи подписки лежат в его
  `.claude/settings.local.json`: привязанные к директории, они достаются окну
  при любом способе открыть его, хоть из дока. Хозяин ключей при этом машинный
  слой, и разъезд с ним значит окно, ходящее по старым ключам, а то и на первую
  подписку; `--fix` переписывает ключи подписки, не трогая написанного человеком
  рядом (разрешения сессии), и сужает права файла, там токен. Копии рядом нет
  значит окном второй подписки над этим проектом не работают, и доктор молчит;
- профили харнесов `devkit/kit/harness/*.toml` разбираются и проходят валидацию.
  Проверяются все, а не только активный: битый профиль находится до того, как
  кто-то на него переключится. Чинится это правкой в devkit, поэтому находка
  остаётся находкой и под `--fix`.

### Раскладка идёт по каждому включённому харнесу

Хуки, права, скиллы, определения агентов и глобальная точка правил
раскладываются не в `~/.claude`, а по путям профиля, и по разу на каждый харнес
из `enabled` (`~/.devkit/harness.local`, сужение проектным слоем
`.devkit/harness.local`). Пути берутся из четырёх ключей: `[hooks] config`,
`[delegate] agents_dir`, `[skills] dir` и `[rules] global_file`. У профиля
claude-code там стоят те же `~/.claude/...`, что раньше были константами, так
что на машине с одним включённым харнесом от переезда не изменилось ни файла.

Смысл переезда во второй подписке: она поднимается тем же клиентом с другим
каталогом конфигурации, включается в `enabled` наравне с первой и получает
полный комплект машинного хозяйства в своём каталоге. Иначе исполнитель на ней
работал бы без ядра правил, без рубежа символов, без прав неинтерактивного
режима и без скиллов, а заметно это стало бы по его текстам, а не сразу.

Каталог такого харнеса лежит в машинном слое, ключом `home` его секции, а
профиль ссылается на него плейсхолдером `{home}`:

```toml
enabled = ["claude-code", "glm-code"]

[glm-code]
home = "~/.devkit/claude-glm"
env = ["CLAUDE_CONFIG_DIR={home}"]
```

Профиль с `{home}` при отсутствующем машинном ключе это находка с готовой
строкой («вписать home в секцию `[glm-code]`»), а не раскладка наугад:
подставить нечего, и молча завести каталог с фигурными скобками в имени хуже,
чем отказать. Ведущий `~/` разворачивается и в `home`, и в путях профиля.

Два включённых харнеса просят один и тот же файл правил проекта, и это норма:
режим и строка импорта у них совпадают, генератор пишет обоим один и тот же
текст, второй проход застаёт файл уже совпавшим. Находка появляется там, где у
одного файла харнесы просят разного текста (разошлись `mode`, `import_line` или
глубина правил): такой файл генератор переписывал бы сам за собой на каждом
проходе, поэтому он не пишется вовсе, а находка называет обоих спорщиков и то,
чем они разошлись. Чинится это правкой профиля либо выключением лишнего харнеса.

Валидатор профилей живёт в `tools/devkitctl/harness.py` вместе с парсером
подмножества TOML. Парсер этот второй: тот же формат читает agentctl своим
кодом на Go (`tomllib` появился в python3.11, а devkitctl обещает голый
python3, тащить же в Go-утилиту первую внешнюю зависимость ради конфига из
строк и массивов не хочется). Расхождение двух реализаций ловится общими
фикстурами `kit/harness/testdata`: на каждый вход там лежит ожидаемый отчёт, и
сверяются с ним обе стороны. Отчёт по любому файлу печатается и руками, это
удобная точка для глаза:

```sh
python3 tools/devkitctl/harness.py kit/harness/claude-code.toml
```

`doctor --fix` доводит обвязку уже подключённого проекта и машины до актуальной:
после `git pull` devkit это способ забрать новые её части одной командой, без
ручного заведения файлов. Большинство правок additive: подключает отвязанные
git-хуки, заводит болванку `.devkit/deploy.local` и строку в `.gitignore`. Если
`deploy.local` уже есть, но заводился до появления очередного ключа (так
`test` не доехал до проектов, подключённых раньше DK-053), `--fix` дописывает
недостающие ключи в конец файла вместе с их комментарием: значения имеющихся
ключей, шапка и их порядок не трогаются, а дописанный ключ остаётся пустым,
поэтому находка про него никуда не девается и по-прежнему просит вписать
команду. Дальше он доводит бинари до версии чекаута тем, что на машине есть:
чекаут на релизном теге, значит ставит бинари этого релиза, иначе собирает тем
же `build` (в тот же каталог назначения, куда ставит `update`), кладёт рядом с ними обёртку
`devkitctl`, кладёт определения субагентов в `[delegate] agents_dir` и скиллы в
`[skills] dir`, дописывает недостающие права машинного контура в
`permissions.allow`. Определение или скилл,
разошедшийся с эталоном (устарел после правки в devkit либо кто-то поправил его
прямо на машине), `--fix` перекладывает: devkit источник правды, и правка
обязана доехать до спавна субагента сама, а не остаться находкой, которую надо
чинить руками на каждой машине. Перекладка не молчаливая, отчёт называет файл и что он разошёлся, так
что подправленное на машине видно в выводе, даже если его тут же перезаписали.
Той же меркой правится и глобальная точка правил, только генерится она заново
целиком, а не перекладывается копией файла: пропавшая заводится, устаревшая
перезаписывается, а руками правленная (нет маркера либо тело разошлось с его
хешем) остаётся находкой, как и рукописный `AGENTS.md`. Тем же порядком он
генерит и обновляет файлы правил проекта (раздел «Файлы правил»).
Заполненное иначе `--fix` не трогает (готовый `deploy=`, рукописный `AGENTS.md`
и правленый руками генерённый файл), а неоднозначное оставляет находкой: битый
импорт и ссылку правит человек, пустые `deploy=` и `test=` ждут команд проекта,
а Go ставится пакетным менеджером с ведома человека: тулчейн это не мелочь
вроде tmux, и тянуть его молча `--fix` не берётся. Неadditive правок
две, и обе называют себя в отчёте. Первая это переезд
снимка квоты: одиночный `~/.devkit/quota.local` `--fix` перекладывает в
`~/.devkit/quota/claude-code.local` (снять его было нечем, кроме панели Claude
Code), и в отчёте называет оба пути. Файл при этом не пропадает, а меняет место;
если по новому пути снимок уже лежит, старый остаётся нетронутым и попадает в
находки. Вторая это удаление вклейки правил, когда последний embed-инструмент
выключен, и удаляется только целый блок с совпавшим `body`. Собранный бинарь
может проиграть в PATH чужой копии, и это тоже находка, а не молчаливая
пересборка на каждом прогоне. Повторный прогон уже ничего не меняет.

`stats` собирает статистику по журналу запусков `.devkit/log`: выводит таблицу
с частотой каждой команды (утилита + субкоманда), долей ошибочных запусков
(код выхода != 0) и итоговой строкой. Битые строки в журнале молча пропускаются.
Разбивку объёма сессий печатает та же команда с `--context`, раздел ниже.

`watch` это сторожок цикла цели, разбор в разделе ниже: обычно его будит
launchd, а руками команда зовётся для проверки.

## Сторожок цикла цели

Цикл цели ведут двое, оболочка `goal-run` и сессия живого чата, и встают они
одинаково незаметно: зависший фон, обрыв соединения, убитая сессия. Изнутри
такой стоп не поймать, ждущая сессия жива и молчит, поэтому сторожок живёт вне
сессии и просыпается по расписанию.

```sh
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py watch
```

Целей под надзором он не выбирает, а читает: реестр `~/.devkit/goals` держит по
файлу на цель, и кладёт этот файл гейт бюджета `agentctl spend --goal`. Гейт
стоит в начале каждого витка и у оболочки, и в чате, так что второго механизма
регистрации не нужно, а замок `.devkit/goal-<ID>.lock` на эту роль не годится:
он есть только у оболочки. Запись знает цель, корень проекта, файл цели и время
последнего витка.

Движение цикла меряется журналом запусков `.devkit/log` проекта: строку туда
пишет каждая утилита devkit при каждом вызове, а виток без вызова утилит не
обходится (один только гейт бюджета оставляет строку не реже витка). Свежая
строка значит, что цикл идёт, и сторожок молчит. Сам он в этот журнал не пишет,
хотя команда и своя: строка раз в пять минут выглядела бы там движением на
вставшем цикле.

Простой дольше порога это громкий зов `hooks/notify.py` с названной целью и
временем простоя. Цель едет и ключом `--task`: по полю события лента дашборда
ведёт от вставшего цикла к строке цели (DK-323). Позвав, сторожок ставит в
запись отметку `stopped`: второй раз
по тому же стопу он молчит (баннер каждые пять минут никого не поднимет), а
движение свежее отметки её снимает, снимает её и гейт следующего витка.

Продолжение цикла сторожок не берёт на себя, а кладёт в текст зова готовую
команду (`python3 <чекаут>/kit/skills/goal-loop/goal-run.py <ID> -C <корень>`):
путь абсолютный, потому что в PATH оболочки нет, а копия, доехавшая на машину
каталогом скилла, не работает вторым входом. Поднимать цикл самому ему нечем. Стоп, доживший до порога простоя, оболочка
своими тремя попытками уже не пережила, и четвёртая из сторожка ничего не
меняет, а вставший цикл в живом чате оболочкой не продолжается вовсе: витки
ушли бы в tmux, и пользователь остался бы перед молчащим чатом, ровно та
слепота, из-за которой в скилле появился раздел «Цикл в чате». Ещё сторожок
работает и там, где цикла быть не должно (`autonomous` снят, цель на паузе), а
запускать по расписанию чужие сессии с деньгами квоты, не спросив человека,
дороже, чем один точный баннер.

Тем же тиком сторожок будит припаркованные вопросом задачи (LLD DK-400,
решение 2). Строка в Blocked с причиной «вопрос: ...» это ожидание человека:
лежащая строка-ответ во входе разговора задачи возвращает её в In progress тем же
`taskctl -C <корень> move <ID> in-progress`, каким парковали; move идёт с
`-m` и `--push`, потому что за будящим никого нет: правка доски коммитится и
пушится тем же тиком по правилу доски, а не висит грязной в чекауте. Вход ищется в
двух деревьях, основном и дерева задачи `../<проект>-<id>`: исполнитель
спрашивает из своего дерева, диспетчер из основного. Прежняя пара имён,
`.devkit/mail/task-<ID>.inbox`, читается наравне с новой
`.devkit/chat/task-<ID>.in` один выпуск (DK-440), чтобы ответ, написанный за
минуту до выката, разбудил задачу тем же тиком. Ответом задаче считается
только безадресная строка: адресованная сессии реплика («`..., сессии <ID>,
из дашборда: ...`») написана живому окну человека, и разбудить ею
припаркованную строку значило бы отправить в origin правку доски ни за чем
(LLD DK-430, решение 2). Адресата сторожок разбирает не своей копией формата, а
тем же импортом подхвата `hooks/chat-in.py`, каким читает срок ожидания;
лежащие адресные строки тик называет отдельной строкой отчёта, чтобы «ответ
написан, а строка стоит» не выглядело поломкой. Будит только «вопрос:»,
«окружение:» и проза ждут своего без реплик, а свежий признак ожидания `.ask`
у входа отдаёт его инструменту ожидания, и будить рано. Возврат строки это
повод решить заново, а не приказ работать: она становится кандидатом
планировщика на общих основаниях, сессию поверх доски сторожок не поднимает.
Бинарь taskctl ищется в PATH, а без него в каталогах установки релиза. Сам
PATH агент несёт в своём plist (ниже, DK-664), но запас на случай plist, ещё
не перевзведённого `--fix`, остаётся: без него припаркованная стояла бы до
ручного прогона. Второй такой отказ это несобравшийся импорт подхвата:
разбирать адресата своей копией формата сторожок не берётся, а будить не
разбирая значит гнать в origin правку доски по реплике, написанной чужой
сессии. Пробуждение по корню на этом тике не идёт вовсе, и тик говорит об этом
строкой «подхват реплики hooks/chat-in.py не загрузился», как говорит про
пропавший бинарь.

Цель, ушедшая из In progress или с доски вовсе, снимается с надзора вместе со
своей записью, а доску сторожок читает сам, а не через `taskctl show`: работать
он обязан и тогда, когда на машине сломано остальное, включая бинари devkit и их
место в PATH.

Порог простоя по умолчанию 45 минут. Виток режет работу вызовами утилит чаще,
чем раз в час, а порог короче десятка минут ловил бы долгую сборку или выкат.
Перебивается он строкой в `~/.devkit/watch.local`, а на разовый прогон флагом:

```sh
# порог на этой машине полтора часа
echo "idle = 90" > ~/.devkit/watch.local
```

Носитель расписания на macOS это launchd-агент `ru.devkit.goal-watch`, его
кладёт и поднимает `doctor --fix`, а показывает он на основной чекаут devkit.
Просыпается агент раз в пять минут: порог решает, когда звать, а агенту довольно
просыпаться чаще любого порога. Каждый прогон пишет строку в
`~/.devkit/goal-watch.log`, и по её свежести доктор говорит, работает ли сам
сторожок: агент поднят, а следа три интервала нет, значит находка. На других
платформах носителя пока нет, и доктор говорит об этом находкой, когда под
надзором есть хоть одна цель: там команду ставят в своё расписание (cron,
systemd) руками.

Агент несёт в `EnvironmentVariables` собранный PATH. Сборщик тот же, что у
launchd-агента дашборда, `dashboard.agent_path`, и якорь тот же, бинарь
dashboard из PATH. Якорь taskctl тесты, заводящие свой стенд доски,
подделывают в PATH проекта. С таким якорем PATH сторожка разъезжался бы от
прогона к прогону. Первым в PATH идёт каталог бинаря dashboard, следом
системные пути launchd, брю-каталоги и `~/.local/bin` с машины.

Без этого PATH launchd даёт агенту голый системный путь. Дети тика (taskctl,
shipctl, dashboard, agentctl) не находят себя. Сторожок крутится вхолостую и
циклически пишет в журнал «taskctl не найден» вместо отчёта разлива (DK-664).

Агент без такого PATH это находка, как и агент вовсе без
`EnvironmentVariables`. `--fix` переписывает его тем же правилом, что агента,
показывающего не на тот чекаут. Бинаря dashboard нет в PATH ни на машине,
собирать PATH агента тогда неоткуда. Класть агент `--fix` не берётся, вместо
этого находка зовёт `devkitctl update` или `build`.

### Страховка брошенного ожидания

Вопрос человеку задаёт инструмент `taskctl ask`, и он же паркует задачу, не
дождавшись ответа. Харнес может убить его ход сигналом `SIGKILL`, который не
перехватывается ничем: признак ожидания остаётся лежать со своим сроком, а
шага с парковкой не случается, и строка молча стоит в In progress до конца
времён. На этот случай парковка получает второго исполнителя.

Корни на этот обход берутся из двух мест. Реестр целей `~/.devkit/goals` знает
только корни живых циклов, а вопрос человеку задают и по задаче, взятой мимо
цикла, поэтому вторым источником идут записи этапов `~/.devkit/runs/*.run`:
поле `root` в них это уже основной чекаут, а кладёт запись каждый вердикт
`agentctl pick` и каждый вопрос `taskctl ask`. Корень без доски пропускается:
запись пережила сам проект. Тем же расширенным обходом идёт и пробуждение
ответом, так что припаркованную вопросом строку будит ответ и у задачи без
цели.

Тем же тиком сторожок смотрит строки In progress: протухший признак
`.devkit/chat/task-<ID>.ask` в основном чекауте или в дереве задачи значит
брошенное ожидание. Причина парковки берётся из того же признака, где вопрос
лежит текстом, а доска коммитится и пушится тем же `move ... -m ... --push`,
каким она пушится при пробуждении.

Реестр чатов `~/.devkit/sessions.log` решает вопрос живости (LLD DK-430,
решение 1): запись называет сессию, ведущую задачу, и хранит путь её
транскрипта готовым полем, а свежесть транскрипта меряется тем же порогом в
двенадцать минут, что на экране дашборда. При живой сессии страховка молчит
и говорит об этом строкой отчёта: убитый ход ожидания не значит убитой
сессии, окно человека работает дальше, и парковка встала бы у него под
руками. Занятость из
`internal/works` тут не годится вовсе: она считает занятой задачу с tmux-сессией
`task-<ID>`, а работа из окна человека мимо этой формулы проходит целиком.

Парковка идёт тем же `move ... --push`, и хвост её иногда спотыкается: доска
переписана и закоммичена, а `git push` отбит (нет origin, чужой ref впереди).
Признак ожидания снимается и в этом случае, иначе он лежал бы вечно, а
неуехавшая доска называется отдельной строкой отчёта: чинит её человек;
следующий тик к этой строке не возвращается. Отказ до правки доски (потолок
висящих вопросов) читается иначе: строка осталась в In progress, признак на
месте, и следующий тик повторит.

### Закрытие агентской задачи из Check

Задачу вида приёмки agent агент по правилам прогоняет и закрывает сам. Сессия
кончается раньше закрытия чаще, чем доживает до него. Прогнанная строка тогда
стоит в Check до следующей живой сессии, и человек утром видит вставший
конвейер там, где делать ему нечего. Тем же тиком сторожок доводит такую
строку до Done.

Кого закрывать, отвечает `taskctl closable`. Своего разбора доски тик не
держит. Вид приёмки, форма файла задачи и рубеж непустого раздела «Проверка»
живут у taskctl, а вторая копия этих правил в питоне разошлась бы с первой на
первой же правке. Разошедшаяся копия закрывает чужую строку и пушит это в
origin.

Готовой команда называет строку Check с четырьмя сошедшимися условиями. Вид
приёмки agent. Погашенный провал. Действующая на последний выкат отметка
«smoke прогнан». Непустой раздел «Проверка» с выводом прогона. Остальные
строки идут ниже, под «отказано:», и каждой названа своя причина.

```sh
taskctl -C ~/projects/myproj closable
```

Закрытие идёт `taskctl -C <корень> close <ID> -m ... --push`. Так же паркует
строку страховка ожидания, своим `move`. За тиком никого нет, а грязная правка
доски в основном чекауте отбила бы следующий `merge` предполётом. Без бинаря
taskctl тик молчит и не трогает ничего: спросить вердикт нечем. Спотыкающийся
хвост читается тут как у парковки. Строка ушла из Check, а `git push` отбит.
Закрытие состоялось, и неуехавшую доску отчёт называет отдельной строкой.

Громкого зова на закрытие нет намеренно. Смысл этой работы в том, чтобы
человека не дёргать, а закрытая задача не повод подойти к машине. Виден тик
журналом `~/.devkit/goal-watch.log`, строкой «задача DK-516 в ... закрыта
тиком», и уходом строки в Done. Кого закроет тик, а кто ждёт человека, `shipctl
status` называет заранее.

### Разлив поезда тем же тиком

Тем же тиком сторожок льёт поезд (LLD DK-306, решение 4). По каждому корню
обоих обходов он зовёт разлив `shipctl -C <корень> ship --drain`. Поезд,
оставшийся без получателя события «очередь освободилась», доезжает до прода
сам и не ждёт ручного ship. Такое случается после перезагрузки и после
падения всех сессий.

Разлив идемпотентен. Пустой поезд, занятая очередь, сломанный прод и занятый
чужим заходом конвейер выходят нулём со строкой «разлив не нужен». Эта
строка идёт только в отчёт тика, а в журнал сторожка попадает значимое,
выкат или провал. Провал вызова не поднимает код выхода тика и не глушит
остальные корни. Уведомлением сторожок себя не дублирует: на провал деплоя
его шлёт shipctl через признак провала и `taskctl fail`, один раз. Бинарь
shipctl ищется в PATH, а без него в каталогах установки релиза, как taskctl
пробуждения. launchd даёт агенту системный PATH. Корень без доски
пропускается молча, разливать там нечего.

```sh
# тот же вызов, что делает тик по каждому корню, руками
shipctl -C ~/projects/myproj ship --drain
```

### Подъём прогона сценария тем же тиком

Строка, выкаченная без человека в окне, получает сессию проверяющего сама
(DK-718). Первым поднимает прогон сам выкат, а тик страхует то, что проехало
мимо: подъём, который не вышел, пачку с закрывшимся раньше времени
диспетчером и строки, ушедшие в Check ещё до появления самого подъёма. По
каждому корню с непустой секцией Check тик зовёт `dashboard check -C <корень>`,
одним вызовом на корень.

Кому прогон нужен и кому его не отдавать, решает дашборд. Автономия проекта,
вид приёмки, отметка smoke и исполнитель разработки живут у утилит, и
вторая копия этих правил разошлась бы с первой на первой же правке (разбор в
`tools/dashboard/README.md`, раздел «Подъём прогона после выката»). Пустая
секция Check не зовёт дашборд вовсе, а «подъём не нужен» идёт только в отчёт
тика. Тем же отказом кончается вопрос по проекту с выкатом за пользователем
(`autonomous = false`): сессию поверх его строк тик не поднимает. В журнал сторожка попадает поднятый прогон и отказ. Без бинаря дашборда
тик говорит об этом строкой. Неподнятый прогон это стоящая очередь выката.

```sh
# тот же вызов, что делает тик, руками
dashboard check -C ~/projects/myproj
```

Это единственное место, где сторожок поднимает сессию поверх доски. Цикл цели
он не поднимает и после стопа, а зовёт человека готовой командой; разбуженную
строку возвращает в кандидаты планировщика и на этом останавливается.

Тем же тиком свежеет снимок квоты обеих подписок (DK-633). Тик зовёт
`agentctl quota refresh --all --if-stale`, и протухший снимок переснимается
даже там, где не идёт ни одной сессии, а дашборд выключен. Перечень подписок,
порог свежести и замок живут в agentctl, тик его только запускает. Съём, отказ
и оставленный исход («оставлено» в счёте: панель не далась либо сторож отката
удержал цифры, переснимет следующий тик) видны строкой со счётом исходов в
журнале сторожка. Разбор по харнесам целиком идёт в отчёт тика, а свежие
снимки журнал не трогают.

## Куда ушёл объём сессии

У `stats` второй источник данных, журналы сессий харнеса
(`~/.claude/projects/<слепок пути проекта>/*.jsonl`). Журнал запусков знает
только, какие команды звали; расход контекста лежит в `message.usage` записей
ассистента, и разбирает его `stats --context`.

```sh
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py stats --context -C ~/projects/myproj
```

Печатается разбивка: старт (префикс первого запроса каждого потока) против
истории (всё, что дописалось дальше: переписка, результаты тулов, тела скиллов),
рядом повторное чтение префикса, дальше перезаписи префикса с их ценой и топ
тулов по объёму результатов. Объём тулов считается в символах, а не в токенах:
это код и вывод команд, а коэффициент 2,45 снят с русской прозы правил и на них
соврал бы.

Считается по потокам, а не по сессиям: журнал одной сессии бьётся на несколько
файлов (рядом с `<id>.jsonl` лежит `<id>/subagents/` с потоками субагентов), и у
каждого потока свой префикс. Запись с `usage` повторяется по числу итераций
ответа, поэтому запросы склеиваются по `requestId`; без склейки объём вырос бы в
разы. Сессия может идти на нескольких моделях, они перечисляются шапкой с числом
запросов на каждую.

Правило подписи перезаписи. Штатное дописывание в хвост оставляет прочитанный
префикс на месте: чтение кеша от запроса к запросу растёт, а запись держится на
объёме прироста. Перезаписью считается запрос, у которого сошлись оба признака:
чтение кеша просело относительно предыдущего запроса того же потока и записано
больше, чем прочитано (`cache_creation > cache_read`). Порога в токенах тут нет
намеренно, оба признака относительные, и правило не надо перенастраивать под
длину сессии или модель. Первый запрос потока это старт, он пишет префикс с нуля
и идёт отдельной строкой, а не нарушением.

Число перезаписей это сторож запрета из [дизайна дерева
контекста](../../docs/lld/DK-100-context-tree.md): механизма, который правит голову
контекста по ходу, devkit себе не заводит, и всплеск перезаписей после правки
devkit виден цифрой, а не догадкой. Часть перезаписей приходит не от devkit, а
от истечения TTL кеша на паузе в работе, поэтому смотрят на сдвиг числа между
периодами, а не на нулевой итог.

## Куда уходит вывод инструментов

`drain` это второй замер по тем же журналам сессий, отвечает на другой вопрос:
не куда ушёл объём старта против истории, а куда село вывода по инструментам и
командам. Превращает разовый скрипт `tstats.py` из DK-148 в регулярную команду
и гоняется как по слепку пути текущего проекта, так и по всему корпусу:

```sh
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py drain -C ~/projects/myproj
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py drain --all
```

Печатается вызовы и объём вывода по инструментам с медианой, p90 и максимумом,
разбор Bash по головной команде конвейера (объём вызова висит на головной,
иначе «git log | head» задвоил бы счёт), sed отдельно по правке файла против
чтения фрагмента `-n Np` против фильтра в конвейере, чтения файлом целиком
против куска через `limit`/`offset`, повторные чтения одного файла внутри
сессии, перцентили размера одного вывода и хвост самых жирных, отказы
разрешений. Привязка результата к вызову идёт по `tool_use_id`, объём вывода
приклеивается к головной команде и инструменту.

Разбор jsonl общий со `stats --context`: модуль `sessions.py` читает записи и
сопоставляет `tool_use` с `tool_result`, второй парсер тех же журналов рядом не
заводится. Токены по usage суммируются как в разовом скрипте, без склейки по
`requestId`: замер повторяет цифры прототипа, а не исправляет их, и
инструментально-командные доли (которые и ведут рубёжи DK-146 и DK-147) от
склейки не зависят.

## Вес резидента

Резидент это текст, который едет в каждый запрос сессии: цепочка файлов правил,
описания определений `kit/agents/` и скиллов. Растёт он монотонно, и заметить это
можно только специально, поэтому вес меряется двумя способами сразу. Расчёт
считает символы по карманам и переводит их в токены коэффициентом 2,45 из
[дизайна дерева контекста](../../docs/lld/DK-100-context-tree.md); он бесплатный, и
его порогом дальше живёт `doctor` (DK-029). Замер спрашивает цену у самого
харнеса и говорит, чему в расчёте верить.

```sh
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py weigh -C ~/projects/myproj
```

`weigh` гоняет два headless-прогона `claude -p` с одинаковым тривиальным
запросом и `--output-format json`. Полный вход прогона это `input_tokens` плюс
запись и чтение кеша (резидент лежит в кешируемом префиксе, и одного
`input_tokens` мало). Базовый прогон идёт без раскладки devkit, целевой с ней, а
разница это цена текста devkit в токенах.

Пол замера (системный промпт харнеса и схемы тулов) зависит от машины:
подключённые MCP-серверы приносят свои схемы. Прогон под пустым `HOME` мерил бы
не ту машину, поэтому оба прогона идут под слепком `~/.claude` во временной
директории, и отличается он ровно раскладкой devkit: глобальной точкой правил,
определениями агентов и скиллами. В слепок не едут транскрипты сессий, история и
прочее тяжёлое, чего в запросе нет; хуки из `settings.json` снимаются, чтобы
замер под подменённым `HOME` ничего на машине не трогал. Целевой прогон идёт не
в самом чекауте, а в директории замера с той же раскладкой правил (`AGENTS.md`
проекта, файлы правил и тонкий файл харнеса): чекаут принёс бы в контекст ещё и
git-статус с листингом файлов, которых у базового прогона нет, и разница вобрала
бы их. Файлы правил кладутся рядом с тонким файлом, и зовёт он их голым именем:
импорт за пределы рабочей директории клиент не разворачивает и молчит об этом,
так что правила до прогона просто не доезжают, а замер выходит занижен ровно на
их вес. Отличие от боевого тонкого файла остаётся только в длине строки импорта
(`@RULES.board.md` против `@.devkit/devkit/RULES.board.md` у проекта с соседним
devkit).

Авторизация клиента в слепок не копируется, но и не теряется. На macOS она
лежит в связке ключей, а ищет её клиент от `HOME` (`~/Library/Keychains`), и
слепок без этого каталога встречает прогон ответом «Not logged in». Каталог
кладётся симлинком на настоящий. На платформах, где такого каталога нет, слепок
остаётся прежним.

Симлинк это единственное место, где слепок смотрит на живой файл машины, и риск
названный: освежая истекающий токен, клиент запишет его в настоящую связку, а не
в одноразовую копию. Копия связки в слепке работает (в той же login-сессии она
открывается и вход из неё читается), но берётся симлинк. Копия положила бы на
диск второй экземпляр всех секретов пользователя, а не только входа в Claude, и
освежённый токен из неё уехал бы в мусор вместе с временной директорией, тогда
как через симлинк освежение доезжает туда же, куда доезжает от обычного запуска
`claude`. Записать на машину замер может ровно это и ровно руками клиента;
раскладку devkit и хуки он не трогает.

Вход гуляет от прогона к прогону, поэтому пар прогонов несколько (`--runs`, по
умолчанию три), а рядом с замером печатается разброс. Точнее разброса замер не
знает, и читать его точнее нельзя. Печатается пара за парой, потом сам замер,
таблица карманов в символах и токенах, коэффициент этого прогона и расхождение
расчёта с замером. Расхождение в проценты это нормально: два способа дизайна
разошлись на 2,5%.

Код возврата 1, когда замер выше потолка резидента (`--limit`, по умолчанию 6 500
токенов из бюджета дизайна), и тогда замер годится шагом сценария проверки, а не
только для чтения глазами. Отдельный код 2 у отказа мерить, и поводов у него
два. Первый это несвежая раскладка на машине: кладёт её `doctor --fix`, а выкат
devkit пересобирает только бинари утилит, так что по вчерашней раскладке замер
соврал бы молча. Перед прогонами `weigh` гоняет те проверки доктора, которые за
раскладку и отвечают (определения агентов, скиллы, файлы правил проекта), и при
находках печатает их и не меряет. Остальной машинный контур (снимок квоты,
tmux) на вес резидента не влияет и мерить не мешает. Второй повод это сорванный
прогон: нет `claude` в PATH, клиент вышел с ошибкой, в ответе нет `usage`.

Команда отдельная, а не флаг `doctor`, потому что прогон стоит денег, требует
`claude` в PATH и сети и занимает минуты, а доктора гоняют в каждой сессии.
Расчёт по карманам живёт функцией `weigh.pockets` отдельно от прогонов: порог
резидента в докторе считается ею же, чтобы обе цифры брались из одного места.
Самопроверка живого клиента не поднимает, вместо него в PATH ложится скрипт,
который отдаёт usage по той раскладке, какую видит.

### Порог в doctor

`doctor` печатает ту же таблицу карманов без единого запроса к сети: расчёт по
символам бесплатный, и в каждой сессии его можно себе позволить. Порогов три,
из бюджета дизайна DK-100, а не из сегодняшнего веса: ядро (`RULES.core.md`)
не длиннее 5 500 символов, ядро доски (`RULES.board.core.md`) не длиннее
1 500, а сумма по всем карманам не выше 6 500 токенов (коэффициент тот же,
2,45 символа на токен). Превышение любого из трёх это отдельная находка,
которая называет карман, его вес в символах и в токенах, порог и разбивку по
всем карманам целиком, чтобы сразу было видно, что именно распухло.

Второй порог на тело каждого скилла в `kit/skills/*/SKILL.md`: тело не резидентно,
но платится записью в контекст в момент вызова, и разбухший скилл это та же
болезнь роста в другом месте. Порог 16 000 символов текста без шапки
frontmatter; превышение это находка с предложением резать скилл надвое.
Меряется тело той же меркой, что и резидент: 16 000 символов это потолок
резидента (6 500 токенов по 2,45 символа, 15 925) с округлением вверх до сотен.
Смысл равенства такой: один вызов скилла стоит сессии не дороже, чем весь
резидент devkit, который она платит безусловно и до всякой работы. Выше этой
черты тело перестаёт быть процедурой и становится второй раскладкой правил, а
вызов уже не дешевле чтения полного текста, ради которого скиллы и заводились
(`RULES.board.md` это 18 тысяч символов). От сегодняшних тел порог не считается
вовсе: DK-029 брала запас в треть над самым толстым скиллом, и такая мерка
объясняет только то, что уже написано.

Оба порога проверяются только в самом чекауте devkit (`root` совпадает с
`DEVKIT`), не в каждом подключённом проекте: карманы резидента и тела скиллов
общие для всех проектов devkit, находка про них не проектная, и в
подключённом проекте её некому чинить.

Проекту достаётся свой порог, на проектную часть резидента: `AGENTS.md` проекта
плюс тонкий файл харнеса, 6 000 символов на двоих (DK-190). Проектная часть это
указатели на долгоживущую доку, а не сама дока, и тяжелее ядра правил
(`RULES.core.md`, сегодня 4 715 символов) ей быть незачем; 6 000 это ядро с
запасом. Взят порог по фактическим весам живых проектов, а не из головы: с
тонкой раскладкой они укладываются с запасом (goonies 768 символов, authn 2 356,
idp-project 3 851), а рукописные `CLAUDE.md`, оставшиеся от подключения до
переезда на `AGENTS.md`, нет (xr-proxy 14 357, it-road-course 48 889, то есть
20 тысяч токенов в каждом запросе сессии). Текст вклейки правил в `AGENTS.md`
считается отдельным карманом и в проектный порог не идёт: писал его генератор, и
сокращать его проекту нечего.

Логика находок (`weigh.evaluate_residency`, `weigh.evaluate_project_residency`,
`weigh.evaluate_skill_body`) отделена от чтения дисков (`weigh.pockets`,
`weigh.skill_body_chars`), поэтому пороги проверяются юнитами без файловой
системы, а стык с диском и с `doctor` отдельными интеграционными тестами
(`tools/devkitctl/weigh_test.py`).

## Самопроверка

Тесты лежат рядом с кодом, каждый модуль своим `<модуль>_test.py`; общий
стенд (копия devkit во временной директории, подставные HOME и PATH) в
`testenv.py`.

Прогон всех компонентов репозитория сразу (go-утилиты, hooks, сюита devkitctl,
скиллы, doctor) это `parallel.py` из корня чекаута:

```sh
python3 tools/devkitctl/parallel.py
```

Го-компоненты раннер находит сам, по факту `go.mod` в подкаталогах `tools/`
(`parallel.go_tools`), а не по хранёному списку: раньше список правился руками
и молча разошёлся с деревом, потеряв модуль (находка DK-367). Каждый
го-компонент это отдельный модуль, гоняется в своём каталоге и не нуждается в
общем `go.work` на корне репозитория: в корне devkit его нет и не будет, `go
test ./...` из toplevel там падает по конструкции, раннер и regcheck (флаг
`-C`, `tools/regcheck/README.md`) обходят это своим каталогом на модуль.

Раннер гонит компоненты одновременно с потолком воркеров: последовательная
цепочка держала сумму компонентов, а они независимы, и стена сходится к самому
тяжёлому звену. Go остаётся с `-count=1`, кэш сборки не чистится. Первый
провал валит прогон: занятые компоненты убиваются по группе процессов,
код возврата ненулевой, а вывод провалившегося печатается целиком. Ключ `test`
гитигнорнутого `.devkit/deploy.local` самого devkit зовёт раннер строкой
`export GOWORK=off; python3 tools/devkitctl/parallel.py` (префикс GOWORK=off
пришёл из находки про чужой go.work, DK-115). Свои тесты у раннера в
`parallel_test.py`, на синтетическом каталоге с короткими скриптами: живые
компоненты для проверки раннера тяжёлые.

Сюита одного devkitctl:

```sh
cd tools/devkitctl && python3 suite.py
```

Раннер `suite.py` гонит тестовые классы отдельными процессами с потолком
воркеров (по умолчанию до двенадцати, ключ `-j`): последовательный discover держит минуты,
а тяжёлый хвост не режется прогонами по модулям, когда один devkitctl_test
занимает больше всей остальной сюиты. Класс это единица параллели неслучайно:
стенд с копией devkit заводится на класс, и классы одного модуля расходятся по
воркерам, не мешая ни друг другу, ни чужим модулям. Счёт тестов раннер
сверяет с последовательным discover и краснеет на расхождении: потерянный
тест это находка прогона, а не молчание, а провалившийся класс печатается
выводом целиком, с трейсбеком. Тот же discover остаётся рабочим способом
прогона, `--list` называет перечень классов. Свои тесты у раннера в
`suite_test.py`, на синтетическом каталоге с короткими модулями: живая сюита
для проверки раннера слишком тяжела.

Стенд держит два рубежа, и оба про то, чтобы прогон не зависел от машины, на
которой запущен.

Настоящий HOME тестам не виден: `testenv` подменяет его пустой директорией на
весь процесс. Инструмент читает раскладку машины через `expanduser`, и тест,
забывший подставить свой HOME (`home=` у `run`, `fake_home` у вызова модуля
прямо в процессе), мерил бы `~/.claude` того, кто запустил прогон: у одного
зелено, у другого красно, и увидеть это можно только у второго. С пустым HOME
такой тест краснеет сразу и у всех. Единственное, за чем стенд ходит в
настоящий HOME, это пути кеша сборки go (`go_cache_env`), иначе сборка бинарей
для прогона `shipctl start` каждый раз компилировала бы стандартную библиотеку
заново.

Копия devkit заводится одна на класс (заводить её на каждый тест дорого), и
за то, что тест вернул её в исходное состояние, отвечает не обещание в
комментарии: `SandboxCase` сверяет слепок копии по содержимому до и после
каждого теста. Невосстановленная правка называется на том тесте, который её
оставил, а не всплывает через полчаса в соседнем. Класс, где шаги нарочно
стоят друг на друге (цепочка вклейки правил), объявляет это полем
`CHAIN = True` и за состояние отвечает сам; дальше класса оно всё равно не
течёт, копия у каждого класса своя.

### Чего стоит исполнение заглушек

Первый запуск свежего скрипта на macOS платит проверку подписи кода (AMFI):
около трети секунды на файл, повторный запуск того же файла уже почти ничего.
Стенд кладёт десяток заглушек бинарей отдельными файлами, и первый доктор
класса собирал эти доли в секунды, а тяжёлые классы с пересборками копили
минуты по всей сюите.

Поэтому заглушки бинарей лежат симлинками на один диспетчер: скрипт с разбором
своего имени (`case "$0"`), каждое имя отвечает строкой `--version` копии
devkit. Диспетчер прогревается холостым запуском при создании стенда, и
симлинки на него исполняются уже без проверки: дюжина заглушек стоит десятки
миллисекунд вместо секунд. Разбор идёт по `$0`, а не по `basename`, потому что
подставной PATH стенда короткий и `basename` в нём нет. Заглушки, чьё тело
это целый скрипт (заглушка go, пакетного менеджера, обёртка devkitctl, taskctl
с доской), остаются отдельными файлами: их запускают считанные разы за прогон,
и выручка диспетчера тут копеечная.

Вторая статья той же природы сидела в локальном сервере релизов
(`update_test`): `serve_forever` опрашивает сокет с интервалом в полсекунды, и
`shutdown` в tearDown каждого из полусотни тестов ждал конца этого цикла
опроса. Явный `poll_interval=0.02` съел полсекунды на тест: сервер тестовой
нагрузкой не загружен, и частый опрос ему ничего не стоит.

Третья статья повторных поездок в git закрыта кешем чтений в `update.git`:
один прогон доктора спрашивает режим чекаута, теги и коммиты по многу раз
(сводка, проверка бинарей, находка про релиз), и каждый вопрос это свой
процесс git. Пока кеш включён (`update.git_cache(True)` в `main`, на прогон
команды), ответы чтений сидят в памяти, а любая меняющая команда его чистит:
fetch и checkout меняют репозиторий, и теги после fetch читаются заново. По
умолчанию кеш выключен: прямые вызовы из тестов ходят в git между
собственными мутациями мимо этого шлюза, и обязанность включать лежит на
команде, у которой повторы внутри.
