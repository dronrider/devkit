# regcheck: краснота регрессионного теста

Механизация правила из RULES.md («Тесты обязательны»): регрессионный тест
должен падать на старом коде и проходить на исправленном, иначе он не ловит
регрессию и покрытием не считается. Проверять это руками (временно вернуть
баг, прогнать, откатить) долго и никто не проверяет; утилита делает то же
самое без единой правки рабочего дерева.

Как устроена проверка:

1. команда теста гоняется в рабочем дереве, обязана пройти;
2. в временный `git worktree` выкладывается старый код (база), поверх него
   из рабочего дерева переносятся только тестовые файлы;
3. команда гоняется там и обязана упасть; worktree убирается в любом исходе.

Ставится в PATH релизом devkit, как taskctl:

```
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py update
```

## Запуск

```
regcheck [-C dir] [--base ref] [--tests f1,f2] [--inline f1,f2] -- <команда теста ...>
```

Типовые случаи:

```
# правка и тест ещё не закоммичены: база выбирается сама (HEAD)
regcheck -- go test ./... -run TestBoardMove

# правка закоммичена на фичеветке: старый код живёт в main
regcheck --base main -- python3 -m pytest tests/test_ops.py
```

Команда теста гоняется в `-C dir` (по умолчанию текущая директория), а не
всегда в корне репозитория: в репозитории без корневого модуля, где
go-утилиты лежат каждая в своём подкаталоге со своим `go.mod` (как devkit,
`tools/<утилита>`), `go test ./...` из корня падает («directory prefix .
does not contain modules», DK-367), потому что корень сам не модуль. Поставить
`-C` на каталог конкретного модуля решает это без общего `go.work`: модуль
самодостаточен и второй прогон (на старом коде) гоняется в том же
относительном месте внутри временного worktree.

```
# devkit: правка и тест в tools/taskctl, общего go.work в корне нет
regcheck -C tools/taskctl -- go test ./... -run TestBoardMove
```

Тестовые файлы ищутся сами среди изменённых относительно базы (`*_test.*`,
`test_*`, `*.spec.*`, каталоги `tests/`, `testdata/` и подобные); если
автопоиск промахнулся, файлы перечисляются флагом `--tests` через запятую.

Выход 0 значит регрессия закрыта. Выход 1 с объяснением: тест красный на
текущем коде (сначала чинить), тест зелёный на старом (не ловит регрессию)
или тестов относительно базы не нашлось. Отдельная причина: база с тестами не
собралась или команда на ней не запустилась, тогда краснота не доказана,
разбор в разделе про сборку базы ниже.

## Инлайновые тесты (правка и тест в одном файле)

Когда тест живёт в том же файле, что и правка (инлайновые тесты Rust
`#[cfg(test)] mod tests { ... }` и подобное), файл целиком на старый код не
перенести: он утащит с собой и исправление. Такие файлы перечисляются флагом
`--inline` через запятую, на базу переносится не файл целиком, а только его
тестовая часть, остальное остаётся базовым (возможно, багованным):

```
regcheck --inline src/lib.rs -- cargo test
```

Границы тестовой части ищутся автоматически: сначала явные маркеры
`regcheck:test-begin` / `regcheck:test-end` (комментарий любого синтаксиса,
работают для любого языка), если их нет, то единственный блок Rust
`#[cfg(test)] mod ... { ... }` по совпадению фигурных скобок. Если в базовой
версии тестовой части ещё не было (тест целиком новый), она просто
дописывается в конец базового файла; если тестовая часть уже была, новая
заменяет её целиком.

Найти тестовую часть однозначно получается не всегда, и тут инструмент не гадает, а
падает с объяснением: несколько блоков `#[cfg(test)]` в файле, маркер без
пары или оба маркера на одной строке, несбалансированные скобки (эвристика
не разбирает строки и комментарии, поэтому фигурная скобка внутри строкового
литерала её собьёт), «mod» не в поддерживаемой форме сразу после атрибута.
Во всех этих случаях нужны явные маркеры `regcheck:test-begin`/
`regcheck:test-end` вокруг тестовой части. Файл без тестовой части вообще
(ни маркеров, ни `#[cfg(test)]`) через `--inline` не проверить: отделить
тест от правки нечем.

Файл, который одновременно подходит под `--inline` и под обычный список
тестовых файлов (автопоиском или явным `--tests`), из списка тестовых файлов
исключается: иначе он сначала копируется на базу целиком, правка утекает
вместе с ним, и дальше проверка врёт про результат. `--inline` в таком
пересечении главнее.

## Когда база с тестами не собирается

Новый тест часто зовёт то, чего в базе ещё нет: новую функцию, новый импорт,
функцию с другой арностью. Тестовая часть, дописанная в конец базового
файла, или тест, перенесённый целиком флагом `--tests`, тогда роняют сборку
базы. Код выхода у такого прогона ненулевой, как и у пойманной регрессии, и
краснотой он не считается. Утилита завершается с ошибкой, печатает причину и
выводит рядом выжимку вывода второго прогона.

```
ошибка: база main с перенесёнными тестами не собралась, краснота ничего не доказывает: тест зовёт то, чего в базе ещё нет (новая функция, импорт, другая арность). Выходы: тест без новых символов либо запись в файле задачи, что regcheck здесь не применим
error[E0425]: cannot find function `helper` in this scope
error: could not compile `probe` (lib test) due to 1 previous error
path: /home/me/proj/.devkit/cmdout/20260916T121108-test-old/out
```

Исход второго прогона судится по ошибке запуска и по выводу. Команда, которую
exec не нашёл или не смог запустить, даёт отказ «не запустилась». Файл
команды должен быть и в базе, либо лежать в PATH. Следы сборки ищутся у любой
команды. Это `error: could not compile` и `error[E` у cargo, `[build failed]`
и `[setup failed]` у go test. Признак упавшего теста известен у `cargo test`
(`test result: FAILED`) и у `go test` (`--- FAIL:`). Ненулевой код без него у
этих двух раннеров тоже не засчитывается. Так падает cargo без манифеста или
go test с неизвестным флагом, и отказ тут «краснота не доказана». У остальных
команд (pytest, npm, sh) признаков нет, и ненулевой код без следов сборки
засчитывается краснотой, как раньше. Следы сборки старше признака упавшего
теста. `go test ./...` с несколькими пакетами печатает оба рядом.

Выхода из отказа два. Тест переписывается без новых символов, чтобы база с
ним собиралась. Либо в файле задачи пишется, что regcheck здесь не применим,
и краснота проверяется руками по скиллу `test-standard`.

Каждый прогон оставляет строку в журнале `.devkit/log` репозитория (время,
код выхода), когда директория `.devkit` заведена: по этому журналу
`shipctl merge` подсказывает при слиянии bug-задачи без зелёного прогона.

## Где regcheck не достаёт

Утилита доказывает красноту там, где есть старый код с багом. У новой
функциональности его нет, и правило «тест обязан ловить поломку» держится
только на исполнителе. Замена ручная: прогнать по свежей правке типовые
мутации и убедиться, что на каждой падает хоть один тест. Мутация, которую
никто не поймал, значит поведение не покрыто, а тест тавтологичен.

Что мутировать, видно по замечаниям ревью самого devkit, где непойманная
поломка это самая частая находка. Реально переживали зелёные тесты вот такие
подмены:

- ранний выход вместо работы (`return None` в начале функции): тест звал код
  так, что до проверяемой ветки дело не доходило;
- сравнение путей строкой вместо `realpath`: подмену тест не отличал;
- растянутая граница, где сутки превращаются в тысячу суток: порог никто не
  проверял;
- фикстура, собранная из головы: живого экрана, на котором признак обязан
  отказать, в наборе не было, и тест оставался зелёным при настоящем дефекте;
- ожидание, посчитанное тем же кодом, который проверяется, и фикстура, где
  порядок вставки случайно совпал с ожидаемым: сортировку можно было убрать
  совсем.

## Ограничения

- Worktree это чистая копия базы: тест, которому нужны несобранные артефакты
  или зависимости из рабочего дерева (`node_modules` и подобное), в нём
  упадёт не из-за бага. Такой тест сначала сделать самодостаточным.
