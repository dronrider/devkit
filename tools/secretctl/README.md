# secretctl: имена агенту, значение в подпроцесс

Утилита цели [DK-207](../../docs/tasks/archive/2026/DK-207.md): исключить попадание секретов в
контекст модели. Принцип цели переворачивает работу с секретом: модель видит
имена, а значение в момент исполнения подставляет утилита. Образец для неё
`token_env` и `token_file` у trackctl (`tools/trackctl/contour.go:171-187`), где
токен уходит в HTTP-вызов, не показывая значение агенту, а ошибка называет имя
переменной, но не значение (`contour.go:176`).

## Первый запуск

Утилита ставится в PATH релизом devkit, как остальные:

```
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py update
```

Команды записи у неё нет, секрет кладёт в хранилище оператор. На машине без
Keychain (и всегда, когда бэкенд назван явно) это файл с правами 0600 в
директории хранилища `~/.devkit/secrets/`, имя файла равно имени секрета:

```
$ mkdir -p ~/.devkit/secrets
$ printf 'sk-ant-demo-0123456789' > ~/.devkit/secrets/DEMO_TOKEN
$ chmod 600 ~/.devkit/secrets/DEMO_TOKEN
```

Дальше секрет виден по имени и подставляется в подпроцесс:

```
$ SECRETCTL_BACKEND=file secretctl names
DEMO_TOKEN
$ SECRETCTL_BACKEND=file secretctl exec DEMO_TOKEN -- sh -c 'echo "длина ${#DEMO_TOKEN}, начало ${DEMO_TOKEN%%-*}"'
длина 22, начало sk
```

Имя в выводе `names` и работающий подпроцесс, ни разу не показавший значение,
и есть наблюдаемый результат. В Keychain секрет кладётся своим порядком
(`security add-generic-password`, раздел «Бэкенды и выбор по окружению» ниже),
а маркер имени всё равно лежит файлом в той же директории.

## Команды

Команды две, и обе держат значение вне stdout самой утилиты:

```
names                          перечисляет имена секретов хранилища, по
                               одному на строку, без значений
exec <имя> -- <команда> ...    запускает команду в подпроцессе, подставив
                               значение секрета в его окружение: имя
                               переменной равно имени секрета
```

Команды, печатающей значение секрета в stdout, у утилиты нет. Это закреплено
тестом «обход всех подкоманд с запросом значения не выводит его в stdout»
(`main_test.go`, `TestNoSubcommandPrintsValue`): он гоняет все имена команд из
usage и все напрашивающиеся по аналогии (`get`, `show`, `print`, `value` и
подобные), и ни одно не должно напечатать значение.

## Команда names

`names` перечисляет имена секретов хранилища в алфавите, по одному на строку.
Значений в выводе нет никогда: на этом стоит принцип цели, и проверяет это и
отдельный тест, и сам факт, что другой команды взять значение нет. Список
берётся из индекса-директории (см. «Бэкенды»), а не из Keychain, поэтому он
доступен без диалога разблокировки и одинаков для обоих бэкендов.

На пустом хранилище `names` это пустой stdout и код 0, а не ошибка: секретов
нет, и утилита честно об этом говорит. Чужие файлы (`.DS_Store`, директории)
молча пропускаются, список от них не ломается.

## Команда exec

`exec <имя> -- <команда> [аргументы...]` достаёт значение секрета и запускает
команду в подпроцессе, подставив значение в переменную окружения с тем же
именем, что у секрета. Так для секрета `GITHUB_TOKEN` подпроцесс получает
переменную `GITHUB_TOKEN`, и набор секретов задаёт набор переменных: модель
оперирует именами, а что в них лежит, решает хранилище.

`--` обязателен: имя секрета отделяется от команды подпроцесса однозначно,
иначе флаги команды путались бы с флагами secretctl. Свои флаги у `exec`
минимальны (стандартные `-h`/`--help` и общий `--version`), подпроцессу же
передаётся всё, что стоит после `--`.

Если переменная с тем же именем уже выставлена в окружение `secretctl`, её
значение перекрывается секретом: так случайно выставленная наружу переменная не
подменяет значение, а утилита остаётся единственным источником правды. Код
выхода подпроцесса пробрасывается как есть, чтобы обвязка видела реальный
исход команды, а не «exec прошёл».

Значение в stdout самой secretctl не попадает. Его печатает подпроцесс, и
только если он сам решит это сделать (например, `exec TOKEN -- env`). Это
контракт команды, и закреплён он тестом `TestExecInjectsSecretIntoSubprocessEnv`
и `TestNoSubcommandPrintsValue`.

## Бэкенды и выбор по окружению

Бэкендов два, и выбираются они по окружению:

- macOS Keychain через бинарь `security`, когда он есть в PATH. Значения
  лежат в Keychain как generic-password: `service` один на все секреты devkit
  (`devkit.secretctl`), `account` равен имени секрета, пароль равен значению.
  Выбор пал на `security` CLI, а не на go-keychain по критерию задачи: утилита
  работает на голой macOS без сторонних зависимостей, что держит принцип devkit
  «ставится на пустую машину».
- файлы с правами 0600 в `~/.devkit/secrets/` в ином случае. Имя файла равно
  имени секрета, содержимое файла равно значению, формат повторяет `token_file`
  у trackctl (`contour.go:179`): хвост из пробелов и переводов строки срезается
  `TrimSpace`, иначе случайный мусор в файле ломал бы подстановку.

Выбор перекрывается переменной `SECRETCTL_BACKEND` (`file` или `keychain`):
ею тесты фиксируют бэкенд, не связываясь с настоящим Keychain, а машина без
Keychain получает `file` явно, без автодетекта.

В обоих случаях индекс имён для `names` держит одна директория
`~/.devkit/secrets/`. Для файлового бэкенда её файлы это и есть значения, для
Keychain это пустые файлы-маркеры: так `names` работает единообразно и не зовёт
`security dump-keychain` (шумный, требует прав и роняет диалог разблокировки
Keychain на неподготовленной машине). Маркер это источник правды для списка
имён, и если маркер есть, а записи в Keychain нет (или наоборот), рассинхрон
виден как честный отказ `exec`, а не молчаливая подстановка.

Имя секрета становится именем файла и `account` в Keychain, поэтому алфавит
имён ограничен: буквы, цифры, знак подчёркивания и дефис. Слеш, точка и пробел
отсекаются на входе, иначе `../` или `.git/config` стали бы путями в файловому
бэкенде. Запись секретов в хранилище делает внешняя утилита или оператор
(`security add-generic-password` для Keychain, просто файл 0600 для файлового
бэкенда), у самой `secretctl` команды записи нет: её контракт только читать и
подставлять.

## Ошибки не светят значение

Отказ `exec` или `names` называет имя секрета или переменной, но не значение.
Тем же порядком, что `token_env` в trackctl (`contour.go:176`): «нет секрета
"NAME"», «не достал секрет "NAME" из Keychain», «не прочитал секрет "NAME"».
Значение другого секрета в ошибку не попадает никогда, что проверяет тест
`TestFileBackendGetMissingNamesSecretNotValue`.
