# shipctl: слияние и откат задач

Механика раздела «Ветки, ревью и деплой» RULES.board.md: самый длинный ручной
процесс из тех, что остаются агенту. Утилита держит порядок шагов и
предусловия, думающая часть (само ревью, команда тестов и выката проекта)
остаётся за исполнителем и передаётся флагами.

Ставится в PATH релизом devkit, вместе с taskctl (который тоже нужен в PATH:
доску двигает он):

```
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py update
```

Корень находится как у taskctl: сначала редирект `devkit.local` из конфига git
(корп-контур, доска в боковой директории рядом с клоном), а без него подъём
поиском `docs/TASKS.md` вверх от текущей директории. При необходимости стартовую
задаёт общий флаг `-C <dir>`, разбор редиректа в
[tools/taskctl/README.md](../taskctl/README.md).

## Команды

```
status                                    очередь выката, поезд, сломанный прод,
                                          деревья задач и копия окна
start <ID> [--slug хвост] [--push]        задачу в работу в отдельном дереве
code <ID> [--dry-run] [--probe]           окно vscode второй подписки на копии
                                          окна, ветка задачи внутри копии
merge <ID> [--test "cmd"] [--deploy "cmd"] [--train] [--push]
ship [--deploy "cmd"] [--push]
revert <ID> [--test "cmd"] [-m "..."] [--push]
```

## Замок конвейера

Предусловия проверяются одно за другим, а между проверкой и checkout с
fast-forward помещается целый чужой заход: пользователь руками, вторая сессия,
исполнитель не по инструкции. Раньше от этого спасало только то, что диспетчер
один и команды гоняет по очереди. Теперь замок на файл `.devkit/ship.lock` в
основном дереве берут все четыре команды, двигающие main или доску: `merge`,
`ship`, `revert` и `start`. Последний в списке не для симметрии, это
единственная из них, которая пишет и коммитит доску в основном дереве, и её
`taskctl move` с пушем посреди чужого слияния бьёт ровно в тот зазор, ради
которого замок и заводится. Занятый замок это чистый отказ, ничего не сделано.

Держится замок дескриптором (`flock`), поэтому снимает его ядро при завершении
процесса, в том числе аварийном: убитое посреди слияния shipctl конвейер не
запирает, а следующий запуск берёт замок как обычно. Сам файл остаётся лежать
пустым, убирать его руками не нужно и нечего. Без директории `.devkit` замок
не берётся, как не пишется и журнал запусков: обвязку заводит `devkitctl`, и в
проекте без неё запирать нечего. `status` замка не берёт: он ничего не двигает.

## Worktree на задачу

Когда над репозиторием параллельно работают несколько сессий, общий чекаут
превращается в проходной двор: незакоммиченные правки одной сессии лежат под
ногами у другой, и чужой файл легко уезжает в посторонний коммит. Поэтому
фичеветка живёт не в общем чекауте, а в своём git worktree.

`start <ID>` берёт задачу в работу: заводит ветку по ID строчными (хвост
имени задаётся `--slug`, получается `dk-005-worktree`) в дереве
`../<проект>-<id>` рядом с проектом и переводит задачу из Backlog в
In progress (коммит доски делает taskctl, `--push` или автономный режим сразу
пушат его). Основной чекаут остаётся на main: там живут доска, мелочь в main
и само слияние. Второй заход на задачу с уцелевшей веткой подхватывает её, а
не заводит новую: старая ветка сильнее `--slug`, второй ветки у задачи не
появится. Осиротелую регистрацию worktree (директорию снесли мимо git)
start и merge чинят сами через `git worktree prune`. В worktree start кладёт
`.devkit` (директория гитигнорнута и сама в новое дерево не попадает): без неё не
пишется журнал запусков и не работает подсказка про regcheck. Свежему дереву
корп-клона start кладёт в неё же и ссылки на соседние деревья правил
(`.devkit/devkit`, `.devkit/local`): корп-репозиторий чужой, ссылки туда не
коммитятся, а без них тонкий файл правил не разворачивается. Копируются они
дословно с готовых ссылок клона, которые положил `devkitctl corp`: дерево задачи
лежит сиблингом клона, и относительные цели сходятся. Своему проекту ссылки не
нужны, их несёт чекаут (DK-193).

`merge` ветку в worktree находит сам: по дереву, из которого запущен, либо,
при запуске с main, по ID среди worktree. Ребейз и тесты идут в дереве
задачи, fast-forward в основном чекауте, после слияния одноразовое дерево
задачи убирается и ветка удаляется (копия окна вместо этого переводится на
слитый коммит, про неё ниже). Дерево с незакоммиченными правками слияние держит, как
грязный чекаут; untracked-черновики слияние не валят, но оставляют worktree
на уборку руками, подсказка уходит в отчёт. `ship`, `revert` и `status` из
worktree тоже работают: доску и очередь они считают по основному дереву.

Старый способ (ветка в общем чекауте, merge с неё) никуда не делся и работает
как раньше: worktree это изоляция для параллельных сессий, а не обязательный
шаг.

## Окно на второй подписке

Клиент claude держит конфиг в каталоге, на который смотрит
`CLAUDE_CONFIG_DIR`, а endpoint и токен берёт из секции `env` его
`settings.json`. Отсюда весь рычаг второй подписки: окно редактора, запущенное
с этой переменной, ходит в её endpoint, соседнее окно без переменной в
подписку Anthropic, и сессии друг о друге не знают. Руками рычаг дёргается
плохо: переменную надо экспортировать перед каждым запуском, а забытый экспорт
молча тратит дорогую подписку.

`code <ID>` открывает окно на копии окна и переключает её на ветку задачи:

```
shipctl code DK-175                 окно vscode на копии окна
shipctl code DK-175 --dry-run       напечатать окружение, редактор не звать
shipctl code DK-175 --probe         сходить в endpoint и назвать модель ответа
```

## Копия на окно, а не на задачу

Дерево на задачу проектировалось под субагентов: диспетчер сидит в основном
чекауте, деревья одноразовые, и уборка их на `merge` это нужное свойство. У
окна редактора жизнь другая, оно переживает задачу, и снос дерева из-под
живого окна убивает окно вместе с сессией и её контекстом (DK-192, живой
случай IRC-097: расширение упало с руганью про native binary, а настоящей
причиной был удалённый рабочий каталог).

Поэтому у окна своя копия репозитория, одна на все задачи: вечное рабочее
дерево `../<проект>-<поставщик>` (на этой машине `../devkit-glm`), заведённое
`git worktree add --detach`. Ветка задачи заводится в ней тем же путём, что
`start` (ветка по ID, перевод доски в In progress), и следующая задача просто
переключает копию на свою ветку. `merge` копию не сносит: он переводит её на
слитый коммит (`checkout --detach`), после чего ветка ни одним деревом не
занята и удаляется как обычно. Окно живо, cwd на месте, под ногами слитое
состояние main, и следующая задача берётся из того же окна. Запускается команда
из любого дерева проекта.

Слитый коммит это не конец пути main: следом идут коммит файла задачи и, у
одиночного `merge`, перевод доски в Check (у поездного -- позже, разом на
весь состав, при `shipctl ship`). Поэтому в самом конце, когда все эти
коммиты уже в main, `merge` и `ship` подтягивают копию заново
(`checkout --detach` на свежий main), независимо от того, чья ветка сливалась
-- собственная копии или дерево другой задачи (одноразовое дерево субагента,
основной чекаут). Копию на ветке (открыта другая задача) или с
незакоммиченным подтяжка не трогает, причина уходит строкой отчёта; копии нет
вовсе -- отчёт про неё молчит, это обычное состояние проекта без второй
подписки, а не отказ.

Что копия отбивает вместо молчаливого переноса:

- незакоммиченные правки прошлой задачи. Переключение на чужую ветку утащило
  бы их с собой, и заметили бы это в лучшем случае на ревью, поэтому отказ с
  перечнем файлов: закоммитить в свою ветку либо убрать. Своя же ветка под
  ногами переключением не считается, окно на ней открывают по многу раз в день;
- ветка задачи, выложенная другим деревом (второе окно, дерево субагента).
  Дважды одну ветку git не выкладывает, и отказ называет, чем её берут на
  чтение: `git checkout --detach <ветка>`, коммиты в неё идут только из
  занявшего дерева.

Ветка задачи, оставленная дозревать (копию переключили на другую задачу), из
деревьев уходит, и `merge` с main её не найдёт. Отказ про это говорит прямо и
зовёт вернуть ветку в копию (`shipctl code <ID>`), а не сообщает, что сливать
нечего.

Одноразовые деревья задач никуда не делись: у субагентов пачки окна нет, им
`shipctl start` заводит дерево на задачу, и `merge` его убирает, как убирал.
Деревья `../<проект>-<id>`, оставшиеся от интерактивных запусков до перехода
на копию, прибираются один раз руками (`git worktree remove`): автоматике
отличить их от рабочего дерева субагента нечем, имя у них одно и то же, а их
список показывает `shipctl status`.

`--dry-run` печатает путь копии, машинный слой, base URL, модель, признак
токена, заголовок окна и команду редактора, после чего выходит: ни окна, ни
копии, ни движения доски. Токен не печатается никогда и нигде, у него есть
только признак «есть» или «нет»; из чужого текста (тело ответа endpoint в
ошибке пробника) он вычищается тоже.

`--probe` стучится в `<base URL>/v1/messages` Anthropic-совместимым запросом и
называет модель из тела ответа. Печать окружения показывает, что окно уйдёт по
нужному адресу, но не что там живая подписка: протухший токен и опечатка в
адресе выглядят на печати одинаково исправно, а различает их только ответ.
Нерабочий endpoint это отказ, окно тогда не открывается.

Каталог конфига лежит в машинном слое, вне репозиториев, и называет его там ключ
`home` секции `[glm-code]` файла `~/.devkit/harness.local` (на этой машине
`~/.devkit/claude-glm`). Слой машинный, а не проектный, потому что подписка
принадлежит машине, и копия ключа в каждом репозитории разошлась бы сама собой;
своей константы у `shipctl` при этом нет, потому что тот же каталог читают
раскладка машинного хозяйства (`devkitctl`) и окружение подпроцесса
делегирования (`agentctl`), а два места под один каталог разъезжаются. Ключа в
машинном слое нет значит второй подписки на машине не заведено, и команда
отказывает строкой про то, куда его вписать. Болванку каталога с пустыми ключами (`ANTHROPIC_BASE_URL`,
`ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_MODEL`) раскладывает `devkitctl doctor
--fix`, права сужает туда же; сами значения берутся в кабинете подписки и
вписываются один раз, а пока их нет, незаполненные ключи называет
`devkitctl doctor` находкой. В devkit ни endpoint, ни токен не едут.

## Окружение живёт в директории, а не в запуске

Раньше ключи ставились процессу редактора при запуске, и окно, переоткрытое
мимо `shipctl` (док, «Open Recent», перезапуск после обновления), молча уходило
на первую подписку: возвращался ровно тот промах, ради которого вторая подписка
и заводилась. Поэтому ключи лежат в самой копии:

- `.claude/settings.local.json` с `ANTHROPIC_BASE_URL`, токеном, `ANTHROPIC_MODEL`
  и `DEVKIT_HARNESS=glm-code` (без имени харнеса сессия в окне считала бы себя
  домашней: детект по переменным тут неоднозначен, `CLAUDECODE=1` виден и там,
  и она разворачивала бы ярусы по чужому маппингу и корректировала вердикты по
  чужому остатку). Права файла сужены, там токен;
- `.vscode/settings.json` с `window.title` вида `[GLM] devkit`: поставщик виден
  в заголовке, а не выводится из имени директории.

Оба файла машинные и в гит не едут: `shipctl code` дописывает их в исключения
самого репозитория (`info/exclude` общего каталога `.git`), а не в
коммитимый `.gitignore`, который уехал бы всем, кто взял проект. Хозяин ключей
остаётся машинным слоем: каждое открытие окна переписывает окружение копии из
него, а разъехавшуюся копию (окно открывали не через `shipctl`) находит
`devkitctl doctor` и чинит `--fix`.

Команда редактора зовётся без `-n`: окно второй подписки одно, и повторный
вызов на той же директории его фокусирует. Флаг был нужен, пока подписка
доставалась окну запуском, чтобы дерево задачи не открылось вкладкой в окне
первой подписки; с окружением в директории этой опасности нет вовсе.

В корп-контуре команда отказывает: там дерево задачи заводится в клоне кода и
называется ключом тикета, а вторая подписка это личный доступ, которому в
репозитории компании делать нечего.

## Слияние

`merge` проверяет предусловия и проводит слияние:

- рабочее дерево чистое, задача в In progress, ни за одной задачей не числится
  провал проверки (см. «Сломанный прод»), в Check нет задач с выкаченным
  кодом (выкаты строго последовательные, непроверенная правка на проде одна;
  LLD и дока ждут в Check подтверждения пользователя, но очередь не держат:
  их коммиты, если и есть, лежат только под docs/ и прод не меняли);
- раздел «Ревью» файла задачи без замечаний с незафиксированным исходом
  (каждая строка кончается «исправлено» либо «отклонено» с причиной);
- ребейз на main, прогон тестов (строка уходит в `sh -c`, берётся из `--test`
  или из ключа `test` в `.devkit/deploy.local`), fast-forward
  без merge-коммита, фичеветка удаляется;
- выкат (см. «Обвязка выката» ниже);
- перевод задачи в Check через taskctl и коммит доски.

На этих предусловиях и держится очередь выката. Тестовых сред нет, прод один,
поэтому непроверенная правка на проде допускается ровно одна: обычно выкат
везёт одну задачу, и если после него что-то сломалось, источник очевиден.
Пачку мелочи везёт поезд, там источник ищется по позадачным сценариям
проверки. Выкаченную задачу от бескодовой (LLD, дока, разбор) отличает не тип
на доске, а git: у первой есть коммиты, трогающие что-то кроме docs/. Заранее
выяснять, свободна ли очередь, поэтому не нужно ни человеку, ни автономному
агенту: на занятой очереди merge падает чистой ошибкой, ничего не поменяв.

Какие коммиты у задачи, shipctl не угадывает, а знает: сразу после
fast-forward `merge` пишет слитый диапазон в раздел «Выкат» файла задачи
(`docs/tasks/<ID>.md`) своим коммитом под docs/, и очередь, состав поезда и
откат читают эту запись. Круг доработки после возврата из Check дописывает в
раздел ещё строку, прежние коммиты остаются. Поиск по ID в subject остался
запасным путём: по нему находятся задачи, слитые до появления записи или
руками мимо shipctl. Раньше он был единственным, и ветка, где ID в сообщения
не попал, пропадала разом из очереди, из поезда и из отката, причём молча:
пустой ответ там неотличим от честного «кода нет».

Файл задачи весь разбирается мимо ограждённых блоков (``` и ~~~): в него по
RULES.board.md вкладывается реальный вывод команд, а в нём запросто окажется и
заголовок раздела, и чужая строка записи. Разбирая такую цитату как свою
разметку, очередь посчитала бы выкаченной не ту задачу, процитированное
замечание без исхода отбило бы слияние, а процитированный заголовок «Сценарий
проверки» заглушил бы подсказку о том, что сценария у задачи нет.

Обратная сторона такого разбора это оборванный файл: незакрытое ограждение
уводит в цитату весь остаток, вместе с настоящими разделами. Угадывать, где
автор забыл закрыть блок, shipctl не берётся (сочти незакрытое ограждение
закрытым, и цитата с одним ограждением снова станет записью), но и молчать про
это нельзя: пропадают разом «Выкат», «Ревью» и «Сценарий проверки». Поэтому
обрыв виден вслух. `status` называет такой файл строкой с номером оборванной
строки, а `merge` по такой задаче отказывает до всякого ребейза: иначе он
дописал бы запись слияния в тот же оборванный хвост и очередь её больше не
увидела бы. Файл задачи в работе живёт на её ветке, поэтому обе команды
читают его в дереве задачи, а не в основном чекауте: там он и пишется, и
строка `status` называет это дерево. Чинится обрыв закрытием ограждения.

Если в коммитах ветки нет ID задачи в subject, merge проходит, но
предупреждает: сам он такие коммиты найдёт по записи, а вот собрать историю
задачи по `git log` уже не выйдет.
Тем же порядком merge подсказывает при слиянии bug-задачи, когда в журнале
запусков `.devkit/log` нет зелёного regcheck за время жизни ветки:
регрессионный тест обязан краснеть на старом коде (RULES.md, «Тесты
обязательны»), а этот шаг по статистике пропускается чаще других. Это
подсказки, не отказы: где regcheck не применим (правка и тест в одном файле),
слияние проходит как шло.

## Следующий шаг конвейера

Последней строкой `status` и `merge` печатают, что делать дальше. Знание «что
дальше» лежит в выводе утилиты, а не в прозе скилла: подсказку читает любая
модель и ровно в ту минуту, когда решение принимается, а прочитанный час назад
абзац к этой минуте уже не работает (DK-180, DK-205). У `status` ветка
выбирается по состоянию конвейера, в порядке срочности: сломанный прод, потом
задачи в Check с их сценариями, потом стоящий поезд, потом работа в In
progress, а на пустой доске приглашение взять задачу. `merge` называет сдачу
задачи (сценарий проверки и `taskctl close`), поездной `merge` предлагает
добрать состав либо выкатить его, `ship` называет сдачу всего состава.

Отдельно проговаривается развилка «кто нажимает кнопку», потому что на ней
агент сходит с конвейера ровно на готовой задаче: `status` при задаче в работе
называет ключ `autonomous` вместе с его значением и файлом
(`.devkit/deploy.local`). При `autonomous = true` следующий шаг это
`shipctl merge <ID>` своими силами, отдельного слова пользователя тут не ждут;
при `autonomous = false` слияние за пользователем, и агент останавливается на
локальном коммите. Тот же ключ и тем же порядком читает `taskctl move <ID>
in-progress`.

## Поезд выката

Мелкие независимые задачи выкатываются пачкой (критерии отбора в
RULES.board.md, «Ветки, ревью и деплой» п. 9), чтобы фиксированная обвязка
(сборка, подпись, раскладка, установка, цикл проверки) платилась один раз, а
не за каждую задачу: `merge --train` проводит то же слияние с полными
предусловиями, но без выката, задача остаётся в In progress, а `ship` одним
деплоем везёт всё накопленное и разом переводит в Check. Каждая задача
проверяется на этом билде по своему сценарию, провал одной чинится точечным
`revert`: он откатывает и перекатывает только её, остальной поезд остаётся на
проде. Откат задачи из ещё не выкаченного поезда деплой не запускает вовсе: до
прода она не доехала, а повторный выкат увёз бы туда остальной поезд раньше
времени.

Точку последнего выката держит лёгкий тег `deployed`, в поезде стоят задачи из
In progress, чьи коммиты кода слиты после него. Коммиты, трогающие только
docs/ (доску, файлы задач, LLD), членства не дают: попутно такие правки едут,
но прод не меняют. Это допущение конвенции devkit: проекту, где docs/ и есть
объект выката (сайт, собираемый из репозитория), фильтр не подходит.
Задача, откаченная внутри окна, из поезда выбывает
(откат узнаётся по префиксу `revert` либо слову «откат» в
subject, поэтому своё сообщение отката через `-m` обязано содержать ID и
слово «откат»). Тег заводит первое `merge --train` на main до себя: что было
на main к этому моменту, считается выкаченным. Дальше тег двигает каждая
точка выката: `ship`, одиночный `merge` и `revert` с повторным выкатом.
Когда shipctl пушит сам (`--push` или автономия), тег уезжает тем же заходом
(`git push -f origin deployed`); при ручном пуше эту команду надо добавить к
своему `git push`, ship про это напоминает. На второй машине тег
подтягивается `git fetch --tags --force`.

После fast-forward `merge --train` смотрит на слитый диапазон и разбирает три
случая:

- весь диапазон под `docs/`. Кода нет, выката задаче не нужно, очередь она не
  держит, и merge переводит её в Check сам, коммитом доски и без выката. Это то
  же поведение, что у одиночного merge с бескодовой задачей, а в отчёт уходит
  строка, что поезд задачу не везёт. Точку выката такое слияние не заводит:
  везти на прод нечего. Раньше такая задача (правка одной доки под типом task
  или bug) молча оставалась в In progress: в поезд она не попадала, а в Check
  переводит только `ship`;
- код есть, задача в поезде. Обычный случай: In progress до `ship`;
- код есть, а в поезде задачи нет. Её коммиты не нашлись ни по ID в subject, ни
  по записи в файле задачи (так бывает, когда верхний коммит ветки распознан
  как откат). Правка на main уже лежит и уедет на прод с чужим выкатом, а `ship`
  задачу не повезёт и в Check не переведёт, поэтому merge говорит про это
  отдельной строкой.

Тем же заходом `merge --train` подсказывает, если в файле задачи нет раздела
«Сценарий проверки». Одиночный выкат везёт одну задачу, и её проверяют по
горячим следам, а поезд переводит в Check всю пачку разом и уже после деплоя:
задача без сценария всплывает там, где проверять её нечем, а прод уже
поменялся. Файл читается в дереве ветки, туда его пишут исполнитель и ревьювер.
Кто переведёт задачу в Check, подсказка называет по ветке: у бескодовой это тот
же merge и прямо сейчас, у остальных будущий `ship`.

Задачи пачки приезжают готовыми вперемешку, и ни одно предусловие merge на
порядок не завязано. Основное дерево чистое, потому что пачка готовится одним
коммитом до старта. В In progress задачу перевёл `start`, а в Check всех разом
переводит `ship`. Замечания ревью merge читает в файле задачи в дереве ветки,
куда пишет и ревьювер. Ребейз и тесты идут после ребейза на текущий main,
поэтому каждая следующая задача проверяется на состоянии с учётом предыдущих.
Тег `deployed` заводит первое поездное слияние, дальше состав считается из git.
Все предусловия при этом завязаны на то, что в каждый момент идёт ровно одна
команда, двигающая main и доску, и держит это замок конвейера.

Критерии отбора в поезд (цена S или M, задачи независимые, не больше 3-5)
остаются на суждении исполнителя: связность «по смыслу» git не видит. Потолок
в 3-5 задач это осознанная плата за пачку: регресс, не пойманный ни одним
сценарием проверки, ищется перебором задач поезда, и чем длиннее поезд, тем
дороже перебор. Но что git видит, `merge --train` проговаривает
предупреждениями: цена задачи не S/M или не оценена, ветка трогает те же
файлы, что уже слитые задачи поезда (правки под docs/ не в счёт), в поезде уже
пять задач и пора `ship`. Слияние при этом проходит.

Одиночный `merge` при непустом поезде отбивается: он увёз бы на прод чужие
непроверенные правки, а в Check перевёл только свою задачу. Либо сливать с
`--train`, либо сначала `ship`. Отбивается и другая аномалия: задача с кодом
в окне выката, выведенная из In progress руками (в Blocked, обратно в
Backlog, в Check мимо ship). Такой код уехал бы на прод без проверки, поэтому
merge и ship стоят, пока задачу не вернут в In progress или не откатят её
коммиты; status аномалию показывает. У защиты есть предел: задача, закрытая в
архив мимо ship, с доски исчезает и для состава невидима, поэтому поездные
задачи закрываются только после ship, из Check.

`revert` чинит прод после провала проверки: откатывает коммиты задачи с main
(берутся из записи в файле задачи и по ID в subject, новые первыми, коммиты
доски и файлов задач не трогаются), одним коммитом, возвращает задачу в In
progress и гасит признак провала, если он стоял. Граница
поиска это прошлый откат той же задачи, поэтому повторные заходы на задачу
откатываются корректно. При конфликте revert отменяется целиком, тогда чинить
форвард-фиксом. Откат задачи, правившей только docs/, повторный выкат не
запускает и тег не двигает: прод не менялся, а деплой увёз бы копящийся
поезд раньше времени.

## Сломанный прод

Проверка на проде кончается одним из двух исходов (RULES.board.md, «Ветки,
ревью и деплой» п. 7), и очередь выката они держат по-разному. Приёмка с
замечаниями это обычный `taskctl move <ID> in-progress`: прод живой, выкат за
задачей проверен, доработка едет следующим кругом, и очередь свободна. Провал
это сломанный прод, он отмечается `taskctl fail <ID> --reason "..."` пометкой в
строке доски, и по ней `merge` и `ship` отказывают: слить чужую задачу поверх
сломанного прода значит смешать её правку с неразобранной поломкой. Проходит
только починка самой проваленной задачи одиночным `merge` (форвард-фикс);
поезд в это время не копится.

Признак снимается сам, руками дочищать нечего: перевод в Check после удачного
`merge` или `ship` гасит его в `taskctl move`, а `revert` зовёт
`taskctl fail --clear` своим заходом и коммитит доску. Отдельной командой
признак снимают только тогда, когда прод починили мимо shipctl.

Обе стороны видно в `status`: сломанный прод идёт строкой с причиной и
способом починки, а выкат за задачей, которая уже ушла из Check с принятыми
замечаниями, называется отдельно. Раньше про такой выкат status молчал: строка
уходила из Check, её коммиты оставались под тегом `deployed`, и ни очередь, ни
поезд задачу не видели, так что следующее слияние проходило поверх
непроверенной правки.

Провалившийся выкат (команда из `deploy` вернула не ноль) в `merge`, `ship` и
в повторном выкате после `revert` громко зовёт `hooks/notify.py`: прод в этот
момент может быть сломан, а в автономном режиме об этом иначе некому узнать
(RULES.board.md, «Ветки, ревью и деплой» п. 8, самый громкий из трёх поводов
DK-063). Уведомитель ищется тем же порядком, что у `taskctl` (см. его
README): `DEVKIT_HOME`, `hooks/` рядом с доской, соседний клон devkit,
`~/projects/devkit`. Не нашёлся или упал сам, ошибка выката всё равно
возвращается как прежде, но с дописанной строкой «уведомление не отправлено:
...»: падать из-за непосланного уведомления нельзя, а молчать про это тоже
нельзя. Репозиторий во временной директории баннера не даёт: отправку
пропускает сам `notify.py` (разбор в его README), причина доезжает припиской
до сообщения команды. Headless-прогоны глушат его `DEVKIT_NOTIFY_OFF=1`,
разбор поводов и уровней в `hooks/README.md`, раздел «Уведомления о сессии».
Перевод задачи в Check при удачном выкате звонит не отсюда, а из
`taskctl move` (см. его README): статус двигает он, и его же зовут `merge` и
`ship`.

`--push` у обеих команд отправляет результат в origin; без него пуш остаётся
за пользователем (RULES.md, «Git» п. 3), кроме автономного режима, где обе
команды пушат и без флага (см. «Обвязка выката»). Сообщение коммита-отката по
умолчанию «revert: <ID> откат ...», в проекте с белым списком префиксов своё
задаётся флагом `-m`; в нём обязаны остаться ID и слово «откат», по ним
границу отката находят revert и состав поезда.

Перед необратимыми шагами merge сверяет локальный main с origin (fetch плюс
проверка, что origin/main не ушёл вперёд): отставший клон, чья доска не знает
о задаче в Check с другой машины, отсекается до слияния, а не на пуше.

## Обвязка выката

Команда выката у каждого проекта своя, и в ней обычно адрес или роль машины,
поэтому она не в коммитимом `AGENTS.md`, а в гитигнорнутом `.devkit/deploy.local`
(болванку заводит `devkitctl new`). Формат простой: строки `key = value`,
`#` это комментарий.

```
deploy = ssh vps 'systemctl restart foo'
test = go test ./...
autonomous = false
deploy_timeout = 30m
```

Команда тестов лежит там же и по той же причине: она такая же принадлежность
проекта, как команда выката, и без ключа процедуре пачки пришлось бы сочинять
`--test` под каждый репозиторий. Явный `--test` сильнее конфига, а нет ни
флага, ни ключа значит прежний отказ: ветка сливается только зелёной. Когда
команда пришла из конфига, merge называет её в отчёте, иначе прогон незнакомой
командой был бы неотличим от прогона своей. Ключ читает только `merge`: `ship`
тестов не гоняет и так (код проверен при слиянии), а у `revert` пустой `--test`
значит «без прогона», и подставить туда команду из конфига значило бы молча
поменять поведение аварийного пути. Откат чинит прод и должен быть быстрым,
прогон тестов на нём остаётся решением того, кто откатывает.

Шаг выката идёт под пределом времени: команда, не кончившаяся за
`deploy_timeout`, убивается вместе с потомками (выкат обычно зовёт сборку или
`ssh`, и смерть одной оболочки оставила бы их висеть), а merge, ship и revert
кончаются провалом, который называет предел, вставшую команду и время
ожидания, и зовёт уведомитель, как на любом провале выката. Без ключа действует
умолчание в 30 минут: запас взят к самой долгой штатной работе выката, полной
кросс-сборке релизных бинарей. Значение читается как длительность Go (`90s`,
`30m`, `2h`), кривое или неположительное это ошибка, а не молчаливый возврат к
умолчанию. Предел действует и на команду из явного `--deploy`: она виснет так
же, как команда из конфига. Тестов предел не касается, у прогона свой таймаут.
Повод у ключа из инцидента DK-153: выкат позвал кросс-сборку, той нужен был
Docker, демон не поднят, и шаг ждал его вечно, молча и без вывода.

`merge` (и `ship` тем же порядком) разбирается с выкатом так:

- явный `--deploy "cmd"` это указание выкатить прямо сейчас, выполняется
  всегда и сильнее конфига (пуш тогда по `--push`, как обычно);
- без флага и при `autonomous = true` shipctl катит команду из `deploy` сам;
- без флага и при `autonomous = false` команда остаётся за пользователем,
  merge печатает, что именно запустить;
- команды нет вовсе (или файла нет) это выкат по плейбуку проекта, как раньше.
  Если при этом поднят `autonomous = true`, merge, ship и revert печатают
  предупреждение, что агенту доверен конвейер, а выкатить нечего.

Объект выката бывает не только серверным. Для приложения выкат это сборка,
подпись и раскладка в канал обновлений, и он так же сводится к команде
`deploy`, а не отдаётся пользователю по умолчанию. Что автоматизируется,
автономный агент делает сам, а за пользователем остаётся только физически
недоступное с машины агента (установка на устройство в руках, сверка глазами):
выкат разрезается на эти две части, а не отдаётся целиком. Чтобы и проверка
после выката была агентской, нужен машинно-читаемый идентификатор выкаченного
билда (эндпоинт версии, запрос через `adb`), который агент запрашивает и
сверяет с ожидаемым.

При `autonomous = true` merge, ship и revert пушат в origin сами, без `--push`,
это часть автономного конвейера: иначе origin отстал бы от задеплоенного прода
и доски, а `revert` по ID не нашёл бы коммитов на origin. Код уходит в origin
до выката, а доска после: pull-выкат тогда тянет с origin уже свежий main,
а строка в Check появляется после успешного деплоя. Revert в автономном
режиме тем же порядком пушит откат и сам катит повторный выкат командой из
`deploy`, прод чинится без ручных шагов. При `autonomous = false` пуш и
повторный выкат остаются за пользователем (или по флагу `--push`).

Флаг автономии виден в `status`, а `devkitctl doctor` ловит пустую или
негитигнорнутую обвязку, в том числе `autonomous = true` без команды выката.

## Корп-контур

В корп-контуре (дизайн в [LLD DK-074](../../docs/lld/DK-074-corp-contour.md))
слияние делает MR-флоу компании, и конвейер честно останавливается на этой
границе, а не изображает её.

`start` остаётся точкой взятия в работу с тремя поправками. Дерево задачи
заводится не рядом с боковой директорией, а рядом с корп-клоном, на который
привязка `.devkit/tracker.local` указывает ключом `repo` (привязку читает
свой плоский разбор `key = value`, парсера TOML нет): там лежит код проекта,
и без этого дерево задачи несло бы одну доску.

В репозитории кода задача названа ключом тикета: по нему идут ветка, коммиты
и MR, а локальный ID доски в корп-артефакты не едет вовсе (DK-074, «Граница
доски и тикета»), это же стережёт рубеж следов. Ключ тикета `start` берёт из
ссылки зеркальной строки, как берёт его `trackctl`, а опознаёт ключом `key`
привязки (общепроектный префикс тикетов); ID строки для этого не годится, он
локальный номер доски, и подстановка его в шаблон была багом DK-124. Ветку
строит шаблон `branch` привязки, ключ тикета им же именует директорию дерева
задачи и `trackctl take`. Строка, которая при заполненном `key` на тикет не
ведёт, это отказ с подсказкой: имя ветки корп-репозитория брать неоткуда, а
локальный ID туда не едет. Привязка без `key` (контур ещё не настроен) `start`
не валит: ветка и дерево остаются домашними, а находка идёт строкой в отчёт.

main или master для новой ветки `start` спрашивает у того же клона, а не у
боковой директории: сразу после `devkitctl corp` она без единого коммита, и
раньше это валило `start`. После перевода строки в In progress `start` зовёт
`trackctl take <ключ тикета>`, тем же порядком, что `merge` зовёт `taskctl`.
Ни отсутствие `trackctl` в PATH, ни неполная привязка (файл есть, а ключа
`repo` в ней нет) `start` не валят: доска не должна вставать из-за трекера,
ветка и дерево задачи остаются домашними, но обе находки видно в отчёте, а не
молчком.

`merge`, `ship` и `revert` в корп-контуре отказывают честной строкой: слияние
и выкат там ведёт MR-флоу компании, а не shipctl. Подсказка называет ручные
шаги (`trackctl submit`, пуш ветки, MR, дальше по процессу контура) вместо
того, чтобы изображать команду, которой здесь нет.

`status` в корп-контуре очередь выката и поезд не считает вовсе (главный
случай Check здесь это «мяч на чужой стороне»: MR открыт, тикет в ревью или
тестировании, и строку двигает не выкат, а `trackctl sync`), но говорит об
этом строкой, а не молчит. Рабочую ветку он называет по клону, на который
указывает ключ `repo` привязки, а не по боковой директории (там своя история
только для доски, и там же он раньше падал на `git rev-parse`, пока в ней не
было ни одного коммита).

## Разрешение на пуш

Правила отдают push в origin пользователю, и держит это git-хук `pre-push` из
devkit: пуш, запущенный из сессии агента, он отбивает. Исключения из правила
идут через утилиты, поэтому shipctl выдаёт хуку разрешение сам, переменной
`DEVKIT_PUSH_OK=1` в окружении своего `git push` и только его (попутные команды
git остаются на наследованном окружении). Так пушатся коммит доски, слияние с
`--push` и весь автономный режим, а самовольный `git push` в той же сессии
рубеж всё равно не пропустит. Разбор устройства в `hooks/README.md`, раздел
«Пуш из сессии агента».

Справка доступна и по `-h`/`--help` у любой подкоманды. Каждый запуск, как у
taskctl, оставляет строку в журнале `.devkit/log` проекта (время, команда,
код выхода), когда директория `.devkit` заведена.
