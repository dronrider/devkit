# taskctl: механика канбан-доски

Утилита для рутинных операций с `docs/TASKS.md` и `docs/TASKS-archive.md`:
завести строку, перевести между статусами, закрыть в архив, пересортировать
Backlog, проверить инварианты. Думающая часть (заголовок, слагаемые ранга по
`RANKING.md`, сценарий проверки) остаётся за исполнителем и передаётся
аргументами, утилита ничего не сочиняет.

Утилита общая для всех проектов с доской, живёт в devkit и едет готовым
бинарём в его релизе. Один раз поставить набор в PATH:

```
python3 ~/projects/devkit/tools/devkitctl/devkitctl.py update
```

Тулчейна для этого не нужно: команда качает тарболл своей платформы, сверяет
сумму и кладёт бинари в каталог назначения; порядок установки с нуля в
[CONNECT.md](../../CONNECT.md). Собрать из исходников это `devkitctl build`, и
это путь разработчика devkit.

Дальше звать `taskctl <команда>` из любого места внутри проекта: корень
находится сам (поиском `docs/TASKS.md` вверх от текущей директории), при
необходимости стартовую директорию задаёт флаг `-C <dir>`.

Перед подъёмом вверх смотрится редирект `devkit.local` из конфига git. Он нужен
корп-контуру, где рабочие файлы devkit лежат не в дереве проекта, а в боковой
директории рядом с ним (`git config devkit.local ../<проект>-local`, разбор в
[LLD DK-074](../../docs/lld/DK-074-corp-contour.md)): ключ задан, значит корнем
считается названная директория, и относительный путь разрешается от основного
чекаута, а не от вершины текущего worktree, чтобы дерево ветки в стороннем
месте видело ту же доску. Ключа нет, значит всё как раньше, и домашние проекты
редиректа не замечают. Форматы доски и файлов задач он не трогает вовсе. Когда
доски нет нигде, а рядом с клоном лежит боковая директория с привязкой к нему,
отказ называет команду восстановления обвязки: её теряют переклонирование и
`git clean -xdf`.

## Команды

```
list [backlog|in-progress|check|blocked] [--json]
                                            доска по секциям без прозы; --json
                                            машинный вывод, Backlog целиком
show <ID> [--json]                          строка задачи, секция, файл задачи
id                                          следующий свободный ID
batch [--limit N]                           кандидаты в поезд выката
draft ["текст"]                             записать идею мимо доски, без текста
                                            он читается со stdin
draft list [--json]                         накопитель: ID, первая строка,
                                            возраст, пометка «отложен»
draft defer <ID> "причина"                  отложить черновик: раздел
                                            «Грумминг» в его файле
draft defer <ID> --clear                    снять пометку об отложенном
draft attach <ID> <TASK-ID>                 приписать черновик к стоящей
                                            строке, файл черновика удаляется
draft drop <ID> --reason "..."              удалить протухший черновик
add --title "..." --type bug|task|LLD --rank "а+б+в+г+д"
    [--cost S|M|L|XL] [--link "..."] [--status ...] [--id XR-NNN]
move <ID> <backlog|in-progress|check|blocked> [--reason "..."]
fail <ID> --reason "..."                    провал проверки: прод сломан
fail <ID> --clear                           прод починен, признак снят
set <ID> [--title "..."] [--type ...] [--rank "..."] [--cost ...] [--link "..."]
file <ID>                                   создать docs/tasks/<ID>.md и ссылку
close <ID> [--commit sha1,sha2] [--date ГГГГ-ММ-ДД] [--link "..."]
dep add <ID> <DEP-ID>                       ID делается после DEP-ID
dep rm <ID> <DEP-ID>                        снять зависимость
dep list [ID] [--json]                      кто после кого; без ID вся доска
sort
lint
init --prefix XR [--name "..."]             скелет доски в корне репозитория
review add <ID> "суть замечания"            замечание в раздел «Ревью»
review resolve <ID> <N> fixed|rejected [--reason "..."]
review show <ID>                            замечания с номерами и исходами
review stats                                свод по живым задачам и архиву
```

Смотреть доску дешевле через `list` и `show`, а не чтением `TASKS.md` целиком:
`list` печатает секции без прозы и обрезает Backlog до верхних десяти строк
(вся секция по `list backlog`), `show` находит задачу и в архиве. На большой
доске это заметная экономия контекста.

У `list`, `show`, `dep list` и `draft list` есть флаг `--json`: машинный вывод для дашборда
(LLD DK-112) и прочей автоматики, которой разбирать печатный текст хрупко.
Печатный вывод при этом не меняется, а `list --json` отдаёт Backlog целиком,
без обрезки: она экономит контекст агента, машинному же читателю нужна вся
доска. В JSON заголовок строки разобран на основу и суффиксы (`after`,
`fail`, `block`), ранг на сумму и слагаемые (`r`, `r_parts`), пометки из-под
строки лежат списком `notes`, а дата последней правки строки полем `moved`
(`2026-03-17`, считается тем же `git blame`, что и возраст в печати, и на
грязном дереве или вне git молчит); у `show --json` закрытая задача приходит с
секцией `archive` и датой закрытия, черновик с секцией `draft`. У
`draft list --json` каждый черновик приходит с ID, первой строкой, путём файла,
датой записи и возрастом сразу в двух видах: днями (`age_days`) и теми же
словами, что печатает `draft list` (`age_words`), чтобы читателю-человеку не
пересчитывать «вчера» по своей шкале. Пустой накопитель это пустой список, а не
отсутствие поля.

Изменяющие команды принимают
`-m "docs(tasks): ..."` и `--push`: закоммитить ровно те файлы, которые
тронула операция (и запушить); что было в индексе до этого, в коммит не
попадает. Пуш доски разрешён правилами и из сессии агента, поэтому taskctl
выдаёт разрешение хуку `pre-push` сам, переменной `DEVKIT_PUSH_OK=1` в
окружении своего `git push` (см. `hooks/README.md`, «Пуш из сессии агента»);
руками тот же пуш из сессии рубеж отобьёт.

Флаг стоит где угодно относительно позиционных аргументов: `review add XR-1 -m
"коммит" "текст"` делает ровно то же, что `review add XR-1 "текст" -m "коммит"`.
Стандартный `flag.Parse` останавливается на первом не-флаге, поэтому команда
снимает позиционный аргумент и продолжает разбор с остатка, а не читает его до
разбора и не бросает хвост (DK-099: форма «флаг перед текстом» уносила и текст,
и сам флаг, `draft -C dir "текст"` шёл за текстом в stdin, а `review add <ID> -m
"..." "текст"` записывал замечанием строку `-m`). Текст, начинающийся с дефиса,
передаётся после `--`: `taskctl draft -- "-C это часть идеи"`. Лишний
позиционный аргумент отбивается ошибкой с называнием самого аргумента: чаще
всего это потерянные кавычки, и молчаливый выброс тут неотличим от нормальной
работы.

Под строкой доски `list` и `show` печатают пометки: выводимые на лету
данные, самой доски они не касаются и в `TASKS.md` не пишутся. У строки в
Check это две оси, ради которых секция и завели, «чего ждут от владельца
прямо сейчас»: держит ли задача очередь выката (раздел «Выкат» в файле
задачи, который пишет `shipctl merge`, значит «код слит», его отсутствие
значит «без выката», как у LLD или разбора) и кто проверяет (заголовок `##
Сценарий проверки (агентский)` в файле значит «сценарий агентский», иначе
«сценарий пользовательский»). Файла задачи нет вовсе (Check пускает и со
ссылкой вместо файла), меток тоже нет: строка печатается как раньше. Под
любой строкой доски, не только Check, идёт возраст: «строка не двигалась N
дней» по дате последнего коммита, тронувшего именно эту строку (один
`git blame --incremental` на файл доски, а не вызов git на строку), а не
даты перевода в текущий статус, для которой в доске нет отдельного поля. Значит это ещё и то, что правка ранга или ссылки строку
«молодит», даже если задача не двигалась по факту, и что переезд в другую
секцию тоже её обнуляет: у только что переведённой в Check строки
«лежит 0 дней» до первого спокойного дня. На незакоммиченной доске (номера
строк рабочей копии и HEAD разъехались бы) и вне git-репозитория возраст
не печатается вовсе, а не считается по случайной строке.

Что утилита держит сама:

- `init` создаёт доску нового проекта (`docs/TASKS.md` с шапкой и секциями,
  `docs/TASKS-archive.md`, `docs/tasks/`) в вершине git-репозитория; префикс
  ID пишется в шапку, и первая задача заводится уже без `--id`;
- сумма R и бакет P считаются из разбивки `--rank`, руками их не передать;
  разбивка проверяется по шкалам `RANKING.md` (серьёзность из {0,25,50,75},
  ценность 0-10, неопределённость 0-5, баг 0 или 5, рычаг 0-5);
- колонка «Цена» держит грубую оценку затрат агента на исполнение (S / M / L /
  XL, шкала в `RANKING.md`), в ранг не входит; `--cost` не передан или «-»,
  значит «не оценено»; доску без этой колонки разбор принимает и переводит в
  новый формат при первой изменяющей команде (на месте это делает
  `taskctl sort`, старый формат подсвечивает lint);
- Backlog отсортирован по R убыванию, при равенстве по возрастанию ID; `add`
  сразу ставит строку в правильное место;
- статусы принимаются в любом регистре («In progress» = in-progress); голый
  путь в `--link` оборачивается в markdown-ссылку, чтобы её видел lint;
- `add` без `--link` ссылается на существующий `tasks/<ID>.md`, а без файла
  ставит в ячейку «-»: однострочному бэклогу файл не положен;
- `draft` записывает сырую идею мимо доски: файл `docs/tasks/drafts/<ID>.md`,
  первая строка текста в заголовок, весь текст в раздел «Черновик». Метаданных
  команда не спрашивает вовсе (ни `--title`, ни `--rank`), потому что грумминг в
  минуту, когда мысль только проявилась, стоит дороже самой мысли, и на этом она
  теряется. На доску черновик не попадает: строка там означает разобранную
  работу, и `batch`, `agentctl pick` и shipctl читают доску, рассчитывая на неё.
  ID выдаётся сразу, чтобы на черновик можно было сослаться («оформи DK-073»),
  поэтому его номер занят и для `id`, и для `add`. Оформление доводит `add --id
  <ID>`: черновик переезжает в `docs/tasks/<ID>.md` (`git mv` с фолбэком на
  rename, как в `close`), и ссылка в строке ведёт уже туда. Если черновик к
  моменту оформления не был закоммичен (например, черновик только что записан
  командой `draft` без `-m`), `git mv` отбивается, срабатывает rename, и в
  коммите с `-m` файл задачи едет как вновь добавленный, а исходный путь
  `drafts/<ID>.md` в pathspec не попадает: git его не знает, и pathspec по
  нему ронял бы коммит, оставляя строку и перенос файла в индексе. Отдельной
  команды на промоушен нет, иначе черновик можно потерять, забыв её позвать.
  Думающая часть
  (заголовок, тип, разбивка ранга, цена) остаётся за грумминговым диалогом, его
  ведёт скилл `board-groom` в devkit. Раз строки на доске нет, накопитель видно
  в других местах: `list` печатает после секций строку с ID и возрастом
  черновиков, `draft list` показывает их с первой строкой текста, `show <ID>`
  находит черновик так же, как находит архив. Находки в `lint` по возрасту нет:
  черновик, полежавший неделю, это нормальная жизнь накопителя, а не поломка
  инварианта. Возраст берётся из строки «записан ГГГГ-ММ-ДД», которую `draft`
  пишет под заголовком файла, а не из времени правки: то сбивают первая же
  правка файла, свежий клон, `shipctl start` со своим worktree и любое
  копирование дерева, после которых годовалый черновик печатается «сегодня». У
  черновика без такой строки (записан он был до её появления) остаётся фолбэк
  на время правки, а команда, которая первой в такой черновик пишет,
  проставляет ему строку из этого времени, пока оно ещё не сбито её же записью;
- разобранный черновик оставляет след: кроме оформления через `add --id` у него
  есть ещё три исхода, и все три держит утилита, потому что результат разбора
  обязан пережить сессию (дизайн в `docs/lld/DK-129-groom-process.md`,
  решение 4; второй довод того решения, отбой ручного пуша `docs/tasks/` в
  `pre-push`, после DK-119 отпал: пуш с диффом только по доске рубеж
  пропускает сам). `draft defer <ID>
  "причина"` откладывает черновик: в его файл дописывается раздел «Грумминг» со
  строкой «- ГГГГ-ММ-ДД, отложен: причина», повторный вызов причину заменяет, а
  `--clear` снимает раздел целиком. Пометка живёт в самом черновике, а не в
  отдельном индексе: она едет с ним в гит, видна человеку без утилиты, а при
  оформлении переезжает в `docs/tasks/<ID>.md` вместе с остальным текстом.
  Печатают её `draft list` («DK-116 (3 дня, отложен 2026-08-05): ...») и хвост
  `list` словом «отложен» без даты, иначе заход по накопителю открывал бы все
  файлы, чтобы узнать, кого уже разбирали. `draft attach <ID> <TASK-ID>`
  приписывает черновик к стоящей строке: текст уезжает разделом «Из черновика
  <ID> (записан ГГГГ-ММ-ДД)» в файл задачи (заголовки черновика опускаются на
  уровень ниже, чтобы не разрывать приписку, а решётка внутри блока кода
  остаётся текстом примера), а файл черновика удаляется, и ссылка «уехал в <TASK-ID>»
  остаётся сообщением коммита. Файл задачи заводится общим `ensureTaskFile`, как
  у `review add`: он уже есть, значит команда трогает два пути, файла не было,
  значит три, и третий это `docs/TASKS.md` со ссылкой, переставленной на новый
  файл (у строки задачи цели ссылка ведёт на файл цели, и переезд ссылки тут
  ожидаемый исход, а не регресс). `draft drop <ID> --reason "..."` удаляет
  протухший черновик через `git rm`; причина обязательна и печатается, потому
  что файла после команды нет и в гите она живёт только сообщением коммита;
- подкоманда `draft` узнаётся точным совпадением первого позиционного
  аргумента с одним из слов `list`, `defer`, `attach`, `drop`; всё остальное это
  текст черновика. Черновик из одного такого слова не записать, но ограничение
  давно действует для `list` и стоит того: без узнавания `draft defer DK-116
  "причина"` молча завёл бы черновик с текстом «defer», выбросив ID и причину;
- текстом черновика не принимается одно слово латиницей: так выглядит промах
  мимо подкоманды, а не идея. `draft show DK-162` и `draft add "текст идеи"`
  раньше падали в ветку записи и заводили черновик с текстом «show» и «add»,
  выбросив настоящий текст, оба раза с кодом возврата 0 и обычным сообщением на
  экране; находка вылезала через день на `draft list`, а исходный текст к тому
  времени доставался разве что из транскрипта сессии (DK-099). Теперь такая
  форма отбивается строкой про то, каких подкоманд у `draft` нет, и про то, что
  черновик целиком печатает `taskctl show <ID>`, а отдельной команды
  `draft show` не завели именно поэтому. Настоящая однословная идея пишется со
  stdin (`echo слово | taskctl draft`);
- `file` создаёт файл задачи со строкой-заголовком и чинит ссылку в строке,
  когда содержимое задачи переросло заголовок; LLD-задаче в бэклоге файл не
  нужен, её строка ссылается прямо на LLD, а отдельный файл с пересказом
  дизайна был бы прокладкой. Команда идемпотентна: у задачи, где уже есть и
  файл, и ссылка, она это подтверждает и выходит с нулём, а не падает (нужно
  при подготовке пачки, где `file` зовётся подряд по всем задачам, а файл есть
  не у всех). На холостом ходу коммитить нечего, поэтому с `-m`/`--push` она
  возвращается раньше `git commit` и нового коммита не создаёт;
- `move` в check держит два рубежа и без них строку не двигает. Первый это
  готовый сценарий проверки: в `docs/tasks/<ID>.md` должен стоять раздел
  «Сценарий проверки» (агентский вариант заголовка тоже годится, а заголовок
  внутри ограждённого блока не считается, это вложенный чужой вывод). Строка,
  чья ссылка ведёт не в файл задачи, а в другой документ, рубеж пропускает:
  LLD-задача описывает проверку в дизайне (RULES.board.md, «Трекинг задач»
  п. 6). Второй рубеж это слитый код: если в репозитории живёт ветка с ID
  задачи (опознание то же, что у `shipctl`: `dk-005`, `dk-005-slug`) и у неё
  есть коммиты впереди main, отказ называет ветку и отправляет в `shipctl
  merge <ID>`, потому что Check значит «код доехал до пользователя», а не
  «код написан». Вне git и в корп-контуре, где доска лежит отдельно от кода,
  ветки не найдётся и второй рубеж молчит. `--force` нет: оба нарушения это
  ровно то, ради чего рубеж стоит в утилите, а не в прозе правил;
- `move` в blocked требует `--reason` и дописывает причину к заголовку, при
  выходе из blocked причина из заголовка снимается. Blocked отдан
  обстоятельствам снаружи доски (ждём смежника, нет доступа, сломано не у нас)
  и только для начатых задач; ожидание своей же задачи это `dep add`, а строка
  из Backlog ждёт там же (RULES.board.md, «Трекинг задач» п. 4). Тем же
  правилом закрыты и обходные пути: `add --status blocked` отбивается (новую
  задачу блокировать нечему), а `dep add` не дописывает незакрытую зависимость
  задаче на блокере, как не дописывает её задаче в работе и на проверке;
- `fail` держит исход проверки задачи, вернувшейся из Check. Провал это
  сломанный прод: команда возвращает строку в In progress и дописывает к
  заголовку пометку «[провал: причина]», по которой shipctl держит очередь
  выката (RULES.board.md, «Ветки, ревью и деплой» п. 7), а уведомитель зовётся
  громко, как на блокере. Второй исход, приёмка с замечаниями, это обычный
  `move` в in-progress: он ничего к строке не приписывает и очередь не трогает.
  Пометка гасится сама, `--clear` нужен только для прода, починенного мимо
  shipctl: перевод в Check её снимает (этим `move` двигают статус `shipctl
  merge` и `ship`), а `revert` зовёт `fail --clear` сам. Причина живёт в
  заголовке, поэтому скобки в ней запрещены так же, как у блокировки, а `close`
  задачи с непогашенной пометкой отбивается: строка ушла бы в архив вместе со
  сломанным продом;
- `move` в check и в blocked зовёт `hooks/notify.py` громко: задача доехала
  до Check или встала на блокере, это поводы, ради которых человек подходит к
  машине (RULES.board.md, «Ветки, ревью и деплой» п. 8), а `shipctl merge` и
  `ship` двигают статус тем же `move`, так что уведомление уходит и оттуда.
  Уведомитель ищется тем же порядком, что у `harnessDir` в
  `tools/agentctl/harness.go`: `DEVKIT_HOME`, `hooks/` рядом с самой доской (когда
  доска и есть devkit), соседний клон devkit, `~/projects/devkit`. Не
  нашёлся или упал, `move` всё равно проходит (это не должно ронять доску),
  но сообщение команды получает строку «уведомление не отправлено: ...»,
  молчать про непосланный повод нельзя. Доска во временной директории
  (синтетический репозиторий из обкатки сценария) баннера не даёт: отправку
  пропускает сам `notify.py`, а приписка «уведомление пропущено: ...» в
  выводе `move` называет причину. Headless-прогоны (тесты, CI) глушат
  его `DEVKIT_NOTIFY_OFF=1`, разбор поводов и уровней в `hooks/README.md`,
  раздел «Уведомления о сессии». Повод уходит словом (`task_check`,
  `task_blocked`, у `fail` `task_fail`): по нему лента дашборда собирает
  события задач в свой фильтр, из одного заголовка тип события не вытащить;
- `set` правит ячейки существующей строки (заголовок, тип, ранг, цену, ссылку);
  P пересчитывается из новой разбивки, строка в Backlog встаёт на место по
  новому рангу, в остальных секциях остаётся где была; у заблокированной
  строки пометка «[блок: ...]» переживает смену заголовка;
- `close` дописывает строку в архив (без колонок R и «Цена», с датой закрытия),
  переносит файл задачи в `tasks/archive/<год>/` (`git mv` с фолбэком на
  обычный rename) и ставит ссылку уже на новое место; при переносе переписывает
  относительные ссылки в самом файле задачи (они разрешались от `docs/tasks/`,
  теперь разрешаются из `docs/tasks/archive/<год>/`) и в других файлах
  репозитория, где на неё ссылаются; живой `TASKS.md` тогда не пухнет, его
  размер привязан к объёму открытой работы, архив append-only и растёт свободно,
  а `ls docs/tasks/` показывает открытую работу; хеши из `--commit` добавляются
  в ячейку ссылки; заодно снимает «[после `<ID>`]» со всех строк доски,
  ссылавшихся на закрытую задачу, и в архивную строку маркер не переносит;
- зависимость между задачами («A делается после B») живёт суффиксом
  заголовка `[после B]` (несколько ID через запятую) перед пометкой «[блок:
  ...]»; хранится только это направление, обратное («кого держит B») taskctl
  считает по доске. `dep add <ID> <DEP-ID>` ставит зависимость (проверяет, что
  обе задачи существуют и добавление не замкнёт цикл), `dep rm` снимает,
  `dep list [ID]` печатает обе стороны (без ID по всей доске); `show` тоже
  печатает «после» и «держит». И `move <ID> in-progress`, и `dep add` на
  задачу, уже стоящую в In progress или Check, с незакрытой (не найденной в
  архиве) зависимостью падают с ошибкой, где назван её ID; `--force` нет;
- `lint` проверяет разбор всех строк, бакеты P, сортировку, дубли ID по доске
  и архиву, формат дат, что локальные markdown-ссылки ведут на существующие
  файлы, что у задачи в работе есть файл `docs/tasks/<ID>.md`, а у задачи в
  Check хотя бы ссылка на сценарий проверки (RULES.board.md, «Трекинг задач»
  п. 3 и 6), что у задачи в Check не живёт неслитой ветки с её ID (обратная
  сторона рубежа `move`: так выглядит перевод в обход ворот правкой доски
  руками и брошенное на полпути слияние), что в `docs/tasks/` не лежит файла, которому не соответствует
  строка ни на доске, ни в архиве (так выглядит правка ID задним числом: за
  прежним именем остаются замечания ревью и запись слитых коммитов, по
  которой shipctl держит очередь выката), а также маркер зависимости: ID из
  «[после ...]» существует (на доске или в архиве), не ссылается сам на себя,
  без дублей внутри маркера, без циклов, и что задача в работе или на проверке
  не держит незакрытую зависимость; отдельной находкой идёт пометка провала
  проверки в Backlog или в Check (задачу отложили вместе со сломанным продом,
  и очередь выката стоит непонятно из-за чего);
- `batch` отбирает кандидатов в поезд выката по тем критериям правила
  (RULES.board.md, «Ветки, ревью и деплой» п. 9), которые читаются с доски.
  Обход идёт по всему Backlog сверху вниз, в порядке доски: пачка приоритет не
  отменяет и берёт верхние подходящие строки, а не самые дешёвые. Проверки идут
  фиксированным порядком, и задача попадает в отказ по первой непрошедшей, то
  есть ровно в одну группу: секция Backlog (остальные секции в отбор не входят
  вовсе и в отказах не печатаются), тип не LLD (у дизайна нет кода и выката он
  не требует), цена S или M (прочерк не годится: не оценено значит, что
  грумминг не доведён до конца), неопределённость не выше 1 (третье слагаемое
  ранга; 2-3 это открытые детали, где диспетчер нужен в цикле), все ID из
  «[после ...]» найдены в архиве, ссылка не совпадает со ссылкой уже отобранной
  задачи (одинаковая непустая ссылка это признак серии, а серия связана по
  смыслу; прочерк ссылкой не считается), лимит пачки не исчерпан (`--limit`, по
  умолчанию 5, верхняя граница правила; число берётся из `agentctl budget`).
  Первая строка вывода машинная, дальше человеческие; отказы сгруппированы по
  причине, пустых групп не печатается:

  ```text
  $ taskctl batch --limit 5
  batch: DK-036, DK-018, DK-021, DK-024, DK-027
  взято: DK-036 (task, M, неопр. 1), DK-018 (task, S, неопр. 1), DK-021 (task, S, неопр. 1), DK-024 (bug, S, неопр. 1), DK-027 (bug, S, неопр. 0)
  ждут незакрытых зависимостей: DK-037, DK-038, DK-039, DK-041, DK-042
  цена не S и не M: DK-040 (L)
  неопределённость выше 1: DK-043 (2), DK-044 (2), DK-045 (2), DK-046 (2), DK-032 (2), DK-049 (3)
  лимит пачки 5 исчерпан: DK-028, DK-029, DK-031, DK-035, DK-025
  одно приложение и пересечение по файлам доска не видит: сверить кандидатов по файлам задач, вторая страховка это предупреждение shipctl merge --train
  ```

  Маркер «[после ...]» есть и у DK-040, и у DK-043..DK-046, но в группе
  зависимостей их нет: цена и неопределённость проверяются раньше. Пустая пачка
  это не пустой вывод, остаются строка `batch: -` и все группы отказов, а кодом
  возврата пустой отбор не ошибка. Два критерия правила из строки не выводятся:
  одно приложение в монорепозитории на доске не записано вовсе, а пересечение по
  файлам у задач без веток не посчитать ничем, файлы появятся только после
  работы исполнителя. Поэтому отбор называет вслух, чего он не проверял, и
  просит сверить кандидатов по файлам задач; вторая страховка стоит там, где
  данные наконец есть, и это предупреждение `shipctl merge --train` про
  затронутые файлы;
- `review` держит формат раздела «Ревью» файла задачи: `add` дописывает
  строку-замечание (файл задачи и ссылка в строке заводятся сами), `resolve`
  фиксирует исход («исправлено» либо «отклонено» с обязательной причиной),
  а `stats` считает по живым задачам и архиву, что ревью реально ловит;
  чужие секции файла не трогаются.

Доску правит только диспетчер и только в основном чекауте (RULES.board.md,
«Доска в руках диспетчера»): изменяющие её команды (`add`, `move`, `set`,
`close`, `sort`, `dep add`, `dep rm`, `file`, `init`, `draft`) из линкованного worktree
отказывают, файла не тронув, и подсказывают запустить команду в основном
чекауте. Линкованное дерево узнаётся расхождением `git rev-parse --git-dir` и
`--git-common-dir`; считается это по корню, который taskctl уже нашёл (по
`-C`, а не по текущей директории), поэтому `taskctl -C <основной чекаут> move
...` из дерева задачи (так делает `shipctl merge`) проходит без помех. Вне
git-репозитория и при недоступном git рубеж молчит. `review add` и `review
resolve` остаются разрешены везде: они меняют только файл задачи. Если `review
add` из worktree заводит задаче файл впервые, ссылку в строке доски она не
чинит, а печатает, что её нужно поправить в основном чекауте. `draft` строку не
трогает, но под рубежом стоит вместе с изменяющими: номер он берёт из той же
сквозной нумерации, и черновик, заведённый на фичеветке, основному чекауту не
виден, так что этот же номер уйдёт следующей задаче. `draft defer`, `draft
attach` и `draft drop` стоят там же и по той же причине: накопитель общий и
живёт в основном чекауте, а пометка, поставленная на фичеветке, основному
чекауту не видна до слияния.

Команда перехода последней строкой печатает следующий шаг конвейера: `move
<ID> in-progress` называет дерево задачи, тесты, ревью и слияние и говорит,
что сдача это Check, а не написанный код; `move <ID> check` зовёт прогнать
сценарий проверки из файла задачи и называет обе его ветки (агентский агент
закрывает сам, пользовательский ждёт слова пользователя); `move <ID> blocked`
напоминает про снятие блокера, `move <ID> backlog` про правку метаданных, а
`close` говорит, что очередь выката освободилась. Знание «что дальше» лежит в
выводе утилиты, а не в прозе скилла: подсказку читает любая модель и ровно в
ту минуту, когда решение принимается (DK-180, DK-191). Подсказка взятия в
работу договаривает развилку «кто нажимает кнопку»: значение ключа
`autonomous` из `.devkit/deploy.local` читается живьём и называется вместе с
файлом, потому что на этой развилке агент сходит с конвейера ровно на готовой
задаче. Ключ этот единственное, что taskctl берёт из обвязки выката, остальное
там читает shipctl.

Правило надёжности: нетронутые строки сохраняются байт в байт, файл вне таблиц
не переформатируется. Строка, которую не удалось разобрать, валит операцию с
ошибкой вида `файл:строка` до какой-либо записи на диск.

Справка доступна и по `-h`/`--help` у любой подкоманды. Каждый запуск оставляет
строку в журнале `.devkit/log` проекта (время, команда, код выхода), если
директория `.devkit` заведена: по журналу видно, что реально гоняется и как
часто падает; файл гитигнорнут (об этом заботится devkitctl).
