# trackctl: разговор с трекером задач

Утилита корп-контура: всё, что ходит в трекер компании (Jira и её родня),
собрано здесь. taskctl остаётся чистой механикой доски `docs/TASKS.md` и в сеть
не ходит ни одной командой, иначе команды доски стали бы медленными и
недетерминированными. Дизайн контура разобран в
[LLD DK-074](../docs/lld/DK-074-corp-contour.md).

Утилита общая для всех корп-проектов, живёт в devkit. Один раз собрать бинарь в
PATH:

```
cd ~/projects/devkit/trackctl && go build -o ~/go/bin/trackctl .
```

и дальше звать `trackctl <команда>` из любого места внутри корп-клона: рабочий
корень находится сам, тем же порядком, что у соседей (сперва редирект
`devkit.local` из конфига git, потом подъём до `docs/TASKS.md`), стартовую
директорию задаёт флаг `-C <dir>`.

## Команды

```
status              привязка проекта, контур, адаптер с перечнем отсутствующих
                    необязательных операций, свежесть последнего sync
issue <KEY>         тикет глазами адаптера: статус и секция доски, тип,
                    заголовок, оценка
take <KEY>          взять тикет в работу: переход в целевой статус секции
                    In progress и assign на пользователя контура
```

Ключ пишется целиком (`ABC-12`) либо одним номером (`12`), префикс тогда
берётся из привязки. Каждая команда оставляет строку в журнале `.devkit/log`,
как соседние утилиты.

`take` это не только переход: тикет In progress без исполнителя в чужом
процессе заметен сразу, поэтому вместе с переходом зовётся `assign` на
пользователя контура. Тикет, который уже в работе, второй раз не переводится,
но исполнителя получает.

## Адаптер

Трекер меняется от компании к компании, поэтому операции прибиты контрактом, а
реализация выбирается по имени из таблицы адаптеров, как разборщики протоколов
в `hooks/hookio.py`. Обязательная часть контракта это интерфейс `adapter`,
необязательные операции вынесены отдельными интерфейсами.

| Операция | Что делает | Обязательна |
|---|---|---|
| `fetch` | статус, тип, заголовок, оценка тикета | да |
| `transition` | перевод тикета в целевой статус с полями | да |
| `assign` | назначить исполнителя тикета | да |
| `estimate` | проставить оценку | да |
| `worklog` | запись времени за дату | да |
| `rank` | записать числовое поле приоритета | нет |
| `comment` | комментарий в тикет | нет |

Необязательная операция, которой у адаптера нет, это честное отсутствие оси:
`trackctl status` называет её вслух вместе с тем, чего из-за неё не
происходит, а команды шагов по ней не делают. Наличие операции само по себе
поводом ходить в неё тоже не служит.

Новый трекер добавляется строкой таблицы `adapters` и своим кодом, контракт при
этом не меняется. Проверяется адаптер по снятым живьём образцам ответов API в
`trackctl/testdata/<адаптер>/`, в сеть тесты не ходят. Живого адаптера в сборке
пока нет, есть контракт, таблица и подложный адаптер тестов, который
записывает вызовы.

## Конфиг: контур и привязка

Уровня два, и оба лежат вне корп-репозитория: контур это свойство компании
(один на все её репозитории, статусы общие), привязка это свойство проекта
(ключ и ветки у каждого свои).

Машинный контур `~/.devkit/tracker/<имя>.local`, формат тот же, что у профилей
харнесов (подмножество TOML):

```toml
adapter = "jira"
base_url = "https://tracker.example"
token_env = "JIRA_TOKEN"
user = "имя в трекере"
cost_s = "4h"
cost_m = "1d"
cost_l = "3d"
rank_field = "customfield_100"

[status]
backlog = ["Open", "Backlog"]
in_progress = ["In Progress"]
check = ["Review", "Testing"]
blocked = ["Blocked", "On Hold"]
done = ["Done", "Closed", "Rejected"]

[fields_in_progress]
assignee = "{user}"
```

Токен в файле не лежит: `token_env` называет переменную окружения, `token_file`
путь к файлу, откуда его читать, тем же порядком, что доступы в
`~/.claude/access.local.md`. Коэффициенты `cost_*` переводят цену задачи в
оценку трекера, `rank_field` называет числовое поле приоритета; и то, и другое
идёт в дело командами границ (задача DK-084).

Проектная привязка `.devkit/tracker.local` в боковой директории, формат плоский
`key = value`, как у `deploy.local`:

```
contour = corp
key = ABC
branch = "{key}-{slug}"
repo = ../corp-repo
```

Плоским формат выбран не только по аналогии: привязку читает и shipctl (шаблон
ветки), а парсера TOML у него нет. Ключ `repo` называет корп-клон, по нему
подсказка утилит находит потерянную обвязку клона.

## Маппинг статусов

Наборы статусов у компаний разные, приводятся они к секциям доски таблицей
`[status]`, а не хардкодом. Таблица работает в обе стороны.

Чтение: статус тикета ищется по спискам секций (регистр не в счёт), найденная
секция и есть секция доски. Маппинг многие-к-одному, чужая детализация (три
вида ревью, две очереди тестирования) складывается в Check, новых секций доски
она не порождает. Статус, которого нет ни в одном списке, это не ошибка
разбора, а находка: команда говорит о ней вслух, а ни тикет, ни строка доски не
двигаются. Лечится находка строчкой в таблице.

Запись: целевой статус секции это первый элемент её списка, остальные синонимы
для чтения.

Пятая секция `done` держит конечные статусы, своей секции доски у неё нет:
закрытые строки живут в архиве. Тикет в `done` даёт подсказку про
`taskctl close`, а не находку, иначе каждый закрытый тикет шумел бы «статус не
расписан». Записи в `done` автоматика не делает никогда: тикет закрывает чужой
процесс, а там, где закрытие ждут от разработчика, оно остаётся ручным шагом,
как пуш и MR.

Переход делается одним шагом в целевой статус. Прямого перехода воркфлоу не
даёт, значит адаптер отказывает и перечисляет доступные, а не ищет путь через
промежуточные статусы: на чужих переходах висят обязательные поля и side-эффекты
(уведомления, автоназначение), и прокликивать их вслепую автоматика не имеет
права. Лекарства два, по сорту преграды. Недостающий промежуточный статус
вписывается в таблицу синонимом, и целевым становится он. Обязательное поле
перехода (assignee, resolution) синонимом не лечится, для него есть плоские
секции `[fields_<секция доски>]`: ключ это поле, как его знает адаптер,
значение строка, `{user}` разворачивается в пользователя контура. Набор секции
уезжает адаптеру целиком, чего в секции нет, то не передаётся, и отказ трекера
остаётся честным отказом с перечнем недостающего.
